# Design a Distributed Lock Service

Design a service that grants time-bounded exclusive ownership of named resources and prevents stale owners from corrupting protected state.

## Scope decisions to make

- Exclusive leases first; defer read/write locks and arbitrary conditions.
- Strongly consistent control plane in one region; discuss cross-region clients as an extension.
- Define whether clients wait, poll, or fail fast on contention.

## Non-functionals to pin down

- Acquire/renew/release QPS, contention distribution, and p99 latency.
- Lease duration, clock assumptions, availability, and correctness priority.
- Maximum acceptable false unavailability versus double ownership.

## The estimation that decides something

Estimate renew traffic as `active_leases / renew_interval`. Use the hottest resource's contention—not average lock QPS—to evaluate queueing and shard ownership.

## Skeleton diagram

```text
Client -> lock API -> consensus group/shard -> lease record + monotonic fencing token
                                        |
Protected storage rejects operations carrying an older token
```

## The hard part

A lease can expire while the old owner is paused and later resumes. Mutual exclusion at the lock service is insufficient; the protected resource must reject stale fencing tokens.

## Tradeoffs to defend

- Lease-based locking versus transaction/conditional-write primitives.
- Fair queues versus throughput and convoying.
- Fixed lease duration versus renewal traffic and false expiry.
- CP correctness versus availability during partition.

## Top failure mode

A GC pause or network partition creates a stale owner that still believes it holds the lock. Define monotonic tokens, downstream enforcement, renewal loss, and client cancellation.

## Pushback ladder

1. Why does a lease alone not prevent stale writes?
2. One resource has thousands of contenders. How do you prevent a retry storm?
3. The protected database cannot validate fencing tokens. Is this lock still safe?
