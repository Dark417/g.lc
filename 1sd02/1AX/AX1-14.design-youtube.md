# Volume 1, Chapter 14: Design Youtube

Design a video platform that accepts large uploads, processes multiple renditions, and delivers playback globally with high availability and controlled egress cost.

## Scope decisions to make

- Upload, transcode, metadata, and video-on-demand playback; defer live streaming and recommendations.
- Originals are durable; derived renditions are reproducible.
- Define copyright/moderation only as an asynchronous extension.

## Non-functionals to pin down

- Uploads/day, average and tail video size, watch QPS, startup latency, rebuffer rate, durability, and processing SLA.
- Regional traffic distribution and CDN hit-rate target.

## The estimation that decides something

Estimate retained original/rendition storage and playback egress. Egress and transcode amplification should determine CDN, encoding ladder, and storage-tier choices.

## Skeleton diagram

```text
Uploader -> resumable upload -> object store -> job queue -> transcode workers
Viewer -> metadata API -> manifest -> CDN -> origin/object store
```

## The hard part

Make upload and transcoding resumable, idempotent, and observable. Define chunk identity, job state, retries, poison inputs, rendition publication, and partial failure recovery.

## Tradeoffs to defend

- Direct-to-object-store upload versus proxying through application servers.
- Eager full encoding ladder versus demand-driven renditions.
- Segment size versus startup latency, request overhead, and cache efficiency.
- Strong metadata consistency versus playback availability.

## Top failure mode

A viral or newly published video misses cache across many regions and overloads origin. Cover origin shield, request coalescing, pre-warm, admission control, and degraded bitrate.

## Pushback ladder

1. How are duplicate transcode jobs prevented from publishing conflicting outputs?
2. A celebrity upload creates a global cache-miss storm. What protects origin?
3. The prompt changes to live streaming. Which assumptions and components break?
