# Volume 1, Chapter 15: Design Google Drive

Design a file storage and synchronization service that supports resumable upload, folders/sharing, multi-device sync, version history, and conflict handling.

## Scope decisions to make

- File/folder metadata, upload/download, sharing, and device sync; defer collaborative document editing.
- Separate strongly consistent metadata from immutable file chunks.
- Define conflict semantics for offline concurrent edits.

## Non-functionals to pin down

- Active users/devices, file-size distribution, sync latency, durability, availability, version retention, and bandwidth limits.
- Security boundary for sharing and revocation.

## The estimation that decides something

Estimate changed bytes versus whole-file bytes and concurrent sync connections. This should decide chunking/delta sync and push-notification strategy.

## Skeleton diagram

```text
Client -> metadata/sync API -> metadata DB + change log -> notification channel
       `-> resumable chunk API -> object/chunk store -> download/CDN
```

## The hard part

Define a sync cursor/change log, idempotent chunk upload, atomic metadata commit, offline conflict detection, versioning, and permission revocation across cached clients.

## Tradeoffs to defend

- Content-defined chunks versus fixed-size chunks.
- Server-authoritative last-writer-wins versus conflict copies/version vectors.
- Block-level deduplication versus privacy and metadata overhead.
- Push invalidation versus polling and reconnect storms.

## Top failure mode

Upload succeeds but metadata commit or notification fails, leaving orphaned chunks or stale clients. Cover staged commits, garbage collection, replayable change logs, and reconciliation.

## Pushback ladder

1. How does a client know it has applied every change exactly once enough?
2. Millions of devices reconnect after an outage. How is the sync service protected?
3. Sharing revocation must take effect immediately across regions. What changes?
