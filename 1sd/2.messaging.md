## 0. One-Minute Version

- Messaging comes in two families
  - **C↔S**: user device ↔ backend
  - **S↔S**: backend service ↔ backend service
  - Two edge cases: C↔C (WebRTC, still needs a server for signaling) and S→external (webhooks)
- For C↔S, ask first: **who speaks first?**
  - Client asks → request/response
  - Server must push → online: SSE / WebSocket; offline: APNs / FCM
- For S↔S, ask first: **does the caller need to wait for the result?**
  - Yes → REST / gRPC
  - No → queue (one consumer) / pub-sub (many consumers) / log (many consumers + replay)
- Every message has two layers
  - **Envelope**: fixed by the protocol (HTTP headers, SSE fields, WebSocket frames, Kafka records)
  - **Payload schema**: defined by you (JSON Schema, protobuf, Avro, GraphQL SDL)
- What interviewers actually probe is not the protocol list, it's the **operations**
  - How many connections per box, how you deploy without a reconnect storm, who assigns sequence numbers, what happens if you crash between the DB write and the publish
- Last time's gap
  - Live comments = server push, one-way, reads far exceed writes → **SSE**, not polling
- 🗣 "First I ask who initiates and whether the caller needs to wait; that picks the family. Then fan-out size and delivery guarantees pick the implementation, and I size the connection tier with numbers."

## 1. The Map: Who Talks To Whom

```
                 ┌──────── C→S  request/response (REST / GraphQL / gRPC)
                 ├──────── S→C  push online  (SSE / WebSocket / long poll)
   Client ───────┼──────── S→C  push offline (APNs / FCM / SMS / email)
                 ├──────── C↔S  bidirectional (WebSocket / gRPC stream / MQTT)
                 ├──────── C↔C  peer-to-peer (WebRTC, signaling via server)
                 └──────── C→S  big files (presigned URL → object storage)

   Service ──────┬──────── S→S  sync   (REST / gRPC)
                 ├──────── S→S  async  1:1   (queue)
                 ├──────── S→S  async  1:N   (pub/sub)
                 ├──────── S→S  async  replayable (log / stream)
                 └──────── S→External (webhook)
```

| Direction | Initiator | Typical problem | Method family |
|---|---|---|---|
| C→S | Client | Read/write data | REST, GraphQL, gRPC |
| S→C online | Server | Live updates | SSE, WebSocket, long poll |
| S→C offline | Server | Notify when app is closed | APNs, FCM, SMS, email |
| C↔S two-way | Both | Chat, games, collaboration | WebSocket, gRPC stream, MQTT |
| C↔C | Both | Audio/video, low-latency transfer | WebRTC |
| S→S sync | Caller | Need the answer now | REST, gRPC |
| S→S async | Producer | Decouple, absorb spikes, many downstreams | Queue, Pub/Sub, Log |
| S→external | Our service | Notify a third party | Webhook |

<a id="s2"></a>
## 2. The 10 Factors That Decide

- Saying these out loud is the "quantitative + factors" part interviewers score
  1. **Direction**: one-way or two-way
  2. **Initiator**: client pulls or server pushes
  3. **Latency**: seconds, hundreds of ms, tens of ms
  4. **Frequency**: once a minute or tens per second
  5. **Payload size**: hundreds of bytes or GBs
  6. **Presence**: user online, backgrounded, offline
  7. **Fan-out**: 1:1 or 1:100k
  8. **Delivery guarantee**: can lose, at-least-once, no duplicates
  9. **Ordering**: needed? within what scope?
  10. **Client type**: browser, mobile, IoT, server
- Tip: factors 2, 7 and 8 narrow the choice fastest

## 3. Schema Essentials (Applies To Every Method)

<a id="s3-1"></a>
### 3.1 Two Layers: Envelope vs Payload

- Plain idea: every message is a letter inside an envelope
  - Envelope = the protocol's format, you can't change it (HTTP headers, SSE `data:` lines, Kafka key/value/headers)
  - Letter = your business structure (`{"comment_id": ..., "text": ...}`)
- In an interview, say both
  - Which protocol (envelope)
  - The payload's fields and types (letter), and how it evolves without breaking old clients

<a id="s3-2"></a>
### 3.2 Where Schemas Are Defined

| Method | Schema language (IDL) | Wire format | Tooling |
|---|---|---|---|
| REST | OpenAPI 3.x + JSON Schema | JSON (also protobuf, XML) | openapi-generator, request validators |
| GraphQL | GraphQL SDL | JSON | Codegen; server validates against SDL |
| gRPC | Protocol Buffers (`.proto`) | Protobuf binary | protoc / buf |
| SSE / WebSocket / MQTT | AsyncAPI + JSON Schema or protobuf | Text JSON or binary | Validate yourself |
| Kafka / queues | Avro / Protobuf / JSON Schema + Schema Registry | Binary or JSON | Registry checks compatibility on write |
| Event envelope | CloudEvents | JSON or HTTP-header binding | SDKs |
| APNs / FCM | Vendor-defined JSON | JSON | Vendor SDKs |
| Webhooks | OpenAPI `webhooks` section / Standard Webhooks spec | JSON + signature headers | Verify signature yourself |

- OpenAPI describes request-response; AsyncAPI describes messages and events
- 🗣 "Contract-first: OpenAPI for request-response, protobuf internally, Avro with a schema registry on Kafka."

<a id="s3-3"></a>
### 3.3 Design Principles

- **Contract-first**: write the schema before the code; schemas live in git and get reviewed
- **Envelope + payload**: every async message shares one envelope
  - `id`: globally unique, the dedup key
  - `type`: event name, e.g. `comment.created`
  - `version` or `schema_id`
  - `occurred_at`: when it happened (UTC, ISO-8601 or epoch ms)
  - `source`: which service produced it
  - `trace_id`: for distributed tracing
  - `data`: the business content
- **IDs as strings** (e.g. Snowflake rendered as a string): JavaScript loses precision on 64-bit integers
- **Naming**: one convention per system (`snake_case` or `camelCase`); events in past tense (`order.placed`), commands imperative (`ReserveInventory`)
- **Time**: always UTC; put units in field names (`timeout_ms`, `size_bytes`)
- **Size**: keep messages small (KB range); put large content in object storage and send a pointer (claim-check pattern)
- **Optional by default**: new fields are optional with sensible defaults
- **Tolerant reader**: consumers ignore unknown fields instead of failing
- **Validate at the edge**: gateways and producers validate; internal hops trust

<a id="s3-4"></a>
### 3.4 Compatibility And Versioning

- Plain idea: producers and consumers never upgrade at the same moment, so every change must be readable by both old and new code
- Two directions
  - **Backward compatible**: new code reads old data
  - **Forward compatible**: old code reads new data

| Change | Safe? | Note |
|---|---|---|
| Add an optional field with a default | Safe | Old consumers ignore it |
| Remove an optional field | Mostly safe | In protobuf, mark the number `reserved` |
| Rename a field | Breaks JSON | Wire-safe in protobuf binary, but breaks JSON mapping and generated code |
| Change a field's type | Breaks | int → string crashes old code |
| Make optional required | Breaks | Old producers don't send it |
| Reuse a protobuf field number | Breaks | Old data gets misparsed |
| Add an enum value | Risky | Old clients must handle "unknown" |

- Versioning strategy
  - REST: URL version `/v1/...` (most common) or header; bump major only on breaking changes
  - GraphQL: no versions; mark old fields `@deprecated`
  - gRPC: version in the package (`comments.v1`)
  - Kafka: Schema Registry compatibility mode (BACKWARD / FORWARD / FULL); incompatible writes are rejected
  - Breaking change: new topic / endpoint, dual-write for a while, then retire the old one
- 🗣 "Additive changes only; breaking changes get a new version and a dual-run period."

<a id="s4"></a>
## 4. Client ↔ Server

<a id="s4-1"></a>
### 4.1 Request / Response ★★★

- Plain idea: client asks, server answers, one question one answer
- When: almost all CRUD; any "user clicked a button" action

| Style | Good | Cost | Choose when |
|---|---|---|---|
| REST (HTTP + JSON) | Simple, cacheable, universal | Many round trips, over-fetching | Default |
| GraphQL | One request gets exactly the fields needed | HTTP caching is hard; heavy queries hurt the backend | Many clients, page fields change often |
| gRPC (HTTP/2 + protobuf) | Binary, strongly typed, fast | Browsers need a gRPC-Web proxy | Mobile, internal APIs |

- Tier 3: Spring MVC / WebFlux, Apollo (GraphQL), grpc-java
- 🗣 "Writes carry an idempotency key, so client retries are safe."

<a id="s4-1-1"></a>
#### 4.1.1 REST: Schema, Principles, Payload ★★★

- Schema: OpenAPI 3.x (YAML), bodies in JSON Schema

```yaml
paths:
  /v1/lives/{liveId}/comments:
    post:
      parameters:
        - { name: liveId, in: path, required: true, schema: { type: string } }
        - { name: Idempotency-Key, in: header, required: true, schema: { type: string } }
      requestBody:
        content:
          application/json:
            schema:
              type: object
              required: [text]
              properties:
                text: { type: string, maxLength: 500 }
      responses:
        "202": { description: Accepted }
        "429": { description: Rate limited }
```

- Principles
  - URLs are nouns (resources); actions come from the HTTP method
  - Method semantics
    - GET: read-only, safe + idempotent
    - PUT: full replace, idempotent
    - PATCH: partial update, usually not idempotent
    - DELETE: idempotent
    - POST: create or action, not idempotent → add `Idempotency-Key`
  - Status codes: 200 / 201 / 202 / 204, 400 / 401 / 403 / 404 / 409 / 412 / 429, 500 / 503
  - **201 vs 202**: return 201 + `Location` only when the resource is readable now; if the write is async (e.g. via Kafka), return 202 and let the client echo its own item optimistically
  - One error format: RFC 9457 `application/problem+json`
  - Cursor pagination (`next_cursor`), not offset
  - Concurrency control: `ETag` + `If-Match`, conflict → 412
  - Long-running work: `202 Accepted` + `Location: /v1/operations/{id}`
- Payload

```http
POST /v1/lives/L42/comments HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Idempotency-Key: 7f3c9a1e-2b...

{"text": "great shot!"}
```

```http
HTTP/1.1 202 Accepted
Content-Type: application/json

{"comment_id": "C9001", "status": "accepted", "created_at": "2026-11-08T20:31:05Z"}
```

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 2
Content-Type: application/problem+json

{"type": "https://api.example.com/errors/rate-limited",
 "title": "Too many comments", "status": 429, "detail": "Max 5 comments per 10s"}
```

- Variations
  - Styles: resource REST (above); RPC-over-HTTP (`POST /v1/comments:moderate`); hypermedia (HAL, JSON:API) ★; OData ★
  - Body formats: JSON (default), protobuf, XML (legacy, S3 multipart), form-urlencoded (forms, OAuth), multipart/form-data (small uploads)
  - Transport: HTTP/1.1 (one request at a time per connection), HTTP/2 (multiplexing, header compression), HTTP/3 over QUIC (better on lossy mobile networks)
  - Patterns: conditional GET (`If-None-Match` → 304); batch endpoint; 202 + operation resource (OCI work requests); streaming responses (chunked, NDJSON); Range requests

<a id="s4-1-2"></a>
#### 4.1.2 GraphQL: Schema, Principles, Payload ★★

- Schema: SDL

```graphql
type Comment { id: ID!  text: String!  author: User!  createdAt: String! }
type Query { comments(liveId: ID!, first: Int = 20, after: String): CommentConnection! }
type Mutation { postComment(liveId: ID!, text: String!): Comment! }
type Subscription { commentAdded(liveId: ID!): Comment! }
```

- Principles
  - Fields are nullable by default; add `!` only when guaranteed
  - Relay connections for pagination (`edges`, `pageInfo.endCursor`)
  - No versions; `@deprecated(reason: "...")`
  - Limit query depth and complexity
  - Persisted queries in production
  - DataLoader to avoid N+1 fetches
- Payload

```http
POST /graphql HTTP/1.1
Content-Type: application/json

{"query": "query($id: ID!){ comments(liveId:$id, first:2){ edges{ node{ id text } } } }",
 "variables": {"id": "L42"}}
```

```json
{"data": {"comments": {"edges": [{"node": {"id": "C1", "text": "hi"}}]}}}
```

- Note: errors usually still return HTTP 200, listed in an `errors` array (absent when there are none)
- Variations: query / mutation / subscription (over WebSocket `graphql-ws` or SSE); persisted queries via GET (CDN-cacheable); federation ★; batching ★

<a id="s4-1-3"></a>
#### 4.1.3 gRPC: Schema, Principles, Payload ★★

- Schema: `.proto`

```protobuf
syntax = "proto3";
package comments.v1;

service CommentService {
  rpc PostComment(PostCommentRequest) returns (Comment);
  rpc StreamComments(StreamRequest) returns (stream Comment);
}

message PostCommentRequest {
  string live_id = 1;
  string text = 2;
  string idempotency_key = 3;
}
message Comment {
  string id = 1;
  string live_id = 2;
  string text = 3;
  int64 created_at_ms = 4;
  int64 seq = 5;
  reserved 6;            // removed field numbers are never reused
}
```

- Principles
  - A field number never changes meaning; mark removed numbers `reserved`
  - Add fields, never change types
  - Version in the package (`comments.v1`)
  - Set a **deadline** on every call and propagate it downstream
  - Use standard status codes (`NOT_FOUND`, `ALREADY_EXISTS`, `RESOURCE_EXHAUSTED`, `UNAVAILABLE`)
  - CI gate with buf breaking-change checks
- Payload (over HTTP/2)

```
:method: POST
:path: /comments.v1.CommentService/PostComment
content-type: application/grpc
grpc-timeout: 500m
authorization: Bearer ...

DATA frame: [1 byte compressed flag][4 bytes length][protobuf bytes]

trailers:
grpc-status: 0
```

- Variations: unary, server streaming, client streaming, bidirectional streaming; gRPC-Web (browser, via Envoy); Connect protocol (same proto over HTTP/1.1 + JSON); JSON transcoding (grpc-gateway)

<a id="s4-2"></a>
### 4.2 Short Polling ★★

- Plain idea: the client asks "anything new?" every N seconds
- How
  1. Client `GET /updates?since=<cursor>`
  2. Server answers immediately, data or empty
  3. Wait N seconds, ask again
- Good: simplest, stateless, works everywhere
- Cost
  - Latency = polling interval
  - Most requests are empty
  - Example: 1M users every 5 s = 200k QPS, nearly all empty
- When: low frequency, tens of seconds of delay OK (order status, job progress, work-request status)
- 🗣 "Polling is fine for job status every 10 seconds; it's wrong for chat."

<a id="s4-2-1"></a>
#### 4.2.1 Schema, Principles, Payload

- Schema: a REST GET (OpenAPI); the key field is the **cursor**
- Principles
  - Opaque server-encoded cursor, not a client timestamp (client clocks drift)
  - Support `ETag` / `If-None-Match` → 304 when unchanged
  - Server tells the client when to come back with `Retry-After`
- Payload

```http
GET /v1/operations/op-123 HTTP/1.1
If-None-Match: "v7"
```

```http
HTTP/1.1 200 OK
ETag: "v8"
Retry-After: 10
Content-Type: application/json

{"id": "op-123", "status": "IN_PROGRESS", "percent_complete": 60,
 "updated_at": "2026-11-08T20:31:05Z"}
```

- Variations: fixed interval; adaptive interval (back off when unchanged); conditional GET (304); HEAD for a version check; fast in foreground, slow in background (mobile battery)

<a id="s4-3"></a>
### 4.3 Long Polling ★★

- Plain idea: the client asks, and the server **holds the request** until data arrives or a timeout hits
- How
  1. Client sends a request with a cursor and a max wait
  2. Server holds it up to 30–60 s
  3. Data → respond; timeout → respond empty
  4. Client immediately sends the next one
- Good: near real-time, plain HTTP, firewall-friendly
- Cost
  - A new request after every message
  - Server holds many open requests (needs a non-blocking framework)
  - Heavy when messages are frequent
- When: **fallback** when WebSocket / SSE is blocked; legacy systems
- Tier 3: Spring `DeferredResult`, WebFlux; Socket.IO polling transport
- 🗣 "Long polling is my fallback when WebSocket is blocked by a proxy."

<a id="s4-3-1"></a>
#### 4.3.1 Schema, Principles, Payload

- Schema: REST GET + `cursor` + `wait`; response carries a batch and the next cursor
- Principles
  - Hold time must be shorter than LB / proxy idle timeouts (see section 5.2)
  - Return a batch, not one message
  - Client re-requests immediately with the new cursor
- Payload

```http
GET /v1/inbox/updates?cursor=abc123&wait=30 HTTP/1.1
```

```json
{"messages": [{"id": "M1", "seq": 101, "text": "hi"},
              {"id": "M2", "seq": 102, "text": "you there?"}],
 "next_cursor": "abc125"}
```

- Timeout with no data: `204 No Content` or an empty list with the same cursor
- Variations: single channel; multiplexed (`?channels=a,b,c`); Comet / Bayeux ★; Socket.IO / SockJS fallback transports

<a id="s4-4"></a>
### 4.4 SSE (Server-Sent Events) ★★★

- Plain idea: the client opens one HTTP connection and the server **keeps writing events into it**; server → client only
- How
  1. Client `new EventSource('/v1/lives/L42/stream')`
  2. Server responds `Content-Type: text/event-stream` and keeps the connection open
  3. Each event is a few text lines ending with a blank line
  4. On disconnect, the browser **reconnects automatically** with `Last-Event-ID`
  5. The server resumes after that id
- Good
  - Plain HTTP: passes proxies, multiplexes on HTTP/2, L7 LBs understand it
  - Built-in reconnect + resume (Last-Event-ID)
  - Simpler than WebSocket
- Cost
  - One direction only; client sends use a normal POST
  - On HTTP/1.1, browsers allow ~6 connections per domain (not an issue on HTTP/2)
  - Text only (binary needs base64)
  - Native `EventSource` can't set custom headers (GET + cookie / query token only)
  - The browser **stops reconnecting** if the server returns non-200, a wrong content type, or 204 — use that deliberately to tell clients to stop
- When: **server pushes, client rarely sends**
  - Live comments, scores, tickers, notification badges, LLM token streaming, progress bars, dashboards
- Tier 3: Spring WebFlux `Flux<ServerSentEvent>`, Node; NGINX needs `proxy_buffering off`
- 🗣 "Live comments are read-heavy and one-directional, so SSE: plain HTTP, auto-reconnect with Last-Event-ID, and posting a comment is just a normal POST."

<a id="s4-4-1"></a>
#### 4.4.1 Schema, Principles, Payload

- Envelope (fixed by the protocol, four fields)
  - `event:` event type (defaults to `message`)
  - `data:` content, may span lines
  - `id:` event id; the browser sends it back as `Last-Event-ID` on reconnect
  - `retry:` suggested reconnect delay (ms)
  - Lines starting with `:` are comments, used as heartbeats
- Payload schema: JSON inside `data`, described per `event` with AsyncAPI / JSON Schema
- Principles
  - `id` increases monotonically within a stream so resume works
  - One `event` name per message type; the client dispatches by name
  - Comment heartbeat every 15–30 s so proxies don't drop the idle connection
  - Server keeps the last N events per stream for resume
  - Use `retry:` with jitter during deploys to spread reconnects
- Payload

```http
GET /v1/lives/L42/stream HTTP/1.1
Accept: text/event-stream
Last-Event-ID: 1833
```

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

retry: 3000

event: comment.batch
id: 1840
data: {"items":[{"comment_id":"C9002","user":"U3","text":"wow"},{"comment_id":"C9003","user":"U8","text":"gg"}]}

: heartbeat

event: viewer.count
id: 1841
data: {"count": 98213}
```

- Variations
  - Default `message` event vs named events
  - Single events vs batched events (hot streams lower the frame rate)
  - Native `EventSource` (GET only) vs fetch-based SSE (`@microsoft/fetch-event-source`): POST + custom headers
    - LLM token streaming = a POST request with an SSE response
  - Auth: cookie, query token, or `Authorization` header with fetch-based SSE
  - HTTP/1.1 vs HTTP/2 (no 6-connection limit on HTTP/2)
  - GraphQL subscriptions over SSE

<a id="s4-5"></a>
### 4.5 WebSocket ★★★

- Plain idea: one HTTP handshake upgrades into a **two-way long-lived connection**; either side sends anytime
- How
  1. Client `GET /ws` with `Upgrade: websocket`
  2. Server responds `101 Switching Protocols`
  3. From then on it's frames over TCP (text or binary), both directions
  4. The app handles heartbeats, acks, reconnects and catch-up itself
- Good: full duplex, low latency, very small per-message overhead
- Cost
  - **Stateful connections**: scaling, deploys and LBs all have to handle them (section 5)
  - Reconnect and catch-up are your job (no Last-Event-ID)
  - Some corporate proxies block it
- When: **both sides send often**
  - Chat, multiplayer games, collaborative editing, trading terminals, voice-room signaling
- Tier 3

| Framework | Good | Cost |
|---|---|---|
| Netty | High performance, many connections per box | Low-level, more code |
| Spring WebSocket / STOMP | Easy integration, topic concept | Average performance |
| Socket.IO | Rooms, auto fallback, auto reconnect | Custom protocol, Node-centric |
| Managed: AWS API GW WebSocket, Pusher, Ably | No ops | Costly, less control; API GW caps connections at 2 h |

- 🗣 "Chat needs both directions at high frequency, so WebSocket; connection servers are stateful and register connection-to-server mappings in Redis."

<a id="s4-5-1"></a>
#### 4.5.1 Schema, Principles, Payload

- Envelope: the protocol only defines frames (opcodes: text / binary / ping / pong / close) and **nothing about content**
- Payload schema: you must define an **envelope**, described with AsyncAPI + JSON Schema or protobuf
- Principles
  - Every message has a `type`; dispatch by type
  - Client messages carry `client_msg_id`; server replies with `ack` (idempotency + "sent" status)
  - Server messages carry a `seq` per conversation; the client detects gaps and refetches (chat only — see 6.8)
  - Protocol version in the handshake: `Sec-WebSocket-Protocol: chat.v1`
  - Heartbeat: protocol ping/pong or app-level `{"type":"ping"}`
  - Cap frame size; upload big content over HTTP and send a reference
  - Close codes carry intent: `1000` normal, `1001` going away (deploy), `1008` policy violation (auth)
- Handshake (use a short-lived connect ticket, not a long-lived JWT, in the URL — URLs end up in logs)

```http
GET /ws?ticket=tk_9f2c HTTP/1.1
Host: chat.example.com
Origin: https://app.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat.v1
```

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat.v1
```

- Frames (text, JSON envelope)

```json
// client → server: send
{"type": "message.send", "client_msg_id": "c-77a1", "chat_id": "G5",
 "body": {"text": "hello"}, "ts": 1794170000000}

// server → client: ack (seq assigned by the per-chat sequencer, see 6.8)
{"type": "message.ack", "client_msg_id": "c-77a1", "msg_id": "M8812", "seq": 342}

// server → client: someone else's message
{"type": "message.new", "msg_id": "M8813", "chat_id": "G5", "seq": 343,
 "from": "U9", "body": {"text": "hey"}, "ts": 1794170000500}

// client → server: read receipt (watermark)
{"type": "receipt.read", "chat_id": "G5", "up_to_seq": 343}

// client → server: catch up after reconnect
{"type": "sync.request", "chat_id": "G5", "after_seq": 340}

// server → client: token expiring, re-auth or reconnect
{"type": "auth.refresh_required", "expires_in_s": 60}
```

- Variations
  - Raw WebSocket + custom JSON envelope (above)
  - Binary frames + protobuf (bandwidth, mobile, games)
  - STOMP over WebSocket: `SEND` / `SUBSCRIBE` / `MESSAGE` frames with `destination` (common in Spring)
  - Socket.IO protocol: `emit(event, data, ack)`, rooms, namespaces, built-in reconnect
  - `graphql-ws`: GraphQL subscriptions
  - MQTT over WebSocket: browsers talking to an MQTT broker
  - WAMP ★
  - Compression: `permessage-deflate` (costs memory per connection)
  - Auth: connect ticket / cookie at handshake, or first message `auth`

<a id="s4-6"></a>
### 4.6 gRPC / HTTP2 Streaming ★★

- Plain idea: gRPC streaming calls; one connection carries a continuous flow
- Four modes: unary; server streaming (like SSE); client streaming (sensor uploads); bidirectional (like WebSocket)
- Good: strongly typed, binary, saves mobile data
- Cost
  - Browsers need gRPC-Web + proxy (unary and server streaming only)
  - **LB pinning**: an L4 LB pins a long-lived HTTP/2 connection to one backend, so load skews; use client-side / xDS load balancing and set server `max_connection_age` so clients rebalance
- When: native mobile ↔ backend, internal service streams
- 🗣 "For a native mobile client I'd use gRPC bidirectional streaming, with max_connection_age so long streams rebalance across servers."

<a id="s4-6-1"></a>
#### 4.6.1 Schema, Principles, Payload

- Schema: `stream` keyword in `.proto`

```protobuf
service ChatService {
  rpc Connect(stream ClientEvent) returns (stream ServerEvent);
}
message ClientEvent {
  oneof event {
    SendMessage send = 1;
    ReadReceipt read = 2;
    Ping ping = 3;
  }
}
message ServerEvent {
  oneof event {
    MessageAck ack = 1;
    NewMessage message = 2;
    Pong pong = 3;
  }
}
```

- Principles
  - `oneof` is the envelope, equivalent to WebSocket's `type`
  - Long streams must handle mid-stream disconnects, deadlines and keepalives
  - New message type = new number in the `oneof`; old clients ignore it
- Payload: a sequence of length-prefixed protobuf frames on HTTP/2, same as 4.1.3

<a id="s4-7"></a>
### 4.7 Mobile Push (APNs / FCM) ★★★

- Plain idea: when the app is backgrounded or killed, notifications go through **Apple's / Google's push service** to the phone
- How
  1. App registers with APNs / FCM at startup and gets a **device token**
  2. App sends the token to our backend; we store `user → tokens`
  3. To notify, our service calls the APNs / FCM API
  4. The OS shows it; when the user opens the app, it fetches the real data
- Good: reaches offline users; battery-friendly (the OS keeps one shared connection)
- Cost
  - **No delivery or ordering guarantee**; rate limits apply
  - Small payload (~4 KB)
  - Offline storage is limited (see 4.7.1)
  - Tokens expire and must be cleaned up
- When: the user is **not online**
- Common combo: WebSocket while online, APNs / FCM while offline
- 🗣 "Push notifications are a hint, not the data; the client syncs the real messages when it opens."

<a id="s4-7-1"></a>
#### 4.7.1 Schema, Principles, Payload

- Schema: defined by Apple / Google; our own data goes in `data` / custom keys
- Offline semantics (why "push is a hint")
  - APNs keeps only the **latest** notification per app while the device is offline
  - FCM stores up to **100** non-collapsible messages per device; past that it discards them and tells the app to do a full sync (Firebase docs)
- Principles
  - Only hints and IDs, no sensitive content (visible on the lock screen)
  - Use `apns-collapse-id` / `collapse_key` to merge similar notifications
  - High priority (immediate) vs normal (battery-friendly, may be delayed)
  - Set a TTL: don't deliver stale notifications
  - Include `chat_id` etc. so the app can fetch the data on open
  - Silent / background pushes are throttled by iOS (priority 5, push-type `background`): best-effort wake-up, never the sync mechanism
- APNs (HTTP/2)

```http
POST /3/device/<device_token> HTTP/2
Host: api.push.apple.com
authorization: bearer <JWT>
apns-topic: com.example.chat
apns-push-type: alert
apns-priority: 10
apns-collapse-id: chat-G5
apns-expiration: 1794173600

{"aps": {"alert": {"title": "Alice", "body": "hey, you there?"},
         "badge": 3, "sound": "default", "thread-id": "chat-G5"},
 "chat_id": "G5", "msg_id": "M8813"}
```

- FCM (HTTP v1)

```json
POST https://fcm.googleapis.com/v1/projects/my-proj/messages:send
{"message": {
   "token": "<device_token>",
   "notification": {"title": "Alice", "body": "hey, you there?"},
   "data": {"chat_id": "G5", "msg_id": "M8813"},
   "android": {"priority": "HIGH", "collapse_key": "chat-G5", "ttl": "3600s"}
}}
```

- Variations
  - Alert push vs silent / background push
  - FCM notification message (OS displays) vs data message (app handles)
  - Single token vs FCM topic vs device group
  - VoIP push (iOS PushKit, incoming calls)
  - Web Push (browsers, VAPID)
  - Other channels: SMS (Twilio), email (SES, SendGrid) — each with templates and unsubscribe rules

<a id="s4-8"></a>
### 4.8 MQTT (IoT) ★

- Plain idea: a very light pub/sub protocol; devices connect to a broker and subscribe to topics
- Good: tiny packets, works on weak networks, QoS 0/1/2, retained messages, Last Will
- When: IoT devices, vehicles, weak-network mobile
- Schema
  - Topic hierarchy is half the schema: `fleet/{region}/{device_id}/telemetry` (wildcards `+`, `#`)
  - Payload: JSON, protobuf or CBOR
  - QoS 2 "exactly once" is **per hop** (client ↔ broker), not end to end
- Tier 3: EMQX, Mosquitto, AWS IoT Core
- 🗣 "For millions of low-power devices I'd use MQTT with QoS 1 and idempotent processing downstream."

<a id="s4-9"></a>
### 4.9 WebRTC (Client ↔ Client) ★

- Plain idea: two clients send audio / video / data **directly**; the server only introduces them
- How
  1. Signaling: peers exchange SDP offer / answer and ICE candidates through our server (usually WebSocket, your own JSON schema)
  2. STUN: each peer learns its public address
  3. NAT traversal succeeds → direct P2P
  4. Fails → relay through a TURN server
  5. Group calls: an SFU (forwards streams without decoding) instead of full mesh
- Cost: NAT traversal complexity; TURN bandwidth is expensive
- Tier 3: LiveKit, mediasoup, Janus (SFU); coturn (TURN)
- 🗣 "WebRTC still needs a server for signaling and TURN fallback; for group calls I'd use an SFU."

<a id="s4-10"></a>
### 4.10 Large File Transfer ★★★

- Plain idea: big files **skip the app servers** and go straight to object storage

| Method | How | When |
|---|---|---|
| Presigned URL | API signs a time-limited upload URL; client uploads directly | Default |
| Multipart upload | Split into parts, upload in parallel, then complete | Hundreds of MB and up |
| Resumable (tus, chunks + offsets) | Remember uploaded chunks; resume after network loss | Mobile, weak networks, big video |
| Chunk + dedup (content hash) | Hash each chunk; skip chunks the server already has | Dropbox-style sync |

- Download: CDN + Range requests; video in small segments (HLS / DASH)
- 🗣 "The API only issues a presigned URL; bytes go straight to object storage, and the object-created event triggers processing."

<a id="s4-10-1"></a>
#### 4.10.1 Schema, Principles, Payload

- Schema: the "request an upload" API is OpenAPI; the upload itself is raw bytes
- Principles
  - Submit metadata (name, size, type, hash) up front; server validates size and type
  - Short-lived URLs (minutes)
  - A presigned **PUT** can't enforce a size range; use a presigned **POST** with a `content-length-range` policy, or sign the exact Content-Length
  - Multipart **requires** the client to call Complete with the part ETags; only then does the object-created event fire
  - Lifecycle rule to abort incomplete multipart uploads (orphaned parts cost money)
  - Content hash for integrity and dedup
- Payload

```http
POST /v1/uploads HTTP/1.1
Content-Type: application/json

{"file_name": "trip.mp4", "size_bytes": 734003200,
 "content_type": "video/mp4", "sha256": "9f2c..."}
```

```json
{"upload_id": "UP-31", "strategy": "multipart", "part_size_bytes": 8388608,
 "parts": [{"part_number": 1, "url": "https://bucket.s3.../trip.mp4?partNumber=1&uploadId=...&X-Amz-Signature=..."}],
 "complete_url": "/v1/uploads/UP-31/complete", "expires_at": "2026-11-08T20:46:05Z"}
```

```http
PUT https://bucket.s3.../trip.mp4?partNumber=1&uploadId=...&X-Amz-Signature=...
Content-Length: 8388608

<8 MB of raw bytes>
```

- tus (resumable protocol)

```http
PATCH /files/24e533e0 HTTP/1.1
Tus-Resumable: 1.0.0
Upload-Offset: 70000
Content-Type: application/offset+octet-stream

<bytes starting at offset 70000>
```

- Variations: single PUT, multipart, tus, chunk + hash dedup; download side: GET, Range, HLS / DASH segments (`.m3u8` playlist listing segment files)

<a id="s5"></a>
## 5. Running Long-Lived Connections ★★★

- This is where interviewers spend their follow-ups for live comments, chat and notifications
- Applies to SSE, WebSocket and gRPC streams

<a id="s5-1"></a>
### 5.1 Sizing The Connection Tier (Worked Math) ★★★

- Assumptions (order of magnitude; varies widely by stack)
  - 10M concurrent viewers at peak
  - ~20–50 KB memory per connection (kernel socket buffers + TLS + app state)
- Memory check
  - 100k connections × 50 KB ≈ 5 GB per node → memory is not the binding limit
  - The binding limits are CPU for TLS and egress bandwidth
- Node count
  - Plan conservatively at 50k connections per node → 10M / 50k = 200 nodes
  - Add ~30% for AZ loss and rolling deploys → ~260 nodes
- Reconnect storm when one node dies
  - 50k clients with jittered backoff spread over 30 s ≈ 1.7k handshakes/s across the cluster → fine
  - Without jitter: 50k handshakes in ~1 s → TLS CPU spike → cascading failures
  - That is why client backoff + jitter is mandatory
- 🗣 "At 50k connections per node, 10M viewers is ~200 nodes plus 30% headroom; memory isn't the limit, TLS CPU and egress are."

<a id="s5-2"></a>
### 5.2 Load Balancers And Idle Timeouts ★★

- LB choice
  - L4 (e.g. NLB) or a WebSocket-aware L7 (e.g. ALB, Envoy)
  - A connection stays on one backend for its lifetime
- Idle timeouts drop quiet connections (verify current values)
  - AWS ALB: 60 s default idle timeout (configurable)
  - AWS NLB: 350 s TCP idle timeout
  - AWS API Gateway WebSocket: 10 min idle, 2 h max connection duration
  - Mobile carrier NATs: often much shorter, unpredictable
- Rule: heartbeat interval shorter than the shortest idle timeout on the path (typically 15–30 s for SSE / WebSocket)
- Half-open connections: if the client vanished without closing, only missed heartbeats reveal it → server closes after N missed pings
- Mobile reality: iOS suspends sockets when the app is backgrounded; don't try to keep a socket alive in the background — switch to OS push
- 🗣 "Heartbeat every 20 seconds, under the ALB's 60-second idle timeout; on mobile background we drop the socket and rely on APNs."

<a id="s5-3"></a>
### 5.3 Auth On Long-Lived Connections ★★

- At connect
  - Short-lived, single-use **connect ticket** from a REST call (`POST /v1/realtime/tickets`), passed at handshake
  - Or cookie + **Origin check** (prevents cross-site WebSocket hijacking, CSWSH)
  - Always WSS / HTTPS (TLS)
- During the connection
  - Token expiry mid-connection: server sends `auth.refresh_required`; client re-auths in-band or reconnects
  - Revocation (user logged out, banned): server closes with `1008`
- Per subscription
  - Authorize every subscribe: can this user join `live:L42` or chat `G5`?
  - Don't trust a channel name the client sends without checking
- Rate limits per connection
  - Inbound messages per second per connection
  - Connection-establishment rate per user / IP
- 🗣 "Auth at handshake with a one-time ticket, authorize every subscribe, and close with 1008 on revocation."

<a id="s5-4"></a>
### 5.4 Backpressure And Slow Clients ★★★

- Problem: one slow phone on a bad network can't keep up; unbounded buffers eat server memory
- Per-connection policy
  - Bounded send buffer per connection
  - When full, pick one by message type
    - **Coalesce**: keep only the latest (viewer count, location)
    - **Drop oldest**: OK for live comments
    - **Disconnect**: client reconnects and resumes via Last-Event-ID / last_seq (chat)
- The Redis hop
  - A slow Pub/Sub subscriber gets disconnected by `client-output-buffer-limit pubsub` and **silently loses messages**
  - Keep connection servers fast at draining Redis; never do slow work in the subscribe callback
- 🗣 "Each connection has a bounded buffer; for comments we drop oldest, for chat we disconnect and let the client resume by sequence."

<a id="s5-5"></a>
### 5.5 Deploys, Draining, Reconnect Storms ★★★

- Never restart every node at once
- Drain 5–10% of nodes at a time
  1. Remove the node from the LB (no new connections)
  2. Tell clients to move
     - WebSocket: close code `1001` (going away)
     - SSE: send a `reconnect` event or close, with a jittered `retry:`
     - gRPC / HTTP/2: GOAWAY
  3. Clients reconnect with jittered backoff to other nodes and resume (Last-Event-ID / last_seq)
  4. Wait for the node's connection count to fall near zero, then stop it
- Keep capacity headroom (section 5.1) so the remaining nodes absorb the moved connections
- 🗣 "Rolling drain in 10% waves with close code 1001 and jittered client backoff; clients resume by sequence, so no messages are lost."

<a id="s5-6"></a>
### 5.6 Routing: How A Message Finds The User's Connection ★★★

- Problem: user B is connected to connection server #7; a message arrives at API server #3. How does it reach #7?

| Option | How | Good | Cost | Choose when |
|---|---|---|---|---|
| Registry + direct RPC | Redis maps connection → server; API looks up and calls #7 | Precise, little waste | Registry upkeep; cleanup when a server dies | 1:1 chat |
| Pub/Sub per user channel | Each server subscribes to its online users' channels | Decoupled | Huge number of channels | Medium scale |
| Pub/Sub per room / topic | A server subscribes to rooms it has viewers for | Efficient fan-out | Hot rooms reach every server | Live comments, group chat |
| Broadcast to all servers | Every server receives, filters locally | Simplest | Wasteful at scale | Small scale |

- Registry data model (multi-device safe)

```
HSET conn:U9 k1f3 cs-7        # field = connection id, value = server
HSET conn:U9 a8d2 cs-12       # second device, does not overwrite the first
SET  connttl:U9:k1f3 1 EX 90  # per-connection TTL, renewed by heartbeat
SADD room:L42:servers cs-3 cs-7 cs-12
```

- Cleanup
  - A connection whose TTL key expired is removed from the hash by a sweeper (or on failed delivery)
  - `room:{id}:servers`: a server removes itself when its last viewer of that room leaves; a periodic job prunes dead servers
- Internal delivery RPC

```protobuf
service Delivery {
  rpc Deliver(DeliverRequest) returns (DeliverResponse);
}
message DeliverRequest {
  repeated string connection_ids = 1;
  bytes envelope = 2;     // forwarded as-is as a WebSocket / SSE frame
}
```

- Delivery fails (server gone) → delete the registry entry → fall back to offline push

<a id="s5-7"></a>
### 5.7 Hot-Room Fan-Out (Worked Math) ★★★

- Assumptions: 1M viewers, 5k comments/s written, ~200 B per comment
- Naive fan-out
  - 5k × 1M × 200 B = **1 TB/s** egress → impossible
  - This number is why sampling exists
- With a display cap (people can read ~10–20 comments/s)
  - Cap 20 comments/s per viewer, batched every 500 ms
  - 20 × 200 B = 4 KB/s per viewer × 1M ≈ 4 GB/s ≈ 32 Gbps total egress
  - At 50k viewers per node: ~1.6 Gbps and ~100k socket writes/s per node → feasible
  - Compression can cut this further (factor varies)
- Redis hop
  - Sample to ~20/s **in the fan-out service, before Redis**
  - **One** PUBLISH per batch; Redis delivers it to every subscribed server (say 20 servers) → 20 × 2 batches/s = 40 deliveries/s → trivial
  - Each server then pushes to its ~50k local viewers
- Redis Cluster caveat: classic `PUBLISH` is broadcast to every cluster node; Redis 7 sharded Pub/Sub (`SPUBLISH`) keeps a channel on one shard
- Beyond one region: a relay tier (regional fan-out servers) between the fan-out service and connection servers
- Which comments to show: viewer's own comments always, friends' comments boosted, then top-K / random sample
- Live comments are **lossy by design**: no gap repair, only resume on reconnect
- 🗣 "One publish per batch, Redis delivers to each subscribed server, each server pushes to its local viewers; we cap the display rate at ~20 per second, which turns 1 TB/s into ~32 Gbps."

<a id="s5-8"></a>
### 5.8 Presence, Typing, Read Receipts, Multi-Device ★★

- Presence
  - Online = a TTL key renewed by heartbeat (`presence:U9`, 60 s)
  - Fan out changes lazily: only to contacts currently viewing the user (visible list), not to all friends
- Typing indicators
  - Ephemeral, never persisted, throttled (send at most every few seconds)
  - Lossy is fine
- Read receipts
  - Store a watermark per user per chat: `last_read_seq`
  - Large groups: show counts, not per-user lists
- Multi-device sync
  - Each device keeps its own cursor (`last_seq` per chat)
  - New device: paged history sync from the message store
- Group fan-out
  - Fan-out on write (copy into each member's inbox): fast reads, expensive for big groups
  - Fan-out on read (one per-chat log, members read it): cheap writes
  - Common: on-write below a group-size threshold, on-read above it
- 🗣 "Presence is a TTL heartbeat fanned out only to people looking at you; receipts are a last-read watermark, not per-message rows."

<a id="s6"></a>
## 6. Server ↔ Server

<a id="s6-1"></a>
### 6.1 Sync: REST / gRPC ★★★

- Plain idea: service A calls service B and **waits**
- When: the result is needed now (user profile, permission check, price)

| Style | Good | Cost | Choose when |
|---|---|---|---|
| REST | Universal, easy to debug | Slower JSON, no strong contract | Cross-team, public APIs |
| gRPC | Fast, protobuf contract, streaming | Fewer debugging tools | High-volume internal calls |

- Required companions
  - Service discovery (K8s DNS, Consul)
  - A **timeout** on every hop
  - Retries only for idempotent operations, **exponential backoff + jitter**, a retry budget
  - Circuit breaker (Resilience4j)
- The catch: availability multiplies down a sync chain
  - Example: 5 services at 99.9% each → ~99.5% end to end
- Schema extras for internal calls
  - Shared proto repo (or buf registry) with breaking-change checks in CI
  - Consumer-driven contract tests (Pact)
  - Propagated headers: `traceparent` (W3C), deadline / remaining timeout, caller identity (mTLS or service token), request id, tenant id

```http
GET /internal/v1/users/U7/profile HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
x-tenant-id: T12
x-request-timeout-ms: 150
```

- 🗣 "Sync only where the caller truly needs the answer; everything else goes async."

<a id="s6-2"></a>
### 6.2 Async: Queue (Point-To-Point) ★★★

- Plain idea: messages go into a queue; **one** consumer processes each
- How
  1. Producer sends
  2. Consumer receives; the message becomes invisible for a while (visibility timeout = a lease)
  3. Success → delete / ack
  4. Failure or timeout → visible again, retried
  5. Too many failures → DLQ
- Long jobs: extend the lease while working (`ChangeMessageVisibility`), or the message reappears and runs twice
- When: task distribution, absorbing spikes, background jobs (email, transcoding, reports)
- Tier 3

| Implementation | Good | Cost |
|---|---|---|
| SQS / OCI Queue | Managed, auto-scaling | Standard queues don't guarantee order; FIFO parallelism = number of message groups |
| RabbitMQ | Flexible routing, low latency, priorities | Self-managed, lower throughput than Kafka |
| Redis list / BullMQ | Simple, fast | Weaker durability |

- Schema and payload
  - Queue messages are usually **commands** ("do X"), imperative names: `TranscodeVideo`
  - Carry `id` for idempotency; `attempt` count helps debugging
  - Size limit: SQS max message size is 1 MiB (raised from 256 KiB in Aug 2025); still use claim-check for large payloads
  - FIFO: `MessageGroupId` sets the ordering scope; `MessageDeduplicationId` dedups

```json
{
  "MessageBody": "{\"id\":\"cmd-5521\",\"type\":\"TranscodeVideo\",\"version\":1,\"occurred_at\":\"2026-11-08T20:31:05Z\",\"source\":\"upload-svc\",\"data\":{\"video_id\":\"V88\",\"input\":\"s3://raw/V88.mp4\",\"profiles\":[\"720p\",\"1080p\"]}}",
  "MessageAttributes": {"type": {"DataType": "String", "StringValue": "TranscodeVideo"}},
  "MessageGroupId": "V88",
  "MessageDeduplicationId": "cmd-5521"
}
```

- Variations: standard vs FIFO; delayed messages; priority queues (RabbitMQ); RabbitMQ exchanges (direct, topic, fanout, headers); request-reply with `reply_to` + `correlation_id`
- 🗣 "Queue for work: each job processed by one worker under a lease it extends while working, DLQ after N failures."

<a id="s6-3"></a>
### 6.3 Async: Pub/Sub (One-To-Many) ★★★

- Plain idea: publish once, **every subscriber** gets a copy
- When
  - One event, many interested parties: order created → inventory, email, analytics
  - Realtime fan-out to connection servers
- Two kinds
  - **Durable**: messages kept for offline subscribers (SNS → SQS, Kafka consumer groups, Google Pub/Sub)
  - **Fire-and-forget**: only currently connected subscribers get it (Redis Pub/Sub)

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| SNS + SQS (fan-out) | Managed, one queue per downstream | No replay (except SNS FIFO archive/replay) | AWS event notification |
| Redis Pub/Sub | Sub-millisecond, simple | Not durable; slow subscribers get cut off; cluster broadcast unless sharded (`SPUBLISH`) | Realtime hop to connection servers |
| Kafka (multiple groups) | Durable, replayable | Heavier | Core event backbone |
| Google Pub/Sub | Managed, global | GCP only | On GCP |

- Schema and payload: **events** ("X happened"), CloudEvents envelope

```json
{"specversion": "1.0",
 "id": "evt-90a1",
 "type": "com.example.order.placed",
 "source": "/order-svc",
 "time": "2026-11-08T20:31:05Z",
 "datacontenttype": "application/json",
 "dataschema": "https://schemas.example.com/order.placed/v2.json",
 "data": {"order_id": "O551", "user_id": "U7", "total_cents": 4599, "items": 3}}
```

```
PUBLISH live:L42 '{"type":"comment.batch","items":[...]}'
SUBSCRIBE live:L42
```

- Principles
  - Past-tense event names; hierarchical topic names (`domain.entity.event`, `live:{id}`)
  - Publishers don't know subscribers → events must be self-describing
  - Filter with message attributes (SNS filter policies) instead of every subscriber receiving everything
- Variations: topic-based vs content-based filtering; durable vs non-durable subscriptions; Redis Streams (durable + consumer groups); event notification (thin, id only) vs event-carried state transfer (full data)
- 🗣 "Redis Pub/Sub for the live fan-out hop because a lost frame is fine; Kafka underneath for anything we must not lose."

<a id="s6-4"></a>
### 6.4 Async: Log / Stream (Kafka) ★★★

- Plain idea: messages are **appended to a log** and kept for a while; each consumer tracks its own position (offset)
- vs queue
  - Queue: deleted after consumption
  - Log: kept; many consumer groups read independently; replay is possible
- How
  1. A topic has N partitions
  2. Producer picks the partition by key → **same key, same partition**
  3. Each partition is replicated (replication factor commonly 3)
  4. In a consumer group, each partition goes to exactly one consumer
  5. Consumers commit offsets
- When: high-throughput ingestion, many downstreams, replay, event sourcing, CDC
- Tier 3: Kafka, OCI Streaming (Kafka-compatible), Kinesis, Pulsar, Redpanda

<a id="s6-4-1"></a>
#### 6.4.1 Ordering, Exactly-Once, Rebalancing, Retries ★★★

- Per-key order holds when
  - The idempotent producer is on (default since Kafka 3.0), so retries don't reorder or duplicate
  - The partition count doesn't change (adding partitions remaps keys)
- Exactly-once boundaries
  - Idempotent producer: no duplicates from producer retries
  - Transactions: atomic consume → transform → produce **within Kafka only**
  - Side effects on an external DB still need idempotent writes (dedup by event id)
- Commit after processing (at-least-once), never before (that's at-most-once)
- Rebalancing
  - Deploys trigger rebalances → lag spikes
  - Fixes: cooperative-sticky assignor, static membership, deploy in small batches
- Retries
  - Kafka has no per-message nack; a poison record blocks its partition
  - Use retry topics (`orders.retry.1m`, `orders.retry.10m`) and a dead-letter topic
- Priority: Kafka has none → separate topics per priority (OTP vs marketing)

<a id="s6-4-2"></a>
#### 6.4.2 Partition Count (Worked Math) ★★

- Metrics ingestion assumptions (order of magnitude)
  - 1M hosts × 100 points every 10 s = 10M points/s
  - ~50 B per point → ~500 MB/s
- Throughput need: at a conservative ~5–10 MB/s per partition → 50–100 partitions
- Parallelism need: if one consumer handles ~20k points/s → 500 consumers → ≥500 partitions
- Take the max, ×2 headroom → ~1,000 partitions
- Retention: 500 MB/s × 86,400 s ≈ 43 TB/day × RF 3 ≈ 130 TB/day
- Live-comment sanity check: one mega stream at 5k/s × 300 B = 1.5 MB/s → fits one partition, so key = live_id is safe
- Hot tenant: salt the key (`tenant#0..7`) + per-tenant quotas
- 🗣 "Partitions = max of throughput need and consumer parallelism, times two; key by live_id is fine because one stream is only ~1.5 MB/s."

<a id="s6-4-3"></a>
#### 6.4.3 Schema, Principles, Payload

- A Kafka record (protocol-defined)
  - `key`: decides partition and ordering scope
  - `value`: business content
  - `headers`: metadata (trace id, event type)
  - `timestamp`, `partition`, `offset` (assigned by the broker)
- Payload schema: Avro / Protobuf / JSON Schema registered in a **Schema Registry**
  - Confluent wire format: the value starts with a magic byte + 4-byte schema id
  - Registry checks each new version against the compatibility mode
- Principles
  - **Key choice = ordering scope = hotspot risk**
  - Default compatibility BACKWARD (upgrade consumers first, then producers)
  - Compacted topics keep only the latest value per key; a null value (tombstone) deletes
- Avro schema

```json
{"type": "record", "name": "CommentCreated", "namespace": "com.example.live",
 "fields": [
   {"name": "comment_id", "type": "string"},
   {"name": "live_id", "type": "string"},
   {"name": "user_id", "type": "string"},
   {"name": "text", "type": "string"},
   {"name": "created_at_ms", "type": "long"},
   {"name": "lang", "type": ["null", "string"], "default": null}
 ]}
```

- One record

```
topic:     live.comments.v1
partition: 17            (= hash(key) % 64)
offset:    9123344
key:       "L42"
headers:   type=comment.created, trace_id=4bf92f35...
timestamp: 1794170000000
value:     [0x00][schema id 118][Avro bytes: comment_id=C9001, live_id=L42, ...]
```

- Variations: event notification vs event-carried state transfer; event sourcing; CDC topics (`before` / `after` / `op`); compacted topics; Kafka transactions; serialization Avro / Protobuf / JSON Schema (plain JSON without a registry is not recommended)
- 🗣 "Kafka keyed by chat_id: per-chat ordering, idempotent producer on, and the partition count caps consumer parallelism."

<a id="s6-5"></a>
### 6.5 Outbox: Atomic DB Write + Publish ★★★

- Problem: the service writes the DB **and** publishes a message; a crash in between loses the message or publishes a phantom
  - Example: control-plane API inserts a work-request row, then enqueues the job — crash after insert = job never runs
- Options

| Option | How | Good | Cost | Choose when |
|---|---|---|---|---|
| Dual write | Write DB, then publish | Simple | Inconsistent on crash | Never |
| Transactional outbox | Insert business row + outbox row in **one transaction**; a relay publishes outbox rows | Atomic, works with any broker | Extra table + relay; relay may publish twice | Default |
| CDC | Stream the DB log (binlog / WAL) to Kafka (Debezium) | No app changes | Depends on DB log; some lag | Existing systems, search / warehouse feeds |
| Change streams | DynamoDB Streams, Mongo change streams | Built in | DB-specific | That DB already |

- The relay can publish twice → consumers are idempotent on event id
- Outbox row schema

```sql
CREATE TABLE outbox (
  id            UUID PRIMARY KEY,      -- = event id, the dedup key
  aggregate_id  TEXT NOT NULL,         -- becomes the Kafka key
  type          TEXT NOT NULL,         -- e.g. work_request.created
  payload       JSONB NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL,
  published_at  TIMESTAMPTZ            -- null until relayed
);
```

- 🗣 "I never dual-write: business row and outbox row in one transaction, a relay publishes, and consumers dedup on event id."

<a id="s6-6"></a>
### 6.6 Server → External: Webhooks ★★

- Plain idea: when an event happens, we POST to a URL the partner gave us
- How
  1. Partner registers a URL and event types
  2. Event happens → enqueue → worker POSTs
  3. Sign with HMAC so the partner can verify
  4. Retry with exponential backoff; eventually DLQ
- Must say: the receiver **must be idempotent** (redelivery happens); include an event id
- Schema: OpenAPI 3.1 `webhooks` section, or the Standard Webhooks spec
- Principles
  - Sign `id.timestamp.body`; receiver rejects old timestamps (replay protection)
  - Receiver 2xx = success; anything else retries
  - Thin payloads (id only, receiver fetches) are safer; fat payloads are more convenient
  - Offer a delivery log and manual redelivery
- Payload

```http
POST https://merchant.example.com/hooks/payments HTTP/1.1
Content-Type: application/json
webhook-id: evt_2Lz9
webhook-timestamp: 1794170000
webhook-signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{"id": "evt_2Lz9", "type": "payment.succeeded", "created": 1794170000,
 "data": {"payment_id": "pay_88", "amount_cents": 4599, "currency": "USD"}}
```

- Variations: fat vs thin payload; per-event vs batched; push (webhook) vs pull (event list API + cursor); CloudEvents HTTP binding (`ce-*` headers)
- 🗣 "Webhooks are at-least-once, signed with HMAC, retried with backoff, and carry an event id for dedup."

<a id="s6-7"></a>
### 6.7 Multi-Step Workflows: Saga ★★

- Problem: a business flow across services (order → reserve inventory → charge) with no distributed transaction

| Style | How | Good | Cost | Choose when |
|---|---|---|---|---|
| Choreography | Each service listens for and emits events | Decentralized, loosely coupled | Flow is scattered, hard to trace | Few steps |
| Orchestration | One orchestrator calls each step in order | Clear flow, easy to monitor | Central component | Many steps, compensation needed |

- On failure: run **compensating actions** (refund, release inventory)
- Messages
  - **Command**: orchestrator → service, imperative
  - **Event / reply**: service → orchestrator, past tense
  - Every message carries `saga_id` (correlation id) and `step`; every step is idempotent

```json
{"type": "ReserveInventory", "saga_id": "S-731", "step": 2,
 "data": {"order_id": "O551", "items": [{"sku": "A1", "qty": 2}]}}

{"type": "InventoryReserved", "saga_id": "S-731", "step": 2,
 "data": {"reservation_id": "R-90", "expires_at": "2026-11-08T20:46:05Z"}}

{"type": "ReleaseInventory", "saga_id": "S-731", "step": 2, "compensation": true,
 "data": {"reservation_id": "R-90"}}
```

- Tier 3: Temporal, AWS Step Functions, Camunda; choreography over Kafka
- 🗣 "Orchestrated saga with Temporal: each step is idempotent and has a compensating action."

<a id="s6-8"></a>
### 6.8 Delivery Guarantees And Sequencing ★★★

<a id="s6-8-1"></a>
#### 6.8.1 Delivery Semantics And Idempotency

| Semantics | Meaning | How you get it | Used for |
|---|---|---|---|
| At-most-once | May lose, never duplicates | Ack before processing | Sampled metrics, live location |
| At-least-once | Never loses, may duplicate | Ack after processing | Default |
| Effectively-once | Never loses, effect not duplicated | At-least-once + **idempotent consumers** | Payments, billing, inventory |

- Idempotent consumers
  - Unique message id + dedup table / unique constraint (with a TTL)
  - Or naturally idempotent operations (set, not increment)

<a id="s6-8-2"></a>
#### 6.8.2 Who Assigns The Sequence Number ★★★

- Problem: chat needs a per-conversation order; Kafka offsets are per partition, not per chat, and not contiguous per key
- Never order by client timestamps (clocks drift)
- Options for a per-chat `seq`

| Option | How | Good | Cost |
|---|---|---|---|
| Atomic counter | Redis `INCR seq:G5` before writing | Simple, fast | Redis failover can repeat or skip numbers unless persisted carefully |
| Conditional DB write | Insert with `seq = last + 1` under a condition (LWT / transaction) | Durable | Slower, contention on hot chats |
| Single writer per partition | The consumer that owns the chat's partition assigns seq in memory and persists it | No coordination | Must recover the counter on rebalance |

- Rules
  - Gaps are tolerable; duplicates and reordering are not
  - Decide whether the client's ack waits for the seq (synchronous sequencer) or arrives later in `message.new`
- Client side
  - Display by seq; detect gaps → `sync.request(after_seq)` (chat only)
  - Live comments: no gap repair (sampling creates gaps on purpose)
- 🗣 "A single writer per chat partition assigns seq; gaps are OK, duplicates aren't, and clients dedup by client_msg_id."

<a id="s6-8-3"></a>
#### 6.8.3 Retries, DLQ, Backpressure

- Retries: exponential backoff + jitter; cap the attempts; **DLQ** holds poison messages
  - DLQ messages also carry `error`, `attempts`, `first_failed_at`
- Backpressure when consumers fall behind
  - Buffer in the queue (short term)
  - Throttle producers (429)
  - Drop / sample (when acceptable)
  - Scale consumers (watch consumer lag)

<a id="s6-9"></a>
### 6.9 S↔S Decision Tree And Table

```
Does the caller need the result now?
├─ Yes ────────────────────────▶ gRPC (internal) / REST (cross-team)
└─ No
   ├─ Must also update our DB atomically? ─▶ Outbox (+ any option below)
   ├─ One consumer per message? ──▶ Queue (SQS / RabbitMQ)
   ├─ Many downstreams?
   │  ├─ Durable / replayable ───▶ Log (Kafka)
   │  └─ Loss OK, ultra-low latency ─▶ Redis Pub/Sub
   ├─ Multi-service business flow? ─▶ Saga (Temporal / events)
   └─ Receiver is external? ──────▶ Webhook
```

| App | Step | Method | Why |
|---|---|---|---|
| Chat | API → store + deliver | Kafka (key = chat_id) | Durable, per-chat order |
| Chat | Deliver to user's server | Registry + RPC, or Redis Pub/Sub | Precise routing |
| Live comments | Write → fan-out | Kafka (key = live_id) → sampled → Redis Pub/Sub | Durable + low-latency fan-out |
| Notification | Business events → notification svc | Kafka / SNS | Many sources |
| Notification | Notification svc → channels | One queue per channel and priority | Isolate failures, separate rate limits |
| Ad click / metrics | Ingestion | Kafka → Flink windowed aggregation | High throughput, replay |
| Order | Order → inventory → payment | Orchestrated saga | Needs compensation |
| Video | Upload done → transcode | Queue (one worker per job) | Long jobs |
| Search | DB change → index | CDC (Debezium) → Kafka | No dual write |
| OCI control plane | Create resource | Work-request row + outbox → queue → worker | Atomic, async |
| Payment | Notify merchant | Webhook | External system |

## 7. End-To-End Flows

- Each flow: numbers → APIs → path → storage → ordering → failure → degradation

<a id="s7-1"></a>
### 7.1 Live Comments ★★★ (The Question I Failed)

- Numbers: 1M viewers on the hottest stream; 5k comments/s written; display cap 20/s per viewer (see 5.7)
- APIs
  - `GET /v1/lives/{id}/stream` → SSE
  - `POST /v1/lives/{id}/comments` (Idempotency-Key) → 202
  - `GET /v1/lives/{id}/comments?before=<cursor>` → recent history

```
Viewer ──SSE──▶ Conn Server ◀── Redis Pub/Sub(live:{id}) ◀── Fan-out svc (sample/batch) ◀── Kafka(key=live_id) ◀── Comment API ◀──POST── Commenter
                                                                                              └──▶ Comment store (history)
```

1. Viewer opens SSE to a connection server; it registers in `room:L42:servers`
2. Commenter POSTs; API rate-limits per user, writes Kafka (key = live_id), returns 202; client echoes its own comment optimistically
3. Storage consumer writes the comment store (Cassandra / DynamoDB: partition `live_id + time bucket`, clustering by time)
4. Fan-out consumer samples / ranks to ≤20/s and batches every 500 ms
5. One PUBLISH per batch to `live:L42`; each subscribed connection server pushes the batch to its local viewers (`event: comment.batch`, `id: <batch seq>`)
6. Reconnect: `Last-Event-ID` → server sends the last few batches from a small in-memory / Redis ring buffer; no gap repair
- Failures
  - Connection server dies → clients reconnect with jitter, resume from Last-Event-ID
  - Redis subscriber too slow → output buffer limit cuts it; server resubscribes; viewers miss a few comments (acceptable)
  - Kafka consumer lag → fan-out falls behind → skip ahead to newest (lossy by design)
- Degradation: lower display cap, larger batches, hide viewer count updates
- 🗣 "Writes go through Kafka for durability and history; the live path is sampled and lossy by design, so a hot stream costs one publish per batch, not per viewer."

<a id="s7-2"></a>
### 7.2 Chat ★★★

- Numbers (example): 100M DAU, 40 messages/user/day → ~4B/day ≈ 50k/s avg, ~150k/s peak
- APIs: WebSocket `message.send` / `message.new` / `receipt.read` / `sync.request`; REST `GET /v1/chats/{id}/messages?after_seq=`

```
A ──WS──▶ ConnSrv1 ─▶ Chat API ─▶ Kafka(chat_id) ─▶ Sequencer/Store consumer ─▶ Cassandra (chat_id, bucket, seq)
                                                          └─▶ Delivery svc ─▶ Registry(Redis)
                                                                   ├─ online ─▶ ConnSrv7 ──WS──▶ B
                                                                   └─ offline ─▶ APNs/FCM ─▶ B's phone
```

1. A sends `message.send` with `client_msg_id`
2. Chat API dedups on `client_msg_id`, writes Kafka (key = chat_id)
3. The consumer owning that partition assigns `seq` (single writer), writes Cassandra, emits `message.ack` back to A via its connection server
4. Delivery service looks up B's connections: online → push `message.new`; offline → APNs / FCM hint
5. B acks delivery → "delivered"; opens → `receipt.read(up_to_seq)` → "read"
6. B reconnects → `sync.request(after_seq)` per chat → paged fetch
- Failures: consumer rebalance → new owner reloads last seq from storage before assigning; duplicate send → dedup on `client_msg_id`
- Group chat: fan-out on write below a size threshold, on read above it (5.8)

<a id="s7-3"></a>
### 7.3 Notification System ★★★

1. Business services emit CloudEvents to Kafka / SNS (via outbox)
2. Notification service: user preferences, dedup on (user, event) within a window, frequency caps, quiet hours
3. Route to queues by **channel × priority** (OTP / transactional vs marketing)
4. Channel workers call APNs / FCM / SES / Twilio; per-provider rate limits; backoff retries → DLQ
5. Invalid-token responses → delete the token
6. In-app: write the notification row; online users get an SSE badge update
- Celebrity fan-out (10M followers): a batch job pages through followers and enqueues in chunks, rate-limited, low priority
- 🗣 "Separate queues per channel and priority, so an OTP never waits behind a marketing blast."

<a id="s7-4"></a>
### 7.4 Async Control-Plane Resource API (OCI) ★★★

- APIs
  - `POST /v1/instances` (opc-retry-token) → 202 + `opc-work-request-id`
  - `GET /v1/workRequests/{id}` → status, percent, errors
1. API validates, checks idempotency token (returns the existing work request on repeat)
2. One transaction: insert resource (state `PROVISIONING`) + work-request row + **outbox** row
3. Relay publishes to a queue / Kafka
4. Worker takes the job under a lease, heartbeats to extend it, executes steps idempotently, updates work-request progress
5. Worker dies → lease expires → another worker resumes from the last completed step
6. Client polls the work request (or gets a notification / webhook)
- 🗣 "The work request is the client's source of truth; outbox makes the row and the job atomic, and leases make workers crash-safe."

<a id="s7-5"></a>
### 7.5 Distributed Job Scheduler ★★★

1. Jobs stored with `next_run_at`, bucketed by time (e.g. per minute)
2. Scheduler instances own bucket ranges (leader election / partition ownership via etcd)
3. Due jobs are enqueued to a work queue (or a delayed queue)
4. Worker takes a job under a lease with heartbeat extension
5. **Fencing token**: each lease carries an increasing token; the side-effect target rejects stale tokens, so a paused worker that wakes up can't double-run
6. At-least-once execution + idempotent jobs
- 🗣 "Leases with heartbeats for liveness, fencing tokens for safety, idempotent jobs for at-least-once delivery."

<a id="s7-6"></a>
### 7.6 Metrics Ingestion ★★

1. Agents batch points locally and send every ~10 s (gRPC / HTTP, compressed)
2. Ingest gateway authenticates, enforces per-tenant quotas, writes Kafka (key = tenant + metric series, salted for hot tenants)
3. Stream processor aggregates windows (1 min, 1 h) and writes a time-series store
4. Raw data retained short-term; downsampled data long-term
- Numbers: see 6.4.2 (10M points/s, ~1,000 partitions)

<a id="s7-7"></a>
### 7.7 Uber Location ★★

1. Driver app reports location every few seconds over WebSocket / gRPC stream
2. Location service updates a geo index (Redis GEO / in-memory quadtree); at-most-once is fine (next update replaces it)
3. During a trip, the rider receives that driver's location over WebSocket / SSE
4. Matching: REST → matching service queries nearby drivers

## 10. Interviewer Follow-Ups And Answers

| Follow-up | Answer |
|---|---|
| Why not polling? | Do the math: 1M users × every 2 s = 500k QPS, mostly empty; latency = interval |
| SSE or WebSocket? | Server-only push → SSE (HTTP, auto-reconnect, Last-Event-ID); frequent two-way → WebSocket |
| How do you scale WebSocket? | Stateless API separate from a stateful connection tier; sizing math (5.1); L4 / WS-aware LB; registry in Redis |
| A node with 50k connections dies? | Clients detect via heartbeat, reconnect with jitter, registry entries expire, resume by Last-Event-ID / last_seq |
| How do you deploy? | Rolling drain in 5–10% waves, close 1001 / SSE retry with jitter, headroom (5.5) |
| How does a message find the user? | Registry connection → server, or per-room pub/sub (5.6) |
| User offline? | Message stored first; APNs / FCM hint; client syncs by last_seq on open |
| Ordering? | Per-chat seq from a single writer; clients display by seq (6.8.2) |
| Duplicates? | At-least-once everywhere; dedup on client_msg_id / event id |
| Hot room? | Sample before Redis, one publish per batch, display cap ~20/s (5.7) |
| Slow client? | Bounded buffer; drop oldest (comments) or disconnect + resume (chat) (5.4) |
| Token expires mid-connection? | In-band refresh or forced reconnect; close 1008 on revocation (5.3) |
| Redis Pub/Sub loses messages? | It's only the live hop; durable data is in Kafka / DB; chat clients repair gaps by seq |
| Crash between DB write and publish? | Outbox in the same transaction; relay; idempotent consumers (6.5) |
| Is Kafka exactly-once enough? | Only within Kafka; external effects need idempotency keys (6.4.1) |
| Schema change? | Additive only; registry in BACKWARD mode; breaking → new version + dual write |
| Why string IDs? | 64-bit integers lose precision in JavaScript |

## 11. Failure Modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Reconnect storm | Node deploy / crash, 50k clients reconnect at once | Connection count drops then spikes, TLS CPU spikes | Client backoff + jitter; rolling drain; headroom |
| Hot-room fan-out overload | Big streamer goes live | Per-channel message rate, push latency | Sample before Redis, batch, relay tier |
| Slow consumer / client | Bad network, slow subscriber | Buffer fill, Redis output buffer disconnects | Bounded buffers, drop / disconnect policy |
| Idle-timeout drops | Heartbeat longer than LB / NAT timeout | Disconnects at a fixed interval | Heartbeat under the shortest timeout |
| Token expiry mid-connection | Long sessions | Auth failures on reconnect | In-band refresh, forced reconnect |
| Consumer lag | Downstream slows | Lag growth | Scale consumers, backpressure, degrade |
| Rebalance storm | Consumer deploy | Lag spikes during deploys | Cooperative-sticky, static membership, small batches |
| Hot partition | One key / tenant dominates | One partition's lag and bytes | Salted keys, per-tenant quotas |
| Poison message | A message always fails | Same offset retried | Retry topics → DLT / DLQ, alert |
| Duplicate delivery | At-least-once retries, relay re-publish | Duplicate rows downstream | Idempotency keys, unique constraints |
| Reordering | Retries, multiple partitions | Client seq gaps | Single-writer seq, idempotent producer |
| Lost job (dual write) | Crash between DB write and enqueue | Work request stuck in ACCEPTED | Outbox; sweeper for stuck requests |
| Schema incompatibility | Breaking producer change | Consumer deserialization errors | Registry checks, CI breaking-change gate |
| Stale push tokens | App uninstalled / device changed | Invalid-token responses | Delete tokens on response |
| Stale registry | Server died without cleanup | Deliveries to missing servers | Per-connection TTL renewed by heartbeat |
