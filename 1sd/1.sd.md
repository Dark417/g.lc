## 0. How To Use This Doc

<a id="s0-1"></a>
### 0.1 The Three Axes

- A system design answer is built on three axes; this doc is organized the same way
  - **Steps** (the interview process): requirements → estimation → API → data model → high-level design → deep dive → wrap-up
  - **Building blocks** (what you draw): nodes, edges between nodes, patterns of 3+ nodes
  - **Qualities** (what you're judged on): scalability, consistency, reliability, security, operability, cost
- Why not put everything under components?
  - Estimation, API design and data modeling are **step outputs**, not boxes on the diagram
  - Reliability and security cut **across** every box
  - Last time's feedback hit exactly these: no numbers (estimation), APIs not matching requirements (API), no data flow (HLD)

```
Section 1      Interview flow and time split
Sections 2–3   Blueprint + three-tier model (Node → Function → Implementation)
Section 4      Step modules: requirements, estimation, API, data model, HLD, deep dive, wrap-up
Sections 5–7   Building blocks: single nodes, two-node edges, three-node patterns
Section 8      Qualities: scalability, consistency, reliability, security, operations, cost
Sections 9–10  LLD / OOD and company lens
Sections 11–12 Study plan and where this fits
```

<a id="s0-2"></a>
### 0.2 How To Think About Any Part

- Same order for every node, edge, step or quality
  1. **Problem**: what it solves
  2. **Factors**: the variables that decide the choice (QPS, latency, consistency, cost, ops)
  3. **Options**: Tier 2 functions / Tier 3 implementations
  4. **Tradeoff**: what each option costs
  5. **Pick**: which one under which condition, in one sentence
- Markers: ★★★ must be able to explain, ★★ should know, ★ know the name

## 1. Interview Flow And Time Split

- Usable time is less than the slot
  - 45-min interview: intro + Q&A take ~8–10 min → ~35 min of design
  - 60-min interview: intro + Q&A take ~10–15 min → ~45–50 min of design

<a id="s1-1"></a>
### 1.1 Time Table

| Step | What to do | 45 min (~35 design) | 60 min (~47 design) | Exit check | Module |
|---|---|---|---|---|---|
| 1 Requirements | 3–5 functional + non-functional | 4 min | 5 min | Interviewer confirms | 4.1 |
| 2 Estimation | QPS, storage, bandwidth, peak | 3 min | 4 min | Each number drives a design decision | 4.2 |
| 3 API | Each API maps to a requirement | 3 min | 5 min | Every API traces back to a requirement | 4.3 |
| 4 Data model | Entities, keys, partition key, store choice | 3 min | 5 min | Access patterns stated | 4.4 |
| 5 High-level + data flow | Boxes + write path + read path | 10 min | 13 min | One-line "job" for each component | 4.5 |
| 6 Deep dive | 1–2 bottlenecks | 9 min | 12 min | Tradeoff stated and a choice made | 4.6 |
| 7 Failure + wrap-up | Failure modes, monitoring, next steps | 3 min | 3 min | 1–2 improvements named | 4.7 |

- 45-min version
  - Data model can merge into step 5, explained while drawing
  - One deep dive; take the interviewer's pick first
- 60-min version
  - Two deep dives: one on scale, one on consistency / failure
- 🗣 Opening line: "I'll spend ~5 minutes on requirements and numbers, then API and data model, then walk the write and read paths, and leave ~10 minutes for deep dives."

<a id="s1-2"></a>
### 1.2 Template Lines For Each Step

- Requirements
  - "Functional: users can X, Y, Z. Out of scope: A, B."
  - "Non-functional: p99 < N ms, availability 99.9x, consistency: eventual is OK for X, strong for Y."
- Estimation
  - "DAU 10M × 20 writes/day ≈ 200M/day ≈ 2.3k/s avg, ~5x peak ≈ 12k/s → one DB primary is not enough, so we partition."
- Data flow
  - "A write goes: client → LB → API service → Kafka → consumer → DB. The API returns after Kafka ack, so latency is bounded by one broker write."

## 2. The Big Blueprint: Nodes And Edges

```
Client
 ├─ DNS ──────────────▶ CDN  (static files, media)
 ├─ HTTPS ────────────▶ LB ─▶ API Gateway ─▶ Services
 │                                             ├─▶ Cache ─▶ DB (primary ⇄ replicas)
 │                                             ├─▶ MQ / Log ─▶ Workers / Stream processing ─▶ Object Store / Search / TSDB
 │                                             └─▶ Pub/Sub ─▶ Connection Tier
 └─ WebSocket / SSE ◀──────────────────────────────────────── Connection Tier

Cross-cutting: Identity & secrets, Coordination (etcd / ZK), Observability (metrics / logs / traces)
```

- Node = a capability (store, compute, forward, queue)
- Edge = an interaction (protocol + consistency + failure handling)
- A question = pick the few key edges and walk them end to end

<a id="s3"></a>
## 3. Three-Tier Model: Node → Function → Implementation

```
Tier 1  Node            Load Balancer
Tier 2  Function        L4 forwarding · L7 routing · health check · TLS termination
Tier 3  Implementation  AWS NLB · ALB · Envoy · NGINX · HAProxy
```

- Tier 1: what the box (or step, or quality) is called
- Tier 2: the specific jobs it does (most of the interview talk is here)
- Tier 3: what implements it
  - The same Tier 2 function can use different implementations with different tradeoffs
- Comparisons happen at two levels
  - Between Tier 2 options: e.g. L4 vs L7, cursor vs offset pagination
  - Between Tier 3 options: e.g. Kafka vs SQS vs RabbitMQ
- The same three tiers apply to step modules (section 4) and qualities (section 8)

<a id="s4"></a>
## 4. Step Modules

<a id="s4-1"></a>
### 4.1 Requirements And Scoping ★★★

- Tier 1: the first 4–5 minutes; the contract for the rest of the interview
- Problem: designing the wrong system, or a generic one
- Tier 2
  - **Functional**: 3–5 core user actions; explicitly name what's out of scope
  - **Non-functional checklist**
    - Scale: users, DAU, peak concurrency
    - Latency: p99 targets per path (read vs write)
    - Availability: 99.9 / 99.99
    - Consistency: per data type (strong for money / bookings, eventual for feeds / counts)
    - Durability: can any data be lost?
    - Security / compliance, multi-tenancy
    - Geography: single region or global
    - Cost sensitivity
  - **Clarifying question bank**
    - Read-heavy or write-heavy?
    - Realtime needed? How fresh?
    - Ordering needed? In what scope?
    - Can messages / events be lost or duplicated?
    - Retention: how long do we keep data?
    - Who are the clients: browser, mobile, other services?
- Tier 3: a written list on the whiteboard; confirm it before moving on
- 🗣 "Let me lock 3–5 functional requirements and the non-functional targets, then confirm with you before I design."

<a id="s4-2"></a>
### 4.2 Estimation ★★★

- Tier 1: the numbers that justify every design choice
- Problem: designs without numbers look generic; interviewers can't tell why you chose anything
- Tier 2: numbers to memorize (order of magnitude)

| Item | Value |
|---|---|
| Seconds per day | 86,400 ≈ 10^5 |
| 1M requests/day | ≈ 12 per second |
| 1B requests/day | ≈ 12k per second |
| Peak factor | 2–5× average |
| Memory read | ~100 ns |
| SSD random read | ~100 µs |
| Same-datacenter round trip | ~0.5 ms |
| Cross-region round trip | ~50–150 ms |
| UUID / Snowflake id | 16 B / 8 B |
| Typical row / small JSON | ~0.5–1 KB |

- Tier 2: per-box capacity (order of magnitude; depends on workload)

| Component | Rough capacity per node |
|---|---|
| Stateless API server | ~1k–10k requests/s |
| Postgres / MySQL primary | ~thousands to low tens of thousands writes/s |
| Redis | ~100k ops/s |
| Kafka partition (planning) | ~5–10 MB/s |
| WebSocket / SSE server | ~50k–100k connections |

- Tier 2: formulas
  - QPS = DAU × actions per user per day ÷ 86,400 × peak factor
  - Storage = writes per day × size × retention days × replication factor
  - Bandwidth = QPS × payload size
  - Servers = peak QPS ÷ per-server QPS, plus ~30% headroom
  - Cache size = hot set (e.g. 20% of daily read keys × value size)
  - Connections = peak concurrent users
- Rule: **every number must change a decision**
  - "12k writes/s peak → beyond one primary → partition by user_id"
  - "2 TB/year → fits a sharded relational DB; no need for a data lake"
- Worked examples: connection tier, hot-room fan-out and Kafka partitions in 2.messaging.md sections 5.1, 5.7, 6.4.2
- 🗣 "10M DAU × 20 writes is ~2.3k writes/s, ~12k at peak, which is past a single primary, so I'll partition by user_id."

<a id="s4-3"></a>
### 4.3 API Design ★★★

- Tier 1: the contract between clients and the system
- Problem: APIs that don't map to requirements (last time's feedback)
- How
  1. List each functional requirement
  2. Write one endpoint / RPC per requirement
  3. Define request and response fields
  4. Add errors, pagination, idempotency, auth
  5. Check: every requirement has an API, every API has a requirement
- Tier 2 decisions

| Decision | Options | Default |
|---|---|---|
| Style | REST / gRPC / GraphQL | REST externally, gRPC internally |
| Resource modeling | Nouns + HTTP verbs; sub-resources | `/v1/listings/{id}/bookings` |
| Pagination | Offset / cursor | Cursor (stable under inserts) |
| Retries | Idempotency key on non-idempotent writes | `Idempotency-Key` header |
| Versioning | URL / header | `/v1/`, bump only on breaking changes |
| Errors | Ad hoc / RFC 9457 problem+json | problem+json + correct status codes |
| Long-running work | Blocking / 202 + operation resource | 202 + `Location: /operations/{id}` |
| Concurrency control | Last write wins / ETag + If-Match | ETag for edits |
| Auth | API key / OAuth2 bearer / mTLS | OAuth2 scopes for users, mTLS for services |
| Rate limits | — | 429 + `Retry-After` |
| Push | Polling / SSE / WebSocket / webhook | See 2.messaging.md |

- Tier 3: OpenAPI, protobuf / gRPC, GraphQL SDL; Spring MVC / WebFlux
- Schemas and real payloads for every style: 2.messaging.md sections 3–4
- 🗣 "Each requirement maps to one endpoint; writes take an idempotency key and long operations return 202 with an operation id."

<a id="s4-4"></a>
### 4.4 Data Modeling And Persistence ★★★

- Tier 1: what you store, where, and how it's keyed
- Plain idea: **start from access patterns, not entities**
- Problem: picking a database by habit, then discovering the main query needs a full scan or a hot partition
- How
  1. List entities (User, Listing, Booking, Message)
  2. List access patterns with rates ("get bookings by listing and date range, 5k/s")
  3. Pick a store per pattern (decision table below)
  4. Choose primary key and partition key
  5. Add indexes for the remaining patterns
  6. Decide consistency and transaction boundaries
  7. Decide retention and archival
- Tier 2: store choice

| Store type | Pick when | Examples |
|---|---|---|
| Relational | Transactions, relations, flexible queries, moderate scale | Postgres, MySQL, Aurora |
| Key-value | Lookups by key, huge scale, simple access | DynamoDB, Redis |
| Wide-column | High writes, time-ordered per key (messages, events) | Cassandra, Bigtable |
| Document | Flexible nested records, changing schema | MongoDB |
| Search | Full-text, fuzzy, faceted filters | Elasticsearch / OpenSearch |
| Time-series | Metrics, downsampling, range by time | Prometheus, InfluxDB, TimescaleDB |
| Object storage | Large blobs (images, video, backups) | S3, OCI Object Storage |
| Graph | Multi-hop relationships | Neo4j (rare in interviews) |
| Cache | Hot reads, counters, leaderboards | Redis, Memcached |

- Tier 2: keys and partitioning
  - Partition key = **spread** (avoid hotspots) + **locality** (one query hits one partition)
  - Time-only keys are hot (all writes hit "now"); combine with an entity id or bucket
  - Composite keys: `(chat_id, time_bucket)` partition + `seq` clustering
  - Secondary indexes cost writes; global indexes are eventually consistent in many NoSQL stores
- Tier 2: normalization vs denormalization
  - Normalize for writes and correctness (relational default)
  - Denormalize for read speed (copy fields, precomputed views); accept update fan-out
- Tier 2: transactions and isolation

| Isolation | Prevents | Still allows |
|---|---|---|
| Read committed | Dirty reads | Lost updates, write skew |
| Repeatable read / snapshot | Non-repeatable reads | Write skew |
| Serializable | All anomalies | Higher latency, retries |

- Tier 2: concurrency control
  - Optimistic: version column / ETag, retry on conflict (low contention)
  - Pessimistic: `SELECT ... FOR UPDATE` (high contention, short transactions)
  - Constraints as guards: unique `(listing_id, date)` makes double booking impossible
- Tier 2: schema evolution and lifecycle
  - Expand → migrate → contract (never a breaking change in one step)
  - TTL for temporary data; hot / cold tiering; archive to object storage
- Tier 3: see the store table above; deep detail in 3.persistence.md
- Example: booking without double booking

```sql
CREATE TABLE listing_night (
  listing_id  BIGINT,
  night       DATE,
  booking_id  BIGINT,          -- null = available
  hold_until  TIMESTAMPTZ,     -- temporary hold during checkout
  version     INT,
  PRIMARY KEY (listing_id, night)
);
-- Reserve: UPDATE ... SET booking_id = ?, version = version + 1
--          WHERE listing_id = ? AND night BETWEEN ? AND ? AND booking_id IS NULL
-- Success only if every night in the range was updated, inside one transaction
```

- 🗣 "I model from access patterns: bookings are read by listing and date range, so the key is (listing_id, night), and a conditional update makes double booking impossible."

<a id="s4-5"></a>
### 4.5 High-Level Design And Data Flow ★★★

- Tier 1: the diagram plus the story of a request
- Problem: boxes without a narrative (last time's feedback)
- How
  1. Draw left to right: client → edge (DNS / CDN / LB / gateway) → services → storage / async
  2. Walk the **write path** hop by hop
  3. Walk the **read path** hop by hop
  4. For each box, one sentence: its job, and why this question needs it
  5. Name the pattern you're using (section 7)
- Tier 2: things to state while drawing
  - Sync vs async boundary (where the client stops waiting)
  - Where state lives (stateless services, stateful stores)
  - Where consistency is strong vs eventual
- 🗣 "Let me walk a write end to end, then a read, and say why each box is here."

<a id="s4-6"></a>
### 4.6 Deep Dive Selection ★★

- Tier 1: the 1–2 places where the design is hardest
- Pick by numbers, not by comfort
  - Highest QPS or fan-out → scaling deep dive (sharding, caching, fan-out)
  - Money / inventory / bookings → consistency deep dive (transactions, idempotency)
  - Long-lived connections → connection tier deep dive (2.messaging.md section 5)
  - Many tenants → isolation and quotas deep dive (8.4)
- Typical deep dives by question type

| Question type | Usual deep dive |
|---|---|
| Realtime (chat, live comments) | Fan-out, connection tier, ordering |
| Booking / payments | Concurrency control, idempotency, saga |
| Feed / social | Fan-out on write vs read, ranking cache |
| Ingestion / analytics | Partitioning, windowed aggregation, late data |
| Control plane / scheduler | Async workflow, leases, outbox |
| Read-heavy (URL shortener) | ID generation, caching, hot keys |

- 🗣 "The hardest part here is X because of these numbers; I'll go deep there."

<a id="s4-7"></a>
### 4.7 Failure Modes And Wrap-Up ★★

- Tier 1: the last 3 minutes
- Tier 2
  - Walk 2–3 failures: a node dies, a dependency is slow, a region fails
  - Monitoring: the 3–4 metrics that would page you
  - Evolution: what you'd change at 10× scale or with more time
- 🗣 "If the cache cluster dies we degrade to the DB with rate limiting; I'd alert on p99 latency and consumer lag; at 10× I'd shard the X table."

<a id="s5"></a>
## 5. Single Nodes

<a id="s5-1"></a>
### 5.1 DNS / GSLB ★★

- Problem: send users to the nearest healthy region
- Factors: user geography, failover speed, TTL
- Tier 2
  - Name resolution
  - Geo / latency routing: pick region by location
  - Health-based failover
  - Weighted routing: canary, migrations
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Route 53 / OCI DNS | Managed, built-in health checks | Bound by TTL, failover is slow (minutes) | Default |
| Anycast (Cloudflare) | Nearest at the network layer, fast failover | Needs own network / vendor | Global low-latency entry |

- The catch: clients cache DNS; shorter TTL means faster failover but more queries
- 🗣 "DNS gets users to a region; LBs handle failures inside the region."

<a id="s5-2"></a>
### 5.2 CDN ★★★

- Problem: static / large content is far from users; origin can't take the read traffic
- Factors: cacheability, update frequency, hit rate, private content
- Tier 2
  - Edge cache: serve nearby
  - Pull vs push: fetch from origin on miss vs pre-warm
  - Invalidation: purge or versioned URLs
  - Signed URLs: protect private content
  - TLS termination, DDoS absorption
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| CloudFront / OCI CDN | Integrates with object storage | Cloud lock-in | Default |
| Cloudflare / Akamai | Many PoPs, strong security | Cost, config complexity | Global, high traffic |

- Pull vs push
  - Pull: simple; first request is slow (cold)
  - Push: hot content in place ahead of time; you manage storage and expiry
- 🗣 "Use versioned URLs instead of purges; purges are slow and eventually consistent."

<a id="s5-3"></a>
### 5.3 Load Balancer ★★★

- Problem: spread requests across machines and drop broken ones
- Factors: protocol (TCP/HTTP), content-based routing needed, connection count, long-lived connections
- Tier 2
  - L4 forwarding: by IP/port, fast, doesn't read content
  - L7 routing: by path / header / cookie
  - Health checks: remove bad nodes
  - Algorithms: round robin, least connections, consistent hashing (stickiness)
  - TLS termination
- Tier 2 comparison

| Function | Good | Cost | Choose when |
|---|---|---|---|
| L4 | Low latency, good for long-lived connections (WebSocket) | Can't route by URL | Connection tier, non-HTTP |
| L7 | Smart routing, can do auth | Parses every request, a bit more latency | Default for HTTP services |

- Tier 3: AWS NLB (L4) · ALB (L7) · Envoy · NGINX · HAProxy
- 🗣 "L4 for WebSocket fleets, L7 for HTTP APIs."

<a id="s5-4"></a>
### 5.4 API Gateway ★★★

- Problem: one entry point for all external requests, handling cross-cutting concerns
- Factors: auth method, rate-limit granularity, multi-tenancy, protocol translation
- Tier 2
  - Authentication / authorization (JWT, OAuth)
  - Rate limiting / quota (per user / per tenant)
  - Routing / versioning
  - Request validation, protocol translation (REST → gRPC)
  - Aggregation (BFF)
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| AWS API Gateway / OCI API GW | Managed, zero ops | Latency and cost grow with calls, many limits | Small–medium traffic, fast launch |
| Kong / Envoy-based | Self-hosted, many plugins | You run it | High traffic, custom needs |
| Spring Cloud Gateway | Java ecosystem, easy to customize | You own performance | Java-heavy team |

- The catch: the gateway is a single point and a hotspot; keep it stateless and horizontally scaled
- 🗣 "The gateway owns auth and rate limiting, so services stay focused on business logic."

<a id="s5-5"></a>
### 5.5 Realtime Connection Tier ★★★

- Problem: the server must push messages to clients (chat, live comments, notifications)
- Factors: concurrent connections, message rate, one-way vs two-way, mobile battery
- Tier 2
  - Hold long-lived connections (WebSocket / SSE)
  - Connection registry: connection → server
  - Fan-out: one message to N connections
  - Heartbeats, reconnects, offline catch-up
  - Draining on deploy, backpressure for slow clients
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Netty / Spring WebFlux (self-built) | Full control, many connections per box | You handle scaling and state | Large-scale core feature |
| Socket.IO | Auto fallback, rooms | Node ecosystem, scaling needs Redis adapter | Fast development |
| AWS API GW WebSocket / AppSync | Managed | High unit price, 2 h connection cap | Small–medium scale |

- 🗣 "Connection servers are stateful; I keep them thin and put routing state in Redis."
- Full detail: 2.messaging.md section 5

<a id="s5-6"></a>
### 5.6 Service Tier (Compute) ★★

- Problem: run business logic and scale horizontally
- Factors: bursty traffic, cold-start tolerance, team ops capacity
- Tier 2
  - Stateless processing (state lives in cache / DB)
  - Autoscaling
  - Service discovery
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Kubernetes (OKE / EKS) | Flexible, biggest ecosystem | Ops complexity | Many long-running services |
| ECS / managed containers | Simple | Less flexible | Medium scale |
| Lambda / OCI Functions | Pay per call, zero ops | Cold starts, time limits | Bursty, event-driven |

- 🗣 "Stateless services let me scale by adding instances behind the LB."

<a id="s5-7"></a>
### 5.7 Cache ★★★

- Problem: DB reads are slow / expensive; hot data is read repeatedly
- Factors: read:write ratio, acceptable staleness, data size, hit rate
- Tier 2
  - Key-value get/set, TTL
  - Eviction: LRU / LFU
  - Data structures: sorted set (leaderboards), counters (rate limits), pub/sub
  - Distribution: sharding (consistent hashing), replication
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Redis | Rich data structures, optional persistence, pub/sub | Single-threaded command execution, big keys are risky | Default |
| Memcached | Multi-threaded, simple KV | No persistence, no data structures | Plain large KV cache only |
| Local cache (Caffeine) | Fastest, no network | Inconsistent across instances | Very hot, staleness OK |

- The catch: invalidation and consistency are the hard part (see 6.5)
- 🗣 "Cache is for latency and DB offload, never the source of truth."

<a id="s5-8"></a>
### 5.8 Relational DB ★★★

- Problem: need transactions, relations, complex queries
- Factors: ACID needed, write QPS, data size, joins
- Tier 2
  - ACID transactions, isolation levels (4.4), indexes, joins
  - Replication: primary + read replicas
  - Sharding: split by key
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| PostgreSQL / MySQL | Mature, general purpose | Single-primary write ceiling | Default |
| Aurora / OCI MySQL HeatWave | Managed, storage auto-grows | Cloud lock-in | Default on cloud |
| Spanner / CockroachDB | Global strong consistency + auto sharding | Higher write latency, cost | Cross-region strong consistency |

- 🗣 "I start with Postgres; I shard only when write QPS or data size forces it."

<a id="s5-9"></a>
### 5.9 NoSQL ★★★

- Problem: huge data, high writes, simple access patterns (by key)
- Factors: are access patterns fixed, consistency needs, write QPS
- Tier 2 (by type)
  - KV: read/write by key
  - Wide-column: partition key + clustering key; good for time series, messages
  - Document: flexible schema
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| DynamoDB / OCI NoSQL | Managed, auto-scaling | Design access patterns up front; hot partitions | KV, predictable access |
| Cassandra | High writes, multi-region | Ops-heavy, eventual consistency | Write-heavy, time series, messages |
| MongoDB | Flexible schema | Large-scale sharding is hard to tune | Documents, changing requirements |

- 🗣 "Wide-column with (chat_id, time_bucket) as partition and seq as clustering key gives ordered history per chat."

<a id="s5-10"></a>
### 5.10 Message Queue / Log ★★★

- Problem: decouple producers and consumers, absorb spikes, async work, many consumers of one stream
- Factors: ordering, replay, throughput, delivery semantics
- Tier 2
  - Queue: each message to one consumer (task distribution)
  - Pub/Sub: each message to all subscribers
  - Log / stream: durable + replayable + ordered within a partition
  - Delivery semantics: at-most-once / at-least-once / effectively-once
  - DLQ, retries, delayed messages
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Kafka / OCI Streaming | High throughput, replay, per-partition order | Ops and tuning heavy | Event streams, ingestion |
| SQS / OCI Queue | Managed, simple, auto-scaling | No replay; FIFO parallelism = message groups | Task queues |
| RabbitMQ | Flexible routing, low latency | Lower throughput than Kafka | Complex routing |
| Redis Pub/Sub / Streams | Very low latency | Weak durability (Pub/Sub) | Realtime fan-out |

- 🗣 "Kafka keeps order within a partition, not across partitions, so I pick the partition key by what must stay ordered."
- Full detail: 2.messaging.md section 6

<a id="s5-11"></a>
### 5.11 Object Storage ★★

- Problem: store large files (images, video, backups) cheaply and durably
- Factors: file size, access frequency, durability needs
- Tier 2
  - PUT/GET whole objects by key
  - Multipart upload, presigned URLs
  - Lifecycle: hot/cold tiers
- Tier 3: S3 / OCI Object Storage / GCS (roughly equivalent)
- The catch: no in-place edits; higher latency than KV
- 🗣 "Metadata in a DB, bytes in object storage."

<a id="s5-12"></a>
### 5.12 Search Index ★★

- Problem: full-text search, fuzzy match, multi-field filters, geo filters
- Factors: tolerance for index lag, query complexity
- Tier 2
  - Inverted index
  - Relevance ranking, aggregations
  - Geo queries (geohash / geo-point filters)
- Tier 3: Elasticsearch / OpenSearch (default) · Solr
- The catch: not the source of truth; synced via CDC, so it lags
- 🗣 "Search is a derived view, fed from the DB through CDC."

<a id="s5-13"></a>
### 5.13 Workers / Scheduler ★★

- Problem: long tasks, scheduled tasks, batch jobs
- Factors: task duration, timing precision, retries and idempotency
- Tier 2
  - Pull tasks from a queue under a lease, retry, timeout
  - Time-based triggers
  - Distributed scheduling: each task runs on one worker at a time (leases + fencing)
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Queue + worker pool | Simple | Weak scheduling | Async tasks |
| Airflow | DAG dependencies, UI | Not for low latency | Data pipelines |
| Temporal | Long workflows, auto retries, durable state | Learning curve | Business workflows |
| Quartz / cron + lock | Simple scheduling | You handle the single point | Small-scale scheduling |

<a id="s5-14"></a>
### 5.14 Coordination ★★

- Problem: nodes need to agree on "who is leader / what is the config"
- Tier 2: leader election, distributed locks, config storage, service registry
- Tier 3: etcd · ZooKeeper · Consul (all built on Raft / ZAB-style consensus)
- The catch: low write throughput; store only small, critical metadata
- 🗣 "I use etcd for leader election with a lease, plus fencing tokens so a stale leader can't write."

<a id="s5-15"></a>
### 5.15 Observability ★★

- Problem: know whether the system is healthy and where it broke
- Tier 2: metrics, logs, traces, alerting
- Tier 3: Prometheus + Grafana · ELK / OpenSearch · OpenTelemetry + Jaeger · Datadog · OCI Monitoring / Logging
- 🗣 "I alert on SLO burn rate, not on every error."

<a id="s5-16"></a>
### 5.16 Stream Processing ★★

- Problem: compute continuously over an unbounded event stream (counts per minute, trending, fraud signals)
- Factors: latency target, correctness under late or duplicate events, state size
- Tier 2
  - Windowing: tumbling (fixed), sliding (overlapping), session (gap-based)
  - Event time vs processing time; **watermarks** decide when a window is complete
  - Late data: allowed lateness, side output, or correction later
  - State + checkpointing: recover after failure without double counting
  - Exactly-once sinks: transactional or idempotent writes
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| Apache Flink | True streaming, strong state + event time | Ops complexity | Low-latency aggregation |
| Spark Structured Streaming | Micro-batch, same API as batch | Higher latency | Already on Spark / Databricks |
| Kafka Streams | Library, no cluster | JVM only, tied to Kafka | Simple per-service processing |
| Kinesis Data Analytics / managed Flink | Managed | Cloud lock-in | AWS shops |

- 🗣 "Flink with event-time tumbling windows and watermarks; late events go to a correction path."

<a id="s5-17"></a>
### 5.17 Identity, Secrets And Keys ★★

- Problem: who is calling, what they may do, and how secrets and data keys are protected
- Tier 2
  - Authentication: users via OIDC / OAuth2; services via mTLS or workload identity
  - Token issuance: short-lived JWT access tokens + refresh tokens
  - Authorization: RBAC / ABAC policies, policy evaluation per request
  - Secrets storage and rotation (DB passwords, API keys)
  - Key management: KMS with envelope encryption (data key encrypted by a master key, often HSM-backed)
  - Certificates: issuance, rotation, revocation (PKI)
- Tier 3: OCI IAM / Vault / KMS, AWS IAM / KMS / Secrets Manager, HashiCorp Vault, Keycloak, OPA
- 🗣 "Short-lived tokens, policy checks at the gateway and service, and envelope encryption with keys in KMS."

## 6. Two-Node Edges

<a id="s6-1"></a>
### 6.1 Client ↔ Gateway: Protocols ★★★

- Problem: how client and server exchange data
- Factors: who initiates, frequency, one-way vs two-way, browser / mobile, proxy traversal
- Tier 2

| Protocol | Direction | Good | Cost | Choose when |
|---|---|---|---|---|
| REST / HTTP | Client pulls | Simple, cache-friendly | Over-fetching, many round trips | Default CRUD |
| GraphQL | Client pulls | Fetch exactly the fields needed | Hard to cache, heavy queries hurt backend | Many clients, changing fields |
| gRPC (HTTP/2) | Optional bidi stream | Efficient binary, strongly typed | Poor browser support | Service-to-service, mobile |
| Short polling | Client pulls | Simplest | Wasted requests, latency = interval | Low frequency, latency OK |
| Long polling | Client pulls | Cheaper than short polling | Reconnect per message | Fallback when WebSocket isn't possible |
| SSE | Server pushes (one-way) | Plain HTTP, auto reconnect | One direction only | Live comments, notifications, tickers |
| WebSocket | Two-way | Low latency, full duplex | Stateful connections, harder to scale | Chat, collaboration, games |
| WebRTC | Peer-to-peer | Lowest A/V latency | Needs STUN/TURN, complex | Video calls |

- Last time's mistake: client polling for live comments → should be SSE
- Tier 3: Spring MVC / WebFlux, grpc-java, Netty, Spring WebSocket / STOMP, Socket.IO
- 🗣 "Reads dominate and only the server pushes, so SSE is enough; WebSocket if clients also send frequently."
- Full detail incl. schemas and payloads: 2.messaging.md section 4

<a id="s6-2"></a>
### 6.2 Client ↔ CDN ★★

- Problem: serve static and media content close to users
- Tier 2: cache key design; TTL and versioned URLs; signed URLs / cookies; Range requests
- Tier 3: CloudFront / OCI CDN / Cloudflare (see 5.2)
- 🗣 "Video segments are immutable, so they cache forever with versioned names."

<a id="s6-3"></a>
### 6.3 Gateway ↔ Services: Sync Calls ★★★

- Problem: route incoming requests to the right backend
- Factors: latency budget, number of services, fault isolation
- Tier 2
  - Service discovery
  - Load balancing: client-side vs server-side
  - Timeouts, retries, circuit breakers
  - mTLS
- Tier 3

| Implementation | Good | Cost | Choose when |
|---|---|---|---|
| K8s Service + DNS | Built in, simple | Limited features | Default |
| Service mesh (Istio / Linkerd) | Uniform retries, mTLS, observability | Complexity, sidecar overhead | Many services, strict security |
| Client library (Resilience4j) | Fine-grained control | Re-implement per language | Java services |

- The catch: retries amplify traffic → backoff + jitter + retry budget are mandatory
- 🗣 "Timeouts on every hop, retries only on idempotent calls, with exponential backoff and jitter."

<a id="s6-4"></a>
### 6.4 Service ↔ Service: Async ★★★

- Problem: the caller doesn't want to wait, or the downstream is slow / down
- Tier 2: point-to-point queue, pub/sub, event log, request-reply over queue
- Tier 3: Kafka · SQS/SNS · RabbitMQ (see 5.10)
- 🗣 "At-least-once delivery plus an idempotency key gives effectively-once processing."
- Full detail: 2.messaging.md section 6

<a id="s6-5"></a>
### 6.5 Service ↔ Cache ↔ DB ★★★

- Problem: fast reads without serving data that's too stale
- Factors: read:write ratio, acceptable inconsistency window, write frequency
- Tier 2

| Strategy | How | Good | Cost | Choose when |
|---|---|---|---|---|
| Cache-aside | On miss read DB and fill; on write update DB then delete cache | Simple, caches only hot data | First-read miss; brief inconsistency | Default |
| Read-through | Cache fetches from DB itself | Simpler app code | Cache must support it | Managed solutions |
| Write-through | Write cache and DB synchronously | Fresh reads | Write latency doubles | Read-heavy, freshness matters |
| Write-behind | Write cache, flush to DB async | Very fast writes | Data loss if cache dies | Counters, loss tolerable |

- Common problems and fixes
  - Thundering herd → single-flight lock / early refresh
  - Cache penetration → cache nulls / Bloom filter
  - Cache delete fails → short TTL as a backstop
- 🗣 "Cache-aside with delete-on-write and a short TTL as a safety net."

<a id="s6-6"></a>
### 6.6 DB ↔ DB: Replication And Sharding ★★★

- Problem: one DB can't handle the reads / writes / data size, or needs high availability
- Tier 2: replication

| Style | Good | Cost | Choose when |
|---|---|---|---|
| Leader-follower async | Fast writes, read scaling | Stale replica reads; failover can lose data | Default |
| Leader-follower sync | No data loss | Higher write latency | Finance, metadata |
| Multi-leader | Writes in multiple regions | Complex conflict resolution | Cross-region writes |
| Leaderless quorum (W+R>N) | High availability, tunable consistency | Read repair, conflicts | Cassandra / Dynamo-style |

- Tier 2: sharding
  - Range: easy range queries, prone to hotspots
  - Hash: even spread, hard range queries
  - Consistent hashing: scaling moves only a small share of data
  - Resharding: double-write + backfill, or virtual shards mapped to physical nodes
- Tier 3: Postgres streaming replication · Vitess · Cassandra · Spanner
- 🗣 "3 replicas, W=2, R=2: one node dies, quorum still holds and reads see the latest write."

<a id="s6-7"></a>
### 6.7 DB → Queue: Outbox / CDC ★★★

- Problem: write the DB and publish a message, and keep them consistent (the dual-write problem)
- Tier 2: dual write (avoid), transactional outbox (default), CDC, change streams
- Tier 3: Debezium · DynamoDB Streams · OCI GoldenGate
- 🗣 "I never dual-write; outbox in the same transaction, then relay to Kafka."
- Full detail: 2.messaging.md section 6.5

<a id="s6-8"></a>
### 6.8 Client ↔ Object Storage ★★

- Problem: large uploads / downloads shouldn't go through app servers
- Tier 2: presigned URL; multipart / resumable upload; upload-complete event triggers processing
- Tier 3: S3 / OCI Object Storage + event notifications
- 🗣 "The API only issues a presigned URL; bytes go straight to object storage."

<a id="s6-9"></a>
### 6.9 Producer → Queue → Consumer ★★★

- Problem: producers outpace consumers; consumers fail
- Tier 2: backpressure; retry + backoff; DLQ; idempotent consumers; consumer parallelism (Kafka = partitions, SQS = consumers)
- 🗣 "Consumer lag is my main scaling signal."

<a id="s7"></a>
## 7. Three-Node Patterns

- Each pattern = the standard answer to a common problem
- Recognize the problem first, then apply the pattern

| # | Pattern | Node chain | Problem solved | Key tradeoff | Used in |
|---|---|---|---|---|---|
| 1 | Realtime fan-out | Service → Pub/Sub → Connection servers → Clients | Push one message to many online users | Hot-room fan-out → sampling / relay tier | Live comments, chat, notifications |
| 2 | Read-heavy | LB → Service → Cache → DB | Many reads, few writes, low latency | Freshness vs hit rate | URL shortener, product pages |
| 3 | Write-heavy ingestion | Gateway → Log → Stream processor → Store | High writes, downstream can lag | Latency vs throughput, at-least-once | Metrics, logs, click counting |
| 4 | Async job | API → Queue → Worker → Status store | Long tasks can't block the request | Client must poll for status | OCI control plane, video transcoding |
| 5 | Derived view | DB → CDC → Search / Cache | Multiple query shapes | Sync lag | Search, recommendations |
| 6 | Rate limit | Gateway → Redis counter | Protect backend, fairness | Accuracy vs performance | Rate limiter |
| 7 | Media pipeline | Client → Object store → Queue → Transcoder → CDN | Process and distribute large files | Cost vs processing speed | YouTube, Instagram |
| 8 | Leader-based work | Scheduler(s) → etcd lease → Workers | Each task runs once | Leader election delay | Distributed scheduler |
| 9 | Reservation / hold | API → DB conditional update + TTL hold → Payment saga | No double booking, no oversell | Hold length vs abandoned carts | Airbnb booking, tickets, flash sale |
| 10 | Feed fan-out | Write → fan-out workers → per-user feed cache; or read-time merge | Personalized feeds at scale | Write cost vs read latency; celebrities | News feed, Instagram, Twitter |
| 11 | Control plane / data plane | API → control-plane DB → config push → data-plane cells | Change config safely; keep serving if control plane fails | Propagation delay vs blast radius | OCI services, LB, DNS, gateways |

<a id="s7-1"></a>
### 7.1 Example: Realtime Fan-Out ★★★

- Problem: a live stream with 1M viewers watching comments
- Design
  1. Client connects to a connection server via SSE
  2. Post comment: API → Kafka (partitioned by live_id)
  3. Fan-out service samples to ~20/s, batches every 500 ms, publishes once to Redis `live:{id}`
  4. Each subscribed connection server pushes the batch to its local viewers
- 🗣 "One publish per batch; Redis delivers it to each subscribed server, and each server pushes to its local viewers."
- Full worked math: 2.messaging.md sections 5.7 and 7.1

<a id="s7-2"></a>
### 7.2 Example: Reservation / Hold ★★★

- Problem: two guests try to book the same listing for overlapping nights
- Design
  1. Guest selects dates → API places a **hold**: conditional update of `listing_night` rows where `booking_id IS NULL` and no active hold, setting `hold_until = now + 10 min`
  2. All nights must succeed in one transaction, otherwise roll back → "dates no longer available"
  3. Payment runs (saga: authorize → confirm booking → capture)
  4. On success, set `booking_id`; on failure or timeout, the hold expires and the nights free up
  5. Idempotency key on the booking request so a retry doesn't create a second booking
- 🗣 "A short hold with a conditional update guarantees no double booking; payment runs as a saga and an expired hold releases the nights."

<a id="s7-3"></a>
### 7.3 Example: Control Plane / Data Plane ★★

- Problem: an OCI-style service must keep serving even if its management API is down
- Design
  1. Control plane: API + DB + workflow (async work requests) for create / update / delete
  2. Changes are versioned and pushed to data-plane cells in stages (canary cell first)
  3. Data plane serves traffic from its last known good config; it never calls the control plane on the hot path
  4. Cells limit blast radius: one cell's failure affects only its tenants
- 🗣 "The data plane keeps serving on last known good config; the control plane rolls changes out cell by cell."

<a id="s8"></a>
## 8. Qualities (Cross-Cutting)

<a id="s8-1"></a>
### 8.1 Scalability ★★★

- Tier 1: handle more load by adding resources, not rewriting
- Tier 2: levers, in the order to reach for them

| Lever | What it buys | Where it breaks |
|---|---|---|
| Vertical scaling | Simple, no code change | Hardware ceiling, single point |
| Stateless horizontal scaling | Linear compute scaling | State must live elsewhere |
| Caching | Read latency, DB offload | Staleness, invalidation |
| Read replicas | Read throughput | Replica lag |
| Async / queues | Absorb spikes, decouple | Eventual consistency, ops |
| CDN | Global read offload | Only for cacheable content |
| Denormalization / precompute | Fast reads | Write fan-out, update cost |
| Sharding / partitioning | Write throughput, data size | Cross-shard queries, hot keys, resharding |

- Tier 3: see nodes in section 5
- 🗣 "I scale reads with cache and replicas first, and only shard when writes or data size force it."

<a id="s8-2"></a>
### 8.2 Consistency And Transactions ★★★

- Tier 1: what readers are guaranteed to see, and how multi-step changes stay correct
- Tier 2
  - CAP: during a network partition, choose consistency or availability
  - PACELC: without a partition, choose latency or consistency
  - Consistency models

| Model | Guarantee | Example use |
|---|---|---|
| Linearizable / strong | Every read sees the latest write | Bookings, balances, leader election |
| Read-your-writes | A user sees their own writes | Profile edits, posting a comment |
| Monotonic reads | Never go back in time | Timelines |
| Causal | Effects after causes | Comment replies |
| Eventual | Converges eventually | Like counts, feeds, search index |

  - Read-your-writes techniques: read from the leader after a write, session token with a version, sticky routing
  - Multi-service changes
    - 2PC: atomic but blocking; rare across services
    - Saga: local transactions + compensation (default for business flows)
    - Outbox: atomic DB write + event
  - Idempotency everywhere retries exist
  - Consensus (Raft / Paxos) for small critical metadata, not for bulk data
  - Clocks: never order events by wall clock across machines; use sequence numbers, logical clocks, or hybrid logical clocks (Spanner uses TrueTime)
- Tier 3: Postgres serializable, Spanner, etcd, Temporal (sagas), Debezium (outbox / CDC)
- 🗣 "Strong consistency only where money or inventory is involved; everything else is eventual with read-your-writes for the author."

<a id="s8-3"></a>
### 8.3 Reliability And Multi-Region ★★★

- Tier 1: keep serving through failures, and recover fast when you can't
- Tier 2
  - Targets: SLI (what you measure), SLO (target, e.g. 99.9%), error budget (allowed failure)
  - Redundancy: N+1 capacity, multi-AZ by default
  - Failure domains (OCI): region → availability domain → fault domain
  - Multi-region modes

| Mode | RPO / RTO | Cost | Choose when |
|---|---|---|---|
| Backup + restore | Hours / hours | Lowest | Non-critical |
| Active-passive (warm standby) | Seconds–minutes / minutes | Medium | Most services |
| Active-active | ~0 / ~0 for reads | Highest; write conflicts | Global, latency-sensitive |

  - Cell-based architecture: independent copies of the stack, each serving a subset of tenants; limits blast radius
  - Bulkheads: separate pools so one dependency can't exhaust everything
  - Timeouts, retries with jitter, circuit breakers (6.3)
  - Load shedding: reject low-priority work first under overload
  - Graceful degradation: serve stale cache, disable non-core features
  - Backups tested by restores; DR drills; chaos testing
- Tier 3: Route 53 / OCI DNS failover, Aurora Global DB, Spanner, cross-region Kafka replication (MirrorMaker), Chaos tools
- 🗣 "Multi-AZ by default, cell-based to cap blast radius, and active-passive across regions with a stated RPO and RTO."

<a id="s8-4"></a>
### 8.4 Security And Multi-Tenancy ★★

- Tier 1: protect data and keep tenants isolated from each other
- Tier 2: security
  - AuthN / AuthZ (5.17); least privilege
  - Encryption in transit (TLS, mTLS internally) and at rest (KMS envelope encryption)
  - Secrets never in code; rotated
  - Input validation, output encoding
  - Abuse: rate limits, WAF, DDoS protection, bot detection
  - Audit logs for sensitive actions
  - PII handling: minimize, encrypt, retention limits
- Tier 2: multi-tenancy models

| Model | How | Good | Cost |
|---|---|---|---|
| Silo | Separate stack / DB per tenant | Strongest isolation | Expensive, many deployments |
| Pool | Shared stack, tenant_id in every row / key | Cheap, efficient | Noisy neighbors, careful authZ |
| Bridge / cell | Groups of tenants per cell | Balance of both | Placement and migration logic |

  - Tenant id in every key and every query; enforce in the data access layer
  - Per-tenant quotas and rate limits (noisy neighbor)
  - Optional per-tenant encryption keys
- Tier 3: OCI IAM compartments / policies, AWS IAM, Vault, WAF, OPA
- 🗣 "Pooled by default with tenant_id in every key and per-tenant quotas; large tenants get their own cell."

<a id="s8-5"></a>
### 8.5 Observability And Operations ★★

- Tier 1: know the system is healthy and change it safely
- Tier 2
  - Golden signals: latency, traffic, errors, saturation
  - Traces across services; structured logs with trace ids
  - Alerts on SLO burn rate
  - Deploy strategies: rolling, blue/green, canary, feature flags
  - Config changes rolled out in stages like code
  - Runbooks, on-call, capacity planning
- Tier 3: Prometheus, Grafana, OpenTelemetry, Datadog, OCI Monitoring; Argo Rollouts, LaunchDarkly
- 🗣 "Canary every deploy and every config change, watch SLO burn, and auto-roll back."

<a id="s8-6"></a>
### 8.6 Cost ★

- Tier 1: say at least one cost tradeoff per design
- Tier 2
  - Main drivers: egress bandwidth, storage, compute, per-request managed-service pricing
  - Levers: storage tiering, caching, batching, compression, sampling, reserved capacity
- 🗣 "Egress dominates this design, so the CDN and batching matter more than server count."

## 9. LLD / OOD ★★

- Tier 1: a separate round at some companies (often Microsoft, sometimes Amazon, Oracle Health)
- Problem: designing classes and interfaces for a bounded problem, often with some code
- How
  1. Clarify use cases and scope
  2. Identify entities → classes
  3. Define relationships (has-a, is-a) and interfaces
  4. Define key methods and state
  5. Apply patterns where they fit
  6. Handle concurrency (locks, thread-safe structures)
  7. Show extensibility (a new type without changing old code)
- Tier 2: principles and patterns
  - SOLID; composition over inheritance
  - Strategy, Factory, Observer, State, Builder, Decorator; Singleton with caution
- Tier 2: classic problems
  - Parking lot, elevator, LRU cache, rate limiter, vending machine, library system, file system, logger, pub-sub, chess / tic-tac-toe
- Tier 3: Java 17 (interfaces, records, enums, `ConcurrentHashMap`, `ReentrantLock`)
- 🗣 "I'll define the interfaces first, keep each class to one responsibility, and use Strategy so new pricing rules don't change existing code."
- Deep doc: 6.lld.md
