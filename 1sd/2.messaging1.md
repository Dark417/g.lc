## 0. One-minute version

- 消息只有两大类
  - **C↔S**：用户设备和后端之间
  - **S↔S**：后端服务之间
  - 两个边角：C↔C（WebRTC，仍靠服务器做 signaling）、S→外部（webhook）
- C↔S 先问一句：**谁先说话？**
  - 客户端要 → request/response
  - 服务端要主动推 → 在线用 SSE / WebSocket，离线用 APNs / FCM
- S↔S 先问一句：**调用方要不要等结果？**
  - 要等 → REST / gRPC
  - 不等 → queue（给一个人）/ pub-sub（给很多人）/ log（还要能重放）
- 每种方式都有两层格式
  - **传输格式**：协议本身定的（HTTP 报文、SSE 字段、WebSocket 帧、Kafka record）
  - **业务 schema**：你自己定的 payload 结构（JSON Schema、protobuf、Avro、GraphQL SDL）
- 上次的坑
  - live comment = 服务端推、单向、读远多于写 → **SSE**
  - 不是 polling
- 🗣 "First I ask who initiates and whether the caller needs to wait; that picks the family. Then delivery guarantees and fan-out size pick the implementation, and I define the payload contract up front."

<a id="s1"></a>
## 1. 全景图：谁和谁说话

```
                 ┌──────── C→S  request/response (REST / GraphQL / gRPC)
                 ├──────── S→C  push online  (SSE / WebSocket / long poll)
   Client ───────┼──────── S→C  push offline (APNs / FCM / SMS / email)
                 ├──────── C↔S  bidirectional (WebSocket / gRPC stream / MQTT)
                 ├──────── C↔C  peer-to-peer (WebRTC, signaling via server)
                 └──────── C→S  big files (presigned URL → object storage)

   Service ──────┬──────── S→S  sync   (REST / gRPC)
                 ├──────── S→S  async  1:1   (queue)
                 ├──────── S→S  async  1:N   (pub/sub)
                 ├──────── S→S  async  replayable (log / stream)
                 └──────── S→External (webhook)
```

| 方向 | 发起者 | 典型问题 | 方法家族 |
|---|---|---|---|
| C→S | 客户端 | 读写数据 | REST、GraphQL、gRPC |
| S→C 在线 | 服务端 | 实时更新 | SSE、WebSocket、long poll |
| S→C 离线 | 服务端 | app 没开也要通知 | APNs、FCM、SMS、email |
| C↔S 双向 | 两边 | 聊天、游戏、协作 | WebSocket、gRPC stream、MQTT |
| C↔C | 两边 | 音视频、低延迟传输 | WebRTC |
| S→S 同步 | 调用方 | 需要立刻拿结果 | REST、gRPC |
| S→S 异步 | 生产方 | 解耦、削峰、多下游 | Queue、Pub/Sub、Log |
| S→外部 | 我们的服务 | 通知第三方 | Webhook |

<a id="s2"></a>
## 2. 选择时看的 10 个因素

- 面试时把这些说出来，就是"quantitative + factors"
  1. **方向**：单向还是双向
  2. **发起者**：客户端拉，还是服务端推
  3. **延迟**：秒级、百毫秒、几十毫秒
  4. **频率**：每分钟一次，还是每秒几十次
  5. **Payload 大小**：几百字节，还是 GB 级文件
  6. **在线状态**：用户在线、后台、离线
  7. **Fan-out**：1 对 1，还是 1 对 10 万
  8. **投递保证**：可以丢、至少一次、不能重复
  9. **顺序**：要不要严格有序，在什么范围内有序
  10. **客户端类型**：浏览器、移动端、IoT、服务器
- 小技巧：先说 2、7、8，最能决定方向

<a id="s3"></a>
## 3. Schema 总论：所有方式共用的规则

<a id="s3-1"></a>
### 3.1 两层格式：传输层 vs 业务层

- Plain idea：每条消息 = 一个"信封"里装一封"信"
  - 信封 = 协议定的格式，你不能改（HTTP 头、SSE 的 `data:` 行、Kafka 的 key/value/headers）
  - 信 = 你定的业务结构（`{"comment_id": ..., "text": ...}`）
- 面试里要说清两件事
  - 用什么协议（信封）
  - payload 的字段和类型（信），以及以后怎么改不破坏老客户端

<a id="s3-2"></a>
### 3.2 Schema 在哪里定义：IDL 一览

| 方式 | Schema 语言（IDL） | 线上格式 | 生成代码 / 校验 |
|---|---|---|---|
| REST | OpenAPI 3.x + JSON Schema | JSON（也可 protobuf、XML） | openapi-generator、请求校验中间件 |
| GraphQL | GraphQL SDL | JSON | codegen、服务端按 SDL 自动校验 |
| gRPC | Protocol Buffers（`.proto`） | protobuf 二进制 | protoc / buf |
| SSE / WebSocket / MQTT | AsyncAPI + JSON Schema 或 protobuf | 文本 JSON 或二进制 | 自己校验 |
| Kafka / 队列 | Avro / Protobuf / JSON Schema + Schema Registry | 二进制或 JSON | Registry 在写入时检查兼容性 |
| 事件通用信封 | CloudEvents | JSON 或 HTTP header 绑定 | SDK |
| APNs / FCM | 厂商定义的 JSON | JSON | 厂商 SDK |
| Webhook | OpenAPI webhooks 段 / Standard Webhooks 规范 | JSON + 签名头 | 自己校验签名 |

- OpenAPI 管"请求-响应"，AsyncAPI 管"消息 / 事件"
- 🗣 "Contract-first: OpenAPI for request-response, protobuf internally, Avro with a schema registry on Kafka."

<a id="s3-3"></a>
### 3.3 通用设计原则

- **Contract-first**：先写 schema，再写代码；schema 进 git、走 review
- **Envelope + payload**：所有异步消息有统一信封
  - `id`：全局唯一，用于去重
  - `type`：事件名，如 `comment.created`
  - `version` 或 `schema_id`
  - `occurred_at`：事件发生时间（UTC，ISO-8601 或 epoch ms）
  - `source`：哪个服务产生的
  - `trace_id`：链路追踪
  - `data`：真正的业务内容
- **ID 设计**：用字符串 ID（如 Snowflake 转字符串），避免 JS 处理 64 位整数丢精度
- **命名**：同一系统统一 `snake_case` 或 `camelCase`；事件名用过去式（`order.placed`），命令用祈使句（`ReserveInventory`）
- **时间**：一律 UTC；字段名带单位（`timeout_ms`、`size_bytes`）
- **大小**：消息保持小（KB 级）；大内容放对象存储，只传引用（claim-check 模式）
- **可选与默认**：新字段默认可选，有合理默认值
- **Tolerant reader**：消费者忽略不认识的字段，不报错
- **在边界校验**：入口（gateway / 生产者）按 schema 校验，内部信任

<a id="s3-4"></a>
### 3.4 兼容性与版本演进

- Plain idea：生产者和消费者不会同时升级，所以 schema 改动必须"新旧都能读"
- 两个方向
  - **Backward compatible**：新代码能读旧数据
  - **Forward compatible**：旧代码能读新数据
- 改动分类

| 改动 | 安全吗 | 说明 |
|---|---|---|
| 加一个可选字段（有默认值） | 安全 | 旧消费者忽略它 |
| 删一个可选字段 | 基本安全 | protobuf 要把编号标 `reserved` |
| 改字段名 | 破坏 | JSON 按名字匹配 |
| 改字段类型 | 破坏 | int → string 会让旧代码崩 |
| 把可选改成必填 | 破坏 | 旧生产者不发 |
| protobuf 复用旧字段编号 | 破坏 | 旧数据会被错误解析 |
| 枚举加新值 | 有风险 | 旧客户端要能处理"未知" |

- 版本策略
  - REST：URL 版本 `/v1/...`（最常见）或 header 版本；只在破坏性改动时升大版本
  - GraphQL：不做版本，用 `@deprecated` 标记旧字段
  - gRPC：package 带版本 `comments.v1`
  - Kafka：Schema Registry 设兼容模式（BACKWARD / FORWARD / FULL），不兼容的写入直接被拒
  - 破坏性改动：新开 topic / 新 endpoint，双写一段时间，再下线旧的
- 🗣 "Additive changes only; breaking changes get a new version and a dual-run period."

<a id="s4"></a>
## 4. Client ↔ Server

<a id="s4-1"></a>
### 4.1 Request / Response ★★★

- Plain idea：客户端问，服务端答，一问一答
- 何时用：绝大多数 CRUD；任何"用户点了一下"的动作

| 方式 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| REST（HTTP + JSON） | 简单、可缓存、通用 | 多次往返、字段冗余 | 默认 |
| GraphQL | 一次拿到需要的字段 | HTTP 缓存难，复杂查询会拖垮后端 | 多端、页面字段多变 |
| gRPC（HTTP/2 + protobuf） | 二进制、强类型、快 | 浏览器要 gRPC-Web 代理 | 移动端、内部 API |

- Tier 3：Spring MVC / WebFlux、Apollo（GraphQL）、grpc-java
- 🗣 "Writes carry an idempotency key, so client retries are safe."

<a id="s4-1-1"></a>
#### 4.1.1 REST：schema、原则、payload

- Schema 怎么定义：OpenAPI 3.x（YAML），body 用 JSON Schema

```yaml
paths:
  /v1/lives/{liveId}/comments:
    post:
      parameters:
        - { name: liveId, in: path, required: true, schema: { type: string } }
        - { name: Idempotency-Key, in: header, required: true, schema: { type: string } }
      requestBody:
        content:
          application/json:
            schema:
              type: object
              required: [text]
              properties:
                text: { type: string, maxLength: 500 }
      responses:
        "201": { description: Created }
        "429": { description: Rate limited }
```

- 设计原则
  - URL 是名词（资源），动作靠 HTTP 方法
  - 方法语义要对
    - GET：只读，safe + idempotent
    - PUT：整体替换，idempotent
    - PATCH：部分更新，一般不 idempotent
    - DELETE：idempotent
    - POST：创建或动作，不 idempotent → 加 `Idempotency-Key`
  - 状态码要对：200 / 201 / 202 / 204、400 / 401 / 403 / 404 / 409 / 412 / 429、500 / 503
  - 错误格式统一：RFC 9457 `application/problem+json`
  - 分页用 cursor（`next_cursor`），不用 offset
  - 并发控制：`ETag` + `If-Match`，冲突返回 412
  - 长任务：`202 Accepted` + `Location: /v1/operations/{id}`
- Payload 长什么样

```http
POST /v1/lives/L42/comments HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Idempotency-Key: 7f3c9a1e-2b...

{"text": "great shot!"}
```

```http
HTTP/1.1 201 Created
Location: /v1/lives/L42/comments/C9001
Content-Type: application/json

{"comment_id": "C9001", "live_id": "L42", "user_id": "U7",
 "text": "great shot!", "created_at": "2026-11-08T20:31:05Z", "seq": 1834}
```

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 2
Content-Type: application/problem+json

{"type": "https://api.example.com/errors/rate-limited",
 "title": "Too many comments", "status": 429, "detail": "Max 5 comments per 10s"}
```

- 变体（穷举）
  - **风格**
    - 资源式 REST（上面）
    - RPC-over-HTTP：`POST /v1/comments:moderate`、AWS/OCI 部分 API 的 `Action=` 风格
    - Hypermedia：HAL、JSON:API（响应带 `_links`）
    - OData：URL 里带查询（`$filter`、`$select`）
  - **Body 格式**：JSON（默认）、protobuf over HTTP、XML（老系统、S3 multipart）、`application/x-www-form-urlencoded`（表单、OAuth）、`multipart/form-data`（小文件上传）
  - **传输版本**
    - HTTP/1.1：一个连接一次一个请求
    - HTTP/2：多路复用、头部压缩
    - HTTP/3（QUIC/UDP）：弱网、移动端更好
  - **特殊模式**
    - 条件请求：`If-None-Match` → `304 Not Modified`
    - 批量接口：`POST /v1/batch`
    - 长任务：202 + operation 资源（OCI work request 就是这个）
    - 流式响应：`Transfer-Encoding: chunked`、NDJSON（每行一个 JSON）
    - Range 请求：`Range: bytes=0-1048575`（下载续传、视频）

<a id="s4-1-2"></a>
#### 4.1.2 GraphQL：schema、原则、payload

- Schema 怎么定义：SDL

```graphql
type Comment { id: ID!  text: String!  author: User!  createdAt: String! }
type Query { comments(liveId: ID!, first: Int = 20, after: String): CommentConnection! }
type Mutation { postComment(liveId: ID!, text: String!): Comment! }
type Subscription { commentAdded(liveId: ID!): Comment! }
```

- 设计原则
  - 字段默认可空，只有确定一定有才加 `!`
  - 分页用 Relay connection（`edges`、`pageInfo.endCursor`）
  - 不做版本，用 `@deprecated(reason: "...")`
  - 限制查询深度和复杂度，防止一个请求拖垮后端
  - 生产环境用 persisted queries（只允许预注册的查询）
  - 防 N+1：DataLoader 批量取数
- Payload 长什么样

```http
POST /graphql HTTP/1.1
Content-Type: application/json

{"query": "query($id: ID!){ comments(liveId:$id, first:2){ edges{ node{ id text } } } }",
 "variables": {"id": "L42"}}
```

```json
{"data": {"comments": {"edges": [{"node": {"id": "C1", "text": "hi"}}]}},
 "errors": []}
```

- 注意：GraphQL 出错时常常仍返回 HTTP 200，错误在 `errors` 数组里
- 变体（穷举）
  - Query（读）、Mutation（写）、Subscription（推送）
  - Subscription 的传输：WebSocket（`graphql-ws` 协议）或 SSE
  - Persisted queries：`GET /graphql?id=<hash>`，可走 CDN 缓存
  - Federation：多个服务各管一部分 schema，网关合并
  - Batching：一个 HTTP 请求里放多个操作

<a id="s4-1-3"></a>
#### 4.1.3 gRPC：schema、原则、payload

- Schema 怎么定义：`.proto`

```protobuf
syntax = "proto3";
package comments.v1;

service CommentService {
  rpc PostComment(PostCommentRequest) returns (Comment);
  rpc StreamComments(StreamRequest) returns (stream Comment);
}

message PostCommentRequest {
  string live_id = 1;
  string text = 2;
  string idempotency_key = 3;
}
message Comment {
  string id = 1;
  string live_id = 2;
  string text = 3;
  int64 created_at_ms = 4;
  int64 seq = 5;
  reserved 6;            // 删掉的字段编号永不复用
}
```

- 设计原则
  - 字段编号一旦用过就永远不能改含义；删除时标 `reserved`
  - 只加字段，不改类型
  - package 带版本（`comments.v1`）
  - 每次调用设 **deadline**，并向下游传递
  - 错误用标准 status code（`NOT_FOUND`、`ALREADY_EXISTS`、`RESOURCE_EXHAUSTED`、`UNAVAILABLE`）
  - 用 buf 的 breaking-change 检查做 CI 门禁
- Payload 长什么样（HTTP/2 上）

```
:method: POST
:path: /comments.v1.CommentService/PostComment
content-type: application/grpc
grpc-timeout: 500m
authorization: Bearer ...

DATA frame: [1 byte 压缩标志][4 bytes 长度][protobuf 二进制]

trailers:
grpc-status: 0
grpc-message:
```

- 变体（穷举）
  - Unary、server streaming、client streaming、bidirectional streaming
  - gRPC-Web：浏览器用，需要 Envoy 等代理转换
  - Connect 协议：同一份 proto，可走 HTTP/1.1 + JSON
  - JSON transcoding（grpc-gateway、Google API annotations）：同一服务对外暴露 REST
  - 负载均衡：客户端侧（xDS）vs 代理侧（Envoy）

<a id="s4-2"></a>
### 4.2 Short polling ★★

- Plain idea：客户端每隔 N 秒问一次"有新的吗？"
- 怎么做
  1. 客户端 `GET /updates?since=<cursor>`
  2. 服务端立即返回，有就给，没有就空
  3. 等 N 秒再问
- 好处：最简单，无状态，任何环境都能用
- 代价
  - 延迟 = 轮询间隔
  - 大部分请求是空的
  - 例：100 万用户每 5 秒一次 = 20 万 QPS，几乎全空
- 何时用：低频、可接受几十秒延迟（订单状态、长任务进度、work request 状态）
- 🗣 "Polling is fine for job status every 10 seconds; it's wrong for chat."

<a id="s4-2-1"></a>
#### 4.2.1 Schema、原则、payload

- Schema：就是一个 REST GET（OpenAPI），关键是 **cursor** 字段
- 原则
  - 用不透明 cursor（服务端编码的位置），不要用客户端时间戳（时钟不准）
  - 支持 `ETag` / `If-None-Match`，没变化时返回 304，省带宽
  - 服务端用 `Retry-After` 告诉客户端下次什么时候来
- Payload

```http
GET /v1/operations/op-123?view=status HTTP/1.1
If-None-Match: "v7"
```

```http
HTTP/1.1 200 OK
ETag: "v8"
Retry-After: 10
Content-Type: application/json

{"id": "op-123", "status": "IN_PROGRESS", "percent_complete": 60,
 "updated_at": "2026-11-08T20:31:05Z"}
```

- 变体（穷举）
  - 固定间隔
  - 自适应间隔：没变化就逐步拉长（退避），有变化就缩短
  - 条件 GET（304）
  - `HEAD` 请求只看版本号
  - 前台快、后台慢（移动端省电）

<a id="s4-3"></a>
### 4.3 Long polling ★★

- Plain idea：客户端问，服务端**不立即回**，等有数据或超时再回
- 怎么做
  1. 客户端发请求，带上 cursor 和最长等待时间
  2. 服务端挂起，最多 30–60 秒
  3. 有消息就返回；超时返回空
  4. 客户端马上再发下一个
- 好处：近实时，走普通 HTTP，防火墙友好
- 代价
  - 每条消息后要重新建请求
  - 服务端要挂住大量请求（要非阻塞框架）
  - 消息密集时开销大
- 何时用：WebSocket / SSE 不可用时的**兜底**；老系统
- Tier 3：Spring `DeferredResult`、WebFlux；Socket.IO 的 polling transport
- 🗣 "Long polling is my fallback when WebSocket is blocked by a proxy."

<a id="s4-3-1"></a>
#### 4.3.1 Schema、原则、payload

- Schema：REST GET + `cursor` + `wait` 参数；响应带一批消息和新 cursor
- 原则
  - 超时要比 LB / 代理的空闲超时短（否则被中间设备掐断）
  - 一次返回一批，不是一条
  - 客户端拿到响应立刻用新 cursor 重发
- Payload

```http
GET /v1/inbox/updates?cursor=abc123&wait=30 HTTP/1.1
```

```json
{"messages": [{"id": "M1", "seq": 101, "text": "hi"},
              {"id": "M2", "seq": 102, "text": "you there?"}],
 "next_cursor": "abc125"}
```

- 超时无数据：`204 No Content` 或 `{"messages": [], "next_cursor": "abc123"}`
- 变体（穷举）
  - 单 channel 长轮询
  - 多路复用：一个请求同时等多个 channel（`?channels=a,b,c`）
  - Comet / Bayeux（老式推送框架）
  - Socket.IO / SockJS 的自动降级 transport

<a id="s4-4"></a>
### 4.4 SSE（Server-Sent Events） ★★★

- Plain idea：客户端开一个 HTTP 连接，服务端**一直往里写**事件，只能服务端 → 客户端
- 怎么做
  1. 客户端 `new EventSource('/v1/lives/L42/stream')`
  2. 服务端返回 `Content-Type: text/event-stream`，不关连接
  3. 每个事件几行文本，空行结束
  4. 断线后浏览器**自动重连**，并带上 `Last-Event-ID`
  5. 服务端从那个 id 之后补发
- 好处
  - 就是 HTTP：过代理、走 HTTP/2 多路复用、L7 LB 能处理
  - 自带重连 + 断点续传（Last-Event-ID）
  - 比 WebSocket 简单
- 代价
  - 只能单向；客户端发消息还得走普通 POST
  - HTTP/1.1 下浏览器每个域名约 6 个连接上限（HTTP/2 下没这个问题）
  - 只能传文本（二进制要 base64）
  - 原生 `EventSource` 不能自定义 header（只能 GET + cookie / query token）
- 何时用：**服务端推、客户端很少发**
  - live comment、比分、股价、通知角标、AI 流式输出、进度条、dashboard
- Tier 3：Spring WebFlux `Flux<ServerSentEvent>`、Node；NGINX 要关 `proxy_buffering`
- 🗣 "Live comments are read-heavy and one-directional, so SSE: plain HTTP, auto-reconnect with Last-Event-ID, and posting a comment is just a normal POST."

<a id="s4-4-1"></a>
#### 4.4.1 Schema、原则、payload

- 传输格式（协议定的，固定 4 个字段）
  - `event:` 事件类型（不写就是 `message`）
  - `data:` 内容，可以多行
  - `id:` 事件 id，浏览器记住它，重连时作为 `Last-Event-ID` 发回
  - `retry:` 建议重连间隔（毫秒）
  - 以 `:` 开头的行是注释，常用作心跳
- 业务 schema：`data` 里放 JSON，用 AsyncAPI / JSON Schema 描述每种 `event`
- 原则
  - `id` 在一个流里单调递增（用 seq），才能断点续传
  - 每种事件一个 `event` 名，客户端按名字分发
  - 每 15–30 秒发一条注释心跳，防止代理断开空闲连接
  - 服务端为每个流保留最近 N 条，用于补发
- Payload

```http
GET /v1/lives/L42/stream HTTP/1.1
Accept: text/event-stream
Last-Event-ID: 1833
```

```
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

retry: 3000

event: comment.created
id: 1834
data: {"comment_id":"C9001","user":"U7","text":"great shot!","ts":1794170000000}

event: comment.batch
id: 1840
data: {"items":[{"comment_id":"C9002","text":"wow"},{"comment_id":"C9003","text":"gg"}]}

: heartbeat

event: viewer.count
id: 1841
data: {"count": 98213}
```

- 变体（穷举）
  - 默认 `message` 事件 vs 命名事件
  - 单条事件 vs 批量事件（热门直播降低帧率）
  - 原生 `EventSource`（只 GET）vs fetch 版 SSE（`@microsoft/fetch-event-source`）：可以 POST + 自定义 header
    - LLM token streaming 就是 POST 请求 + SSE 响应
  - 认证：cookie、query token、fetch 版用 `Authorization` header
  - HTTP/1.1 vs HTTP/2（后者没有 6 连接限制）
  - GraphQL subscription over SSE

<a id="s4-5"></a>
### 4.5 WebSocket ★★★

- Plain idea：一次 HTTP 握手升级成**双向长连接**，两边随时发
- 怎么做
  1. 客户端 `GET /ws`，带 `Upgrade: websocket`
  2. 服务端返回 `101 Switching Protocols`
  3. 之后是 TCP 上的帧，两边随时发（文本或二进制）
  4. 应用层自己做心跳、ack、重连、补发
- 好处：全双工、低延迟、每条消息开销很小
- 代价
  - **有状态连接**：扩容、部署、LB 都要处理
  - 断线重连、补发要自己做（没有 Last-Event-ID）
  - 部分企业代理会拦
- 何时用：**两边都频繁发**
  - 聊天、多人游戏、协同编辑、交易终端、语音房信令
- 扩展要点
  - LB 用 **L4** 或支持 WebSocket 的 L7，连接会固定在一台机器
  - 连接注册表：`user_id → connection server`，放 Redis
  - 单机连接数是"数万到数十万"量级，取决于内存和框架（order of magnitude）
- Tier 3

| 框架 | 好处 | 代价 |
|---|---|---|
| Netty | 高性能、单机连接多 | 底层，代码多 |
| Spring WebSocket / STOMP | 集成方便，有 topic 概念 | 性能一般 |
| Socket.IO | 房间、自动降级、自动重连 | 自定义协议，Node 为主 |
| 托管：AWS API GW WebSocket、Pusher、Ably | 免运维 | 贵、可控性差 |

- 🗣 "Chat needs both directions at high frequency, so WebSocket; connection servers are stateful and register user-to-server mappings in Redis."

<a id="s4-5-1"></a>
#### 4.5.1 Schema、原则、payload

- 传输格式：协议只定了帧（opcode：text / binary / ping / pong / close），**不管内容**
- 业务 schema：必须自己定一个**信封**，用 AsyncAPI + JSON Schema 或 protobuf 描述
- 原则
  - 每条消息有 `type`，按类型分发
  - 客户端发的消息带 `client_msg_id`，服务端回 `ack`，用于幂等和"已发送"状态
  - 服务端推的消息带 `seq`（按会话递增），客户端发现缺口就补拉
  - 带协议版本：握手时 `Sec-WebSocket-Protocol: chat.v1`
  - 心跳：协议 ping/pong 或应用层 `{"type":"ping"}`
  - 限制单帧大小；大内容走 HTTP 上传，只发引用
- 握手

```http
GET /ws?token=eyJ... HTTP/1.1
Host: chat.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat.v1
```

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat.v1
```

- 帧内容（text frame，JSON 信封）

```json
// client → server：发消息
{"type": "message.send", "client_msg_id": "c-77a1", "chat_id": "G5",
 "body": {"text": "hello"}, "ts": 1794170000000}

// server → client：确认
{"type": "message.ack", "client_msg_id": "c-77a1", "msg_id": "M8812", "seq": 342}

// server → client：别人发来的消息
{"type": "message.new", "msg_id": "M8813", "chat_id": "G5", "seq": 343,
 "from": "U9", "body": {"text": "hey"}, "ts": 1794170000500}

// client → server：已读回执
{"type": "receipt.read", "chat_id": "G5", "up_to_seq": 343}

// 重连后补发
{"type": "sync.request", "chat_id": "G5", "after_seq": 340}
```

- 变体（穷举）
  - 裸 WebSocket + 自定义 JSON 信封（上面）
  - 二进制帧 + protobuf（省带宽，移动端、游戏）
  - STOMP over WebSocket：帧有 `SEND` / `SUBSCRIBE` / `MESSAGE` 命令和 `destination` 头（Spring 常用）
  - Socket.IO 协议：`emit(event, data, ack)`、rooms、namespace，自带重连
  - `graphql-ws`：GraphQL subscription
  - MQTT over WebSocket：浏览器接 MQTT broker
  - WAMP：RPC + pub/sub
  - 压缩：`permessage-deflate` 扩展
  - 认证：握手时 query token / cookie；或连接后第一条消息发 `auth`

<a id="s4-6"></a>
### 4.6 gRPC / HTTP2 streaming ★★

- Plain idea：gRPC 的流式调用，一个连接上持续收发
- 四种模式
  - Unary：一问一答
  - Server streaming：一问多答（类似 SSE）
  - Client streaming：多问一答（上传传感器数据）
  - Bidirectional streaming：类似 WebSocket
- 好处：强类型、二进制、移动端省流量
- 代价：浏览器原生不支持，要 gRPC-Web + 代理
- 何时用：移动端 app 和后端、内部服务之间的流
- 🗣 "For a native mobile client I'd use gRPC bidirectional streaming instead of WebSocket for typed messages."

<a id="s4-6-1"></a>
#### 4.6.1 Schema、原则、payload

- Schema：`.proto` 里用 `stream` 关键字

```protobuf
service ChatService {
  rpc Connect(stream ClientEvent) returns (stream ServerEvent);
}
message ClientEvent {
  oneof event {
    SendMessage send = 1;
    ReadReceipt read = 2;
    Ping ping = 3;
  }
}
message ServerEvent {
  oneof event {
    MessageAck ack = 1;
    NewMessage message = 2;
    Pong pong = 3;
  }
}
```

- 原则
  - 用 `oneof` 做消息类型的"信封"，等价于 WebSocket 里的 `type`
  - 长流要处理连接中途断开、deadline、keepalive
  - 加新消息类型 = 在 `oneof` 里加新编号，旧客户端会忽略
- Payload：HTTP/2 上一串长度前缀的 protobuf 帧，同 4.1.3
- 变体：unary / server / client / bidi；gRPC-Web 只支持 unary 和 server streaming

<a id="s4-7"></a>
### 4.7 Mobile push（APNs / FCM） ★★★

- Plain idea：app 在后台或被杀掉时，经由 **Apple / Google 的推送服务**把通知送到手机
- 怎么做
  1. App 启动时向 APNs / FCM 注册，拿到 **device token**
  2. App 把 token 上报给我们的服务端，存 `user → tokens`
  3. 要通知时，我们的服务调用 APNs / FCM API
  4. 系统推送到设备，用户点开再拉取完整数据
- 好处：离线也能触达，省电（系统统一维持连接）
- 代价
  - **不保证送达、不保证顺序**，有频率限制
  - payload 很小（APNs 约 4 KB 量级）
  - token 会失效，需要清理
- 何时用：用户**不在线**时
- 常见组合：在线走 WebSocket，离线走 APNs / FCM
- 🗣 "Push notifications are a hint, not the data; the client syncs the real messages when it opens."

<a id="s4-7-1"></a>
#### 4.7.1 Schema、原则、payload

- Schema：由 Apple / Google 定义，我们只能在 `data` / 自定义字段里放自己的东西
- 原则
  - 只放提示和 ID，不放敏感内容（锁屏可见）
  - 用 `collapse-id` / `collapse_key` 合并同类通知（10 条新消息只显示最新一条）
  - 区分高优先级（立即）和普通优先级（省电，可延迟）
  - 设 TTL：过期就别送了
  - 推送里带 `chat_id` 等，app 打开后用它去拉数据
- APNs（HTTP/2）

```http
POST /3/device/<device_token> HTTP/2
Host: api.push.apple.com
authorization: bearer <JWT>
apns-topic: com.example.chat
apns-push-type: alert
apns-priority: 10
apns-collapse-id: chat-G5
apns-expiration: 1794173600

{"aps": {"alert": {"title": "Alice", "body": "hey, you there?"},
         "badge": 3, "sound": "default", "thread-id": "chat-G5"},
 "chat_id": "G5", "msg_id": "M8813"}
```

- FCM（HTTP v1）

```json
POST https://fcm.googleapis.com/v1/projects/my-proj/messages:send
{"message": {
   "token": "<device_token>",
   "notification": {"title": "Alice", "body": "hey, you there?"},
   "data": {"chat_id": "G5", "msg_id": "M8813"},
   "android": {"priority": "HIGH", "collapse_key": "chat-G5", "ttl": "3600s"}
}}
```

- 变体（穷举）
  - Alert 推送（用户看得见）vs 静默 / 后台推送（`content-available: 1`，唤醒 app 同步）
  - FCM notification message（系统直接显示）vs data message（app 自己处理）
  - 单设备 token vs FCM topic（订阅主题群发）vs 设备组
  - VoIP 推送（iOS PushKit，来电）
  - Web Push（浏览器，VAPID 签名）
  - 其他渠道：SMS（Twilio）、Email（SES、SendGrid）——各自有模板和退订规则

<a id="s4-8"></a>
### 4.8 MQTT（IoT） ★

- Plain idea：极轻量的 pub/sub 协议，设备连 broker，订阅 topic
- 好处：小包、弱网友好、有 QoS 0/1/2、保留消息
- 何时用：IoT 设备、车载、弱网移动场景
- Tier 3：EMQX、Mosquitto、AWS IoT Core
- 🗣 "For millions of low-power devices I'd use MQTT with QoS 1 rather than WebSocket."

<a id="s4-8-1"></a>
#### 4.8.1 Schema、原则、payload

- Schema 分两部分
  - **Topic 层级**就是一半的 schema：`fleet/{region}/{device_id}/telemetry`
  - Payload：JSON、protobuf 或 CBOR（更紧凑），用 AsyncAPI 描述
- 原则
  - Topic 从大到小，便于用通配符订阅（`fleet/us/+/telemetry`、`fleet/#`）
  - 不要把可变值（时间戳）放进 topic
  - QoS 按需求选：0 最多一次、1 至少一次、2 恰好一次（慢）
  - 设 Last Will（设备掉线时 broker 自动发"离线"消息）
  - 状态类消息用 retained（新订阅者立刻拿到最新值）
- Payload

```
PUBLISH
  topic:   fleet/us-east/dev-881/telemetry
  qos:     1
  retain:  false
  payload: {"ts": 1794170000, "lat": 32.78, "lon": -96.80, "battery": 0.74}

CONNECT 时的 Last Will
  topic:   fleet/us-east/dev-881/status
  payload: {"online": false}
  retain:  true
```

- 变体：MQTT 3.1.1 vs 5（5 加了 user properties、response topic、shared subscription）；MQTT over WebSocket；MQTT-SN（传感器网络）

<a id="s4-9"></a>
### 4.9 WebRTC（Client ↔ Client） ★★

- Plain idea：两个客户端**直接**传音视频 / 数据，服务器只负责撮合
- 怎么做
  1. Signaling：双方通过我们的服务器（通常 WebSocket）交换 SDP offer / answer 和 ICE candidate
  2. STUN：拿到自己的公网地址
  3. 打洞成功 → P2P 直连
  4. 打洞失败 → 走 TURN 服务器中转
  5. 多人会议：用 SFU（选择性转发服务器）而不是全 P2P
- 好处：延迟最低，服务器不扛媒体流量（P2P 时）
- 代价：NAT 穿透复杂；TURN 带宽成本高；多人要 SFU
- 何时用：视频通话、语音、屏幕共享
- Tier 3：Janus、mediasoup、LiveKit（SFU）；coturn（TURN）
- 🗣 "WebRTC still needs a server for signaling and TURN fallback; for group calls I'd use an SFU."

<a id="s4-9-1"></a>
#### 4.9.1 Schema、原则、payload

- Schema 分两部分
  - **Signaling 消息**：WebRTC 不规定，自己定（通常走 WebSocket，JSON 信封）
  - **SDP**：会话描述，格式由标准定义（编解码器、媒体方向、ICE 信息）
  - Data channel 里的消息：自己定（同 WebSocket 信封）
- 原则
  - Signaling 带 `call_id` 和发送方 / 接收方
  - ICE candidate 可以逐条发（trickle ICE），加快建连
  - Data channel 可选可靠有序（像 TCP）或不可靠无序（像 UDP，游戏用）
- Payload（signaling，走 WebSocket）

```json
{"type": "call.offer", "call_id": "K77", "from": "U7", "to": "U9",
 "sdp": "v=0\r\no=- 4611 2 IN IP4 127.0.0.1\r\ns=-\r\nt=0 0\r\nm=audio 9 UDP/TLS/RTP/SAVPF 111\r\n..."}

{"type": "call.answer", "call_id": "K77", "sdp": "v=0\r\n..."}

{"type": "call.ice", "call_id": "K77",
 "candidate": "candidate:1 1 UDP 2122260223 192.168.1.5 54400 typ host"}
```

- 变体：P2P（2 人）、SFU（多人，服务器转发不解码）、MCU（服务器混流，贵）；data channel 可靠 / 不可靠

<a id="s4-10"></a>
### 4.10 大文件传输 ★★★

- Plain idea：大文件**不经过应用服务器**，直接传到对象存储

| 方式 | 怎么做 | 何时用 |
|---|---|---|
| Presigned URL | API 签发一个有时效的上传 URL，客户端直传 | 默认 |
| Multipart upload | 文件切块并行上传，最后合并 | 百 MB 以上量级 |
| Resumable（tus 协议、分块 + 断点） | 记住已传块，断网后续传 | 移动端、弱网、大视频 |
| Chunk + dedup（content hash） | 每块算 hash，已有的不传 | Dropbox 类同步 |

- 下载：CDN + range request；视频切成小段（HLS / DASH）
- 🗣 "The API only issues a presigned URL; bytes go straight to object storage, and an upload-complete event triggers processing."

<a id="s4-10-1"></a>
#### 4.10.1 Schema、原则、payload

- Schema：申请上传的 API 用 OpenAPI 定义；上传本身是原始字节
- 原则
  - 元数据（文件名、大小、类型、hash）在申请时就提交，服务端校验大小和类型
  - URL 短时效（分钟级）、限定 content-type 和大小
  - 用 content hash 做完整性校验和去重
  - 上传完成由对象存储事件触发后续处理，不依赖客户端回调
- Payload

```http
POST /v1/uploads HTTP/1.1
Content-Type: application/json

{"file_name": "trip.mp4", "size_bytes": 734003200,
 "content_type": "video/mp4", "sha256": "9f2c..."}
```

```json
{"upload_id": "UP-31", "strategy": "multipart", "part_size_bytes": 8388608,
 "parts": [{"part_number": 1, "url": "https://bucket.s3.../trip.mp4?partNumber=1&uploadId=...&X-Amz-Signature=..."}],
 "complete_url": "/v1/uploads/UP-31/complete", "expires_at": "2026-11-08T20:46:05Z"}
```

```http
PUT https://bucket.s3.../trip.mp4?partNumber=1&uploadId=...&X-Amz-Signature=...
Content-Length: 8388608

<8 MB 原始字节>
```

- tus（断点续传协议）

```http
PATCH /files/24e533e0 HTTP/1.1
Tus-Resumable: 1.0.0
Upload-Offset: 70000
Content-Type: application/offset+octet-stream

<从第 70000 字节开始的数据>
```

- HLS 播放清单（下载侧）

```
#EXTM3U
#EXT-X-TARGETDURATION:4
#EXTINF:4.0,
seg_00001.ts
#EXTINF:4.0,
seg_00002.ts
```

- 变体：单次 PUT、multipart、tus、分块 + hash 去重；下载侧：直接 GET、Range、HLS / DASH 分段

<a id="s4-11"></a>
### 4.11 C↔S 决策树和总表

```
谁先说话？
├─ 客户端 ──────────────────────▶ REST / GraphQL / gRPC
└─ 服务端要推
   ├─ 用户离线 / app 在后台 ────▶ APNs / FCM（+ SMS / email）
   └─ 用户在线
      ├─ 客户端也频繁发？
      │  ├─ 是 ────────────────▶ WebSocket（mobile 可选 gRPC stream）
      │  └─ 否 ────────────────▶ SSE
      ├─ 延迟能接受几十秒？ ─────▶ short polling
      └─ WS/SSE 被拦？ ─────────▶ long polling 兜底
特殊：音视频 ▶ WebRTC ｜ 大文件 ▶ presigned URL ｜ IoT ▶ MQTT
```

| App | 步骤 | 方法 | 原因 |
|---|---|---|---|
| Chat | 发消息 | WebSocket（已连着就复用） | 双向高频 |
| Chat | 收消息（在线） | WebSocket | 同上 |
| Chat | 收消息（离线） | APNs/FCM + 上线后拉取 | app 不在前台 |
| Live comment | 看评论 | **SSE** | 单向推、读多 |
| Live comment | 发评论 | REST POST | 低频，不需要长连接 |
| Notification | 站内角标 | SSE 或轮询 | 单向 |
| Notification | 手机通知 | APNs/FCM | 离线 |
| Uber | 司机上报位置 | WebSocket / gRPC stream（每几秒） | 持续上行 |
| Uber | 乘客看司机位置 | WebSocket 或 SSE | 持续下行 |
| Google Docs | 协同编辑 | WebSocket | 双向、低延迟 |
| 股票 / 比分 | 行情 | SSE（浏览器）/ WebSocket（交易终端） | 单向 vs 双向 |
| LLM 应用 | token 流式输出 | SSE（POST + fetch 版） | 单向流 |
| YouTube | 上传 | presigned + resumable | 大文件 |
| YouTube | 播放 | CDN + HLS 分段 | 大文件、可缓存 |
| OCI work request | 查状态 | short polling（或 webhook） | 低频 |
| 视频通话 | 媒体 | WebRTC（signaling 走 WebSocket） | 最低延迟 |
| 多人游戏 | 状态同步 | WebSocket / UDP | 双向、低延迟 |
| IoT 设备 | 遥测 | MQTT | 弱网、低功耗 |

<a id="s5"></a>
## 5. Server ↔ Server

<a id="s5-1"></a>
### 5.1 同步：REST / gRPC ★★★

- Plain idea：服务 A 调服务 B，**等结果**
- 何时用：结果马上要用（查用户资料、校验权限、读价格）

| 方式 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| REST | 通用、易调试 | JSON 慢、无强契约 | 跨团队、公开 API |
| gRPC | 快、protobuf 契约、流式 | 调试工具少 | 内部高频调用 |

- 必备配套
  - Service discovery（K8s DNS、Consul）
  - 每一跳都有 **timeout**
  - 重试只对幂等操作，**指数退避 + jitter**
  - Circuit breaker（Resilience4j）
- The catch：同步调用链越长，可用性越低
  - 例：5 个服务各 99.9% → 链路约 99.5%
- 🗣 "Sync only where the caller truly needs the answer; everything else goes async."

<a id="s5-1-1"></a>
#### 5.1.1 Schema、原则、payload

- Schema：同 4.1.1（OpenAPI）和 4.1.3（proto）
- 内部调用额外要求
  - 共享 proto 仓库（或 buf registry），CI 做 breaking-change 检查
  - Consumer-driven contract test（Pact）：消费者写期望，提供者 CI 验证
  - 统一传递的 header
    - `traceparent`（W3C trace context）
    - deadline / 剩余超时（gRPC 自动传）
    - 调用方身份（mTLS 证书或 service token）
    - `x-request-id`、租户 id
- Payload（内部 REST 例）

```http
GET /internal/v1/users/U7/profile HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
x-tenant-id: T12
x-request-timeout-ms: 150
```

- 变体：REST、gRPC、GraphQL federation（网关后的子图）、Thrift（老系统）

<a id="s5-2"></a>
### 5.2 异步：Queue（点对点） ★★★

- Plain idea：消息进队列，**一个**消费者处理一次
- 怎么做
  1. 生产者 send
  2. 消费者 receive，消息暂时不可见（visibility timeout）
  3. 处理成功 → delete / ack
  4. 失败或超时 → 重新可见，重试
  5. 超过次数 → DLQ
- 何时用：任务分发、削峰、后台作业（发邮件、转码、生成报告）
- Tier 3

| 实现 | 好处 | 代价 |
|---|---|---|
| SQS / OCI Queue | 托管、自动扩展 | 标准队列不保证顺序；FIFO 吞吐有限 |
| RabbitMQ | 灵活路由、低延迟、优先级 | 自运维，吞吐不如 Kafka |
| Redis list / BullMQ | 简单、快 | 持久性弱 |

- 🗣 "Queue for work: each job processed by one worker, visibility timeout for retries, DLQ after N failures."

<a id="s5-2-1"></a>
#### 5.2.1 Schema、原则、payload

- Schema：body 用 JSON Schema / protobuf / Avro；外面是统一信封（3.3）；队列本身还有**属性**
- 原则
  - 消息是**命令**（"去做 X"），名字用祈使句：`TranscodeVideo`
  - 带 `id` 供幂等；带 `attempt` 次数方便排查
  - 大 payload 放对象存储，只发引用（SQS 单条约 256 KB 量级上限）
  - FIFO 队列：`MessageGroupId` 决定顺序范围，`MessageDeduplicationId` 去重
- Payload（SQS 例）

```json
{
  "MessageBody": "{\"id\":\"cmd-5521\",\"type\":\"TranscodeVideo\",\"version\":1,\"occurred_at\":\"2026-11-08T20:31:05Z\",\"source\":\"upload-svc\",\"data\":{\"video_id\":\"V88\",\"input\":\"s3://raw/V88.mp4\",\"profiles\":[\"720p\",\"1080p\"]}}",
  "MessageAttributes": {"type": {"DataType": "String", "StringValue": "TranscodeVideo"}},
  "MessageGroupId": "V88",
  "MessageDeduplicationId": "cmd-5521",
  "DelaySeconds": 0
}
```

- 变体（穷举）
  - 标准队列（至少一次、近似有序）vs FIFO（按 group 有序 + 去重）
  - 延迟消息（`DelaySeconds`、RabbitMQ 延迟插件）
  - 优先级队列（RabbitMQ）
  - RabbitMQ 路由：direct、topic（通配）、fanout、headers exchange
  - Request-reply over queue：带 `reply_to` + `correlation_id`
  - 命令消息 vs 事件消息（队列里一般放命令）

<a id="s5-3"></a>
### 5.3 异步：Pub/Sub（一对多） ★★★

- Plain idea：发布一次，**所有订阅者**各收一份
- 何时用
  - 一个事件多方关心：订单创建 → 库存、邮件、分析
  - 实时 fan-out 到多台 connection server
- 两种 pub/sub
  - **持久型**：订阅者离线时消息保留（SNS → SQS、Kafka 消费组、Google Pub/Sub）
  - **即发即忘型**：只发给当前在线订阅者（Redis Pub/Sub）

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| SNS + SQS（fan-out） | 托管、每个下游一个队列 | 不能重放 | AWS 事件通知 |
| Redis Pub/Sub | 亚毫秒、简单 | 不持久，订阅者断开就丢 | 实时推到 connection server |
| Kafka（多消费组） | 持久、可重放 | 重 | 事件驱动核心 |
| Google Pub/Sub | 托管、全球 | 绑定 GCP | GCP 上 |

- 🗣 "Redis Pub/Sub for the live fan-out hop because a lost frame is fine; Kafka underneath for anything we must not lose."

<a id="s5-3-1"></a>
#### 5.3.1 Schema、原则、payload

- Schema：**事件**（"X 发生了"），用 CloudEvents 信封 + 业务 schema
- 原则
  - 事件名用过去式：`order.placed`、`comment.created`
  - Topic / channel 命名有层次：`domain.entity.event` 或 `live:{id}`
  - 发布方不知道谁在订阅 → 事件要自描述，带够下游需要的字段
  - 用消息属性做过滤（SNS filter policy），不要让每个订阅者都收全部
- Payload（CloudEvents JSON）

```json
{"specversion": "1.0",
 "id": "evt-90a1",
 "type": "com.example.order.placed",
 "source": "/order-svc",
 "time": "2026-11-08T20:31:05Z",
 "datacontenttype": "application/json",
 "dataschema": "https://schemas.example.com/order.placed/v2.json",
 "data": {"order_id": "O551", "user_id": "U7", "total_cents": 4599, "items": 3}}
```

- Redis Pub/Sub（实时 fan-out 那一跳）

```
PUBLISH live:L42 '{"type":"comment.created","seq":1834,"comment_id":"C9001","text":"great shot!"}'
SUBSCRIBE live:L42
PSUBSCRIBE live:*        # 模式订阅
```

- 变体（穷举）
  - Topic-based（按主题）vs content-based（按消息属性过滤）
  - 持久订阅 vs 非持久订阅
  - SNS → 多个 SQS（每个下游一个队列，各自重试）
  - Redis channel / pattern 订阅；Redis Streams（带持久和消费组）
  - Event notification（只说"变了"+ id，订阅者回查）vs event-carried state transfer（带完整数据）

<a id="s5-4"></a>
### 5.4 异步：Log / Stream ★★★

- Plain idea：消息**追加写入日志**，保存一段时间，消费者自己记录读到哪（offset）
- 和 queue 的区别
  - Queue：消费完删掉
  - Log：不删，多个消费组各读各的，可以回放
- 怎么做（Kafka）
  1. Topic 分成多个 partition
  2. 生产者按 key 选 partition → **同一 key 有序**
  3. 每个 partition 有副本（replication factor 常见为 3）
  4. 消费组内，一个 partition 只给一个消费者
  5. 消费者提交 offset
- 何时用：高吞吐 ingestion、多下游消费、需要重放、event sourcing、CDC 管道
- Tier 3：Kafka、OCI Streaming、Kinesis、Pulsar、Redpanda
- The catch
  - 并行度 = partition 数，事后加 partition 会打乱 key 映射
  - 只有 partition 内有序
- 🗣 "Kafka keyed by chat_id: per-chat ordering, and the partition count caps consumer parallelism."

<a id="s5-4-1"></a>
#### 5.4.1 Schema、原则、payload

- 一条 Kafka record 的结构（协议定的）
  - `key`：决定分区和顺序
  - `value`：业务内容
  - `headers`：元数据（trace id、schema id、事件类型）
  - `timestamp`、`partition`、`offset`（broker 分配）
- 业务 schema：Avro / Protobuf / JSON Schema，注册到 **Schema Registry**
  - 生产者写入时，value 开头带 schema id（几个字节）
  - Registry 按兼容模式检查新版本，不兼容直接拒绝
- 原则
  - **Key 的选择 = 顺序的范围 = 热点的风险**
    - chat_id：会话内有序；一个超大群会成热点
    - user_id：用户内有序
  - 兼容模式默认 BACKWARD（先升级消费者，再升级生产者）
  - Compacted topic：同 key 只保留最新值，value 为 null（tombstone）表示删除
  - 事件 vs 状态：事件 topic 保留一段时间；状态 topic 用 compaction 永久保留最新
- Avro schema 例

```json
{"type": "record", "name": "CommentCreated", "namespace": "com.example.live",
 "fields": [
   {"name": "comment_id", "type": "string"},
   {"name": "live_id", "type": "string"},
   {"name": "user_id", "type": "string"},
   {"name": "text", "type": "string"},
   {"name": "created_at_ms", "type": "long"},
   {"name": "lang", "type": ["null", "string"], "default": null}
 ]}
```

- 一条 record

```
topic:     live.comments.v1
partition: 17            (= hash(key) % 64)
offset:    9123344
key:       "L42"
headers:   type=comment.created, trace_id=4bf92f35..., schema_id=118
timestamp: 1794170000000
value:     <Avro 二进制: comment_id=C9001, live_id=L42, user_id=U7, text="great shot!", ...>
```

- CDC 事件（Debezium 信封）

```json
{"before": null,
 "after": {"comment_id": "C9001", "live_id": "L42", "text": "great shot!"},
 "op": "c",
 "source": {"db": "live", "table": "comments", "lsn": 2391823},
 "ts_ms": 1794170000123}
```

- 变体（穷举）
  - Event notification（薄事件）vs event-carried state transfer（胖事件）
  - Event sourcing：事件就是数据源，状态靠重放得到
  - CDC topic（`before` / `after` / `op`）
  - Compacted topic（KV 最新状态）
  - Kafka transactions（读-处理-写原子）
  - 序列化：Avro（Kafka 生态默认）、Protobuf、JSON Schema、纯 JSON（无 registry，不推荐）

<a id="s5-5"></a>
### 5.5 服务器层内部路由：消息怎么找到用户所在的连接 ★★★

- Problem：用户 B 连在 connection server #7，消息从 API server #3 进来，怎么送到 #7？

| 方案 | 怎么做 | 好处 | 代价 | 选择条件 |
|---|---|---|---|---|
| 注册表 + 直连 | Redis 存 `user → server`；API 查到后 RPC 到 #7 | 精准、少浪费 | 注册表要维护，server 挂了要清理 | 1:1 聊天 |
| Pub/Sub 按用户 channel | 每台 server 订阅自己在线用户的 channel | 解耦 | channel 数量巨大 | 中等规模 |
| Pub/Sub 按房间 / 主题 | server 订阅它有观众的房间 | fan-out 高效 | 热门房间所有 server 都收 | live comment、群聊 |
| 广播给所有 server | 每台都收，自己过滤 | 最简单 | 浪费，规模大就不行 | 小规模 |

- 热门房间（10 万观众）
  - 不是逐用户推，而是**每台 server 收一次**，再本地推给它的观众
  - 消息太多时：服务端批量（每 100–500 ms 一批）+ 采样
- 🗣 "For a hot live stream, fan-out is per connection server, not per viewer: 100k viewers on 50 servers means 50 publishes."

<a id="s5-5-1"></a>
#### 5.5.1 Schema、原则、payload

- 注册表的数据结构（Redis）

```
HSET conn:U9 server cs-7 conn_id k1f3 device ios since 1794170000
EXPIRE conn:U9 90                       # 心跳续期，server 挂了自动过期
SADD room:L42:servers cs-3 cs-7 cs-12    # 这个房间有观众的 server
```

- 内部投递 RPC（API → connection server）

```protobuf
service Delivery {
  rpc Deliver(DeliverRequest) returns (DeliverResponse);
}
message DeliverRequest {
  repeated string user_ids = 1;
  bytes envelope = 2;     // 原样转给客户端的 WebSocket / SSE 帧
}
```

- 原则
  - 注册表条目带 TTL，靠心跳续期
  - 同一用户多设备：一个 user 对应多个 conn
  - 投递失败（server 不在了）→ 删除注册表条目 → 走离线推送

<a id="s5-6"></a>
### 5.6 Server → 外部系统：Webhook ★★

- Plain idea：事件发生时，我们 POST 到对方给的 URL
- 怎么做
  1. 对方注册 URL 和订阅的事件
  2. 事件发生 → 入队 → worker 发 POST
  3. 带签名（HMAC）让对方验证
  4. 失败指数退避重试，最终进 DLQ
- 必提：**对方必须幂等**（会重复投递）；带 event id
- 何时用：支付结果通知、CI 回调、长任务完成通知
- 🗣 "Webhooks are at-least-once, signed with HMAC, retried with backoff, and carry an event id for dedup."

<a id="s5-6-1"></a>
#### 5.6.1 Schema、原则、payload

- Schema：OpenAPI 3.1 的 `webhooks` 段，或遵循 Standard Webhooks 规范
- 原则
  - 签名覆盖 `id.timestamp.body`，接收方校验并拒绝过旧时间戳（防重放）
  - 对方 2xx = 成功；其他都重试
  - 薄 payload（只给 id，对方回查）更安全；胖 payload 更方便
  - 提供"重新发送"和投递日志页面
- Payload

```http
POST https://merchant.example.com/hooks/payments HTTP/1.1
Content-Type: application/json
webhook-id: evt_2Lz9
webhook-timestamp: 1794170000
webhook-signature: v1,K5oZfzN95Z9UVu1EsfQmfVNQhnkZ2pj9o9NDN/H/pI4=

{"id": "evt_2Lz9", "type": "payment.succeeded", "created": 1794170000,
 "data": {"payment_id": "pay_88", "amount_cents": 4599, "currency": "USD"}}
```

- 变体（穷举）
  - 胖 payload vs 薄 payload（只给 id）
  - 每事件一次 vs 批量投递
  - 推（webhook）vs 让对方拉（事件列表 API + cursor）
  - CloudEvents HTTP binding（元数据放在 `ce-*` header）

<a id="s5-7"></a>
### 5.7 多步流程：Saga ★★

- Problem：跨多个服务的业务（下单 → 扣库存 → 扣款），没有分布式事务

| 方式 | 怎么做 | 好处 | 代价 | 选择条件 |
|---|---|---|---|---|
| Choreography（协同） | 每个服务听事件、发事件 | 去中心、松耦合 | 流程分散，难追踪 | 步骤少 |
| Orchestration（编排） | 一个编排器按顺序调各服务 | 流程清晰、好监控 | 编排器是中心 | 步骤多、要补偿 |

- 失败时：执行**补偿动作**（退款、释放库存）
- Tier 3：Temporal、AWS Step Functions、Camunda；协同用 Kafka
- 🗣 "Orchestrated saga with Temporal: each step has a compensating action."

<a id="s5-7-1"></a>
#### 5.7.1 Schema、原则、payload

- 两类消息
  - **Command**：编排器 → 服务，"去做 X"，祈使句
  - **Event / Reply**：服务 → 编排器，"X 已完成 / 失败"，过去式
- 原则
  - 所有消息带 `saga_id`（correlation id）和 `step`
  - 每个 command 有对应的补偿 command
  - 每个步骤幂等（重试不会扣两次款）
- Payload

```json
{"type": "ReserveInventory", "saga_id": "S-731", "step": 2,
 "data": {"order_id": "O551", "items": [{"sku": "A1", "qty": 2}]}}

{"type": "InventoryReserved", "saga_id": "S-731", "step": 2,
 "data": {"reservation_id": "R-90", "expires_at": "2026-11-08T20:46:05Z"}}

{"type": "ReleaseInventory", "saga_id": "S-731", "step": 2, "compensation": true,
 "data": {"reservation_id": "R-90"}}
```

- 变体：编排 vs 协同；Temporal workflow（用代码写流程）vs Step Functions（JSON 状态机）

<a id="s5-8"></a>
### 5.8 投递保证 ★★★

- **投递语义**

| 语义 | 含义 | 怎么得到 | 用在 |
|---|---|---|---|
| At-most-once | 可能丢，不重复 | 先 ack 再处理 | metrics 采样、实时位置 |
| At-least-once | 不丢，可能重复 | 处理完再 ack | 默认 |
| Effectively-once | 不丢，效果不重复 | at-least-once + **幂等消费** | 支付、计费、库存 |

- 幂等消费的做法
  - 消息带唯一 id；消费者用去重表 / unique 约束
  - 或者操作本身幂等（set 而不是 increment）
- **顺序**
  - 全局有序：几乎不需要，代价极高
  - 按 key 有序：Kafka partition key、SQS FIFO message group
  - 客户端排序：每条消息带 **seq**，客户端按序展示、发现缺口就补拉
- **重试**：指数退避 + jitter；限制次数；**DLQ** 存放毒消息
- **背压**：消费跟不上时
  - 队列缓冲（短时）
  - 限制生产方（429）
  - 丢弃 / 采样（可接受时）
  - 扩消费者（看 consumer lag）
- Schema 层面的配合
  - 信封里的 `id` 就是去重键
  - `seq` 字段让客户端检测乱序和缺口
  - DLQ 消息额外带 `error`、`attempts`、`first_failed_at`，方便排查
- 🗣 "At-least-once plus idempotent consumers; ordering only per key, and the client reorders by sequence number."

<a id="s5-9"></a>
### 5.9 S↔S 决策树和总表

```
调用方要等结果吗？
├─ 要 ─────────────────────────▶ gRPC（内部）/ REST（跨团队）
└─ 不要
   ├─ 只要一个消费者处理？ ───────▶ Queue（SQS / RabbitMQ）
   ├─ 多个下游都要？
   │  ├─ 要持久 / 重放 ──────────▶ Log（Kafka）
   │  └─ 丢了没关系、要极低延迟 ─▶ Redis Pub/Sub
   ├─ 跨多个服务的业务流程？ ─────▶ Saga（Temporal / 事件）
   └─ 对方是外部系统？ ─────────▶ Webhook
```

| App | 步骤 | 方法 | 原因 |
|---|---|---|---|
| Chat | API → 存储 + 投递 | Kafka（key = chat_id） | 持久、按会话有序 |
| Chat | 投递到用户所在 server | 注册表 + RPC，或 Redis Pub/Sub | 精准路由 |
| Live comment | 写入 → fan-out | Kafka（key = live_id）→ Redis Pub/Sub | 持久 + 低延迟 fan-out |
| Notification | 业务事件 → 通知服务 | Kafka / SNS | 多来源 |
| Notification | 通知服务 → 各渠道 | 每渠道一个 queue（push / email / SMS） | 隔离失败、独立限速 |
| Ad click | 事件采集 | Kafka → Flink 窗口聚合 | 高吞吐、可重放 |
| 订单 | 下单 → 库存 → 支付 | Orchestrated saga | 要补偿 |
| 视频 | 上传完成 → 转码 | Queue（每个任务一个 worker） | 长任务 |
| 搜索 | DB 变更 → 索引 | CDC（Debezium）→ Kafka | 不双写 |
| OCI control plane | 创建资源 | API 写 work request → queue → worker | 异步长任务 |
| 支付 | 结果通知商户 | Webhook | 外部系统 |

<a id="s6"></a>
## 6. 端到端：把 C↔S 和 S↔S 拼起来

<a id="s6-1"></a>
### 6.1 Live comments ★★★（上次的题）

```
Viewer ──SSE──▶ Conn Server ◀── Redis Pub/Sub(live:{id}) ◀── Fan-out svc ◀── Kafka(key=live_id) ◀── Comment API ◀──POST── Commenter
                                                                              └──▶ Comment DB (history)
```

1. 观众：SSE 连到 connection server，订阅 `live_id`
2. 发评论：REST POST（带 Idempotency-Key）→ Comment API
3. API 写 Kafka（按 live_id 分区），立即返回 201
4. 一个消费者写 DB（历史）；另一个做 fan-out
5. Fan-out 发到 Redis channel `live:{id}`
6. 每台有该直播观众的 connection server 收到一次，推给本机观众（SSE `event: comment.created`，`id: seq`）
7. 断线重连：SSE 带 Last-Event-ID，从缓存补最近 N 条
8. 热门直播：服务端每 ~200 ms 推一个 `comment.batch` + 超过阈值时采样

<a id="s6-2"></a>
### 6.2 Chat ★★★

```
A ──WS──▶ ConnSrv1 ─▶ Chat API ─▶ Kafka(chat_id) ─▶ Message store (Cassandra)
                                         └─▶ Delivery svc ─▶ Registry(Redis: B→ConnSrv7)
                                                   ├─ online ─▶ ConnSrv7 ──WS──▶ B
                                                   └─ offline ─▶ APNs/FCM ─▶ B's phone
```

1. A 通过 WebSocket 发 `message.send`，带 `client_msg_id`（幂等）
2. 写 Kafka（key = chat_id 保证会话内有序），回 `message.ack` 给 A（"已发送"）
3. 存储消费者写 Cassandra（主键 chat_id + seq）
4. 投递服务查注册表：B 在线 → 推 `message.new` 到 ConnSrv7；离线 → APNs / FCM
5. B 收到后回 ack → "已送达"；打开 → `receipt.read` → "已读"
6. B 上线后发 `sync.request`（after_seq），拉取缺失消息

<a id="s6-3"></a>
### 6.3 Notification system ★★★

1. 各业务服务发 CloudEvents 事件到 Kafka / SNS
2. 通知服务：查用户偏好、去重（按事件 id）、限频
3. 按渠道放入不同 queue（push / email / SMS）
4. 渠道 worker 调用 APNs / FCM / SES / Twilio，失败退避重试 → DLQ
5. 站内通知：写 DB + 在线用户通过 SSE 推角标

<a id="s6-4"></a>
### 6.4 Uber 位置 ★★

1. 司机 app 每几秒通过 WebSocket / gRPC stream 上报位置
2. 位置服务写入 geo index（Redis GEO / 内存 quadtree），at-most-once 可接受
3. 行程中：乘客通过 WebSocket / SSE 接收该司机位置
4. 匹配请求：REST → 匹配服务查附近司机

## 7. 面试官常追问 + 回答

| 追问 | 回答要点 |
|---|---|
| 为什么不用 polling？ | 算一下：100 万用户 × 每 2 秒 = 50 万 QPS，大部分是空响应；延迟 = 间隔 |
| SSE 和 WebSocket 怎么选？ | 只要服务端推 → SSE（HTTP、自动重连、Last-Event-ID）；双向高频 → WebSocket |
| WebSocket 怎么扩容？ | 无状态 API + 有状态连接层分开；L4 LB；注册表放 Redis；滚动部署时客户端退避重连 |
| 消息怎么找到用户的连接？ | 注册表 user → server，或按房间 pub/sub；见 5.5 |
| 用户离线怎么办？ | 消息先落库；推 APNs / FCM 提示；上线后按 last_seq 拉取 |
| 怎么保证顺序？ | 按会话 key 分区；每条带 seq；客户端按 seq 排，有缺口补拉 |
| 会不会重复？ | 会，at-least-once；client_msg_id / event id 去重 |
| 热门房间怎么办？ | 按 server fan-out 而不是按用户；批量推送；采样；只推给可见窗口 |
| Connection server 挂了？ | 客户端检测心跳超时 → 重连到别的 server → 更新注册表 → 用 Last-Event-ID / last_seq 补发 |
| 心跳间隔怎么定？ | 比 LB / NAT 空闲超时短（常见 30–60 秒量级）；移动端更长以省电 |
| Redis Pub/Sub 丢消息怎么办？ | 它只负责实时那一跳；持久数据在 Kafka / DB；客户端靠 seq 发现缺口补拉 |
| 为什么评论写入要过 Kafka？ | 削峰；写 DB 和 fan-out 两个下游解耦；可重放 |
| 消息格式以后要改怎么办？ | 只加可选字段；Schema Registry 设 BACKWARD；破坏性改动走新版本 + 双写 |
| 为什么 ID 用字符串？ | 64 位整数在 JS 里会丢精度；字符串也方便以后换 ID 方案 |

## 8. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| 重连风暴 | connection server 部署 / 宕机，10 万客户端同时重连 | 连接数骤降再骤升，CPU 飙升 | 客户端指数退避 + jitter；分批滚动部署 |
| 热门房间 fan-out 打爆 | 大主播开播 | 单 channel 消息速率、推送延迟 | 批量、采样、分层 fan-out |
| 消费积压 | 下游变慢 | consumer lag 增长 | 扩消费者；背压；降级（只保核心） |
| 毒消息 | 某条消息总处理失败 | 同一 offset 反复重试 | 次数上限 → DLQ，告警 |
| 重复投递 | at-least-once 重试 | 下游出现重复记录 | 幂等 key、unique 约束 |
| 乱序 | 多分区 / 重试 | 客户端 seq 缺口 | 按 key 分区；客户端按 seq 重排 |
| Schema 不兼容 | 生产者先发了破坏性改动 | 消费者反序列化报错 | Registry 兼容检查；CI 做 breaking-change 检测 |
| Push token 失效 | 用户卸载 / 换机 | APNs / FCM 返回无效 token | 清理 token 表 |
| 注册表过期 | server 挂了没清理 | 推送到不存在的 server | 注册表条目带 TTL，心跳续期 |
