# Ultimate System Design Preparation Plan

This is the operating plan for `1sd/`: what to learn, how to practice, how to measure readiness, and how to compress the work into two or three weeks. Customize the time budget; preserve the learning order and feedback loop.

## 1. Target and quality bar

**Primary target:** Google L4 / Amazon SDE II interview readiness.  
**Forward visibility:** understand what L5 adds without turning every L4 answer into an over-engineered senior design.

The owner profile is backend-heavy: Java 17, Spring Boot, AWS, event-driven systems, and observability. Build on that experience honestly. Do not imply production experience with technologies that are only conceptual.

Before starting a ramp, verify the actual round shape. For a Google/Amazon distributed-system round, use this plan directly. For consultancy, bank, or vendor loops where LLD and Java/Spring depth are more likely, keep the L4 foundation but shift part of the output budget to class modeling, concurrency, transactions, and API implementation. The broader priority context is retained in [`1bp.md`](./1bp.md); it does not lower the answer quality bar here.

A defensible answer has:

- explicit assumptions, functional requirements, and numeric non-functional requirements;
- one estimate that changes an architecture decision;
- a clear request/data flow, API contract, and keyed data model;
- mechanism-level reasoning, not a list of products;
- alternatives, tradeoffs, and the condition that would reverse the choice;
- failure behavior, degraded mode, observability, recovery, and rollout thinking;
- a concise close that states the design's invariant and weakest assumption.

## 3. Readiness outcomes

Question count is not the metric. Readiness means:

1. **Cold-open decomposition:** in under five minutes, bound an unseen prompt, state numeric NFRs, and identify at least 80% of the relevant primitives.
2. **Defensible assembly:** trace one request end to end, define keys and invariants, and defend the major storage/consistency choice under pushback.
3. **Timed performance:** score at least 3/4 on every rubric dimension in three consecutive 45-minute runs.
4. **Recovery:** when a premise changes or a flaw is exposed, revise the design without becoming rigid or restarting the whole answer.

## 4. What to learn, in order

### Stage 0 — Learn the round

Read `0flow.md`. Practice the phase transitions and hard stops before studying more systems. The round tests verbal production under a clock, not document recall.

Deliverable: a blank-board 45-minute outline you can reproduce in two minutes.

### Stage 1 — Build the foundation

Learn `00.base/` in interview order:

1. requirements and NFR prioritization;
2. back-of-envelope estimation;
3. high-level request and data flow;
4. APIs and contracts;
5. data modeling and access patterns;
6. databases, indexing, replication, and transactions;
7. caching and invalidation;
8. queues, streams, ordering, and delivery semantics;
9. consistency and concurrency;
10. partitioning and hot-key handling;
11. reliability, backpressure, and disaster recovery;
12. observability, security, and capacity engineering.

For each concept, be able to answer four questions: What mechanism creates the property? What does it cost? What defeats it? Where would you choose the alternative?

### Stage 2 — Master the transferable primitives

Use the primitive registry in `build.md`. Prioritize the P0 set: fan-out, hot keys, idempotency, sagas, geospatial indexing, consistent hashing, top-K, quorum/replication, delivery semantics, cache invalidation, backpressure, rate limiting, sharding, and inverted indexes.

Deliverable per primitive: a 90-second explanation, one failure mode, one deciding number, and one question where it is the hard part.

### Stage 3 — Assemble core systems

Use `01.core/` and the design chapters in `1AX/`. Start with rate limiting, distributed cache, IDs, key-value storage, API gateway, locking, CDN/load balancing, notifications, feeds, chat, and search autocomplete.

Do not read a full reference before a cold attempt. Skeletons are prompts; completed packets are post-attempt review material.

### Stage 4 — Expand by pattern, not by product name

Use Alex Xu chapters to compare recurring patterns:

- read-heavy lookup: URL shortener, CDN, cache, object storage;
- fan-out and realtime: news feed, notifications, chat, nearby friends;
- partitioned state: key-value store, message queue, metrics, ad aggregation;
- correctness under contention: reservation, payment, wallet, stock exchange;
- media/data pipelines: YouTube, crawler, Maps, Drive.

Focus on the delta between designs. If two questions exercise the same primitives, one full run plus one five-minute cold-open is enough.

### Stage 5 — Add domain breadth

Sample the categorized folders only after the core transfers. Choose questions that introduce a missing primitive or a company-relevant domain. Avoid reading every skeleton merely to mark coverage.

## 5. The practice loop

### A. Cold-open — 5 minutes

Use three to five times per week.

1. State the user and bounded scope.
2. Give three to five functional requirements and explicit non-goals.
3. Rank numeric NFRs.
4. Name the primitives and likely hard part.
5. Compare against the packet; log misses by cause.

### B. Focused defense — 20 minutes

Use after a cold-open or weak timed phase.

1. Draw the request/data flow.
2. State keys, ownership, and the correctness invariant.
3. Defend one major choice against two alternatives.
4. Answer three escalating pushbacks: mechanism, scale/failure, premise reversal.

### C. Full run — 45 minutes plus 15 minutes review

Use two or three times per week during an interview ramp.

1. Speak aloud and record the attempt.
2. Follow the hard stops in `0flow.md`.
3. Self-grade before reading the reference.
4. Replay only the two weakest phases.
5. Log the failure cause and one corrective drill.

Budget roughly **30% intake / 70% output**. Reading is the remedy for a mechanism gap, not for sequencing or articulation gaps.

## 6. Scoring rubric

Score 1–4. A 3 is the L4 target-hire bar; a 4 is an L5-visible signal.

| Dimension | 3 — target hire | 4 — senior visibility |
| --- | --- | --- |
| Scoping | Bounded scope and named non-goals | Proposed a scope cut and stated what it buys |
| Estimation | Number changed a decision | Number killed an option in real time |
| Architecture | End-to-end trace with keyed data model | Ranked NFRs visibly govern the design |
| Deep dive | Algorithm, state, concurrency, and failure | Mechanism-level failure semantics and migration |
| Tradeoffs | Alternative and reason rejected | Flip condition and second-order consequence |
| Failure/ops | Blast radius, signal, mitigation, degraded mode | Rollout, recovery, cost, and operational ownership |
| Communication | Drove phases and recovered from interruption | Named time cuts and reframed pushback crisply |

The weakest dimension gates readiness. Do not average away a 2.

## 7. Customizable time model

Choose a daily block and scale the number of reps, not the learning order.

| Available time | Recommended block |
| --- | --- |
| 30 min | 1 cold-open + 1 primitive recall + 10-minute defense |
| 60 min | 1 full 45-minute run + rapid grade, or 2 focused defenses |
| 90 min | 1 full run + review + targeted concept repair |
| 120 min | 1 full run + review + 2 cold-opens; avoid a second full run |

If coding or another interview dimension is the current bottleneck, keep system design to maintenance mode: two cold-opens and one focused defense per week.

## 8. Two-week intensive schedule

Use when the interview is close and fundamentals are partly familiar. Default load: 90–120 minutes/day, six days/week.

| Day | Learn | Produce |
| --- | --- | --- |
| 1 | `0flow`, requirements, NFRs | 3 cold-opens; record the five-minute opening |
| 2 | Estimation, APIs, data modeling | 2 estimation drills + one core skeleton |
| 3 | Databases, replication, consistency | Full run: key-value store or URL shortener |
| 4 | Caching, partitioning, hot keys | Focused defenses: distributed cache + rate limiter |
| 5 | Messaging, idempotency, sagas | Full run: notification or payment flow |
| 6 | Reliability, backpressure, observability | Failure-table drill on Days 3 and 5 |
| 7 | Review only | Scorecard review; repair the two weakest primitives |
| 8 | Fan-out, presence, ordering | Full run: feed or chat |
| 9 | Geospatial, top-K, search | 3 cold-opens across Maps/leaderboard/autocomplete |
| 10 | CDN, object/media delivery | Full run: CDN, YouTube, or object storage |
| 11 | Correctness under contention | Focused defenses: reservation, wallet, distributed lock |
| 12 | Multi-region, DR, security | Full run with a region-failure premise reversal |
| 13 | Company-shaped breadth | Two unseen cold-opens + adversarial mock |
| 14 | Consolidate | Final full run; review failure log; learn nothing new |

## 9. Three-week balanced schedule

Use when building from a rustier foundation. Default load: 60–90 minutes/day, five or six days/week.

### Week 1 — Foundation and primitives

- Day 1: flow, scope, NFR ranking, three cold-opens.
- Day 2: estimation, APIs, data models, two decision-forcing calculations.
- Day 3: databases, indexing, replication, consistency.
- Day 4: caching, sharding, hot keys, consistent hashing.
- Day 5: messaging, delivery semantics, idempotency, sagas.
- Day 6: reliability, backpressure, observability, security.
- Day 7: off or recall-card review.

Checkpoint: explain every P0 primitive in 90 seconds and score at least 80% on two cold-opens.

### Week 2 — Core assembly

- Day 8: rate limiter and distributed cache focused defenses.
- Day 9: full run — key-value store or unique ID generator.
- Day 10: API gateway, load balancer, and CDN comparison.
- Day 11: full run — notification, feed, or chat.
- Day 12: search, crawler, top-K, and geospatial cold-opens.
- Day 13: full run — payment, reservation, or wallet.
- Day 14: scorecard and failure-log repair.

Checkpoint: no rubric dimension below 3 on one recorded run.

### Week 3 — Adversarial performance

- Day 15: full unseen run with strict phase hard stops.
- Day 16: targeted mechanism repair from the failure log.
- Day 17: premise-reversal drills on two prior designs.
- Day 18: full company-relevant run; add behavioral story hooks honestly.
- Day 19: multi-region outage, hot partition, and dependency-failure drills.
- Day 20: final unseen run and compact review cards.
- Day 21: rest or light verbal recall; no new material.

Checkpoint: three consecutive runs with every dimension at 3 or above.

## 10. Failure log and corrective action

Log failures by cause, not question name.

| Cause | Symptom | Corrective drill |
| --- | --- | --- |
| Scope | Too many questions; no bounded MVP | Five-minute propose-and-confirm openings |
| Estimation | Math never changes the design | Ten number-to-decision drills |
| Mechanism | Cannot explain how the property is created | Read one `00.base` topic or primitive card |
| Assembly | Knows pieces but cannot connect them | Cold-open unseen recombinations |
| Sequencing | Runs out of time before failures | Visible phase timer with hard stops |
| Articulation | Correct idea, vague explanation | Re-say the phase in 90 seconds |
| Pushback | Defends the first answer rigidly | Alternative + flip-condition ladder |

## 11. Build and generation gates

- Follow `build.md` whenever generating or updating a question answer.
- Default to one-page skeletons. Generate full 45-minute artifacts only for priority questions and only after a cold attempt.
- Keep L4 as the default. Mark L5 additions as separable deltas.
- Cite precise numbers or label them as assumptions/order-of-magnitude estimates.
- Never invent production incidents or personal experience.
- Update `1index.md` whenever a question is added, moved, renamed, or deduplicated.

## 12. Anti-patterns

- Reading the solution first.
- Silent-only practice.
- Treating question count as progress.
- Naming products without mechanisms and costs.
- Designing active-active multi-region before requirements justify it.
- Spending ten minutes on estimation that forces no decision.
- Building more repository structure when the failure log calls for speaking reps.

## 13. Reference hierarchy

Use primary sources for mechanics and operations: *Designing Data-Intensive Applications*, Google SRE material, AWS Builders' Library, and official technology documentation. Use Alex Xu for interview decomposition and pattern recognition, then validate implementation-specific claims against primary sources.
