# Volume 1, Chapter 13: Design A Search Autocomplete System

Design a service that returns relevant query suggestions as a user types, with low tail latency, high read volume, and regularly refreshed rankings.

## Scope decisions to make

- Prefix suggestions for text queries; defer semantic and personalized ranking initially.
- Separate offline/streaming aggregation from the online serving path.
- Define moderation, locale, and freshness boundaries.

## Non-functionals to pin down

- Peak keystroke QPS, p99 latency, result count, freshness SLA, and availability.
- Query corpus size, prefix distribution, and acceptable ranking approximation.

## The estimation that decides something

Estimate keystroke amplification and the serving index size. Use prefix skew to decide cache policy and whether popular-prefix results must be precomputed.

## Skeleton diagram

```text
Query logs -> aggregate/rank -> build versioned prefix index -> serving fleet
User typing -> API/cache -------------------------------------> top-K lookup
```

## The hard part

Choose the prefix data structure and update model: trie/radix tree or prefix-keyed top-K lists, sharding, versioned rollout, and ranking freshness without mutating the serving index unsafely.

## Tradeoffs to defend

- Trie lookup versus precomputed prefix-to-top-K records.
- Batch rebuild versus streaming incremental updates.
- Global popularity versus personalization and privacy.
- Exact ranking versus memory and update cost.

## Top failure mode

A hot short prefix overloads a shard or a partial index rollout returns inconsistent results. Cover caching, replication, immutable versions, atomic activation, and rollback.

## Pushback ladder

1. How is top-K stored and updated for each prefix?
2. Trends must appear within seconds at 10× query volume. What changes?
3. Results must be personalized while preserving privacy. Which path is replaced?
