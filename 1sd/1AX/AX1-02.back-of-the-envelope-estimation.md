# Volume 1, Chapter 2: Back-of-the-envelope Estimation

Estimation is useful only when it removes an option, sizes a boundary, or exposes a bottleneck. Use [`../00.base/02.back-of-envelope-estimation.md`](../00.base/02.back-of-envelope-estimation.md) for the detailed concept reference.

## Interview sequence

1. State assumptions as round numbers.
2. Compute average and peak throughput.
3. Size the dominant payload, hot set, retained state, or concurrent connections.
4. State uncertainty as a range or sensitivity.
5. Say the architecture decision the result forces.

## Minimal formula set

- `average QPS = operations per day / 86,400`
- `peak QPS = average QPS × burst factor`
- `storage = writes × bytes/write × retention × replication/overhead`
- `bandwidth = requests/sec × bytes/request`
- `concurrency = arrival rate × average service time` (Little's Law)
- `fan-out work = source writes × recipients/write`

## Decision examples

| Result | Decision it can force |
| --- | --- |
| Hot set fits memory with headroom | Cache can absorb the dominant read path |
| One partition exceeds write capacity | Change the key, salt it, or aggregate locally |
| Fan-out work exceeds worker budget | Use a hybrid push/pull split |
| Egress dominates cost | Add CDN, compression, tiering, or lower-fidelity variants |
| Concurrent connections dominate | Size by sockets/memory and use event-driven I/O |

## Failure modes

- Computing averages and ignoring peaks or skew.
- Presenting false precision from invented inputs.
- Spending five minutes on arithmetic that changes nothing.
- Estimating global totals but not the hottest key, shard, tenant, or region.

## Recall card

Given any prompt, produce one estimate in 90 seconds and finish with: “Therefore I will choose/reject X.”
