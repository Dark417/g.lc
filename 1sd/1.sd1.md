## 0. 怎么用这份文档

- 每个节点、每条边，都按同一个顺序想
  1. **Problem**：它要解决什么问题
  2. **Factors**：决定选择的变量（QPS、latency、consistency、成本、运维）
  3. **Options**：有哪些做法（Tier 2 功能 / Tier 3 框架）
  4. **Tradeoff**：每个做法付出什么
  5. **Pick**：在什么条件下选哪个，一句话
- 这正好对应上次 SD 的 feedback
  - 没有数字 → 第 2 步强制写 factors
  - 组件没对上问题 → 第 1 步先写 problem
  - 没讲 data flow → 第 5、6 节全是"边"，边就是 data flow
- 标记
  - ★★★ 必须会讲，★★ 应该会，★ 知道名字即可

<a id="s1"></a>
## 1. 面试流程与时间分配

- 可用时间其实比标称少
  - 45 min 面试：开场 + 结尾提问约 8–10 min → 设计约 35 min
  - 60 min 面试：开场 + 结尾约 10–15 min → 设计约 45–50 min

<a id="h1"></a>
### 时间表

| 步骤 | 做什么 | 45 min（设计 ~35） | 60 min（设计 ~47） | 出口检查 |
|---|---|---|---|---|
| 1 Requirements | functional 3–5 条 + non-functional | 4 min | 5 min | 面试官点头确认 |
| 2 Estimation | QPS、storage、read:write、peak | 3 min | 4 min | 每个数字指向一个设计决定 |
| 3 API | 每个 API 对应一条 requirement | 3 min | 5 min | 逐条能指回 requirement |
| 4 Data model | 主表 / key / partition key | 3 min | 5 min | 说出访问模式 |
| 5 High-level + data flow | 画框 + write path + read path | 10 min | 13 min | 每个组件一句"职责" |
| 6 Deep dive | 1–2 个瓶颈 | 9 min | 12 min | 有 tradeoff 和选择 |
| 7 Failure + wrap-up | failure modes、监控、下一步 | 3 min | 3 min | 说出 1–2 个改进 |

- 45 min 版本的取舍
  - Data model 可以并进 step 5，边画边说
  - Deep dive 只挑 1 个，面试官指定的优先
- 60 min 版本
  - Deep dive 做 2 个：一个 scale，一个 consistency / failure
- 🗣 开场一句："I'll spend ~5 minutes on requirements and numbers, then API, then walk the write and read paths, and leave ~10 minutes for deep dives."

<a id="h2"></a>
### 每一步的模板句

- Requirements
  - "Functional: users can X, Y, Z. Out of scope: A, B."
  - "Non-functional: p99 < N ms, availability 99.9x, consistency: eventual is OK for X, strong for Y."
- Estimation
  - "DAU 10M × 20 writes/day ≈ 200M/day ≈ 2.3k/s avg, ~5x peak ≈ 12k/s → one DB primary is not enough, so we partition."
- Data flow
  - "A write goes: client → LB → API service → Kafka → consumer → DB. The API returns after Kafka ack, so latency is bounded by one broker write."

## 2. 总蓝图：节点和边

```
Client
 ├─ DNS ──────────────▶ CDN  (static files, media)
 ├─ HTTPS ────────────▶ LB ─▶ API Gateway ─▶ Services
 │                                             ├─▶ Cache ─▶ DB (primary ⇄ replicas)
 │                                             ├─▶ MQ / Log ─▶ Workers ─▶ Object Store / Search
 │                                             └─▶ Pub/Sub ─▶ Connection Tier
 └─ WebSocket / SSE ◀──────────────────────────────────────── Connection Tier

贯穿全部: Coordination (etcd / ZK), Observability (metrics / logs / traces)
```

- 节点 = 一种能力（存、算、转发、排队）
- 边 = 一种交互（协议 + 一致性 + 失败处理）
- 一道题 = 选出几条关键的边，把它们走通

<a id="s3"></a>
## 3. 三层模型：Node → Function → Implementation

```
Tier 1  Node            Load Balancer
Tier 2  Function        L4 转发 · L7 路由 · health check · TLS 终止
Tier 3  Implementation  AWS NLB · ALB · Envoy · NGINX · HAProxy
```

- Tier 1：这个盒子叫什么
- Tier 2：它具体干哪几件事（面试里讲这一层最多）
- Tier 3：用什么实现
  - 同一个 Tier 2 功能，可以有不同框架，tradeoff 不同
- 比较发生在两层
  - Tier 2 之间：例如 L4 vs L7，push vs pull
  - Tier 3 之间：例如 Kafka vs SQS vs RabbitMQ

<a id="s4"></a>
## 4. 单节点 Single Nodes

<a id="s4-1"></a>
### 4.1 DNS / GSLB ★★

- Problem：把用户送到最近、健康的 region
- Factors：用户地理分布、failover 速度、TTL
- Tier 2
  - 名字解析
  - Geo / latency routing：按位置选 region
  - Health-based failover
  - Weighted routing：灰度、迁移
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Route 53 / OCI DNS | 托管，带 health check | 受 TTL 限制，切换慢（分钟级） | 默认 |
| Anycast（Cloudflare） | 网络层就近，切换快 | 需要自有网络 / 供应商 | 全球低延迟入口 |

- The catch：DNS 缓存在客户端，TTL 越短切换越快，查询量越大
- 🗣 "DNS gets users to a region; LBs handle failures inside the region."

<a id="s4-2"></a>
### 4.2 CDN ★★★

- Problem：静态 / 大文件离用户太远，源站扛不住读流量
- Factors：内容是否可缓存、更新频率、命中率、私有内容
- Tier 2
  - Edge cache：就近返回
  - Pull vs push：被动回源 vs 主动预热
  - Invalidation：purge 或 versioned URL
  - Signed URL：保护私有内容
  - TLS 终止、DDoS 吸收
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| CloudFront / OCI CDN | 和对象存储集成 | 绑定云厂商 | 默认 |
| Cloudflare / Akamai | 节点多，安全能力强 | 成本、配置复杂 | 全球、大流量 |

- Pull vs push（Tier 2 对比）
  - Pull：简单，冷启动第一次慢
  - Push：热门内容提前到位，要管理存储和过期
- 🗣 "Use versioned URLs instead of purges; purges are slow and eventually consistent."

<a id="s4-3"></a>
### 4.3 Load Balancer ★★★

- Problem：把请求分到多台机器，去掉坏掉的机器
- Factors：协议（TCP/HTTP）、是否要按内容路由、连接数、长连接
- Tier 2
  - L4 转发：按 IP/端口，快，不看内容
  - L7 路由：按 path/header/cookie
  - Health check：踢掉坏节点
  - 算法：round robin、least connections、consistent hashing（粘性）
  - TLS termination
- Tier 2 对比

| 功能 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| L4 | 低延迟，适合长连接（WebSocket） | 不能按 URL 路由 | 连接层、非 HTTP |
| L7 | 智能路由、可做认证 | 每个请求要解析，多一点延迟 | HTTP 服务默认 |

- Tier 3：AWS NLB（L4）· ALB（L7）· Envoy · NGINX · HAProxy
  - Envoy：现代 L7，mesh 常用，配置复杂
  - NGINX：通用、成熟
  - HAProxy：高性能 L4/L7，配置简单
- 🗣 "L4 for WebSocket fleets, L7 for HTTP APIs."

<a id="s4-4"></a>
### 4.4 API Gateway ★★★

- Problem：所有外部请求的统一入口，做横切关注点
- Factors：认证方式、限流粒度、多租户、协议转换
- Tier 2
  - Authentication / authorization（JWT、OAuth）
  - Rate limiting / quota（per user / per tenant）
  - Routing / versioning
  - Request validation、协议转换（REST → gRPC）
  - Aggregation（BFF）
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| AWS API Gateway / OCI API GW | 托管，零运维 | 延迟和成本随调用量涨，限制多 | 中小流量、快速上线 |
| Kong / Envoy-based | 自托管、插件多 | 要运维 | 大流量、定制需求 |
| Spring Cloud Gateway | Java 生态、易定制 | 自己扛性能 | 团队 Java 为主 |

- The catch：gateway 是单点和热点，要无状态 + 水平扩展
- 🗣 "The gateway owns auth and rate limiting, so services stay focused on business logic."

<a id="s4-5"></a>
### 4.5 Realtime Connection Tier ★★★

- Problem：服务端要主动推消息给客户端（聊天、live comment、通知）
- Factors：并发连接数、消息频率、单向还是双向、移动端耗电
- Tier 2
  - 维持长连接（WebSocket / SSE）
  - 连接注册表：user → 哪台 connection server
  - Fan-out：一条消息推给 N 个连接
  - 心跳、重连、离线补发
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Netty / Spring WebFlux 自建 | 控制力强，单机连接数高 | 自己处理扩容和状态 | 大规模核心功能 |
| Socket.IO | 自动降级、房间概念 | Node 生态，扩容要 Redis adapter | 快速开发 |
| AWS API GW WebSocket / AppSync | 托管 | 单价高，延迟不可控 | 小中规模 |

- The catch：连接是有状态的，扩容和部署都要处理断线重连
- 🗣 "Connection servers are stateful; I keep them thin and put routing state in Redis."

<a id="s4-6"></a>
### 4.6 Service Tier（计算层） ★★

- Problem：跑业务逻辑，要能水平扩展
- Factors：流量是否突发、冷启动容忍度、团队运维能力
- Tier 2
  - 无状态处理（状态放到 cache / DB）
  - Autoscaling
  - Service discovery
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Kubernetes（OKE / EKS） | 灵活、生态最全 | 运维复杂 | 多服务、长期运行 |
| ECS / 托管容器 | 简单 | 灵活度低 | 中等规模 |
| Lambda / OCI Functions | 按调用付费、零运维 | 冷启动、时长限制 | 突发、事件驱动 |

- 🗣 "Stateless services let me scale by adding instances behind the LB."

<a id="s4-7"></a>
### 4.7 Cache ★★★

- Problem：DB 读太慢 / 太贵，热点数据重复读
- Factors：读写比、能接受的旧数据时间、数据大小、命中率
- Tier 2
  - Key-value 读写、TTL
  - Eviction：LRU / LFU
  - 数据结构：sorted set（排行榜）、counter（限流）、pub/sub
  - 分布式：分片（consistent hashing）、复制
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Redis | 数据结构丰富，持久化可选，pub/sub | 单线程模型，大 key 有风险 | 默认 |
| Memcached | 多线程，纯 KV 简单 | 无持久化、无数据结构 | 只要简单大 KV 缓存 |
| 本地 cache（Caffeine） | 最快，无网络 | 多实例间不一致 | 极热、可容忍不一致 |

- The catch：缓存失效和一致性是主要难点（见 5.5）
- 🗣 "Cache is for latency and DB offload, never the source of truth."

<a id="s4-8"></a>
### 4.8 Relational DB ★★★

- Problem：需要事务、关系、复杂查询
- Factors：是否需要 ACID、写 QPS、数据量、join 需求
- Tier 2
  - ACID 事务、索引、join
  - 复制：primary + read replicas
  - 分片：按 key 拆库
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| PostgreSQL / MySQL | 成熟、通用 | 单 primary 写上限 | 默认 |
| Aurora / OCI MySQL HeatWave | 托管，存储自动扩展 | 绑定云 | 云上默认 |
| Spanner / CockroachDB | 全球强一致 + 自动分片 | 写延迟更高、成本高 | 跨区强一致 |

- 🗣 "I start with Postgres; I shard only when write QPS or data size forces it."

<a id="s4-9"></a>
### 4.9 NoSQL ★★★

- Problem：海量数据、高写入、访问模式简单（按 key）
- Factors：访问模式是否固定、一致性要求、写 QPS
- Tier 2（按类型）
  - KV：按 key 读写
  - Wide-column：partition key + clustering key，适合时间序列、消息
  - Document：灵活 schema
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| DynamoDB / OCI NoSQL | 托管，自动扩展 | 访问模式要提前设计，热分区 | KV、可预测访问 |
| Cassandra | 高写入、多 region | 运维复杂，最终一致 | 写多、时间序列、消息 |
| MongoDB | schema 灵活 | 大规模分片调优难 | 文档型、需求多变 |

- 🗣 "Wide-column with (chat_id, timestamp) as key gives me ordered message history per chat."

<a id="s4-10"></a>
### 4.10 Message Queue / Log ★★★

- Problem：解耦生产和消费、削峰、异步处理、一份数据多方消费
- Factors：是否需要顺序、能否重放、吞吐、投递语义
- Tier 2
  - Queue：一条消息给一个消费者（任务分发）
  - Pub/Sub：一条消息给多个订阅者
  - Log / stream：持久化 + 可重放 + 分区内有序
  - 投递语义：at-most-once / at-least-once / effectively-once
  - DLQ、重试、延迟消息
- Tier 2 对比

| 模型 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Queue | 简单，按任务扩消费者 | 消费完就没了，不能重放 | 任务处理 |
| Log | 可重放，多消费组，分区有序 | 运维重，分区数决定并行度 | 事件流、多下游 |

- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Kafka / OCI Streaming | 高吞吐、可重放、分区有序 | 运维和调优重 | 事件流、ingestion |
| SQS / OCI Queue | 托管、简单、自动扩展 | 无重放，FIFO 吞吐有限 | 任务队列 |
| RabbitMQ | 灵活路由、低延迟 | 吞吐不如 Kafka | 复杂路由 |
| Redis Pub/Sub / Streams | 极低延迟 | 持久性弱 | 实时 fan-out |

- 🗣 "Kafka keeps order within a partition, not across partitions, so I pick the partition key by what must stay ordered."

<a id="s4-11"></a>
### 4.11 Object Storage ★★

- Problem：存大文件（图片、视频、备份），便宜且耐久
- Factors：文件大小、访问频率、耐久性要求
- Tier 2
  - PUT/GET 整个对象，按 key
  - Multipart upload、presigned URL
  - 生命周期：冷热分层
- Tier 3：S3 / OCI Object Storage / GCS（基本等价）
- The catch：不能就地修改，延迟比 KV 高
- 🗣 "Metadata in a DB, bytes in object storage."

<a id="s4-12"></a>
### 4.12 Search Index ★★

- Problem：全文搜索、模糊匹配、多字段过滤
- Factors：数据更新延迟容忍度、查询复杂度
- Tier 2
  - 倒排索引
  - 相关性排序、聚合
- Tier 3：Elasticsearch / OpenSearch（默认）· Solr
- The catch：不是 source of truth，靠 CDC 同步，会有延迟
- 🗣 "Search is a derived view, fed from the DB through CDC."

<a id="s4-13"></a>
### 4.13 Workers / Scheduler ★★

- Problem：耗时任务、定时任务、批处理
- Factors：任务时长、是否要精确时间、重试和幂等
- Tier 2
  - 从队列拉任务、重试、超时
  - 定时触发
  - 分布式调度：保证一个任务只被一个 worker 执行
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Queue + worker pool | 简单 | 定时能力弱 | 异步任务 |
| Airflow | DAG 依赖、可视化 | 不适合低延迟 | 数据管道 |
| Temporal | 长流程、自动重试、状态持久 | 学习成本 | 业务工作流 |
| Quartz / cron + lock | 简单定时 | 要自己处理单点 | 小规模定时 |

<a id="s4-14"></a>
### 4.14 Coordination ★★

- Problem：多节点之间就"谁是 leader / 配置是什么"达成一致
- Tier 2：leader election、分布式锁、配置存储、服务注册
- Tier 3：etcd · ZooKeeper · Consul（都基于 Raft / ZAB 类共识）
- The catch：写吞吐低，只存少量关键元数据
- 🗣 "I use etcd for leader election with a lease, plus fencing tokens so a stale leader can't write."

<a id="s4-15"></a>
### 4.15 Observability ★★

- Problem：知道系统是否健康、坏了在哪
- Tier 2：metrics、logs、traces、alerting
- Tier 3：Prometheus + Grafana · ELK / OpenSearch · OpenTelemetry + Jaeger · Datadog
- 🗣 "I alert on SLO burn rate, not on every error."

<a id="s5"></a>
## 5. 两节点组合 Edges

<a id="s5-1"></a>
### 5.1 Client ↔ Gateway：协议 ★★★

- Problem：客户端和服务端怎么交换数据
- Factors：谁主动发起、频率、双向还是单向、浏览器 / 移动端、穿透代理
- Tier 2：协议对比

| 协议 | 方向 | 好处 | 代价 | 选择条件 |
|---|---|---|---|---|
| REST / HTTP 1.1 | 客户端拉 | 简单、缓存友好 | 冗余字段、多次往返 | 默认 CRUD |
| GraphQL | 客户端拉 | 一次取所需字段 | 缓存难、复杂查询会压垮后端 | 多端、字段需求多变 |
| gRPC（HTTP/2） | 双向流可选 | 高效二进制、强类型 | 浏览器支持差 | 服务间、移动端 |
| Short polling | 客户端拉 | 最简单 | 浪费请求、延迟 = 间隔 | 低频、可接受延迟 |
| Long polling | 客户端拉 | 比短轮询省 | 每条消息一次重连 | 无法用 WebSocket 时兜底 |
| SSE | 服务端推（单向） | 基于 HTTP，自动重连 | 只能单向 | live comment、通知、股价 |
| WebSocket | 双向 | 低延迟、全双工 | 有状态连接，扩容难 | 聊天、协作、游戏 |
| WebRTC | P2P | 音视频延迟最低 | 需 STUN/TURN，复杂 | 视频通话 |

- 上次的坑：live comment 用了 client polling
  - 正确思路：读远多于写、服务端推、单向 → SSE 或 WebSocket
- Tier 3：同一协议，不同框架

| 协议 | 框架 | 好处 | 代价 |
|---|---|---|---|
| REST | Spring MVC | 成熟，阻塞模型简单 | 每请求一线程，高并发吃内存 |
| REST | Spring WebFlux | 非阻塞，连接多时省资源 | 调试难 |
| gRPC | grpc-java | 官方、性能好 | 需要 proto 管理 |
| WebSocket | Netty | 单机连接数高 | 底层，开发量大 |
| WebSocket | Spring WebSocket / STOMP | 集成方便 | 性能不如 Netty |
| WebSocket | Socket.IO | 自动降级、房间 | 非 Java，扩容靠 Redis adapter |
| SSE | Spring WebFlux `Flux` | 实现简单 | 每连接占资源 |

- 🗣 "Reads dominate and only the server pushes, so SSE is enough; WebSocket if clients also send frequently."

<a id="s5-2"></a>
### 5.2 Client ↔ CDN ★★

- Problem：静态和媒体内容就近返回
- Factors：可缓存性、私有性、更新频率
- Tier 2
  - Cache key 设计（是否含 query、header）
  - TTL 与 versioned URL
  - Signed URL / cookie
  - Range request（视频分段）
- Tier 3：CloudFront / OCI CDN / Cloudflare（见 4.2）
- 🗣 "Video segments are immutable, so they cache forever with versioned names."

<a id="s5-3"></a>
### 5.3 Gateway ↔ Services：同步调用 ★★★

- Problem：入口请求转给正确的后端服务
- Factors：延迟预算、服务数量、故障隔离
- Tier 2
  - Service discovery：服务实例在哪
  - 负载均衡：客户端侧 vs 服务端侧
  - 超时、重试、circuit breaker
  - mTLS
- Tier 3

| 实现 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| K8s Service + DNS | 自带，简单 | 功能有限 | 默认 |
| Service mesh（Istio / Linkerd） | 重试、mTLS、观测统一 | 复杂、sidecar 开销 | 服务多、安全要求高 |
| 客户端库（Resilience4j） | 精细控制 | 每种语言都要实现 | Java 服务 |

- The catch：重试会放大流量 → 必须有退避 + jitter + 重试预算
- 🗣 "Timeouts on every hop, retries only on idempotent calls, with exponential backoff and jitter."

<a id="s5-4"></a>
### 5.4 Service ↔ Service：异步 ★★★

- Problem：调用方不想等，或下游会慢 / 挂
- Factors：是否需要结果、顺序、投递语义
- Tier 2

| 方式 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Point-to-point queue | 削峰、负载均衡 | 一个消费者 | 任务 |
| Pub/Sub | 一对多 | 订阅者各自处理失败 | 事件通知 |
| Event log | 可重放、多消费组 | 运维重 | 事件驱动架构 |
| Request-reply over queue | 异步但要结果 | 复杂，需 correlation id | 长任务 |

- Tier 3：Kafka · SQS/SNS · RabbitMQ（见 4.10）
- 🗣 "At-least-once delivery plus an idempotency key gives effectively-once processing."

<a id="s5-5"></a>
### 5.5 Service ↔ Cache ↔ DB ★★★

- Problem：读快，同时不读到太旧的数据
- Factors：读写比、可接受的不一致时间、写频率
- Tier 2：缓存策略

| 策略 | 怎么做 | 好处 | 代价 | 选择条件 |
|---|---|---|---|---|
| Cache-aside | 读 miss 时查 DB 回填；写 DB 后删 cache | 简单，只缓存热数据 | 首次 miss；有短暂不一致 | 默认 |
| Read-through | cache 自己去 DB 取 | 应用代码简单 | 需要 cache 支持 | 托管方案 |
| Write-through | 写 cache 同步写 DB | 读一致性好 | 写延迟加倍 | 读多且要求新鲜 |
| Write-behind | 先写 cache，异步写 DB | 写极快 | cache 挂了丢数据 | 计数、可容忍丢失 |

- 常见问题和解法
  - Thundering herd（热点过期，大量请求打到 DB）→ 单飞锁 / 提前刷新
  - Cache penetration（查不存在的 key）→ 缓存空值 / Bloom filter
  - 删除 cache 失败 → 短 TTL 兜底
- 🗣 "Cache-aside with delete-on-write and a short TTL as a safety net."

<a id="s5-6"></a>
### 5.6 DB ↔ DB：复制与分片 ★★★

- Problem：单库扛不住读 / 写 / 数据量，或要高可用
- Factors：一致性要求、写 QPS、跨 region
- Tier 2：复制方式

| 方式 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| Leader-follower 异步 | 写快，读扩展 | 读副本可能旧，failover 可能丢数据 | 默认 |
| Leader-follower 同步 | 不丢数据 | 写延迟增加 | 金融、元数据 |
| Multi-leader | 多 region 都能写 | 冲突解决复杂 | 跨 region 写 |
| Leaderless quorum（W+R>N） | 高可用、可调一致性 | 读修复、冲突 | Cassandra/Dynamo 类 |

- Tier 2：分片方式
  - Range：范围查询方便，易热点
  - Hash：分布均匀，范围查询难
  - Consistent hashing：扩缩容只迁移少量数据
- Tier 3：Postgres streaming replication · Vitess（MySQL 分片） · Cassandra · Spanner
- 🗣 "3 replicas, W=2, R=2: one node dies, quorum still holds and reads see the latest write."

<a id="s5-7"></a>
### 5.7 DB → Queue：Outbox / CDC ★★★

- Problem：写 DB 同时发消息，两者要一致（dual write 问题）
- Factors：能否接受延迟、是否改应用代码
- Tier 2

| 方式 | 好处 | 代价 | 选择条件 |
|---|---|---|---|
| 直接双写 | 简单 | 一边成功一边失败 → 不一致 | 不推荐 |
| Transactional outbox | 同一事务写 outbox 表，再转发 | 多一张表和一个转发器 | 默认 |
| CDC（读 DB 日志） | 应用无感 | 依赖 binlog / WAL，有延迟 | 已有系统、同步搜索 / 数仓 |

- Tier 3：Debezium（CDC → Kafka）· DynamoDB Streams · OCI GoldenGate
- 🗣 "I never dual-write; outbox in the same transaction, then relay to Kafka."

<a id="s5-8"></a>
### 5.8 Client ↔ Object Storage ★★

- Problem：大文件上传下载不要经过应用服务器
- Tier 2
  - Presigned URL：服务端签名，客户端直传
  - Multipart / resumable upload
  - 上传完成事件 → 触发处理
- Tier 3：S3 / OCI Object Storage + 事件通知
- 🗣 "The API only issues a presigned URL; bytes go straight to object storage."

<a id="s5-9"></a>
### 5.9 Producer → Queue → Consumer ★★★

- Problem：生产比消费快、消费会失败
- Factors：可接受的延迟、失败率、顺序要求
- Tier 2
  - Backpressure：队列积压时限流生产方
  - Retry + 指数退避
  - DLQ：多次失败的消息隔离
  - 幂等消费：idempotency key / 去重表
  - 消费并行度：Kafka = 分区数，SQS = 消费者数
- 🗣 "Consumer lag is my main scaling signal."

<a id="s6"></a>
## 6. 三节点模式 Patterns

- 每个模式 = 一个常见问题的标准解法
- 先认出问题，再套模式

| # | 模式 | 节点链 | 解决的问题 | 关键 tradeoff | 用在哪些题 |
|---|---|---|---|---|---|
| 1 | Realtime fan-out | Service → Pub/Sub → Connection servers → Clients | 一条消息推给很多在线用户 | 热门房间 fan-out 爆炸 → 分层 fan-out / 采样 | live comment、聊天、通知 |
| 2 | Read-heavy | LB → Service → Cache → DB | 读多写少，要低延迟 | 新鲜度 vs 命中率 | URL shortener、商品页 |
| 3 | Write-heavy ingestion | Gateway → Log → Stream processor → Store | 高写入，下游可慢 | 延迟 vs 吞吐，at-least-once | metrics、日志、点击统计 |
| 4 | Async job | API → Queue → Worker → Status store | 长任务不能同步等 | 用户要轮询状态 | OCI control plane、视频转码 |
| 5 | Derived view | DB → CDC → Search / Cache | 多种查询方式 | 同步延迟 | 搜索、推荐 |
| 6 | Rate limit | Gateway → Redis counter | 保护后端、公平 | 精确度 vs 性能 | 限流器 |
| 7 | Media pipeline | Client → Object store → Queue → Transcoder → CDN | 大文件处理和分发 | 成本 vs 处理速度 | YouTube、Instagram |
| 8 | Leader-based work | Scheduler(s) → etcd lease → Workers | 任务只执行一次 | 选主延迟 | 分布式调度器 |

<a id="s6-1"></a>
### 6.1 例：Realtime fan-out（补上次的坑） ★★★

- Problem：一场直播，10 万人同时看评论
- 数字
  - 写：1k comments/s
  - 读：1k × 100k = 1 亿次推送/s（不可能逐条推）
- 设计
  1. Client 通过 SSE 连到 connection server
  2. 写评论：API → Kafka（按 live_id 分区）
  3. Fan-out service 消费，发到 Redis Pub/Sub channel `live:{id}`
  4. 每台 connection server 订阅它负责的 live_id，推给本机连接
  5. 热门直播：服务端每 100 ms 批量推送 + 采样
- 🗣 "Fan-out happens per connection server, not per user, so 100k viewers on 50 servers means 50 publishes, not 100k."
