## 0. One-Minute Version

- **Model from access patterns, not entities**: list the queries with their rates first, then pick stores and keys
- **Store choice follows the dominant pattern**: relational for transactions and flexible queries; KV / wide-column for huge scale by key; search, time-series, object storage for their niches
- **Keys decide everything**: the partition key sets both spread (no hot spots) and locality (one query, one partition)
- **Correctness lives in the database**: isolation levels, conditional writes and unique constraints prevent double booking and lost updates better than app code
- **Scale in order**: indexes → caching → read replicas → partitioning → sharding
- The catch: every scaling step trades something (staleness, cross-shard queries, operational load)
- 🗣 "I list access patterns with rates, choose the store per pattern, then pick a partition key that spreads writes but keeps each query on one partition."

<a id="s1"></a>
## 1. The Modeling Method ★★★

<a id="s1-1"></a>
### 1.1 Seven Steps

1. **Entities**: the nouns (User, Listing, Booking, Message, WorkRequest)
2. **Access patterns**: every read and write the requirements imply, with a rate
3. **Store per pattern**: use the decision table in section 2
4. **Primary key and partition key**: chosen from the hottest pattern
5. **Secondary indexes**: for the remaining patterns
6. **Consistency and transactions**: which writes must be atomic, which reads must be fresh
7. **Lifecycle**: retention, archival, deletion

<a id="s1-2"></a>
### 1.2 Access-Pattern Worksheet

| # | Pattern | Type | Rate (peak) | Freshness | Store / key |
|---|---|---|---|---|---|
| 1 | Get listing by id | Read | 50k/s | Seconds OK | Cache → `listings` PK |
| 2 | Search listings by city + dates | Read | 10k/s | Minutes OK | Search index |
| 3 | Reserve nights for a listing | Write | 500/s | Strong | `listing_night` PK (listing_id, night) |
| 4 | List a guest's bookings | Read | 2k/s | Read-your-writes | Index on `bookings(guest_id, check_in)` |

- Fill this on the whiteboard in step 4; it is the bridge between API and data model
- 🗣 "Pattern 3 needs strong consistency and pattern 2 tolerates minutes of lag, so they live in different stores."

<a id="s2"></a>
## 2. Choosing A Store ★★★

<a id="s2-1"></a>
### 2.1 Decision Tree

```
Need multi-row transactions or ad hoc queries?
├─ Yes ── data fits a sharded / single primary? ──▶ Relational (Postgres / MySQL / Aurora)
│        └─ needs global strong consistency ─────▶ Spanner / CockroachDB
└─ No
   ├─ Access by key, huge scale ────────────────▶ KV (DynamoDB / OCI NoSQL)
   ├─ High writes, ordered per key (time) ──────▶ Wide-column (Cassandra / Bigtable)
   ├─ Full-text / fuzzy / faceted / geo search ─▶ Search index (OpenSearch)
   ├─ Metrics over time ────────────────────────▶ Time-series DB
   ├─ Large blobs ──────────────────────────────▶ Object storage + metadata in a DB
   └─ Hot reads, counters, leaderboards ────────▶ Redis (cache, not source of truth)
```

<a id="s2-2"></a>
### 2.2 Store Types Compared

| Type | Good at | Bad at | Examples |
|---|---|---|---|
| Relational | ACID, joins, constraints, flexible queries | Write ceiling of one primary; sharding is manual | Postgres, MySQL, Aurora |
| Distributed SQL | SQL + horizontal scale + strong consistency | Higher write latency, cost | Spanner, CockroachDB, YugabyteDB |
| Key-value | Predictable latency at any scale | Queries beyond the key; access patterns fixed up front | DynamoDB, OCI NoSQL, Redis |
| Wide-column | Very high write throughput, time-ordered rows per key | No joins, limited secondary indexes, eventual by default | Cassandra, ScyllaDB, Bigtable |
| Document | Flexible nested data, evolving schema | Cross-document transactions and joins are weaker | MongoDB |
| Search | Inverted index, relevance, aggregations, geo | Not a source of truth; near-real-time lag | Elasticsearch, OpenSearch |
| Time-series | Compression, downsampling, time-range queries | General queries | Prometheus, InfluxDB, TimescaleDB |
| Object storage | Cheap durable blobs, lifecycle tiers | No in-place update; higher latency | S3, OCI Object Storage, GCS |
| Graph | Multi-hop relationship queries | Scale-out is hard; rare in interviews | Neo4j, Neptune |

<a id="s2-3"></a>
### 2.3 Polyglot Persistence

- Real systems combine stores: source of truth + derived views
  - Postgres (truth) → CDC → OpenSearch (search) + Redis (hot reads)
- Rule: exactly **one** source of truth per piece of data; everything else is derived and rebuildable
- 🗣 "Postgres is the source of truth for bookings; search and cache are derived views fed by CDC."

<a id="s3"></a>
## 3. Relational In Depth ★★★

<a id="s3-1"></a>
### 3.1 Indexes

- Plain idea: an index is a sorted copy of some columns with pointers to rows, so lookups skip a full scan
- **B-tree index** (default): good for equality, ranges, sorting
- **Composite index order matters**
  - Index `(guest_id, check_in)` serves `WHERE guest_id = ? ORDER BY check_in`
  - It does **not** serve `WHERE check_in > ?` alone (leftmost-prefix rule)
- **Covering index**: includes all columns the query needs → no table lookup
- **Partial index**: only rows matching a condition (`WHERE status = 'ACTIVE'`)
- **Hash / GIN / GiST** (Postgres): equality-only, full-text / JSONB, geo
- The catch
  - Every index slows writes and uses storage
  - Low-selectivity columns (e.g. boolean) rarely help
  - Functions on columns (`WHERE lower(email) = ?`) skip the index unless indexed by that expression
- 🗣 "Composite index (guest_id, check_in) serves the 'my trips' query with no sort step."

<a id="s3-2"></a>
### 3.2 Transactions And Isolation

- Plain idea: a transaction groups writes so they all happen or none do (ACID: atomicity, consistency, isolation, durability)
- Anomalies to know

| Anomaly | What happens | Example |
|---|---|---|
| Dirty read | Read uncommitted data | See a booking that later rolls back |
| Non-repeatable read | Same row read twice gives different values | Price changes mid-checkout |
| Lost update | Two read-modify-writes, one overwrites the other | Two inventory decrements become one |
| Write skew | Two transactions read the same set, each writes something that breaks a rule together | Two doctors both go off-call, leaving none |
| Phantom | A range query returns new rows on re-run | Overlapping booking inserted between check and insert |

- Isolation levels

| Level | Prevents | Still allows | Notes |
|---|---|---|---|
| Read committed | Dirty reads | Lost update, write skew, phantoms | Postgres default |
| Repeatable read / snapshot | Non-repeatable reads, (in Postgres) lost updates via errors | Write skew | MySQL InnoDB default is repeatable read |
| Serializable | All of the above | — | Retries on conflict; more latency |

- MVCC (multi-version concurrency control): readers see a snapshot and don't block writers; old versions are cleaned up later (vacuum in Postgres)
- 🗣 "Read committed is fine for most reads; for booking I use a conditional update or serializable so overlapping reservations can't both commit."

<a id="s3-3"></a>
### 3.3 Concurrency Control

| Technique | How | Good | Cost | Choose when |
|---|---|---|---|---|
| Optimistic | `version` column; `UPDATE ... WHERE id = ? AND version = ?`; retry on 0 rows | No locks, scales | Retries under contention | Low contention (profile edits) |
| Pessimistic | `SELECT ... FOR UPDATE` inside a short transaction | No retries | Blocks others; deadlock risk | High contention, short transactions |
| Conditional write | `UPDATE ... WHERE booking_id IS NULL` | Atomic check-and-set in one statement | Must check rows affected | Claims, reservations, state machines |
| Unique constraint | `UNIQUE (listing_id, night)` | Impossible to violate | Errors to handle | Invariants ("one booking per night") |
| `FOR UPDATE SKIP LOCKED` | Workers grab unlocked rows | Simple DB-backed job queue | DB load at scale | Small/medium job queues |
| Advisory locks | App-defined lock ids | Flexible | Easy to misuse | Rare coordination |

- 🗣 "The database enforces the invariant: a unique key on (listing_id, night) means double booking fails at commit even if the app has a bug."

<a id="s3-4"></a>
### 3.4 Query Patterns

- **Keyset pagination**: `WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 50`
  - Stable and fast at any depth; offset pagination slows down and skips / repeats rows under inserts
- **N+1 queries**: one query for a list, then one per item → batch with `IN (...)` or a join
- **Counting**: `COUNT(*)` on big tables is expensive; keep counters or approximate counts
- **Soft delete**: `deleted_at` column; remember to filter and to index it if needed

<a id="s3-5"></a>
### 3.5 Scaling A Relational Database

| Step | What | Buys | Costs |
|---|---|---|---|
| 1 | Indexes, query fixes | Often 10–100× on bad queries | Write overhead |
| 2 | Connection pooling (PgBouncer, HikariCP) | Many app instances share few DB connections | Pool tuning |
| 3 | Vertical scaling | Simple | Ceiling, cost |
| 4 | Read replicas | Read throughput | Replica lag → stale reads |
| 5 | Cache in front | Read latency, load | Invalidation |
| 6 | Table partitioning (by time / range) | Smaller indexes, fast drop of old data | Partition key in queries |
| 7 | Sharding (app-level, Vitess, Citus) | Write throughput, data size | Cross-shard queries, resharding, ops |

- 🗣 "Before sharding I'd add replicas and a cache, and partition the table by month so old data drops cheaply."

<a id="s4"></a>
## 4. NoSQL In Depth ★★★

<a id="s4-1"></a>
### 4.1 Key-Value: DynamoDB-Style Modeling

- Plain idea: every item has a **partition key** (PK) and optional **sort key** (SK); you can only query efficiently by PK (and ranges on SK)
- How to model
  1. Write down access patterns first (section 1.2)
  2. Pick PK / SK so the main pattern is one `Query` on one PK
  3. Add global secondary indexes (GSIs) for other patterns
- Example: chat messages

| PK | SK | Attributes |
|---|---|---|
| `CHAT#G5` | `MSG#000342` | from, text, ts |
| `USER#U9` | `CHAT#G5` | last_read_seq, muted |

- Single-table design: many entity types in one table, distinguished by key prefixes; fewer round trips, harder to evolve
- Key features
  - **Conditional writes** (`attribute_not_exists`, `version = :v`): atomic check-and-set
  - **Transactions**: up to a bounded number of items per transaction (check current limit)
  - **TTL**: items expire automatically
  - **Streams**: change feed for CDC
  - Capacity: on-demand vs provisioned; adaptive capacity helps but a single hot key is still limited per partition
- The catch: GSIs are eventually consistent; new access patterns may need a new index or a migration
- 🗣 "PK = CHAT#id, SK = MSG#seq, so loading a conversation page is one Query with a range on the sort key."

<a id="s4-2"></a>
### 4.2 Wide-Column: Cassandra-Style Modeling

- Plain idea: rows are grouped by **partition key** and sorted inside the partition by **clustering columns**
- Rules
  - Design one table **per query** (denormalize freely)
  - Keep partitions bounded: time-bucket large keys, e.g. `(chat_id, month)`
  - Partition size guidance is in the tens to ~100 MB range (order of magnitude); unbounded partitions hurt reads and repairs
- Example

```sql
CREATE TABLE messages (
  chat_id   text,
  bucket    text,        -- e.g. '2026-11'
  seq       bigint,
  sender    text,
  body      text,
  PRIMARY KEY ((chat_id, bucket), seq)
) WITH CLUSTERING ORDER BY (seq DESC);
```

- Consistency is tunable per query: `ONE`, `QUORUM`, `ALL`; with RF = 3, `QUORUM` writes + `QUORUM` reads overlap
- Lightweight transactions (`IF NOT EXISTS`) use Paxos: correct but slow; use sparingly
- **Tombstones**: deletes are markers; many deletes in one partition make reads slow until compaction
- 🗣 "Partition by (chat_id, month), cluster by seq descending, so the latest page is one sequential read."

<a id="s4-3"></a>
### 4.3 Document Stores ★

- Store nested JSON documents; index fields inside documents
- Good for aggregates read and written together (an order with its line items)
- The catch: unbounded arrays inside a document grow without limit; cross-document consistency is weaker than SQL

<a id="s5"></a>
## 5. How Storage Engines Work ★★

<a id="s5-1"></a>
### 5.1 B-Tree vs LSM Tree

| | B-tree | LSM tree |
|---|---|---|
| Write path | Update pages in place (plus WAL) | Append to memtable + WAL, flush sorted files (SSTables), merge later (compaction) |
| Reads | One tree walk | Check memtable + several SSTables; Bloom filters skip files |
| Writes | Random I/O | Sequential I/O → high write throughput |
| Space / amplification | Some fragmentation | Write amplification from compaction; temporary space for merges |
| Used by | Postgres, MySQL InnoDB, Oracle DB | Cassandra, RocksDB, ScyllaDB, Bigtable, DynamoDB (internally varies) |

- 🗣 "LSM trees turn random writes into sequential ones, which is why Cassandra handles write-heavy chat history well."

<a id="s5-2"></a>
### 5.2 Other Internals Worth Knowing

- **WAL (write-ahead log)**: every change is logged before it's applied → crash recovery and replication source
- **Bloom filter**: tells "definitely not in this file" → skips disk reads in LSM stores
- **MVCC**: multiple versions per row → readers don't block writers
- **Compaction strategies**: size-tiered (write-optimized) vs leveled (read-optimized)

<a id="s6"></a>
## 6. Partitioning And Sharding ★★★

<a id="s6-1"></a>
### 6.1 Strategies

| Strategy | How | Good | Bad |
|---|---|---|---|
| Range | Split by key ranges | Range scans | Hot spots on sequential keys (time) |
| Hash | `hash(key) % N` or hash ranges | Even spread | Range scans scatter; changing N moves most keys |
| Consistent hashing | Keys and nodes on a ring, virtual nodes | Adding a node moves ~1/N of keys | More complex |
| Directory / lookup | A table maps key → shard | Flexible placement, easy moves | Extra lookup, directory must be HA |
| Geo / tenant | By region or tenant | Data residency, isolation | Uneven sizes |

<a id="s6-2"></a>
### 6.2 Choosing The Partition Key

- Must have **high cardinality** (many distinct values)
- Must spread **writes** evenly (not just data)
- Should keep the **hottest query** on one partition
- Examples
  - Chat: `chat_id` (+ time bucket) — good; `sender_id` — bad for loading a conversation
  - Metrics: `(tenant, series_id)` — good; `timestamp` — every write hits the newest partition
  - Bookings: `listing_id` — keeps a listing's nights together for the conditional update

<a id="s6-3"></a>
### 6.3 Hot Keys

- Causes: celebrity accounts, viral items, a dominant tenant, time-based keys
- Fixes
  - **Salting / write sharding**: `key#0..N-1`, read by scatter-gather
  - **Caching** hot reads (with request coalescing)
  - **Splitting** a big tenant onto dedicated partitions / cells
  - **Sharded counters**: N sub-counters summed on read

<a id="s6-4"></a>
### 6.4 Resharding

- Options
  - Consistent hashing / virtual shards: move a few virtual shards to the new node
  - Double-write migration: write old + new, backfill, verify, switch reads, stop old writes
  - Directory-based: update the mapping per key range
- Always: throttle the backfill, verify with checksums, keep a rollback path
- 🗣 "I use many virtual shards mapped to fewer physical nodes, so adding capacity is moving virtual shards, not rehashing everything."

<a id="s6-5"></a>
### 6.5 Cross-Shard Concerns

- Queries across shards → scatter-gather (slow) or a separate derived index
- Global secondary indexes → eventually consistent copies keyed differently
- Transactions across shards → avoid; use sagas / outbox, or distributed SQL

<a id="s7"></a>
## 7. Replication And Consistency ★★★

<a id="s7-1"></a>
### 7.1 Replication Styles

| Style | How | Good | Cost |
|---|---|---|---|
| Leader-follower async | Leader ships log to followers | Fast writes, read scaling | Lag; failover may lose recent writes |
| Leader-follower sync / semi-sync | Wait for ≥1 follower ack | No loss on single failure | Higher write latency |
| Consensus (Raft / Paxos) | Majority must agree | Strong consistency, automatic failover | Latency of a majority round trip |
| Multi-leader | Several regions accept writes | Local writes everywhere | Conflict resolution |
| Leaderless quorum | Write to W, read from R of N | Availability, tunable | Read repair, conflicts, sloppy quorum caveats |

<a id="s7-2"></a>
### 7.2 Handling Replica Lag

- Read-your-writes: read from the leader for a short window after a user writes, or carry a version / LSN token and wait until the replica catches up
- Monotonic reads: pin a user to one replica
- Critical reads (balances, inventory) go to the leader

<a id="s7-3"></a>
### 7.3 Failover And Split Brain

- Failover steps: detect leader failure → elect / promote a follower → repoint clients
- Risk: two leaders accept writes (split brain)
- Fix: consensus-based election + **fencing tokens** (storage rejects writes from an old leader's lower token)

<a id="s7-4"></a>
### 7.4 Multi-Region Data

- **Home region** per user / tenant: writes go to the home region, reads may be local
- Global tables (multi-leader) for low-latency writes everywhere, with last-writer-wins or CRDTs (conflict-free replicated data types) for merge
- Strongly consistent global data: Spanner-style (higher write latency)
- 🗣 "Each tenant has a home region for writes; other regions serve stale-tolerant reads."

<a id="s8"></a>
## 8. Caching As A Persistence Partner ★★

- Patterns (cache-aside, read-through, write-through, write-behind): see 1.sd.md section 6.5
- Cache key design: include version / tenant (`v2:tenant:T12:listing:42`)
- TTLs with jitter so keys don't expire together (cache avalanche)
- Stampede protection: request coalescing (single-flight), early refresh
- Negative caching for "not found" (penetration)
- Never the source of truth; plan for the cache being empty (cold start load on the DB)

<a id="s9"></a>
## 9. Specialized Stores ★★

<a id="s9-1"></a>
### 9.1 Search Index

- Documents → analyzed fields → inverted index
- Near-real-time: new documents become searchable after a refresh (default ~1 s in Elasticsearch / OpenSearch)
- Mapping design: which fields are full-text (analyzed) vs exact (keyword) vs numeric / geo
- Fed by CDC or outbox; rebuildable from the source of truth
- Combine filters (city, dates, price) with relevance ranking; availability often checked against the source of truth after search

<a id="s9-2"></a>
### 9.2 Time-Series

- Data: `(series_id, timestamp) → value`, append-mostly
- Compression (delta + gorilla-style encoding), downsampling (1 s → 1 min → 1 h), retention per tier
- Cardinality (number of distinct series) is the main scaling risk

<a id="s9-3"></a>
### 9.3 Object Storage

- Bytes in object storage, metadata (owner, size, hash, status) in a DB
- Keys: avoid hot prefixes at extreme scale (add a hash prefix if the store needs it)
- Durability via replication or erasure coding; lifecycle rules move data to cheaper tiers

<a id="s9-4"></a>
### 9.4 Geo Data

| Approach | How | Good for |
|---|---|---|
| Geohash | Encode lat/lon to a string; shared prefix = nearby | Simple prefix queries in KV / search |
| Quadtree | Split space into 4 until cells are small enough | Uneven density (cities vs rural) |
| S2 / H3 cells | Hierarchical cells on a sphere | Uniform cells, ride-sharing / maps |
| Redis GEO / PostGIS | Built-in geo indexes | Nearby queries out of the box |

<a id="s9-5"></a>
### 9.5 Counters And Leaderboards

- Counters
  - Exact, moderate rate: DB row with atomic increment
  - High rate: Redis `INCR` + periodic flush to DB, or sharded counters
  - Approximate is often fine for views / likes
- Leaderboards: Redis sorted sets (`ZADD`, `ZREVRANGE`); periodic snapshot to durable storage

<a id="s10"></a>
## 10. Data Lifecycle ★★

- **Schema migrations**: expand → migrate → contract
  1. Add the new column / table (nullable)
  2. Dual-write old and new; backfill old rows in throttled batches
  3. Switch reads to the new field
  4. Stop writing the old field; drop it later
- **Backfills**: idempotent, resumable, rate-limited, observable
- **Retention and archival**: TTL for temporary data; move old data to object storage (Parquet) for analytics
- **Deletion**: hard delete vs soft delete; data-subject deletion (GDPR) must reach backups / derived stores within policy
- **Backups**: snapshots + point-in-time recovery (PITR); test restores regularly
- 🗣 "Migrations are expand-migrate-contract, so every deploy is backward compatible and can roll back."

---

<a id="s11"></a>
## 11. Derived Data ★★★

| Technique | What | When |
|---|---|---|
| Materialized view | Precomputed query result kept in sync | Expensive aggregations read often |
| CQRS | Separate write model and read model(s) | Very different read and write shapes |
| CDC | Stream DB changes (WAL / binlog) to Kafka | Feed search, cache, warehouse without touching app code |
| Outbox | Write business row + event row in one transaction | Reliable events from app writes |
| Event sourcing | Store events as the source of truth; derive state by replay | Audit-heavy domains (ledgers); rarely needed otherwise |

- Rule: derived stores must be **rebuildable** from the source of truth or the event log
- 🗣 "Writes hit Postgres; Debezium streams changes to Kafka, which feeds OpenSearch and invalidates Redis."

<a id="s12"></a>
## 12. Worked Data Models

<a id="s12-1"></a>
### 12.1 Booking (Airbnb) ★★★

- Patterns: reserve nights (strong), view a listing's calendar (fresh), guest's trips (read-your-writes), search (stale OK)

```sql
CREATE TABLE listing_night (
  listing_id  BIGINT,
  night       DATE,
  booking_id  BIGINT,          -- null = free
  hold_id     BIGINT,
  hold_until  TIMESTAMPTZ,
  price_cents INT,
  PRIMARY KEY (listing_id, night)
);

CREATE TABLE booking (
  booking_id      BIGINT PRIMARY KEY,
  listing_id      BIGINT NOT NULL,
  guest_id        BIGINT NOT NULL,
  check_in        DATE NOT NULL,
  check_out       DATE NOT NULL,
  status          TEXT NOT NULL,      -- HELD, CONFIRMED, CANCELLED
  idempotency_key TEXT UNIQUE,
  total_cents     BIGINT NOT NULL,
  currency        CHAR(3) NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL
);
CREATE INDEX ON booking (guest_id, check_in);
```

- Hold: conditional update of every night in the range where `booking_id IS NULL AND (hold_until IS NULL OR hold_until < now())`; all rows or rollback
- Shard by `listing_id` → the conditional update stays on one shard
- Search index holds listing attributes + a coarse availability summary; final availability is checked against `listing_night`

<a id="s12-2"></a>
### 12.2 Chat Messages ★★★

- Store: Cassandra / DynamoDB
- Key: partition `(chat_id, month)`, clustering `seq DESC`
- Per-user state: `(user_id) → chat_id, last_read_seq, muted`
- Dedup: `(chat_id, client_msg_id)` with a TTL to absorb retries
- Media: object storage; message holds the object key

<a id="s12-3"></a>
### 12.3 URL Shortener ★★

- KV: `short_code → long_url, owner, created_at, expires_at`
- ID: base62 of a Snowflake id, or pre-generated key ranges per server
- Read path: CDN / cache → KV; analytics as async events

<a id="s12-4"></a>
### 12.4 OCI Work Requests ★★★

```sql
CREATE TABLE work_request (
  id               TEXT PRIMARY KEY,     -- ocid-like opaque id
  tenant_id        TEXT NOT NULL,
  resource_id      TEXT NOT NULL,
  operation        TEXT NOT NULL,        -- CREATE_INSTANCE, ...
  status           TEXT NOT NULL,        -- ACCEPTED, IN_PROGRESS, SUCCEEDED, FAILED
  percent_complete INT NOT NULL DEFAULT 0,
  retry_token      TEXT,
  lease_owner      TEXT,
  lease_until      TIMESTAMPTZ,
  fencing_token    BIGINT NOT NULL DEFAULT 0,
  created_at       TIMESTAMPTZ NOT NULL,
  updated_at       TIMESTAMPTZ NOT NULL,
  UNIQUE (tenant_id, retry_token)
);
```

- Same transaction inserts the resource row, the work request and an outbox row
- Workers claim with a conditional update on `lease_until < now()` and increment `fencing_token`

## 13. Failure Modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Hot partition | Celebrity / viral key / time-based key | One partition's throttling, p99 spikes | Salting, caching, split tenant |
| Lost update | Concurrent read-modify-write | Counts don't add up | Optimistic version, atomic update |
| Double booking | Check-then-insert race | Overlapping bookings | Conditional update / unique constraint |
| Replica lag surprise | User reads own write from a replica | "My change disappeared" reports | Read-from-leader window, version tokens |
| Split brain | Failover without fencing | Divergent writes | Consensus election + fencing tokens |
| Unbounded partition | Chat / tenant grows forever | Slow reads, repair issues | Time buckets |
| Tombstone pile-up | Many deletes in one partition | Slow reads in Cassandra | TTL design, compaction, avoid delete-heavy patterns |
| Migration outage | Breaking schema change in one deploy | Errors after deploy | Expand-migrate-contract |
| Cache stampede | Hot key expires | DB load spike | Single-flight, early refresh, TTL jitter |
| Derived store drift | Missed CDC events | Search shows stale / missing items | Reconciliation job, rebuild from source |
