## 0. One-minute version
- Problem: riders need a nearby driver fast; drivers need fair, clear offers
- Done
  - Match or "no drivers" within 60 s; median far lower
  - A ride never gets two drivers; a driver never holds two live offers
  - Driver positions in the index are < ~10 s old
  - A matching crash never strands a rider's request
- Deciding factors
  - Location write rate, because ~600K raw updates/s must stay queryable
  - Exclusive offers, because many matchers race for the same nearest driver
  - Durable matching workflow, because a match spans tens of seconds
  - Geographic hot spots, because a stadium empties into one cell
- Approach
  - Redis geo index sharded by city, in-memory, ephemeral; adaptive client updates
  - `SET NX PX` offer lock per driver + conditional accept on the ride row
  - Ride state machine in DB; per-city queue; timeouts as state, not threads
  - Short batch windows per cell for surges; push to both apps
- 🗣 "Two hard parts: keeping a fresh, queryable map of 3M moving cars, and making sure every offer is exclusive even when matchers race."

## 1. Requirements
- Scope (FR): users should be able to…
  1. Rider: get a fare estimate for pickup → destination
  2. Rider: request a ride and see live status (matching, driver en route)
  3. Driver: go online, receive offers, accept/decline
  4. Driver: report pickup / drop-off; rider sees driver location live
- Out of scope: payments, ratings, pooling, scheduled rides, multiple car types
- Done (NFR)

| NFR | Target | Why |
|---|---|---|
| Match time | p50 < 15 s, hard cap 60 s | Riders abandon after a minute |
| Offer exclusivity | 1 live offer per driver; 1 driver per ride | Double dispatch wastes drivers, angers riders |
| Location freshness | Index lag < 10 s | Stale position = wrong nearest driver |
| Availability | 99.99% request path | Outage strands people on the street |
| Surge | ~100K requests in minutes in one region | Concerts, NYE |

- Deciding factors (from "what breaks Done?")
  - ★★★ Location ingest + nearby query
    - If wrong: index lags or melts; we offer the wrong driver
  - ★★★ Exclusive offers under concurrency and timeouts
    - If wrong: one driver gets 100 popups; a late accept double-assigns
  - ★★ Durable matching
    - If wrong: a matcher restart silently drops rides in progress
  - ★★ Hot cells
    - If wrong: one shard holding downtown saturates during an event
- **L5**
  - Ask: optimize for rider wait or driver utilization? It changes match policy
  - Ask: one city first, or global day one? Drives regional partitioning

## 2. Estimation
- Only numbers that move the design
- Location writes
  - 3M active drivers (video's figure; likely high) / 5 s = 600K/s
  - Adaptive updates (offline, parked, rural) cut it maybe 3–6× → 100–200K/s
- Location memory: 3M × ~100 B ≈ 300 MB: tiny; throughput is the issue
- Redis: order of magnitude 100K simple ops/s per shard
  - 200K/s writes + queries ≈ a few shards per big city, ~20–30 globally
- Ride requests
  - Order of magnitude 10M trips/day ≈ ~100–1000/s globally (public filings say more; still small)
  - Surge: 100K requests over ~10 min in one region ≈ ~170/s: matching work, not raw QPS
- Takeaway: location ingest is the scale problem; matching is the correctness problem
- **L5**: each match does ~1 radius query + up to ~5 offers × 10 s
  - Concurrency in a surge = requests in flight × timers, so timers must be cheap

## 3. API
| Endpoint | Shape | FR |
|---|---|---|
| `POST /v1/fare-estimates` | `{pickup, dropoff}` -> `{estimateId, price, eta, expiresAt}` | 1 |
| `POST /v1/rides` | `{estimateId}` + `Idempotency-Key` -> `202 {rideId, status: MATCHING}` | 2 |
| `GET /v1/rides/{id}/events` | SSE stream: status, driver, driver location | 2, 4 |
| `POST /v1/drivers/me/location` | `{lat, lng, heading, speed, ts}` (batch ok) | 3 |
| `POST /v1/offers/{offerId}/accept` | -> `200 {rideId}` / `409 expired` | 3 |
| `POST /v1/rides/{id}/trip-events` | `{type: PICKED_UP \| DROPPED_OFF}` | 4 |

- Identity from JWT, never from body
- Fare estimate signed and short-lived
  - Prevents a client from replaying a cheap old price
- Accept by `offerId`, not `rideId`
  - A stale accept for an expired offer gets `409`, not a ride
- Driver channel: persistent WebSocket for offers + location; push (APNs/FCM) as fallback
- **L5**: location over the socket, batched every few seconds
  - Cuts per-request overhead vs one HTTP call per ping

## 4. Data model
- Ride (DynamoDB or Postgres; key `ride_id`)
  - `ride_id, rider_id, driver_id?, status, pickup, dropoff, price, offer_id?, offer_driver_id?, offer_expires_at, version, created_at`
  - Status: `MATCHING → OFFERED → ACCEPTED → EN_ROUTE → IN_TRIP → COMPLETED | CANCELED | NO_DRIVERS`
- Driver (key `driver_id`)
  - `driver_id, status (OFFLINE | AVAILABLE | ON_TRIP), current_ride_id?, vehicle...`
- Driver locations (Redis, per city shard)
  - `GEOADD drivers:{city} lng lat driver_id`
  - `HSET drv:{driver_id} ts status` with TTL ~30 s
    - Missing hash = stale driver; skip
- Trip location trail: append to a stream → object storage (for receipts, disputes)
- **L5**: ride table partitioned by `ride_id`; secondary index on `(driver_id, status)`
  - Lets us assert "driver has at most one active ride" cheaply

## 5. HLD, flows, deep dives

### 5.1 Architecture
- Plain idea: a fast in-memory map of cars, plus a careful state machine for each ride

```text
Rider app --HTTPS/SSE--> API GW --> Ride svc ---- Ride DB (state machine)
                                      |  enqueue per city
                                      v
Driver app <--WebSocket--> Gateway  Matching workers --> Offer lock (Redis SET NX PX)
     | location (batched)                 |  GEOSEARCH
     v                                    v
  Location svc ---------------------> Geo index (Redis, sharded by city)
```

- Ride svc: estimates (maps API ETA × rate card), ride CRUD, status events
- Matching workers: stateless; pull from per-city queue; all state in DB/Redis
- Location svc: validates pings, writes geo index, fans out to rider SSE during trips
- 🗣 "Location is a high-write, throwaway index in memory; the ride is a durable state machine in the database."

### 5.2 Request-to-match flow
1. Rider `POST /rides` → ride row `MATCHING` → message on `match:{city}` queue
2. Worker: `GEOSEARCH drivers:{city} FROMLONLAT … BYRADIUS 3 km ASC COUNT 20`
3. Filter: fresh `drv:*` hash, status `AVAILABLE`
4. For each candidate: try offer lock; skip if held
5. Lock won: conditional update ride → `OFFERED` with `offer_id`, `offer_expires_at = now+10s`
6. Push offer to driver socket; schedule a delayed "offer-timeout" message
7. Accept → conditional update (5.4); timeout message → next candidate
8. No candidate in 60 s → `NO_DRIVERS`, notify rider

### 5.3 Deep dive: location index ★★★
- Plain idea: keep only "where is every car now" in memory, sliced by city
- Picture it: Manhattan shard holds ~50K online cars
  - A radius query reads a few geohash cells, not the whole city
- How it works
  1. Driver app batches pings over the socket every ~4 s
  2. Location svc writes `GEOADD` + refreshes `drv:{id}` TTL
  3. Redis geo = sorted set; score is a 52-bit geohash
  4. `GEOSEARCH` scans the center cell + neighbors (handles boundary misses)
- Why this store

| Option | Good at | Bad at | Choose when |
|---|---|---|---|
| Postgres + PostGIS (GiST R-tree) | Rich queries, durable | Index churn at 100K+ writes/s | Static places (Yelp) |
| Redis GEO (geohash) | Fast writes, simple, built-in radius | Single-shard per key; no durability | Default: moving drivers |
| H3 cells + KV (cell → set) | Uniform hexagons, easy neighbor rings | Build it yourself | Uber-scale, pricing per cell |
| Quad tree in memory | Adapts to density | Rebalancing under constant moves | Uneven, slow-changing data |

- Default: Redis GEO per city, unless you also need per-cell analytics (then H3)
- The catch
  - One key per city = one shard; a mega-city can outgrow it
    - Split key by geohash prefix (e.g. 5 chars) and query neighbor keys
  - Redis loss = rebuild from the next ~5 s of pings; acceptable (data is ephemeral)
- Reduce writes: adaptive client cadence
  - Offline: none; parked: every 30–60 s; on trip or near demand: every 4 s
- 🗣 "Driver locations are ephemeral, so I keep them in Redis geo sets per city and rebuild from pings if a node dies."
- **L5**
  - Accuracy: snap GPS to roads; drop jumps above max speed
  - ETA ranking beats straight-line distance (river, highway); rank top 20 by routing ETA

### 5.4 Deep dive: exclusive offers ★★★
- Plain idea: a driver can hold one offer, and only the offered driver can win the ride
- Picture it: 3 matchers all pick driver D for 3 riders
  - Only one gets D; others move to their next candidate in milliseconds
- How it works
  1. Driver lock: `SET offer:{driverId} {rideId} NX PX 12000`
     - Atomic check-and-set; `NX` fails if someone holds it
  2. Ride claim: `UPDATE ride SET status='OFFERED', offer_id=?, offer_driver_id=? WHERE id=? AND status='MATCHING'`
  3. Accept: `UPDATE ride SET status='ACCEPTED', driver_id=? WHERE id=? AND offer_id=? AND offer_expires_at > now()`
     - Also flip driver `AVAILABLE → ON_TRIP` with a condition on status
  4. Timeout: conditional update back to `MATCHING`, only if `offer_id` still matches
  5. Release driver lock (delete only if value = our rideId, via Lua)
- Why the DB condition, not just the lock
  - Locks can expire while a slow accept is in flight
  - The ride row's conditional write is the real source of truth
- The catch
  - Check-then-set (GET, then SET) races; must be one atomic command
  - DynamoDB TTL delete is lazy (can lag a long time), so it's not a lock
    - Use a conditional write comparing `expires_at` to now instead
- 🗣 "The Redis lock stops duplicate popups; the conditional update on the ride row is what guarantees one driver per ride."
- **L5**
  - Fencing: `offer_id` acts as a fencing token; a stale holder can't win
  - Driver declines often? Track decline rate; deprioritize in ranking, not block

### 5.5 Deep dive: durable matching workflow ★★
- Plain idea: the ride's state lives in the DB; workers are just hands
- How it works
  1. Queue per city (SQS FIFO or Kafka partition by city)
  2. Worker processes one step, writes state, schedules the next step (delayed message)
  3. Worker crash: message redelivers; step is idempotent via conditional updates
  4. Sweeper finds rides stuck in `OFFERED` past expiry (backstop, not primary)
- Option: workflow engine (Temporal, or Uber's Cadence) for timers and retries
  - Good when steps grow (pooling, re-dispatch); more infra to run
- FIFO blocking (video's point): per-city partitions keep a rural request from blocking downtown
- 🗣 "Each match step is a conditional state transition plus a delayed message, so any worker can pick it up after a crash."

### 5.6 Deep dive: surges and hot cells ★★
- Plain idea: when demand spikes in one place, match in small batches, not one by one
- How it works
  1. Requests in a hot cell collect for ~2 s
  2. Solve assignment for the batch (min total ETA), then send offers
  3. Surge multiplier per cell raises price, pulls drivers in, lowers demand
- Why batching: greedy one-by-one gives the first rider the best car, not the system
- Hot shard: split city key into geohash-prefix keys; read replicas for queries
- Rate limit ride requests per rider (doc 02)
- **L5**: pre-scale matching workers on known events (calendar-driven)

### 5.7 Live updates ★★
- Rider: SSE on `GET /rides/{id}/events` (status + driver position every few seconds)
- Driver: WebSocket for offers; offers also go via push if the socket is down
- Connection gateways are stateless per message; route by `rideId` through Redis pub/sub
- 🗣 "Rider status is server push over SSE; the driver gets offers on a WebSocket with push as fallback."

## 6. Trade-offs
| Decision | Chose | Gave up | Flip when |
|---|---|---|---|
| Geo store | Redis GEO per city | Durability, complex queries | Need per-cell analytics: H3 |
| Freshness | ~4 s adaptive pings | Some battery/data | Rural: slower cadence |
| Exclusivity | Redis lock + DB conditional write | One more moving part | Single matcher per city |
| Matching | Greedy, batch in hot cells | Global optimum | Pool/shared rides |
| Workflow | DB state + delayed messages | Engine features | Many steps: Temporal/Cadence |
| Regions | Cell-per-region stacks | Easy cross-region trips | Never for matching |

## 7. Reliability and observability
| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Geo shard down | Node crash | Query errors, empty results | Replica promote; rebuild from pings |
| Stale drivers | App backgrounded | `drv:*` TTL expiry | Skip expired; ask app to resume |
| Double assignment | Late accept after timeout | Conditional update fails | Return `409` to driver |
| Stuck ride | Lost timeout message | Sweeper finds old `OFFERED` | Reset to `MATCHING` |
| Surge overload | Event ends | Queue depth per city | Batch matching, surge price, pre-scale |

- Idempotency: `Idempotency-Key` on `POST /rides` (double-tap = one ride)
- Metrics
  - Time-to-match p50/p95, `NO_DRIVERS` rate per city
  - Offer accept rate, offer timeouts
  - Location lag (now − last ping) p99, geo shard ops/s
- **L5**: SLO "95% of requests matched or failed within 60 s"; alert on burn rate

## 8. Wrap-up: is it done?
| Done | Met by |
|---|---|
| Match within 60 s | In-memory geo query + quick offer loop + 60 s cap |
| No double dispatch | `SET NX PX` driver lock + conditional ride updates with `offer_id` |
| Fresh positions | Adaptive pings, TTL'd driver hash, Redis writes |
| No stranded rides | DB state machine, redelivered queue steps, sweeper |

### 9.2 What the video has that I must not forget
- Postgres lat/long range query fails: 1D B-trees, wide scans, write rate
- Quad tree vs geohash rule: density vs update frequency
- Two consistency rules, one easy (per ride) and one hard (per driver)
- Cron reset delay: up to 55 s of a driver wrongly locked
- No user ID in request body; take it from the JWT
- "Skip early estimation, do it when it decides something"

### 9.3 What the video missed or under-specified
- ★★★ Lock acquire race
  - "Check if locked, then set" lets two matchers both lock
  - Fix: one atomic `SET NX PX`
- ★★★ DynamoDB TTL as a lock
  - TTL deletion is a background process; items can linger long after expiry
  - Fix: conditional write on an `expires_at` attribute
- ★★★ Late accept after timeout
  - Driver taps accept at 10.5 s after the offer moved on
  - Fix: accept carries `offer_id`; conditional update rejects stale ones
- ★★ Rider live status and driver tracking: "notification, polling, or otherwise"
  - Fix: SSE for rider, WebSocket for driver
- ★★ Geohash boundary: query neighbor cells (on board, not in talk)
- ★ Hot city keys exceeding one Redis shard
- Facts to double-check

| Video claim | Check | Verdict |
|---|---|---|
| PostGIS uses a quad tree | PostGIS spatial index is GiST (R-tree) | Wrong structure; point stands |
| Postgres ~2–4K TPS | Simple writes reach tens of K/s on good hardware | Too low; still far from 600K |
| Uber uses hexagons, built in-house | H3, open-sourced by Uber in 2018 | Correct (not octagons) |
| Android push via Firebase | Firebase Cloud Messaging | Correct |
| Geohash = base32 string | Geohash spec: interleaved bits, base32 | Correct; "split in fours" is a simplification |
| DynamoDB TTL removes the lock row | AWS: deletion typically within days of expiry | Not timely enough for 5 s |
