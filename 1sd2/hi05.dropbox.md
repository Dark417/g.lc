## 0. One-Minute Version

- Problem
  - People keep files on many devices and want one copy that is always the same everywhere
- Done
  - No file is ever lost or silently overwritten
  - A 50 GB upload survives a dropped connection
  - An edit shows up on other devices within seconds to tens of seconds
- Deciding factors
  - Moving big files reliably, without our servers in the data path
  - Knowing exactly what changed, in what order, per folder
  - Handling two devices editing the same file
- Approach
  - Files split into content-hashed chunks, uploaded straight to blob storage
  - A file version is a list of chunk hashes, committed in one metadata write
  - Each folder tree keeps an ordered change journal with a cursor
  - A conflict becomes a "conflicted copy", never a silent overwrite
- 🗣 "Bytes go to blob storage, truth goes to metadata. A version only exists once its chunk list is committed, and sync is just reading the journal after my cursor."

<a id="s1"></a>
## 1. Requirements

<a id="s1-1"></a>
### 1.1 Functional ★★★

- In scope
  1. Upload a file (up to 50 GB)
  2. Download a file
  3. Sync a folder automatically across a user's devices
  4. See recent versions of a file and restore one
- Out of scope, said aloud
  - Sharing and permissions beyond the owner, real-time co-editing, search, building our own blob store
- Questions I'd ask, with my assumptions
  - Max file size? **50 GB**
  - Offline edits allowed? **Yes; devices reconcile when back online**
  - Version history? **Keep 30 days of versions**
  - How fast must sync feel? **Seconds to tens of seconds, not milliseconds**
- L5
  - Ask about shared folders early
    - Sharing turns one user's journal into a journal per shared folder ("namespace")
    - That changes the partition key

<a id="s1-2"></a>
### 1.2 Non-Functional ★★★

- Durability
  - Committed file data is never lost
  - Blob storage gives this; S3 is designed for 11 nines (AWS docs)
- Integrity
  - What a device has matches the committed version, verified by hashes
- Consistency split
  - Per-file commits: strong
    - One version wins; the loser becomes a conflicted copy
  - Cross-device view: eventual
    - Seconds of lag is fine
- Availability
  - Upload and download stay up even if sync notifications are degraded
- Latency targets (mine, not sourced)
  - Change visible on another online device: p95 < 10 s
  - Metadata calls: p99 < 200 ms
- Efficiency
  - Don't re-upload bytes we already have
  - Don't re-download whole files for small edits
- L5
  - Turn these into SLOs: commit success rate, sync lag p95, reconciliation diff count
  - Name the invariant: a version's chunk list only references chunks that exist

<a id="s2"></a>
## 2. Estimation (Only What Changes The Design) ★★

- Rule: every number below changes a decision
- All numbers are order of magnitude, my assumptions

| Quantity | Estimate | Design decision it drives |
|---|---|---|
| Users / active devices | 500M users, ~100M devices online | Sync check rate is the hot path, not uploads |
| Files | ~1,000 per user, so ~5×10^11 rows | Metadata must be sharded; shard key = namespace |
| Upload time | 50 GiB at 100 Mbps ≈ 72 min | Must be resumable; chunk-level progress |
| Chunks of 50 GB | 4 MiB chunks: ~12,800 chunks | Above S3 multipart's 10,000-part limit; use larger parts or our own chunk objects |
| Naive polling | 100M devices / 30 s ≈ 3.3M QPS | Don't hit the DB per poll; use a long-poll notify tier |
| Small edit to 1 GB file | 1 changed chunk = 4 MiB, not 1 GiB | Delta sync is worth the complexity |

- 🗣 "The scary number isn't storage — blob storage handles that. It's 100 million devices asking 'anything new?' every few seconds."
- L5
  - Dedup saves real storage: many users store the same installers and media
    - Ratio unknown here; I'd measure before promising a number

<a id="s3"></a>
## 3. API ★★★

- Each endpoint maps to a requirement
- Auth: user and device come from the token, never the body

| # | Endpoint | Req | Notes |
|---|---|---|---|
| 1 | `POST /v1/uploads` | FR1 | Body: path, size, chunk hashes; returns which hashes are missing + upload URLs for them |
| 2 | `PUT <presigned-url>` | FR1 | Client sends chunk bytes straight to blob storage |
| 3 | `POST /v1/uploads/{id}/commit` | FR1, FR3 | Body: `parentVersion`; creates the version; 409 on conflict |
| 4 | `GET /v1/files/{fileId}?version=` | FR2 | Returns chunk list + short-lived download URLs |
| 5 | `GET /v1/namespaces/{ns}/changes?cursor=` | FR3 | Journal entries after cursor + new cursor + `hasMore` |
| 6 | `GET /v1/namespaces/{ns}/longpoll?cursor=` | FR3 | Holds ~60 s; returns `{changes: true}` early when something lands |
| 7 | `GET /v1/files/{fileId}/versions`, `POST …/restore` | FR4 | Restore = new version pointing at old chunks |

- Why upload is three calls
  - Bytes never pass our servers: gateways cap bodies (AWS API Gateway: 10 MB)
  - Asking "which hashes are missing" first gives dedup and resume for free
- Commit request shape

```json
{ "uploadId": "u_81", "path": "/Docs/plan.pdf", "parentVersion": 41,
  "chunks": ["sha256:9f2c...", "sha256:a71e..."], "size": 8388608 }
```

- L5
  - All mutating calls take an `Idempotency-Key` (the device's operation ID)
  - Download URLs expire in minutes and are scoped to one object

<a id="s4"></a>
## 4. Data Model ★★★

<a id="s4-1"></a>
### 4.1 Tables

- Metadata store: a sharded relational store (Postgres / Vitess-style, or Spanner)
  - Why: commit needs a transaction (new version + file pointer + journal row)
  - DynamoDB with transactions would also work; deciding factor = team familiarity

```sql
file(ns_id, file_id, path, current_version, deleted BOOLEAN)
  -- PK (ns_id, file_id); unique (ns_id, path) for live files
file_version(ns_id, file_id, version, size, chunk_hashes TEXT[],
             content_hash, created_by_device, created_at)
  -- PK (ns_id, file_id, version)
journal(ns_id, seq BIGINT, file_id, version, op)   -- op: put | delete | move
  -- PK (ns_id, seq); seq strictly increasing per namespace
chunk(hash PK, size, blob_key, ref_count, created_at)
upload(upload_id PK, ns_id, path, chunk_hashes, state, expires_at)
```

- Key choices
  - Shard everything by `ns_id`
    - A user's folder (or a shared folder) lives on one shard
    - Its journal can be ordered locally, no global clock
  - `seq` is the cursor: the client stores the last `seq` it applied
  - Chunks are content-addressed
    - Same bytes, same hash, stored once
  - `ref_count` lets garbage collection delete chunks no version uses
- Client side (local DB)
  - Per file: path, fileId, version, chunk hashes, local mtime
  - Plus the last cursor per namespace

<a id="s4-2"></a>
### 4.2 L5

- Hot namespace
  - A huge shared team folder can overload one shard
  - Split that namespace's journal by sub-tree, or give it a dedicated shard
- Chunk table is global, sharded by `hash`
  - The commit checks chunk existence across shards
  - That check happens at upload-init time, not inside the commit transaction

<a id="s5"></a>
## 5. High-Level Design And Deep Dives

<a id="s5-1"></a>
### 5.1 Architecture ★★★

```
Client [watcher | chunker | local DB | sync engine]
  ├─▶ API Gateway (auth, rate limit) ─▶ Metadata Svc ─▶ Metadata DB (sharded by ns)
  │                                        └─▶ Notify Svc ◀─ journal append events
  ├─▶ Blob Storage (S3) via presigned URLs (chunk PUT / GET)
  └─▶ Notify tier (long-poll, ~60 s holds) — "your namespace changed"
Background: Chunk GC, Version pruning (30 days), Reconciliation audit
```

- One line per component
  - **Client sync engine**: watches the folder, chunks and hashes, applies remote changes
  - **Metadata service**: upload init, commit, changes, versions; the only writer of truth
  - **Blob storage**: holds chunk bytes; durability lives here
  - **Notify tier**: tells clients "something changed"; holds no data
  - **GC / pruning**: deletes unreferenced chunks and old versions

<a id="s5-2"></a>
### 5.2 Flow: Upload A File ★★★

1. Watcher (`FSEvents` on macOS, `ReadDirectoryChangesW` / `FileSystemWatcher` on Windows) sees a change
2. Client waits until the file is stable, then splits it into chunks
3. Client hashes each chunk (SHA-256)
4. `POST /uploads` with the hash list
   - Server answers: "I'm missing these 3; here are presigned URLs"
5. Client PUTs only the missing chunks, in parallel (e.g. 4 at a time)
6. Client calls commit with `parentVersion`
   - Server re-checks every chunk exists
   - In one transaction: insert version, move the file pointer, append a journal row
7. Server publishes "ns changed, seq N" to the notify tier
- Resume after a crash
  - Re-run step 4; already-stored chunks are not missing, so only the rest go up
- 🗣 "The commit is the only moment a new version becomes real. Chunks without a commit are just garbage for GC to collect."
- L5
  - Content-defined chunking (e.g. FastCDC, rolling hash) instead of fixed 4 MiB
    - Inserting one byte at the start of a fixed-chunk file shifts every chunk
    - Content-defined boundaries keep most chunks identical, so delta stays small
  - Verify on the server: blob storage checks a per-part checksum on upload
    - The commit refuses hashes that don't match

<a id="s5-3"></a>
### 5.3 Flow: Sync To Other Devices ★★★

1. Device B holds a long-poll on `/longpoll?cursor=812`
2. Commit on device A appends `seq 813`; the notify tier wakes device B
3. B calls `/changes?cursor=812` and gets entry 813: file X, version 42
4. B compares chunk hashes with its local DB
5. B downloads only the chunks it lacks, rebuilds the file in a temp path
6. B atomically renames it into place, stores cursor 813
- Why long-poll for notify, not WebSocket
  - The client only needs "something changed", server-to-client
  - A held HTTP request works through proxies and needs no session state
  - Dropbox's own API exposes `files/list_folder/longpoll` for this
- Why the journal, not "files updated since T"
  - Timestamps from many writers can tie or skew
  - A per-namespace `seq` is gap-free and ordered
  - Deletes and moves show up too
- L5
  - Notify tier sizing
    - ~100M held connections at an assumed ~100K per node (order of magnitude) = ~1,000 nodes
    - Cheap to scale because it's stateless
  - Fallback: if notify is down, clients poll `/changes` every 60 s with jitter; nothing is lost

<a id="s5-4"></a>
### 5.4 Deep Dive: Conflicts ★★★

- The problem
  - Device A and device B both edit `plan.pdf` from version 41 while offline
- Detection
  - Each commit carries `parentVersion`
  - Commit succeeds only if `current_version == parentVersion` (checked in the transaction)
- Resolution
  1. First commit wins and becomes version 42
  2. Second gets 409
  3. Its client renames its copy to "plan (B's conflicted copy 2026-11-11).pdf"
  4. It uploads that as a new file
- Why not merge
  - Binary files can't be merged safely; the user decides
- Why not last-writer-wins
  - It silently destroys one person's work, which breaks "Done"
- 🗣 "Version numbers make conflicts visible; conflicted copies make them safe."
- L5
  - Moves and deletes also conflict
    - Edit on A, delete on B: keep the edited file
    - Data loss is worse than an extra file
  - Rename loops and case-only renames across macOS and Windows need explicit rules

<a id="s5-5"></a>
### 5.5 Deep Dive: Download, Delta, And Versions ★★

- Download = fetch the version's chunk list, then GET chunks from blob storage in parallel
- Delta sync = only chunks whose hash isn't in the local DB
- Restore = a new version whose chunk list equals the old one
  - Zero bytes copied
- Compression per chunk, chosen by type
  - Text compresses well
  - JPEG / MP4 barely shrink, so skip them
- CDN: not by default
  - Users mostly fetch their own files from a nearby region
  - Add only for widely shared public links
- L5
  - Version pruning after 30 days decrements `ref_count`
  - GC deletes chunks at zero only after a grace period
    - Protects in-flight uploads that will reference them

<a id="s5-6"></a>
### 5.6 Deep Dive: Integrity And Reconciliation ★★

- Every chunk is verified by hash on upload and after download
- Daily reconciliation per device
  1. Client sends a hash of its whole tree (or per-folder hashes)
  2. Server compares with the committed tree
  3. Mismatch: walk down folder hashes to find the differing files, then re-sync them
- L5
  - Hash tree (Merkle-style) per namespace makes the comparison cheap
    - Matching top hashes mean the whole sub-tree matches

<a id="s6"></a>
## 6. Trade-Offs ★★

| Decision | Chose | Alternative | Why |
|---|---|---|---|
| Upload path | Presigned direct to blob | Through our servers | Body limits; no double bandwidth |
| Chunk identity | Content hash | Index / offset | Gives resume, dedup, integrity in one |
| Change feed | Per-namespace journal + cursor | Query by `updatedAt` | Ordered, gap-free, includes deletes |
| Notify | Long-poll | WebSocket / pure polling | One-way signal; cheap; polling at 3M QPS hurts |
| Conflicts | Conflicted copy | Last-writer-wins | Never lose user work |
| Event bus (Kafka) | Not on the critical path | Kafka as source of truth | The journal table already is the log; Kafka only for analytics |

- Consistency vs availability
  - Commits per namespace are strongly consistent, on the namespace's primary shard
  - Reads of history and downloads can use replicas and stay available
- L5
  - Dedup across users is a privacy risk: "does this hash exist?" leaks whether someone has a file
  - Scope dedup to the user, or hide existence checks behind the upload flow

<a id="s7"></a>
## 7. Reliability, Failures, Ops

<a id="s7-1"></a>
### 7.1 Failure Modes ★★

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Upload dies halfway | Network drop | Upload stays `pending` | Re-init; only missing chunks go up |
| Chunk uploaded, commit lost | Crash between steps | Orphan chunks | GC after grace period; client retries commit idempotently |
| Two offline edits | Concurrent commits | 409 on commit | Conflicted copy |
| Notify tier down | Node loss | Hold count drops | Clients fall back to 60 s polling |
| Metadata shard down | Primary failure | Health checks | Fail over to replica; commits 503 briefly, uploads retry |
| Local DB corrupted | Disk / crash | Reconciliation mismatch | Rebuild local DB from server tree + hashes |

<a id="s7-2"></a>
### 7.2 Idempotency ★★★

- Upload init and commit take the device operation ID as `Idempotency-Key`
- Re-sending a commit returns the same version, not a second one
- Chunk PUTs are naturally idempotent: same hash, same bytes

<a id="s7-3"></a>
### 7.3 Observability (L5) ★★

- SLIs: commit success rate, sync lag (commit to applied on other device), upload resume rate
- Invariants audited nightly
  - Every chunk referenced by a version exists in blob storage
  - No live version references a chunk with `ref_count` 0

<a id="s8"></a>
## 8. Wrap-Up

- Recap against Done
  - No loss: blob durability + commit only after all chunks exist
  - Large files: direct, chunked, resumable uploads
  - Fast sync: journal + cursor + long-poll notify + delta chunks
  - No silent overwrite: parent-version check + conflicted copies
- With more time
  - Shared folders and ACLs, LAN sync between nearby devices, selective sync, end-to-end encryption

### 9.2 What The Video Has That I Must Not Forget

- Trust but verify on chunk status; don't let the client mark chunks complete alone
- Gateway body limit (10 MB) as the reason bytes bypass the server
- The 50 GB at 100 Mbps ≈ 1 h 12 min number to justify resumable uploads
- Compression only for compressible types; store the algorithm in metadata
- The client box is big here: local DB, watcher, sync logic belong in the diagram
- Event bus with cursor as the "real Dropbox" option, and why it may be overkill

<a id="s9-3"></a>
### 9.3 What The Video Missed Or Under-Specified

- ★★★ Conflicts
  - Two devices editing the same file is the core sync problem
  - The video never says who wins or how to avoid silent overwrite
- ★★★ Atomic version commit
  - Updating chunks in place lets another device read a half-new file
  - A version should be an immutable chunk list committed in one write
- ★★ Ordering of changes
  - "Changed since timestamp" can miss or reorder concurrent writes and deletes
  - A per-namespace sequence number fixes it cheaply, without Kafka
- ★★ Fixed-size chunks and delta
  - Inserting bytes shifts every fixed chunk; content-defined chunking keeps delta small
- ★★ Polling cost
  - 100M devices polling hit the DB hard
  - A long-poll notify tier separates "anything new?" from "what's new?"
- ★ Dedup and privacy, GC of orphan chunks, idempotent commit
- Facts to double-check from the video
  - 5 MB chunks for a 50 GB file with S3 multipart upload
    - S3 allows at most 10,000 parts, minimum 5 MiB each except the last (AWS docs)
    - 50 GB / 5 MiB is more than 10,000 parts, so part size must be larger (≥ ~5.2 MiB)
  - "Long polling doesn't fit"
    - Dropbox's own public API offers `files/list_folder/longpoll` for exactly this change signal
  - API Gateway 10 MB payload limit: matches AWS docs (REST API payload 10 MB)
  - Presigned URL expiry: configurable; SDK presigners commonly default to 15 minutes
