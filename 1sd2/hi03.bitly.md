## 0. One-minute version
- Problem: long URLs are hard to share; people want short, stable links
- Done
  - A code never points to two URLs, ever
  - Redirect p99 < 50 ms server-side, ~200 ms end-to-end
  - Redirects keep working when a region or the DB primary is down
  - Expired or malicious links stop resolving quickly
- Deciding factors
  - Code generation, because uniqueness must hold across many writers and failovers
  - Read path, because redirects outnumber creates ~1000:1 with hot links
  - Abuse, because a shortener is a free phishing and scraping tool
- Approach
  - Range-leased counter from a durable store + bijective encode + PK as backstop
  - CDN/edge + Redis read-through, short TTLs, negative caching
  - Safe-browsing check on create, per-user create limits, non-sequential codes
- 🗣 "The two hard parts are generating unique short codes without a bottleneck, and serving a 1000:1 read path from memory."

## 1. Requirements
- Scope (FR): users should be able to…
  1. Create a short URL from a long URL
     - Optional custom alias, optional expiration
  2. Be redirected from a short URL to the original
  3. (Stretch) see click counts for their links
- Out of scope: editing destination, user management, link-in-bio pages
- Done (NFR)

| NFR | Target | Why |
|---|---|---|
| Uniqueness | Zero code collisions, including after failover | A wrong redirect is a security bug |
| Redirect latency | p99 < 50 ms at server; ~200 ms end-to-end | Feels instant to humans |
| Scale | 100M DAU, 1B URLs total | Given |
| Availability | Redirect 99.99%; create 99.9% | Broken links hurt every page they're on |
| Consistency | New link resolvable within ~1 s | Sharing takes longer than that |

- Deciding factors (from "what breaks Done?")
  - ★★★ Code generation
    - If wrong: duplicate codes after a counter reset, or a global lock bottleneck
  - ★★★ Read path
    - If wrong: DB takes 100K RPS peaks; one viral link melts a shard
  - ★★ Abuse
    - If wrong: domain lands on blocklists; all our links get flagged
- **L5**
  - Ask: same long URL twice, same code or new one?
    - Per-user dedupe is a product choice; global dedupe leaks who shortened what
  - Ask: is analytics a revenue feature? It decides 301 vs 302

## 2. Estimation
- Only numbers that move the design
- Reads
  - 100M DAU × ~1 click = 10^8/day ÷ ~10^5 s = ~1K RPS average
  - Viral peaks ×10–×100: 10K–100K RPS
- Writes
  - 1B URLs over ~5 years ≈ 200M/yr ≈ 6/s average; peaks maybe 100/s
- Ratio ~1000:1, so optimize reads; writes are tiny
- Storage: ~500 B/row × 1B = 500 GB
  - One Postgres primary holds it; no sharding needed for size
- Code space
  - 62^6 ≈ 56.8B; 62^7 ≈ 3.5T
  - 1B codes in 56.8B space: counter never collides
  - Random 6-char: expected ~8.8M collisions by 1B codes (n²/2N)
- Hot set: top 1% of links ≈ 10M rows × ~150 B ≈ 1.5 GB in Redis
- **L5**: cache hit ratio drives DB load
  - 100K RPS × 1% miss = 1K DB reads/s; fine for a primary + replicas

## 3. API
| Endpoint | Shape | FR |
|---|---|---|
| `POST /v1/urls` | `{longUrl, alias?, expiresAt?}` -> `201 {shortUrl, code, expiresAt}` | 1 |
| `GET /{code}` | -> `302 Location: longUrl` / `404` / `410 Gone` | 2 |
| `GET /v1/urls/{code}/stats` | -> `{clicks, byDay[]}` | 3 |
| `DELETE /v1/urls/{code}` | owner only -> `204` | ops |

- Errors on create
  - `409 Conflict` alias taken
  - `422` URL unsafe or invalid
  - `429` create limit hit
- `410 Gone` for expired, so clients and crawlers stop retrying
- Header `Idempotency-Key` on POST
  - Prevents a client retry from minting two codes
- **L5**: redirect host on a separate domain (e.g. `bit.ly`) from the API host
  - Isolates cookies and lets the CDN cache the redirect host aggressively

## 4. Data model
```sql
CREATE TABLE url (
  code        VARCHAR(16) PRIMARY KEY,   -- generated or alias
  long_url    TEXT NOT NULL,
  user_id     BIGINT,
  created_at  TIMESTAMPTZ NOT NULL,
  expires_at  TIMESTAMPTZ,
  status      SMALLINT NOT NULL DEFAULT 0 -- 0 active, 1 blocked, 2 deleted
);
CREATE INDEX ON url (user_id, created_at);  -- "my links"
CREATE INDEX ON url (expires_at) WHERE expires_at IS NOT NULL;
```
- PK on `code` = B-tree point lookup; also the final uniqueness guard
- `status` lets abuse team kill a link without deleting history
- Clicks: not in this table
  - Append-only events to a stream, rolled up elsewhere
- Store: Postgres primary + 2 read replicas
  - Why not DynamoDB: works fine too (key-value by `code`)
  - Pick Postgres for the user index and simple ops; Dynamo if multi-region writes
- **L5**: if we outgrow one node, shard by hash of `code`
  - Every redirect then hits exactly one shard

## 5. HLD, flows, deep dives

### 5.1 Architecture
- Plain idea: a tiny write path and a huge, cached read path

```text
          create                                   redirect
Client -> API svc -> Safe-browse check        Client -> CDN edge (short TTL)
             |  lease range                               | miss
             v                                            v
        ID allocator (Postgres seq)          Redirect svc -> Redis (read-through)
             |                                            | miss
             v                                            v
          Postgres primary  ---- async replicas ----> read replica
                                     Redirect svc -> click events -> Kafka -> rollups
```

- One codebase can serve both; deploy as two fleets so reads scale alone
- 🗣 "Writes are six per second; the design is really about the read path and the ID generator."

### 5.2 Create flow
1. Validate URL (scheme http/https, length, not our own domain)
2. Safe-browsing lookup; reject known-bad
3. If alias: `INSERT ... ON CONFLICT DO NOTHING`; 0 rows = `409`
4. Else: take next ID from the local lease; encode to code; insert
5. Insert conflict (should never happen): take next ID, retry once, alert
6. Return `201` with the code
- Alias uses the PK atomically; no check-then-insert race

### 5.3 Deep dive: code generation ★★★
- Plain idea: hand out numbers in blocks; turn each number into a short scrambled string
- Picture it: a ticket roll per server
  - Each API server takes 1,000 tickets at once; prints codes from its roll
- How it works
  1. Server calls `SELECT nextval('url_id_seq')` with sequence increment 1,000
  2. Gets range [n, n+999], keeps it in memory
  3. Each create takes the next number locally: no network call
  4. Number goes through a bijective scramble, then base62 → ~6–7 chars
  5. PK insert is the backstop: a duplicate fails loudly, never overwrites
- Why a durable sequence, not Redis `INCR`
  - Redis replication is async; failover can lose recent increments
  - The new primary then reissues numbers already used: duplicate codes
  - Postgres sequences are WAL-logged; a promoted replica won't go back far
    - Even then, the PK insert catches any reuse
- The catch
  - Server crash loses its unused block: gaps, harmless at 56B+ space
  - Raw sequential codes leak volume and allow scraping
- Scramble options
  - Sqids-style encoding: obfuscation, not secrecy; decodable with the alphabet
  - Format-preserving encryption (keyed): non-guessable, still bijective
- Alternatives

| Option | Good at | Bad at | Choose when |
|---|---|---|---|
| Random + collision check | No coordination | Extra read; retries grow as space fills | Small scale, simple |
| Hash(long URL) | Free dedupe of same URL | Same collisions as random; truncation | You want same URL = same code |
| Range-leased counter | No collisions, no hot path call | Needs scramble for privacy | Default |
| Snowflake 64-bit | No central store | ~11 chars in base62: too long | Internal IDs, not short codes |
| Pre-generated key pool | Fast, random-looking | Pool service + "used" tracking | Need random codes, no crypto |

- Default: range-leased counter + keyed scramble, unless codes must be fully random
- 🗣 "I lease ID blocks from a durable sequence, scramble them bijectively, and let the primary key catch anything that slips."
- **L5**
  - Multi-region writes: give each region its own ID range (high bits)
    - No cross-region coordination; still globally unique
  - Reserve a code namespace for aliases (e.g. aliases ≥ 8 chars or blocklist)
    - Prevents an alias squatting a future generated code

### 5.4 Deep dive: read path ★★★
- Plain idea: answer most redirects from memory near the user
- Layers
  1. CDN edge caches `GET /{code}` with `Cache-Control: max-age=60`
  2. Redirect service checks Redis: `code -> {longUrl, expiresAt, status}`
  3. Miss: read replica by PK, populate Redis, return
- 302 vs 301

| Option | Good at | Bad at | Choose when |
|---|---|---|---|
| 301 | Browsers cache; least load | We lose clicks; can't revoke reliably | Pure redirect, no analytics |
| 302 + short `max-age` | Edge absorbs bursts; we still see most traffic | Some edge hits unlogged | Default |
| 302 no-cache | Every click logged | Full load on us | Analytics is billed |

- Default: 302 with a short edge TTL; clicks counted at the edge logs if exact counts needed
- Cache rules
  - Redis TTL = min(1 day, expiresAt - now): never serve an expired link
  - Negative cache misses for ~60 s: scanners hitting random codes don't reach the DB
  - Block/delete: write DB, then delete Redis key and purge CDN path
- Hot link (viral)
  - One code at 50K RPS: CDN takes it; Redis sees little
  - Without CDN: local in-process LRU (a few seconds TTL) on redirect servers
- The catch: blocked malware link may live up to edge TTL; keep TTL short
- 🗣 "Redis TTL never exceeds the link's expiry, and misses are cached too, so scanners can't hammer the DB."
- **L5**
  - Request coalescing on miss (one DB read per code per server)
    - Prevents a cache stampede when a hot key expires
  - Clicks: redirect svc emits events to Kafka async; never block the redirect

### 5.5 Deep dive: abuse ★★
- Plain idea: shorteners hide destinations, so attackers love them
- Controls
  - On create: Google Safe Browsing (or similar) check; block known-bad
  - Async rescan of popular links; flip `status` to blocked
  - Per-user and per-IP create limits (token bucket, see doc 02)
  - Non-sequential codes stop bulk enumeration
  - Rate-limit 404s per IP on the redirect path
- Interstitial warning page for flagged-but-uncertain links
- 🗣 "If our domain gets blocklisted, every link we've ever made breaks, so abuse control is a core requirement."

### 5.6 Expiration ★★
- Read path enforces it: `expiresAt < now` gives `410`
- Cache TTL capped at expiry (5.4)
- Cleanup job deletes or archives expired rows daily using the partial index
- Don't recycle expired codes
  - Old printed links would suddenly point somewhere new

## 6. Trade-offs
| Decision | Chose | Gave up | Flip when |
|---|---|---|---|
| ID gen | Leased sequence + scramble | Fully random codes | Need zero guessability |
| Store | Postgres + replicas | Native multi-region writes | Writes from many regions |
| Redirect | 302 + short edge TTL | Perfect click counts | Billing on clicks |
| Consistency | Async replicas, ~1 s lag | Instant global visibility | Never for this product |
| Services | Two fleets, one codebase | Some deploy simplicity | Tiny team: one fleet |
| Expired codes | Never reused | A little code space | Never |

## 7. Reliability and observability
| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Duplicate code | Counter rollback after failover | PK violation count > 0 | Durable sequence; skip ahead; alert |
| Cache stampede | Hot key expiry | DB QPS spike | Coalescing; jittered TTL |
| DB primary down | Crash | Create errors | Promote replica; redirects still served from cache/replicas |
| Region down | Outage | Health checks | DNS/anycast to other region; replicas there |
| Phishing wave | Bulk creates | Safe-browse hit rate spike | Tighter limits; block accounts |

- Degradation order
  - Creates can fail; redirects must not
  - Redirect svc reads replicas and cache; doesn't need the primary
- Idempotency: `Idempotency-Key` table (key → code, 24 h)
- Metrics
  - Redirect p50/p99, cache hit ratio (edge, Redis), 404 rate
  - Create rate, safe-browse rejects, PK conflicts
- Alert: click volume drops sharply = something broke upstream
- **L5**: SLOs per path (redirect 99.99%, create 99.9%), error budgets

## 8. Wrap-up: is it done?
| Done | Met by |
|---|---|
| Never two URLs per code | Durable leased IDs + PK backstop + no code reuse |
| Redirect fast | CDN + Redis + PK lookup on replica |
| Redirects survive failures | Read path independent of primary; multi-AZ replicas |
| Expired/malicious stop | TTL capped at expiry; status flag + purge; safe-browse |

- "Don't do math up front unless it decides something"

### 9.3 What the video missed or under-specified
- ★★★ Redis global counter can go backwards
  - Async replication + failover reissues numbers: duplicate codes
  - Fix: durable sequence; PK as backstop
- ★★★ Alias check-then-insert race
  - Two users claim `/evan` at once; both pass the check
  - Fix: atomic insert on the PK (`ON CONFLICT`)
- ★★ Cache vs expiration
  - Read-through LRU can serve a link after it expires
  - Fix: TTL capped at expiry
- ★★ Abuse: no safe-browsing, no blocklist path, only "rate limiting" for scraping
- ★★ Negative caching for scanners probing random codes
- ★ Alias vs generated-code namespace collision
- ★ Never reuse expired codes
- Facts to double-check

| Video claim | Check | Verdict |
|---|---|---|
| ~880K collisions for 1B random codes in 62^6 | n²/2N = 10^18 / (2 × 5.68×10^10) ≈ 8.8M | Off by 10× |
| 62^6 ≈ 56B; 62^7 ≈ 3.5T | 56.8B; 3.52T | Correct |
| 301 cached by "DNS servers potentially" | DNS caches name records, not HTTP; browsers/proxies/CDNs cache 301 | Wrong for DNS |
| 302 "never cached" | Cacheable if `Cache-Control`/`Expires` say so (RFC 9110) | Default only |
| Postgres PK uses a B-tree | Postgres docs: PK creates a unique B-tree index | Correct |
| "SSDs in the hundreds of TB" | Largest enterprise SSDs ~100+ TB (2025) | Order of magnitude ok |
