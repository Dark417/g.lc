## 0. One-Minute Version

- What
  - Users search events, view a live seat map, hold seats, pay, get tickets
- Why it's hard
  - Zero oversell, while 1M people hit one event that has ~50K seats
- How
  - Seat state lives in Postgres, keyed by (event, seat)
  - A hold is one conditional UPDATE with an `expires_at`
  - Payment goes through Stripe; the seat is marked SOLD only if the hold is still ours
  - Search runs on Elasticsearch, fed by CDC
  - Seat map: static layout from the CDN, live availability pushed over SSE
  - Hot events go behind a token-gated waiting room
- The catch
  - The database isn't the bottleneck; read stampedes and payment races are
- 🗣 "Correctness lives in one conditional write on the seat row; everything else exists to keep a million people away from that row."

<a id="s1"></a>
## 1. Requirements

<a id="s1-1"></a>
### 1.1 Functional ★★★

- In scope
  1. Search events by text, location, date, category
  2. View an event: details plus a seat map with live availability
  3. Hold 1–N seats (limit, e.g., 6) for 10 minutes
  4. Pay and confirm; receive tickets
  5. View my orders / tickets
- Out of scope, said aloud
  - Admin event creation, resale / transfer, refunds, dynamic pricing
- Questions I'd ask, with my assumptions
  - Assigned seats or general admission? **Both; GA = a counted pool**
  - Max seats per order? **6**
  - Hold length? **10 min, visible countdown**
  - Global or one region? **Global users; each event is sold in one home region**
- L5
  - Ask about fairness policy: FIFO, lottery, or verified-fan presale
  - Ask about bots and scalpers: they decide the waiting-room design

<a id="s1-2"></a>
### 1.2 Non-Functional ★★★

- Correctness
  - **No oversell, ever**: a seat is sold at most once
  - Holds expire within seconds of 10 min, not "eventually"
- Consistency split
  - Booking path: strong (linearizable per seat)
  - Search / event pages: eventual, seconds of lag is fine
- Latency targets (my targets, not sourced)
  - Search p99 < 300 ms
  - Seat map load p99 < 500 ms
  - Hold p99 < 200 ms
- Availability
  - Browse 99.9%; booking 99.95% during on-sales
  - Under overload: degrade browse first, protect booking
- Scale shape
  - Read >> write (~100:1 normally; far higher during on-sales)
  - Bursty: on-sale spikes many orders of magnitude above baseline
- Fairness and abuse
  - Bots must not take most of the inventory
- L5
  - Turn NFRs into SLOs and alerts (§7.4)
  - Name the invariant you'll audit: `count(SOLD per seat) ≤ 1`

<a id="s2"></a>
## 2. Estimation (Only What Changes The Design) ★★

- Rule: every number below changes a decision; otherwise skip it
- All numbers are order of magnitude, my assumptions

| Quantity | Estimate | Design decision it drives |
|---|---|---|
| Events / year | ~1M | Event metadata is small; cache all of it |
| Seats per event | avg ~5K, max ~100K | Ticket rows ~5B/yr × ~200 B ≈ 1 TB/yr; partition by event, archive past events |
| Writes per seat | ~2–5 over its life | Per-row contention is low; one Postgres primary per event is fine |
| On-sale demand | ~1M users, ~50K seats | ~20:1 demand; a waiting room is needed, not a bigger DB |
| Seat map reads if polling every 2 s | 1M / 2 s = 500K QPS | Don't poll the DB; push diffs over SSE |
| Availability as bitmap | 100K seats = 100K bits ≈ 12.5 KB | Whole map fits in one Redis value; cheap to push |

- 🗣 "The write load is tiny — 50K seats change state a few times each. The real load is a million people reading the same 12 KB."
- L5
  - Size the SSE tier: ~1M connections at an assumed ~50K–100K per node (order of magnitude) = ~10–20 nodes per hot event
  - Size admission rate from booking throughput, not from server capacity (§5.5)

<a id="s3"></a>
## 3. API ★★★

- Each endpoint maps to a requirement
- Auth: user identity from the JWT, never from the body

| # | Endpoint | Req | Notes |
|---|---|---|---|
| 1 | `GET /v1/search?q=&lat=&lng=&radius=&from=&to=&cat=&cursor=` | FR1 | Cursor pagination; returns event summaries |
| 2 | `GET /v1/events/{eventId}` | FR2 | Static: event, venue, performer, seat-map layout URL; cacheable |
| 3 | `GET /v1/events/{eventId}/availability` | FR2 | Dynamic: bitmap + `version`; short TTL |
| 4 | `GET /v1/events/{eventId}/availability/stream` | FR2 | SSE; diffs after `version` |
| 5 | `POST /v1/events/{eventId}/holds` | FR3 | Body `{seatIds[] or gaQty}`; `Idempotency-Key`; 201 `{holdId, expiresAt}` / 409 |
| 6 | `DELETE /v1/holds/{holdId}` | FR3 | User releases early |
| 7 | `POST /v1/holds/{holdId}/checkout` | FR4 | Creates order + Stripe PaymentIntent; returns `clientSecret` |
| 8 | `POST /v1/webhooks/stripe` | FR4 | Signed; idempotent on Stripe event ID |
| 9 | `GET /v1/orders/{orderId}`, `GET /v1/me/orders` | FR4, FR5 | Client polls / SSE for final status |

- Why the event and its availability are separate endpoints (#2 vs #3)
  - Static data caches for hours at the CDN
  - Availability changes every second
  - One combined endpoint can't be cached at all
- Hold response shape

```json
{ "holdId": "h_9f2", "eventId": "e_1", "seatIds": ["A-12","A-13"],
  "expiresAt": "2026-11-09T18:10:00Z" }
```

- L5
  - Waiting room endpoints: `POST /v1/events/{id}/queue` returns `{ticketPos}`; an admission token comes later over SSE
  - Booking endpoints #5–#7 require that admission token for gated events, checked at the gateway
  - Errors as problem+json: `SEAT_TAKEN`, `HOLD_EXPIRED`, `LIMIT_EXCEEDED`

<a id="s4"></a>
## 4. Data Model ★★★

<a id="s4-1"></a>
### 4.1 Tables

- Store: Postgres
  - Why: per-row conditional updates, transactions across seats + order, mature ops
  - DynamoDB would also work (conditional writes + transactions); deciding factor = team familiarity

```sql
event(event_id PK, venue_id, performer_id, name, starts_at, category,
      on_sale_at, gated BOOLEAN, home_region)

seat_inventory(
  event_id, seat_id,                 -- PK (event_id, seat_id)
  section, row_label, price_cents,
  status TEXT,                       -- AVAILABLE | HELD | SOLD
  hold_id, hold_user_id, hold_expires_at TIMESTAMPTZ,
  order_id, version BIGINT)
  PARTITION BY HASH (event_id)

hold(hold_id PK, event_id, user_id, seat_ids[], expires_at, state)
order(order_id PK, hold_id UNIQUE, user_id, event_id, amount_cents,
      state, stripe_payment_intent UNIQUE, created_at)
idempotency(key PK, user_id, response_json, created_at)
```

- Key choices
  - PK (event_id, seat_id): every booking query hits one event
  - `hold_expires_at` is the source of truth for expiry
    - Status `HELD` with a past `expires_at` counts as available
  - `order.hold_id UNIQUE`: one order per hold, even under double-click
  - `stripe_payment_intent UNIQUE`: webhook replays can't double-confirm
- Index: `(event_id, status)` for the availability rebuild

<a id="s4-2"></a>
### 4.2 Search Index

- Elasticsearch document per event
  - `name`, `performer`, `venue` (text), `location` (geo_point), `starts_at`, `category` (keyword)
- Fed by CDC (§5.2); never written by services directly

<a id="s4-3"></a>
### 4.3 L5

- Partitioning
  - Hash-partition by `event_id` within one primary
  - Shard across clusters by `event_id` only when one primary can't keep up
  - Pin each mega-event to its own shard (a "cell") so one on-sale can't hurt others
- Lifecycle
  - Past events move to cold storage after N days
  - Keeps the hot table small

<a id="s5"></a>
## 5. High-Level Design And Deep Dives

<a id="s5-1"></a>
### 5.1 Architecture ★★★

```
Client ─▶ CDN (static pages, seat-map layout, search cache)
   └──▶ Edge waiting room ─▶ API Gateway (JWT, rate limit, admission check)
            ├─▶ Search Svc ─▶ Elasticsearch ◀─ Indexer ◀─ Kafka ◀─ Debezium(CDC)
            ├─▶ Event Svc ─▶ Redis (event cache) ─▶ Postgres
            ├─▶ Availability Svc ─▶ Redis (bitmap + pub/sub) ─▶ SSE nodes ─▶ Client
            └─▶ Booking Svc ─▶ Postgres (seat_inventory, hold, order)
                     ├─▶ Stripe ──webhook──▶ Booking Svc
                     └─▶ Outbox ─▶ Kafka ─▶ Ticketing / Email workers
```

- One line per component
  - **CDN**: serves static content; absorbs most read traffic
  - **Waiting room**: holds back excess users for gated events
  - **Gateway**: auth, per-user rate limit, admission-token check
  - **Search Svc + ES**: text + geo + date queries
  - **Event Svc**: event details, cached
  - **Availability Svc**: keeps the live bitmap; pushes diffs
  - **Booking Svc**: holds, checkout, webhook; the only writer of seat state
  - **Outbox**: reliable "order confirmed" events for ticket issuing and email

<a id="s5-2"></a>
### 5.2 Flow: Search ★★

1. Client calls `GET /search`; CDN returns a cached response if the same normalized query was seen within ~30 s
2. Search Svc builds an ES bool query: `match` on text, `geo_distance`, `range` on date, `term` on category
3. ES returns event IDs and summaries
- Sync path
  - Postgres change, Debezium reads WAL, Kafka topic, Indexer upserts into ES
  - Lag: seconds; fine, since search is eventual
- Why CDC, not dual-write
  - A dual-write can succeed in one store and fail in the other, silently
- L5
  - Make the indexer idempotent: upsert by event_id with the source LSN as version
  - Run a nightly reconciliation that compares counts / checksums between Postgres and ES
  - Bucket the query cache key: round lat/lng to a geohash cell, so the CDN cache can actually hit

<a id="s5-3"></a>
### 5.3 Flow: Hold A Seat ★★★

1. Client calls `POST /events/e1/holds {seatIds:[A-12,A-13]}` with an Idempotency-Key
2. Booking Svc checks the key; on a repeat it returns the stored response
3. One transaction:

```sql
UPDATE seat_inventory
SET status='HELD', hold_id=:h, hold_user_id=:u,
    hold_expires_at=now()+interval '10 min', version=version+1
WHERE event_id=:e AND seat_id = ANY(:seats)
  AND (status='AVAILABLE'
       OR (status='HELD' AND hold_expires_at < now()));
-- rowcount must equal len(seats), else ROLLBACK and return 409
INSERT INTO hold(...);
```

4. Commit; publish `{seat, HELD, version}` to Availability Svc
5. Return 201 with `expiresAt`
- Why this is correct
  - Postgres row locks serialize the two writers on each seat
  - The WHERE clause re-checks state after acquiring the lock
  - All-or-nothing across multiple seats, inside one transaction
- Expiry
  - Correctness needs no cron: an expired hold is simply grabbable
  - A sweeper every ~30 s resets expired rows to AVAILABLE and publishes the change
    - Only for cleanliness and so the map updates; not for correctness
- 🗣 "Expiry is a predicate in the WHERE clause, not a background job. The sweeper only tidies up."
- Why not a Redis lock as the source of truth
  - Redis failover can lose recent keys (replication is async), so two users could hold one seat
  - Correctness would then fall back to the DB anyway; I'd rather start there
  - Redis stays useful as a fast pre-filter and for the live map
- L5
  - Deadlocks: lock seats in a fixed sort order (`ORDER BY seat_id` via `SELECT … FOR UPDATE`) when holding many seats
  - GA pool: a counter row `UPDATE ga SET held=held+:n WHERE held+sold+:n <= capacity`
    - That row is hot: split it into K sub-counters (e.g., 16) and pick one at random
  - Per-user limit enforced in the same transaction: count active holds + sold for `user_id`

<a id="s5-4"></a>
### 5.4 Flow: Pay And Confirm ★★★

1. `POST /holds/{h}/checkout`
   - Verify the hold belongs to the caller and `expires_at > now()+60 s`
   - Insert `order(PENDING)`, unique on `hold_id`
   - Create a Stripe PaymentIntent with `capture_method=manual` and an idempotency key = order_id
   - Return `clientSecret`
2. Client confirms the card with Stripe.js; card data never touches our servers
3. Stripe calls our webhook with `payment_intent.amount_capturable_updated` (authorized)
4. Booking Svc runs one transaction:

```sql
UPDATE seat_inventory SET status='SOLD', order_id=:o
WHERE event_id=:e AND seat_id = ANY(:seats)
  AND hold_id=:h AND status='HELD';   -- note: no expiry check here
-- if rowcount == n: order -> PAID, insert outbox row, then capture the payment
-- else: order -> FAILED, cancel the PaymentIntent (releases the authorization)
```

5. Outbox, Kafka, ticketing worker issues tickets and sends email
- Why authorize first, capture later
  - We never charge a user for a seat they didn't get
  - A failure between "seat SOLD" and "capture" is retried by a reconciler
- Expiry vs payment race
  - Hold extended by a few minutes once checkout starts (bounded, e.g., +5 min once)
  - SOLD transition requires `hold_id` match, so a re-held seat can't be sold twice
- Webhook safety
  - Verify Stripe signature
  - Dedupe on Stripe event ID; `stripe_payment_intent` is UNIQUE
  - Webhooks can arrive late or out of order: client polls `GET /orders/{id}` meanwhile
- L5
  - Reconciler job: every few minutes, compare PENDING orders against Stripe's PaymentIntent status
    - Covers lost webhooks
  - Card authorizations expire (Stripe docs: typically ~7 days for online card payments), far longer than our flow
  - Order state machine: `PENDING → PAID → TICKETED`, plus `FAILED` and `EXPIRED`; illegal transitions rejected in SQL

<a id="s5-5"></a>
### 5.5 Deep Dive: The On-Sale Surge ★★★

- Problem
  - 1M users, 50K seats, all at 10:00:00
  - Without control: the DB, the SSE tier and the users' experience all fail together
- Waiting room design
  1. Before on-sale: users join a waiting room page served from the edge (cheap, static)
  2. At open: everyone already waiting gets a **random** position (fair, no reward for refresh scripts)
  3. Later arrivals queue FIFO behind them
  4. Queue store: Redis sorted set `queue:{event}` scored by position
  5. Admission controller lets in `R` users per second
     - R is set from target booking throughput, e.g., 500 admitted/s
  6. Admitted users get a short-lived signed token (JWT, `eventId`, `userId`, exp 15 min)
  7. Gateway rejects booking calls for gated events without a valid token
- Why the token matters
  - Without enforcement, bots skip the queue and call the hold API directly
- Feedback loop
  - Lower R if hold latency or error rate rises
  - Stop admitting when inventory is sold out; tell the queue immediately
- 🗣 "The waiting room converts an unbounded spike into a fixed admission rate that I choose from the booking throughput."
- L5
  - Bot defense: per-account and per-device limits, CAPTCHA on queue entry, verified-fan presale codes
  - Put the waiting room at the edge (CDN workers) so the origin never sees the 1M
  - Isolation: the hot event's booking runs on its own shard / cell
  - Queue position visible to users with estimated wait; honest "sold out" exit

<a id="s5-6"></a>
### 5.6 Deep Dive: Live Seat Map ★★

- Two parts
  - Layout: venue SVG, versioned, on the CDN for days
  - Availability: one bitmap per event in Redis, bit = seat index
- Load
  - Client fetches layout (CDN) + bitmap (`GET /availability`, Redis, ~12.5 KB max)
- Updates
  1. Booking Svc commits a change, publishes `{eventId, seatIdx, state, version}`
  2. Availability Svc applies it to the bitmap and fans out via Redis pub/sub to SSE nodes
  3. SSE nodes push diffs to subscribed clients; batch every ~200 ms
- Why SSE
  - Only server-to-client traffic; works through HTTP infrastructure; auto-reconnect with `Last-Event-ID`
  - WebSocket only if the client needed to send a stream back
- Gap repair
  - Every diff carries a `version`; on a gap, the client re-fetches the bitmap
- L5
  - Hot-room fan-out: 1M subscribers × updates; coalesce into per-section batches
  - When the waiting room is on, only admitted users (~thousands) need the live map; the rest see the queue page
  - Long polling as fallback for networks that break SSE

<a id="s5-7"></a>
### 5.7 Caching Summary ★★

| Data | Where | TTL / invalidation |
|---|---|---|
| Event, venue, performer | CDN + Redis | Hours; invalidate on change via CDC |
| Seat-map layout | CDN | Versioned URL; never invalidated |
| Search results | CDN | ~30 s; key on normalized query |
| Availability bitmap | Redis | Live; rebuilt from Postgres on miss |
| Seat state (truth) | Postgres | Never cached for writes |

<a id="s6"></a>
## 6. Trade-Offs ★★

| Decision | Chose | Alternative | Why |
|---|---|---|---|
| Hold store | Postgres row + `expires_at` | Redis TTL lock | One source of truth; Redis failover can't double-hold |
| Expiry | Predicate + sweeper | Cron as correctness | Exact expiry; cron lag can't extend holds |
| Payment | Authorize, then capture | Charge immediately | Never charge for a seat we failed to sell |
| Search sync | CDC | Dual-write | No silent divergence |
| Live map | SSE + bitmap diffs | Polling / WebSocket | Server-to-client only; cheap per update |
| Surge | Token-gated waiting room | Autoscale everything | Inventory is fixed; more servers don't create seats |

- Consistency vs availability
  - Booking chooses CP: if the event's primary is down, holds fail fast (503) rather than risk oversell
  - Browse chooses AP: serve stale cache rather than an error
- L5
  - Single home region per event: booking writes go to one region, so no cross-region consensus on the hot path
  - Cost: users far from the home region add ~100 ms per write (order of magnitude); acceptable for a few writes per purchase

## 7. Reliability, Failures, Ops

<a id="s7-1"></a>
### 7.1 Failure Modes ★★

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Postgres primary dies | Hardware / AZ loss | Health checks, replication lag | Fail over to sync replica; holds return 503 during failover |
| Redis bitmap lost | Node failure | Cache miss | Rebuild from `seat_inventory` by event; correctness unaffected |
| Webhook lost | Network / Stripe retry exhausted | PENDING order age alarm | Reconciler queries Stripe |
| Capture fails after SOLD | Stripe error | Order stuck in PAID-not-captured | Retry capture; void + release seat if it keeps failing |
| CDC lag | Kafka / indexer down | Consumer lag metric | Search goes stale; replay from offset |
| Thundering herd at open | On-sale start | Request rate, p99 | Waiting room; lower admission rate |

<a id="s7-2"></a>
### 7.2 Idempotency And Retries ★★★

- Hold and checkout take an Idempotency-Key; stored response returned on retry
- Stripe calls use our order_id as the idempotency key
- Webhooks deduped on event ID
- Retries: exponential backoff + jitter; hold endpoint not retried by gateway after a 409

<a id="s7-3"></a>
### 7.3 Backpressure ★★

- Gateway per-user rate limit (token bucket)
- Booking Svc caps in-flight DB transactions; excess returns 429 with `Retry-After`
- Admission rate is the main lever

<a id="s7-4"></a>
### 7.4 Observability (L5) ★★

- SLIs
  - Hold success p99 latency, hold error rate, checkout success rate
  - Hold-expiry lag (now − expires_at of rows still HELD)
  - Webhook-to-SOLD latency; reconciler fix count
- Invariant audit
  - Hourly query: any seat with two PAID orders = page someone
- On-sale runbook
  - Load test at 2× expected demand days before; pre-warm caches and SSE nodes; feature flag for the waiting room

<a id="s9-3"></a>
### 9.3 What The Video Missed Or Under-Specified

- ★★★ Multi-seat atomicity
  - Video holds one seat per request; real orders need N seats all-or-nothing
- ★★★ Confirm doesn't check who holds the seat
  - Video's confirm path writes BOOKED; needs `hold_id` / user match, or another user's hold can be overwritten
- ★★★ Payment vs expiry race
  - A user can pay at 9:59 while the TTL expires at 10:00 and someone else holds the seat
  - Fix: authorize, then capture only if the SOLD transition succeeds
- ★★★ Redis lock as source of truth
  - Video accepts lost locks on failover and relies on the DB to reject the loser at purchase
  - That loser may have already been charged; needs refund logic the video doesn't mention
- ★★ Idempotency
  - No idempotency keys on reserve / confirm; no webhook dedupe
- ★★ N lookups per seat map
  - Video checks Redis per ticket ID; for 50K seats that is 50K keys per page load
  - A bitmap answers in one read
- ★★ Waiting room bypass
  - Without a token checked at the gateway, bots call the reserve API directly
- ★★ No estimation at all
  - Fine as a stance, but my old Oracle feedback flagged missing numbers; a few targeted numbers are safer
- ★ Facts to double-check from the video
  - ES geo: the speaker hedged on "quad trees and geohashing"; modern ES indexes `geo_point` with BKD trees (Elastic docs)
  - The "node query cache" exists (Elasticsearch `indices.queries.cache`, LRU, default up to 10,000 queries per node), but it caches filter results, not full search responses; the shard request cache is a separate thing (Elastic docs)

  - Same shape as: airline seats, hotel rooms, restaurant tables, flash sales, Airbnb booking
