## 1. Intro and delivery framework

- Question: design WhatsApp, or design Messenger
  - Very common; one of the most-requested videos
- Delivery framework: the series of steps for the interview
  - Mid-level and senior: follow it as closely as you can
  - Staff with 20 years of experience: fine to color outside the lines
  - Purpose: cover the important bits, and help you think as you go
  - Candidates who follow it tend, on average, to do better (with exceptions)
- Steps: requirements, core entities, API, (data flow), high-level design, deep dives
- WhatsApp context (write-up)
  - Send and receive encrypted messages and calls from phones and computers
  - Famously built on Erlang
  - Known for very high scale with a small engineering and infrastructure footprint

## 2. Functional requirements

- Requirements are where you talk with the interviewer to set scope
  - Sometimes you even debate what's in and out
- Good requirements become stepping stones for the high-level design
  - Candidates who get lost or run out of time usually set poor, non-actionable requirements
- Spend about 5 minutes here
  - Enough to think through product edge cases
  - Produce a concise list of functional and non-functional requirements
- Technique: put yourself in the user's shoes
  - Open the app: first you see a list of chats with people and groups
- Requirements
  1. **Start group chats**
     - "Group" is the general case; a group of 2 is a 1:1 chat
     - Limit 100 participants (write-up)
  2. **Send and receive messages**
     - A message goes to all members of the chat
     - I receive anything sent to a chat I belong to
  3. **Media attachments**
     - Ask: are there constraints on messages? Video, audio?
     - Interviewer says yes, so we add media
  4. **Get messages sent while offline**
     - Mobile apps disconnect often (phone off overnight)
     - On reconnect I expect every message received while offline
     - Up to 30 days (write-up)
     - Write-up: not obvious to everyone, but interesting; the interviewer will likely steer you to it
- Could ask about audio/video calls, or seeing whether friends are online
- Keep the list short
  - No need to write "below the line" items if you don't have time
- Don't over-expand scope; it creates problems when time runs short
  - If extra requirements don't come quickly, ask the interviewer "anything else in mind?" and move on
- Out of scope (write-up)
  - Audio and video calling
  - Interactions with businesses
  - Registration and profile management

## 3. Non-functional requirements

- How the system performs while it delivers the functional requirements
  - Not end-user features
- Write-up tip: if you haven't used the app much, first ask how most users use it
  - 1:1 or large groups? How often do people send?
  - Not requirements as such, but they drive later decisions
- **Low latency, quantified: < 500 ms**
  - Many candidates stop at "low latency"; quantify it instead
  - Nobody compares two phones side by side
  - A wait of a few beats feels slow
  - 100 ms vs 500 ms isn't really noticeable
  - Gives room in the design; we spend this 500 ms budget later
- **Guaranteed delivery**
  - Strange if I sent a message and it never arrived
- **Billions of users, high throughput**
  - Web-scale default: 100 million or 1 billion users
  - WhatsApp: "I think it's actually a couple billion"
  - Defer message-count estimates until you know more of the design
  - No need for back-of-the-envelope math yet
- **Don't store messages longer than needed** (WhatsApp-specific)
  - Keep messages on the server just long enough for the functional requirements
  - For a private app, data is "toxic sludge"
  - Either delete it or encrypt it so even you can't read it; then you don't carry the liability
- **Fault tolerant**
  - Huge system: things fail all the time
  - Single components must not take the app down
- Below the line if time allows: spam, security, scraping of contact info
- Write-up note: out-of-scope features show product thinking, but it's a nice-to-have
  - Don't burn time on it

## 4. Core entities

- Not explicitly scored
  - Interviewers judge the final design and how you got there
- Still important: getting entities wrong makes design mistakes easy
  - Product-style interviews (e.g., Meta product architecture) care a lot about entity identity
  - Identity choices drive the data model and API
- Actors first
  - All users are peers; no privileged actors
  - Contrast: Uber has riders and drivers; YouTube has creators and viewers
- Entities, walked from the requirements
  - **User**
  - **Chat** (2–100 users)
  - **Message**
  - **Client** (device)
- Key insight for offline delivery
  - A person isn't offline; a device is
  - My phone was off, my laptop was on the whole time
  - Track delivery per client: every message must reach my phone and laptop eventually
- Don't spend extra time here; the discussion shows you're thinking about the nouns

## 5. Connection choice and API

### 5.1 Choosing the connection

- Options (from the Real-time Updates deep dive)
  - Long polling, SSE, WebSockets, WebRTC
- Decision questions
  1. Latency sensitive? If not, use polling
     - Here: 500 ms delivery, so polling doesn't fit
  2. Frequent two-way traffic between client and server?
     - Yes: messages go back and forth constantly, so SSE doesn't fit
  3. Peer-to-peer, or audio/video?
     - Not in our requirements, so no WebRTC
- Conclusion: **WebSockets**
  - Real WhatsApp: "I think" a plain TLS connection, without WebSocket overhead
  - Same principle: a persistent connection that ferries messages both ways
- REST alone doesn't fit: no way to push messages server to client
- Write-up: WebSockets over TLS; a custom protocol over raw TLS/TCP would also work

### 5.2 Commands

- Not a traditional REST API; no standard for describing a WebSocket API
- Describe it as commands sent to the server and commands received from it
- Sent (client to server)
  - `createChat`
  - `sendMessage`
  - `createAttachment` (to be revised in the design)
  - `modifyChatParticipants` (add or remove a user)
- Received (server to client)
  - `newMessage`
  - `chatUpdate`: chat created, or participants changed ("Sandra is no longer in the group")
- Shapes (write-up)

```json
// -> createChat
{ "participants": [], "name": "" } -> { "chatId": "" }

// -> sendMessage
{ "chatId": "", "message": "", "attachments": [] }
  -> { "status": "SUCCESS" | "FAILURE", "messageId": "" }

// -> createAttachment   (amended later)
{ "body": ..., "hash": ... } -> { "attachmentId": "" }

// -> modifyChatParticipants
{ "chatId": "", "userId": "", "operation": "ADD" | "REMOVE" } -> "SUCCESS" | "FAILURE"

// <- chatUpdate
{ "chatId": "", "participants": [] } -> "RECEIVED"

// <- newMessage
{ "chatId": "", "userId": "", "message": "", "attachments": [] } -> "RECEIVED"
```

- Clients ack each received command, so the server knows not to resend (write-up)
  - The message ack is non-obvious but crucial to not losing messages
- Tactics
  - Skip full bodies: say "this is the rough scaffolding; I'll come back as details firm up"
  - API and HLD are usually iterative; interviewers understand
  - Don't leave the interviewer in a lurch
    - An obvious mistake you don't flag gets noted as "missed," even if you knew
    - Say out loud where you're stopping short or simplifying
- No data-flow step here: not a data-heavy infra system

## 6. High-level design

- Approach: satisfy each functional requirement as simply as possible, then evolve
  - Tempting to jump to an optimized system; don't
  - Very experienced (staff) candidates may skip the basics
- Why build basic first
  1. That's how real systems are designed: evolved organically
  2. Jumping to optimal leaves gaps, and you lose track of where you are
     - If scaling distracts you and the system doesn't work, it's hard to give you credit
- Write-up: for infra-style interviews, reason on a single node first; the path to scale is usually straightforward from there

### 6.1 Start group chats

- Client opens a WebSocket to a **single-node chat server**
  - One instance simplifies everything; the problems it creates get solved later
- Chat server writes to **DynamoDB**
  - Any key-value store works; a relational DB would too
  - Aside: the "relational doesn't scale" belief is false
    - Shopify reported its MySQL doing millions of transactions per second on Black Friday (as he recalls)
    - Some interviewers may still believe it; adapt
- Flow: client sends `createChat`, server creates records
- Tables
  - `Chat`: id, name, other metadata
  - `ChatParticipant`: chatId, participantId
- Two queries matter
  1. All participants of a chat
     - Composite primary key: partition key `chatId`, sort key `participantId`
  2. All chats a user is in
     - GSI with partition key `participantId` (sort key `chatId`, write-up)
     - DynamoDB keeps the GSI in sync automatically (write-up)
- Small chats: one DynamoDB transaction writes the chat + participants (write-up)
  - Near 100 participants, batch the writes (write-up)

### 6.2 Send and receive messages

- Easy in the single-server case
  - Every client is connected to this one server (e.g., 1,000 connections)
- Server keeps an in-memory hash map: client/user → WebSocket connection
- Flow
  1. Client sends `sendMessage` with chatId
  2. Server queries `ChatParticipant` for participant IDs
  3. For each participant, find their socket in the map and push `newMessage`
- Limits at this stage
  - No durability: messages aren't stored
  - Only works for currently connected users
  - Fine as a "live chat room"
- Write-up: say out loud this is terrible for scale, to stop the interviewer itching

### 6.3 Media attachments

- Example: a video of my kids for Grandma and the family
- Naive: `Attachments` table in DynamoDB, uploaded over the WebSocket
  - Broken twice over
    1. DynamoDB isn't built for large blobs; videos can be hundreds of MB
    2. Uses already-busy chat servers for heavy upload bandwidth
  - GB payloads next to "OMW" text messages: that disparity signals something's wrong
- Better: chat server writes blobs to **S3**
  - S3 is made for multi-GB payloads, with the availability and throughput we need
  - Still pushes big data through the chat server
- Best: **pre-signed URLs**
  1. Client asks the chat server for an upload target
  2. Chat server uses its credentials to get a pre-signed URL from S3
     - A URL with embedded auth and a TTL ("upload here within the next hour")
  3. Client uploads directly to S3
  4. Client sends the S3 URL inside its normal message
  5. Recipients get the URL and download from S3
- Open problems
  - Expire media after all recipients got it; maybe keep only 30 days
  - Stop users treating the bucket like Google Drive
- Reuses the existing messaging path
- Write-up's three levels
  - Bad: attachments in the DB
  - Good: through the chat server to blob storage, 30-day TTL
  - Great: direct upload with a pre-signed URL (`getAttachmentTarget` command)
  - A CDN adds little: at most 100 recipients, so cache benefit is small (write-up)
  - Write-up: "This is in fact how WhatsApp actually works": attachments go through a separate HTTP service

### 6.4 Offline delivery

- Until now we relied on live connections; offline users have none
- Store messages: `Message` table
  - id, contents, senderId, timestamp
  - The chat server sets the timestamp, to keep it reasonably consistent
- Add an **Inbox** table: recipientId, messageId
  - One entry per recipient per undelivered message
- Send flow
  1. Client sends `sendMessage` (chatId, contents)
  2. Server looks up participants (primary key on `ChatParticipant`; no GSI needed)
  3. One **transaction**: 1 row in `Message`, 1 row per recipient in `Inbox`
     - DynamoDB transactions support up to 100 items
     - So group size ≤ 100 ("I guess 99" recipients)
  4. Push to each connected participant via the socket map
  5. Client sends an **ack** for the message ID
  6. On ack, server deletes that `Inbox` row
- Reconnect flow
  1. Read the client's Inbox for undelivered message IDs
  2. Load those messages
  3. Push them; client acks each; server deletes the Inbox rows
- Guarantee: eventual delivery to any client that reconnects periodically
  - Online clients still get messages immediately
- Write-up adds: return SUCCESS/FAILURE with the message ID to the sender after the write
- Write-up throughput estimate
  - 200M active users × ~20 messages/day = 4B messages/day ≈ 40K messages/s
  - 1:1: one write to `Message` + one to `Inbox`
  - With groups, roughly 100K writes/s
  - Fine for DynamoDB with userId as partition key
- Cleanup: video uses a cleanup service (section 9); write-up uses DynamoDB TTL on both tables
- Keep reminding the interviewer: you know this doesn't scale yet

## 7. Deep dive: check the NFRs

- Deep dives: satisfy NFRs, handle the interviewer's add-ons, refine
  - Iterative: find an issue, fix it, move on
- Not a terrible start, even as a single node
- **Low latency**: already met for connected clients
  - Write to the DB, push on the existing socket immediately
- **Guaranteed delivery**: met
  - Written to `Message` + `Inbox` server-side; delivered on reconnect
- **Billions of users**: not met; next section
- Write-up: all levels should spot that a single host won't scale
  - Mid-level: interviewer may drive the deep dives
  - Senior/staff: you should look around corners yourself

## 8. Deep dive: billions of users (scaling chat servers)

### 8.1 How many servers

- WhatsApp famously served ~2 million connections per server
  - Write-up says 1–2 million per host
  - Likely higher on modern hardware
- Order of magnitude: hundreds, maybe ~1,000 chat servers
- Write-up: 1B users, ~200M connected at once
- Write-up tip: do back-of-envelope math just-in-time, when you need it for a bottleneck

### 8.2 Load balancer: L4, least connections

- Web servers are stateless
  - An L7 LB terminates HTTP and forwards each request to any server
- WebSockets are connection-oriented: the client must keep its server
- **L4 load balancer**
  - Client opens a TCP connection to the LB
  - LB opens a matching connection to a chat server
  - Client disconnects, LB disconnects too
  - The LB becomes invisible: like the client connected directly
- Routing policy: **least connections**
  - The chat server's main resource is connections (~2M max)
  - New servers get filled quickly, until roughly equal to the others
- Write-up nuance
  - Many modern L7 LBs support WebSockets
  - But we need no L7 features (path/header routing, spreading requests per connection)
  - So L4 is enough and generally faster

### 8.3 The routing problem

- Horizontal scale breaks message delivery
  - User A on chat server 1, user B on chat server 2
  - Server 1 has no socket for B
- Fundamental problem: routing between chat servers
- Write-up: "Don't be tempted" to just add a LB and hosts; it doesn't work

### 8.4 Option: Kafka topic per user (bad)

- Idea: a topic per user
  - On connect, the server subscribes to that user's topic
  - To send, write to each recipient's topic; their server reads and pushes
- Why it fails
  - Kafka isn't built for billions of topics
  - Topics are heavy: ~50–100 KB each (write-up: ~50 KB), so terabytes just for setup
    - Write-up: 50 TB+ for 1B users
  - Not built for rapid subscribe/unsubscribe of tiny short-lived "micro topics"
- Write-up: "super topics" per chat server end up reinventing the better options

### 8.5 Option: consistent hash ring (good)

- Idea: a user always belongs to a known server
  - To message the user, send to that server
- Changes
  - Drop the LB; expose chat servers via DNS so clients connect directly
  - Add a **chat registry**: tells a client which server to connect to
  - Store the ring config in **ZooKeeper or etcd**, synced to all nodes
- Send flow
  1. A asks the registry: "I'm user A, which server?" → server 1
  2. A sends to server 1; server 1 writes `Message` + `Inbox`
  3. Server 1 checks ZooKeeper: B belongs to server 2
  4. Server 1 calls server 2 directly: "new message for user B"
  5. Server 2 checks its map; if B is connected, pushes it
  - Two hops instead of one
- Problems
  - **Scaling is an orchestration job**
    - 4 → 5 servers: most users stay; ~20% on the edges move
    - Signal the change in ZooKeeper/etcd
    - Servers slowly disconnect misassigned users; they reconnect via the registry
    - Slowly, to avoid a mass reconnect (write-up: thundering herd)
    - During the move, send to both old and new servers: overhead and stress
  - Hot servers: uneven load possible
  - Write-up: every chat server connects to every other, so servers must be big and few
  - Write-up rates it "Good," not "Great": it creates problems you must be ready to discuss

### 8.6 Option: Redis Pub/Sub (great)

- Keep Kafka's good idea, externalizing server-to-server routing, with a lighter tool
- How Redis Pub/Sub works
  - Subscribe to a topic (a string)
  - Redis keeps an internal hash map of which sockets listen to which topic
  - Publish: Redis looks up listeners and forwards the message
  - "A very dumb socket server"
- Guarantee: **at most once**
  - Normally bad; fine here because durability is already handled
  - Messages are in durable storage; clients fetch undelivered ones on connect
  - Clients can also poll periodically, or get some other "messages waiting" signal
  - Pub/Sub only provides the real-time, < 500 ms path
- Flow
  1. Client connects to any server (least connections)
  2. That server subscribes to the user's ID topic in Redis
  3. On send, after writing to the DB, the sender's server publishes to each recipient's topic
  4. Redis forwards to the subscribed server
  5. That server pushes over the user's socket
- Write path order (write-up)
  1. Write `Message` + `Inbox` (durable)
  2. Return success to the sender
  3. Publish to Pub/Sub (best effort)
  - If step 3 fails, the message is still stored and arrives on reconnect or poll
- Costs
  - Scaling the Redis cluster: same topic-move orchestration problem
  - Topics spread across cluster nodes, so every chat server connects to every Redis node
    - N × M connections; a problem only at trillions of accounts
  - Redis does little but echo between sockets, so the cluster can be small
  - Extra latency: single-digit ms (write-up)
- Write-up vs Kafka: Pub/Sub stores no messages and keeps no consumer offsets
  - Channels are in-memory pointers to subscriber connections
  - Shard channels by user ID across a Redis cluster
- Write-up evidence: Canva benchmark, 100,000 mouse-position updates/s on one Redis host at 27% utilization

### 8.7 Channel per user or per chat? (write-up)

- Depends on chats per user and chat size (write-up)
- Scenario 1: 250 chats per user, all 1:1 (write-up)
  - Per chat: subscribe to 250 channels per connected user; publish to 1
  - Per user: subscribe to 1; publish to 1
  - Per user wins
- Scenario 2: 1 chat per user, 100 participants (write-up)
  - Per chat: subscribe 1, publish 1
  - Per user: subscribe 1, publish 99
  - Per chat saves publishes
- WhatsApp is dominated by 1:1 chats, and groups cap at 100, so: **per user** (write-up)
- Senior add-on: big chats are a "celebrity problem" (write-up)
  - Adaptive: chats above a threshold (say 25) get their own channel
  - On connect, subscribe to those chat channels plus the user channel
  - Publish big-chat messages to the chat channel
  - When a chat crosses the threshold, publish to both briefly while servers subscribe

## 9. Deep dive: don't store messages longer than needed

- Rule: undelivered after 30 days means never delivered
  - Kept messages are a privacy liability; very expensive for Meta when it goes wrong
- **Cleanup service**
  - Secondary index on `Message.timestamp`; delete messages older than 30 days
  - Add a timestamp to `Inbox`; same cleanup for stale entries
  - When deleting the last Inbox row for a message (all clients got it), delete the message too
  - Possible race conditions, but the 30-day guard rail limits the damage
- Write-up alternative: DynamoDB TTL on items
- Storage estimate
  - 1B users × 100 messages/day = 100B messages/day
  - Cap content at 1 KB → 100 TB/day
  - Worst case × 30 days if nothing were delivered
  - Most messages are delivered and removed quickly
  - So the DB holds on the order of a few hundred TB
  - A lot, but achievable on modern systems
- Note: the write-up's estimate differs (200M active × 20/day = 4B/day; section 6.4)

## 10. Extension: multiple devices

- Today every table keys off the recipient user ID (one user, one delivery)
- Add a **Client** entity: userId, clientId
- Change everything that refers to a user to refer to a client
  - `Inbox` gets a recipient **clientId**
  - Video: Pub/Sub topics become per client
  - Write-up: Pub/Sub doesn't change; servers keep subscribing by userId
- Send: participants → each participant's clients → deliver to each
- Cost: Inbox rows multiply (100 people × 5 devices)
  - Cap active clients per user: 2–3 (write-up: 3)
  - Carry the cap into group size, to stay under DynamoDB's 100-item transaction limit
- Write-up adds: a way to deactivate dead clients, so we stop storing for them

## 11. Extension: presence and last seen

### 11.1 Presence (video)

- Green dot next to online contacts; none or red when offline
- Needs product definition: which users care about whose presence
- Simple: polling
  - Table: userId, status
  - Socket connects: write "available"; socket closes: write "unavailable"
  - Query the table when you want to know
- Live updates: reuse Pub/Sub
  - Users subscribe to the presence of specific users
  - Disconnect events are published to that topic and pushed to watchers
- Main challenge: fan-out
  - One disconnect shouldn't trigger thousands or tens of thousands of notifications
  - Limit how many users can watch a given user at once

### 11.2 Last seen (write-up)

- Bad: write `lastSeen` on every action or heartbeat (write-up)
  - 200M connected, heartbeats every 10–30 s: millions of writes/s
  - Stale the moment it's written; paying for consistency we don't need
- Great: use active connections (write-up)
  - `LastSeen` table: one row per user, updated only on disconnect
  - Conditional write: only if the new timestamp is greater (two servers can't race)
  - `getLastSeen` request: the server, in parallel
    1. Reads `LastSeen` and publishes `updateLastSeen` (DATABASE) to the requester's channel
    2. Forwards `getLastSeen` to the target's channel
  - If the target is connected, its server publishes `updateLastSeen` = ONLINE
  - Client merges: ONLINE means green; else show the last disconnect time
  - Costs: the two replies may arrive apart; the UI must handle it
  - Costs: relies on servers reporting disconnects; also write on connect for robustness

## 12. Write-up-only deep dives

### 12.1 WebSocket fails silently (write-up)

- A socket can look open while it's actually dead; TCP keepalives take minutes (write-up)
- Bad: rely on TCP timeouts (write-up)
- Good: ack timeout with server-side retry (write-up)
  - No ack in 500–2,000 ms → retry; after a few, close the socket; client reconnects and syncs
  - Only detects failures while sending
- Great: application-level heartbeats (write-up)
  - Ping every 10–30 s; pong due within ~5 s; else close
  - 200M users at 10 s → 20M ping/pongs per second; tiny, so fine
  - Upper bound: 10 s interval + 5 s timeout = detect within 15 s

### 12.2 Redis drops a message (write-up)

- Inbox guarantees eventual delivery; the goal is quick recovery for connected clients (write-up)
- Good: periodic polling every 30–60 s (write-up)
  - 200M users every 30 s ≈ 7M queries/s; interval trades latency for load
- Good: per-chat sequence numbers with gap detection (write-up)
  - Redis `INCR` per chat; client sees #5 after #3 → resync
  - Gap found only when a later message arrives
- Great: per-user sequence piggybacked on heartbeats (write-up)
  - One counter per user; every message to the user increments it
  - Heartbeat carries the current value; client behind → sync now
  - Catches misses within one heartbeat, across all chats
  - Cost: an atomic counter dependency
- Production combines all three: heartbeats, sequence numbers, polling backstop (write-up)

### 12.3 Out-of-order messages (write-up)

- Answer: don't enforce ordering directly (write-up)
  - Exact order needs waiting for late messages and reordering (like Flink watermarks)
  - Users want new messages fast more than perfect order
- Servers sync clocks with NTP and stamp the receive time (write-up)
- Clients sort by that server timestamp: consistent order on every client (write-up)
- Occasionally a message pops in above a later one; users accept that (write-up)

## 13. What is expected at each level

- Depends on the interviewer and the company
- **Mid-level**
  - Newer to system design
  - Should touch WebSocket management, consistent hashing, Pub/Sub, database design, without depth
  - Roughly familiar; calling out challenges is a bonus
  - No perfect design expected
  - Write-up: 80% breadth / 20% depth; interviewer probes basics ("what do WebSockets do?")
  - Write-up E4 bar: clear API, working HLD; scaling has rough edges, but you know its flaws
- **Senior**
  - Familiar with all core concepts: load balancers, WebSockets, consistent hashing for stateful services
  - Mistakes happen; no specialist knowledge expected
  - Must assemble a system that scales and meets requirements
  - Write-up: 60/40; consistent hashing is essential; know long-running socket mechanics
  - Write-up E5 bar: speed through the HLD, spend time on scaling and robustness
    - Discuss trade-offs like partitioning by chat vs by user
- **Staff**
  - Zoom in on the interesting parts
    - The statefulness of chat servers
    - The data model serving fast queries and very fast writes
  - Generalize experience into solutions
  - Not "senior but better": different focus, larger toolkit
  - Write-up: 40/60; interviewer intervenes only to focus, not steer
  - Write-up bar: 2–3 levels deep on failure modes and bottlenecks
    - Fault tolerance, DB optimization, regionalization, cell-based architecture
- **Managers**: usually held to senior level; staff-level is the rare exception
- Further reading: the Real-time Updates deep dive (SSE, WebSockets, consistent hashing)

```
             |                                |               |
        DynamoDB                         Redis Pub/Sub     S3 (media)
   Chat, ChatParticipant(+GSI)          topic per user     pre-signed
   Message, Inbox, Client               at-most-once       upload/download
             |
      Cleanup service (30 days)
```

- Send path
  1. `sendMessage` → chat server
  2. Look up `ChatParticipant` (and `Client` per user)
  3. Transaction: `Message` + `Inbox` rows (≤ 100 items)
  4. Return SUCCESS + messageId (write-up)
  5. Publish to each recipient's Redis topic
  6. Recipient's server pushes `newMessage`; client acks; `Inbox` row deleted
- Reconnect path: read `Inbox` → load messages → push → ack → delete
- Media: get pre-signed URL → upload to S3 → send URL in message → recipients download
- Rejected routing options: naive LB, Kafka topic per user
- Alternative: consistent hash ring + chat registry + ZooKeeper/etcd
