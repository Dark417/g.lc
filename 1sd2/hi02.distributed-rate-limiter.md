## 0. One-minute version
- Problem: one client can flood shared backends and hurt everyone else
- Done
  - A client's admitted rate stays near its limit (small, bounded overshoot)
  - Check adds < 5 ms p99 to a request
  - Limiter outage never takes the site down, never leaves backends naked
  - Rule change live everywhere in seconds, no deploy
- Deciding factors
  - Atomic check across many gateways, because read-modify-write races over-admit
  - One round trip in the hot path, because 1M RPS × extra hops kills latency
  - Failure posture, because the store will go down sometime
  - Hot keys, because one big API key can melt one shard
- Approach
  - Token bucket in Redis Cluster, one Lua script per check, server clock
  - Limiter as a library inside the gateway, store co-located in-region
  - Local in-memory fallback limiter; fail-closed only for sensitive rules
  - Local token leasing for keys above a hot threshold
- 🗣 "The hard part isn't the algorithm. It's an atomic, one-round-trip check, and knowing what happens when the store is gone."

## 1. Requirements
- Scope (FR): the system should be able to…
  1. Identify a client by user ID, API key, or IP
  2. Apply layered rules (per user, per IP, per endpoint, per tier)
  3. Allow or reject each request within the check budget
  4. Return 429 + `Retry-After` and remaining-quota headers
  5. Change rules at runtime, without a deploy
- Out of scope
  - Volumetric DDoS (L3/L4): CDN or edge scrubbing handles it first
  - Billing-grade quota (monthly API usage): needs exact, durable counts
- Done (NFR, with numbers)

| NFR | Target | Why this number |
|---|---|---|
| Check latency | < 5 ms p99 added | Users notice stacked middleware cost |
| Throughput | 1M RPS peak | Given: 100M DAU social app |
| Accuracy | Over-admit ≤ ~1–5% | Protection, not billing |
| Availability | Limiter down ≠ site down | It guards; it must not become the outage |
| Rule propagation | < 10 s | Ops needs to react during an incident |

- Deciding factors (from "what breaks Done?")
  - ★★★ Concurrency across N gateways
    - If wrong: two gateways both admit the last token
  - ★★★ Hot-path cost
    - If wrong: two or three Redis hops per request blow the latency budget
  - ★★★ Store failure
    - If wrong: fail-open floods backends; fail-closed is a self-made outage
  - ★★ Hot keys
    - If wrong: a partner key doing 50K RPS saturates one shard
- **L5**
  - Ask who owns limits: platform team vs each service team
    - Drives self-serve rule API, validation, and audit log
  - Separate "protection limits" from "commercial quotas"
    - Different accuracy, durability, and failure posture

## 2. Estimation
- Only numbers that change the design
- Request load
  - 1M RPS; ~3 rules per request (user, IP, endpoint)
  - Naive: 3M Redis calls/s
  - One script checking all rules for one client: 1M calls/s
- Store throughput per primary
  - Simple Lua script: order of magnitude 50K–100K calls/s
  - Benchmark on real hardware before committing
  - 1M / 50K = 20 primaries; plan ~30 for headroom and hot keys
- Memory
  - Bucket = 2 fields + key overhead, order of magnitude 100 B
  - 100M users + ~200M IP keys ≈ 30 GB order of magnitude
  - Fits easily across 30 primaries; memory is not the bottleneck
- Takeaway: throughput sizes the cluster, not memory
- **L5**
  - Peak vs average: size for 2–3× peak bursts (canonical pattern)
  - Cross-region RTT is tens of ms (order of magnitude)
    - So any global-sync design must be async

## 3. API
- Internal interface (library call inside the gateway), mapped to FRs

| Call | Shape | FR |
|---|---|---|
| `check` | `(clientKeys[], route, cost=1) -> {allowed, remaining, resetAt, retryAfterMs, ruleId}` | 1, 2, 3 |
| `PUT /rules/{id}` | `{match, limit, burst, window, mode: enforce/shadow, failMode}` | 5 |
| `GET /rules?version=` | snapshot + version | 5 |

- External response on reject (FR 4)

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
RateLimit-Limit: 100
RateLimit-Remaining: 0
RateLimit-Reset: 12
```

- `cost` lets an expensive endpoint consume more than one token
- **L5**
  - `mode: shadow` logs would-be rejects without enforcing
    - Prevents a bad new rule from blocking real users on day one
  - Return `ruleId` in an internal header for debugging, not to clients

## 4. Data model
- Rules: source of truth in a SQL table, versioned
  - `rule_id, match (tier, route, key_type), limit, burst, window, fail_mode, mode, version`
- Buckets: Redis hash, one per (client, rule)

```text
key:   rl:{user:123}:r7      # {user:123} = hash tag
value: tokens=42.5, ts=1731190000123   # ms
TTL:   ~ 2 x time to full refill
```

- Hash tag `{user:123}`
  - All of one client's rules land in one slot
  - One script can check them all atomically
- TTL
  - Idle buckets expire; a missing key = full bucket
  - Prevents unbounded memory from one-off IPs
- **L5**
  - IP keys with hash tag on the IP, user keys on the user
    - A request touching both = two slots = two calls
    - Accept it, or check IP limits locally (coarse) and user limits in Redis

## 5. HLD, flows, deep dives

### 5.1 Architecture
- Plain idea: check at the front door, keep state in one fast shared place

```text
Client -> CDN/WAF (DDoS) -> Gateway [limiter lib + rules in memory] -> Services
                                 |  1 Lua call            ^ push
                                 v                        |
                      Redis Cluster (in-region)     Rule service (SQL + etcd watch)
```

- Gateway (Envoy, or a Spring Cloud Gateway fleet)
  - Verifies JWT, extracts user ID, tier, API key, client IP
  - Runs the limiter as a library: no extra service hop
- Redis Cluster: sharded buckets, replicas per primary
- Rule service: CRUD + validation; publishes snapshots via etcd watch
- Why gateway, not per-service
  - Per-service memory has no global view
  - Separate limiter service adds a hop; Envoy's global RLS does this, at a cost
- 🗣 "I put the check in the gateway as a library, so the only network cost is one Redis call."

### 5.2 Algorithm: token bucket ★★★
- Plain idea: a bucket fills at a steady rate; each request takes a token
- Picture it: limit 10/s, burst 20
  - Idle client has 20 tokens; can fire 20 at once
  - Then sustains 10/s
- How it works
  1. Read `tokens`, `ts`
  2. `tokens = min(burst, tokens + (now - ts) × rate)`
  3. If `tokens >= cost`: subtract, allow
  4. Write back `tokens`, `ts = now`
- The catch
  - Burst size is a product choice; too big defeats protection
  - No exact "reset time"; compute retry as `(cost - tokens) / rate`
- Why not the others

| Option | Good at | Bad at | Choose when |
|---|---|---|---|
| Fixed window | Trivial, 1 counter | 2× burst at boundary | Coarse daily quotas |
| Sliding log | Exact | Memory per request | Low-volume, exact limits |
| Sliding counter | 2 ints, smooth | Approximate | Edge counting at huge key counts |
| Token bucket | Burst + steady rate, 2 fields | Tuning two knobs | Default for APIs |
| GCRA | 1 field, same semantics | Harder to explain | You want minimal state (L5) |

- Default: token bucket, unless you need exact counting (sliding log)
- 🗣 "Token bucket gives me burst tolerance and a steady rate with two numbers per client."

### 5.3 Deep dive: atomic check, one round trip ★★★
- Plain idea: do read, compute, and write as one indivisible step inside Redis
- Picture it: Alice has 1 token; gateway A and B read "1" at the same time
  - Both admit; she got 2 for 1
- How it works
  1. Gateway calls `EVALSHA` with the client's keys and rule params
  2. Redis runs the script single-threaded; no other command interleaves
  3. Script uses `redis.call('TIME')`, not the gateway clock
  4. Script returns allowed, remaining, retry-after
- Sketch (two keys, both must pass, deduct only if both pass)

```lua
local t = redis.call('TIME'); local now = t[1]*1000 + math.floor(t[2]/1000)
local res = {}
for i, k in ipairs(KEYS) do
  local rate, burst = tonumber(ARGV[2*i-1]), tonumber(ARGV[2*i])
  local b = redis.call('HMGET', k, 'tokens', 'ts')
  local tok = tonumber(b[1]) or burst; local ts = tonumber(b[2]) or now
  tok = math.min(burst, tok + (now - ts) * rate / 1000)
  if tok < 1 then return {0, i} end           -- reject, which rule
  res[i] = tok
end
for i, k in ipairs(KEYS) do
  redis.call('HSET', k, 'tokens', res[i] - 1, 'ts', now)
  redis.call('PEXPIRE', k, 60000)
end
return {1, 0}
```

- The catch
  - All keys must be in one slot (hash tag), or Cluster rejects the script
  - Long scripts block the shard; keep them O(rules)
- Why server time matters
  - Gateways' clocks skew by ms; refill math then drifts per gateway
  - One clock (Redis primary) removes that error
- Alternatives
  - `WATCH/MULTI` optimistic: retries under contention, worse for hot keys
  - `INCR` + `EXPIRE` fixed window: atomic already, but boundary burst
- 🗣 "Read-modify-write across gateways races, so the whole bucket update runs as one Lua script on the shard."
- **L5**
  - Script is loaded once, called by SHA; handle `NOSCRIPT` by reloading
  - On failover the new primary may lack the cached script; same handling

### 5.4 Deep dive: failure posture ★★★
- Plain idea: decide per rule what "store down" means, and degrade, don't flip
- How it works
  1. Redis call has a tight timeout (e.g. 2–5 ms) and a circuit breaker
  2. Breaker open: gateway switches to a local in-memory token bucket
  3. Local limit = global limit / number of gateways (known from discovery)
  4. Rules marked `failMode: closed` (login, SMS, payments) reject instead
- Picture it: limit 1,000/s, 50 gateways
  - Each gateway enforces 20/s locally per client
  - Client skewed to few gateways may be over- or under-limited; acceptable briefly
- The catch
  - Blanket fail-closed turns a cache blip into a site outage
  - Blanket fail-open removes protection exactly during overload
- Real-world default
  - Envoy's rate limit filter defaults to allowing traffic if the service fails
    - `failure_mode_deny` defaults to false (Envoy docs)
- Replication
  - One replica per primary, async; failover loses the last few updates
  - Effect: a few clients get a few extra tokens; within the accuracy NFR
- 🗣 "I don't pick open or closed globally. Default is degrade to a local limiter; fail-closed only where abuse costs money."
- **L5**
  - Backends need their own load shedding; the limiter is not the last line
  - Load test the fallback path; untested fallbacks fail on the day you need them

### 5.5 Deep dive: hot keys ★★
- Plain idea: one client too hot for one shard gets tokens handed out in batches
- Picture it: partner key at 50K RPS, shard handles 50K total
  - Every check hits one shard; neighbors on that shard time out
- How it works (token leasing)
  1. Gateway detects key over a threshold (e.g. > 1K RPS locally)
  2. Script grants a lease: take 100 tokens at once
  3. Gateway spends them locally; asks again when low
  4. Unused tokens expire with the lease (short TTL)
- Effect: Redis calls drop ~100×; overshoot bounded by lease size × gateways
- Alternative: local pre-filter that rejects obvious abusers before Redis
- 🗣 "For hot keys I lease tokens in batches, trading a little accuracy for 100× fewer shard calls."
- **L5**
  - Adaptive lease size from observed rate
  - Shuffle-sharding tenants so one hot tenant hurts few neighbors

### 5.6 Deep dive: rules propagation ★★
- Plain idea: rules live in memory on every gateway; changes are pushed
- How it works
  1. Rule service writes SQL (truth), bumps version, writes snapshot to etcd
  2. Gateways watch the etcd key; on change, fetch and validate
  3. Swap the in-memory rule set atomically (copy-on-write)
  4. Gateway reports its active version; dashboard shows convergence
- The catch
  - A bad rule propagates in seconds too
  - So: validation, shadow mode, staged rollout by gateway group
- Gateways keep last-known-good on disk; start even if etcd is down
- 🗣 "Rules are pushed via watch, held in memory, versioned, and canaried like code."

### 5.7 Deep dive: client identity ★★
- Order of preference: API key > user ID (verified JWT) > IP
- IP caveats
  - Corporate NAT and mobile carriers put thousands behind one IP
  - Trust `X-Forwarded-For` only from your own proxies
- Layering: an authenticated request is checked on user and route; anonymous on IP
- **L5**: IPv6 users rotate addresses; limit on the /64 prefix (canonical pattern)

### 5.8 Multi-region (L5) ★
- Plain idea: enforce per region; global accuracy costs cross-region latency
- Options
  - Per-region limit = global / regions: simple, unfair if traffic is skewed
  - Per-region buckets + async sync of usage every ~1 s: closer, bounded overshoot
  - Single global store: exact, but tens of ms per check; violates NFR
- Default: per-region enforcement, async rebalancing for large tenants

## 6. Trade-offs

| Decision | Chose | Gave up | Flip it when |
|---|---|---|---|
| Placement | Gateway library | Business context beyond the request | Limits need DB data per request |
| Store | Redis Cluster | Durability of counts | Billing-grade quota |
| Atomicity | Lua script | Script ops complexity | Single gateway instance |
| Failure | Local fallback | Exactness during outage | Rule protects money/abuse |
| Replication | Async | Last updates on failover | Never for this use case |
| Over-limit | Reject fast (429) | Smoothing | Batch/internal jobs: queue |

## 7. Reliability and observability
- Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Shard down | Node crash | Breaker opens, error rate | Replica promotion; local fallback meanwhile |
| Hot shard | One big client | Per-shard CPU skew | Token leasing; move slot |
| Bad rule | Typo in config | Reject rate spike after version change | Shadow mode; rollback to prior version |
| Retry storm | Clients retry on 429 | 429 rate climbs | `Retry-After` + client jittered backoff |
| Clock drift | Gateway-side math | Uneven admits per gateway | Use Redis `TIME` |

- Idempotency: a check isn't idempotent (it consumes a token)
  - Gateway must not retry a timed-out check blindly; treat as failure path
- Metrics
  - Allowed / rejected per rule and tier
  - Check latency p50/p99, Redis timeouts, breaker state
  - Fallback-mode gateway count
  - Rule version per gateway
- Alerts: rejected share jumps; any gateway in fallback > 1 min
- **L5**: SLO on the limiter itself, e.g. 99.99% of checks < 5 ms

## 8. Wrap-up: is it done?

| Done criterion | Met by |

| Admitted rate near limit | Atomic Lua token bucket; bounded overshoot from leases and failover |
| < 5 ms p99 | In-gateway library, one in-region Redis call, pooled connections |
| Outage ≠ site down | Breaker + local fallback; fail-closed only on marked rules |
| Rules live < 10 s | etcd watch push, in-memory swap, version tracking |

### 9.3 What the video missed or under-specified
- ★★★ Clock source
  - Refill is computed with gateway time; skew distorts it
  - Fix: Redis `TIME` inside the script
- ★★★ Blanket fail-closed
  - Rejecting all traffic when a cache shard dies is a self-made outage
  - Video's own "local fallback" is the better default; make it primary
- ★★ Multiple rules per request
  - Layered rules mean several keys; needs same-slot hash tags to stay atomic
- ★★ Hot keys
  - Sharding by client doesn't help one huge client
- ★★ Key expiry (TTL)
  - Without it, every IP ever seen stays in memory
- ★ Shadow mode and rule rollout safety
- ★ Retry storms on 429: clients need backoff with jitter
- Facts to double-check

| Video claim | Check | Verdict |
|---|---|---|
| Redis Cluster has "something like 60,000" slots | Cluster spec: 16,384 slots, CRC16(key) mod 16384 | Wrong number; speaker hedged |
| "Not consistent hashing" | Spec: fixed hash slots, not a hash ring | Correct |
| Replication is async | Cluster spec: async; `WAIT` only reduces loss | Correct |
| TCP handshake "20–50 ms" | One RTT; sub-ms in-DC, tens of ms only cross-region (TLS adds RTTs) | Only true far away |
| 429 = Too Many Requests | RFC 6585 | Correct |
| `X-RateLimit-*` headers | De facto; IETF draft standardizes `RateLimit-*` | Fine; know both |
