## 1. Intro

- A microblogging service like Twitter "consistently ranks as one of the top five" SD questions
  - Asked at Facebook, Amazon, Netflix, Google
- Evan conducted hundreds of interviews at Meta; calls out dos and don'ts as he goes

## 2. Requirements

- Two goals
  1. You and the interviewer agree before designing
  2. A clear feature list you'll reference throughout
- **Functional** = core features users expect
  - Create an account and log in
  - Create, edit, delete tweets
  - Follow other users
  - View followed users' tweets on the home page (timeline)
  - Like, reply, retweet
  - Search tweets
- **Non-functional** = quality attributes
  - Scale to hundreds of millions of DAU; high volume of tweets created and read
  - Highly available: 99.99% uptime
  - Security and privacy of user data
  - Very low latency for loading tweets
- Far from complete: real Twitter has DMs, integrity systems, ad networks
  - "They had 17 years to build it and we have 45 minutes"
  - Pick the core and confirm with the interviewer
- **Pro tip: don't spend more than 5 minutes here**
  - One of the most common mistakes; requirements matter but aren't the interesting part

## 3. Front door: clients, load balancer, API gateway

- Work left to right along the request lifecycle
- **Clients**: web app, mobile (iOS, Android)
- **Load balancer**: distributes traffic across servers; key to scalability
  - Two points worth raising
  - 1. Routing algorithm
    - Round robin: rotate evenly
    - Least connections: fewest current connections
    - IP hash: same client IP to the same server
  - 2. OSI layer
    - L4 (transport, TCP)
    - L7 (application, HTTP/HTTPS): can route on content (URL, headers)
  - Choice: **round robin** (simple, fair, no persistent connections, stateless backends)
  - **L7**: content-based routing for feature rollouts and more complex traffic management
- **API gateway** fleet: microservice architecture
  - Small independent services, each owning one piece of functionality
  - The gateway forwards each request to the right service
- Client + LB + API gateway appear in ~90% of SD interviews; a good place to start

## 4. Services from the requirements

- Key services map closely to the functional requirements
- **Tweet CRUD service**: create, edit, delete
  - Likes and retweets are updates to existing tweets, so they live here too
- **Reply service**: separate, to scale independently (viral tweets)
- **Search service**
- **Timeline service**
- **Profile service**: accounts, profiles, followers, social graph

## 5. Tweet CRUD service

- Needs: create/edit/delete, likes, retweets, metadata (timestamps, user IDs, media)
- NFR: very high throughput; tweets, likes, retweets are among the most frequent operations, especially reads
- Storage: NoSQL document DB
  - Twitter uses an internal NoSQL DB called **Manhattan**
  - Here: open-source **MongoDB**
  - Good for rapid, frequent reads and writes
  - No complex joins: a request returns the tweet document
- Tweet document (JSON): author, content, timestamps, hashtags, mentions, location, media refs, retweets, likes
- **Media in S3** (blob storage)
  - Built for vast unstructured data; fast retrieval at any scale
  - In an interview with media: very likely blob storage, and S3 is a great choice
- Write path
  1. Client POSTs; LB sends to the API gateway
  2. Gateway forwards to tweet CRUD
  3. Service uploads media to S3, creates the document
  - Edits follow a similar path
- **Rate limiter** on the write path: caps tweets per user per period (bots degrade the service)
- Read path: must be "lightning quick"
  - **Cache** (Redis or Memcached) for popular tweets; avoids hitting the DB every time
  - **CDN** for static content, media, even popular tweets; closer to global users

## 6. Reply service

- Replies in a **separate document store**
- Why not inside the tweet document? Not terrible for a small service, but:
  1. **Scalability**: popular tweets get thousands of replies; the tweet doc would bloat; scale replies independently
  2. **Performance**: fetch a tweet without all its replies
     - Twitter shows the first dozen/20/50 replies; more load as you scroll
- Rate limiter on the reply write path too
- Reads: replies bundled with the tweet, not read separately
  - Reply DB **indexed by tweetId**; fetch and cache replies with the tweet
- Reply document: like a tweet document plus a `tweetId` field (the indexed one)

## 7. Search service

- Complex enough to be its own interview; simplified here
- Scanning the document DB would be too slow
- **Elasticsearch** text index
  - Reverse (inverted) indexes on tweet content, username, hashtag
  - Fast search for tweets, profiles, trending topics
  - Distributed search engine for large data sets, low latency, high reliability
  - Need full-text search in an interview? Elasticsearch is "likely a really strong bet"
- **CDC (change data capture)** keeps the index current
  - Captures changes in the tweet DB and propagates them to Elasticsearch

## 8. Timeline service: fan-out on read vs write

- Social media interviews spend a lot of time here (Facebook, Twitter)
- Simplified: timeline = posts from people you follow; no recommendation system
- **Fan-out on read**
  - On request: get followed accounts, fetch their tweets, sort by time, return
  - Slow and expensive; fails the low-latency NFR
- **Fan-out on write**
  1. New tweet goes on a **message queue** (buffer so bursts don't overwhelm downstream)
  2. **Fan-out service workers** pull tweets off the queue
  3. For each, query the author's followers
  4. Prepend the tweet to each follower's **timeline cache**
  - More write-intensive; reads are fast because the timeline is prebuilt
  - Prioritizes read speed, matching the NFR
- **Catch: mega influencers** (Elon, Drake) with millions of followers
  - Updating every follower's cache could overwhelm the system
  - **Hybrid**: fan-out on write for normal users; fan-out on read for mega accounts
  - On timeline load, fetch the mega accounts' latest tweets and merge into the cached feed

## 9. Profile and auth services

- **User data in SQL**: username, email, bio
  - Efficient queries on structured attributes; ACID integrity; joins and aggregations for user analytics
- **Follower connections in a graph DB**
  - Tailor-made for social networks
  - Grows into a "gold mine": follow suggestions, recommendations, integrity
- **Separate auth service** used by the profile service
  - Authentication and authorization are critical and specialized
  - Tighter security, focused maintenance, easier integration with other services or third parties

## 10. Security

- No SD interview is complete without security, monitoring, testing
1. **Authentication and authorization**: legitimate users, right permissions (auth service)
2. **Encryption**: HTTPS in transit; at rest is usually "flipping a switch" in modern DBs
3. **Rate limiting**: beyond tweets/replies, **IP rate limiting at the API gateway** against DDoS
4. **Input validation**: sanitize input against SQL injection, XSS; on client and server

## 11. Monitoring

1. **Health checks**: Prometheus + Grafana dashboards; know immediately if a service is down
2. **Logging**: every action logged; **ELK** (Elasticsearch stores, Logstash processes, Kibana visualizes)
   - All services send logs centrally; drawn as one ELK box
3. **Real-time alerts**: traffic surges, repeated failed logins; Alertmanager or PagerDuty with Prometheus, to email/Slack

## 12. Testing

1. **Load testing** before new features: find bottlenecks and failure points
2. **Automated testing** in CI (Jenkins, GitHub Actions): unit + integration tests, important with microservices
3. **Backup and recovery testing**: regular backups, periodic restore drills

        Tweet CRUD  Reply CRUD  Search     Timeline    Profile -> Auth
        (+limiter) (+limiter)   |             |           |
         |   |       |       Elasticsearch  Queue ->    SQL users
     MongoDB S3   Replies DB   <- CDC       fan-out     Graph DB
      + cache    (idx tweetId)  from tweets  workers ->  (followers)
                                           timeline cache
