## 1. How Oracle runs SD rounds

```
"Design X" (vague) → you scope → simple v1 → +requirement → scale → +requirement → tradeoffs
```

- Start simple, iterate
  → rewarded explicitly: "grungy solution now" (Act now, iterate)
- Vague on purpose
  → they score the questions you ask
- LLD prompts
  → API + schema + class layout + concurrency in one round
- Always two approaches ready for any locking/consistency question
- HM round
  → draw _your_ JPMC system, defend under "why not Y"
- First-hand quirks (1p3a): SD 可能塞在 BQ 轮最后 10 分钟; HM 轮 SD 可能变纯项目聊天; managerial 轮设计完还要 **EoE (Estimation of Effort) + rough spec document**; 时间管理是最常见失分点

## 7. Discussion-level DB internals (60 s each, no full design)

- MVCC
  → readers see snapshot version; writers create new version; no read locks
  → defeater: write skew under snapshot isolation; vacuum/undo growth
- B-tree index
  → balanced, high fan-out, leaf-linked; O(log n) lookup; range scans
  → defeater: random inserts → page splits; write amplification vs LSM
- 2PC
  → prepare → commit; coordinator log
  → defeater: blocking on coordinator crash; prefer saga/outbox
- Replication
  → sync vs async; log shipping; RPO/RTO
- Point-in-time restore
  → full backup + WAL/redo replay to timestamp
- Execution plan
  → index vs seq scan; join order; stats freshness

### #3 Cache system — distributed-cache half (P0)

- Crux: cache tier as a *service* — placement, invalidation, and what happens when a cache node dies (answer: nothing durable was there)
- HLD: client library → consistent-hash ring of cache nodes (sd04 §10.1 ring, no replication or N=2 async) → backing store on miss
- Data: values with TTL + version; no durability promises; `mc:{tenant}:{key}` namespacing
- Reuse: ring from sd04; stampede/`getOrLoad` + two-tier from sd03 §10.4; invalidation via pub/sub
- Defeater: "replicate cache nodes for durability" — a cache that must not lose data is a KV store; call it what it is (sd04)

### #5 Logging system / log file system (LLD, P0)

- Crux: append-heavy writes that must never block the app + time-range reads
- Core: in-process ring buffer → background flusher → size/time-rotated segment files → compress + upload closed segments; query = binary search over segment time-index then scan
- Data: `segment_meta(file, t_min, t_max, size, sealed)`; filename = `{stream}-{epoch}.log`
- Reuse: LC 635 truncate-by-granularity retrieval (1.coding-1.md); segment chain is #22's storage layer in miniature
- Defeater: "fsync every line" — batch fsync (group commit) or you've built a 100-writes/s logger; state the loss window (last N ms) explicitly

### #2 Design Uber (P0)

- Crux: driver-rider matching on live location — geo index that updates every few seconds without melting
- HLD: rider request → matching service (geo lookup: geohash/quadtree cells, #26's index) → nearest available drivers → offer/accept state machine → trip service (state, fare); locations via driver-app heartbeats into an in-memory geo store (Redis GEO / cell → driver set)
- Data: `drivers(id, cell, status, last_seen)` hot in memory; `trips(id, rider, driver, state, route…)` durable; location history to a stream for ETA/ML, not the hot path
- Reuse: heartbeat + presence = #9 的 push 模型; surge/quota = sd02 thinking
- Defeater: "store live locations in SQL" — 10⁶ drivers × 4 s updates is a write firehose; memory + stream, SQL only for durable trip state
- 报告注: 面试官盯 scalability/bottleneck; 按 matching → location → trip 分块讲, 每块给瓶颈和 10× 方案

### #6 Healthcare data ingestion pipeline (P0)

- Crux: 医疗数据 = 不能丢 + 不能错序处理 + 审计; throughput 是次要矛盾
- HLD: sources → ingestion API (schema validate, auth) → Kafka (partition by patient/facility) → processors (幂等, DLQ) → storage (raw lake + structured store) → monitoring/alerting; failed records → DLQ + replay 工具
- Reuse: sd01 的 at-least-once + idempotency; #22 的 log 语义; compliance/audit = sd06 的审计思路
- Defeater: "at-most-once 保吞吐" — 医疗场景丢数据 = 事故; at-least-once + 幂等消费才是正解
- 报告注: 8 个讨论点是题面明示 — 照单全走一遍就是满分结构

### #7 Software load balancer L4/L7 (P0)

- Crux: L4 (connection, 快, 看不懂内容) vs L7 (request, 慢一点, 能路由/重写/终止 TLS) — 先选层并说为什么
- HLD: VIP → LB fleet (自身要 HA: ECMP/anycast 或 active-passive + VRRP) → backend pools; policies: RR / least-conn / consistent-hash (session 亲和); healthchecks: active probe + passive (连续失败摘除, 半开恢复)
- Defeater: "LB 单点" — LB 自己也要冗余; 以及 healthcheck 抖动 → 加 hysteresis
- 报告注: 讨论核心就是 policies + healthchecks 两块

### #8 Internal metric ingestion service (P0)

- Crux: 读写路径彻底分离 — 写是海量 append, 读是聚合查询
- HLD: 客户端 agent (本地聚合/采样, 批量发, 断点缓冲) → gateway (auth, rate limit) → Kafka (shard by metric+tenant) → 写入 TSDB (时间分片) → 查询层独立 scale
- Reuse: agent 端 = #9 push 模型; sharding/quorum 词汇 = sd04
- Defeater: "agent 每个点都实时发" — 本地 10s 聚合 + 批量, 否则网络先炸
- 报告注: 题面点名 client-side agent logic / sharding / availability / decoupling write & query / infra choice — 按这五点分节讲

### #9 Edge-device health monitoring @ millions (P0)

- Crux: pull (中心探测, 网络放大) vs push (设备心跳, 中心聚合) @ 1M 台
- HLD: push 为主 — 设备定期心跳 → 区域 collectors → 流处理判定 missing (N 个周期无心跳) → pull 探测 double-confirm → 告警; 心跳带版本/指标捎带
- Reuse: presence = bank VM-monitoring 条目; collectors 分层 = 树形聚合
- Defeater: "中心每 30s ping 1M 台" — 探测风暴; pull 只用于确认可疑设备
- 报告注: 报告人答案 push 为主 + pull double-confirm, 面试官接受

### #10 Scale a monolithic service (P0)

- 讨论题 60-s 骨架: 先测量找瓶颈 → 垂直扩容/缓存 (最便宜) → 读写分离 → 按 bounded context 拆 microservices (先拆最热/变更最快的) → 每个 component 独立 scale + 独立部署; 拆分代价: 分布式事务→saga, 联查→API 组合, 运维复杂度
- Defeater: "直接全拆" — strangler fig 渐进拆, 先拆边缘再拆核心
- 报告注: 就是拆分叙事 + 每个 component 的 bottleneck 怎么解

### #11 Video streaming global (P0)

- Crux: 上传/转码 (异步流水线) 与播放 (CDN 边缘) 完全分离; 全球分发 = CDN + 区域源站
- HLD: upload (chunked, #14 的模式) → 转码集群 (多分辨率 HLS/DASH 段) → object storage → CDN; 播放走 manifest + 自适应码率; 元数据/推荐单独服务
- Reuse: Alex Xu vol 1 YouTube 章; upload 容错 = #14
- Defeater: "源站直接服务视频" — 带宽成本与延迟; CDN 命中率是第一指标
- 报告注: 题面从 URL (schemaName, host, port) 起步 — 先把解析/路由讲清再进入流媒体

### #12 Remote Browser Isolation (P0)

- Crux: 浏览发生在远端隔离容器, 终端只收像素/DOM 流 — 安全边界在哪一层
- HLD: 用户 → gateway (authn/authz, per-tenant) → 调度到 virtual node 池 (每会话一容器, 用完即毁) → 页面渲染在容器, 像素流/重构 DOM 经 edge server 低延迟回传; rate limiting + 会话录制审计
- Reuse: gateway/quota = sd02; 租户隔离/审计 = sd06-07 词汇; edge = CDN 思路
- Defeater: "所有用户共享浏览器进程" — 逃逸即全租户沦陷; 每会话隔离 + 最小权限
- 报告注: 题面点名 authn/authz/data streaming/gateways/rate limiting/virtual nodes/edge — 按点覆盖

### #13 E-commerce recommendation system (P0)

- Crux: 离线/近线/在线三层 — 浏览历史进流, 模型离线训, 在线只做召回+排序
- HLD: 行为事件 → Kafka → 特征存储; 离线训练 (协同过滤/双塔) 产出 embedding + 候选索引; 在线: 召回 (ANN/规则) → 排序 (轻模型) → 过滤去重; 冷启动用热门/类目
- Defeater: "在线实时训练" — 延迟与稳定性; 近线更新 embedding 已足够
- 报告注: 基于浏览历史 — 讲清事件采集 → 特征 → 召回排序链路即可

### #14 大文件上传容错 (P0)

- 60-s 骨架: init (拿 upload_id) → 分 chunk (每块 checksum, 失败单块重传) → 断点续传 (已收 chunk 列表查询) → 幂等提交 (chunk 序号+hash 去重) → complete (整体 hash 校验合并); 参考 S3 multipart
- Defeater: "整文件重传" — 只重传失败块; "先合并再校验" — 边收边校验
- 报告注: 单点问题, 答到 chunk + 校验 + 续传 + 幂等 + 整体 hash 即完整

### #15 Chat app 1B / 10M DAU (P0)

- Crux: guaranteed delivery = 服务端持久化 + ack + 幂等重投; 在线走长连接, 离线走收件箱+推送
- HLD: client ↔ gateway (WebSocket, 连接注册) → chat service → 消息持久化 (按会话分片) → 投递 (在线 push / 离线 inbox + notification); 已读/未读游标; 群聊扇出写 vs 扇出读
- Data: `messages(conv_id, seq, sender, body, ts)` 按 conv 分片, seq 单调; `inbox(user, conv, last_ack_seq)`
- Reuse: Alex Xu vol 1 chat 章; presence = #9; 幂等 = sd07 §9.1
- Defeater: "at-least-once 就是 exactly-once" — 客户端按 (conv, seq) 去重才成立; 说清 ack 链路 (client→server→storage→ack)
- 报告注: 题面点名 API design / DB choices / guaranteed delivery — delivery 讲最细

### #18 Ticket booking / flash sale (P1)

- Crux: N users, 1 seat — contention on a tiny hot set; oversell = incident, undersell = lost money
- HLD: browse (cached, stale-ok) → hold seat (TTL lease, sd05 §8 row-lease pattern: `UPDATE seats SET state='HELD', hold_until=... WHERE seat_id=? AND state='FREE'`) → pay → confirm (state machine HELD→BOOKED, fence = version column)
- Data: `seats(event_id, seat_id, state, version, hold_until, order_id)`; partial index on FREE; holds expire by reaper
- API: `POST /events/{id}/holds {seat_ids}` → 200 hold_id + expires | 409; `POST /holds/{id}/confirm` idempotent by hold_id
- Flash-sale layer: queue + admission (virtual waiting room) in front; inventory counter in Redis `DECR` with floor-at-zero Lua (sd02 script pattern) as the fast gate, DB as truth
- Defeater: "lock the whole event row" — serializes all seats; lock the *seat*, or shard inventory counters

### #22 Kafka-like distributed log (P2)

- Crux: ordered, replicated, replayable append-only log — ordering is *per partition*, never global
- HLD: topic → partitions → each an append-only segment file chain; leader + ISR replicas per partition; consumers pull with offsets they own
- Data: segment files + sparse index (offset → file position); consumer offsets in an internal topic; retention by time/size, compaction by key
- Reuse: leader-per-shard = sd01 shard lease; replication/quorum vocabulary from sd04 §10.2 (acks=all ≈ W=quorum)
- Defeater: "consumers ack per message" — Kafka's model is offset-based; per-message ack is the work-queue model (SQS) — know which one the interviewer means (sd01 §14 Kafka defeater is the mirror of this)

### #23 Thread-safe DB connection pool (LLD, P2)

- Crux: bounded resource lending under concurrency — borrow blocks with timeout, returns must be leak-proof
- Core: `BlockingQueue<Conn>` idle + `Semaphore(maxSize)` for total; borrow: acquire permit (timeout) → poll idle → else create; return: validate → offer back (or close + release permit on failure); try-with-resources wrapper so leaks are compile-visible
- Python mirror: `queue.Queue(maxsize)` + context manager (`with pool.borrow() as conn:`)
- Extras that score: validate-on-borrow (cheap `SELECT 1` only if idle > 30 s), max-lifetime eviction, leak detector (borrowed > N s → log stack)
- Reuse: this is sd03's lock discipline + sd05's lease-thinking applied to sockets; HikariCP = the reference (ConcurrentBag, no fairness)
- Defeater: "grow the pool under load" — DB max_connections is the real ceiling; a bigger pool past ~2×cores often *reduces* throughput

### #24 E-commerce / cart (P2)

- Crux: cart = per-user low-contention writes (easy) vs checkout = inventory + payment consistency (the actual question — steer there)
- HLD: cart in KV (sd04; LWW-with-merge: union items, max qty — say the merge rule) → checkout = saga: reserve inventory → charge → confirm, compensations in reverse (sd07 §9.2)
- Data: `carts(user_id) → items jsonb` in KV; `inventory(sku, available, version)` optimistic-locked in SQL; `orders` state machine
- Reuse: idempotent charge via Idempotency-Key (sd07 §9.1); JPMC anchor: Aurora canonical + Mongo read model (CQRS) — your own story
- Defeater: "decrement inventory when adding to cart" — carts abandon; reserve only at checkout with TTL holds (#18's pattern)

### #25 Typeahead (P2)

- Crux: p99 < 50 ms per keystroke; results are *precomputed*, not searched
- HLD: offline pipeline aggregates query counts → builds trie/FST with top-k cached **at each node** → immutable snapshot shipped to serving fleet (double-buffer swap); serve = walk prefix, return stored top-k
- Data: trie node = `{children, top_k: [(term, score)]}`; shard by prefix range; hot prefixes ("a") are pure cache hits
- Reuse: build/serve split = CP/DP separation (4.oci-architecture §2); snapshot swap = static stability
- Defeater: "update the trie on every query" — online updates wreck tail latency; batch rebuild (minutes-stale is fine for suggestions)

### #26 Proximity search / Yelp (P3)

- Crux: "points near (lat,lng)" needs a spatial index — B-tree on lat, lng can't do circles
- HLD: geohash (prefix = cell; neighbors of cell for edge cases) or quadtree; candidates from cell + 8 neighbors → exact distance filter → rank
- Data: `places(geohash6, place_id, lat, lng, ...)` indexed on `(geohash6)`; or PostGIS/Redis GEO and say you'd buy not build
- Defeater: "geohash prefix alone" — cell-boundary neighbors missed; always query the 8 neighbors too

### #27 Distributed file / object storage (P3)

- Crux: huge immutable blobs — separate *metadata* (small, hot, consistent) from *data* (big, dumb, replicated)
- HLD: metadata service (name → chunk list → chunk locations; strongly consistent, sd04-style or Raft) + chunk servers (64 MB chunks, N=3 across FDs); client writes chunks then commits manifest; erasure coding for cold data (1.5× vs 3× cost)
- Reuse: placement = sd04 ring or explicit allocator; repair = anti-entropy (sd04 §10.3)
- Defeater: "store blobs in the KV store" — 400 KB item caps exist because big values wreck compaction; claim-check pattern instead

### #28 Meeting-room booking / door access (LLD, P3)

- Crux: interval conflict detection + authz
- Core: per-room ordered set of bookings; conflict iff `new.start < existing.end AND new.end > existing.start`; insert under per-room lock or DB exclusion constraint — `EXCLUDE USING gist (room_id WITH =, tstzrange(start_t, end_t) WITH &&)` (the one-line schema answer that wins the round)
- Reuse: LC 56 Merge Intervals (1.coding-1.md merge) is the algorithmic core; access control = RBAC story from JPMC
- Defeater: "check-then-insert" — TOCTOU double-booking; the constraint or lock must be atomic with the insert

### #29 Backup + point-in-time restore (discussion only)

- 60 s answer: full snapshot + continuous WAL archive; restore = latest full < T, replay WAL to T; RPO = archive lag, RTO = restore + replay time; test restores monthly or you have backups, not restore capability
- Defeater: "replicas are backups" — replicas replicate your DROP TABLE instantly

### #30 Distributed transaction coordinator / 2PC (discussion only)

- 60 s answer: prepare (all vote, persist redo) → commit; coordinator log is truth; blocks on coordinator crash between phases — participants hold locks → prefer sagas/outbox (sd07 §9.2, sd01 §10.2) for cross-service; 2PC only intra-trust-domain (XA, spanner-style with Paxos coordinator)
- Defeater: "2PC gives exactly-once across services" — it gives atomicity while blocking; availability is the price

### #31 B-tree index class layout (discussion only)

- 60 s answer: `Node{keys[], children[]|values[], leaf, next_leaf}`; high fan-out (page-sized nodes, ~100s of keys) → 3–4 levels for billions; leaf-linked for range scans; insert splits upward at capacity
- vs LSM (sd04 §9): B-tree = read-optimized in-place; LSM = write-optimized append; that contrast is usually the actual question
