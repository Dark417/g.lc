#### 295. [Find Median from Data Stream](https://leetcode.com/problems/find-median-from-data-stream/) [H]

Description: Maintain a running median as numbers are added.

Idea: Two heaps — a max-heap for the lower half, a min-heap for the upper half. Push into `small`, spill its top into `large` to enforce the ordering invariant, then rebalance so `small.size()` is either equal to or one greater than `large.size()`.

**Java note.** Python fakes a max-heap by negating every value. Java has a real one via `Collections.reverseOrder()`, so the negation and the sign-flipping arithmetic all disappear.

```java
class MedianFinder {
    private final PriorityQueue<Integer> small = new PriorityQueue<>(Collections.reverseOrder());
    private final PriorityQueue<Integer> large = new PriorityQueue<>();

    public MedianFinder() {}

    public void addNum(int num) {
        small.offer(num);
        large.offer(small.poll());                 // top of small moves over: keeps small <= large
        if (large.size() > small.size()) small.offer(large.poll());
    }

    public double findMedian() {
        if (small.size() > large.size()) return small.peek();
        return (small.peek() + large.peek()) / 2.0;
    }
}
// Time: O(log n) per insert, O(1) median, Space: O(n)
```

⚠️ `(small.peek() + large.peek()) / 2` would do integer division. The `2.0` is load-bearing.

#### 432. [All O`one Data Structure](https://leetcode.com/problems/all-oone-data-structure/) [H]

Description: Support `inc`, `dec`, `getMaxKey`, and `getMinKey`, all in O(1).

Idea: A doubly-linked list of **count buckets** kept in ascending count order, each holding the set of keys with that count, plus a map `key -> bucket`. Incrementing a key moves it to the adjacent bucket, creating that bucket only if it does not already exist. Because counts change by exactly one, the neighbour is always the only candidate — that is what makes it O(1) rather than O(log n).

**Java note.** Buckets use `LinkedHashSet` so `iterator().next()` is deterministic; Python's `set` iteration order is arbitrary, which is fine for the problem but harder to reason about.

```java
class AllOne {
    private static final class Bucket {
        final int count;
        final Set<String> keys = new LinkedHashSet<>();
        Bucket prev, next;

        Bucket(int count) { this.count = count; }
    }

    private final Bucket head = new Bucket(0);      // sentinel: lowest counts side
    private final Bucket tail = new Bucket(0);      // sentinel: highest counts side
    private final Map<String, Bucket> bucketOf = new HashMap<>();

    public AllOne() {
        head.next = tail;
        tail.prev = head;
    }

    private void insertAfter(Bucket node, Bucket fresh) {
        fresh.prev = node;
        fresh.next = node.next;
        node.next.prev = fresh;
        node.next = fresh;
    }

    private void unlink(Bucket node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    public void inc(String key) {
        Bucket cur = bucketOf.get(key);

        if (cur == null) {                          // new key, count becomes 1
            Bucket first = head.next;
            if (first == tail || first.count != 1) {
                first = new Bucket(1);
                insertAfter(head, first);
            }
            first.keys.add(key);
            bucketOf.put(key, first);
            return;
        }

        Bucket nxt = cur.next;
        if (nxt == tail || nxt.count != cur.count + 1) {
            nxt = new Bucket(cur.count + 1);
            insertAfter(cur, nxt);
        }
        nxt.keys.add(key);
        bucketOf.put(key, nxt);

        cur.keys.remove(key);
        if (cur.keys.isEmpty()) unlink(cur);
    }

    public void dec(String key) {
        Bucket cur = bucketOf.get(key);
        if (cur == null) return;

        if (cur.count == 1) {                       // drops to 0: key leaves entirely
            bucketOf.remove(key);
            cur.keys.remove(key);
            if (cur.keys.isEmpty()) unlink(cur);
            return;
        }

        Bucket prev = cur.prev;
        if (prev == head || prev.count != cur.count - 1) {
            prev = new Bucket(cur.count - 1);
            insertAfter(cur.prev, prev);
        }
        prev.keys.add(key);
        bucketOf.put(key, prev);

        cur.keys.remove(key);
        if (cur.keys.isEmpty()) unlink(cur);
    }

    public String getMaxKey() {
        Bucket b = tail.prev;
        return b == head ? "" : b.keys.iterator().next();
    }

    public String getMinKey() {
        Bucket b = head.next;
        return b == tail ? "" : b.keys.iterator().next();
    }
}
// Time: O(1) per operation, Space: O(n)
```

#### 460. [LFU Cache](https://leetcode.com/problems/lfu-cache/) [H]

Description: Design a cache with O(1) `get`/`put` and least-frequently-used eviction, breaking ties by least-recently-used.

Idea: Three maps plus a `minFreq` pointer. `keyToVal` and `keyToFreq` hold the entries; `freqToKeys` maps each frequency to the keys at that frequency, **in insertion order**, so the tie-break is free. Every access bumps a key's frequency, and `minFreq` only ever needs to increase by one — when the bucket it points at empties during a touch, the key that emptied it just moved to `minFreq + 1`.

**Java note.** Python uses `OrderedDict` with `popitem(last=False)` for the per-frequency LRU order. Java's equivalent is `LinkedHashSet`, whose `iterator().next()` gives the oldest inserted key; re-inserting an existing element does *not* refresh its position, which is exactly the behaviour needed here since every touch removes the key from one bucket and adds it to another.

```java
class LFUCache {
    private final int cap;
    private int minFreq;
    private final Map<Integer, Integer> keyToVal = new HashMap<>();
    private final Map<Integer, Integer> keyToFreq = new HashMap<>();
    private final Map<Integer, LinkedHashSet<Integer>> freqToKeys = new HashMap<>();

    public LFUCache(int capacity) { this.cap = capacity; }

    /** Move a key from freq f to f + 1, maintaining minFreq. */
    private void touch(int key) {
        int freq = keyToFreq.get(key);
        LinkedHashSet<Integer> bucket = freqToKeys.get(freq);
        bucket.remove(key);
        if (bucket.isEmpty()) {
            freqToKeys.remove(freq);
            if (minFreq == freq) minFreq++;         // the emptying key went to freq + 1
        }
        keyToFreq.put(key, freq + 1);
        freqToKeys.computeIfAbsent(freq + 1, k -> new LinkedHashSet<>()).add(key);
    }

    public int get(int key) {
        if (!keyToVal.containsKey(key)) return -1;
        touch(key);
        return keyToVal.get(key);
    }

    public void put(int key, int value) {
        if (cap == 0) return;

        if (keyToVal.containsKey(key)) {
            keyToVal.put(key, value);
            touch(key);
            return;
        }

        if (keyToVal.size() == cap) {
            LinkedHashSet<Integer> bucket = freqToKeys.get(minFreq);
            int evict = bucket.iterator().next();   // oldest key at the lowest frequency
            bucket.remove(evict);
            if (bucket.isEmpty()) freqToKeys.remove(minFreq);
            keyToVal.remove(evict);
            keyToFreq.remove(evict);
        }

        keyToVal.put(key, value);
        keyToFreq.put(key, 1);
        freqToKeys.computeIfAbsent(1, k -> new LinkedHashSet<>()).add(key);
        minFreq = 1;                                 // the new key is the least frequent
    }
}
// Time: O(1) per operation, Space: O(capacity)
```

#### 716. [Max Stack](https://leetcode.com/problems/max-stack/) [H]

Description: A stack supporting `push`, `pop`, `top`, `peekMax`, and `popMax`.

Idea: A doubly-linked list gives stack order with O(1) removal from the middle — which `popMax` needs, since the maximum can sit anywhere. A `TreeMap<value, list of nodes>` gives the maximum in O(log n), and the list's **last** node is the most recently pushed copy of that value, which is the one `popMax` must remove.

**Java note.** The Python solution uses a heap with lazy deletion and an `alive` flag: `popMax` is amortized O(log n) but a pathological sequence can leave the heap arbitrarily large with dead entries. Java's `TreeMap` supports exact removal, so this version is worst-case O(log n) with no garbage — a genuinely better structure, not a transliteration.

```java
class MaxStack {
    private static final class Node {
        final int val;
        Node prev, next;

        Node(int val) { this.val = val; }
    }

    private final Node head = new Node(0);          // sentinel: bottom of the stack
    private final Node tail = new Node(0);          // sentinel: top of the stack
    private final TreeMap<Integer, List<Node>> byValue = new TreeMap<>();

    public MaxStack() {
        head.next = tail;
        tail.prev = head;
    }

    private void appendToTop(Node node) {
        Node last = tail.prev;
        last.next = node;
        node.prev = last;
        node.next = tail;
        tail.prev = node;
    }

    private void detach(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    public void push(int x) {
        Node node = new Node(x);
        appendToTop(node);
        byValue.computeIfAbsent(x, k -> new ArrayList<>()).add(node);
    }

    public int pop() {
        Node node = tail.prev;
        detach(node);
        removeFromIndex(node);
        return node.val;
    }

    public int top() { return tail.prev.val; }

    public int peekMax() { return byValue.lastKey(); }

    public int popMax() {
        int max = byValue.lastKey();
        List<Node> nodes = byValue.get(max);
        Node node = nodes.remove(nodes.size() - 1);  // most recently pushed copy
        if (nodes.isEmpty()) byValue.remove(max);
        detach(node);
        return max;
    }

    private void removeFromIndex(Node node) {
        List<Node> nodes = byValue.get(node.val);
        nodes.remove(nodes.size() - 1);              // the popped node is the newest of its value
        if (nodes.isEmpty()) byValue.remove(node.val);
    }
}
// Time: push/pop/peekMax/popMax O(log n), top O(1), Space: O(n)
```

#### 146. [LRU Cache](https://leetcode.com/problems/lru-cache/) [M]

Description: Design a cache with O(1) `get` and `put`, evicting the least-recently-used key when full.

Idea: Hash map `key -> node` plus a doubly-linked list ordered by recency. The map gives O(1) lookup, the list gives O(1) reordering, and sentinel head/tail nodes remove every null check from the splice logic.

**Java note.** Java also ships this: `LinkedHashMap` with `accessOrder = true` plus an overridden `removeEldestEntry` is a five-line LRU (see `26U/0.nc150-java.md#lc-0146`). Interviewers usually want the hand-rolled version, so that is what is written here — but knowing the built-in exists is worth a sentence.

```java
class LRUCache {
    private static final class Node {
        int key, val;
        Node prev, next;

        Node(int key, int val) { this.key = key; this.val = val; }
    }

    private final int cap;
    private final Map<Integer, Node> cache = new HashMap<>();
    private final Node head = new Node(0, 0);       // most-recent side
    private final Node tail = new Node(0, 0);       // least-recent side

    public LRUCache(int capacity) {
        this.cap = capacity;
        head.next = tail;
        tail.prev = head;
    }

    private void remove(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    private void addFront(Node node) {
        node.prev = head;
        node.next = head.next;
        head.next.prev = node;
        head.next = node;
    }

    public int get(int key) {
        Node node = cache.get(key);
        if (node == null) return -1;
        remove(node);
        addFront(node);
        return node.val;
    }

    public void put(int key, int value) {
        Node node = cache.get(key);
        if (node != null) {
            node.val = value;
            remove(node);
            addFront(node);
            return;
        }

        node = new Node(key, value);
        cache.put(key, node);
        addFront(node);

        if (cache.size() > cap) {
            Node lru = tail.prev;
            remove(lru);
            cache.remove(lru.key);                  // node stores its key precisely for this
        }
    }
}
// Time: O(1) per operation, Space: O(capacity)
```

⚠️ The node must store its `key`, not just its value. Eviction finds the node from the *list* and then needs to delete it from the *map* — without the key that lookup is impossible.

#### 208. [Implement Trie (Prefix Tree)](https://leetcode.com/problems/implement-trie-prefix-tree/) [M]

Description: Implement a trie supporting insert, search, and prefix queries.

Idea: Each node holds 26 child slots and an `end` flag marking a complete word. `search` and `startsWith` differ only in whether they check `end`.

**Java note.** Python uses a `dict` per node. Java's fixed `TrieNode[26]` array is faster and allocation-free per lookup, since the alphabet is known and small. Use a `HashMap<Character, TrieNode>` only when the alphabet is large or unknown (Unicode, arbitrary bytes).

```java
class Trie {
    private static final class TrieNode {
        final TrieNode[] children = new TrieNode[26];
        boolean end;
    }

    private final TrieNode root = new TrieNode();

    public Trie() {}

    public void insert(String word) {
        TrieNode node = root;
        for (char ch : word.toCharArray()) {
            int i = ch - 'a';
            if (node.children[i] == null) node.children[i] = new TrieNode();
            node = node.children[i];
        }
        node.end = true;
    }

    public boolean search(String word) {
        TrieNode node = walk(word);
        return node != null && node.end;
    }

    public boolean startsWith(String prefix) {
        return walk(prefix) != null;
    }

    private TrieNode walk(String s) {
        TrieNode node = root;
        for (char ch : s.toCharArray()) {
            node = node.children[ch - 'a'];
            if (node == null) return null;
        }
        return node;
    }
}
// Time: O(L) per operation where L is word length, Space: O(total chars inserted)
```

#### 355. [Design Twitter](https://leetcode.com/problems/design-twitter/) [M]

Description: Design a simplified Twitter with `postTweet`, `getNewsFeed` (10 most recent), `follow`, and `unfollow`.

Idea: Each user keeps an append-only list of `(time, tweetId)`, and a follow set. The feed is "merge k sorted lists, take 10" — seed a max-heap with each followee's newest tweet, then pop and push that user's next-newest.

**Java note.** Python stores negative timestamps so `heapq`'s min-heap behaves like a max-heap, and relies on tuple comparison for ordering. Java uses an explicit comparator on `int[]`, so timestamps stay positive and the intent is visible at the call site.

```java
class Twitter {
    private int time = 0;
    private final Map<Integer, List<int[]>> tweets = new HashMap<>();      // user -> {time, tweetId}
    private final Map<Integer, Set<Integer>> follows = new HashMap<>();

    public Twitter() {}

    public void postTweet(int userId, int tweetId) {
        tweets.computeIfAbsent(userId, k -> new ArrayList<>()).add(new int[]{++time, tweetId});
    }

    public List<Integer> getNewsFeed(int userId) {
        Set<Integer> followed = follows.computeIfAbsent(userId, k -> new HashSet<>());
        followed.add(userId);                        // you always see your own tweets

        // {time, tweetId, ownerId, nextIndex}, newest first
        PriorityQueue<int[]> heap = new PriorityQueue<>((a, b) -> b[0] - a[0]);
        for (int uid : followed) {
            List<int[]> tw = tweets.get(uid);
            if (tw == null || tw.isEmpty()) continue;
            int i = tw.size() - 1;
            heap.offer(new int[]{tw.get(i)[0], tw.get(i)[1], uid, i - 1});
        }

        List<Integer> res = new ArrayList<>();
        while (!heap.isEmpty() && res.size() < 10) {
            int[] top = heap.poll();
            res.add(top[1]);
            int i = top[3];
            if (i >= 0) {
                int[] prev = tweets.get(top[2]).get(i);
                heap.offer(new int[]{prev[0], prev[1], top[2], i - 1});
            }
        }
        return res;
    }

    public void follow(int followerId, int followeeId) {
        follows.computeIfAbsent(followerId, k -> new HashSet<>()).add(followeeId);
    }

    public void unfollow(int followerId, int followeeId) {
        if (followerId == followeeId) return;        // cannot unfollow yourself
        Set<Integer> s = follows.get(followerId);
        if (s != null) s.remove(followeeId);
    }
}
// Time: getNewsFeed O((k + 10) log k) for k followees, others O(1), Space: O(users + tweets)
```

#### 380. [Insert Delete GetRandom O(1)](https://leetcode.com/problems/insert-delete-getrandom-o1/) [M]

Description: Design a set supporting O(1) `insert`, `remove`, and `getRandom`.

Idea: An `ArrayList` of values gives O(1) uniform random access; a map `value -> index` gives O(1) lookup. Removal is the trick: swap the target with the **last** element, update that element's index, then remove from the end — deleting from the middle of a list would be O(n).

**Java note.** Python's `random.choice(list)` becomes `list.get(random.nextInt(list.size()))`.

```java
class RandomizedSet {
    private final List<Integer> vals = new ArrayList<>();
    private final Map<Integer, Integer> index = new HashMap<>();
    private final Random random = new Random();

    public RandomizedSet() {}

    public boolean insert(int val) {
        if (index.containsKey(val)) return false;
        index.put(val, vals.size());
        vals.add(val);
        return true;
    }

    public boolean remove(int val) {
        Integer i = index.get(val);
        if (i == null) return false;

        int last = vals.get(vals.size() - 1);
        vals.set(i, last);                           // move the tail into the hole
        index.put(last, i);
        vals.remove(vals.size() - 1);                // O(1): removing from the end
        index.remove(val);
        return true;
    }

    public int getRandom() {
        return vals.get(random.nextInt(vals.size()));
    }
}
// Time: O(1) per operation, Space: O(n)
```

⚠️ Order matters when removing the *last* element: `index.put(last, i)` runs before `index.remove(val)`, so when `val == last` the stale entry is cleaned up rather than resurrected.

#### 622. [Design Circular Queue](https://leetcode.com/problems/design-circular-queue/) [M]

Description: Implement a fixed-size circular queue.

Idea: A fixed array plus a head index and a live count. Storing the **count** rather than a tail index is what makes full and empty distinguishable — with two indices alone, `head == tail` is ambiguous.

```java
class MyCircularQueue {
    private final int k;
    private final int[] q;
    private int head;
    private int count;

    public MyCircularQueue(int k) {
        this.k = k;
        this.q = new int[k];
    }

    public boolean enQueue(int value) {
        if (isFull()) return false;
        q[(head + count) % k] = value;
        count++;
        return true;
    }

    public boolean deQueue() {
        if (isEmpty()) return false;
        head = (head + 1) % k;
        count--;
        return true;
    }

    public int Front() { return isEmpty() ? -1 : q[head]; }

    public int Rear() { return isEmpty() ? -1 : q[(head + count - 1) % k]; }

    public boolean isEmpty() { return count == 0; }

    public boolean isFull() { return count == k; }
}
// Time: O(1) per operation, Space: O(k)
```

#### 895. [Maximum Frequency Stack](https://leetcode.com/problems/max-frequency-stack/) [M]

Description: Design a stack that always pops the element with the highest frequency, breaking ties by the most recently pushed.

Idea: Track `val -> freq` and `freq -> stack of vals`, plus a running `maxFreq`. Pushing a value onto the stack for *its new frequency* means each frequency level keeps its own recency order, so the tie-break falls out for free. Popping takes from the `maxFreq` stack and decrements `maxFreq` when that level empties.

The non-obvious part: a value is left in *every* lower-frequency stack it passed through, and that is correct — after popping one copy, the remaining copies are exactly what the lower levels hold.

```java
class FreqStack {
    private final Map<Integer, Integer> freq = new HashMap<>();
    private final Map<Integer, Deque<Integer>> group = new HashMap<>();
    private int maxFreq;

    public FreqStack() {}

    public void push(int val) {
        int f = freq.merge(val, 1, Integer::sum);
        maxFreq = Math.max(maxFreq, f);
        group.computeIfAbsent(f, k -> new ArrayDeque<>()).push(val);
    }

    public int pop() {
        Deque<Integer> top = group.get(maxFreq);
        int val = top.pop();
        freq.merge(val, -1, Integer::sum);
        if (top.isEmpty()) maxFreq--;
        return val;
    }
}
// Time: O(1) per operation, Space: O(n)
```

#### 981. [Time Based Key-Value Store](https://leetcode.com/problems/time-based-key-value-store/) [M]

Description: A key-value store where each key holds timestamped values; `get` returns the value at the largest timestamp `<=` the query.

Idea: One sorted map per key. "Largest key at or below x" is precisely `TreeMap.floorEntry`.

**Java note.** This one does not translate. The Python solution binary-searches a list of tuples with `bisect_right(arr, (timestamp, chr(127)))` — a hack that fabricates a sentinel string guaranteed to sort after any real value, exploiting lexicographic tuple comparison. Java has no tuple ordering and no such sentinel, so the natural Java solution is a different structure entirely: `TreeMap.floorEntry` says what the code means, in one call.

```java
class TimeMap {
    private final Map<String, TreeMap<Integer, String>> store = new HashMap<>();

    public TimeMap() {}

    public void set(String key, String value, int timestamp) {
        store.computeIfAbsent(key, k -> new TreeMap<>()).put(timestamp, value);
    }

    public String get(String key, int timestamp) {
        TreeMap<Integer, String> tm = store.get(key);
        if (tm == null) return "";
        Map.Entry<Integer, String> e = tm.floorEntry(timestamp);   // largest key <= timestamp
        return e == null ? "" : e.getValue();
    }
}
// Time: set O(log n), get O(log n), Space: O(n)
```

Alternative when the problem guarantees strictly increasing timestamps (as LeetCode does): keep a plain `ArrayList` per key and hand-roll the binary search, giving O(1) `set`. That version is in `26U/0.nc150-java.md#lc-0981`.

#### 1146. [Snapshot Array](https://leetcode.com/problems/snapshot-array/) [M]

Description: An array supporting O(1) snapshots and historical value queries.

Idea: Do not copy the array on `snap` — that would be O(length) per snapshot. Instead each index keeps its own history of `(snapId, value)` records, and `snap` just increments a counter. A query binary-searches that index's history for the newest record at or before the requested snapshot.

**Java note.** Same problem as 981: Python's `bisect_right(arr, (snap_id, float('inf')))` relies on tuple ordering with an infinite sentinel. Rewritten with a per-index `TreeMap` and `floorEntry`.

```java
class SnapshotArray {
    private final TreeMap<Integer, Integer>[] history;
    private int snapId;

    @SuppressWarnings("unchecked")
    public SnapshotArray(int length) {
        history = new TreeMap[length];
        for (int i = 0; i < length; i++) {
            history[i] = new TreeMap<>();
            history[i].put(0, 0);                    // every index starts at 0
        }
    }

    public void set(int index, int val) {
        history[index].put(snapId, val);             // overwrites within the same snapshot
    }

    public int snap() {
        return snapId++;                             // O(1): no copying
    }

    public int get(int index, int snapId) {
        return history[index].floorEntry(snapId).getValue();
    }
}
// Time: set/get O(log S), snap O(1), Space: O(length + total sets)
```

#### 1472. [Design Browser History](https://leetcode.com/problems/design-browser-history/) [M]

Description: Implement browser history with `visit`, `back`, and `forward`.

Idea: Two stacks. `back` moves the current page onto the forward stack; `visit` clears the forward stack, because navigating somewhere new discards the branch you could have gone forward into. Keeping the current page on top of `backStack` (rather than in its own field) is what makes `back(steps)` a simple loop with the `size() > 1` guard.

```java
class BrowserHistory {
    private final Deque<String> backStack = new ArrayDeque<>();
    private final Deque<String> forwardStack = new ArrayDeque<>();

    public BrowserHistory(String homepage) {
        backStack.push(homepage);
    }

    public void visit(String url) {
        backStack.push(url);
        forwardStack.clear();                        // the forward branch is now unreachable
    }

    public String back(int steps) {
        while (steps > 0 && backStack.size() > 1) {  // never pop past the homepage
            forwardStack.push(backStack.pop());
            steps--;
        }
        return backStack.peek();
    }

    public String forward(int steps) {
        while (steps > 0 && !forwardStack.isEmpty()) {
            backStack.push(forwardStack.pop());
            steps--;
        }
        return backStack.peek();
    }
}
// Time: back/forward O(steps), visit O(1) amortized, Space: O(n)
```

Alternative: an `ArrayList` plus a current-index pointer, where `visit` truncates everything after the index. Same complexity, and `forward` becomes O(1); worth mentioning as the follow-up.

#### 155. [Min Stack](https://leetcode.com/problems/min-stack/) [E]

Description: Design a stack supporting `push`, `pop`, `top`, and retrieving the minimum element in O(1).

##### Approach 1: Parallel min-stack

Idea: Keep a second stack whose top is always the minimum of everything currently in the main stack. Pushing the running minimum at every level makes `pop` a plain pop on both.

```java
class MinStack {
    private final Deque<Integer> st = new ArrayDeque<>();
    private final Deque<Integer> minSt = new ArrayDeque<>();

    public MinStack() {}

    public void push(int val) {
        st.push(val);
        minSt.push(minSt.isEmpty() ? val : Math.min(val, minSt.peek()));
    }

    public void pop() {
        st.pop();
        minSt.pop();
    }

    public int top() { return st.peek(); }

    public int getMin() { return minSt.peek(); }
}
// Time: O(1) per operation, Space: O(n)
```

##### Approach 2: Single stack of deltas

Idea: Store `val - min` instead of `val`. A negative entry means this push lowered the minimum, so popping it recovers the previous minimum as `min - delta`.

**Java note.** `val - min` can exceed `int` range when values straddle `Integer.MIN_VALUE`/`MAX_VALUE`, so the deltas are stored as `long`. Python's unbounded integers hide this; Java does not.

```java
class MinStack {
    private final Deque<Long> stack = new ArrayDeque<>();
    private long min;

    public MinStack() {}

    public void push(int val) {
        if (stack.isEmpty()) {
            stack.push(0L);
            min = val;
        } else {
            stack.push(val - min);                   // long arithmetic: cannot overflow
            if (val < min) min = val;
        }
    }

    public void pop() {
        long popped = stack.pop();
        if (popped < 0) min = min - popped;          // this push had set the minimum
    }

    public int top() {
        long t = stack.peek();
        return (int) (t > 0 ? t + min : min);
    }

    public int getMin() { return (int) min; }
}
// Time: O(1) per operation, Space: O(n)
```

#### 225. [Implement Stack using Queues](https://leetcode.com/problems/implement-stack-using-queues/) [E]

Description: Implement a LIFO stack using only queue operations.

##### Approach 1: One queue, rotate on push

Idea: After enqueuing the new element, rotate every *previous* element to the back. The queue front is then always the most recently pushed element, so `pop` and `top` are O(1).

```java
class MyStack {
    private final Queue<Integer> q = new ArrayDeque<>();

    public MyStack() {}

    public void push(int x) {
        q.offer(x);
        for (int i = q.size() - 1; i > 0; i--) {     // rotate the older elements behind x
            q.offer(q.poll());
        }
    }

    public int pop() { return q.poll(); }

    public int top() { return q.peek(); }

    public boolean empty() { return q.isEmpty(); }
}
// Time: push O(n), others O(1), Space: O(n)
```

##### Approach 2: Two queues, work on pop

Idea: Push is O(1). On pop, move all but the last element to the second queue, take the survivor, then swap the roles of the two queues.

**Java note.** Python swaps queues with tuple assignment `self.q1, self.q2 = self.q2, self.q1`. Java needs an explicit temporary — or, as below, non-final fields and a three-line swap.

```java
class MyStack {
    private Queue<Integer> q1 = new ArrayDeque<>();
    private Queue<Integer> q2 = new ArrayDeque<>();

    public MyStack() {}

    public void push(int x) { q1.offer(x); }

    public int pop() {
        while (q1.size() > 1) q2.offer(q1.poll());
        int val = q1.poll();
        Queue<Integer> tmp = q1;                     // no tuple assignment in Java
        q1 = q2;
        q2 = tmp;
        return val;
    }

    public int top() {
        int val = pop();
        q1.offer(val);                               // q1 is now empty-ish; re-push is safe
        return val;
    }

    public boolean empty() { return q1.isEmpty(); }
}
// Time: pop/top O(n), push O(1), Space: O(n)
```

#### 232. [Implement Queue using Stacks](https://leetcode.com/problems/implement-queue-using-stacks/) [E]

Description: Implement a FIFO queue using only two stacks.

Idea: Lazy transfer. Push onto `inStack`; on `pop`/`peek`, dump `inStack` into `outStack` (which reverses the order) **only when `outStack` is empty**. Every element is moved at most once, so each operation is amortized O(1) even though a single `pop` can be O(n).

```java
class MyQueue {
    private final Deque<Integer> inStack = new ArrayDeque<>();
    private final Deque<Integer> outStack = new ArrayDeque<>();

    public MyQueue() {}

    public void push(int x) { inStack.push(x); }

    /** Refill only when out is empty — refilling early would break the ordering. */
    private void transfer() {
        if (outStack.isEmpty()) {
            while (!inStack.isEmpty()) outStack.push(inStack.pop());
        }
    }

    public int pop() {
        transfer();
        return outStack.pop();
    }

    public int peek() {
        transfer();
        return outStack.peek();
    }

    public boolean empty() { return inStack.isEmpty() && outStack.isEmpty(); }
}
// Time: amortized O(1) per operation, Space: O(n)
```

## Synchronization

Concurrent data-structure design: the IDE-based OA and machine-coding round where you are handed a single-threaded structure and told "now make it safe under `n` threads", or handed a scenario and told to build the structure from scratch.

What is actually graded, in order:

1. **Correctness of the invariant** — name the shared mutable state and show no interleaving can break it.
2. **Atomicity of compound operations** — nearly every bug in this round is a check-then-act that is not atomic. `containsKey` then `put` is two operations, and the gap is where you lose.
3. **Locking granularity** — a single global lock is correct and usually the right first answer. Whether you can then justify a finer scheme (per-key, striped, read-write, lock-free) is what separates the grades.
4. **Liveness** — no deadlock, no lost wakeup, no unbounded growth.
5. **Not over-engineering** — reaching for `StampedLock` when `ConcurrentHashMap.merge` would do reads as a red flag.

Say the invariant out loud before writing code. "At most `capacity` entries exist, and the eviction victim is always the globally least-recently-used key" is a sentence you can then defend line by line.

### Toolkit

#### Primitives, and when each is the right answer

| Primitive | Use when | Notes |
| --- | --- | --- |
| `synchronized` | One short critical section, no timeout needed | Reentrant, released on exception automatically. Simplest correct answer. |
| `ReentrantLock` | You need `tryLock`, a timeout, or several `Condition`s | Must `unlock()` in `finally` — no automatic release. |
| `ReentrantReadWriteLock` | Reads vastly outnumber writes **and** reads do not mutate | Writers can starve unless constructed fair. A read lock cannot be upgraded to a write lock. |
| `StampedLock` | Read-dominated and you have measured RRWL as the bottleneck | Optimistic reads are not reentrant and must be validated. Rarely worth it in an interview. |
| `ConcurrentHashMap` | A map that many threads touch | Per-operation atomicity only — see the trap below. |
| `Atomic*` / `LongAdder` | A single counter or reference | `LongAdder` beats `AtomicLong` under heavy write contention. |
| `Semaphore` | Bounding *how many* threads may proceed (pools, download slots) | `tryAcquire(timeout)` gives you backpressure with a deadline. |
| `CountDownLatch` | Wait for `n` one-off events | Single use — cannot be reset. |
| `CyclicBarrier` / `Phaser` | Threads rendezvous repeatedly | Reusable, unlike a latch. |
| `BlockingQueue` | Producer/consumer handoff | Prefer it over hand-rolled `wait`/`notify` unless the question asks you to hand-roll. |
| `ExecutorService` | Anything that runs tasks | Never `new Thread()` in a design answer. |
| `CompletableFuture` | Composing async steps, chaining per-key work | `thenCompose` for sequencing, `allOf` for fan-in. |
| `volatile` | One flag or an immutable snapshot reference | Gives visibility and ordering, **not** atomicity. `volatile int i; i++` is still a race. |
| immutable / `record` | The value never changes after publication | Needs no synchronization at all. The cheapest correct answer — reach for it first. |

#### The memory model, in three sentences

Without synchronization there is no guarantee another thread ever sees your write — the JIT and the CPU may reorder or cache it indefinitely. A *happens-before* edge is what forces visibility, and you get one from: releasing a lock the other thread acquires, writing a `volatile` the other thread reads, `Thread.start()` / `Thread.join()`, and safe publication of `final` fields from a constructor. `volatile` fixes visibility and ordering but never makes a read-modify-write atomic.

#### The five bugs that fail this round

**1. Check-then-act.** The single most common failure.

```java
// BROKEN: two threads can both pass the check
if (!map.containsKey(k)) map.put(k, compute());
if (count < limit) count++;
if (!queue.isEmpty()) queue.poll();

// FIXED: one atomic operation, or one lock covering both steps
map.computeIfAbsent(k, key -> compute());
map.putIfAbsent(k, v);
map.merge(k, 1, Integer::sum);
counter.incrementAndGet();
Integer head = queue.poll();          // returns null instead of throwing
if (head != null) { ... }
```

⚠️ `ConcurrentHashMap` makes each *call* atomic, not each *sequence of calls*. A `ConcurrentHashMap` guarded by nothing is still racy the moment your logic spans two calls.

**2. Lost wakeup — `if` instead of `while`.**

```java
// BROKEN: spurious wakeups are legal, and another thread may win the race
// between notify() and this thread reacquiring the monitor.
if (queue.isEmpty()) wait();

// FIXED: always re-check the condition in a loop
while (queue.isEmpty()) wait();
```

Same rule for `Condition.await()`. And prefer `notifyAll()` / `signalAll()` unless you can prove every waiter is interchangeable — a `notify()` that wakes the wrong waiter deadlocks the system.

**3. Nested locks taken in inconsistent order.** Two threads locking `A` then `B` and `B` then `A` deadlock. Two fixes: impose a **global order** (lock by ascending id), or **do not hold one lock while acquiring another** — release the first, then take the second, and re-validate. The second is usually simpler and is what most of the solutions below do.

**4. Escaping references.** Handing out your internal collection or node lets callers mutate it outside your lock. Return `List.copyOf(...)` or an immutable snapshot.

**5. Unbounded growth.** A per-client map keyed by client id, with no eviction, is a memory leak in a long-running service. If you create per-key state, say how it is reclaimed.

#### Choosing granularity — the three-step answer

Interviewers want to hear the progression, not the endpoint:

1. **One lock over the whole structure.** Correct, trivially reviewable. Bottleneck: every operation serializes.
2. **Split the lock.** Per-key locks (if keys are independent), striping into `N` segments (if keys are many and you want bounded lock count), or read-write (if reads dominate and are truly read-only).
3. **Remove the lock.** `ConcurrentHashMap` + atomics, CAS retry loops, or immutable snapshots swapped through a `volatile`. Only when the invariant is per-key or fits in one CAS.

Striping is the standard middle answer: `locks[spread(key.hashCode()) & (STRIPES - 1)]`, with `STRIPES` a power of two. It bounds the number of lock objects while letting unrelated keys proceed in parallel.

⚠️ Do not do expensive work, block, or touch the same map inside `ConcurrentHashMap.computeIfAbsent` — the bin is locked for the duration, and re-entering the same map from the mapping function can deadlock. Create cheap, empty state there and populate it afterwards.

#### S1. Per-client LRU cache with a shared memory budget

**Context.** A multi-tenant API caches responses per client. The process has one memory budget shared by every client, but no single noisy client may evict everyone else's data. Build a cache with `get(clientId, key)` / `put(clientId, key, value)` that is safe under many request threads, keeps a per-client LRU order, caps each client at `perClientMax` entries, and keeps the total across all clients at or under `globalCapacity`.

**Invariant.** Every client's entries are a correct LRU list capped at `perClientMax`; the sum over all clients never stays above `globalCapacity`; and when the global budget is exceeded, the victim is the LRU entry of the *largest* client.

**Shared mutable state.** The client map, each client's list and map, and the global size counter.

**Design.** Each client gets its own independent LRU with its own lock, so two clients never contend. A `ConcurrentHashMap` holds the clients and an `AtomicInteger` tracks the global total.

The critical decision is the global eviction path. The tempting version — while holding client A's lock, find the biggest client B and lock it — takes two client locks in an order that depends on runtime data, which is exactly bug pattern 3. **So the budget is enforced with no client lock held**: insert under A's lock, release it, then lock one victim at a time. That is why `enforceGlobalBudget` is called after the `try`/`finally` block rather than inside it.

Victim selection reads each client's `size` without locking. That is a deliberately approximate read — picking a slightly stale "largest client" only affects *which* entry is evicted, never whether the invariant holds, and the loop re-reads on the next pass.

```java
import java.util.*;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantLock;

public class PerClientLruCache<K, V> {

    private static final class Node<K, V> {
        final K key;
        V value;
        Node<K, V> prev, next;

        Node(K key, V value) { this.key = key; this.value = value; }
    }

    /** One independent LRU list per client, guarded by its own lock. */
    private static final class ClientCache<K, V> {
        final ReentrantLock lock = new ReentrantLock();
        final Map<K, Node<K, V>> map = new HashMap<>();
        final Node<K, V> head = new Node<>(null, null);
        final Node<K, V> tail = new Node<>(null, null);
        final int maxEntries;
        /** Written only under {@code lock}; volatile so victim selection can read it lock-free. */
        volatile int size;
        boolean dead;

        ClientCache(int maxEntries) {
            this.maxEntries = maxEntries;
            head.next = tail;
            tail.prev = head;
        }

        void unlink(Node<K, V> n) {
            n.prev.next = n.next;
            n.next.prev = n.prev;
        }

        void addFront(Node<K, V> n) {
            n.prev = head;
            n.next = head.next;
            head.next.prev = n;
            head.next = n;
        }

        V get(K key) {
            Node<K, V> n = map.get(key);
            if (n == null) return null;
            unlink(n);
            addFront(n);
            return n.value;
        }

        /** @return net change in entry count (+1 new, 0 overwrite or evicted-on-insert). */
        int put(K key, V value) {
            Node<K, V> n = map.get(key);
            if (n != null) {
                n.value = value;
                unlink(n);
                addFront(n);
                return 0;
            }
            n = new Node<>(key, value);
            map.put(key, n);
            addFront(n);
            size = size + 1;                       // safe: always under lock
            int delta = 1;
            while (size > maxEntries && evictLru()) delta--;
            return delta;
        }

        boolean evictLru() {
            Node<K, V> lru = tail.prev;
            if (lru == head) return false;
            unlink(lru);
            map.remove(lru.key);
            size = size - 1;
            return true;
        }

        boolean remove(K key) {
            Node<K, V> n = map.remove(key);
            if (n == null) return false;
            unlink(n);
            size = size - 1;
            return true;
        }
    }

    private final int globalCapacity;
    private final int perClientMax;
    private final ConcurrentHashMap<String, ClientCache<K, V>> clients = new ConcurrentHashMap<>();
    private final AtomicInteger totalSize = new AtomicInteger();

    public PerClientLruCache(int globalCapacity, int perClientMax) {
        if (globalCapacity <= 0 || perClientMax <= 0) {
            throw new IllegalArgumentException("capacities must be positive");
        }
        this.globalCapacity = globalCapacity;
        this.perClientMax = perClientMax;
    }

    public V get(String clientId, K key) {
        ClientCache<K, V> c = clients.get(clientId);
        if (c == null) return null;
        c.lock.lock();
        try {
            return c.get(key);
        } finally {
            c.lock.unlock();
        }
    }

    public void put(String clientId, K key, V value) {
        int delta = 0;
        while (true) {
            // The mapping function only allocates — never block inside computeIfAbsent.
            ClientCache<K, V> c = clients.computeIfAbsent(clientId, id -> new ClientCache<>(perClientMax));
            boolean retired;
            c.lock.lock();
            try {
                retired = c.dead;                  // retired between lookup and lock: retry
                if (!retired) delta = c.put(key, value);
            } finally {
                c.lock.unlock();
            }
            if (!retired) break;
        }
        if (delta != 0) totalSize.addAndGet(delta);
        enforceGlobalBudget();                     // deliberately OUTSIDE the client lock
    }

    public boolean remove(String clientId, K key) {
        ClientCache<K, V> c = clients.get(clientId);
        if (c == null) return false;
        boolean removed;
        c.lock.lock();
        try {
            removed = c.remove(key);
        } finally {
            c.lock.unlock();
        }
        if (removed) totalSize.decrementAndGet();
        return removed;
    }

    /** Call when a tenant disconnects, so per-client state cannot accumulate forever. */
    public void removeClient(String clientId) {
        ClientCache<K, V> c = clients.remove(clientId);
        if (c == null) return;
        c.lock.lock();
        try {
            c.dead = true;                         // a racing put() will notice and retry
            totalSize.addAndGet(-c.size);
            c.map.clear();
            c.head.next = c.tail;
            c.tail.prev = c.head;
            c.size = 0;
        } finally {
            c.lock.unlock();
        }
    }

    /**
     * Evict from the largest client until the global budget holds.
     * Takes at most ONE client lock at a time — never nests.
     */
    private void enforceGlobalBudget() {
        while (totalSize.get() > globalCapacity) {
            ClientCache<K, V> victim = null;
            int worst = 0;
            for (ClientCache<K, V> c : clients.values()) {
                int s = c.size;                    // approximate by design
                if (s > worst) {
                    worst = s;
                    victim = c;
                }
            }
            if (victim == null) return;            // nothing left to evict

            boolean evicted;
            victim.lock.lock();
            try {
                evicted = victim.evictLru();
            } finally {
                victim.lock.unlock();
            }
            if (evicted) totalSize.decrementAndGet();
            else return;                           // victim emptied under us; retry next call
        }
    }

    public int size() { return totalSize.get(); }

    public int clientCount() { return clients.size(); }
}
// Time: O(1) per get/put (plus O(clients) per eviction pass), Space: O(globalCapacity + clients)
```

**Interleavings this defends against.**

- *Two threads putting for the same new client.* `computeIfAbsent` guarantees exactly one `ClientCache` is created; the loser sees the winner's instance.
- *Put racing with `removeClient`.* Without the `dead` flag the put would land in an orphaned cache and permanently inflate `totalSize`, causing the cache to over-evict forever. The flag turns it into a retry.
- *Two threads over budget at once.* Both run `enforceGlobalBudget`; each eviction is guarded by the victim's lock and each decrement is atomic, so they cannot double-count one entry. They may evict one entry more than strictly necessary, which is acceptable for a cache.

`totalSize` briefly under-counts between releasing the client lock and the `addAndGet`. That can delay an eviction by one operation; it can never let the total grow without bound, because the next `put` re-checks.

**Follow-ups.**

- *True global LRU instead of largest-client.* Requires one global recency ordering, which reintroduces a single contended structure — the honest answer is that per-client isolation and global LRU are in tension, and multi-tenant systems deliberately choose isolation.
- *Byte-based budget rather than entry count.* Replace the counters with sizes; nothing structural changes.
- *Auto-retiring empty clients.* Do it in `clients.computeIfPresent`, taking the client lock inside the mapping function — bin lock then client lock. That order is safe only because `put` releases the bin lock before taking the client lock, so no cycle exists. Getting that argument right is the whole answer.
- *Guaranteed minimum per tenant.* Skip any client at or below its reserved floor during victim selection.

#### S2. Thread-safe LRU cache under read-heavy load

**Context.** An existing single-threaded `LRUCache` (see [146](#lc-0146)) is being moved behind a service that serves thousands of concurrent reads. Make it thread-safe, then make it scale.

**The trap.** "Reads dominate, so use a `ReadWriteLock`" is wrong here, and interviewers ask precisely because it sounds right. In an LRU, `get` **moves the node to the front** — it is a writer. Guarding it with a read lock corrupts the linked list. Either accept that `get` takes the write lock, or change the recency mechanism.

##### Approach 1: One lock (the correct first answer)

Idea: Wrap the existing structure. Simple, obviously correct, and genuinely fine when the critical section is a few pointer swaps.

```java
import java.util.*;
import java.util.concurrent.locks.ReentrantLock;

public class SynchronizedLruCache<K, V> {
    private final int capacity;
    private final LinkedHashMap<K, V> map;
    private final ReentrantLock lock = new ReentrantLock();

    public SynchronizedLruCache(int capacity) {
        this.capacity = capacity;
        this.map = new LinkedHashMap<>(16, 0.75f, true) {      // true = access order
            @Override
            protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                return size() > SynchronizedLruCache.this.capacity;
            }
        };
    }

    public V get(K key) {
        lock.lock();
        try {
            return map.get(key);        // reorders the list, so this is a WRITE
        } finally {
            lock.unlock();
        }
    }

    public void put(K key, V value) {
        lock.lock();
        try {
            map.put(key, value);
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return map.size();
        } finally {
            lock.unlock();
        }
    }
}
// Time: O(1) per operation, serialized. Space: O(capacity)
```

⚠️ `Collections.synchronizedMap(new LinkedHashMap<>(...))` looks equivalent but is not: iteration over it still requires manual synchronization, and any compound operation of yours is still racy.

##### Approach 2: Striped segments

Idea: Shard into `S` independent LRU segments, each with its own lock and its own capacity `capacity / S`. Keys hash to a segment, so unrelated keys never contend, and lock count is bounded regardless of key count.

The honest cost: eviction becomes **per-segment** LRU, not global LRU. With a decent hash and `S` small relative to capacity, hit rates are close — but say it, do not hide it.

```java
import java.util.*;
import java.util.concurrent.locks.ReentrantLock;

public class StripedLruCache<K, V> {

    private static final class Segment<K, V> {
        final ReentrantLock lock = new ReentrantLock();
        final LinkedHashMap<K, V> map;

        Segment(int cap) {
            this.map = new LinkedHashMap<>(16, 0.75f, true) {
                @Override
                protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                    return size() > cap;
                }
            };
        }
    }

    private final Segment<K, V>[] segments;
    private final int mask;

    @SuppressWarnings("unchecked")
    public StripedLruCache(int capacity, int stripes) {
        int s = Integer.highestOneBit(Math.max(1, stripes));   // round down to a power of two
        this.mask = s - 1;
        this.segments = new Segment[s];
        int perSegment = Math.max(1, capacity / s);
        for (int i = 0; i < s; i++) segments[i] = new Segment<>(perSegment);
    }

    private Segment<K, V> segmentFor(K key) {
        int h = key.hashCode();
        h ^= (h >>> 16);                    // spread: raw hashCode often has weak low bits
        return segments[h & mask];
    }

    public V get(K key) {
        Segment<K, V> seg = segmentFor(key);
        seg.lock.lock();
        try {
            return seg.map.get(key);
        } finally {
            seg.lock.unlock();
        }
    }

    public void put(K key, V value) {
        Segment<K, V> seg = segmentFor(key);
        seg.lock.lock();
        try {
            seg.map.put(key, value);
        } finally {
            seg.lock.unlock();
        }
    }

    public int size() {
        int total = 0;
        for (Segment<K, V> seg : segments) {
            seg.lock.lock();
            try {
                total += seg.map.size();
            } finally {
                seg.lock.unlock();
            }
        }
        return total;                       // a snapshot, not an instant
    }
}
// Time: O(1) per operation, contention only within a stripe. Space: O(capacity)
```

**Follow-ups.**

- *Can `get` ever be lock-free?* Yes, if you drop strict LRU. Store a `volatile long lastAccess` per entry, write it on read with no lock, and have eviction sample a handful of entries and drop the oldest. That is approximately what production caches (Caffeine, Redis) do, and it is the real answer to "make reads scale".
- *Why not `ConcurrentHashMap` alone?* It gives you the map but no recency order and no eviction. You still need the list, and the list is what needs the lock.

#### S3. Bounded blocking queue

**Context.** A worker pool consumes tasks produced by request threads. Build a fixed-capacity queue where `enqueue` blocks while full and `dequeue` blocks while empty, with many producers and many consumers. (LC 1188.)

**Invariant.** Size is always in `[0, capacity]`; no element is delivered twice or lost; a blocked thread is always eventually woken when its condition can hold.

##### Approach 1: `synchronized` + `wait`/`notifyAll`

Idea: One monitor guards the deque. Both waits use `while`, not `if` — spurious wakeups are legal, and between `notifyAll` and reacquiring the monitor another thread may have consumed the slot.

```java
import java.util.ArrayDeque;
import java.util.Deque;

public class BoundedBlockingQueue<E> {
    private final Deque<E> queue = new ArrayDeque<>();
    private final int capacity;

    public BoundedBlockingQueue(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
        this.capacity = capacity;
    }

    public synchronized void enqueue(E element) throws InterruptedException {
        while (queue.size() == capacity) wait();     // WHILE, never IF
        queue.offerLast(element);
        notifyAll();                                 // may have unblocked a consumer
    }

    public synchronized E dequeue() throws InterruptedException {
        while (queue.isEmpty()) wait();
        E value = queue.pollFirst();
        notifyAll();                                 // may have unblocked a producer
        return value;
    }

    public synchronized int size() { return queue.size(); }
}
// Time: O(1) per operation, Space: O(capacity)
```

⚠️ `notify()` instead of `notifyAll()` deadlocks here. With one monitor and two kinds of waiter, `notify` can wake a producer when only consumers can make progress; that producer re-checks, waits again, and the wakeup is consumed forever. Use `notifyAll`, or move to two `Condition`s.

##### Approach 2: `ReentrantLock` with two `Condition`s

Idea: Separate waiting rooms mean a signal only ever reaches a thread that can actually proceed, so `signal()` is safe and cheaper than `notifyAll()`. This is how `ArrayBlockingQueue` is written, and it also gives you timeouts.

```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public class BoundedBlockingQueue<E> {
    private final Deque<E> queue = new ArrayDeque<>();
    private final int capacity;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBlockingQueue(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("capacity must be positive");
        this.capacity = capacity;
    }

    public void enqueue(E element) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.size() == capacity) notFull.await();
            queue.offerLast(element);
            notEmpty.signal();                  // exactly one consumer can proceed
        } finally {
            lock.unlock();
        }
    }

    public E dequeue() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) notEmpty.await();
            E value = queue.pollFirst();
            notFull.signal();
            return value;
        } finally {
            lock.unlock();
        }
    }

    /** @return null if nothing arrived before the deadline. */
    public E poll(long timeout, TimeUnit unit) throws InterruptedException {
        long nanos = unit.toNanos(timeout);
        lock.lockInterruptibly();
        try {
            while (queue.isEmpty()) {
                if (nanos <= 0) return null;
                nanos = notEmpty.awaitNanos(nanos);   // returns the REMAINING time
            }
            E value = queue.pollFirst();
            notFull.signal();
            return value;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return queue.size();
        } finally {
            lock.unlock();
        }
    }
}
// Time: O(1) per operation, Space: O(capacity)
```

⚠️ `awaitNanos` returns the time *remaining*, not the time elapsed. Reassigning `nanos` is what makes the timeout loop terminate; recomputing it from a fresh timestamp on every spurious wakeup would let the deadline drift forever.

**Follow-up.** In production, use `ArrayBlockingQueue` or `LinkedBlockingQueue` — say so. This question exists to see whether you understand what they do, not because you should reimplement them.

#### S4. Thread-safe cache with TTL and background eviction

**Context.** An in-memory cache where each entry carries a TTL. Expired entries must never be returned, and must not accumulate even if nobody ever reads them again. Many threads read and write concurrently.

**Design.** Two mechanisms, both needed:

- **Lazy expiry** on read makes correctness immediate but reclaims nothing for keys nobody reads.
- **Active expiry** in a background sweeper reclaims memory but must not scan every key on every tick.

**The key move: no lock at all.** Make the entry an immutable value holding both value and deadline, keep it in a `ConcurrentHashMap`, and use the two-argument `map.remove(key, entry)` — which removes *only if the mapping still points at that exact entry*. That is a compare-and-swap, and it makes the classic race harmless: if a writer replaced the entry between our read and our removal, our remove simply fails and the fresh entry survives.

```java
import java.util.Optional;
import java.util.concurrent.*;

public class TtlCache<K, V> implements AutoCloseable {

    /** Immutable: safely publishable, needs no synchronization of its own. */
    private static final class Entry<V> {
        final V value;
        final long expiresAtNanos;

        Entry(V value, long expiresAtNanos) {
            this.value = value;
            this.expiresAtNanos = expiresAtNanos;
        }

        boolean isExpired(long now) { return now - expiresAtNanos >= 0; }
    }

    private record ExpiryRef<K>(K key, long expiresAtNanos) {}

    private final ConcurrentHashMap<K, Entry<V>> map = new ConcurrentHashMap<>();
    private final PriorityBlockingQueue<ExpiryRef<K>> expiries =
        new PriorityBlockingQueue<>(16, (a, b) -> Long.compare(a.expiresAtNanos(), b.expiresAtNanos()));
    private final ScheduledExecutorService sweeper;

    public TtlCache(long sweepPeriodMillis) {
        sweeper = Executors.newSingleThreadScheduledExecutor(r -> {
            Thread t = new Thread(r, "ttl-cache-sweeper");
            t.setDaemon(true);                       // never block JVM shutdown
            return t;
        });
        sweeper.scheduleAtFixedRate(this::evictExpired,
            sweepPeriodMillis, sweepPeriodMillis, TimeUnit.MILLISECONDS);
    }

    public void put(K key, V value, long ttlMillis) {
        if (ttlMillis <= 0) throw new IllegalArgumentException("ttl must be positive");
        long expiresAt = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(ttlMillis);
        map.put(key, new Entry<>(value, expiresAt));
        expiries.offer(new ExpiryRef<>(key, expiresAt));
        // A stale ExpiryRef for an overwritten key is left in the queue on purpose;
        // the sweeper validates against the map before removing anything.
    }

    public Optional<V> get(K key) {
        Entry<V> entry = map.get(key);
        if (entry == null) return Optional.empty();
        if (entry.isExpired(System.nanoTime())) {
            map.remove(key, entry);      // CAS: only removes if still THIS entry
            return Optional.empty();
        }
        return Optional.of(entry.value);
    }

    public boolean remove(K key) { return map.remove(key) != null; }

    /** Package-visible for tests; also runs on the sweeper thread. */
    int evictExpired() {
        long now = System.nanoTime();
        int removed = 0;
        while (true) {
            ExpiryRef<K> head = expiries.peek();
            if (head == null || head.expiresAtNanos() - now > 0) break;
            if (!expiries.remove(head)) break;                 // another sweeper took it

            Entry<V> current = map.get(head.key());
            if (current == null) continue;                     // already gone
            if (current.expiresAtNanos != head.expiresAtNanos()) continue;  // stale ref: key was rewritten
            if (map.remove(head.key(), current)) removed++;    // CAS again
        }
        return removed;
    }

    /** Live entries. O(n) because expired-but-unswept entries must be skipped. */
    public int size() {
        long now = System.nanoTime();
        int count = 0;
        for (Entry<V> e : map.values()) if (!e.isExpired(now)) count++;
        return count;
    }

    @Override
    public void close() { sweeper.shutdownNow(); }
}
// Time: get/put O(1), sweep O(evicted * log n), Space: O(n)
```

**Why not `ReadWriteLock`?** Because lazy expiry *mutates on read*. Holding the read lock you discover the entry is expired, but you cannot remove it — and `ReentrantReadWriteLock` cannot upgrade a read lock to a write lock (attempting it deadlocks instantly). You would have to release, re-acquire as a writer, and re-validate. The immutable-entry plus CAS-remove design sidesteps the whole problem.

⚠️ Use `System.nanoTime()`, not `currentTimeMillis()`, for deadlines — the wall clock can jump backwards on NTP correction and freeze your TTLs. Compare with subtraction (`now - deadline >= 0`) rather than `now >= deadline`, so the comparison survives `nanoTime` overflow.

**Follow-ups.**

- *Bounded size as well as TTL* — compose with the LRU above. TTL decides *validity*; LRU decides *which valid entry to sacrifice*.
- *Sweeper cost* — a `PriorityBlockingQueue` sweep touches only expired keys. Redis instead samples random keys, trading exactness for a strict bound on sweep time.
- *Cache stampede* — when a hot key expires, every thread misses at once and hammers the origin. Fix with `map.computeIfAbsent`-style single-flight or a `CompletableFuture` placeholder so only one loader runs.

#### S5. Per-client rate limiter

**Context.** An API gateway allows each client `n` requests per second with a burst allowance. `allow(clientId)` is called from every request thread. One client's traffic must not slow down another's.

**The race.** Two threads read "1 token left", both decide to proceed, both decrement — two requests admitted under a limit of one. Reading the token count and decrementing it must be a single atomic step.

**Design.** A `ConcurrentHashMap<String, Bucket>` with the lock on the *bucket*, not on the map. Different clients then never contend at all. Tokens refill lazily from elapsed time, so there is no background thread and memory is O(1) per client.

##### Approach 1: Per-bucket lock

```java
import java.util.concurrent.ConcurrentHashMap;

public class TokenBucketRateLimiter {

    private static final class Bucket {
        double tokens;
        long lastRefillNanos;

        Bucket(double tokens, long now) {
            this.tokens = tokens;
            this.lastRefillNanos = now;
        }
    }

    private final double capacity;
    private final double tokensPerNano;
    private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();

    public TokenBucketRateLimiter(double capacity, double refillPerSecond) {
        this.capacity = capacity;
        this.tokensPerNano = refillPerSecond / 1_000_000_000.0;
    }

    public boolean allow(String clientId) {
        long now = System.nanoTime();
        // Mapping function is cheap and non-blocking — safe inside computeIfAbsent.
        Bucket b = buckets.computeIfAbsent(clientId, id -> new Bucket(capacity, now));

        synchronized (b) {                       // lock the BUCKET, never the map
            long elapsed = now - b.lastRefillNanos;
            if (elapsed > 0) {
                b.tokens = Math.min(capacity, b.tokens + elapsed * tokensPerNano);
                b.lastRefillNanos = now;
            }
            if (b.tokens < 1.0) return false;
            b.tokens -= 1.0;                     // check and decrement, atomically
            return true;
        }
    }

    public int trackedClients() { return buckets.size(); }
}
// Time: O(1) per call, contention only between requests of the SAME client. Space: O(clients)
```

##### Approach 2: Lock-free CAS

Idea: The whole bucket state fits in one immutable object, so a `compareAndSet` retry loop replaces the lock entirely. This is the "remove the lock" step of the granularity progression, and it is only possible because the invariant is per-key and fits in a single reference.

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicReference;

public class CasTokenBucketRateLimiter {

    /** Immutable snapshot of a bucket; swapped atomically. */
    private record State(double tokens, long timestampNanos) {}

    private final double capacity;
    private final double tokensPerNano;
    private final ConcurrentHashMap<String, AtomicReference<State>> buckets = new ConcurrentHashMap<>();

    public CasTokenBucketRateLimiter(double capacity, double refillPerSecond) {
        this.capacity = capacity;
        this.tokensPerNano = refillPerSecond / 1_000_000_000.0;
    }

    public boolean allow(String clientId) {
        AtomicReference<State> ref = buckets.computeIfAbsent(
            clientId, id -> new AtomicReference<>(new State(capacity, System.nanoTime())));

        while (true) {
            State cur = ref.get();
            long now = System.nanoTime();
            long elapsed = Math.max(0, now - cur.timestampNanos());
            double tokens = Math.min(capacity, cur.tokens() + elapsed * tokensPerNano);

            if (tokens < 1.0) {
                // Still publish the refill so the next caller does not recompute from scratch.
                ref.compareAndSet(cur, new State(tokens, now));
                return false;
            }
            if (ref.compareAndSet(cur, new State(tokens - 1.0, now))) return true;
            // CAS lost: another thread updated the bucket first. Re-read and retry.
        }
    }
}
// Time: O(1) amortized, lock-free. Space: O(clients)
```

**Follow-ups.**

- *Idle clients leak.* `buckets` grows with every distinct client id ever seen. Reclaim with the TTL cache above, or a periodic sweep dropping buckets that are full and untouched for a while (a full bucket is indistinguishable from a fresh one, so dropping it is safe).
- *Distributed.* Per-process state does not enforce a global limit. Move to Redis and make the check-and-decrement atomic there — a Lua script, or `INCR` plus `EXPIRE` on a fixed-window key.
- *Tell the caller when to retry.* The bucket already knows: `(1 - tokens) / refillRate` is the `Retry-After`.
- *Which algorithm?* See the comparison table under [Design a Rate Limiter](1.java-oop.md#ood-ratelimiter) in the OOP file — fixed window, sliding log, sliding counter, token bucket.

#### S6. Bounded connection pool with acquire timeout

**Context.** At most `maxSize` connections may exist to a database. Callers `acquire()` a connection, use it, and `release()` it. A caller that cannot get one within a timeout must fail fast rather than block forever.

**Design.** Two orthogonal concerns, and conflating them is the usual mistake:

- **How many may exist** → a `Semaphore` with `maxSize` permits. Acquiring a permit is the *right to hold* a connection.
- **Which object you get** → a concurrent queue of idle connections, created lazily.

Because the permit is acquired first, the queue can never be asked for more connections than exist, and `poll()` returning `null` unambiguously means "create a new one".

```java
import java.util.Queue;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Supplier;

public class ConnectionPool<T> implements AutoCloseable {

    private final Semaphore permits;
    private final Queue<T> idle = new ConcurrentLinkedQueue<>();
    private final Supplier<T> factory;
    private final AtomicInteger created = new AtomicInteger();
    private final AtomicBoolean closed = new AtomicBoolean();

    public ConnectionPool(int maxSize, Supplier<T> factory) {
        if (maxSize <= 0) throw new IllegalArgumentException("maxSize must be positive");
        this.permits = new Semaphore(maxSize, true);     // fair: FIFO, no starvation
        this.factory = factory;
    }

    /** @return a connection, or null if none became available before the deadline. */
    public T acquire(long timeout, TimeUnit unit) throws InterruptedException {
        if (closed.get()) throw new IllegalStateException("pool is closed");
        if (!permits.tryAcquire(timeout, unit)) return null;      // backpressure, not a hang

        boolean handedOut = false;
        try {
            T conn = idle.poll();
            if (conn == null) {
                conn = factory.get();                            // permit held: cannot exceed maxSize
                created.incrementAndGet();
            }
            handedOut = true;
            return conn;
        } finally {
            if (!handedOut) permits.release();                   // factory threw: do not leak the permit
        }
    }

    public void release(T connection) {
        if (connection == null) throw new IllegalArgumentException("cannot release null");
        idle.offer(connection);
        permits.release();                                       // return the permit LAST
    }

    public int idleCount() { return idle.size(); }

    public int createdCount() { return created.get(); }

    public int availablePermits() { return permits.availablePermits(); }

    @Override
    public void close() { closed.set(true); }
}
```

**Caller discipline.** The whole design collapses if a caller forgets to release, so state the contract:

```java
T conn = pool.acquire(1, TimeUnit.SECONDS);
if (conn == null) throw new TimeoutException("no connection available");
try {
    use(conn);
} finally {
    pool.release(conn);      // ALWAYS in finally — a leaked permit is permanent
}
// Time: O(1) per acquire/release, Space: O(maxSize)
```

⚠️ Order matters in `release`: put the connection back on the queue *before* releasing the permit. Reversed, a woken thread can win the permit, find the queue empty, and construct a connection beyond `maxSize`.

**Follow-ups.**

- *Health checks* — validate on borrow and discard a dead connection, decrementing `created` and constructing a fresh one under the same permit.
- *Idle eviction* — shrink the pool after a quiet period; the `Semaphore` is unaffected because permits bound the maximum, not the current count.
- *Fairness* — `new Semaphore(n, true)` prevents a hot thread from starving others, at some throughput cost. Worth naming as a deliberate choice.

#### S7. Per-key ordered job executor

**Context.** An order-processing service handles events concurrently, but events for the *same* order must be applied in arrival order. Events for *different* orders should run fully in parallel. Build `submit(key, task)` on a shared thread pool.

**Invariant.** For any key, tasks execute in submission order and never overlap; tasks for different keys have no ordering constraint; and per-key bookkeeping disappears once a key goes idle.

**Design.** Do not create a thread per key — that does not scale. Instead keep, per key, a `CompletableFuture` representing "everything submitted so far for this key", and chain the new task onto it. The chaining must be atomic with respect to other submitters, which is exactly what `ConcurrentHashMap.compute` gives: the read of the old tail and the write of the new tail happen under the bin lock.

Cleanup uses the two-argument `remove(key, expectedValue)` again: the entry is dropped only if the completed future is still the tail, so a submission racing with completion cannot lose its chain.

```java
import java.util.concurrent.*;

public class KeyedSerialExecutor implements AutoCloseable {

    private final ExecutorService pool;
    private final ConcurrentHashMap<String, CompletableFuture<Void>> tails = new ConcurrentHashMap<>();

    public KeyedSerialExecutor(int threads) {
        this.pool = Executors.newFixedThreadPool(threads);
    }

    public CompletableFuture<Void> submit(String key, Runnable task) {
        // compute() holds the bin lock, making read-old-tail + write-new-tail atomic.
        // The mapping function only builds futures — it never runs the task inline.
        CompletableFuture<Void> newTail = tails.compute(key, (k, prevTail) -> {
            CompletableFuture<Void> prior =
                (prevTail == null) ? CompletableFuture.completedFuture(null) : prevTail;
            // handle(): a failed task must not poison the rest of the chain for this key.
            return prior.handle((ignored, error) -> null)
                        .thenRunAsync(task, pool);
        });

        // Drop the entry only if this future is STILL the tail; otherwise a later
        // submission already chained onto it and must not be orphaned.
        newTail.whenComplete((ignored, error) -> tails.remove(key, newTail));
        return newTail;
    }

    public int activeKeys() { return tails.size(); }

    @Override
    public void close() {
        pool.shutdown();
    }

    public boolean awaitTermination(long timeout, TimeUnit unit) throws InterruptedException {
        pool.shutdown();
        return pool.awaitTermination(timeout, unit);
    }
}
// Time: O(1) per submit, Space: O(active keys + queued tasks)
```

**Interleavings this defends against.**

- *Two threads submitting for the same key at once.* `compute` serializes them on the bin, so one observes the other's tail and chains behind it. Without `compute` — say, `get` then `put` — both would chain onto the same prior tail and run in parallel, breaking the ordering guarantee.
- *A task completing while another is being submitted.* If completion ran a plain `tails.remove(key)`, it could delete a tail that a concurrent submitter had just chained onto, and the next submission for that key would start a fresh chain running concurrently with the queued one. The value-matching `remove` makes this impossible.
- *A task throwing.* `handle` converts failure to a normal completion for chaining purposes, so one bad event does not wedge that key forever. The returned future still reports the failure to the caller.

**Follow-ups.**

- *Bounding the backlog.* Nothing here limits how many tasks queue up for one hot key. Add a per-key counter rejecting beyond a depth, or use a bounded pool queue with a caller-runs policy.
- *Fairness across keys.* A key with thousands of queued tasks can monopolize the pool. Fix with a round-robin scheduler over ready keys rather than free chaining.
- *Why not one single-threaded executor per key?* It works and is simpler to explain, but it allocates a thread per key — fine for tens of keys, fatal for millions.

#### S8. Download manager with bounded parallelism

**Context.** Download a list of URLs with at most `maxConcurrent` transfers in flight, report progress as each finishes, return all results, and support cancellation. (The CodeSignal "multi-threaded download manager with resource limiting" shape.)

**Design.** Three separable pieces, each with the right primitive:

- **Thread supply** → an `ExecutorService`. Never `new Thread()`.
- **Concurrency cap** → a `Semaphore`. This is independent of pool size: the pool may be large while permits keep only `maxConcurrent` transfers active.
- **Fan-in** → `CompletableFuture.allOf`, not a `CountDownLatch`, so the caller can compose rather than block.

Progress is a counter touched by every worker, so it must be atomic — `progress++` on a plain `int` loses updates.

```java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Function;
import java.util.function.IntConsumer;

public class DownloadManager implements AutoCloseable {

    public record Result(String url, String body, String error) {
        public boolean ok() { return error == null; }
    }

    private final ExecutorService pool;
    private final Semaphore slots;
    private final AtomicBoolean cancelled = new AtomicBoolean();

    public DownloadManager(int poolSize, int maxConcurrent) {
        this.pool = Executors.newFixedThreadPool(poolSize);
        this.slots = new Semaphore(maxConcurrent);
    }

    /**
     * @param onProgress called with the completed count after each download; must be
     *                   cheap and thread-safe, since it runs on worker threads.
     */
    public CompletableFuture<List<Result>> downloadAll(List<String> urls,
                                                       Function<String, String> fetcher,
                                                       IntConsumer onProgress) {
        AtomicInteger completed = new AtomicInteger();
        List<CompletableFuture<Result>> futures = new ArrayList<>(urls.size());

        for (String url : urls) {
            futures.add(CompletableFuture.supplyAsync(() -> {
                if (cancelled.get()) return new Result(url, null, "cancelled");
                try {
                    slots.acquire();                       // blocks until a transfer slot frees
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();    // restore the flag, never swallow it
                    return new Result(url, null, "interrupted");
                }
                try {
                    if (cancelled.get()) return new Result(url, null, "cancelled");
                    return new Result(url, fetcher.apply(url), null);
                } catch (RuntimeException e) {
                    return new Result(url, null, String.valueOf(e.getMessage()));
                } finally {
                    slots.release();                       // ALWAYS, or the pool wedges
                    onProgress.accept(completed.incrementAndGet());
                }
            }, pool));
        }

        return CompletableFuture.allOf(futures.toArray(new CompletableFuture[0]))
            .thenApply(ignored -> futures.stream().map(CompletableFuture::join).toList());
    }

    /** Best-effort: in-flight transfers finish, queued ones short-circuit. */
    public void cancel() { cancelled.set(true); }

    @Override
    public void close() { pool.shutdownNow(); }
}
// Time: O(n) tasks with at most maxConcurrent active, Space: O(n) futures
```

**Points the grader is looking for.**

- `slots.release()` in `finally`. A permit leaked on an exception is permanent, and the manager silently stops after `maxConcurrent` failures — a bug that only shows up under load.
- Catching the per-task exception and turning it into a `Result` rather than letting `allOf` fail the whole batch. "One bad URL must not kill the run" is a requirement you should volunteer.
- Restoring the interrupt flag with `Thread.currentThread().interrupt()`. Swallowing `InterruptedException` is a genuine code-review failure — it makes the task uncancellable.
- `cancelled` as an `AtomicBoolean` (a `volatile boolean` would also do). A plain `boolean` may never become visible to the workers at all.

**Follow-ups.**

- *Retries with backoff* — wrap the fetch in a loop, sleeping `base * 2^attempt` with jitter. Jitter matters: without it, all failures retry in lockstep.
- *Hard cancellation* — keep the `Future`s and call `cancel(true)`, which interrupts blocked workers. Only works if the fetch is interruptible.
- *Rate limiting rather than concurrency limiting* — a `Semaphore` bounds simultaneous transfers, not requests per second. Those are different constraints; combine with S5 if both are required.

#### S9. Deadlock-free account transfer

**Context.** `transfer(from, to, amount)` must move money atomically — both balances change or neither does — and must survive many threads transferring in every direction, including `A→B` and `B→A` simultaneously.

**The deadlock.** The obvious implementation locks `from` then `to`. Thread 1 doing `A→B` holds `A` and wants `B`; thread 2 doing `B→A` holds `B` and wants `A`. Neither ever proceeds. This is bug pattern 3, and it is the entire point of the question.

**Fix: a global lock order.** Always acquire in ascending account id, regardless of transfer direction. A consistent order makes a cycle impossible.

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Bank {

    public static final class Account {
        private final long id;
        private long balanceCents;
        private final ReentrantLock lock = new ReentrantLock();

        Account(long id, long balanceCents) {
            this.id = id;
            this.balanceCents = balanceCents;
        }

        public long id() { return id; }

        public long balance() {
            lock.lock();
            try {
                return balanceCents;
            } finally {
                lock.unlock();
            }
        }
    }

    private final ConcurrentHashMap<Long, Account> accounts = new ConcurrentHashMap<>();

    public Account open(long id, long openingCents) {
        Account a = new Account(id, openingCents);
        if (accounts.putIfAbsent(id, a) != null) throw new IllegalStateException("duplicate id " + id);
        return a;
    }

    public Account get(long id) {
        Account a = accounts.get(id);
        if (a == null) throw new IllegalArgumentException("no such account " + id);
        return a;
    }

    /** @return false if funds were insufficient. */
    public boolean transfer(long fromId, long toId, long amountCents) {
        if (amountCents <= 0) throw new IllegalArgumentException("amount must be positive");
        if (fromId == toId) throw new IllegalArgumentException("cannot transfer to the same account");

        Account from = get(fromId);
        Account to = get(toId);

        // Global order: always lock the lower id first, whichever way the money moves.
        Account first = fromId < toId ? from : to;
        Account second = fromId < toId ? to : from;

        first.lock.lock();
        try {
            second.lock.lock();
            try {
                if (from.balanceCents < amountCents) return false;
                from.balanceCents -= amountCents;
                to.balanceCents += amountCents;
                return true;
            } finally {
                second.lock.unlock();
            }
        } finally {
            first.lock.unlock();
        }
    }

    /**
     * Alternative when there is no natural order (e.g. objects without ids):
     * take both locks with tryLock and back off completely if either fails.
     */
    public boolean transferWithBackoff(long fromId, long toId, long amountCents)
            throws InterruptedException {
        Account from = get(fromId);
        Account to = get(toId);

        while (true) {
            if (from.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                try {
                    if (to.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                        try {
                            if (from.balanceCents < amountCents) return false;
                            from.balanceCents -= amountCents;
                            to.balanceCents += amountCents;
                            return true;
                        } finally {
                            to.lock.unlock();
                        }
                    }
                } finally {
                    from.lock.unlock();       // release BOTH before retrying — never hold and spin
                }
            }
            Thread.sleep(1);                  // brief backoff so contenders desynchronize
        }
    }

    public long totalAssets() {
        long total = 0;
        for (Account a : accounts.values()) total += a.balance();
        return total;                          // not an atomic snapshot — see follow-ups
    }
}
// Time: O(1) per transfer, Space: O(accounts)
```

⚠️ If ids can collide (locking by `System.identityHashCode` rather than a unique id), the ordering breaks down on ties. The standard fix is a third "tie-breaker" lock held only while acquiring the two equal-ranked locks.

**Follow-ups.**

- *A consistent total across all accounts.* `totalAssets` above sums balances one lock at a time, so a transfer in flight can be double-counted or missed. A truly atomic snapshot needs a global read-write lock (transfers take the read lock, the audit takes the write lock) — worth naming as the price of the guarantee.
- *Can this be lock-free?* Not for two accounts: a single CAS cannot cover two independent memory locations. That needs a multi-word CAS or an STM, which is why real ledgers use database transactions.
- *Ordering by hash instead of id.* Fine, provided the tie-breaker above exists.

#### S10. Interleaving primitives (LC 1114 / 1115)

**Context.** The smallest possible signalling drills, and common OA warm-ups. They test one thing: can you make thread B wait for thread A without busy-waiting and without a lost wakeup?

**LC 1114 — Print in Order.** Three threads call `first`, `second`, `third` in arbitrary order; output must be `first second third`. A `Semaphore` starting at zero is a one-shot gate: `acquire()` blocks until someone `release()`s it.

```java
import java.util.concurrent.Semaphore;

public class Foo {
    private final Semaphore runSecond = new Semaphore(0);   // 0 permits == closed gate
    private final Semaphore runThird = new Semaphore(0);

    public Foo() {}

    public void first(Runnable printFirst) throws InterruptedException {
        printFirst.run();
        runSecond.release();                                 // open the gate for second()
    }

    public void second(Runnable printSecond) throws InterruptedException {
        runSecond.acquire();                                 // waits however long it takes
        printSecond.run();
        runThird.release();
    }

    public void third(Runnable printThird) throws InterruptedException {
        runThird.acquire();
        printThird.run();
    }
}
// Time: O(1), Space: O(1)
```

**LC 1115 — Print FooBar Alternately.** Two threads, `n` iterations each, output `foobarfoobar...`. Two semaphores ping-pong: each side releases the other's permit and waits for its own.

```java
import java.util.concurrent.Semaphore;

public class FooBar {
    private final int n;
    private final Semaphore fooTurn = new Semaphore(1);      // foo goes first
    private final Semaphore barTurn = new Semaphore(0);

    public FooBar(int n) { this.n = n; }

    public void foo(Runnable printFoo) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            fooTurn.acquire();
            printFoo.run();
            barTurn.release();
        }
    }

    public void bar(Runnable printBar) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            barTurn.acquire();
            printBar.run();
            fooTurn.release();
        }
    }
}
// Time: O(n), Space: O(1)
```

**Why semaphores rather than `wait`/`notify` here.** A `Semaphore` permit is *remembered*: releasing before anyone waits still lets the later `acquire()` through. `notify()` is not remembered — if it fires before the other thread calls `wait()`, the signal is lost and the program hangs forever. That asymmetry is exactly what these problems are testing, and it is why the `wait`/`notify` version needs a guarded state variable plus a `while` loop while the semaphore version needs neither.

**The rest of the family.** LC 1116 Print Zero Even Odd (three semaphores, same pattern), 1117 Building H2O (two semaphores plus a `CyclicBarrier` for the rendezvous of three), 1195 Fizz Buzz Multithreaded, 1226 The Dining Philosophers (five forks — order the forks or cap concurrent diners at four to break the cycle, the same lock-ordering idea as S9).
