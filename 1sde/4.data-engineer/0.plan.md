## Part A — SQL Study Plan

### A1. Practice guidelines (how, not just what)

1. **Type every query in the Databricks SQL editor.** Not LeetCode's editor, not a notepad. The failure last round was editor-under-observation fluency; you fix that only in the same environment. Solve on LeetCode if you want the judge, then re-type the pattern in Databricks against a fixture table.
2. **Pattern-name-first method.** Before typing, say aloud: "this is top-N-per-group → ROW_NUMBER partition." Naming the pattern before the syntax is what interviewers hear as fluency, and it stops blank-page freeze.
3. **Skeleton-first typing.** Write `SELECT … FROM … WHERE … GROUP BY …` scaffolding immediately, then fill. Never stare at an empty editor.
4. **Narrate while writing.** "I'll aggregate per company first, then filter on the aggregate with HAVING." The Monday/Tuesday interview is a spoken performance; rehearse the speaking, not just the typing.
5. **Timebox: 4 minutes per problem.** Over 4 minutes → read the solution, close it, re-type from memory, and queue the problem for a next-day cold redo. Struggle-then-retype beats long struggle.
6. **Spaced redo list.** Keep a `missed.md`. Every session starts with yesterday's misses, cold. A problem leaves the list only after one clean cold solve.
7. **No AI during drills.** You'll use AI on the job for authoring; the interview tests the verification skill underneath. Practice bare.
8. **Verify like a DE.** After each query, sanity-check: row count plausible? NULLs handled? Did the join fan out? Run `COUNT(*)` before/after joins once per session as a ritual — it's also an interview-worthy habit to mention.

### A4. Most-likely live prompts (rehearse as spoken performances)

- "Count X per Y, only groups over N" (tier 1 — last round's exact failure)
- "Give me the latest record per company" (tier 3)
- "Which records are in the vendor feed but not our platform?" (tier 2 — maps to your reconciliation story; say so when you finish it)
- "Quarter-over-quarter change" (tier 4)
- "Find and remove duplicates" (tiers 1+5)

### A5. Traps to pre-arm

- `NOT IN (subquery)` returns nothing if subquery has a NULL → use anti-join.
- Aggregate in WHERE → error; that's HAVING's job.
- Window functions can't go in WHERE → wrap in CTE/subquery, filter outside.
- `COUNT(DISTINCT a, b)` behavior differs by engine → `COUNT(DISTINCT concat_ws('|',a,b))` or subquery; say the hedge aloud.
- Ties: know when the asker wants RANK (ties share, gaps) vs DENSE_RANK vs ROW_NUMBER (arbitrary tiebreak — name the nondeterminism).
- Joining before deduping the many-side → fan-out; dedupe first.
