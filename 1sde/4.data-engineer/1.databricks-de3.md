## 1. Lakehouse & Platform Architecture

### Concepts

- **Warehouse vs lake vs lakehouse.** Warehouse: proprietary storage+compute coupled, great SQL/BI, poor semi-structured & ML access, expensive at raw scale. Lake: cheap open files on S3, but no ACID, no schema enforcement, "data swamp" failure mode. **Lakehouse**: open files (Parquet) + a transactional metadata layer (Delta) + governance (UC) → one copy of data serving BI and ML. The defeater to volunteer: for pure low-latency point lookups a lakehouse is still the wrong tool — that's what Aurora is for in your stack.
- **Control plane vs data plane.** Databricks-managed control plane (UI, job scheduler, notebooks metadata); your-cloud data plane (compute in your AWS account, data in your S3). Matters at JPMC: data never leaves the bank's account; security reviews hinge on this.
- **Photon.** Native C++ vectorized engine, transparent for SQL/DataFrame ops, priced into DBUs; does not accelerate Python UDFs/RDDs.
- **DBFS vs UC volumes/external locations.** Legacy DBFS mounts are being displaced by UC-governed external locations and volumes — one sentence of awareness signals currency.

### Interview Q&A

**Q1.1 Why did the industry move to lakehouse? (8)** Two-copy problem: lake for ML + warehouse for BI meant duplicate storage, drift between copies, and a sync pipeline nobody loved. Delta added the missing warehouse properties (ACID, enforcement, performance via skipping/clustering) directly on the lake. Defeater: "lakehouse replaces everything" is oversold — OLTP and sub-second serving still live elsewhere.

**Q1.2 Where does Databricks sit vs Glue/EMR/Redshift in your JPMC world? (7)** All Spark-or-SQL engines on S3 data. Glue = serverless AWS-native ETL (our SQS-triggered ingest); EMR = self-managed Spark, most control/most ops; Redshift = warehouse for BI; Databricks = the developer-experience + Delta + governance layer where curation lives. Deciding variable: who operates it and where governance must live.

**Q1.3 What's Photon and when doesn't it help? (6)** As above; not for UDF-heavy or RDD code — another reason §Doc-3 pushes built-in functions.

## 2. Delta Lake Internals — the depth differentiator

### 2.1 Transaction log mechanics

A Delta table = data files (Parquet) + `_delta_log/` containing ordered JSON commits (`000…N.json`), checkpointed to Parquet every ~10 commits so readers don't replay thousands of JSONs. Each commit lists **add**/**remove** file actions + stats (min/max per column per file) + metadata (schema). "The table at version N" = the set of files the log says are live at N.

What the log buys, mechanically:

- **ACID:** writers prepare files, then atomically commit one log entry. Readers see a consistent snapshot (the log version they started with).
- **Concurrency:** optimistic — two writers race to commit version N+1; loser re-checks for logical conflict (same files touched?) and retries or fails (`ConcurrentModificationException` family). Defeater: high-frequency concurrent MERGEs to the same partition = conflict storms; fix by partition-aligning writers or serializing.
- **Time travel:** old versions = old file sets still on storage; `VERSION AS OF` reconstructs from the log.
- **Data skipping:** per-file min/max stats let the engine skip files whose range can't match the predicate.

**Q2.1 "What happens, step by step, when you write to a Delta table?" (10)** Executors write new Parquet files → driver builds a commit (add actions + stats) → atomic put of the next log JSON → readers at older versions unaffected; new readers see new version. If the commit loses a race: conflict check → retry. This answer, delivered smoothly, is worth more than any recited feature list.

**Q2.2 ACID across tables? (7)** No — transactionality is per-table. Multi-table consistency needs orchestration-level design (write silver, then gold; consumers read gold only) or idempotent re-runs. Saying this unprompted is L3+ signal.

### 2.2 MERGE INTO

Mechanism: pass 1 joins source↔target to identify target files containing matches; pass 2 rewrites those files entirely (Parquet immutable). Cost drivers: unclustered target (every file might match), wide merge condition, many touched files. Mitigations: cluster/partition on merge keys; add pruning predicates to the ON clause (`AND t.ingest_date >= '...'`); **deletion vectors** (DBR 12+, GA since ~2023): deletes/updates mark rows in a sidecar bitmap instead of rewriting files — massive win for scattered small updates, compacted later by OPTIMIZE.

**Q2.3 "Your nightly MERGE went from 10 to 40 minutes. Diagnose." (9)** Ordered: (1) Spark UI / query profile — which stage grew: the join (source grew? stats stale?) or the write (touched-file count exploded?); (2) `DESCRIBE HISTORY` — numTargetFilesRewritten trend; (3) small-file creep on target → OPTIMIZE; (4) merge condition stopped pruning (date predicate fell off after a refactor); (5) skew on merge key. Give the _procedure_, not one guess — procedure is what "independent" sounds like.

### 2.3 Time travel, VACUUM, RESTORE

`VERSION AS OF` / `TIMESTAMP AS OF` for audit/debug; `RESTORE TABLE t TO VERSION AS OF n` for rollback after a bad deploy (it's a new commit re-adding old files — history preserved). `VACUUM` physically deletes unreferenced files past retention (default 7 days) → time travel beyond that dies. Defeaters: VACUUM with short retention while a long-running reader/stream still references old files → reader breaks; RESTORE doesn't resurrect files VACUUM already removed.

**Q2.4 "Bad code corrupted yesterday's load. Recover." (8)** `DESCRIBE HISTORY` to find last good version → `RESTORE` → re-run fixed pipeline (idempotent, so safe) → post-mortem: add an expectation/constraint that would have caught it. The last clause is the L3 part.

### 2.4 Layout: OPTIMIZE, Z-ORDER, liquid clustering, partitioning

- **Small-file problem:** streaming/micro-batches + over-partitioning ⇒ thousands of tiny files ⇒ per-file open cost + metadata bloat ⇒ slow scans. Fix: scheduled `OPTIMIZE` (compact toward ~1GB), optimized-write table properties, sane output partitioning before write.
- **Z-ORDER:** multi-dimensional sort across files so min/max stats become selective → file skipping on those columns. Full-rewrite operation; effectiveness collapses past ~3–4 columns.
- **Liquid clustering:** successor — `CLUSTER BY` on the table, incremental re-clustering, no full rewrites, tolerates changing query patterns; mutually exclusive with hive partitioning on the same table.
- **Partitioning:** only for large tables (≳1TB) on low-cardinality always-filtered columns (ingest_date), or for lifecycle drops. High-cardinality partitioning is the canonical junior mistake (small-file explosion). Modern default rec: liquid clustering + skipping; partition only with a clear pruning/retention argument.

**Q2.5 "How would you lay out a 5TB filings table queried by company and date?" (9)** Answer with the deciding variables: query predicates (company=high cardinality → cluster not partition; date → partition or cluster), write pattern (streaming appends → beware small files), retention (drop-by-month → date partitioning earns its keep). Default: partition by ingest month, liquid-cluster by company; scheduled OPTIMIZE. Then name what would change your mind.

### 2.5 Schema enforcement & evolution

Writes must match schema (enforcement) — silent-corruption prevention. Evolution is opt-in: `mergeSchema` (add columns) per write; `overwriteSchema` destructive. Discipline point to volunteer: schema change should be a gated, reviewed event — your Liquibase-changelog + StructType drift-test regime is exactly this; it's your strongest authenticity card, play it.

### 2.6 Constraints & CDF

- `NOT NULL` and `CHECK` constraints fail the _write_ (vs DLT expectations which can drop/quarantine rows — know the difference, Q4.2).
- **Change Data Feed:** `delta.enableChangeDataFeed=true` → `table_changes('t', v1, v2)` yields row-level insert/update_pre/update_post/delete with versions → downstream consumes deltas instead of full re-reads; feeds incremental gold or an external serving store (your Aurora).

**Q2.6 CDF vs reprocessing — when each? (6)** CDF when downstream is expensive relative to change volume and needs increments; full recompute when logic changed (CDF replays _data_ changes, not _logic_ changes). That distinction is the whole answer.

## 3. Ingestion

### 3.1 Auto Loader (cloudFiles) — know this cold, it maps to your SQS experience

- Streaming source that incrementally discovers new files. **Directory listing mode** (default): repeatedly lists the prefix — simple, fine to ~thousands of files; incremental listing optimizations exist but listing cost grows with directory size. **File notification mode:** S3 event → SNS → SQS; Auto Loader consumes queue messages — scales to millions of files, lower latency, needs permissions to create/manage the queue. _This is architecturally identical to your JPMC SQS-triggered Glue ingest — say that sentence in the interview._
- **Exactly-once file processing:** discovered files tracked in RocksDB state inside the checkpoint; a file is processed once even across restarts. Defeaters: delete the checkpoint ⇒ full reprocess (duplicates unless sink-side idempotent); notification mode misses files that landed before the subscription existed → `cloudFiles.backfillInterval` / initial backfill option.
- **Schema:** inference with `cloudFiles.schemaLocation` (schema tracked & versioned); on new column, stream stops with an evolution event and resumes with evolved schema (`addNewColumns` mode); type mismatches land in `_rescued_data` instead of failing the row. Defeater: inference samples — low-frequency columns can be mistyped; production tables should pin schemas or land bronze as strings and cast in silver.

**Q3.1 Auto Loader vs COPY INTO vs plain batch read? (9)** COPY INTO: idempotent SQL bulk load, tracks loaded files, good for scheduled batch of moderate file counts, no streaming infra. Auto Loader: continuous/incremental at scale with checkpointed state. Plain `spark.read`: one-off, no bookkeeping. Deciding variable: arrival pattern + file volume. Default: Auto Loader for feeds, COPY INTO for periodic drops.

**Q3.2 "How do you guarantee a vendor file is processed exactly once, end to end?" (9)** Layers: Auto Loader checkpoint (file-level once) → but _end-to-end_ also needs an idempotent write (MERGE on business key, or append with dedupe in silver) because at-least-once sneaks in at the edges (checkpoint restore, manual re-drops of a corrected file). Naming the corrected-file-re-drop case is the L3 detail: same filename, new content — file-level tracking says "seen"; handle via versioned drop paths or content hash.

**Q3.3 Late or malformed data? (8)** Malformed: `_rescued_data` / permissive parse into bronze, quarantine table + alert on quarantine growth, never silently drop. Late: bronze is append-only so late rows land fine; silver dedupe latest-per-key handles replaces; gold aggregations over event time need either recompute windows (re-aggregate last N days each run) or streaming watermarks (Doc 3 §10).

## 4. Pipelines & Orchestration

### 4.1 DLT / Lakeflow declarative pipelines

Declare tables (SQL or Python) — engine infers the DAG from references, manages retries, clusters, lineage, event log. **Expectations**: `CONSTRAINT valid_price EXPECT (price > 0) ON VIOLATION DROP ROW | FAIL UPDATE` (or warn-only) with per-run metrics in the event log. Buys: quality-as-code + less orchestration boilerplate. Costs: DLT-flavored runtime, less control, unit testing is clumsier. Choose DLT for standard medallion flows; Jobs+notebooks for custom logic. Defeater: `DROP ROW` silently shrinking your data is its own incident class — always alert on drop-rate, don't just set-and-forget.

### 4.2 Workflows/Jobs

Task DAGs (notebook/SQL/pipeline/dbt tasks), per-task clusters, schedules + file-arrival triggers, retries with backoff, timeout, `max_concurrent_runs=1` to prevent overlap (know why: overlapping non-idempotent runs corrupt), **repair run** = rerun only failed tasks with same run parameters. Alerts on failure/duration to email/Slack/PagerDuty.

**Q4.1 Databricks Jobs vs Airflow? (7)** Same DAG concepts. Jobs: native, zero extra infra, tightest Databricks integration. Airflow: cross-system orchestration (when the DAG spans Databricks + Glue + on-prem), richer backfill semantics, org-standard in many enterprises. JD mentions Airflow → your line: "our DAGs live in Databricks Jobs and SQS-triggered Glue; the concepts — DAGs, retries, backfills, SLAs — transfer directly, happy to work in Airflow."

**Q4.2 DLT expectation vs table CHECK constraint? (7)** Constraint fails the whole write (hard gate, protects the table); expectation acts per row (drop/warn) with metrics (protects the pipeline's flow while surfacing quality). Use constraints for invariants that must never be violated (NOT NULL keys), expectations for dirty-world filtering you want measured.

**Q4.3 "Design the backfill story." (8)** Same code path, parameterized date range (widget/job parameter); write via MERGE or `replaceWhere` partition overwrite so re-runs are idempotent; run at bounded parallelism to protect the warehouse/cluster budget; verify with reconciliation counts per day vs source. Anti-pattern to name: a hand-edited "backfill notebook" that drifts from prod logic.

**Q4.4 A task fails at 3am. Walk me through the morning. (9)** Job run page → failed task → error + logs → classify: transient (source timeout → repair run) vs data (new malformed feed → quarantine growth, fix parse, replay) vs logic (recent deploy → rollback/RESTORE) → repair run, not full rerun, because upstream tasks succeeded and are idempotent anyway → then the guardrail: alert/expectation so this class pages before consumers notice. Rehearse this aloud; it _is_ the "independent engineer" question.

## 5. Unity Catalog & Governance

- Namespace: **metastore → catalog → schema → table/view/volume/function**, three-part names. Grants are ANSI SQL (`GRANT SELECT ON SCHEMA fin.silver TO data_readers`), inherited downward, group-based in practice.
- **Managed vs external tables:** managed = UC controls storage location & lifecycle (DROP deletes data); external = table over a path you manage (DROP removes metadata only). External locations bind path ↔ storage credential (IAM role) ↔ grants.
- Row/column security: dynamic views or row filters / column masks (`is_account_group_member()` style) — relevant in a bank (mask PII columns for most groups).
- **Lineage** auto-captured table/column level across queries, jobs, DLT. **System tables** (`system.billing.usage`, audit) for cost & access review.
- Defeater: UC governs Databricks compute paths; a principal with raw S3 access bypasses it — hence external-location IAM hygiene is part of governance, not separate.

**Q5.1 New analyst needs read access to gold only. (7)** Group membership → `GRANT USAGE ON CATALOG` + `GRANT USAGE ON SCHEMA gold` + `GRANT SELECT` on schema; nothing on bronze/silver. Say "group, never individual" and you're done.

**Q5.2 Managed vs external — which for your lakehouse and why? (7)** Deciding variable: who else must read the files (external tools → external tables/locations) and whether UC lifecycle control is acceptable. In a bank with multi-engine access (Athena/Glue), external is common; managed is the Databricks-native default going forward. Name both, pick per constraint.

**Q5.3 "Who queried this table last month / what does this dashboard depend on?" (6)** Audit system tables for access; lineage graph for dependencies — know these exist and where (Catalog Explorer lineage tab), that's the whole bar.

## 6. Compute & Performance

### Compute selection

| Compute               | For                       | Deciding property                                                                 |
| --------------------- | ------------------------- | --------------------------------------------------------------------------------- |
| Job cluster           | Production pipelines      | Ephemeral, isolated, cheapest DBUs                                                |
| All-purpose           | Interactive dev           | Shared, always-on cost risk                                                       |
| SQL warehouse         | BI/analyst/serving SQL    | Photon + concurrency autoscaling (adds clusters for concurrency, not bigger ones) |
| Serverless (jobs/SQL) | Ops-free, spiky           | Fast start, per-second billing, less tuning control                               |
| Pools                 | Cold-start-sensitive jobs | Pre-warmed instances                                                              |
| Policies              | Governance                | Cap sizes/types → cost control at org scale                                       |

Autoscaling: horizontal workers within min/max; warehouse sizing = per-query power, warehouse cluster count = concurrency. Auto-stop/auto-termination = the #1 cost lever; the tradeoff is cold-start latency.

**Q6.1 "Your Databricks bill doubled. Investigate." (8)** `system.billing.usage` by workspace/SKU/tag → usual suspects in order: all-purpose cluster left running (no auto-terminate), warehouse auto-stop disabled, a job's cluster oversized after a copy-paste, OPTIMIZE/maintenance jobs running too often, dev running on Photon warehouses. Then the guardrail: cluster policies + tags + a weekly cost report. Procedure + guardrail = the L3 shape.

### Performance triage (SQL/warehouse side — Spark-level detail in Doc 3)

Query History → **Query Profile**: which operator dominates? Scan-heavy → skipping not engaging (layout §2.4: cluster/Z-order; check predicate matches clustering columns; partition pruning happening?). Shuffle/join-heavy → join order, broadcast eligibility, stats. Result-heavy → someone SELECT \*'d a wide table into a notebook.
Rules of thumb: files pruned/read ratio is the first number to look at; "it got slow over time" with no code change ≈ small files or clustering decay → OPTIMIZE; "slow for everyone at 9am" ≈ warehouse concurrency → scale out clusters not up size.

**Q6.2 "A dashboard query takes 4 min; used to take 20s." (9)** Query Profile diff mindset: rows/files scanned trend (layout decay → OPTIMIZE/re-cluster), plan change (stats → ANALYZE / stale broadcast), warehouse queueing (concurrency), data simply grew (then it's a modeling fix: pre-aggregate a gold table, not a bigger warehouse). Offering the modeling fix instead of "bigger compute" is the senior tell.

## 7. Modeling & Data Quality

- **Medallion, defended:** bronze = raw, append-only, source-shaped → replay after logic bugs + audit trail (in a bank: evidentiary value). Silver = conformed, deduped, typed, validated → the one place quality rules run; entity-joinable. Gold = consumption-shaped aggregates per use case → consumers never touch raw; blast radius of upstream change contained. Defeater: it's a convention — collapse layers when replay/conformance don't justify latency+storage; saying when _not_ to is the judgment signal.
- **Grain first.** Every table has an explicit grain (one row per company-filing-version); most modeling bugs are grain bugs (accidental fan-out, double counting). State grain before writing any gold table.
- **Keys:** business key vs surrogate; dedupe rule (latest by updated_at per business key) lives in silver, once.
- **SCD2 in Delta:** MERGE two-branch pattern — close current row (`is_current=false, end_date=now`) when tracked columns changed; insert new version. Union-source trick for single-pass MERGE. Query current = `is_current`. Defeater: out-of-order late updates corrupt interval chains → event-time ordering or periodic repair job.
- **Quality layers:** constraints (hard invariants) < expectations (measured filters) < reconciliation checks (row counts / sums vs source per load) < alerts on staleness (`MAX(ingest_ts)` age). A pipeline without a staleness alert fails silently — the worst failure mode in DE.

**Q7.1 "Design the medallion flow for the vendor filings feed." (9)** Speak it as: bronze `filings_raw` append-only with `_rescued_data` + ingest metadata (file, ts) at grain=one row per file-record; silver `filings` deduped latest-per-(company, filing_id) with types + expectations + reconciliation vs bronze counts; gold `filings_by_company_quarter` at stated grain for the consumer. Then one operational sentence: staleness alert on silver, drop-rate alert on expectations. You've built exactly this in fin-lakehouse — anchor it there.

## 8. UI Playbook — the live-demo fix

Persona: DE who adds resources, maintains schema, monitors ingestion. Run twice (Sun), third time Mon eve. Every motion <10 seconds.

**Ops loop (ritualize):**

1. Workflows → runs list → filter failed → open run → failed task → logs → **Repair run** (know the button by name).
2. Task's Spark UI → Stages → longest stage → shuffle read/write, max-vs-median task time (skew read).
3. Pipelines → graph → event log → expectations metrics (drop counts).
4. SQL → Query History → slowest → **Query Profile** → dominant operator, files pruned/read.
5. SQL Alerts → where you'd build a staleness alert (query + condition + destination).

**Schema drills:** Catalog Explorer: create catalog/schema/table; per-table tabs: columns/sample/Details(location, format)/History (narrate each Delta operation)/Lineage/Permissions (make one GRANT). Editor: `ALTER TABLE ADD COLUMN` → `DESCRIBE HISTORY` → `SELECT ... VERSION AS OF`. Then the bridge line: "at work, schema changes go through Liquibase changelogs with a drift test; UI ALTER is break-glass."

**Resource drills:** create SQL warehouse (size / min-max clusters / auto-stop — say each tradeoff aloud); create a job with a job cluster; open cluster Event log + Metrics once.

**Ingestion drills:** open a streaming query's metrics (rows/sec, batch duration, backlog); locate a checkpoint path and say what deleting it means; run one `COPY INTO`; find `system.billing.usage` and run one group-by on it (also a SQL rep).

## 9. AWS Context (JPMC stack)

**Q9.1 S3→SQS→pipeline trigger. (9)** S3 event notification on prefix → SQS → consumer (your Glue trigger; Auto Loader file-notification is the same shape). Include: DLQ for poison messages, at-least-once ⇒ idempotent consumer keyed on object key, visibility timeout tuned to processing time. One story covers your production system _and_ Auto Loader internals — highest-leverage answer you own.

**Q9.2 SQS semantics. (9)** Standard: at-least-once, best-effort order, unbounded throughput → dedupe on consumer. Visibility timeout: too short = duplicates, too long = slow recovery. FIFO: ordering per message-group + dedup id, throughput cost. Default: standard + idempotent consumer.

**Q9.3 Why Aurora next to a lakehouse? (8)** OLTP/serving (point lookups, transactional writes, your enrichment APIs) vs OLAP (scans/aggregates/history). Analytics on Aurora starves the transactional workload; point-serving off Delta is slow. Sync bridge: CDC/CDF.

**Q9.4 S3 one-liners. (7)** Strong read-after-write consistency (since 2020); request-rate scales per prefix (~3.5k PUT / 5.5k GET) → spread hot write patterns across prefixes; lifecycle to IA/Glacier for bronze cost; multipart for large objects.

**Q9.5 Glue vs Databricks; Glue Catalog vs UC. (7)** Both Spark: Glue serverless AWS-native ingest (current state), Databricks for curation/DX/Delta/governance. Catalogs: both metastores; Glue Catalog serves Athena/EMR/Redshift Spectrum; UC adds fine-grained grants + lineage cross-workspace; UC can federate Glue as a foreign catalog.

**Q9.6 Why not Lambda for ETL? (6)** 15-min cap, memory ceiling, no distributed compute — event glue only (your mock-data injector is the right-sized example).

**Q9.7 Databricks→S3 access. (6)** UC storage credential (IAM role) + external location binding path→credential→grants; keep humans out of raw S3 so table grants stay meaningful.
