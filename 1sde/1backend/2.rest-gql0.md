# 1. REST

## 1.1 Resource modeling & paths

**Q1: How do you design resource paths?**

**L4** — Nouns for resources, plural collections, hierarchy only where real ownership exists: `/instruments`, `/instruments/{id}`, `/instruments/{id}/documents`. HTTP method carries the verb. Nesting ≤2 levels; deeper children get promoted to top level with a filter (`/documents?instrumentId=x`) because deep paths force clients to know full ancestry to address one object. Consistent casing (kebab), no trailing verbs, ids opaque to clients.

**L5** — The real decision is _what the resource is_: a resource should align with (a) a unit of consistency — things that must change atomically are one resource, (b) an authorization boundary — if a path segment doesn't change who can touch it or its lifecycle, it's a query param, (c) a cache granularity. Get those wrong and no URL convention saves you: e.g., modeling "instrument + its enrichment overlay" as one resource means every correction invalidates the whole instrument cache entry and inherits vendor-data permissions; splitting them (`/instruments/{id}` vendor-of-record, `/instruments/{id}/corrections` overlay) gave us independent authz (banker-only corrections), independent cache lifetimes, and safe re-ingest — the split _is_ the design, the paths just spell it.

**Q2: Nouns vs verbs — when do you break the rule?**

**L4** — When the operation isn't CRUD on any stored noun: state transitions and domain actions. Options: sub-resource POST (`POST /payments/{id}/capture`), or custom-method suffix (`POST /instruments/{id}:reindex`, Google AIP-136 style). Never tunnel actions through PATCH with magic fields.

**L5** — The mechanism-level reason: PATCH-with-magic-fields destroys three properties at once — auditability (the action is smeared into a diff), authorization (you can't grant "may capture" separately from "may edit"), and idempotency semantics (a transition has different retry rules than a field edit). Modeling the action as its own resource (`POST /instruments/{id}/corrections` → correction with id, status, actor, timestamp) restores all three and gives you a natural surface for idempotency keys and async status. Defeater for action endpoints: they proliferate — gate new ones behind "is this really not a state field?" review, or you end up with 40 verbs and no model.

**Q3: Path vs query vs body?**

**L4** — Path = identity, required, hierarchical. Query = optional read modifiers: filter/sort/page/projection. Body = the representation on writes. No payload in query strings; GET carries no body.

**L5** — Two mechanisms decide edge cases. (1) _Caching_: HTTP caches key on URL + headers listed in `Vary`; criteria in a POST body are invisible to every cache in the path. (2) _Leakage_: URLs land in access logs, proxies, browser history, `Referer` — PII/secrets never go in path or query. Those two collide on complex search: sensitive or >~8KB criteria (order of magnitude; proxy URL caps are config, not spec) push you to `POST /instruments/search` and you consciously pay the cacheability cost — or restore it with a server-computed criteria hash you can 302 to. Say "I know what I'm trading" and this question is done.

**Q4: Bulk operations?**

**L4** — `POST /instruments:batchGet {ids:[...]}` for reads (avoids URL length limits); `POST /corrections:batch` for writes returning a per-item result array (`207`-style multi-status semantics: each item has its own status/code), never all-or-nothing unless the domain demands a transaction.

**L5** — The design fork is _atomic vs. independent_ and it must be explicit in the contract: independent items → partial success + per-item errors + idempotency key per item (retry only failures); atomic → one transaction, one status, and a size cap because transaction duration scales with batch size and long transactions hold locks/bloat (Postgres: long-running txn blocks vacuum — canonical failure pattern behind "the DB got slow every night at batch time"). Cap batch size in the contract (e.g., 500), return `413`/`400` over it; unbounded batch endpoints are just DoS with extra steps.

**Q5: HATEOAS — do you use it?**

**L4** — Know it: responses embed links/affordances (`_links: {approve: ...}`) so clients navigate by relation, not hardcoded URLs. In practice: rarely fully, because clients are codegen'd against OpenAPI and don't follow links.

**L5** — The honest, senior answer: full HATEOAS pays off when the _client UI is state-driven by the server_ (which buttons appear = which links present) — we used exactly that slice: the enrichment UI rendered "correct" affordances from per-field permission flags the API computed, which is HATEOAS's value (server owns the state machine) without the ceremony. Full hypermedia for machine-to-machine APIs mostly adds payload and parsing for links nobody follows. Name the slice you kept and why; don't cargo-cult either direction.

## 1.2 Params & input validation

**Q6/Q7: How and where do you validate?**

**L4** — Three layers. (1) _Syntactic_ at the edge: Bean Validation on request DTOs, triggered by `@Valid`, fails before controller logic with `MethodArgumentNotValidException`. (2) _Semantic_ in the application service: cross-field rules, referential existence, state-dependent rules ("cannot correct a locked record"). (3) _Persistence constraints_ (NOT NULL, FK, UNIQUE, CHECK) as the last line — they catch bugs; they are not the UX.

```java
public record CorrectionRequest(
    @NotBlank String field,
    @NotNull @Size(max = 4000) String newValue,
    @NotBlank @Size(max = 500) String reason) {}

@PostMapping("/instruments/{id}/corrections")
ResponseEntity<CorrectionView> correct(@PathVariable String id,
                                       @Valid @RequestBody CorrectionRequest req) { ... }
```

**L5** — Three upgrades over the layered answer. (1) _Parse, don't validate_: convert raw input into a domain type that cannot represent the invalid state, once, at the boundary — an `Isin` value class whose factory rejects bad checksums means inner code never re-checks and two checks can never drift apart. The failure this kills: validation done in controller A but not batch-entry-point B — same service, two doors, one guarded (canonical failure pattern; our Glue path vs API path had exactly this risk until both parsed through the same domain types). (2) _Collect, don't fail-fast_ for semantic errors: return all violations in one response or clients ping-pong one fix per round trip. (3) _Symmetric outbound validation_ at trust boundaries: the API validating "internal" pipeline data felt redundant until a vendor schema drift shipped nulls through Glue — contract tests between pipeline output schema and API expectations turned that from prod incident to CI failure.

```java
public final class Isin {
  private final String value;
  private Isin(String v) { this.value = v; }
  public static Isin parse(String raw) {
    if (raw == null || !raw.matches("[A-Z]{2}[A-Z0-9]{9}[0-9]") || !luhnOk(raw))
      throw new InvalidIsinException(raw);
    return new Isin(raw);
  }
}
```

**Q8: What do you return on failure?**

**L4** — `400` (or `422` for well-formed-but-semantically-invalid, if you keep the distinction) with a structured body: stable machine code, human message, per-field errors array.

**L5** — RFC 9457 Problem Details (`application/problem+json`; supersedes 7807): `type/title/status/detail/instance` + `errors[]` extension. The mechanism value: clients branch on stable `type` URIs, which is what lets you reword English without breaking integrations; Spring Boot 3 supports it natively (`ProblemDetail`, `spring.mvc.problemdetails.enabled=true`). Two defeaters: don't echo raw values of sensitive fields into messages (client logs), and keep the `errors[].field` paths in the _request's_ shape (JSON pointer), not your entity's — leaking internal field names couples clients to your model.

**Q9: Parse-don't-validate — say it as a principle.**

**L4** — Validation that returns boolean leaves you holding the same untrusted type; parsing returns a _new, narrower type_ whose existence proves the check ran. Push all such conversions to the boundary; the core speaks only domain types.

**L5** — The type system becomes the enforcement mechanism: you _cannot_ pass a raw `String` where `Isin` is required, so the "did anyone validate this?" question is unaskable — that's a mechanical gate in your own vocabulary, same family as your Terraform grep gates: correctness by construction over correctness by review.

## 1.3 Versioning & evolution

**Q10: How do you version?**

**L4** — URI (`/v1/...`), header (`Accept: application/vnd.co.v1+json`), or query param. URI is the pragmatic default: visible, routable at the gateway, cache keys differ naturally, testable in a browser. Bump only on breaking changes; additive changes ride the same version.

| Option               | Buys you                                                     | Costs you                                                          | Choose when                |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ | -------------------------- |
| URI `/v1`            | Obvious routing, natural cache separation, easy canary split | URL sprawl; purist objection (identity changes)                    | Default; public/partner    |
| `Accept` header      | Stable URLs; per-representation versioning                   | Invisible in logs; `Vary: Accept` cache complexity; harder to test | Media-type-driven orgs     |
| None + additive-only | No migration cliffs, no version matrix                       | Discipline + diff tooling to prevent breaks                        | Internal, both sides owned |

**Q11: When is versioning the wrong answer?**

**L5** — Strong position: a live version is a _liability multiplier_ — test matrix, support surface, and security patch surface all scale with version count; v1 lingers for years precisely because you can't see who calls it. So the primary investment is not the version scheme, it's (a) tolerant-reader discipline (clients ignore unknown fields — pinned by consumer-driven contract tests, e.g., Pact, so "tolerant" is verified, not assumed), (b) per-consumer usage telemetry from day one — the telemetry, not the scheme, is what lets you delete code, (c) `Deprecation`/`Sunset` headers as machine-readable notice. What breaks at scale without this: the Big Rewrite v2 that never finishes because v1 traffic never reaches zero and nobody can prove which fields are dead. GraphQL made field-level telemetry native (§2.9) — that asymmetry is _why_ no-versioning is credible there and aspirational in REST.

**Q12: Walk through expand-contract for a breaking change.**

**L4** — Rename `cusipId` → `identifier`: (1) _expand_ — add `identifier`, server writes/serves both; (2) migrate consumers on their own schedule, watching per-field usage; (3) _contract_ — when `cusipId` reads ~0, deprecate formally, then remove. Same pattern for DB columns (dual-write, backfill, cut reads, drop) and message schemas.

**L5** — The property this buys is _no flag-day_: at every instant, every deployed consumer version works — which is the only deployment-safe stance when you don't control client deploys. Costs: dual-write windows are consistency risk (two fields can diverge if one write path misses one field — guard with an assertion/reconciliation job during the window) and the contraction step is the one that slips forever without a dated ticket + telemetry threshold ("remove when <10 req/day for 30 days"). Note the direct bridge to Vanguard's Scenario 1 (column added, deploy order wrong): that incident _is_ what happens when expand-contract ordering is violated — expand must reach every reader before any writer produces the new shape; state the rule as "readers before writers, contract readers last."

## 1.4 Contract & schema

**Q13/Q14: Enforcing the contract; contract-first vs code-first?**

**L4** — OpenAPI 3.x is the contract. Code-first: springdoc generates spec from annotations — low friction, spec is documentation. Contract-first: spec is the artifact in the repo, reviewed in PRs, codegen for server stubs and client SDKs; gateway can validate requests against it.

**L5** — Deciding variable: _number of independent consumers_. One internal consumer → code-first fine. Multiple teams → contract-first plus two mechanical gates: (1) breaking-change diff in CI (`oasdiff`/`openapi-diff`) so an incompatible change fails _your_ build, not their runtime; (2) consumer-driven contract tests (Pact) pinning the fields consumers actually rely on — because a spec diff can't know consumer X depends on an undocumented behavior or a field you consider incidental. A generated spec nobody diffs is a screenshot, not a contract.

**Q15: What actually breaks contracts in practice?**

**L5** — Ranked by frequency (canonical patterns): (1) nullability drift — field documented required goes null under a new code path; (2) enum widening — server adds a value, client `switch` has no default and throws; contract rule: clients must treat enums as open sets, or server must version enum additions; (3) semantic change under stable shape — same field, new meaning/unit (the worst: no tool catches it; only review + changelog discipline); (4) error-shape changes — teams version success payloads and freely mutate error bodies that clients also parse; (5) ordering/pagination guarantees silently weakened. The L5 point: schema tools catch (1)–(2) mechanically; (3)–(5) need contract _tests_ + human review — know which gate catches which class.

## 1.5 Status codes & error design

**Q16: Which codes do you actually use?**

**L4** — Deliberately small set: `200` read/update, `201`+`Location` create, `202` accepted-async, `204` no-body, `304` conditional hit, `400` invalid, `401` unauthenticated, `403` forbidden, `404` absent (or concealed), `409` state conflict, `412` precondition failed, `422` semantic invalid (if used), `429`+`Retry-After`, `500` bug, `502/503/504` downstream/overload/timeout.

**Q19 (fold-in): Why codes matter — retryability.**

**L5** — Codes are a _retry and monitoring protocol_: clients and infra branch on class. 4xx = deterministic, don't retry; 5xx/429/timeouts = retryable with backoff. The two costliest miscodes: 500-for-validation (clients retry hopeless requests, amplifying load exactly during incidents) and 200-with-error-body (opts out of every generic monitor, cache, and retry policy in the path). 404-vs-403 is an information-leak decision: for guessable IDs, return 404 uniformly for both absent and forbidden or you've shipped an existence oracle for other tenants' instruments. 409 vs 412: 412 = a precondition _header_ failed (If-Match/ETag — stale client); 409 = business-state conflict; conflating them costs you the ability to separate "user needs refresh" from "rule violation" in your Datadog error taxonomy.

**Q17/Q18: Error bodies + global handling.**

**L4** — One `@RestControllerAdvice`; domain exceptions map to `ProblemDetail` with stable `type` URI and `extensions`; catch-all logs at ERROR with correlation id, returns opaque 500 (no stack traces, no internal messages).

```java
@RestControllerAdvice
class ApiErrors {
  @ExceptionHandler(CorrectionConflictException.class)
  ProblemDetail conflict(CorrectionConflictException e, HttpServletRequest req) {
    var pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Correction conflicts with newer version");
    pd.setType(URI.create("https://errors.myco.com/correction-conflict"));
    pd.setProperty("instrumentId", e.instrumentId());
    pd.setProperty("traceId", MDC.get("traceId"));
    return pd;
  }
  @ExceptionHandler(Exception.class)
  ProblemDetail fallback(Exception e) {
    log.error("unhandled", e);
    var pd = ProblemDetail.forStatus(500);
    pd.setProperty("traceId", MDC.get("traceId"));
    return pd; // opaque by design
  }
}
```

**L5** — Structural points beyond the code: (1) the advice is _taxonomy enforcement_ — every new exception type must map to exactly one status + type URI, reviewed like schema; anything falling through to the 500 catch-all is a smell you can alert on (count of unmapped exceptions as a metric). (2) Echo the trace id in the body — a client screenshot becomes greppable in Splunk; single highest-ROI ops feature in an error format. (3) Perf defeater: exceptions as control flow in hot paths — `fillInStackTrace` costs microseconds each (order of magnitude, JVM-dependent); expected high-frequency outcomes return result objects; exceptions stay exceptional.

## 1.6 Idempotency & retries

**Q20: Definitions.**

**L4** — Idempotent: N identical requests leave server state as 1 (responses may differ). Spec: GET/HEAD/PUT/DELETE idempotent; POST/PATCH not (PATCH is iff the patch is absolute). Safe (no state change): GET/HEAD.

**L5** — Defeater: method idempotency covers _resource state_, not side effects — a PUT that also publishes an SNS event per call is idempotent in Aurora and duplicative on the bus. Idempotency is designed per effect: in my pipeline, the upsert was idempotent (natural key + deterministic transform), the SNS publish was at-least-once, and downstream consumers deduped on business key + version. End-to-end you get at-least-once + consumer dedupe; "exactly-once" as a claim should always be unpacked to that or it's hand-waving.

**Q21: Idempotency keys end-to-end.**

**L4** — Client sends `Idempotency-Key: <uuid>` on POST. Server: atomically claim the key + execute; replay with same key returns stored response; same key different body → `422`; key still in-flight → `409` + `Retry-After`. TTL the keys (Stripe: 24h, as of Stripe docs).

```sql
CREATE TABLE idempotency_keys (
  key            text PRIMARY KEY,
  request_hash   text NOT NULL,
  response_status int,
  response_body  jsonb,
  state          text NOT NULL DEFAULT 'IN_PROGRESS',  -- IN_PROGRESS | DONE
  created_at     timestamptz NOT NULL DEFAULT now()
);
```

```java
@Transactional
public CorrectionView create(String key, CorrectionRequest req) {
  try {
    jdbc.update("INSERT INTO idempotency_keys(key, request_hash) VALUES (?,?)",
                key, sha256(req));                       // claims via PK
  } catch (DuplicateKeyException dup) {
    var row = load(key);
    if (!row.requestHash().equals(sha256(req))) throw new KeyReuseException();
    if (row.state().equals("IN_PROGRESS")) throw new RetryLaterException();
    return row.storedResponse();
  }
  var result = corrections.apply(req);                    // same txn as claim
  jdbc.update("UPDATE idempotency_keys SET state='DONE', response_status=?, response_body=? WHERE key=?",
              201, toJson(result), key);
  return result;
}
```

**L5** — The correctness hinge is _atomicity of claim and effect_: claim-row insert and business write in one DB transaction (unique/PK constraint arbitrates the race) — check-then-act without that constraint has a window where two concurrent retries both pass the check and both execute: the double-payment race. When effects span systems (DB write + S3 + SNS), single-txn atomicity is gone; then either (a) outbox pattern — effect and outbox row in one txn, relay publishes with at-least-once + consumer dedupe, or (b) make each effect independently deduplicable. Storage choice deciding variable: same relational DB when the effect lives there (atomicity free); Redis/DynamoDB conditional put when it doesn't, accepting stored-response/effect divergence on crash. Also: keys must be scoped per consumer (key collision across tenants = replaying someone else's response — access-control bug wearing a caching costume).

**Q22/Q23: Retry strategy; retries across layers.**

**L4** — Retry only idempotent ops or keyed POSTs; only on 429/502/503/504/connect-timeout; exponential backoff + full jitter; cap attempts (~3) and total time budget; honor `Retry-After`.

**L5** — Scale mechanisms: (1) _full jitter_ (AWS Architecture Blog, 2015) — synchronized backoff produces retry waves that re-kill a recovering service; jitter decorrelates the herd. (2) _Retry budgets over per-request caps_ — cap retries at ~10–20% of live request volume (Envoy/Finagle implement this) because during a real outage per-request retries multiply offered load 3–4× exactly when capacity is lowest; retry storms are the canonical amplifier in many public outage writeups. (3) _One retry owner_: client SDK × service mesh × gateway × your RestClient each retrying 3× = 81 attempts worst case; decide the layer that owns retries (usually outermost caller holding the idempotency key), disable elsewhere — an architecture decision, not a library flag. (4) Read-timeout ≠ failure: the request may have committed; that's _why_ only idempotent/keyed operations are retryable on timeout, and why "we retry on timeout" without a key is a data-corruption confession.

## 1.7 Caching

**Q24/Q25: Layers; ETag mechanics.**

**L4** — Layers: HTTP (`Cache-Control: max-age, public/private`, `Vary`) → CDN/proxy/browser; conditional requests: server emits `ETag`, client revalidates `If-None-Match`, `304` on match saves the body; application cache: Caffeine (local) / Redis (shared) under the service layer, keyed + TTL'd.

**L5** — Know which resource an ETag saves: Spring's `ShallowEtagHeaderFilter` renders the full body then hashes → saves _bandwidth only_; a version-derived ETag (row `version` column) can short-circuit before building the body → saves compute + DB. Claim the one you shipped. ETag's second job outranks its first: `If-Match` on writes = optimistic concurrency over HTTP (§1.8) — one header, two features. Local-vs-shared tradeoff: Caffeine = ns reads, N inconsistent copies, dies with the pod (fine — reference data: instrument types, enum tables); Redis = one copy, ~ms, plus a new dependency whose outage becomes _your_ outage → treat cache-down as degrade-to-source with load shedding, never as hard failure.

**Q26/Q27: Invalidation; stampedes.**

**L4** — TTL as the correctness bound; event-driven eviction (SNS/Redis pub-sub on write) shrinks staleness; version-in-key (`instrument:{id}:v{n}`) turns invalidation into a pointer swap. Stampede: on hot-key expiry, request coalescing (Caffeine `LoadingCache` collapses concurrent loads per key) or a short lock/`singleflight`; optionally jitter TTLs so keys don't expire in phase.

**L5** — Doctrine: _never cache what you can't bound the staleness of, and put the bound in the contract_ ("prices ≤60s stale"). Event-driven invalidation's defeater is delivery loss — the eviction message drops, entry lives to TTL; therefore TTL is the guarantee, events are an optimization; TTL=∞-because-we-evict-on-write is a latent incident. Stampede math: hot key at 2k req/s with a 300ms rebuild = ~600 concurrent rebuilds on expiry without coalescing — the DB sees a spike that looks like an attack (canonical failure pattern: "cache expiry took down the primary"). In my platform: correction writes bumped row version (new cache key), request-scoped read-your-writes in the GraphQL layer, cross-session staleness bounded at 60s TTL — corrections visible immediately to the corrector, bounded-late to everyone else, and I can say that sentence to an interviewer with numbers.

## 1.8 Concurrency & async

**Q28: Long-running operations?**

**L4** — Never hold the connection: `202 Accepted` + `Location: /operations/{id}`; operation resource carries status/progress/result-link/error; poll, or push via webhook/SNS when the caller is a service.

**L5** — This is the LRO pattern (Google AIPs formalize it). The decisions with deciding variables: server-driven poll interval in the response (or clients hammer you); operation retention ≥ client-crash + retry window; idempotency key on the _initiating_ POST so a retry doesn't spawn twin jobs; and terminal-state immutability (a DONE operation never changes — clients cache it forever). Scale flip: polling cost is O(consumers × frequency) — few consumers (my mock-data Lambda's test orchestrators) poll fine and it's debuggable; many consumers → push. The 202 contract also cleanly absorbs "the batch is still running" — which is exactly the REST face you'd put on your Glue pipeline if asked to expose ingest status (Q38).

**Q29: Concurrent updates?**

**L4** — Optimistic locking: `@Version` column (JPA bumps + guards in the UPDATE's WHERE) or ETag + `If-Match` at the HTTP layer; mismatch → `409/412`; client re-reads, re-applies, retries. Pessimistic `SELECT ... FOR UPDATE` only for short, high-conflict critical sections.

```java
@Entity class InstrumentOverlay {
  @Id String id;
  @Version long version;      // Hibernate: UPDATE ... SET version=?+1 WHERE id=? AND version=?
  ...
}
```

**L5** — Deciding variable: conflict rate × retry cost vs. blocking cost. Optimistic default because it holds nothing across user think-time and degrades gracefully; defeater: hot-row contention where retry loops livelock — there, serialize writes per aggregate through a queue (single-writer) instead of escalating to pessimistic locks that pin DB connections (each blocked request = one Hikari connection; pool 20, waiter 21 queues → tail-latency cliff; canonical failure pattern). Name the subtle lost-update: ORM read-modify-write where the version check isn't in the UPDATE's WHERE — two PATCHes to different fields both "succeed" and one silently vanishes; the guard is the SQL predicate, not the annotation's existence. HTTP mapping: `If-Match: "v17"` → 412 tells the _client_ its view is stale — pushes the merge decision to the human who can actually make it, which for banker corrections is the correct owner.

**Q30: Slow downstream inside a sync endpoint?**

**L4** — Timeouts (connect + read, aggressive), circuit breaker (Resilience4j) so a dead dependency fails fast instead of queueing threads, bulkhead isolating its thread/connection budget, and a degraded response (cached/partial + flag) where the domain tolerates it.

**L5** — The mechanism that kills you without these: thread occupancy. Tomcat 200 threads × 30s hung read = 200 requests to a _healthy_ endpoint queue behind a sick dependency — the outage spreads sideways (canonical pattern: "service B down took service A with it"). Budget arithmetic an interviewer respects: caller's SLO 500ms → downstream read timeout ≤ ~300ms so the caller can still fail cleanly inside its own budget; timeouts must _nest_, outermost largest. Circuit breaker's defeater: half-open probes on a shared pool can re-saturate a barely-recovered dependency — cap probe concurrency. Degraded-response doctrine for financial data: serve stale only with a staleness marker the UI shows; silently stale prices are worse than errors.

## 1.9 Pagination & performance

**Q31: Offset vs cursor?**

**L4** — Offset: simple, page-jumping, but O(offset) scan and unstable under concurrent inserts (dupes/skips as rows shift). Keyset/cursor: `WHERE (k, id) > (:k, :id) ORDER BY k, id LIMIT :n` — O(1) seek at any depth, stable — but no random page access and needs a deterministic unique sort.

```sql
-- keyset page after (issued_at, id) with tiebreaker; composite index required
SELECT * FROM instruments
WHERE (issued_at, id) > (:last_issued_at, :last_id)
ORDER BY issued_at, id
LIMIT 51;   -- fetch n+1: 51st row's existence = hasNextPage
```

**L5** — Mechanism: Postgres has no row-number index — `OFFSET 100000` reads and discards 100k rows; p99 grows linearly with depth (order of magnitude: deep pages go 10–100× slower; measure yours). Keyset defeaters: (1) non-unique sort key without the id tiebreaker in _both_ ORDER BY and WHERE → skips/dupes at boundaries; (2) mutable sort key (`updated_at`) → rows migrate across the cursor mid-scan — fine for feeds, wrong for reconciliation exports (there: snapshot semantics, export by immutable `ingest_id` range); (3) the composite index must match the sort exactly or you've built a slow keyset. Contract: cursors opaque (base64 the tuple) so encoding can change without a breaking change; `n+1` fetch is the standard hasNext mechanism — say it, it's the kind of concrete detail that reads as "has done this."

**Q32: Diagnosing a slow endpoint?**

**L4** — Datadog APM: p50/p95/p99 per endpoint → one slow trace's waterfall: app vs DB vs downstream. DB: `EXPLAIN (ANALYZE, BUFFERS)`, missing index, ORM N+1. Fix; re-measure the same percentile.

**L5** — Discipline that separates levels: (1) percentiles, never averages — bimodal cache-hit/miss (5ms/900ms) averages into fiction; (2) _latency vs queueing_: p99 up while DB time flat = pool saturation (Tomcat threads, Hikari) — pool utilization metrics are the tell, and the fix is capacity/limits, not query tuning; (3) N+1 is the #1 Spring finding — Hibernate statistics or a query-count assertion in an integration test makes the fix a _ratchet_ (regression gate), your own pattern; (4) fix-speed vs safety, from my composite-key story: `EXPLAIN` showed a seq scan the single-column index couldn't serve → immediate mitigation `CREATE INDEX CONCURRENTLY` in prod (no table lock, reversible, minutes) → durable fix (key redesign) through the release train behind a dark-read comparison (new path computed and diffed, not served) → recurrence guard: the query-plan assertion joined CI. That four-beat structure — mitigate, fix, verify, ratchet — is the story shape Vanguard's DB-incident question wants.

## 1.10 Security (they asked: "how did you secure your application")

**Q33/Q34: Layers, concretely.**

**L4** — Edge: TLS everywhere, gateway does authN — OIDC/JWT (internal SSO), token validated per request (signature via JWKS, `iss`/`aud`/`exp`). **L5** — The two OWASP API risks that matter most in practice (OWASP API Security Top 10, as of 2023 edition): **BOLA** (broken object-level authorization — #1): authenticating the caller but not checking _this caller may touch this id_; the guard is authZ keyed on the object, enforced in one place (service layer), never per-controller ad hoc — my permission-resolution redesign was exactly centralizing that decision so a new endpoint couldn't forget it (correct-by-construction again). **Excessive data exposure**: serializing entities straight to JSON ships fields the client shouldn't see; DTO-per-view is the boring, correct defense. # 2. GraphQL

## 2.1 Flow, schema, resolvers

**Q39: Explain your GraphQL flow end-to-end.**

**L4** — Client POSTs `{query, variables, operationName}` to one `/graphql` endpoint. Server pipeline: **parse** (query string → AST) → **validate** (AST vs schema: fields exist, args typed, fragments legal, no spec violations) → **execute** (walk the tree; each field invokes its resolver with the parent's result; children resolve after parents) → response shaped exactly like the query: `{data, errors}`. My stack: Spring for GraphQL over graphql-java, schema-first SDL in `src/main/resources/graphql/`, `@QueryMapping`/`@SchemaMapping` controllers delegating to the same application services the REST controllers use — one service layer, two protocol faces.

**L5** — Say the execution model precisely, because everything else hangs off it: execution is a _level-ordered tree walk where sibling fields and list elements resolve independently_ — that independence is what enables parallelism (§2.6), is where N+1 is born (§2.4), and is why per-request state (DataLoader registry, auth context) travels via `GraphQLContext`/`DataFetchingEnvironment` rather than thread-locals (resolvers may hop threads). Operationally split the failure classes at the pipeline boundary: parse/validate failures → `errors`, **no** `data` key (client bug; deterministic; never retry); execution failures → **partial** `data` + `errors` (§2.3). Around it: schema SDL is the reviewed contract artifact (schema diff in CI — GraphQL's `oasdiff` equivalent, e.g., graphql-inspector), depth/complexity instrumentation in front of execution (§2.7), and per-operation-name metrics out the back (Datadog tag: `operationName`) — anonymous queries are unmonitorable queries.

**Q40: What is a resolver, exactly?**

**L4** — A function per schema field: `(parent, args, context, info) → value | CompletableFuture<value>`. graphql-java default resolver = property/getter lookup on the parent — so plain fields on a fetched object cost nothing extra. You write explicit resolvers where a field needs its own fetch or shaping. Root `Query`/`Mutation` field resolvers are the entry points.

**L5** — The schema is a _promise that any legal field combination is cheap_; resolvers are where the promise is kept. So L5 resolver design is batching-topology design, decided per field: (a) resolves off the parent row → free, default resolver; (b) needs another entity → DataLoader, always, no exceptions in list positions; (c) cost can't be bounded → _don't expose it as a nested field_ — we exposed `documents(first: Int!)` with a required, capped limit instead of a bare `documents` list. That third category is the one candidates miss: the cheapest guardrail is the field you refuse to add. Also: resolvers must be authz-aware or delegated to services that are — a resolver is a new door to the same room (§2.10).

**Q41: Schema design for your domain?**

**L4** — Types mirror the _read model consumers need_, not DB tables: `Instrument`, `Offering`, `Document`, `Correction`. `!` non-null only where absence is impossible; enums for closed sets; input types for mutation args; `interface Node { id: ID! }` for shared identity; connections on all lists.

```graphql
type Instrument implements Node {
  id: ID!
  isin: String
  status: InstrumentStatus!
  issuer: Issuer # nullable: partner-service sourced
  documents(first: Int!, after: String): DocumentConnection!
  corrections(first: Int!, after: String): CorrectionConnection!
}
type Query {
  instrument(id: ID!): Instrument
  instruments(
    filter: InstrumentFilter
    first: Int!
    after: String
  ): InstrumentConnection!
}
```

**L5** — Two decisions with defeaters. (1) **Nullability is an availability decision**: per spec, a null in a non-null position propagates up to the nearest nullable ancestor — one failed `issuer!` inside a list can null the entire list or the whole `data`. Rule we ran: fields backed by _other services_ stay nullable (degrade to holes), fields from our own row are non-null (absence = bug, want the explosion). That's error-blast-radius design expressed in the type system. (2) **Demand-driven surface**: expose fields consumers asked for, not columns you have — under no-versioning (§2.9) every field is a permanent liability; the failure prevented is the 200-field God type where nobody can prove which 12 are live. Extra L5 morsel: model _identity_ deliberately — global `ID` should be opaque and stable (we base64'd `type:pk`), because Apollo client normalization and federation `@key` both stand on it; leaking raw numeric PKs as IDs is a migration trap.

**Q42: Schema-first vs code-first?**

**L4** — Schema-first: SDL files are the source of truth; resolvers bind to them (Spring for GraphQL's default). Code-first: schema generated from annotated code (Netflix DGS supports both; code-first common in JS/Python — Nexus, Strawberry).

**L5** — Deciding variable: _who reviews the contract_. Schema-first makes the SDL a language-neutral artifact product owners and consumer teams can read and diff in PRs — the contract review happens on the contract, not on Java. Code-first optimizes single-team velocity and type-safety-by-construction but buries contract changes inside implementation diffs, where a resolver refactor can silently reshape the schema. With multiple consumer teams (our case, and Vanguard's), schema-first + CI schema-diff is the defensible default; say code-first is fine for one-team internal graphs and you've shown judgment, not allegiance.

**Q43: Your actual wiring (be ready to draw it).**

**L4/L5 fused (this one is "prove you built it")** — `@Controller` classes: `@QueryMapping instrument(@Argument String id)` → application service → repository; nested `@SchemaMapping(typeName="Instrument") issuer(...)` returning `CompletableFuture` via DataLoader; `BatchLoaderRegistry` registers mapped batch loaders at startup; `DataFetcherExceptionResolverAdapter` for the error taxonomy; `WebGraphQlInterceptor` pulls auth principal + trace id into `GraphQLContext`; instrumentation beans for depth/complexity caps; Datadog metrics tagged by operation name; GraphiQL enabled non-prod only. Being able to rattle the _bean names_ is what makes "I used Spring for GraphQL" credible under cross-examination.

## 2.2 Filtering & pagination

**Q44: Filtering?**

**L4** — Typed filter inputs: `instruments(filter: InstrumentFilter)` with `InstrumentFilter { types: [InstrumentType!], issuedAfter: Date, text: String }`; resolver compiles it to SQL predicates / OpenSearch query. No raw query strings, no generic string DSLs.

**L5** — The fork is **closed vocabulary vs. generic filter DSL** (`{field, op, value}` trees, and-or nesting). The DSL demos beautifully and is a footgun: it is a slow-query construction kit handed to clients — every expressible combination must be index- or mapping-backed or someone will find the seq scan for you in prod; and it's unvalidatable at the type level (field names as strings). Doctrine: _a filter field is a capacity commitment_ — adding one means committing an index/OpenSearch mapping and gets reviewed as such. That's also the real answer to "how do you prevent expensive queries": prevention at schema-design time is static and unbypassable; runtime cost analysis (§2.7) is the fuse behind it. Text search: route `text:` to OpenSearch, ids back to Aurora for hydration — say the two-store split out loud, it matches your resume's architecture and invites a question you want.

**Q45: Connections — mechanics + code.**

**L4** — Relay Connection spec: `(first: Int!, after: String)` → `{ edges { node cursor } pageInfo { hasNextPage endCursor } }`. Cursor = keyset position (§1.9 mechanics), opaque base64. Standardized envelope: every client, tool, and cache handles paging identically.

```java
@SchemaMapping(typeName = "Instrument")
public CompletableFuture<Connection<Document>> documents(Instrument parent,
    @Argument int first, @Argument String after, DataFetchingEnvironment env) {
  int limit = Math.min(first, 100);                       // hard cap, schema promise kept
  var cursor = Cursor.decode(after);                      // (createdAt, id) tuple
  return env.<DocKey, List<Document>>getDataLoader("docsPage")
            .load(new DocKey(parent.id(), cursor, limit + 1))   // n+1 rows
            .thenApply(rows -> Connections.from(rows, limit));  // 101st row => hasNextPage
}
```

**L5** — Why the ceremony beats `{items, nextCursor}`: per-edge cursors allow resume-from-any-item; `pageInfo` carries hasNext without sentinel hacks (the fetch-n+1 mechanism — name it); and the uniform shape is what lets Apollo's normalized cache and federation handle paged data generically — the envelope is infrastructure, not bureaucracy. Defeaters: `totalCount` is not free — a `COUNT(*)` can cost more than the page (Postgres counts by scanning; order of magnitude: full-index scan on millions of rows); we made it opt-in and approximate (OpenSearch `track_total_hits` bounded) — "exact counts on demand" is a requirement to push back on, with the alternative of "≈10,000+" UX. And `first` is non-null with a server-side clamp: the schema says required, the resolver enforces the ceiling — belt and suspenders because schema can't express max values.

**Q46: totalCount / page-jumping pushback?**

**L5** — When product insists on page numbers + exact totals: offset pagination _bounded_ (cap max page × size so the O(offset) cost has a ceiling), count served from a maintained counter or search-engine estimate, and honesty that deep-linking page 4,000 is a non-goal. Naming the bounded-offset compromise beats both purist refusal and naive compliance.

## 2.3 Errors & exceptions

**Q47: How does GraphQL error handling differ from REST?**

**L4** — Transport is (almost always) HTTP 200; errors ride in the body's `errors[]`: `message`, `path`, `locations`, `extensions`. Three classes: **request errors** (parse/validate — `errors` only, no `data`), **field errors** (resolver threw — that field becomes null per nullability rules, siblings survive → _partial results_), **transport errors** (genuine non-200: gateway auth, 429, 5xx). Client must check both channels.

**Q48: Built-in vs custom — what did you use?**

**L4** — Custom taxonomy on top of the built-in shape: `DataFetcherExceptionResolverAdapter` mapping domain exceptions → `GraphQLError` with stable `extensions.code` + graphql-java `ErrorClassification`; unknown exceptions → sanitized `INTERNAL_ERROR` (default-deny: never leak internal messages into `errors[].message`).

```java
@Component
class GqlExceptions extends DataFetcherExceptionResolverAdapter {
  @Override protected GraphQLError resolveToSingleError(Throwable ex, DataFetchingEnvironment env) {
    return switch (ex) {
      case CorrectionConflictException c -> GraphqlErrorBuilder.newError(env)
          .errorType(ErrorType.BAD_REQUEST)
          .message("Correction conflicts with a newer version")
          .extensions(Map.of("code", "CORRECTION_CONFLICT",
                             "instrumentId", c.instrumentId(),
                             "traceId", MDC.get("traceId")))
          .build();
      case AccessDeniedException a -> GraphqlErrorBuilder.newError(env)
          .errorType(ErrorType.FORBIDDEN)
          .message("Not permitted").extensions(Map.of("code", "FORBIDDEN")).build();
      default -> null;   // falls through to sanitized INTERNAL_ERROR
    };
  }
}
```

**Q49: Errors-as-data — the design fork.**

**L5** — The spec's `errors[]` is for _exceptional_ failures; **expected, business-meaningful outcomes belong in the schema** as union result types:

```graphql
union CorrectInstrumentResult =
  | CorrectionSuccess
  | FieldLockedError
  | StaleVersionError
type FieldLockedError {
  field: String!
  lockedBy: String!
  message: String!
}
type Mutation {
  correctInstrument(input: CorrectInput!): CorrectInstrumentResult!
}
```

Why unions win for these: they're _introspectable_ (codegen forces clients to handle each case — the compiler is your contract test), _extensible without breaking_ (add a union member = additive), and _typed_ (structured data per error kind, not string codes by convention). Costs: schema surface + client match boilerplate → doctrine: unions for mutations and expected read failures; `errors[]` for genuine faults (bugs, outages, authz). Two operational defeaters worth volunteering: (1) HTTP-200-always **blinds generic monitoring** — your dashboards say 200s while every body carries errors; you must emit an error-rate metric from the `errors[]` array tagged by `extensions.code` (`Canonical failure pattern`: the "healthy" GraphQL API that had been failing for hours); (2) the exception resolver is the _only_ leak barrier — a missed mapping means a raw Hibernate message in a client-visible error; default-deny with an allowlist, and alert on INTERNAL_ERROR rate.

**Q50: Partial results — client contract.**

**L5** — A `data`+`errors` response is a transport _success_; blanket retry re-executes the parts that worked (and re-runs any committed mutation prefix — §2.8). Correct client behavior: render what resolved, per-field fallback for what didn't, targeted refetch of the failed subtree if needed (Apollo `errorPolicy: all` exists for exactly this). Server-side you _choose_ blast radius via nullability (§2.1): nullable field = hole in the page; non-null = amputate the subtree. Saying "partial results are a feature I configure with nullability, not an accident" is the L5 sentence.

## 2.4 N+1 & DataLoader

**Q51: What is N+1?**

**L4** — List of N parents + a child field: 1 fetch for parents, then the child resolver runs once per parent → N more calls. `instruments(first: 50) { issuer { name } }` = 1 + 50 issuer lookups. Structural, not a bug: execution resolves list items independently (§2.1), so any per-entity fetch in a list position amplifies.

**Q52: DataLoader — mechanism + code.**

**L4** — Per-request batch + cache. Resolvers call `load(key)` → future; DataLoader accumulates keys during the execution step, dispatches one `batchLoadFn(keys)` (`WHERE id IN (...)`), completes all futures, caches key→value for the request. 51 queries → 2.

```java
@Configuration
class Loaders {
  @Bean BatchLoaderRegistry registry(IssuerRepository repo, Executor gqlExecutor) {
    var registry = new DefaultBatchLoaderRegistry();
    registry.forTypePair(String.class, Issuer.class)
        .withName("issuers")
        .registerMappedBatchLoader((Set<String> ids, BatchLoaderEnvironment env) ->
            Mono.fromCallable(() -> repo.findByIds(ids))     // one IN-query
                .subscribeOn(Schedulers.fromExecutor(gqlExecutor)));
    return registry;
  }
}

@SchemaMapping(typeName = "Instrument")
CompletableFuture<Issuer> issuer(Instrument i, DataLoader<String, Issuer> issuers) {
  return issuers.load(i.issuerId());     // Spring injects the named loader
}
```

**L5 (mechanism)** — Why batching works at all: graphql-java's execution strategy tracks field-resolution _levels_ and dispatches registered loaders when a level's demands are gathered (`as of` graphql-java's per-level dispatching instrumentation) — batching is a property of cooperative scheduling between executor and loaders, not magic.

**Q53: DataLoader defeaters (this is where they sort levels).**

**L5** — (1) **Blocking kills it**: `.join()` on a loader future inside a resolver stalls the very thread that would trigger dispatch → deadlock or one-key "batches"; loaders demand end-to-end async resolvers. (2) **Per-request scope is a correctness rule**: a shared/global loader cache serves user A's authz-filtered issuer to user B and stale rows forever — cache lifetime = request lifetime, and any real cache goes _under_ the batch fn, consciously. (3) **Batch-fn contract**: results must map to input keys incl. misses (mapped loader sidesteps ordering bugs; list loader with misaligned order = silent wrong-data, worst failure class). (4) **Batching flattens breadth, not depth**: 4 nested levels = ≥4 sequential dispatch rounds minimum; deep schemas need denormalized read models, not more loaders. (5) **The relocated N+1**: your batch fn calls `repo.findByIds` which lazy-loads a collection per row → N+1 reborn one layer down, invisible from the GraphQL layer; the guard is mechanical — assert query counts in an integration test (§2.11). (6) IN-list limits: thousands of keys per batch → split batches (`maxBatchSize`) or hit parameter/plan limits.

**Q54: N+1 in REST?**

**L4** — Client-side: GET list then GET-per-item — the chatty client. REST fixes: `?expand=issuer` compound docs, purpose-built aggregate endpoints, BFF.

**L5** — Sharpest framing: GraphQL doesn't create N+1, it _relocates_ it. REST's lives client→server: visible in access logs, paid in RTTs, throttled by browser connection limits. GraphQL's lives server→DB behind one request: invisible in access logs, paid in DB connections — strictly better _iff batched_; unbatched, you've hidden a fan-out where ops tooling can't see it. One paragraph, and it answers "GraphQL vs REST performance" better than any benchmark.

## 2.5 Caching

**Q55: Why is caching harder?**

**L4** — REST keys on URL → HTTP/CDN caching free. GraphQL: one endpoint, POST bodies, unbounded query shapes → HTTP caches blind. Caching relocates: client normalized caches (Apollo, keyed `__typename:id`), per-request DataLoader dedupe, application caches under resolvers.

**Q56: The four layers, with deciding variables.**

**L5** — Ordered by ROI for an authed internal API: (1) **Entity cache under resolvers** (Caffeine/Redis, `instrument:{id}:v{n}`): shape-agnostic, shared with REST, invalidation via version bump — where ours lived; highest leverage because every query shape hits it. (2) **DataLoader per-request dedupe**: correct by construction, zero staleness risk, free. (3) **Whole-response caching** only via persisted queries / GET-with-hash: restores URL-keyability — worth it for public read-heavy graphs; for authed APIs `Vary: Authorization` fragments it to uselessness, skip. (4) **Client normalized cache**: powerful, but a correctness footgun — needs globally stable unique IDs and consistent selections, staleness invisible to the server; you _design for it_ (opaque global IDs, §2.1) even if you don't operate it. Governing defeater: **field-level authz breaks response caching entirely** — same query, different viewer, different data; cache below the authz boundary, never above.

**Q57: APQ mechanics (know it even unused).**

**L4/L5** — Automatic Persisted Queries: client sends SHA-256 of the query; server cache-misses → client sends full text once → thereafter hash-only, and queries can go over **GET** → CDN-cacheable, infra-retryable (`as of` Apollo APQ docs). Distinguish from the _allowlist_ flavor: build-time registration where unknown hashes are rejected — that one is a security control (§2.7); APQ alone is bandwidth + GET restoration, not protection (any client can register any query). Conflating them is a common candidate error — drawing the line is free L5 signal.

**Q58: What did you actually run?**

Entity cache with version-bump invalidation (60s TTL bound), DataLoader per request, no whole-response cache (internal, authed), required-and-clamped `first` so the uncached worst case stays bounded, read-your-writes for the correcting session. Defensible, boring, true.

## 2.6 Concurrency & async

**Q59: Are resolvers concurrent?**

**L4** — Query fields: yes — siblings and list elements may resolve concurrently; returning `CompletableFuture` makes it explicit and graphql-java composes them. **Mutations: spec mandates serial execution of top-level mutation fields in document order** — `{ debit credit }` is deterministic; that asymmetry is _the_ exam favorite.

**Q60: Executors, pools, virtual threads.**

**L5** — Parallelism is determined by _where futures complete_, not by the framework: blocking JDBC on the transport thread serializes everything (and starves a reactive transport entirely). Blocking work goes to a bounded executor sized to the true constraint — which is the **Hikari pool, not CPU**: 50 concurrent resolvers vs 20 connections = 30 parked threads and a tail-latency cliff; the concurrency limit belongs at the executor/loader (bulkhead) and must be ≤ pool. **Virtual threads** (Java 21 — bridges their other question): `spring.threads.virtual.enabled=true` (Boot 3.2+) makes thread-per-task free for blocking code and deletes pool-sizing guesswork for _threads_ — but VTs mint no DB connections; the queue moves from thread pool to connection pool, and the fix for connection scarcity is still capacity/limits/replicas. Caveat if pushed: VT pinning inside `synchronized` around JDBC was the known trap; JDK 24 (JEP 491) largely removed it — knowing the JEP number is cheap credibility.

**Q61: When does async pay?**

**L5** — Only when one query fans out to _independent_ sources — our instrument + OpenSearch text hits + partner doc-service metadata overlapped three backends in one round trip; that's real latency subtraction. Single-DB queries: async buys nothing and costs stack-trace legibility. Naming the boundary — "async where there's fan-out, sync where there isn't" — outranks enthusiasm in either direction.

## 2.7 Query safety & performance

**Q62: Defending against expensive queries — ordered by leverage.**

**L4** — Depth limit (~10), complexity budget (cost/field × list multipliers, reject pre-execution via instrumentation), required + capped `first` everywhere, per-request and per-loader timeouts, persisted-query allowlist for known clients, gateway rate limits.

**L5** — Rank and admit weaknesses: **schema-level guardrails first** (capped `first`, no unbounded lists, closed filters) — _static_, unbypassable, free at runtime; **complexity analysis is a fuse, not a firewall** — multipliers are estimates and one mis-costed field is a bypass; **the allowlist is the only complete defense** (arbitrary-query risk → 0), right for a fixed internal consumer set, at the cost of a registration step and ad-hoc queries (keep GraphiQL+introspection non-prod). Pair prevention with **detection**: per-operation-name p95/cost in Datadog — a cost regression surfaces as a _named_ trend, not anonymous noise. Depth limits double as the cycle defense (`instrument → issuer → instruments → …` via recursive fragments). Aliasing defeater: `a: instruments(first:100) b: instruments(first:100) …` ×50 multiplies cost inside legal depth — complexity budgets must count aliases (naive depth checks don't; this is the known bypass).

**Q63: Overfetch/underfetch — the honest version.**

**L4** — REST fixed payloads: 40 fields fetched, 4 used (overfetch); 3 calls per screen (underfetch). GraphQL: field selection solves both at the wire contract — the founding pitch (Facebook mobile, public history 2012→2015 open-sourcing).

**L5** — Two catches to volunteer. (1) Selection trims the _wire_, not the _backend_: `SELECT *` into a full entity moves waste from network to DB/heap; end-to-end demand-driven needs projection push-down (Q64) — done selectively or not at all. (2) The counter-cost: exact selection makes every client query shape a distinct performance profile — REST's rigidity is also its _predictability_ (capacity-plan 5 endpoints vs an open query space); persisted queries are how you claw predictability back. Closing line: **"GraphQL trades payload efficiency for load predictability — then you spend tooling to buy the predictability back."**

**Q64: Projection push-down.**

**L5** — `env.getSelectionSet()` → requested field names → column list / OpenSearch `_source` filter. Real gains on wide types (our instrument row: 150+ attributes; fetching 6 vs 150 columns matters — TOAST'd wide columns especially); cost: couples resolvers to storage layout and breaks the "service layer returns whole entities" simplicity, so we did it for the two widest types only, behind the service interface. "Selective, measured, behind the boundary" is the defensible posture.

## 2.8 Retries

**Q65: Retry semantics — queries vs mutations.**

**L4** — Queries are reads → semantically retryable, but travel as POSTs, so no infra auto-retry: client-library logic, on transport errors/5xx/429 only — never on in-body `errors` (deterministic: same query, same failure). Mutations: unsafe by default; idempotency exactly as REST POST (§1.6) — key as mutation input or header + server-side key store.

**L5** — Subtleties: (1) partial-result responses are transport successes — blanket retry re-executes what worked; per-field fallback or targeted subtree refetch instead. (2) **Serial mutation execution means a multi-field mutation document that dies midway has committed a prefix** — whole-document retry re-runs committed fields → client convention: one mutation field per document; multi-step ops become one server-side transactional mutation. (3) APQ's GET restores infra-level retry/caching for reads — the fix, not the default. This trio is a fully-armored answer to a question most candidates fumble with "queries yes, mutations no."

## 2.9 vs REST, federation, evolution

**Q66: When do you pick which?**

**L4** — GraphQL: many client types with divergent needs, aggregation across backends, fast-iterating frontends, one flexible contract over N bespoke endpoints. REST: few stable-shape consumers, HTTP-cache leverage, files/binary, webhooks, operational simplicity, public surfaces where arbitrary queries are unacceptable. They coexist: our GraphQL faced product UIs, REST faced system integrators, one service layer beneath both.

**L5** — Decide on _organizational_ variables: GraphQL moves integration cost from server team (bespoke endpoints per consumer) into schema design + governance tooling — a win iff consumer-team count is high and you'll actually run the governance. State the price plainly: GraphQL replaces commodity HTTP infrastructure — caching (§2.5), retries (§2.8), monitoring semantics (§2.3) — with bespoke application-layer equivalents you now own and staff. One backend + one consumer + CRUD = REST, full stop; proposing GraphQL there is résumé-driven architecture. Saying that last sentence, in a GraphQL interview, is the strongest single credibility move available.

**Q67: Supergraph / federation — what, why, how it actually executes.**

**L4** — Supergraph = one composed schema over multiple **subgraphs**, each owned and deployed by a domain team; a router (Apollo Router) plans each operation across subgraphs and joins entities. Subgraphs declare entities with `@key(fields: "id")`; other subgraphs contribute fields to them. Why: one graph for clients + independent team ownership — vs monolithic schema (single deploy bottleneck, merge contention) and vs schema stitching (the predecessor: manual gateway-side merging, brittle — what federation replaced).

```graphql
# instruments-subgraph
type Instrument @key(fields: "id") {
  id: ID!
  isin: String
  status: InstrumentStatus!
}
# pricing-subgraph
extend type Instrument @key(fields: "id") {
  id: ID! @external
  price: Price
}
```

**L5** — Name the router's **query plan**: the operation decomposes into per-subgraph fetches sequenced by key dependencies; downstream subgraphs are called via `_entities(representations: [...])` — so an innocent client query becomes a _sequential multi-hop fan-out_, and **cross-subgraph joins are N+1 at the service tier**: entity resolvers must batch representations exactly as DataLoader batches ids, one layer up. The real product is **governance**: composition checks in CI reject a subgraph change that breaks the supergraph _before deploy_ — the org-scale mechanism behind no-versioning. When it's wrong: federation earns its router + registry + composition pipeline at roughly 3+ teams owning distinct domains (order of magnitude, not doctrine); one team = monolithic schema, say so. (`as of` Apollo Federation v2 docs. Vanguard asked "what/why supergraph" — this buys/costs/mechanism triple is the expected shape.)

**Q68: Evolution without versions.**

**L4** — Additive freely; breaking = add-new-alongside + `@deprecated(reason:)` + migrate consumers + remove at ~zero usage. No `/v2` graphs.

**L5** — The load-bearing mechanism is **field-level usage telemetry per client** (router/gateway metrics): without it deprecation is a prayer; with it, contraction is a query ("which clients still read `cusipId`?") and removal is a dated, gated ticket. This native per-field observability is _why_ the no-versioning stance is credible in GraphQL and aspirational in REST (§1.3) — drawing that contrast across protocols is a cross-cutting L5 move interviewers remember.

## 2.10 GraphQL security

**Q69: Where does authz live?**

**L4** — AuthN at the gateway/interceptor (JWT → principal into `GraphQLContext`). AuthZ in the _service layer_ — object- and field-level checks where domain context exists — not sprinkled per-resolver. `@PreAuthorize` on `@SchemaMapping` methods works but delegating to centrally-enforced services means a new resolver can't forget the check (correct-by-construction, same doctrine as §1.10 BOLA).

**L5** — GraphQL-specific surfaces: (1) **introspection off in prod** for external-facing graphs (schema = free recon map; keep it on internally where DX wins); (2) **the resolver-is-a-new-door problem** — REST endpoint audited, GraphQL exposes the same entity via a nested path nobody threat-modeled; the fix is authz at the service/entity layer so _every_ door hits the same lock; (3) **batching/alias abuse** as brute-force amplifier (50 aliased login mutations in one request defeats per-request rate limits — count operations/aliases, not HTTP requests, in the limiter); (4) CSRF: GraphQL-over-GET (APQ) needs the same CSRF posture as any GET-with-effects — keep mutations POST-only; (5) field-level redaction beats field-level errors for confidential-but-present data (return null, don't advertise existence via FORBIDDEN — the 404-vs-403 concealment logic, GraphQL edition).

## 2.11 Testing (they ask "what tests did you implement")

**Q71: Testing GraphQL?**

**L4** — Slice tests with `@GraphQlTest` + `GraphQlTester`: execute documents against the schema with mocked services — validates schema-resolver binding, arg coercion, error mapping. Integration: full context + Testcontainers Postgres, real queries through HTTP. Contract: schema diff in CI (breaking-change detection) + codegen'd client types failing compilation on drift.

```java
@GraphQlTest(InstrumentController.class)
class InstrumentControllerTest {
  @Autowired GraphQlTester tester;
  @MockBean InstrumentService svc;

  @Test void fetchesIssuerBatched() {
    tester.document("""
        { instruments(first: 2) { edges { node { issuer { name } } } } }""")
      .execute()
      .path("instruments.edges[*].node.issuer.name")
      .entityList(String.class).hasSize(2);
  }
}
```

**Q73: The query-count regression gate (your signature move — say it).**

**L5** — The N+1 fix that isn't tested regresses on the next innocent field addition. Mechanical ratchet: integration test wraps the datasource (e.g., datasource-proxy / p6spy), executes the representative query, asserts `queryCount ≤ 2`. Now un-batching a resolver _fails CI_ instead of paging on-call — external verification over self-review, the same principle as your Terraform grep gates and Liquibase drift tests, and you should draw that line explicitly in the interview: it presents a coherent engineering philosophy, not a bag of tricks. REST side (Q72) mirrors: `@WebMvcTest` slices for controller+advice mapping (assert Problem Details shape per exception), Testcontainers integration, Pact for consumer contracts, and the query-count gate on the hot read endpoints.

## 2.x L5-only

**Q74: The 5,000 RPS consumer on GraphQL + Aurora Serverless (their Scenario 2 — internalize the skeleton, don't script it).**
**(1) Evaluate**: baseline QPS and per-operation cost profile — persisted queries make the new load _enumerable_ (a finite set of shapes to plan for, versus an open query space; this is §2.7's predictability point becoming a capacity tool); Aurora Serverless capacity model is the trap to name — ACU autoscaling reacts in tens of seconds (order of magnitude; `as of` Aurora Serverless v2 docs) which chases a step-function of sustained 5k RPS badly → provisioned instances + read replicas; connection math: pods × Hikari pool vs Postgres `max_connections` → RDS Proxy/pgbouncer multiplexing.
**(2) Design for isolation first, speed second** ("cannot impact existing consumers" is a _structural_ requirement): dedicated read replicas or a dedicated deployment cell for the new consumer behind the same schema (bulkhead), per-consumer token-bucket at the gateway so their 5k cannot cannibalize the neighbors, entity-cache layer sized for their (narrow, persisted) query set, allowlist so nothing off-plan executes.
**(3) Test**: load-test the named operations at 1.5–2× target against production-shaped data volumes, soak for pool/leak behavior, game-day a replica failover mid-load.
**(4) Rollout**: percentage ramp gated on SLOs (p99, `errors[]`-derived error rate, replica lag), automatic rollback thresholds, per-consumer dashboards. Differentiator sentence: _"zero-downtime tolerance means I protect existing consumers structurally — cells and limits — before I optimize anything."_

**Q75: Mutation design doctrine.** One mutation field per document (§2.8's committed-prefix hazard); verb-specific mutations (`correctInstrument`, `lockField`) over generic `updateInstrument` (audit + authz granularity — the REST custom-action logic, GraphQL edition); input types with idempotency key; union results (§2.3); mutations return the mutated entity so client caches update in one round trip.

**Q76: One graph over Aurora + MongoDB + OpenSearch (your actual system as a design question).** Entity residency: canonical instruments in Aurora; documents in Mongo behind the broker; text search in OpenSearch returning ids hydrated from Aurora (search results are always canonical-fresh; index lag only affects _recall_, not displayed data — name that property, it's subtle and true). DataLoaders per backend; nullable cross-store fields so one degraded store degrades fields, not pages (§2.1 nullability-as-availability, applied); the graph is the place cross-store consistency semantics become _visible_ to consumers — which is the argument for GraphQL in this architecture, stated as a conclusion rather than a preference.
