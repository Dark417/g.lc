# PART 1 — SPARK: WHAT PROBLEM IT SOLVES

## 1.1 The world before: MapReduce

Hadoop MapReduce (2004-ish) solved a real problem — run a computation across 1,000 cheap machines and survive machine failures — with a deliberately rigid model:

1. **Map** — each machine processes its local chunk, emits key-value pairs.
2. **Shuffle** — pairs are sorted and routed so all values for a key land on one machine.
3. **Reduce** — each machine aggregates its keys, writes to HDFS.

The rigidity is the point: because every stage boundary wrote to disk, a failed machine just re-ran its task from the last on-disk checkpoint. Fault tolerance came free from being slow.

**What hurt:**

| Problem                                 | Consequence                                                                                                                                              |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Every job writes to HDFS between stages | An iterative algorithm (ML training, graph traversal) re-reads from disk every iteration. 10 iterations = 10 full disk round trips.                      |
| One job = one map + one reduce          | Any real ETL is 5–10 jobs chained by hand, each materializing to disk, each scheduled separately                                                         |
| Only two operators                      | Joins, filters, aggregations all hand-coded as map/reduce logic. Hundreds of lines for a `GROUP BY`.                                                     |
| Batch only                              | No interactive query, no streaming. Different systems for each — Hive for SQL, Storm for streaming, Mahout for ML, each with its own cluster and format. |
| Java-only, verbose                      | Word count is ~60 lines                                                                                                                                  |

The industry response was a zoo: Hive, Pig, Storm, Impala, Giraph, Mahout — each a separate engine over the same HDFS data.

## 1.2 Spark's answer

Spark (2010, AMPLab; Matei Zaharia) made two moves.

**Move 1 — keep intermediate data in memory, but stay fault tolerant via lineage.**
The RDD abstraction records _how_ a dataset was computed (its lineage of transformations) rather than checkpointing the data itself. Lose a partition, recompute it from its parents. You get memory speed without giving up recovery. That single idea is why iterative workloads went from hours to minutes.

**Move 2 — a general DAG instead of fixed map→reduce.**
You express a whole pipeline as one DAG of transformations. The engine plans it end to end, pipelines narrow operations together, and only materializes at shuffle boundaries. Ten MapReduce jobs collapse into one Spark job with three shuffles.

Everything else followed from those two:

- **One engine, many workloads** — SQL, streaming, ML, and graph all compile down to the same DAG execution. One cluster, one format, one skillset. This is the "unified" claim, and it's the actual historical significance of Spark.
- **Rich API** — `filter`, `join`, `groupBy`, `window` as first-class operations in Scala, Python, SQL, R.
- **Catalyst optimizer + Tungsten** (Spark 2.x) — you write DataFrame/SQL, the optimizer rewrites it. Predicate pushdown, column pruning, join reordering happen without you.

Word count goes from ~60 lines of Java to one line of PySpark. That matters less than it sounds, but the optimizer matters a lot: a novice's DataFrame code often beats an expert's hand-tuned MapReduce.

## 1.3 The comparison, compressed

|                     | MapReduce               | Spark                                           |
| ------------------- | ----------------------- | ----------------------------------------------- |
| Intermediate data   | Disk (HDFS) every stage | Memory, spilling to disk when needed            |
| Fault tolerance     | Re-read from disk       | Recompute from lineage                          |
| Job shape           | map → shuffle → reduce  | Arbitrary DAG                                   |
| Iterative workloads | Terrible                | The design target                               |
| Workloads supported | Batch                   | Batch, SQL, streaming, ML, graph                |
| Optimizer           | None                    | Catalyst (rule + cost based)                    |
| Typical speedup     | —                       | 10–100× on iterative, ~3–10× on single-pass ETL |

**Where Spark is still the wrong answer:** small data (a single Postgres query beats a cluster), low-latency point lookups (milliseconds — that's a KV store), high-concurrency transactional writes, and true per-event streaming with sub-second latency (Flink is the better fit; Spark is micro-batch).

## 1.4 The execution model — the L4 floor

You need this fluently. It's the substrate under every performance question.

```
Driver (your code, the plan, the scheduler)
  │  splits the DAG at shuffle boundaries
  ▼
Job ──► Stage 1 ──shuffle──► Stage 2 ──shuffle──► Stage 3
           │                    │
           ├─ Task (partition 0)─┤     one task per partition,
           ├─ Task (partition 1)─┤     run on Executors
           └─ Task (partition N)─┘
```

- **Partition** — the unit of parallelism. A DataFrame is N partitions; N tasks run at once (bounded by total cores).
- **Transformation** — lazy. Builds the plan. `filter`, `select`, `join`, `groupBy`.
- **Action** — triggers execution. `count`, `write`, `collect`, `show`.
- **Job** — one action.
- **Stage** — a span of the job with no shuffle in it. New shuffle = new stage.
- **Task** — one stage's work on one partition.
- **Narrow transformation** — output partition depends on one input partition (`filter`, `select`). No data movement.
- **Wide transformation** — output depends on many input partitions (`groupBy`, `join`, `distinct`). Requires a **shuffle**.

**A shuffle, physically:** every task writes its output sorted by destination partition to local disk; every downstream task then fetches its slice from every upstream executor over the network. Disk write + all-to-all network. It's the single most expensive thing in Spark, and "how many shuffles does this job have" is the first performance question worth asking.

**Driver vs executor:** driver runs your `main`, builds the plan, schedules tasks, and holds anything you pull back. Executors run tasks and hold cached data. `collect()` on a large DataFrame kills the driver — this is the #1 rookie failure.

**AQE (Adaptive Query Execution)** — on by default in modern Spark. At runtime, using real shuffle statistics, it coalesces oversized partition counts down, converts a sort-merge join to a broadcast join when a side turns out small, and splits skewed partitions. It means you tune less than older material suggests. It cannot fix skew that exists before the first shuffle.

## 2.3 The "unified" claim, stated precisely

The pitch is: one copy of your data in an open format, one governance model, many engines.

- Before: data in S3 as Parquet for Spark, copied to Redshift for BI, copied again to a feature store for ML. Three copies, three permission systems, three definitions of "revenue."

That's the actual argument, and it's worth being able to state in two sentences. The honest caveat: it's true within Databricks, and "open format" is genuine (Delta is open source, UniForm bridges to Iceberg), but the governance and tooling layer is proprietary and is where the lock-in lives.

# PART 3 — DELTA LAKE: THE FORMAT UNDER EVERYTHING

## 3.1 What a Delta table physically is

```
s3://bucket/tables/instruments/
├── part-00000-....snappy.parquet     ← plain Parquet data files
├── part-00001-....snappy.parquet
└── _delta_log/
    ├── 00000000000000000000.json     ← commit 0: {metaData, protocol, add ...}
    ├── 00000000000000000001.json     ← commit 1: {add, remove, commitInfo}
    ├── ...
    └── 00000000000000000010.checkpoint.parquet   ← every 10 commits, consolidated
```

Each JSON commit is a list of **actions**: `add` a file, `remove` a file, set `metaData` (schema, partitioning), set `protocol`, record `commitInfo` (who, what operation, when).

**The one insight that makes everything else obvious: the table is the log, not the files.** A Parquet file sitting in the directory that no `add` action references is invisible to readers. From that:

| Property               | Falls out of the log because...                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **Atomicity**          | A crashed job leaves orphan Parquet files but no commit — readers never see them          |
| **Time travel**        | Replay the log to commit N, read that file set                                            |
| **Data skipping**      | Min/max stats per file live _in the log_, so the planner skips files without opening them |
| **Cheap metadata**     | No `LIST` on millions of S3 objects; the log knows the file set                           |
| **Schema enforcement** | `metaData` is the schema of record; a mismatched write is rejected                        |

Corollary: never `rm` files out of a Delta directory, and never hand-write Parquet into one.

## 3.2 ACID on object storage

**Optimistic concurrency control.** A writer reads the current version, does its work, then tries to create the next numbered log file. If that filename already exists, someone else committed first — the writer re-reads, checks whether the conflict is real (do our file sets actually overlap?), and retries or fails.

The whole thing rests on an atomic _create-if-not-exists_ for the log file. S3 now supports conditional writes; historically Databricks used a commit coordination service, which is why multi-writer OSS Delta on S3 used to be a footgun.

**Practical consequence:** blind appends rarely conflict. Two MERGEs touching the same files do. If you need parallel writers, give them disjoint partition predicates.

## 3.3 The operations you'll actually use

```sql
-- Time travel
SELECT * FROM instruments VERSION AS OF 42;
SELECT * FROM instruments TIMESTAMP AS OF '2026-07-29';

-- What happened to this table
DESCRIBE HISTORY instruments;          -- version, operation, user, metrics
DESCRIBE DETAIL  instruments;          -- numFiles, sizeInBytes → small-file check

-- Undo a bad write
RESTORE TABLE instruments TO VERSION AS OF 41;

-- Upsert
MERGE INTO instruments t
USING updates s
  ON t.instrument_id = s.instrument_id
 AND t.event_date >= current_date() - 30      -- ← prunes target files. Do not omit.
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;

-- Replace a well-defined slice atomically (cheaper than MERGE for full reloads)
INSERT OVERWRITE instruments REPLACE WHERE event_date = '2026-07-29' SELECT ...;

-- Maintenance
OPTIMIZE instruments;                   -- compact small files
VACUUM  instruments RETAIN 168 HOURS;   -- delete unreferenced files older than 7d
```

**Three rules worth memorizing:**

1. **Always put a static predicate in a MERGE's ON clause.** Without one, MERGE scans the entire target table. This is the single most common cause of "our merge takes four hours."
2. **Dedupe the source before MERGE.** Two source rows matching one target row throws.
3. **Don't lower VACUUM retention below 7 days.** The default protects in-flight readers and long-running streams from having files deleted underneath them.

## 3.4 Schema enforcement vs evolution

- **Enforcement is the default and it's a feature.** A write whose schema doesn't match is rejected.
- **`mergeSchema`** adds new columns on append. **`overwriteSchema`** replaces the schema wholesale.

The policy, not the syntax, is the L4-worthy part: enable `mergeSchema` at **bronze** (contract: capture whatever the source sent), disable it at silver and gold (a surprise column means an unreviewed contract change). `overwriteSchema` in a production job is nearly always a bug — it's how someone silently drops a column three dashboards depend on.

# PART 4 — MEDALLION ARCHITECTURE

## 4.1 The layers

```
   source ──► BRONZE ──► SILVER ──► GOLD ──► BI / ML / apps
              raw        clean      business
```

| Layer      | Contract                                                           | Contains                                                                                                               | Schema policy                          |
| ---------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| **Bronze** | "We never lose what the source sent"                               | Raw records as received, append-only, plus ingest metadata: `_source_file`, `_ingest_ts`, `_batch_id`, `_rescued_data` | Permissive — `mergeSchema` on          |
| **Silver** | "This is correct, deduplicated, and stable to build on"            | Typed, cleansed, deduplicated, conformed, joined to reference data. Normalized.                                        | Enforced — schema changes are reviewed |
| **Gold**   | "This answers a specific business question and matches the report" | Aggregates, star schemas, denormalized serving tables                                                                  | Enforced, and shaped for consumption   |

## 4.2 Why bronze must stay raw and immutable

Two reasons, both operational:

- **Replay.** If silver logic was wrong, fix the transform and rebuild from bronze — without re-fetching from a source that may have a retention window or rate limit.
- **Blame assignment.** When a downstream number is wrong, bronze is the evidence that settles whether the source sent bad data or we transformed it badly. That ends most cross-team arguments in one query.

Storage is the cheapest thing in the stack. Manage bronze with retention and tiering, never by deleting the raw record.

## 4.3 Does Databricks enforce it?

**No.** This is a real interview question and the answer is nuanced.

**Not enforced:**

- Nothing stops you creating one catalog with 400 tables and no layers.
- No naming convention is required. `bronze`/`silver`/`gold` are just schema names you chose.
- No lint rule prevents a dashboard querying a bronze table directly.
- Nothing prevents putting business logic in silver, which is the most common way medallion degrades.

**Strongly encouraged — the platform is shaped for it:**

- **Pipelines** make layering natural: you declare a streaming table from Auto Loader (bronze), then a table reading it (silver), then a materialized view (gold), and the dependency DAG is inferred from the references. Doing it any other way is more work.
- **Expectations** (`EXPECT` constraints in pipelines) give you a natural quality gate at the bronze→silver boundary.
- **Streaming tables vs materialized views** map cleanly onto the layers: append-only incremental ingest vs recomputed aggregates.
- **UC schemas + grants** make the layer a permission boundary — grant analysts `SELECT` on gold only.
- Every tutorial, template, and demo uses it.

**The honest framing for an interviewer:** medallion is a _convention_, not a feature. Databricks enforces nothing; it makes the convention the path of least resistance and gives you the primitives (schemas, grants, expectations, streaming tables) to enforce it yourself if you choose. In practice you enforce it with UC grants and code review, not with a platform setting.

**Where teams get it wrong** — worth being able to name one:

- Silver tables that are really gold (business logic in the shared clean layer). Then two teams need contradictory logic and there's nowhere to put it.
- Bronze that isn't actually raw because someone "just cleaned up the dates on ingest." Now replay reproduces the bug.
- No quarantine path, so bad records either kill the pipeline or vanish silently.

# PART 5 — THE OBJECTS YOU WORK WITH

## 5.1 The namespace

```
Metastore  (one per region; attached to workspaces)
└── Catalog                    e.g.  dev | staging | prod
    └── Schema (= database)    e.g.  bronze | silver | gold
        ├── Table              managed | external | streaming table
        ├── View               standard | materialized view
        ├── Volume             managed | external  ← non-tabular files
        ├── Function           UDFs, row filters, column masks
        └── Model              MLflow registered models
```

Everything is `catalog.schema.object`. Three levels, always.

**Environment pattern:** catalog per environment (`dev.silver.instruments` vs `prod.silver.instruments`), not workspace per environment. Then promotion is a config change — the same code with a different catalog parameter.

## 5.2 Tables

**Managed vs external**

|                       | Managed                             | External                                                                          |
| --------------------- | ----------------------------------- | --------------------------------------------------------------------------------- |
| Who owns the location | UC picks it                         | You specify `LOCATION 's3://...'`                                                 |
| `DROP TABLE`          | Deletes the data                    | Deletes only the metadata                                                         |
| Optimization          | Automatic (predictive optimization) | You schedule OPTIMIZE/VACUUM                                                      |
| Use when              | Default — almost always             | Other systems write the files directly, or you're adopting existing data in place |

**Default to managed.** You get automatic layout maintenance and a simpler lifecycle. Reach for external only when something outside Databricks writes to that path.

**Table types you'll see:**

| Type                  | What it is                                                                             | Created by                               |
| --------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------- |
| **Delta table**       | The normal thing                                                                       | `CREATE TABLE`, `df.write.saveAsTable`   |
| **Streaming table**   | A Delta table maintained by incremental appends, with checkpoint state managed for you | Pipelines, or `CREATE STREAMING TABLE`   |
| **Materialized view** | A Delta table holding a query result, refreshed incrementally when possible            | Pipelines, or `CREATE MATERIALIZED VIEW` |
| **View**              | Just a stored query, no data                                                           | `CREATE VIEW`                            |
| **Foreign table**     | A table in another system (Glue Catalog, Postgres, Snowflake) surfaced through UC      | Lakehouse Federation                     |

## 5.3 Volumes — the part people skip

A **volume** is governed storage for files that aren't tables. Same UC grants, same audit trail, but the content is a filesystem, not a schema.

```
/Volumes/<catalog>/<schema>/<volume>/path/to/file.pdf
```

**Use a volume for:**

- Landing zones for raw files before Auto Loader parses them
- Unstructured data: PDFs, images, audio — the RAG/document-processing input
- Libraries: JARs, wheels, init scripts
- Files a job must read or write with plain filesystem semantics
- Model artifacts, config files, exports handed to another team

**Use a table for:** anything you will query with SQL. If it's rows and columns, it's a table.

**Managed vs external volume** mirrors tables: managed = UC owns the path; external = you point it at an existing S3 prefix (useful when a legacy process already drops files there).

**Why this exists:** before volumes, non-tabular files lived on DBFS or in raw S3 paths with cluster-scoped IAM — ungoverned, unauditable, and a way around table permissions. Volumes close that hole.

**Common flow:**

```
vendor SFTP ──► S3 ──► external volume ──► Auto Loader ──► bronze table
```

## 5.4 DBFS — know it, don't use it

DBFS is the legacy workspace-scoped filesystem, with the notorious `/dbfs/` and `dbfs:/` paths and no real governance. It's deprecated in favor of volumes. Recognize it in old material; don't write new code against it. This is a small but reliable signal in an interview — knowing that volumes _replaced_ DBFS for governed file storage shows you're current.

# PART 6 — LAKEFLOW JOBS (orchestration) — FULL DEPTH

**What it is:** Databricks' native orchestrator. A **job** is a DAG of **tasks** with schedules, dependencies, retries, parameters, and notifications. It's the procedural half of the platform — _you_ say what runs in what order.

## 6.1 Anatomy

```
Job "silver-instruments-prod"
├── schedule: cron 0 15 2 * * ?   (or trigger: file arrival / continuous)
├── job parameters: {catalog: prod, run_date: {{job.start_time.iso_date}}}
├── job clusters: [etl_cluster]   ← shared across tasks, started once
├── permissions / run_as: service principal
├── notifications: on_failure, on_duration_warning
├── max_concurrent_runs: 1
└── tasks:
    ├── ingest_bronze     (notebook)      cluster=etl_cluster
    ├── build_silver      (python_wheel)  depends_on=[ingest_bronze]
    ├── quality_gate      (sql)           depends_on=[build_silver]
    ├── branch            (if/else)       condition on quality_gate result
    │    ├── publish_gold (pipeline)      if passed
    │    └── alert        (notebook)      if failed
    └── notify            (notebook)      depends_on=[...], run_if=ALL_DONE
```

## 6.2 Task types

| Type              | Use for                                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Notebook**      | Interactive-authored logic; fine as a thin entry point                                                                                              |
| **Python wheel**  | The production answer — packaged, versioned, unit-testable code                                                                                     |
| **Python script** | A `.py` file from a volume, workspace, or git                                                                                                       |
| **JAR**           | Scala/Java Spark jobs                                                                                                                               |
| **SQL**           | A query, a file, an alert, or a dashboard refresh                                                                                                   |
| **Pipeline**      | Triggers a Lakeflow declarative pipeline. Must be a _triggered_ pipeline — continuous pipelines can't be job tasks (they're already always running) |
| **dbt**           | Runs a dbt project                                                                                                                                  |
| **Run job**       | Calls another job — composition and reuse                                                                                                           |
| **If/else**       | Conditional branching on a value                                                                                                                    |
| **For each**      | Loops a task over a list — the dynamic fan-out primitive                                                                                            |

## 6.3 Dependencies and control flow

- `depends_on` builds the DAG. Independent tasks run in parallel automatically.
- **`run_if`** controls execution when upstream outcomes vary:

| `run_if`                             | Runs when                                                                                    |
| ------------------------------------ | -------------------------------------------------------------------------------------------- |
| `ALL_SUCCESS` (default)              | Every dependency succeeded                                                                   |
| `AT_LEAST_ONE_SUCCESS`               | Any dependency succeeded                                                                     |
| `NONE_FAILED`                        | Nothing failed (skips are OK)                                                                |
| `ALL_DONE`                           | Everything finished, regardless of outcome — **use this for cleanup and notification tasks** |
| `AT_LEAST_ONE_FAILED` / `ALL_FAILED` | Failure-handling paths                                                                       |

- **If/else task** branches on a condition (often a value from an upstream task).
- **For each task** iterates a nested task over an input array, with a concurrency limit. This is how you fan out over a list of tables or dates without writing N tasks.

## 6.4 Parameters and passing values

**Job parameters** (job-level, available to all tasks) and **task parameters** (per task). Dynamic value references are the useful part:

```
{{job.id}}  {{job.run_id}}  {{job.start_time.iso_date}}
{{task.name}}  {{task.run_id}}
{{job.parameters.catalog}}
{{tasks.<task_name>.values.<key>}}      ← taskValues, see below
```

**In a notebook**, parameters arrive as widgets:

```python
dbutils.widgets.text("catalog", "dev")
catalog = dbutils.widgets.get("catalog")
```

**In a wheel**, they arrive as `argv`:

```python
# entry_point in setup.py: silver = instruments.entry:main
import argparse
def main():
    p = argparse.ArgumentParser()
    p.add_argument("--catalog", required=True)
    p.add_argument("--run-date", required=True)
    args = p.parse_args()
```

**taskValues** pass data between tasks (small values only — a count, a status, a path):

```python
# upstream task
dbutils.jobs.taskValues.set(key="rows_loaded", value=row_count)

# downstream task
n = dbutils.jobs.taskValues.get(taskKey="build_silver", key="rows_loaded", default=0)
```

Use taskValues for control flow, never for data. If you need to pass a dataset, write a table.

## 6.5 Triggers

| Trigger                         | Use for                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Scheduled (cron + timezone)** | The default. Nightly/hourly batch.                                                                   |
| **File arrival**                | Run when new files land in a volume/external location — event-driven ingest without a running stream |
| **Continuous**                  | Keep the job always running, restarting on completion — for streaming jobs                           |
| **Table update**                | Run when an upstream table gets new data                                                             |
| **Manual / API**                | Backfills, external orchestrators, CI                                                                |

## 6.6 Compute choice per task

- **Job compute** — created for the run, terminated after. ~half the DBU rate of all-purpose. **This is the production answer.**
- **Shared job cluster** — one cluster defined at job level, reused by multiple tasks. Avoids paying N cluster startups for an N-task DAG. Big practical win.
- **Serverless** — no startup wait, no idle cost, less config. Good for short tasks and bursty jobs.
- **All-purpose** — for development only. Running scheduled production on an all-purpose cluster is the most common and most expensive mistake in a Databricks org.

## 6.7 Reliability settings — the ones that matter

| Setting                                         | Why                                                                                                                                                                   |
| ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`timeout_seconds`**                           | Set on every task. A hung job never fails, so it never alerts. This is the worst failure mode and the most-forgotten setting.                                         |
| **`max_retries` + `min_retry_interval_millis`** | Retry transient failures (spot preemption, cloud throttle). **Only safe if the task is idempotent** — retrying a blind append duplicates data.                        |
| **`max_concurrent_runs`**                       | Set to 1 for pipelines that mutate a table, or a long run overlaps the next schedule and two writers fight.                                                           |
| **Notifications**                               | `on_failure` is table stakes. Also set **`on_duration_warning`** — that's your freshness SLA signal.                                                                  |
| **`run_as`**                                    | Run production as a **service principal**, not a person. Otherwise the job dies when that person's token or account changes.                                          |
| **Repair run**                                  | Re-runs only the failed tasks and their downstream, reusing successful results. Learn this — it's the difference between a 5-minute recovery and a 3-hour full rerun. |
| **Queueing**                                    | Holds a run instead of skipping it when concurrency is capped.                                                                                                        |

Don't build production jobs in the UI. Define them in a **Databricks Asset Bundle**:

# PART 7 — LAKEFLOW SPARK DECLARATIVE PIPELINES — FULL DEPTH

**What it is:** the declarative half. You declare **datasets** and how they're derived; the platform infers the DAG from the references, orders execution, manages checkpoints and state, retries progressively (task → flow → pipeline), and enforces data quality.

Formerly Delta Live Tables. Built on Apache Spark Declarative Pipelines (now open source), with Databricks-specific extensions.

**Jobs vs Pipelines in one line:** Jobs orchestrate _tasks_ procedurally. Pipelines derive _datasets_ declaratively.

## 7.1 Core concepts

| Concept               | What it is                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------- |
| **Pipeline**          | The unit of deployment and execution. Owns its source code, compute, target catalog/schema, and configuration. |
| **Flow**              | A processing step — reads sources, writes to one target. The unit of retry and parallelism.                    |
| **Streaming table**   | Append-only target, processed incrementally. Each source row is read once; checkpoint managed for you.         |
| **Materialized view** | Target holding a query result, refreshed (incrementally where possible) on each update.                        |
| **View**              | Intermediate, not persisted — for readable decomposition inside the pipeline.                                  |
| **Sink**              | Write to an external target (e.g. Kafka, or a Delta table outside the pipeline).                               |
| **Expectation**       | A data quality constraint with a defined action on violation.                                                  |

**The distinction that gets asked:** streaming table for _incremental ingest of new data_ (bronze, and silver appends). Materialized view for _derived results that must reflect the whole current state_ (gold aggregates, dimension joins). If reprocessing everything on each run would be wrong or too slow, you want a streaming table.

## 7.2 A pipeline, in Python

```python
import dlt                              # module name still `dlt`
from pyspark.sql import functions as F

# ---------- BRONZE: streaming table from Auto Loader ----------
@dlt.table(
    name="bronze_instruments",
    comment="Raw vendor feed, as received.",
    table_properties={"quality": "bronze"},
)
def bronze_instruments():
    return (
        spark.readStream.format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaEvolutionMode", "rescue")   # unknown fields -> _rescued_data
        .load("/Volumes/prod/landing/vendor_feed/")
        .withColumn("_source_file", F.col("_metadata.file_path"))
        .withColumn("_ingest_ts", F.current_timestamp())
    )

# ---------- SILVER: expectations + typed cleansing ----------
@dlt.table(name="silver_instruments")
@dlt.expect_or_drop("valid_id", "instrument_id IS NOT NULL")
@dlt.expect_or_fail("schema_sane", "notional IS NULL OR notional >= 0")
@dlt.expect("fresh", "ingest_ts > current_date() - INTERVAL 2 DAYS")   # warn only
def silver_instruments():
    return (
        dlt.read_stream("bronze_instruments")                # ← this reference builds the DAG
        .select(
            F.trim("instrumentId").alias("instrument_id"),
            F.to_date("issueDate", "yyyy-MM-dd").alias("issue_date"),
            F.col("notional").cast("decimal(18,2)").alias("notional"),
            "_ingest_ts",
        )
    )

# ---------- GOLD: materialized view ----------
@dlt.table(name="gold_daily_notional")
def gold_daily_notional():
    return (
        dlt.read("silver_instruments")
        .groupBy("issue_date")
        .agg(F.sum("notional").alias("total_notional"),
             F.count("*").alias("n"))
    )
```

Note: **you never write the DAG.** `dlt.read_stream("bronze_instruments")` _is_ the dependency declaration.

## 7.3 Expectations — the quality gate

| Decorator / clause           | On violation                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------ |
| `@dlt.expect("name", cond")` | Record the violation in metrics, **keep the row**. Warn-only.                  |
| `@dlt.expect_or_drop(...)`   | Drop the row, record it. The quarantine-ish default.                           |
| `@dlt.expect_or_fail(...)`   | Fail the whole update. For "the pipeline is broken," not "this record is bad." |

SQL form:

```sql
CREATE OR REFRESH STREAMING TABLE silver_instruments (
  CONSTRAINT valid_id EXPECT (instrument_id IS NOT NULL) ON VIOLATION DROP ROW,
  CONSTRAINT sane     EXPECT (notional >= 0)             ON VIOLATION FAIL UPDATE
)
AS SELECT ... FROM STREAM(bronze_instruments);
```

**The rule:** `fail` for conditions meaning the _pipeline_ is broken (schema mismatch, zero rows, a required join matching nothing). `drop`/`expect` for conditions meaning a _record_ is broken. Conflating them gives you either a pipeline that dies nightly over three bad rows, or one that silently publishes a table missing 40% of its data.

Expectation metrics land in the **event log**, so you can chart drop rates and alert on a _change_ in reject rate — which is what actually detects a vendor changing their feed.

As of 2026 you can also store expectations centrally in Unity Catalog tables, so quality rules are version-controlled and shared across pipelines rather than duplicated in code.

## 7.4 AUTO CDC — CDC and SCD without hand-written MERGE

This replaces `APPLY CHANGES INTO`, and it's the biggest single reason to use pipelines. It handles out-of-order events and SCD Type 1/2 for you — no watermark code, no two-action MERGE trick.

```sql
CREATE OR REFRESH STREAMING TABLE silver_issuers;

AUTO CDC INTO silver_issuers
FROM STREAM(bronze_issuer_changes)
KEYS (issuer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY change_ts                 -- resolves out-of-order events
COLUMNS * EXCEPT (operation, change_ts)
STORED AS SCD TYPE 2;                 -- or TYPE 1
```

Python equivalent: `dlt.create_auto_cdc_flow(...)`. Writing this by hand as a MERGE is ~40 lines plus the null-key union trick for SCD2 — this is three.

## 7.5 Pipeline modes and settings

| Setting                            | Options                                                                                                    | Notes                                                                                                                        |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Execution mode**                 | **Triggered** — runs, processes what's available, stops. **Continuous** — always running, low latency.     | Triggered is the default and usually right. Continuous costs you a 24/7 cluster. Only triggered pipelines can be a job task. |
| **Development vs Production mode** | Dev: cluster is reused and not terminated, no retries — fast iteration. Prod: fresh cluster, full retries. | Dev mode saves you minutes per iteration. Never leave prod pipelines in dev mode.                                            |
| **Target catalog/schema**          | Where tables are published                                                                                 | Parameterize by environment                                                                                                  |
| **Configuration**                  | Key-value config readable via `spark.conf.get`                                                             | How you parameterize source paths per environment                                                                            |
| **Compute**                        | Autoscaling min/max, serverless option                                                                     | Serverless removes most compute tuning                                                                                       |
| **Channel**                        | CURRENT / PREVIEW                                                                                          | Leave on CURRENT for prod                                                                                                    |
| **Full refresh**                   | Reprocess everything from scratch                                                                          | Destroys and rebuilds — check downstream impact first                                                                        |

## 7.6 The event log

Every pipeline writes a structured **event log** — a queryable table of flow progress, expectation metrics, lineage, cluster events, and errors. This is your observability surface:

```sql
SELECT timestamp, details:flow_progress:data_quality:expectations
FROM event_log(TABLE(prod.silver.silver_instruments))
WHERE event_type = 'flow_progress';
```

Chart drop rate per expectation, alert on the delta. Knowing the event log exists is a strong L4 signal — it's the difference between "pipelines handle quality" and "here's how I'd monitor it."

## 7.7 When _not_ to use pipelines

Be able to say this — enthusiasm without limits reads as marketing.

- **Arbitrary imperative control flow** — call an API, branch on an external condition, loop with side effects. Pipelines are declarative; that's a job.
- **Tight control over compute or Spark configs** — pipelines manage compute for you.
- **Portability off Databricks** — this is real lock-in. Spark Declarative Pipelines being open-sourced softens it, but the Databricks extensions are Databricks-only.
- **Non-Delta targets as the primary output** — sinks exist, but it's not the sweet spot.
- **A pipeline that's really one query** — a scheduled SQL task in a job is simpler.

## 7.8 Jobs vs Pipelines — the decision

|              | Lakeflow Jobs                                                                                              | Lakeflow Pipelines                                                 |
| ------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Model        | Procedural: you order the tasks                                                                            | Declarative: DAG inferred from dataset references                  |
| You manage   | Checkpoints, retry semantics, dependency order, idempotency                                                | Almost none of it                                                  |
| Best at      | Heterogeneous DAGs, control flow, calling external systems, orchestrating _everything including pipelines_ | Bronze→silver→gold ETL, CDC, streaming ingest, quality enforcement |
| Data quality | You write the checks                                                                                       | Built in via expectations                                          |
| CDC / SCD    | Hand-written MERGE                                                                                         | `AUTO CDC`                                                         |
| Lock-in      | Low (it's a scheduler)                                                                                     | Higher                                                             |

**They compose, and that's the normal production shape:** a **job** is the outer orchestrator, and one of its tasks is a **pipeline**.

```
Job (nightly 02:15)
├── task: wait_for_vendor_file      (file arrival / sensor)
├── task: run_pipeline              ← Lakeflow pipeline: bronze→silver→gold
├── task: reconcile_counts          (SQL — data test)
└── task: refresh_dashboard         (SQL, run_if: ALL_SUCCESS)
```

**Default recommendation for an L4:** use pipelines for the medallion transformation core, use jobs for orchestration and everything that isn't a dataset derivation. Use jobs alone if you need imperative control or portability.

## 8.1 The deployment shape

```
┌─ Databricks CONTROL PLANE (Databricks' AWS account) ────────────┐

│  Unity Catalog metadata                                          │
└──────────────────────────┬───────────────────────────────────────┘
                           │ launches / coordinates

│  S3 buckets: workspace root + your table/volume locations        │
└──────────────────────────────────────────────────────────────────┘
```

**The interview-relevant point:** with classic compute, your data and the compute touching it stay in your AWS account and VPC. Serverless compute runs in Databricks' account (with network controls available). That distinction is the first thing a security review asks about.

## 8.2 S3 access — the chain you must be able to draw

Users never hold AWS credentials. Access is brokered by Unity Catalog:

```
AWS IAM role (trust policy → Databricks)
   ▲
   │ referenced by
STORAGE CREDENTIAL   (UC object wrapping the IAM role)
   ▲
   │ scoped to a path by
EXTERNAL LOCATION    (UC object: s3://bucket/prefix + credential)
   ▲
   │ backs
EXTERNAL TABLE  or  EXTERNAL VOLUME
```

Grants (`READ FILES`, `WRITE FILES`, `CREATE TABLE`) are issued on the **external location**. Because the credential lives in UC and not on the cluster, a user can't bypass row filters or column masks by reading the bucket directly. That's the whole security argument, and it's the concrete difference from the old instance-profile model where whoever could create a cluster could attach an IAM role and read everything.

Managed tables/volumes use a metastore- or catalog-level storage root, configured the same way.

```hcl
resource "databricks_storage_credential" "s3" {
  name = "instruments-cred"
  aws_iam_role { role_arn = aws_iam_role.uc.arn }
}

resource "databricks_external_location" "landing" {
  name            = "instruments-landing"
  url             = "s3://my-bucket/landing"
  credential_name = databricks_storage_credential.s3.name
}
```

## 8.5 Glue → Databricks, mapped

If you know Glue, you already know most of this. The mapping:

| AWS Glue                                  | Databricks                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |

# PART 9 — WHAT AN L4 ACTUALLY DOES

A concrete loop, so you can talk about the work rather than the features:

1. **Land raw** — vendor drops files to S3; an external volume makes them governed; Auto Loader ingests to a bronze streaming table with `_rescued_data` and ingest metadata.
2. **Clean to silver** — a pipeline with expectations: drop bad rows, fail on structural breakage, dedupe, type, conform. `AUTO CDC` if the source is a change feed.
3. **Shape gold** — materialized views for the aggregates the business actually asks for.
4. **Orchestrate** — a job wraps it: file-arrival trigger → pipeline task → reconciliation SQL task → dashboard refresh. Timeouts and `on_duration_warning` set.
5. **Ship it** — job and pipeline defined in an Asset Bundle in git, deployed to `dev` then `prod`, differing only in the catalog parameter.
6. **Operate** — event log and expectation drop rates on a dashboard; alerts on failure, duration exceeded, and reject-rate change; `DESCRIBE HISTORY` and `RESTORE` when something goes wrong; repair-run rather than full rerun.
7. **Maintain** — OPTIMIZE/VACUUM (or predictive optimization), watch `DESCRIBE DETAIL` for small-file drift, keep the DBR version pinned and upgrade deliberately.

That list _is_ the L4 job description. If you can narrate it end to end, you'll interview well.

# PART 10 — 50 L4 INTERVIEW QUESTIONS + ANSWERS

Answers are at L4 depth: correct, mechanism-aware, bounded. Not exhaustive — that's the next round.

## A. Spark fundamentals (1–10)

**1. What problem does Spark solve that MapReduce didn't?**
MapReduce wrote to disk between every stage and only offered map + reduce. Spark keeps intermediate data in memory and expresses the whole pipeline as a general DAG, so iterative and multi-step workloads stop paying repeated disk round trips. Fault tolerance still works because RDD lineage lets Spark recompute a lost partition instead of re-reading a checkpoint.

**2. Transformation vs action.**
Transformations are lazy and build the plan (`filter`, `select`, `join`, `groupBy`). Actions trigger execution (`count`, `collect`, `show`, `write`). One action = one job. Laziness is why a DataFrame used twice without caching recomputes twice.

**3. Narrow vs wide transformation.**
Narrow: each output partition depends on one input partition — no data movement (`filter`, `select`, `withColumn`). Wide: output depends on many input partitions, requires a shuffle (`groupBy`, `join`, `distinct`, `orderBy`, window functions).

**4. What is a shuffle and why is it expensive?**
Map-side tasks write output partitioned by destination to local disk; reduce-side tasks fetch their slice from every upstream executor over the network. It's a full disk write plus all-to-all network transfer, so it's bounded by disk and network rather than CPU. Minimizing shuffles is the main structural performance lever.

**5. Job, stage, task, partition.**
Job = one action. Stage = a span of the job with no shuffle in it; a shuffle creates a stage boundary. Task = one stage's work on one partition. Partition = the unit of parallelism; N partitions means up to N tasks in flight.

**6. Driver vs executor.**
Driver runs your code, builds the plan, schedules tasks, and holds anything returned to it. Executors run tasks and hold cached data. The driver is a single point of failure and the thing that dies when you `collect()` a large result.

**7. Why is `collect()` dangerous, and what would you use instead?**
It pulls every row into driver memory. Use `take(n)`/`limit(n).collect()` for a peek, write to a table for real output, or `toLocalIterator()` to stream partitions. My rule: driver-side collection is for control-flow values only, never for payload.

**8. What is AQE?**
Adaptive Query Execution re-optimizes at runtime using real shuffle statistics: it coalesces an oversized shuffle-partition count down, converts sort-merge to broadcast join when a side turns out small, and splits skewed partitions. On by default. It can't prevent the first bad exchange, because it only sees stats after shuffling.

**9. What causes data skew and how do you spot it?**
One key holds far more rows than the others — commonly a `NULL`/`UNKNOWN` sentinel, one dominant tenant, or a backfill concentrated on one date. In the Spark UI: max task duration far above median (>5×) with a matching spike in shuffle read size for those tasks.

**10. Name three ways to handle skew.**
(a) Broadcast the small side so there's no shuffle at all. (b) Let AQE's skew join split the oversized partitions. (c) Salt the hot keys — add a random suffix on the large side, explode the small side across the salt values — and only for the hot keys, not the whole DataFrame. Best fix is often upstream: don't let unmapped records collapse into one join key.

## B. Delta Lake (11–19)

**11. What is a Delta table physically?**
Parquet data files plus a `_delta_log/` directory of ordered JSON commits containing actions (`add`, `remove`, `metaData`, `protocol`, `commitInfo`), with a Parquet checkpoint every 10 commits. The table is defined by the log — an unreferenced Parquet file in the directory is invisible.

**12. How does Delta provide ACID on S3?**
Optimistic concurrency: a writer reads the current version, does its work, then atomically creates the next numbered log file. If that name already exists, it re-reads, checks for a real conflict, and retries. It depends on an atomic create-if-not-exists for the log file.

**13. How does time travel work and what limits it?**
Replay the log to a version and read that file set. Two independent retentions limit it: log retention (default 30 days) and deleted-file retention (default 7 days). If VACUUM removed the data files, time travel fails even with the log entry present.

**14. What does VACUUM do and what's the risk?**
Deletes data files no longer referenced by the current version and older than the retention threshold (7 days default). Lowering retention breaks in-flight readers and long-running streams that hold a file list, and destroys time travel. Don't go below the longest job runtime plus margin.

**15. How do you make a MERGE fast?**
Add a static partition or clustering predicate to the `ON` clause so Delta prunes target files — without one, MERGE scans the entire target. Also dedupe the source on the merge key first (multiple matches throw), and enable deletion vectors so small updates don't rewrite whole files.

**16. MERGE vs `INSERT OVERWRITE ... REPLACE WHERE`?**
MERGE for row-level upserts when you only have changed rows. `REPLACE WHERE` for atomically replacing a complete slice — a full daily reload. Running MERGE on a full daily extract is a common and expensive mistake; the slice replacement is a bulk file swap instead of a per-row match.

**17. Schema enforcement vs evolution — what's your policy?**
Enforcement is the default and I keep it. I enable `mergeSchema` at bronze, where the contract is "capture what the source sent," and disable it at silver and gold, where a new column means an unreviewed contract change. `overwriteSchema` in production is nearly always a bug.

**18. Partitioning vs Z-ORDER vs liquid clustering.**
Partitioning = physical directories, coarse, and effectively permanent. Z-ORDER = multi-dimensional co-location applied during OPTIMIZE, must be re-run, good for a few columns. Liquid clustering = incremental, self-maintaining, and changeable after the fact. For a new table I'd use liquid clustering and skip partitioning unless I need whole-partition atomic replacement.

**19. What's the small-files problem and how do you fix it?**
Many small writes (streaming micro-batches, frequent MERGEs, over-partitioning) produce thousands of tiny files, so task and metadata overhead dominates the actual work. Fix with OPTIMIZE, optimized writes, auto-compaction, or predictive optimization — and check `DESCRIBE DETAIL` for `numFiles` vs `sizeInBytes`.

## C. Medallion & pipeline design (20–25)

**20. Explain the medallion architecture.**
Bronze = raw as received, append-only, with ingest metadata. Silver = cleansed, typed, deduplicated, conformed — the trustworthy operational layer. Gold = business-level aggregates and serving shapes. The layers are contract boundaries, not just names.

**21. Does Databricks enforce medallion?**
No. It's a convention, not a feature — nothing stops you creating 400 flat tables. But the platform is shaped for it: pipelines infer the layer DAG from dataset references, expectations give you a natural quality gate, streaming tables and materialized views map onto ingest vs derived layers, and UC schemas plus grants let you make each layer a permission boundary. You enforce it with grants and code review, not a setting.

**22. Why must bronze stay raw?**
So you can replay when silver logic was wrong, without re-fetching from a source that may have a retention window. And so you can prove whether bad data came from the source or from your transform — that's the query that ends cross-team arguments.

**23. How do you make a batch pipeline idempotent?**
Identify the unit of work by something deterministic (a business date, a source batch id), never wall-clock "now." Then use `REPLACE WHERE` on that slice, or MERGE on a stable business key, or Delta's `txnAppId`/`txnVersion`. Never blind-append something that might rerun. Extend the same discipline to side effects — a notification or external write needs its own idempotency key.

**24. How do you handle late-arriving data?**
Process by event time, not processing time, and reprocess a trailing window (say the last 3 days) each run — which is why the write must be idempotent. In streaming, a watermark defines the lateness bound; I'd route past-watermark records to a quarantine table with an alert rather than dropping them silently.

**25. Where do you put data quality checks and what happens on failure?**
At the bronze→silver boundary. Fail-fast for conditions meaning the pipeline is broken — schema mismatch, row count outside a band, a required join matching nothing. Quarantine (drop to a rejects table) for individual bad records. Quarantine without an alert and an owner is just slower data loss, so I alert on reject-_rate change_, not absolute volume.

## D. Lakeflow Jobs (26–34)

**26. What is a Lakeflow Job?**
Databricks' native orchestrator: a DAG of tasks with dependencies, schedules or event triggers, per-task retries and timeouts, parameters, branching and looping, and notifications. It's the procedural layer — you specify the order.

**27. Name the task types you'd use.**
Notebook, Python wheel, Python script, JAR, SQL, pipeline, dbt, run-job, if/else, and for-each. Production logic goes in a wheel; notebooks are fine as thin entry points.

**28. Notebook vs wheel for production — which and why?**
Wheel. It's importable, unit-testable with plain pytest, versioned, and reviewable as normal files. I keep business logic in pure functions that take and return DataFrames and know nothing about session creation or `dbutils`, with a thin entry point that wires config and calls them.

**29. How do you pass values between tasks?**
`dbutils.jobs.taskValues.set/get` for small control-flow values — a row count, a status, a path. Job and task parameters plus dynamic references like `{{job.start_time.iso_date}}` for inputs. Never pass a dataset through taskValues; write a table.

**30. All-purpose vs job compute vs shared job cluster.**
All-purpose is interactive, stays alive, and costs the most per DBU — development only. Job compute is created for the run and terminated after, at roughly half the rate — the production answer. A shared job cluster is one cluster reused across the job's tasks, so an N-task DAG doesn't pay N startups. Production jobs running on all-purpose clusters is the most common cost mistake in a Databricks org.

**31. Which reliability settings do you always set?**
A `timeout` on every task — a hung job never fails, so it never alerts. Retries, but only where the task is idempotent. `max_concurrent_runs = 1` for anything mutating a table. Failure notifications _and_ a duration-exceeded alert, which is really the freshness SLA. And `run_as` a service principal, not a person.

**32. What is a repair run?**
Re-runs only the failed tasks and their downstream dependents, reusing the successful upstream results. It's the difference between a five-minute recovery and a full three-hour rerun, and it's the first thing to reach for after a mid-DAG failure.

**33. How do you deploy a job across environments?**
Databricks Asset Bundles: the job, its tasks, clusters, and schedule declared in `databricks.yml` with per-target overrides, deployed via `databricks bundle deploy -t prod`. Promotion changes only configuration — catalog name, cluster size, schedule — never code. Building jobs in the UI leaves them untracked and undiffable.

**34. Job triggers besides cron?**
File arrival (run when new files land in a volume or external location), table update, continuous (keep restarting for streaming), and manual/API for backfills and CI.

## E. Lakeflow Pipelines (35–43)

**35. What is a Lakeflow Spark Declarative Pipeline?**
The declarative counterpart to jobs: you declare datasets and how they're derived, and the platform infers the DAG from the references, orders execution, manages checkpoints and state, retries progressively, and enforces quality via expectations. Formerly Delta Live Tables.

**36. Streaming table vs materialized view.**
Streaming table: append-only, processes each source row once, checkpoint managed for you — for ingest and incremental silver. Materialized view: holds a query result refreshed (incrementally where possible) to reflect current state — for gold aggregates and dimension joins. If reprocessing everything each run would be wrong or too slow, you want a streaming table.

**37. How does a pipeline know the dependency order?**
From the references. `dlt.read("bronze_x")` or `FROM STREAM(bronze_x)` inside a table definition _is_ the dependency declaration — you never write the DAG. The pipeline runs flows in the correct order with maximum parallelism.

**38. What are expectations and what are the three actions?**
Row-level constraints with a defined violation action: `expect` (record the violation, keep the row), `expect_or_drop` (drop and record), `expect_or_fail` (fail the whole update). Fail for conditions meaning the pipeline is broken; drop for individual bad records.

**39. Where do you see expectation metrics?**
The pipeline event log — a queryable table of flow progress, quality metrics, lineage, and errors. I'd chart drop rate per expectation and alert on a change in that rate, since a jump usually means the source changed.

**40. What is AUTO CDC?**
The declarative CDC API (formerly `APPLY CHANGES INTO`): you give it the keys, a sequencing column, and optionally a delete condition, and it applies changes as SCD Type 1 or Type 2 — handling out-of-order events without hand-written watermarks. It replaces roughly forty lines of MERGE, including the null-key union trick SCD2 otherwise needs.

**41. Triggered vs continuous mode.**
Triggered processes what's available and stops — cheaper, and the default. Continuous stays running for low latency, at the cost of a 24/7 cluster. Only triggered pipelines can be a job task, since a continuous one is already always running.

**42. Development vs production mode.**
Development reuses the cluster without terminating it and skips retries, so iteration is fast. Production uses a fresh cluster with full retry behavior. Leaving a production pipeline in development mode is a real and common mistake.

**43. When would you _not_ use a pipeline?**
When you need imperative control flow (call an API, branch on an external condition), when you need tight control over compute and Spark configs, when portability off Databricks matters, or when the "pipeline" is really one scheduled query. Those are jobs.

## F. Unity Catalog, tables, volumes (44–47)

**44. Describe the Unity Catalog namespace.**
Metastore → catalog → schema → object (table, view, volume, function, model). Everything is `catalog.schema.object`. Permissions live above the workspace, so the same table has one permission model regardless of which workspace or engine reads it. Standard pattern is catalog per environment.

**45. Managed vs external table.**
Managed: UC owns the location and lifecycle, `DROP` deletes the data, and layout maintenance can be automatic. External: you specify the location, drop removes only metadata, and you own OPTIMIZE/VACUUM. Default to managed; use external when something outside Databricks writes those files.

**46. What is a volume and when do you use one instead of a table?**
Governed storage for non-tabular files, addressed as `/Volumes/catalog/schema/volume/...`, with the same UC grants and audit trail. Use it for landing zones, PDFs and images, JARs and init scripts, and exports. Use a table for anything you'll query with SQL. Volumes replaced DBFS, which had no real governance.

**47. How do row filters and column masks differ from a dynamic view?**
They attach to the table, so there's no way to route around them by querying the base table. With a dynamic view you also have to revoke base-table access, and eventually someone forgets. For new work, filters and masks are strictly better.

## G. AWS integration (48–50)

**48. How does Databricks get access to my S3 data?**
An AWS IAM role, wrapped in a UC **storage credential**, scoped to a path by an **external location**, which backs external tables and volumes. Grants are issued on the external location. Users never hold AWS credentials, so they can't bypass row filters by reading the bucket directly.

**49. What's the control plane / data plane split on AWS?**
The control plane — workspace UI, scheduler, UC metadata — runs in Databricks' account. With classic compute, the EC2 clusters run in your VPC and your data stays in your S3, which is what a security review wants to hear. Serverless compute runs in Databricks' account with separate network controls.

**50. How would you port an AWS Glue PySpark job to Databricks?**
Replace `GlueContext`/`DynamicFrame` with plain SparkSession and DataFrame (schema resolution becomes explicit casts plus `_rescued_data`), job bookmarks with Auto Loader or Structured Streaming checkpoints, Glue Catalog with Unity Catalog, `getResolvedOptions` with job parameters, Parquet output with Delta, and Glue job config with an Asset Bundle. I'd port one job end to end first — including CI and a reconciliation test diffing the output against the Glue output — before doing the rest, and decide the file layout deliberately at migration time rather than replicating the old partitioning.
