# "How Do You Design REST / GraphQL?" — Compact Interviewer Q&A

Format: interviewer asks the way they actually ask; answer is what you say out loud — 30–60 seconds each. Anchor system: your instrument enrichment platform (Aurora + Mongo doc broker + OpenSearch, GraphQL for UIs, REST for integrators).

---

## Part 1 — REST

**Q: Walk me through how you'd design a REST API for your instrument platform.**
I start from the domain, not URLs. A resource should line up with three things: a unit of consistency, an authorization boundary, and a cache granularity. So vendor data and human corrections are _separate_ resources — `/instruments/{id}` and `/instruments/{id}/corrections` — because they have different permissions, different lifetimes, and corrections need their own audit trail. Then the conventions are the easy part: plural nouns, methods as verbs, nesting max two levels, deeper children promoted to top level with a filter.

**Q: Where do parameters go — path, query, or body?**
Path is identity, query is optional read modifiers — filter, sort, page — body is the representation on writes. Two mechanisms decide the edge cases: caches key on URL plus `Vary`, so anything selecting the response variant must be in the URL; and URLs leak into logs and history, so PII never goes there. Those collide on complex search — sensitive or large criteria push me to `POST /search`, and I consciously give up cacheability for it.

**Q: Something isn't CRUD — like "correct a field." What then?**
An explicit action sub-resource: `POST /instruments/{id}/corrections`, returning a correction with its own id. Never a PATCH with magic fields — that smears the action into a diff, so you lose auditability, you can't grant the permission separately, and retry semantics get muddy. Modeling the action as a resource restores all three and gives me a natural place for an idempotency key.

**Q: How do you version?**
URI versioning — `/v1` — as the pragmatic default: visible, routable, cache-friendly. But my real position is that versioning is a failure mode; every live version multiplies test and support surface. So I invest in additive-only evolution: tolerant readers verified by consumer contract tests, per-consumer usage telemetry from day one, and expand-contract for breaking changes — add the new field, dual-serve, migrate consumers on telemetry, remove on a dated ticket. The telemetry, not the scheme, is what lets you delete code.

**Q: How do you handle errors?**
Small deliberate status-code set, because codes are a retry protocol: 4xx means deterministic, don't retry; 5xx and 429 mean back off and retry. The two miscodes that hurt most: 500 for validation — clients retry hopeless requests during incidents — and 200-with-error-body, which opts out of every monitor and retry policy in the path. Bodies are RFC 9457 Problem Details with a stable `type` code and the trace id echoed, so a client screenshot is greppable in Splunk. One `@RestControllerAdvice` enforces the taxonomy; anything falling to the catch-all 500 is a metric I alert on.

**Q: A client retries a POST and you charge twice. Prevent that.**
Idempotency key: client sends a UUID header; I claim it with an insert into a keys table — primary key arbitrates the race — in the _same transaction_ as the business write. Replay returns the stored response; same key with a different body is a 422; key still in-flight is 409 with Retry-After. The hinge is atomicity of claim and effect — check-then-act without the constraint leaves a window where two retries both execute. When effects span systems, that atomicity is gone, so I use an outbox and make downstream consumers dedupe.

**Q: What's your retry policy as a caller?**
Retry only idempotent or keyed operations, only on 429/5xx/timeouts, exponential backoff with full jitter — jitter exists because synchronized backoff produces waves that re-kill a recovering service. And one layer owns retries; client SDK times mesh times gateway each retrying 3× is 27 attempts. A timeout isn't a failure — the write may have committed — which is exactly why retry-on-timeout without a key is a data-corruption confession.

**Q: Caching?**
Bound the staleness and put it in the contract — "60 seconds" — or don't cache. TTL is the guarantee; event-driven eviction is an optimization, because eviction messages get lost. Version-in-key makes invalidation a pointer swap: correction bumps the row version, new cache key. ETags do double duty — `If-None-Match` for reads, `If-Match` for optimistic concurrency on writes. And on hot keys, request coalescing, or an expiry becomes six hundred concurrent rebuilds hitting the primary.

**Q: Two users edit the same record.**
Optimistic locking — version column, checked in the UPDATE's WHERE clause, surfaced over HTTP as ETag/If-Match. Mismatch is a 412: the client's view is stale, re-read and re-apply — that pushes the merge decision to the human who can make it, which for banker corrections is correct. Pessimistic locks only for short high-conflict sections, because blocked requests pin pool connections and that's a tail-latency cliff.

**Q: How do you paginate a large listing?**
Keyset: `WHERE (sort_key, id) > cursor ORDER BY sort_key, id LIMIT n+1` — the n-plus-first row is my hasNext. Offset makes Postgres read and discard the offset — depth-linear latency — and shifts under concurrent inserts. Keyset needs the id tiebreaker in both clauses or you skip rows at boundaries, and a mutable sort key means rows migrate across the cursor — fine for feeds, wrong for reconciliation exports, where I'd snapshot by immutable ingest id instead. Cursors are opaque base64 so the encoding can change.

**Q: Security?**
AuthN once at the edge — JWT via SSO, validated on every hop anyway. AuthZ in the service layer where object context exists, because the number-one API vulnerability is BOLA — authenticated caller, no check that _this_ caller may touch _this_ id. I centralized permission resolution so a new endpoint can't forget the check — correct by construction. DTOs per view, never entity serialization; append-only audit on mutations; no PII in URLs or logs.

## Part 2 — GraphQL

**Q: Now design the GraphQL layer. Where do you start?**
Same service layer, different contract philosophy. The schema is a promise that any legal field combination is cheap — so schema design is batching-topology design. Per field: resolves off the parent row, free; needs another entity, DataLoader, no exceptions in list positions; cost can't be bounded, I don't expose the field — `documents(first: Int!)` with a required capped limit, never a bare list. The cheapest guardrail is the field you refuse to add.

**Q: How do you decide nullability?**
It's an availability decision, not data modeling. Per spec, a null in a non-null position cascades to the nearest nullable ancestor — one failed non-null field inside a list can null the whole page. So: fields backed by other services stay nullable and degrade to holes; fields from my own row are non-null because absence there is a bug I want loud. That's blast-radius design in the type system.

**Q: Explain N+1 and your fix.**
Fifty instruments with `issuer` is one query plus fifty lookups, because execution resolves list items independently — structural, not a bug. DataLoader batches per request: resolvers return futures, the engine gathers keys per level, dispatches one `WHERE id IN`, caches per request. Three defeaters I watch: blocking on a loader future stalls dispatch — deadlock; a shared loader cache leaks data across users — scope is per-request, always; and if the batch function lazy-loads per row, N+1 is reborn one layer down — so an integration test asserts query count ≤ 2, and un-batching fails CI instead of paging on-call.

**Q: Doesn't GraphQL just have worse performance than REST here?**
GraphQL relocates N+1, it doesn't create it. REST's version is the chatty client — visible in access logs, paid in round trips. GraphQL moves it server-side behind one request — invisible in logs, paid in DB connections. Strictly better if you batch; unbatched, you've hidden a fan-out where ops tooling can't see it.

**Q: Error handling — built-in or custom?**
Both, split by kind. Genuine faults go through the built-in `errors` array via an exception resolver — stable code in extensions, trace id, default-deny so internal messages never leak. Expected business outcomes go in the schema as union results — `CorrectInstrumentResult = Success | FieldLocked | StaleVersion` — because unions are introspectable, codegen forces clients to handle each case, and extending one is additive. And since everything is HTTP 200, I emit my own error-rate metric from the errors array — otherwise dashboards say healthy while every response carries failures.

**Q: Pagination?**
Relay connections — edges, cursors, pageInfo — keyset underneath, same n+1-row trick for hasNext. The envelope earns its ceremony: per-edge resume, and clients and caches handle paging generically. `totalCount` is the trap — a count can cost more than the page — so it's opt-in and approximate. `first` is required in schema and clamped in the resolver, because schema can't express a maximum.

**Q: How do you protect against expensive queries?**
Ordered by leverage: schema guardrails first — capped `first`, closed filter vocabulary where every filter field is a committed index — static and unbypassable. Then depth limits and a complexity budget as a fuse, not a firewall — multipliers are estimates, and naive depth checks miss alias abuse: fifty aliased copies of the same query inside legal depth. For a fixed consumer set, a persisted-query allowlist is the only complete defense. Detection alongside: per-operation-name latency in Datadog, so a regression is a named trend.

**Q: Caching?**
Where REST caches on URL for free, GraphQL makes me choose layers. Highest ROI: entity cache under the resolvers, version-keyed, shared with REST, shape-agnostic. DataLoader gives per-request dedupe free and correct. Whole-response caching only via persisted queries over GET — pointless on an authed internal API where authorization fragments the cache. Governing rule: field-level authz breaks response caching — cache below the authz boundary, never above.

**Q: Can clients retry GraphQL?**
Queries: semantically yes, but they're POSTs, so it's client-library logic on transport errors only — never on in-body errors, those are deterministic. Mutations need idempotency keys, same as REST POST. The subtle one: the spec runs top-level mutation fields _serially_, so a multi-mutation document that dies midway has committed a prefix — whole-document retry re-runs committed work. Convention: one mutation per document.

**Q: GraphQL vs REST — when each?**
Organizational variables, not taste. GraphQL moves integration cost from building bespoke endpoints into schema governance — worth it with many consumer teams, and only with the discipline to run governance. The price stated plainly: you replace commodity HTTP infrastructure — caching, retries, monitoring semantics — with application-layer equivalents you now own. One backend, one consumer, CRUD shapes: REST, full stop. We ran both off one service layer — GraphQL for product UIs, REST for integrators.

**Q: What's a supergraph, and why?**
One composed schema over subgraphs each team owns and deploys; a router plans queries across them, joining entities declared with `@key`. It replaced stitching, which was manual gateway merging. Two things worth knowing: the router's query plan makes cross-subgraph joins the new N+1 — entity resolvers must batch representations, DataLoader logic one layer up; and the real product is governance — composition checks in CI reject a subgraph change that breaks the graph before deploy. Worth the machinery at roughly three-plus domain teams; below that, monolithic schema, and I'd say so.

_Drill order: N+1, nullability, expensive-query defense, idempotency, supergraph — those five carry the most cross-examination weight for Vanguard._
