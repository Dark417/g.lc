## 0. Your Questions, Answered

**Q0.1 — "Does Spark have a cloud?"**
No. Spark is open-source software — an engine, like PostgreSQL is an engine. It runs wherever you give it machines: your laptop (local mode), a cluster you operate (standalone/YARN/Kubernetes), or someone's managed platform. **Databricks is a company** (founded by Spark's creators) that sells hosted, optimized Spark plus the platform around it (Delta, UC, Photon, notebooks). EMR, Glue, and Dataproc are AWS/Google's ways of running the same engine. So: Spark has no cloud; clouds have Spark.

**Q0.2 — "On local, Spark uses my RAM, the JVM underneath, and mimics splitting data and workers — is the number of nodes/chunks configurable?"**
Almost exactly right, with one precision: in local mode (`local[*]`) there are **no separate worker nodes at all** — driver and executor live inside **one JVM process** on your machine, and "executor slots" are just threads. The data-splitting is real, not mimicked: your DataFrame is genuinely cut into partitions and processed in parallel by those threads, running the same code paths as a cluster. Configurable locally: **parallelism** (`local[4]` = 4 threads), **chunk count** (`spark.sql.shuffle.partitions`, or `repartition(n)`), and JVM memory (`spark.driver.memory`). _Not_ configurable locally: node count — there's only one process. (You _can_ run a multi-JVM standalone cluster or Docker cluster on one laptop to truly mimic nodes, but it's rarely worth it — see Q0.4.)

**Q0.3 — "Are nodes managed, or do I never touch that level?"**
You configure nodes **declaratively, never operationally.** On Databricks you write the cluster spec — instance type, min/max workers, autoscaling, DBR version, Photon on/off — and Databricks provisions the VMs, installs Spark, wires networking, replaces dead nodes. You never SSH into a worker or patch an OS. Glue abstracts even harder: you pick worker _type and count_ (G.1X/G.2X, number of workers) and see nothing below that. EMR is the option where you _do_ touch more (your cluster, your ops) — which is exactly why managed platforms won. So the DE's altitude is: **cluster spec = yes, machines = no.**

**Q0.4 — "Can local mode mimic cluster behavior?"**
Functionally yes, physically no. Same API, same Catalyst plans, same partition logic — so **logic and unit tests transfer perfectly**, and this is why local testing is standard practice. What local mode canNOT reproduce: real **network shuffle** (local shuffle is memory/disk on one box — cluster shuffle cost is invisible locally), executor-level OOM behavior, skew pain at scale, S3 I/O characteristics, and Databricks-only pieces (Photon, UC permissions, Auto Loader against cloud storage). Practical rule: **correctness locally, performance on the cluster.** A job that's fast locally can crawl on real data — never extrapolate timing.

**Q0.5 — "When developing, do I have to push to the cloud to use the 'actual JVM'?"**
The local JVM _is_ an actual JVM running actual Spark — `pip install pyspark` (Java required underneath) gives you the real engine, small. Your four development options, in the order you'll meet them:

1. **Databricks notebook on a cluster** — code runs remotely from keystroke one; the default for exploration.
2. **Local PySpark** — real Spark in your venv; ideal for unit tests (pytest + a local SparkSession fixture) and logic development on sample data.
3. **Databricks Connect** — the hybrid: you write/run code in your local IDE, but it's compiled to a plan and shipped (via Spark Connect/gRPC) to a remote Databricks cluster for execution. Local editor ergonomics, cluster-scale execution, real UC tables.
4. **Deploy** — Asset Bundles / Terraform / CI pushing jobs to Workflows for production.
   Standard team flow: logic + tests local, integration on a dev cluster (notebook or Connect), production via CI. Saying this flow in the interview is itself a signal you've shipped.

**Q0.6 — "Lambda vs Glue vs Databricks — what sizes are we talking about?"**
Decide by _data-per-run_ and _what else you need_, not brand:
| Runtime | Sweet spot per run | Character | Wrong when |
|---|---|---|---|
| Lambda | KB → a few GB, one process, <15 min | Event glue: trigger jobs, per-object validation, notifications | Data needs distribution, or runtime >15 min |
| Glue | GB → tens of TB, batch | Serverless Spark ETL, AWS-native, bookmarks, per-DPU billing | Interactive dev, tight iteration, non-AWS governance needs |
| Databricks | GB → PB, batch + streaming + interactive | The platform: Delta/UC/Photon/notebooks/DLT | Trivial single-file tasks (overkill), pure event glue |
Boundary sentence for interviews: "single-process data → single-process tools (pandas/DuckDB in Lambda); distributed data → distributed engines; and I choose Glue vs Databricks by ecosystem and workflow, since the engine is the same Spark."

**Q0.7 — "What defines streaming? When Databricks 'uses streams,' is it consuming a stream, splitting it into chunks, processing chunk by chunk?"**
Your description is essentially correct — and the precise vocabulary upgrade is worth points. **Batch** = bounded input: read it all, process, done. **Streaming** = unbounded input: data keeps arriving forever, so the job processes _increments_ and must remember its position (**checkpoint**). Spark Structured Streaming is specifically **micro-batch**: it models the stream as an infinitely growing table, and on each **trigger** it takes "everything new since my checkpoint" as one micro-batch, processes it with the normal batch engine, commits results + new offsets atomically, repeats. So yes: chunks processed one by one — the chunks are micro-batches (typically seconds of data or a set of new files), _not_ record-by-record (that's Flink's model, or Spark's niche continuous mode). This is exactly why `trigger(availableNow=True)` can exist: "take all chunks currently available, process, stop" — streaming bookkeeping on a batch schedule.

**Q0.8 — "PySpark translates into Java and rests on the JVM — is PySpark secretly Java?"**
Close: Spark is written in **Scala** (a JVM language), and your PySpark code doesn't get _translated_ — it gets _relayed_. The `pyspark` library is a thin Python client: each DataFrame call crosses the **Py4J** bridge as an instruction to the Scala/JVM objects on the driver, which build the plan. Your data almost never enters Python — it lives and moves entirely in JVM executors. The one exception is a Python UDF, which forces rows out to Python worker processes and back (the §2.7 cost). This is why PySpark ≈ Scala Spark in speed for pure DataFrame code: the Python layer is instructions, not execution.

**Q0.9 — "When a task fails, who reruns it? Who's responsible at each level, and where is it configured?"**
Answered fully in §1.3 — the short version: **Spark itself retries tasks** (automatic, `spark.task.maxFailures`=4) and stages; **Databricks Workflows retries whole jobs/tasks** per the retry policy _you_ configure; **you** click Repair Run for anything that exhausted retries. Three nested safety nets, three different owners.

## 1. Layer Boundaries — the full stack and what you configure at each level

### 1.1 The stack, bottom to top

```
L6  YOUR CODE          PySpark DataFrame calls, SQL            you write
L5  PYTHON CLIENT      pyspark lib, Py4J bridge → JVM          invisible
L4  SPARK ENGINE       driver JVM: Catalyst plan → stages/tasks
                       executor JVMs: run tasks on partitions   Scala inside
L3  CLUSTER            nodes (VMs), autoscaling, Photon, DBR    you spec, platform runs
L2  PLATFORM           Databricks control plane / Glue service  vendor-run
L1  CLOUD              EC2/S3/VPC in the bank's AWS account     bank's infra teams
```

### 1.2 What is configurable at each level (the answer to "number of clusters / nodes / chunks")

| Level                  | Knob                                                                                                                              | Where set                                    | Typical owner      |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- | ------------------ |
| Code                   | **Partition count ("chunks")**: `repartition(n)`, `coalesce(n)`; partition columns on write; caching; broadcast hints             | Your code                                    | You                |
| Spark conf             | `spark.sql.shuffle.partitions` (default 200; AQE coalesces at runtime), AQE flags, `autoBroadcastJoinThreshold`, task retry count | Cluster spark conf / `spark.conf.set`        | You                |
| Cluster                | **Number of nodes**: min/max workers + autoscaling; instance type (memory-vs-compute); Photon; DBR version; spot vs on-demand     | Cluster/job-cluster spec (UI/JSON/Terraform) | You, within policy |
| **Number of clusters** | One per job task (job clusters, ephemeral); warehouses scale **cluster count** for concurrency (min/max clusters)                 | Job spec / warehouse config                  | You                |
| Orchestration          | Job **retries**, timeout, `max_concurrent_runs`, schedule/trigger, alerts                                                         | Workflows job settings                       | You                |
| Platform               | Cluster **policies** (allowed sizes/types), pools, UC grants                                                                      | Admin console / Terraform                    | Platform team      |
| Cloud                  | VPCs, IAM, instance availability                                                                                                  | Bank infra                                   | Not you            |

The interview-ready compression: **"I control chunks in code, parallelism in Spark conf, nodes in the cluster spec, retries in the job spec — and the platform team fences what sizes I'm allowed to pick via policies."**

### 1.3 Failure & rerun responsibility — who retries what

| Failure                                     | Who retries                    | Mechanism                                                                                  | Your config                                   |
| ------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------ | --------------------------------------------- |
| One task fails (bad executor, transient S3) | **Spark scheduler**, automatic | Re-run task on another executor; possible because lineage/plan can recompute any partition | `spark.task.maxFailures` (4) — rarely touched |
| Straggler task                              | Spark (optional)               | Speculative execution runs a duplicate, first wins                                         | `spark.speculation`                           |
| Executor/node dies                          | Spark + platform               | Databricks replaces the node; Spark reschedules its tasks                                  | none — this is what "managed" buys            |
| Whole stage fails repeatedly                | Spark                          | Stage retry, then job fails                                                                | —                                             |
| **Job run fails**                           | **Databricks Workflows**       | Retry policy: N retries, backoff, timeout                                                  | You set per task — the config that matters    |
| Retries exhausted / data bug                | **You**                        | Fix cause → **Repair Run** (only failed tasks re-run)                                      | Idempotent writes make this safe              |

Why idempotency is non-negotiable drops out of this table: retries at three levels are _normal operation_, so every write must tolerate re-execution (MERGE / replaceWhere — §4).

## 2. Core Concepts, One Level Deeper

### 2.1 Lazy evaluation — deeper

Every transformation appends to an **unresolved logical plan** — literally a tree of operations, no data touched. At an action, the plan goes through: analysis (resolve names/types against the catalog) → optimization (Catalyst rewrites) → physical planning (pick join algorithms, scans) → execution. Three practical consequences beyond "errors surface late": (1) **plan-level dedup doesn't exist across actions** — calling `count()` then `write()` recomputes everything twice unless you cache; each action is a fresh job. (2) You can inspect the plan before paying for it: `df.explain(True)` shows all four plan stages. (3) Referencing a DataFrame variable many times is free — it's a plan object, not data; the cost model lives entirely at actions.

### 2.2 Driver & executors — deeper

**Driver:** runs your Python + the JVM SparkSession; holds the plan, the DAG scheduler (splits into stages), the task scheduler (assigns tasks to executor slots), and tracks shuffle/block metadata. Driver death = application death — no retry above it (that's the Workflows layer's job). Driver-side dangers: `collect()`/`toPandas()` (pull all data into one process), very many partitions (scheduler overhead), huge broadcast variables.
**Executors:** JVM processes with N **cores** (task slots) and a shared memory pool split between execution memory (shuffles, joins, sorts) and storage memory (cache) — the pool is unified and they steal from each other, which is why heavy shuffles evict caches. Each task processes one partition; total parallelism = executors × cores. Sizing intuition worth saying: fewer fat executors = better for broadcast reuse; more slim executors = better isolation; Databricks defaults are sane and you tune by _node type/count_ rather than executor internals.

### 2.3 Catalyst — deeper

A rule-based + cost-based plan rewriter operating on the logical plan tree. The rewrites that matter in interviews, each one sentence: **predicate pushdown** — filters travel down to the scan so Parquet/Delta skip row groups/files (this is why filtering early _in code order_ barely matters but filtering on native columns vs UDF output matters enormously); **column pruning** — only referenced columns are read (columnar formats make this a huge I/O win; `select` early is still good hygiene); **constant folding / null propagation** — trivia tier; **join reordering & strategy selection** — with table statistics, chooses broadcast vs sort-merge and orders multi-joins (why `ANALYZE TABLE ... COMPUTE STATISTICS` and Delta's auto-collected stats matter: stale stats → wrong strategy → your Q "why didn't it broadcast"). Boundary: Catalyst optimizes _what it can see_ — UDFs are opaque black boxes that block reasoning through them.

### 2.4 AQE — deeper

Catalyst plans with _estimates_; AQE corrects with _facts_, re-planning at each stage boundary using the just-completed shuffle's real statistics. Its three moves: (1) **coalesce shuffle partitions** — 200 defaults become however many the data justifies, killing the tiny-task overhead problem that used to require hand-tuning `shuffle.partitions`; (2) **runtime join switching** — a side that turned out <threshold after filters flips sort-merge → broadcast mid-flight; (3) **skew-join splitting** — a shuffle partition detected as huge (default heuristics: ~5× median and above a size floor) is split into sub-partitions, and the other side's matching partition is duplicated to each — automatic salting for _joins_. What AQE does **not** fix: skewed **aggregations** (manual salting still yours, §4.13), skew from a fundamentally hot key at the source, or a bad broadcast estimate that OOMs before stats exist. Interview framing: "AQE moved a class of manual tunings into the engine; my job is knowing which class is left."

### 2.5 DataFrame API — deeper

A DataFrame = `Dataset[Row]` on the JVM: a plan + a schema, not data. Schema-awareness is the entire advantage over RDDs: knowing types and columns is what enables pruning, pushdown, columnar execution, Photon, and whole-stage codegen (Spark compiles operator chains into single JVM functions — why chained `withColumn`s don't cost N passes). The Python objects (`DataFrame`, `Column`) are handles; expressions like `F.col("a") + 1` build JVM expression trees — which is why arbitrary Python (`if row.a > 1`) can't appear inside them and `F.when` exists. One more depth click: `df.rdd` exits to the legacy layer and forfeits all optimization — a smell if you see it in review.

### 2.6 Shuffle — deeper

Mechanics: each **map-side** task partitions its output rows by key-hash into per-reducer buckets, sorts/spills them to local disk as shuffle files; then each **reduce-side** task fetches its bucket from _every_ map task over the network and merges. Cost = serialize + disk write + network + deserialize, all × data volume — and it's also a _barrier_: the reduce stage can't start until the map stage finishes (why one straggler delays everything downstream — the skew mechanism). Memory pressure: build-side hash tables and sorts live in execution memory; overflow spills to disk (slow) or OOMs (dead). Everything in performance work reduces to this section: broadcast joins exist to delete a shuffle; AQE exists to right-size and rebalance it; salting exists to un-skew it; map-side partial aggregation exists to shrink it; `repartition` _is_ one, on purpose.

### 2.7 UDF — deeper

Row UDF path: JVM serializes row batches → sends to a Python worker process on the executor → your function runs per row → results serialized back. Costs: (a) serialization both ways, (b) Python-side execution speed, (c) **optimizer opacity** — Catalyst can't push a filter through your UDF or prune inside it, and Photon falls back off for that operator. **pandas UDFs** fix (a) and (b) substantially — Arrow columnar transfer + vectorized pandas execution — but not (c): still a black box in the plan. That's the full mental model behind the ladder built-ins > pandas UDF > row UDF, and behind the review rule "filter on native columns _before_ the UDF, so pushdown still protects the scan." Bonus depth for L4 flavor: higher-order functions (`F.transform`, `F.filter`, `F.aggregate` on array columns) cover many would-be UDFs while staying inside Catalyst.

## 3. SQL ↔ PySpark (unchanged core — keep drilling)

Same Catalyst plans, same speed; choice is authoring, not performance. `createOrReplaceTempView` + `spark.sql()` ↔ DataFrame chains interchangeably; `selectExpr` / `F.expr` for inline SQL. SQL for readable set logic, Python for parameterization/loops/tests. Bilingual pattern table lives in Doc 1/Doc 2 §10 — if you blank in one language mid-interview, translate from the other _out loud_; the translation reads as fluency.

## 4. Features, Classes, Functions — expanded to interview scope

Coverage check against real DE loops: entry point · IO · expressions · aggregation · joins · windows · UDFs · JSON/arrays · dedup patterns · partitions/writes · cache · explain · Delta ops · streaming · testing. That's the interview surface; anything beyond (RDD API, MLlib, GraphX) is out of DE scope and fine to say so.

**4.1 SparkSession** — entry point; on Databricks pre-built as `spark`; `spark.read.table("cat.sch.t")` for UC, `spark.conf.set` for session tuning.

**4.2 Reader/Writer**

```python
df = (spark.read.format("json").schema(s).load(path))        # explicit schema in prod
(out.write.format("delta").mode("append").partitionBy("ingest_date").saveAsTable(t))
(day.write.format("delta").mode("overwrite")
    .option("replaceWhere", "ingest_date='2026-08-08'").saveAsTable(t))   # idempotent backfill
```

Solves: schema drift (explicit > inference) and safe re-runs. `mode` semantics — append / overwrite / errorifexists / ignore — know cold.

**4.3 Columns & F.\*** — `withColumn`, `when/otherwise`, `cast` (decimal for money), `coalesce`, date functions, `regexp_extract`, `concat_ws`, `trim/upper`. Staying in `F.*` = staying optimized.

**4.4 Semi-structured: from_json / explode — the vendor-feed toolkit (previously missing, interview-likely)**

```python
schema = "STRUCT<instrument_id: STRING, terms: ARRAY<STRUCT<name: STRING, value: STRING>>>"
parsed = raw.withColumn("j", F.from_json("body", schema))
flat = (parsed.select("file_name", "j.instrument_id", F.explode_outer("j.terms").alias("term"))
              .select("file_name", "instrument_id", "term.name", "term.value"))
```

Solves: your actual JPMC shape — vendor JSON with nested arrays → normalized rows. Defeaters: `explode` drops rows with null/empty arrays (use `explode_outer`); malformed JSON → nulls, so pair with a `_corrupt`/rescued pattern into quarantine, never silent drops. Also know dot-path access (`j.instrument_id`) and `schema_of_json` for exploration.

**4.5 GroupedData** — `groupBy().agg()`, conditional aggregation (`F.sum(F.when(...))` = SQL CASE pivot), `approx_count_distinct` tradeoff, `pivot()` exists.

**4.6 Joins** — how-args incl. `left_semi`/`left_anti`; `F.broadcast`; fan-out discipline (cardinality first, dedupe N-side, count before/after); key-type mismatch silently kills pruning.

**4.7 Window** — latest-per-key (THE pattern), lag/lead, running/moving frames, explicit `rowsBetween` over default frames; orderBy-without-partitionBy = parallelism collapse.

**4.8 Dedup family — the semantics question interviewers love**
`distinct()` whole-row · `dropDuplicates(cols)` **arbitrary survivor** (nondeterministic run to run — reproducibility bug) · window rn=1 = _deterministic chosen_ survivor. If asked to "dedupe," ask which semantics — that question is the senior move.

**4.9 UDF / pandas UDF** — §2.7 ladder; higher-order array functions as the UDF-avoider.

**4.10 repartition / coalesce / partitionBy** — chunks in code; write-time file-count control; `coalesce(1)` straggler warning; align `repartition("col")` with `partitionBy("col")`.

**4.11 cache/persist** — multi-action reuse only; unified memory steals from shuffle; measure first; never for correctness.

**4.12 explain / Spark UI / Query Profile** — `PushedFilters`, `PartitionFilters`, join node type, count `Exchange`s; UI: max-vs-median task = skew; input size trend = growth.

**4.13 Salting (manual skew fix for aggregations)**

```python
salted = df.withColumn("salt", (F.rand()*8).cast("int"))
final = (salted.groupBy("company","salt").agg(F.sum("revenue").alias("s"))
               .groupBy("company").agg(F.sum("s").alias("total_rev")))
```

Solves: the hot-key aggregation AQE doesn't fix.

**4.14 DeltaTable** — `merge` with pruning predicate in ON; `restoreToVersion`; `versionAsOf` reads; `DESCRIBE HISTORY` via SQL. The idempotency answer in code.

**4.15 Streaming** — `cloudFiles` source, checkpoint = identity, `availableNow` = incremental-on-a-schedule, `foreachBatch` for MERGE sinks (idempotent per `batch_id` — batches replay), watermark only when event-time aggregating.

**4.16 Testing (one paragraph that impresses)** — pytest fixture building a `local[2]` SparkSession; transformations as pure functions `def dedupe(df): ...` tested on tiny hand-built DataFrames with `assertDataFrameEqual` (pyspark.testing); integration on a dev cluster. Ties §0.5 together and almost nobody at L3 says it — cheap differentiation.

## 5. Conceptual & Debugging Q&A (delta from v2 — new/upgraded only)

**Q. Where exactly does my Python code run vs my data? (8)** Code: driver-side Python builds plans over Py4J; data: JVM executors end-to-end; the two meet only at UDFs (Python workers on executors) and at `collect()` (data pulled to driver). Two-sentence answer, big signal.

**Q. What can you configure at each level of the stack? (8)** The §1.2 compression: chunks in code, parallelism in Spark conf, nodes in cluster spec, retries in job spec, fenced by platform policies.

**Q. A task failed at 2am but the job succeeded — explain. (7)** Spark's task retry absorbed it (maxFailures=4, rescheduled on another executor); invisible by design; only exhausted retries escalate to job failure and the Workflows retry policy. Bonus: speculative execution for stragglers.

**Q. Why does the same code run fine locally and OOM on the cluster? (7)** Local ran a sample in one JVM with no real network shuffle; cluster met full volume, real shuffle memory pressure, and skew. Correctness transfers, performance doesn't; diagnose on the cluster's own UI, don't extrapolate.

**Q. df.count() then df.write() — how many times is the data read? (7)** Twice — each action is an independent job over the plan; cache if the reuse is worth memory, or restructure to a single write and get counts from Delta history/metrics.

## 6. Design Questions (new)

**D1. Design the daily vendor-filings pipeline end to end. (10)** Frame in deciding variables then commit: arrival = hourly S3 drops → Auto Loader `availableNow` on a scheduled job (streaming bookkeeping, batch cost); bronze append-only + `_rescued_data` + quarantine expectations; silver latest-per-key MERGE with pruning predicate, reconciliation counts vs bronze; gold stated-grain aggregates; staleness + drop-rate alerts; backfill = same code + `replaceWhere`. Close with what changes the design: tighter SLA → continuous trigger; CDC source → CDF propagation.

**D2. The filings table will be queried by company and date at 5TB — layout? (9)** Variables: predicates (date always → partition by month or cluster; company high-cardinality → liquid cluster, never partition), write pattern (streaming appends → optimized writes + scheduled OPTIMIZE), retention (month-drop lifecycle favors date partitioning). Default: month partition + liquid cluster by company; say what evidence (query profile files-pruned ratio) would revise it.

**D3. Same logic must serve batch backfill AND incremental daily — one codebase, how? (8)** Transformations as pure DataFrame functions, parameterized source (`readStream` cloudFiles vs `read` with date range) feeding the same functions; sinks idempotent (MERGE/replaceWhere) so both paths re-run safely; tests hit the pure functions. This is the "no hand-edited backfill notebook" principle as architecture.

**D4. You inherit a 40-step notebook pipeline, no tests, runs 6h — first two weeks? (8)** Observe before touching: UI/profile to find the 2–3 dominating stages (usually one bad join or UDF); add reconciliation checks around the whole thing (row counts/sums) as a behavioral safety net; then refactor the hot spots into tested functions; only then optimize (broadcast/layout/AQE checks). Sequencing — measure, guard, refactor, tune — is the answer they're grading.

**D5. When would you argue AGAINST Spark? (7)** Data fits one machine (pandas/DuckDB — faster, simpler, cheaper); sub-second serving (that's Aurora/OLTP); true per-event latency (Flink/continuous); tiny event glue (Lambda). Knowing the tool's negative space is an L4 flash — use your reconciliation-agent "should it even have been multi-agent" instinct here; same muscle.
