## 1. Why Distributed Systems Exist

### 1.1 The single-machine walls

```
        ┌──────────── one big server ────────────┐
 load ─▶│ CPU wall │ RAM wall │ disk/NIC wall │  │──▶ p99 explodes
        └──────────┴──────────┴────────────────┘
              ▲ also: one power supply = one blast radius
```

- The naive design is always the same: one service, one database, synchronous calls. You must be able to say _what breaks first and at what number_.
  → **Throughput wall.** A well-tuned Postgres on a big box handles order of magnitude 10k–50k simple writes/sec (order of magnitude — workload-dependent). A TikTok-scale feed does millions of events/sec. No vertical scale closes a 100× gap.
  → **Storage wall.** Single-node disks top out at tens of TB practical; petabyte datasets _must_ be split.
  → **Latency wall (geography).** Speed of light: ~70–80 ms RTT US-east ↔ Europe, ~150+ ms US ↔ Asia (order of magnitude, physics-bound). No server placement fixes this for a global user base — you need servers _near_ users.
  → **Availability wall.** One machine ≈ 99.9% at best (hardware, kernel, deploys). Business wants 99.95–99.99%. Only redundancy (more machines) gets you there.
- 🗣 "We distribute for one of four reasons: throughput past one box, data past one disk, latency past one region, or availability past one failure. Name which one _this_ system needs before adding any distributed machinery."

### 1.2 What distribution buys and what it costs

```
  BUY: scale-out, fault-tolerance, locality
  PAY: partial failure, no shared clock, unreliable network, concurrency everywhere
```

- Distribution is a trade: you exchange the _simple failure model_ of one machine (it's up or it's down) for horizontal scale — and inherit a much nastier failure model.
  → **Partial failure.** In a monolith, a crash kills everything consistently. Distributed: node A committed, node B didn't, and _neither knows the other's state_. Every distributed problem is downstream of this.
  → **No global clock.** Two nodes cannot agree what "now" is; NTP skew is order of ms, can spike to seconds. Anything relying on wall-clock ordering across nodes (timestamp-ordered IDs, "last write wins") has a defeater built in.
  → **Unreliable network.** Messages are lost, delayed, duplicated, reordered. Consequence: _you cannot distinguish "slow" from "dead"_ — this single fact is why timeouts, retries, idempotency, and leases exist.
  → **The 8 fallacies** (Deutsch/Gosling, canonical): network is reliable, latency is zero, bandwidth is infinite, network is secure, topology doesn't change, one admin, transport cost is zero, network is homogeneous. Every fallacy maps to a mechanism that exists to compensate for it.
- The interview framing: every distributed _primitive_ (partition, replica, queue, cache, lease, consensus) exists to solve exactly one of these problems. Justify each primitive with the number/failure that forced it — "distributed by default" is the #1 graded anti-pattern.

## 2. What Is Actually "Distributed" — A Taxonomy

### 2.1 The three layers: compute, state, coordination

```
  [ Coordination ]  leader election, locks, membership, config   ← hardest
  [ State        ]  data: shards, replicas, caches, queues       ← hard
  [ Compute      ]  stateless services behind a LB               ← easy
```

- **Distributed compute** is nearly free: stateless services behind a load balancer scale by adding instances. If your service holds no state, "distributed" costs you almost nothing.
  → Defeater: it's only free _because_ the hard state was pushed somewhere else (DB, cache, queue). "Stateless" means "someone else's state problem."
- **Distributed state** is where the real questions live: which node owns which data (sharding), how many copies (replication), who is allowed to write (leadership), what readers see (consistency).
- **Distributed coordination** is the hardest and should be _minimized_: leader election, distributed locks, membership. Prefer a lease over consensus; prefer a single well-partitioned owner over a lock; use off-the-shelf (ZooKeeper, etcd, DynamoDB conditional writes) — never build consensus in an interview or in prod.
  → 🗣 "My default is to _avoid_ coordination by design — partition so each key has exactly one owner — and only reach for locks/leases when ownership genuinely can't be partitioned."

### 2.2 What must be globally unique vs. what can be local

| Thing                          | Uniqueness scope                  | Enforced by                                                  | Defeater / gotcha                                                         |
| ------------------------------ | --------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Entity ID (user, order, video) | Global, forever                   | ID generator (§4)                                            | Clock skew, machine-ID collisions                                         |
| Username / email               | Global                            | Unique index on the _owning_ shard (route by the key itself) | Cross-shard uniqueness needs a lookup service or global index — extra hop |
| Idempotency key                | Global per operation, bounded TTL | Unique constraint + dedup store                              | TTL shorter than max retry window ⇒ duplicates return                     |
| Leader (per partition)         | One at a time                     | Lease / election (etcd, ZK, DynamoDB lock)                   | Old leader with expired lease keeps writing ⇒ need fencing tokens         |
| Sequence / offset              | Per partition (not global!)       | The partition's log                                          | People assume global order; Kafka orders _within_ a partition only        |
| Cache entries, derived views   | None — eventually consistent      | TTL + invalidation                                           | Serving stale data is the accepted cost                                   |

- The interview move: when the interviewer says "we need a unique X," immediately ask **scope** (global vs. per-partition vs. per-user) and **who enforces it** (generator at write time vs. constraint at commit time). Scope decides cost: per-partition uniqueness is free; global uniqueness requires either routing-by-key or coordination.

## 3. Geo-Routing: The TikTok-Style Question

### 3.1 How a request finds its cluster

```
 user ──▶ DNS (GeoDNS)          ──▶ nearest region's VIP
      ──▶ Anycast IP (optional) ──▶ nearest POP, BGP-routed
      ──▶ L7 LB / API gateway   ──▶ service cluster [hot path]
      ──▶ cell/shard router     ──▶ the cell owning this user
```

1. **GeoDNS** — resolver's location maps hostname → nearest region's IP. Coarse (resolver ≠ user), cached (TTL delays failover), but simple and universal.
2. **Anycast** — same IP announced from many POPs; BGP delivers to topologically nearest. Sub-DNS-TTL failover; used by CDNs/edges (Cloudflare, Google front ends). Defeater: BGP "nearest" is hops, not latency, and route flaps can move long-lived connections.
3. **L7 gateway** — TLS termination, authn, rate limiting, then routes by _application_ identity (user ID, tenant), not IP.
4. **Cell router** — the important design step: consistent mapping `user_id → home cell/region` looked up from a small, heavily cached directory (control plane).

- Key distinction to say out loud: **IP gets you to the nearest _edge_; user ID gets you to the _owning_ cell.** Those are different routing decisions with different mechanisms.
  → 🗣 "Route by geography for latency, route by identity for state. The edge is chosen by IP/anycast; the home cell is chosen by a user→cell directory."

### 3.2 User homing and data residency

- Each user gets a **home region** (assigned at signup by geo, or by law — e.g. EU data residency). Writes go to the home region [hot path]; other regions hold async read replicas [async].
  → Travelling user: reads served locally from a replica (stale by replication lag, order of 100 ms–seconds cross-region); writes forwarded to home region (+1 RTT). State the tradeoff — it's the standard answer.
  → Rehoming (user moves): background migration + dual-read window — a mini data migration, mention it as extended scope.
- **Cell architecture** (canonical pattern, not a specific incident): partition _everything_ — compute + state — into self-contained cells of, say, 1–5 M users each. A bad deploy or hot key takes out one cell, not the platform. This is the blast-radius answer Amazon loves.

## 4. Global Unique IDs

### 4.1 The design space

```
  UUIDv4 ── no coordination, random, 128-bit, unsortable
  UUIDv7 ── no coordination, time-ordered, 128-bit (RFC 9562, 2024)
  Snowflake ── 64-bit, time-ordered, needs machine-ID assignment
  DB auto-inc + step ── simple, DB is SPOF/bottleneck
  Ticket server ── central counter, batched (Flickr pattern)
```

| Option                            | Buys you                                                        | Costs you                                                                                   | Choose when                                                                           |
| --------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **UUIDv4**                        | Zero coordination, generate anywhere (client!)                  | 128-bit; random ⇒ B-tree index pages splatter (write amplification in MySQL/PG); unsortable | Correlation IDs, idempotency keys, low-write-rate entities                            |
| **UUIDv7**                        | Zero coordination + time-ordered (index-friendly)               | 128-bit; timestamp leaks creation time                                                      | Modern default when 128 bits are acceptable (as of RFC 9562, 2024)                    |
| **Snowflake**                     | 64-bit (fits `BIGINT`), time-ordered, ~4M IDs/sec/node capacity | Needs unique machine IDs (coordination at _deploy_ time); clock-skew handling               | High-write-rate entities needing compact sortable IDs — the standard interview answer |
| **DB sequence / auto-inc + step** | Trivial, strictly monotonic per DB                              | Central DB is the bottleneck & SPOF; step/offset scheme is rigid                            | Single-region, moderate write rate                                                    |
| **Ticket server**                 | Central but batched (grab ranges of 1000)                       | Still central-ish; IDs leak count/business volume                                           | Legacy MySQL shops (Flickr's published design)                                        |

- Deciding variables, in order: **(1) must IDs be sortable by time?** (feeds, pagination by ID ⇒ yes) **(2) size budget** (64 vs 128 bit — index size, URL length) **(3) can you assign machine IDs?** (K8s: use a coordination store or StatefulSet ordinal).
- Sortability defeater: time-ordered IDs leak information (creation time, and with Snowflake, rough volume) — flag it if the interviewer raises security/privacy.

### 4.2 Snowflake in depth (+ Java implementation)

```
  64-bit ID:  | 1 sign | 41 timestamp(ms, custom epoch) | 10 machine | 12 sequence |
              41 bits ≈ 69 years   1024 machines   4096 ids/ms/machine
```

- Layout (Twitter's published design): 41-bit ms timestamp since a custom epoch (~69 years of range), 10-bit machine ID (1024 nodes), 12-bit per-ms sequence (4096 IDs/ms/node ⇒ ~4.09 M IDs/sec/node ceiling).
- **The clock-skew defeater — always state it unprompted.** If the node's clock moves _backwards_ (NTP correction, VM migration), naively you mint duplicate IDs. Mitigations, weakest → strongest:
  → refuse to issue until clock catches up (availability hit, correct);
  → keep issuing on the _last seen_ timestamp, burning sequence space (bounded skew only);
  → persist last timestamp; on restart, wait it out.
- Machine-ID assignment is the hidden coordination: ZooKeeper/etcd ephemeral node, DynamoDB conditional write, or StatefulSet ordinal. Two nodes sharing a machine ID silently mint colliding IDs — detection is hard (constraint violations far downstream), so prevent, don't detect.

```java
/** Minimal Snowflake. Thread-safe via synchronized; ~4M ids/sec/node ceiling by design. */
public final class Snowflake {
    private static final long EPOCH = 1704067200000L;          // 2024-01-01 custom epoch
    private static final long MACHINE_BITS = 10, SEQ_BITS = 12;
    private static final long MAX_SEQ = (1L << SEQ_BITS) - 1;  // 4095

    private final long machineId;                              // must be unique, externally assigned
    private long lastTs = -1L, seq = 0L;

    public Snowflake(long machineId) { this.machineId = machineId; }

    public synchronized long nextId() {
        long ts = System.currentTimeMillis();
        if (ts < lastTs) throw new IllegalStateException("clock moved back " + (lastTs - ts) + "ms");
        if (ts == lastTs) {
            seq = (seq + 1) & MAX_SEQ;
            if (seq == 0) ts = spinUntilNextMs(lastTs);        // 4096 ids in this ms exhausted
        } else seq = 0;
        lastTs = ts;
        return ((ts - EPOCH) << (MACHINE_BITS + SEQ_BITS)) | (machineId << SEQ_BITS) | seq;
    }
    private long spinUntilNextMs(long last) {
        long ts; do { ts = System.currentTimeMillis(); } while (ts <= last); return ts;
    }
}
```

- Follow-up you _will_ get: "why `synchronized` and not lock-free?" — contention is one hot object per node; an uncontended/lightly contended `synchronized` block is order of tens of ns (biased/thin locks); the ceiling is the 4096/ms format limit, not the lock. A CAS loop version exists but buys nothing here — say that.

## 5. Idempotency, Uniqueness, Consistency in the Database

### 5.1 Idempotency: the mechanism, not the word

```
 client ──(POST /payments, Idempotency-Key: K)──▶ API
   API ──▶ INSERT dedup(K) ── unique violation? ──▶ return stored response
        └▶ else: do work, store response keyed by K, commit atomically
```

- **Why it exists:** the network makes retries mandatory (you can't tell slow from dead), and retries turn "charge the card" into "charge the card twice." Exactly-once _delivery_ is impossible over an unreliable network; the achievable thing is **at-least-once delivery + idempotent processing = effectively-once**. 🗣 Say that sentence verbatim — it's the L4→L5 separator.
- The mechanism, as an exact sequence (per side-effecting endpoint):
  1. Client generates key `K` (UUIDv4) _before_ first attempt; reuses `K` on every retry.
  2. Server, **in the same transaction as the business write**: `INSERT INTO idempotency(key, response) …`.
  3. Unique-violation ⇒ operation already ran ⇒ fetch stored response, return it. No violation ⇒ proceed, store response, commit.
  4. Failure _after_ commit but before client got the response ⇒ client retries with `K` ⇒ step 3 returns the stored response. This is the exact window the pattern closes.
- Defeaters to volunteer:
  → dedup row **TTL shorter than the client's max retry window** ⇒ duplicate slips through. Set TTL ≥ retry horizon (24 h is a common order).
  → dedup store _separate_ from the business DB (e.g. Redis) ⇒ the check and the write aren't atomic ⇒ crash between them duplicates. Same-transaction is the strong version.
  → key scoped too broadly (per user instead of per operation) ⇒ legitimate second purchase rejected.
- Kafka/SQS consumer version: at-least-once redelivery is the contract; consumer dedups on `(event_id)` unique insert, or makes the handler naturally idempotent (`UPSERT` to a state keyed by entity). Anchor this in your Glue/SQS pipeline experience — "our pipeline was at-least-once from SQS, so every write was an idempotent upsert keyed by instrument ID + version."

### 5.2 Uniqueness across shards

```
  claim "username unique globally"  +  data sharded by user_id
  ⇒ the unique index lives on the WRONG shard key. Two fixes:
     (a) route the claim by ITS OWN key   (b) global lookup table
```

- A unique constraint only works on the node that sees _all_ candidate values. Sharded by `user_id`, no single shard sees all usernames ⇒ the DB constraint can't help you.
- Fix (a) — **shard the uniqueness by the unique key itself**: a `username → user_id` claim table sharded by `hash(username)`. Registering = insert into the owning shard (unique index enforces), then create the user. Two writes across shards ⇒ needs a saga/cleanup for the half-done case.
- Fix (b) — a small **global directory** (single strongly consistent store: Postgres, DynamoDB with condition expression) just for claims. Fine because username claims are low-write-rate even at huge scale — say the rate argument out loud; it's what justifies "central" here.
- General rule 🗣: "uniqueness is enforced where all candidates collide — either route by the unique key so they collide on one shard, or accept a coordination point and justify it with the write rate."

### 5.3 Consistency models with defeaters

```
  strong ──────────────────────────────▶ weak
  linearizable > sequential > causal > session guarantees > eventual
  (cost: latency+availability)          (cost: anomalies you must tolerate)
```

| Model                          | Guarantee (working version)                                                                         | Defeater / what it does NOT give                                                                                                  | Where you'd pick it                                                         |
| ------------------------------ | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Linearizable**               | Every read sees the latest completed write; operations appear atomic at a single point in real time | Costs a coordination round-trip; unavailable under partition (CAP); "serializable" is a _different_ axis (isolation, not recency) | Balances, inventory counts, lock/lease state                                |
| **Sequential**                 | All nodes see the same order, but not necessarily real-time-fresh                                   | You can read stale data even though everyone agrees on order                                                                      | Rarely named in interviews; know it exists                                  |
| **Causal**                     | If A could have caused B, everyone sees A before B                                                  | Concurrent (unrelated) writes may appear in different orders on different nodes                                                   | Comments-and-replies, social graphs                                         |
| **Read-your-writes** (session) | A user always sees their own writes                                                                 | Only _their_ writes; other users still see stale                                                                                  | Profile edits — route the user's reads to leader or their session's replica |
| **Monotonic reads** (session)  | A user never sees time go backwards                                                                 | Cross-user staleness untouched                                                                                                    | Sticky-route users to one replica                                           |
| **Eventual**                   | Replicas converge if writes stop                                                                    | No bound on _when_; concurrent writes need a merge rule (LWW loses data under clock skew!)                                        | Feeds, counts, caches, analytics                                            |

- The interview shape is always: **per store, name the model** — "ledger writes linearizable via the leader; feed reads eventual from replicas; profile edits read-your-writes by pinning to leader for N seconds after write." Never one model for the whole system.
- LWW (last-write-wins) defeater — say it before they ask: LWW under clock skew silently drops the _later_ logical write. If merges matter, use version vectors or app-level merge, or serialize writes through one leader per key.

## 6. Distributed vs. Sharding vs. Replication

### 6.1 The three concepts, disentangled

```
  DISTRIBUTED SYSTEM  = the umbrella: many nodes, one system
       ├── SHARDING     = split the data      → solves CAPACITY (write/storage scale)
       ├── REPLICATION  = copy the data       → solves AVAILABILITY + read scale
       └── COORDINATION = agree on ownership  → the price of the two above
```

| Concept          | Problem it solves                                     | What it costs you                                                       | New failure it introduces                                         | The number that forces it                                        |
| ---------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------- |
| **Sharding**     | Writes/storage exceed one node                        | Cross-shard queries & transactions get hard; resharding is an operation | Hot partition; fan-out queries; broken global constraints (§5.2)  | Write QPS or dataset size past one node's ceiling                |
| **Replication**  | One node's death kills you; read QPS exceeds one node | Lag (async) or write latency (sync); conflict handling                  | Stale reads; failover data loss (async); split brain              | Availability target > single node's ~99.9%; read:write ratio ≫ 1 |
| **Coordination** | Someone must own each shard / be leader               | Latency, complexity, an extra dependency (ZK/etcd)                      | Election storms; fencing bugs; the coordinator's own availability | Existence of sharding/replication                                |

- 🗣 "Sharding scales _writes and storage_; replication scales _reads and survives failures_. They're orthogonal and real systems compose them: N shards × M replicas each. Kafka is the clean example — a topic has partitions (sharding) and each partition has replicas with a leader (replication)."
- They answer _different interview questions_: "how do you handle 1M writes/sec" ⇒ sharding. "What if a node dies" / "how do you serve 100:1 read ratio" ⇒ replication. Don't answer one with the other.

### 6.2 Sharding (partitioning) in depth

```
  key ──hash──▶ ring position ──▶ owning node        (consistent hashing)
       ──range─▶ [a-f]→n1 [g-p]→n2 …                 (range)
       ──lookup▶ directory: key→shard                (directory)
```

- **Hash sharding** — uniform spread, kills range scans. Naive `hash(key) mod N` defeater: changing N remaps ~everything ⇒ use **consistent hashing** (only ~K/N keys move on membership change) with **virtual nodes** (100–256 per physical node, order of magnitude) to smooth load; this is Dynamo/Cassandra's published design.
- **Range sharding** — range scans work, natural for time-series; defeater: sequential keys (timestamps, auto-inc) make the newest shard permanently hot. HBase/Bigtable model; needs auto-splitting.
- **Directory** — explicit `key → shard` map (control plane); maximal flexibility (move any key), at the cost of a lookup dependency that must itself be cached + highly available. This is what "cell router" (§3.1) is.
- **Choosing the partition key is the whole game.** Criteria: (1) high cardinality, (2) even load — not just even _count_; one celebrity = hot key regardless, (3) matches the dominant access pattern so queries hit one shard.
  → Hot-key mitigations, ordered: cache the hot key in front → **key salting** (split `bieber` into `bieber#0..9`, fan-in on read) → isolate the tenant on dedicated capacity. Anchor: your DynamoDB partition-key design experience — say what key you chose and why.
- **Resharding** without downtime (exact sequence, the L5 add-on): 1. provision new topology; 2. dual-write old+new; 3. backfill history old→new (idempotent copy); 4. verify counts/checksums; 5. cut reads over; 6. stop old writes; 7. decommission. Failure at any step ⇒ reads still consistent because cutover (step 5) happens only after verification.

### 6.3 Replication in depth

```
  client ──write──▶ LEADER ──sync/async──▶ follower1
                     │                └──▶ follower2
  reads: leader (fresh) or followers (stale by lag)
```

- **Leader-follower (single-writer)** is the default answer. All writes serialize through the leader (this _is_ what buys per-key linearizability); followers replay the log.
  → **Sync replication**: leader waits for follower ack ⇒ zero-loss failover (RPO=0), + write latency, and one slow follower stalls writes ⇒ hence **semi-sync** (wait for 1 of N).
  → **Async**: fast writes; defeater: leader dies ⇒ un-replicated tail is lost (RPO > 0) and a promoted stale follower can fork history. State RPO/RTO when asked about failover.
- **Failover sequence** (know it cold): 1. detect leader failure via missed heartbeats past timeout (can't tell slow from dead — timeout too low ⇒ false failovers); 2. elect the most-up-to-date follower; 3. **fence the old leader** (revoke lease / fencing token) so a zombie can't accept writes — skipping this is **split brain**, both accept writes, data diverges; 4. repoint clients (config push / DNS / proxy).
- **Leaderless / quorum (Dynamo-style)**: write to W replicas, read from R, of N total. `W+R > N` overlaps read & write sets.
  → Defeater everyone misses: quorum overlap gives you _read-sees-latest-acknowledged-write_ only absent concurrent writes and sloppy quorums; it is **not** full linearizability without read-repair discipline. Concurrent writes still need version vectors + merge.
- **Multi-leader**: only for multi-region write-locally; conflicts are now a _feature of normal operation_, not a failure — need deterministic merge. Avoid unless the geo requirement forces it, and say so.

### 6.4 CAP / PACELC in one screen

- **CAP, stated precisely:** _during a network partition_, a distributed store chooses: refuse some requests (CP) or serve possibly-stale/conflicting data (AP). C here = linearizability. No partition ⇒ no forced choice — most "CAP" invocations in interviews are wrong because no partition is in play.
- **PACELC** (the better tool): if **P**artition, **A** vs **C**; **E**lse, **L**atency vs **C**onsistency. The "else" branch is the everyday tradeoff: sync replication = consistency at latency cost; async = latency at staleness cost.
- 🗣 "I'd rather talk PACELC: even without failures we're trading latency against consistency on every write, via sync vs async replication."

## 7. Interview Tradeoff Questions

**Q: Why not just one big Postgres?**
**L4:** Works to order 10k+ writes/sec and a few TB — and I'd start there. Past that: storage ceiling, single-node availability (~99.9%), and geographic latency. Distribute only when a named number breaks.
**L5:** + The migration path matters more than the end state: single PG → read replicas (read scale + failover) → functional split (move the heaviest table out) → shard the one table that needs it, keeping everything else simple. Sharding _everything_ on day one is how you get a distributed system with none of the benefits and all the costs.

**Q: Sharding vs replication — when do I need which?**
**L4:** Sharding when write throughput or data size exceeds one node. Replication when availability target or read ratio demands it. Orthogonal; usually composed.
**L5:** + The composition has an ordering: replicate first (availability is usually the earlier requirement, and replicas are operationally cheap); shard last (resharding, cross-shard queries, and broken constraints are permanent taxes). Also name the _unit_: you shard a keyspace, you replicate a partition.

**Q: How would you generate IDs for a sharded orders table?**
**L4:** Snowflake-style 64-bit: time-sortable (pagination, index-friendly), no runtime coordination, 4M/sec/node. UUIDv7 if 128 bits are fine. Never DB auto-increment across shards.
**L5:** + The two operational risks are clock skew (refuse-or-wait policy, persist last timestamp across restarts) and machine-ID uniqueness (leased from etcd/DynamoDB, not configured by hand). And I'd note ID-embedded timestamps leak creation time — matters for public IDs.

**Q: What happens when a shard gets hot?**
**L4:** Detect via per-partition metrics (p99, throughput skew). Mitigate: cache in front → salt the key and fan-in reads → isolate the tenant.
**L5:** + Prevention beats reaction: pick a key whose _load_ (not count) is uniform; and design the fan-in read path _before_ salting is needed, because retrofitting scatter-gather onto a hot path during an incident is miserable. Also: salting breaks per-key ordering — if consumers rely on order, that's a real cost, not a detail.

**Q: Leader dies mid-write — what does the client see?**
**L4:** Depends on where it died: before commit ⇒ timeout, retry hits new leader, idempotency key dedups. After commit, before ack ⇒ retry returns stored response (§5.1). Async replication ⇒ the committed-but-unreplicated tail may be lost on failover.
**L5:** + The zombie case: old leader isn't dead, just partitioned — without fencing it keeps acking writes that the new timeline never saw. Fencing token (monotonic epoch checked by the storage layer) is the fix; leases alone aren't enough because clocks.

## 8. Java Concurrency: Coding Pop-Ups

### 8.1 The distributed ↔ local analogy map

```
  ONE JVM, MANY THREADS          ≈        MANY NODES, ONE SYSTEM
  (shared memory + caches)                (shared "state" + replicas)
```

| Local (Java)                             | Distributed                                                                   | Shared mechanism                             |
| ---------------------------------------- | ----------------------------------------------------------------------------- | -------------------------------------------- |
| CPU core caches vs main memory           | Replica lag vs leader                                                         | Copies drift; need explicit sync points      |
| `volatile` (visibility)                  | Read-your-writes / fresh read from leader                                     | Force reading the authoritative copy         |
| `synchronized` / lock (mutual exclusion) | Single leader per key / distributed lock                                      | Serialize writers                            |
| CAS (`compareAndSet`)                    | Conditional write (DynamoDB `ConditionExpression`, optimistic version column) | Optimistic: attempt, detect conflict, retry  |
| ABA problem                              | Lost update via stale read-modify-write                                       | Version/stamp the value                      |
| Happens-before                           | Causal consistency                                                            | Order guaranteed only along stated edges     |
| `ConcurrentHashMap` striping             | Sharding                                                                      | Split the contention domain                  |
| Deadlock (lock ordering)                 | Distributed deadlock / saga stuck                                             | Acquire in global order / timeout+compensate |

- This table is your secret weapon: when a design-round interviewer pivots to "ok, how do you do this _in code_," walk the analogy — it demonstrates both sides at once. 🗣 "Threads sharing memory have the same problems as nodes sharing state — stale copies, lost updates, ordering — just with nanosecond stakes instead of millisecond."

### 8.2 Java Memory Model: visibility & happens-before

```
  Thread A: write x ──┐ without a happens-before edge,
  Thread B: read  x ──┘ B may see the OLD x forever (cache/reorder)
```

- **The problem:** compilers and CPUs reorder, and each core caches. Without synchronization, a write by thread A is _not guaranteed ever visible_ to thread B, and operations can appear reordered.
- **Happens-before (HB)** is the JMM's contract: if `A happens-before B`, A's effects are visible to B. The edges to know:
  → program order within one thread;
  → `unlock(m)` HB subsequent `lock(m)` (same monitor);
  → **volatile write HB subsequent volatile read** of the same field;
  → `Thread.start()` HB everything in the thread; everything in the thread HB `join()` returning;
  → transitivity — and the practical trick: a volatile write/read pair _publishes_ all writes that preceded the volatile write (piggybacking).
- **`volatile`** = visibility + ordering, **not atomicity**. `volatile int c; c++` is still a lost-update race (read-modify-write is three steps). Defeater question they love. Use `AtomicInteger` or a lock.
- **`final` fields** get safe-publication guarantees after the constructor completes — this is exactly why double-checked locking needs `volatile` on the instance field (pre-Java-5 DCL was genuinely broken; canonical pattern).

### 8.3 The lock toolbox

| Tool                     | Buys you                                                                  | Costs you                                                   | Choose when                                        |
| ------------------------ | ------------------------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------- |
| `synchronized`           | Simple, JVM-optimized (biased→thin→fat inflation), auto-release           | No timeout, no interruptibility, no fairness, one condition | Default. Short critical sections                   |
| `ReentrantLock`          | `tryLock(timeout)`, interruptible, fairness option, multiple `Condition`s | Manual `unlock()` in `finally` (leak = deadlock)            | Need timeout/fairness/multiple wait-sets           |
| `ReentrantReadWriteLock` | Parallel readers                                                          | Writer starvation possible (non-fair); heavier              | Read-heavy shared structure with occasional writes |
| `StampedLock`            | Optimistic reads: read without locking, `validate()` after                | Non-reentrant; trickier API                                 | Very read-hot, short reads (Java 8+)               |

- `wait/notify` vs `Condition.await/signal`: same semantics, but always `while (!condition) wait()` — **spurious wakeups** are permitted by the spec; an `if` is the classic bug.
- Deadlock: 4 conditions (mutual exclusion, hold-and-wait, no preemption, circular wait); the practical fix is **global lock ordering** (or `tryLock` with backoff). Distributed analogue: sagas with timeouts instead of 2PC's blocking.

### 8.4 Lock-free: CAS, atomics, ABA

- **CAS** — `compareAndSet(expected, new)`: hardware instruction (x86 `cmpxchg`); succeeds only if current == expected; on failure, re-read and retry. This is optimistic concurrency at the instruction level, and the exact analogue of a DynamoDB conditional write or a `WHERE version = ?` update.
- `AtomicInteger/Long/Reference`, `LongAdder` — the follow-up: under heavy contention `AtomicLong` CAS-retry storms; `LongAdder` shards the counter across cells and sums on read (_sharding, again_ — say it) ⇒ faster writes, weaker read (a momentary sum, not a linearizable point). Perfect metrics counter; wrong for "check balance then spend."
- **ABA**: value went A→B→A between your read and CAS; CAS succeeds but the world changed. Fix: `AtomicStampedReference` (version stamp) — identical in spirit to an optimistic-locking version column.

### 8.5 Concurrent collections

- **`ConcurrentHashMap`** (Java 8+): per-bin locking — CAS to insert into an empty bin, `synchronized` on the bin's head node otherwise; reads are lock-free (volatile reads). Bins convert to red-black trees past 8 entries (hash-collision defense).
  → Defeaters: `size()` is an estimate under concurrency; iterators are _weakly consistent_ (no `ConcurrentModificationException`, may or may not see concurrent updates); compound check-then-act is still racy — use `compute/merge/putIfAbsent`, the atomic compound ops.
- `CopyOnWriteArrayList` — every mutation copies the array ⇒ O(n) writes, perfectly consistent snapshot iteration. Listener lists: yes. Anything write-heavy: no.
- `BlockingQueue` (`ArrayBlockingQueue` bounded / `LinkedBlockingQueue`) — producer-consumer with built-in **backpressure**: bounded queue + blocking `put()` _is_ backpressure. Distributed analogue: bounded SQS + a rate-limited consumer. Always bound the queue; unbounded queues turn overload into OOM.

### 8.6 Executors, futures, virtual threads

- `ThreadPoolExecutor(core, max, keepAlive, queue, rejectionHandler)` — the trap everyone hits: with an **unbounded queue, `max` never matters** (pool grows past core only when the queue is _full_). Bound the queue; pick the rejection policy deliberately (`CallerRunsPolicy` = backpressure by making the submitter do the work).
  → Sizing (order-of-magnitude heuristics): CPU-bound ⇒ ~#cores; IO-bound ⇒ cores × (1 + wait/compute).
- `CompletableFuture` — async composition: `supplyAsync → thenApply/thenCompose → exceptionally/handle`; `allOf` for fan-out/fan-in. Know that `thenApply` runs on the completing thread unless you use `*Async` variants with an explicit pool.
- **Virtual threads** (Java 21, JEP 444): thread-per-request at millions scale; carrier threads park on blocking IO instead of pinning an OS thread. Defeaters to name: `synchronized` blocks could **pin** the carrier (fixed in JDK 24, JEP 491 — as of that release); no benefit for CPU-bound work; thread-locals get expensive at that cardinality.

### 8.7 Canonical coding pop-ups with code

**(1) Thread-safe lazy singleton — the DCL question**

```java
public final class Config {
    private static volatile Config instance;          // volatile is THE point
    private Config() {}
    public static Config get() {
        Config c = instance;                          // one volatile read
        if (c == null) {
            synchronized (Config.class) {
                c = instance;
                if (c == null) instance = c = new Config();
            }
        }
        return c;
    }
}
// Why volatile: without it, another thread can observe a non-null but
// PARTIALLY CONSTRUCTED instance (store reordered before field init).
// Simpler alternatives to mention: enum singleton; static holder idiom.
```

**(2) Bounded buffer with Condition (the producer-consumer classic)**

```java
class BoundedBuffer<T> {
    private final Object[] items; private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();
    BoundedBuffer(int cap) { items = new Object[cap]; }

    void put(T t) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) notFull.await();   // while, not if!
            items[tail] = t; tail = (tail + 1) % items.length; count++;
            notEmpty.signal();
        } finally { lock.unlock(); }
    }
    @SuppressWarnings("unchecked")
    T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) notEmpty.await();
            T t = (T) items[head]; items[head] = null;
            head = (head + 1) % items.length; count--;
            notFull.signal(); return t;
        } finally { lock.unlock(); }
    }
}
// In prod: ArrayBlockingQueue. In the interview: they want THIS, by hand.
```

**(3) Optimistic update — the CAS loop**

```java
AtomicLong balance = new AtomicLong();
long withdraw(long amt) {
    while (true) {
        long cur = balance.get();
        if (cur < amt) throw new IllegalStateException("insufficient");
        if (balance.compareAndSet(cur, cur - amt)) return cur - amt;
        // CAS failed ⇒ someone raced us ⇒ re-read, re-check, retry
    }
}
// Say the bridge: this loop IS optimistic locking; the DB version is
// UPDATE acct SET bal = bal - ? , version = version+1
//   WHERE id = ? AND version = ? AND bal >= ?   (retry on 0 rows)
```

**(4) Simple token-bucket rate limiter (single node)**

```java
class TokenBucket {
    private final long capacity, refillPerSec;
    private double tokens; private long lastNanos;
    TokenBucket(long capacity, long refillPerSec) {
        this.capacity = capacity; this.refillPerSec = refillPerSec;
        this.tokens = capacity; this.lastNanos = System.nanoTime();
    }
    synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        tokens = Math.min(capacity, tokens + (now - lastNanos) / 1e9 * refillPerSec);
        lastNanos = now;
        if (tokens >= 1) { tokens -= 1; return true; }
        return false;
    }
}
// Distributed version: per-node buckets with divided quota (cheap, approximate)
// or Redis+Lua atomic bucket (accurate, +1 network hop) — name the tradeoff.
```

**Rapid-fire Q&A (design-round pop-up form)**

**Q: `volatile` vs `synchronized`?**
**L4:** `volatile` = visibility + ordering for a single field, no mutual exclusion; `synchronized` = both, over a compound section. `volatile` can't fix `count++`.
**L5:** + volatile write/read creates a happens-before edge that publishes _all prior writes_, which is why the safe-publication idioms (DCL, one-shot flags) work; and under the hood it constrains reordering (fences), it isn't "read from main memory" folklore.

**Q: How does `ConcurrentHashMap` achieve thread safety without locking the whole map?**
**L4:** Java 8+: CAS insert into empty bins, per-bin `synchronized` otherwise, lock-free volatile reads. Contention domain = one bin, not the map.
**L5:** + That _is_ sharding-the-lock; same idea as `LongAdder` cells and DB partitioning — shrink the contention domain. Trade: aggregate ops (`size`, iteration) become weakly consistent. If asked pre-8 trivia: segment-based striping (16 segments).

**Q: Strong vs eventual consistency — in _code_ terms?**
**L4:** Strong = every reader sees the write immediately (like reading a `volatile` after its write, or reading under the same lock). Eventual = readers may see stale copies for a while (like a plain field with no HB edge — except distributed lag is bounded by replication, whereas an unsynchronized read may _never_ see it).
**L5:** + That last clause is the subtle bit: the JMM without an HB edge gives you _no_ convergence promise at all — weaker than eventual consistency. Synchronization edges (volatile/locks) are the local analogue of read-from-leader; choosing which reads take the edge is the same design act as choosing which reads hit the leader.

**Q: You mentioned a queue between services. Show me backpressure locally.**
**L4:** Bounded `BlockingQueue`: `put()` blocks producers when full — the producer slows to the consumer's rate. Unbounded queue = deferred OOM.
**L5:** + Or `ThreadPoolExecutor` with a bounded queue + `CallerRunsPolicy`: rejection pushes work onto the submitting thread, throttling intake. Distributed mirror: bounded SQS visibility + consumer-side rate limit + DLQ after N receives; the DLQ is the "rejection handler."
