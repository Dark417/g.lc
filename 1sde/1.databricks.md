# Databricks / Spark / Lakehouse — Interview Study Guide

Same structure as the messaging and collections guides:

- **Part 1 — Index.** Questions only, system → subsection. Read a line, answer aloud, then check Part 2.
- **Part 2 — Answers.** Every question twice. `L4` = correct, concrete, mechanism-aware. `L5` = adds the tradeoff, the failure mode, the cost model, the ownership boundary.
- **Part 3 — Code.** PySpark 3.5 / DBR 14-15 LTS reference implementations + SQL + Terraform.
- **Part 4 — Positioning.** How you answer "how much Databricks have you actually used?" without lying and without losing the room.

**Read Part 4 first.** You have **AWS Glue + PySpark**, not Databricks. That is a real and defensible position — Glue _is_ managed Spark, so ~70% of this guide is knowledge you already own under a different brand name. The other ~30% (Delta internals, Unity Catalog, DLT, Photon, DBU cost model) is platform-specific and you have to learn it as platform knowledge, not claim it as experience.

**The interviewer's frame:** for a Databricks-in-the-JD role, L4 means _you can build and debug pipelines on the platform_. L5 means _you own the platform decisions_ — file layout, cost, governance model, and what breaks at 3am. If your answer never names a config knob, a metric, or a dollar, it's an L4 answer no matter how long it is.

# PART 2 — ANSWERS

## System 1 — Spark execution model

### 1.1 Architecture

**`SP-1` Driver, executor, cluster manager**

- `L4` Driver runs your `main`, builds the logical plan, schedules tasks, holds the `SparkSession` and all broadcast/accumulator state. Executors are JVMs on worker nodes that run tasks and hold cached blocks. Cluster manager (on Databricks: the Databricks control plane over the cloud provider) allocates the VMs.
- `L5` The split that matters operationally: driver is a **single point of failure and a single point of memory pressure**. Anything that pulls data back — `collect`, `toPandas`, large broadcasts, a huge query plan from 200 chained transformations — dies on the driver. On Databricks the control plane holds metadata/notebooks/job config; your data stays in the data plane (your cloud account, classic compute) — that separation is the answer to "where does my data live" in a security review.

**`SP-2` Job → stage → task**

- `L4` One action = one job. A job splits into stages at shuffle boundaries. A stage runs one task per partition. Tasks in a stage are identical code on different data.
- `L5` The unit of retry is the task; the unit of recompute on failure is the stage. That's why a wide dependency is expensive to lose — losing one partition of a shuffled RDD can force recomputation of upstream parents. It's also why "number of stages" is the first thing I read in the UI: if a job I expect to be a scan-filter-write has six stages, someone added a shuffle I didn't intend.

**`SP-3` Narrow vs wide**

- `L4` Narrow: each output partition depends on one input partition — `map`, `filter`, `union`, `withColumn`, `coalesce`. Wide: output partition depends on many inputs, requires shuffle — `groupBy`, `join` (non-broadcast), `distinct`, `repartition`, window functions, `orderBy`.
- `L5` The design rule I work from: push all narrow work before the first wide one, and try to make the pipeline have exactly one shuffle where possible. Also note the exceptions people miss — `union` is narrow but leaves you with a bad partition count; a window function partitioned by the same key you already grouped by can reuse the exchange if you don't break the partitioning in between.

**`SP-4` Lazy evaluation and actions**

- `L4` Transformations only build the plan. Actions trigger execution: `count`, `collect`, `show`, `write`/`save`, `take`, `foreach`, `toPandas`.
- `L5` Laziness is why the same DataFrame recomputes if you use it twice without caching, and it's the #1 source of "why did my job read S3 three times." It's also why timing a cell in a notebook lies — the time lands on whichever cell has the action. When I profile, I anchor on the Spark UI job timeline, not on notebook cell wall clock.

**`SP-5` Initial partition count on read**

- `L4` For file sources it's driven by total input size, `spark.sql.files.maxPartitionBytes` (128 MB default), the open-cost heuristic, and the number of files. Non-splittable compression (gzip) forces one partition per file. For JDBC it's 1 unless you supply `partitionColumn`/`lowerBound`/`upperBound`/`numPartitions`.
- `L5` The two failure shapes both come from here. Thousands of tiny files → thousands of tiny tasks, scheduler overhead dominates. A handful of large gzip files → no parallelism at all, and no amount of cluster is going to help. This is exactly the argument for Auto Loader + compaction at the bronze boundary rather than fighting it downstream. On the JDBC side, defaulting to 1 partition is the classic ingestion bottleneck — I've hit that pulling from Aurora.

**`SP-6` What a shuffle physically is**

- `L4` Map-side tasks write records partitioned by the target partition into local shuffle files (data + index) on the executor's local disk. Reduce-side tasks fetch their slice over the network from every map executor. It's a full disk write plus an all-to-all network transfer.
- `L5` Three consequences: (a) shuffle is bounded by local disk and network, so instance type and disk matter more than CPU on shuffle-heavy jobs; (b) losing an executor loses its shuffle files, forcing recompute — that's the argument against aggressive spot on the workers of a long shuffle-heavy job; (c) shuffle files are the reason `spark.sql.shuffle.partitions` is a real tuning lever, not cosmetics.

**`SP-7` Catalyst phases**

- `L4` Unresolved logical plan → analysis (resolve names against the catalog) → logical optimization (rule-based: predicate pushdown, column pruning, constant folding, filter reordering) → physical planning (candidate plans, cost-based join selection) → code generation to RDD operations.
- `L5` The practically useful part is knowing which rules you can defeat. A Python UDF is a black box — Catalyst can't push a predicate through it or prune columns behind it. Same for non-deterministic expressions. When someone's pipeline is mysteriously slow, my first read of `df.explain(True)` is: did the filter actually land on the scan node, and is `ReadSchema` narrower than the table?

**`SP-8` Tungsten / whole-stage codegen**

- `L4` Tungsten is off-heap, cache-aware binary memory management with `UnsafeRow`, avoiding JVM object overhead and GC. Whole-stage codegen fuses a chain of operators into a single generated Java method so there's no per-row virtual call between operators.
- `L5` The tell: in the UI, a stage with `WholeStageCodegen (n)` is fused and fast. Operators that break codegen — some Python UDFs, certain joins, very wide plans that exceed the 64 KB method limit — show up unfused. That's a real diagnostic: "the plan fell out of codegen at this node" explains a 2-3× regression better than any guess.

**`SP-9` RDD vs DataFrame vs Dataset**

- `L4` RDD: JVM objects, no optimizer, full type safety. DataFrame: `Dataset[Row]`, fully optimized by Catalyst, no compile-time type safety. Dataset (Scala/Java only): typed, but lambdas are opaque to Catalyst.
- `L5` In PySpark this collapses to "use the DataFrame API, and treat every Python UDF as a tax." A Python UDF serializes rows out to a Python process and back; pandas UDFs (Arrow, vectorized) cut that dramatically; a native Spark SQL expression costs nothing. My ordering is always: built-in expression → `pandas_udf` → Python UDF only if unavoidable. In Scala, typed `Dataset` operations similarly block optimization, so it's a real tradeoff, not a free upgrade.

**`SP-10` AQE**

- `L4` Adaptive Query Execution re-optimizes at runtime using actual shuffle statistics. Three things: coalesce shuffle partitions, switch sort-merge join to broadcast when a side turns out small, and split skewed partitions in a skew join. On by default since Spark 3.2 / all current DBRs.
- `L5` AQE is why `shuffle.partitions` tuning matters less than it used to — set it generously and let coalescing fix the tail. But know the limits: AQE reacts to what it has _already_ shuffled, so it can't prevent the first bad exchange; it can't fix skew from a source that's skewed before the join; and dynamic partition pruning is a separate feature. When I say "AQE handles it," the follow-up is always "and what does AQE not handle" — that's the L5 answer.

**`SP-11` Photon**

- `L4` Photon is Databricks' vectorized C++ execution engine that replaces parts of the JVM physical plan. Best on SQL and DataFrame operations — scans, filters, joins, aggregations. You pay a higher DBU rate but often finish faster, so total cost can drop.
- `L5` It doesn't help — and you're paying more for nothing — when the workload is dominated by Python UDFs, ML training, or anything Photon can't cover, since unsupported operators fall back to the JVM. The honest evaluation is empirical: run the same job with and without, compare DBU × runtime, not runtime alone. In the UI, look for `PhotonResultStage` and check what fraction of the plan is actually Photon-executed.

### 1.2 Memory & resources

**`SP-12` Executor memory layout**

- `L4` Container memory = JVM heap (`spark.executor.memory`) + overhead (`spark.executor.memoryOverhead`, off-heap, Python processes, netty buffers). Inside heap: reserved (~300 MB) → unified region (`spark.memory.fraction`, default 0.6) split between execution and storage (`spark.memory.storageFraction` 0.5) → the remainder is user memory for your own data structures.
- `L5` The unified region is _dynamic_: execution can evict cached storage blocks when it needs room, but storage cannot evict execution. That asymmetry is why over-caching causes silent recompute rather than an error, and why "cache everything" degrades a job invisibly. In PySpark, memoryOverhead is the one people get wrong — Python worker processes live outside the JVM heap, so heavy pandas UDFs blow the container, not the heap, and the error message points at YARN/K8s killing the container rather than at your code.

**`SP-13` Spill**

- `L4` Spill is Spark writing intermediate data (sort buffers, aggregation maps, join build side) to local disk because it doesn't fit in execution memory. In the Spark UI stage page: `Spill (memory)` and `Spill (disk)` columns.
- `L5` Spill isn't automatically bad — it's the mechanism that keeps a job from OOMing. It's a problem when the spill is large relative to shuffle read, or concentrated in a few tasks (that's skew wearing a spill costume). The fix order: more partitions first (cheaper), then more memory per executor, then restructure the join. Throwing memory at spill without checking partition counts is the classic junior move.

**`SP-14` Cores per executor**

- `L4` 4–5 cores per executor is the conventional sweet spot. Too many cores per JVM causes HDFS/object-store throughput contention and GC pauses that stall all threads at once; too few wastes memory on JVM overhead and loses broadcast sharing.
- `L5` The real argument is blast radius and memory sharing: all cores in an executor share the heap, so one skewed task can starve its four neighbors, and losing that executor loses more cached and shuffle data at once. On Databricks you don't set this directly the way you do on EMR/YARN — you pick a node type and the runtime configures it — so the interview-correct framing is "I choose instance type by workload shape: memory-optimized for wide shuffles and caching, compute-optimized for CPU-bound transforms, storage-optimized when shuffle spill dominates."

**`SP-15` Driver OOM vs executor OOM**

- `L4` Driver OOM: `collect`/`toPandas` on a big result, broadcasting something too large, an enormous query plan, or thousands of parallel jobs from a loop. Executor OOM: skewed partition, too few partitions, huge `groupBy` state, cartesian join, or Python overhead exceeding memoryOverhead.
- `L5` The diagnostic separation is what they're testing. Driver OOM correlates with a specific line of driver-side code and no task failures. Executor OOM shows a small number of failing tasks, usually with a huge shuffle read on those tasks, and often preceded by heavy spill. I treat "many tasks fine, few tasks dead" as skew until disproved, and "all tasks dead" as under-partitioning or an under-sized cluster.

**`SP-16` `collect()`**

- `L4` Pulls every row to the driver JVM. Fine for small aggregates, fatal for large results. Alternatives: `limit(n).collect()`, `take(n)`, write to a table and read downstream, or `toLocalIterator()` to stream partitions one at a time.
- `L5` The pattern I actually enforce in review: driver-side collection is allowed only for _control-flow_ data — a list of partition keys, a row count, a config lookup — never for payload. If someone needs a Pandas DataFrame for a library, the question is whether the work can be pushed into a `pandas_udf` on the executors instead, which keeps it distributed.

## System 2 — Performance & tuning

### 2.1 Diagnosis

**`PF-1` 3× slower, no code change**

- `L4` Ordered: (1) input data volume/shape changed, (2) file count exploded (small files), (3) skew appeared in a key, (4) cluster config or DBR version changed, (5) upstream table layout changed — someone stopped running OPTIMIZE, (6) contention on shared compute, (7) source system slower.
- `L5` I compare two runs, not one run against intuition. Same job, last good run vs bad run, in the Spark UI: total input bytes, number of tasks, max-vs-median task duration, shuffle read/write, spill. That table tells you which of the seven it is within a couple of minutes. The subtle one that gets missed most: nobody changed the code, but the _upstream_ table's file layout degraded because a streaming writer has been appending small files for three weeks. That's the argument for compaction being a scheduled owned job, not an afterthought.

**`PF-2` Four numbers in the Spark UI**

- `L4` (1) Task duration distribution — min/median/max on the stage page. (2) Shuffle read/write bytes. (3) Spill (memory/disk). (4) Input bytes vs the bytes you expected to read.
- `L5` I'd add the fifth, which is the ratio: max task duration ÷ median. Above ~5× is skew, full stop. And I read the SQL tab's plan node metrics — `number of files read` and `ReadSchema` — because that's where you catch a missing partition filter or a missing column prune, which is a 10× problem that no amount of cluster tuning fixes.

**`PF-3` Long tail in task duration**

- `L4` A few tasks take far longer than the rest. Candidates: data skew on the join/group key, non-splittable input files, spill concentrated in those tasks, or a straggler node (bad disk, spot preemption, noisy neighbor).
- `L5` Distinguish them by looking at shuffle _read size_ per task alongside duration. Large read + long duration = data skew. Normal read + long duration = straggler node or GC, and speculative execution is the mitigation. Long duration on the first tasks of a scan stage = non-splittable files. Getting this classification right is the difference between salting a key (correct) and adding nodes (wasted money).

**`PF-4` Skew vs spill vs small files vs GC**

- `L4` Skew: max task ≫ median, uneven shuffle read. Spill: spill columns non-zero, tasks slow but even. Small files: huge task count, tiny input per task, scan stage dominates. GC: high GC time column, sawtooth in executor metrics.
- `L5` They co-occur and cause each other, which is why an ordered checklist beats pattern matching. Skew causes spill in the hot task; small files cause driver-side scheduling pressure that looks like the driver hanging; GC pressure is usually a symptom of too little memory _per task_, i.e. under-partitioning. I fix in this order: file layout → partition count → skew handling → memory. Fixing memory first almost always masks the real cause.

### 2.2 Skew

**`PF-5` Causes of skew**

- `L4` A key with hugely disproportionate frequency. Classic cases: `NULL` or a sentinel like `'UNKNOWN'`/`-1` used as a default, one enormous customer/tenant, a date column where one day holds a backfill, a currency or country code where one dominates.
- `L5` In my domain — instrument/offering data — the shape is exactly this: a handful of issuers or a single default `issuer_id` for unmapped records dominates a join key. The design fix is upstream: don't let NULL collapse into a join key; route unmapped records to a quarantine path in silver rather than joining them. That's a data-model fix, and it's more durable than salting, which is a runtime patch.

**`PF-6` Salting**

- `L4` Append a random suffix `0..N-1` to the skewed key on the large side; explode the small side into N copies, one per salt value; join on `(key, salt)`; drop the salt. Spreads the hot key across N partitions.
- `L5` Costs: N× row multiplication on the replicated side, extra shuffle, and code that's hard to read and easy to break. So I salt only the skewed keys — split the DataFrame into hot-key and cold-key halves, salt only the hot half, union the results. And I reach for it only after AQE skew join and broadcast have failed, because both are free.

**`PF-7` AQE skew join**

- `L4` With `spark.sql.adaptive.skewJoin.enabled`, AQE detects partitions larger than `skewedPartitionFactor` × median and above `skewedPartitionThresholdInBytes`, splits them into sub-partitions, and replicates the matching side. Works for sort-merge joins.
- `L5` Limits worth naming: it only sees skew _after_ the shuffle, so you still pay the skewed write; it needs the stats, so it's weaker on the first stage of a plan; it doesn't help skew in a `groupBy` aggregation the same way; and it doesn't help if a single key exceeds what one task can hold, since the split is by partition, not by key. That last case is where you must salt or pre-aggregate.

**`PF-8` Broadcast join**

- `L4` Small side is collected to the driver and broadcast to every executor, so no shuffle on the large side. Threshold: `spark.sql.autoBroadcastJoinThreshold`, default 10 MB. Force with `broadcast(df)` / hint `/*+ BROADCAST(t) */`; disable by setting the threshold to `-1`.
- `L5` It backfires three ways: the "small" table isn't small at runtime (stale or missing stats — very common on non-Delta sources), driver memory can't hold it, or you broadcast into a loop and re-broadcast every iteration. AQE mitigates the stats problem by converting to broadcast after the fact. My rule: broadcast a dimension table only when I control its size contractually (a lookup table with a known row bound), never a table that grows with the business.

### 2.3 Joins & shuffle

**`PF-9` Join strategy selection**

- `L4` Broadcast hash join, shuffle hash join, sort-merge join, broadcast nested loop, cartesian. Spark picks based on estimated sizes, join type, and whether the keys are sortable — broadcast if under threshold, otherwise sort-merge by default.
- `L5` The lever is statistics. On Delta, `ANALYZE TABLE ... COMPUTE STATISTICS` and file-level stats make the estimate real; on raw Parquet the optimizer is often guessing off file size, which is how you end up with a sort-merge join between a 5 GB table and a 2 MB table. Hints exist (`BROADCAST`, `MERGE`, `SHUFFLE_HASH`) but I treat a required hint as a smell — it means the stats are wrong and someone will hit the same problem in the next query.

**`PF-10` Sort-merge join**

- `L4` Both sides shuffled by the join key into the same number of partitions, each partition sorted by key, then merged in a single pass. Cost: two shuffles plus two sorts.
- `L5` Why it's the default: it's the only strategy with predictable memory behavior at scale, since sorted merge streams rather than holding a hash table. Its weakness is exactly skew — the merge is per-partition, so one fat key serializes. And knowing it sorts is what tells you that a subsequent `orderBy` on the same key might be free, and that pre-bucketed/clustered data can skip the exchange entirely.

**`PF-11` `spark.sql.shuffle.partitions`**

- `L4` Default 200 — a fixed number unrelated to your data or cluster. Too low on big data (giant partitions, spill), absurdly high on small data (thousands of empty tasks).
- `L5` With AQE on, the guidance inverted: set it _high_ (e.g. `auto` on Databricks, or a few thousand) and let AQE coalesce down based on real sizes. Without AQE, the manual heuristic is target ~128–200 MB per shuffle partition, and pick a multiple of total executor cores so the last wave isn't half-empty. I'd state both, because a lot of interviewers still have the pre-AQE answer in their head and you want to show you know which era you're in.

**`PF-12` `repartition` vs `coalesce`**

- `L4` `repartition(n)` is a full shuffle, can increase or decrease, produces even partitions, and can repartition by column. `coalesce(n)` only decreases, avoids a shuffle by merging adjacent partitions, and produces uneven partitions.
- `L5` The trap is that `coalesce(1)` before a write doesn't just merge the write — it collapses the _parallelism of the upstream stage_, so your whole transform runs single-threaded. If I need one output file after heavy computation, I use `repartition(1)` (accepting the shuffle) or, better on Delta, write normally and let optimized writes / OPTIMIZE handle file sizing. `repartition(col)` is also how you pre-partition to make a downstream write layout match your partition columns and avoid every task writing to every partition directory.

**`PF-13` Bucketing**

- `L4` Pre-shuffling a table into a fixed number of hash buckets on a column at write time, so joins and aggregations on that column can skip the exchange. Metastore-tracked; both sides must have the same bucket count and column.
- `L5` It's largely obsolete on Databricks: it's brittle (any bucket-count mismatch silently disables the benefit), it fixes the layout forever, and it interacts badly with incremental writes producing small files per bucket. Liquid clustering supersedes it — same goal (co-locating related data) without the rigidity, and it can be changed after the fact. I'd name bucketing as "the Hive-era answer" and say what replaced it, which is the answer they're actually fishing for.

### 2.4 File layout

**`PF-14` Small files**

- `L4` Cause: many small writes — streaming micro-batches, per-partition writes with high task counts, frequent MERGEs. Symptom: task count ≫ data volume warrants, scan stage dominates, metadata listing is slow. Fix: `OPTIMIZE` (bin-packing), optimized writes + auto-compaction on Delta, fewer output partitions, compaction job at the bronze boundary.
- `L5` The economics: object storage charges per request and the driver has to list and plan every file, so 100k × 1 MB files can cost more in listing and scheduling than the actual compute. On Delta the metadata layer helps (the log knows the files, so no `LIST` storm) but the per-file task overhead remains. I treat compaction as an owned scheduled job with its own SLA, not a manual cleanup — that's the ownership framing.

**`PF-15` Hive-style partitioning**

- `L4` Physically splits data into directories by column value, so a filter on that column skips whole directories. Good for low-cardinality, high-selectivity filter columns — typically a date. Rule of thumb: each partition should hold at least ~1 GB; don't partition a table under ~1 TB at all.
- `L5` Over-partitioning is far more common and more damaging than under-partitioning — partitioning by `customer_id` or by timestamp-to-the-hour creates millions of tiny directories and destroys the table. My current default on Databricks: don't partition, use liquid clustering; partition only when there's a genuine lifecycle need, like deleting or overwriting a whole date's data with `replaceWhere`.

**`PF-16` Z-ORDER vs liquid clustering vs partitioning**

- `L4` Partitioning = physical directories, coarse, immutable choice. Z-ORDER = multi-dimensional co-location within files during OPTIMIZE, improves data skipping on up to ~3–4 columns, must be re-run after writes. Liquid clustering = Databricks' newer incremental clustering, set with `CLUSTER BY`, self-maintaining, changeable without rewriting the table.
- `L5` My recommendation for a new table today: liquid clustering on the high-selectivity filter/join columns, no partitioning, and rely on Delta file statistics for skipping. The deciding tradeoffs are (a) liquid clustering can be _changed_ — partition columns can't, without a full rewrite; (b) Z-ORDER's full rewrite cost grows with the table while liquid clustering is incremental; (c) partitioning still wins for the one specific case of atomic whole-partition replacement.

**`PF-17` File sizing and OPTIMIZE**

- `L4` Target ~128 MB–1 GB per file. `OPTIMIZE table` bin-packs small files. `delta.autoOptimize.optimizeWrite` repartitions before write; `delta.autoOptimize.autoCompact` compacts small files after write. Databricks also does auto-tuning of target file size based on table size.
- `L5` Tradeoff: auto-compaction adds latency to every write, which is wrong for a low-latency streaming path. So the pattern I'd defend is optimized writes on (cheap, prevents the problem) plus scheduled OPTIMIZE off-peak (batched, doesn't tax the hot path), and auto-compact on only for tables where write latency doesn't matter. Also: OPTIMIZE on a table with a running streaming reader creates data-change conflicts unless the reader is configured to ignore them.

**`PF-18` What breaks pushdown and pruning**

- `L4` Predicate pushdown breaks on: filters applied after a UDF, filters on a column produced by a non-deterministic expression, type mismatches that force a cast on the column side, and `OR` across different sources. Column pruning breaks on `select *`, and on UDFs taking the whole row/struct.
- `L5` The verification, not the theory, is the L5 part: `df.explain("formatted")` and read `PushedFilters` and `ReadSchema` on the scan node. If a filter isn't in `PushedFilters`, it's being applied after the read and you're paying full I/O. The most common real-world instance I'd cite is a string date column compared to a date literal — the implicit cast lands on the column, pruning dies, and the job reads the whole table.

### 2.5 Caching

**`PF-19` `cache` / `persist` / `checkpoint`**

- `L4` `cache()` = `persist(MEMORY_AND_DISK)`. `persist(level)` lets you choose: `MEMORY_ONLY`, `MEMORY_AND_DISK`, `DISK_ONLY`, `_SER` variants, `_2` replicated. All are lazy — materialized on the next action. `checkpoint()` writes to reliable storage and **truncates the lineage**; it's eager and requires a checkpoint dir.
- `L5` The distinction that matters: cache is a performance optimization that Spark may evict; checkpoint is a correctness/stability tool for cutting an unbounded lineage — the classic case is an iterative loop where the plan grows every iteration until the driver chokes building it. In practice on Delta, the third option beats both: write the intermediate to a Delta table. It's durable, inspectable, restartable, and shared across jobs. I'd rather materialize a silver table than cache a 200 GB DataFrame.

**`PF-20` When caching hurts**

- `L4` When the DataFrame is used only once; when it doesn't fit and evicts other cached data or forces recompute; when it eats execution memory and causes spill; when the data changes and you serve stale cached results.
- `L5` The asymmetry from `SP-12` is the reason it's _silently_ harmful: execution evicts storage, so the failure mode isn't an error, it's your job quietly recomputing the cached branch while you believe it's cached. I check `Storage` tab fraction-cached before trusting any cache. And I unpersist explicitly — leaving caches around in a long-running job or a shared all-purpose cluster is a real source of "why is everyone's query slow today."

**`PF-21` Delta cache vs Spark cache**

- `L4` Delta/disk cache (formerly Delta cache) automatically caches remote Parquet files on the worker's local NVMe, transparently, at the file level — no code, survives across queries and users on the cluster. Spark cache is explicit, per-DataFrame, holds the _deserialized/optimized_ result in the unified memory region.
- `L5` They compose: disk cache accelerates the scan, Spark cache stores post-computation results. On Databricks with a disk-cache-accelerated instance type, the disk cache alone removes most of the reason people reach for `.cache()` on a raw table read — that's a good "you know the platform, not just Spark" answer. Spark cache still earns its keep for an expensive _computed_ intermediate reused several times in one job.

## System 3 — Delta Lake

### 3.1 Format & guarantees

**`DL-1` What a Delta table is physically**

- `L4` A directory of Parquet data files plus a `_delta_log/` directory. The log is an ordered sequence of JSON commit files (`000...000.json`, `...001.json`) each containing atomic actions — `add`, `remove`, `metaData`, `protocol`, `commitInfo`. Every 10 commits, a Parquet checkpoint file consolidates state so readers don't replay the whole history.
- `L5` The key insight is that the table _is the log_, not the files — a Parquet file on disk that isn't referenced by an `add` action is invisible. That's what gives you atomicity (a half-written batch of Parquet is simply never committed), time travel (replay the log to version N), and cheap metadata (min/max stats per file live in the log, so data skipping needs no file access). It's also why you never `rm` files out of a Delta directory, and why a `_delta_log` on cheap-but-eventually-consistent storage is a correctness risk.

**`DL-2` ACID on object storage**

- `L4` Optimistic concurrency control. A writer reads the current table version, does its work, then attempts to commit by atomically creating the next numbered log file. If that filename already exists, someone else won; the writer re-reads, checks whether the conflict is real, and retries.
- `L5` The dependency is on an atomic **put-if-absent** for the log file. S3 historically had no such primitive, which is why Databricks used a commit coordination service; S3 now supports conditional writes, and Delta has `LogStore` implementations per cloud. This is the right answer to "can I run Delta outside Databricks on S3 with multiple writers" — yes, but only with the right LogStore/commit coordination, and that's a real footgun in self-managed OSS Delta.

**`DL-3` Write conflicts**

- `L4` Two concurrent writers conflict when their read/write sets overlap. Append vs append: usually fine (blind appends don't conflict). MERGE/UPDATE/DELETE vs a concurrent write to the same files: conflict → `ConcurrentModificationException` family (`ConcurrentAppendException`, `ConcurrentDeleteReadException`).
- `L5` Mitigation is partition/predicate disjointness: if two MERGEs are scoped by a `WHERE` on different partitions or clustering ranges, Delta can prove they don't overlap and both commit. So the design answer to "we need parallel writers" is to shard the writers by a partition predicate, not to add retries. Blind retry on a conflicting MERGE is how you get duplicate work or a livelock at scale.

**`DL-4` Time travel**

- `L4` `SELECT * FROM t VERSION AS OF 12` or `TIMESTAMP AS OF '2026-07-01'`; `spark.read.option("versionAsOf", 12)`. Works by replaying the log to that version and reading the file set it referenced.
- `L5` Bounded by two independent retentions: `delta.logRetentionDuration` (default 30 days — how long log entries survive) and `delta.deletedFileRetentionDuration` (default 7 days — how long removed data files survive VACUUM). Time travel to a version whose _files_ were vacuumed fails even if the log entry exists. Practical uses: audit, reproducing a report, `RESTORE` after a bad write, and diffing two versions to prove what changed — that last one is genuinely useful in a data-incident postmortem.

**`DL-5` VACUUM**

- `L4` Deletes data files no longer referenced by the current table version and older than the retention threshold (default 7 days). `VACUUM t RETAIN 168 HOURS`. Does not touch the log.
- `L5` The danger: `RETAIN 0 HOURS` breaks in-flight readers and long-running streams, and destroys time travel. Databricks blocks retention below 7 days unless you explicitly disable the safety check — and the reason that check exists is that a concurrent reader holding a file list can have files deleted out from under it. My rule: never lower retention below the longest-running job's duration plus a wide margin, and treat the retention setting as a table-level contract documented with the table, not a knob someone tweaks to save storage.

**`DL-6` Schema enforcement vs evolution**

- `L4` Enforcement: a write whose schema doesn't match is rejected — that's the default and it's a feature. Evolution: `.option("mergeSchema","true")` on append adds new columns; `overwriteSchema` on overwrite replaces the schema entirely; `MERGE ... WITH SCHEMA EVOLUTION` for merges. Type widening is limited; incompatible type changes require a rewrite.
- `L5` The policy question is more interesting than the syntax: I enable `mergeSchema` at the **bronze** boundary (where the contract is "capture whatever the source sent") and disable it at silver and gold (where a surprise column means an unreviewed contract change). `overwriteSchema` in a production job is almost always a bug — it's how someone silently drops a column that three dashboards depend on. That maps directly to what I do today with a third-party feed of 150+ attributes: schema drift from the vendor should surface as an alert and a quarantined record, not as a silently reshaped table.

**`DL-7` Delta vs Iceberg vs Hudi vs Parquet**

- `L4` Parquet: columnar file format, no transactions, no metadata layer. Delta: transaction log + Parquet, deep Databricks integration, strong MERGE. Iceberg: open table format with a manifest-tree metadata design, hidden partitioning, strong multi-engine adoption (Snowflake, Trino, Flink). Hudi: originally optimized for streaming upserts, copy-on-write vs merge-on-read table types.
- `L5` The 2026-relevant framing: the formats have converged on features, so the deciding factor is engine ecosystem and governance, not capability. Delta if the org is Databricks-centric; Iceberg if you need multiple query engines as first-class citizens. Also name UniForm — Delta tables can expose Iceberg/Hudi metadata so external engines read them — because it's the standard answer to "we already committed to Iceberg." Not knowing UniForm exists is a tell that you've only read older material.

**`DL-8` Deletion vectors**

- `L4` Instead of rewriting a whole Parquet file to remove a few rows, Delta writes a small bitmap marking deleted row positions. Readers apply it. Makes DELETE/UPDATE/MERGE much faster (merge-on-read), at the cost of a read-side merge until compaction rewrites the files.
- `L5` The tradeoff is write amplification vs read amplification, the same one Hudi's copy-on-write/merge-on-read exposes explicitly. Deletion vectors are a big win for GDPR-style scattered deletes and for MERGE-heavy CDC pipelines. The operational catch: accumulated DVs degrade reads, so you need `OPTIMIZE` (with the purge behavior) on a schedule, and older readers/engines need a protocol version that understands them — that's a compatibility question to raise before enabling it on a table other systems read.

**`DL-9` Change Data Feed**

- `L4` `delta.enableChangeDataFeed = true` makes Delta record row-level changes with `_change_type` (`insert`, `update_preimage`, `update_postimage`, `delete`), readable via `table_changes('t', startVersion, endVersion)` or as a streaming source.
- `L5` It's the clean way to propagate changes from silver to gold incrementally instead of recomputing an aggregate over the whole table. Costs: extra written data for change files, and it only applies from the version you enabled it. The alternative — reading the Delta table as a stream — gives you appends only and chokes on updates/deletes (`ignoreChanges` gives you _rewritten files_, not row-level deltas, which people conflate constantly). Knowing that distinction is a strong signal.

**`DL-10` Generated columns, constraints, column mapping**

- `L4` Generated columns: `date GENERATED ALWAYS AS (CAST(ts AS DATE))` — computed on write and usable for partition pruning even when the query filters on `ts`. `CHECK` constraints and `NOT NULL` reject bad rows at write time. Column mapping (`name`/`id` mode) decouples logical column names from Parquet physical names, enabling rename and drop.
- `L5` The generated-column trick is genuinely useful: partition by the generated date, and Delta can translate a filter on the raw timestamp into a partition filter — you get pruning without forcing every consumer to filter on the partition column. CHECK constraints are the cheapest data quality gate available and they're enforced by the engine, not by a downstream test — that's the argument for putting them on silver tables. Column mapping is a one-way protocol upgrade, so decide before external consumers attach.

**`DL-11` Shallow vs deep clone**

- `L4` `CREATE TABLE b SHALLOW CLONE a` copies only the metadata/log, pointing at the source's files — instant, near-zero storage. `DEEP CLONE` copies data files too — an independent table.
- `L5` Shallow clone is the right tool for creating a prod-data dev/test environment in seconds, or for a pre-migration safety snapshot. The hazard is lifecycle coupling: a `VACUUM` on the source can delete files the shallow clone still references, breaking it. So the rule is shallow clone for short-lived experiments, deep clone for anything that must outlive the source's retention window or cross a governance boundary.

### 3.2 Write patterns

**`DL-12` `MERGE INTO`**

- `L4` `MERGE INTO target USING source ON cond WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ...`. Delta finds candidate target files matching the condition, rewrites those files (or writes deletion vectors), and commits.
- `L5` The performance rule: **always add a static partition/clustering predicate to the ON condition** so Delta can prune target files — `ON t.id = s.id AND t.event_date >= current_date() - 3`. Without it, MERGE scans the whole target table, and that's the single most common cause of "our merge takes 4 hours." Second rule: the source must be deduplicated on the merge key, or MERGE throws on multiple matches. Third: deletion vectors and liquid clustering both materially change MERGE cost, so the answer today differs from the 2021 answer.

**`DL-13` Idempotent writes**

- `L4` Batch: `.option("txnAppId", "my-job").option("txnVersion", batch_id)` — Delta records the pair and silently skips a duplicate commit. Streaming: the checkpoint plus Delta's transactional commit gives idempotency per micro-batch; in `foreachBatch`, use the provided `batchId` as `txnVersion`.
- `L5` This is the piece most candidates miss and it maps directly to messaging idempotency, which I've built with SQS: at-least-once delivery upstream means the sink must be idempotent, and you want the dedup key to be _deterministic and derived from the batch_, not a UUID. `foreachBatch` is explicitly at-least-once — it can re-execute the same `batchId` — so any non-Delta side effect inside it (an SNS publish, an external API call) must carry its own idempotency key. That's the failure mode I'd raise in design review.

**`DL-14` SCD Type 1 vs Type 2**

- `L4` Type 1: overwrite in place, no history — a MERGE with `WHEN MATCHED THEN UPDATE SET *`. Type 2: keep history with `valid_from`/`valid_to`/`is_current` — close the old row (update `valid_to`, `is_current = false`) and insert a new one.
- `L5` The implementation detail interviewers probe: SCD2 needs _two_ actions for one changed key, but MERGE only allows one action per matched row. The standard trick is to union the source with a "staged update" copy whose merge key is nulled so it falls into the NOT MATCHED branch and inserts the new version, while the matched branch closes the old one. I'd also mention comparing a hash of the tracked columns rather than column-by-column equality, so a no-op update doesn't create a spurious version.

**`DL-15` MERGE vs `replaceWhere`**

- `L4` MERGE for row-level upserts where you only have changed rows. `df.write.mode("overwrite").option("replaceWhere", "event_date = '2026-07-29'")` for atomically replacing a well-defined slice — a full daily reload.
- `L5` `replaceWhere` is dramatically cheaper when you have the _complete_ data for a partition, because it's a bulk file swap rather than a per-row match. My selection rule: if the source is a full extract for a time slice → `replaceWhere`; if the source is a CDC stream of changed rows → MERGE. Getting a full daily extract and running MERGE on it is a very common and very expensive mistake. `replaceWhere` also gives clean idempotent reruns for backfills, which matters for `MD-6`.

**`DL-16` Concurrent writers**

- `L4` Both attempt to commit the next log version; one wins, the loser re-reads and retries or fails with a concurrency exception depending on whether the conflict is genuine. Appends to disjoint data generally both succeed.
- `L5` What I'd actually design: single-writer-per-table as the default ownership rule, with concurrency introduced deliberately via disjoint partition predicates when throughput demands it. The reason is that OCC degrades badly under contention — high-frequency small MERGEs from N writers spend more time retrying than working. If the requirement is genuinely high-concurrency writes, the honest answer is that a lakehouse table is the wrong primitive and you want a transactional store in front of it, landing to Delta in batches. That's the same conclusion I reached choosing Aurora Postgres for the transactional side and the analytical store for serving.

## System 4 — Databricks platform

### 4.1 Compute

**`DB-1` All-purpose vs job vs SQL warehouse**

- `L4` All-purpose: interactive, shared, stays alive, highest DBU rate — for notebooks and exploration. Job compute: created for a job run, terminated after, roughly half the DBU rate — for scheduled production. SQL warehouse: optimized for BI/SQL, Photon, serverless option, auto-stop — for dashboards and analysts.
- `L5` The single biggest cost lever in most orgs is that production jobs are running on all-purpose clusters because someone scheduled a notebook against their dev cluster. Enforcing job compute for scheduled work via cluster policies is a concrete, defensible cost win — usually 40–50% on that workload with no code change. That's the kind of answer that shows you'd own the platform, not just use it.

**`DB-2` Serverless vs classic**

- `L4` Serverless: Databricks manages the compute in their account, near-instant start, no idle cost, less configurability, higher per-DBU rate. Classic: runs in _your_ cloud account (VPC), full control of instance types, init scripts, networking, and instance profiles; minutes to start; you pay cloud infra + DBU.
- `L5` Decide on three axes: (a) startup latency and bursty workloads favor serverless — no 5-minute cluster spin-up for a 90-second job; (b) network/compliance requirements often force classic, because your data plane, private endpoints, and existing IAM roles live in your VPC; (c) cost is not obviously in either direction — serverless wins on idle and short jobs, classic wins on long steady jobs where you can use spot and reserved capacity. In a regulated environment, (b) usually decides it before (a) or (c) get a vote.

**`DB-3` DBR and LTS**

- `L4` Databricks Runtime = a versioned image bundling Spark, Delta, Photon, Python/Scala libraries, and Databricks-specific optimizations. Variants: standard, ML (adds ML libraries and GPU support). LTS versions get extended support windows.
- `L5` Pin production to an **LTS** version, upgrade deliberately on a schedule with a test pass, and never use `latest` in a job definition — a runtime upgrade silently changes Spark behavior, default configs, and library versions. I'd manage DBR version as code in the bundle/Terraform so an upgrade is a reviewed PR with a diff, which is exactly how I handle Terraform-managed infra today.

**`DB-4` Autoscaling**

- `L4` The cluster adds workers when tasks are pending and removes them when idle, between configured min and max. Databricks uses an optimized autoscaling that can scale down more aggressively than the vanilla Spark dynamic allocation.
- `L5` It disappoints on streaming because a continuously running micro-batch job looks busy at a steady low level — there's no idle window to trigger scale-down, and scale-up lags behind a burst by the VM provisioning time. It also fights with caching: a scaled-down node takes its cached blocks with it. So: autoscale batch and ad-hoc, fix the size for steady streaming, and set `min` high enough that the first micro-batch after a restart isn't catastrophically slow.

**`DB-5` Spot instances**

- `L4` Use spot for workers to cut cost substantially; keep the **driver on-demand**, because losing the driver kills the whole application while losing a worker only costs a task retry. Databricks supports spot-with-fallback to on-demand.
- `L5` The deeper cost is shuffle: a preempted worker takes its shuffle files with it, forcing stage recomputation, so a long shuffle-heavy job on aggressive spot can be _slower and more expensive_ than on-demand. My policy: spot for short/idempotent/retry-tolerant batch, on-demand or a high on-demand floor for long jobs, streaming, and anything with a tight SLA.

**`DB-6` Cluster policies**

- `L4` Admin-defined templates that constrain cluster creation — allowed instance types, max workers, mandatory auto-termination, required tags, DBR version pinning, spot ratios. Users create clusters only within the policy.
- `L5` They're the control plane for cost and compliance and they're what makes chargeback possible: enforce a `cost_center`/`project` tag, and now the billing system tables can attribute spend. Without policies, you get 200 all-purpose clusters with no auto-termination and no way to tell whose they are. This is the platform-ownership answer to `FM-3`.

**`DB-7` DBU and cost drivers**

- `L4` A DBU is Databricks' unit of processing consumed per hour, varying by compute type (all-purpose > jobs), by SKU/tier, and by whether Photon is on. Your bill = DBUs × rate + underlying cloud VM/storage/network cost (for classic).
- `L5` What actually drives spend, in the order I'd investigate: idle all-purpose clusters without auto-termination; production jobs on all-purpose compute; over-provisioned clusters for jobs that are I/O bound; Photon enabled on workloads it can't accelerate; and small-file layouts inflating runtime. Note the counter-intuitive one: Photon and bigger nodes cost more per hour but often reduce total cost by finishing faster — cost has to be measured as DBU-hours per job, not as node price. System tables (`system.billing.usage`) plus mandatory tags are how you make this measurable rather than anecdotal.

### 4.2 Code & delivery

**`DB-8` Workflows / Jobs**

- `L4` A job is a DAG of tasks (notebook, JAR, Python wheel, SQL, dbt, DLT pipeline, or another job) with dependency edges, per-task retries, timeouts, schedules or file-arrival/continuous triggers, and email/webhook notifications on start/success/failure/duration-exceeded.
- `L5` Design points I'd raise: set a **timeout** on every task (a hung job that never fails never alerts — the worst failure mode), use task-level retries only for genuinely transient failures and never for a non-idempotent write, share one job cluster across tasks to avoid paying N cluster startups, and use `duration exceeded` alerts as the freshness SLA signal rather than only alerting on failure.

**`DB-9` Notebooks vs wheels**

- `L4` Notebooks are great for exploration and are legitimate as thin job entry points. Production logic belongs in a Python package (wheel) or JAR: importable, unit-testable in plain pytest, versioned, code-reviewed as normal files.
- `L5` The pattern I'd defend: business logic in pure functions that take and return DataFrames and know nothing about Spark session creation or paths; a thin notebook or `entry_point` that wires config → calls the function → writes. That makes the core testable without a cluster and makes the same code runnable from a job, a backfill, or a test. Notebooks-as-production fails on diffability, imports, and testing — I'd say that directly rather than hedge.

**`DB-10` Databricks Asset Bundles**

- `L4` DABs define jobs, pipelines, clusters, and notebooks declaratively in `databricks.yml`, with per-target (dev/staging/prod) overrides, deployed via `databricks bundle deploy`. Infrastructure-as-code for workspace assets.
- `L5` The problem they solve is that job definitions used to live in the UI — untracked, undiffable, un-promotable, and different in every environment. DABs put them in git next to the code they run. Relative to Terraform: I'd use Terraform for the account-level and long-lived infrastructure (workspaces, Unity Catalog metastore, external locations, IAM) and DABs for the application-level assets that ship with each release. Mixing them at the same layer is where teams get into state conflicts.

**`DB-11` CI/CD**

- `L4` Code in git, Databricks Git folders/Repos for the workspace view. Pipeline: lint → unit tests (pytest, local Spark or Databricks Connect) → build wheel → `bundle deploy` to dev → integration test against a dev catalog → promote to staging → prod. Environment separation via separate catalogs and/or workspaces.
- `L5` Two things I'd insist on: (a) integration tests run against _real Delta tables in a dev catalog seeded by shallow clone of prod_, because Spark bugs live in data shape, not in logic; (b) promotion changes only configuration — catalog name, cluster size, schedule — never code, which is what makes "it worked in staging" mean something. Secrets come from secret scopes backed by the cloud KMS, never from bundle variables.

**`DB-12` `dbutils`, widgets, secrets**

- `L4` `dbutils.widgets` parameterizes notebooks (job parameters map to widgets). `dbutils.fs` for file ops, `dbutils.notebook.run` for chaining, `dbutils.jobs.taskValues` for passing values between tasks. Secrets: `dbutils.secrets.get(scope, key)`, backed by a Databricks-managed or cloud KMS-backed scope.
- `L5` The trap: `dbutils.secrets.get` returns a redacted value when printed, but the redaction is display-level — writing a secret into a DataFrame, a log line built by string concatenation, or an exception message can leak it. Rule: secrets go straight into a client constructor and nowhere else. Also, `dbutils` doesn't exist outside Databricks, so any code that calls it isn't unit-testable — another argument for the thin-entry-point structure in `DB-9`.

**`DB-13` Delta Live Tables**

- `L4` DLT is declarative pipeline framework: you define tables/views with `@dlt.table` or SQL, declare dependencies implicitly through references, and DLT handles orchestration, incremental processing, retries, checkpoints, and data quality via `EXPECT` constraints. Supports streaming tables, materialized views, and `APPLY CHANGES INTO` for CDC/SCD.
- `L5` Where it wins: teams that would otherwise hand-roll checkpoint management, dependency ordering, and quality checks; and CDC, where `APPLY CHANGES` replaces a lot of fragile MERGE code. Where I'd **not** use it: pipelines needing arbitrary imperative control flow, tight control over compute/config, or portability off Databricks — DLT is a hard lock-in, and its opinionated model fights you when your problem doesn't fit. It also has its own compute billing tier. Naming the lock-in explicitly is the L5 move; enthusiasm without it reads as a marketing answer.

### 4.3 Governance

**`DB-14` Unity Catalog object model**

- `L4` Metastore (one per region, attached to workspaces) → catalog → schema (database) → table/view/volume/function/model. Three-level namespace: `catalog.schema.table`. Grants use standard SQL `GRANT ... ON ... TO`, with privileges inheriting down the hierarchy.
- `L5` The point of UC is that identity and permissions live _above_ the workspace, so the same table has one permission model regardless of which workspace, cluster, or engine reads it — that replaces the old model where cluster-scoped instance profiles decided access, and a user with cluster-create rights could bypass everything. The standard environment pattern is catalog-per-environment (`dev`/`staging`/`prod`) rather than workspace-per-environment, which makes promotion a config change.

**`DB-15` Managed vs external tables**

- `L4` Managed: UC owns the data location and lifecycle — `DROP TABLE` deletes the data. External: you specify a `LOCATION` in your own storage; drop removes only the metadata. Access to cloud storage goes through a **storage credential** (a cloud IAM role) bound to an **external location** (a path), and grants on the external location control who can create tables there.
- `L5` I'd default to managed tables — you get automatic layout optimization, predictive optimization, and simpler lifecycle — and reserve external for data that other systems must write directly, or existing data you can't move. The security argument for the credential/location indirection is the one to make: users never hold cloud credentials, so there's no path to read the bucket around UC's row/column controls. That's exactly the property an auditor asks for.

**`DB-16` Row filters, column masks, dynamic views**

- `L4` Row filter: a UDF attached to a table that returns a boolean, applied as a predicate per query. Column mask: a UDF applied to a column's value, e.g. redact unless the caller is in a group. Dynamic views: a view using `current_user()` / `is_account_group_member()` in its logic.
- `L5` Filters and masks are strictly better than dynamic views for new work because they attach to the table, so there's no way to route around them by querying the base table — with views you must also revoke base-table access, and someone eventually forgets. In my current work the analogue is role- and document-type-based access control resolved in application code; the lakehouse version pushes that same policy into the data layer, which is more durable because it can't be bypassed by a new consumer.

**`DB-17` Lineage, audit, system tables**

- `L4` UC captures table- and column-level lineage automatically for queries run through it, exposes it in the UI and via API. Audit logs record who did what. System tables (`system.access.audit`, `system.billing.usage`, `system.query.history`, `system.lakeflow.*`) make governance and cost queryable as SQL.
- `L5` Column-level lineage is the thing that makes impact analysis tractable: "we're changing this vendor field — what breaks?" goes from a week of grep to a query. And system tables are what turn cost management from a monthly surprise into a monitored metric — I'd build a dashboard on `system.billing.usage` grouped by the mandatory tags from `DB-6`, with an alert on week-over-week deltas. That pairs the governance answer with the cost answer, which is what an owner does.

**`DB-18` Delta Sharing**

- `L4` An open protocol for sharing live Delta tables across organizations or clouds without copying — the provider grants a share, the recipient reads directly with any Delta Sharing client (including non-Databricks).
- `L5` It replaces the "nightly extract to a SFTP/S3 bucket per partner" pattern, which is where stale data, versioning drift, and access-revocation problems come from. The governance win is that revocation is immediate and access is auditable, versus a copy you can never take back. In a financial data context — distributing instrument or reference data to counterparties — that's the natural fit, and the honest caveat is that the recipient side needs a compatible client and that egress cost is still yours.

## System 5 — Pipeline design

**`MD-1` Medallion architecture**

- `L4` Bronze: raw ingested data, append-only, source schema preserved, plus ingest metadata (source file, ingest timestamp, batch id). Silver: cleansed, deduplicated, type-cast, conformed, joined to reference data — the trustworthy operational layer. Gold: business-level aggregates and dimensional models shaped for consumption.
- `L5` The layers are a _contract_ boundary, not a naming convention. Bronze's contract is "we never lose what the source sent." Silver's is "this is correct and deduplicated, and its schema is stable enough to build on." Gold's is "this answers a specific business question and its numbers match the report." The failure mode I've seen is silver tables that are actually gold — business logic baked into what everyone treats as the shared clean layer — and then two teams need contradictory logic and there's nowhere to put it. My current pipeline maps cleanly: API ingest → bronze; Glue ETL cleansing 150+ attributes → silver; the normalized serving views consumers query → gold.

**`MD-2` Why bronze stays immutable**

- `L4` So you can replay. If silver logic was wrong, you fix the transform and rebuild from bronze without re-fetching from the source — which may not even be possible if the source is an API with a retention window.
- `L5` It's also the audit and debugging artifact: when a downstream number is wrong, bronze is what proves whether the source sent bad data or we transformed it badly. That distinction ends most cross-team arguments in one query. The cost is storage, which is the cheapest thing in the stack — and you can manage it with tiering and retention rather than by deleting the raw record.

**`MD-3` Idempotency and replay in batch**

- `L4` A rerun of the same logical batch must produce the same table state. Mechanisms: `replaceWhere` on a deterministic partition, MERGE on a stable business key, or Delta's `txnAppId`/`txnVersion`. Never `append` a batch that could rerun.
- `L5` The requirement is that the _unit of work_ be identified by something deterministic — a business date, a source batch id — not by wall-clock "now," because a retry at 00:05 must target the same slice as the run at 23:55. That's the same discipline as an idempotency key on a payment. And idempotency has to extend past the table write: if the job also publishes a notification or updates a downstream index, those need their own dedup key or you get duplicate side effects on every retry.

**`MD-4` Late-arriving data**

- `L4` Batch: process by _event_ time, not processing time, and reprocess a trailing window (e.g. last 3 days) every run so late records land in the right slice. Streaming: watermarks define how late is too late; records past the watermark are dropped from stateful operations.
- `L5` The design decision is explicit: what's the lateness bound, and what happens past it? Silent drops are unacceptable in a financial context — I'd route past-watermark records to a quarantine table and alert on volume, so "we're systematically losing data from one source" is visible instead of invisible. The trailing-window reprocess is why `replaceWhere` on a date range beats append: rerunning the last 3 days must be idempotent.

**`MD-5` Data quality gates**

- `L4` Three postures: fail-fast (abort the run — right for a broken schema or a catastrophic row count drop), quarantine (route bad rows to a side table, keep processing — right for individual malformed records), fail-open (log and continue — right almost never, but sometimes for non-critical enrichment). Tools: Delta `CHECK` constraints, DLT `EXPECT`/`EXPECT OR DROP`/`EXPECT OR FAIL`, or explicit filter + write to a `_rejects` table.
- `L5` The rule I'd apply: fail-fast on anything that indicates the _pipeline_ is broken (schema mismatch, row count outside a band, a required join producing 0 matches), quarantine anything that indicates _a record_ is broken. Conflating them is how you get either a pipeline that dies nightly over three bad rows, or one that silently publishes a table missing 40% of its data. And quarantine without an alert and an owner is just a slower form of data loss.

**`MD-6` Backfill design**

- `L4` Backfill must be idempotent and partitioned so it can run in slices, must not break concurrent readers, and must be rate-limited so it doesn't starve the production pipeline of compute. Use `replaceWhere` per date slice; run on separate job compute.
- `L5` Two things I'd add for real safety: write to a shadow/clone table first and swap or diff before touching the served table, so a bad backfill is a no-op rather than an incident; and version-stamp the run so time travel can show exactly which rows a given backfill changed. Also worth naming the concurrency conflict — a backfill MERGE and the nightly MERGE hitting the same partitions will fight under OCC, so they need either disjoint predicates or a scheduling lock.

**`MD-7` Dimensional modeling on a lakehouse**

- `L4` Yes. Star schemas still serve BI best — a fact table with conformed dimensions is what makes a semantic layer and a self-service tool comprehensible. What changed is that storage is cheap and joins are fast enough that heavy denormalization is no longer mandatory.
- `L5` The nuance: dimensional modeling is now a _gold-layer presentation_ choice, not a physical necessity. Silver stays normalized and close to the source; gold materializes the star for consumption. And some of the old rules relax — surrogate key generation via monotonic sequences is awkward in a distributed engine, so hashed business keys are usually the better choice, and SCD2 is a MERGE pattern (`DL-14`) rather than an ETL tool feature.

**`MD-8` Orchestration**

- `L4` Databricks Workflows: native, no extra infrastructure, task-level retries, cheapest path, tight integration with clusters and DLT. Airflow: better for heterogeneous DAGs spanning non-Databricks systems, richer scheduling semantics, dynamic DAGs, but it's infrastructure you own.
- `L5` Recommendation: **Workflows by default**, Airflow only when the DAG genuinely spans systems Databricks doesn't run — an on-prem extract, an API call, a downstream warehouse load. The common anti-pattern is Airflow used purely as a scheduler that fires one Databricks job, which buys nothing and adds an operational component. If both exist, keep the boundary clean: Airflow owns cross-system sequencing, Workflows own everything inside Databricks.

**`MD-9` Testing a Spark pipeline**

- `L4` Three tiers. Unit: pure transform functions taking/returning DataFrames, tested against small in-memory fixtures with local Spark. Integration: the real job against a dev catalog with seeded Delta tables. Data tests: assertions on the output — row counts, null rates, uniqueness of keys, referential integrity, reconciliation totals.
- `L5` The structural prerequisite is `DB-9` — logic in importable pure functions, no session creation or `dbutils` inside them. For fixtures, small handwritten DataFrames beat sampled prod data because they encode the edge case you're testing. And I'd separate "tests that gate a deploy" (unit + integration, in CI) from "tests that gate a _publish_" (data tests, in the pipeline, blocking the gold write) — they fail for different reasons and need different owners. That's the same split as unit tests versus the mock-data end-to-end harness I built for our platform.

## System 6 — Streaming

**`ST-1` Micro-batch model and triggers**

- `L4` Structured Streaming runs a query repeatedly over new data as an incremental micro-batch, maintaining offsets and state. Triggers: default (as fast as possible), `processingTime="5 minutes"`, `Trigger.AvailableNow` (process all available data in batches, then stop), `Trigger.Once` (deprecated in favor of AvailableNow), and continuous processing (experimental, rarely used).
- `L5` The important framing: streaming here is _incremental batch_, not per-record. That means the tuning levers are batch-shaped — `maxFilesPerTrigger`/`maxBytesPerTrigger` to bound batch size, and the trigger interval as your latency/cost dial. A 5-minute trigger on a cluster you'd otherwise keep idle is usually cheaper and simpler than "real" streaming, and most "we need streaming" requirements are actually "we need fresher than daily."

**`ST-2` Checkpoints**

- `L4` The checkpoint directory holds source offsets (what's been read), a commit log (what's been fully processed), the query metadata, and the state store for stateful operations. It's what makes restart resume rather than restart-from-scratch.
- `L5` Deleting a checkpoint is a production incident because the stream restarts from the source's configured start position — reprocessing everything (duplicates downstream if the sink isn't idempotent) or skipping everything, depending on `startingOffsets`. Checkpoints are also tied to the query's plan: some code changes (adding a stateful operator, changing the aggregation key) are not checkpoint-compatible and require a planned reset with a documented reprocessing strategy. Treat "is this change checkpoint-compatible" as a required review question — it's the streaming equivalent of a schema migration.

**`ST-3` Exactly-once**

- `L4` End-to-end exactly-once requires a replayable source (offset-tracked) plus an idempotent or transactional sink. Delta sinks give it because the micro-batch commit is atomic and offset-linked. It is _effectively-once output_, not exactly-once processing — the batch can be recomputed.
- `L5` The honest caveat is `foreachBatch`: it's at-least-once, so the same `batchId` can execute twice, and any external side effect inside it must be idempotent on its own. This is exactly the guarantee model I work with in SQS — at-least-once delivery, dedup enforced at the sink with a unique constraint. I'd say plainly: "exactly-once" is a property of the sink contract, not something the streaming engine grants you for free.

**`ST-4` `foreachBatch`**

- `L4` Gives you each micro-batch as a normal DataFrame plus its `batchId`, so you can use batch-only operations — MERGE, multi-sink writes, writes to JDBC/external systems — inside a streaming query.
- `L5` It's the workhorse because the native streaming Delta sink only appends; anything upsert-shaped (CDC into silver) has to go through `foreachBatch` + MERGE. Two rules: `.persist()` the batch DataFrame if you write it to more than one sink, or you recompute the whole upstream per sink; and use the `batchId` as your idempotency token (`txnVersion`, or a dedup key for an external system) since it's stable across retries.

**`ST-5` Auto Loader**

- `L4` `cloudFiles` source for incrementally ingesting new files from object storage, with schema inference and evolution, and scalable file discovery. Two discovery modes: directory listing (default, simple) and file notification (SNS/SQS on AWS, Event Grid on Azure) where the cloud pushes new-file events into a queue.
- `L5` The mode choice is the real question: directory listing degrades as the directory grows — listing millions of objects per trigger dominates runtime — so file notification is the answer at scale, at the cost of provisioning and owning the notification infrastructure. That's directly my existing world: SNS→SQS fan-out with a DLQ, IAM permissions, and queue monitoring. I'd also flag that Auto Loader keeps its own RocksDB-backed file registry, so it won't reprocess a file even if the notification is redelivered — and the `_rescued_data` column is where unexpected fields go instead of being dropped, which is the right bronze-layer behavior for a vendor feed with drifting schema.

**`ST-6` Watermarks and state**

- `L4` `withWatermark("event_time", "10 minutes")` tells Spark how late data can be, so it can drop state older than max-seen-event-time minus the threshold. Without a watermark, stateful aggregations and stream-stream joins grow state without bound. State is kept in a state store, checkpointed each batch.
- `L5` The tuning reality: state size is the main streaming failure mode. RocksDB state store (default on recent DBR) keeps state off-heap on local disk, so it handles far larger state than the legacy HDFS-backed in-memory store without GC death — that's the fix to recommend when someone reports growing batch durations and executor OOM on a stateful stream. Also, changing a watermark or a stateful operator on an existing query is a checkpoint compatibility issue (`ST-2`).

**`ST-7` Stream-static vs stream-stream joins**

- `L4` Stream-static: each micro-batch joins against the current snapshot of a static table — cheap, no state, but the static side is re-read per batch (broadcast it if small). Stream-stream: requires watermarks on both sides plus a time-range condition, and maintains buffered state for both sides.
- `L5` A subtlety worth stating: in a stream-static join, updates to the static table are picked up on the _next_ micro-batch, so results aren't reproducible against a fixed snapshot — for auditability you may need the dimension versioned and joined by effective date rather than by "current." Stream-stream joins are where state blows up, so I'd push back on them unless the requirement genuinely needs correlating two live streams; often the right design is landing one stream to Delta and doing a stream-static join.

**`ST-8` `Trigger.AvailableNow`**

- `L4` Processes all currently available data in multiple micro-batches (respecting rate limits) and then terminates. Combines streaming's incremental bookkeeping with batch's finite lifecycle.
- `L5` It's underused and it's often the right answer: you keep the exact-once checkpoint/offset machinery of streaming, but run on a scheduled job cluster that terminates — so you pay for minutes, not for a 24/7 cluster, and you get restartability and incremental semantics for free. For a requirement of "fresh within 15 minutes," a scheduled AvailableNow job is usually cheaper and more operable than a continuously running stream. I'd lead with this as the cost-conscious recommendation.

**`ST-9` Streaming MERGE into Delta**

- `L4` `readStream` → `foreachBatch(lambda df, batch_id: ...)` → dedupe the batch on the key, then `MERGE INTO target USING batch ON key AND partition_predicate`, with `txnVersion = batch_id` for idempotency.
- `L5` The ceiling is that MERGE rewrites files (or writes deletion vectors) and takes an OCC commit per batch, so a 10-second trigger against a large target table will spend most of its time on merge overhead. Levers, in order: widen the trigger interval so batches are bigger and merges fewer; scope the merge with a tight partition/clustering predicate; enable deletion vectors; and if throughput still doesn't fit, switch to append-only bronze plus a periodic compaction/merge into silver — decoupling ingest latency from merge cost. That "append fast, merge on a schedule" restructuring is the answer I'd give if they push on scale.

## System 7 — Migration & comparison

**`MG-1` Glue vs Databricks**

- `L4` Both are managed Spark. Glue: serverless, tightly integrated with AWS (Glue Catalog, IAM, S3, EventBridge), pay per DPU-hour, minimal cluster management, weaker interactive/notebook experience, older Spark versions historically, and a job-shaped mental model. Databricks: richer runtime (Photon, Delta optimizations, disk cache), far better interactive and collaborative tooling, Unity Catalog governance, DLT, MLflow — at a higher per-unit cost and as a separate vendor.
- `L5` Where I'd say each wins: Glue is fine and cheaper for straightforward scheduled ETL that's already inside AWS and doesn't need interactivity or a governance layer. Databricks earns its premium when you have many teams sharing data (governance and lineage become the real product), when interactive analytics and ML sit alongside the pipelines, or when query performance on large tables matters enough that Photon and Delta layout optimization pay for themselves. My honest experience note: I've built the Glue side of this — SQS-triggered PySpark jobs cleansing a 150-attribute instrument feed into Aurora, DynamoDB, and OpenSearch — so the Spark and pipeline reasoning transfers directly; what's new to me on Databricks is the platform layer, not the engine.

**`MG-2` EMR vs Databricks**

- `L4` EMR gives you the open-source stack on managed EC2 — maximum control, lowest license cost, and maximum operational burden (you tune YARN, manage versions, build your own notebook/governance story). Databricks bundles a tuned runtime, governance, and tooling at a per-DBU premium.
- `L5` The decision is really "do you have a platform team." EMR's TCO looks lower until you count the engineers maintaining bootstrap actions, Spark upgrades, and a homegrown metastore. EMR Serverless narrows the operational gap. I'd choose EMR when the workload is a small number of stable, high-volume jobs run by a team that already owns Spark expertise, and Databricks when the user base is broad and heterogeneous.

**`MG-3` Snowflake vs Databricks SQL**

- `L4` Snowflake: mature warehouse, excellent SQL performance and concurrency, proprietary storage format (though it now reads Iceberg), simpler for pure BI. Databricks SQL: warehouse-grade SQL over open Delta tables, unified with the Spark/ML/streaming stack, no separate copy of the data.
- `L5` The convergent-competitor framing: both are moving toward the other's territory, so it's rarely a pure capability comparison. Choose Databricks when the same data must serve SQL, streaming, and ML and you don't want two copies and two governance models — the "one copy, many engines" argument. Choose Snowflake when the workload is overwhelmingly BI with high concurrency and a non-engineering analyst population, where its operational simplicity is real. I would not claim a large performance gap either way in an interview; benchmark claims from both vendors are contested and saying so is more credible than picking a side.

**`MG-4` When _not_ to migrate off Aurora/Redshift**

- `L4` Don't move OLTP to a lakehouse — Delta is not a transactional row store; single-row lookups, high-concurrency point writes, and sub-100 ms latency belong in Postgres/DynamoDB. Don't move a small warehouse that already meets its SLA and cost, purely for architectural fashion.
- `L5` The line I'd draw: if the access pattern is "fetch one entity by key, thousands of times a second," or "many small transactional writes," the lakehouse is the wrong primitive at any scale. In my current platform that's exactly why the serving layer is Aurora Postgres and DynamoDB with OpenSearch for search, while the heavy transformation is Spark — and I'd bring the same split to a lakehouse design rather than trying to make Delta serve an API. Saying "here's where I would _not_ use the thing you're hiring me for" is usually the strongest credibility move available.

**`MG-5` Porting a Glue PySpark job to Databricks**

- `L4` Concretely: (1) replace `GlueContext`/`DynamicFrame` with plain `SparkSession`/DataFrame — `DynamicFrame` has no equivalent, so its schema-resolution behavior (`resolveChoice`) becomes explicit casts and a rescued-data column; (2) replace Glue job bookmarks with Auto Loader or Structured Streaming checkpoints; (3) replace Glue Catalog references with Unity Catalog three-level names; (4) replace `getResolvedOptions` with widgets/job parameters; (5) write to Delta instead of Parquet, and swap partition-overwrite logic for `replaceWhere` or MERGE; (6) define the job in a Databricks Asset Bundle instead of Glue job config/CloudFormation.
- `L5` Sequencing matters more than the mechanics: I'd port one job end-to-end as a vertical slice — including the bundle, CI, and a reconciliation test that diffs Databricks output against the Glue output for the same input window — before porting the rest. That proves the whole toolchain and gives you a correctness gate. I'd also decide the file layout deliberately at migration time rather than replicating the Glue partitioning, since that's the one-time cheap moment to move from Hive partitioning to liquid clustering. And I'd flag the two things that surprise people: bookmarks have no drop-in equivalent, and IAM-based S3 access becomes storage credentials + external locations, which is a security review, not a code change.

**`MG-6` Cost-model warnings for a stakeholder**

- `L4` You now pay two vendors — DBUs to Databricks plus cloud infrastructure (for classic compute). Interactive clusters cost more per hour than job clusters. Idle clusters without auto-termination cost real money. Photon and serverless have higher per-unit rates.
- `L5` The honest framing I'd give a stakeholder up front: expect the raw compute line to go _up_ versus Glue, and justify it on total cost — engineering time, governance, and query performance — not on infra price. Then make it measurable from day one: mandatory cost-center tags via cluster policies, a dashboard on `system.billing.usage`, job compute enforced for scheduled work, and auto-termination on everything. Migrations that go badly financially are almost always the ones where nobody set up attribution until month three.

## System 8 — Failure modes & ownership

**`FM-1` Nightly job fails at 3am**

- `L4` (1) Read the failure: which task, which stage, what exception. (2) Classify: transient infra (spot preemption, cloud API throttle) → retry; data issue (schema mismatch, bad record, missing upstream partition) → fix data or quarantine; resource (OOM, disk full) → resize/repartition; upstream dependency missing → check the producer. (3) Fix or safely rerun. (4) Confirm downstream consumers.
- `L5` The part that separates an owner: I don't rerun until I know whether the job is idempotent, because a blind rerun of a non-idempotent append duplicates data and turns a delayed table into a wrong table. Sequence is: assess blast radius → decide rerun vs restore-and-rerun → communicate expected freshness to consumers → fix → then write the follow-up so the same failure alerts earlier next time. On Delta, `DESCRIBE HISTORY` tells me exactly which version the failed run left behind, and `RESTORE` gives me a clean starting point.

**`FM-2` Table partially written or wrong**

- `L4` Options in order: (a) `DESCRIBE HISTORY` to find the last good version; (b) `RESTORE TABLE t TO VERSION AS OF n` — atomic, and itself a new version so it's reversible; (c) if the bad data spans one slice, `replaceWhere` overwrite of that slice from a corrected rerun; (d) full rebuild from bronze if the transform logic was wrong.
- `L5` Note first that a _partial_ write shouldn't be possible on Delta — the commit is atomic, so an interrupted job leaves uncommitted files, not a half table. If the table looks partially written, the real diagnosis is usually a multi-statement job that committed step 1 and failed at step 2, which is an argument for making the whole publish one atomic commit (write to a staging table, then atomic swap/`replaceWhere`) rather than several. Then: restore, verify with a reconciliation query against the source, notify consumers of the versions affected, and record which downstream artifacts need rebuilding.

**`FM-3` Spend jumped 4×**

- `L4` Query `system.billing.usage` grouped by workspace, SKU, cluster, and tag, comparing this period to last. Usual suspects: a new or runaway job, all-purpose clusters without auto-termination, a job moved off job compute, autoscale max raised, a data volume increase, or a streaming job left running.
- `L5` I'd separate "more work" from "less efficient work": DBU-hours per job run, trended, tells you which. A job whose runtime doubled at constant input is a performance regression (`PF-1`), not a cost problem, and the fix is different. Then the durable fix is structural — cluster policies enforcing auto-termination and job compute, mandatory tags for attribution, and a weekly alert on spend deltas — because a one-time cleanup regresses within a quarter.

**`FM-4` Downstream numbers are wrong**

- `L4` Bisect the pipeline: reconcile counts and key aggregates at each layer against the layer above — source vs bronze, bronze vs silver, silver vs gold. The first layer where they diverge localizes the bug. Use time travel to compare the current version to the last known-good.
- `L5` What makes this fast is having the reconciliation queries pre-built as scheduled data tests (`MD-9`), so the answer to "where did it break" is a dashboard, not an investigation. Column-level lineage from UC narrows which transform touches the bad field. And I'd resist the pressure to patch gold directly — fixing the symptom at the presentation layer means the same wrong number reappears next run and now there are two sources of truth.

**`FM-5` Pipeline SLA**

- `L4` Three dimensions: **freshness** (data is no older than X), **completeness** (all expected records/partitions present), **correctness** (values pass defined quality checks and reconcile to source). Each needs a measurable metric and a threshold.
- `L5` The distinction that matters is SLA vs SLO vs the internal budget you actually run to — publish the SLA loosely to consumers, alert internally well before it's breached. Freshness is measured by max event/ingest timestamp in the table, not by "the job succeeded," because a job can succeed on zero rows. That's the most common gap I'd fix first: success-based alerting misses the silent-empty failure entirely.

**`FM-6` What to page on**

- `L4` Page: job failure on a business-critical pipeline, freshness SLA breach, completeness check failure (row count outside band), and a hard data-quality gate failure that blocked a publish. Dashboard only: cost trends, small-file counts, task skew, spill, quarantine volume below threshold, individual retried tasks.
- `L5` The principle is page on _consumer-visible_ conditions, dashboard on _engineer-relevant_ ones — otherwise the pipeline that self-heals via retry wakes someone up and the alert gets muted, and then the real one gets missed too. Two specifics I'd add: alert on duration-exceeded, not just failure, because a hung job never fails; and alert on quarantine _rate change_, not absolute volume, since a steady 0.1% reject rate is normal and a jump to 5% means the vendor changed something.

## 3.1 Testable job structure (the `DB-9` pattern)

```python
# src/instruments/transforms.py  — pure, no session, no dbutils, unit-testable
from pyspark.sql import DataFrame, functions as F, Window

def cleanse_instruments(raw: DataFrame) -> DataFrame:
    """Bronze -> silver. Deterministic, no side effects."""
    return (
        raw
        .withColumn("instrument_id", F.trim(F.col("instrumentId")))
        .withColumn("issue_date", F.to_date("issueDate", "yyyy-MM-dd"))
        .withColumn("notional", F.col("notional").cast("decimal(18,2)"))
        .filter(F.col("instrument_id").isNotNull())
    )

def dedupe_latest(df: DataFrame, key: str, order_by: str) -> DataFrame:
    """Keep the newest record per key — required before MERGE (DL-12)."""
    w = Window.partitionBy(key).orderBy(F.col(order_by).desc())
    return (df.withColumn("_rn", F.row_number().over(w))
              .filter(F.col("_rn") == 1)
              .drop("_rn"))

def split_valid(df: DataFrame):
    """Quarantine pattern (MD-5): returns (good, rejected)."""
    ok = F.col("instrument_id").isNotNull() & (F.col("notional") >= 0)
    return df.filter(ok), df.filter(~ok).withColumn("_reject_ts", F.current_timestamp())
```

from delta.tables import DeltaTable

def upsert(batch_df, batch_id: int):
    batch_df.persist()                                    # ST-4: reused below
    deduped = dedupe_latest(batch_df, "instrument_id", "ingest_ts")
    (DeltaTable.forName(spark, "main.silver.instruments").alias("t")
        .merge(deduped.alias("s"),
               # DL-12: static predicate so Delta prunes target files
               "t.instrument_id = s.instrument_id AND t.issue_date >= current_date() - 30")
        .whenMatchedUpdateAll(condition="s.ingest_ts > t.ingest_ts")
        .whenNotMatchedInsertAll()
        .execute())

    .writeStream

## 3.4 SCD Type 2 MERGE (`DL-14`)

```sql
-- The two-action trick: union a null-keyed copy so it falls into NOT MATCHED
MERGE INTO main.silver.dim_issuer AS t
USING (
  SELECT s.issuer_id AS merge_key, s.* FROM staged s
  UNION ALL
  SELECT NULL AS merge_key, s.*                 -- forces the INSERT of the new version
  FROM staged s JOIN main.silver.dim_issuer d
    ON s.issuer_id = d.issuer_id
   AND d.is_current = true
   AND d.row_hash <> s.row_hash                 -- hash compare, not column-by-column
) AS src
ON t.issuer_id = src.merge_key AND t.is_current = true
WHEN MATCHED AND t.row_hash <> src.row_hash THEN
  UPDATE SET t.is_current = false, t.valid_to = src.effective_ts
WHEN NOT MATCHED THEN
  INSERT (issuer_id, name, row_hash, valid_from, valid_to, is_current)
  VALUES (src.issuer_id, src.name, src.row_hash, src.effective_ts, NULL, true);
```

## 4.1 The honest-framing script

You have **Glue + PySpark**, not Databricks. Handle it the same way we handled Kafka: pivot to the adjacent real experience, don't fake depth.

> "My Spark experience is on AWS Glue rather than Databricks — I own a PySpark ETL that cleanses 150+ attributes off a 30k-instrument/day feed into Aurora, DynamoDB and OpenSearch, triggered off SQS. So the engine, the tuning, the partitioning and skew work, and the pipeline design all transfer directly. What's new to me on Databricks is the platform layer — Unity Catalog, DLT, the DBU cost model, and Delta's internals versus plain Parquet — and I've worked through those deliberately because the layout and governance decisions are where the leverage is."

Rules:

- Never say "I've used Databricks" or list it as a skill. Say **"Spark on Glue"** and let them map it.
- When asked something purely platform-specific, answer the mechanism and mark the boundary: _"Here's how liquid clustering works and why I'd choose it over Z-ORDER — I haven't run it in production, my equivalent decision was partition design on Glue/S3."_
- Volunteer the transfer, don't wait to be caught. Overclaiming dies on the second follow-up.
