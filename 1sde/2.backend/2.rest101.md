## 1. What REST actually is (101)

### L4 knowledge

- **Why:** bespoke remote calls made clients depend on service-specific operations and interaction rules.
- **Mechanism:** REST constrains how components exchange resource representations so intermediaries can understand the interaction.
- **Client–server:** separate presentation from data and business logic.
- **Stateless requests:** send the context needed to interpret each request.
  - Resource state remains on the server.
  - Conversation state is not hidden in one server instance between requests.
- **Cacheability:** identify whether a response may be reused.
- **Uniform interface:** identify resources, manipulate representations, send self-descriptive messages, and expose hypermedia controls.
- **Layering:** gateways and proxies participate without clients knowing the entire topology.
- **Optional code on demand:** a server may extend client behavior with executable code.
- **Use:** public or partner resource APIs and stable business operations.

```text
Client -> gateway/authentication -> controller -> application service
                                               |-> authorization/domain rules
                                               |-> repository -> Aurora
                                               |-> cache
                                               `-> transactional outbox -> consumers
Client <- status + headers + representation/error <- response mapper
```

### L5 extra

- Statelessness removes affinity to one application instance.
  - Database contention, shared dependencies, and admission control still limit scaling.
- Common resource-oriented HTTP APIs implement only part of REST's constraints.
  - Explain which properties the actual API relies on instead of claiming full hypermedia compliance.
- Safe methods must not request a business mutation.
  - Incidental logging or accounting does not invalidate safety.
  - A GET that approves a payment is unsafe because prefetchers or retries can trigger it.
- Define shared API conventions and enforce them in review or CI.
  - This prevents every service from inventing its own pagination and error contract.
- **Related:** [Q5: HATEOAS](#rest-q5).

## 2. Anatomy — what a request consists of

### L4 knowledge

```http
POST /v1/instruments/abc123/corrections HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
Accept: application/json
Idempotency-Key: <one-key-per-intent>

{"field":"couponRate","newValue":"4.25","reason":"vendor typo","expectedOverlayVersion":17}
```

- **Method:** the intended operation and its HTTP semantics.
- **Path:** the target resource or collection.
- **Query:** filters, sorting, pagination, and projection for the selected collection.
- **Headers:** authentication, media types, conditional requests, retry guidance, and tracing.
- **Body:** the representation or action input.
- **GET/DELETE body:** avoid it in portable APIs because HTTP assigns no generally defined semantics to that content.

### 2.1 What the UI must send (headers/body checklist)

- `Authorization`: credentials appropriate to the API's authentication contract.
- `Content-Type`: format of the sent body; unsupported types can receive `415`.
- `Accept`: formats the client can receive; unavailable representations can receive `406`.
- `Idempotency-Key`: stable across retries of one logical write.
- `If-Match`: strong validator of the resource being updated.
- `If-None-Match`: validator for a conditional read.
- Trace context or correlation ID: propagate a validated value, or let the server create one.
- Body: typed business data; omit fields the caller is not permitted to write.

### 2.2 What the server sends back

- Status: whether the request succeeded, failed, or was accepted for later execution.
- `Content-Type`: response format.
- `Location`: created-resource or operation-status URL when the API contract provides one.
- `ETag`: validator of the selected representation.
- `Cache-Control`: explicit storage and reuse policy.
- `Retry-After`: guidance for throttling or temporary unavailability when available.
- Correlation ID: exposed for support and linked to internal diagnostics.

### L5 extra

- URLs appear in browser history and infrastructure logs.
  - Put secrets and sensitive search criteria in appropriately protected headers or bodies.
  - Scrub those locations from logs too.
- Complex search may justify POST with a body.
  - Ordinary HTTP caches do not key on the search body.
  - A stored search resource can supply a later GET URL, but its access control and retention need an explicit contract.
- Bound page sizes, date ranges, filter cardinality, body size, and batch size.
  - Choose limits from measured query and dependency costs.
- Strict unknown-field rejection helps catch typos in write DTOs.
  - Tolerant response readers help additive evolution.
  - Choose the policy separately for each direction.
- Generate clients from a reviewed contract, then test required headers and retry behavior.
- **Related:** [Q3: parameter placement](#rest-q3).

## 3. What a "resource" is

### L4 knowledge

- **Resource:** an identifiable domain concept.
- **Representation:** the JSON or other view exchanged with clients.
- A resource need not map one-to-one to a database table.
  - `/instruments/{id}` can combine vendor state, correction state, and computed fields.
- Collections use plural names.
- Nested paths express meaningful ownership.
- Independently addressable children can use top-level paths with parent filters.

### L5 extra

- Evaluate three boundaries when choosing resources:
  - **Consistency:** what must change atomically?
  - **Authorization:** who may read or modify each part?
  - **Caching:** what changes together and can share a validator?
- These are design pressures, not a requirement that every transaction or cache entry equal one resource.
- Separate vendor records from human corrections when they have different writers and retention rules.
  - Re-ingestion updates vendor data.
  - Corrections remain independently auditable.
  - The merged read model applies an explicit precedence rule.
- Stable opaque IDs reduce coupling to database keys.
  - UUIDs do not replace object-level authorization.
  - Sequential IDs can be valid when enumeration is acceptable and authorization is enforced.
- Review filters against supported index and search plans.
  - An index per field alone does not guarantee every filter combination is cheap.
- **Related:** [Q1–Q5](#rest-resource-modeling).

## 4. General design principles & naming

### L4 knowledge

| Method | Meaning | Safe | Idempotent by HTTP semantics | Usual body |
|---|---|---|---|---|
| GET | Retrieve representation | Yes | Yes | None |
| HEAD | Retrieve response metadata | Yes | Yes | None |
| POST | Create or perform an action | No | No | Action or creation input |
| PUT | Create or replace at target URI | No | Yes | Replacement representation |
| PATCH | Apply defined changes | No | Not guaranteed | Patch document |
| DELETE | Remove target association | No | Yes | Usually none |

- Use consistent path casing and JSON field naming.
- Use timestamps with explicit offsets; distinguish timestamps from calendar dates.
- Define decimal precision and scale for rates or money.
  - Decimal strings are one interoperability choice.
- Define PATCH semantics explicitly.
  - JSON Merge Patch uses absent members for no change and null for removal.
  - Array replacement differs from element-level patch operations.
- Model corrections, approvals, and ingest runs as domain resources where they have identity or lifecycle.
- Use explicit action endpoints where a resource update poorly expresses the operation.

### L5 extra

- Repeating an absolute patch can be idempotent; an increment patch generally is not.
  - Evaluate the complete operation, including domain effects.
- A state transition expressed by PATCH can be valid.
  - Prefer an explicit action when it clarifies authorization, auditing, and retry semantics.
- Freeze shared response envelopes, error shapes, units, and pagination guarantees early.
- Return the new representation when it saves a follow-up read.
  - Use `204` when callers do not need a response body.
- For bulk APIs, declare atomicity before choosing response shape.
  - Independent items: per-item outcomes and per-item deduplication.
  - Atomic batch: one transaction, bounded size, one commit result.
  - `207` belongs to WebDAV; ordinary JSON APIs can use a documented `200` result envelope.
- **Related:** [Q2: actions](#rest-q2), [Q4: bulk](#rest-q4), [Q20: idempotency](#rest-q20).

## 5. Status codes — mapped to scenarios

### L4 knowledge

| Scenario | Code | Client behavior |
|---|---|---|
| Successful response with body | `200` | Consume representation |
| Resource created | `201` | Use returned resource and location |
| Accepted for later processing | `202` | Follow operation status; completion is not guaranteed |
| Successful response without body | `204` | Do not parse JSON |
| Conditional read unchanged | `304` | Reuse the stored representation |
| Malformed or invalid request | `400` | Correct request |
| Missing or invalid credentials | `401` | Follow authentication challenge; no blind retry loop |
| Forbidden operation | `403` | Surface permission failure |
| Missing or deliberately concealed resource | `404` | Follow resource visibility policy |
| Unacceptable response format | `406` | Change `Accept` |
| Business-state conflict | `409` | Follow documented conflict handling |
| Failed request precondition | `412` | Re-read and reconcile |
| Content too large | `413` | Reduce payload |
| Unsupported request media type | `415` | Change `Content-Type` |
| Well-formed but semantically invalid input | `422` | Correct input; use consistently with `400` policy |
| Required precondition missing | `428` | Supply the required conditional header |
| Throttled | `429` | Delay an eligible retry |
| Unexpected server failure | `500` | Treat outcome as potentially ambiguous |
| Gateway received invalid upstream response | `502` | Retry only if safe and useful |
| Temporarily unavailable or overloaded | `503` | Honor retry guidance within deadline |
| Gateway upstream timeout | `504` | Treat write outcome as potentially ambiguous |

### L5 extra

- Status class alone is not a retry policy.
  - `429` is a retry candidate despite being 4xx.
  - An in-progress `409` may permit retry under the API contract.
  - A `500` may represent a repeatable bug or an ambiguous committed write.
- Distinguish failed `If-Match` (`412`) from a domain-state conflict (`409`).
- Avoid successful status codes for failed REST operations.
  - Generic monitors and clients otherwise misclassify the result.
- Use a consistent concealment policy where existence is confidential.
- `Location` and `Retry-After` are useful API conventions where appropriate.
  - Do not describe them as universally mandatory on every `201`, `202`, `429`, or `503`.
- **Related:** [Q16–Q19](#rest-status-errors).

## 6. Error handling design

### L4 knowledge

- **Why:** per-controller error shapes force consumers to implement unrelated parsers.
- Centralize domain-exception mapping in Spring `@RestControllerAdvice`.
- Use RFC 9457 Problem Details with `application/problem+json`.
  - `type`: stable problem identifier.
  - `title`: summary.
  - `status`: HTTP status when included.
  - `detail`: occurrence-specific explanation.
  - `instance`: occurrence identifier when supplied.
- Add bounded validation details and a trace ID as extensions.
- Clients branch on stable identifiers, not English text.

### L5 extra

- Map errors as a reviewed taxonomy alongside success schemas.
- Preserve framework handling of binding, validation, and HTTP exceptions.
  - A broad catch-all must not turn every unmapped framework 4xx into `500`.
- Unknown server failures receive a sanitized response and internal diagnostics.
  - Never echo SQL, stack traces, tokens, or sensitive input values.
- Report field paths using the public request shape.
- Collect independent validation errors within bounded work.
  - Stop early for authentication failures, malformed payloads, or expensive dependent checks.
- Count server faults by stable error code and endpoint template.
  - Keep trace IDs in logs, not metric labels.
- Use result objects for frequent expected outcomes where exception allocation is a measured cost.
- **Related:** [Q8](#rest-q8), [Q17/Q18](#rest-q17).

## 7. Caching (server design → client behavior)

### L4 knowledge

```text
Browser -> CDN/proxy -> service -> local/shared cache -> source
 policy       policy   validator       key/TTL          freshness
```

- **Why:** repeated reads otherwise rebuild the same view and load the source.
- HTTP caching uses request identity, response policy, and applicable `Vary` fields.
- `private`: shared caches must not store the complete response.
- `no-store`: instruct caches not to store the response.
- `no-cache`: stored responses require validation before reuse.
- `If-None-Match` can yield `304` for unchanged reads.
- Application caches use explicit keys, expiration, and invalidation.

### L5 extra

- Define freshness from the source event to the displayed value.
  - Replica lag, cache-fill races, and multiple cache layers all contribute.
  - TTL bounds residence time; it is not by itself an end-to-end staleness guarantee.
- Versioned keys require a trustworthy way to find the current version.
  - A stale version pointer can keep selecting an obsolete entry.
- A version-derived ETag must cover every dependency that changes the representation.
  - A merged vendor-plus-overlay view cannot use only the overlay's version.
- A body-hash ETag generally saves transfer after rendering.
  - An early validator check may also avoid materialization work.
- Coalesce hot-key loads and jitter expiry across keys.
- On cache failure, use bounded source fallback only within source capacity.
  - Shed load or fail explicitly when fallback would overload the database.
- `Vary: Authorization` is not an authorization check and does not replace `private` or `no-store`.
- **Related:** [Q24–Q27](#rest-caching).

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| HTTP cache | Reuse response under HTTP policy | Avoids origin work on valid hits | Viewer and freshness boundaries require care | Public or explicitly private cacheable reads |
| Local cache | In-process entries | Avoids a network hop | Copies diverge; memory multiplies per instance | Small reference data with tolerable staleness |
| Shared cache | Network-accessed entries | Reuse across instances | Adds dependency and network cost | Shared working set justifies operation cost |
| Source read | Fetch current source state | Simplifies cache consistency | Source load and latency | Strict freshness or low reuse |

- **Default:** cache only with a stated freshness and authorization contract.

## 8. Idempotency — and how the *client* does the key

### L4 knowledge

- **Why:** the server can commit while the client loses the response.
- One logical intent receives one key before its first transmission.
- Persist enough state to recover the intent and original payload after a supported client crash.
  - Browser storage choice must match reload, tab-close, and sensitive-data requirements.
  - Backend callers can store the key with a job or outbox record.
- Retries reuse the same key and payload.
- A changed user intent receives a new key after the previous intent is resolved.
- Double-clicks must share one pending intent; button disabling is only a usability measure.

### L5 extra

- Scope uniqueness by tenant/caller and operation.
- Bind the key to a canonical request fingerprint.
- Claim the key, commit the business effect, and store its response in one transaction when they share a database.
- Authorize replay access; never return a different tenant's stored response.
- Keep the key pending for ambiguous failures, throttling, and documented in-flight conflicts.
  - A blanket “retire after any 4xx” rule is incorrect.
- Choose retention from the maximum supported retry/reconciliation window.
  - After expiry, reusing the key can create a new operation.
  - Durable business uniqueness may need to outlive the response cache.
- External effects need an outbox and downstream deduplication or another explicit recovery protocol.
- **Related:** [Q20–Q23](#rest-idempotency).

## 9. Retry (client policy)

### L4 knowledge

- Retry only when repeating the operation is safe or reliably deduplicated.
- Retry only failures that may improve without changing intent.
- Use bounded exponential backoff with full jitter.
- Bound both attempts and elapsed time.
- Honor `Retry-After` without exceeding the caller's deadline.
- A timeout leaves a write outcome unknown; it does not prove rollback.

### L5 extra

- Assign one owner for the logical operation's retry policy.
  - Audit SDK, gateway, mesh, and application retries together.
  - Three total attempts at each of three layers can create 27 downstream attempts.
- Add a service-wide retry budget tied to sustainable capacity.
  - A percentage is a tuning choice, not a universal default.
- Propagate deadlines; reserve time for local work and response delivery.
- Use per-dependency concurrency limits and bounded queues.
- Circuit breakers stop repeated calls to a failing dependency.
  - Bound half-open probes so recovery checks do not overload it again.
- **Related:** [Q22/Q23](#rest-q22), [Q30](#rest-q30).

## 10. Pagination

### L4 knowledge

- Request: `GET /instruments?first=50&after=<cursor>`.
- Response: `{items, pageInfo:{hasNext,endCursor}}`.
- Require or default a bounded positive page size; document clamping versus rejection.
- Use a deterministic sort with a unique tiebreaker.
- Fetch `n+1` rows to establish whether another page exists.
- Clients resume using the returned cursor and stop when `hasNext` is false.

### L5 extra

- Indexed keyset pagination seeks to a boundary and scans the next page.
  - Its work avoids scanning all preceding pages.
  - It is not literally O(1); index height, filtering, and rows scanned still matter.
- Include the tiebreaker in the cursor, predicate, ordering, and supporting index.
- Define null ordering and support for ascending or descending sorts.
- Base64 provides encoding, not secrecy or tamper protection.
  - Validate cursor structure and bind it to sort/filter context.
  - Sign it if integrity is needed; still parameterize SQL and enforce tenant authorization.
- Mutable sort keys can move rows across page boundaries.
- An immutable key alone does not freeze the dataset.
  - Exact reconciliation needs a snapshot or a versioned export dataset and retention policy.
- Exact totals may cost more than a page.
  - Make them optional, maintained, or explicitly approximate where requirements allow.
- **Related:** [Q31](#rest-q31).

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bounded offset | Skip rows before a page | Simple page numbers | Deep scans; shifts under writes | Small bounded lists |
| Keyset | Continue after ordered tuple | Predictable deep traversal with matching index | No direct page jump; mutations can move rows | Large interactive lists |
| Snapshot export | Traverse a fixed dataset | Consistent reconciliation | Storage or snapshot lifetime cost | Audits and exact bulk extraction |

- **Default:** keyset for large lists; snapshots for exact exports.

## 11. Client end-to-end (tie it together)

### L4 knowledge

```text
Read instrument and overlay version
  -> user submits -> persist intent K + payload
  -> POST correction with K and expectedOverlayVersion
     -> 201: render committed result; finish intent
     -> 409 stale overlay: re-read; user reconciles; new intent
     -> 422 validation: show field errors; corrected input is new intent
     -> timeout/eligible 503: bounded backoff; same K
     -> 429: delayed retry within deadline; same K
     -> 202: retain operation ID; track eventual outcome
```

- Display the correlation ID for actionable support reports.
- Return or fetch the committed representation using a read-your-writes policy.
- Inject retry, validation, conflict, and lost-response failures when exercising the client.

### L5 extra

- Separate two concurrency contracts:
  - Updating `/overlays/{id}` can use its own strong ETag with `If-Match`; failure is `412`.
  - Creating `/instruments/{id}/corrections` can include `expectedOverlayVersion`; a domain mismatch is `409`.
- Do not silently use a parent resource's ETag as the conditional validator of a different target URI.
- Check a completed idempotency replay before reapplying the original business precondition.
  - The first successful write may have changed the version itself.
  - Returning the stored success preserves the original intent's result.
- Never automatically overwrite newer state after a stale-view response.
  - Reconciliation belongs to the domain policy or the human who understands the competing edits.
- **Related:** [Q36: full design](#rest-q36).

## 12. Validation, contracts, and evolution

### L4 knowledge

- Validate request syntax and sizes at the boundary.
- Validate semantic and state-dependent rules in the application service.
- Use database constraints for invariants under races.
- Parse primitive input into domain types when construction can enforce validity.
- Review OpenAPI schemas and response/error examples as the consumer contract.
- Prefer compatible additions over renaming or repurposing existing fields.

### L5 extra

- Route API and batch entry points through the same domain checks.
- Test nullability, enum evolution, units, error shapes, ordering, and pagination guarantees.
- Use breaking-change diffs for detectable schema changes.
  - Use consumer tests and review for behavioral assumptions those diffs cannot see.
- Expand-contract migration:
  - Deploy schema and tolerant readers first.
  - Add the new field or representation alongside the old one.
  - Dual-serve and reconcile any dual writes.
  - Migrate consumers using usage evidence.
  - Remove the old contract only under an agreed retirement policy.
- REST servers usually cannot observe which fields of a returned JSON body clients read.
  - Use version/projection telemetry, consumer inventories, and migration acknowledgments.
  - Do not infer unused fields merely from endpoint traffic.
- **Related:** [Q6–Q15](#rest-validation), [Q37](#rest-q37).

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| URI version | `/v1/...` | Visible routing and distinct URLs | Multiple versions cost support | Independent partner consumers |
| Media-type version | Version selected through `Accept` | Stable resource URI | Negotiation and cache variants need care | Representation-driven API conventions |
| Additive evolution | Maintain one compatible contract | Smaller support matrix | Requires compatibility discipline | Controlled clients or stable semantics |
| Contract-first | Reviewed spec drives implementation | Consumer-visible changes reviewed early | Extra coordination | Multiple independent teams |
| Code-first with gates | Generate and diff implementation schema | Lower authoring overhead | Diffing misses some behavior | Small teams with contract tests |

- **Default:** additive evolution; select explicit versioning when consumer migration constraints require it.

## 13. Concurrency, async operations, and dependency isolation

### L4 knowledge

- Optimistic concurrency guards writes with a version predicate in the database update.
- A failed conditional HTTP request receives `412`; a domain conflict normally receives `409`.
- Long-running work returns an operation resource instead of holding a connection indefinitely.
- Operation state includes progress, outcome, result link, and structured failure details.
- Downstream calls have explicit timeouts and concurrency limits.

### L5 extra

- Compare conflict frequency and retry cost against the cost of blocking.
  - Use optimistic control for ordinary human edits.
  - Use short pessimistic transactions or a per-aggregate queue for sustained contention.
- `202` should follow durable acceptance, not only an in-memory enqueue.
- Deduplicate initiation and worker effects separately.
- Bound polling frequency and operation retention.
- Keep terminal business outcomes stable.
  - Signed result links can expire even if the outcome is immutable.
- Isolate unhealthy dependencies with bulkheads and load shedding.
- Serve degraded financial data only with a domain-approved freshness marker.
- **Related:** [Q28–Q30](#rest-concurrency), [Q38](#rest-q38).

## 14. Security, performance, and testing

### L4 knowledge

- Authenticate callers and validate tokens according to the trust boundary.
- Enforce object- and field-level authorization in shared application services.
- Map responses into permitted DTO views; do not serialize persistence entities indiscriminately.
- Restrict write DTO fields to prevent mass assignment.
- Record mutation actor, target, change, reason, and time in an audit trail.
- Trace slow endpoints across application, database, cache, and downstream calls.
- Test controller contracts, real persistence behavior, and representative client flows.

### L5 extra

- Validate service identity or delegated caller context on internal hops.
  - A protected internal network does not itself establish caller authorization.
- Apply least privilege, secret rotation, bounded requests, and redacted logs.
- For browser cookie authentication, include CSRF defenses.
  - CORS is a browser sharing policy, not authorization.
- Diagnose queue wait separately from query execution time.
  - Observe connection-pool acquisition, worker utilization, and dependency saturation.
- Establish query-count budgets for representative reads with controlled fixtures.
  - A two-query threshold is fixture-specific, not universal.
- Test same-key concurrent requests, committed-write/lost-response recovery, stale writes, and cross-tenant replay.
- Use consumer contracts and database-backed tests to catch behavior that schema diffs miss.
- **Related:** [Q32–Q35](#rest-performance), [Q72: REST testing](#rest-q72).

## 15. Failure modes

### L4 knowledge

- The following are canonical failure patterns, not claims about specific production incidents.

| Failure | Trigger | Detection | Mitigation |
|---|---|---|---|
| Duplicate correction | Response lost; retry gets new key | Duplicate business intent | Stable key and atomic claim/effect |
| Lost update | Version read but absent from write predicate | Concurrent-write test | Atomic compare-and-update |
| Stale response | Replica lag or stale cache refill | Data-age metrics | End-to-end freshness policy |
| Cache stampede | Hot-key expiration | Concurrent loads and source spike | Coalescing, expiry jitter, admission control |
| Retry storm | Multiple layers retry independently | Attempts per logical request | One owner and global budget |
| Neighbor outage | Slow dependency monopolizes pool | Queue wait and saturation | Bulkheads, deadlines, shedding |
| Contract break | Nullability, units, or enum assumptions change | Consumer tests and schema diffs | Additive migration and review |
| Tenant data leak | Missing object check or cache scope | Negative authorization tests | Central authorization and scoped keys |
| Pagination gaps | Mutable sort or incomplete cursor | Snapshot reconciliation test | Full tuple and export snapshot |
| Lost async job | `202` before durable acceptance | Accepted jobs without progress | Durable queue/outbox and watchdog |

### L5 extra

- For each failure, name who detects it and who owns recovery.
- Define measurable rollback and load-shedding thresholds before a rollout.
- Test failures at the boundary between commit and acknowledgment.
  - These reveal correctness gaps that happy-path tests do not exercise.

## 16. Further thinking

### L4 knowledge

- Rehearse one instrument correction from HTTP input through commit to client recovery.
- Explain one chosen alternative and its concrete cost for each mechanism.

### L5 extra

- **Ownership:** who owns contract retirement, replay retention, reconciliation, and audit access?
- **Scale:** which tenant, query shape, hot key, or write aggregate can monopolize capacity?
- **Consistency:** where can source, cache, read replica, and search index disagree?
- **Change:** what evidence permits removing a version or weakening a guarantee?

## Interview questions

<a id="rest-resource-modeling"></a>

### 1.1 Resource modeling & paths

<a id="rest-q1"></a>

**Q1: How do you design resource paths?**

**L4**

- Use plural resource collections: `/instruments` and `/instruments/{id}/corrections`.
- Let the HTTP method carry the operation.
- Nest only where ownership helps consumers; prefer shallow paths as a convention, not an HTTP rule.
- Use consistent casing and stable IDs.

**L5 extra**

- Choose boundaries around consistency, authorization, lifecycle, and cache behavior.
- Separate vendor records from human corrections when they have different writers and retention policies.
- Expose a merged instrument view without forcing its representation to match a database table.
- Splitting paths alone does not enforce permissions; shared service logic must enforce them.

<a id="rest-q2"></a>

**Q2: Nouns vs verbs — when do you break the rule?**

**L4**

- Use resource creation for actions that produce an identifiable result, such as a correction or approval record.
- Use an explicit POST action when ordinary resource mutation poorly represents the operation.
- Examples: `POST /payments/{id}/capture` or a documented custom method such as `POST /instruments/{id}:reindex`.

**L5 extra**

- Make transition permissions, audit meaning, and retry behavior explicit.
- A PATCH transition is valid when its contract defines those properties clearly.
- An action resource gives long-running work a natural ID, status, and idempotency scope.
- Review new actions against the domain model to prevent an uncontrolled collection of RPC-like verbs.

<a id="rest-q3"></a>

**Q3: Path vs query vs body?**

**L4**

- Path: resource identity and meaningful ownership.
- Query: filter, sort, page, and projection parameters.
- Header: cross-cutting metadata such as authorization, validators, and tracing.
- Body: typed creation, replacement, patch, or action data.

**L5 extra**

- Ordinary HTTP cache selection uses method/URI and applicable request headers, not arbitrary POST-body criteria.
- URLs can appear in logs, browser history, and referrers; keep credentials and sensitive criteria out of them.
- Large or sensitive search criteria may justify POST, with an explicit caching tradeoff.
- A protected stored-search resource can return a GET location; define its authorization and retention.
- GET and DELETE bodies have no generally defined HTTP semantics, so avoid them for portable clients.

<a id="rest-q4"></a>

**Q4: Bulk operations?**

**L4**

- Offer bounded batch reads or writes when consumers would otherwise loop over individual endpoints.
- Declare whether the batch is atomic or each item is independent.
- For independent items, return a documented JSON envelope containing each item's result and error.
- HTTP 207 is a WebDAV status, not the default for ordinary JSON bulk APIs.

**L5 extra**

- Independent items need stable per-item identity and deduplication so clients retry only unresolved work.
- Atomic batches need one transaction and one commit outcome.
- Bound batch size by payload, transaction duration, locks, and database parameter limits.
- Long PostgreSQL transactions can delay dead-tuple cleanup and retain resources.
- A limit such as 500 items is only an illustrative starting point; validate it against the workload.

<a id="rest-q5"></a>

**Q5: HATEOAS — do you use it?**

**L4**

- HATEOAS puts navigation links and available actions in representations.
- Clients follow documented link relations instead of constructing every URL themselves.
- Many resource-oriented HTTP APIs use static contracts and implement only part of the full REST constraints.

**L5 extra**

- Hypermedia can help a UI follow a server-owned state machine as available actions change.
- Permission flags alone are not full hypermedia, but they illustrate server-driven affordances.
- Links do not replace authorization; the server must recheck an action when invoked.
- Choose hypermedia when consumers actually use navigation or affordances; otherwise account for its payload and client complexity.

<a id="rest-validation"></a>

### 1.2 Params & input validation

<a id="rest-q6"></a>
<a id="rest-q7"></a>

**Q6/Q7: How and where do you validate?**

**L4**

- Validate syntax, required fields, and size bounds on request DTOs at the HTTP boundary.
- Use Bean Validation through `@Valid` for applicable Spring MVC request-body validation.
- Enforce cross-field and state-dependent domain rules in application services.
- Use database NOT NULL, UNIQUE, FK, and CHECK constraints as the final concurrency-safe invariant boundary.

**L5 extra**

- Parse raw inputs into domain types so API and batch entry points share the same validity rules.
- Collect independent, inexpensive semantic violations to reduce fix-and-resubmit cycles.
- Stop early for malformed input, unauthorized requests, or expensive dependent validation.
- Test pipeline-output and API expectations together to catch vendor-schema drift.
- Validation before the transaction cannot replace database checks when state can change concurrently.

- **Mechanism snippets:** illustrative excerpts; surrounding application types and imports are omitted.

```java
    @NotBlank @Size(max = 500) String reason) {}

@PostMapping("/instruments/{id}/corrections")
```

<a id="rest-q8"></a>

**Q8: What do you return on failure?**

**L4**

- Return a consistent validation status: 400, or 422 for well-formed but semantically invalid input.
- Return a stable machine identifier, a readable explanation, and bounded per-field details.
- Use request-field paths so consumers can highlight the correct input.

**L5 extra**

- Use RFC 9457 Problem Details and `application/problem+json`.
- Spring supports `ProblemDetail`; centralize mapping rather than building unrelated error payloads per controller.
- Clients branch on the stable problem type, so wording changes do not break integrations.
- Do not echo sensitive input, internal property names, SQL, or stack traces.
- Include a trace ID that connects a client report to restricted internal diagnostics.

<a id="rest-q9"></a>

**Q9: Parse-don't-validate — say it as a principle.**

**L4**

- Validation that returns a boolean leaves the caller holding the same untrusted primitive.
- Parsing can return a narrower domain type whose construction checks the invariant.
- Require that type in core service signatures instead of repeating string checks.

**L5 extra**

- A private constructor and controlled factory make bypassing the check mechanically harder.
- Route every ingress path through the same factory, including batch jobs.
- The type proves only its construction-time invariant; current permissions, uniqueness, and changing business state still require runtime checks.
- Do not confuse a syntactically valid identifier with an existing or authorized resource.

<a id="rest-versioning"></a>

### 1.3 Versioning & evolution

<a id="rest-q10"></a>

**Q10: How do you version?**

**L4**

- Version only when the required change cannot preserve the supported contract.
- URI versions such as `/v1` are easy to route, inspect, and separate in cache keys.
- Media-type versions use content negotiation and require matching cache-variant handling.
- Compatible additions can stay in the existing version.

**L5 extra**

- Choose based on consumer independence and the organization's contract-review conventions.
- Every live version adds a support, testing, and security-maintenance surface.
- Plan retirement with a consumer inventory and usage evidence before adding a version.
- Document deprecation and sunset dates; communication does not replace migration evidence.

| Option               | Buys you                                                     | Costs you                                                          | Choose when                |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------ | -------------------------- |
| URI `/v1`            | Obvious routing, natural cache separation, easy canary split | URL sprawl; purist objection (identity changes)                    | Default; public/partner    |
| `Accept` header      | Stable URLs; per-representation versioning                   | Invisible in logs; `Vary: Accept` cache complexity; harder to test | Media-type-driven orgs     |
| None + additive-only | No migration cliffs, no version matrix                       | Discipline + diff tooling to prevent breaks                        | Internal, both sides owned |

<a id="rest-q11"></a>

**Q11: When is versioning the wrong answer?**

**L4**

- Prefer an optional additive field when it meets the new requirement.
- Keep existing semantics stable while consumers migrate.
- Avoid creating a version for every implementation or internal-schema change.

**L5 extra**

- A version does not solve unknown consumer ownership or incomplete migrations.
- Verify tolerant response readers with consumer tests rather than assuming unknown fields are ignored.
- Observe version and explicit projection usage where available.
- REST servers cannot ordinarily observe which fields a client reads from a returned JSON body.
- Use consumer acknowledgments and an agreed retirement policy before removing such fields.

<a id="rest-q12"></a>

**Q12: Walk through expand-contract for a breaking change.**

**L4**

- For `cusipId` to `identifier`, add the new field while continuing to serve the old one.
- Migrate consumers independently.
- Remove the old field only after supported consumers finish migration.

**L5 extra**

- Expand the storage schema and compatible readers before enabling new writers.
- If dual writing is required, reconcile the two representations during the migration window.
- Use a dated contraction task with an explicit compatibility gate.
- Keep a rollback path while both forms remain live.
- The same pattern applies to database columns and message schemas, but their consumer and deployment boundaries differ.

<a id="rest-contracts"></a>

### 1.4 Contract & schema

<a id="rest-q13"></a>
<a id="rest-q14"></a>

**Q13/Q14: Enforcing the contract; contract-first vs code-first?**

**L4**

- Maintain an OpenAPI contract describing requests, responses, and errors.
- Contract-first: review the specification before generating stubs or clients.
- Code-first: generate the specification from implementation and annotations.
- Either approach needs examples and verification against actual behavior.

**L5 extra**

- Use independent consumer count and contract-review ownership as deciding variables.
- Run a breaking-change diff on the reviewed/generated specification in CI.
- Add consumer-driven tests for assumptions the schema cannot express.
- A generated specification without compatibility checks can still drift silently.
- Gateway request validation does not prove domain correctness or response compatibility.

<a id="rest-q15"></a>

**Q15: What actually breaks contracts in practice?**

**L4**

- Contracts include required fields, nullability, enums, units, error shapes, sort order, and pagination guarantees.
- Preserve documented behavior or migrate it explicitly.
- Test both success and failure responses.

**L5 extra**

- An added enum value can break an exhaustive client; require an unknown-value path or coordinate migration.
- A field can keep its type while changing units or meaning; schema diffs do not reliably catch that.
- Nullability drift can break generated clients even when sample responses still look valid.
- Error formats deserve the same compatibility discipline as successful payloads.
- Use schema gates for structure and consumer tests plus review for behavioral assumptions.

<a id="rest-status-errors"></a>

### 1.5 Status codes & error design

<a id="rest-q16"></a>

**Q16: Which codes do you actually use?**

**L4**

- Use the scenario table in knowledge §5 as the shared status vocabulary.
- Distinguish creation (201), accepted work (202), and completed work without a body (204).
- Distinguish invalid input, authentication, authorization, state conflict, and failed preconditions.
- Return a structured error body where the status permits one.

**L5 extra**

- Codes are part of the client and monitoring contract.
- Use 412 for failed conditional headers and 409 for domain-state conflicts.
- Use a consistent 404 concealment policy when resource existence is sensitive.
- Do not return 500 for known validation failures or 200 for a failed REST operation.
- Retry eligibility still depends on operation safety and the documented failure, not just the status class.

<a id="rest-q19"></a>

**Q19 (fold-in): Why codes matter — retryability.**

**L4**

- A client should distinguish request correction, authentication recovery, delayed retry, and terminal failure.
- Retry only operations that are safe to repeat or reliably deduplicated.
- Respect attempt limits and an overall deadline.

**L5 extra**

- 429 can be retried despite being 4xx; some documented in-progress 409 responses can too.
- Not every 5xx is transient, and a timed-out write may already have committed.
- Misclassifying validation as 500 encourages pointless retry load.
- Returning 200 with an error body hides failures from ordinary HTTP-level monitoring.
- Publish stable error codes and explicit retry guidance for exceptions to default policy.

<a id="rest-q17"></a>
<a id="rest-q18"></a>

**Q17/Q18: Error bodies + global handling.**

**L4**

- Centralize domain-error mapping in `@RestControllerAdvice`.
- Return Problem Details with a stable type and optional field-error extensions.
- Return an opaque server error for unknown faults and retain details in protected logs.

**L5 extra**

- Preserve Spring's standard handling of HTTP, binding, and validation exceptions.
- A broad catch-all must not remap framework 4xx failures into 500.
- Review error taxonomy changes as contract changes.
- Monitor unmapped server-fault rate and link reports through trace IDs.
- Use ordinary result objects for frequent expected outcomes when exception overhead is a measured concern.

- **Mechanism snippets:** illustrative excerpts; surrounding application types and imports are omitted.

```java
@RestControllerAdvice
class ApiErrors extends ResponseEntityExceptionHandler {
  @ExceptionHandler(CorrectionConflictException.class)
  ProblemDetail conflict(CorrectionConflictException e, HttpServletRequest req) {
    var pd = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Correction conflicts with newer version");
    pd.setType(URI.create("https://errors.myco.com/correction-conflict"));

  }
  @ExceptionHandler(Exception.class)

    var pd = ProblemDetail.forStatus(500);
    pd.setProperty("traceId", MDC.get("traceId"));
    return pd; // opaque by design
  }
}
```

<a id="rest-idempotency"></a>

### 1.6 Idempotency & retries

<a id="rest-q20"></a>

**Q20: Definitions.**

**L4**

- Idempotent means repeated identical requests have the same intended server effect as one request.
- Responses can differ: a repeated DELETE can report that the resource is already absent.
- GET, HEAD, PUT, and DELETE are idempotent by HTTP semantics.
- POST and PATCH are not guaranteed idempotent; an absolute patch can be designed to be so.

**L5 extra**

- Safe methods request no business mutation, though incidental logging is allowed.
- Database idempotency does not automatically deduplicate events or external side effects.
- An upsert needs a stable uniqueness key and defined update semantics.
- An outbox relay can deliver more than once; consumers need business-event deduplication where duplicate effects matter.
- State exactly which effects are deduplicated and for how long instead of claiming unrestricted exactly-once delivery.

<a id="rest-q21"></a>

**Q21: Idempotency keys end-to-end.**

**L4**

- The client creates one key per logical intent and persists it before sending.
- Every retry reuses the key and original payload.
- The server binds the key to a request fingerprint and stores the completed response.
- Same-key/different-input requests fail under a documented 409 or 422 policy.

**L5 extra**

- Scope the key by tenant/caller and operation; authorize replay access.
- When state shares a database, claim the key, write the business effect, and store the response in one transaction.
- Use uniqueness arbitration rather than check-then-act.
- A completed replay should return the original outcome even if that write changed the original version precondition.
- A single uncommitted claim is not a separately visible in-progress record; competitors may wait on the unique constraint.
- For durable in-flight status, design a separate lease/recovery protocol and protect against an expired worker executing late.
- Choose retention from the supported retry window; Stripe's documented at-least-24-hour pruning eligibility is a product policy, not an HTTP rule.
- Use an outbox or independently deduplicable downstream effects when the operation crosses systems.

- **Mechanism snippets:** illustrative excerpts; surrounding application types and imports are omitted.

```sql
CREATE TABLE idempotency_keys (
  tenant_id text NOT NULL,
  operation text NOT NULL,
  key text NOT NULL,
  request_hash text NOT NULL,
  response_status integer,
  response_body jsonb,
  response_headers jsonb,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, operation, key)
);

-- Inside the same transaction as the business write and response storage:
INSERT INTO idempotency_keys (tenant_id, operation, key, request_hash)
VALUES (:tenant, :operation, :key, :hash)
ON CONFLICT (tenant_id, operation, key) DO NOTHING
RETURNING key;
```

- **PostgreSQL transaction flow:**
  - A returned INSERT row owns the new intent; write the effect and stored response before commit.
  - ON CONFLICT with no returned row identifies a competing key; load and compare its committed fingerprint before replay.
  - Under Read Committed, a subsequent statement can see the row committed while uniqueness arbitration waited.
  - Bound lock waits; restart safely on serialization failures or cleanup races.
  - Do not catch a uniqueness exception and keep querying in the aborted transaction; use ON CONFLICT, a savepoint, or a fresh transaction.

<a id="rest-q22"></a>
<a id="rest-q23"></a>

**Q22/Q23: Retry strategy; retries across layers.**

**L4**

- Retry eligible transient failures only for repeatable or keyed operations.
- Use exponential backoff with full jitter.
- Cap attempts and total elapsed time.
- Honor Retry-After without waiting beyond the caller's deadline.

**L5 extra**

- Jitter prevents many recovering clients from sending their retries in synchronized waves.
- Apply a service-wide retry budget so per-request caps do not multiply outage traffic without bound.
- Audit SDK, gateway, mesh, and application retries and assign one logical retry owner.
- Three total attempts at each of four layers can create 81 downstream attempts.
- A read timeout does not prove rollback; keep the same intent key while reconciling the outcome.
- Choose retry budgets and attempt counts from capacity and latency requirements, not universal constants.

<a id="rest-caching"></a>

### 1.7 Caching

<a id="rest-q24"></a>
<a id="rest-q25"></a>

**Q24/Q25: Layers; ETag mechanics.**

**L4**

- HTTP caches follow explicit cache policy and applicable Vary fields.
- If-None-Match can return 304 and avoid transferring an unchanged representation.
- Local caches hold per-instance entries; shared caches reuse entries across instances.
- Application-cache keys must include relevant resource and tenant/view scope.

**L5 extra**

- A shallow body-hash ETag computes the body first, mainly saving transfer.
- A version-derived validator can avoid materialization only if checking that version is cheaper and covers all representation dependencies.
- If-Match uses strong comparison against the target representation; enforce the corresponding atomic write guard.
- Local caches trade a network hop for per-instance memory and divergence.
- Shared-cache failure needs bounded fallback, admission control, and explicit shedding when the source cannot absorb the load.

<a id="rest-q26"></a>
<a id="rest-q27"></a>

**Q26/Q27: Invalidation; stampedes.**

**L4**

- Use expiration and write-triggered invalidation together.
- Versioned keys select a new entry when data changes.
- Coalesce concurrent loads for a hot key and jitter expiry across keys.

**L5 extra**

- TTL bounds residence time, not source age; include replica lag, refill races, and other cache layers in the freshness budget.
- Versioned keys work only when readers discover the current version reliably.
- Treat dropped invalidation events as an expected failure and define the remaining stale-read bound.
- Illustrative stampede sizing: 2,000 reads/second times a 0.3-second rebuild allows about 600 overlapping loads without coalescing.
- Read-your-writes can require using the returned representation or reading a source that has observed the write.
- Expose a domain-approved staleness marker when degraded data is allowed.

<a id="rest-concurrency"></a>

### 1.8 Concurrency & async

<a id="rest-q28"></a>

**Q28: Long-running operations?**

**L4**

- Return 202 after durable acceptance of long-running work.
- Provide an operation resource with state, progress, result links, and failure details.
- Clients poll at a bounded interval or use a supported notification mechanism.

**L5 extra**

- Deduplicate the initiating POST so retries do not create twin jobs.
- Workers also need duplicate-delivery and crash-recovery handling.
- Retain operations for the supported client recovery window.
- Terminal business outcomes should be stable, but signed result URLs may expire.
- Polling work grows with consumers and frequency; choose notifications when that load justifies their delivery/reconciliation complexity.

<a id="rest-q29"></a>

**Q29: Concurrent updates?**

**L4**

- Use a version column and include the expected version in the update predicate.
- JPA @Version is one implementation; confirm the generated update actually checks it.
- Map a failed If-Match to 412 and a domain-state conflict to the documented conflict response.
- Clients re-read and reconcile rather than blindly overwriting.

**L5 extra**

- Choose optimistic control when conflicts are uncommon and retries are cheaper than blocking.
- Use short pessimistic critical sections or per-aggregate serialization when contention stays high.
- Never hold a database lock during human think time.
- Waiting requests can exhaust a connection pool even when each lock holder appears healthy.
- For correction creation, an expected overlay version can be a body-level domain precondition; do not misuse a different resource's ETag.

- **Mechanism snippets:** illustrative excerpts; surrounding application types and imports are omitted.

```java
@Entity class InstrumentOverlay {
  @Id String id;
  @Version long version;      // Hibernate: UPDATE ... SET version=?+1 WHERE id=? AND version=?
  ...
}
```

<a id="rest-q30"></a>

**Q30: Slow downstream inside a sync endpoint?**

**L4**

- Set connect, read, and overall operation deadlines.
- Bound per-dependency concurrency and queueing.
- Use a circuit breaker to stop repeated calls to a failing dependency.
- Return an explicit failure or a documented degraded representation.

**L5 extra**

- A hung dependency can occupy the request or database pool and delay unrelated endpoints.
- Reserve downstream time within the caller's deadline, including queueing and local response work.
- Bound half-open probes to avoid overwhelming a dependency just as it recovers.
- Use separate pools or limits where one dependency would otherwise consume all capacity.
- Financial stale-data fallback needs an explicit freshness marker and domain approval.

<a id="rest-performance"></a>

### 1.9 Pagination & performance

<a id="rest-q31"></a>

**Q31: Offset vs cursor?**

**L4**

- Offset supports simple page numbers but scans and discards preceding rows.
- Keyset uses a cursor predicate and matching deterministic ordering.
- Include a unique tiebreaker and a supporting composite index.
- Fetch n+1 rows to compute whether another page exists.

**L5 extra**

- Indexed keyset work avoids scanning all prior pages; it is not literally O(1).
- Include sort direction, null handling, and filter context in the cursor contract.
- Mutable sort keys can move rows across boundaries during traversal.
- Use snapshot or versioned-dataset semantics for exact reconciliation; an immutable ID alone is insufficient.
- Base64 is encoding, not authorization, secrecy, or integrity.
- Validate cursors, parameterize queries, and apply tenant filters independently.
- Bound offset depth when page jumping is a real product requirement.

- **Mechanism snippets:** illustrative excerpts; surrounding application types and imports are omitted.

```sql
-- keyset page after (issued_at, id) with tiebreaker; composite index required
SELECT * FROM instruments
WHERE (issued_at, id) > (:last_issued_at, :last_id)
ORDER BY issued_at, id
LIMIT 51;   -- fetch n+1: 51st row's existence = hasNextPage
```

<a id="rest-q32"></a>

**Q32: Diagnosing a slow endpoint?**

**L4**

- Measure endpoint-template p50, p95, and p99 latency.
- Inspect representative slow traces across application, database, and downstream spans.
- Use query plans and database metrics to check indexes, scans, and ORM N+1.
- Re-measure under the same workload after the fix.

**L5 extra**

- Separate pool-acquisition and queue wait from execution time.
- Flat query time with rising endpoint latency is a reason to inspect pools and queues, not proof of one specific cause.
- Use representative fixtures and query-count budgets to keep a batching fix from regressing.
- For an index mitigation, CREATE INDEX CONCURRENTLY permits ordinary writes but still uses locks and may wait; it is not a zero-cost operation.
- For a deeper key redesign, compare the new read path against the old path before serving it.
- Describe incident work as mitigation, durable fix, verification, and a regression guard; only claim incidents you actually handled.

<a id="rest-security"></a>

### 1.10 Security (they asked: "how did you secure your application")

<a id="rest-q33"></a>
<a id="rest-q34"></a>

**Q33/Q34: Layers, concretely.**

**L4**

- Authenticate at entry boundaries and validate token signature, issuer, audience, and expiration as applicable.
- Use Spring Security for route/method policy and shared services for object-level authorization.
- Apply role and attribute checks to the actual target object.
- Use permitted response DTOs and restricted write DTOs.
- Record mutations in an audit trail and keep secrets out of source control.

**L5 extra**

- BOLA occurs when an authenticated caller can act on an unauthorized object ID.
- Centralizing object checks prevents REST, GraphQL, and batch entry points from silently diverging.
- Field-level read and write checks prevent overexposure and mass assignment.
- Secure internal service identity or delegated caller context; gateway authentication alone does not secure every bypass path.
- Use least-privilege service identities, rotated secrets, and redacted logs.
- For cookie-authenticated browser requests, include CSRF defenses; CORS is not an authorization mechanism.

<a id="rest-q35"></a>

**Q35: Which financial-data controls would you discuss?**

**L4**

- Discuss object and field permissions, sensitive-data handling, and mutation audit records.
- Audit actor, target, before/after values where permitted, time, and reason.
- Keep PII and credentials out of URLs and ordinary logs.

**L5 extra**

- Append-only rows still require access control, retention, and tamper-detection or external retention controls where needed.
- Restrict audit readers as well as writers; an audit stream can contain sensitive data.
- For vendor file ingestion, describe the actual managed-transfer/SFTP-to-bucket path only at the depth you operated.
- Distinguish an interview design proposal from a production control you can substantiate.

<a id="rest-l5-design"></a>

### 1.x L5 design questions

<a id="rest-q36"></a>

**Q36: Design the correction API end-to-end.**

**L4**

- Create an append-only correction resource under POST /instruments/{id}/corrections.
- Validate input and authorize the caller for the object and affected field group.
- Use an idempotency key and expectedOverlayVersion in the creation body.
- Return the correction representation on commit or a structured domain conflict.

**L5 extra**

- Atomically check overlay version, write the correction/audit state, record the replay response, and insert any outbox event.
- Keep vendor-of-record data separate from human corrections so re-ingestion cannot erase audit history.
- Define precedence when a correction races vendor ingestion; overlay-wins is a domain choice, not a universal rule.
- Derive the merged-view validator from all dependencies that affect that view.
- Publish outbox events with downstream deduplication and a replay policy.
- For direct updates to an overlay resource, use its own If-Match validator and 412 semantics.
- Test lost responses, same-key races, stale views, cache lag, and cross-tenant replay.

<a id="rest-q37"></a>

**Q37: Partner needs a breaking change next sprint.**

**L4**

- Try an additive field or representation first.
- Dual-serve during consumer migration.
- Use a new version when compatibility cannot meet the requirement.

**L5 extra**

- Choose among additive change, expand-contract, new version, and a negotiated retirement based on consumer independence and deployment control.
- Identify the owner of every affected consumer.
- Set a dated migration and rollback plan.
- Use observed version/projection usage plus consumer confirmation; ordinary REST payload field reads are invisible to the server.
- Do not remove the old contract just because an arbitrary traffic threshold is low.

<a id="rest-q38"></a>

**Q38: REST face on a batch/ETL boundary.**

**L4**

- Expose ingest runs at /ingest-runs/{id}.
- Return 202 only after durable acceptance.
- Include status, counts, progress, and structured error summaries.
- Expose per-file results as bounded sub-resources.

**L5 extra**

- Deduplicate initiation separately from worker deliveries and database effects.
- Model a deliberate re-run as a new intent with its own identity and provenance.
- Make natural-key upserts deterministic where repeated ingestion should converge.
- Define retention, cancellation semantics, terminal outcomes, and recovery of abandoned work.
- An upsert alone does not deduplicate notifications or external writes; use explicit effect-level recovery.

<a id="rest-q72"></a>

### Q72. How do you test REST?

**L4**

- Use `@WebMvcTest` to check routes, validation, response statuses, and Problem Details mapping.
- Use real-database integration tests for persistence constraints and transaction behavior.
- Use consumer contract tests to preserve relied-upon success and failure behavior.

**L5 extra**

- Race two same-key requests and assert one committed effect with a replayable response.
- Simulate a committed write whose response is lost, then retry with the original key.
- Assert a stale conditional write fails without overwriting newer state.
- Verify cross-tenant reads, writes, and idempotency replays are denied.
- Set fixture-specific query-count budgets on hot endpoints to prevent N+1 regressions.
- Exercise client handling of 429, 503, timeouts, validation failures, and concurrency conflicts.
