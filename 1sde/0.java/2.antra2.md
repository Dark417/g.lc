## 1. Java Core & JVM

### 1.1 Java 17 new features (asked 2×)

**L4**

- Sealed classes — restrict which classes may extend a type
- Records — immutable data carriers, generated equals/hashCode/toString
- Pattern matching for `instanceof` — no explicit cast
- Text blocks, switch expressions (arrow syntax)
- My usage: records for DTOs/events; sealed interfaces for closed hierarchies (instrument types); 17 is LTS → enterprise standard

**L5**

- The theme is data-oriented programming: records + sealed + pattern matching together
  → sealed type + exhaustive switch = compiler proves every case handled
  → replaces visitor-pattern boilerplate
- Defeaters:
  → records are shallowly immutable — a record holding a mutable `List` is still mutable unless you copy in the compact constructor
  → sealed forces `final`/`sealed`/`non-sealed` on every permitted subclass — a maintenance contract, not just syntax
- 🗣 "Records + sealed + pattern matching give the JVM algebraic data types — invariants move into the type system."

### 1.2 Java 21 new features

**L4**

- Virtual threads (Loom) — cheap JVM-scheduled threads; blocking code scales like async
- Record patterns + pattern matching for switch → final
- Sequenced collections (`getFirst`/`getLast`)
- Structured concurrency, string templates → preview
- Headline: thread-per-request Spring handles tens of thousands of concurrent requests without reactive rewrites

**L5**

- Mechanism: a blocked virtual thread unmounts from its carrier platform thread at JDK park points → blocking I/O is cheap
- Defeaters:
  → `synchronized` pinned the carrier in 21 (fixed JDK 24, JEP 491) — hot synchronized sections could exhaust carriers
  → ThreadLocal: each virtual thread gets its own copy → memory blowup with heavy TL caching
  → connection pools and pinning must be audited — "just enable it" is not free
- Structured concurrency is the long-term win: parent scope owns child lifetimes → cancellation/error propagation stop being ad-hoc

### 1.3 Where do you use sealed classes?

**L4**

- Closed domain hierarchies: sealed `Instrument` permits `Bond`, `Equity`, `Fund`
- Payoff: switch-over-type becomes exhaustive
  → adding a subtype breaks the build everywhere unhandled — compile-time, not runtime
- Used for instrument-type routing in my reconciliation flow

**L5**

- Sealed + records + switch = sum types; invariants move from runtime checks/default branches into the type system
- Defeater: permitted subclasses must live in the same module/package
  → for domain models you own — wrong for extensible plugin points (keep those open)
- vs enums: enums = sealed _singletons_; sealed classes = sealed _families with per-instance state_

### 1.4 Virtual thread vs OS thread

**L4**

- OS (platform) thread: kernel thread
  → ~1MB stack reserved, OS-level creation/context switch → caps at thousands
- Virtual thread: JVM-managed, scheduled onto a small carrier pool
  → pay-as-you-go heap stacks → millions feasible
- Blocking a virtual thread is cheap: JVM unmounts it instead of blocking the kernel thread

**L5**

- Mechanism: continuations — retrofitted I/O parks the continuation, copies stack to heap, frees the carrier
- Defeaters:
  → `synchronized` (pre-24) and JNI frames pin the carrier
  → CPU-bound work gains nothing — still N cores
  → no pooling by design: pool the _resources_ (DB connections), not threads
- At scale the failure moves: thread exhaustion → _downstream_ exhaustion
  → 100k virtual threads happily open 100k DB connection requests
  → semaphores/rate limits replace thread pools as the throttle

### 1.5 Parallel stream vs standard stream — when to use which

**L4**

- Sequential: calling thread. `parallelStream()`: splits via Spliterator onto the common ForkJoinPool
- Use parallel only when ALL hold:
  → CPU-bound work
  → large in-memory collection (~10k+ elements, non-trivial per-element cost)
  → no shared mutable state
- I/O-bound work or inside a web request → stay sequential

**L5**

- Defeater 1: common FJP is JVM-global
  → a parallel stream doing blocking I/O starves every other parallel stream + CompletableFuture default executor
- Defeater 2: splitting cost depends on source
  → ArrayList splits O(1); LinkedList/iterator sources split terribly → parallelism can be net negative
- In a Spring request path: almost never parallelStream — explicit bounded executor so capacity is owned and observable
- Deciding variable: cost-per-element × count vs fork/join overhead, and CPU vs I/O bound

### 1.6 Can we change state in a subclass of a record parent class?

**L4**

- Trick question — records cannot be a parent class:
  → implicitly `final`, cannot be extended
  → cannot extend another class (they extend `java.lang.Record`)
  → components are final fields — nothing to mutate
- Need a hierarchy? → sealed interface that records implement

**L5**

- Design intent: a record is a transparent nominal tuple — API fully derived from state
  → extension would break the compiler-generated equals/hashCode contract
- Escape hatch: `sealed interface X permits RecordA, RecordB` — hierarchy without state inheritance
- Remaining hole: record field referencing a mutable object is still mutable through the reference — immutability is shallow

### 1.7 HashMap vs ConcurrentHashMap / how does HashMap work

**L4**

- HashMap:
  → bucket array, index = `hash(key) & (capacity-1)`
  → collisions: linked list → red-black tree past 8 entries/bucket (Java 8+)
  → resize at load factor 0.75
  → NOT thread-safe: concurrent writes lose entries / corrupt structure
- ConcurrentHashMap:
  → per-bin CAS + synchronized (no segment locks since Java 8)
  → lock-free reads; no null keys/values

**L5**

- CHM reads = volatile reads, no lock → get() scales linearly with readers
- Writes: CAS an empty bin, or synchronize on the bin head → contention is per-bucket, not per-map
- Defeaters:
  → `size()` is an estimate under concurrency
  → compound actions (check-then-put) still race — use `compute`/`putIfAbsent`
  → 🗣 "thread-safe map ≠ thread-safe logic"
- Treeify needs Comparable keys; equal-hash attack degrades to O(log n) not O(n) — deliberate Java 8 DoS defense

### 1.8 LinkedList vs ArrayList

**L4**

- ArrayList: resizable array
  → O(1) index access, amortized O(1) append, O(n) middle insert/delete (shifting)
- LinkedList: doubly-linked
  → O(1) insert/delete _at a known node_, O(n) to find it, O(n) index access
- Practice: ArrayList wins almost everywhere — cache locality

**L5**

- LinkedList's O(1) rarely materializes:
  → O(n) traversal to reach the node
  → per-node heap object: 3 references overhead, pointer-chasing defeats prefetch, GC pressure
- Honest defaults: ArrayList by default → ArrayDeque for queue/stack → LinkedList ~never
- Interview trap: reciting Big-O without the constant-factor/locality story

### 1.9 What is a Collection / Java 8 Stream API

**L4**

- Collection framework: `Collection` tree (List, Set, Queue) + Map alongside; impls: ArrayList, HashSet, HashMap
- Streams: declarative lazy pipelines
  → intermediate ops (map/filter/sorted) build; terminal op (collect/reduce) executes once
  → streams don't store data; single-use per instance

**L5**

- Mechanism: laziness + fusion — intermediates fuse into one pass
  → `filter().map().findFirst()` short-circuits, touches only needed elements
- Defeaters:
  → stateful lambdas/side effects = undefined under parallel
  → `groupingBy` materializes everything — a stream is not a memory free pass
- Optional discipline: return from finders; never fields/params

### 1.10 Checked vs unchecked exceptions / how do you handle exceptions

**L4**

- Checked (extends Exception): must declare or catch — recoverable, caller can act (IOException)
- Unchecked (RuntimeException): programming errors / unrecoverable — propagate freely
- My service pattern:
  → translate low-level exceptions into a small domain hierarchy
  → handle once at the boundary: `@RestControllerAdvice` → HTTP codes + consistent error body

**L5**

- Where to convert: catch low → wrap with context (ids, operation) → rethrow → handle once at the edge
  → catch-log-rethrow at every layer = triple-logged noise, zero new information
- Checked compose badly with lambdas/streams; frameworks are runtime-first
  → practical rule: checked only when the _immediate_ caller has a real recovery
- Classify retryable vs terminal explicitly (e.g. `TransientException` marker)
  → this classification is what retry/circuit-breaker policy hangs off
  → get it wrong → poison-pill errors retry forever

### 1.11 JVM heap vs stack

**L4**

- Stack: per-thread
  → frames: locals, operand stack, return addresses
  → freed on return; overflow → StackOverflowError
- Heap: shared, all objects, GC-managed; exhaustion → OutOfMemoryError
- References on the stack → objects on the heap

**L5**

- Nuances:
  → escape analysis: JIT can scalar-replace non-escaping objects — "all objects on heap" is the spec model, not always physical
  → Metaspace (class metadata) = native memory, OOMs separately
  → platform stacks reserve ~512KB–1MB each — exactly the cost virtual threads remove (heap-allocated continuations)
- Heap is generational (young/old in G1/Parallel)
  → allocation = pointer bump; short-lived garbage nearly free

### 1.12 App throws OOM — what do you do / GC parameters (Kafka consumer OOM variant)

**L4**

- Read _which_ OOM first — each names a different cause:
  → `Java heap space` / `GC overhead limit exceeded` / `Metaspace` / `unable to create native thread`
- Capture evidence: `-XX:+HeapDumpOnOutOfMemoryError` → Eclipse MAT dominator tree → retaining path
  → usual culprits: unbounded caches/collections, oversized batch reads
- Fix the leak or bound the buffer; raise `-Xmx` only after proving the working set is legitimately larger

**L5**

- Kafka consumer specifics — fetch buffering is the mechanism:
  → `max.poll.records`, `fetch.max.bytes`, `max.partition.fetch.bytes` bound memory per poll
  → many partitions on one consumer multiplies it
  → canonical pattern: OOM right after a rebalance concentrated partitions
- You don't "trigger GC with a parameter" (`System.gc()` is a smell) — you _choose and size_ the collector:
  → G1 + `-XX:MaxGCPauseMillis`; diagnose with `-Xlog:gc*`
  → old gen climbing monotonically = leak; healthy sawtooth hitting ceiling = undersized
- Guardrail: alert on old-gen occupancy trend + GC time %, not on the OOM itself

### 1.13 Mockito: usage / mock vs spy / what mocking library

**L4**

- JUnit 5 + `@ExtendWith(MockitoExtension.class)`
  → `@Mock` full stub; `when(...).thenReturn(...)`; `@InjectMocks` wires; `verify()` asserts interactions
- Mock = entirely fake. Spy = wraps a real object
  → real methods run unless stubbed
  → stub spies with `doReturn(...).when(spy)` to avoid invoking the real method
- Mock ports/boundaries (repos, clients, queues) — not value objects

**L5**

- Heavy `verify()` couples tests to implementation
  → prefer state assertions; reserve interaction verification for true side effects (message published, rollback called)
- Spy = usually a design smell (class doing two things) → fix is extraction, not `doReturn`
- Mock only at the architectural boundary (hexagonal ports); real objects inside
  → this is what keeps tests refactor-safe
  → ArgumentCaptor + asserting captured payload beats loose `any()` matchers

## 2. Spring Boot & Spring Framework

### 2.1 Auto-configuration — how does it work

**L4**

- `@SpringBootApplication` → `@EnableAutoConfiguration`
  → loads candidates from `META-INF/spring/...AutoConfiguration.imports` in each starter
- Each candidate gated by conditions:
  → `@ConditionalOnClass` — dependency present
  → `@ConditionalOnMissingBean` — you haven't defined your own
  → `@ConditionalOnProperty` — config toggles
- Result: add `starter-data-jpa` + datasource props → working EntityManager, zero XML

**L5**

- Key mechanism: _ordering + back-off_
  → auto-config runs after user config; `@ConditionalOnMissingBean` defers to your beans
  → the extension contract = override by defining, not by excluding
- Debug: `--debug` condition evaluation report, or actuator `conditions` endpoint
- Defeater: conditions evaluate against the classpath
  → a transitive dependency can silently activate config (e.g. two datasource starters)
  → `spring.autoconfigure.exclude` is the escape hatch but a smell — fix the classpath

### 2.2 What is component scan

**L4**

- `@ComponentScan`: which packages to scan for `@Component`/`@Service`/`@Repository`/`@Controller` → register as beans
- `@SpringBootApplication` implies scanning from its own package downward
  → why the main class sits at the root package
- Beans outside the tree are invisible → `scanBasePackages` or explicit import

**L5**

- Mechanism: classpath scan via ASM metadata reading (no class loading) at startup → BeanDefinition registration before instantiation
  → scan breadth affects startup time in big monoliths
- Design tension: broad scanning is convenient but implicit
  → for libraries/shared modules: explicit `@Configuration` + auto-config imports so consumers opt in
- Canonical failure: "my @Service isn't found" = bean defined above/outside the main class's package

### 2.3 Spring Boot Actuator

**L4**

- Production-readiness endpoints: `/health` (liveness/readiness groups), `/metrics` (Micrometer), `/info`, `/env`, `/loggers` (runtime level changes), `/threaddump`, `/heapdump`
- Usage: `/health` → LB + k8s probes; `/metrics` → Datadog via Micrometer registry

**L5**

- Liveness vs readiness semantics:
  → liveness fail → pod restart; readiness fail → pulled from LB only
  → DB check wired into _liveness_ → restart storms during a DB blip (canonical outage pattern)
- Attack surface: `/env`, `/heapdump` leak secrets
  → expose minimum; separate management port behind network policy
- Micrometer = vendor-neutral metrics; tags/dimensions designed there, not in the backend

### 2.4 @Autowired — what/why / injecting without it

**L4**

- Injects a dependency by type (narrowed by qualifier/name on ambiguity) during bean creation
- Why: classes declare _what_ they need, not how to build it → container manages lifecycles; tests substitute fakes
- Without `@Autowired`: single-constructor injection is implicit since Spring 4.3
  → declare as constructor parameter — the recommended style anyway

**L5**

- Constructor injection wins for concrete reasons:
  → fields `final` — safe publication, no partially-constructed state
  → instantiable in plain unit tests without Spring
  → too-many-dependencies becomes visible in the constructor
- Field injection: breaks under proxies; lets circular dependencies "work" via late injection
  → hides a design error that constructor injection correctly turns into a startup failure
- Resolution chain: by type → `@Qualifier` → parameter name
  → knowing it = fast `NoUniqueBeanDefinitionException` debugging

### 2.5 What is @Qualifier

**L4**

- Multiple beans of one type → `@Qualifier("name")` picks which to inject
- Without it: `NoUniqueBeanDefinitionException` unless one bean is `@Primary`
- Example: primary vs DLQ `QueueClient` implementations at different call sites

**L5**

- Better options:
  → custom qualifier annotation (meta-annotated `@Qualifier`) — compiler-checked, no strings
  → structural: two interfaces if the beans serve genuinely different roles
- `@Primary` = default; `@Qualifier` = override → the intended "default + special case" pair
- Qualifier-ing constantly = the type design is wrong; the container is compensating for a modeling problem

### 2.6 Transaction propagation / REQUIRED vs REQUIRES_NEW / where used

**L4**

- Propagation = how `@Transactional` relates to an existing transaction
- REQUIRED (default): join caller's TX or start one → one atomic unit
- REQUIRES_NEW: suspend caller's TX, run own → commits independently even if outer rolls back
- My use: REQUIRES_NEW for audit/outcome logging that must persist when the business op fails

**L5**

- Implemented in the proxy interceptor
  → self-invocation (`this.method()`) bypasses it entirely — the classic "inner REQUIRES_NEW didn't work" bug
- REQUIRES_NEW holds a _second_ connection while the first is suspended
  → pool deadlock under load: outer holds conn A, waits for conn B the pool can't supply
  → size the pool for it, or move audit writes to an after-commit event
- Rollback rules: only unchecked roll back by default
  → checked exceptions commit unless `rollbackFor` set — silent data-corruption source

### 2.7 Spring Security internal flow

**L4**

- Servlet filter chain (`SecurityFilterChain`), in order:
  → authentication filter extracts credentials → builds `Authentication`
  → `AuthenticationManager` → delegates to `AuthenticationProvider`s (DAO + PasswordEncoder, or JWT decoder)
  → success → `SecurityContextHolder` (thread-local)
  → then authorization: URL rules (HttpSecurity DSL) + method rules (`@PreAuthorize`)
- Failures: AuthenticationEntryPoint → 401; AccessDeniedHandler → 403

**L5**

- Two-phase split matters: authentication filters establish identity; `AuthorizationFilter` + `AuthorizationManager` enforce later
  → customize at the right phase
- Stateless JWT APIs: disable session creation + CSRF
  → CSRF defends cookie sessions; irrelevant for header tokens — saying _why_ is the differentiator
- Thread-local SecurityContext breaks under async/reactive handoffs
  → context doesn't follow the thread
  → `DelegatingSecurityContextExecutor` / reactive context propagation — a real production bug class

### 2.8 Spring Batch: retry vs skip

**L4**

- Both = chunk-step fault tolerance policies
- Retry: re-attempt the same item on _transient_ failure (deadlock, timeout), bounded, with backoff
- Skip: give up on a specific bad item — log via SkipListener, continue — for data errors that will never succeed
- Rule: retry infrastructure errors, skip poison data — classify exceptions explicitly into the two buckets

**L5**

- Mechanism: failure inside a chunk → chunk TX rolls back → items reprocessed one-by-one to isolate the offender
  → writers must be idempotent or the re-scan double-applies side effects
- Failure modes:
  → retry without an exception whitelist → retries terminal errors against the limit (waste + alert noise)
  → skip without `skipLimit` → silently discards a whole corrupt feed
- Guardrail: bounded skip + listener that quarantines the record somewhere queryable
  → this is the DLQ question in pipeline form

### 2.9 Validate a REST request / validate + dedupe input

**L4**

- Syntactic: Bean Validation on the DTO
  → `@NotNull`/`@Size`/`@Pattern`, nested `@Valid`; triggered by `@Valid` on the controller param
  → violations → 400 with field errors via `@RestControllerAdvice`
- Semantic (cross-field, existence): service layer, not annotations
- Dedupe: idempotency key (client-supplied or canonical-payload hash)
  → unique constraint or Redis `SET NX EX`; replays return the original result

**L5**

- Layering is the point: cheap syntax checks fail fast at the edge; semantic checks need repositories behind the boundary
  → mixing them couples the API contract to persistence
- Concurrency-correct dedupe = unique constraint in the write itself
  → two requests race → one insert wins → loser catches the violation, reads the winner's result
  → Redis SETNX: lower latency but adds a TTL window + a second consistency domain
- Defeater: hashing the payload breaks when clients retry with trivially different payloads (timestamps)
  → client-generated idempotency key is the durable contract

### 2.10 Circuit breaking, timeouts, retries / Resilience4j / low threshold effect

**L4**

- Resilience4j:
  → `@CircuitBreaker` — opens past failure-rate threshold over sliding window → half-open → probe → close
  → `@Retry` — bounded attempts, exponential backoff + jitter, transient exceptions only
  → `@TimeLimiter` + client timeouts; `@Bulkhead` caps concurrency
- Order: timeout inside retry inside breaker; fallback method for degraded responses
- Threshold too low → breaker opens on normal noise
  → self-inflicted outage: rejecting calls to a healthy dependency, open/half-open flapping

**L5**

- Breaker's job: load shedding — convert slow failures into fast failures
  → what stops thread-pool/connection exhaustion from cascading
- Retries at scale are dangerous: retry storms amplify load on a degraded dependency
  → N services × 3 retries = 3× traffic at the worst moment
  → cap with budgets/jitter; never retry non-idempotent writes without an idempotency key
- Timeouts must be shorter upstream than downstream (deadline propagation)
  → else caller gives up while work continues → orphaned work + duplicates
  → canonical pattern behind "double writes during the incident"

### 2.11 Spring Boot app is slow — what do you do

**L4**

- Bound it first: which endpoint, since when, p50 vs p99, correlated with deploy/traffic — from APM traces, not guesses
- Follow the trace to the dominant span:
  → DB (missing index, N+1)
  → downstream call without timeout
  → pool exhaustion (DB/HTTP pool at max)
- Fix the dominant cost → verify on the same metric → add an alert on it

**L5**

- Triage tree:
  → p99-only regression → GC pauses, pool queueing, slow shard
  → uniform shift → deploy or dependency latency
  → throughput collapse under load → saturation (threads/connections), not per-request cost
- Concrete tooling:
  → SQL logs / hibernate statistics for N+1
  → HikariCP active/pending for pool starvation
  → async-profiler flame graph for CPU; GC logs for pauses
- Principle: measure → dominant bottleneck → fix → re-measure
  → optimizing off the critical path is decoration

### 2.12 JPA vs Hibernate / other ways to connect to DB

**L4**

- JPA = spec (EntityManager, JPQL, annotations); Hibernate = dominant impl + extensions (Session, HQL, caching)
- Spring Data JPA = repository interfaces + derived queries on top
- Alternatives: JdbcTemplate / Spring Data JDBC (explicit SQL), jOOQ (type-safe SQL), MyBatis
  → I use JdbcTemplate for bulk/reporting where ORM state management is overhead

**L5**

- Real decision: do you benefit from a stateful persistence context?
  → dirty checking, identity map, lazy loading pay off for rich domain writes
  → same features cause N+1, LazyInitializationException, surprise UPDATEs
- Read-heavy/set-based → projections/DTOs or plain SQL beat entities
- Flush ordering + first-level cache explain most "why did Hibernate do that" bugs
- Default: Spring Data JPA for CRUD aggregates; explicit SQL where the JOIN strategy is worth controlling

### 2.13 WebClient vs RestTemplate

**L4**

- RestTemplate: classic blocking client, maintenance mode
- WebClient: non-blocking/reactive (WebFlux); usable from blocking apps via `.block()`
- RestClient (Spring 6.1+): modern _synchronous_ client, WebClient-style fluent API
- Today: RestClient in servlet apps; WebClient for streaming / true async composition

**L5**

- The distinction is threading: WebClient on Reactor Netty holds no thread during I/O wait
  → valuable at high fan-out concurrency
  → but `.block()` inside MVC just moves the blocking + adds a second event-loop runtime to operate
- Virtual threads (21) make blocking RestClient scale comparably for most workloads
  → removes the main argument for reactive complexity in ordinary services
- Whatever client: set connect/response timeouts explicitly
  → defaults are effectively infinite in several stacks
  → "no timeout" is the root cause behind most cascading-failure postmortems

### 2.14 Exclude configuration from Spring Boot

**L4**

- Auto-config: `@SpringBootApplication(exclude = ...)` or `spring.autoconfigure.exclude`
- Own components: `@ComponentScan` excludeFilters
- Conditional instead of excluded: `@Profile`, `@ConditionalOnProperty`
- Tests: `@TestConfiguration`, slice tests (`@WebMvcTest`) load only what's needed

**L5**

- Prefer conditional over excluded:
  → exclusion is a global hammer; breaks when another module legitimately needs the bean
  → `@ConditionalOnProperty` documents intent, tunable per environment
- If excluding auto-config, ask why it activated
  → usually a dependency that shouldn't be on the classpath — fixing the pom is more durable than suppressing the symptom

### 2.15 TDD / production standards / code coverage

**L4**

- TDD: failing test → minimal code to pass → refactor
  → suite = executable spec + regression net
- Our bar: PR review · unit + integration tests in CI (Testcontainers) · static analysis · ~80% coverage floor on changed lines, enforced as a gate
- Deploys blocked on green pipeline

**L5**

- Coverage is a floor detector, not a quality metric
  → 100% lines with assertion-free tests proves nothing
  → mutation testing (PIT) is the honest signal: tests must fail when code is broken
- Test at the right seam: unit on domain logic → contract tests at boundaries → few e2e
  → inverted pyramid = flaky suites
- TDD's actual payoff is design pressure (testable = decoupled), not the ritual

## 3. Kafka & Messaging (SQS/SNS/RabbitMQ)

### 3.1 How does Kafka work / why Kafka / what is a Kafka event

**L4**

- Distributed, partitioned, replicated commit log:
  → producers append records (key, value, headers, timestamp) to topic partitions
  → brokers persist sequentially to disk
  → consumers pull at their own pace; position = committed offsets
  → messages age out by retention — not deleted on consumption
- Why over a queue: replay · multiple independent consumer groups · per-partition ordering · very high throughput
- Event in my project: an immutable fact — e.g. `OfferingRecordEnriched` — downstream services react to it

**L5**

- Throughput mechanisms:
  → sequential appends + OS page cache
  → zero-copy (`sendfile`) on the consume path
  → producer batching + compression
  → 🗣 "Kafka is fast because it does almost no per-message work"
- Log-not-queue is the strategic difference: decouples producers from N consumers _in time_
  → replay, late-joining consumers, reprocessing after a bug fix — impossible with delete-on-ack queues
- Defeaters:
  → ordering per partition only
  → consumer lag monitoring is your responsibility
  → wrong fit: request/reply RPC, small random-access — REST/queues territory

### 3.2 How do you ensure message ordering in Kafka

**L4**

- Order guaranteed only _within a partition_
  → route order-dependent messages to one partition via a consistent key (accountId) — default partitioner hashes the key
- No global order across partitions
- Producer: `enable.idempotence=true`
  → allows `max.in.flight.requests.per.connection` up to 5 while preserving order on retries

**L5**

- Defeater 1: without idempotence, in-flight > 1 breaks even per-partition order
  → batch 2 succeeds while batch 1 retries and lands after
  → idempotent producer = per-partition sequence numbers enforced by the broker
- Defeater 2: increasing partition count remaps key→partition
  → destroys order across the boundary — plan partition counts up front for ordered topics
- Defeater 3: ordering ends at consumption
  → concurrent thread-pool processing per partition reintroduces reordering
  → process per-partition serially, or key-order within the executor

### 3.3 Consumer lagging / rebalancing / performance — root cause and fix

**L4**

- Quantify first: lag per partition (Burrow/Datadog/`kafka-consumer-groups`)
  → all partitions lagging = throughput problem
  → one partition = hot key or stuck message
- Frequent rebalances:
  → exceeded `max.poll.interval.ms` (poll batch processed too slowly)
  → missed heartbeats (GC pauses, pod restarts) — look for "leaving group" in logs
- Fixes:
  → reduce `max.poll.records`; raise `max.poll.interval.ms`
  → speed up per-record processing: batch DB writes, remove sync remote calls
  → scale consumers up to at most partition count

**L5**

- Name the rebalance→lag death spiral:
  → slow processing → eviction → rebalance pauses the whole group → lag grows → restarted consumer gets a bigger backlog → exceeds interval again
  → break the loop: smaller poll batches · offloaded processing with manual commits · cooperative-sticky assignor (less stop-the-world)
- Three root-cause families:
  → consume-side cost → fix processing
  → produce-side spike → scale partitions/consumers
  → skew → hot key → fix the keying
- Consumers beyond partition count sit idle
  → the scaling ceiling is a topic-creation decision → lag SLOs should feed partition sizing

### 3.4 Consumer processed but crashed before committing offset — what happens?

**L4**

- Restart/rebalance resumes from last _committed_ offset
  → already-processed records delivered again = at-least-once → duplicates are the consumer's problem
  → hence side effects must be idempotent
- The mirror image: commit before processing = at-most-once → crash loses messages instead

**L5**

- Frame as the two-phase problem: "process" and "commit offset" are writes to two systems — not atomically combinable without machinery → you pick your anomaly
- Robust patterns:
  → idempotent writes keyed by event/business id — dedupe at the sink
  → transactional outbox
  → Kafka→Kafka exactly-once via transactions (offsets committed with output records)
  ◆ scope ends at Kafka's boundary — an external DB write is still your idempotency problem
- Auto-commit widens the window unpredictably (timer during poll)
  → anything that matters: `enable.auto.commit=false`, commit after effects are durable

### 3.5 Idempotent Kafka consumer / fraud events safely reprocessable (design)

**L4**

- Stable id per event (event id or transactionId)
- Conditional write: insert into `processed_events` with a UNIQUE constraint _in the same DB transaction_ as the business write
  → replays hit the constraint → skip
- Commit the Kafka offset only after the TX commits
- Result: at-least-once delivery, exactly-once _effect_

**L5**

- Why it works: collapses "did I process this?" and "the effect" into one atomic commit in one system
  → the dedupe store must share the transaction with the side effect — else you've just moved the two-phase gap
- Alternatives by context:
  → natural idempotency: upsert + version/monotonic check — best for state-replacement writes
  → DynamoDB conditional writes when the sink is Dynamo
  → Redis seen-set only for best-effort dedupe — TTL creates a correctness window
- Fraud-specific:
  → make the decision deterministic on the event (no wall-clock dependence) so replay converges
  → prune the dedupe table by event-time watermark — unbounded growth is this pattern's operational failure

### 3.6 Kafka DLQ / handling failed messages (any queue)

**L4**

- Flow: bounded retries (backoff, optionally tiered retry topics) → still failing → publish to dead-letter topic
  → with diagnostic headers: exception, original topic/partition/offset, attempt count
  → consumer commits and moves on — stops one poison message blocking the partition
- DLQ operations: alert on depth/age · dashboard · re-drive path back to source after the fix

**L5**

- The critical classification: transient vs terminal
  → retrying a deserialization error = pure waste → straight to DLQ
  → DLQ-ing a transient DB outage → floods DLQ with messages that were never bad
  → 🗣 "the error taxonomy drives the policy — 'retry everything N times' fails both ways"
- Re-drive must preserve idempotency
  → consumer sees old events after new ones — ordering is broken by definition once a message detours through a DLQ
- Spring Kafka: `DefaultErrorHandler` + `DeadLetterPublishingRecoverer` with backoff
- Guardrail metric: DLQ **age** — depth alone hides a stuck re-drive

### 3.7 REST vs Kafka (sync vs async between services)

**L4**

- REST: synchronous request/response
  → immediate answer, natural backpressure
  → coupled to callee availability and latency
- Kafka: asynchronous fire-and-record
  → decoupled in time; log absorbs spikes; N consumers react independently
  → eventual consistency; no immediate response
- Rule: queries/workflows needing an answer now → REST; facts/state changes others react to → events

**L5**

- Deeper contrast = failure coupling:
  → sync chain multiplies availability: three 99.9% hops ≈ 99.7%; latency spikes propagate up
  → event bus converts a consumer outage into _lag_ instead of caller errors — the real resilience argument
- Honest costs:
  → duplicate delivery · ordering scope · schema evolution as a public contract (Avro/Schema Registry + compatibility rules)
  → debugging much harder — correlation ids + tracing become mandatory
- Real systems are hybrid: commands sync, facts async — either/or is the junior tell

### 3.8 SQS vs SNS

**L4**

- SQS = queue: consumers pull; one consumer processes each message; unprocessed wait → buffering + work distribution
- SNS = pub/sub push: fans out to all subscribers (SQS, Lambda, HTTP, email); not stored for later consumers — no replay
- Standard pattern: SNS→SQS fanout — SNS routes, each queue buffers per service with its own retry/DLQ

**L5**

- Why fanout: decouples delivery from processing
  → per-subscriber backpressure, DLQs, independent consumption rates
  → 🗣 "resilience lives in the queue; routing lives in the topic"
- Defeaters:
  → SQS standard: at-least-once + best-effort ordering — dedupe is on you
  → FIFO: ordering per message group + dedupe-id semantics, but throughput capped per group
  → SNS filter policies push routing into subscription config — cheap, but treat them as versioned IaC or you lose track

### 3.9 Do SQS standard queues guarantee ordering within a message group? (Y/N)

**L4**

- **No.** Message groups are a FIFO-queue concept
  → standard queues: no groups, best-effort ordering, at-least-once (possible duplicates)
- Need per-group ordering → FIFO queue + MessageGroupId

**L5**

- Cost of the FIFO answer:
  → ordering serializes consumption per group — a stuck message blocks its group
  → throughput bounded per group
  → "exactly-once" = 5-minute dedupe-id window; beyond it, idempotency is still your job
- Senior close: "No — and before reaching for FIFO, check whether sink-side idempotency + a version check makes ordering unnecessary."

### 3.10 RabbitMQ queue 500 → 5k — debug

**L4**

- Depth growing = consume rate < publish rate → split it:
  → publish spike? (upstream event, retry storm — publish metrics)
  → consume drop? (consumer crashes/restarts, slower processing, slow downstream — consumer count, ack rate, latency)
- Also check:
  → unacked pileup — consumer holding without acking, prefetch too high
  → poison message redelivering in a loop
- Fix the dominant side: scale consumers, fix the slow dependency, DLQ the poison

**L5**

- Rabbit-specific trap: nack + requeue=true → message cycles at the head forever
  → consumes all throughput while depth grows
  → guardrail: bounded retries + DLX; quorum queues expose `x-delivery-count`
- Memory/flow control: Rabbit backpressures _publishers_ at memory watermarks
  → a deep queue can degrade publishers cluster-wide — storage is not a free buffer (unlike Kafka)
- Structural fix if recurring: lazy/quorum queues for depth tolerance — or admit the workload is a log and belongs in Kafka

### 3.11 How long are messages retained?

**L4**

- Kafka: time/size-based per topic (`retention.ms`, commonly 7 days default), independent of consumption
  → compacted topics: latest record per key kept indefinitely
- SQS: 1 minute – 14 days (default 4 days); deleted when the consumer deletes after processing
- RabbitMQ: until consumed/acked, or per-queue TTL

**L5**

- Kafka retention = your replay + recovery window
  → must exceed worst-case consumer outage + reprocessing time
  → canonical incident: consumer down over a long weekend, retention 3 days → silent data loss as the log ages out
- Related-but-different knob people confuse: SQS visibility timeout
  → in-flight redelivery timer — set shorter than processing time and you _manufacture_ duplicates

### 3.12 Multiple topics / consumer walkthrough

**L4**

- Spring Kafka `@KafkaListener`: multiple topics or a pattern; concurrency N = N consumer threads splitting partitions
- Pipeline shape: batch → deserialize + validate → idempotency check → transform → persist → publish downstream → manual ack
  → failures → error handler → retries with backoff → DLQ
- Separate listeners/groups per topic when SLAs or scaling profiles differ

**L5**

- One consumer on many topics couples their fates:
  → poison message / slow sink on topic A stalls polls + rebalances that also hit topic B
  → isolation → separate containers/groups unless genuinely one logical stream
- Ack strategy = the at-least-once contract:
  → `MANUAL_IMMEDIATE` after durable effects
  → per-record ack costs throughput; per-batch widens the duplicate window on crash — pick per SLA
- Concurrency capped by partition count per topic → "just increase concurrency" hits a topic-design ceiling

## 4. AWS — Lambda

### 4.1 What is Lambda / why / story / where used

**L4**

- Event-driven serverless compute:
  → ship a function; AWS provisions/scales execution environments per concurrent event
  → billed per invocation + GB-second; no servers, patching, idle cost
- Fits: event glue (S3/SQS/DynamoDB Streams triggers) · spiky or low-volume workloads · scheduled jobs
- My story: test-data injection utility
  → on-demand Lambda injecting 30+ record types for end-to-end testing → cut debugging setup ~80%
  → fit: irregular invocation, zero standing infra, clean IAM scoping

**L5**

- The trade: operational control (runtime tuning, long-lived connections, local state) ↔ elasticity + zero idle cost
- Deciding variables:
  → invocation pattern — steady high volume favors containers on cost
  → 15-minute hard duration ceiling
  → cold-start latency tolerance
- Concurrency is the unit of scaling _and_ failure:
  → burst scales environments to the account/reserved cap, each re-running init
  → downstream connection limits (Aurora) are what Lambda bursts break first
  → mitigations: RDS Proxy, SQS-buffered invocation

### 4.2 Cold start — what is it / manage it / "true cold start"

**L4**

- Cold start = new execution environment: download code → start runtime → run init (JVM, Spring context, SDK clients)
  → seconds for Java; warm invocations reuse and skip it all
- Mitigations:
  → provisioned concurrency (pre-warmed)
  → SnapStart for Java (restore a post-init snapshot)
  → smaller artifacts, lazy/light init, heavy frameworks out of the handler path

**L5**

- "True" cold start = full environment creation _including your init phase_ (vs warm-start variance)
- Java mechanism: JIT + classloading + DI container dominate
  → SnapStart (CRaC snapshot restored per environment) cuts it ~an order of magnitude
  → caveat: restore requires uniqueness hygiene — re-seed randomness, refresh credentials/connections via runtime hooks
- Provisioned concurrency = paying for idle again
  → if you need it at steady high traffic, compare honestly against Fargate — Lambda may be the wrong shape
- Scaling _bursts_ cause cold starts even at steady state → p99 SLOs decide the mitigation, not averages

### 4.3 Lambda vs ECS / vs Spring Boot service / "Lambda architecture"

**L4**

- Lambda: per-event, scales to zero, 15-min cap, no standing process → glue, spikes, low/irregular volume
- ECS (Fargate): long-running containers, runtime control, persistent connections + in-memory state, better $/compute at sustained load
- My default: Spring Boot on ECS for core APIs; Lambda for event handlers + operational tooling
- If they mean data-eng "Lambda architecture": dual batch + speed layers merged at query time
  → largely superseded by streaming-first/Kappa (single Delta/Kafka pipeline)

**L5**

- Cost crossover: per-ms pricing wins at low utilization, loses badly at sustained high RPS
- Operational crossover: connection/state management
  → pools, caches, websockets all want a long-lived process
- Hard constraints: cold starts, 15-min limit
- Account-wide concurrency = shared blast radius
  → one runaway function starves others → reserved concurrency is the isolation tool
- Asking _which_ "Lambda architecture" they mean is itself a good senior move — the term collision is real

### 4.4 Increase Lambda concurrency / avoid throttling

**L4**

- Concurrency = in-flight executions; regional account pool (default 1,000, raisable by quota request)
- Per function:
  → reserved concurrency — guaranteed slice + hard cap
  → provisioned concurrency — pre-initialized for latency
- SQS-triggered: event-source `maximumConcurrency` throttles intake
- So: raise quota → reserve for critical functions → provision latency-sensitive paths

**L5**

- More concurrency is often the wrong fix — will _downstream_ survive it?
  → Lambda happily scales to 1,000 concurrent DB writers and takes Aurora down
  → reserved concurrency is a _brake_ as much as a guarantee
- Throttle behavior differs by invocation type:
  → sync → 429 to caller
  → async → retried with backoff → DLQ
  → stream-based → blocks the shard/partition
- Senior framing: concurrency limits are bulkheads — partition the account pool so a bursty function can't starve the payment path

### 4.5 Debug a Lambda error

**L4**

- CloudWatch Logs: per-invocation log group, find REPORT line + stack trace, correlate by request id
- Metrics: Errors, Throttles, Duration, IteratorAge (streams) → failing vs throttled vs timing out
- X-Ray: which downstream call inside the invocation is slow/failing
- Async sources: failure destination / DLQ holds the original event payload

**L5**

- Triage split:
  → timeout — Duration ≈ configured max, no exception → hung downstream call with no client timeout
  → throttle — 429s, _no logs at all_ → capacity, not code
  → init failure — error before handler → config/permissions
  → handler exception — the only one the stack trace directly explains
- Async retries twice by default → un-idempotent handler double-fires _during debugging_
- Failure destinations (full event) beat log archaeology — you can replay the exact input
- Structured JSON logs + correlation id propagated from the source event = what makes cross-service tracing possible

### 4.6 DynamoDB Streams → Lambda throws — what happens, how to prevent

**L4**

- Stream invocation is ordered per shard → a failing batch retries _blocking that shard_
  → default: until the record expires (24h for DynamoDB Streams) → poison pill stalls everything behind it
- Prevention (event source mapping settings):
  → `maximumRetryAttempts`
  → `bisectBatchOnFunctionError` — split batch to isolate the bad record
  → `onFailure` destination (SQS/SNS) for failed records
  → partial-batch responses (`ReportBatchItemFailures`)

**L5**

- Mechanism: stream sources trade availability for ordering
  → retry-forever default is _correct_ for ordered processing, catastrophic for throughput
  → the settings above choose how much ordering you sacrifice to keep the shard moving
- Detection: rising `IteratorAge` = stuck shard
  → alarm on it _before_ the 24h expiry silently drops data
- Handler idempotency non-negotiable — retries + bisection guarantee re-delivery of processed records

### 4.7 Lambda authorizer with API Gateway

**L4**

- A function API Gateway invokes before your integration:
  → receives token (TOKEN type) or full request context (REQUEST type)
  → validates — e.g. JWT signature vs IdP JWKS, expiry, audience
  → returns an IAM policy (Allow/Deny) + optional context forwarded to the backend
- Configure per API/route; authorizer-result TTL caches decisions per token; unauthorized → 401/403 before your service

**L5**

- Decision point: plain JWT validation → built-in JWT authorizer (HTTP APIs) / Cognito authorizer — less code, less latency
  → Lambda authorizer earns its cost only when authorization needs _logic_ (tenant lookups, entitlements, custom formats)
- Caching sharp edge:
  → policy cached per token for the TTL → revocation lags by up to TTL
  → a coarse cached Deny can block legitimate follow-ups with different context — cache-key granularity must match authz granularity
- Fail-closed + authorizer cold starts sit on every request's critical path → provision accordingly

### 4.8 Lambda + "stream"

**L4**

- Sense 1 — consuming stream sources: Kinesis, DynamoDB Streams, Kafka/MSK
  → event source mapping polls shards → invokes with ordered batches
- Sense 2 — response streaming: stream the response progressively (large payloads, LLM tokens) instead of buffering
- In our context usually sense 1: near-real-time reaction to table/stream changes

**L5**

- The event source mapping is the real machine:
  → owns polling, batching (`batchSize`, `maxBatchingWindow`), per-shard ordering, parallelization factor, failure policy
  → tuning happens there, not in the handler
- Throughput = shard count × parallelization factor → sharding is the ceiling (same shape as Kafka partitions)
- Response streaming changes billing/limits (time-to-first-byte wins)
  → only function URLs / specific integrations support it — verify before designing around it

## 5. AWS — DynamoDB & Aurora

### 5.1 Aurora vs DynamoDB

**L4**

- Aurora: relational (PostgreSQL/MySQL-compatible)
  → SQL, joins, ACID transactions, ad-hoc queries
  → storage auto-scales; compute instance-based (or Serverless v2)
- DynamoDB: managed key-value/wide-column
  → single-digit-ms at any scale; provisioned or on-demand throughput
  → access by key + pre-designed indexes only — no joins, no ad-hoc flexibility
- Rule: relational modeling / evolving queries / cross-entity TX → Aurora; known access patterns at scale with strict latency → Dynamo
- Our platform: canonical records in Aurora (integrity, SQL consumers); Dynamo for high-throughput lookups

**L5**

- Real dividing line: _must you know your queries up front?_
  → Dynamo forces access-pattern-first design; changing your mind later = migration
  → Aurora lets queries evolve, at the cost of instance sizing + connection management
- Scaling shapes:
  → Dynamo: horizontal by partition, no connection concept — pairs perfectly with Lambda bursts
  → Aurora: reads via replicas, writes vertical; connection limits are what serverless bursts break (hence RDS Proxy)
- Consistency:
  → Aurora: real multi-row ACID
  → Dynamo: item-level atomicity + bounded `TransactWriteItems` (100 items) — cross-entity invariants are more work

### 5.2 Partition key design / partition vs sort key

**L4**

- Partition key hash determines physical placement → it must:
  → serve the primary access pattern as an equality lookup
  → distribute load — high cardinality, no hot value
- Sort key: orders items within a partition
  → range queries (`begins_with`, between), one-to-many modeling
  → e.g. PK=`customerId`, SK=`ORDER#2026-08-19#id` → "orders for a customer, by date"
- Design starts from the access-pattern list, not entities

**L5**

- Physics: ~3,000 RCU / 1,000 WCU per partition (AWS docs)
  → a hotter single key throttles regardless of table capacity
  → adaptive capacity rebalances but cannot split _one key's_ traffic
- Known-hot keys → write sharding: `key#1..N` suffix, fan-in on read
  → cost: N-fold read amplification
- Senior tell: SK taxonomies for item collections (single-table design, entity types sharing PK)
  → fewer round trips ↔ schema opacity + painful migrations

### 5.3 LSI vs GSI

**L4**

- LSI: same partition key, alternate sort key
  → strongly-consistent reads possible
  → must exist at table creation; shares the 10GB item-collection limit
- GSI: entirely different partition+sort key
  → created anytime, own throughput
  → eventually consistent only
- Default to GSI; LSI only for strong consistency on an alternate sort within the same partition

**L5**

- GSIs are async-replicated shadow tables — the source of both gotchas:
  → replication lag → read-after-write can miss on the GSI
  → an under-provisioned GSI's throttling backpressures _base-table writes_ — index config can take down your write path
- LSI 10GB item-collection cap is a hard wall that arrives without warning on large customers
- Projection = the cost lever: ALL doubles storage + write cost → project only what queries read

### 5.4 Fix a hot partition purely by adding a GSI on the same key? (Y/N)

**L4**

- **No.** Same partition key → same hash distribution → same key hot on the index
  → and GSI replication _adds_ write load
- Real fixes: write sharding (key suffix) · different partition key that spreads traffic · caching (DAX/ElastiCache) if the heat is read-side

**L5**

- Underlying rule, worth stating:
  → 🗣 "Key-distribution problems are never fixed by adding capacity or replicas of the same distribution."
  → true for Dynamo partitions, Kafka partition keys, DB shard keys alike — fix at the keying/write-pattern layer
- Adaptive capacity buys headroom for moderate skew (isolates a hot key onto its own partition)
  → but caps at per-partition maxima — sustained single-key heat past ~1,000 WCU is a design problem by definition

### 5.5 Update a table's partition key at runtime?

**L4**

- You can't:
  → primary key schema immutable after creation
  → item key attributes can't be updated in place (delete + re-insert only)
- Key redesign = migration: new table → backfill (Scan / S3 export + transform) → dual-write during cutover → verify → flip readers

**L5**

- Production-grade migration adds:
  → DynamoDB Streams (or app-layer dual-write) to capture writes during backfill — don't lose the delta
  → idempotent backfill (conditional puts) so re-runs converge
  → verification: counts + sampled item diffs
  → rollback plan: keep the old table until confidence
- Cheaper alternative sometimes: a GSI with the desired key as _its_ partition key, serve the new pattern from the index
  → valid exactly when eventual consistency + write amplification are acceptable

### 5.6 Can we join in DynamoDB?

**L4**

- No join operation — queries hit one table or one index
- Joins are handled by _design_:
  → single-table design: related entities under one PK → one Query returns the "pre-joined" item collection
  → or app performs multiple queries, joins in memory
- Genuinely relational ad-hoc joins → wrong tool → Aurora signal

**L5**

- Principle: Dynamo moves the join from query time to _write time_
  → materialize the shapes reads need (denormalization, item collections, GSIs as alternate joins)
  → trade storage + write complexity for constant-time reads — pays only when access patterns are stable
- Analytics joins over Dynamo data → exported copy (S3 export → Athena/Spark), never the serving path
- "No joins" without the design substitute is the L3 answer — the substitute _is_ the answer

### 5.7 How did you improve DynamoDB cost/performance?

**L4**

- Levers used:
  → billing mode fit: on-demand for spiky/unknown; provisioned + auto-scaling for steady (much cheaper sustained)
  → trim GSI projections to what queries read
  → batch ops (BatchGetItem/BatchWriteItem)
  → shorter payloads — attribute _names_ count toward size
  → TTL to expire dead data free
  → kill hot-path Scans with the right GSI
- Measure: consumed capacity + throttles per table/index, before and after

**L5**

- Structural insight: cost = access-pattern efficiency
  → RCU per 4KB, WCU per 1KB → item size and read shape _are_ the bill
  → biggest win usually: Scan+filter (pays for everything scanned, not returned) → keyed Query
- Eventually-consistent reads cost half of strong reads
  → defaulting to strong everywhere = paying double for a guarantee most reads don't need
- DAX/cache tier changes economics for read-heavy hot keys
  → adds an invalidation problem — only with measured read skew

## 6. AWS — Other Services

### 6.1 Why S3 / what is S3

**L4**

- Object storage: durable (11-nines design durability, AWS docs), effectively unlimited, pay-per-GB, HTTP access by key
- Default landing zone: files, data lake, backups, static assets
- Why we used it:
  → cheap durable storage decoupled from compute
  → event notifications (S3 → Lambda/SQS) to trigger processing
  → lifecycle policies for cold tiers; IAM/bucket policies for access

**L5**

- Precise properties:
  → strongly consistent read-after-write since Dec 2020 — stale answers still say "eventual"
  → throughput scales per key _prefix_
  → object store ≠ filesystem: no appends, no atomic renames
  ◆ exactly why table formats (Delta/Iceberg) exist — transactional semantics on top
- Cost drivers: storage class + request patterns
  → lifecycle to IA/Glacier for cold data
  → millions of tiny objects → per-request cost dominates → compaction is a necessity, not a nicety

### 6.2 Why EC2 / what is EC2

**L4**

- Raw VMs: pick instance type, OS, networking; run anything
  → full control; full responsibility — patching, scaling (ASGs), utilization
- Use when: custom runtimes, OS-level control, GPUs, long-lived stateful workloads
- Standard containerized services → ECS/Fargate removes host management

**L5**

- Axis: control ↔ operational surface
  → modern default: climb the ladder (EC2 → ECS on EC2 → Fargate → Lambda) until a requirement stops you
- Cost mechanics at scale: reserved/savings plans vs on-demand vs spot
  → spot for interruptible batch = 60–90% off; interruption handling is the price
- "We used EC2 because it was there" = junior tell; naming the requirement that pinned you = senior

### 6.3 Step Functions — what / why / states

**L4**

- Managed workflow orchestrator: state machine (ASL/JSON) coordinating Lambdas + AWS services
  → handles sequencing, branching, retries + backoff, error catching, timeouts
  → per-run execution history visible
- States: Task · Choice · Parallel · Map (fan-out) · Wait · Pass · Succeed · Fail
- Why: replaces hand-rolled orchestration; long-running multi-step flows become durable + observable

**L5**

- Orchestration vs choreography:
  → Step Functions centralizes the flow — explicit, debuggable, one home for saga/compensation logic
  → choreography = looser coupling, but the workflow exists only implicitly across services
  → pick orchestration when the _process_ is the domain object (approvals, provisioning, human steps)
- Standard vs Express is the real choice:
  → Standard: exactly-once orchestration, up to 1 year, per-transition pricing
  → Express: at-least-once, 5 min, cheap at volume → steps must be idempotent
- Defeater: high-frequency low-value hops through Standard gets expensive fast — that traffic belongs on queues

### 6.4 EventBridge / can rules filter by details? (Y/N) / scheduled triggering

**L4**

- Serverless event bus: sources publish → rules match on event _content_ → route to targets (Lambda, SQS, Step Functions, API destinations)
- **Yes** — event patterns filter on any field
- Scheduled triggering across services → EventBridge Scheduler (cron/rate, any target) — successor to CloudWatch Events cron

**L5**

- vs SNS:
  → EventBridge: content routing, schema registry, SaaS sources, archive/replay → the _integration_ bus
  → SNS: raw high-throughput low-latency fanout primitive
  → deciding variable: routing sophistication vs throughput/latency
- Delivery: at-least-once, retry + DLQ per target, no ordering → consumers dedupe, same as everywhere
- Scheduler adds one-off `at()` schedules, timezones, flex windows — why it's the current recommendation over cron rules

### 6.5 What is CloudFront

**L4**

- AWS CDN: caches at edge locations → users hit a nearby edge, not your origin (S3, ALB, API Gateway)
  → lower latency, less origin load, DDoS absorbed at edge (WAF/Shield)
- Typical: static assets/SPA from S3; cache behaviors per path; TTLs via cache policies/headers

**L5**

- Design work = cacheability partitioning:
  → immutable assets: long TTL + hashed filenames
  → dynamic API paths: short/no TTL — still gain edge TLS termination + origin connection reuse
- Invalidation is slow and costs money → versioned URLs beat invalidation as deploy strategy
- Private content: signed URLs/cookies push authz to the edge
- Origin Access Control locks S3 so the CDN is the only path
  → public bucket alongside CloudFront = canonical misconfiguration

### 6.6 CloudWatch / which metrics do you monitor

**L4**

- Telemetry backbone: metrics (built-in + custom) · logs (Insights queries) · alarms (→ SNS/paging) · dashboards
- What I watch:
  → services: p99 latency, error rate, saturation (CPU/mem, pools)
  → queues/streams: depth/age, consumer lag, IteratorAge
  → Lambda: Errors, Throttles, Duration
  → DBs: connections, replica lag, throttled requests
- Alarms page on symptoms (SLO burn); dashboards explain causes

**L5**

- Philosophy: alert on _user-facing symptoms_ tied to SLOs, not every resource metric
  → cause-based alerts (CPU high) → pager fatigue
  → symptom-based (availability, latency budget burn) → catches what matters regardless of cause
- Mechanics:
  → standard metrics = 1-min resolution; high-resolution costs extra
  → Logs Insights bills per GB scanned → structured JSON + correlation id is what makes it usable
- Composite alarms + anomaly detection cut flapping
- 🗣 "Every page must be actionable, or you're training the team to ignore pages."

### 6.7 What is IAM

**L4**

- Identity + authorization: identities (users, groups, roles) + JSON policies (actions on resources, with conditions)
- Services assume _roles_ → temporary credentials
  → e.g. ECS task role reads one bucket + one queue — least privilege, no long-lived keys in code

**L5**

- Evaluation model is the substance:
  → explicit Deny > Allow > implicit deny
  → across identity policies + resource policies + permission boundaries + SCPs
  → debugging "access denied" = knowing which layer denied
- Roles + STS = the security architecture: auditable assumption (CloudTrail), expiring credentials, cross-account as a trust-policy question
- Practice: IaC'd per-service roles, resource-level ARNs, conditions
  → wildcard `Action: *` in a reachable role = the finding every audit starts with

### 6.8 X-Ray — what and why

**L4**

- Distributed tracing: stitches a request across services (API GW → Lambda/ECS → DynamoDB/HTTP) into a trace
  → per-segment timing + errors, plus a service map
- Why: logs say _that_ each service ran; the trace says _where_ time went and which hop threw

**L5**

- Mechanism: trace id propagates via headers; SDK/agent records segments and samples
  → default ~1 req/sec + 5% → latency-analysis tool, not an audit log; rare errors can be unsampled → tune rules on critical paths
- Traces / metrics / logs answer different questions (where / how much / why); correlation ids tie them
  → we fronted this with Datadog APM — same model; naming the model matters more than the vendor
- OpenTelemetry: instrument once, export anywhere — the current standard to mention

### 6.9 API Gateway benefit / serverless containers for blue-green

**L4**

- Gateway: single entry point + centralized cross-cutting concerns
  → authn/z, rate limiting, TLS, routing, validation, caching
  → services don't reimplement them; clients don't couple to internal topology
- Serverless containers for blue-green: **ECS on Fargate** + CodeDeploy blue/green behind an ALB
  → two target groups, shifted traffic, auto-rollback on alarms; App Runner for simplest cases

**L5**

- Gateway's deeper value: decouple public contract from internal structure
  → services split/merge/move behind stable routes; policy becomes configuration
  → cost: an availability-critical hop; temptation to bury business logic in it (ESB anti-pattern — keep it dumb)
- Blue-green mechanism: two identical environments, traffic-level cutover, instant rollback
  → defeaters:
  ◆ DB schema must be compatible across both colors — expand/contract migrations
  ◆ in-flight state: drain connections, dual-compatible consumers

## 7. Databases & SQL

### 7.1 SQL vs NoSQL

**L4**

- SQL: relational schema, joins, ACID, ad-hoc querying — model once, ask new questions later
- NoSQL: a family (key-value, document, wide-column, graph)
  → trades relational flexibility for horizontal scale, flexible schemas, predictable latency on known patterns
- Default SQL for transactional business data; NoSQL when a specific access pattern at a specific scale demands it

**L5**

- The line has blurred: Postgres does JSONB + read scaling; Dynamo does transactions
- Durable decision variables:
  → do you know your queries up front? (NoSQL's requirement)
  → cross-entity invariants needed? (SQL's strength)
  → scaling shape: partition-per-key horizontal vs primary-writer vertical
- Consistency semantics differ underneath:
  → SQL: isolation levels within one node's TX domain
  → distributed NoSQL: per-item atomicity + tunable/eventual consistency
  → pretending either gives you the other = where correctness bugs come from

### 7.2 `WHERE age != NULL` — what happens? Does `age != 10` return NULL rows?

**L4**

- `age != NULL` → **zero rows**
  → any comparison with NULL = UNKNOWN, not true → no row passes
  → correct: `age IS NOT NULL`
- `age != 10` also **excludes** NULL rows — NULL != 10 is UNKNOWN, WHERE keeps only TRUE
  → include them: `WHERE age != 10 OR age IS NULL`

**L5**

- Mechanism: three-valued logic (TRUE/FALSE/UNKNOWN), WHERE filters on TRUE only — same rule, four disguises:
  → `NOT IN` with a NULL in the list returns nothing — the classic production bug
  → CHECK constraints _pass_ on UNKNOWN
  → aggregates ignore NULLs
- Null-safe inequality: `IS DISTINCT FROM`
- This is a fluency probe: answer instantly, then volunteer the NOT IN trap — operational knowledge, not trivia

### 7.3 What is a partial index?

**L4**

- Index over only rows matching a predicate:
  → `CREATE INDEX ON orders (customer_id) WHERE status = 'PENDING'`
  → small, cheap to maintain, serves queries that include the predicate
- Ideal when queries target a small hot subset (active/pending/unprocessed) of a large table

**L5**

- Two mechanisms:
  → writes to non-matching rows skip index maintenance → write amplification drops
  → planner uses it only when it can _prove_ the query predicate implies the index predicate
  ◆ parameterized status / unprovable inequality → silent seq-scan fallback — the operational gotcha
- Killer pattern — partial **unique** index:
  → `UNIQUE (email) WHERE deleted_at IS NULL` = "one active account per email" — inexpressible with plain unique
- Engine note: Postgres/SQLite; SQL Server = filtered indexes; MySQL lacks them

### 7.4 SQL tuning — slow query

**L4**

- Plan first: `EXPLAIN ANALYZE`
  → seq scans where an index applies · misestimated row counts · expensive join/sort nodes
- Common fixes:
  → composite index: equality columns first, then range/sort
  → non-sargable predicates: `WHERE fn(col) = x` defeats the index → index the expression / move fn to the constant side
  → select needed columns only; keyset pagination over deep OFFSET
- Verify with the plan + p99 after — not vibes

**L5**

- Statistics layer: misestimates from stale stats → planner picks nested loops over hashes (or vice versa)
  → sometimes the fix is feeding the planner truth (ANALYZE, raise stats targets on skewed columns), not adding indexes
- Covering indexes (INCLUDE) → index-only scans, no heap fetches — visible as "Heap Fetches" in the plan
- Systemic:
  → every index taxes writes + vacuum → index strategy is a portfolio decision per read/write mix
  → 🗣 "the fastest query is the one you stop running" — cache/precompute beats micro-tuning a reasonable plan

### 7.5 Transactions — DB / Spring / project

**L4**

- Transaction = atomic unit with ACID: all statements commit or roll back together, isolated per isolation level
- Spring: `@Transactional` on the service method
  → proxy opens TX, commits on success, rolls back on runtime exceptions; propagation/isolation as attributes
- Project: canonical record persistence + processed-event bookkeeping in one TX → replays stay idempotent

**L5**

- Bites:
  → proxy-only — self-invocation bypasses it
  → rollback defaults exclude checked exceptions → `rollbackFor`
  → connection held for the whole method → remote HTTP call inside a TX holds a pool connection hostage — classic pool exhaustion
- Isolation = the tradeoff surface:
  → READ COMMITTED (typical default) permits non-repeatable reads
  → REPEATABLE READ/serializable cost throughput; may force retry-on-serialization-failure
- Transactions end at the DB boundary → cross-service = sagas/outbox — the segue interviewers want

### 7.6 Stored procedures / triggers / cursors / packages / calling from Spring

**L4**

- Stored procedure: precompiled DB logic, invoked by name with params — explicit call
- Trigger: fires automatically on table events (INSERT/UPDATE/DELETE) — you don't call it
- Cursor: row-by-row iteration inside procedural code
- Package (Oracle): groups procedures/functions, spec/body, shared state
- From Spring: `JdbcTemplate`/`SimpleJdbcCall` or `@Procedure`, mapping IN/OUT params

**L5**

- The stance they're probing: business logic in the DB
  → buys: fewer round trips, set-based performance, invariants near the data
  → costs: weak testability, opaque versioning, vendor lock-in, invisible coupling
  ◆ triggers especially — side effects nobody sees in the code path → canonical "why did this row change" incident
- Legitimate today: data-adjacent bulk ops, legacy estates; new services keep logic in the app, DB for constraints
- Cursors signal row-by-row thinking → the set-based rewrite is usually orders faster — that's the senior answer

### 7.7 Pagination

**L4**

- Offset: `LIMIT/OFFSET`, Spring `Pageable` — fine for admin UIs with page numbers
- Keyset/cursor: `WHERE (created_at, id) < (:last...) ORDER BY created_at DESC, id DESC LIMIT n`
  → default for anything large
- Why: OFFSET scans and discards all skipped rows → deep pages get linearly slower, shift under inserts

**L5**

- Mechanism: keyset seeks directly into the index at the last-seen composite key
  → O(page) per request regardless of depth
  → stable under concurrent inserts — no skipped/duplicated rows across pages (offset can't promise this)
- Requirements/costs:
  → deterministic total order — always include a unique tiebreaker column, with a matching index
  → no random page jumps; cursor must encode the sort
- Same pattern in DynamoDB natively: `LastEvaluatedKey`/`ExclusiveStartKey` — recognizing the cross-store pattern is the senior note

## 8. Microservices, Architecture & System Design

### 8.1 How do services communicate / request flow API→DB

**L4**

- Synchronous: REST/GraphQL via internal ALB/gateway
  → for queries + commands needing an immediate answer
  → timeouts, retries, circuit breakers on every client
- Asynchronous: SNS/SQS + Kafka
  → facts and workflows — producer persists → publishes → consumers process independently, own DLQs
- Request flow: client → API Gateway (authn, throttle) → ECS service (validate → business logic → repository) → Aurora → events published post-commit

**L5**

- Rule: sync for _queries in the user's critical path_; async for _state propagation_
  → sync chains multiply latency + compound availability
  → async converts downstream outages into lag
- The dual-write at the boundary: "persist then publish" can lose the publish on crash
  → fix: transactional outbox — event row commits with the business row, relay to broker
  → naming it unprompted is a differentiator
- Every async edge needs: idempotent consumer + DLQ + correlation id end-to-end — else debugging is archaeology

### 8.2 Global transactions / SAGA

**L4**

- No ACID across services — no shared TX manager; 2PC avoided (blocking coordinator, availability coupling)
- Saga: sequence of local transactions, each publishing the trigger for the next
  → failure → _compensating transactions_ undo completed steps (release inventory, refund payment)
- Two styles:
  → choreography — services react to each other's events — simple flows
  → orchestration — Step Functions / saga orchestrator — central visibility + error handling

**L5**

- What sagas give up: atomicity AND isolation
  → intermediate states are visible (reserved-but-unpaid order exists) → domain must model pending states explicitly
  → compensations are _semantic_ undos, not rollbacks — can't un-send an email; send a correction
- Design consequences:
  → every step idempotent (retries)
  → compensations retryable, can't fail permanently — or you need manual-intervention queues
  → orchestration beats choreography past ~3 steps — the implicit event web becomes undebuggable
- 🗣 "Consistency moves from the database to the process design."

### 8.3 CQRS / read-write model consistency

**L4**

- Split write model (commands, validated domain logic, normalized store) from read model (denormalized projections per view)
  → connected by events updating the projections
- Value: each side scales/evolves independently
- Consistency = eventual: projection updates after event propagation
  → read-your-writes tricks: return the write result · version tokens · author reads the write model

**L5**

- Costs = the senior content:
  → two models to maintain
  → projection rebuild machinery — replayable events (why CQRS pairs with an event log)
  → lag monitoring as a first-class SLO
  → projection updaters are consumers: dedupe + ordering apply
- Staleness contract must be explicit per view:
  → "search lags 5s" fine · "balance lags 5s" not — that classification is the design work
- Defeater: CQRS on simple CRUD = pure overhead — earns its cost only when read/write shapes genuinely diverge

### 8.4 DDD / monolith → microservice boundaries

**L4**

- DDD: model around the business domain
  → ubiquitous language · entities/value objects/aggregates · strategic part = _bounded contexts_
  → context = boundary where a model and its terms are consistent ("Account" in billing ≠ identity)
- Decomposition: bounded contexts are the seams
  → clusters that change together and share language
  → never split by technical layer — a "database service" or "validation service" is the anti-pattern

**L5**

- Boundary-finding signals:
  → transactional scope — data that commits together stays together (an aggregate IS a consistency boundary)
  → team/ownership lines — Conway's law as a tool
  → rate-of-change clustering (commit history)
  → where the language changes meaning
- Migration mechanics: strangler fig
  → facade routes traffic → extract one context at a time → anti-corruption layer translates models → DB split _last_
- Failure prevented: cutting too fine too early = distributed monolith
  → every action fans across five services with 2PC-shaped problems → coarse-first, split-when-forced

### 8.5 Design: idempotent SQS order processing / duplicate orders at peak

**L4**

- Assume duplicates — SQS standard is at-least-once, clients retry
- Every order event carries a stable idempotency key (client-generated request id)
- Atomic dedupe-with-effect:
  → unique constraint in the orders table (or `processed_events` in the same Aurora TX), or DynamoDB conditional write
  → duplicate → constraint hit → treat as success, return original outcome
- Delete the SQS message only after the durable effect

**L5**

- Load-bearing decision: _where atomicity lives_
  → dedupe-check and side-effect must share one atomic operation in one system
  → "check Redis then write DB" is subtly broken — crash between them reopens the window
  → 🗣 "unique constraint in the write itself is the gold standard"
- Peak-hour UI duplicates → add the front door:
  → idempotency-key header minted when checkout renders → double-clicks collapse server-side
  → disable-on-click = UX defense-in-depth, never the mechanism
- Retention: dedupe record must outlive max retry horizon (SQS retention + client retries) → TTL after
  → store the _result_ with the key so replays return the original response, not an error

### 8.6 Design: file upload, 100k/day / unstable upload link

**L4**

- 100k/day ≈ 1–2/sec average with bursts → presigned S3 URLs:
  → API authenticates, validates metadata, issues time-limited presigned PUT
  → client uploads directly to S3 — service never proxies bytes
- Post-upload: S3 event → SQS → processor (scan/validate/thumbnail) async → status update → client polls or gets notified
- "Sometimes fails" debugging — usual suspects:
  → presigned URL expiry (slow uploads outliving TTL) · clock skew
  → large files needing multipart · LB/proxy idle timeout · CORS on a browser subset

**L5**

- Why presigned is the architectural point:
  → bandwidth + availability burden moves to S3 → scaling becomes a metadata problem
  → security surface shrinks to URL issuance
  → defeaters: no inline content inspection (async scan + quarantine bucket before promotion) · URL leakage within TTL
- Multipart with per-part retry = what makes large/flaky uploads reliable
  → "unstable link" bugs are very often single-PUT uploads that should have been multipart
- Intermittent-failure discipline:
  → 🗣 "intermittent means conditional" — slice failures by file size / client / region / time
  → the dimension separating success from failure names the cause

### 8.7 Migrate 150 REST APIs to GraphQL

**L4**

- Not a rewrite — a facade migration:
  → GraphQL layer (federation-ready) in front of existing REST; resolvers delegate to current endpoints
  → migrate consumers screen-by-screen where aggregation pays most; REST stays until traffic drains
- Schema from the _domain_ — never transliterate 150 endpoints into 150 fields
- DataLoader batching in from day one

**L5**

- Strategic risks:
  → schema is a one-way door — a REST-shaped schema forfeits the benefit
  → N+1 amplification: naive resolver graph turns one query into hundreds of REST calls → DataLoader + batch endpoints are prerequisites
  → authorization moves per-endpoint → per-field — flat "authenticated = allowed" leaks data through traversal
- Operational: persisted queries + depth/complexity limits before exposure; per-field resolver latency measured
- Federation lets each team own its subgraph — that org-scaling property is usually the real justification

### 8.8 Fault tolerance / scaling / vertical vs horizontal

**L4**

- Fault tolerance layers:
  → redundancy: multi-AZ, N+1 behind LB + health checks
  → isolation: timeouts, retries (backoff+jitter), circuit breakers, bulkheads per dependency
  → degradation: fallbacks, feature flags
  → async buffering: queues absorb downstream outages
- Scaling: horizontal by default — stateless behind LB, autoscaled
  → vertical: quick lever, hard ceiling, a restart — DBs and singleton-ish components
  → horizontal prerequisite: statelessness — session/state in Redis/DB

**L5**

- Fault tolerance = _containing_ failure, not preventing it
  → per dependency ask: "what happens when it's _slow_?" — slow is worse than down
  → slow dependencies exhaust caller resources and cascade → fast-fail + shed-load beats queue-and-hope
- Scaling nuance: horizontal moves the bottleneck to shared state
  → stateless tier is trivial; the _coordination_ (DB connections, locks, hot keys) is the actual problem
  → why the follow-up analysis is always about the datastore
- Autoscaling on the wrong signal (CPU for I/O-bound) does nothing → scale on the saturated resource or SLO burn

### 8.9 New release broken in prod / local fine prod not / HTTP 503

**L4**

- Mitigate first, diagnose second:
  → errors correlate with release → roll back or flip the flag → investigate with preserved evidence
- Local-vs-prod checklist:
  → config/env vars · data shape + volume · dependency versions · network/IAM/security groups · concurrency races · container resource limits
- 503 = "no healthy backend or overloaded":
  → LB target health (failing checks?) · health check misconfigured · pool/thread saturation · downstream failing the health check

**L5**

- Rollback-first requires rollback-_safe_ releases:
  → backward-compatible schema (expand/contract) · dual-compatible consumers · flags decoupling deploy from release
  → teams that can't roll back debug in production under pressure — the real failure
- 503 producers, distinguished:
  → LB: zero healthy targets → registration/health-check config
  → service: rejecting under saturation → queue/pool metrics
  → upstream proxy timeout misread as backend failure
  → LB access logs' error-source field tells you which
- Prod-only bugs = _environment as input_: diff effective config + data, don't re-read the code
  → afterwards close the gap: config parity, prod-like staging data

### 8.10 Zero-downtime deployment / rollback mechanics

**L4**

- Rolling or blue-green behind the LB:
  → new version alongside old · readiness gates traffic admission · connections drain before termination
- Rollback:
  → redeploy previous immutable image tag through the same pipeline
  → blue-green: shift traffic back to the still-warm old environment instantly
  → CodeDeploy/Spinnaker automate shifting + auto-rollback on alarms during bake

**L5**

- Invisible requirement: N and N+1 run _simultaneously_ during any zero-downtime deploy
  → DB schema (expand/contract: add-nullable → dual-write → migrate → contract), message schemas, API contracts must all tolerate one version skew
  → most "zero-downtime" failures are compatibility failures, not traffic-shifting failures
- Canary refines blue-green: 1–5% first → judged automatically against SLO metrics → promote or revert
- Rollback must be _rehearsed_: an untested rollback path is a hypothesis
  → schema-coupled releases silently destroy it — why migrations deploy separately from code

### 8.11 Design SSO with Spring Boot + API Gateway + Redis + JWT

**L4**

- Central auth service: login (delegate to IdP/OIDC), issues short-lived JWT access + refresh token
- Gateway validates JWT per request (signature/claims, JWKS cached) → forwards identity context → services stateless
- Redis holds what JWTs can't:
  → refresh-token store · revocation denylist (checked at gateway) · shared session metadata if needed
- SSO: all apps redirect to the same auth service — existing session → no re-login

**L5**

- Core tension: stateless (verify anywhere, no lookup) ↔ irrevocable until expiry
  → answer: short access TTL (minutes) + refresh rotation + gateway-only denylist
  → bounds revocation lag to the access TTL; per-request cost = one signature check + one cache hit
- Key management is the real ops surface: JWKS rotation with `kid` + overlap windows — or rotation becomes an outage
- Name the standard: this is OIDC (authorization code + PKCE for browsers)
  → hand-rolling token issuance where Cognito/Okta fits = build-vs-buy miss

### 8.12 Low-latency multi-tenant search re-ranking (design)

**L4**

- Two-stage retrieval:
  → stage 1: candidate generator (inverted index / ANN) returns top-N cheaply
  → stage 2: re-ranker scores those N with a richer model, reorders, keeps best few
  → re-ranking only N (hundreds) is what bounds latency
- Multi-tenancy: tenant id partitions everything
  → per-tenant indices/filtered namespaces · per-tenant feature configs + model variants · per-tenant quotas
- Latency budget end-to-end (e.g. 150ms p99) allocated per stage; features precomputed/cached; model on a low-latency tier

**L5**

- Latency engineering is mostly _feature plumbing_, not the model:
  → precompute doc features offline · cache user/tenant features (Redis, TTL) · one vectorized scoring call
  → adaptive N under load — fewer candidates = graceful degradation; shed re-ranking entirely (serve stage-1 order) = circuit-breaker fallback
- Multi-tenant tradeoff: shared model + tenant features (cheap, cold-start-friendly) vs per-tenant models (quality ceiling, ops sprawl)
  → deciding variable: tenant data volume + divergence
- p99 tails come from cache misses + GC → measure the tail; hedged requests for feature fetches = classic mitigation

## 9. Security & Auth

### 9.1 How do you secure an application / API / web service (asked ~6×)

**L4**

- Layered:
  → TLS everywhere
  → authn: OIDC/JWT — no home-rolled crypto
  → authz: endpoint level AND resource level (RBAC + ownership checks)
  → input validation + output encoding (injection/XSS)
  → secrets in Secrets Manager/SSM — never code or committed env files
  → rate limiting at the gateway
  → dependency scanning (Dependabot/Snyk) + least-privilege IAM for the service itself
  → audit logging on sensitive operations

**L5**

- Frame as defense-in-depth against _named_ failure classes:
  → broken object-level authorization (OWASP API #1) — the per-resource ownership check teams forget
  → injection — parameterized queries only
  → SSRF — egress controls when the app fetches URLs
  → credential leakage — short-lived STS over static keys
- Security is a pipeline property: SAST/dependency/IaC gates in CI, not a review-time activity
- Threat-model by data sensitivity — public catalog API ≠ payments API
  → 🗣 "knowing where to spend is the architect skill"

### 9.2 How does JWT work / how do FE+BE secure it / validation

**L4**

- Three base64url parts: header (alg, kid) · payload (sub, exp, iat, aud, iss) · signature (issuer-signed, RS256 typical)
- Backend validation:
  → verify signature against issuer's public key (JWKS, cached)
  → check exp, iss, aud
  → no DB lookup — the stateless win
- Frontend: `Authorization: Bearer` header
  → store in memory, or httpOnly + Secure + SameSite cookie for web
  → localStorage = XSS-readable = the flagged anti-pattern

**L5**

- Claims are the contract:
  → `aud` stops a token for service A replaying at service B
  → `kid` enables key rotation with overlap
  → clock-skew tolerance on `exp` is deliberate slack
- Real vulnerability classes:
  → libraries skipping `aud`/`iss` checks
  → historic `alg: none` / HS256-with-public-key confusion → allowlist the algorithm server-side
- Signature proves _authenticity_, not _freshness of authorization_
  → entitlement changes and revocations lag until expiry → short TTL + refresh rotation is the architecture
- Never put secrets/PII in the payload — encoded, not encrypted

### 9.3 Where do you store tokens / JWT in the DB?

**L4**

- Access tokens: NOT in a DB — self-validating by design
  → browser: in-memory or httpOnly Secure cookie, not localStorage
- Server-side storage is for:
  → refresh tokens — hashed, revocable, rotated on use
  → optional denylist of revoked jti in Redis until natural expiry
- Storing every JWT and checking per request = rebuilding sessions, forfeiting the stateless benefit

**L5**

- It's a spectrum:
  → pure JWT — zero lookup, zero revocation
  → opaque session ids — one lookup, instant revocation
  → standard midpoint: short-TTL JWT + stored refresh + gateway denylist
  → 🗣 "place a design on that spectrum with its revocation-lag number" — that's the senior answer
- Refresh rotation + reuse detection: an old rotated token replayed ⇒ revoke the whole family — concrete defense against refresh theft
- Storage choice selects your attack, not whether:
  → cookies → CSRF (SameSite + tokens) · headers → XSS exposure

### 9.4 User logs out but the JWT is still valid

**L4**

- Statelessness = logout can't invalidate an issued token by itself, so:
  → delete token client-side
  → revoke the refresh token server-side — no new access tokens
  → if immediate invalidation required: jti → Redis denylist, TTL = remaining lifetime, checked at gateway
- Short access TTL (5–15 min) bounds exposure either way

**L5**

- State the tradeoff: a per-request denylist check reintroduces a stateful lookup
  → small (one Redis GET at the gateway) but real
  → failure mode must be decided: fail-open = revocation gap during Redis outage · fail-closed = Redis becomes an availability SPOF
- Most systems: refresh revocation + short TTL suffices; denylist reserved for compromise/privileged logout
- 🗣 "Logout in a JWT system is a policy about _future_ tokens, plus an optional bounded denylist for present ones — pure statelessness and instant revocation are mutually exclusive."

### 9.5 OAuth + JWT / authn+authz in Spring Security

**L4**

- OAuth 2.0 = delegation/authorization framework
  → grants: authorization code + PKCE (user-facing), client credentials (service-to-service)
- OIDC = identity layer on top (ID token); JWT = the common token _format_
- Spring: resource server
  → `spring-boot-starter-oauth2-resource-server` + `issuer-uri` → JWKS validation out of the box
  → authz: route rules + `@PreAuthorize` on scopes/roles; converter maps claims → authorities

**L5**

- Depth-signaling distinctions:
  → ID token is for the _client_ to know the user; access token is for the _API_ — sending ID tokens to APIs is a common misuse
  → scopes are coarse client-level permissions; per-resource authz still lives in domain logic — scope checks alone leave object-level holes
- Method security runs through proxies — same self-invocation caveat as `@Transactional`
- Claim→authority mapping is where multi-IdP and role-format mismatches get normalized
  → centralize in one converter or every service drifts

### 9.6 What is CORS, how do you deal with it

**L4**

- Browser mechanism relaxing same-origin policy:
  → cross-origin request → browser sends Origin (preflights non-simple requests with OPTIONS)
  → server must return `Access-Control-Allow-Origin` (+ methods/headers) for the browser to release the response
- Fix server-side: Spring `CorsConfiguration`/`@CrossOrigin` or at the gateway
  → allowlist exact origins/methods/headers; `allowCredentials` requires a non-wildcard origin

**L5**

- Commonly wrong:
  → CORS is _browser-enforced_ — protects users from malicious sites reading responses; does NOT protect your API from non-browser clients → not an authorization mechanism
  → preflight adds a round trip → `Access-Control-Max-Age` caches it
- Classic misconfiguration: reflecting the request Origin with credentials enabled — disables the protection entirely
- Architectural: same-origin deployment (reverse-proxy the API under the app's origin) removes the problem class
  → 🗣 "configuring CORS well is good; not needing it is better"

### 9.7 GraphQL directives / supergraph authentication

**L4**

- Directive = schema annotation with behavior:
  → `@auth(requires: ADMIN)` enforced by server/gateway
  → federation wiring: `@key`, `@external`
- Federated supergraph auth:
  → router authenticates once (validates JWT) → forwards identity/claims via trusted headers
  → subgraphs enforce per-field/entity authz with that context
  → subgraph endpoints network-locked so only the router reaches them

**L5**

- Trust boundary is the substance:
  → gateway-authenticates + subgraph-authorizes ⇒ subgraphs must trust forwarded identity
  → requires locking the path (mTLS/private routing) — or re-validate per subgraph at latency cost
  → design fork: forward raw JWT vs mint an internal context token
- Field-level authz is structurally different from REST: one query traverses many resources
  → declarative schema-level auth beats resolver-scattered checks for auditability
  → caveat: authorization _data_ (ownership) still needs domain lookups
- Cost/depth limiting is a security control here — unbounded query shapes are a DoS vector REST doesn't have

## 10. GraphQL

### 10.1 GraphQL vs REST / how did you use it / architecture

**L4**

- REST: fixed endpoints, server-decided shapes
- GraphQL: typed schema; client requests exactly the fields it needs in one query
- GraphQL wins when:
  → diverse clients (mobile vs web shapes)
  → views aggregate many resources — one query replaces an endpoint fan-out
- REST stays simpler for: uniform CRUD, file transfer, cache-heavy public APIs (native HTTP caching)
- Ours: GraphQL for the record preview/correction UI over domain services; REST for service-to-service

**L5**

- Under-discussed costs:
  → HTTP caching largely breaks (everything POST /graphql) → per-field caching or persisted queries + GET
  → rate limiting moves from per-endpoint to query-cost analysis
  → monitoring shifts to per-field resolver latency
  → flexible query surface = DoS/authz surface → depth/complexity limits, field-level auth
- Organizational win: schema as typed introspectable contract, deprecation instead of URL versioning
- 🗣 "GraphQL is a client-aggregation technology — one client + simple shapes = overhead; five clients stitching six services = payoff."

### 10.2 N+1 — how do you handle it (asked 3×)

**L4**

- Problem: query for N parents, resolver fetches each parent's children individually → 1 + N calls
  → 100 orders → 100 customer lookups
- Fix: **DataLoader** — per-request batching + caching
  → child resolvers enqueue keys → loader coalesces into one batched call (`WHERE id IN (...)` / batch endpoint) → caches within the request
- Spring GraphQL: `@BatchMapping` (or registered DataLoaders) replaces per-entity `@SchemaMapping`

**L5**

- Mechanism: DataLoader _defers_ — collect keys during traversal, dispatch once
  → why it must be per-request: a shared cache leaks data across users and goes stale
- Defeaters:
  → batching helps only if downstream has a batch shape — a REST dependency without a bulk endpoint caps you; the fix moves to that service
  → nested loaders still multiply — N+1 per _level_
  → DB `IN` list has practical limits → temp-table joins or redesigned projections beyond it
- Systemic answer for read-heavy graphs: precomputed read model (CQRS projection) — traversal never hits OLTP

### 10.3 Overfetching / underfetching

**L4**

- Overfetching: REST returns the full resource for 2 needed fields → wasted bandwidth, coupling
  → GraphQL: the query names exactly the returned fields
- Underfetching: one REST response isn't enough → sequential follow-ups
  → GraphQL: one query traverses relationships (order → customer → address) in one round trip
- That pairing is the core pitch

**L5**

- Honest completion: the _client's_ problem becomes the _server's_ efficient-resolution problem
  → without DataLoader / lookahead projections you've moved N+1 from network to backend
  → field selection can drive the SQL SELECT list (lookahead) — few teams do it
- "Ask for anything" = worst-case queries define capacity → complexity budgets make it plannable again
- REST's own answers (sparse fieldsets, compound documents, BFFs) work too
  → 🗣 "GraphQL standardizes what REST teams hand-roll"

## 11. CI/CD, Kubernetes, Terraform & Deployment

### 11.1 Explain your CI/CD pipeline (asked ~6×)

**L4**

- CI (on PR): build → unit + integration tests (Testcontainers) → static analysis + coverage gates
- On merge: immutable Docker image (Jib) → tag with commit SHA → ECR + vulnerability scan
- CD (Spinnaker): promote the SAME artifact dev → staging (smoke/e2e) → prod

- Infra changes travel separately: Terraform plan/apply with review

**L5**

- Principles behind the stages:
  → one immutable artifact promoted everywhere — rebuild-per-env means you tested something other than what you shipped
  → config injected per environment, not baked
  → every gate mechanical — a human "looks fine" is not a gate
  → deploy decoupled from release via flags
- Pipeline speed is a first-class property: a 40-min pipeline changes behavior (batching, skipped tests) → itself a reliability risk
- Rollback path is part of the pipeline's definition of done
  → bake-time metrics auto-judging the canary = the difference between CD and "automated hoping"

### 11.2 Pipeline fails after merge / rollback on deploy errors

**L4**

- Red main = team's top priority: revert or fix forward within minutes — main must stay releasable
- Deploy failure: automated rollback on health-check/alarm thresholds
  → redeploy previous image tag, or shift traffic back (blue-green)
  → quarantine the failed artifact; preserve incident evidence before the environment recycles

**L5**

- Three failure planes, three responses:
  → CI failure — bad code → revert/fix-forward, cheap
  → deploy failure — bad rollout → automated rollback, must be rehearsed
  → post-deploy regression — bad behavior → the expensive one; caught only if canary judgment watches SLOs during bake
- Rollback-safety prerequisite: compatibility across one version skew
  → previous version must run against the _current_ database → expand/contract, tolerant consumers
  → teams discover this during their worst incident unless it's a release-checklist rule
- Optimize time-to-restore; revert-first beats debug-first when users are impacted

### 11.3 Containerization vs orchestration

**L4**

- Containerization (Docker): app + dependencies → an image that runs identically anywhere
  → solves "works on my machine", dependency isolation
- Orchestration (K8s/ECS): manages _fleets_:

- One is the unit; the other is the system managing units

**L5**

- Conceptual core: the reconciliation loop
  → declare desired state; controllers continuously converge actual toward it
  → node failure becomes a non-event — same pattern as Terraform for infra
- Tradeoff axis: control vs operational load
  → full K8s: extensibility (operators, CRDs), portability — at real platform-team cost
  → ECS/Fargate: "just run my containers" — less ecosystem breadth
  → deciding variable: platform engineering capacity + needs beyond stateless services
- Anti-pattern: K8s for three microservices — orchestration overhead must amortize over a fleet

### 11.4 K8s: scaling / pod down debugging / verifying deployment success

**L4**

- Scaling: HPA on CPU/mem/custom metrics between min/max · `kubectl scale` manual · Cluster Autoscaler adds nodes
- Pod down:

  → `kubectl logs --previous` — pre-crash logs

**L5**

  ◆ JVM: set `-XX:MaxRAMPercentage` or the JVM ignores the cgroup and gets killed
- HPA nuance: CPU-scaling an I/O-bound service does nothing → scale on RPS/queue depth/custom
- Scale-down needs PodDisruptionBudgets + graceful termination (preStop, SIGTERM) — or you shed live requests
- Verification maturity: rollout success = SLO metrics during a bake window, judged automatically — same canary principle as everywhere

### 11.5 Terraform multi-env (5 EC2 dev, 10 prod) / per-env Spring config

**L5**

## 12. AI / GenAI / LLM Evaluation

### 12.1 How do you evaluate LLM / RAG responses (asked 3× in one loop)

**L4**

- Split the system before evaluating it:
  → **retrieval**: did the right chunks come back — recall@k, precision@k, MRR vs a labeled query→doc set
  → **generation**: faithful to retrieved context + correct — faithfulness/groundedness, answer relevance, correctness vs gold answers
- Build a versioned eval set of real queries + expected outcomes
  → deterministic checks (exact/contains/schema) + LLM-as-judge for open-ended quality
  → run on every prompt/model/index change — like a test suite
- Stack: Ragas (RAG metrics) · promptfoo/DeepEval (harness) · Langfuse (tracing, prod traces → eval sets)

**L5**

- Three disciplines that separate real eval from vibes:
  → LLM-as-judge must be validated against human labels (agreement / Cohen's kappa) before its scores mean anything
  ◆ 🗣 "an unvalidated judge is a random number generator with confidence"
  → know the noise floor — on 50 examples, a few points of delta is statistically nothing; size the set for the effect you need to detect
  → model eval ≠ system eval — end-to-end deltas can come from retrieval, prompt, chunking, or model; only component metrics attribute cause
- Close the loop with production: sample real traffic → label failures → feed back into the eval set
  → the set tracks the actual distribution, not launch-day assumptions

### 12.2 Accuracy dropped 81% → 59% — what's the problem? How do you get the score / framework / library / service?

**L4**

- Diagnose by decomposition + diff. First: what changed?
  → model version · prompt · retrieval index/re-embedding · chunking · data source · the eval set itself (changed set = incomparable scores)
- Split the failure:
  → retrieval metrics dropped (recall@k) → index/embeddings/ingestion — common: re-index with a different embedding model, broken doc pipeline
  → retrieval held → generation — prompt regression, model drift, context truncation
- Scores: fixed labeled eval set through a harness
  → Ragas/DeepEval metrics · promptfoo or CI job as runner · Langfuse (or Bedrock Evaluations) for traces + datasets

**L5**

- A 22-point cliff is a step change from a deploy, not gradual drift — highest-prior causes:
  → silent model-version update — pin versions; "latest" aliases are a production hazard
  → embedding-model mismatch between index-time and query-time
  ◆ vectors from different models are mutually meaningless — retrieval quietly returns noise
  → upstream data-pipeline break — empty/truncated chunks
- Senior process:
  → bisect with component evals
  → reproduce on ~10 failing examples and _read them_ — failure taxonomy beats aggregate metrics for diagnosis
  → check eval-set integrity before trusting the number at all
- Prevention: version-pin everything (model, prompt, embedder, index build) · eval-gate every change in CI · online proxy metrics so the cliff is caught before a human notices

### 12.3 What is reranking / when / how do we know it's better

**L4**

- Second-stage scorer:
  → stage 1 (BM25 / vector ANN) returns top-k cheaply
  → cross-encoder reranker scores each candidate _jointly with the query_ → reorders → keep best few for context
- When: after retrieval, before prompt assembly
- Better? A/B on retrieval metrics — NDCG/MRR/precision@k on the labeled set — plus downstream answer quality, minus the latency cost

**L5**

- Mechanism explains the tradeoff:
  → bi-encoders embed query and doc _independently_ — cacheable vectors, fast ANN, no query-doc interaction
  → cross-encoders attend across the pair — much better relevance, O(k) inferences per query, uncacheable
  → 🗣 "cheap recall wide, expensive precision narrow"
- Reranking pays when recall@50 is high but precision@5 is weak
  → it cannot recover documents stage 1 never returned — recall problems are fixed in retrieval (hybrid search, better embeddings), not ranking
- Judge end-to-end: better NDCG that doesn't move faithfulness isn't worth 80ms of p95 — include the latency budget in the eval

### 12.4 How did you use Claude/Copilot / good prompts / modes / when AI is wrong

**L4**

- Claude Code as an autonomous coding agent (plan → execute → verify against a spec file); Copilot for inline completion
- Modes: chat/ask (explain, design) · edit (scoped changes) · agent (multi-step + tool use — runs tests, fixes its own failures)
- Good prompt: role + task + constraints + context (code/schema) + output format + examples
  → for code: acceptance criteria the output must satisfy
- Reliable: well-represented patterns with verifiable outputs (boilerplate, tests, refactors)
- Unreliable: niche APIs, version-specific details, anything it can't verify — hallucinated methods, confidently wrong edge cases

**L5**

- Operating principle: output quality is bounded by _verifiability_
  → correctness checked mechanically — tests as oracles, compilers, linters, grep gates
  → never the model's self-review: a model reviewing itself shares the priors that produced the error
- Spec files (CLAUDE.md/AGENTS.md) as persistent source of truth beat re-prompting; plan-then-execute catches scope errors before they become code
- Wrong-results taxonomy → different mitigation each:
  → cutoff staleness → retrieval/docs
  → plausible-API hallucination → verification gates
  → context truncation losing constraints → context curation
  → instruction conflict → tighter specs

### 12.5 Guiding a team on AI / rules for Java-Angular projects / saving tokens

**L4**

- Team rules:
  → AI-generated code passes the same review + CI gates — no green-light lane
  → repo-level spec file encodes conventions (architecture, naming, test requirements, forbidden patterns)
  → explicit policy for sensitive code/data
  → match tool strengths to tasks: tests, migrations, boilerplate first; novel design last

**L5**

- The deeper play is process design:

## 13. Angular & Frontend

### 13.1 Signal vs Observable / zone

**L4**

- **Signal**: synchronous reactive value container
  → `signal(0)` — read by calling; `set`/`update`; `computed()` derives; `effect()` for side effects
  → framework tracks dependencies → re-renders precisely what changed
- **Observable** (RxJS): lazy _stream_ of values over time
  → rich operators (map, switchMap, debounce), explicit subscribe/teardown
- Split: signals for UI state; observables for events + async streams (HTTP, websockets, input over time)
  → bridge: `toSignal()` / `toObservable()`
- **Zone.js**: monkey-patches async APIs so Angular knows when to run change detection
  → signals enable fine-grained, zoneless change detection

**L5**

- Mechanism contrast:
  → signals: dependency graph, pull-based, glitch-free synchronous propagation — no subscription management, no leak class
  → observables: push-based, time-aware — backpressure, cancellation, combination semantics signals don't have
  → 🗣 "signals replace _state_ uses of RxJS, not _event-stream_ uses"
- Why Angular introduced them:
  → zone-based CD re-checks the whole component tree per async event — O(app) per tick
  → signal reactivity makes invalidation O(actually-changed) → path to zoneless — the performance headline
- Migration guidance: new state as signals · streams stay RxJS · convert at the boundary with `toSignal`

### 13.2 State management / NgRx and its functions

**L4**

- Ladder by scale:
  → component state (signals) → shared service-with-signals → NgRx for large apps (one store, devtools, enforced unidirectional flow)
- NgRx pieces:
  → **Store** — single immutable state tree
  → **Actions** — events describing what happened
  → **Reducers** — pure functions computing next state
  → **Selectors** — memoized queries
  → **Effects** — side effects (API calls) listening to actions, dispatching results
- Modern **SignalStore** = same discipline, lighter

**L5**

- What NgRx actually buys:
  → serializable action log — auditability, devtools replay
  → enforced purity — predictable transitions, trivially testable reducers
  → memoized selector graphs — render efficiency
- Cost: real ceremony per feature → honest recommendation: signals/SignalStore default; full NgRx when multiple teams share complex interdependent state
- Failure prevented: state scattered across stateful services mutated from everywhere
  → "who changed this and when" unanswerable
  → 🗣 "choose the _discipline_ always, the _framework_ by team size"

### 13.3 RxJS operators/observers / lifecycle hooks / ngOnInit vs constructor

**L4**

- Observer = the consumer: `{next, error, complete}` passed to `subscribe`
- Operators = pipeable transforms: `map`, `filter`, `debounceTime`, `distinctUntilChanged`, `switchMap`, `catchError`
- Canonical example — typeahead:
  → `valueChanges.pipe(debounceTime(300), distinctUntilChanged(), switchMap(q => api.search(q)))`
- Lifecycle:
  → constructor: DI only — inputs not set yet
  → `ngOnInit`: after inputs bound — initialization goes here
  → `ngOnChanges` on input changes · `ngOnDestroy` teardown (unsubscribe)

**L5**

- Flattening-operator choice is the depth marker:
  → `switchMap` — cancel previous → search, last-write-wins
  → `concatMap` — preserve order → sequential writes
  → `mergeMap` — max concurrency → can reorder responses (the subtle bug)
  → `exhaustMap` — ignore while busy → submit buttons, double-click protection
- Subscription leaks = the canonical Angular bug class
  → structural fixes: `async` pipe · `takeUntilDestroyed` · signals — never manual bookkeeping
- Senior note: `inject()` + signal inputs are shifting init patterns — tracking that shift is the signal

### 13.4 Angular performance / 12→16 migration / micro-frontends + module federation

**L4**

### 14.1 Redis: decrement inventory only if stock remains (no oversell under concurrency)

**L4**

- Core: check + decrement must be atomic — GET-then-DECR races and oversells
- Lua script executes atomically on the server:

```lua
-- KEYS[1]=stock key, ARGV[1]=qty
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock >= tonumber(ARGV[1]) then
  return redis.call('DECRBY', KEYS[1], ARGV[1])
end
return -1  -- insufficient
```

- Call with `EVALSHA`; -1 → reject the order

**L5**

- Alternatives and why Lua wins:
  → `DECRBY` + compensating `INCRBY` on negative — works, but exposes a transient negative value
  → `WATCH/MULTI` optimistic TX — works, retries under contention
  → Lua = clean critical section because Redis executes scripts single-threaded
- Durability caveat: Redis is not a ledger
  → pair the fast-path reservation with an authoritative DB record (reservation row / conditional update) + reconcile
- Idempotency: store `order:{id}` with SETNX _inside the same script_ → client retries don't double-decrement

### 14.2 Kafka consumer → DB, safely reprocessable after crash (fraud events)

**L4**

- Manual commit AFTER a DB transaction that atomically writes:
  → the business effect
  → a `processed_events(event_id UNIQUE)` row
- Replay → unique constraint fires → skip → commit offset

```java
@KafkaListener(topics = "fraud-events")
public void onEvent(ConsumerRecord<String, FraudEvent> rec, Acknowledgment ack) {
    try {
        service.processIdempotently(rec.value()); // one TX: processed_events insert + business write
    } catch (DuplicateKeyException dup) { /* already processed — fall through */ }
    ack.acknowledge();
}
```

**L5**

- State the invariant aloud:
  → 🗣 "an offset commit is a lie unless the effect is durable first — effect-transaction, then ack"
- Sizing:
  → prune the dedupe table by event-time watermark
  → batch consumption: whole batch in one TX for throughput ↔ wider redelivery set on crash (all idempotent → safe)
- If the sink were Kafka instead of a DB → transactions/EOS apply there
  → knowing where that guarantee's boundary ends is the differentiator

### 14.3 Lambda: dedupe events / SQS→DynamoDB idempotent / S3→process→DynamoDB (Python)

**L4**

```python
import json, boto3
table = boto3.resource("dynamodb").Table("orders")

def handler(event, context):
    failures = []
    for r in event["Records"]:
        body = json.loads(r["body"])
        try:
            table.put_item(
                Item={"order_id": body["orderId"], "amount": str(body["amount"]), "status": "PROCESSED"},
                ConditionExpression="attribute_not_exists(order_id)")
        except table.meta.client.exceptions.ConditionalCheckFailedException:
            pass  # duplicate — already processed, succeed silently
        except Exception:
            failures.append({"itemIdentifier": r["messageId"]})
    return {"batchItemFailures": failures}
```

- The conditional write **is** the dedupe — no separate seen-set
- Partial-batch response retries only the failed records

**L5**

- Enable `ReportBatchItemFailures` on the event source mapping
  → else the whole batch retries, re-delivering successes — harmless only because we're idempotent, but wasteful
- S3-triggered variant: S3 can fire duplicate notifications → object key/version-id is the idempotency key
- Warm reuse: initialize clients outside the handler
- Audit-write variants: audit item + state change in one `TransactWriteItems` if both must hold

### 14.5 Reverse words without split

**L4**

- Two-pointer scan from the end, extract words manually:

```java
public String reverseWords(String s) {
    StringBuilder sb = new StringBuilder();
    int i = s.length() - 1;
    while (i >= 0) {
        while (i >= 0 && s.charAt(i) == ' ') i--;   // skip spaces
        if (i < 0) break;
        int end = i;
        while (i >= 0 && s.charAt(i) != ' ') i--;   // walk the word
        if (sb.length() > 0) sb.append(' ');
        sb.append(s, i + 1, end + 1);
    }
    return sb.toString();
}
```

- Handles leading/trailing/multiple spaces · O(n) time, O(n) output

**L5**

- Follow-ups to volunteer:
  → in-place char-array variant: reverse the whole array, then reverse each word — the "no extra space" version
  → invariant: `i` always sits just before the current word
- Fluency detail: `StringBuilder.append(CharSequence, start, end)` avoids substring allocations

### 14.8 Design a Cart REST API (whiteboard) / procedure for a new REST API

**L4**

- Resources + verbs:
  → `POST /carts` — create (201 + Location)
  → `GET /carts/{id}`
  → `POST /carts/{id}/items` — add item (productId, qty)
  → `PATCH /carts/{id}/items/{itemId}` — change qty
  → `DELETE /carts/{id}/items/{itemId}`
  → `POST /carts/{id}/checkout`
- Status codes: 400 validation · 404 unknown · 409 conflict (stock/state) · 401/403 auth
- Procedure: clarify requirements + consumers → model resources + state transitions → contract-first (OpenAPI) reviewed with consumers → implement with validation, idempotency, pagination, versioning decided up front

**L5**

- Senior touches:
  → idempotency keys on `checkout` and item-add — retries must not double-charge/double-add
  → optimistic concurrency: `ETag` / `If-Match` on cart mutation — two tabs editing one cart
  → cart = the aggregate boundary; checkout transitions state and locks mutation — a state machine, not CRUD
  → TTL/expiry semantics for abandoned carts
- Process answer they're fishing for: contract-first + consumer review
  → 🗣 "the API is a product with users, not an implementation detail"
