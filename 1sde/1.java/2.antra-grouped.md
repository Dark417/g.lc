<a id="vanguard-1"></a>

### Answers

#### Self intro (60–75 seconds, memorized cold open)

> "I'm a backend engineer, four years at JPMorgan Chase in Dallas, on a capital-markets instrument platform. Three layers of it were mine: an AWS ingestion pipeline that takes vendor offering feeds — PySpark on Glue, ~40,000 records a day, 200+ attributes — normalizes them into a canonical model in Aurora Postgres and publishes enriched events over SNS; a set of Spring Boot services on ECS exposing that data through GraphQL and REST so bankers can preview, correct, and consume records, with a MongoDB-backed document service behind it; and the operational side — I built the test-data injection tooling, took production support rotations, and did the tracing and root-cause work in Datadog and CloudWatch. More recently I led an agent-based reconciliation system on Google ADK and Bedrock that compares vendor emails against persisted records. What I'm looking for is more of the platform and data-infrastructure side of that work."

Then stop. Do not narrate your resume top to bottom; the intro's job is to hand them three threads to pull.

#### Biggest technical challenge (STAR, use the DB performance story)

Situation: `[FILL: which query/endpoint, what latency, what user impact]`. Task: fix without a risky schema change under load. Action — the four-beat structure: **diagnose** (`EXPLAIN ANALYZE` showed a sequential scan the existing single-column index couldn't serve), **mitigate** (`CREATE INDEX CONCURRENTLY` in production — no table lock, reversible, minutes not days), **fix durably** (composite key redesign through the normal release train, validated with a dark-read comparison — new path computed and diffed against the old, not served), **ratchet** (query-plan/query-count assertion added to CI so a regression fails the build instead of paging on-call). Result: `[FILL: p99 before → after]`.
🗣 "Mitigate fast and reversibly, fix slowly and safely, then make the fix impossible to undo silently."

#### Conflict story

Structure: disagreement was **technical and specific**, not personal; you sought the deciding data; you disagreed-and-committed when the call went the other way. Good candidate: `[FILL — e.g. multi-agent vs. deterministic pipeline for the reconciliation system]`. The honest, high-signal version of that one: four of the five steps were deterministic and only the email extraction genuinely needed a model; you argued the simpler design, and whichever way it landed, you can articulate the tradeoff now. Never a story where you were simply right and they were simply wrong.

#### Cross-team coordination (they asked this twice — have two versions)

Frame around **interface and sequencing**, not meetings: agree the contract first (schema, event shape, error semantics), agree who deploys in what order, write it down where both teams can see it, then run a joint dry run in a lower environment. Concrete anchor: `[FILL — vendor feed contract with the upstream team, or SNS event contract with downstream consumers]`. Close with the guardrail: contract tests in CI so the agreement is verified continuously, not remembered.

#### Mentoring / helping a teammate

Small and specific beats grand: pairing a newer engineer through their first production support rotation, or writing the runbook for `[FILL]` after answering the same question three times. Signal you want: you fixed the _system_ (docs, tooling, gate), not just the instance.

#### Joining a new team / adjusting

Talk about learning the team's release cadence and review norms before proposing changes, and one thing you deliberately did _their_ way despite preferring another. Interviewers are screening for someone who won't arrive and start rewriting.

#### Proud/fun build

The Lambda test-data injector: 30+ record types injectable on demand, cut debugging cycles by ~80% `[FILL: baseline — 80% of what?]`. Why it's a good story: unglamorous, multiplied everyone's velocity, and you can explain the design (idempotent injection, cleanup, environment isolation).

#### Influenced the team with a new technique

Best fit: mechanical verification — grep gates, coverage floors, Liquibase drift tests, query-count assertions in CI — as a substitute for reviewer vigilance. The one-liner: _"Reviewers get tired; gates don't."_ Or the AI-assisted workflow (Copilot/Claude Code with spec files and mechanical gates) if they lean that direction.

#### Your top best-practice opinion (prepare this — it's a signature question)

> "External verification over self-review. Any quality property I care about should be enforced by something mechanical — a test that asserts query counts, a schema diff that fails the build, a coverage floor, a drift test between the Liquibase changelog and the code's schema definitions. Code review catches design problems; it does not reliably catch regressions, because reviewers are inconsistent and I'm the most inconsistent reviewer of my own code."

## 3. Production Support & Operations

### Questions

- How do you handle production support in your recent project **[x2]**
- Have you been on call? Describe the on-call flow
- A DB production performance issue story: what was the problem, how did you balance fix speed vs. safe release, why composite key, how did you prevent recurrence
- App performance degraded / workflow slow — where do you start troubleshooting and collecting latency data

<a id="vanguard-3"></a>

### Answers

#### How do you handle production support (asked twice)

Flow: alert fires (Datadog monitor or CloudWatch alarm) → triage severity and blast radius → **mitigate before diagnosing** (roll back, feature-flag off, scale, or re-drive from DLQ) → trace across services by correlation id → root cause → remediation ticket with priority → postmortem/writeup if customer-impacting → guardrail so the same alert can't recur silently. Name your rotation shape: `[FILL: weekly rotation, N engineers, business hours vs 24/7]`.

#### On-call specifics they'll probe

- What paged you most often, and what you did about it structurally `[FILL]`.
- Runbook existence and quality.
- How you decide rollback vs. fix-forward: **rollback unless the bad state is already persisted** — if data is written, rolling back code doesn't undo it, so fix-forward plus a repair job.

#### Slow workflow — where do you start

"Is it latency or queueing?" APM first: p50/p95/p99 for the endpoint, then one slow trace's waterfall — time in app, DB, or downstream. Flat DB time with rising p99 means pool saturation (Tomcat threads, Hikari connections), not slow queries — different fix entirely (capacity/limits). Then `EXPLAIN ANALYZE`, then GC/heap if the JVM is suspect. Always re-measure the same percentile after the fix; averages lie on bimodal endpoints.

## 4. Monitoring & Observability

### Questions

- What monitoring tools (JVM, API performance, alerting, logs, APM)
- What metrics + alerts do you have
- What do you save in logs — fields, correlation ID, trace ID, span ID, others

<a id="vanguard-4"></a>

### Answers

**Layers, and what you watch at each:**

| Layer          | Tool                     | Key signals                                                                                |
| -------------- | ------------------------ | ------------------------------------------------------------------------------------------ |
| Infrastructure | CloudWatch               | ECS task count/restarts, CPU/mem, ALB 5xx, target health                                   |
| APM / traces   | Datadog APM              | p50/p95/p99 per endpoint & operation, error rate, trace waterfall, service map             |
| JVM            | Datadog JVM metrics      | heap after GC, GC pause time & frequency, thread count, Hikari pool active/idle/pending    |
| Logs           | Splunk / CloudWatch Logs | structured JSON, correlation id, error codes                                               |
| Business       | custom metrics           | records ingested per run, validation failures, corrections submitted, SNS publish failures |

**Alerts — the rule:** alert on symptoms users feel (error rate, p99 latency, queue age, DLQ depth), not on causes (CPU). Every alert needs a runbook link and an owner or it becomes noise.

**What's in a log line:** timestamp, level, service, environment, **correlation id** (per client request, propagated across services), **trace id / span id** (from the APM tracer — trace = whole request, span = one unit of work inside it), logger, message, and structured business context (instrumentId, ingestRunId, actor). Never: tokens, PII, full request bodies on sensitive endpoints. Log 4xx at INFO, 5xx at ERROR — otherwise the ERROR stream is 95% user typos and everyone ignores it.

🗣 "Correlation id ties one user action across services; trace/span ids tie one request's timing tree together. You want both — one for support, one for performance."

## 5. Java & Spring

### Questions

- Java 21 new features
- What is a virtual thread, how does it help us
- Inheritance vs. composition
- Design patterns familiarity (+ resume-anchored: where did you use builder?)
- Code review scenario: singleton component with an **un-synchronized ArrayList** field that requests add to/remove from — what concern do you write in the review?
- Spring MVC: what does DispatcherServlet do
- Where did you use multithreading

<a id="vanguard-5"></a>

### Answers

- Concurrency depth: [Java reference §7](1java0.md#java-concurrency) — memory model, locks, executors, futures, virtual threads, Spring context boundaries, and L4/L5 answers.

- Quick answers follow; the concurrency reference above contains the threading deep dive.

**Java 21 features.** Virtual threads (JEP 444), pattern matching for switch, record patterns, sequenced collections, structured concurrency (preview). Say which you've actually used; "I've read about virtual threads and here's what they change" is a fine, honest answer.

**Virtual threads — how they help.** Lightweight threads scheduled by the JVM onto a small pool of carrier threads; a blocking call parks the virtual thread and frees the carrier instead of blocking an OS thread. So thread-per-request becomes cheap for I/O-bound work and you stop tuning pool sizes. **Defeater to volunteer:** they don't create database connections — if your bottleneck is a 20-connection Hikari pool, virtual threads just move the queue from the thread pool to the connection pool. They help I/O-bound concurrency, not throughput limited by a downstream resource.

**Inheritance vs composition.** Inheritance = "is-a", couples subclass to superclass internals, one parent, breaks encapsulation (fragile base class). Composition = "has-a", swappable at runtime, testable via injection. Default to composition; use inheritance for genuine subtype polymorphism within your own controlled hierarchy. Spring is a composition machine — that's what DI _is_.

**DispatcherServlet.** The front controller: single servlet receiving all requests, then delegating — `HandlerMapping` resolves the handler, `HandlerAdapter` invokes it, argument resolvers bind path variables/body/params, the return value goes through `HttpMessageConverter` (Jackson) or a `ViewResolver`, and `HandlerExceptionResolver` handles thrown exceptions (this is where `@RestControllerAdvice` plugs in). Interceptors run before/after the handler.

**Code review: singleton with an unsynchronized ArrayList.** This is the one they want you to nail:

> "Spring singletons are shared across all request threads, so that field is shared mutable state with no synchronization. Three problems: `ArrayList` isn't thread-safe, so concurrent add/remove can corrupt the internal array or size counter and produce lost elements, `ArrayIndexOutOfBoundsException`, or an infinite loop on resize; iteration while another thread mutates throws `ConcurrentModificationException`; and even without corruption there's no happens-before edge, so one thread may never see another's writes. But the bigger question is _why_ there's mutable per-request state on a singleton at all — if it's accumulating request data, that's a memory leak and a cross-request data-leak risk. My comment: move the state into the request scope, or if it's genuinely shared, use a concurrent collection with a bounded size and explain the eviction policy."

**Design patterns / where did you use builder.** Have concrete answers: builder for `[FILL: request/DTO construction, e.g. the canonical instrument object with 200+ attributes]`, strategy for `[FILL: per-vendor normalization]`, template method or chain for `[FILL: validation pipeline]`. Vague "yes I know patterns" answers score zero.

## 8. AWS

### Questions

- Where did you use AWS **[x2]**; how many years
- Where did you use Lambda; if you implement a brand-new Lambda service, how would you configure it
- (From checklist: AWS is a top-3 expected area)

<a id="vanguard-6"></a>

### Answers

**Where and how long.** Four years, daily. ECS (Fargate services + task definitions), Lambda, Glue/PySpark, Aurora Postgres, DynamoDB, S3, SNS/SQS, OpenSearch, CloudWatch, Terraform for all of it, ECR, plus Bedrock on the AI work.

**"If you built a brand-new Lambda, how would you configure it?"** They want to hear that you know the operational surface:

- **Trigger & concurrency**: event source (SQS/SNS/API GW/EventBridge), batch size, and **reserved concurrency** — not just to guarantee capacity but to _cap_ it, because an unbounded Lambda will happily exhaust your RDS connections.
- **Memory/timeout**: memory also buys CPU, so raising memory can lower cost by lowering duration; timeout set below the caller's own budget.
- **Networking**: in-VPC only if it needs private resources (Aurora), with the ENI/cold-start cost that implies; otherwise keep it out of the VPC.
- **IAM**: one role per function, least privilege, no wildcard resources.
- **Config & secrets**: environment variables for config, Secrets Manager/Parameter Store for secrets, never baked into the image.
- **Failure handling**: retries (SQS visibility timeout vs. async invoke retries differ), a DLQ or on-failure destination, and **idempotency** because retries are guaranteed, not hypothetical.
- **Observability**: structured JSON logs, CloudWatch metrics/alarms on errors/throttles/duration p99, X-Ray or Datadog tracing.
- **Deploy**: Terraform + versioned artifact, alias-based deploys.
- **Cold start**: measure before optimizing; provisioned concurrency only if a latency SLO demands it.

## 9. Messaging / Kafka

### Questions

- Where did you use Kafka and how
- What Kafka connector did you use
- Message queue story (from design-doc checklist)

<a id="vanguard-7"></a>

### Answers

Answer honestly at your depth. If Kafka was peripheral, say so and pivot to SNS/SQS where you have real depth — a confident "here's exactly what I did with it" beats a vague survey.

**Fundamentals to have cold:**

- Topic → partitions → ordered, append-only log; offset per partition. **Ordering is guaranteed within a partition only** — across partitions there is none. Partition key determines placement, so ordering per instrument means keying by instrument id.
- Consumer groups: one partition to one consumer within a group; adding consumers past the partition count adds nothing. Rebalance on membership change pauses consumption.
- Delivery: at-least-once by default (commit offset after processing). At-most-once = commit first. Exactly-once needs idempotent producer + transactions, and only within Kafka.
- Producer: `acks=all` + `min.insync.replicas` for durability; `enable.idempotence=true` or `max.in.flight.requests.per.connection > 1` can reorder on retry.
- Kafka Connect: source/sink connectors for moving data without custom code — say which you used or say you didn't.
- **vs SNS/SQS**: Kafka is a retained, replayable log (consumers own their offset, can rewind); SQS is a queue where consumed messages are deleted. Choose Kafka for replay, event sourcing, multiple independent consumers over history; SNS/SQS for simple fan-out and decoupling with managed ops.

## 10. Data / ETL / Databases

### Questions

- Explain the ETL pipeline: flow, your role, ownership, design, transform & validation steps, challenges, redesign question
- Comfortable with both Cassandra and Postgres?
- Composite key decision (from DB perf story)
- ETL / ML pipeline + training + inference serving story

<a id="vanguard-8"></a>

### Answers

**Pipeline walkthrough.** Vendor API/file → Glue PySpark job → schema validation against the contract → normalization into canonical domain objects → upsert into Aurora on the natural key → publish enriched event to SNS. Orchestration/scheduling: `[FILL]`. Your role: `[FILL — be precise about co-built vs. owned]`.

**Transform & validation steps.** Type coercion, unit/format normalization across vendors, reference-data lookups, required-field checks, cross-field consistency, dedupe on the natural key.

**⚠️ The open question that has appeared in every review — resolve it now:** what happens to records that fail validation? Pick the truth and say it in one sentence: quarantined to a separate S3 prefix/table with the rejection reason and re-driven after a fix / sent to a DLQ / dropped with a metric / the whole batch fails. If it was "dropped with a count logged," say that — and say what you'd do differently. An honest weak answer beats an invented strong one.

**Challenges.** Vendor schema drift, late-arriving data, small files, skew on `[FILL]`, idempotent reprocessing.

**"If you redesigned it?"** Strong answer shape: schema contracts enforced at the boundary with an explicit quarantine path and a re-drive tool; idempotency by construction so any batch can be safely replayed; observability on data quality (validation failure rate as a first-class metric, not a log line); and a decision on incremental vs. full-refresh driven by the vendor's change-feed support. Optionally: whether the medallion/lakehouse layering would have suited it better — but only if you're ready to defend that at depth.

**Cassandra vs Postgres.** Postgres: relational, ACID, joins, strong secondary indexes, single-primary — choose for correctness-critical transactional data (our canonical records). Cassandra: wide-column, no joins, tunable consistency, partition-key-driven, linear write scaling across a ring — choose for high-volume time-series/event writes with known access patterns. The deciding variable is whether you need cross-entity transactions and ad-hoc query flexibility (Postgres) or write throughput and multi-region availability with query patterns fixed at design time (Cassandra). Be honest about hands-on depth with Cassandra.

### Answers

You're a backend candidate; they know. Aim for correct-and-bounded, not deep.

**Angular change detection.** Angular builds a tree of components; after any potentially-state-changing event (DOM event, HTTP response, timer — patched by Zone.js), it runs change detection top-down through the tree, comparing bound expressions to their previous values and updating the DOM where they differ. `ChangeDetectionStrategy.OnPush` restricts a component to re-checking only when its `@Input` references change, an event fires inside it, or an observable it subscribes to via `async` emits — that's the main performance lever. (Newer Angular offers signals as a finer-grained alternative; know the name.) **Contrast with React**: React re-renders a virtual DOM subtree and diffs it; Angular checks bindings directly against the component tree. Same goal, different mechanism.

**Lazy loading.** Route-level: a feature module/route is compiled into a separate JavaScript bundle, and that bundle is only fetched when the user first navigates to the route — so the initial bundle is smaller and first paint is faster. **Where does the effect happen?** Not at deploy, not at server render — **in the browser at runtime**: the build (deploy time) _splits_ the bundles; the browser _fetches_ the extra chunk on navigation. That two-part answer is exactly what their follow-up is probing. Tradeoff: first navigation to a lazy route pays a network fetch, mitigated by preloading strategies.

**Reactive vs template-driven forms.** Template-driven: form model is implicit, built from directives in the template, async, easier for simple forms. Reactive: the form model is explicit in the component (`FormGroup`/`FormControl`), synchronous, unit-testable without the DOM, composable validators, better for dynamic or complex forms. Default to reactive for anything non-trivial.

**Your frontend story.** React admin portal: Figma designs → permission-management workflows, reusable components in a monorepo, integrated with GraphQL/REST. `[FILL: what was hard — permission rule modeling? state management?]`

## 15. Coding / OOD

### Questions

- **Elevator system** (given skeleton: `ElevatorSystem.assign(ElevatorCommand)` with one rider, and `Elevator.step()` logic). Direction enum, destinations list, event loop provided.

<a id="vanguard-13"></a>

### Answers

They gave you the skeleton, so they'll grade design sense, not algorithms. Structure your answer as: clarify → state the scoring rule → code → name what you'd add.

**Clarify first (say these out loud):** one rider at a time as stated; is `fromFloor` a hall call with a direction, or is `toFloor` known at assignment? Capacity/weight — in scope? Ties broken how?

**Assignment: score every elevator, pick the minimum.** The scoring rule _is_ the interview.

```java
public Elevator assign(ElevatorCommand cmd) {
    return elevators.stream()
        .min(Comparator.comparingInt(e -> cost(e, cmd)))
        .orElseThrow();
}

/** Lower is better. Idle: pure distance. Moving toward the call in the same
 *  direction: distance (it can pick up en route). Otherwise: it must finish
 *  its run and come back — penalize by the detour. */
private int cost(Elevator e, ElevatorCommand cmd) {
    int here = e.getCurrentFloor(), from = cmd.getFromFloor();
    Direction callDir = from < cmd.getToFloor() ? Direction.UP : Direction.DOWN;
    return switch (e.getDirection()) {
        case IDLE -> Math.abs(here - from);
        case UP -> (here <= from && callDir == Direction.UP)
                ? from - here
                : (e.furthestDestination() - here) + (e.furthestDestination() - from);
        case DOWN -> (here >= from && callDir == Direction.DOWN)
                ? here - from
                : (here - e.lowestDestination()) + (from - e.lowestDestination());
    };
}
```

**`step()` — one tick of simulated time:**

```java
public void step() {
    if (destinations.isEmpty()) { direction = Direction.IDLE; return; }
    if (destinations.contains(currentFloor)) {   // arrive: open, unload/load
        destinations.remove(Integer.valueOf(currentFloor));
        if (destinations.isEmpty()) { direction = Direction.IDLE; return; }
    }
    int target = nextTargetInCurrentDirection();  // SCAN: keep going, then reverse
    direction = target > currentFloor ? Direction.UP
              : target < currentFloor ? Direction.DOWN : Direction.IDLE;
    if (direction == Direction.UP) currentFloor++;
    else if (direction == Direction.DOWN) currentFloor--;
}
```

**Then volunteer what you left out** — this is where the level shows: destinations should be a `TreeSet` (or two heaps) so "next stop in this direction" is O(log n) instead of a scan; the algorithm is the elevator/SCAN disk-scheduling algorithm, which prevents starvation of far-floor requests that pure nearest-first causes; the event loop and `assign` mutate shared elevator state from different threads, so `destinations` needs to be thread-confined to the simulation thread or guarded — _say this even if they don't ask_, it connects directly to their singleton/ArrayList question; capacity/weight becomes a filter before scoring; and real systems batch hall calls and optimize globally rather than greedily per call.

## 16. System Design Scenarios (given verbatim in prior loops)

### Questions

**Scenario 1 — schema change deployed in wrong order.** Daily vendor files → batch ingest → Aurora → replicated to Redshift for ops + analytics. New column added; deploy order wrong; staging/history has mixed old/new files; production impact. Walk through: (a) investigation & root cause, (b) fast service restoration, (c) deployment strategy to prevent recurrence.

**Scenario 2 — 10–100x traffic onboarding.** GraphQL APIs on Aurora Serverless, multiple consumers. New business-critical consumer at ~5,000 sustained RPS, zero downtime tolerance, must not degrade existing consumers. Walk through: (a) evaluate current architecture & bottlenecks, (b) design for the load, (c) test before release, (d) monitoring & deployment.

<a id="vanguard-14"></a>

### Answers

#### Scenario 1 — schema change deployed in the wrong order

**Investigate.** Establish the timeline first: what deployed when (ingest job, Aurora DDL, Redshift replication, downstream consumers) versus when failures started. Then determine which side is inconsistent — are files arriving with the new column while the ingest job doesn't know it, or is the job emitting the new column while Redshift's target table lacks it? Quantify blast radius: which partitions/dates contain mixed-shape data, how many rows, which downstream consumers already read bad data. Check whether historical reprocessing has already propagated the mix.

**Restore service fast.** Mitigate before fixing: stop the bleeding (pause the staging/history job so more mixed data isn't produced), then unblock the consumer side by making the reader tolerant — the additive column defaults to null for old files. Roll back the _deploy_, not the data, unless bad rows are already persisted — in which case identify the affected key range and re-drive from the raw landing zone, which is only safe because ingestion is idempotent on the natural key. Communicate an ETA and a data-correctness statement to downstream consumers early; in a bank, silent recovery is worse than a slow one.

**Prevent it.** The rule: **expand-contract, readers before writers.**

1. Add the column as nullable and deploy every _reader_ that tolerates it first (Redshift target, consumers).
2. Then deploy the _writer_ that starts populating it.
3. Backfill history in a controlled job.
4. Only then make it required / remove the old field.
   Guardrails behind the rule: schema versioning on the file contract itself so the job can branch instead of guessing; a schema-compatibility check in CI (the ingest job's expected schema diffed against the contract) so an incompatible change fails the build; deploy ordering encoded in the pipeline rather than in a runbook step someone can skip; and a canary/dry-run on a sample file before the full run.
   🗣 "Schema changes are a distributed deploy, not a DDL statement — order them like one."

#### Scenario 2 — 5,000 RPS new consumer on GraphQL + Aurora Serverless

Full skeleton in [REST / GraphQL interview depth](../1.backend/2.rest-gql.md) Q74. Compressed:

1. **Evaluate** — baseline current QPS and per-operation cost; enumerate the new consumer's query shapes (persisted queries make the load finite and plannable); Aurora Serverless ACU scaling reacts on the order of tens of seconds, which is wrong for a sustained step change → provisioned + read replicas; connection math (pods × pool size vs `max_connections`) → RDS Proxy.
2. **Design for isolation first, speed second** — the "must not impact existing consumers" clause is structural: dedicated read replicas or a dedicated deployment cell, per-consumer rate limits at the gateway, cache layer for their narrow query set, allowlisted operations.
3. **Test** — load test the named operations at 1.5–2× target on production-shaped data; soak for pool leaks; game-day a replica failover under load.
4. **Deploy & monitor** — percentage ramp gated on SLOs (p99, error rate, replica lag), automatic rollback thresholds, per-consumer dashboards.
   🗣 "Zero downtime tolerance means I protect existing consumers structurally — cells and limits — before I optimize anything."
