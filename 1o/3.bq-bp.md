## 2. Story A — Permission resolution: role → attribute, layered

- One-liner: "I refactored the document broker's authorization from role checks to a layered attribute-based resolver, without breaking any existing caller."
- Values it carries: **Take Pride in Your Work** (primary) · Nail the Basics · Challenge ideas, champion execution · Put Customers First (internal consumers)
- 1P3A groups: R3 (complex project / tech decision / optimization) · R4 (ambiguity) · R8 (collaboration)

### STAR

- S — Document broker service on the Market Monitor platform: search, upload, download of documents for financial entities. Authorization was **role-based**: `[N]` roles, checks scattered as `if role in (...)` across `[N]` endpoints
- T — New requirements couldn't be expressed by role alone: access depended on **document type** and **request attributes** (entity, `[e.g., desk / region / classification]`). Each new rule meant touching every check. I owned the redesign
- A
  → Inventoried every existing check and wrote them down as a rule table first — role × document type × attribute → allow/deny. That table became the spec and the parity test
  → Designed a **layered resolver**: layer 1 role, layer 2 document type, layer 3 request attributes; explicit **deny overrides allow**; unknown → deny
  → Centralized into one resolution component; endpoints call `resolve(principal, resource, action)` instead of inline checks
  → Migration: ran old and new resolvers **side by side in shadow mode** for `[N days]`, logged every divergence, fixed rules until zero diff, then flipped behind a flag `[confirm you did this — if not, say what you actually did: parity test suite?]`
  → Added **audit logging** on every decision: who, what, which rule fired — because a permission system without an audit trail can't be debugged in prod
- R — `[N]` new rules added since without touching endpoint code; audit trail used `[N]` times for access questions; zero authorization regressions at cutover `[confirm]`
- Cost you paid: `[N]` extra weeks vs patching roles again; had to convince `[who]` that a refactor beat another patch

### Follow-ups → answers

- _Why refactor instead of adding one more role?_ → Roles were being invented to encode attributes ("role for desk X readers"); role count was growing per requirement, not per job function. That's the smell: the model was wrong, not incomplete
- _How did you know you didn't break anything?_ → Rule table as spec → parity tests; shadow evaluation; audit log of divergences. Say the mechanism, not "we tested thoroughly"
- _Precedence — what if layers conflict?_ → Deny wins; more specific layer wins over less specific for allows; unknown attribute → deny. Precedence is written down, not implicit
- _Performance?_ → Resolution is in the request path; `[cached principal attributes / rule table in memory]`; `[N ms]` p99 added `[or: not measured, request path was already DB-bound]`
- _What would you do differently?_ → `[pick one honestly: e.g., policy-as-data (rules in a table) from day one instead of code; or start shadow mode earlier]`
- _Isn't this over-engineering for `[N]` roles?_ → The trigger was three requirements in a row that roles couldn't express. Before that, roles were correct. Name the trigger
- _How is this like PKI?_ (they may not ask; you can offer) → Same shape as certificate policy: issuance allowed by (principal, CA, key usage, tenant) — attribute-based, deny-by-default, audited

### Trap

- Don't say "ABAC" as a buzzword first; describe the three layers, then name it
- Don't claim zero bugs unless true

## 3. Story B — Upload timestamp truncation → MongoDB metadata store

- One-liner: "A firm-wide storage API truncated upload time to the minute, so users couldn't see which document was latest; I added our own millisecond metadata store so ordering was correct."
- Values: **Put Customers First** (primary) · Nail the Basics · Act Now, Iterate · Own without ego (fixed a problem outside our service's fault)
- 1P3A groups: R5 (critical bug / customer impact) · R4 (unfamiliar problem / debugging) · R3 (design decision)

### STAR

- S — Document service stored files via the firm-wide document storage platform's API. Users upload documents against an entity; the entity page lists them newest-first
- T — Bug report: `[who — bankers?]` uploaded multiple versions within a minute; the page showed the wrong one as latest. Storage API returned upload time **truncated to the minute** — ties sorted arbitrarily. We didn't own that API
- A
  → Reproduced: two uploads 20 s apart, both timestamps identical → confirmed it's the storage layer, not our sort
  → Options considered:
  ◆ ask the storage team to fix → `[they said N weeks / not on roadmap]`; we can't hold a user-visible bug for that
  ◆ sort by our own upload call order → fragile across instances
  ◆ **own the metadata**: record every upload in our MongoDB with millisecond timestamp + storage document id → chosen
  → Write order: upload to storage first, get the id, then write metadata — so a metadata row never points at a missing file. If metadata write fails → `[retry / orphan cleanup job / log + alert — say what you did]`
  → Backfilled existing documents' metadata from the storage listing `[confirm]`
  → Front end sorts on our timestamp; storage timestamp kept as secondary
- R — Latest-document ordering correct; `[N]` support tickets → 0; metadata store later used for `[search / filtering / audit — confirm]`
- Cost: we now own a second source of truth and its consistency

### Follow-ups → answers

- _Why Mongo, not Postgres?_ → `[real reason: already in the service? document-shaped metadata with variable fields? team familiarity?]` — say the real one; then: "either would work; the decision was owning metadata, not the engine"
- _Two stores — what if they disagree?_ → Write order (file first) prevents dangling metadata; the failure case is a file with no metadata → `[reconciliation job / retry]`. Name the failure and the fix; don't claim it can't happen
- _Idempotency?_ → Upload retried by client → duplicate file? → `[dedupe by content hash / client request id — or admit you'd add it]`
- _Why not push the storage team harder?_ → Did both: filed the fix with them, and unblocked users now. "Customers win every time" — the fix on their side landed `[later / never]`
- _What's the customer impact number?_ → `[N users / N tickets / how often uploads collide]`
- _What would you do differently?_ → `[e.g., own metadata from day one for any external storage; or add the content hash earlier]`

### Trap

- Interviewer may try "so you worked around another team instead of fixing root cause" → answer: root cause was in a platform we don't own; we fixed the _user's_ problem and filed theirs. That's the Put Customers First ordering

## 4. Story C — Lambda mock-data injector for end-to-end testing

- One-liner: "Our pipeline depended on a vendor API to produce test data; I built a Lambda that fires mock records into SNS/SQS on demand, so end-to-end tests became a button, not a wait."
- Values: **Act Now, Iterate** (primary) · Nail the Basics · Innovate together (adopted by team) · Take Pride
- 1P3A groups: R3 (productivity of team / optimization) · R7 (testing culture) · R8

### STAR

- S — Financial-instrument data pipeline: vendor API → `[ingestion service]` → SNS/SQS → Glue/PySpark → Aurora → downstream events. Unit tests per service existed; **end-to-end** testing required real vendor data arriving, which we didn't control in dev/test
- T — Every schema or logic change needed an E2E run; waiting on vendor data made iteration slow and coverage thin. Nobody assigned this; I built it
- A
  → v1 (grungy, `[N days]`): Lambda that takes a record type + attribute overrides and publishes a synthesized message to the same SNS topic the vendor path uses — so every downstream hop is exercised for real
  → Attribute control: templates per record type with overridable fields → can force edge cases (nulls, boundary values, `[N]` attributes) at will
  → v2: `[what you added — e.g., 30+ record types, batch mode, schema kept in sync with the contract so drift fails the injector first, CLI/ API trigger, cleanup of injected records]`
  → Guardrails: dev/test environments only `[how enforced — env check / IAM]`; injected records tagged so they're distinguishable
- R — Debugging time on pipeline changes down `[~80% — confirm basis]`; adopted by `[N]` engineers; became the standard pre-merge E2E check `[confirm]`
- Cost: another thing to maintain; mocks drift from the real vendor payload if not tied to the contract → that's why v2 tied them

### Follow-ups → answers

- _Why Lambda vs a script?_ → On-demand, no host, callable from CI and from a laptop, same IAM as the pipeline. A script on someone's machine dies with them
- _Mocks drift from reality — how do you know your tests mean anything?_ → Templates generated from `[the contract / schema definitions / a captured real sample]`; plus periodic replay of `[N]` real records. Honest: mocks test _our_ logic, not the vendor's; the vendor contract test is separate
- _When is a grungy solution the wrong call?_ → When it's one-way: schema migrations, keys, permissions (ties to Story A). A test tool is reversible — perfect for grungy-first
- _What was wrong with v1?_ → `[hardcoded types / no cleanup / no batch — pick the true one]`
- _How did you get adoption?_ → Demo'd on a real bug reproduction `[which]`; wrote a 1-page README; put it in the PR checklist
