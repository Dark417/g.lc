## 2. Loop structure

```
[Round 1] HackerRank live, 1 hr, 1 engineer
   │  ~10–15 min resume/behavioral  +  ~40–45 min coding
   ▼
[Final] 4 rounds (recruiter) — reports say 4–5
   ├─ Engineer #1: coding / LLD / tech discussion + behavioral slice
   ├─ Engineer #2: same mix (sometimes HLD, sometimes debug/SOLID refactor)
   ├─ Hiring manager: project deep-dive + behavioral (occasionally coding)
   └─ Key interviewer ("bartender"): outside team, OCI values, mediates debrief
   ▼
[Debrief] within 48 hrs → offer
```

- Status 2026-09-09: Round 1 passed; final loop next
  → 4 rounds in ~4 hours: 2 system design, 1 bar raiser (key interviewer), 1 coding
  → Prep focus: system design (`2.sd/`), IC3 baseline with IC4 stretch signals
- Round 1 (your Friday Sept 4, 11am)
  → Expect **compiling, running code** that passes interviewer-provided tests
  → Usually 1 problem; sometimes 2 shorter ones
  → Difficulty: LC Medium, occasionally Hard
  → Short resume walkthrough first — have a 90-second JPMC pitch ready
  → Email recruiter next day (their explicit instruction)
- Engineer rounds
  → Mix of coding (often 2 mediums), LLD/HLD, deep tech discussion
  → Some rounds: given a class, refactor to SOLID / find the bug
  → Behavioral slice at start or end
- Hiring manager round
  → Draw your architecture, defend every decision under "why X not Y"
  → Behavioral on OCI values
- Key interviewer / bartender round
  → From a different team/org, not your hiring team
  → Purely behavioral, or behavioral + curveball puzzle (one report: Josephus, 10-min timer)
  → Goes resume point-by-point; probes job changes, stakeholder conflict, design justification
  → Reported as the toughest round; also mediates your debrief
- Competencies
  → Recruiter sends assigned competencies (OCI values, technical, role) once final is scheduled
  → Ask for them if not received

## 3. Scoring — what earns points

- Three explicit buckets (recruiter)
  → Qualifying questions before coding — quality of your questions
  → The solution — correctness, then complexity
  → Test cases you write and run yourself
- Implicit buckets (candidate reports)
  → Think-aloud; treat interviewer as a senior peer you'd ask for guidance
  → If you don't know, say so + name what resource you'd use
  → Brute force → iterate is acceptable; incomplete "perfect" solution is not
- 🗣 Opening script for every coding problem
  → "Before I code: input size? duplicates? sorted? nulls/empties? expected return on invalid input? memory constraint?"
  → "Approach: X, O(n log n) time, O(n) space. Alternative: Y. I'll start with X."
  → After coding: "Let me add three tests: empty, single element, the edge that breaks naive."

```
difficulty:  ████████░░ Medium   ██░░░░░░░░ Hard   █░░░░░░░░░ Easy
```

- Difficulty
  → Predominantly LC Medium

## 11. Coding signature: design-style + concurrency

- LRU Cache ★★★ — treat as mandatory
  → HashMap + doubly linked list, O(1) get/put
  → Follow-up: thread-safe version
  ◆ Coarse: `synchronized` on get/put — simple, correct, contended
  ◆ Better: `ReentrantReadWriteLock` — reads still mutate recency, so RW lock buys little
  ◆ Java-idiomatic: `LinkedHashMap(cap, 0.75f, true)` + `removeEldestEntry` wrapped in a lock
  ◆ Defeater: "lock-free LRU" is a research topic; say sharded/striped locks instead
- Design Browser History ★
- Music player LLD ★; Logging file system ★; Parking lot / meeting-room style
- Hit counter / rate limiter (sliding window, token bucket) — ties to `2.sd/2.sd.md`
- Factory pattern; refactor-to-SOLID given a class ★
- Concurrency
  → Print odd/even alternately from two threads (wait/notify or `Semaphore`) ★
  → Write and run a deadlock, then fix with lock ordering ★
  → Thread-safe LRU (above)
  → Producer/consumer with `BlockingQueue`

## 13. Live-round protocol (HackerRank)

```
0–2 min  restate + clarify    →  2–5 min approach + complexity
5–25 min code (talk)          →  25–35 min run tests + fix
35–40 min edge cases + optimize discussion
```

- Clarify (score bucket #1)
  → Input size / value range → drives O(n²) vs O(n log n)
  → Sorted? duplicates? negatives? nulls/empties?
  → Return type on invalid input — throw vs sentinel
  → Can I use library sort / collections?
- Approach
  → State brute force + its complexity in one sentence
  → State target approach + complexity; pick and go
- Code
  → Compiling Java; real names; helper methods
  → Narrate at decision points, not every line
- Tests (score bucket #3)
  → Run the provided tests first
  → Add: empty, single, all-same, max size, the naive-breaker
  → Say "this test guards the off-by-one on the right boundary"
- Stuck
  → Say what you'd search / who you'd ask; ask interviewer a directed question
  → Recruiter: they _want_ to guide — following guidance is scored positively
- Setup before Round 1
  → HackerRank account, Java 17 template with `Scanner`/`BufferedReader` boilerplate memorized
  → Practice 5 problems inside HackerRank's editor — different keybindings than LC

## 15. PKI domain learning priorities

- Use 2–3 focused weeks as a planning estimate for an initial domain ramp; demonstrate understanding and debugging ability rather than claiming production PKI expertise.

- **Tier 1 — must know cold before any technical round**
- **Asymmetric vs symmetric crypto**; what a key pair is; why you sign with a private key and verify with a public one. Digital signature vs encryption vs MAC — three different things, commonly conflated.
- **X.509 certificate anatomy**: subject, issuer, validity window, public key, extensions (SAN, key usage, extended key usage, basic constraints), signature. Why SAN replaced CN for hostname validation.
- **Chain of trust**: leaf → intermediate(s) → root. Why CA designs commonly protect roots offline and use intermediates for routine signing; deployment policies vary. Path building and path validation — and why path *building* is harder than it sounds (multiple valid chains, cross-signing).
- **Certificate lifecycle**: key generation → CSR → issuance → distribution/installation → renewal → **rotation** → revocation → expiry. The operational reality: expiry is a preventable outage mode; automate renewal and monitor time-to-expiry.
- **Revocation**: CRL vs OCSP vs OCSP stapling — and the honest problem, that revocation checking is unreliable (soft-fail browsers, CRL size, OCSP responder availability), **short-lived certificates** reduce the exposure window but still require renewal availability and an explicit compromise/revocation policy.
- **TLS handshake** (1.2 vs 1.3): what's exchanged, where the certificate is validated, what forward secrecy means, how a typical full TLS 1.3 handshake reduces TLS round trips relative to a full TLS 1.2 handshake; resumption and 0-RTT have separate constraints. **mTLS**: both sides present certificates — the standard for service-to-service trust in a cloud platform.
- **Key management**: HSMs, KMS, key hierarchies (root key → data key), envelope encryption, key rotation without re-encrypting everything, and why protected CA signing keys should remain non-exportable in the HSM. Leaf keys and envelope data keys have different handling rules; rewrapping a data key differs from re-encrypting payload data.

- **Tier 2 — strong signal if you have it**
- **ACME protocol** (how Let's Encrypt automates issuance) — a public reference model for automated issuance, without assuming OCI uses that protocol internally.
- **Certificate Transparency** logs — Merkle-tree append-only logs of issued certs; why they exist (misissuance detection).
- **SPIFFE/SPIRE** — workload identity in cloud platforms; the conceptual successor to "give every service a cert."
- **Trust stores** — how an OS/JVM decides what a root is; `cacerts`; the operational pain of distributing trust changes.
- Java specifics: `KeyStore`, `TrustManager`/`X509TrustManager`, `SSLContext`, JCA/JCE providers, Bouncy Castle, keytool. Prepare a Java/TLS debugging example; this is a practice hypothesis, not a confirmed question.

- **Tier 3 — awareness only**
- Post-quantum migration (NIST ML-KEM/ML-DSA standardized 2024) — knowing "key exchange and certificate signatures migrate separately, with algorithm-dependent size and compatibility costs" is enough.
- HSM standards (PKCS#11), FIPS 140-3, certificate policies/CPS.

- **Fastest path**: use the introductory and standards references below, then *do* it: issue a private CA with `openssl` or `step-ca`, sign a leaf, wire mTLS between two local Spring Boot services, and deliberately break it — expired cert, wrong SAN, missing intermediate — and read the exact error each produces. **That last exercise is worth more than any reading**, because reproducing failures gives you concrete evidence for debugging answers.

- Existing detailed reference: [PKI / KMS / certificate-service packet](2.sd/s5.01.PKI-KMS-mechanisms.md); OCI vocabulary and AWS analogies: [architecture notes](4.1o-arch.md).

## 19. Trap points — small follow-ups that sink solved problems

> Philosophy: the interviewer doesn't judge you by the solve. They judge by the follow-up.
> Solving = you practiced. Follow-up = you understand.
> Rule for every practiced problem: prepare its 3 standard follow-ups (complexity edge, mechanism underneath, "what if input changes").
> Every answer below is 1–3 lines. Say mechanism, then defeater. Memorize the 🗣 lines.

### 19.1 Complexity traps

- HashMap get/put is O(1)?
  - average O(1); worst O(n) on collision pile-up
  - Java 8+: bin treeifies at 8 entries → worst O(log n)
  - 🗣 "Amortized O(1), worst O(log n) since Java 8 treeification."
- ArrayList add is O(1)?
  - amortized O(1); resize copies → single add can be O(n)
- String concat in a loop
  - `s += x` is O(n²) total (copy each time) → StringBuilder O(n)
- Sorting lower bound
  - comparison sorts ≥ O(n log n)
  - counting/radix/bucket beat it because they don't compare — need bounded key range
- Recursion space
  - space = max stack depth; balanced tree O(log n), skewed O(n)
  - 10⁵ deep recursion in Java → StackOverflowError → go iterative
- Amortized vs worst — when they ask "worst case?"
  - don't repeat the average; name the adversarial input
- Hash of what?
  - O(1) map ops assume O(1) hashCode; hashing a long string key is O(len) — counts in total complexity
- Two nested loops but O(n)?
  - sliding window / two pointers: each pointer moves ≤ n total → amortized O(n). Say "each element enters and leaves the window once"

### 19.2 Java internals traps

- `==` on Integer
  - compares references; cache −128..127 makes small ones "work" then break
  - 🗣 "Always equals() for boxed types; the Integer cache is why it lies in tests."
- Integer overflow
  - `int` max ~2.1e9; sums/products of 1e5 elements × 1e5 values overflow → use long
  - `Math.abs(Integer.MIN_VALUE)` is still negative
  - comparator `(a, b) -> a - b` overflows → `Integer.compare(a, b)`
- Binary search mid
  - `mid = (lo + hi) / 2` overflows → `lo + (hi - lo) / 2`
- `Arrays.sort`
  - primitives: dual-pivot quicksort, not stable, adversarial worst O(n²)
  - objects: TimSort, stable, O(n log n) worst
  - 🗣 "Primitive sort isn't stable; object sort is TimSort and stable."
- HashMap internals (asked constantly at Oracle)
  - array of bins; index = (n−1) & hash; collision → linked list → red-black tree at 8, back to list at 6
  - default capacity 16, load factor 0.75, resize doubles and rehashes
  - keys must have consistent hashCode/equals; mutating a key after insert loses it
  - iteration order undefined (LinkedHashMap for order, TreeMap for sorted)
- HashMap vs Hashtable vs ConcurrentHashMap
  - Hashtable: legacy, one lock on everything
  - CHM: per-bin locking/CAS, no null keys, weakly consistent iterators, no lock on read
- fail-fast vs fail-safe
  - ArrayList/HashMap iterators throw ConcurrentModificationException on structural change (best-effort, not guaranteed)
  - concurrent collections iterate over a snapshot/weakly consistent — no exception, maybe stale
- PriorityQueue
  - iteration is NOT sorted order; only peek/poll respect order
  - default min-heap; remove(Object) is O(n)
- String
  - immutable; substring copies (since Java 7); `equals` for content
- char arithmetic
  - `'c' - 'a'` = int; `(char)('a' + 2)` = 'c'; count array `new int[26]`
- Pass by value
  - references passed by value: reassigning a param doesn't affect caller; mutating the object does
- `finally` with return
  - finally's return overrides try's return and swallows exceptions — never return in finally
- equals/hashCode contract
  - equal objects must have equal hashCodes; override both or HashMap breaks

### 19.3 Per-pattern traps

- Binary search
  - boundary: `while (lo <= hi)` with `hi = mid - 1` vs `while (lo < hi)` with `hi = mid` — pick one template, state the invariant
  - infinite loop: `lo < hi` with `lo = mid` and mid rounding down → use `mid = lo + (hi - lo + 1) / 2` or restructure
  - rotated array: decide which half is sorted first
  - 🗣 "My invariant: answer is always in [lo, hi]; loop shrinks it by ≥1 each step."
- Sliding window
  - shrink condition: while window invalid, move left — "while", not "if"
  - window with negatives: prefix-sum + map, plain window breaks (monotonicity lost)
- BFS
  - mark visited when ENQUEUEING, not when dequeuing → else duplicates blow the queue
  - level size snapshot: `int sz = q.size()` before the inner loop
- DFS / recursion
  - base case first; visited set for graphs (trees don't need one — unless parent pointers)
  - grid DFS: bounds check before recurse; mark before recurse (or you revisit)
  - deep input → iterative with explicit stack
- Topological sort
  - cycle detection: processed count < n → cycle → return empty/false; say it unprompted
- Heap / top-K
  - K largest → MIN-heap of size k (pop the smallest); most people say max-heap and waste memory
  - heapify is O(n), n pushes are O(n log n)
- Intervals
  - sort by start; merge condition `cur.start <= prev.end` — decide if touching intervals merge, ask
- Linked list
  - dummy head removes head-deletion special case
  - cycle: Floyd slow/fast; find entry: reset one to head, advance both by 1
  - always null-check `fast != null && fast.next != null`
- Tree
  - null root first line
  - BST validity: range (min, max) passed down, not just parent-child compare
  - LCA in BST uses values; LCA in BT needs recursion on both sides
- DP
  - state the recurrence aloud before coding; base cases and iteration order are where bugs live
  - 1D rolling array: iterate direction matters (knapsack: reverse for 0/1)
- Backtracking
  - choose → recurse → UNCHOOSE; forgetting to remove from path is the classic bug
- In-place / no extra space
  - ask "does output/recursion stack count?" before promising O(1)

### 19.4 Testing / edge-case checklist (say these unprompted)

- empty input · single element · all duplicates · all same value
- negative numbers · zero · Integer.MIN/MAX (overflow probe)
- already sorted · reverse sorted · k > n · k = 0
- null (reject or handle — say which)
- the naive-breaker: the input that kills the brute force
- 🗣 closing line: "Three tests: empty, single, and the boundary case — here's why each."

### 19.5 Concurrency mini-traps

- volatile
  - visibility + ordering, NOT atomicity; `count++` on volatile is still a race
- synchronized
  - mutual exclusion + visibility; on `this` vs class vs private lock object — prefer private final lock
- wait/notify
  - wait MUST be in a `while (condition)` loop (spurious wakeups + recheck); wait releases the lock, sleep doesn't
- deadlock
  - 4 conditions: mutual exclusion, hold-and-wait, no preemption, circular wait; break by global lock ordering
- ConcurrentHashMap
  - thread-safe per op; check-then-act still races → `computeIfAbsent` / `putIfAbsent`
- AtomicInteger
  - CAS loop; lock-free ≠ wait-free; heavy contention → LongAdder
- ThreadLocal
  - per-thread copy; leak risk in thread pools (remove after use)
- 🗣 "volatile gives visibility, synchronized/CAS gives atomicity; you usually need the second."

### 19.6 Distributed mini-traps + KV core in 10 lines

- Idempotency
  - at-least-once delivery is a fact; exactly-once effect = dedupe key at the consumer
  - 🗣 "The queue can't be exactly-once; the handler is, via an idempotency key."
- Ordering
  - per-partition/per-key only; global order needs a single sequencer = bottleneck
- CAP one-liner
  - under partition choose availability or consistency; CA doesn't exist in a partition-prone network
- Retry
  - exponential backoff + jitter + budget; retries without jitter synchronize into waves
- Cache
  - cache-aside: read miss → load → set; write → invalidate (not update); staleness bounded by TTL
- **Distributed KV — the core, 10 lines** (your gap; this is the minimum to sound coherent)
  1. Partition: consistent hashing → adding a node moves ~1/N keys, not all
  2. Virtual nodes → even spread
  3. Replicate each key to N=3 nodes across failure domains
  4. Write acked after W replicas; read asks R; W+R>N ⇒ read overlaps a written copy
  5. So W=2/R=2/N=3 tolerates one dead node on each path
  6. Partition happens → replicas diverge → THE core problem
  7. Detect divergence: version per write (timestamp LWW, or vector clock)
  8. LWW: simple, but concurrent writes silently lose one — say this defeater
  9. Repair: read repair (on quorum reads) + anti-entropy (Merkle tree diff) in background
  10. 🗣 "Quorum gives overlap, versioning detects conflict, repair converges replicas — consistency is a spectrum you tune with W and R."
- Leader vs leaderless
  - leader (Raft): ordered, supports CAS; leader failover = brief write unavailability
  - leaderless (Dynamo): always writable; conflicts are yours to resolve

### 19.7 "I don't know" protocol (scored positively at Oracle)

- Never bluff a mechanism; bluffing one layer deep is how you look like you understand nothing
- Formula: honest + adjacent + resource
  - "I haven't used X in production."
  - "The closest thing I've worked with is Y, which solves it by Z."
  - "I'd check the official docs / ask a senior — with a mentor I'd confirm my plan is A then B."
- Then ask one directed question back — they award points for question quality

### 20.4 Concept answers from this round's review

- Live comments / live feed (the miss)
  - Persistent connection per client: SSE (server-to-client, simplest) or WebSocket (bidirectional); long-poll as fallback
  - Stateless connection servers hold `board_id → connections`
  - New comment → DB → publish to `board:{id}` (Redis pub/sub or Kafka) → each subscribed connection server pushes to its sockets
  - Hot board with 1M viewers = fan-out hot key: spread subscribers across servers, coalesce comments per ~100 ms
  - Follow-ups: per-board ordering, slow-client backpressure, reconnect with `Last-Event-ID`
  - "Connection pool" is a DB-side concept; client side, the concern is socket count per server and fan-out cost
- Sharding vs replication

| | Sharding | Replication |
|---|---|---|
| Solves | too much data / writes for one node | availability, read scale, durability |
| Cost | cross-shard queries, rebalancing, hot shard | lag; writes still go to one leader |
| When | dataset or write QPS beyond one primary | almost always, from day one |

- All four combos exist; most services live at "no shard + replicas" (RDS primary + read replicas, Redis primary + replica)
- Sharded and replicated: each shard is its own replica set (Redis Cluster, Cassandra, Mongo sharded, Vitess)
- Who writes
  - Leader-based: one elected primary per shard; replicas serve reads; failover = brief write gap
  - Leaderless: any node takes writes, quorum W+R>N; no failover gap, conflicts to resolve
- Stale replica read: route the user's reads to primary for N seconds after a write, or sticky routing
- Hot key
  - Hot read: local in-process cache with short TTL, replicate the key (`key#0..9`), singleflight on miss
  - Hot write: split/salt the key and sum on read, batch increments, move counters to Redis
  - Hot shard: better composite key, split the shard, isolate the whale tenant
  - 🗣 "Reads: cache closer and replicate the key. Writes: split the key or batch. Shards: fix the key or isolate the whale."
- Rate limiter burst = token bucket
  - `rate` = sustained limit, `capacity` = max burst; lazy refill from `(tokens, last_ts)`
  - Leaky bucket smooths, no burst; fixed window bursts 2× at the boundary by accident; sliding counter for per-window promises
