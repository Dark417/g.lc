## 2. Loop structure

```
[Round 1] HackerRank live, 1 hr, 1 engineer
   │  ~10–15 min resume/behavioral  +  ~40–45 min coding
   ▼
[Final] 4 rounds (recruiter) — reports say 4–5
   ├─ Engineer #1: coding / LLD / tech discussion + behavioral slice
   ├─ Engineer #2: same mix (sometimes HLD, sometimes debug/SOLID refactor)
   ├─ Hiring manager: project deep-dive + behavioral (occasionally coding)
   └─ Key interviewer ("bartender"): outside team, OCI values, mediates debrief
   ▼
[Debrief] within 48 hrs → offer
```

- Status 2026-09-09: Round 1 passed; final loop next
  → 4 rounds in ~4 hours: 2 system design, 1 bar raiser (key interviewer), 1 coding
  → Prep focus: system design (`2.sd/`), IC3 baseline with IC4 stretch signals
- Round 1 (your Friday Sept 4, 11am)
  → Expect **compiling, running code** that passes interviewer-provided tests
  → Usually 1 problem; sometimes 2 shorter ones
  → Difficulty: LC Medium, occasionally Hard
  → Short resume walkthrough first — have a 90-second JPMC pitch ready
  → Email recruiter next day (their explicit instruction)
- Engineer rounds
  → Mix of coding (often 2 mediums), LLD/HLD, deep tech discussion
  → Some rounds: given a class, refactor to SOLID / find the bug
  → Behavioral slice at start or end
- Hiring manager round
  → Draw your architecture, defend every decision under "why X not Y"
  → Behavioral on OCI values
- Key interviewer / bartender round
  → From a different team/org, not your hiring team
  → Purely behavioral, or behavioral + curveball puzzle (one report: Josephus, 10-min timer)
  → Goes resume point-by-point; probes job changes, stakeholder conflict, design justification
  → Reported as the toughest round; also mediates your debrief
- Competencies
  → Recruiter sends assigned competencies (OCI values, technical, role) once final is scheduled
  → Ask for them if not received

## 3. Scoring — what earns points

- Three explicit buckets (recruiter)
  → Qualifying questions before coding — quality of your questions
  → The solution — correctness, then complexity
  → Test cases you write and run yourself
- Implicit buckets (candidate reports)
  → Think-aloud; treat interviewer as a senior peer you'd ask for guidance
  → If you don't know, say so + name what resource you'd use
  → Brute force → iterate is acceptable; incomplete "perfect" solution is not
- 🗣 Opening script for every coding problem
  → "Before I code: input size? duplicates? sorted? nulls/empties? expected return on invalid input? memory constraint?"
  → "Approach: X, O(n log n) time, O(n) space. Alternative: Y. I'll start with X."
  → After coding: "Let me add three tests: empty, single element, the edge that breaks naive."

> Round 1 (Fri Sept 4, 11am): HackerRank live, ~45 min coding, running code + own tests + complexity.

```
difficulty:  ████████░░ Medium   ██░░░░░░░░ Hard   █░░░░░░░░░ Easy
style:       algorithmic 60% · design/LLD 25% · concurrency/impl 15%
```

- Difficulty
  → Predominantly LC Medium

  → More "implement a thing" problems (LRU, browser history, expression eval)

## 11. Coding signature: design-style + concurrency

- LRU Cache ★★★ — treat as mandatory
  → HashMap + doubly linked list, O(1) get/put
  → Follow-up: thread-safe version
  ◆ Coarse: `synchronized` on get/put — simple, correct, contended
  ◆ Better: `ReentrantReadWriteLock` — reads still mutate recency, so RW lock buys little
  ◆ Java-idiomatic: `LinkedHashMap(cap, 0.75f, true)` + `removeEldestEntry` wrapped in a lock
  ◆ Defeater: "lock-free LRU" is a research topic; say sharded/striped locks instead
- Design Browser History ★
- Music player LLD ★; Logging file system ★; Parking lot / meeting-room style
- Hit counter / rate limiter (sliding window, token bucket) — ties to `2.sd/2.sd.md`
- Factory pattern; refactor-to-SOLID given a class ★
- Concurrency
  → Print odd/even alternately from two threads (wait/notify or `Semaphore`) ★
  → Write and run a deadlock, then fix with lock ordering ★
  → Thread-safe LRU (above)
  → Producer/consumer with `BlockingQueue`

## 13. Live-round protocol (HackerRank)

```
0–2 min  restate + clarify    →  2–5 min approach + complexity
5–25 min code (talk)          →  25–35 min run tests + fix
35–40 min edge cases + optimize discussion
```

- Clarify (score bucket #1)
  → Input size / value range → drives O(n²) vs O(n log n)
  → Sorted? duplicates? negatives? nulls/empties?
  → Return type on invalid input — throw vs sentinel
  → Can I use library sort / collections?
- Approach
  → State brute force + its complexity in one sentence
  → State target approach + complexity; pick and go
- Code
  → Compiling Java; real names; helper methods
  → Narrate at decision points, not every line
- Tests (score bucket #3)
  → Run the provided tests first
  → Add: empty, single, all-same, max size, the naive-breaker
  → Say "this test guards the off-by-one on the right boundary"
- Stuck
  → Say what you'd search / who you'd ask; ask interviewer a directed question
  → Recruiter: they _want_ to guide — following guidance is scored positively
- Setup before Round 1
  → HackerRank account, Java 17 template with `Scanner`/`BufferedReader` boilerplate memorized
  → Practice 5 problems inside HackerRank's editor — different keybindings than LC

```java
class LRU<K,V> extends LinkedHashMap<K,V> {
  private final int cap;
  LRU(int cap){ super(cap, 0.75f, true); this.cap = cap; }
  @Override protected boolean removeEldestEntry(Map.Entry<K,V> e){ return size() > cap; }
}
```

## 15. PKI domain learning priorities

- Use 2–3 focused weeks as a planning estimate for an initial domain ramp; demonstrate understanding and debugging ability rather than claiming production PKI expertise.

- **Tier 1 — must know cold before any technical round**
- **Asymmetric vs symmetric crypto**; what a key pair is; why you sign with a private key and verify with a public one. Digital signature vs encryption vs MAC — three different things, commonly conflated.
- **X.509 certificate anatomy**: subject, issuer, validity window, public key, extensions (SAN, key usage, extended key usage, basic constraints), signature. Why SAN replaced CN for hostname validation.
- **Chain of trust**: leaf → intermediate(s) → root. Why CA designs commonly protect roots offline and use intermediates for routine signing; deployment policies vary. Path building and path validation — and why path *building* is harder than it sounds (multiple valid chains, cross-signing).
- **Certificate lifecycle**: key generation → CSR → issuance → distribution/installation → renewal → **rotation** → revocation → expiry. The operational reality: expiry is a preventable outage mode; automate renewal and monitor time-to-expiry.
- **Revocation**: CRL vs OCSP vs OCSP stapling — and the honest problem, that revocation checking is unreliable (soft-fail browsers, CRL size, OCSP responder availability), **short-lived certificates** reduce the exposure window but still require renewal availability and an explicit compromise/revocation policy.
- **TLS handshake** (1.2 vs 1.3): what's exchanged, where the certificate is validated, what forward secrecy means, how a typical full TLS 1.3 handshake reduces TLS round trips relative to a full TLS 1.2 handshake; resumption and 0-RTT have separate constraints. **mTLS**: both sides present certificates — the standard for service-to-service trust in a cloud platform.
- **Key management**: HSMs, KMS, key hierarchies (root key → data key), envelope encryption, key rotation without re-encrypting everything, and why protected CA signing keys should remain non-exportable in the HSM. Leaf keys and envelope data keys have different handling rules; rewrapping a data key differs from re-encrypting payload data.

- **Tier 2 — strong signal if you have it**
- **ACME protocol** (how Let's Encrypt automates issuance) — a public reference model for automated issuance, without assuming OCI uses that protocol internally.
- **Certificate Transparency** logs — Merkle-tree append-only logs of issued certs; why they exist (misissuance detection).
- **SPIFFE/SPIRE** — workload identity in cloud platforms; the conceptual successor to "give every service a cert."
- **Trust stores** — how an OS/JVM decides what a root is; `cacerts`; the operational pain of distributing trust changes.
- Java specifics: `KeyStore`, `TrustManager`/`X509TrustManager`, `SSLContext`, JCA/JCE providers, Bouncy Castle, keytool. Prepare a Java/TLS debugging example; this is a practice hypothesis, not a confirmed question.

- **Tier 3 — awareness only**
- Post-quantum migration (NIST ML-KEM/ML-DSA standardized 2024) — knowing "key exchange and certificate signatures migrate separately, with algorithm-dependent size and compatibility costs" is enough.
- HSM standards (PKCS#11), FIPS 140-3, certificate policies/CPS.

- **Fastest path**: use the introductory and standards references below, then *do* it: issue a private CA with `openssl` or `step-ca`, sign a leaf, wire mTLS between two local Spring Boot services, and deliberately break it — expired cert, wrong SAN, missing intermediate — and read the exact error each produces. **That last exercise is worth more than any reading**, because reproducing failures gives you concrete evidence for debugging answers.

- Existing detailed reference: [PKI / KMS / certificate-service packet](2.sd/s5.01.PKI-KMS-mechanisms.md); OCI vocabulary and AWS analogies: [architecture notes](4.1o-arch.md).

## 17. PKI interview prompts and transferable hooks

- **Practice prompts inferred from the domain; not confirmed interview questions.**
- "Design a certificate issuance service for a cloud platform." (The obvious one. Think: API, request validation, authorization — who may request a cert for which name — signing via HSM, high availability of a signing path that can't replicate its key freely, audit logging, rate limiting, CT submission when required by public-trust policy (not indiscriminately for private names), storage of issued certs, revocation propagation.)
- "How would you handle rotating a widely-used intermediate CA without downtime?" (Expand-contract, applied to trust: distribute any required new trust anchors or pinned-intermediate updates *before* switching issuance. An intermediate beneath an already-trusted root may need only a complete served chain; a root change requires trust-store rollout. Readers before writers, with overlap and telemetry before retirement.)
- "A service is failing TLS handshakes intermittently. Debug it." (Chain incomplete on one host behind a load balancer; clock skew; SAN mismatch; expired intermediate; OCSP responder timeout.)
- "How do you build a service that must never lose an audit record?"
- Multi-tenancy: isolation, per-tenant limits, noisy neighbor.
- Backward compatibility of an API across cloud regions on different versions.

- **Your best hooks into their domain** (use these deliberately):
- Certificate lifecycle ≈ the schema/contract evolution problem you already reason about well: expand-contract, readers before writers, telemetry-gated removal, no flag days.
- mTLS and trust distribution ≈ the cross-service authorization work on Market Monitor.
- Expiry-driven outages ≈ your production support and guardrail instincts — the answer is automation plus alerting on time-to-expiry, not vigilance.
