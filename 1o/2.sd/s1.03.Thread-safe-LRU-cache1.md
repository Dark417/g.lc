## Interview framing

### The one-paragraph version, before any quoting

- A cache is a small fast box that remembers answers so you do not have to ask the slow expensive source again.
  - The slow expensive source is called the **origin**, and here it is a database.
- The box is small on purpose. When it is full and a new answer arrives, something has to be thrown out.
- **LRU** stands for **Least Recently Used**. It is the rule for choosing what to throw out.
  - Throw out whatever has gone longest without being touched.
- Everything hard in this question comes from three additions on top of that simple rule.
  1. Many threads use the box at once, and the box must not break.
  2. When the answer is missing, someone has to go fetch it, and 5,000 threads must not all go fetch it at once.
  3. Eventually the box is not one box in one process but a shared box across many machines, and now the
     answer inside it can be *wrong*, not just missing.

> Target: OCI IC3 ownership of a bounded platform component.

**What this says in plain words**

- The bar being aimed at is a mid-level engineer at Oracle Cloud Infrastructure (OCI) who owns one
  well-defined piece of a platform end to end.
- "Bounded platform component" means one box with a clear edge.
  - A cache library, a rate limiter, a load balancer.
  - Not an entire product, and not the company's whole storage strategy.

**Why it matters**

- It sets how deep to go. You are expected to own the internals of this one component completely.
- It also sets how wide *not* to go. Redesigning the database is out of scope and reads as avoidance.

**Why it matters**

  - Failure mode two: opening with a multi-region cache mesh when the question asked for a data structure.

> Naive: a `ConcurrentHashMap` plus a `synchronized` wrapper around a linked list, and a loader called on every miss.

**What this says in plain words**

This is the answer most candidates give first. It contains three mistakes, one per component.

1. **`ConcurrentHashMap`** is Java's thread-safe hash map. Many threads can read and write it at once
   without corrupting it.
   - The trap: it makes *the map* safe. It says nothing about a second data structure sitting next to it.
2. **`synchronized` around the linked list** means "only one thread at a time inside the list code".
   - The trap: the map has one lock and the list has a different lock.
   - A thread can be inside the map's lock and the list's lock at different instants, so another thread can
     observe the pair mid-update.
   - The two structures are consistent only if one lock covers *both*.
3. **A loader called on every miss** means: whenever the key is absent, immediately go ask the database.
   - The trap: 5,000 threads miss the same key in the same millisecond and send 5,000 database queries.

**Worked example of why the split lock fails**

- Capacity 3. Current list order, most recent first: `[C, B, A]`. The map holds `A`, `B`, `C`.
- Thread A runs `get(A)`, so it must move `A` to the front.
- Thread B runs `put(D, 4)`. The cache is full, so it must evict the least recent, which is `A`.

| Step | Thread A | Thread B | Shared state after the step |
|---|---|---|---|
| 1 | Reads map, finds node `A` | — | List `[C, B, A]` |
| 2 | — | Reads map, decides victim is `TAIL.prev`, which is `A` | List `[C, B, A]` |
| 3 | Unlinks `A` from the tail | — | List `[C, B]`; node `A` detached but still in the map |
| 4 | — | Unlinks `A` again, using its now-stale `prev` and `next` | List pointers cross-linked; `B.next` points at a detached node |
| 5 | Links `A` back in after `HEAD` | — | List `[A, C, B]` |
| 6 | — | Removes `A` from the map | Node `A` is in the list with no map entry |

- Final state: the list contains a node that the map does not know about.
  - Size accounting is now wrong by one. The cache thinks it holds 3 entries; the list holds 4 nodes.
  - `get(A)` returns a miss, but `A` still occupies capacity forever.
  - It can never be evicted by key, because eviction removes `victim.key` from the map and the map no
    longer has that key.
  - This is a permanent memory leak inside a structure whose entire job is to bound memory.

**Why it matters**

- The naive answer is not "less optimal". It is *wrong*. It produces silent corruption, not slowness.

> First break: every exact-LRU hit mutates shared recency state, so a read lock is wrong and a single lock serializes all threads.

**What this says in plain words**

Three ideas in one line.

1. **A cache hit is a write.**
   - Intuitively `get` only reads. In an exact LRU it does not.
   - A hit must move that entry to the most-recently-used position, which rewrites pointers shared by
     every thread.
2. **Therefore a read-write lock does not help.**
   - A **read-write lock** lets unlimited readers in at once, but only one writer, and only when no readers
     are present. It is a large win for read-mostly data.
   - It is useless here, because the "reads" are writes. Every reader would have to take the write side.
3. **Therefore one plain lock serializes everybody.**
   - With 32 application threads and one lock, exactly one thread is ever inside the cache. The other 31
     wait. The cache becomes a single-lane bridge.

**Why it matters**

- This is the central tension of the whole question.
  - Exactness of recency order and parallelism are in direct conflict.
  - Every later decision (stripes, buffered reads, CLOCK) is a way of trading one for the other.

> Second break: a slow loader returns after a newer `put` or `remove`, and its stale value silently repopulates the cache.
> The same race reappears across nodes once the cache is shared.

**What this says in plain words**

1. **A loader is slow and runs outside the lock**, because you must never hold a lock across a network call.
2. **While it is out there, the world can change.** Someone can `put` a new value for that key, or `remove`
   the key entirely.
3. **When the loader comes back, it writes what it read a moment ago.** It overwrites newer truth with
   older data, and nothing logs an error. That is the "silently" part.
4. **Going distributed does not fix it, it multiplies it.** Now the stale write can come from a different
   machine, so an in-process lock cannot prevent it.

**Worked example with real times**

- Time 0 ms: Thread A misses key `user:42`. It calls the database. The database is loaded; the query takes 180 ms.
- Time 20 ms: Thread B runs `put("user:42", {name: "Bob"})` because the user just renamed themselves.
  The cache now holds `{name: "Bob"}`.
- Time 180 ms: Thread A's database call returns `{name: "Alice"}`, the value as of time 0 ms.
- Time 181 ms: Thread A writes `{name: "Alice"}` into the cache.
- Result: the cache serves `Alice` to every caller for the next 30 seconds, even though the write of `Bob`
  succeeded and the database says `Bob`.
- Nothing crashed. No exception was thrown. The system is simply lying.

**Why it matters**

- This class of bug is the reason the design carries a **generation** counter per key, explained in detail
  later. Without it, a cache with a loader is a stale-data generator with extra steps.

> Minimum primitives
> A map for node identity
> A doubly linked list for `O(1)` recency
> One lock over both
> A per-key generation to fence asynchronous loads
> A source version once the cache is distributed.

**What this says in plain words**

These are the five parts. Nothing can be removed; each buys exactly one thing.

1. **A hash map for identity.**
   - Given a key, find the entry in one step instead of scanning.
   - A **hash map** turns a key into an array position by hashing it, so lookup cost does not depend on how
     many entries exist.
   - Looking up 1 key among 100,000 costs the same as among 10.
2. **A doubly linked list for recency in `O(1)`.**
   - A **doubly linked list** is a chain of nodes where each node knows both neighbours: `prev` and `next`.
   - Because each node knows both neighbours, you can cut a node out of the middle with about 4 pointer
     writes and no searching.
   - **`O(1)`** means the cost does not grow with the number of entries: 4 pointer writes whether the cache
     holds 10 entries or 100,000.
3. **One lock over both.**
   - The map and the list are two views of one truth.
   - A lock that covers only one of them lets a thread see them disagree.
4. **A per-key generation to fence asynchronous loads.**
   - A **generation** is a counter attached to a key. Every explicit `put` or `remove` bumps it.
   - A loader records the counter when it starts, and refuses to publish if the counter changed while it
     was away.
   - That is what "fence" means: a check that rejects work which arrived too late.
5. **A source version once distributed.**
   - Across machines a local counter is not enough, because the other machine has its own counter.
   - Instead, carry the database's own version number for the row, so any machine can tell which of two
     values is newer.

**Why it matters**

- If you can name these five and say what each buys, you can rebuild the whole answer from scratch in the
  room. That is the point of a "minimum primitives" list.

> 🗣 "The map gives identity, the list gives recency, one lock gives the invariant; everything after that is fencing stale work."

**What this says in plain words**

- This is the quotable summary. It splits the design into two halves.
  - Half one is the data structure: map, list, lock.
  - Half two is everything else — single-flight, TTL, invalidation, source versions — and all of it exists
    for one reason, to stop old work from overwriting new work.
- An **invariant** is a statement that must be true every time an operation finishes.
  - Here: "every key in the map has exactly one node in the list, and every list node is in the map".

**Why it matters**

- Interviewers remember the sentence that organises the answer.
- This one converts a sprawling topic into a two-part story you can navigate out loud without notes.

> "I will build an in-process exact LRU first, then add thread safety, coalesced loading, TTL, and finally a cache-aside shared tier."

**What this says in plain words**

- This sentence is a table of contents spoken aloud, in dependency order.
  - **In-process** means the cache lives inside your service's own memory, not on a separate server.
  - **Exact LRU** means the eviction order is truly least-recently-used, not an approximation.
  - **Coalesced loading** means many simultaneous misses for the same key produce one database call.
  - **TTL** stands for **time to live**: an expiry stamp after which the entry is treated as absent.
  - **Cache-aside** means the application, not the cache, loads on a miss and writes the result back.
    The cache never talks to the database itself.
  - **Shared tier** means a cache process that other service instances also use, such as a Redis or
    Memcached cluster.

**Why it matters**

- Saying the plan first buys you 45 minutes of not being interrupted, because the interviewer knows the
  distributed part is coming and does not need to prompt for it.

> "First I confirm whether LRU must be exact, whether capacity is entries or bytes, and how much staleness callers tolerate."

**What this says in plain words**

Three clarifying questions, each of which changes the design materially.

1. **Exact or approximate LRU?**
   - Exact forces one lock over the whole structure.
   - Approximate allows splitting the cache into independent pieces that never coordinate.
2. **Capacity in entries or bytes?**
   - 100,000 entries of 1 KB is 100 MB.
   - 100,000 entries where one of them is 50 MB is a heap crash.
   - Counting entries is `O(1)`. Counting bytes means one insert may evict several entries in a row.
3. **How stale may a value be?**
   - "Two minutes is fine" and "revocation must take effect instantly" are not the same system.
   - The second one may mean: do not cache this data at all.

**Why it matters**

- Each of the three answers eliminates half the design space.
- Asking them at minute 6 is cheap. Discovering them at minute 40 forces a rewrite on the whiteboard.

> "Then I size memory and origin load, which decides one lock versus stripes and whether single-flight is mandatory."

**What this says in plain words**

- Estimates are not decoration. Each number forces a specific choice.
  - Memory size decides whether entry-count capacity is safe or whether byte weighting is required.
  - **Origin load**, meaning requests per second that reach the database, decides whether coalescing misses
    is an optimisation or a hard requirement.
  - Throughput per lock decides whether one lock survives, or whether you need **stripes**, meaning several
    independent sub-caches each with their own lock.

**Why it matters**

- The difference between a junior and a senior estimate is the sentence after the number.
  - "120 MB" is trivia.
  - "120 MB, therefore an entry count alone does not bound heap, therefore add a byte weight" is design.

> "The deep dive is the map-plus-list invariant under one lock and the generation check that stops a stale load overwriting a newer write."

**What this says in plain words**

- You are naming, in advance, the two things you intend to prove.
  1. The data-structure invariant, and why one lock is the only way to hold it.
  2. The fencing check that makes asynchronous loading safe.

**Why it matters**

- Deep dives go badly when the interviewer picks the topic and it is your weakest one.
- Volunteering the topic means you dive where you are strongest, and it still reads as depth, not evasion.

## Requirements — IC3 baseline

> Numerical targets are interview assumptions unless an adjacent primary source states otherwise.

**What this says in plain words**

- Every number in this file was chosen by the author to make the design concrete.
- None of them came from an Oracle document, unless a link right next to the number says otherwise.

**Why it matters**

- An interviewer will sometimes challenge a number: "where does 100,000 entries come from?"
- The correct answer is "it is my assumption; here is what changes if it is 10 million".
- The wrong answer is inventing a source. That is the single fastest way to lose credibility.

### The clarifying-questions table, one row at a time

> | Exact or approximate LRU? | Exact in-process; approximate acceptable when striped | Exact LRU forces one lock over map and list |

**What this says in plain words**

1. **The question.** Must eviction order be truly least-recently-used, or is "roughly the oldest" fine?
2. **The assumed answer.** Exact while the cache lives in one process. Once you split it into stripes,
   approximate is accepted.
3. **Why it changes the design.** Exactness means there is one global ordering of all entries.
   One global ordering means one lock, because two threads cannot both be authoritative about "which entry
   is oldest".

**Worked example of the difference**

- Capacity 4, one exact list, most recent first: `[D, C, B, A]`. Insert `E`. The victim is `A`. No ambiguity.
- Now split into 2 stripes by hashing the key.
  - Stripe 0 holds `[D, B]`, stripe 1 holds `[C, A]`, and each has capacity 2.
  - Insert `E`, which hashes to stripe 0. The victim is `B`, not `A`.
  - `B` was touched more recently than `A`, so the eviction is "wrong" by exact-LRU standards.
- The stripe design evicted a warmer key. In exchange, two threads can now work at once.

**Why it matters**

- This single row is the fork in the road for the entire design.
- If the answer is "approximate is fine", the rest of the concurrency discussion becomes much easier and
  much less interesting.

> | Capacity unit? | Entry count first; byte weight as a follow-up | Byte weight makes one insert evict many entries |

**What this says in plain words**

1. **Counting entries** is simple. Size is an integer; insert bumps it by 1; evict drops it by 1.
2. **Counting bytes** means each entry carries a weight, and insert must evict in a loop until there is room.
3. The prompt starts with entries because it is the classic data-structure question; bytes are the realistic
   follow-up.

**Worked example**

- Capacity as entries: 100,000 entries. Insert the 100,001st. Evict exactly one. Cost is constant.
- Capacity as bytes: budget 120 MB, currently using 119.9 MB. Insert a 5 MB value.
  - You must evict until at least 5 MB is free.
  - If the tail entries are each 1 KB, that is roughly 5,000 evictions in one `put` call.
  - Each eviction is `O(1)`, but 5,000 of them under the lock is roughly 5,000 times the critical-section
    length.
  - At around 100 ns per eviction, that is about 0.5 ms inside the lock, blocking all 32 threads.
- That is why the source later says byte-weighted insertion is not `O(1)` in the worst case.

**Why it matters**

- An entry count bounds the *number* of things, not the *memory*. Memory is what actually kills the process.

> | Are values mutable? | Immutable by contract | The cache cannot make caller mutations thread-safe |

**What this says in plain words**

1. **Immutable** means: once created, the object never changes. To "change" it you build a new one.
2. The cache hands the *same object reference* to every caller that asks for that key.
3. If one caller mutates that object, every other caller sees the mutation instantly, with no lock, from
   any thread. That is a data race the cache cannot prevent.

**Worked example of the bug**

- Cache holds key `config:billing` mapped to a `Settings` object with field `retries = 3`.
- Thread A calls `get("config:billing")` and receives a reference to that object.
- Thread B calls `get("config:billing")` and receives a reference to *the same* object.

| Step | Thread A | Thread B | Observable state |
|---|---|---|---|
| 1 | Reads `settings.retries` and sees `3` | — | `retries = 3` |
| 2 | — | Sets `settings.retries = 0` for a local experiment | `retries = 0` |
| 3 | Reads `settings.retries` again and sees `0` | — | `retries = 0` |
| 4 | — | — | Every future `get` also sees `0`, permanently |

- Thread A's own logic now disagrees with itself between two lines of code.
- The cache did nothing wrong. It returned the same value it stored. The contract was broken by the caller.

**Fixes, in order of preference**

1. Make values immutable, ideally enforced at the API boundary by a type that has no setters.
2. If the value must be mutable, return a defensive copy on every `get`.
   - Cost: an allocation and a copy per hit, which at 100,000 hits per second is significant.

**Why it matters**

- This is a requirement, not an implementation detail. It belongs in the contract the caller signs.

> | Who loads on a miss? | Caller-supplied loader; one origin call per key at a time | Forces single-flight, a deadline, and generation fencing |

**What this says in plain words**

1. **The cache does not know how to fetch anything.** The caller passes in a function.
   - This keeps the cache generic: it works for database rows, HTTP responses, computed results, anything.
2. **At most one call per key is in flight at a time.** That is **single-flight**.
3. That choice forces three mechanisms into the design.
   - A registry of in-flight loads, so a second caller can find and join the first one.
   - A **deadline**, so a hung origin does not leave callers waiting forever.
   - **Generation fencing**, so a load that returns late does not overwrite newer data.

**Why it matters**

- Notice the structure of the row: one requirement answer drags three mechanisms in with it.
- Being able to say "this answer forces those three" is exactly the reasoning being tested.

> | Staleness tolerance? | Seconds for reference data; zero for authorization | Decides TTL-only versus version-validated or uncached path |

**What this says in plain words**

1. **Different data classes tolerate different lag.** One cache policy for everything is wrong.
2. **Reference data** — country lists, product catalogues, pricing tiers — can be seconds out of date and
   nobody is harmed.
3. **Authorization data** — "is this token revoked?", "does this user still have admin?" — must not be stale
   at all. A 30-second stale permission is a 30-second security hole.
4. Consequently there are three possible treatments, not one.
   - TTL only: cheap, bounded staleness.
   - Version validated: the cache holds a value plus a version, and a read confirms the version is current.
   - Uncached: the read always goes to the authoritative source.

**Worked example**

- An admin revokes a user's access at 12:00:00.
- The permission was cached at 11:59:45 with a 30-second TTL, so it expires at 12:00:15.
- Between 12:00:00 and 12:00:15 the user still passes authorization checks: 15 seconds of unauthorised access.
- If the check happens 200 times per second, that is roughly 3,000 requests served under a revoked permission.

**Why it matters**

- This is the row that most often becomes a pushback later: "the cache must enforce immediate revocation".
- Having already classified data by staleness tolerance lets you answer "then that class is not cached",
  instead of trying to defend a TTL that cannot meet the requirement.

> | Deployment shape? | In-process first, then cache-aside over an authoritative database | Invalidation and source versions join the contract |

**What this says in plain words**

1. **Phase one** is a library inside the service. There is one copy per process, and it dies at restart.
2. **Phase two** adds a shared cache cluster in front of the database, used by all service instances.
3. Phase two introduces two brand-new concerns that did not exist in phase one.
   - **Invalidation**: when the database changes, someone must delete or update the cached copy, and that
     someone is a message crossing a network, which can be lost or delayed.
   - **Source versions**: with several writers, you need a way to know which of two values is newer, and
     an in-process counter cannot answer that.

**Why it matters**

- The jump from in-process to distributed is not "the same thing, bigger". It is a different problem class.
- Section [Single-flight loading, TTL, LFU, and distributed consistency](#e103-7) walks the new problems in detail.

> | Multi-tenant? | Yes, one namespace per tenant | Per-tenant byte budgets stop noisy-tenant eviction |

**What this says in plain words**

1. **Multi-tenant** means many customers share one deployment of the service.
2. **Namespace** means every cache key is prefixed with the tenant, so tenant A's key `user:42` and
   tenant B's key `user:42` are different cache entries.
3. **Per-tenant byte budgets** cap how much of the shared cache one tenant may occupy.

**Worked example of the noisy tenant**

- A shared cache holds 100,000 entries, used by 50 tenants.
- In steady state each tenant holds roughly 2,000 entries and enjoys a 95% hit rate.
- Tenant 17 runs a nightly export that reads 2,000,000 distinct rows in ten minutes.
- With no per-tenant budget, tenant 17's reads evict every other tenant's entries within seconds.
  - The other 49 tenants' hit rate collapses from 95% to near 0%.
  - Origin load jumps from 5,000 reads/s to nearly 100,000 reads/s.
- With a per-tenant budget of 2,400 entries, tenant 17 can only evict its own entries.
  - Its own hit rate collapses. The other 49 tenants never notice.

**Why it matters**

- Isolation is a correctness property in a multi-tenant system, not a nicety.
- Without it, one customer's batch job is an outage for everyone else.

### Functional scope

> Start with the in-process LLD prompt.
> `get` returns a value or miss.
> `put` inserts or replaces a value.
> Access and replacement move an entry to most-recent position.
> Capacity is an entry count for the initial solution.
> Reject null keys and values.
> Reject nonpositive capacity.

**What this says in plain words**

- **LLD** means **low-level design**: the data-structure and API level, as opposed to boxes-and-arrows
  high-level design.
- Six separate rules are stated. One at a time:

1. **`get` returns a value or a miss.**
   - "A miss" must be distinguishable from "a stored null". That is why nulls are rejected outright.
2. **`put` inserts or replaces.**
   - Replacing an existing key must not increase the size, because the key was already counted.
   - Forgetting this is a classic bug: size grows past capacity while the map holds only `N` keys.
3. **Both access and replacement count as recency.**
   - A `get` moves the entry to most-recent.
   - A `put` on an existing key also moves it to most-recent.
4. **Capacity is an entry count in version one.** Byte weighting is a stated follow-up, not version one.
5. **Reject null keys and values.**
   - A null key has no hash and no equality; a null value is indistinguishable from a miss.
6. **Reject nonpositive capacity.**
   - Capacity 0 means every `put` immediately evicts what it just inserted, which is a cache that cannot
     hold anything but still costs work. Capacity −1 is meaningless.

**Worked example of the replace bug**

- Capacity 3. Contents, most recent first: `[C, B, A]`, size counter 3.
- Call `put(B, 99)`.
  - Correct behaviour: `B` exists, so overwrite its value, move it to the front. List `[B, C, A]`, size stays 3.
  - Buggy behaviour: blindly create a node, insert, `size = 4`, evict the tail `A`.
    - Now the map has two entries for `B` or one orphaned node, and `A` was evicted for no reason.

**Why it matters**

- These six rules are the acceptance tests. An interviewer who asks "what about capacity 1?" is checking
  whether you thought about boundaries at all.

> Follow-ups
> Thread safety.
> TTL expiration.
> Coalesced value loading.
> LFU eviction.
> Distributed cache-aside deployment.

**What this says in plain words**

- This is the known order in which the question escalates. Each item is a separate 5-to-10-minute extension.
  1. **Thread safety** — make it correct with 32 threads.
  2. **TTL expiration** — entries also expire by time, not only by pressure.
  3. **Coalesced value loading** — one origin call per key, shared by all waiters.
  4. **LFU eviction** — **Least Frequently Used**: evict by access count rather than by recency.
  5. **Distributed cache-aside** — the shared tier and everything it drags in.

**Why it matters**

- Knowing the escalation ladder means you can pre-load the next answer while still finishing the current one.
- It also tells you not to spend 20 minutes on the base LRU: four more topics are waiting.

### The non-functional requirements table

> | Concurrent callers | `32` application threads | One cache lock; stripes only after measured contention |

**What this says in plain words**

- 32 threads will use this cache at the same time.
- Version one gives all 32 a single lock.
- Stripes are added only if a profiler shows the lock is the bottleneck.

**Why it matters**

- 32 is small enough that one lock is plausible. At 3,200 threads it would not be.
- Naming the number is what makes "start with one lock" a defensible decision instead of laziness.

> | Capacity | `100,000` entries per instance | Eviction under the same lock as insertion |

**What this says in plain words**

1. Each process holds up to 100,000 entries.
2. Eviction happens under the same lock as insertion, in the same critical section.
3. That is what keeps "size never exceeds capacity when an operation returns" true.

**What breaks without it**

- If insertion took the lock, released it, then re-took the lock to evict, another thread could insert in the
  gap. Size would briefly exceed capacity, and under sustained load "briefly" becomes "permanently".

> | Throughput | `100,000 operations/s` benchmark | `O(1)` map/list work; no I/O inside the lock |

**What this says in plain words**

1. The target is 100,000 cache operations per second across the whole process.
2. Two rules make that achievable.
   - All work inside the lock is constant time.
   - No **I/O** — no network calls, no disk reads, no logging to a file — happens while holding the lock.

**Worked example of why I/O inside the lock is fatal**

- A database call takes 5 ms. That is 5,000 µs.
- Holding the lock for 5,000 µs means the cache can serve at most 200 operations per second, because only
  one thread is inside at a time.
- The target is 100,000 per second. One I/O call inside the lock costs you a factor of 500.

> | Local operation latency | p99 < `1 ms`, excluding a loader | Constant-time critical section; loader runs outside the lock |

**What this says in plain words**

1. **p99** means the 99th percentile: 99 out of 100 operations finish faster than this.
   - It is the right metric because averages hide the stalls that users actually notice.
2. The 1 ms budget covers cache work only. Time spent inside a caller's loader does not count against it.
3. That exclusion is only honest because the loader genuinely runs outside the lock.

**Why it matters**

- If the loader ran inside the lock, every other thread's cache latency would include somebody else's
  database call, and the p99 claim would be a fiction.

> | Loader deadline | `200 ms` | Bounded future timeout; flight removed on timeout or error |

**What this says in plain words**

1. A loader gets 200 ms. After that the attempt fails.
2. A **future** is a placeholder object for a result that is not ready yet. Callers wait on it.
3. When the deadline fires, the in-flight record is deleted, so the next caller starts a fresh attempt
   instead of joining a dead one.

**What breaks without it**

- A hung origin — a database that accepts the connection and never answers — would accumulate waiting
  threads forever.
- With 32 threads and no deadline, the whole service is blocked in about 32 requests. The cache becomes the
  outage instead of preventing it.

> | Distinct concurrent loads | At most `128` | Semaphore over active flights, separate from per-key coalescing |

**What this says in plain words**

1. Single-flight bounds the number of loads **per key** to 1.
2. It does *not* bound the number of **distinct keys** loading at once. 50,000 different missing keys means
   50,000 concurrent loads.
3. So a second, independent limit is needed: at most 128 loads in total.
4. A **semaphore** is a counter with a fixed number of permits. A thread takes a permit before starting and
   returns it when done. When permits run out, the next thread waits.

**Worked example**

- Cold start: the cache is empty and 100,000 requests per second arrive for distinct keys.
- Single-flight alone: every request is a distinct key, so it coalesces nothing. 100,000 concurrent
  database calls.
- With a 128 permit semaphore: at most 128 calls are in flight.
  - If each call takes 20 ms, throughput is `128 / 0.02 s = 6,400 loads per second`.
  - The origin sees 6,400 reads/s instead of 100,000 reads/s: a factor of about 15 protection.
  - Everyone else fails fast or waits, which is a choice you make explicitly, not an accident.

**Why it matters**

- These are two different problems that look like one. Confusing them is a common and visible mistake.

> | Persistence | 0 durable local cache entries required | Disposable entries; the database owns durable truth |

**What this says in plain words**

1. Nothing in the cache needs to survive a restart. Zero entries, deliberately.
2. **Durable** means it survives a crash, usually by being on disk with a flush.
3. The database owns the truth. The cache owns only a copy.

**Why it matters**

- This one line eliminates a huge amount of work: no write-ahead log, no replication, no recovery protocol.
- It also justifies the later refusal of **write-back** caching, where losing the cache would lose data.

> | Distributed staleness bound | TTL `30 s` plus invalidation lag, disclosed to callers | TTL plus durable change-event invalidation; version check on publication |

**What this says in plain words**

Four claims are stacked in this row.

1. **The staleness bound is not just the TTL.** It is the TTL *plus* however long invalidation messages take
   to arrive.
2. **It is disclosed to callers.** It is part of the API contract, written down, not folklore.
3. **Durable change events** carry the invalidations, so a consumer restart does not silently drop them.
4. **A version check on publication** stops an old loader reinstalling a value after the invalidation
   already arrived.

**Worked example of the real bound**

- TTL is 30 s.
- Invalidation is published from the database commit and typically arrives in 2 s, with a p99 of 8 s.
- Worst realistic staleness is not 30 s and not 8 s. It is the interaction.
  - Write commits at `t = 0`.
  - Invalidation arrives at `t = 8 s` (p99) and deletes the entry, so the visible stale window is 8 s.
  - If the invalidation is *lost*, TTL is the backstop, and the stale window is up to 30 s.
- So the disclosed bound is "up to 30 s, typically under 2 s". Both numbers belong in the contract.

**Why it matters**

- Callers design their own retries and user-facing messages around this number.
- An undisclosed bound means every caller invents their own guess, and the guesses are always optimistic.

### Invariants

> Every live key maps to exactly one list node.
> Every non-sentinel list node appears in the map.
> Map size equals live list length.
> Size is at most capacity when a public operation completes.
> A successful `get` moves the node under the same lock used by eviction.
> A load publishes only if no newer `put`, `remove`, or `clear` happened for that key since the load was registered.

**What this says in plain words**

Six statements that must be true whenever the cache is not mid-operation.

1. **One key, one node.** No key ever has two nodes. Two nodes for one key means one of them is unreachable
   and leaks, and eviction may remove the wrong one.
2. **No orphan nodes.** Every real node is findable by key.
   - A **sentinel** is a fake node used as a permanent `HEAD` and `TAIL` marker so the list code never has
     to special-case the empty list or the ends. Sentinels are excluded because they hold no user data.
3. **The two counts agree.** If the map has 100,000 keys, the list has 100,000 real nodes.
4. **Capacity holds at the boundary.** During a `put` the size may momentarily be `capacity + 1`, inside the
   lock, before eviction runs. No other thread can observe that, because they are all outside the lock.
5. **`get` and eviction share a lock.** This is the sentence that rules out a read-write lock, stated as an
   invariant rather than as advice.
6. **Loads are fenced.** A load result is installed only if nothing newer happened to that key.

**Why sentinels are worth the two extra nodes**

- Without sentinels, `unlink(node)` needs four branches: node is head, node is tail, node is both, node is
  in the middle.
- With sentinels, it is unconditional:

```text
node.prev.next = node.next
node.next.prev = node.prev
```

- Fewer branches means fewer places for a concurrency bug to hide, and a shorter critical section.

**Why it matters**

- Invariants are what you assert in tests. "Run 1,000,000 random operations, then check all six" is a test
  that finds real bugs, and it is a strong thing to volunteer in an interview.

### Non-goals

> Durable or replicated cache contents.
> Write-back caching where the cache is the system of record.
> Cross-tenant sharing of cached values.
> Range queries or secondary indexes over cached keys.

**What this says in plain words**

Four things this design explicitly refuses to do.

1. **No durability or replication.** Losing the cache loses nothing but speed.
2. **No write-back.** In **write-back** caching, writes land in the cache and are flushed to the database
   later. That makes the cache the system of record, and a crash loses accepted writes.
3. **No cross-tenant sharing.** Even if two tenants would compute the same value, they get separate entries.
   Sharing would be a data-leak path.
4. **No range queries or secondary indexes.** The cache answers "give me key K", not "give me all keys
   starting with `user:`" and not "give me everything with `status = active`".

**Why it matters**

- Non-goals are how you stop the interviewer from drifting into a different system.
- Each one is also a defensible position: you can say *why* it is excluded, which is the point.

**The three write patterns, since only one is a non-goal**

| Pattern | What happens on a write | Strength | Weakness |
|---|---|---|---|
| Write-through | Write the database and the cache together, synchronously | Cache is never stale relative to that writer | Every write pays cache latency too; caches data nobody reads |
| Write-around | Write only the database; let the next read populate the cache | Write-heavy keys never pollute the cache | The next read after a write is always a miss |
| Write-back | Write only the cache; flush to the database later | Fastest writes; absorbs bursts | A crash loses acknowledged writes, so the cache must be durable |

- This design is effectively write-around plus explicit invalidation, and write-back is a stated non-goal.

## Capacity and consequence — IC3 baseline

- The rule for this whole section: an estimate that does not change a decision is noise. Delete it.
- Each estimate below ends with the decision it forces, and that final line is the part that earns points.

### Memory estimate

> Assume `1 KB` value and `200 B` combined key/node overhead.

**What this says in plain words**

- One cached entry is not just the value. It is the value plus the machinery around it.
- The breakdown of the 200 B of overhead, roughly:
  - The key string itself, for example `tenant-17:user:42`, at around 40 B.
  - The node object header and its four or five fields: `key`, `value`, `prev`, `next`, `expiry`,
    `generation`.
  - The hash-map entry that points at the node.
- 1 KB for the value is a stated assumption: a serialised user record or a small configuration blob.

**Why it matters**

- Engineers routinely size caches by value bytes only and are then surprised by 20% extra heap.
- At 100,000 entries the 200 B overhead is 20 MB, which is not a rounding error.

> `100,000 × 1.2 KB ≈ 120 MB` before table slack and JVM/allocator overhead.

**What this says in plain words**

1. The arithmetic: `100,000 × 1.2 KB = 120,000 KB ≈ 117 MB`, rounded to 120 MB.
2. **Table slack** is the empty space a hash map keeps so collisions stay rare.
   - A hash map that is 100% full degenerates: lookups start scanning.
   - Typical load factor is 0.75, so an array of about 131,072 slots backs 100,000 entries.
   - Those extra slots are real memory: about 31,000 unused reference slots, roughly 0.25 MB at 8 B each,
     plus the array itself.
3. **JVM and allocator overhead** is the per-object header and the padding the runtime adds.
   - On a 64-bit JVM an object header is around 12 to 16 B, and objects are padded to 8-byte boundaries.

**Why it matters**

- The honest number is "120 MB plus overhead", not "120 MB".
- If your container limit is 128 MB, this cache alone will kill it, and the arithmetic that said 120 MB
  looked fine.

> Object layout depends on runtime configuration.
> Measure retained heap rather than treating this estimate as a JDK constant.

**What this says in plain words**

1. **Object layout is not fixed.** It changes with flags and heap size.
   - Compressed object pointers (**compressed oops**) store references in 4 B instead of 8 B, and the JVM
     turns them off automatically above roughly 32 GB of heap.
   - Turning them off can grow the same object graph by tens of percent with no code change.
2. **Retained heap** is the memory that would be freed if this object were released, including everything
   only it points to.
   - It is the number that matters. **Shallow size**, the object's own bytes, is not.
3. So: measure with a heap profiler; do not trust the estimate as a constant.

**Worked example**

- A 100,000-entry cache measured at 118 MB retained on a 16 GB heap with compressed oops on.
- The same service is moved to a 64 GB heap for an unrelated reason, and compressed oops turn off.
- Every reference grows from 4 B to 8 B. With roughly 6 references per entry, that is 24 B extra per entry.
- `100,000 × 24 B = 2.4 MB` from references alone, plus header growth and repadding, which realistically
  lands around 10 to 15% total growth.
- Nobody changed the cache. The capacity that fit now does not.

> Decision: an entry-count cap alone does not bound heap
> Add a byte weight and a maximum entry size once values are not uniform.

**What this says in plain words**

1. **Counting entries bounds the count, not the memory.** It is only a memory bound if every entry is the
   same size.
2. Two mechanisms fix it.
   - A **byte weight** per entry, with the capacity expressed in bytes.
   - A **maximum entry size**, so one huge value cannot be admitted at all.

**Worked example of why the maximum entry size is separate**

- Byte budget: 120 MB. Entry limit: none.
- A caller stores one 200 MB value.
  - Without a maximum entry size, the cache accepts it, then evicts *every other entry* trying to get under
    budget, and still exceeds it.
  - The cache is now one entry, 200 MB, over budget, with a 0% hit rate for everyone else.
- With `max_entry_bytes = 4 MB`, the 200 MB value is rejected at the door.
  - The caller gets an error and fetches directly from the origin.
  - The cache keeps its 120,000 small entries and its 95% hit rate.

**Why it matters**

- This is the decision line. The 120 MB estimate exists only to produce it.

### Origin impact

> At `100,000 reads/s` and `95%` hit rate, origin receives `5,000 reads/s`.

**What this says in plain words**

- **Hit rate** is the fraction of reads answered from the cache.
- The arithmetic: `100,000 × (1 − 0.95) = 5,000` reads per second reach the database.

**Why it matters — the sensitivity is the real lesson**

| Hit rate | Reads reaching the origin, out of 100,000/s | Change versus 95% |
|---|---|---|
| 99% | 1,000/s | 5× less |
| 95% | 5,000/s | baseline |
| 90% | 10,000/s | 2× more |
| 80% | 20,000/s | 4× more |
| 50% | 50,000/s | 10× more |

- A hit rate dropping from 95% to 90% sounds like a 5-point dip. It doubles database load.
- That non-linearity is why hit rate is the first metric to alarm on, ahead of latency.

> A cold cache may send `100,000 reads/s` to the origin.

**What this says in plain words**

- **Cold** means empty: right after a process restart or a deployment.
- The hit rate is 0%, so every single read is a miss, and every miss becomes an origin call.
- The database briefly sees 20× its steady-state load.

**Worked example across a fleet**

- 40 service instances, each serving 2,500 reads/s, so 100,000 reads/s total.
- A rolling deploy restarts them in 4 batches of 10.
- Each batch of 10 comes back cold and, for its warm-up window, sends its full 25,000 reads/s to the
  database instead of 1,250 reads/s.
- If the database can serve 20,000 reads/s, a single batch of 10 instances is enough to saturate it.
- The classic outcome: the deploy "causes" a database outage, and the deploy is blamed rather than the
  missing admission control.

> Admission control and gradual warming matter more than a perfect eviction policy during restart.

**What this says in plain words**

1. **Admission control** means limiting how much work is allowed to start, rather than accepting everything
   and hoping. The 128-flight semaphore is admission control.
2. **Gradual warming** means filling the cache deliberately and slowly rather than by absorbing a traffic
   spike.
   - Load the top 5,000 keys by past popularity at a bounded rate before taking full traffic.
   - Or return the instance to the load balancer at 10% traffic weight and ramp it over 5 minutes.
3. **The eviction policy is irrelevant when the cache is empty.** With 0 entries there is nothing to evict,
   so the choice between LRU, LFU and CLOCK has no effect during exactly the window that hurts most.

**Why it matters**

- Candidates love to optimise eviction policy. It is the intellectually interesting part.
- The outage happens during the window when eviction policy does nothing at all.

> Decision: single-flight per key plus a `128`-flight cap is mandatory, not an optimization
> The cold-start number is what breaks the origin.

**What this says in plain words**

1. Single-flight is not a nice-to-have. Without it the system has a known failure mode on every deploy.
2. The two mechanisms cover two different shapes of the problem.
   - Single-flight handles **one hot key** missed by many threads.
   - The 128-flight cap handles **many distinct keys** missed at once.
3. The cold-start number, 100,000 reads/s to the origin, is what turns "optimisation" into "requirement".

**Worked example of the two mechanisms doing different jobs**

- Scenario A, hot key: 5,000 threads all miss `config:global` in the same 10 ms window.
  - Single-flight: 1 origin call, 4,999 waiters attached to the same future.
  - The 128-flight cap contributes nothing here; there was only ever 1 distinct key.
- Scenario B, cold start: 50,000 distinct keys missed in one second.
  - Single-flight contributes nothing; every key is distinct, so there is nothing to coalesce.
  - The 128-flight cap holds concurrency at 128 and everything else queues or fails fast.
- Neither mechanism substitutes for the other. You need both.

### Throughput decision

> At `100,000 operations/s` across `32` threads, one lock must hold each critical section under roughly `10 µs` to stay below saturation

**What this says in plain words**

- The arithmetic, step by step.
  1. The lock is a serial resource: only one thread is inside it at a time.
  2. In one second there are 1,000,000 µs of lock time available.
  3. To serve 100,000 operations per second, each operation may hold the lock for
     `1,000,000 µs / 100,000 ops = 10 µs`.
  4. At exactly 10 µs the lock is 100% utilised, which in queueing terms means unbounded waiting.
  5. So 10 µs is the saturation point, and the real target must be well below it.

**Why it matters — the queueing effect**

| Critical section length | Lock utilisation at 100,000 ops/s | What the waiting looks like |
|---|---|---|
| 1 µs | 10% | Essentially no waiting |
| 2 µs | 20% | Occasional waiting, invisible |
| 5 µs | 50% | Wait time now comparable to the work itself |
| 8 µs | 80% | Wait time roughly 4× the service time |
| 10 µs | 100% | Queue grows without bound; latency runs away |

- The number of threads does not change the throughput ceiling. 32 threads or 320, the lock still serves
  one at a time.
- More threads past saturation make it *worse*, because more threads are spinning or parking and the
  operating system spends more time on context switches.

> An `O(1)` pointer update is well inside that budget.

**What this says in plain words**

- The actual work under the lock is: one hash lookup, about four pointer writes, and possibly one eviction.
- On modern hardware that is on the order of 100 ns, which is 0.1 µs.
- 0.1 µs against a 10 µs budget is 1% utilisation at 100,000 ops/s.

**Why it matters**

- It says one lock is *not* obviously wrong. It has roughly 100× headroom on paper.
- That headroom is what justifies starting simple instead of building stripes on day one.
- The caveat is that this is the *uncontended* cost. Under contention, cache-line bouncing between CPU cores
  can multiply it, which is why the next lines say "measure".

> Begin with one lock.
> Profile lock wait time under the actual key distribution.
> Stripe only when contention is the measured bottleneck.

**What this says in plain words**

Three steps in order, and the order is the point.

1. **Begin with one lock.** It is correct, simple, and provably maintains the invariant.
2. **Profile lock wait time.** Not throughput, not CPU — specifically the time threads spend *waiting to
   acquire*.
   - **Lock contention** is what happens when a thread wants a lock another thread holds.
   - Measure it as the interval between requesting the lock and obtaining it.
3. **Stripe only if that wait is the bottleneck.** Under the *actual* key distribution, because a skewed
   distribution behaves nothing like a uniform one.

**Worked example of why the key distribution decides it**

- Uniform distribution: 100,000 distinct keys accessed evenly.
  - With 16 stripes, each stripe takes about 1/16 of the traffic. Contention drops roughly 16×.
- Skewed distribution: one key, `config:global`, is 40% of all reads.
  - With 16 stripes, 40% of all traffic still hashes to a single stripe.
  - That one stripe is now hotter than the original single lock was per-stripe, and the other 15 are idle.
  - Striping did nothing for the real bottleneck, and it cost you exact LRU.
- Same code, same 16 stripes, two completely different outcomes. Only measurement tells them apart.

> Decision: keep exact LRU under one lock until profiling shows lock wait in the latency budget
> Stripes trade exactness for parallelism and must be a measured choice.

**What this says in plain words**

1. The default is one lock and exact LRU.
2. The trigger for changing it is specific: lock wait time has become a visible share of the 1 ms p99 budget.
3. Stripes are a trade, not an upgrade. You are paying exact eviction order to buy parallelism.

### The lock striping arithmetic, worked out

The source mentions stripes repeatedly, so here is the number behind them.

**The setup**

- 64 threads, all hammering the cache, keys uniformly distributed.
- 16 stripes. Each stripe is an independent map plus list plus lock, holding `100,000 / 16 = 6,250` entries.
- A key is assigned to a stripe by `hash(key) % 16` — sometimes using different high bits from the hash than
  the bucket index uses, so that stripe assignment and bucket assignment do not correlate.

**Expected contention with one lock**

- 64 threads, 1 lock.
- At any instant 1 thread holds it and up to 63 are waiting.
- Expected queue length at the lock is 63 in the worst case. Every operation's latency includes the time for
  everyone ahead of it.

**Expected contention with 16 stripes**

- 64 threads spread across 16 locks is `64 / 16 = 4` threads per stripe on average.
- Expected queue length per lock drops from 63 to 3.
- Parallelism goes from 1 concurrent operation to up to 16.
- That is roughly a 16× throughput ceiling increase, and roughly a 16× drop in average wait.

**The collision probability that keeps it honest**

- Threads do not distribute themselves neatly, 4 per stripe. They land randomly.
- The chance that two specific threads pick the same stripe is `1/16 = 6.25%`.
- With 64 threads and 16 stripes, by the balls-in-bins result the busiest stripe typically holds around 8 to
  9 threads, not 4.
- So the realistic improvement is roughly 7× to 8×, not the ideal 16×.

**What you give up, concretely**

- Capacity becomes per-stripe: 6,250 entries each, not 100,000 shared.
- If one tenant's keys happen to hash into 3 stripes, those 3 stripes evict constantly at 6,250 entries each
  while the other 13 sit half empty.
- Global LRU order no longer exists. The cache can evict an entry touched 1 second ago from a hot stripe
  while keeping one untouched for 10 minutes in a cold stripe.

**The rule of thumb for choosing the stripe count**

| Stripes | Concurrency ceiling | Per-stripe capacity at 100,000 total | Wasted capacity risk |
|---|---|---|---|
| 1 | 1 | 100,000 | none; exact LRU |
| 4 | 4 | 25,000 | low |
| 16 | 16 | 6,250 | moderate; skew starts to show |
| 64 | 64 | 1,562 | high; a skewed tenant thrashes its stripes |
| 256 | 256 | 390 | severe; each stripe is too small to be useful |

- The usual guidance is stripes at roughly 2× to 4× the number of CPU cores, capped so each stripe still
  holds a useful working set.
- More stripes is not monotonically better. Past a point you are running many tiny caches, not one cache.

## Architecture and flow — IC3 baseline

### Reading the diagram

The source draws this:

```text
Cache facade
  | one lock protects both structures
  +-- hash map: key -> Node(key, value, prev, next, expiry, generation)
  +-- recency list: HEAD <-> most recent <-> ... <-> least recent <-> TAIL
  +-- in-flight loads: key -> Flight(future, captured generation)

Loader runs outside cache lock -> origin with deadline and concurrency bound

Distributed extension (cache-aside):
Service local cache -> shared cache shard -> authoritative database
Database transaction -> durable change event -> cache invalidation consumers
Ring / policy store (control plane) -> shard membership + tenant budgets -> service clients
```

**What this says in plain words, line by line**

1. **Cache facade.** A **facade** is the public object callers hold. It exposes `get`, `put`, `remove`,
   and hides the three structures behind it.
2. **One lock protects both structures.** The single most important line in the diagram. Everything under
   the facade is guarded by one lock.
3. **The hash map.** Key to `Node`. The node carries six things.
   - `key`, so eviction can find the map entry to delete.
   - `value`, the cached payload.
   - `prev` and `next`, the list pointers.
   - `expiry`, the TTL deadline.
   - `generation`, the fence counter.
4. **The recency list.** `HEAD` and `TAIL` are **sentinels**: permanent dummy nodes holding no user data.
   - Immediately after `HEAD` is the most recently used entry.
   - Immediately before `TAIL` is the least recently used entry, which is the next eviction victim.
5. **The in-flight loads map.** Key to `Flight`.
   - A **`Flight`** is the record of "somebody is already fetching this key". It holds the shared future and
     the generation captured when the load started.
6. **Loader runs outside the cache lock.** The origin call has a deadline and a concurrency bound.
7. **Distributed extension.** Three separate flows.
   - Read path: local cache, then shared cache shard, then the authoritative database.
   - Invalidation path: a database transaction produces a durable change event, which invalidation
     consumers turn into cache deletes.
   - Control plane: the ring and policy store tells clients which shard owns which key and what each
     tenant's budget is.

### Why the map and the list are both required

This is the central data-structure argument, so it gets a full walkthrough.

**Each structure alone fails at exactly one thing**

| Structure alone | What it does well | What it cannot do |
|---|---|---|
| Hash map only | Find a value by key in `O(1)` | Tell you which entry is least recently used; the map has no order at all |
| Doubly linked list only | Maintain order, move a *known* node in `O(1)` | Find the node for a key without scanning, which is `O(N)` |
| Array or `ArrayList` | Cheap to index | Removing from the middle shifts everything after it, which is `O(N)` |
| Singly linked list | Maintain order with less memory | Unlinking a node needs its predecessor; finding it is `O(N)` |

- The hash map contributes **identity**: key to node, in one step.
- The doubly linked list contributes **order**: move any node to the front in constant pointer work.
- Combined, both operations are `O(1)`, and neither structure could give you both alone.

**Why singly linked does not work, in detail**

- To unlink node `X` you must set `predecessor.next = X.next`.
- A singly linked node knows `X.next` but not its predecessor.
- Finding the predecessor means walking from `HEAD`, which is `O(N)`. At 100,000 entries that is up to
  100,000 steps on a cache hit, which destroys the whole point.
- A doubly linked node knows `X.prev` directly, so unlinking is:

```text
X.prev.next = X.next
X.next.prev = X.prev
```

- Two writes, no search, regardless of cache size.

**Worked example: capacity 3, tracing every operation**

Starting state: empty. Notation is most-recent-first, so `[C, B, A]` means `C` is newest and `A` is the next
eviction victim.

| # | Operation | Map after | List after (most recent first) | What happened inside |
|---|---|---|---|---|
| 1 | `put(A, 1)` | `{A}` | `[A]` | New node, inserted after `HEAD`. Size 1 of 3. |
| 2 | `put(B, 2)` | `{A, B}` | `[B, A]` | New node after `HEAD`. `A` slides toward the tail. Size 2 of 3. |
| 3 | `put(C, 3)` | `{A, B, C}` | `[C, B, A]` | New node after `HEAD`. Size 3 of 3. Cache is now full. |
| 4 | `get(B)` | `{A, B, C}` | `[B, C, A]` | Map finds `B` in one step. Unlink `B` from the middle, relink after `HEAD`. **Note the list changed on a read.** |
| 5 | `get(A)` | `{A, B, C}` | `[A, B, C]` | Same: found by map, moved to front. `C` is now the victim. |
| 6 | `put(D, 4)` | `{A, B, D}` | `[D, A, B]` | Size would be 4. Victim is `TAIL.prev` = `C`. Unlink `C`, delete key `C` from the map, then insert `D`. |
| 7 | `get(C)` | `{A, B, D}` | `[D, A, B]` | Miss. `C` was evicted at step 6. No list change on a miss. |
| 8 | `put(A, 99)` | `{A, B, D}` | `[A, D, B]` | `A` exists. Overwrite the value, move the node to the front. **Size stays 3; no eviction.** |
| 9 | `get(B)` | `{A, B, D}` | `[B, A, D]` | Hit; moved to front. `D` is now the victim even though it was inserted most recently at step 6. |
| 10 | `put(E, 5)` | `{A, B, E}` | `[E, B, A]` | Victim is `D`. Insert `E`. |

**The three lessons in that trace**

1. **Step 4 and step 5 are reads that mutate shared state.** This is the whole reason a read-write lock fails.
2. **Step 8 does not evict.** Replacing an existing key must not grow the size. Getting this wrong is the
   most common LRU implementation bug.
3. **Step 9 to step 10 shows recency beating insertion order.** `D` was inserted more recently than `B`,
   but `B` was *touched* more recently, so `D` dies first. LRU tracks access, not age.

**The pointer work for step 4, spelled out**

- Before: `HEAD <-> C <-> B <-> A <-> TAIL`.
- Unlink `B`:
  - `B.prev.next = B.next`, so `C.next = A`.
  - `B.next.prev = B.prev`, so `A.prev = C`.
  - List is now `HEAD <-> C <-> A <-> TAIL`, with `B` detached.
- Insert `B` after `HEAD`:
  - `B.prev = HEAD`.
  - `B.next = HEAD.next`, which is `C`.
  - `HEAD.next.prev = B`, so `C.prev = B`.
  - `HEAD.next = B`.
- Six pointer writes. Zero searching. Identical cost at 10 entries or 100,000.

### Component ownership

> Cache facade owns the map/list invariant.
> Mechanism bought: one lock makes every public operation linearizable over both structures.
> Cost paid: every hit serializes on that lock until stripes are added.

**What this says in plain words**

1. **The facade owns the invariant.** One object is responsible for map and list agreeing. Nothing else may
   touch them.
2. **The mechanism bought is linearizability.**
   - **Linearizable** means every operation appears to take effect at one single instant, and all threads
     agree on the order.
   - Concretely: if `put(A, 1)` returns before `get(A)` starts, `get(A)` returns 1. Always. No exceptions.
3. **The cost paid is serialisation.** Every hit takes the lock, so throughput is capped by one lock.

**Why the "mechanism bought / cost paid" shape matters**

- Every component in this design states both. A design where every component is pure upside is a design
  where you have not thought about the downside yet.
- An interviewer specifically listens for the cost sentence.

> Loader owns origin access.
> Mechanism bought: runs outside the lock with a deadline, so a slow origin never blocks hits.
> Cost paid: the result can be stale on return, so publication must be fenced by generation.

**What this says in plain words**

1. All origin access goes through the loader. The cache itself never opens a connection.
2. The mechanism bought: a 5-second database stall does not stop other keys being served from memory.
3. The cost paid: by running outside the lock, the loader loses all guarantees about what happened while it
   was away, so its result must be re-validated before installation.

**Worked example of the benefit**

- With the loader inside the lock: one 5,000 ms database stall blocks the lock for 5,000 ms.
  - All 32 threads pile up. Zero cache operations complete for 5 seconds.
  - The cache, whose job is to survive origin problems, has become the amplifier of them.
- With the loader outside the lock: the stalled thread waits on a future.
  - The other 31 threads keep taking and releasing the lock at about 0.1 µs each.
  - Roughly 5,000,000 other cache operations complete during that same stall.
- Same stall. Two completely different service outcomes.

> Shared cache shard owns cross-instance reuse.
> Mechanism bought: one origin load serves many instances
> Hit rate survives instance restarts.
> Cost paid: a network hop on every local miss and a second place where stale values live.

**What this says in plain words**

1. **Cross-instance reuse.** When instance 7 loads a value, instances 1 to 40 can all use it.
2. **Hit rate survives restarts.** Instance 7 restarting empties only *its* local cache. The shared tier
   still holds everything, so instance 7 warms up from the shared tier at microseconds per key instead of
   from the database at milliseconds per key.
3. **Cost one: a network hop.** A local hit is roughly 100 ns. A shared-tier hit is roughly 500 µs including
   the round trip. That is about 5,000× slower, though still 10× to 100× faster than the database.
4. **Cost two: a second staleness location.** You now have two copies of every value that can be wrong, and
   invalidating one does not invalidate the other.

**Worked example of the restart benefit**

- No shared tier: instance 7 restarts cold with 2,500 reads/s. All 2,500 go to the database until it warms.
  Warming 100,000 entries at a bounded 128 concurrent loads of 20 ms each takes
  `100,000 / (128 / 0.02) ≈ 15.6 seconds` of degraded service.
- With a shared tier: instance 7's misses go to the shared tier, which already holds them.
  - The database sees roughly zero extra load.
  - The shared-tier round trip is 500 µs, so the user-visible impact is added latency, not an outage.

**Worked example of the second-staleness cost**

- The database updates row `user:42` at `t = 0`.
- The invalidation consumer deletes the key from the shared tier at `t = 2 s`.
- Instance 12's *local* cache still holds the old value, with 25 seconds of TTL left.
- Instance 12 serves the stale value until `t = 27 s`, long after the shared tier was corrected.
- Two cache layers means two staleness windows, and they do not expire together.

> Authoritative database plus change-event stream owns truth and invalidation.
> Mechanism bought: commit-then-invalidate with durable delivery bounds how long a stale copy survives.
> Cost paid: invalidation is asynchronous, so a stale read is possible for a bounded window.

**What this says in plain words**

1. **The database is authoritative.** When the cache and the database disagree, the database is right by
   definition.
2. **Commit-then-invalidate is an ordering rule.** Commit the transaction first, *then* send the
   invalidation. Never the other way round.
3. **Durable delivery** means the change event is persisted, so a consumer that crashes can re-read it
   rather than losing it.
4. **The cost is asynchrony.** The invalidation takes time to arrive, so there is a window where the cache
   is knowingly wrong.

**Why the order "commit then invalidate" matters, as a step table**

Invalidate-then-commit, the wrong order:

| Step | Writer thread | Reader thread | Cache state |
|---|---|---|---|
| 1 | Deletes `user:42` from the cache | — | Empty for that key |
| 2 | — | `get(user:42)` misses, calls the loader | Empty |
| 3 | — | Loader reads the database, sees the **old** value | Empty |
| 4 | — | Installs the old value into the cache | Old value cached |
| 5 | Commits the new value to the database | — | Old value cached, database has the new one |

- The cache now holds the old value with a full TTL ahead of it, and no further invalidation is coming,
  because the invalidation already happened at step 1.
- The stale window is not "a few seconds". It is the full TTL, and after a lost invalidation it can be
  indefinite.

Commit-then-invalidate, the right order:

| Step | Writer thread | Reader thread | Cache state |
|---|---|---|---|
| 1 | Commits the new value to the database | — | Old value still cached |
| 2 | — | `get(user:42)` hits, returns the old value | Old value cached |
| 3 | Publishes the change event | — | Old value cached |
| 4 | — | — | Consumer deletes the key |
| 5 | — | `get(user:42)` misses, loads, sees the **new** value | New value cached |

- The stale window is bounded by the delivery lag, typically 2 seconds, and it self-heals.
- This still is not airtight: the reader's loader at step 5 could have started before step 1 and return
  later with the old value. That is exactly the race the generation and source-version fences close, and it
  is covered in [section 7](#e103-7).

> Ring and policy store is the control plane.
> Mechanism bought: shard membership and tenant budgets change without redeploying clients.
> Cost paid: clients must cache the last-known ring so the data plane keeps serving when this store is down (static stability).

**What this says in plain words**

1. **Control plane versus data plane.**
   - The **data plane** is the path a user request takes: client, cache, database, response.
   - The **control plane** is the path configuration takes: "there are now 12 shards, not 10".
   - They must fail independently. Control-plane death must not stop the data plane.
2. **The ring** is the map from key-hash to cache node. Changing it adds or removes cache servers.
3. **Tenant budgets** are the per-tenant byte caps.
4. **The mechanism bought** is dynamic reconfiguration: change the shard count without a code deploy.
5. **The cost paid** is that clients must keep a local copy of the last-known ring.

**What static stability means, concretely**

- **Static stability** is the property that a system keeps working, in its current configuration, when the
  thing that *changes* the configuration is unavailable.
- The test question: "the ring store has been down for 2 hours. What is broken?"
  - Correct answer: nothing user-visible. Clients serve on the last ring they saw. You cannot *change* the
    shard count, but you also probably were not trying to.
  - Wrong answer: every cache lookup fails, because clients ask the ring store which shard to use on every
    request.
- The wrong design turns a configuration-store outage into a total outage. That is a control-plane
  dependency in the data path, and it is one of the most common real-world availability bugs.

### Complexity claims

> A hash lookup returns the node directly.
> Unlinking a known doubly linked node costs constant pointer work.
> Searching a list for the key would cost `O(N)`.

**What this says in plain words**

1. The map hands you the node object itself, not a copy and not an index.
2. Because you hold the node, and it knows both neighbours, unlinking is two pointer writes.
3. Without the map you would scan the list, which at 100,000 entries averages 50,000 comparisons per hit.

**The numbers**

| Approach | Work per hit at 100,000 entries | Rough time |
|---|---|---|
| Map lookup plus pointer surgery | 1 hash, 1 compare, ~6 pointer writes | ~100 ns |
| List scan plus pointer surgery | ~50,000 compares on average | ~250 µs |

- The ratio is about 2,500×. And under one lock, 250 µs per hit caps the cache at about 4,000 operations per
  second instead of 100,000.

> Expected `get` and count-bounded `put` are `O(1)`.
> Hash-table resizing is amortized.
> Byte-weighted insertion may evict multiple entries.
> Lock waiting and loader execution are not covered by the data-structure complexity.

**What this says in plain words**

Four careful qualifications on the `O(1)` claim.

1. **"Expected" means average, not guaranteed.** A hash map is `O(1)` on average; a pathological set of
   colliding keys degrades it. Java 8 and later mitigate this by turning a long bucket chain into a balanced
   tree, making the worst case `O(log N)` rather than `O(N)`.
2. **"Amortized" covers resizing.** When the table grows past its load factor it allocates a bigger array
   and rehashes everything, which is `O(N)` for that one insert.
   - Spread over the `N` inserts that caused the growth, the average stays `O(1)`.
   - **Amortized** means "averaged over a sequence", not "always".
   - The practical consequence: one unlucky `put` can take milliseconds while the table rehashes 100,000
     entries, and it does so *inside the lock*. Pre-sizing the map to the final capacity avoids this
     entirely, and is worth doing.
3. **Byte-weighted insertion breaks the bound.** Evicting until 5 MB is free may take thousands of
   evictions, as calculated in [section 3](#e103-3).
4. **`O(1)` describes the data structure, not the wall clock.**
   - Waiting 900 µs for a lock is not counted by `O(1)`.
   - A 180 ms loader call is not counted by `O(1)`.
   - Telling an interviewer "it is `O(1)`" while the operation takes 180 ms is technically true and
     practically useless. Saying which parts the bound covers is the senior version.

### The `get` trace

> → Acquire the cache lock.
> → Find the node by key.
> → Remove and miss if it is expired.
> → Otherwise unlink and move it to the most-recent position.
> → Return the value after releasing the lock.

**What this says in plain words, step by step**

→ **Acquire the cache lock.** Nothing is read before the lock is held. Reading the map without the lock
could observe a half-updated list.

→ **Find the node by key.** One hash lookup. If absent, this is a miss and the operation ends.

→ **Remove and miss if it is expired.** Compare the node's `expiry` against the current monotonic time.
Expired means: unlink it, delete it from the map, and report a miss. This is **lazy expiration** — the entry
is removed when it is next touched, not by a timer.

→ **Otherwise unlink and move it to most-recent.** The six pointer writes shown earlier.

→ **Return the value after releasing the lock.** The value reference is captured inside the lock, but
returned to the caller after release, so no caller code runs while the lock is held.

**Why that last step is not pedantic**

- If the value were returned while still holding the lock, and the caller's code ran inline — a listener, a
  logging call, a `toString()` — that caller code would execute inside the critical section.
- Caller code can do anything: block on I/O, take another lock, call back into the cache.
- Calling back into the cache while it holds the lock is a **reentrancy** question; taking another lock in
  the opposite order from some other thread is a **deadlock**.
- The rule is simple and absolute: no foreign code inside the lock.

**Worked example of the deadlock this prevents**

- Thread A holds the cache lock and invokes a caller listener, which tries to take lock `L`.
- Thread B holds lock `L` and calls `cache.get(...)`, which tries to take the cache lock.

| Step | Thread A | Thread B | Result |
|---|---|---|---|
| 1 | Takes the cache lock | — | Cache lock held by A |
| 2 | — | Takes lock `L` | `L` held by B |
| 3 | Calls the listener, which requests `L` | — | A blocks, still holding the cache lock |
| 4 | — | Calls `cache.get`, which requests the cache lock | B blocks, still holding `L` |
| 5 | Blocked forever | Blocked forever | Deadlock; both threads are stuck |

- Neither thread can proceed and neither will time out. The service needs a restart.
- The whole class of bug disappears if no foreign code ever runs inside the lock.

## API and data model — IC3 baseline

### The operation table, row by row

> | `get(key)` | Optional value; counts as access | Idempotent for value; expiration and recency update happen under lock |

**What this says in plain words**

1. **It returns an `Optional`**, meaning "a value or nothing", rather than returning `null`.
   - Returning `null` is ambiguous: does it mean "absent" or "present, holding null"? Rejecting null values
     removes the ambiguity, and `Optional` makes it visible in the type.
2. **It counts as an access**, so it changes recency. A read is a write to the list.
3. **Idempotent for value** means calling it twice returns the same value.
   - **Idempotent** means doing it `N` times has the same effect as doing it once.
   - The value is idempotent; the *side effects* are not. Two `get` calls move the node twice and may expire
     the entry on the first call.
4. **Expiration and recency both happen under the lock**, in the same critical section as eviction.

**Why the idempotency caveat matters**

- A reviewer who reads "idempotent" and assumes "no side effects" will write a retry loop that silently
  reorders the recency list. Saying *what* is idempotent, and what is not, is the precise version.

> | `put(key, value)` | Insert or replace; counts as access | Repeat with same value is harmless; update existing entry without increasing size |

**What this says in plain words**

1. One method covers both insert and replace. There is no separate `update`.
2. A `put` is an access, so it moves the entry to most-recent.
3. Repeating the same `put` is harmless: same value, same size, only the recency position changes.
4. **Replacing must not increase size.** The key was already counted.

**What breaks without the size rule**

- Capacity 100,000, all slots used. A hot key is re-`put` 1,000 times per second.
- Buggy version: each `put` increments size to 100,001 and evicts the tail.
  - 1,000 innocent entries are evicted per second, purely because one key is being refreshed.
  - Hit rate collapses and nobody can explain why, because the eviction metric looks "normal".

> | `remove(key)` | Remove current entry and invalidate an older load | Idempotent; advances generation even if the entry is absent |

**What this says in plain words**

1. `remove` deletes the entry if present.
2. It also **invalidates any in-flight load** for that key, which is the non-obvious half.
3. It is idempotent: removing an absent key is a success, not an error.
4. **It advances the generation even when the key is absent.** This is the subtle and important part.

**Why removing an absent key must still bump the generation**

- The key is absent precisely *because* a load is in flight and has not published yet.
- If `remove` did nothing for an absent key, the in-flight loader would publish a moment later and the
  removal would be silently undone.

| Step | Time | Thread A (reader) | Thread B (remover) | Cache state |
|---|---|---|---|---|
| 1 | 0 ms | `getOrLoad(user:42)` misses; registers a `Flight` capturing generation 7 | — | Absent; flight registered |
| 2 | 5 ms | Loader is out at the database | — | Absent |
| 3 | 20 ms | — | `remove(user:42)`; key is absent | Absent |
| 4a | 20 ms | — | **Buggy:** returns early, generation stays 7 | Absent |
| 5a | 180 ms | Loader returns; generation still 7, so it publishes | — | **Deleted value is back in the cache** |
| 4b | 20 ms | — | **Correct:** bumps generation to 8 | Absent, generation 8 |
| 5b | 180 ms | Loader returns; captured 7, current is 8, so it discards | — | Still absent; removal held |

- The buggy path resurrects deleted data for a full TTL. If the removal was a GDPR deletion or a permission
  revocation, that is a compliance or security incident, not a cache miss.

> | `getOrLoad(key, loader)` | Coalesce one in-flight load per key | Joins the existing flight; loader deadline and shared-future cancellation policy |

**What this says in plain words**

1. **`getOrLoad`** is the combined operation: return the cached value, or fetch it if absent.
2. **Coalesce** means: if a fetch for this key is already running, do not start a second one. Attach to the
   first.
3. **Cancellation policy** is the part most implementations get wrong.
   - One waiter timing out must not cancel the shared future.
   - If it did, the one impatient caller would fail the other 4,999 waiters who were happy to wait.
   - So the *waiter's* timeout is local to that waiter; only the flight's own deadline cancels the work.

> | `clear()` | Clear entries and invalidate old load generations | Idempotent; a cache epoch fences all outstanding loads |

**What this says in plain words**

1. `clear` empties the cache.
2. It must also invalidate every outstanding load, not just the stored entries.
3. Bumping every key's generation one by one would be `O(N)` over potentially 100,000 keys, inside the lock.
4. Instead there is one **cache epoch** counter for the whole cache. `clear` increments it once.
   - Every `Flight` captures the epoch at registration.
   - On publication a flight compares both its generation and its epoch.
   - One integer increment invalidates every outstanding load at once.

**The numbers**

- Per-key bumping: 100,000 map writes inside the lock, roughly 5 to 10 ms of blocked cache.
- Epoch bumping: 1 write, well under 1 µs.
- Same guarantee, four orders of magnitude cheaper.

> | `stats()` | Approximate counters are acceptable | Do not claim a globally atomic snapshot without locking |

**What this says in plain words**

1. Hit counts, miss counts and eviction counts are maintained as cheap counters.
2. They are read without the lock, so the numbers may not be mutually consistent at one instant.
3. Claiming a consistent snapshot would require taking the lock for the duration of the read, which makes
   observability itself a source of contention.

**Why it matters**

- `hits + misses` may not exactly equal the operation count at any instant. That is fine for a metric you
  graph over a 60-second window.
- It would not be fine for billing. Knowing which of your numbers need to be exact is the point.

> | `PUT /caches/{ns}/entries/{key}` (shared tier) | Value, absolute `expiresAt`, optional expected `source_version` | Version mismatch returns `409`; absolute expiry keeps a retry from extending TTL |

**What this says in plain words**

Three design choices are packed into this row.

1. **`expiresAt` is absolute, not a relative TTL.**
   - The request carries "expires at 12:00:30", not "expires in 30 seconds".
   - **What breaks with a relative TTL:** the client sends the write, it times out at the client after 29 s,
     and the client retries. The server applies a fresh 30 s. The entry now lives 59 s, not 30 s. Every
     retry extends the staleness window, and a retry storm can extend it indefinitely.
   - With an absolute timestamp, retrying is harmless: the same instant is written again.
2. **`source_version` is an optional precondition.**
   - The writer says "install this only if the stored version is still 41".
   - This is **compare-and-swap** at the API level: read a version, compute, write only if the version is
     unchanged.
3. **A mismatch returns `409 Conflict`.**
   - `409` means "your assumption about the current state was wrong".
   - The correct client response is to re-read and recompute, not to retry the identical request. Retrying
     the same request will conflict again forever.

**Worked example of the version check earning its keep**

- Row `user:42` is at `source_version = 41`.
- Instance A's loader read version 41 at `t = 0`, and its network path is slow.
- At `t = 50 ms` the row is updated to version 42, and instance B writes version 42 to the shared tier.
- At `t = 200 ms` instance A tries to write its version-41 value.
  - Without the check: version 41 overwrites version 42. Every reader now sees the older value.
  - With the check: instance A sent "expected version 41", the stored version is 42, so the tier returns
    `409` and the stale write is rejected.

> | `DELETE /caches/{ns}/entries/{key}` (shared tier) | Invalidate | Idempotent; absent key returns `204` |

**What this says in plain words**

1. Deleting invalidates the shared copy.
2. Deleting an absent key returns `204 No Content`, a success.
3. That is what makes invalidation retryable: the consumer can redeliver the same delete ten times safely.

**Why `404` would be the wrong answer**

- Invalidation consumers retry on failure. With **at-least-once delivery**, duplicates are normal.
- If a duplicate delete returned `404`, every consumer would need logic to distinguish "harmless duplicate"
  from "real problem", and someone would eventually alert on it.
- Returning `204` makes the retry path trivially correct.

### The keyed state table

> | Node | `key` in the local map | Value, prev, next, expiry, generation; sentinels never hold user values |

- Every field earns its place.
  - `key`: eviction arrives via the list and needs the key to delete the map entry.
  - `value`: the payload.
  - `prev` and `next`: recency position.
  - `expiry`: the TTL deadline, as a monotonic timestamp.
  - `generation`: the fence counter for that key.
- Sentinels are `Node` objects too, but they hold no key and no value, and they are never eviction candidates.

> | Flight | `key` in the in-flight map | Shared future, captured generation, captured cache epoch; removed on success and error |

- The `Flight` is how a second caller finds an existing load instead of starting a duplicate.
- It captures *two* fences.
  - The per-key generation, which `put` and `remove` bump.
  - The cache-wide epoch, which `clear` bumps.
- It is removed on both success and failure. Forgetting the failure path is a real leak: a failed flight
  left in the map blocks all future loads of that key forever, because every caller joins a future that
  already failed.

> | Generation | `key` | Advanced by `put` and `remove`; tombstone retained only while a flight can still reference it |

- A **tombstone** is a record that something used to exist.
- Here the tombstone is the generation counter for a key with no live entry.
- It must outlive the entry, because a flight registered before the removal may still return and needs
  something to compare against.
- It must not be kept forever, or the generation map grows without bound and becomes its own memory leak.
- The retention rule: keep it while any flight could still reference it, which is bounded by the 200 ms
  loader deadline plus a safety margin.

> | Shared entry | `(tenant, namespace, key_hash)` | Bytes, `source_version`, `expires_at`; disposable |

- The shared-tier key is a triple, and each part does a job.
  - `tenant` gives isolation: tenant A cannot name tenant B's entry.
  - `namespace` separates data classes within one tenant, each with its own TTL and budget.
  - `key_hash` is the actual lookup key, hashed so key length is bounded and the original key is not exposed.
- `source_version` is what makes conditional writes possible.
- `expires_at` is absolute, for the reason given above.
- "Disposable" repeats the non-goal: losing it costs latency, not data.

> | Ring metadata | `ring_version` | Token to node mapping; clients keep the last-known version |
> | Tenant policy | `(tenant, namespace)` | `maxBytes`, `maxEntryBytes`, `defaultTtl`; versioned |

- These two are the only relational state in the entire design, which is why they are the only tables in
  the DDL.
- Clients keeping the last-known ring version is the static-stability mechanism from
  [section 4](#e103-4): the data plane does not stop when the control plane does.

### The reference DDL

> Nodes, flights, generations, and shared entries live in process or cache-node memory; only the tenant policy and the ring directory are relational.

**What this says in plain words**

- Most of this system's state is deliberately *not* in a database.
- Saying that explicitly is required by the authoring rules, and it is also the honest answer: inventing
  tables for the LRU list would be fiction.

Now the two tables that do exist.

```sql
CREATE TABLE cache_namespace_policies (
  tenant_id text NOT NULL, namespace text NOT NULL,
  max_bytes bigint NOT NULL CHECK (max_bytes > 0),
  max_entry_bytes integer NOT NULL CHECK (max_entry_bytes > 0),
  default_ttl_ms integer NOT NULL CHECK (default_ttl_ms > 0),
  version bigint NOT NULL CHECK (version > 0),
  updated_at timestamptz NOT NULL,
  PRIMARY KEY (tenant_id, namespace),
  CHECK (max_entry_bytes <= max_bytes)
);
```

**What each line buys**

1. **`PRIMARY KEY (tenant_id, namespace)`** is a composite, tenant-first key.
   - Tenant-first means every query is naturally scoped to one tenant, and a missing tenant filter is a
     syntax-level mistake rather than a silent cross-tenant read.
2. **`CHECK (max_bytes > 0)`** stops a budget of 0, which would mean a cache that can hold nothing while
   still doing all the work.
3. **`CHECK (max_entry_bytes > 0)`** likewise.
4. **`CHECK (max_entry_bytes <= max_bytes)`** is the interesting one.
   - It encodes an invariant *between two columns*: one entry may never be allowed to exceed the whole
     budget.
   - Without it, an operator could set `max_entry_bytes = 500 MB` inside a `max_bytes = 120 MB` namespace.
     Every admitted large value would immediately evict the entire namespace.
   - The database refuses the impossible configuration, so no code needs to defend against it.
5. **`version bigint`** is the **If-Match validator**.
   - **If-Match** is the HTTP header carrying "I expect the current version to be X".
   - It is the same compare-and-swap idea as `source_version`, applied to configuration.
   - It stops two operators overwriting each other's policy edits.

```sql
CREATE TABLE cache_rings (
  ring_version bigint NOT NULL,
  state text NOT NULL CHECK (state IN ('STAGED','ACTIVE','RETIRED')),
  created_at timestamptz NOT NULL, activated_at timestamptz,
  PRIMARY KEY (ring_version),
  CHECK ((state = 'STAGED') = (activated_at IS NULL))
);
CREATE UNIQUE INDEX cache_rings_one_active ON cache_rings (state) WHERE state = 'ACTIVE';
```

**What each line buys**

1. **`ring_version` is monotonic.** Clients compare versions to decide whether their cached ring is stale.
2. **The three states** describe a ring's lifecycle: built but not live, live, replaced.
3. **`CHECK ((state = 'STAGED') = (activated_at IS NULL))`** is a two-way consistency check.
   - A staged ring must have no activation time.
   - A non-staged ring must have one.
   - Written as an equality between two booleans, it enforces both directions in a single clause.
4. **`cache_rings_one_active`** is a **partial unique index**: unique only over rows where
   `state = 'ACTIVE'`.
   - Effect: at most one ring can be active, enforced by the database.
   - **What breaks without it:** two rings both marked `ACTIVE` during a botched rollout. Half the clients
     read ring 11, half read ring 12, and the two rings disagree about which node owns key `user:42`.
     Writes land on one node and reads on another, so the shared tier appears to lose data.
   - This is one line of DDL preventing a genuinely painful production incident.

```sql
CREATE TABLE cache_ring_tokens (
  ring_version bigint NOT NULL, token bigint NOT NULL,
  node_id text NOT NULL, endpoint text NOT NULL,
  PRIMARY KEY (ring_version, token),
  FOREIGN KEY (ring_version) REFERENCES cache_rings
);
CREATE INDEX cache_ring_by_node ON cache_ring_tokens (ring_version, node_id);
```

**What each line buys**

1. **A token is a position on the hash ring.** Consistent hashing is explained in [section 7](#e103-7);
   for now, a token is a number on a circle, and each node owns several of them.
2. **`PRIMARY KEY (ring_version, token)`** means no two nodes can claim the same position in the same ring.
   - Two owners for one position is an ambiguous routing decision, and different clients would resolve it
     differently.
3. **The foreign key** stops tokens existing for a ring that was never created.
4. **`cache_ring_by_node`** is an access-path index: "show me every token owned by node 7".
   - That is exactly the query you run when decommissioning a node, and without the index it is a full scan
     of every token in the ring.

> The ring tables are cluster-wide, not tenant-scoped, because tokens map to shared nodes; tenant isolation comes from the policy row and the scoped key, not from the ring.

**What this says in plain words**

1. The ring has no `tenant_id`, and that is deliberate, not an oversight.
2. The physical nodes are shared infrastructure. There is no "tenant 17's ring".
3. Isolation is enforced in two other places.
   - The policy row caps how much a tenant may store.
   - The key itself starts with the tenant id, so lookups cannot cross tenants.

**Why calling this out matters**

- The authoring rules require tenant-scoped keys, so a table without one looks like a mistake.
- Explaining *why* the exception is correct, and naming where isolation actually lives, is the difference
  between an oversight and a decision.

> The companion keeps `ring_version -> [(token, node_id, endpoint)]` as text metadata; it is split here into `cache_rings` and `cache_ring_tokens` so a staged ring can be validated before the single `ACTIVE` row changes.

**What this says in plain words**

1. A sibling document models the ring as one row with a blob of text.
2. This file splits it into two tables, and says so rather than letting the two documents quietly disagree.
3. The reason for splitting: with real rows you can insert a staged ring, run validation queries against it,
   and only then flip the active flag.
   - With a text blob, "validation" means parsing a string in application code, and the database can enforce
     nothing.

### State ownership notes

> `Node` owns the key required for map removal on eviction.

- Eviction starts from the list: the victim is `TAIL.prev`.
- Having found the node, you must also delete it from the map, and that needs the key.
- If the node did not store its key, you would have to scan the map for the value that matches the node,
  which is `O(N)` and turns eviction from constant time into a 100,000-entry scan.
- This is the answer to pushback Q1 in section 11 — *not yet written*.

> Sentinels never contain user values and are never evicted.

- If `TAIL.prev` is `HEAD`, the list is empty and there is nothing to evict.
- Forgetting that check evicts the `HEAD` sentinel, which detaches the entire list from its anchors and
  corrupts every subsequent operation.

> Immutable values are the default contract.
> Returning a mutable value does not make mutations to that object thread-safe.

- This restates the requirement from [section 2](#e103-2) at the point where the API is defined, because
  this is where callers actually read it.
- The cache guarantees safe *publication*: a value stored by one thread is fully visible to another.
- It guarantees nothing about what happens to the object afterwards.

> An access-ordered `LinkedHashMap` can supply the same basic ordering.
> It still requires external synchronization for concurrent structural access.
> Access-order `get` changes its ordering structure.

**What this says in plain words**

1. **`LinkedHashMap`** is a Java class that already is a hash map plus a linked list.
   - Constructed with `accessOrder = true`, a `get` moves the entry to the end, which is LRU ordering.
   - Overriding `removeEldestEntry` gives automatic eviction at a size bound.
   - You can write a working single-threaded LRU cache in about 8 lines with it.
2. **It is not thread-safe**, so you still need your own lock around it.
3. **Its `get` is structurally modifying** in access-order mode, which has a concrete consequence:
   iterating while another thread calls `get` throws `ConcurrentModificationException`. Even a "read-only"
   iteration is unsafe.

**When to mention it in the interview**

- Mention it after implementing the structure by hand, never instead of it.
- The question is testing whether you can build the mechanism. Naming the library version afterwards shows
  practical judgement; leading with it reads as avoiding the question.

## LRU algorithm and thread safety — IC3 baseline

### The pseudocode, unpacked

The source gives this:

```text
PUT(key, value), under the cache lock:
    validate capacity, key, value, and entry size
    advance key generation for every explicit put, including absent keys
    if key exists:
        replace value
        unlink its node and add it after HEAD
        preserve the generation already advanced at operation entry
        return
    create node, insert into map, add after HEAD
    if size exceeds capacity:
        victim = TAIL.prev
        unlink victim
        remove victim.key from map
```

**Line by line**

> PUT(key, value), under the cache lock:

- Everything below runs with the lock held. There is no point in the body where the lock is released and
  retaken.
- That single property is what makes the invariant hold: no other thread can observe any intermediate state.

> validate capacity, key, value, and entry size

- Validation happens *first*, before any structure is touched.
- Four checks: capacity is positive, the key is non-null, the value is non-null, and the value is not larger
  than `max_entry_bytes`.
- **Why validation must come first:** if you insert and then discover the value is 200 MB, you have already
  mutated the map and list and must now unwind. Unwinding is where bugs live. Rejecting at the door needs no
  unwind.

> advance key generation for every explicit put, including absent keys

- This is the fence being armed.
- **"Every explicit put"** means a `put` from a caller, as opposed to a publication from a loader. A loader
  publishing its result does *not* bump the generation; it only checks it.
- **"Including absent keys"** is the same subtlety as `remove`: the key may be absent precisely because a
  load is in flight, and that load must be invalidated.

**Worked example**

| Step | Time | Thread A (loader) | Thread B (writer) | Generation | Cache |
|---|---|---|---|---|---|
| 1 | 0 ms | `getOrLoad(k)` misses, registers flight, captures gen 12 | — | 12 | absent |
| 2 | 30 ms | at the database | `put(k, "new")` | 13 | `"new"` |
| 3 | 180 ms | returns `"old"`; captured 12, current 13 | — | 13 | `"new"` retained |

- Without the bump at step 2, step 3 would install `"old"` over `"new"`.

> if key exists: replace value / unlink its node and add it after HEAD / preserve the generation already advanced at operation entry / return

- Three things happen and one thing deliberately does not.
  1. The value is overwritten in place, on the existing node.
  2. The node is moved to most-recent.
  3. The generation stays at the value bumped at entry; it is not bumped a second time.
  4. **Size is not touched, and no eviction runs.** The early `return` is what guarantees that.
- The early return is the fix for the replace bug from [section 5](#e103-5): re-`put`ting a hot key 1,000
  times per second must not evict 1,000 innocent entries.

> create node, insert into map, add after HEAD

- The new-key path. Note the order: map first, then list. Under one lock the order does not matter for
  correctness, and that is precisely the point — with two locks it would.

> if size exceeds capacity: victim = TAIL.prev / unlink victim / remove victim.key from map

- Eviction is **insert-then-evict**, not evict-then-insert.
  - Size momentarily reaches `capacity + 1` inside the lock.
  - No other thread can see it, because they are all outside the lock.
  - The invariant is "size is at most capacity **when a public operation completes**", and that still holds.
- `victim = TAIL.prev` is why the list is maintained at all: the eviction candidate is found in one pointer
  dereference rather than a scan.
- `remove victim.key from map` is why the node stores its key.

**Why insert-then-evict rather than evict-then-insert**

| Order | Peak resident entries | Advantage | Disadvantage |
|---|---|---|---|
| Insert then evict | `capacity + 1` | Simple; one code path; the new entry is definitely admitted | A momentary one-entry overshoot |
| Evict then insert | `capacity` | Never overshoots, which matters under a hard byte bound | You may evict before knowing the insert will succeed |

- For an entry-count cap, a one-entry overshoot is irrelevant, so insert-then-evict wins on simplicity.
- Under a hard byte bound with 50 MB values, a 50 MB overshoot is not irrelevant, which is why
  [section 9](#e103-9) revisits this.

### The capacity-2 trace

> `put(A,1)` gives `[A]`.
> `put(B,2)` gives `[B,A]`.
> `get(A)` gives `[A,B]`.
> `put(C,3)` gives `[C,A]` and evicts `B`.
> `put(A,4)` gives `[A,C]` without another eviction.

**What this says in plain words**

| # | Operation | List after (most recent first) | Evicted | The point being made |
|---|---|---|---|---|
| 1 | `put(A,1)` | `[A]` | — | First insert; size 1 of 2 |
| 2 | `put(B,2)` | `[B, A]` | — | Second insert; `A` is now the victim |
| 3 | `get(A)` | `[A, B]` | — | **A read reordered the list.** `B` is now the victim |
| 4 | `put(C,3)` | `[C, A]` | `B` | Full, so evict `TAIL.prev` = `B`, then insert `C` |
| 5 | `put(A,4)` | `[A, C]` | — | `A` exists: overwrite, move to front, **no eviction** |

- Step 3 is the concurrency thesis in one line: a `get` wrote to shared state.
- Step 5 is the replace rule: size stayed 2.
- Step 4 shows the payoff of step 3: had `get(A)` not reordered, `A` would have been evicted instead of `B`,
  and the next `get(A)` would have missed.

### Why a read lock is insufficient

> A hit writes recency pointers.
> Two readers can corrupt the list while the map remains valid.
> `ConcurrentHashMap` protects its own structure, not the combined invariant.

**What this says in plain words**

1. **A hit writes.** Already established, but this is where it becomes an argument about lock choice.
2. **Two "readers" can corrupt the list.** Under a read lock both are admitted simultaneously, and both
   perform pointer surgery.
3. **`ConcurrentHashMap` does not help.** It guarantees the map's internal structure is never corrupted. The
   list is not part of the map, so it is outside that guarantee entirely.

### The exact race, as a step table

This is the single most important worked example in the file, so it is done twice: once for two concurrent
`get` calls, once for a `get` racing an eviction.

**Setup**

- Capacity 4. List, most recent first: `[D, C, B, A]`.
- Full pointer picture:

```text
HEAD <-> D <-> C <-> B <-> A <-> TAIL
```

- Thread A calls `get(B)`. Thread B calls `get(C)`. Both are hits. Both must move their node to the front.
- Both are admitted at once because the design wrongly used a shared read lock.

**The unlink-then-insert sequence each thread intends to run**

```text
1. n.prev.next = n.next          // unlink, first write
2. n.next.prev = n.prev          // unlink, second write
3. n.prev = HEAD                 // insert, first write
4. n.next = HEAD.next            // insert, second write
5. HEAD.next.prev = n            // insert, third write
6. HEAD.next = n                 // insert, fourth write
```

**Race one: two concurrent hits interleave**

| Step | Thread A (`get(B)`) | Thread B (`get(C)`) | Resulting pointer state |
|---|---|---|---|
| 1 | Reads `B.prev = C`, `B.next = A` | — | unchanged: `HEAD<->D<->C<->B<->A<->TAIL` |
| 2 | — | Reads `C.prev = D`, `C.next = B` | unchanged |
| 3 | `B.prev.next = B.next`, so `C.next = A` | — | `HEAD<->D<->C<->A<->TAIL`, `B` detached |
| 4 | — | `C.prev.next = C.next`, so `D.next = B` | **`D.next = B`, but `B` was just detached** |
| 5 | `B.next.prev = B.prev`, so `A.prev = C` | — | `A.prev = C`, and `C` is being detached |
| 6 | — | `C.next.prev = C.prev`, so `B.prev = D` | `B.prev = D`; `B` is detached yet points into the list |
| 7 | `B.prev = HEAD`; `B.next = D`; `D.prev = B`; `HEAD.next = B` | — | `HEAD<->B<->D<->...` |
| 8 | — | `C.prev = HEAD`; `C.next = B`; `B.prev = C`; `HEAD.next = C` | `HEAD<->C<->B<->D<->...` |

**The corrupted list after step 8**

- Walk forward from `HEAD`: `HEAD -> C -> B -> D -> B -> D -> B -> ...`
  - `D.next` was set to `B` at step 4 and never corrected, because Thread B's later writes assumed `C` was
    still between `D` and `B`.
  - Forward traversal is now an infinite loop between `D` and `B`.
- Walk backward from `TAIL`: `TAIL -> A -> C -> HEAD`.
  - `A.prev` was set to `C` at step 5, so the backward chain skips `B` and `D` entirely.
- Forward and backward traversals disagree about the list's contents. There is no consistent list any more.

**The concrete consequences**

1. **Eviction loops forever or evicts the wrong key.**
   - `victim = TAIL.prev` is `A`, which is at least a real node here, but any code that walks the list to
     count or validate spins forever between `D` and `B`.
   - A background integrity check or a metrics sweep that iterates the list never returns, pinning one CPU
     core at 100% while holding the lock.
2. **Entries become unevictable and leak.**
   - `D` is no longer reachable in the backward direction, so it will never become `TAIL.prev`.
   - It occupies a slot in the map and 1.2 KB of heap forever.
   - Repeat this race a few thousand times a day and the process runs out of memory in a week, with no
     obvious cause, because the map size looks correct.
3. **Size accounting drifts from reality.**
   - The size counter counts logical entries. The list now has an inconsistent shape.
   - The cache may believe it holds 4 entries while forward traversal finds infinitely many and backward
     traversal finds 2.
4. **The map is still perfectly valid.**
   - Every key still maps to a node. `ConcurrentHashMap` did its job flawlessly.
   - This is why "I used a `ConcurrentHashMap`" is not an answer: the corruption is entirely in the structure
     the map does not own.

**Race two: a hit racing an eviction**

- Same setup, `[D, C, B, A]`, capacity 4.
- Thread A calls `get(A)`, a hit on the least-recent entry.
- Thread B calls `put(E, 5)`, which must evict `TAIL.prev`.

| Step | Thread A (`get(A)`) | Thread B (`put(E,5)`) | State |
|---|---|---|---|
| 1 | Map lookup finds node `A` | — | `[D, C, B, A]` |
| 2 | — | Reads `victim = TAIL.prev`, which is `A` | Both threads now hold node `A` |
| 3 | Unlinks `A` from the tail | — | `[D, C, B]`, `A` detached, still in the map |
| 4 | — | Unlinks `A` using its stale `prev`/`next` | `B.next` and `TAIL.prev` now cross-linked |
| 5 | Links `A` after `HEAD` | — | `[A, D, C, B]` |
| 6 | — | `map.remove("A")` | **Node `A` is in the list; the map has no entry for it** |
| 7 | — | Inserts `E`; size counter reads 4, so no further eviction | `[E, A, D, C, B]`: five real nodes, four map entries |

**Final state and its consequences**

- The list holds 5 nodes; the map holds 4 keys.
- `get(A)` now returns a miss even though the caller was handed a value at step 5. The same logical read
  succeeded and then permanently stopped succeeding.
- `A`'s node can never be removed by key, because eviction deletes `victim.key` from the map and there is no
  map entry to delete. The 1.2 KB is leaked.
- The cache is permanently one entry over capacity, and every future eviction inherits that offset. After
  1,000 occurrences the cache holds 101,000 nodes under a 100,000 cap, and the memory bound that justified
  the whole design is simply false.

**The fix, stated as the rule**

- One lock, held across the map lookup, the expiry check, the unlink, the relink, the insert, and the
  eviction.
- Both threads in both races would then run their full sequence to completion, one after the other, and
  every intermediate state stays private.

### Lock discipline

> Release in a `finally` block.

- In Java: `lock.lock(); try { ... } finally { lock.unlock(); }`.
- **What breaks without it:** any exception inside the critical section — a `NullPointerException` from a bad
  key, an `OutOfMemoryError` during a resize — leaves the lock held forever.
- The next thread to call `get` blocks permanently. With 32 threads, the service is dead within 32 requests,
  and the stack traces point at an innocent `get`, not at the original exception.

> Avoid callbacks while holding the lock.

- Restates the rule from [section 4](#e103-4). Foreign code inside the lock can block on I/O, take another
  lock in the opposite order, or re-enter the cache.
- The deadlock step table in section 4 shows the exact failure.

> Stable, side-effect-free key hashing/equality is part of the caller contract.

**What this says in plain words**

1. **Stable** means `hashCode()` returns the same number every time for the same logical key.
2. **Side-effect-free** means `hashCode()` and `equals()` do not mutate anything, do no I/O, and do not take
   locks.
3. This is a requirement on the *caller's key class*, which the cache cannot verify.

**Worked example of a mutable key**

- The key is a `List<String>`, whose `hashCode()` depends on its contents.
- `put(["a","b"], v)`. The key hashes to bucket 17. The entry is stored there.
- The caller then does `key.add("c")`, mutating the list it already handed over.
- `get(["a","b","c"])` hashes to bucket 42 and finds nothing.
- `get(["a","b"])` hashes to bucket 17, finds the node, and `equals` now fails, because the stored key is
  `["a","b","c"]`.
- The entry is now unreachable by *any* key. It occupies capacity and can only leave by eviction.
- Worse, if `hashCode()` did I/O — a database lookup for a canonical id, say — it would be doing that I/O
  inside the lock, on every single `get`, and the 10 µs critical-section budget would be exceeded by a
  factor of hundreds.

> A single internal lock does not prevent deadlocks caused by arbitrary external callbacks.

- One lock, taken alone, can never deadlock: deadlock requires a cycle, and a cycle requires two locks.
- But the cache's lock plus a caller's lock is two locks, and the cache cannot see the caller's lock or
  control the order in which it is taken.
- So the claim "one lock means no deadlock" is only true if no foreign code runs inside it. The claim carries
  its own defeater, and stating both is the point.

### Exact failure if the rule is broken

> Locking the map while leaving list surgery unlocked leaves a node reachable from the map but unlinked from the list, or linked twice.
> The next eviction then removes the wrong key or loops on a corrupted `prev/next` pair.

**What this says in plain words**

- Three distinct bad states, and both symptoms, were demonstrated in the two step tables above.

| Bad state | How it arises | Symptom |
|---|---|---|
| In the map, not in the list | One thread unlinks while another re-inserts, and the map write wins | Entry occupies capacity, never evictable, never returned |
| In the list, not in the map | Eviction removes the map entry while a hit re-links the node | `get` misses on a node that is physically present; permanent leak |
| Linked twice | Two threads both insert the same node after `HEAD` | Forward traversal cycles; eviction loops or spins a CPU |

### Stripes

> Each stripe owns a separate map and list.
> Capacity and LRU order become local to each stripe.
> A hot stripe can evict while another stripe is underutilized.

**What this says in plain words**

1. A stripe is a complete independent cache: its own map, its own list, its own lock, its own size counter.
2. There is no global recency order any more. There are `N` unrelated orders.
3. Capacity is divided, so one busy stripe thrashes while others sit half empty.

**The arithmetic, restated with the required numbers**

- **16 stripes, 64 threads.**
- With one lock: 1 thread inside, up to 63 waiting. Concurrency ceiling is 1.
- With 16 stripes and uniform keys: `64 / 16 = 4` threads per stripe on average. Concurrency ceiling is 16.
- Probability two given threads collide on a stripe: `1/16 = 6.25%`.
- Balls-in-bins reality: with 64 balls in 16 bins, the busiest bin typically holds about 8 to 9, not 4.
  - So the realistic speedup is about 7× to 8×, not 16×.
- Per-stripe capacity at a 100,000 total: `100,000 / 16 = 6,250` entries.

**What the exactness loss looks like concretely**

- Uniform keys, 16 stripes, 6,250 entries each.
  - Key `X` was touched 1 second ago and lives in stripe 3, which is full.
  - Key `Y` has not been touched for 10 minutes and lives in stripe 9, which holds 2,000 of 6,250 entries.
  - An insert into stripe 3 evicts `X`, the 1-second-old entry, while the 10-minute-old `Y` survives.
  - Global exact LRU would have evicted `Y`. Striped LRU cannot even see `Y`.
- Skewed keys, one key at 40% of traffic.
  - That key hashes to exactly one stripe, which therefore carries 40% of all operations.
  - The other 15 stripes share 60%, about 4% each.
  - Contention on the hot stripe is barely better than the single-lock case, and you paid exact LRU for
    nothing.

**Why the recency list is the hardest part to make concurrent**

This deserves its own treatment, because it is the reason real caches do not look like this design.

1. **Every operation writes to the same two or three memory locations.**
   - `HEAD.next` is written by *every single hit*, because every hit moves a node to the front.
   - `TAIL.prev` is written by every eviction.
   - So even a "lock-free" list would have all 64 threads doing compare-and-swap on the same word.
2. **That produces cache-line contention even without a lock.**
   - **False sharing** is when independent variables share one 64-byte CPU cache line, so a write to one
     invalidates the other core's copy of both.
   - Here it is not even false sharing: it is *true* sharing of `HEAD.next`. Every core must take exclusive
     ownership of that line before writing.
   - A cross-core cache-line transfer costs on the order of 100 ns, which is the same order as the entire
     rest of the operation. At 64 threads the line ping-pongs continuously and throughput can fall *below*
     the single-lock version.
3. **A lock-free doubly linked list is genuinely hard.**
   - Removing a node requires changing two pointers in two different nodes, atomically.
   - A single **compare-and-swap** updates one word. There is no portable two-word CAS.
   - Correct lock-free doubly linked lists exist but need mark bits, helping protocols, and a memory
     reclamation scheme such as hazard pointers or epoch-based reclamation. That is a research-grade
     component, not an interview answer.
4. **So the industry solution is to stop maintaining exact recency on the read path.**

**What real caches actually do**

| Technique | Mechanism | What it buys | What it gives up |
|---|---|---|---|
| Buffered reads (Caffeine, Guava) | A hit appends the node reference to a small per-thread or striped ring buffer and returns immediately. One thread later drains the buffers and applies the moves under the list lock. | The read path never touches `HEAD`. Reads become nearly contention-free. | Recency is applied late. A node accessed 1 ms ago may not have moved yet. If a buffer is full, the access is dropped entirely. |
| Sampled LRU (Redis `allkeys-lru`) | No list at all. On eviction, pick `N` random keys (default 5, configurable), read each one's last-access timestamp, evict the oldest of the sample. | Zero bookkeeping on reads. A read only stamps a timestamp on its own object. | Eviction is approximate. With 5 samples it picks a genuinely old key most of the time, but not the oldest. Redis 4.0 added a pool of best candidates across rounds to improve it. |
| CLOCK / second chance | Entries sit in a circular array, each with a 1-bit reference flag. A read sets the bit. Eviction advances a hand: if the bit is 1, clear it and move on; if it is 0, evict. | A read is a single bit write with no list, no lock, and no ordering. | Only two levels of recency: "touched since the hand last passed" or not. It cannot distinguish 1 second ago from 1 minute ago. |
| TinyLFU admission (Caffeine) | A **count-min sketch** estimates each key's access frequency in a few kilobytes. On a miss, compare the candidate's estimated frequency with the eviction victim's, and admit the candidate only if it is higher. | Scan resistance: a one-off sequential scan never displaces the genuinely popular working set. | Probabilistic estimates; needs periodic aging so last week's popularity does not dominate forever. |

**The numbers that justify the switch**

- Exact LRU under one lock: about 0.1 µs of work per operation, but serialised, so roughly 1,000,000
  operations/s of theoretical ceiling and far less under real contention.
- Buffered reads: the read path is an array append plus an index increment, on a striped buffer, so it
  parallelises across cores. Published Caffeine benchmarks reach tens of millions of reads per second on
  multi-core hardware — one to two orders of magnitude beyond an exact-LRU single lock.
- CLOCK: one bit write per read. There is no coordination at all.

**What to say in the interview**

- Build exact LRU under one lock, because it is what the prompt asked for and its invariant is provable.
- Then name buffered reads, sampled LRU, and CLOCK as what production caches do, and say *why*: the recency
  list is the contended structure, so the fix is to stop updating it synchronously on reads.
- That sequence shows you can both build the exact thing and know why the exact thing is not what ships.

## Single-flight loading, TTL, LFU, and distributed consistency — IC3 baseline

### Stampede prevention

Before quoting anything, here is the problem this section exists to solve.

**Cache stampede, with the numbers**

- **Cache stampede**, also called a **thundering herd** or a **dog-pile**, is what happens when one popular
  key stops being cached and every request that needed it goes to the origin at the same moment.
- The setup:
  - Key `config:global` is read by every request. Traffic is 5,000 requests per second.
  - It was cached at 12:00:00 with a 30-second TTL, so it expires at 12:00:30.
  - The origin query for it takes 200 ms.
- What happens at 12:00:30 with no protection:

| Time | Event | Concurrent origin calls |
|---|---|---|
| 12:00:30.000 | The entry expires. The next `get` misses. | 1 |
| 12:00:30.001 | 5 more requests arrive, all miss, all call the origin | 6 |
| 12:00:30.100 | 500 requests have arrived in 100 ms, all missed | 500 |
| 12:00:30.200 | The first call returns and populates the cache. 1,000 requests arrived in total, and 1,000 origin calls were issued. | 1,000 |

- One expiry produced **1,000 identical database queries in 200 ms**, which is 5,000 queries per second of
  pure duplicate work, for a single key.
- With 5,000 requests per second and a 1-second origin call it would be 5,000 concurrent queries.
- The secondary effect is worse than the primary one.
  - The database's connection pool is, say, 100 connections. 1,000 queries queue behind 100.
  - The origin call time rises from 200 ms to 2,000 ms under that load.
  - A longer origin call means a longer miss window, which means *more* piled-up requests, which means an
    even longer origin call. This is a positive feedback loop, and it is why stampedes turn into outages
    rather than into slow periods.
  - Meanwhile every *other* query to that database is now queueing behind 1,000 copies of one query. The
    blast radius is the whole database, not one key.

**How single-flight bounds it**

- **Single-flight** means: at most one origin call per key is in progress. Everyone else waits on the same
  result.
- The same scenario with single-flight:

| Time | Event | Concurrent origin calls |
|---|---|---|
| 12:00:30.000 | First `get` misses, registers a `Flight`, calls the origin | 1 |
| 12:00:30.001 | 5 more requests miss, find the `Flight`, attach to its future | 1 |
| 12:00:30.100 | 500 requests have attached to the same future | 1 |
| 12:00:30.200 | The origin returns. The value is installed. All 1,000 waiters are completed from one result. | 1 |

- Origin calls drop from 1,000 to 1: a **1,000× reduction**, and the bound is a constant, not a percentage.
- Note what single-flight does *not* do: nobody got a faster answer. All 1,000 waited about 200 ms. The
  origin was protected; the latency was not improved.
- Note also what it does not cover: 1,000 *different* keys expiring at once coalesce into nothing, because
  there is nothing to coalesce. That is the job of the 128-flight semaphore from [section 2](#e103-2).

**The related mitigations worth naming**

| Technique | Mechanism | Effect |
|---|---|---|
| Single-flight / request coalescing | One in-flight load per key; others join | Bounds duplicate calls to 1 per key |
| TTL jitter | Store TTL as `30 s ± random(0–3 s)` per entry | Stops 10,000 keys loaded together from expiring together |
| Early / probabilistic refresh | Refresh in the background when, say, 90% of the TTL has elapsed | Nobody ever waits on a miss for a hot key |
| Serve-stale-while-revalidate | On expiry, return the old value and refresh in the background | Latency stays flat; staleness window widens by one refresh |
| Distributed lease | One node takes a short lease in the shared tier before loading | Extends coalescing across machines, best-effort |

- TTL jitter matters more than it looks. Ten thousand entries warmed during a single deploy all carry the
  same expiry instant, so they all expire in the same millisecond 30 seconds later. Single-flight bounds each
  key to 1 call, so you get 10,000 concurrent calls, not 1. Jitter spreads them across 3 seconds, turning
  10,000 simultaneous loads into about 3,300 per second, which the 128-flight cap can then absorb.

> Keep only one `Flight` object for an active key load.

- The `Flight` is the coordination point. Its presence in the in-flight map *is* the statement "somebody is
  already on it".
- Registering the `Flight` and checking the cache must happen in the same critical section. Otherwise two
  threads both find the cache empty, both find the in-flight map empty, and both register — the very
  duplication you were preventing.

> Waiters wait outside the cache lock.

- Waiters take the lock, find the `Flight`, copy the future reference, release the lock, and *then* block.
- **What breaks without it:** 1,000 threads blocked on a 200 ms future while holding the cache lock means
  the cache serves zero operations for 200 ms. Every other key becomes unavailable because one key was
  missing.

> Complete futures outside the lock because completion callbacks may execute inline.

- Completing a future can run callbacks that other threads attached to it — `thenApply`, `whenComplete`,
  and similar.
- Those callbacks are caller code, and in Java's `CompletableFuture` they frequently run **inline** on the
  completing thread.
- So `future.complete(value)` inside the lock is exactly the forbidden "foreign code inside the critical
  section" from [section 4](#e103-4), just hidden behind a library call rather than an explicit callback.
- The fix: install the value under the lock, remove the `Flight` under the lock, release the lock, and only
  then call `complete`.

### The single-flight flow

> → Under lock, check cache and the in-flight map.
> → Join an existing flight or register a new flight with the current key generation and cache epoch.
> → Release lock and perform the bounded origin load.
> → Reacquire lock and compare the flight identity, generation, and epoch.
> → Install only if no intervening write, removal, or clear invalidated the load.
> → Remove this exact flight from the in-flight map.
> → Release lock and complete the future with the result or error.

**Step by step**

→ **Under lock, check cache and the in-flight map.** Both checks in one critical section, so the decision is
atomic. A value found in the cache ends the operation immediately.

→ **Join or register.** If a `Flight` exists, copy its future and leave. If not, create one and record two
numbers: the key's current generation and the cache-wide epoch.

→ **Release lock and load.** The origin call happens with no lock held, under the 200 ms deadline and the
128-permit semaphore.

→ **Reacquire lock and compare three things.** All three are needed, and each catches a different failure.

| Check | What it catches | What goes wrong if omitted |
|---|---|---|
| Flight identity | The in-flight map now holds a *different* `Flight` for this key, because yours was removed by a `remove` and a newer one registered | You would remove the newer flight from the map, orphaning its waiters, who then wait forever |
| Generation | A `put` or `remove` touched this key while you were away | Your stale value overwrites the newer write |
| Cache epoch | A `clear()` happened while you were away | Your value repopulates a cache the operator deliberately emptied |

→ **Install only if all three still match.** Otherwise discard the loaded value.

→ **Remove this exact flight.** Not "the flight for this key" — *this object*, compared by identity. Removing
by key alone can delete a successor flight that a different thread is depending on.

→ **Release lock, then complete the future.** For the inline-callback reason above.

**The whole race, as a step table**

- Key `k`, generation 12, not cached. Loader takes 180 ms.

| Step | Time | Thread A (`getOrLoad`) | Thread B | Generation | In-flight map | Cache |
|---|---|---|---|---|---|---|
| 1 | 0 ms | Lock. Cache empty, in-flight empty. Register `Flight₁` capturing gen 12, epoch 3. Unlock. | — | 12 | `{k: Flight₁}` | empty |
| 2 | 10 ms | At the origin | — | 12 | `{k: Flight₁}` | empty |
| 3 | 20 ms | — | `put(k, "new")`: lock, bump gen to 13, install `"new"`, unlock | 13 | `{k: Flight₁}` | `"new"` |
| 4 | 180 ms | Origin returns `"old"`. Lock. | — | 13 | `{k: Flight₁}` | `"new"` |
| 5 | 180 ms | Flight identity matches `Flight₁`. Epoch matches 3. **Generation captured 12, current 13 — mismatch.** | — | 13 | `{k: Flight₁}` | `"new"` |
| 6 | 180 ms | Discard `"old"`. Remove `Flight₁`. Unlock. | — | 13 | `{}` | `"new"` |
| 7 | 181 ms | Complete the future with the current cached value `"new"`, or a retryable conflict | — | 13 | `{}` | `"new"` |

- The stale value never reaches the cache, and the caller is not lied to: it either gets the current value or
  a documented error.

**Contrast with the unfenced version**

| Step | Time | Thread A | Thread B | Cache |
|---|---|---|---|---|
| 4' | 180 ms | Origin returns `"old"`. No generation check. | — | `"new"` |
| 5' | 180 ms | Installs `"old"` | — | **`"old"`** |
| 6' | 180 ms to 30 s | — | — | Serves `"old"` for the full TTL |

- Thread B's `put` returned success. The database says `"new"`. The cache says `"old"` for 30 seconds. No
  error was logged anywhere.

### Stale-load rule

> A concurrent explicit `put` wins over an older load.
> A concurrent `remove` prevents that load from repopulating the cache.
> If invalidated, return a current value or a documented retryable conflict.
> Do not silently reinsert the stale origin result.

**What this says in plain words**

1. **Explicit writes beat loads.** A `put` is a caller stating a fact. A load is the cache guessing at the
   origin's state as of some earlier instant. The stated fact wins.
2. **A `remove` is a veto, not just a delete.** It prevents the in-flight load from resurrecting the key.
3. **The caller must be told something true.** Two acceptable answers:
   - Return whatever the cache currently holds, which is the newer value.
   - Return a retryable conflict, documented in the API, so the caller can decide.
4. **Silently reinserting is the one forbidden option.** It is worse than an error, because nothing observes
   it. Errors get alarms; silent staleness gets a support ticket three weeks later.

### Flight cleanup

> Remove on success and exception.

- The failure path is the one people forget, and it is the one that breaks the service.
- **What breaks without it:** the loader throws. The `Flight` stays in the map holding a failed future. Every
  subsequent `getOrLoad` for that key finds the `Flight`, joins it, and immediately receives the same
  failure. The key is permanently unloadable until the process restarts, even after the origin recovers.

> A timed-out waiter must not cancel work needed by all other waiters.

- 1,000 waiters, one of them with a 50 ms client deadline while the loader needs 180 ms.
- If that one waiter's timeout cancelled the shared future, the other 999 — who were prepared to wait 200 ms
  — would all fail because of one impatient caller.
- The rule: a waiter's timeout removes *that waiter*. Only the flight's own 200 ms deadline cancels the work.

> Bound flights for different keys separately from per-key coalescing.

- Restates the two-mechanism point: single-flight bounds duplication per key, the semaphore bounds total
  concurrency. Neither substitutes for the other.

> Retain generation tombstones only while needed to fence outstanding work.

- The tension, stated as two failures:
  - Drop tombstones too early and a late load sees no generation to compare against, so it publishes stale
    data. That is the bug the fence existed to prevent.
  - Keep them forever and the generation map grows without bound. A workload touching 10,000,000 distinct
    keys per day accumulates 10,000,000 tombstones, which is a bigger memory leak than the cache it protects.
- The correct retention window is bounded by the loader deadline: 200 ms plus a safety margin. Nothing older
  than that can still be in flight.

### TTL

> Check expiration against monotonic elapsed time in-process.

**What this says in plain words**

1. **Monotonic time** only ever moves forward and ignores wall-clock adjustments. In Java it is
   `System.nanoTime()`.
2. **Wall-clock time** is "what a calendar says", and it can jump. In Java it is `System.currentTimeMillis()`.
3. TTL comparisons must use monotonic time.

**What breaks with wall-clock time**

- NTP corrects the machine's clock backwards by 5 minutes.
- Every entry's `expiresAt`, computed as "now plus 30 s" in wall-clock terms, is now 5 minutes in the future
  relative to the corrected clock.
- The entire cache stops expiring for 5 minutes and 30 seconds, serving stale data with no way to detect it.
- A forward jump is the mirror failure: every entry expires at once, and you get 100,000 simultaneous misses,
  which is a self-inflicted stampede.
- Neither failure appears in testing, because test clocks do not jump.

**The nuance for the shared tier**

- Monotonic clocks are per-machine and their zero point is arbitrary, so a monotonic reading cannot be sent
  across a network.
- That is why the shared-tier `PUT` carries an absolute wall-clock `expiresAt`: it is the only kind of
  timestamp two machines can both interpret.
- The cost is a dependency on reasonably synchronised clocks, which is why the staleness bound in
  [section 2](#e103-2) is disclosed with slack rather than stated as exact.

> Lazy removal prevents serving expired entries.

- **Lazy removal** means the expiry check happens on access, not on a timer.
- A `get` that finds an expired node removes it and reports a miss, which is step three of the `get` trace.
- This is what guarantees *correctness*: an expired value is never returned, whether or not any cleaner ran.

> Bounded background cleanup releases expired memory that is never read again.

- Lazy removal alone has a memory problem: an expired entry that is never read again is never removed.
- Worked example:
  - 100,000 entries are cached during a batch job. The job ends and none of those keys is ever read again.
  - All 100,000 expire 30 seconds later, and all 100,000 stay in memory holding about 120 MB.
  - They are only reclaimed when eviction pressure from *other* keys eventually pushes them out of the tail,
    which may be hours, or never if traffic dropped.
- So a background sweeper is needed, and it must be **bounded**: examine at most, say, 1,000 entries per pass,
  every 100 ms, taking the lock briefly for each small batch.
- **What breaks without the bound:** a sweeper that scans all 100,000 entries under the lock blocks the cache
  for 5 to 10 ms, which at 100,000 operations per second means about 1,000 operations stalled per pass. The
  cleaner becomes the latency problem.
- Division of labour: lazy removal owns *correctness*, background cleanup owns *memory*.

> TTL does not prove freshness relative to a concurrent origin update.

- A 30-second TTL guarantees "this value is at most 30 seconds old". It guarantees nothing about whether the
  origin changed 1 second ago.
- Worked example: the database row is updated at 12:00:01. The cached copy was loaded at 12:00:00 with a
  30-second TTL. It is *within* its TTL and *wrong* for 29 seconds.
- TTL bounds age. It does not detect change. Detecting change needs invalidation or version validation.

### LFU follow-up

> `key -> node` stores current frequency.
> `frequency -> recency list` resolves equal-frequency ties by LRU.
> `minFrequency` identifies the next eviction bucket.
> `Access moves a node to the next frequency bucket.`
> If the old minimum bucket empties, advance the minimum.
> Long-lived popularity needs aging or an admission policy to avoid retaining yesterday's hot keys forever.

**What this says in plain words**

- **LFU** stands for **Least Frequently Used**: evict the entry with the fewest accesses, not the oldest.
- The structure is LRU plus one level of indexing.
  1. Each node stores its own access count.
  2. There is a map from frequency to a list of all nodes with that frequency, and each such list is itself
     kept in LRU order.
  3. `minFrequency` records the lowest non-empty frequency, so eviction finds its bucket in one step.
  4. An access increments the node's count and moves it from bucket `f` to bucket `f + 1`.
  5. If bucket `f` is now empty and `f` was the minimum, the minimum increases by one.

**Worked example, capacity 3**

| # | Operation | Buckets after (frequency: entries, most recent first) | `minFrequency` | Evicted |
|---|---|---|---|---|
| 1 | `put(A,1)` | `1: [A]` | 1 | — |
| 2 | `put(B,2)` | `1: [B, A]` | 1 | — |
| 3 | `get(A)` | `1: [B]`, `2: [A]` | 1 | — |
| 4 | `get(A)` | `1: [B]`, `3: [A]` | 1 | — |
| 5 | `put(C,3)` | `1: [C, B]`, `3: [A]` | 1 | — |
| 6 | `get(B)` | `1: [C]`, `2: [B]`, `3: [A]` | 1 | — |
| 7 | `put(D,4)` | `1: [D]`, `2: [B]`, `3: [A]` | 1 | `C` |

- At step 7 the cache is full. `minFrequency` is 1, that bucket holds only `C`, so `C` is evicted.
- Note that `C` was inserted at step 5, *more recently* than `A` and `B`. Pure LRU would have evicted `A`.
  LFU evicted `C` because `C` was accessed once and `A` three times.
- The tie-break matters: if bucket 1 held `[D, C]`, the victim would be the least recently used of the two,
  which is why each bucket is an LRU list rather than a set.

**Why eviction is still `O(1)`**

- Find the bucket via `minFrequency`: one map lookup.
- Take that bucket's tail: one pointer dereference.
- No scanning of frequencies and no sorting, which is what a naive "find the minimum count" implementation
  would need.

**The aging problem, with numbers**

- A key accessed 1,000,000 times last Monday sits in bucket 1,000,000.
- It has not been touched since. Today's genuinely hot key has been accessed 500 times and sits in bucket 500.
- Eviction always picks from the lowest bucket, so today's hot key is evicted while last Monday's dead key is
  immortal.
- Two standard fixes:
  1. **Aging**: periodically halve every frequency, for example every 10 minutes. Last Monday's 1,000,000
     decays through 500,000, 250,000 and so on, reaching 500 in about 110 minutes and continuing down.
     A count-min sketch makes this cheap: halve every counter in the sketch in one pass.
  2. **Windowed counting**: only count accesses within a sliding window, so history simply falls off the back.
- **Admission policy** is the complementary idea: instead of asking "who deserves to be evicted", ask
  "does this new key deserve to be admitted at all". TinyLFU compares the candidate's estimated frequency
  with the victim's and admits only if the candidate wins. A one-off scan of 1,000,000 rows never displaces
  the working set, because each scanned key has an estimated frequency of 1.

### Distributed consistency boundary

This is the part that is genuinely new when the cache stops being in-process, so it starts with the problems
rather than the quotes.

**What was true in-process and stops being true**

| Property | In one process | Across machines |
|---|---|---|
| One lock can order all operations | Yes. Take the lock, you are authoritative. | No. There is no shared lock, and taking one over the network costs milliseconds and can fail. |
| The generation counter totally orders writes to a key | Yes. One counter, one memory location. | No. Each machine has its own counter, and they are unrelated numbers. |
| An entry exists or does not | Yes. One map. | No. It may exist on 3 nodes and not on 2 others, all simultaneously. |
| Removing an entry removes it | Yes. One map write. | No. It removes it *here*. Other nodes' copies are untouched. |
| Time comparisons are reliable | Yes. One monotonic clock. | No. Monotonic clocks are not comparable across machines, and wall clocks drift. |
| A failed write means nothing was written | Yes. | No. A timeout means you do not know whether the write applied. |

**The genuinely new problems**

1. **Invalidation is a message, and messages get lost or delayed.** In-process, invalidation was a function
   call that could not fail. Now it is a network delivery with a lag distribution and a loss probability.
2. **Every node has an independent copy with an independent TTL.** Forty instances means up to 40 stale
   copies expiring at 40 different instants.
3. **Which node owns a key becomes a question.** In-process there was one map. Now there is routing, and
   routing can be temporarily inconsistent between clients.
4. **Adding or removing a cache node moves keys.** That was not a concept before, and it is where consistent
   hashing enters.
5. **The origin can be hit by many nodes at once for the same key.** In-process single-flight bounded that to
   1. Across 40 instances the bound is 40, unless something coordinates them.
6. **Partial failure exists.** One shard of ten can be down: 10% of keys unavailable while 90% are perfect.
   In-process there was no such state.

**Consistent hashing: what it solves, with numbers**

- The naive routing rule is `node = hash(key) % N`, where `N` is the number of cache nodes.
- With `N = 10`, add one node so `N = 11`. Now recompute for every key.
  - `hash(key) % 10` and `hash(key) % 11` agree only when the two remainders coincide, which is roughly
    1 time in 11.
  - So about **91% of keys move to a different node**.
  - Every moved key is a miss on the new node, so the hit rate falls from 95% to about 9% instantly.
  - Origin load jumps from 5,000 reads/s to roughly 91,000 reads/s: a self-inflicted cold start caused by
    adding capacity.
- **Consistent hashing** fixes exactly this.
  - Imagine a circle of hash values, from 0 to 2⁶⁴−1.
  - Each node is placed at several positions on that circle. Those positions are the **tokens** in the
    `cache_ring_tokens` table from [section 5](#e103-5).
  - A key is hashed to a point on the circle, and it belongs to the first node clockwise from that point.
  - Adding a node inserts new tokens. Only the keys falling between each new token and its clockwise
    predecessor move. Everything else stays where it was.
  - Going from 10 nodes to 11 moves roughly `1/11 ≈ 9%` of keys instead of 91%.

| Routing scheme | Keys moved when going from 10 nodes to 11 | Hit rate immediately after | Origin load spike from 5,000/s |
|---|---|---|---|
| `hash(key) % N` | ~91% | ~9% | ~91,000/s |
| Consistent hashing | ~9% | ~86% | ~14,000/s |

- **Virtual nodes** are why each physical node gets many tokens rather than one.
  - With 1 token per node and 10 nodes, the circle is divided into 10 arcs of random length. The largest arc
    is typically 2 to 3 times the average, so one node receives 2 to 3 times its fair share of keys.
  - With 150 tokens per node, each node owns 150 small arcs, and the law of large numbers flattens the
    distribution to within a few percent of even.
  - Virtual nodes also make removal graceful: a departing node's 150 arcs are absorbed by many different
    successors rather than dumping its entire load onto one neighbour.

**What consistent hashing does *not* solve**

- **It does not fix a hot key.** A single key hashes to a single point and therefore to a single node. If that
  one key is 40% of traffic, one node takes 40% of traffic no matter how many tokens exist.
  - The remedy is different: replicate the hot value to every instance's local cache, or shard the key
    artificially into `key#0` through `key#9` and pick one at random per read.
- **It does not make invalidation reliable.** Routing tells you where a key lives; it says nothing about
  whether the delete message arrived.
- **It does not give consistency.** Two clients briefly holding different ring versions will route the same
  key to different nodes: one writes to node 4 while the other reads from node 7. The read misses, loads from
  the origin, and writes its own copy. Now two nodes hold copies of one key, and invalidating one does not
  invalidate the other.
- **It does not bound the ring's own staleness.** That is what `ring_version`, the single `ACTIVE` row, and
  the expand-then-move-then-contract rollout order exist for.

Now the source lines.

> Database remains authoritative.
> Database commit precedes invalidation.
> Durable change delivery reduces lost invalidations.

**What this says in plain words**

1. **Authoritative** means: when the cache and the database disagree, the database is right by definition.
2. **Commit first, then invalidate.** The step tables in [section 4](#e103-4) show why the reverse order
   caches a stale value with a full TTL and no further invalidation coming.
3. **Durable delivery** means the change event is persisted before it is acknowledged, so a consumer crash
   replays it rather than losing it.
   - "Reduces" is the honest verb. It does not say "eliminates".
   - A durable log with at-least-once delivery still loses invalidations when a consumer commits its offset
     before applying the delete, or when the topic's retention expires before a lagging consumer catches up.
   - That residual risk is exactly why TTL remains as a backstop.

> A loader that read before the commit can still race to repopulate stale data.
> Retain an invalidation version watermark while older loads can still publish.
> Compare that watermark and the loaded source version during conditional cache insertion.
> Deleting the entry without retaining a version fence still allows an old loader to repopulate it.

**What this says in plain words**

Four statements building one mechanism.

1. **Commit-then-invalidate is not sufficient by itself.** A loader that started before the commit can
   return after the invalidation and reinstall the old value.
2. **A watermark is needed.** An **invalidation watermark** is "the highest source version we have been told
   about for this key", kept even after the entry is deleted.
3. **Insertion becomes conditional.** A load may publish only if its `source_version` is at least the
   watermark.
4. **A bare delete is not a fence.** Deleting removes the value but leaves nothing behind to reject the old
   loader's write.

**The race and the fix, side by side**

Without a watermark:

| Step | Time | Reader node | Writer | Shared tier |
|---|---|---|---|---|
| 1 | 0 ms | Miss on `user:42`; loader reads the database and gets version 41 | — | empty |
| 2 | 40 ms | still in flight | Commits version 42 | empty |
| 3 | 60 ms | still in flight | Publishes the invalidation | empty |
| 4 | 80 ms | still in flight | — | Consumer deletes `user:42`; nothing was there |
| 5 | 200 ms | Loader returns version 41; installs it | — | **version 41 cached, TTL 30 s** |

- The delete at step 4 accomplished nothing, because the value had not been written yet. The stale write
  arrives afterwards, and 30 seconds of wrong data follow.

With a watermark:

| Step | Time | Reader node | Writer | Shared tier |
|---|---|---|---|---|
| 1 | 0 ms | Loader reads the database, gets version 41 | — | empty, watermark absent |
| 2 | 40 ms | still in flight | Commits version 42 | empty |
| 3 | 60 ms | still in flight | Publishes the invalidation carrying version 42 | empty |
| 4 | 80 ms | still in flight | — | Consumer deletes and **records watermark = 42** |
| 5 | 200 ms | Loader offers version 41; `41 < 42`, so the write is rejected with `409` | — | still empty, watermark 42 |
| 6 | 201 ms | Reader re-reads the database, gets version 42, writes it | — | **version 42 cached** |

- The stale write is refused. The reader recovers by re-reading, so the caller still gets a correct answer.
- The watermark has the same retention trade-off as the generation tombstone: keep it while any pre-commit
  loader could still return, bounded by the loader deadline plus delivery slack, then discard it so it does
  not accumulate.

> TTL bounds residence time after insertion.
> It bounds source staleness only with assumptions about source lag and load duration.
> A short local TTL alone is not a strong-consistency protocol.

**What this says in plain words**

1. **TTL bounds how long a value stays cached after it was written.** That part is exact and mechanical.
2. **TTL bounds how far behind the origin the value is only under assumptions.** Specifically: that the value
   was fresh when loaded, and that the load took a bounded time.
3. **TTL is not a consistency protocol.** It is a garbage-collection policy that happens to limit staleness.

**Worked example of TTL underestimating staleness**

- Loader starts at 12:00:00 and reads the database, which returns the value as of 12:00:00.
- The loader is slow: GC pause plus a retry, so it publishes at 12:00:10.
- TTL is 30 s from publication, so the entry expires at 12:00:40.
- The value was accurate as of 12:00:00 and is served until 12:00:40. That is **40 seconds** of staleness from
  a "30-second" TTL.
- Shorten the TTL to 5 s and the worst case is still 15 s, because the 10-second load is unaffected by the
  TTL.
- Conclusion: the disclosed staleness bound must be `TTL + worst-case load duration + invalidation lag`, not
  just the TTL. Writing 30 s when the truth is 40 s is the kind of number an interviewer will test.

> Distributed single-flight
> A lease can reduce duplicate origin loads.
> Lease expiry can permit two loaders.
> Version checks protect publication
> The lease is an efficiency mechanism.

**What this says in plain words**

1. **The problem.** In-process single-flight bounds origin calls per key to 1 *per instance*. With 40
   instances the bound is 40, and on a synchronised expiry all 40 fire at once.
2. **A lease is the cross-machine version.** Before loading, a node attempts an atomic
   "set-if-not-exists" on a lock key in the shared tier, with a short expiry — for example
   `SET lock:user:42 node7 NX PX 5000`.
   - The winner loads. The losers wait briefly and re-read the cache.
3. **The lease can fail to be exclusive.** Node 7 wins a 5-second lease and then pauses for 6 seconds in
   garbage collection. The lease expires. Node 12 acquires it and also starts loading. Two loaders exist,
   and node 7 does not know its lease is gone.
   - Making the lease longer does not fix it; it just trades duplicate loads for longer stalls when a lease
     holder dies.
   - This is the standard result that a distributed lock with a timeout cannot guarantee mutual exclusion
     without **fencing tokens** validated by the resource itself.
4. **So correctness cannot rest on the lease.** The version check on publication is what actually protects
   the data, and it works whether one loader or five were running.
5. **The lease is therefore an efficiency mechanism, not a safety mechanism.** Being precise about which
   guarantees come from which mechanism is exactly what the deep-dive phase is scoring.

**The numbers**

- 40 instances, one hot key expiring simultaneously.
  - No coordination: 40 origin calls.
  - With a lease: typically 1, occasionally 2 or 3 when leases expire under GC pauses.
  - So the lease removes about 95% of the duplication and guarantees nothing.
- The version check removes 100% of the *incorrectness* and nothing of the duplication.
- You need both, and you must be able to say which one does which.

| Serve-stale-while-revalidate | Return the expired value and refresh in the background | Keeps latency flat, widens staleness |
| Early refresh | Refreshing before expiry, at say 90% of the TTL | Avoids waiting on a miss for hot keys |
| Lease | A short-lived exclusive claim held in the shared tier | Cross-machine coalescing, best effort |
| Fencing token | A monotonic number the resource itself validates | What a timeout-based lease lacks |
| Generation | Per-key counter bumped by explicit `put` and `remove` | The in-process fence |
| Cache epoch | One cache-wide counter bumped by `clear` | Invalidates all outstanding loads at once |
| Tombstone | A retained record that something existed | The generation kept after removal |
| Watermark | The highest source version known to have been invalidated | The distributed equivalent of a generation |
| Conditional insertion | Writing only if a version precondition holds | How the watermark is enforced |
| Compare-and-swap (CAS) | Write only if the current value still matches what was read | The pattern behind version checks |
| `source_version` | The database's version number for a row | Orders two values without a shared lock |
| `409 Conflict` | HTTP status meaning the assumed state was wrong | The rejection of a stale write |
| Monotonic time | A clock that only moves forward and ignores adjustments | The only safe basis for in-process TTL |
| Wall-clock time | Calendar time, which can jump forwards or backwards | Needed across machines; unsafe for local TTL |
| NTP | The protocol that corrects machine clocks | The source of the jumps that break wall-clock TTL |
| Lazy removal | Removing an expired entry when it is next touched | Owns correctness of expiry |
| Background cleanup | A bounded sweeper removing expired entries nobody reads | Owns memory reclamation |
| LFU (Least Frequently Used) | Evict by access count rather than recency | The stated follow-up policy |
| Frequency bucket | The list of all entries sharing an access count | The LFU index |
| `minFrequency` | The lowest non-empty frequency | Makes LFU eviction `O(1)` |
| Aging | Periodically decaying frequency counts | Stops yesterday's hot keys being immortal |
| Admission policy | Deciding whether a new entry may enter at all | The complement to an eviction policy |
| TinyLFU | Frequency-sketch admission policy | Gives scan resistance |
| Count-min sketch | Compact probabilistic frequency counter | Makes aging and admission cheap |
| Scan resistance | A one-off sequential read not destroying the working set | What admission control buys |
| Authoritative source | The component whose value is correct by definition | The database |
| Commit-then-invalidate | Commit the write before sending the invalidation | The mandatory ordering |
| Invalidation | Deleting a cached copy after the source changed | The distributed correctness mechanism |
| Invalidation lag | Time from commit to cache delete | Added to TTL for the real staleness bound |
| Durable change event | A persisted change notification surviving a consumer crash | Reduces lost invalidations |
| At-least-once delivery | Messages may repeat but should not be lost | Why deletes must be idempotent |
| Consistent hashing | Hash keys and nodes onto a circle; a key belongs to the next node clockwise | Moves ~1/N of keys when N changes, not ~all |
| Modulo hashing | `hash(key) % N` routing | Moves ~91% of keys when 10 nodes become 11 |
| Virtual node / token | One of many ring positions a physical node owns | Evens out load and smooths removals |
| Ring | The key-hash to node mapping | The shared tier's routing table |
| `ring_version` | Monotonic id of a ring generation | Lets clients detect a stale ring |
| Hot key | One key taking a disproportionate share of traffic | Not solved by consistent hashing |
| Partial failure | Some shards down while others are healthy | A state that did not exist in-process |
| Strong consistency | Reads always reflect the latest committed write | What TTL explicitly does not provide |
| Bounded staleness | A written guarantee of the maximum lag | What this design actually provides |

## Failure, operations, and security

### Reading the failure table

Each row answers five questions in order: what broke, who notices, how you find out, what the system does
while broken, and how it gets better. The rows below are the same rows as the source, expanded.

> | Cache restart | One instance or shard | Hit-rate drop | Bounded origin fallback | Warm popular keys gradually |

1. **What broke.** A process restarted, so its in-memory cache is empty.
2. **Blast radius: one instance.** The other 39 instances are unaffected, because nothing is shared in the
   local tier. That containment is a property of the design, not luck.
3. **Detection: hit-rate drop.** That instance's hit rate goes from 95% to 0% and climbs back as it warms.
   Alerting on per-instance hit rate catches it; alerting on fleet-average hit rate would hide it, because one
   instance out of 40 moves the average by about 2 points.
4. **Degraded behavior: bounded origin fallback.** Misses go to the origin, but the 128-flight semaphore caps
   how much of that reaches the database. Bounded is the operative word.
5. **Recovery: gradual warming.** Ramp traffic weight from 10% to 100% over a few minutes, or preload the top
   keys at a bounded rate, as computed in [section 3](#e103-3).

> | Origin stalls | Keys being loaded | Load deadline and flight count | Fail bounded loads; optional stale reads by policy | Clear completed flights and recover gradually |

1. **Blast radius is only the keys being loaded.** Keys already cached are still served at 0.1 µs. This is the
   payoff of running loaders outside the lock.
2. **Detection is two signals, not one.**
   - Deadline exceedances rising means individual loads are slow.
   - Active flight count sitting at 128 means the semaphore is saturated, so queueing has begun.
   - Together they distinguish "the origin is slow" from "the origin is slow *and* we are now the bottleneck".
3. **Degraded behavior offers a policy choice.**
   - Fail the load and return an error: correct, and visible to the caller.
   - Serve the expired value past its TTL: available, and knowingly stale.
   - The right answer depends on the data class from [section 2](#e103-2). Reference data should serve stale;
     authorization data must fail.
4. **Recovery is gradual.** Removing the deadline or lifting the flight cap the moment the origin recovers
     re-floods it with the entire backlog. Ramp the cap back up.

> | Invalidation lost | Affected key copies | Version lag or sampled mismatch | TTL expiration with disclosed staleness | Replay durable invalidation or flush affected scope |

1. **The hard part is detection**, because a lost invalidation is silent by construction. Nothing errors.
2. **Two detection mechanisms.**
   - **Version lag**: compare the newest `source_version` present in the cache against the database's current
     version for a sample of keys. A persistent gap means invalidations are not arriving.
   - **Sampled mismatch**: a background job reads, say, 100 random cached keys per minute directly from the
     database and compares values. At 100 samples per minute over a 100,000-key cache, a systematic problem
     affecting 10% of keys is detected within a minute or two with high probability; a single lost message
     may never be sampled, which is why TTL remains the backstop.
3. **Degraded behavior is TTL expiry**, and the staleness is disclosed, so callers are not surprised.
4. **Recovery has two levels.** Replay the durable change log from a known offset, or flush an entire
   namespace and take the cold-start cost knowingly.

> | Loader races with put/remove | One key | Deterministic concurrency test | Newer mutation wins | Reject stale flight publication |

1. This is the generation-fence race from [section 7](#e103-7), listed as an operational item to make the
   point that it is *expected*, not exceptional.
2. **"Deterministic concurrency test"** is the interesting entry. You do not detect this in production; you
   prove it in a test.
   - Inject a latch into the loader so it blocks at a chosen point.
   - Run the `put` while the loader is parked.
   - Release the loader and assert the newer value survived.
   - The test is deterministic because the interleaving is forced, not raced. A test that relies on timing
     would pass 999 times out of 1,000 and teach you nothing.
3. **Recovery is not "fix it later"** — it is the mechanism itself rejecting the publication. The failure is
   handled inline.

> | Scan pollutes cache | A workload cohort | Eviction rate and hit ratio | Reduced hit rate | Change admission/eviction after measuring |

1. **Cache pollution** is when low-value entries displace high-value ones.
2. The signature is unmistakable: eviction rate rises to match insertion rate while hit rate falls.
   - Normal steady state: 100,000 reads/s, 5,000 insertions/s, 5,000 evictions/s, 95% hit rate.
   - During a 2,000,000-row scan: insertions and evictions both at 30,000/s, hit rate at 30%.
   - The ratio of evictions to hits is the tell. High eviction with low hit rate means you are filling the
     cache with things nobody reads twice.
3. **The remedy is measured, not reflexive.** An admission policy such as TinyLFU fixes it, but adding one
   before measuring means you cannot tell whether it helped.

> | Mutable value changed externally | Shared readers | Invariant/assertion failures in caller | No cache-level protection | Immutable values or defensive copies |

1. This is the only row whose degraded behavior is "no cache-level protection", and saying so is the point.
2. The cache cannot detect it, cannot prevent it, and cannot recover from it. It is a contract violation.
3. The symptom appears in the *caller's* code — an assertion firing, a field that changed between two lines —
   which is why it is so hard to trace back to the cache.

> | Shared cache shard unavailable | Keys hashed to that shard | Connection errors; ring health | Local cache plus circuit-broken origin fallback | Ring update; gradual rewarm of the replacement shard |

1. **Blast radius is a slice, not everything.** With 10 shards, one down means 10% of keys lose their shared
   copy. The other 90% are unaffected. That partial-failure mode did not exist in-process.
2. **A circuit breaker** is the mechanism that stops retrying a dead dependency.
   - Closed: requests flow normally.
   - Open: requests fail immediately without attempting the call, after a failure threshold is crossed.
   - Half-open: after a cooldown, let a few probe requests through to test recovery.
   - **What breaks without it:** every request for those 10% of keys waits for a 2-second connection timeout.
     At 32 threads, 10% of 100,000 reads/s means the thread pool is saturated by timeouts within
     milliseconds, and the 90% of keys that were fine become unavailable too. The circuit breaker is what
     keeps a 10% dependency failure at 10% impact.
3. **Recovery is gradual rewarm**, because a replacement shard is cold and will otherwise send its whole
   share of misses to the origin at once.

> | Ring / policy store unavailable | No membership or budget changes | Config poll failures | Data plane serves on last-known ring and policy (static stability) | Restore store; clients reconcile to the newest `ring_version` |

1. **Blast radius is deliberately tiny**: you lose the ability to *change* configuration, not the ability to
   serve.
2. This is **static stability** from [section 4](#e103-4), and the row exists to make it testable: "kill the
   ring store and confirm the data plane is unaffected" is a real game-day exercise.
3. **Recovery is reconciliation.** When the store returns, clients move to the newest `ring_version`. Because
   only one row can be `ACTIVE`, they all converge on the same ring.

> | Single dominant hot key | One lock or one shard | Per-key access counter | Serve from a local replica of the hot value | Replicate hot keys to every instance; shorten their TTL |

1. **Blast radius names both scales at once**: in-process it is one lock, distributed it is one shard. Same
   phenomenon, two manifestations.
2. **Detection needs per-key counters**, typically a heavy-hitters sketch rather than a full counter per key.
   Aggregate metrics cannot show that one key is 40% of traffic.
3. **The remedy is replication, and it has a specific cost.**
   - Copy the hot value into every instance's local cache, so reads never leave the process.
   - Forty local copies means forty independent staleness windows, so shorten the TTL for that key
     specifically, for example from 30 s to 3 s.
   - That is a 10× increase in origin load *for that key* — 40 instances refreshing every 3 s is about 13
     loads/s — in exchange for removing 40% of traffic from one shard. Cheap trade, but state it as a trade.

### Observe

> Hit ratio per namespace and per tenant.
> Lock wait time and critical-section duration.
> Active flight count and loader deadline exceedances.
> Eviction rate versus insertion rate.
> Invalidation lag from commit to cache delete.
> Stale-publication rejections.

**Why each one exists, and what a bad value looks like**

| Metric | Why it exists | Healthy | Unhealthy, and what it means |
|---|---|---|---|
| Hit ratio per namespace and tenant | Drives origin load non-linearly; aggregates hide per-tenant problems | 95% | 90% means origin load doubled. One tenant at 20% while others are at 95% means that tenant's workload does not fit its budget |
| Lock wait time | The single trigger for striping | Under 10 µs | 200 µs is 20% of the 1 ms p99 budget spent waiting, so stripe now |
| Critical-section duration | Distinguishes "the lock is held too long" from "too many threads want it" | ~0.1 µs | 5 ms means something forbidden is inside the lock: I/O, a callback, or a rehash |
| Active flight count | Shows whether the semaphore is the bottleneck | Well under 128 | Pinned at 128 means loads are queueing and the origin is the constraint |
| Deadline exceedances | Shows origin health from the cache's viewpoint | Near 0 | Rising means the origin is slow before the origin's own alarms fire |
| Eviction rate versus insertion rate | Detects pollution and undersizing | Evictions ≈ insertions at steady state, both low | Both very high with a falling hit ratio means a scan is thrashing the cache |
| Invalidation lag | The second half of the disclosed staleness bound | p99 under 2 s | p99 at 45 s means the disclosed 30 s bound is a lie and callers are being misled |
| Stale-publication rejections | Proves the fence is doing work | Small and non-zero | Exactly zero forever is suspicious: either there is no concurrency or the check is not wired up |

- The last row is the subtle one. A safety mechanism that never triggers is indistinguishable from a safety
  mechanism that is broken. A small non-zero count is evidence it works.

### Retry discipline

> Retry a loader only on transient origin errors, with backoff and jitter, inside the `200 ms` deadline.

1. **Transient** means it might succeed if tried again: a connection reset, a timeout, a `503`.
   - **Permanent** means it will not: a `404`, a malformed query, an authorization failure. Retrying those
     burns the deadline and adds load for nothing.
2. **Backoff** means waiting longer between attempts. **Jitter** means randomising that wait.
   - Without jitter, 1,000 clients that failed together retry together, so the retry is itself a stampede.
   - With jitter, the same 1,000 retries spread across a window.
3. **Inside the 200 ms deadline** is the constraint that makes this concrete: the deadline covers the *whole*
   operation including retries, so a realistic budget is a 60 ms attempt, a 20 ms jittered wait, a second
   60 ms attempt, and a margin. Retries do not get to extend the promise made to the caller.

> Never retry inside the lock.

- A retry contains a wait. A wait inside the lock blocks all 32 threads for its duration.
- One 20 ms backoff inside the lock costs about 2,000 operations at 100,000 ops/s. The retry helped one key
  and stalled everyone.

> A `409` on a versioned shared-tier write means reload, not retry the same write.

- `409` means "your version precondition was wrong". The precondition will still be wrong next time.
- Retrying the identical request loops forever. The correct response is to re-read the current version and
  recompute. Getting this distinction wrong turns a conflict into an infinite retry storm.

> Waiters on a shared flight do not each retry the origin
> The flight retries once for all.

- The retry lives inside the flight, not inside each waiter.
- **What breaks without it:** 1,000 waiters each retrying twice is 2,000 extra origin calls, which is the
  stampede reintroduced through the error path. The whole benefit of coalescing is lost precisely when the
  origin is already unhealthy.

### Tenant isolation

> Tenant identity is part of every key, so one tenant cannot resolve another tenant's entry.

- Isolation is structural, not a permission check. The key `tenant-17:user:42` simply is not the key
  `tenant-99:user:42`.
- **Why structural beats a check:** a forgotten authorization check is a data leak. A forgotten key prefix is
  a cache miss, which is a performance bug rather than a security incident. Make the failure mode the cheap
  one.

> Byte budgets and entry-size caps are enforced per namespace.
> Per-tenant flight caps stop one tenant's cold start consuming the origin budget.

1. **Memory isolation** comes from the byte budget: the noisy-tenant example in [section 2](#e103-2).
2. **Origin-capacity isolation** is a separate axis and needs a separate mechanism.
   - Worked example: the global flight cap is 128. Tenant 17 starts a cold batch job and legitimately misses
     on thousands of distinct keys, taking all 128 permits. The other 49 tenants now cannot load anything, so
     their hit-rate misses turn into errors — even though their memory budget was never touched.
   - Per-tenant caps, for example 16 permits each with a shared overflow pool, bound each tenant's share.
3. Two budgets, two failure modes. Having one does not give you the other.

> Cache metrics are labeled by tenant so a noisy tenant is attributable.

- Without tenant labels the incident report says "hit rate dropped". With them it says "tenant 17's export
  job at 03:00 evicted everyone". The second one can be fixed.
- The cost is **cardinality**: 50 tenants times 6 metrics times several namespaces is thousands of time
  series. That is manageable; the same labelling per *key* would not be, which is why key-level detail lives
  in a sketch rather than in metrics.

### Rollout and rollback safety

> Serialize values with a versioned encoding
> A rolled-back client must still decode entries written by the newer build.

- The shared tier holds bytes written by whichever build happened to run.
- **The failure this prevents:** deploy build 2, which writes a new serialisation format. Build 2 has a bug
  and is rolled back. Build 1 now reads build 2's bytes and throws a deserialisation exception on every hit.
  - The rollback, which was supposed to restore service, instead turns every cache hit into an error.
  - The fix is to put a format version byte in front of every value, so an old build recognises "format 2,
    which I cannot read" and treats it as a miss rather than an exception.
- Treating an undecodable entry as a miss is the mechanism that makes rollback survivable: worst case you
  take a cold-cache cost, which is a known bounded problem.

> Change ring membership by expanding first, moving ownership, then contracting.

- The three-phase order exists so that no key is ever unowned.
  1. **Expand**: add the new node and its tokens, but ownership does not change yet.
  2. **Move**: shift ownership of the affected ranges to the new node, with both the old and new owners
     reachable during the transition.
  3. **Contract**: remove the departing node's tokens once nothing routes to it.
- **What breaks with a one-step swap:** during the swap window some clients hold ring 11 and some hold ring
  12. A key whose owner changed is written on one node and read from the other. The read misses, loads from
  the origin, and writes a second copy. Two copies of one key now exist on two nodes, and an invalidation
  that deletes one leaves the other serving stale data indefinitely — the TTL is the only backstop.

> Canary a new cache library on one instance
> Compare hit ratio and lock wait before fleet rollout.

- A **canary** is one instance running the new build while the rest run the old one, so the two can be
  compared under identical real traffic.
- The two comparison metrics are chosen deliberately.
  - Hit ratio catches a policy regression: the new eviction policy keeps the wrong things.
  - Lock wait catches a concurrency regression: the new implementation holds the lock longer.
- Neither would be visible in a unit test or a synthetic benchmark, because both depend on the real key
  distribution.

> Deploying clients must not flush the shared tier
> Only local caches restart.

- A deploy empties 40 local caches. That is expected and is why gradual warming exists.
- A deploy that also flushed the shared tier would remove the very thing that makes the restart cheap.
  - With the shared tier intact: 40 instances warm from the shared tier at about 500 µs per key, and the
    database sees almost no extra load.
  - With the shared tier flushed: 40 instances warm from the database simultaneously, which is the full
    100,000 reads/s cold-start spike from [section 3](#e103-3).
- So "flush the cache on deploy", which sounds like good hygiene, is the mechanism that converts a routine
  deploy into a database outage.

## Alternatives and IC4 stretch

### The option table, explained

> | Exact LRU with one lock | Map and ordered list | Simple linearizable operations | Recency lock contention | Interview baseline and measured moderate load |

- **What it is:** the design built in sections 4 to 6.
- **Strength:** **linearizable** operations, meaning every call appears to happen at one instant and all
  threads agree on the order. That is the strongest and easiest-to-reason-about guarantee available.
- **Weakness:** every hit takes the one lock, so throughput is capped by one lock.
- **Choose when:** the prompt asks for exact LRU, or you have measured that lock wait is not in your latency
  budget.

> | Striped LRU | Independent bounded caches | Less lock contention | No exact global LRU | Approximate eviction is acceptable |

- **What it is:** `N` complete caches, chosen by `hash(key) % N`.
- **Strength:** roughly 7× to 8× more parallelism at 16 stripes and 64 threads, from the balls-in-bins
  arithmetic in [section 3](#e103-3).
- **Weakness:** capacity and recency become per-stripe, so a hot stripe evicts 1-second-old entries while a
  cold stripe keeps 10-minute-old ones.
- **Choose when:** you have measured lock wait as the bottleneck *and* confirmed the key distribution is not
  dominated by one hot key, because striping does nothing for skew.

> | LFU | Frequency buckets with tie ordering | Retains recurring keys | Historical frequency can dominate | Workload has stable popularity |

- **What it is:** the frequency-bucket structure from [section 7](#e103-7).
- **Strength:** a key read 1,000 times survives a burst of one-off reads, which LRU cannot promise.
- **Weakness:** without aging, last Monday's 1,000,000-access key outranks today's 500-access key forever.
- **Choose when:** popularity is stable over hours or days. For a workload where the hot set turns over every
  few minutes, LRU tracks it better.

> | Approximate admission/recency | Buffered access or frequency sketch | Lower contention and scan resistance | More complex policy | Production workload justifies a mature cache library |

- **What it is:** what Caffeine actually does — buffered reads plus TinyLFU admission, from
  [section 6](#e103-6).
- **Strength:** the read path stops touching the contended `HEAD` pointer, and a scan cannot displace the
  working set.
- **Weakness:** the policy is probabilistic, so you cannot state a simple invariant about what will be
  evicted. Debugging "why was this key evicted" becomes genuinely hard.
- **Choose when:** this is production, not an interview. The honest recommendation is to use a mature library
  rather than reimplement a count-min sketch.

> | No cache | Direct origin reads | Simplest freshness semantics | Origin cost and latency | Load is small or correctness dominates |

- **What it is:** delete the cache.
- **Strength:** there is no staleness, no invalidation, no stampede, and no consistency contract to disclose.
  Every read is correct by construction.
- **Weakness:** the origin absorbs 100,000 reads/s and every read pays database latency.
- **Choose when:** the load is small enough that the database does not care, or correctness is worth more than
  latency — which is exactly the authorization case from [section 2](#e103-2).
- Keeping this row in the table is deliberate. A design discussion that cannot consider *not* building the
  thing is not a design discussion.

**The recommendation, with the deciding variable**

- Start with exact LRU under one lock.
- The deciding variable for moving off it is **measured lock wait time as a fraction of the p99 latency
  budget**.
  - Under about 5% of the 1 ms budget: stay. The simplicity is worth more than the parallelism.
  - Above about 20%: stripe, after checking that the key distribution is not skewed.
  - If it is skewed: striping is the wrong fix. Replicate the hot key instead.

### IC4 stretch — explicit consistency choice

> Keep ordinary reference data in a bounded-staleness cache.
> Read critical authorization state from an authoritative or version-validated path.
> A revocation requirement may reverse the latency-first design.

**What this says in plain words**

1. **Two data classes, two caching policies.** One policy for everything is the mistake.
2. **Reference data** gets the 30-second TTL cache. Staleness is disclosed and harmless.
3. **Authorization state** gets either no cache or a version-validated read.
4. **"May reverse the latency-first design"** is the strong claim: a hard revocation requirement can make the
   correct answer "do not cache this at all", which inverts the premise of the whole question.

**What version-validated means, concretely**

- The cache holds the value plus its `source_version`.
- On read, instead of trusting the TTL, the client asks the origin "is version 41 still current for
  `perm:user:42`?"
- That round trip returns a boolean and a version, not the payload.
  - A full read might transfer 4 KB and take 5 ms.
  - A version check transfers about 20 B and takes 1 ms.
- So it is roughly 5× faster than an uncached read and far cheaper in bytes, while being exactly as fresh.
- The cost is that you did not remove the round trip, only shrank it. It is a middle option between "cache
  and hope" and "never cache".

**The numbers that decide it**

- Authorization checks at 200/s, with a 15-second stale window from the [section 2](#e103-2) example, means
  about 3,000 requests served under a revoked permission.
- If the requirement is "revocation within 1 second", no TTL achieves it, because the TTL is the *maximum*
  staleness and you would need a TTL under 1 second.
  - A 1-second TTL at 200 reads/s means 200 origin reads/s for that key with no coalescing, or about 40/s with
    single-flight across 40 instances. At that point the cache is saving almost nothing, so the version-check
    or uncached path is both simpler and more correct.

### IC4 stretch — 10× load

> Measure skew before adding stripes.
> A single dominant key may shift the bottleneck from eviction to value loading or serialization.
> Separate per-tenant byte budgets to prevent a noisy tenant evicting all shared entries.

**What this says in plain words**

1. **Skew first, stripes second.** At 1,000,000 reads/s, if one key is 40% of traffic, that key alone is
   400,000 reads/s and no amount of striping helps.
2. **The bottleneck moves.** This is the non-obvious part.
   - At 100,000 reads/s the constraint was the lock: about 0.1 µs of pointer work, serialised.
   - At 1,000,000 reads/s for one hot key, the pointer work is still 0.1 µs, but if the value must be
     deserialised on each read — say 4 KB of JSON at roughly 20 µs — then 1,000,000 reads/s needs 20 seconds
     of CPU per second, which is 20 cores doing nothing but parsing.
   - The fix is a different one entirely: cache the *deserialised object*, not the bytes, so the parse happens
     once per load rather than once per read.
   - Recognising that the bottleneck moved is the level signal. Adding stripes here would be solving last
     year's problem.
3. **Per-tenant budgets become mandatory at 10×.** At 100,000 reads/s a noisy tenant is an annoyance; at
   1,000,000 reads/s the eviction rate is high enough that one tenant can cycle the entire cache in seconds.

### IC4 stretch — hard byte bound

> Reject an oversized value before allocating/publishing it.
> Account for values being loaded and buffered outside the cache.
> Evict-before-insert avoids a temporary resident-cache overshoot but does not bound total process memory.

**What this says in plain words**

1. **Reject before allocating.** Check the declared size before building the object, not after.
   - If the loader already deserialised a 200 MB value into the heap, rejecting it at the cache boundary is
     too late: the 200 MB is already allocated, and under memory pressure the process may die before the
     rejection returns.
2. **In-flight values count too.** This is the number most people miss.
   - Worked example: the flight cap is 128, values average 1 MB. That is up to 128 MB held in loader buffers
     *outside* the cache's accounting.
   - The cache reports 120 MB of 120 MB used, which looks perfect, while the process is actually holding
     248 MB.
   - A cache byte budget is not a process memory budget. The flight cap multiplied by the maximum entry size
     is a second, separate memory commitment: `128 × 4 MB = 512 MB` in the worst case, which may exceed the
     cache itself by 4×.
3. **Evict-before-insert helps, but only with the resident set.**
   - It removes the one-entry, or one-large-value, overshoot inside the cache.
   - It does nothing about loader buffers, serialisation scratch space, or the response objects already handed
     to callers.
   - Saying "this bounds the cache, not the process" is precisely the kind of carried defeater the quality bar
     asks for.

### IC4 stretch — cost and blast radius

> The shared tier's memory is the dominant cost
> TTL and byte budgets are cost controls, not only hygiene.
> Cell the shared tier per tenant group or region so a shard loss or a hot tenant strands one cell, not every caller.
> Keep the local cache as a data-plane fallback so a shared-tier outage degrades hit ratio rather than availability.

**What this says in plain words**

1. **Memory is the bill.** A shared cache tier is priced on RAM, and RAM is expensive per byte compared with
   disk or CPU.
   - Order-of-magnitude illustration: 10 nodes holding 64 GB each is 640 GB of RAM. At managed in-memory cache
     prices of roughly 10 to 20 US dollars per GB per month, that is on the order of 6,000 to 13,000 dollars
     per month. Labelled as order of magnitude, not a quote.
2. **TTL is a cost lever.** Halving the TTL from 30 s to 15 s roughly halves the resident set for
   write-rare, read-rare keys, because entries leave sooner. It also roughly doubles origin load for those
   keys. That is a direct dollars-for-dollars trade between cache RAM and database capacity, and framing it
   that way is a stronger answer than framing TTL as correctness hygiene.
3. **Cells bound the blast radius.** A **cell** is a complete independent copy of the tier serving a subset of
   tenants or one region.
   - Without cells: 500 tenants on 10 shards. One shard dies and 10% of *every* tenant's keys are gone, so all
     500 tenants degrade.
   - With 5 cells of 100 tenants each: one shard dies inside cell 3 and only those 100 tenants degrade. The
     other 400 see nothing.
   - The cost is lower efficiency: 5 cells each need their own headroom, so the total provisioned capacity is
     higher than one big pool.
4. **The local cache is the fallback.** Because every instance keeps its own in-process cache, a total
   shared-tier outage means misses go straight to the origin, throttled by the flight cap.
   - The hit ratio falls from 95% to whatever the local tier alone achieves, perhaps 70%.
   - Availability does not fall to zero. That is a graceful degradation, and it is a property of keeping two
     tiers rather than one.

### Weakest assumption

> Immutable values and a `95%` hit rate
> A mutable value or a scan-heavy workload invalidates both the safety argument and the origin-load estimate.
> Mitigation: enforce immutability at the API boundary and measure hit ratio per workload cohort before trusting the origin budget.

**What this says in plain words**

1. **Two assumptions are named, not one.**
   - Immutability, which the entire thread-safety argument rests on.
   - The 95% hit rate, which the entire capacity argument rests on.
2. **Each has a specific defeater.**
   - A mutable value breaks safety: the step table in [section 2](#e103-2) shows Thread A's own logic
     disagreeing with itself between two lines.
   - A scan-heavy workload breaks the estimate: the hit-rate sensitivity table in [section 3](#e103-3) shows
     95% to 80% quadrupling origin load, from 5,000 to 20,000 reads/s.
3. **The mitigations are concrete, not "be careful".**
   - Enforce immutability in the *type system* at the API boundary, so a mutable value cannot be passed.
   - Measure hit ratio per **workload cohort** — per endpoint, per job, per tenant — because a fleet average of
     95% can hide one cohort sitting at 40%.

**Why naming this yourself is worth points**

- An interviewer is going to find the weakest assumption. The only question is whether you find it first.
- Finding it first converts a challenge into agreement, and it demonstrates that you know which parts of your
  own design are load-bearing.

### Over-engineering warning

> Do not build a custom lock-free eviction policy before proving the single-lock invariant.
> Do not add a shared tier when the local hit rate already meets the origin budget.

**What this says in plain words**

1. **Do not write a lock-free cache.** From [section 6](#e103-6): a correct lock-free doubly linked list needs
   mark bits, helping protocols, and hazard pointers or epoch-based reclamation. It is a research-grade
   component, and the bug it introduces will be a rare non-deterministic corruption you cannot reproduce.
   - The single-lock version is about 150 lines and provably correct. Ship that.
2. **Do not add a shared tier you do not need.** Adding one buys cross-instance reuse and costs:
   - a network hop of roughly 500 µs on every local miss,
   - a second place where stale values live, with its own independent TTL,
   - a routing layer, a ring, a control plane, and a whole new failure row,
   - and real money in RAM.
   - Worked check: local hit rate is 95%, origin load is 5,000 reads/s, and the database comfortably serves
     20,000 reads/s. The shared tier would reduce origin load from 5,000 to perhaps 1,000 reads/s — an
     improvement against a constraint that was never binding. You paid for all the complexity above to solve
     a problem you did not have.
