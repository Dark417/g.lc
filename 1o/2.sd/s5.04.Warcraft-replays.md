## 2. Crux and why it is hard

```
100M readers ──► one identical "today" page ──► ~1K new replays/day
                (read-heavy, shared view)      (write-trivial, but duplicated 2–8×)
```

- Naive design: one Postgres, `SELECT * ORDER BY played_at DESC OFFSET n`, files on local disk.
  → Breaks first on **reads**: 100M DAU hitting the same list ≈ 10K+ QPS on one DB.
  → Second break: **duplicate uploads** — a 4v4 game has 8 clients, each holding the same replay.
- The write side is tiny. This is **not** a partitioning problem.
  → 🗣 "This is a cache problem at 10K QPS, because everyone reads the same list; and an idempotency problem on writes, because every game arrives 2–8 times."
- Cost of being wrong:
  → Stale list by 30 s: nobody cares (eventual is fine).
  → Duplicate replay shown twice, or wrong winner: users notice → dedup and metadata must be **strongly consistent** (one row per game).

## 4. Capacity and consequence — IC3 baseline

```
writes:  100 players × 10 games ×  (2..8 uploads)  ≈ 1K games/day, ≤8K upload attempts/day
reads:   100M DAU × 3 list views ≈ 300M/day ≈ 3.5K QPS avg, ~10K QPS peak (3× assume)
```

- Storage
  → 1K replays × 1 MB = **1 GB/day → ~365 GB/yr**. Trivial. S3 Standard, no tiering needed for years.
- Downloads
  → assume 10% of DAU download 1 replay → 10M/day × 1 MB = **10 TB/day egress**.
  → This is the real cost line → **CDN in front of S3**, immutable objects, `Cache-Control: max-age=1y`.
- Metadata DB
  → 1K rows/day → a single Postgres with 2 read replicas is oversized. Bottleneck is never the DB if the cache works.
- Hot set
  → today's list ≈ 1K rows × ~500 B JSON = **0.5 MB**. The entire day fits in one Redis value.
- 🗣 "Three numbers drive this: 10K list QPS, 10 TB/day egress, 0.5 MB hot set. So: CDN + Redis for reads, S3 + Postgres for truth."

## 5. Architecture and flow — IC3 baseline

```
WRITE PATH  (~1K games/day, arrives 2-8x)
=========================================

  Uploader ──(1) POST /uploads──────────► API [hot]
     │                                     │ returns presigned URL
     │──(2) PUT bytes ───────────────────► S3 staging/  [async]
     │──(3) POST /complete ──────────────► API ──► SQS parse-queue [async]
                                                        │
                                                        ▼
                                                 Parser worker [async]
                                                   │ parse header → fingerprint
                                                   ├──► Postgres  INSERT ON CONFLICT(fingerprint)
                                                   ├──► S3 replays/{sha256}.w3g  (immutable)
                                                   └──► Redis DEL list:latest


READ PATH  (~10K QPS peak, everyone reads the same feed)
========================================================

  Browser ──GET /replays──► CDN (30s TTL) ──miss──► API [hot] ──► Redis list:latest ──miss──► Postgres replica
                              │                                                            (keyset query)
                              │
  Browser ──GET /download──► CDN ──miss──► S3 replays/{sha256}.w3g   (max-age=1y)
```

- **API service [hot path]** — stateless Spring Boot on ECS; two routes: `/uploads` (writes) and `/replays` (reads). Split into two services only when scaling needs diverge; not in MVP.
- **S3 [async storage]** — `staging/` for raw uploads (24 h lifecycle delete), `replays/{sha256}.w3g` for accepted, content-addressed, immutable.
- **SQS + parser workers [async]** — parse `.w3g` header, compute fingerprint, dedup, write metadata. Decouples upload latency from parsing; retries for free.
- **Postgres [truth]** — one row per game, unique on fingerprint. Read replicas for non-cached queries.
- **Redis [hot path]** — `list:latest` (whole recent window as one sorted blob) + `replay:{id}`.
- **CDN [hot path]** — caches `GET /v1/replays` responses for 30 s and serves replay bytes from S3 forever.

### Write path (numbered)

1. Client `POST /v1/uploads {sha256, size_bytes}` with `Idempotency-Key` — API returns `upload_id` + presigned S3 PUT URL (sync). If `sha256` already accepted → return existing `replay_id`, done.
2. Client PUTs bytes to `staging/{upload_id}` — after 1. If it fails, client retries; nothing server-side changed.
3. Client `POST /v1/uploads/{upload_id}/complete` — API verifies object exists (`HEAD`), enqueues `ParseReplay{upload_id}` to SQS, returns `202`. If enqueue fails → 500, client retries step 3 (idempotent).
4. Worker receives message, downloads staging object, validates magic bytes + version — on failure → mark upload `rejected`, delete staging object, ack message (terminal, not retryable).
5. Worker parses header → `fingerprint`, players, map, mode, `played_at`, duration, winner.
6. Worker `INSERT INTO replays … ON CONFLICT (fingerprint) DO NOTHING RETURNING id`.
   → Inserted: copy object to `replays/{sha256}.w3g`, insert `replay_players`, mark upload `accepted`.
   → Conflict: link upload to existing replay as a contributor, delete staging object, mark `duplicate`.
7. Worker `DEL list:latest` in Redis, acks SQS message. If the worker dies between 6 and 7 → SQS redelivers; step 6 is idempotent, step 7 re-runs. Cache stays stale ≤ TTL in the worst case.

### Read path (numbered)

1. Browser `GET /v1/replays?limit=50` → CDN. Hit (≤30 s old) → return. Otherwise forward.
2. API `GET list:latest` from Redis (a sorted JSON array of the last ~2K replays). Hit → slice by cursor, return.
3. Miss → single-flight lock (`SET lock:list NX PX 2000`), query Postgres `ORDER BY played_at DESC, id DESC LIMIT 2000`, `SET list:latest EX 60`, return. Other requests waiting on the lock retry after 50 ms.
4. Cursor beyond the cached window → keyset query straight to a read replica (rare; deep pages).
5. `GET /v1/replays/{id}/download` → `302` to `https://cdn/replays/{sha256}.w3g`; download counter incremented via Redis `INCR`, flushed to Postgres every 60 s (approximate is fine).

## 6. API — IC3 baseline

```
GET  /v1/replays?limit=50&cursor=<opaque>&mode=1v1&player=<id>   → {items:[…], next_cursor}
GET  /v1/replays/{id}                                            → metadata + players + download_url
GET  /v1/replays/{id}/download                                   → 302 → CDN
POST /v1/uploads          (Idempotency-Key)  {sha256,size_bytes} → {upload_id, put_url, expires_at}
POST /v1/uploads/{id}/complete                                   → 202 {status:"queued"}
GET  /v1/uploads/{id}                                            → {status: queued|accepted|duplicate|rejected, replay_id?}
```

- Cursor = base64(`played_at`, `id`) of the last item. Opaque to clients; server can change encoding freely.
- Auth: reads are public; uploads require a player token or ladder-system API key. Uploader must appear in the parsed player list or be the system key — prevents random users injecting replays.
- Internal contract: `ParseReplay{upload_id, sha256, staging_key, v:1}` — versioned so parser changes don't break in-flight messages.

## 7. Data model — IC3 baseline

```
replays 1──N replay_players N──1 players
replays 1──N replay_uploads      (audit / idempotency / contributors)
```

```sql
CREATE TABLE replays (
  id           TEXT PRIMARY KEY,               -- ULID, public, time-sortable
  fingerprint  CHAR(64) NOT NULL UNIQUE,       -- game identity (see §8)
  sha256       CHAR(64) NOT NULL,              -- first accepted file's content hash
  mode         TEXT NOT NULL,                  -- '1v1','2v2','3v3','4v4'
  map_id       INT  NOT NULL,
  played_at    TIMESTAMPTZ NOT NULL,           -- from replay header, not upload time
  duration_s   INT  NOT NULL,
  game_version TEXT NOT NULL,
  winner_team  SMALLINT,
  size_bytes   INT  NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX replays_feed ON replays (played_at DESC, id DESC);          -- the listing
CREATE INDEX replays_mode_feed ON replays (mode, played_at DESC, id DESC);

CREATE TABLE replay_players (
  replay_id TEXT REFERENCES replays(id), slot SMALLINT, player_id INT NOT NULL,
  team SMALLINT NOT NULL, race CHAR(1) NOT NULL, is_winner BOOL NOT NULL,
  PRIMARY KEY (replay_id, slot)
);
CREATE INDEX replay_players_by_player ON replay_players (player_id, replay_id);

CREATE TABLE replay_uploads (
  id TEXT PRIMARY KEY, uploader_id INT NOT NULL, sha256 CHAR(64) NOT NULL,
  replay_id TEXT REFERENCES replays(id),
  status TEXT NOT NULL,                        -- queued|accepted|duplicate|rejected
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

- Why Postgres, not DynamoDB: 1K writes/day, relational queries (player pages, map pages), one unique constraint doing the dedup. DynamoDB buys nothing here and costs the `ON CONFLICT` simplicity.
- Sort by `played_at` (from header), not `created_at`: a replay uploaded 3 days late belongs to the day it was played. Defeater: a client with a wrong clock can push a game into the future — clamp `played_at <= now() + 5 min` at parse time.
- Hot-partition risk: none at this scale; at 100× write volume, partition `replays` by month (range partition on `played_at`).

## 8. Deep dive A — replay identity and dedup — IC3 baseline

```
8 clients ──► 8 uploads ──► parse header ──► same fingerprint ──► 1 row (unique constraint)
```

- Intuition: the replay ID must identify the **game**, not the **file**, because one game yields up to 8 files.
- Two candidate keys:
  → `sha256(file)`: correct **only if** every client writes byte-identical bytes. If the header embeds the saving player's slot or timestamp, the 8 files differ and you store 8 "replays".
  → `fingerprint = sha256(map_hash ‖ game_version ‖ random_seed ‖ sorted(player names, slots) ‖ played_at bucketed to 1 s)`: derived from parsed header, identical across clients.
  ◆ Defeater: two games with the same players, map, seed, and second — practically impossible; the random seed is the discriminator.
  ◆ Defeater: parser bug in one version yields a different fingerprint → duplicates appear. Version the fingerprint algorithm (`fp_v`) and backfill on change.
- How it is computed (Java 17):

```java
// fields come from the .w3g header blocks (see w3g_format spec / w3gjs parser)
record GameHeader(int version, int build, String mapPath, long randomSeed,
                  List<Slot> slots) {}
record Slot(int slotId, String playerName, int team, int race) {}

static String fingerprint(GameHeader h) {
    String canonical = String.join("|",
        "fp_v1",                                  // algorithm version
        Integer.toString(h.version()),
        Integer.toString(h.build()),
        h.mapPath().toLowerCase(),
        Long.toString(h.randomSeed()),            // the real discriminator
        h.slots().stream()
         .sorted(Comparator.comparingInt(Slot::slotId))
         .map(s -> s.slotId() + ":" + s.playerName().toLowerCase() + ":" + s.team())
         .collect(Collectors.joining(",")));
    return HexFormat.of().formatHex(
        MessageDigest.getInstance("SHA-256").digest(canonical.getBytes(UTF_8)));
}
```

→ Include only fields every client sees identically: version, map, random seed, slot/player/team.
→ Exclude: replay length (a player who leaves early saves a shorter file), saving player's slot, upload time.
→ The `.w3g` header carries no wall-clock timestamp `(verify against spec)` — so `played_at` comes from the uploader's `complete()` call or the ladder system, and is **not** part of the key.

- Decision: **public id = ULID**, **uniqueness = fingerprint**, **content hash = storage key**.
  → ULID gives clean, time-sortable URLs; the 64-char fingerprint is an internal constraint.
  → 🗣 "The ID is not the hash. The hash is how I know two uploads are the same game."
- Race: two of the 8 uploads parsed concurrently on different workers.
  1. Both compute the same fingerprint.
  2. Both run `INSERT … ON CONFLICT (fingerprint) DO NOTHING RETURNING id`.
  3. Postgres serializes on the unique index; exactly one gets a row back.
  4. The loser runs `SELECT id FROM replays WHERE fingerprint = ?`, records itself in `replay_uploads` as `duplicate`, deletes its staging object.
     → No locks, no Redis, no coordination. The unique index **is** the coordinator.
- Which file do we keep? The first accepted. If files differ per client, optionally keep all under `replays/{replay_id}/{slot}.w3g` — only if the product needs per-perspective replays. Default: keep one.
- **L5:** the 4v4 case is where a naive "hash the file and dedup" silently produces 8 rows and nobody notices until the feed looks spammy. The guardrail is a parse-time test fixture: 8 real client files of one game must collapse to one fingerprint in CI.

## 9. Deep dive B — feed listing, pagination, caching — IC3 baseline

```
Postgres (played_at DESC, id DESC) ──► Redis list:latest (top 2000) ──► CDN (30 s) ──► client groups by day
```

- Intuition: "show today, backfill from yesterday" is just "newest first, always". The day boundary is presentation.
  → Server returns a continuous descending stream; the client inserts "Today / Yesterday" headers using `played_at` in the **user's** timezone.
  → Defeater of doing it server-side: "today" differs per timezone → cache fragments per timezone → cache hit rate collapses. Keep the server timezone-agnostic.
- Pagination: **keyset**, not offset.
  → `WHERE (played_at, id) < (:cursor_ts, :cursor_id) ORDER BY played_at DESC, id DESC LIMIT 50` — uses `replays_feed` index, O(page) regardless of depth.
  → Offset defeater: a new replay inserted while paging shifts every offset → duplicated/skipped items on page 2. Also `OFFSET 100000` scans 100K rows.
  → `id` in the tuple breaks ties when two games end in the same second.
- Cache layout:
  → `list:latest` = one JSON array of the newest ~2000 replays (≈1 MB). Any page inside the window is an in-memory slice. Deep pages (rare) go to a replica.
  → Alternative: cache per page (`list:p1`, `list:p2`…) — cheaper per key, but invalidation touches N keys and page boundaries drift. Rejected at this write rate.
  → Invalidation: worker `DEL`s on every accepted insert (~1K/day — fine). TTL 60 s as a safety net for missed invalidations.
- Hot key: 100M readers on one Redis key.
  → 10K QPS on a single key is within one Redis node's range `(order of magnitude; verify against your instance)` but it is a single point of contention.
  → Mitigations in order: (1) CDN caches the JSON for 30 s, so origin sees ~1 req/30 s per edge/page combo; (2) in-process cache in the API (Caffeine, 5 s) absorbs bursts; (3) Redis read replicas if still hot.
- Stampede on invalidation: all API pods miss at once and hammer Postgres.
  → Single-flight lock (`SET lock:list NX PX 2000`); losers wait 50 ms and re-read. Alternative: worker _rebuilds_ the key instead of deleting it (write-through), which removes the miss entirely — preferred once traffic justifies it.
- **L5:** the 30 s CDN TTL is the real consistency contract. State it out loud: "a new replay appears within ~30 s for everyone; the DB is strongly consistent, the feed is eventually consistent by design." At 10× writes nothing changes; at 100× (100K/day) the 2000-window is < 1 hour of data and deep pages hit the replica — that's when you shard the cache by day.

## 10. Failure, operations, and security

| Failure | Trigger | Blast radius | Detection | Degraded behavior | Recovery |
| --- | --- | --- | --- | --- | --- |
| Duplicate replays in the feed | Fingerprint algorithm change or a parser bug | Feed quality only; no data loss | Daily job asserts `GROUP BY fingerprint HAVING count(*) > 1` returns zero rows; CI fixture suite | The feed shows the same game twice; downloads still work | Version the algorithm as `fp_v`, backfill the new fingerprint, merge the duplicate rows under the older id |
| Stampede on a `list:latest` miss | Cache delete followed by a read burst | Postgres replica CPU | Replica QPS spike at the moment of invalidation | Requests queue behind the single-flight lock and add roughly 50 ms | Single-flight lock plus a write-through rebuild by the parser worker; never delete without a rebuild path |
| Orphaned staging objects | Client never calls `complete` | Storage cost only | Staging bucket size metric | None visible to users | A 24 h lifecycle rule deletes `staging/`; alarm if the bucket exceeds a day of uploads |
| Poison replay file | Malformed or adversarial `.w3g` crashes the parser | Parser worker restart loop; the parse queue backs up | Oldest-message age on the parse queue | New replays stop appearing; the existing feed keeps serving | Parse inside a try/catch with a size cap and a wall-clock limit; three delivery attempts then the dead-letter queue, and the upload is marked `rejected` |
| Clock skew on `played_at` | Client with a wrong clock | One replay pinned to the top of the feed for days | Alert when a parsed `played_at` exceeds `now()` | Feed ordering is wrong at the head | Clamp `played_at` at parse time to the earlier of parsed and upload time; fall back to upload time when the header is implausible |
| CDN origin down | API or Redis outage | All uncached reads | 5xx rate at the edge | `stale-if-error` serves the last good list; downloads are unaffected because they read storage directly | Restore the origin; the long download TTL means the expensive path never depended on it |
| Wrong uploader | A user uploads someone else's game | Feed integrity | Uploader identity absent from the parsed player list | The upload is rejected before it reaches the feed | Reject unless the uploader appears among the parsed players or presents the ladder system key |
| Redis unavailable | Node failure or an eviction storm | Every list read falls through to Postgres | Redis error rate; replica QPS | The feed still serves from replicas at higher latency, and the CDN absorbs most of it | Single-flight guards the replicas; the 30 s edge TTL is the real shield, so Redis is an optimization and never the system of record |
| Fingerprint collision | Two genuinely different games derive the same identity | Two games merged into one row | Player-list mismatch check at insert time | One game is silently missing from the feed | Carry enough entropy in the fingerprint: player set, map, start time, duration. On mismatch fall back to the content hash and alarm |

- Retry discipline
  - Retryable: object upload, queue enqueue, Redis operations, transient parser I/O.
  - Terminal: bad magic bytes, unsupported replay version, uploader not in the game.
  - Terminal failures surface as `rejected` with a reason the client can display.
  - Every retry carries the same idempotency key, so a retried upload never creates a second game row.
- Observability
  - Cache hit rate at the edge and at Redis, reported separately, because they fail for different reasons.
  - Duplicate-fingerprint count per day, which is the single number proving dedup still works.
  - Parse queue age and dead-letter depth.
  - Egress bytes per day, which is a cost line rather than a health line.
- Isolation and abuse
  - Reads are public, so the isolation question is upload abuse rather than tenancy.
  - Rate limit uploads per player token; the ladder system key carries its own higher quota.
  - Presigned URLs are scoped to one key, one method, and a short expiry.
  ⇒ A leaked URL cannot become a general write grant.
- Rollout safety
  - The parse message carries a schema version.
  ⇒ A parser deploy never breaks messages already in flight.
  - A fingerprint change ships behind a new `fp_v` with a backfill, never as an in-place redefinition.

## 11. Alternatives and IC4 stretch

| Option | What it is | Strength | Weakness | Choose when |
| --- | --- | --- | --- | --- |
| Header fingerprint as the dedup key | Parse the replay and derive a game identity from players, map, start time, and duration | Works even when clients write different bytes for the same game | Needs a parser before dedup, so dedup becomes asynchronous | Byte-identity across clients is unproven, which is the assumed case here |
| Content hash as the dedup key | The `sha256` of the uploaded file | Trivial, synchronous, no parser on the dedup path | Eight clients emitting eight byte-different files for one game defeat it entirely | You have measured that every client emits identical bytes |
| One cache value for the whole feed | The recent window stored as a single sorted value | One key to warm, no page-boundary drift, sub-millisecond slicing | A single hot key, and every write invalidates the whole window | Write rate is tiny relative to reads, as it is here at roughly 1K games a day |
| Per-page cache keys | Cache each page of the listing separately | Invalidation touches only the affected page | Page boundaries drift as new items arrive, so cached pages disagree with each other | Writes are frequent enough that whole-window invalidation would thrash |
| Edge cache with a 30 s TTL | Cache the listing response at the CDN | Removes well over 99% of reads before they reach your infrastructure | Up to 30 s of staleness, and purge is not instant | Staleness of tens of seconds is acceptable, which the clarifying questions established |
| Postgres as the metadata truth | One row per game with a unique fingerprint constraint | The unique index gives dedup for free under concurrency, and player and map filters stay relational | Single-writer scaling ceiling | Write volume is small, which it is by three orders of magnitude |
| A wide-column store | Key-value metadata with secondary indexes | Scales writes horizontally without thought | Conditional puts plus secondary indexes to reproduce what one unique index already does | Write volume genuinely exceeds a single relational writer, which this workload does not |
| Replay bytes in the database | Store the file alongside the metadata as a binary column | One system instead of two, and transactional with the metadata | Roughly 10 TB a day of egress would leave the database rather than a CDN | Never at this egress; only for tiny files under strict transactional need |

- IC4 stretch
  - Stronger requirement
    - Make the feed personalized rather than global, for example replays by players the viewer follows.
    - The single shared cache entry stops working, because the response now varies per viewer.
    ⇒ Split into a shared cacheable candidate list plus a small per-viewer filter applied at read time.
    ⇒ The expensive part stays shared and only the cheap part becomes per-viewer.
  - 10x and 100x load
    - 10x reads change nothing, because the edge already absorbs them.
    - 10x writes are roughly 10K games a day, which no component notices.
    - 100x writes are the first real change.
    → Partition `replays` by month and shard the feed cache by day.
    ⇒ Invalidation then touches one shard instead of the whole window.
  - Cost and blast radius
    - Egress near 10 TB a day dominates the bill, and that is a CDN contract question rather than an architecture question.
    - A bad parser deploy is bounded by the dead-letter queue.
    ⇒ A poison file costs a backlog, not an outage.
  - Migration and rollout
    - Changing the fingerprint is the one genuinely hard migration, because it redefines identity.
    → Ship a new `fp_v` column, backfill it, compare both columns for a week, then move the unique constraint.
- Weakest assumption
  - That the parsed header yields a stable game identity across every client build.
  - It is unverified, and every dedup guarantee rests on it.
  → Collect eight client files from one 4v4 game and diff the parsed fields before committing to the design.
- Over-engineering warning
  - Do not shard the database, and do not reach for a log-structured broker.
  - At roughly 1K writes a day both add operational surface and buy nothing.
  - The tell is proposing partitioning before naming the write rate.
  - Say the write rate out loud first; it ends the argument in one sentence.

## 12. Interview pushback and validation

- **Why not just hash the file for dedup?**
  → **IC3 baseline:** a content hash dedups only when every client writes identical bytes, and that is not assumed, so identity comes from the parsed header. The content hash still becomes the storage key, which keeps objects immutable and cacheable.
  → **IC4 stretch:** verify the assumption empirically with eight client files from one 4v4 before locking it in, and keep both columns during the transition, so a wrong guess costs a backfill rather than a redesign.
- **Why is the day boundary computed on the client?**
  → **IC3 baseline:** timezones. A server-side notion of today fragments the cache once per timezone.
  → **IC4 stretch:** the deeper reason is cache cardinality. A timezone-agnostic descending stream keeps exactly one cache entry serving every viewer, so the grouping decision is really a caching decision wearing a product costume.
- **Page 1 changes while I am reading page 3. What happens?**
  → **IC3 baseline:** the keyset cursor pins the reader to a specific `(played_at, id)`, so new items appear above and nothing shifts underneath. An offset would duplicate or skip rows.
  → **IC4 stretch:** the cursor is opaque and server-encoded, so its encoding can change without breaking clients holding old cursors, which matters once the sort key gains a partition component.
- **Is that feed cache not a single hot key?**
  → **IC3 baseline:** yes, deliberately. The edge absorbs well over 99% of reads at a 30 s TTL and an in-process cache takes the bursts, so the key is shielded rather than exposed.
  → **IC4 stretch:** one well-shielded hot key beats many keys with drifting page boundaries. The moment personalization arrives that calculus flips, and the shared candidate set plus per-viewer filter becomes the right shape.
- **Premise reversal: the reads are not shared at all, because every viewer gets a personalized feed. Defend the design now.**
  → **IC3 baseline:** most of it survives. Postgres as truth, object storage behind a CDN for bytes, and keyset pagination never depended on sharing.
  → **IC4 stretch:** the piece that dies is the single cache entry, which was the entire read strategy. Reads become a cacheable shared candidate set plus a cheap per-viewer filter, and the cost profile moves from egress-dominated to compute-dominated. Naming which pieces die is the point; a design where every piece survives every premise change was never a design.
- **Premise reversal: the write rate is one million games a day, not one thousand. What breaks first?**
  → **IC3 baseline:** whole-window cache invalidation breaks first, long before storage or the database, because every write would invalidate the entire feed.
  → **IC4 stretch:** shard the feed cache by day and partition `replays` by month, then change invalidation from a delete into an append onto a per-shard sorted set. Only after that does the single-writer database become the binding constraint.
- **What if the parser worker dies mid-insert?**
  → **IC3 baseline:** the queue redelivers after the visibility timeout. The insert is idempotent through `ON CONFLICT DO NOTHING`, the object copy is idempotent by key, and the cache invalidation is idempotent.
  → **IC4 stretch:** the ordering matters more than the idempotency. Committing the row before invalidating the cache means a crash between them leaves a stale cache for at most the TTL. The reverse order can serve a feed that is missing a row which already exists, which is the worse failure.
- **Egress near 10 TB a day. Is that acceptable?**
  → **IC3 baseline:** it is the bill, and it is exactly why bytes come from a CDN with a one-year TTL on immutable objects rather than from the origin.
  → **IC4 stretch:** compression is the obvious next lever and probably a trap, because the replay format is already compressed internally. Measure the ratio before proposing it, and negotiate the CDN commit tier before touching the architecture.

- Validation scenarios
  - Upload the same 4v4 game from all eight clients and assert exactly one row appears in `replays`.
  - Kill the parser worker between the database insert and the cache invalidation, then assert the feed self-heals within the TTL.
  - Submit a truncated file and a deliberately malformed file and assert both reach the dead-letter queue as `rejected` without restarting the worker pool.
  - Set a client clock a week ahead and assert the replay does not pin to the top of the feed.
  - Invalidate the feed cache under a synthetic 10K QPS read load and assert the replica QPS spike stays bounded by the single-flight lock.
  - Hold a cursor, insert 500 new replays, page forward, and assert no duplicated or skipped rows.

## 13. Recall card

- "This is a cache problem at 10K QPS because everyone reads the same list, and an idempotency problem on writes because every game arrives two to eight times."
- "Three numbers drive it: 10K list QPS, roughly 10 TB a day of egress, and a 0.5 MB hot set. So an edge cache and Redis for reads, object storage and Postgres for truth."
- "Dedup on the parsed game identity, not on the bytes, because eight clients do not agree on the bytes."
- "Keyset cursors pin the reader's position; an offset duplicates and skips on a live feed."
- "The write side of this system is a rounding error; every scaling instinct belongs on the read side."

- Wrap-up script
  - "The crux is a shared, nearly static feed read by 100 million people, fed by a trickle of writes that each arrive two to eight times."
  - "I keep truth in Postgres behind a unique game fingerprint, bytes in object storage behind a CDN, and the feed in one cache value read through keyset cursors."
  - "MVP0 is upload, parse, insert, list, with no cache at all, and in week one I watch cache hit rate, duplicate-fingerprint count, and egress."
  - "At ten times nothing changes; at a hundred times writes I partition by month and shard the feed cache by day, and if the feed ever becomes personalized the single cache entry is the piece that has to be redesigned."
