## Interview framing

The level, the evidence, why the problem is hard, and the sentences to open with.

---

> - Target: OCI IC3 ownership of a bounded platform component.
>   - `IC3 baseline` is what must land in every phase.
>   - `IC4 stretch` adds architecture changes under stronger constraints.
>   - These are preparation labels, not Oracle's official rubric.

**What this says in plain words**
You answer as an engineer who owns one clearly-bordered piece of infrastructure, including its failures and its pager. `IC3 baseline` is the floor; `IC4 stretch` is depth added when pushed. Both labels are a study device, not a company grading scale.

**Why it matters**

1. **Bounded controls scope.** Inside the box: allocating isolated sessions, streaming them, controlling their egress, and destroying them. Outside: how the user authenticated, how the enterprise network is built, how the browser engine itself is hardened.
2. **The baseline is a checklist.** Skip the cleanup proof and you dropped a required item.
3. **The labels are yours.** Saying "this is the IC4 answer" claims knowledge of their rubric you do not have.

---

> - Evidence: retain the first-hand report attribution in [the bank](2.sd.md#1infra).
>   - The architecture below is a proposed interview answer.
>   - It does not claim to reproduce Oracle's implementation or an interviewer's accepted answer.

**What this says in plain words**
Someone reported being asked this in a real Oracle interview. The design here is this preparation's own answer, not a leaked design.

**Why it matters**
High confidence the question gets asked, no claim that this architecture is what the interviewer wanted.

---

> - Why this is hard
>   - Naive: run a headless browser in a container per user, relay pixels over a WebSocket, and delete the container when the tab closes.

**What this says in plain words**
The obvious design has four parts: one container per user, a real browser inside it with no window, its screen sent to the user as images over a persistent connection, and the container deleted when the user leaves.

**Why it matters**
It is what everyone proposes, and it is roughly the right shape. The failures are not in the shape; they are in the boundaries.

- Worked example of it being fine: an internal demo with 5 users on a trusted network, opening known-safe sites. The container boundary is adequate and nobody is attacking it.

---

> -   - First break: a hostile page escapes the shared kernel, or the browser reaches the instance metadata endpoint and turns the farm into an SSRF platform against the control plane.

**What this says in plain words**
Two security failures, and the second is the one that turns a bad day into a catastrophe.

1. **A hostile page escapes the shared kernel.**
   - Containers on one host share one operating system kernel. Isolation is enforced by that kernel.
   - Worked example: a page exploits a browser bug to run native code inside the container, then exploits a kernel bug to break out of the container entirely. It is now running on the host, alongside every other tenant's container on that machine.
   - The browser is the most-attacked piece of software in existence, and this design deliberately points it at hostile content all day. Treating the container boundary as sufficient assumes the kernel has no exploitable bugs, which is not an assumption anyone can make.
2. **The browser reaches the instance metadata endpoint.**
   - Cloud instances expose a special internal address that returns credentials for the machine's identity. Any process on the instance can read it, with no authentication, because being on the instance *is* the authentication.
   - SSRF stands for server-side request forgery: making a server issue requests on the attacker's behalf to places the attacker cannot reach directly.
   - Worked example of the full chain: a hostile page navigates the isolated browser to the metadata address. The browser fetches it and the page reads the response, which contains credentials for the worker's cloud identity. The attacker now has whatever those credentials can do, from inside your infrastructure, with no exploit required at all. Not a browser bug; just a URL.
   - This is why the design blocks private and control-plane address ranges at egress rather than relying on the browser to refuse.

---

> -   - Second break: the allocator loses a response and leaks workers, a stale token attaches to a recycled worker address, and a disconnect quietly leaves the user browsing unisolated.

**What this says in plain words**
Three more failures, and these are the lifecycle and correctness ones.

1. **A lost response leaks workers.**
   - Worked example: the controller asks for a worker. The worker is created. The response is lost in the network. The controller retries and creates a second worker. The first is now running, costing memory, belonging to nobody, and invisible unless something reconciles.
2. **A stale token attaches to a recycled worker address.**
   - Worked example: user A's session ends and worker address `10.2.4.19` is returned to the pool. Thirty seconds later user B's session is allocated at the same address. User A's browser, holding a connection token issued 45 seconds ago, reconnects to `10.2.4.19` and lands in user B's session, seeing their screen.
   - The token was validly signed. It simply referred to a session that no longer exists at that address.
3. **A disconnect quietly leaves the user browsing unisolated.**
   - Worked example: the stream drops and the client falls back to loading the site directly in the local browser so the user is not interrupted. The hostile content now executes on the corporate laptop, which is precisely the thing the entire product exists to prevent.
   - It is the worst failure in the list because it is invisible: the user's browsing continues and looks normal.

---

> -   - Minimum primitives
> -     - A hard isolation boundary per session
> -     - Egress enforced at connection time after DNS resolution
> -     - Short-lived generation-bound tokens
> -     - Durable desired state reconciled against worker inventory.

**What this says in plain words**
Four parts you cannot drop.

1. **A hard isolation boundary per session.** Stronger than a shared kernel, so a browser escape does not reach other tenants.
2. **Egress enforced at connection time after DNS resolution.**
   - Not when the URL is checked, but when the outbound TCP connection is actually made, against the address DNS returned.
   - This ordering is the entire defence against DNS rebinding, expanded in the isolation section.
3. **Short-lived generation-bound tokens.** A token is valid for seconds and names a specific generation of a specific session, so it cannot be reused against recycled capacity.
4. **Durable desired state reconciled against worker inventory.** What should exist is written down and continuously compared against what does exist.

---

> - 🗣 “Treat the worker as the attacker; the design is what a compromised worker still cannot reach, and how the control plane proves it is gone.”

**What this says in plain words**
A quotable one-liner; the 🗣 marker means say it roughly verbatim. Three claims:

1. Assume the worker is compromised. Not that it might be; that it is.
2. The design's content is what a compromised worker still cannot reach.
3. And how the control plane *proves* a worker is gone, rather than assuming it.

**Why it matters**
It reframes the whole question within ten seconds.

- Most candidates design to prevent compromise, which is unachievable against a browser rendering arbitrary hostile content.
- This sentence assumes compromise and asks what remains true anyway, which is a question that can actually be answered.
- The word *proves* in the second half sets up the lifecycle section: "we asked it to terminate" is not proof, and the difference becomes a real mechanism later.

---

> - Opening script
>   - “I will use disposable isolated browser sessions with explicit user ownership, controlled egress, and a reconciled lifecycle.”

**What this says in plain words**
The first sentence, announcing four decisions: sessions are disposable, ownership is explicit, egress is controlled, and the lifecycle is reconciled rather than assumed.

**Why it matters**
Each word is load-bearing. *Disposable* means no profile cleanup problem. *Explicit ownership* means the token story. *Controlled egress* means the metadata defence. *Reconciled* means the leak defence.

---

> -   - “First I confirm the rendering model, whether sessions persist, and which transfers and destinations are in scope.”

**What this says in plain words**
Three questions before designing.

1. **Rendering model**, because pixels versus reconstructed content is a completely different trust boundary.
2. **Session persistence**, because persistent profiles create a data-cleanup problem that disposable sessions do not have.
3. **Transfers and destinations**, because clipboard, uploads, downloads, and private sites each add their own policy surface.

---

> -   - “Then I size memory, streaming bandwidth, and warm capacity from ten thousand concurrent sessions.”

**What this says in plain words**
Three estimates from the one headline number, and the third is the unusual one: warm capacity means workers kept running and idle so a session can start quickly.

---

> -   - “The deep dive is the isolation boundary, token binding to a session generation, and reconciliation of allocation and destruction.”

**What this says in plain words**
Three deep-dive topics announced in advance: what the sandbox actually is, how a token is tied to a specific session generation, and how allocation and destruction are made to converge.

---

> -   - “I will close with failure handling, tenant isolation, and where I would change the design for private sites or multiple regions.”

**What this says in plain words**
Announces the ending: failures, multi-tenancy, and the two most likely requirement changes.

**Why it matters**
Naming private sites in advance is shrewd: it is the most common follow-up, because every enterprise eventually wants internal applications isolated too, and it breaks the simple Internet-only egress rule.

---

> - Numerical targets below are interview assumptions unless a reference explicitly supplies them.
>   - Validate performance targets with the actual payload and deployment topology.

**What this says in plain words**
Every number is an assumption unless cited, and real targets must be measured with real sites on the real deployment.

**Why it matters**
Worked example of why it matters more here than usual: 512 mebibytes per session is a guess about browser memory. A single site with heavy media can use several times that, and the entire capacity plan is built on that one number.

## Requirements — IC3 baseline

The numbers warning, the clarifying table, functional scope with the baseline decisions, the numeric target table, invariants, and non-goals.

---

> - Numerical targets are interview assumptions unless an adjacent primary source states otherwise.

**What this says in plain words**
Every number here was chosen to make the design concrete. None came from Oracle unless a link says so.

**Why it matters**
Worked example: at 10,000 concurrent sessions you need a warm pool, capacity reservations, and cell planning. At 50 sessions a single host runs the whole service and none of that applies.

---

> | Question | Assumed answer | Why it changes the design |
> |---|---|---|
> | Pixel stream or reconstructed DOM/drawing commands? | Pixel stream | Simple trust boundary; bandwidth becomes the dominant cost |
> | Persistent login state or disposable sessions? | Disposable | No profile storage; cleanup is reprovision, not deletion |
> | Are clipboard, uploads, and downloads permitted? | Disabled until scanning paths exist | Each transfer direction needs its own policy and quarantine path |
> | Are private enterprise sites in scope? | No; Internet-only | Egress blocks private and control-plane ranges outright |
> | Required isolation boundary? | VM/microVM per session | Sets memory cost and allocation latency |
> | Single region or global users? | One region first, residency policy known | Affinity and warm pool are regional; failover is a visible reset |
> | Peak concurrency? | `10,000` sessions | Drives memory, egress, and warm-capacity math |

**What this says in plain words**
Seven questions, the assumed answer, and what each decides.

- **Row: Pixel stream or reconstructed content?**
  - Pixel streaming sends images or video of the rendered page. The alternative reconstructs a sanitized version of the page and renders it locally.
  - Worked example of the trust difference: with pixels, the only thing crossing to the endpoint is an image. An image decoder has a small, well-understood attack surface. With reconstructed content, a sanitizer must correctly neutralize arbitrary hostile markup and scripting, and any gap in that sanitizer puts hostile content back on the endpoint, which is the exact thing the product prevents.
  - The cost of choosing pixels: bandwidth becomes the dominant expense, because you are streaming video for every user all day.
- **Row: Persistent or disposable sessions?**
  - Disposable, so nothing survives the session.
  - Worked example of the cleanup difference: with persistent profiles, ending a session means deleting cookies, cached files, local storage, and any temporary files the browser wrote, thoroughly enough that the next tenant cannot recover them. That is best-effort deletion across a filesystem you do not fully control. With disposable sessions, the whole environment is destroyed and a fresh one is created, which is a far easier property to argue for.
- **Row: Clipboard, uploads, downloads?**
  - Disabled until scanning paths exist.
  - Each direction is a separate hole. Worked example: a download is a file from a hostile site reaching the corporate endpoint, which is the exact transfer isolation was supposed to stop. An upload is corporate data leaving to an untrusted site. Clipboard is both, in miniature, and continuously.
  - Disabling them first is scope discipline: turn the feature on once its policy and scanning path is designed, rather than shipping the hole and fixing it later.
- **Row: Private enterprise sites?**
  - No, Internet-only, which lets egress block all private address ranges outright.
  - Worked example of why this simplifies enormously: with Internet-only, the egress rule is "deny every private and cloud-internal range, allow the rest by policy". It is a small, auditable rule. Once internal sites are in scope, some private addresses must be allowed, and the rule becomes a per-tenant allowlist of internal destinations, which is both larger and riskier.
- **Row: Isolation boundary?**
  - A virtual machine or microVM per session. A microVM is a lightweight virtual machine with a minimal device model, designed to boot in well under a second.
  - Worked example of what it buys: a container escape lands the attacker on the shared host kernel. A microVM escape must first break the browser, then the guest kernel, then the hypervisor. The hypervisor is a much smaller, much more scrutinized interface than a full kernel.
  - The cost: more memory per session, and slower start.
- **Row: Single region or global?**
  - One region first, with the data residency policy known.
  - Worked example of residency mattering: a European tenant's browsing may be required to stay in Europe. That is a legal constraint on placement, not a latency preference, and it constrains failover as well.
- **Row: Peak concurrency, 10,000 sessions.** The number every estimate derives from.

---

> - Functional scope
>   - Frame the enterprise browser-isolation prompt.
>     - Users browse untrusted sites through remote browser sessions.
>     - Active site content executes in an isolated worker.
>     - The endpoint receives a constrained rendered representation.
>     - Input travels back to the remote session.

**What this says in plain words**
The product in four sentences.

1. Users browse untrusted sites through a remote session rather than locally.
2. Active content, meaning scripts and plugins, runs in the isolated worker.
3. The endpoint receives only a constrained rendering, not the content.
4. Keystrokes and mouse events travel back to the remote session.

**Why it matters**
The direction of each arrow is the security model.

- Hostile content flows *to* the worker and stops there.
- Only pixels flow *from* the worker to the endpoint.
- Only input events flow back, and those originate from the trusted side.
- Worked example of the asymmetry mattering: a page containing a browser zero-day exploit reaches the worker and may compromise it. The endpoint receives an image of the page. The exploit never travels to the laptop, because images are not scripts.

---

> -   - Baseline decisions
> -     - Use pixel streaming to keep the rendering trust boundary easy to explain.
> -     - Use disposable per-user sessions.
> -     - Allow approved Internet destinations through a controlled egress proxy.
> -     - Disable clipboard and file transfer until their policy/scanning paths are specified.

**What this says in plain words**
The four choices restated as decisions, with a reason attached to the first.

**Why it matters**
"easy to explain" is an unusual and honest justification. In a security design, a boundary you can explain fully is worth more than a cleverer one you cannot, because a boundary nobody can reason about completely is a boundary nobody can verify.

---

> | Requirement | Target | Enforced by |
> |---|---|---|
> | Concurrent sessions | `10,000` | Regional capacity reservation; per-tenant concurrency quota |
> | Warm session allocation | p99 < `5 s` | Warm pool of `20%` spare workers; allocator returns an operation handle |
> | Input-to-render latency | p99 < `150 ms` for users near the region | Regional placement; encoder frame budget; adaptive bitrate |
> | Session-service availability | `99.9%` | Stateless controllers across fault domains; sessions pinned to one worker |
> | Idle timeout / reconnect grace | `15 min` / `60 s` | Expiry reconciler on the session table |
> | Worker termination after closure | Within `60 s` | Lifecycle reconciler; alert on orphan age |
> | Connection token lifetime | `60 s`, one use, generation-bound | Ticket table with `consumed_at`; gateway validates generation |
> | Data-plane independence | Existing streams survive a 5 min controller outage when session/policy validity exceeds 5 min | Cached binding plus locally enforced expiry; reconnect still checks authorization |

**What this says in plain words**
Eight promises, each with a number and a mechanism.

- **Row: Concurrent sessions, 10,000.** Held by a regional capacity reservation and a per-tenant quota, so one tenant cannot consume the whole pool.
- **Row: Warm session allocation, p99 under 5 seconds.**
  - Worked example of why a warm pool is required: booting a fresh microVM and starting a browser takes perhaps 10 to 30 seconds. Meeting a 5-second target means the worker must already be running, which is exactly what the warm pool is.
- **Row: Input-to-render latency, p99 under 150 milliseconds.**
  - This is the whole user experience. Worked example of the budget: the network round trip to a nearby region might be 30 milliseconds, the browser must process the input and repaint, and the frame must be encoded and decoded. 150 milliseconds is tight but usable; beyond about 200 the interface feels detached from the mouse.
  - "for users near the region" is the defeater. A user 200 milliseconds away cannot be served within 150, whatever the design does.
- **Row: Session-service availability, 99.9%.**
  - Note this is lower than other designs in the bank, and the reason is in the enforcing column: sessions are pinned to one worker. A pinned session cannot be made highly available by adding controllers, so the honest target is lower.
- **Row: Idle timeout 15 minutes, reconnect grace 60 seconds.**
  - Two different timers. Idle timeout ends a session nobody is using. Reconnect grace holds a session briefly when the connection drops.
  - Worked example of the grace: a user's laptop switches from wired to wireless and the stream drops for 8 seconds. Within the 60-second grace, they reconnect to the same worker with their page intact. Without it, every network blip would destroy their browsing session.
- **Row: Worker termination within 60 seconds of closure.**
  - Enforced by the reconciler, with an alarm on orphan age. The alarm matters as much as the target: a worker that failed to terminate must become visible, not merely be retried forever in silence.
- **Row: Connection token lifetime, 60 seconds, one use, generation-bound.**
  - Three independent restrictions. Worked example of each doing separate work: 60 seconds limits the window for a stolen token. One use means a captured token that was already redeemed is worthless. Generation binding means even a fresh unused token cannot land on a different session that now occupies the same worker.
- **Row: Data-plane independence.**
  - The most carefully worded row. Existing streams survive a 5-minute controller outage, *when the session and policy validity exceed 5 minutes*.
  - Worked example of the conditional mattering: if a session's authorization expires 2 minutes into the outage, the gateway must end it, because continuing would mean serving a user whose access has lapsed. Static stability is bounded by the validity of what was cached, not by the length of the outage.
  - And "reconnect still checks authorization": an existing stream continues, but a *new* connection always re-checks, so the outage cannot be used to obtain fresh access.

---

> - Invariants
>   - Session ownership is bound to authenticated tenant and user.
>   - A worker cannot reach control-plane credentials, metadata endpoints, or other tenants.
>   - Reused capacity must not expose a prior session's cookies, memory, or files.
>   - A disconnect never silently changes the user to unisolated browsing.

**What this says in plain words**
Four statements true at every instant.

1. **Ownership is bound to an authenticated identity.** Possessing a session identifier is never sufficient.
2. **A worker cannot reach credentials, metadata, or other tenants.** The three targets named explicitly, because each has its own mechanism: no credentials issued, metadata blocked at egress, network separation between tenants.
3. **Reused capacity exposes nothing from before.** Cookies, memory, and files all named, because they are three different leakage paths through one reused worker.
4. **A disconnect never silently drops isolation.**
   - The one the whole product depends on. Worked example of the violation: a client library that falls back to direct loading on stream failure. The user keeps browsing, sees no difference, and hostile content is now executing on their laptop. The failure is invisible to the user and to the service.

---

> - Non-goals
>   - Persistent browser profiles across sessions.
>   - Private-site connectors into the enterprise network.
>   - Transparent live migration of a running session between regions.

**What this says in plain words**
Three exclusions.

1. **Persistent profiles.** Users log in again each session. The cost is convenience; the benefit is that cleanup is destruction rather than deletion.
2. **Private-site connectors.** Internal applications are not reachable through this service in the baseline.
3. **Transparent live migration.** A session cannot move between regions while running.
   - Worked example of what is being excluded: live-migrating a running virtual machine with a browser's full memory state across regions, without the user noticing. It is technically possible and enormously expensive. The alternative offered is a visible reset: the user is told the session restarted and opens their page again.

**Why it matters**
The third is a preemptive defence against a question that sounds reasonable and is disproportionately expensive to answer with a yes.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Pixel streaming | Sending rendered images or video of a page rather than the page itself. | The simplest trust boundary, at the cost of bandwidth. |
| DOM reconstruction | Rebuilding a sanitized version of the page and rendering it on the endpoint. | Cheaper bandwidth, but the sanitizer becomes attack surface. |
| Active content | Scripts, plugins, and anything that executes rather than merely displays. | What must stay on the worker side of the boundary. |
| Disposable session | A session with no persistent profile, destroyed entirely when it ends. | Turns cleanup into reprovisioning. |
| microVM | A lightweight virtual machine with a minimal device model, designed to boot very fast. | The isolation boundary, stronger than a container and cheaper than a full VM. |
| Hypervisor | The layer isolating virtual machines from each other and the host. | A much smaller interface to attack than a full kernel. |
| Data residency | A legal requirement that data stay within a geography. | Constrains placement and failover, not just latency. |
| Warm pool | Workers kept running and idle so allocation does not wait for a boot. | The only way to meet a 5-second allocation target. |
| Operation handle | An identifier returned immediately for work that completes later. | Lets allocation be asynchronous without holding a connection. |
| Adaptive bitrate | Adjusting stream quality to available bandwidth. | Keeps latency within budget on a poor connection. |
| Reconnect grace | A short window in which a dropped stream can rejoin the same live session. | Survives ordinary network blips without destroying the session. |
| Orphan worker | A running worker no session record points to. | Its age is alarmed on, because silent retries hide the failure. |
| Generation binding | Tying a token to one incarnation of a session, not just its identifier. | Stops a valid token landing on recycled capacity. |
| One-use token | A credential invalidated the first time it is redeemed. | A captured token that was already used is worthless. |
| Static stability | Continuing to operate correctly without the control plane, from locally cached state. | Bounded here by the validity of what was cached. |
| Unisolated fallback | Silently loading a site locally when the isolated stream fails. | Explicitly forbidden; it defeats the entire product. |
| Live migration | Moving a running virtual machine between hosts or regions without interruption. | Excluded as disproportionately expensive. |

## Capacity and consequence — IC3 baseline

Four estimates. Each ends in the decision it forces.

---

> - Memory
>   - Assume `512 MiB` reserved per active browser session.
>   - `10,000 × 512 MiB = 5,120,000 MiB ≈ 4.88 TiB`.
>   - An additional `20%` warm capacity increases the reservation to about `5.86 TiB`.
>   - Real browser footprints and CPU demands must be benchmarked with representative sites.
>   - Decision: microVM-per-session is affordable at this scale only on dense hosts
>     - CPU per session probably binds before memory, so the benchmark decides host shape, not the memory arithmetic.

**What this says in plain words**

1. **512 mebibytes per session** covers the browser process, the guest operating system, and the encoder.
2. **10,000 × 512 MiB ≈ 4.88 tebibytes** of memory for active sessions.
3. **Plus 20% warm capacity ≈ 5.86 tebibytes** reserved in total.
4. **The real figure must be benchmarked**, and CPU as well as memory.

**Why it matters — the decision**
Two conclusions, and the second overrides the first.

- **Affordable only on dense hosts.** Worked example: at 512 gibibytes per host, 5.86 tebibytes needs about 12 hosts, each running roughly 900 microVMs. That is a high density and it constrains the host type.
- **CPU probably binds before memory, so the benchmark decides host shape.**
  - The important admission. Worked example: a browser rendering an animated page can consume most of a core continuously. A host with 128 cores cannot run 900 such sessions, whatever its memory. If the real ratio is closer to a quarter core per session, the host supports about 500 sessions and memory is not the constraint at all.
  - The memory arithmetic was done, and then explicitly demoted. That is the estimate doing its job: it establishes the scale and then identifies that a different resource decides the answer.

---

> - Streaming bandwidth
>   - At an assumed average `2 Mbit/s/session`, egress is `20 Gbit/s`.
>   - Animation-heavy sites can exceed this average.
>   - Bandwidth can dominate cost before control-plane requests do.
>   - Decision: the encoder must adapt bitrate and frame rate per session, and gateways sit near users, because egress is the cost line that scales with usage.

**What this says in plain words**

1. **2 megabits per second per session** as an average for video-like streaming of a browser.
2. **10,000 × 2 = 20 gigabits per second** of continuous outbound traffic.
3. **Heavy sites exceed the average.** Worked example: a page with autoplaying video can use 8 to 10 megabits per second. A thousand such sessions is 10 gigabits per second from 10% of the fleet.
4. **Bandwidth dominates cost.** Worked example of the comparison: the control plane handles about 5.6 session creations per second, which is trivial. Meanwhile 20 gigabits per second flows continuously, and in most clouds egress is billed per byte. The expensive part of this system is the part that never appears in a request-rate estimate.

**Why it matters — the decision**
Two mechanisms, both driven by the bandwidth number.

- **Adapt bitrate and frame rate per session.** Worked example: a user reading a static page needs almost no frames. Suppressing identical frames drops that session to near zero while a video session keeps its full rate. Adaptation is not a quality feature here, it is the primary cost control.
- **Gateways near users.** Shorter paths mean lower latency and, in many topologies, cheaper transit.

---

> - Session creation
>   - With `30 min` average lifetime, steady churn is approximately `10,000 / 1,800 = 5.6 new sessions/s`.
>   - Shift changes or regional recovery create bursts.
>   - Warm capacity must cover allocation latency and the expected burst, not just average churn.
>   - Decision: size the warm pool to the burst, not the mean
>     - `2,000` warm workers absorb a `400/s` burst for the `5 s` allocation window before latency degrades.

**What this says in plain words**

1. **Steady churn is 5.6 new sessions per second.** 10,000 sessions each lasting 1,800 seconds means about 5.6 end and 5.6 begin every second.
2. **But bursts are far larger.** Worked example: 09:00 on a Monday, when several thousand employees start work within a few minutes. Or a regional recovery, when every session that was lost is recreated at once.
3. **So size to the burst.** The arithmetic: a burst of 400 sessions per second sustained for the 5-second allocation window needs 2,000 warm workers to absorb it without anyone waiting for a cold boot.

**Why it matters — the decision**
Sizing to the mean would be catastrophic and would look correct on paper.

- Worked example: a warm pool sized for 5.6 new sessions per second holds perhaps 30 workers. The Monday-morning burst of 400 per second exhausts it in under a tenth of a second, and the remaining thousands of users wait 20 to 30 seconds each for a cold boot, at exactly the moment the entire company is trying to start work.
- The general principle: warm capacity is insurance against burst, and insurance sized to the average claim is not insurance.

---

> - Placement
>   - Begin with one regional pool and explicit affinity.
>   - Add regions when user latency or regional resilience requires them.
>   - Decision: a session is pinned to one worker for its life, so placement is decided once at creation.

**What this says in plain words**

1. **One regional pool, with explicit affinity.** Affinity means a session's traffic always reaches the same worker.
2. **Add regions only for latency or resilience**, not by default.
3. **A session is pinned for life.**

**Why it matters — the decision**
Pinning is forced by where the state lives, and it has consequences everywhere else.

- Worked example of why pinning is unavoidable: the session's entire state is the browser's memory, its cookies, its open tabs, its scroll position, and its rendering context. None of that is in a database. It exists only inside that one worker's memory, so nothing else can serve the session.
- The consequences run through the whole design: the availability target is lower because a pinned session cannot fail over, the reconnect grace exists so a network blip does not lose that state, and regional failover is a visible reset rather than a migration.
- Worked example of the contrast: a stateless web service loses a machine and its requests land elsewhere with nobody noticing. Here, losing the worker loses the browsing session, and the only honest response is to tell the user it restarted.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Mebibyte / tebibyte | 1,048,576 bytes and 1,099,511,627,776 bytes, written `MiB` and `TiB`. | The units the memory estimate uses. |
| Reserved memory | Memory committed to a session whether or not it is fully used. | Reservation, not usage, is what limits density. |
| Dense host | A machine configured to run an unusually large number of workloads. | What microVM-per-session requires to be affordable. |
| Host shape | The CPU, memory, and network configuration of a machine type. | Decided by the CPU benchmark, not the memory arithmetic. |
| Binding constraint | The resource that runs out first and therefore determines capacity. | Probably CPU here, despite the memory arithmetic. |
| Egress | Outbound network traffic leaving the provider's network. | Billed per byte in most clouds, and the dominant cost here. |
| Adaptive bitrate | Adjusting stream quality to match available bandwidth and content. | The primary cost control, not a quality feature. |
| Idle-frame suppression | Not sending frames when the screen has not changed. | Drops a reading session's bandwidth to near zero. |
| Churn | The rate at which sessions end and new ones begin. | 5.6 per second at steady state, and irrelevant to sizing. |
| Burst | A short period with a far higher arrival rate than the mean. | What the warm pool must actually absorb. |
| Warm pool | Workers already running and idle, ready to be assigned. | Sized to the burst, at roughly 2,000 workers. |
| Cold boot | Starting a worker from nothing, taking tens of seconds. | What the warm pool exists to avoid on the user's path. |
| Affinity | Routing a session's traffic consistently to the same worker. | Required because the session state lives only there. |
| Pinning | A session bound to one worker for its entire life. | Forced by state location, and it caps availability. |
| Volatile state | State existing only in memory, lost when the process dies. | The browser's entire session, which is why failover is a reset. |

## Architecture and flow — IC3 baseline

Diagram first, then each component with the mechanism it buys and the price it charges, then one session traced end to end.

---

> ```text
> Enterprise user -> authentication/policy API -> session controller -> allocator
>         |                                                    |
>         +-- authenticated streaming gateway <-> isolated browser worker
>                                                           |
>                                                    controlled egress proxy
>                                                           |
>                                                     approved Internet sites
>
> Session DB / operation outbox -> worker lifecycle reconciler
> Policy service -> versioned policy snapshots -> gateways and egress enforcement
> ```

**What this says in plain words**
A control path across the top, a data path down the middle, and two supporting loops at the bottom.

**Reading the control path**

1. **Enterprise user → authentication and policy API.** Who is this, and what are they allowed to do?
2. **→ session controller.** Records that a session should exist.
3. **→ allocator.** Turns that intent into an actual worker.

**Reading the data path**

1. **User → authenticated streaming gateway.** The user's persistent connection terminates here, not at the worker.
2. **Gateway ↔ isolated browser worker.** Pixels one way, input the other. The double arrow is the only bidirectional link in the diagram.
3. **Worker → controlled egress proxy → approved Internet sites.**
   - The critical property is what is *absent*: there is no arrow from the worker directly to the Internet. Every outbound connection goes through the proxy.
   - Worked example of why the missing arrow is the design: if the worker had any direct network path out, a compromised browser would use it and the entire egress policy would be advisory. The proxy must be the only route, enforced by network configuration rather than by the worker's cooperation.

**Reading the supporting loops**

- **Session database and operation outbox → worker lifecycle reconciler.** Desired state feeding a loop that makes reality match it.
- **Policy service → versioned snapshots → gateways and egress enforcement.** Policy flows outward to the two places that enforce it.

**Why it matters**
The user never touches the worker directly. Two components sit between them, the gateway and, on the other side, the proxy, and both enforce policy. A compromised worker is surrounded.

---

> - Session controller (control plane)
>   - Authorizes the user and tenant quota.
>   - Persists desired session state before requesting worker allocation.
>   - Returns an operation handle for asynchronous allocation.
>   - Cost: two round trips to reach `READY`, and a reconciler is required because intent and inventory can diverge.

**What this says in plain words**
Three jobs and one cost.

1. **Authorize the user and check the tenant quota.** Before anything is created.
2. **Persist desired state *before* requesting allocation.** The ordering is the whole point.
   - Worked example of the wrong order: allocate a worker, then record it. The controller crashes between the two. A worker is running that no record mentions, consuming 512 mebibytes indefinitely, and nothing will ever find it.
   - With the right order, a crash leaves a record with no worker, which the reconciler sees and fixes. The failure is visible rather than invisible, which is always the better direction.
3. **Return an operation handle.** The caller gets an identifier immediately and polls, rather than waiting.
4. **The cost: two round trips, and a reconciler is mandatory.**
   - "a reconciler is required because intent and inventory can diverge" states plainly that the reconciler is not optional cleanup. It is a structural consequence of separating intent from inventory, and the design does not work without it.

---

> - Allocator and lifecycle reconciler (control plane)
>   - Turns desired state into worker inventory using session ID plus generation as the operation identity.
>   - Cost: reconciliation loops consume inventory API budget and add a bounded delay to cleanup.

**What this says in plain words**
The component that makes reality match intent, using session identifier plus generation as the identity of every operation.

**Why it matters**
The choice of operation identity is what makes retries safe.

- Worked example: the allocator asks for a worker for session `s-4471` generation 1. The response is lost. It retries with the same identity. The inventory system recognizes the identity and returns the existing worker instead of creating a second.
- Without generation in the identity, a session reallocated after a failure would reuse `s-4471` and could be matched against the old, dead allocation.
- The cost is honest: the loop makes API calls continuously, and cleanup is bounded by loop frequency rather than immediate. Worked example: a loop running every 20 seconds means a worker may live up to 20 seconds past its termination, which is why the requirement says within 60 seconds rather than instantly.

---

> - Isolated worker (data plane)
>   - Executes hostile web content inside the chosen sandbox boundary.
>   - A VM/microVM boundary can reduce shared-kernel exposure compared with a container alone.
>   - The design still requires browser and host patching.
>   - Cost: slower start and higher memory per session than a shared-kernel container.

**What this says in plain words**
Where the dangerous work happens, with two carefully hedged claims.

1. **"can reduce shared-kernel exposure"**, not eliminate. A hypervisor is a smaller attack surface than a kernel, and hypervisor escapes exist.
2. **"still requires browser and host patching"**, which is the line that stops the isolation boundary being oversold.
   - Worked example: a microVM boundary does nothing about an unpatched browser being compromised in the first place. It limits the blast radius to one session. Patching remains the primary defence, and isolation is the containment.
3. **The cost: slower start and more memory.** The reason the warm pool exists.

---

> - Streaming gateway (data plane)
>   - Routes only to the authorized session owner.
>   - Carries interactive traffic without exposing worker management ports.
>   - Holds the session-to-worker binding and policy snapshot, so existing streams survive a controller outage.
>   - Cost: cached bindings mean revocation propagates with snapshot delay, not instantly.

**What this says in plain words**
Three jobs and one cost.

1. **Routes only to the authorized owner.** The enforcement point for the ownership invariant.
2. **Carries interactive traffic without exposing management ports.**
   - Worked example of what is being prevented: if the user's connection reached the worker directly, the worker's management interfaces would be network-reachable from wherever the user is. The gateway exposes exactly one thing, the stream, and nothing else about the worker.
3. **Holds the binding and policy locally**, which is what lets streams survive a controller outage.
4. **The cost: revocation is not instant.**
   - Worked example: an administrator revokes a user's access at 14:00. The gateway is holding a cached binding and policy snapshot. Until the snapshot refreshes, that user's existing stream continues. The bound is the snapshot age, which is why the requirements table ties data-plane independence to the validity period rather than to the outage length.
   - This is the genuine tension in the design: caching buys availability and costs revocation speed, and both matter in a security product.

---

> - Egress proxy (data plane)
>   - Enforces destination policy after DNS resolution and on connection establishment.
>   - Rechecks redirect destinations.
>   - Blocks private/control-plane address ranges for the baseline Internet-only service.
>   - Cost: every outbound connection pays a policy check
>     - The proxy is a shared chokepoint that needs its own capacity plan.

**What this says in plain words**
Four points, and the first is the mechanism the entire security model rests on.

1. **Enforce after DNS resolution, at connection establishment.**
   - The timing is everything, and the isolation section explains why in full. The short version: checking the hostname earlier does not bind the check to the address actually connected to.
2. **Recheck redirects.**
   - Worked example: an allowed site returns a redirect to a blocked destination. Without a recheck, the browser follows it and the policy was bypassed by one HTTP response header.
3. **Block private and control-plane ranges.** The metadata endpoint defence, stated as an address-range rule rather than a URL rule.
4. **The cost: a chokepoint with its own capacity plan.**
   - Worked example: 10,000 sessions each opening perhaps 20 connections per page load, with users navigating every few seconds, is thousands of new connections per second all passing one component. If the proxy saturates, every session's browsing stalls simultaneously.
   - The compensating property, from the failure table, is that the proxy failing means pages fail closed rather than escaping, because there is no other route out.

---

> - Policy service (control plane)
>   - Publishes versioned snapshots to gateways and egress.
>   - Cost: a policy change is eventually consistent across enforcement points.

**What this says in plain words**
Policy is published as numbered snapshots to the two enforcement points, and a change reaches them with a delay.

**Why it matters**
The version number is what makes the delay manageable.

- Worked example: an administrator tightens an allowlist at 14:00, creating version 48. Gateways adopt version 48 over the next snapshot interval. During that window you can say exactly which enforcement points are on 47 and for how long, rather than having an unbounded "eventually".

---

> → Authenticate user and check tenant session quota.  
> → Persist `ALLOCATING` session with a stable create idempotency key.  
> → Allocate a worker and bind it to a session generation.  
> → Load policy and issue a short-lived session-scoped connection token.  
> → Connect the user to the streaming gateway and current worker.  
> → Apply egress and interaction policies during browsing.  
> → On close or expiry, revoke the stream and reconcile worker destruction.

**What this says in plain words**
One session traced end to end. Walked concretely:

User `alice` at tenant `acme` opens an untrusted site.

1. **Authenticate and check quota.**
   - Alice's identity is verified, and `acme` is at 340 of its 500 concurrent sessions, so the request proceeds.
2. **Persist `ALLOCATING` with an idempotency key.**
   - A row is written saying session `s-9912` should exist, before any worker is requested.
   - Worked example of the key: alice's client times out and retries. The same idempotency key finds the existing row and returns session `s-9912` rather than creating a second session and a second worker.
3. **Allocate a worker and bind it to a generation.**
   - A warm worker is taken from the pool, and the binding records session `s-9912`, generation 1, worker `w-3318`.
4. **Load policy and issue a connection token.**
   - Policy version 48 is loaded into the worker's egress rules. A token is issued for session `s-9912`, generation 1, valid 60 seconds, one use.
5. **Connect the user to the gateway and current worker.**
   - The gateway validates the token's signature, its expiry, its single-use status, and its generation against the current binding. All four must pass.
6. **Apply egress and interaction policies while browsing.**
   - Every outbound connection is checked at the proxy. Clipboard and transfers are refused per policy.
7. **On close or expiry, revoke the stream and reconcile destruction.**
   - Two distinct actions: the stream is revoked immediately, and destruction is *reconciled*, meaning the system confirms the worker is actually gone rather than assuming the request succeeded.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Control plane | The path that manages configuration and lifecycle: authorization, allocation, policy. | Its outage stops new sessions, not existing streams. |
| Data plane | The path carrying the user's live session: gateway, worker, egress proxy. | Must survive a control-plane outage within cached validity. |
| Desired state | What should exist, recorded durably before anything is created. | Writing it first makes a crash leave a visible gap rather than an invisible orphan. |
| Operation handle | An identifier returned immediately for work completing later. | Makes allocation asynchronous. |
| Operation identity | The `(session, generation)` pair naming an allocation request. | Makes a retried allocation return the existing worker. |
| Reconciler | A loop comparing desired state against observed inventory and acting on the difference. | Structurally required, not optional cleanup. |
| Inventory API | The interface reporting which workers actually exist. | Observed state, which may lag or contain orphans. |
| Sandbox boundary | The isolation mechanism containing hostile code. | Reduces exposure; it does not replace patching. |
| Management port | An administrative interface on a worker. | Never exposed to the user's connection. |
| Session-to-worker binding | The record of which worker currently serves a session. | Cached at the gateway so streams survive a controller outage. |
| Snapshot delay | The bounded lag before a policy or binding change reaches an enforcement point. | The price of caching, and it slows revocation. |
| Connection-time enforcement | Checking policy when the outbound connection is made, against the resolved address. | The only check that cannot be bypassed by DNS tricks. |
| Redirect recheck | Re-applying policy to a destination reached via a redirect. | Without it, one response header bypasses the allowlist. |
| Control-plane address range | Internal cloud addresses, including the metadata endpoint. | Blocked outright in the Internet-only baseline. |
| Chokepoint | A single component every request must pass. | Enforces policy absolutely, and needs its own capacity plan. |
| Fail closed | Denying traffic when the enforcement point is unavailable. | What happens when the proxy is down, because no other route exists. |
| Idempotency key | A caller-supplied string making a repeated create request safe. | Stops a timeout producing two sessions and two workers. |
| Generation | A counter identifying one incarnation of a session. | Part of the binding and of every token. |

## API and data model — IC3 baseline

The interface table, the state table, the reference SQL, what it omits, the state machine, and the conventions.

---

> | Surface | Contract | Conflict/error behavior |
> |---|---|---|
> | `POST /v1/sessions` | URL, desired region; returns session/operation ID with `202` | Same idempotency key plus different normalized request returns `409`; over quota returns `429` |
> | `GET /v1/sessions/{id}` | Lifecycle and connection readiness | `404` for another tenant's ID; owner/administrator authorization |
> | `POST /v1/sessions/{id}:connect` | Short-lived audience-bound connection token | `409` if the session is not `READY` or `DISCONNECTED`; token bound to generation and expiry |
> | `DELETE /v1/sessions/{id}` | Request termination with `202` | Idempotent; cannot revive an expired generation |
> | `GET /v1/operations/{id}` | Allocation/termination result | Distinguish accepted intent from ready worker or observed destruction |

**What this says in plain words**
Five interfaces: create, read, connect, delete, and check an operation.

- **Row: `POST /v1/sessions`.**
  - Returns `202` with an identifier, because allocation takes seconds.
  - "Same idempotency key plus different normalized request returns `409`."
    - Worked example: a client retries with key `k-882` but a different target URL. Returning the original session would silently give the user a session for the wrong site. Detecting the mismatch and returning a conflict is the honest behavior.
    - *Normalized* matters: the comparison is against a canonical form, so trivial differences like parameter order do not create spurious conflicts.
  - `429` over quota, which is the per-tenant concurrency limit being enforced at the door.
- **Row: `GET /v1/sessions/{id}`.**
  - `404` for another tenant's identifier, not `403`. `403` would confirm the session exists, which leaks that another tenant has a session with that identifier.
- **Row: `POST /v1/sessions/{id}:connect`.**
  - Issues a short-lived, audience-bound token. *Audience-bound* means the token names which gateway may accept it, so a token captured by one component cannot be replayed to another.
  - `409` unless the session is `READY` or `DISCONNECTED`. Those two are precisely the states where a connection makes sense: freshly ready, or within the reconnect grace.
  - Worked example of the state check mattering: a connect request for a `TERMINATING` session. Issuing a token would let a user attach to a worker that is being destroyed, mid-destruction.
- **Row: `DELETE /v1/sessions/{id}`.**
  - `202`, because destruction is also asynchronous. "cannot revive an expired generation" means deleting an already-gone session is a no-op rather than resurrecting anything.
- **Row: `GET /v1/operations/{id}`.**
  - "Distinguish accepted intent from ready worker or observed destruction" is the key phrase, and it recurs throughout the file.
  - Worked example: the operation may report accepted, meaning the request was recorded; ready, meaning a worker exists and is healthy; or destroyed, meaning the worker's absence was confirmed. Collapsing these into "done" is precisely the bug the lifecycle section warns about.

---

> | State | Key | Fields and invariant |
> |---|---|---|
> | Session | `(tenant_id, session_id)` | Owner, desired/observed state, worker ID, generation, expiry |
> | Worker assignment | `worker_id` | At most one live session assignment per worker |
> | Create dedup | `(tenant_id, idempotency_key)` | Request hash and resulting session ID |
> | Policy | `(tenant_id, policy_version)` | Allowed destinations, transfer permissions, session limits |
> | Connection ticket | `(tenant_id, ticket_hash)` | Session ID, generation, expiry, `consumed_at`; one use |
> | Lifecycle outbox | `event_id` | Session ID, expected generation, desired action |

**What this says in plain words**
Six kinds of state, and two of the keys carry the design's central properties.

- **Row: Session.** Holds *both* desired and observed state in one row, which is what lets the reconciler see a divergence by reading a single record.
- **Row: Worker assignment, keyed by `worker_id` alone.**
  - The key choice *is* the invariant: one row per worker means at most one session can be assigned to it, enforced by the database rather than by careful code.
  - Worked example of the bug this makes impossible: two concurrent allocations both pick warm worker `w-3318`. The second insert violates the primary key and fails, so one allocation retries with a different worker. Without this key, two sessions could share a worker and see each other's browsing.
- **Row: Create dedup.** Keyed by tenant and idempotency key, holding the request hash so a mismatched retry is detectable.
- **Row: Policy.** Versioned per tenant.
- **Row: Connection ticket, keyed by `ticket_hash`.**
  - The *hash*, never the ticket. Worked example of why: if the table stored ticket values, anyone with read access to the database could use them to connect to live sessions. Storing only a hash means the table can verify a presented ticket and cannot produce one.
- **Row: Lifecycle outbox.** Carries the *expected* generation, which is what makes a queued action safe to deliver late.

---

> - Reference DDL
>   - Keys and uniqueness match the state table above and the [companion schema](../../1sde/1.backend/2.rest102.md#infra-6).
>   - Worker inventory, encoder state, input sequence, and frame queues are runtime state on the worker and gateway; only sessions, assignments, tickets, policy, and the outbox are relational.

**What this says in plain words**
The SQL covers the durable control state. Everything to do with the live stream is runtime state on the worker and gateway, named explicitly so the reader does not look for it.

---

> ```sql
> CREATE TABLE policies (
>   tenant_id text NOT NULL, policy_version bigint NOT NULL CHECK (policy_version >= 1),
>   allowed_destinations jsonb NOT NULL,      -- normalized URL/egress rules, re-checked at connect time
>   transfer_permissions jsonb NOT NULL,      -- download, upload, clipboard directions
>   max_sessions integer NOT NULL CHECK (max_sessions >= 0),
>   created_at timestamptz NOT NULL,
>   PRIMARY KEY (tenant_id, policy_version)
> );
> ```

**What this says in plain words**
Policy rows are versioned and immutable: a change creates a new version rather than editing an existing one.

- **`allowed_destinations`** with the comment "re-checked at connect time", naming where enforcement happens at the point of definition.
- **`transfer_permissions`** covering download, upload, and clipboard as *directions*, because each direction is a separate decision. Worked example: an organization may allow uploads to a partner site while forbidding downloads from anywhere, and clipboard out but not in.
- **`max_sessions CHECK (>= 0)`.** Zero is allowed and meaningful: it disables the service for a tenant without deleting their configuration.
- **Versioned primary key** makes policy history immutable, so you can always answer which policy a given session was created under.

---

> ```sql
> CREATE TABLE sessions (
>   tenant_id text NOT NULL, session_id text NOT NULL, owner_id text NOT NULL,
>   policy_version bigint NOT NULL,
>   desired_state text NOT NULL CHECK (desired_state IN ('READY','CLOSED')),
>   observed_state text NOT NULL
>     CHECK (observed_state IN ('ALLOCATING','READY','DISCONNECTED','TERMINATING','CLOSED')),
>   worker_id text,                           -- null until a worker is bound
>   generation bigint NOT NULL CHECK (generation >= 1),
>   expires_at timestamptz NOT NULL, version bigint NOT NULL,
>   PRIMARY KEY (tenant_id, session_id),
>   FOREIGN KEY (tenant_id, policy_version) REFERENCES policies
> );
> CREATE INDEX sessions_owner ON sessions (tenant_id, owner_id, observed_state, session_id);
> CREATE INDEX sessions_expiry ON sessions (expires_at)
>   WHERE observed_state IN ('READY','DISCONNECTED');
> CREATE INDEX sessions_reconcile ON sessions (observed_state, session_id)
>   WHERE observed_state IN ('ALLOCATING','TERMINATING');
> ```

**What this says in plain words**
The central table, and the split between desired and observed state is its most important feature.

- **`desired_state` has two values; `observed_state` has five.**
  - Desired is what someone asked for: the session should be ready, or it should be closed. There is no intermediate intent.
  - Observed is where reality currently stands, including the transitional states.
  - Worked example of the pair in use: desired `CLOSED` with observed `TERMINATING` means a termination is in progress. Desired `READY` with observed `ALLOCATING` means a creation is in progress. The reconciler's entire job is to read a row and drive observed toward desired.
- **`worker_id` nullable**, because a session exists before a worker is bound, which is the ordering the controller enforces.
- **`generation CHECK (>= 1)`**, starting at 1 so zero is never a valid generation and cannot be produced by an uninitialized field.
- **`version bigint`** for compare-and-set on updates, separate from the generation. Two different counters: version detects concurrent edits to the row, generation identifies incarnations of the session.
- **`sessions_owner` on `(tenant_id, owner_id, observed_state, session_id)`.** Serves "what sessions does this user currently have?", which is the quota check and the user's own view.
- **`sessions_expiry`, a partial index** on `expires_at`, covering only `READY` and `DISCONNECTED` rows.
  - Worked example of why partial: the expiry sweeper only cares about sessions that can expire. Closed sessions never can. A full index would grow with all history; this one stays proportional to live sessions.
- **`sessions_reconcile`, a partial index** on the two transitional states.
  - The reconciler's work queue as an index. Worked example: 10,000 sessions of which 40 are mid-transition. The reconciler reads 40 rows per pass instead of scanning 10,000.

---

> ```sql
> CREATE TABLE worker_assignments (
>   worker_id text NOT NULL, tenant_id text NOT NULL, session_id text NOT NULL,
>   generation bigint NOT NULL, assigned_at timestamptz NOT NULL,
>   PRIMARY KEY (worker_id),                  -- at most one live session per worker
>   UNIQUE (tenant_id, session_id, generation),
>   FOREIGN KEY (tenant_id, session_id) REFERENCES sessions
> );
> ```

**What this says in plain words**
The binding table, with two uniqueness rules enforcing two different properties.

1. **`PRIMARY KEY (worker_id)`**: a worker serves at most one session. The isolation property, enforced by the database.
2. **`UNIQUE (tenant_id, session_id, generation)`**: one generation of a session has at most one worker.
   - Worked example of what this catches: a retried allocation that got through and produced a second worker for the same generation. The second insert conflicts, so the duplicate is detected at the moment it would be recorded rather than discovered later as an orphan.
- Together they make the relationship strictly one-to-one per generation, in both directions, which is exactly the property the isolation argument needs.

---

> ```sql
> CREATE TABLE session_create_dedup (
>   tenant_id text NOT NULL, idempotency_key text NOT NULL,
>   request_hash text NOT NULL, session_id text NOT NULL,
>   expires_at timestamptz NOT NULL,          -- retained past the client retry horizon
>   PRIMARY KEY (tenant_id, idempotency_key),
>   FOREIGN KEY (tenant_id, session_id) REFERENCES sessions
> );
> CREATE INDEX session_create_dedup_expiry ON session_create_dedup (expires_at);
> ```

**What this says in plain words**
The create-deduplication table.

- **`request_hash`** is what turns a plain idempotency key into a safe one, by detecting a key reused for different content.
- **`expires_at`** with "retained past the client retry horizon".
  - Worked example of getting it wrong: the record expires after 60 seconds, but the client library retries for up to 5 minutes. A retry at 3 minutes finds no record and creates a second session with a second worker. The retention must exceed the longest retry the clients actually perform.

---

> ```sql
> CREATE TABLE connection_tickets (
>   tenant_id text NOT NULL, ticket_hash text NOT NULL,   -- hash only, never the ticket
>   session_id text NOT NULL, generation bigint NOT NULL,
>   expires_at timestamptz NOT NULL, consumed_at timestamptz,
>   PRIMARY KEY (tenant_id, ticket_hash),
>   FOREIGN KEY (tenant_id, session_id) REFERENCES sessions
> );
> CREATE INDEX connection_tickets_expiry ON connection_tickets (expires_at) WHERE consumed_at IS NULL;
> ```

**What this says in plain words**
The one-use token table, with three independent restrictions stored as three fields.

- **`ticket_hash`** only, with the comment repeated from the state table because it is a rule that must not be relaxed.
- **`generation`** stored with the ticket, which is what the gateway compares against the current binding.
- **`consumed_at` nullable.** Null means unused. Setting it is the single-use enforcement.
  - Worked example of the race: two requests present the same ticket simultaneously. The conditional update setting `consumed_at` succeeds for exactly one of them, and the loser is rejected. The atomicity comes from the database, not from a check-then-act sequence in the gateway.
- **`connection_tickets_expiry`, a partial index** on unconsumed tickets only, so the cleanup job sees a small set.

---

> ```sql
> CREATE TABLE lifecycle_outbox (
>   event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
>   tenant_id text NOT NULL, session_id text NOT NULL,
>   expected_generation bigint NOT NULL,      -- reconciler CAS target; a bumped generation makes the event a no-op
>   desired_action text NOT NULL CHECK (desired_action IN ('ALLOCATE','TERMINATE')),
>   created_at timestamptz NOT NULL, sent_at timestamptz,
>   FOREIGN KEY (tenant_id, session_id) REFERENCES sessions
> );
> CREATE INDEX lifecycle_outbox_unsent ON lifecycle_outbox (event_id) WHERE sent_at IS NULL;
> ```

**What this says in plain words**
A durable queue of actions the reconciler should take, written in the same transaction as the state change that requires them.

- **`expected_generation`** with the comment "a bumped generation makes the event a no-op". This is the most elegant line in the schema.
  - Worked example: an `ALLOCATE` event is queued for session `s-9912` generation 1. Before it is processed, the session is invalidated and reallocated at generation 2. When the stale event finally runs, its expected generation of 1 does not match the current 2, so it does nothing. No cancellation mechanism is needed; the generation makes stale work harmless by construction.
- **`desired_action` restricted to two values.** Allocate and terminate, matching the two desired states.
- **`sent_at` nullable**, with a partial index on unsent rows, so the drain query reads only pending work regardless of how much history exists.

---

> - Not captured by the DDL
>   - Observed worker inventory comes from the inventory API; `worker_assignments` is the intended binding, and the reconciler compares the two.
>   - Ticket values, WebRTC/WebSocket stream state, and sandbox cookies or disks never reach SQL.
>   - Deviation from the companion: table names follow this file (`sessions`, `connection_tickets`), states are `ALLOCATING`/`CLOSED` rather than `PROVISIONING`/`TERMINATED`, and `policies`, `worker_assignments`, `session_create_dedup`, and `lifecycle_outbox` are added because the state table names them.

**What this says in plain words**
Three notes.

1. **The assignments table is intent, not observation.** Worked example of the distinction: a row says worker `w-3318` serves session `s-9912`. The inventory API says `w-3318` no longer exists. The row was never wrong about intent; reality diverged, and finding that divergence is the reconciler's job.
2. **Ticket values, stream state, and sandbox contents never reach SQL.** The security-relevant absence: the database never holds anything that could be used to impersonate a session or recover a user's browsing.
3. **The companion deviations**, listed with the reason: the state names differ, and four tables are added because this file's state table names them.

---

> - State machine
>
> → `ALLOCATING` becomes `READY` only after worker health and policy loading succeed.  
> → `READY` becomes `DISCONNECTED` during the reconnect grace interval.  
> → A valid reconnect returns the same generation to `READY`.  
> → Closure, expiry, or revoked access enters `TERMINATING`.  
> → Confirmed worker destruction enters `CLOSED`.

**What this says in plain words**
Five transitions, and each carries a precondition that is the actual content.

1. **`ALLOCATING` → `READY` only after health and policy both succeed.**
   - Worked example of the alternative: marking ready when the worker starts. The user connects to a browser whose egress policy has not loaded yet, so its first outbound connections are unfiltered. The precondition closes a window measured in hundreds of milliseconds during which the product does not work.
2. **`READY` → `DISCONNECTED` during the grace interval.** A distinct state, not a deletion, which is what allows return.
3. **A valid reconnect returns the *same generation* to `READY`.**
   - The generation does not advance on reconnect, which is what lets the user rejoin the same worker with their page intact.
4. **Closure, expiry, or revoked access enters `TERMINATING`.** Three different causes, one state, because the cleanup is identical.
5. **Confirmed destruction enters `CLOSED`.**
   - *Confirmed*, not requested. The single most important word in the state machine, and the lifecycle section explains exactly what goes wrong without it.

---

> - Conventions
>   - Every state transition is a compare-and-set on `(session_id, generation, version)`.
>   - `202` plus an operation ID is the pattern for allocation and termination
>   - The operation reports observed state, not intent.

**What this says in plain words**
Two rules applying everywhere.

1. **Every transition is a compare-and-set on three fields.**
   - Compare-and-set means the update applies only if the row still matches the values you read.
   - Worked example: the reconciler reads session `s-9912` at generation 1, version 7, and tries to set observed state to `READY` only if it is still generation 1 and version 7. If anything changed in between, the update affects zero rows and the reconciler re-reads. No locks, and no lost updates.
2. **`202` plus an operation identifier, and the operation reports observed state.**
   - Worked example of the discipline: polling a termination operation returns "terminating" until destruction is confirmed, then "destroyed". It never returns "destroyed" because the request was accepted. The API refuses to report intent as if it were reality, which is the same principle as the `CLOSED` precondition.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| `202` | The HTTP status meaning accepted for processing, not completed. | Allocation and termination are both asynchronous. |
| `409` | The HTTP status meaning conflict. | A reused idempotency key with different content, or a connect in the wrong state. |
| `429` | The HTTP status meaning too many requests. | Returned when a tenant is at its concurrency quota. |
| `404` versus `403` | Not found versus forbidden. | `403` would confirm another tenant's session exists. |
| Normalized request | A canonical form of a request used for comparison. | Stops trivial differences producing false conflicts. |
| Audience-bound token | A token naming which component may accept it. | Prevents replay to a different component. |
| Desired versus observed state | What was asked for, versus where reality currently is. | Both in one row, so a divergence is visible in a single read. |
| Generation | A counter identifying one incarnation of a session. | Advanced on reallocation; unchanged on reconnect. |
| Version | A counter for detecting concurrent edits to a row. | Distinct from generation; used for compare-and-set. |
| Compare-and-set | An update that applies only if the row still matches what was read. | Concurrency control without locks. |
| Partial index | An index covering only rows matching a condition. | Keeps expiry and reconciliation queues small regardless of history. |
| Ticket hash | A fingerprint of a token, stored instead of the token. | The table can verify a ticket and cannot produce one. |
| `consumed_at` | The timestamp a one-use ticket was redeemed. | Null means unused; setting it atomically enforces single use. |
| Outbox | A durable queue written in the same transaction as the state change requiring it. | Survives a crash between deciding and acting. |
| Expected generation | The generation an outbox event was written for. | A newer generation makes the stale event a harmless no-op. |
| Immutable versioned policy | Policy rows that are added rather than edited. | Lets you answer which policy a session ran under. |
| Transfer direction | Download, upload, and clipboard treated as separate permissions. | Each is a distinct data path with its own risk. |
| Confirmed destruction | Observing that a worker is gone, rather than that termination was requested. | The precondition for `CLOSED`. |

## Isolation and session ownership — IC3 baseline

The first deep dive. Treating the worker as hostile, destination checks, session affinity, connection tokens, and transfer policies.

---

> - Treat the browser worker as potentially compromised.
>   - Do not give it tenant-wide cloud credentials.
>   - Deny cloud instance metadata access unless a tightly scoped broker explicitly needs it.
>   - Separate worker and control-plane networks.
>   - Apply CPU, memory, process, and network limits.
>   - Concrete assumption: `2 vCPU`, `512 MiB`, and a per-session egress cap enforced at the proxy.

**What this says in plain words**
The governing assumption, then four consequences.

1. **No tenant-wide cloud credentials.**
   - Worked example: if the worker holds a credential that can list a tenant's storage buckets, a single browser compromise reads that tenant's data. The worker needs to render a web page; it needs no cloud permissions at all.
2. **Deny instance metadata access.**
   - The metadata endpoint is a fixed internal address that returns credentials for the machine's identity, with no authentication, because being on the machine is the authentication.
   - Worked example of the attack in full: a hostile page causes the browser to fetch the metadata address and reads the response through ordinary scripting. It now holds the worker's cloud identity. No exploit, no memory corruption, just a URL that the browser was willing to fetch.
   - "unless a tightly scoped broker explicitly needs it" is the escape hatch: if something genuinely needs a credential, a separate small component fetches it and hands over only the narrow thing required, so the worker never touches metadata itself.
3. **Separate worker and control-plane networks.**
   - Worked example: the worker is on a network with no route to the controller, the session database, or the allocator. A compromised worker cannot reach them even if it obtains credentials, because there is no path. Network separation and credential separation are two independent defences, and the design uses both.
4. **CPU, memory, process, and network limits.**
   - Worked example of the attack these stop: a page that opens thousands of processes or allocates unbounded memory. Without limits it exhausts the host and degrades every co-located session. With limits it exhausts its own quota and is throttled or terminated.
   - The concrete figures, 2 virtual CPUs, 512 mebibytes, and a per-session egress cap, make the limits checkable rather than aspirational.

**Why it matters**
The structure is layered defence: even with a browser compromise, the attacker has no credentials, no network path to the control plane, and no way to consume more than one session's resources. Each layer assumes the previous one failed.

---

> - Destination checks
>   - Parse and normalize the URL at the policy boundary.
>   - Resolve through controlled DNS.
>   - Enforce the resolved destination at the egress connection.
>   - Reapply checks after redirects and reconnects to prevent DNS-rebinding bypass.
>   - A URL allowlist checked once at navigation is not egress control
>   - The connection-time check is the mechanism.

**What this says in plain words**
Four steps in a required order, then a flat statement about what does not work.

1. **Parse and normalize the URL.**
   - Worked example of why normalization is not cosmetic: `http://example.com@evil.com/` looks like it points at `example.com` and actually connects to `evil.com`, because everything before the `@` is a username. Percent-encoding, unicode lookalikes, and unusual port syntax all create similar confusions. Normalization resolves the URL to its true components before any comparison.
2. **Resolve through controlled DNS.** A resolver you operate, so the answers can be logged, restricted, and not poisoned by the worker.
3. **Enforce the *resolved destination* at the egress connection.** The address actually being connected to, at the moment of connection.
4. **Reapply after redirects and reconnects.**

**The DNS rebinding attack, in full, because it is what the ordering exists to defeat:**

→ A hostile page navigates to `attacker.example`, which is not on any blocklist.  
→ Your resolver asks for its address and the attacker's DNS server answers `93.184.216.34`, a perfectly ordinary public address, with a time-to-live of 1 second.  
→ The URL check passes, because the hostname is allowed and the address is public.  
⇒ One second later the cached answer expires.  
→ The browser resolves the same hostname again and this time receives `169.254.169.254`, the metadata address.  
→ The browser connects there, because as far as it is concerned this is the same allowed site.  
⇒ Without a connection-time check, the policy decision made one second ago is applied to a completely different destination.

- The defence is the ordering: the check is bound to the address the connection actually goes to, at the moment it goes there. A hostname that resolves somewhere forbidden is blocked on that connection regardless of what it resolved to earlier.

**Why the last two lines are stated so bluntly**
"A URL allowlist checked once at navigation is not egress control" is a direct refutation of the intuitive design. Checking the URL feels like enforcement and is not, because the thing being checked, a hostname, is not the thing that determines where the packets go.

---

> - Session affinity
>   - Browser memory and cookies live in one worker.
>   - A replacement gateway may reconnect to that same worker.
>   - A failed worker loses volatile page state.
>   - Restarting a worker does not transparently recreate a live session.

**What this says in plain words**
Four consequences of where the state lives.

1. **Everything is in one worker.** Memory, cookies, open tabs, scroll position, form contents, and login state.
2. **A replacement gateway can reconnect to the same worker.** The gateway is stateless with respect to the session, so losing one is survivable.
   - Worked example: the gateway serving alice fails. A different gateway looks up the binding, finds worker `w-3318`, validates a new ticket, and reconnects. Alice sees a brief interruption and her page is intact.
3. **A failed *worker* loses everything.** No replacement can recover it.
4. **Restarting does not recreate the session.**
   - Worked example of the tempting wrong idea: "restart the worker and reopen the same URL". The user would get a fresh page at the same address, without their login, their form data, or their scroll position. That is a new session wearing the old one's name, and presenting it as a recovery would be misleading.

**Why it matters**
The asymmetry is the point: gateway failure is recoverable, worker failure is not. It follows directly from which component holds the state, and it explains the availability target, the reconnect grace, and why regional failover is a visible reset.

---

> - Connection tokens
>   - Keep lifetime short and audience specific.
>   - Validate the current session generation.
>   - A stale token cannot attach to a recycled worker address.
>   - Possession of a session ID alone never grants access.
>   - Exact failure: a gateway that validates the token signature but not the generation lets a `60 s`-old ticket reach whichever session now owns the recycled worker.

**What this says in plain words**
Four rules and the exact failure if one is missed.

1. **Short lifetime and audience-specific.** 60 seconds, and naming which gateway may accept it.
2. **Validate the current generation**, not merely that the token is well-formed.
3. **A stale token cannot attach to recycled capacity.** The property the previous rule delivers.
4. **A session identifier alone is never access.** Identifiers appear in logs, in support tickets, and in browser history. They are names, not credentials.

**The exact failure, walked through:**

| Time | Event |
|---|---|
| 14:00:00 | Alice's session `s-9912` generation 1 is on worker `w-3318`. A ticket is issued. |
| 14:00:10 | Alice's session ends. Worker `w-3318` is destroyed and its address returns to the pool. |
| 14:00:35 | Bob's session `s-5580` generation 1 is allocated and lands on a new worker at the same address. |
| 14:00:50 | Alice's client reconnects using the ticket issued at 14:00:00, still within its 60-second life. |

- **With signature validation only:** the ticket is genuine and unexpired, so the gateway accepts it and connects alice to the worker at that address, which is now bob's session. Alice sees bob's screen.
- **With generation validation:** the ticket names session `s-9912` generation 1. The gateway checks the current binding for the worker and finds session `s-5580` generation 1. They do not match, so the connection is refused.
- The token was never forged. Every cryptographic check passed. The failure is entirely about binding a credential to a *specific incarnation* rather than to a well-formed claim.

**Why it matters**
It is the clearest example in the file of a security bug that no amount of cryptography prevents. The signature proves the token was issued by you; it says nothing about whether the thing it names still exists.

---

> - Transfer policies
>   - Downloads enter quarantine and policy/scanning before endpoint delivery.
>   - Uploads have size and type limits.
>   - Clipboard directions are independently controlled.
>   - Pixel rendering does not prevent a user from typing credentials into a phishing page.

**What this says in plain words**
Three transfer rules and one honest limitation.

1. **Downloads are quarantined and scanned before reaching the endpoint.**
   - Worked example of why the isolation does not cover this: the entire product exists to stop hostile content reaching the laptop. A download is hostile content reaching the laptop, by request. The file must be held, inspected, and released by policy, or the download path is a hole straight through the boundary.
2. **Uploads have size and type limits.** The reverse direction: corporate data leaving to an untrusted site.
3. **Clipboard directions are independently controlled.**
   - Worked example: an organization may allow copying *into* the isolated session, so users can paste a URL, while forbidding copying *out*, so page content cannot be extracted. Two separate permissions for what feels like one feature.
4. **Pixel rendering does not prevent phishing.**
   - The limitation that must be stated. Worked example: a user visits a convincing fake login page inside the isolated session and types their corporate password. The isolation worked perfectly: no code reached their laptop. The credential was still stolen, because the user typed it and the keystrokes were forwarded to the remote session by design.
   - The system defends against *code* crossing the boundary. It cannot defend against a human being deceived, and claiming otherwise is the over-engineering warning later in the file.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Compromised worker | The assumption that hostile code is already running in the worker. | The premise every rule in this section follows from. |
| Instance metadata endpoint | A fixed internal address returning cloud credentials with no authentication. | Reachable by a plain fetch, so it must be blocked at egress. |
| Credential broker | A small separate component that fetches a credential and hands over only what is needed. | The narrow exception to blocking metadata. |
| Network separation | Placing workers on a network with no route to the control plane. | A second defence independent of credentials. |
| Resource limits | Caps on CPU, memory, processes, and bandwidth per session. | Stop one hostile page degrading co-located sessions. |
| URL normalization | Resolving a URL to its true components before comparison. | Defeats confusions like `http://good.com@evil.com/`. |
| Controlled DNS | A resolver you operate, whose answers can be logged and restricted. | Step two of the destination check. |
| Resolved destination | The actual address a connection will go to. | The only thing worth enforcing on. |
| Connection-time enforcement | Applying policy at the moment the outbound connection is established. | The mechanism; a navigation-time URL check is not. |
| DNS rebinding | A hostname resolving to an allowed address during a check and a forbidden one at connection. | The attack that makes connection-time checks mandatory. |
| Time-to-live | How long a DNS answer may be cached. | A very short one is what makes rebinding fast enough to matter. |
| Session affinity | A session's traffic always reaching the same worker. | Required because the state exists only there. |
| Volatile page state | Browser memory, cookies, tabs, and form contents. | Lost when the worker dies, and unrecoverable. |
| Audience-specific token | A token naming which component may accept it. | Prevents replay to a different component. |
| Generation validation | Checking that a token's named incarnation matches the current binding. | The check that prevents attaching to recycled capacity. |
| Recycled address | A worker address returned to the pool and reassigned to a new session. | The reason a valid token can point at the wrong session. |
| Quarantine | Holding a downloaded file for inspection before releasing it. | The download path would otherwise cross the boundary. |
| Clipboard direction | Copy-in and copy-out treated as separate permissions. | One may be allowed while the other is not. |
| Phishing | Deceiving a person into revealing credentials. | Not mitigated by isolation, and the claim must not be made. |

## Lifecycle reconciliation — IC3 baseline

The second deep dive. The reconcile pseudocode, the consistency boundary, concurrency, why sessions are not reused, and the exact failure.

---

> ```text
> RECONCILE(session):
>     read desired state, generation, and current reconciler owner epoch
>     if allocating and no matching worker exists:
>         allocate using session ID + generation as operation identity
>     if duplicate workers exist:
>         retain one valid assignment and terminate extras
>     if terminating or expired:
>         revoke connect tokens / routing
>         terminate all workers for this generation
>         conditionally mark closed only after destruction is observed
>         require the same session generation and current reconciler owner epoch
> ```

**What this says in plain words**
One pass of the reconciliation loop, handling three cases.

1. **Read desired state, generation, and the reconciler owner epoch.**
   - The epoch is a fencing token for the reconciler itself. Worked example of why it is needed: two reconciler instances both believe they are active after a network partition. Without an epoch, both act on the same sessions, terminating and allocating in conflict. With one, only the holder of the current epoch may write.
2. **Allocating with no matching worker: allocate, using session identifier plus generation as the operation identity.**
   - The identity makes the allocation request itself idempotent. Worked example: the loop runs every 20 seconds, and an allocation that is genuinely in flight takes 25. The second pass reissues the request with the same identity, and the inventory system returns the existing worker rather than creating a second.
3. **Duplicate workers exist: retain one valid assignment, terminate the extras.**
   - The self-healing case for the leak described at the top of the file. Worked example: a lost response caused two workers for generation 1. The pass keeps the one recorded in the assignment table and terminates the other.
4. **Terminating or expired: four steps, in a deliberate order.**
   - **Revoke connect tokens and routing first.** Before destroying anything, make it impossible to reach.
     - Worked example of the wrong order: terminate the worker, then revoke routing. In the gap, a reconnect attempt reaches a half-destroyed worker, or the routing entry points at an address about to be reassigned.
   - **Terminate all workers for this generation.** Plural, because duplicates may exist.
   - **Conditionally mark closed only after destruction is observed.** The precondition that the whole section is about.
   - **Require the same generation and the current epoch.** The write is conditional on both, so a stale pass cannot close a session that has since moved on.

---

> - Consistency boundary
>   - The session table holds desired state and is the source of truth.
>   - Worker inventory is observed state and may lag or contain orphans.
>   - The reconciler is the only writer that moves observed state toward desired state.

**What this says in plain words**
Three statements defining who is authoritative about what.

1. **The session table is the source of truth for intent.** What should exist.
2. **Worker inventory is observation.** What does exist, possibly stale, possibly containing things nothing points at.
3. **One writer.** The reconciler alone moves observation toward intent.

**Why it matters**
The single-writer rule is what makes the system analyzable.

- Worked example of multiple writers: the controller terminates a worker directly on a `DELETE`, and the reconciler also terminates workers it finds orphaned, and an expiry sweeper terminates expired ones. Three components acting on the same worker with no coordination. Two may terminate the same worker while a third allocates a replacement, and the resulting behavior depends on timing.
- With one writer, every change to inventory has one cause, one ordering, and one place to look when it goes wrong. Other components change *desired* state, which is a database row, and let the reconciler act.

---

> - Concurrency
>   - Each reconcile pass is a compare-and-set on the session generation.
>   - Reconnecting to the same live worker keeps the session generation and consumes a fresh one-use connection ticket.
>   - Reallocation or security invalidation advances the generation and fences old workers and tickets.

**What this says in plain words**
Three rules about when the generation changes, and it is the most important distinction in the section.

1. **Each pass is a compare-and-set on the generation.** A pass that started under generation 1 cannot write if the session has moved to generation 2.
2. **Reconnect keeps the generation, and consumes a fresh ticket.**
   - Worked example: alice's network drops for 8 seconds. Her session is still generation 1 on worker `w-3318` with her page intact. She requests a new ticket, which is issued for generation 1, and reconnects to the same worker. The generation did not move, because the session itself did not change.
   - A fresh ticket each time is what makes the one-use rule meaningful: reconnecting is not reusing.
3. **Reallocation or security invalidation advances the generation, fencing old workers and tickets.**
   - Worked example of reallocation: worker `w-3318` crashes. A new worker is allocated at generation 2. Every ticket naming generation 1 is now invalid, and any writes from the old worker carrying generation 1 are rejected.
   - Worked example of security invalidation: an administrator revokes alice's access. Advancing the generation immediately invalidates every outstanding ticket without having to find and delete them individually.

**Why the distinction matters**
It is the difference between a session continuing and a session being replaced.

- Continuing: same generation, same worker, same page, new ticket.
- Replaced: new generation, new worker, lost page, everything from before fenced off.
- A design that advanced the generation on every reconnect would destroy a user's page on every network blip. One that never advanced it could not fence a compromised or replaced worker.

---

> - No session reuse before destruction/clean reset is established.
>   - Reprovisioning an ephemeral worker is easier to defend than best-effort deletion of profile files.
>   - Persistent profiles need separate encrypted tenant-scoped storage and a defined retention policy.

**What this says in plain words**
Capacity is not reused until the previous occupant is provably gone.

1. **Reprovisioning beats deletion, and the argument is about what can be defended.**
   - Worked example of best-effort deletion: end a session, delete the browser profile directory, cached files, and local storage, then hand the worker to the next user. To claim safety you must argue that you found every location the browser wrote to, that nothing survives in memory, that no temporary file was missed, and that this remains true after every browser update.
   - Worked example of reprovisioning: destroy the entire environment and create a fresh one. The argument is that a destroyed virtual machine's memory and disk are gone. That is one claim about one mechanism, and it stays true when the browser changes.
   - The general principle: prefer a security property you can state in one sentence over one requiring an exhaustive enumeration.
2. **Persistent profiles, if ever added, need their own encrypted tenant-scoped storage and a retention policy.**
   - Not stored on shared workers. A separate, deliberately designed store, because the moment data outlives a session it becomes data you are holding on someone's behalf.

---

> - Exact failure
>   - Marking `CLOSED` when the terminate request is accepted, rather than when destruction is observed, lets the allocator reuse a worker that still holds the previous session's cookies.
>   - The reconciler therefore treats a `202` from the inventory API as intent and polls for the observed result.

**What this says in plain words**
The precise consequence of confusing a request with its effect.

**The failure, walked through:**

| Time | Event |
|---|---|
| 14:00:00 | Alice's session ends. The reconciler sends a terminate request for worker `w-3318`. |
| 14:00:00 | The inventory API returns `202`, meaning the request was accepted. |
| 14:00:00 | The session is marked `CLOSED` and `w-3318` returns to the available pool. |
| 14:00:01 | The termination has not actually happened. The host is busy, or the request is queued. |
| 14:00:02 | Bob's session is allocated and assigned `w-3318`. |
| 14:00:02 | Bob connects to a worker still running alice's browser, with her cookies and her logged-in sessions. |

- Bob is now inside alice's browsing session. Every isolation mechanism in the design worked correctly. The failure is a single state transition made one step too early.
- The fix is stated plainly: treat `202` as intent and poll for the observed result. The session becomes `CLOSED` only when the inventory API confirms the worker no longer exists.

**Why it matters**
It is the concrete justification for the recall card line "closed means destruction was observed, not requested", and it shows the same pattern as the generation-validation failure in the previous section: a credential or state that is perfectly valid in form and wrong about reality.

- The general lesson worth stating aloud: in a distributed system, an accepted request and a completed effect are different facts, and any state machine that treats them as the same one will eventually reuse something it should not have.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Reconciliation loop | A repeating pass comparing desired state to observed inventory and acting on the difference. | The mechanism that fixes leaks and confirms destruction. |
| Reconciler owner epoch | A fencing number ensuring only one reconciler instance may write. | Stops two instances acting in conflict after a partition. |
| Operation identity | The `(session, generation)` pair naming an allocation request. | Makes a reissued request return the existing worker. |
| Duplicate worker | A second worker created for one generation, usually by a lost response. | Detected and terminated by the loop. |

## Failure, operations, and security

A nine-row failure table, then what to observe, retry discipline, tenant isolation, and rollout safety.

---

> | Failure | Blast radius | Detection | Degraded behavior | Recovery |
> |---|---|---|---|---|
> | Allocator crashes after create | One session | Desired/observed mismatch | Session remains allocating | Reconcile operation identity; remove duplicate workers |
> | Browser worker crashes | Its session | Worker health and stream loss | Explain session reset; no unisolated fallback | Create fresh session after authorization |
> | Gateway disconnects | Its streams | Stream heartbeat | Reconnect within grace to same live worker | Replace gateway and validate generation |
> | Session DB or controller unavailable (control plane) | New sessions and terminations | Controller error rate, outbox age | Existing streams continue on cached bindings; no new sessions | Fail over replica; reconciler drains the outbox |
> | Policy service unavailable | New/expired policies | Snapshot age | Existing sessions obey bounded cached policy; reject unsafe new authorization | Refresh policy and terminate revoked sessions |
> | Egress proxy unavailable | Its sessions' outbound traffic | Proxy health, connection failures | Pages fail closed; no direct egress path exists | Replace proxy capacity; sessions resume without reset |
> | Region loses capacity | Regional sessions | Allocation latency and spare capacity | Reject or queue new sessions with deadline | Route new sessions elsewhere under residency policy |
> | Worker cleanup fails | Residual resource/data | Orphan inventory | Worker stays quarantined and unavailable for reuse | Retry termination and alert on age |
> | Expensive malicious page | Its resource quota | CPU/memory/network limits | Throttle or terminate that session | Patch and replenish clean capacity |

**What this says in plain words**
Nine failures, with radius, detection, degraded behavior, and recovery.

- **Row: Allocator crashes after create.**
  - Detection is "desired/observed mismatch", which is the reconciler's ordinary reading rather than a special alarm. The design makes this failure a routine input.
- **Row: Browser worker crashes.**
  - Degraded behavior is the strongest entry in the table: "Explain session reset; no unisolated fallback".
  - Worked example: alice's worker dies mid-browsing. The correct behavior is to tell her the session restarted and start a new one after re-authorizing. The forbidden behavior is quietly loading the site in her local browser so she does not notice.
  - Recovery says "after authorization", so a crash is not a way to obtain a session without a fresh check.
- **Row: Gateway disconnects.**
  - Reconnect within grace to the *same live worker*, and recovery validates the generation. The worker survived; only the connection was lost.
- **Row: Session DB or controller unavailable.**
  - Radius is new sessions and terminations only. Existing streams continue on cached bindings.
  - Detection includes outbox age, which reveals how much lifecycle work is queued and unprocessed.
  - Worked example of what the outage costs: nobody can start a browsing session, and nothing is being cleaned up, so worker inventory drifts upward until the outage ends.
- **Row: Policy service unavailable.**
  - "obey bounded cached policy; reject unsafe new authorization" is two different behaviors for two different cases.
  - Worked example: existing sessions keep their cached allowlist, which is safe because it was valid recently. A new session requiring a policy the gateway does not hold is refused rather than allowed with no policy. Continuing on stale policy is acceptable; starting with none is not.
  - Recovery includes terminating revoked sessions, settling the debt the cached window created.
- **Row: Egress proxy unavailable.**
  - "Pages fail closed; no direct egress path exists" is the security property showing up as an availability failure.
  - Worked example: the proxy dies, so every isolated browser can reach nothing. Pages stop loading. This is bad for users and correct: the alternative, a fallback direct path, would mean an unfiltered browser reaching the Internet from inside your infrastructure.
  - "sessions resume without reset" is the compensation: the workers were fine, so restoring the proxy restores browsing with pages intact.
- **Row: Region loses capacity.**
  - "Reject or queue new sessions with deadline". A queue with a deadline, not an unbounded one.
  - Worked example: a user waiting 45 seconds for a session has almost certainly given up. Queueing past a deadline builds work for people who have left.
- **Row: Worker cleanup fails.**
  - Degraded behavior: "Worker stays quarantined and unavailable for reuse".
  - This is the lifecycle rule enforced at the operational level. A worker whose destruction could not be confirmed is never returned to the pool, so the failure costs capacity rather than safety.
  - Recovery retries and alerts on age, so the leak becomes visible rather than accumulating silently.
- **Row: Expensive malicious page.**
  - Contained by the per-session limits. Recovery mentions patching, acknowledging that an expensive page may be an exploitation attempt rather than merely a heavy site.

---

> - Observe
>   - Allocation latency and warm-pool depth.
>   - Orphan worker count and oldest orphan age.
>   - Oldest `TERMINATING` session.
>   - Egress policy denials by tenant.
>   - Stream reconnect rate and generation mismatches.
>   - Log lifecycle and policy decisions
>   - Avoid recording page contents and credentials by default.
>   - Restrict access to destination history according to the product's privacy policy.

**What this says in plain words**
Five measurements and three logging rules.

1. **Allocation latency and warm-pool depth.** Depth is the leading indicator: it falls before latency rises, giving warning before users are affected.
2. **Orphan count and oldest orphan age.**
   - Both, and the age matters more. Worked example: 3 orphans with the oldest 30 seconds old means the reconciler is working normally. 3 orphans with the oldest 4 hours old means something is permanently stuck, and the count alone would not distinguish them.
3. **Oldest `TERMINATING` session.** The direct measure of whether the cleanup promise is being met.
4. **Egress policy denials by tenant.**
   - Worked example of the two readings: a steady low rate is normal, users occasionally visiting blocked sites. A sudden spike from one tenant is either a misconfigured policy or a session repeatedly probing forbidden destinations, which is what a compromised worker attempting SSRF looks like.
5. **Stream reconnect rate and generation mismatches.**
   - Generation mismatches are the security-relevant one. Worked example: a background rate is expected, from tickets going stale during ordinary reconnects. A spike means either a bug in ticket issuance or someone replaying old tickets, and it is exactly the signal the recycled-worker attack would produce.

**The three logging rules**

1. **Log lifecycle and policy decisions.** Who created what, what policy applied, what was denied.
2. **Do not record page contents and credentials by default.**
   - Worked example of the danger: a debugging feature that captures request bodies from the isolated browser. Those bodies contain whatever users typed into pages, including passwords. The log store is now more sensitive than the system it monitors.
3. **Restrict destination history per the privacy policy.**
   - Worked example: the full list of sites each employee visited is a record of their browsing habits. It may be necessary for security investigation and it is not something every operator should be able to read casually.

---

> - Retry discipline
>   - Clients retry create and connect with backoff and jitter under the same idempotency key.
>   - The reconciler retries inventory calls indefinitely with backoff
>   - Termination is never abandoned.
>   - A `409` generation conflict is a signal to re-read state, not to retry the same request.

**What this says in plain words**
Three rules, and the second contains an absolute.

1. **Clients retry under the same idempotency key.** The key is what makes the retry safe rather than duplicating.
2. **The reconciler retries inventory calls indefinitely, and termination is never abandoned.**
   - "never abandoned" is unusual, because most retry advice includes giving up.
   - Worked example of why: a worker that could not be terminated is holding a previous session's cookies and memory. Giving up leaves it running indefinitely, and if it were ever returned to the pool a user would land inside someone else's session. The only acceptable outcomes are destroyed or permanently quarantined with an alarm, never forgotten.
3. **A `409` generation conflict means re-read, not retry.**
   - Worked example: the reconciler tries to close session `s-9912` at generation 1 and receives a conflict, because the session is now at generation 2. Retrying the same request will fail identically forever. The conflict is information: the world moved, so re-read and decide again from current state.
   - The general rule worth stating: a conflict is a signal about state, not a transient error, and retrying it unchanged is always wrong.

---

> - Tenant isolation
>   - Per-tenant quotas on concurrent sessions, memory, and egress bandwidth.
>   - Worker execution environments are isolated per session.
>   - A host may serve multiple isolated environments only under the declared VM/sandbox boundary.
>   - Different tenants never share one live browser profile or session environment.
>   - A tenant's token receives `404` on another tenant's session IDs, not `403`, to avoid existence leaks.
>   - Policy snapshots are tenant-scoped
>   - One tenant's allowlist cannot widen another's egress.

**What this says in plain words**
Five rules.

1. **Quotas on three dimensions.** Sessions, memory, and egress bandwidth are separately capped, because a tenant within its session quota can still consume disproportionate bandwidth.
2. **Isolation is per session, not per tenant.**
   - Worked example of the distinction: two sessions belonging to the *same* tenant still get separate environments. One user's compromised session must not reach a colleague's, because the threat is hostile web content, and hostile content does not respect organizational boundaries.
3. **A host may serve many environments only under the declared boundary.**
   - The honest statement of density: sharing a host is acceptable because of the microVM boundary, and the argument depends entirely on that boundary holding.
4. **`404`, not `403`.** The existence-leak rule, restated where tenancy is enforced.
5. **Policy snapshots are tenant-scoped, and one tenant's allowlist cannot widen another's.**
   - Worked example of the bug this prevents: policies merged into one enforcement table at the proxy. Tenant A allows `partner.example`. Tenant B's session reaches it too, because the rule was not scoped. Every allowlist entry silently becomes universal.

---

> - Rollout and rollback safety
>   - Patch by draining old worker images and allocating new generations
>   - Running sessions finish on the old image.
>   - Roll controllers and gateways by fault domain
>   - Cached bindings keep streams alive through the deploy.
>   - Policy schema changes ship with a version
>   - Enforcement points reject an unknown version rather than failing open.

**What this says in plain words**
Three rules, one per component type.

1. **Patch workers by draining, with running sessions finishing on the old image.**
   - Worked example: a browser security patch. New sessions get the patched image; existing sessions run to completion on the old one, up to the 15-minute idle timeout.
   - The tension worth naming: during the drain, sessions are still running the vulnerable browser. For an actively-exploited vulnerability you may need to terminate them instead, accepting that every affected user's session resets. That is a judgement call, and the drain is the default rather than the only option.
2. **Roll controllers and gateways by fault domain, with cached bindings keeping streams alive.**
   - Worked example: a gateway restarts during a deploy. Its streams drop, and clients reconnect within the 60-second grace to the same live workers through another gateway. Users see a brief interruption and keep their pages.
3. **Policy schema changes ship with a version, and enforcement points reject unknown versions rather than failing open.**
   - The most important rule of the three. Worked example of failing open: a policy snapshot in a new format reaches a gateway that cannot parse it. Treating an unparseable policy as "no restrictions" means a deploy ordering mistake removes every egress restriction fleet-wide.
   - Rejecting instead means the gateway keeps its last known-good policy and alarms, so the failure costs freshness rather than enforcement.
   - The general principle for any security enforcement point: an unparseable rule is a denial, never a permission.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Blast radius | How much of the system one failure affects. | Separates one session from an entire region. |
| Desired/observed mismatch | A difference between what should exist and what does. | The reconciler's ordinary input, not a special alarm. |
| Unisolated fallback | Silently loading a site locally when the isolated stream fails. | Forbidden; it defeats the product. |
| Reconnect grace | The window in which a dropped stream may rejoin the same live worker. | Keeps a deploy or blip from destroying a session. |
| Outbox age | How long lifecycle work has been queued unprocessed. | Reveals a stalled control plane. |
| Bounded cached policy | Continuing on a recently-valid policy for a limited window. | Safe, unlike starting with no policy at all. |
| Fail closed | Denying traffic when the enforcement point is unavailable. | Why a dead proxy stops browsing rather than releasing it. |
| Queue deadline | A limit on how long a request may wait before being rejected. | Stops work accumulating for users who have left. |
| Quarantined worker | A worker whose destruction could not be confirmed, kept permanently out of the pool. | Trades capacity for safety. |
| Warm-pool depth | How many idle workers remain available. | Falls before allocation latency rises. |
| Orphan age | How long the oldest unreferenced worker has existed. | Distinguishes a working reconciler from a stuck one. |
| Egress denial rate | How often outbound connections are blocked, per tenant. | A spike can indicate a compromised worker probing. |
| Generation mismatch | A token naming an incarnation that is no longer current. | The signal a recycled-worker attack would produce. |
| Idempotency key | A caller-supplied string making a repeated request safe. | What makes client retries harmless. |
| `409` conflict | A response meaning the state has moved on. | Information to re-read, never something to retry unchanged. |
| Per-session isolation | Separate environments even for two sessions of one tenant. | Hostile content does not respect organizational boundaries. |
| Existence leak | Revealing that a resource exists through an error code. | Why `404` rather than `403`. |
| Tenant-scoped policy | Policy evaluated only within the tenant it belongs to. | Stops one allowlist widening another's egress. |
| Image drain | Retiring an old worker image by allocating new sessions on the new one. | Running sessions finish undisturbed. |
| Fail open on unknown version | Treating an unparseable policy as permitting everything. | The catastrophic default this design explicitly rejects. |

## Alternatives and IC4 stretch

The option table, four stretch items, the weakest assumption, the over-engineering warning, and a mechanism reference.

---

> | Option | What it is | Strength | Weakness | Choose when |
> |---|---|---|---|---|
> | Pixel stream | Remote render sent as images/video | Simple active-content boundary | Bandwidth, latency, accessibility cost | Baseline hostile-content isolation |
> | Sanitized DOM or drawing commands | Reconstruct safe representation | Potentially lower bandwidth | Renderer/sanitizer attack surface and compatibility | Product can own and validate this complexity |
> | Per-session VM boundary | Separate guest isolation | Reduces shared-kernel exposure | Startup and resource cost | Strong enterprise isolation requirement |
> | Shared-kernel container | Process/resource isolation | Fast and dense | Kernel becomes shared trust boundary | Risk model permits and hardening is demonstrated |
> | Secure web gateway only | Inspect/filter requests | Lower execution cost | Web code still runs on endpoint | Isolation is unnecessary for the threat model |

**What this says in plain words**
Five options across three decisions: what is sent to the endpoint, what the isolation boundary is, and whether to isolate at all.

- **Row: Pixel stream.**
  - The weakness list includes accessibility, which is easy to overlook and genuinely serious.
  - Worked example: a screen reader works by reading the page's structure. A pixel stream has no structure, only an image. Text selection, browser zoom, and find-in-page all stop working for the same reason. For an enterprise with accessibility obligations this is not a minor cost.
- **Row: Sanitized DOM or drawing commands.**
  - Lower bandwidth, at the cost of a sanitizer that must be correct against arbitrary hostile input.
  - Worked example of the risk: the sanitizer must neutralize every form of script injection, in every markup construct, across every browser quirk, forever. A single gap puts executable content back on the endpoint, which is the one thing the product exists to prevent.
  - "Choose when: product can own and validate this complexity" is doing real work. It is not a warning against the approach; it is a statement that it requires a team permanently dedicated to the sanitizer.
- **Row: Per-session VM boundary.** The chosen option, with startup and resource cost as the acknowledged price.
- **Row: Shared-kernel container.**
  - "Choose when: risk model permits and hardening is demonstrated." Two conditions, and *demonstrated* is the strict one: not "we applied hardening" but "we can show it works".
- **Row: Secure web gateway only.**
  - Filtering requests without isolating execution. Much cheaper, and it leaves web code running on the endpoint.
  - Right when the threat model accepts that, which the premise-reversal question examines directly.

---

> - IC4 stretch — negotiated cuts
>   - Defer persistent profiles to simplify cross-tenant cleanup.
>   - Defer private-site connectors to simplify egress policy.
>   - Explain the user convenience those cuts sacrifice.

**What this says in plain words**
Two features deliberately cut, and a requirement to be honest about what each costs the user.

1. **Persistent profiles deferred.** Cleanup becomes destruction rather than deletion.
   - The user cost: logging in again every session. Worked example: an employee who uses six internal-facing SaaS applications re-authenticates to all six each time. That is a real daily friction, and pretending otherwise would be dishonest.
2. **Private-site connectors deferred.** Egress policy stays a simple deny-private rule.
   - The user cost: internal applications cannot be used through the isolated browser at all.
3. **Explain what the cuts sacrifice.**
   - The instruction that makes this an IC4 item rather than a scoping note. Worked example of the weak version: "we cut persistent profiles to reduce complexity". The strong version: "we cut persistent profiles, which means users re-authenticate each session; we chose that because it converts an exhaustive deletion argument into a single destruction claim, and we would revisit it if login friction drove adoption down".

---

> - IC4 stretch — multi-region placement
>   - Place new sessions close to the user while honoring residency.
>   - An existing session remains pinned unless application-level restart is acceptable.
>   - Regional failover means new sessions plus a visible reset, not transparent memory migration.

**What this says in plain words**
Three rules for adding regions.

1. **Place new sessions near the user, within residency constraints.** Latency and law together, and the law wins.
   - Worked example: a German employee travelling in Singapore. Latency argues for Singapore; residency policy may require Frankfurt. The session goes to Frankfurt and the user accepts higher latency.
2. **An existing session stays pinned.** The consequence of state living in the worker.
3. **Regional failover is new sessions plus a visible reset.**
   - Worked example: a region is lost. Every session there is gone, along with every user's pages and logins. New sessions start elsewhere and users are told their sessions restarted. There is no transparent migration, because the state was never anywhere else.

---

> - IC4 stretch — 10× load
>   - `100,000` sessions imply about `48.8 TiB` of reserved memory and `200 Gbit/s` of egress at the same assumptions.
>   - Shard the allocator and session table by cell
>   - One cell's inventory API budget must not throttle another.
>   - Egress cost now dominates
>   - Bitrate adaptation and idle-frame suppression save more than more hosts.

**What this says in plain words**
Three changes at ten times the scale.

1. **The arithmetic.** 48.8 tebibytes of memory and 200 gigabits per second of egress.
2. **Shard the allocator and session table by cell, with separate inventory API budgets.**
   - The API budget point is the specific one. Worked example: the cloud's inventory API allows some number of calls per second per account. One cell's reconciler looping hard during an incident consumes the shared budget, and every other cell's reconciler starts getting throttled. Cells that share a rate limit are not independent, however separate their data is.
3. **Egress dominates, and adaptation beats capacity.**
   - Worked example of the leverage: suppressing frames for idle sessions might cut average bandwidth by half. At 200 gigabits per second that is 100 gigabits per second saved, continuously, from an encoder change. No amount of additional hosts reduces egress at all; only sending less does.

---

> - IC4 stretch — cost and blast radius
>   - Track per-tenant concurrency, memory, and egress budgets separately.
>   - Cell the worker fleet so a bad image or kernel patch stalls one cell, not the region.
>   - Keep enough warm capacity to absorb the drain wave during a patch.

**What this says in plain words**
Three points.

1. **Three separate budgets per tenant.** A tenant within its session count can still be the largest consumer of bandwidth.
2. **Cell the fleet so a bad image stalls one cell.**
   - Worked example: a kernel patch causes workers to fail to boot. Rolled fleet-wide, no session can start anywhere. Rolled cell by cell, one cell's allocations fail and the rest continue, which turns a total outage into a partial one that is also easy to diagnose.
3. **Warm capacity must absorb the drain wave.**
   - The non-obvious one. Worked example: patching drains old workers, so sessions end and users immediately start new ones. That recreation wave looks exactly like a Monday-morning burst, and it happens during a deploy when some capacity is already unavailable. Warm capacity must be sized for patching, not only for organic bursts.

---

> - Weakest assumption
>   - `512 MiB` and `2 Mbit/s` per session are averages
>   - Media-heavy enterprise workloads can double both and halve effective capacity.
>   - Mitigation: benchmark with representative sites, enforce per-session limits so one heavy session cannot starve neighbors, and alarm on warm-pool depth.

**What this says in plain words**
Both headline numbers are averages, and averages are the wrong shape for capacity planning.

1. **The assumption.** 512 mebibytes and 2 megabits per second per session.
2. **Doubling both halves capacity.**
   - Worked example: if real usage is 1 gibibyte and 4 megabits per second, then 10,000 sessions need 9.76 tebibytes and 40 gigabits per second. The fleet was provisioned for half that, so it supports 5,000 sessions and fails at 5,001 in the middle of a working day.
3. **Three mitigations, each doing different work.**
   - **Benchmark with representative sites.** Not synthetic pages, but the sites employees actually use.
   - **Per-session limits so one heavy session cannot starve neighbours.** Converts a shared-capacity problem into a contained one: the heavy session is throttled rather than everyone degrading.
   - **Alarm on warm-pool depth.** The leading indicator, giving warning before allocation latency rises.

---

> - Over-engineering warning
>   - Do not claim remote browser isolation eliminates phishing or every browser/sandbox escape.
>   - Do not build live VM migration for regional failover when a visible session reset is acceptable.

**What this says in plain words**
Two warnings of different kinds.

1. **Do not overclaim the security.**
   - Worked example of phishing surviving isolation: a user visits a convincing fake login page inside the isolated session and types their corporate password. No code reached their laptop. The credential is stolen anyway, because the user typed it and the keystrokes are forwarded by design.
   - Worked example of escapes surviving: a microVM boundary is stronger than a container and hypervisor escapes exist. The claim is reduced blast radius, not impossibility.
   - Overclaiming is a real risk in a security product: an organization that believes phishing is solved stops training for it.
2. **Do not build live migration when a reset is acceptable.**
   - Worked example of the cost: live-migrating a running virtual machine with a browser's full memory across regions, faster than the user notices, is one of the harder things in systems engineering. A visible reset is a dialog box saying the session restarted. Asking whether the reset is acceptable first is the whole point; often it is.

---

> - Mechanism reference

**What this says in plain words**
A self-assessment grid. The middle column is a checklist; the fourth column is what actually distinguishes a stronger answer.

**Why the fourth column is the one to score**
The difference is rarely more content. It is a different kind of claim about the same content.

- **Row: Requirements.**
  - Must land: the rendering model, disposable sessions, the transfer policy, and Internet-only egress.
  - Adds: naming the cuts and what each buys.
  - Separating signal: *negotiating* scope rather than accepting it.
  - Worked example of the difference: accepting "build browser isolation" and designing everything, versus saying "I will cut persistent profiles and private-site connectors; the first turns cleanup from an exhaustive deletion argument into a single destruction claim, the second keeps egress policy to one deny-private rule, and both cost the user real convenience". The second shapes the problem before solving it.
- **Row: Estimates.**
  - Must land: memory, egress, churn, and the warm pool.
  - Adds: letting the burst size the pool, and naming the heavy-site case.
  - Separating signal: "a number changes the host shape or pool size".
  - Worked example of passing it: "5.86 tebibytes of memory suggests about 12 dense hosts, but a browser can consume most of a core, so CPU probably binds first and the benchmark decides host shape". The memory arithmetic was done and then explicitly demoted, which is a number changing a decision.
- **Row: Architecture.**
  - Must land: five components and one request traced.
  - Adds: the control and data plane split so streams survive a controller outage.
  - Separating signal: every component states both its mechanism and its price.
- **Row: Deep dive.**
  - Must land: treating the worker as the attacker, connection-time egress enforcement, generation-bound tokens, and the reconciler.
  - Adds: observed versus intended destruction, and generation compare-and-set across reconnect.
  - Separating signal: reasoning *across* the database and inventory boundary.
  - Worked example: the session table says a worker should exist; the inventory says whether it does. Every interesting failure lives in the gap, and a candidate who reasons only within one side has described half the system.
- **Row: Operations.**
  - Must land: the failure table, orphan alarms, and tenant quotas.
  - Adds: cells, image drain by generation, and fail-closed policy versions.
  - Separating signal: volunteering the cleanup proof before being asked.
  - Worked example of what "cleanup proof" means: not "we terminate the worker", but "we mark the session closed only when the inventory confirms the worker is gone, and a worker whose destruction we cannot confirm is quarantined permanently with an alarm on its age".
- **Row: Wrap.**
  - Must land: the recap and the central tradeoff.
  - Adds: naming the per-session averages as the weakest assumption.

## Interview pushback and validation

Eight challenges, each with a baseline and a stretch answer, then seven things to test.

---

> - Q1: Why are containers not the entire security story?
>   - **IC3 baseline**
>     - Hostile code still interacts with a shared host kernel.
>   - **IC4 stretch**
>     - Select the isolation boundary against the tenant threat model and patch/escape blast radius.

**What is really being asked**
Containers are the default answer for isolating a workload. Why is that insufficient here?

**The baseline answer, expanded**
Containers isolate using the kernel, so the kernel is inside the trust boundary rather than outside it.

- Worked example: hostile code in a container makes system calls to the same kernel serving every other container on the host. A kernel vulnerability reachable through those calls is an escape onto the host and therefore into every co-located tenant's session.
- The specific reason it matters *here*: this system deliberately points the most-attacked software in existence at hostile content, continuously, by design. Assuming the kernel's system-call surface has no exploitable bugs is an assumption nobody can make about a surface that large.

**The stretch answer, expanded**
The boundary is a choice against a threat model, not a universally correct answer.

- Worked example where a container is right: a single-tenant deployment rendering only pre-approved internal sites. The threat model does not include hostile content, and the density and startup speed are worth more.
- Worked example where it is not: a multi-tenant service rendering arbitrary Internet content for competing enterprises. One escape reaches another company's browsing session.
- "patch/escape blast radius" is the framing to say aloud: the question is not whether an escape can happen, but how much it reaches when it does.

---

> - Q2: A user reconnects after the worker address is reused.
>   - **IC3 baseline**
>     - Session generation and token audience must match the current assignment.
>   - **IC4 stretch**
>     - Revoke routing and credentials before recycling capacity.

**What is really being asked**
The cross-session exposure scenario, asked directly.

**The baseline answer, expanded**
Two checks, both required at connect time.

- Worked example: alice's ticket names session `s-9912` generation 1. The worker at that address now serves bob's session `s-5580` generation 1. The gateway compares the ticket's session and generation against the current binding, finds a mismatch, and refuses.
- Token audience is the second check: the ticket names which gateway may accept it, so a ticket cannot be replayed to a different gateway that might hold a different binding.

**The stretch answer, expanded**
Ordering, not just checking.

- Worked example of the ordering: revoke routing and credentials *before* the address returns to the pool. Then even a gateway that somehow skipped the generation check has no route to send the connection down.
- The principle: a check that must be performed correctly is weaker than a state that makes the wrong thing impossible. Doing both is the design.

---

> - Q3: The allocator created a worker but lost the response.
>   - **IC3 baseline**
>     - Reconcile using stable session/generation identity.
>   - **IC4 stretch**
>     - Inventory and remove orphan resources even after the originating operation expires.

**What is really being asked**
The worker-leak scenario, and whether the reconciler actually covers it.

**The baseline answer, expanded**
The operation identity makes the retry return the existing worker instead of creating another.

- Worked example: the allocator requests a worker for `(s-9912, gen 1)`. The worker is created and the response is lost. The next reconcile pass reissues the request with the same identity, and the inventory returns the existing worker rather than a second one.

**The stretch answer, expanded**
Identity-based reconciliation does not cover everything, and this names the gap.

- Worked example of the gap: the session was deleted entirely, or the operation record expired after its retention. There is now a running worker and nothing in the session table refers to it. Reconciling by identity finds nothing, because there is no identity left to reconcile.
- The answer is a second, independent sweep: enumerate what the inventory says exists, compare against the assignment table, and terminate anything with no owner.
- The general point worth stating: identity-based reconciliation fixes divergence between two records, and inventory-based sweeping fixes things no record mentions. A complete design has both.

---

> - Q4: The requirement changes to private enterprise applications.
>   - **IC3 baseline**
>     - Add an authorized private connector rather than allowing arbitrary internal destinations.
>   - **IC4 stretch**
>     - Isolate connectors per tenant and enforce destination identity at that boundary.

**What is really being asked**
The most likely real-world requirement change, and whether it breaks the egress model.

**The baseline answer, expanded**
Add a connector; do not relax the address rule.

- Worked example of the wrong approach: change egress policy from "deny private ranges" to "allow the customer's internal range". Now a compromised worker can reach anything on that network, including systems nobody intended to expose. One rule change turned the isolation service into a route into the enterprise.
- The connector approach: a specific authorized component that proxies to specific named applications. The worker reaches the connector; the connector reaches only what it is configured for. The deny-private rule at egress stays intact.

**The stretch answer, expanded**
Two additions, and the second is the sharper one.

1. **Per-tenant connectors.** Worked example: a shared connector reachable by every tenant's workers is a path from tenant A's compromised session into tenant B's internal network.
2. **Enforce destination identity at the connector boundary.**
   - Not just the address, but proof of which service it is, typically by verifying its certificate.
   - Worked example: an attacker who can influence internal DNS points the allowed application name at a machine they control. An address check passes. Verifying the destination's certificate identity fails, because the attacker's machine cannot present a certificate for that service.

---

> - Q5: Can a region fail without disrupting sessions?
>   - **IC3 baseline**
>     - Volatile browser state is lost in the baseline.
>   - **IC4 stretch**
>     - Negotiate restart semantics before proposing expensive state replication.

**What is really being asked**
Whether you will promise regional resilience you cannot deliver cheaply.

**The baseline answer, expanded**
No. The session's entire state is in that worker's memory, and the region holding it is gone.

- Worked example of what is lost: every open tab, every logged-in site, every partly-filled form, for every user in that region, simultaneously.
- It is not a gap in the design; it is a direct consequence of where the state lives, and there is no cheap alternative.

**The stretch answer, expanded**
Ask what "without disrupting" needs to mean before designing for it.

- Worked example of the negotiation: "a visible reset where the user is told their session restarted and reopens their page" costs almost nothing. "Transparent continuation with the page intact" requires replicating browser memory continuously across regions, which is enormously expensive and would double the memory and bandwidth budgets.
- Usually the reset is acceptable, and the strong move is to establish that in one question rather than to design the expensive thing unasked.

---

> - Q6: What happens if the user closes the tab abruptly?
>   - **IC3 baseline**
>     - Stream timeout starts a reconnect grace period, then termination.
>   - **IC4 stretch**
>     - Desired-state reconciliation cleans up resources even if every notification was lost.

**What is really being asked**
The ordinary case: users close tabs without any graceful shutdown, all day.

**The baseline answer, expanded**
Nothing notifies anyone. The stream goes quiet, a timeout fires, the 60-second grace begins, and termination follows.

- Worked example of why the grace still applies: a closed tab and a dropped network connection look identical from the server. The grace covers both, and the cost of waiting 60 seconds on a genuinely closed tab is one worker held briefly.

**The stretch answer, expanded**
The important property is that cleanup does not depend on any notification arriving.

- Worked example of a notification-based design failing: the client sends a close message on tab close. The user's laptop loses power instead. No message is sent. The worker runs until something else notices, and if nothing else is watching, it runs forever.
- With desired-state reconciliation, the session's expiry time is in the database. The reconciler sees it has passed and terminates the worker, regardless of whether any message was ever sent. Notifications become an optimization that makes cleanup faster, never the mechanism that makes it happen.

---

> - Q7 (premise reversal): Why isolate at all instead of a secure web gateway with URL filtering?
>   - **IC3 baseline**
>     - A gateway inspects requests but the page still executes on the endpoint, so a zero-day in the local browser is unmitigated.
>   - **IC4 stretch**
>     - Choose the gateway when the threat model accepts endpoint execution
>     - The deciding variable is whether the endpoint is trusted, not the cost of the farm.

**What is really being asked**
The premise reversal, and the most valuable question here. This design is expensive. A filtering gateway costs a fraction. Why build the farm?

**The baseline answer, expanded**
A gateway filters *which* pages load. It does not change *where* they execute.

- Worked example: a filtering gateway blocks known-bad domains and scans downloads. A user visits a legitimate, allowed news site that happens to be serving a malicious advertisement exploiting an unpatched browser bug. The gateway sees a request to an allowed domain and permits it. The exploit runs on the corporate laptop.
- The gateway's model assumes bad content comes from identifiably bad places. Isolation makes no such assumption, because the code never reaches the endpoint regardless of where it came from.

**The stretch answer, expanded**
Concede the gateway is right in its own context, and name the actual deciding variable.

- **The deciding variable is whether the endpoint is trusted, not cost.**
- Worked example where the gateway is correct: fully-managed corporate laptops, patched within hours, running an endpoint detection agent, with users trained and browsing mostly known sites. The endpoint is trusted to survive an occasional exploit attempt, and the gateway's cost-benefit is far better.
- Worked example where isolation is correct: contractor devices, unmanaged machines, or a threat model including targeted zero-days. The endpoint cannot be trusted, so the only defence is to stop code reaching it.
- Naming the deciding variable, and explicitly rejecting cost as the deciding variable, is what makes this the strong answer. Cost decides *whether you can afford* the right answer; it does not decide which answer is right.

---

> - Q8: The session database is down. Do users lose their browsers?
>   - **IC3 baseline**
>     - No
>     - Gateways hold the session-to-worker binding, so existing streams continue while new sessions and terminations wait.
>   - **IC4 stretch**
>     - Bound the cached-binding lifetime so a revoked user cannot browse for longer than the snapshot age during the outage.

**What is really being asked**
Does a control-plane outage become a data-plane outage?

**The baseline answer, expanded**
No. Gateways hold the binding locally, so existing streams continue.

- Worked example: a 5-minute database outage. 10,000 users keep browsing. What fails is starting a new session and completing a termination, and the outbox accumulates the deferred work.

**The stretch answer, expanded**
There is a security cost to that availability, and naming it is the whole value of the answer.

- Worked example of the cost: an administrator revokes alice's access at 14:00. The database is down, so the revocation cannot propagate. Alice's gateway is holding a cached binding and a cached policy, and her stream continues. She browses with access she no longer has.
- The bound is the cached lifetime: if snapshots are valid for 5 minutes, alice can browse at most 5 minutes past revocation, and that number is stated rather than discovered.
- This is the honest tension in the design. Caching buys availability during a control-plane outage and costs revocation speed. Both matter in a security product, and the resolution is to bound the window and state it, not to pretend it does not exist.

---

> - Validation scenarios
>   - Cross-tenant session-ID access.
>   - Stale connection token against a recycled worker.
>   - Redirect and DNS-rebinding attempts to blocked addresses.
>   - Duplicate session creation after timeout.
>   - Worker crash during an authenticated site session.
>   - Cleanup failure followed by allocator reuse attempt.
>   - Controller outage while a user reconnects within the grace window.

**What this says in plain words**
Seven tests, each mapping to a mechanism discussed earlier.

1. **Cross-tenant session-ID access.** Request another tenant's session identifier and assert the response is `404`, not `403`, so existence is not confirmed.
2. **Stale connection token against a recycled worker.** The direct test of generation validation: reproduce the exact timeline from the isolation section and assert the connection is refused.
3. **Redirect and DNS-rebinding attempts.** Point a hostname at an allowed address, let the check pass, then re-point it at the metadata address and assert the connection is blocked. Separately, follow a redirect to a blocked destination and assert the recheck fires.
4. **Duplicate session creation after timeout.** Retry a create with the same idempotency key past the client timeout and assert one session and one worker exist.
5. **Worker crash during an authenticated site session.** Assert the user is told the session reset, and specifically that no unisolated fallback occurs.
6. **Cleanup failure followed by allocator reuse attempt.** The direct test of the `CLOSED` precondition: make termination fail, then attempt to allocate that worker, and assert the allocation is refused because destruction was never observed.
7. **Controller outage while a user reconnects within the grace window.** Assert the reconnect succeeds from cached bindings, and that authorization is still checked.

**Why it matters**
Each item names a mechanism that could be wrong and the observation that would reveal it. Three of the seven are direct reproductions of failures described earlier in the file, which is what makes the list credible rather than generic.

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Shared host kernel | One kernel serving every container on a machine, and enforcing their isolation. | Inside the trust boundary, which is why containers are insufficient here. |
| System-call surface | The set of kernel entry points a workload can invoke. | Too large to assume free of exploitable bugs. |
| Threat model | The explicit statement of who the attacker is and what they can do. | Decides which isolation boundary is correct. |

## Recall card

Five one-liners and a four-sentence closing script, memorized rather than improvised.

---

> - “Execute untrusted content remotely and keep the worker outside the control-plane trust boundary.”

**What this says in plain words**
Two decisions: hostile content runs on a server rather than the laptop, and that server is treated as outside the trusted zone rather than inside it.

**Why it matters**
The second half is the part most designs get wrong.

- Worked example: a design that runs browsers remotely but gives each worker a cloud identity and a route to the control plane has moved the attack from the laptop to the inside of the infrastructure, which is worse. Remote execution alone is not the security property; remote execution *outside the trust boundary* is.

---

> - “Bind every stream to tenant, user, session, and generation.”

**What this says in plain words**
Four levels of identity on every connection, not one.

**Why it matters**
Each level closes a different failure.

- Worked example of each doing separate work: tenant stops cross-organization access. User stops a colleague attaching to your session. Session stops a token for one session reaching another. Generation stops a valid token reaching recycled capacity.
- Dropping any one of the four leaves a specific, demonstrable hole, and the generation is the one most often omitted because it is the least obvious.

---

> - “Use durable desired state to reconcile allocation and destruction.”

**What this says in plain words**
Write down what should exist, then continuously drive reality toward it, for both creating and destroying.

**Why it matters**
"and destruction" is the half that is usually missing.

- Worked example: most systems reconcile toward a running state, because a missing worker is visible when someone tries to use it. A worker that should not exist is invisible: nobody is looking for it, and it consumes resources and holds a previous session's data indefinitely.
- Reconciling destruction is what makes the cleanup promise enforceable rather than aspirational.

---

> - “Availability failures may reset a session, but never silently bypass isolation.”

**What this says in plain words**
It is acceptable to lose a user's browsing session. It is never acceptable to keep them browsing with the isolation removed.

**Why it matters**
It states the priority order that decides every degraded-path decision in the design.

- Worked example: the egress proxy is down. The choice is between pages failing to load and letting workers reach the Internet directly. This sentence settles it: fail the pages.
- Worked example: the stream drops. The choice is between telling the user their session reset and quietly loading the site locally. This sentence settles that too.
- A single principle that resolves a whole class of decisions is exactly what a recall card line should be.

---

> - “Closed means destruction was observed, not requested.”

**What this says in plain words**
A session is only closed once the system has confirmed the worker no longer exists.

**Why it matters**
It is the shortest statement of the exact failure from the lifecycle section.

- Worked example: mark closed on the accepted termination request, return the worker to the pool, and the next user connects to a worker still running the previous user's browser with their cookies.
- The distinction between an accepted request and a completed effect is one of the most generally useful ideas in distributed systems, and this line is the crispest form of it in the whole file.

---

> - Wrap-up script
>   - “The design is disposable per-session workers behind an authenticated streaming gateway, with a controlled egress proxy and a controller that persists desired state before allocating.”

**What this says in plain words**
Sentence one: four components, each named by the property that matters.

**Why it matters**
"persists desired state before allocating" is an ordering claim inside an architecture description, and it is the ordering that makes leaks detectable.

---

> -   - “The key invariant is that a worker is treated as compromised, so it cannot reach credentials, metadata, or other tenants, and a session is closed only when destruction is observed.”

**What this says in plain words**
Sentence two: the security premise, its three consequences, and the lifecycle precondition.

**Why it matters**
It compresses both deep dives into one sentence. The three named targets are three separate mechanisms, and the closing clause is the lifecycle section's entire conclusion.

---

> -   - “The main tradeoff is VM-per-session isolation, which buys a hard boundary at the price of memory and allocation latency.”

**What this says in plain words**
Sentence three: what you chose and what it costs.

- Bought: a boundary where escape requires defeating the browser, the guest kernel, and the hypervisor.
- Paid: roughly 512 mebibytes per session and a start time that forces a warm pool of about 2,000 workers.

**Why it matters**
Both costs are concrete and both shaped the design elsewhere, so the tradeoff is demonstrably real rather than a formality.

---

> -   - “My weakest assumption is the per-session memory and bandwidth average; I would benchmark representative sites before committing host shape.”

**What this says in plain words**
Sentence four: the flaw, and the specific first action.

**Why it matters**
The assumption is unusually load-bearing, because both numbers feed every capacity decision.

- Worked example: if real usage is double both figures, the fleet supports 5,000 sessions rather than 10,000, and it fails at 5,001 during a working day.
- "representative sites" is the operative phrase: benchmarking synthetic pages would confirm the assumption while telling you nothing about the sites employees actually use.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Trust boundary | The line separating components you rely on from those you do not. | The worker is deliberately placed outside it. |
| Four-level binding | Tenant, user, session, and generation on every stream. | Each closes a different, demonstrable hole. |
| Generation | A counter identifying one incarnation of a session. | The most commonly omitted of the four bindings. |
| Desired state reconciliation | Recording what should exist and driving reality toward it. | Applied to destruction as well as allocation. |
| Reconciling destruction | Confirming that something which should not exist is actually gone. | The half most designs omit, because absence is invisible. |
| Silent isolation bypass | Continuing to serve a user with the isolation removed and no indication. | The one outcome ranked worse than losing a session. |
| Observed destruction | Confirmation from the inventory that a worker no longer exists. | The precondition for `CLOSED`. |
| Intent versus effect | An accepted request versus a completed action. | The distinction the closing one-liner compresses. |
| VM-per-session boundary | A separate guest isolation domain for each session. | The main tradeoff: a hard boundary for memory and latency. |
| Host shape | The CPU, memory, and network configuration of a machine type. | What the benchmark must decide before capacity is committed. |
