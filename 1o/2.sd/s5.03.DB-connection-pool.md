## 1. Crux and why it is hard

- Naive approach
  - Connect, authenticate, query, close, once per request.
  - Order of magnitude: milliseconds to tens of milliseconds of handshake, TLS, and auth for sub-millisecond useful work.
- First break is concurrency, not latency
  - The process opens as many connections as it has in-flight requests.
  - The database hits `max_connections` and rejects everyone, including health checks and the operator's session.
  - It reads as "database down", not "one service is greedy".
- Second break is health and accountability
  - Caching without a bound only moves the ceiling.
  - A connection the database or a firewall already killed is discovered mid-transaction.
  - A borrower that forgets to return removes capacity permanently and silently.
- Minimum primitives
  - **Bounded lending** — a semaphore whose permits are "connections allowed to exist".
  - **Idle reuse** — a deque holding connections that exist but are not lent.
  - **Borrow timeout** — bounded wait, then a typed error, so exhaustion is alarmable rather than latent latency.
  - **Leak-proof return** — an `AutoCloseable` wrapper so returning is the default path.
  - **Health of the lent thing** — validation on borrow, `maxLifetime`, a reaper.
- 🗣 "It is a bounded resource lender: a semaphore bounds how many connections may exist, a deque only stores the idle ones, and the API makes returning impossible to forget."

## 2. Clarifying questions

| Question | Assumed answer | Why it changes the design |
|---|---|---|
| Maximum pool size? | `20` per process `(assume)`, derived in §4 | Sets the permit count and this process's share of database `max_connections` |
| Behavior at exhaustion? | Block up to `500 ms` `(assume)`, then throw | Chooses `tryAcquire(timeout)` over unbounded `acquire()`; makes exhaustion alarmable |
| Minimum idle? | `= maxSize`, a fixed-size pool | Removes grow/shrink churn; costs idle connections held on the database |
| Transactional workload? | Yes, some borrows span several statements | Sizing must use hold time, not query time |
| One database or many? | One pool per endpoint; routing lives above | A pool shared across shards cannot bound any one shard |
| Fairness required? | No, unfair `(assume)` | Higher throughput; fair mode only when starvation is measured |
| Per-connection statement cache? | Yes | Argues for LIFO idle order so warm connections stay warm |
| Who else connects? | A sibling service and operators | The ceiling must be a budget, not all of `max_connections` |
| Fixed host or failover VIP? | Load-balanced VIP | Forces `maxLifetime` so connections rebalance after failover |

## 3. Requirements

- Every number is an interview assumption unless a source is named beside it.

| Requirement | Target | Enforced by |
|---|---|---|
| Warm borrow latency | p99 < `1 ms` `(assume)` | Non-blocking `pollFirst()` on the idle deque; no I/O on the warm path |
| Cold borrow latency | p99 < `50 ms` `(assume)` | Creation runs under an already-held permit, off any shared lock |
| Bounded existence | Never more than `20` connections exist | `Semaphore(20)`; a permit is held for the whole lifetime of "this connection exists" |
| Exhaustion behavior | Fail at `500 ms` with a typed `PoolExhaustedException` | `tryAcquire(500, MILLISECONDS)` returning `false` |
| Leak visibility | Hold beyond `30 s` `(assume)` logs the borrow stack | Scheduled task armed at borrow, cancelled at return — HikariCP `leakDetectionThreshold` |
| Dead connections never lent | `0` in steady state | Validate on borrow when idle age > `30 s` `(assume)` via `Connection.isValid(1)` |
| Connection age bound | No connection older than `30 min` `(assume)` is lent | `maxLifetime` in the reaper plus a check on return |
| Idle trim | Idle beyond `10 min` `(assume)` closed above `minIdle` | Reaper eviction pass |
| Permit conservation | Permit leak count `= 0` per test run | Release in `finally` on every path; asserted in §7 |
| Shutdown bound | Drain within `10 s` `(assume)` | Stop lending, close idle, bounded await, force-close |
| Durable state | `0` rows persisted by the pool | Pure process memory; see §6 |

- Invariants (proved in §7)
  - `permitsAcquired == idle + inUse + beingCreated` at every quiescent point.
  - A connection is in exactly one of idle, in-use, destroyed.
  - A wrapper is single-use: after `close()` it never delegates again.
  - A connection whose validation or session reset failed is destroyed, never returned.
- Non-goals
  - Query routing, read/write splitting, sharding.
  - Statement-cache semantics beyond "per connection".
  - Distributed transactions and XA recovery.
  - Cross-process coordination of the global budget — see §12.

## 4. Capacity and consequence

- Database-side ceiling
  - PostgreSQL's `max_connections` default is `100` (sourced: PostgreSQL connection settings).
  - Each backend is a process with its own work memory, so the ceiling is a memory and scheduling budget.
  - Decision: the per-process ceiling is `(this service's database budget) / (process count)`, not application concurrency
    - A `60`-connection budget over `8` processes gives `7`, so `20` per process either overcommits or requires raising `max_connections` deliberately with memory to back it.
- `cores × 2`
  - HikariCP's wiki gives `connections = (core_count × 2) + effective_spindle_count` (sourced: "About Pool Sizing").
  - A connection is a database worker; `× 2` covers the time each worker is blocked on I/O rather than executing.
  - Decision: an `8`-core SSD-backed database sizes to `16`–`20`, and application thread count never enters the number
    - `1,000` app threads over a `20`-connection pool is the correct shape; the pool is the throttle.
- Little's law
  - `L = λ × W`: connections busy = borrow rate × hold time.
  - `100/s × 50 ms = 5` busy. Same rate at `500 ms` hold = `50` busy, which exceeds a `20` pool by 2.5×.
  - Provisioning at exactly `L` leaves roughly half of arrivals queueing, so size to `L` plus headroom.
  - Decision: maximum sustainable rate is `maxSize / W`, `400/s` at `20` and `50 ms`
    - Exceeding it means fixing `W`, unless `maxSize` is still below `cores × 2`.
- Timeout consequence
  - `500 ms` timeout at `50 ms` hold tolerates about ten hold-times of queue before failing.
  - Decision: the timeout is a load-shedding knob and must sit below the caller's own deadline
    - Otherwise the pool completes work for a client that already gave up.
- Footprint
  - Order of magnitude: a socket, a receive buffer, and a statement cache per connection — single-digit MB client-side, more server-side.
  - `20 × 8` processes = `160` sockets against one database.
  - Decision: connection count is a shared cross-service resource and belongs in a capacity review with the database owner, not in each service's local config.

## 5. Architecture and flow

```text
Application threads (many)
        |
        v
+-------------------------------------------------------------+
|  Pool                                                        |
|    Semaphore(maxSize)  <- sole source of truth for           |
|                           "how many may exist"               |
|    idle : LIFO deque of PooledConn   (exists, not lent)      |
|    inUse: PooledConn -> Borrow(thread, at, stack, leakTask)  |
|    Reaper (one scheduled thread)                             |
|      - evict idle older than idleTimeout, above minIdle      |
|      - retire any connection older than maxLifetime          |
+-------------------------------------------------------------+
        |  factory.create()   (only while holding a permit)
        v
   JDBC driver -> TCP/TLS -> database backend process
```

- Semaphore owns existence.
  - Bought: one integer bounds every connection that exists, including those still being created.
  - Cost: it must be released on every path or the pool shrinks permanently.
- Idle deque owns storage of unlent connections.
  - Bought: `O(1)` handoff; LIFO keeps a small working set warm, so statement and plan caches stay hot.
  - Cost: LIFO lets the coldest connections age indefinitely, which is why the reaper is not optional.
- In-use registry owns accountability.
  - Bought: turns "the pool is empty" into "these stacks are holding connections".
  - Cost: a stack capture per borrow is armed only for the leak task.
- Reaper owns time-based health.
  - Bought: bounds connection age and idle age without adding work to the borrow path.
  - Cost: eviction races borrowers, so it must use the same permit accounting.
- `PooledConn` wrapper owns the return contract.
  - Bought: `close()` means return, so try-with-resources makes the correct path the shortest path.
  - Cost: every method delegates, and use-after-close must be rejected.
- Factory owns creation.
  - Bought: creation under a held permit means a recovery storm cannot exceed `maxSize` sockets.
  - Cost: a slow connect burns a permit while producing nothing, so connect timeout must be under borrow timeout.

**Warm borrow trace**

→ Caller enters `try (var c = pool.borrow(500))`.  
→ `tryAcquire(500 ms)` succeeds; existence is reserved.  
→ `idle.pollFirst()` returns a connection idle `3 s`, below the `30 s` validation threshold, so no round-trip.  
→ Register in `inUse`, stamp `borrowedAt`, arm the leak task.  
→ Block exit calls `close()` on the wrapper, not the socket.  
→ Cancel the leak task, stamp `idleSince`, push to the front of the deque.  
→ Release the permit in `finally`.  

**Cold and unhealthy trace**

→ `tryAcquire` succeeds after `120 ms`.  
→ `idle.pollFirst()` returns a connection idle `90 s`, so `isValid(1)` runs and returns `false` — the database restarted.  
⇒ Destroy it, but keep the permit, so existence accounting is unchanged.  
→ `factory.create()` opens a replacement under that same permit.  
→ The caller never learns the old connection died.

## 6. API and data model

| Operation | Contract | Idempotency and conflict behavior |
|---|---|---|
| `borrow(timeoutMs)` | Returns a `PooledConn` or throws `PoolExhaustedException` | Not idempotent; the timeout is measured from entry, including validation retries |
| `PooledConn.close()` | Returns to the pool; never closes the raw socket | Idempotent — a second `close()` is a no-op, not a second permit release. The most important idempotency rule here |
| `PooledConn.markBroken()` | Forces destroy on return | Idempotent; destroyed exactly once |
| `evict(conn)` | Retires one connection | Immediate while idle; flagged and retired on return while in use |
| `shutdown(drainMs)` | Stop lending, close idle, bounded await, force-close | Idempotent; a second call returns immediately |
| `stats()` | `{total, idle, inUse, beingCreated, waiters, created, destroyed, timeouts, leaks}` | Approximate snapshot; not atomic across counters |

- Keyed in-memory state

| State | Key | Fields and invariant |
|---|---|---|
| Permit counter | none — one scalar | Connections allowed to exist; `acquired == idle + inUse + beingCreated` |
| Idle deque | position, LIFO | Connections that exist and are not lent; each appears at most once |
| In-use registry | `PooledConn` identity | `borrowingThread`, `borrowedAt`, `borrowStack`, `leakTaskHandle`, `broken` |
| Per-connection metadata | `PooledConn` identity | `createdAt` drives `maxLifetime`; `idleSince` drives validation and idle eviction; `useCount`, `retireOnReturn` |
| Waiter set | the semaphore's own queue | Threads blocked in `tryAcquire`; exported only as a gauge |

- Relational state: none
  - This subject has essentially no relational state of its own, so there is no DDL to write and inventing a schema would be dishonest.
  - Every structure above is process memory and restarts empty; nothing here is persisted.
  - The raw connections are kernel sockets plus server-side backends, not pool-owned records.
  - `maxSize` and the timeouts are deployment config, not a table read at runtime.
  - The only legitimate relational state — a fleet-wide connection-budget registry — is an IC4 stretch in §12, not part of the baseline.

## 7. Bounded lending and the permit invariant — IC3 baseline

```text
INVARIANT:  permitsAcquired == idle.size() + inUse.size() + beingCreated

  permitsAcquired = maxSize - permits.availablePermits()
  beingCreated    = threads between "permit acquired" and
                    "connection is in inUse, or destroyed"
```

- Why two structures rather than one
  - The semaphore answers "how many may exist"; the deque answers "which are unlent". Different invariants, each trivially correct alone.
  - A single structure must answer both, and that is where the classic bug lives: a thread that has decided to create is in neither collection, so a size check under-counts and the pool overshoots.
- The rule that makes it hold
  - Acquire the permit **before** deciding to reuse or create.
  - Release **only** at a terminal state for this borrow: back in idle, or destroyed.
  - Never release mid-transition.

| Path | Line that preserves it | State after |
|---|---|---|
| Borrow, reuse idle | `tryAcquire` true, then `idle.pollFirst()` moves one entry to `inUse` | idle−1, inUse+1, permits unchanged |
| Borrow, create new | `tryAcquire` true, then `factory.create()` under `beingCreated` | beingCreated+1 then inUse+1 |
| Borrow times out | `tryAcquire` false ⇒ no permit taken, nothing to release | unchanged |
| Validation fails on a polled connection | `c.destroy()` then loop to `factory.create()` **still holding the permit** | idle−1, beingCreated+1; permit deliberately retained |
| `factory.create()` throws | `catch { permits.release(); throw; }` | beingCreated−1, permit returned |
| Healthy return | `finally { permits.release(); }` after `idle.offerFirst(c)` | inUse−1, idle+1 |
| Broken return | `c.destroy()` then the same `finally { permits.release(); }` | inUse−1, nothing added to idle |
| Reaper evicts idle | Only after `idle.remove(c)` wins and `permits.tryAcquire()` accounts for it | idle−1, permit returned |
| `close()` called twice | `closed.compareAndSet(false, true)` guards the whole body | no second release; preserved by the CAS, not by discipline |
| Shutdown | Lending disabled first, then idle drained with per-connection permit accounting | converges to all permits available |

**Exact failure if the rule is broken**

→ The permit is released before the connection is pushed to idle.  
⇒ Another borrower takes that permit, finds the deque empty, and creates.  
⇒ `maxSize + 1` connections exist; the database ceiling is breached once per race.

→ The permit is released twice on the double-`close()` path.  
⇒ `availablePermits()` exceeds `maxSize` and the pool grows without bound under a leaky caller.  
→ Guard `close()` with a CAS, or use Python's `BoundedSemaphore`, which raises on over-release instead of drifting.

→ The permit is not released when validation and creation both fail.  
⇒ Every outage permanently shrinks the pool.  
⇒ Eventually every borrow times out although the database recovered.
- Fairness
  - Unfair lets a returning thread re-acquire immediately, which is higher throughput on a warm connection.
  - Defeater: under sustained contention a waiter can starve.
  - Switch to fair only when the wait histogram shows a tail the p99 does not explain; fair mode parks and unparks on every handoff.

## 8. Borrow and return, including every exception path — IC3 baseline

**Pseudocode**

```text
borrow(timeoutMs):
    deadline = now + timeoutMs
    if not permits.tryAcquire(timeoutMs): throw PoolExhausted   # no permit taken
    try:
        loop:
            c = idle.pollFirst()
            if c is null: return register(factory.create())     # create under permit
            if c.age > maxLifetime:            c.destroy(); continue   # permit held
            if c.idleAge > validateIfIdle and not c.isValid(1):
                                               c.destroy(); continue   # permit held
            if now > deadline: throw PoolExhausted             # validation ate budget
            return register(c)
    catch e:
        permits.release()          # the only permit release on the borrow path
        throw e

release(c, broken):
    try:
        cancel leak task; remove from inUse
        if broken or c.retireOnReturn or c.age > maxLifetime or shuttingDown:
            c.destroy()
        else:
            c.idleSince = now; idle.offerFirst(c)              # LIFO: warm stays warm
    finally:
        permits.release()                                      # always, every path
```

- Python — the mechanism in the smallest form

```python
import queue, threading, time
from contextlib import contextmanager


class Pool:
    def __init__(self, factory, max_size=20, borrow_timeout=0.5,
                 validate_if_idle=30.0, max_lifetime=1800.0):
        self.factory = factory
        self.idle = queue.LifoQueue()                        # LIFO keeps conns warm
        self.permits = threading.BoundedSemaphore(max_size)  # raises on over-release
        self.borrow_timeout = borrow_timeout
        self.validate_if_idle = validate_if_idle
        self.max_lifetime = max_lifetime

    def _acquire_conn(self, deadline):
        """Runs with a permit already held; returns a usable connection."""
        while True:
            try:
                conn = self.idle.get_nowait()
            except queue.Empty:
                return self.factory()                        # create under permit
            now = time.monotonic()
            too_old = now - conn.created_at > self.max_lifetime
            stale = now - conn.idle_since > self.validate_if_idle
            if too_old or (stale and not conn.is_valid()):
                conn.close_raw()                             # permit deliberately kept
                if time.monotonic() > deadline:
                    raise TimeoutError("pool exhausted during validation")
                continue
            return conn

    @contextmanager
    def borrow(self):
        deadline = time.monotonic() + self.borrow_timeout
        if not self.permits.acquire(timeout=self.borrow_timeout):
            raise TimeoutError("pool exhausted")             # no permit taken
        conn = None
        try:
            conn = self._acquire_conn(deadline)
            yield conn
            conn.idle_since = time.monotonic()
            self.idle.put(conn)                              # healthy return
        except Exception:
            if conn is not None:
                conn.close_raw()                             # broken: destroy, not reuse
            raise
        finally:
            self.permits.release()                           # every path, exactly once
```

- What each exception path does
  - `acquire` false ⇒ no permit taken ⇒ `finally` never runs ⇒ nothing to release.
  - `_acquire_conn` raises ⇒ `conn` is still `None` ⇒ only the permit is released.
  - The caller's body raises ⇒ destroy, because a failed statement may leave an open transaction or unread results.
  - The healthy path stamps `idle_since` before publishing, so a concurrent reaper never reads a stale timestamp.

**Java 17 — borrow, release, wrapper, reaper**

→ `borrow` takes a permit, then loops over idle candidates until one passes age and validity.  
→ `PooledConn.close()` is the only return path and is idempotent through a CAS.  
→ `release` chooses destroy versus idle, then releases the permit in `finally`.  
→ The reaper sweeps idle entries on a fixed period and never touches in-use entries.  

```java
import java.sql.Connection;
import java.util.Deque;
import java.util.Map;
import java.util.concurrent.*;

public final class Pool implements AutoCloseable {

    interface ConnFactory { Connection create() throws Exception; }

    private final Deque<PooledConn> idle = new ConcurrentLinkedDeque<>();
    private final Map<PooledConn, Borrow> inUse = new ConcurrentHashMap<>();
    private final Semaphore permits;              // sole bound on existence
    private final ConnFactory factory;
    private final ScheduledExecutorService keeper =
            Executors.newSingleThreadScheduledExecutor(r -> {
                Thread t = new Thread(r, "pool-reaper"); t.setDaemon(true); return t; });
    private final int maxSize;
    private final long validateIfIdleMs = 30_000L, maxLifetimeMs = 1_800_000L;
    private final long idleTimeoutMs = 600_000L,  leakThresholdMs = 30_000L;
    private volatile boolean shuttingDown = false;

    record Borrow(Thread owner, long atNanos, Throwable stack, Future<?> leakTask) { }
    record Stats(int total, int idle, int inUse, int waiters) { }

    Pool(ConnFactory factory, int maxSize) {
        this.factory = factory;
        this.maxSize = maxSize;
        this.permits = new Semaphore(maxSize);    // unfair: throughput over strict FIFO
        keeper.scheduleWithFixedDelay(this::reap, 30, 30, TimeUnit.SECONDS);
    }

    public PooledConn borrow(long timeoutMs) throws Exception {
        if (shuttingDown) throw new IllegalStateException("pool is shutting down");
        long deadline = System.nanoTime() + TimeUnit.MILLISECONDS.toNanos(timeoutMs);
        if (!permits.tryAcquire(timeoutMs, TimeUnit.MILLISECONDS))
            throw new PoolExhaustedException(stats());   // no permit taken: nothing to undo
        try {
            PooledConn c;
            while ((c = idle.pollFirst()) != null) {
                if (c.ageMs() > maxLifetimeMs
                        || (c.idleMs() > validateIfIdleMs && !c.valid())) {
                    c.destroy();                          // permit intentionally retained
                    if (System.nanoTime() > deadline)
                        throw new PoolExhaustedException(stats());
                    continue;
                }
                return register(c);
            }
            return register(new PooledConn(this, factory.create()));  // create under permit
        } catch (Exception e) {
            permits.release();                            // only release on this path
            throw e;
        }
    }

    private PooledConn register(PooledConn c) {
        Future<?> leak = keeper.schedule(() -> reportLeak(c),
                                         leakThresholdMs, TimeUnit.MILLISECONDS);
        inUse.put(c, new Borrow(Thread.currentThread(), System.nanoTime(),
                                new Throwable("borrow site"), leak));
        return c;
    }

    /** Called only by PooledConn.close(); never by application code. */
    void release(PooledConn c, boolean broken) {
        Borrow b = inUse.remove(c);
        if (b != null) b.leakTask().cancel(false);
        try {
            if (broken || shuttingDown || c.ageMs() > maxLifetimeMs) c.destroy();
            else idle.offerFirst(c.touch());              // LIFO: warm connections first
        } finally {
            permits.release();                            // every path, exactly once
        }
    }

    private void reap() {
        for (PooledConn c : idle.toArray(new PooledConn[0])) {
            if (c.ageMs() <= maxLifetimeMs && c.idleMs() <= idleTimeoutMs) continue;
            if (!idle.remove(c)) continue;                // a borrower won the race
            if (!permits.tryAcquire()) { idle.offerLast(c); continue; }  // cannot account
            try { c.destroy(); } finally { permits.release(); }
        }
    }

    private void reportLeak(PooledConn c) {
        Borrow b = inUse.get(c);
        if (b != null) { /* WARN with b.stack() and b.owner(): names the offending path */ }
    }

    Stats stats() {
        return new Stats(maxSize - permits.availablePermits(), idle.size(),
                         inUse.size(), permits.getQueueLength());
    }

    @Override public void close() throws Exception {
        shuttingDown = true;                              // stop lending first
        PooledConn c;
        while ((c = idle.pollFirst()) != null)
            if (permits.tryAcquire()) {
                try { c.destroy(); } finally { permits.release(); }
            }
        if (!permits.tryAcquire(maxSize, 10, TimeUnit.SECONDS))
            inUse.keySet().forEach(PooledConn::destroy);  // bounded drain, then force
        else permits.release(maxSize);
        keeper.shutdownNow();
    }

    static final class PoolExhaustedException extends RuntimeException {
        PoolExhaustedException(Stats s) { super("pool exhausted: " + s); }
    }
}
```

→ The wrapper makes returning the default: `close()` returns, it never closes the socket.  
→ A second `close()` must be a no-op, or the permit is released twice and the bound is destroyed.  

```java
import java.util.concurrent.atomic.AtomicBoolean;

public final class PooledConn implements AutoCloseable {
    private final Pool pool;
    private final java.sql.Connection raw;
    private final long createdAtNanos = System.nanoTime();
    private volatile long idleSinceNanos = System.nanoTime();
    private final AtomicBoolean closed = new AtomicBoolean(false);
    private volatile boolean broken = false;

    PooledConn(Pool pool, java.sql.Connection raw) { this.pool = pool; this.raw = raw; }

    public java.sql.Connection raw() {
        if (closed.get()) throw new IllegalStateException("connection already returned");
        return raw;
    }
    public void markBroken() { this.broken = true; }

    long ageMs()  { return (System.nanoTime() - createdAtNanos) / 1_000_000L; }
    long idleMs() { return (System.nanoTime() - idleSinceNanos) / 1_000_000L; }
    boolean valid() { try { return raw.isValid(1); } catch (Exception e) { return false; } }
    PooledConn touch() { this.idleSinceNanos = System.nanoTime(); return this; }
    void destroy() { try { raw.close(); } catch (Exception ignored) { } }

    @Override public void close() {
        if (!closed.compareAndSet(false, true)) return;   // idempotent: no double release
        boolean dirty = broken;
        try {
            if (!raw.getAutoCommit()) { raw.rollback(); raw.setAutoCommit(true); }
        } catch (Exception e) {
            dirty = true;                                 // reset failed: do not reuse
        }
        pool.release(this, dirty);
    }
}
// try (PooledConn c = pool.borrow(500)) { c.raw().prepareStatement("..."); }
```

- Why the rollback-on-return exists
  - A caller that threw mid-transaction leaves an open server-side transaction and held locks.
  - Returning it hands the next borrower someone else's uncommitted state, and an `idle in transaction` backend blocks vacuum and pins row locks for every other client.
  - Reset failure is treated as broken: a session that cannot be proven clean is not reusable.

## 9. Validation, eviction, maxLifetime, leak detection — IC3 baseline

- Validation on borrow
  - Validate only above `30 s` `(assume)` idle age, via `Connection.isValid(timeout)` or a driver `SELECT 1`.
  - Always-validate adds a round-trip to every borrow, roughly doubling warm-borrow latency for a check that almost always passes.
  - Defeater: threshold validation is probabilistic
    - A connection can die inside the window, so callers must still handle a connection error and the pool must destroy on it.
- `maxLifetime`
  - Retire past `30 min` `(assume)`, with jitter so the pool does not retire everything at once.
  - Bought: connections drift back onto a new primary after failover instead of pinning; DNS and LB changes take effect within one lifetime; per-session server-side leaks are bounded; middlebox idle expiry is pre-empted rather than discovered.
  - Cost: a steady reconnect rate, which must sit below what the database's auth path absorbs.
  - Rule: keep `maxLifetime` under any infrastructure-imposed connection timeout.
- Idle eviction
  - Above `minIdle`, close connections idle beyond `10 min` `(assume)`.
  - With `minIdle == maxSize` this pass does nothing, which is the deliberate fixed-pool trade: idle database resources for zero connect latency on a spike.
- Leak detection
  - Arm at borrow for `30 s` `(assume)`; cancel on return; on fire, log the captured stack at WARN.
  - It captures a stack rather than a counter because "the pool is empty" is useless while "these three stacks held connections for four minutes" names the bug.
  - Defeater: a firing task is not proof of a leak
    - A slow query looks identical; separate them by hold time, which is unbounded for a leak and bounded by the statement timeout for a query.
  - The structural fix is the wrapper, not the detector: try-with-resources makes a leak require an explicit mistake.
- Reaper race
  - Remove from the deque before closing and account for the permit, or eviction and borrow both claim the same connection.
  - `idle.remove(c)` is the arbitration: exactly one side gets `true`.
- Shutdown
  - Order matters: set `shuttingDown`, drain idle, bounded await on in-use, then force.
  - Reversing the first two lets a borrow slip in after the drain.
  - Force-closing after a bounded drain is correct, because an unbounded drain turns a deploy into an outage.

## 10. Sizing math and why growing the pool is usually wrong — IC3 baseline

- The formula that sets the ceiling
  - `maxSize ≈ (database cores × 2) + effective spindles` (sourced: HikariCP "About Pool Sizing").
  - `× 2` is not application slack; it covers the fraction of time each database worker is blocked on storage or network.
  - Decision: the ceiling is a property of the database, so two services against one `8`-core database share the `16`–`20`, they do not each get it.
- The formula that says whether you are near it
  - `busy = λ × W`. `100/s × 50 ms = 5`. `100/s × 500 ms = 50`.
  - Decision: compare `λ × W` to `maxSize` before touching config
    - Far below `maxSize` with timeouts ⇒ a leak, not capacity.
    - Above `maxSize` because `W` grew ⇒ the query or the transaction, not the pool.
- Why growing usually makes it worse
  - Past the database's parallel capacity, added connections add context switching, lock contention, and buffer-pool pressure instead of throughput.
  - Each connection is a backend with its own work memory, so `N` connections multiply the cost of one expensive sort.
  - The queue does not disappear; it moves into the database, where the application's timeout cannot shed it.
  - 🗣 "A connection pool is a throttle. Growing it past the database's capacity does not raise throughput; it moves the queue somewhere you cannot shed load from."
- The three real causes of exhaustion, in check order
  - Leak — hold time unbounded, detector names a stack. Fix the code.
  - Slow statement or long transaction — hold histogram shifts right, database shows long-running or idle-in-transaction backends. Fix the query, add a statement timeout.
  - Genuine demand — `λ × W` exceeds a pool already below `cores × 2`. Only now is growing correct, and only to the database budget.

| Knob | Start from | Trades | Change when |
|---|---|---|---|
| `maxSize` | `cores × 2` `(assume 20)` | Database parallelism vs. application queueing | `λ × W` exceeds it *and* the database has headroom |
| `minIdle` | `= maxSize` | Idle database resources vs. cold-start latency | Traffic is spiky and connect latency shows in p99 |
| `borrowTimeout` | `500 ms` `(assume)` | Load shedding vs. transient tolerance | Always keep it below the caller's own deadline |
| `connectTimeout` | `< borrowTimeout` | Fast failure vs. slow DNS/TLS tolerance | A slow connect must not eat the whole borrow budget |
| `validateIfIdle` | `30 s` `(assume)` | Round-trip tax vs. dead-connection risk | The network kills idle connections aggressively |
| `maxLifetime` | `30 min` `(assume)` | Reconnect rate vs. staleness and failover pinning | Must sit below any infrastructure idle timeout |
| `leakThreshold` | `30 s` `(assume)` | Log noise vs. leak visibility | Set above the p999 legitimate hold time |
| Fairness | unfair | Throughput vs. starvation | The wait tail is unexplained by the p99 |

## 11. Failure, operations, and security

| Failure | Blast radius | Detection | Degraded behavior | Recovery |
|---|---|---|---|---|
| Database restart kills idle connections | Every process holding idle connections; first borrows after restart | `isValid` failures spike; connect rate jumps | Borrows destroy the dead connection and create a replacement, costing one connect latency | Lazy replacement via validate-on-borrow; `maxLifetime` churns survivors validation missed |
| Network partition mid-borrow | One caller's transaction and that connection | SQLException on the statement; connection-error metric | Wrapper marked broken, connection destroyed instead of returned, permit released | Retry only if idempotent; the next borrow creates a fresh connection |
| Slow query hogs connections | The whole pool, so every caller of the service | Hold histogram shifts right; borrow timeouts rise while database CPU stays low | Borrow timeouts shed load at the pool boundary instead of piling into the database | Statement and transaction timeouts; fix the query or index; do not grow the pool |
| Connection leak in caller code | Pool shrinks permanently until restart | Leak detector logs a borrow stack; `inUse` gauge never falls | Fewer usable connections, then exhaustion with a typed error | Fix the missing try-with-resources at the named site; restart restores capacity |
| Thundering rebuild after database recovery | The database's auth path, fleet-wide | Connect-rate spike; auth latency; `max_connections` errors during recovery | Creation under a permit caps each process at `maxSize` sockets | Jittered connect backoff; stagger `maxLifetime` so retirement is not synchronized |
| Sibling service exhausts `max_connections` | Every client of that database, operators included | `FATAL: too many clients already`; connect failures with an empty local pool | Borrows fail fast at connect instead of hanging | Budget `max_connections` per service; keep `superuser_reserved_connections`; cap the offender by role |
| Firewall or NAT drops idle TCP state | Idle connections, found by the next borrower | `isValid` failures on long-idle connections; RST on first use | Threshold validation catches most before a caller does | Keep `maxLifetime` and `idleTimeout` under the middlebox timeout; TCP keepalive shorter still |
| Pool shutdown with in-flight work | Requests in flight during a deploy | Shutdown log records in-use count at drain start | Lending stops at once; idle closed; in-use gets a bounded grace period | Drain traffic before shutdown; force-close at the bound so a hung statement cannot block the deploy |
| Reaper thread dies | Age and idle limits silently unenforced | Reaper heartbeat; connection-age gauge stops advancing | Pool still lends; connections age past `maxLifetime` | Wrap the reaper body in try/catch so one exception cannot kill the scheduled task; alarm on stale heartbeat |
| Credential rotation invalidates the password | New connections only | Auth errors on connect while borrows still succeed | Serves from idle until connections age out, then fails | Refresh the credential supplier before `maxLifetime` retires the last connection |

- Observe
  - `total`, `idle`, `inUse`, `waiters` gauges — sustained `waiters > 0` is the saturation signal.
  - Borrow wait histogram, kept separate from the hold-time histogram.
  - Borrow timeout rate, alarmed; connection create and create-failure rates.
  - Connection age distribution, to prove `maxLifetime` fires.
  - Leak detections with stacks at WARN; validation failure rate as the early network/database signal.
- Retry discipline
  - Do not retry `PoolExhaustedException` in-process: it is a load signal, and retrying adds load.
  - Retry connect failures with exponential backoff and jitter, bounded by the borrow deadline.
  - Never retry a statement that may have committed; only idempotent operations, or those with an idempotency key.
  - Do not run a long retry while holding a permit — that is capacity denied to everyone else.
- Isolation and security
  - One pool per endpoint **and** per credential; sharing across credentials makes session state ambiguous.
  - Reset session state on return — autocommit, isolation, search path, temp tables.
  - That reset is a security boundary in multi-tenant services: an unreset `SET ROLE` is a privilege leak, not a style bug.
  - Never log the URL or credentials in the exhaustion error; log the stats.
- Rollout and rollback
  - Change one knob at a time; `maxSize` and `borrowTimeout` together make the result uninterpretable.
  - Canary a `maxSize` increase on one instance and watch database CPU and lock waits, not only application latency.
  - Keep the sum of local ceilings under the database budget always, so rollback never needs a database change.

## 12. Alternatives and IC4 stretch

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Semaphore plus idle queue (this design) | Permits bound existence; a deque stores idle | Two small invariants, each provable on a whiteboard; creation is naturally bounded | Two structures to keep consistent; needs `finally` discipline on every path | Interview baseline, and any hand-rolled pool whose correctness must be argued |
| Single synchronized structure | One lock over a list plus a counter | Simplest to state; one place to reason about | "Being created" is neither idle nor in use, so the counter is hand-maintained; the lock spans the create decision | Very low concurrency, or a teaching example |
| HikariCP `ConcurrentBag` with thread-local stripes | A shared bag plus per-thread lists so a returning thread reuses its own connection | Removes hot-path queue contention; production-proven; brings leak detection, `maxLifetime`, keepalive for free | Affinity can strand connections on parked threads; harder to reason about under virtual threads | Production Java services — the correct real answer, and the next optimization over the deque |
| External proxy pool such as PgBouncer | A process multiplexing many client connections onto few server connections | Bounds connections fleet-wide, not per process; transaction pooling raises the ratio sharply | Another hop and failure domain; transaction pooling breaks session state, prepared statements, `SET`, advisory locks, `LISTEN/NOTIFY` | Many or elastic processes where per-process pools cannot sum to a safe total |
| Per-request connection, no pool | Connect, query, close | No pooling bugs; leaks are impossible | Handshake and auth per request; unbounded connections under load — the exact failure this design prevents | Batch jobs, CLI tools, single-connection cron tasks |
| Framework `DataSource` defaults | Rely on the container's pool untouched | No code to own | Defaults are rarely the right size; the pool is still there, just unexamined | Never as an answer — the question is asking you to look inside |

- Recommendation
  - Deciding variable: how many processes share one database.
  - Few and fixed ⇒ a per-process pool; HikariCP in production, this design on the whiteboard.
  - Many or elastic ⇒ per-process pool **plus** a proxy, because per-process ceilings cannot sum to a safe total when the count is not fixed.
- IC4 stretch — stronger requirement: a fleet-wide budget
  - The baseline bounds one process; bounding the fleet is structurally a different problem, because a local semaphore cannot enforce a global bound.
  - In increasing cost: static division by max replica count; a proxy tier that becomes the real ceiling; a lease service handing out allowances — the `s3.05` mechanism applied to connections.
  - Take static division first; move to a proxy only when the replica count becomes elastic.
- IC4 stretch — 10× load
  - 10× the rate at the same hold time raises `λ × W` 10×, but the ceiling does not move, because `cores × 2` did not change.
  - The structural response is to remove borrows, not add connections: cache reads, batch writes, route reads to replicas with their own pool, shard.
  - The pool's job at 10× is to shed cleanly: borrow timeout becomes the primary shedding control and `waiters` becomes the autoscaling signal.
  - Under virtual threads, 10× more concurrent tasks change nothing about the ceiling — which is the point worth saying aloud.
- IC4 stretch — cost and blast radius
  - Each connection is a server-side process with its own memory, so raising `max_connections` raises the database's memory floor, the instance size, and the bill.
  - An oversized pool converts a slow-query incident from "one service degrades" into "the database is unavailable to everyone".
  - Control: give each service its own database role with a per-role connection limit, so the database enforces the budget instead of trusting every service's config; reserve connections for operators so incidents stay diagnosable.
- IC4 stretch — migration and rollout
  - Moving to a proxy tier: point a canary at the proxy, keep its local pool but shrink it, compare hold time and error rate, then roll forward.
  - Never introduce the proxy and change local `maxSize` in one deploy; the two have opposite failure signatures.
  - Keep the sum of local ceilings under `max_connections` at every step so rollback never needs a database change.
  - Transaction-pooling mode is the hazard: audit session-scoped features first, because their failure is silent and correctness-affecting, not a connection error.
- Weakest assumption
  - That hold time is stable near `50 ms`.
  - Every sizing number collapses if hold time is bimodal, because the average hides the tail that actually occupies the pool.
  - Mitigation: measure the hold histogram per query shape before trusting `λ × W`, and bound the tail with a statement timeout rather than hope.
- Over-engineering warning
  - Do not build thread-local striping, a lock-free bag, or adaptive sizing before proving the permit invariant and measuring contention.
  - Almost every real pool incident is a leak or a slow query, and none of those optimizations fixes either.
  - Do not add a proxy tier when the process count is fixed and small; it buys a bound you already have and costs a hop, a failure domain, and a session-semantics hazard.

## 13. Interview pushback and validation

- Q1: The pool is exhausted under load. Why not just raise `maxSize`?
  - **IC3 baseline**
    - Check hold time first: exhaustion at a low `λ × W` means a leak or a slow query, and more connections only spread the same stall wider.
    - The ceiling is the database's `cores × 2`, so raising past it buys no throughput.
  - **IC4 stretch**
    - Past parallel capacity, added connections add context switching, lock contention, and per-backend memory, so measured throughput falls while latency rises.
    - It also moves the queue from the pool, where the timeout can shed it, into the database, where it is invisible and unsheddable.
- Q2: Why a semaphore plus a queue instead of one synchronized structure?
  - **IC3 baseline**
    - The permit bounds *existence* — idle plus in-use plus being-created. The queue only stores idle.
    - Two separate invariants, each trivially correct.
  - **IC4 stretch**
    - The merge failure is specific: a thread that has decided to create is in neither collection, so a size check under-counts and two threads both create, breaching the ceiling once per race.
    - HikariCP keeps the same separation and stripes only the storage half; the bound stays central.
- Q3: Why not validate on every borrow?
  - **IC3 baseline**
    - It adds a round-trip to a check that almost always passes, roughly doubling warm-borrow latency.
    - Threshold validation plus `maxLifetime` covers the realistic cases.
  - **IC4 stretch**
    - Validation is probabilistic at any threshold, so callers must still handle connection errors.
    - Under a per-borrow `SELECT 1`, a database that is slow but alive makes validation itself the bottleneck, so always-validate deepens brownouts instead of preventing them.
- Q4: Why is unbounded wait on exhaustion wrong?
  - **IC3 baseline**
    - It hides an incident as latency: callers pile up and nothing alarms until the service is stalled.
    - A bounded timeout produces a typed error, a metric, and an alarm.
  - **IC4 stretch**
    - The timeout must be under the caller's deadline, or capacity is spent completing work for a client that already disconnected.
    - `waiters` is the autoscaling signal, and unbounded wait removes it because saturation never manifests as failure.
- Q5 (premise reversal): The database is a serverless autoscaling endpoint with no fixed `max_connections`. Defend the bounded pool.
  - **IC3 baseline**
    - The bound is still the throttle keeping one service from consuming the backend, and still the only place load can be shed against a deadline the caller controls.
    - Autoscaling has a lag; a burst needs client-side bounding during it.
  - **IC4 stretch**
    - The bound changes meaning rather than disappearing: it stops being a safety limit against `max_connections` and becomes a cost and blast-radius limit, because unbounded concurrency against a metered backend is an unbounded bill.
    - The sizing input changes too — the ceiling now derives from the cost budget and the provider's documented per-connection limits, not an observable core count.
    - `maxLifetime` matters more, not less, because an autoscaling endpoint moves and connections must rebalance onto new capacity.
- Q6 (premise reversal): You have `5,000` short-lived Lambda-style workers; one pool per process is wrong. Now what?
  - **IC3 baseline**
    - A per-process pool cannot help when the process outlives its connection by less than the payback period — every invocation pays a connect.
    - `5,000` workers at even one connection each is far past any `max_connections`, so per-process bounding cannot sum to a safe total.
    - The answer is an external proxy such as PgBouncer, or the platform's managed proxy, as the real ceiling.
  - **IC4 stretch**
    - Transaction pooling is what makes the ratio worthwhile and is also the hazard: prepared statements, `SET`, advisory locks, `LISTEN/NOTIFY`, and temp tables break silently, so the migration starts with an audit, not a config change.
    - Keep a tiny per-worker pool of `1`–`2` anyway so a warm container skips the handshake, and let the proxy own the global bound.
    - If the workload is genuinely one request per invocation, question whether a connection-oriented database fits at that fan-out at all.
- Q7: A borrower throws mid-transaction. What happens to the connection?
  - **IC3 baseline**
    - It is destroyed, not returned: the session may hold an open transaction, locks, and unread results.
    - The permit is still released in `finally`, so pool capacity is unchanged.
  - **IC4 stretch**
    - Destroying on every application-level exception is wasteful, so the refinement is to attempt rollback and autocommit reset and destroy only if the reset fails.
    - Operationally this is about `idle in transaction`: a returned connection with an open transaction blocks vacuum and holds row locks for every other client of the database.
- Q8: The pool is empty — leak or slow query?
  - **IC3 baseline**
    - Hold time separates them: a leak's is unbounded, a slow query's is bounded by the statement timeout.
    - The leak detector's captured stack names the borrow site directly.
  - **IC4 stretch**
    - Cross-check the database: a slow query shows an active backend running a statement, a leak shows an idle backend with an open session and no statement.
    - The fixes differ — automatic return through the wrapper versus a statement timeout and an index — and neither is `maxSize`.
- Validation scenarios
  - `maxSize = 1`, two threads: the second blocks then times out with a typed error, never creating a second connection.
  - Borrow then throw: the connection is destroyed and `availablePermits()` returns to `maxSize`.
  - Double `close()`: `availablePermits()` never exceeds `maxSize`.
  - Kill every server-side backend while idle: the next borrows validate, destroy, recreate, and succeed.
  - Hold past `leakThreshold`: exactly one WARN with the borrow stack, and no correctness effect.
  - `maxLifetime = 1 s`: age never exceeds it and the reaper never races a borrower into a double close.
  - Reaper and borrower contend for one idle connection: exactly one wins `idle.remove`, and the invariant holds after.
  - `shutdown` with one connection in use: lending stops, drain waits, force-close at the bound.
  - Randomized concurrent borrow/return/evict for `60 s`: assert `permitsAcquired == idle + inUse + beingCreated` at every quiescent point.

## 14. Recall card

- "A semaphore bounds how many connections may exist; the deque only stores the idle ones — two invariants, each trivially correct."
- "Acquire the permit before deciding to reuse or create, and release it only once the connection is idle again or destroyed."
- "`close()` on the wrapper means return, and it must be idempotent, or one leaky caller destroys the bound."
- "Size to the database's `cores × 2`, then check `λ × W` — if they disagree, the problem is hold time, not the pool."
- "The pool is a throttle: growing it past the database's capacity moves the queue somewhere you cannot shed load from."
