## 1. Crux and why it is hard

- Naive one: blobs as rows in the metadata store.
  - Item-size caps exist because large values wreck compaction and cache locality.
  - Backup and rebalance become blob-sized problems.
- Naive two: one large file server — single point of failure, ceiling of one machine's disks.
- First break: a client uploads 900 GB of a 1 TB object and dies.
  - If the namespace was mutated incrementally, a reader sees a truncated object that never existed.
- Second break: three copies land on three hosts sharing one rack power feed.
  - "Survives host loss" was never true for a correlated failure.
- Minimum primitives
  - Split **metadata** (small, hot, strongly consistent, sharded) from **data** (large, dumb, replicated or coded).
  - **Immutable content-addressed chunks**, so a retried write is idempotent by construction.
  - Visibility is one **manifest commit** after every byte is durable.
  - **Repair and scrub**, so redundancy is a maintained invariant, not a one-time placement.
  - **Garbage collection** for chunks no manifest references.
- 🗣 "Metadata is a strongly-consistent database problem; data is a placement-and-repair problem. Never let the two mix."
- 🗣 "The upload is not the commit. Bytes become an object at exactly one transaction."

## 2. Clarifying questions

| Question | Assumed answer | Why it changes the design |
|---|---|---|
| Object size range? | 1 KB to 5 TB; chunk above 64 MB `(assume)` | Decides whether chunking exists and whether coding amortizes |
| Mutability? | Write-once; overwrite makes a new version | Removes in-place update and range locking from scope |
| Consistency? | Read-after-write on a committed version | Metadata must be strongly consistent; data may be eventually placed |
| Durability / availability? | 11 nines, 99.9% `(assume)` | Drives copy count, domain spread, repair rate |
| Access pattern? | Whole-object GET plus range GET | Fixed chunk size makes offset→seq a division |
| Tenancy and delete? | Multi-tenant with quotas; tombstone now, reclaim later | Keys are tenant scoped; synchronous erase of 5 TB is a self-inflicted IO outage |

## 3. Requirements

- Functional scope: `PUT` including multipart, `GET` whole or ranged, `HEAD`, `DELETE` with tombstone, prefix `LIST` with pagination, and maintained redundancy on every chunk.
- Targets are interview assumptions unless a linked source says otherwise.

| Requirement | Target | Enforced by |
|---|---|---|
| GET first byte | p99 < 100 ms in region `(assume)` | Cached metadata lookup, then a direct client→chunk-server read that never crosses the metadata tier |
| GET throughput | ≥ 1 GB/s per large object `(assume)` | Parallel reads across ≥ 8 chunk servers, one stream per chunk |
| Commit latency | p99 < 200 ms `(assume)` | Commit is one transaction on one shard; bytes are already durable |
| Atomic visibility | 0 partially visible objects | Version row flips to `COMMITTED` in one transaction after all chunks are durable |
| Durability | 11 nines annual `(assume, order of magnitude)` | 3 copies across 3 fault domains or 8+4 coding, plus repair inside the window |
| Repair window | Under-replicated chunk restored < 60 min `(assume)` | Prioritized queue, one-copy chunks first, reserved repair bandwidth |
| Corruption detected | 100% of reads verified | Per-chunk SHA-256 on every read plus a 14-day scrub cycle `(assume)` |
| Metadata availability | 99.9% per shard `(assume)` | Replicated consensus group per shard (`s3.04`) |
| Scale | 10^11 objects, exabyte capacity | Hash-sharded metadata; chunk servers added without a namespace rewrite |
| Tenant isolation | No tenant exceeds its provisioned rate | Per-tenant token buckets at the gateway (`s1.01`) plus per-bucket quota |

- Invariants
  - A chunk id equals the SHA-256 of its bytes, so a chunk is present or absent, never updated.
  - A version is visible only in state `COMMITTED`, with its minimum durable placements recorded.
  - Copies of one chunk occupy distinct fault domains.
  - A chunk is deletable only when unreferenced and past the orphan grace period.
- Non-goals: POSIX semantics (append, subtree rename, hard links), in-place range mutation, cross-object transactions, and strong consistency of any cross-region copy.

<a id="s502-4"></a>

## 4. Capacity and consequence

- All workload values are sizing assumptions.
- Metadata footprint: `10^9 objects × ~500 B ≈ 500 GB`, plus chunk rows for the large tail.
  - Decision: metadata is an ordinary sharded-database problem, so it can afford consensus replication and strong consistency.
- Data footprint: `10^9 × 5 MB = 5 PB` logical; `15 PB` raw at 3 copies, `7.5 PB` at 8+4.
  - Decision: that gap is the whole cost case, so redundancy is a per-bucket setting, never a global constant.
- Chunking and manifest: a 1 TB object at 64 MB is `16,384` chunks and `~1.3 MB` of manifest; 5 TB is `81,920` rows.
  - Decision: chunk rows live apart from the version row and are paged, and very large objects need a bigger chunk size — hence chunk size stored per version.
- Repair bandwidth: one 16 TB disk at a reserved `200 MB/s` from a single source takes `≈ 22 hours`.
  - Decision: the 60-minute window is unreachable from one source, so placement must scatter a disk's chunks over hundreds of peers and repair must read them in parallel.
- Coding amplification: rebuilding one 8+4 fragment reads `8`, so recovery moves ~`8×` the lost bytes.
  - Decision: a coded pool needs ~8× the repair bandwidth budget, capping how much of the fleet can be coded before network, not disk, binds.
- Small objects: a 10 KB object under 8+4 becomes `12` fragments of `1.25 KB`, each with a placement row.
  - Decision: below `(assume) 1 MB` coding costs more in rows and IOPS than it saves in bytes, forcing a hybrid policy instead of one scheme.

## 5. Architecture and flow

```text
                    client
                       |
                 [ API gateway ]   auth, tenant quota, signed grants
                       |
        +--------------+---------------------------+
        |                                          | (grants only,
  metadata service                                 |  never bytes)
  strongly consistent, hash-sharded                v
  bucket/key/version -> manifest            chunk servers (data plane)
  chunk id -> placements                    immutable checksummed chunks
        |                                   3 copies across fault domains
        |                                      or k+m coded fragments
        v                                          ^
  placement + repair  --- heartbeat, inventory diff, scrub ---+
        |
        v
  garbage collector: chunks referenced by no committed manifest
```

- API gateway: buys auth and quota, pays one control-path hop, deliberately off the byte path.
- Metadata service: buys atomic visibility and read-after-write, pays consensus write latency.
  - Defeater: atomicity holds only while one version lives entirely on one shard.
- Chunk servers: buy linear capacity and direct client bandwidth, pay a repair obligation on every byte.
- Placement and repair: buys the maintained-redundancy invariant, pays background IO budgeted against foreground traffic.
- Garbage collector: buys the freedom to write bytes before committing, pays a grace period of disk held by orphans.

**PUT trace**

→ Gateway authenticates the tenant, resolves the bucket, checks quota.  
→ Metadata opens an upload and returns an upload id plus a placement plan.  
→ Client splits the stream into fixed 64 MB chunks and hashes each to get its content id.  
→ Client writes each chunk to its targets in parallel; each write is idempotent by content id.  
→ Chunk servers persist, fsync, record the checksum, acknowledge.  
⇒ Nothing is visible yet; a crash here leaves orphan chunks and no object.  
→ Client commits with the ordered chunk list and expected entity tag.  
→ Metadata verifies durable placements, then writes version and chunk rows in one transaction.  
⇒ The object becomes visible at that commit, all or nothing.  

**GET trace**

→ Gateway authorizes and resolves `(bucket, key)` to the latest committed version.  
→ Metadata returns the chunk list and placements, from cache when warm.  
→ Client reads chunks in parallel from the nearest healthy placement, verifying each against its content id.  
⇒ A mismatch fails only that placement; the read retries elsewhere and files a repair task.

## 6. API and data model

| Operation | Contract | Idempotency and conflicts |
|---|---|---|
| `PUT /b/{bucket}/o/{key}` | Single-shot upload; returns version and tag | Content hash makes a retry a no-op; concurrent PUTs make two versions, last commit wins |
| `POST /b/{bucket}/u` | Open a multipart upload | Same idempotency key returns the same `upload_id` |
| `PUT /b/{bucket}/u/{id}/{part}` | Upload one part; returns its content id | Idempotent by content id; a differing re-upload replaces the pending part only |
| `POST /b/{bucket}/u/{id}/commit` | Atomic commit of the ordered part list | Same list and tag returns the same version; a different list on a committed upload is `409` |
| `GET /b/{bucket}/o/{key}` | Whole object or `Range` | Safe; `If-Match` pins an entity tag |
| `DELETE /b/{bucket}/o/{key}` | Tombstones the latest version | Repeat delete is a no-op |
| `GET /b/{bucket}/o?prefix=&cursor=` | Ordered key-range page | Cursor is the last key returned; no unpaginated list |

| State | Key | Fields and invariant |
|---|---|---|
| Object version | `(tenant_id, bucket, key, version)` | Size, entity tag, state; visible only when `COMMITTED` |
| Manifest entry | `(tenant_id, bucket, key, version, seq)` | Ordered chunk reference plus byte offset |
| Chunk | `(chunk_id)` | Size, scheme, refcount; content addressed |
| Placement | `(chunk_id, node_id)` | Fault domain, fragment index, presence state |
| Node | `(node_id)` | Fault domain, capacity, free space, health |
| Pending upload | `(tenant_id, bucket, upload_id)` | Uncommitted part list; expires |

- Reference DDL
  - Names here win over the [companion schema](../../1sde/1.backend/2.rest102.md#platform-6); the deviation is that `chunks` and `chunk_placements` are global rather than tenant scoped, with `tenant_scope` recording that cross-tenant deduplication is off by default.

```sql
CREATE TABLE object_versions (
  tenant_id text NOT NULL, bucket text NOT NULL, key text NOT NULL,
  version bigint NOT NULL,                        -- monotonic per (tenant,bucket,key)
  size_b bigint NOT NULL,
  chunk_size_b integer NOT NULL,                  -- fixed per version: offset -> seq by division
  etag text NOT NULL,                             -- hash over the ordered chunk id list
  state text NOT NULL,                            -- PENDING | COMMITTED | TOMBSTONED
  redundancy text NOT NULL DEFAULT 'REPLICA_3',   -- REPLICA_3 | EC_8_4
  committed_at timestamptz,
  PRIMARY KEY (tenant_id, bucket, key, version),
  UNIQUE (tenant_id, bucket, key, etag, version), -- a retried commit cannot fork a version
  CHECK (state IN ('PENDING','COMMITTED','TOMBSTONED')),
  CHECK (redundancy IN ('REPLICA_3','EC_8_4')),
  CHECK (size_b >= 0 AND chunk_size_b > 0),
  CHECK ((state = 'COMMITTED') = (committed_at IS NOT NULL))
);
CREATE INDEX obj_list ON object_versions (tenant_id, bucket, key, version DESC)
  WHERE state = 'COMMITTED';                      -- prefix listing + latest-version lookup
CREATE INDEX obj_by_age ON object_versions (tenant_id, bucket, committed_at)
  WHERE state = 'COMMITTED';                      -- lifecycle and tiering sweeps

CREATE TABLE object_chunks (
  tenant_id text NOT NULL, bucket text NOT NULL, key text NOT NULL,
  version bigint NOT NULL,
  seq integer NOT NULL,                           -- 0-based position in the object
  chunk_id text NOT NULL,                         -- sha256 hex of the bytes
  size_b integer NOT NULL,
  offset_b bigint NOT NULL,                       -- first byte within the object
  PRIMARY KEY (tenant_id, bucket, key, version, seq),
  FOREIGN KEY (tenant_id, bucket, key, version) REFERENCES object_versions,
  UNIQUE (tenant_id, bucket, key, version, offset_b),   -- no two chunks claim one offset
  CHECK (seq >= 0 AND size_b > 0 AND offset_b >= 0)
);
CREATE INDEX chunk_backrefs ON object_chunks (chunk_id);  -- "who still needs this chunk?"

CREATE TABLE chunks (
  chunk_id text PRIMARY KEY,                      -- content address; never mutated
  size_b integer NOT NULL,
  required_copies integer NOT NULL,               -- 3, or k+m = 12
  min_readable integer NOT NULL,                  -- 1, or k = 8
  tenant_scope text NOT NULL,                     -- blocks cross-tenant dedup by default
  refcount integer NOT NULL DEFAULT 0,            -- committed manifests referencing it
  created_at timestamptz NOT NULL,
  CHECK (size_b > 0 AND refcount >= 0),
  CHECK (required_copies >= min_readable AND min_readable >= 1)
);
CREATE INDEX chunk_gc ON chunks (created_at) WHERE refcount = 0;   -- GC candidate sweep

CREATE TABLE nodes (
  node_id text PRIMARY KEY,
  fault_domain text NOT NULL, availability_domain text NOT NULL,
  capacity_b bigint NOT NULL, free_b bigint NOT NULL,
  health text NOT NULL,                           -- UP | DRAINING | DOWN | DECOMMISSIONED
  last_heartbeat_at timestamptz NOT NULL,
  CHECK (health IN ('UP','DRAINING','DOWN','DECOMMISSIONED')),
  CHECK (free_b >= 0 AND free_b <= capacity_b)
);
CREATE INDEX node_alloc ON nodes (availability_domain, fault_domain, free_b DESC)
  WHERE health = 'UP';                            -- allocator candidate scan

CREATE TABLE chunk_placements (
  chunk_id text NOT NULL, node_id text NOT NULL,
  fragment_index integer NOT NULL DEFAULT 0,      -- 0 for replicas; 0..k+m-1 when coded
  state text NOT NULL,                            -- WRITING | PRESENT | SUSPECT | LOST
  fault_domain text NOT NULL,                     -- denormalized so spread is enforceable here
  verified_at timestamptz,                        -- last successful scrub
  PRIMARY KEY (chunk_id, node_id),
  FOREIGN KEY (chunk_id) REFERENCES chunks,
  FOREIGN KEY (node_id) REFERENCES nodes,
  CHECK (state IN ('WRITING','PRESENT','SUSPECT','LOST')),
  CHECK (fragment_index >= 0)
);
CREATE UNIQUE INDEX placement_domain_spread       -- the fault-domain rule as an invariant
  ON chunk_placements (chunk_id, fault_domain, fragment_index)
  WHERE state IN ('WRITING','PRESENT');
CREATE INDEX placement_by_node ON chunk_placements (node_id, state);  -- dead-node repair scan
CREATE INDEX placement_scrub ON chunk_placements (verified_at) WHERE state = 'PRESENT';

CREATE TABLE pending_uploads (
  tenant_id text NOT NULL, bucket text NOT NULL, upload_id text NOT NULL,
  key text NOT NULL, chunk_size_b integer NOT NULL, idempotency_key text,
  expires_at timestamptz NOT NULL,                -- abandoned uploads become GC input
  PRIMARY KEY (tenant_id, bucket, upload_id),
  UNIQUE (tenant_id, bucket, idempotency_key),
  CHECK (chunk_size_b > 0)
);
```

- What is **not** relational
  - Chunk bytes are files on chunk-server disks addressed by content id with an on-disk checksum footer; the database holds only the reference and the placement.
  - The read-path cache keyed by `(tenant, bucket, key, version)` is derived state, always rebuildable.
  - Heartbeat and inventory streams reconcile into `nodes` and `chunk_placements` periodically; the in-memory view is fresher than the table.
  - The repair queue is an in-memory priority queue rebuilt from `chunk_placements` on restart.
  - Access logs and usage counters append to an event log (`s3.06`), not row updates.
  - `buckets` (redundancy default, coding threshold, quota) is a small control-plane table omitted here.

## 7. Write path and manifest commit — IC3 baseline

- One ordering rule carries the correctness argument: every byte is durable **before** any metadata says the object exists, and visibility is exactly one transaction.
- Why it works
  - Content addressing makes writing the same chunk twice indistinguishable from writing it once.
  - A partial upload leaves only orphans, and orphans are garbage, never a visible object.
  - The commit verifies placements, so an object cannot be committed at a redundancy the fleet did not achieve.

**Failure boundaries to volunteer**

→ The client dies after 15,000 of 16,384 chunks.  
⇒ No version row exists, so readers see nothing and the pending upload expires.  
→ Garbage collection reclaims the orphans after the grace period.

→ A chunk upload is retried after a timeout.  
⇒ The chunk id is the hash of the same bytes, so the retry is the same write.  
→ No duplicate storage and no correctness question.

→ The commit is retried after an ambiguous timeout.  
⇒ `UNIQUE (tenant, bucket, key, etag, version)` plus the upload id makes the second commit return the existing version.  
→ One committed part list yields exactly one version.

- Pseudocode
  - `for each fixed-size block: cid = sha256(block)`
  - `targets = plan_placement(cid, redundancy, distinct fault domains)`
  - `write to every target, idempotent by cid, wait for fsync ack`
  - `append (seq, cid, size, offset) to a local manifest`
  - `commit(manifest): one transaction — verify placements, bump refcounts, insert COMMITTED version`

```python
import hashlib

CHUNK = 64 * 1024 * 1024  # fixed size: offset -> seq is a division (see the read path)

def put_object(meta, store, tenant, bucket, key, stream):
    manifest, offset, seq = [], 0, 0
    for block in read_blocks(stream, CHUNK):
        cid = hashlib.sha256(block).hexdigest()        # content address
        acked = 0
        for node in meta.plan_placement(cid, bucket):  # distinct fault domains
            if store.put(node, cid, block):            # idempotent by cid; fsync before ack
                acked += 1
        if acked < meta.min_durable(bucket):
            raise DurabilityShortfall(cid, acked)      # never commit under-durable bytes
        manifest.append({"seq": seq, "cid": cid, "size": len(block), "offset": offset})
        offset += len(block)
        seq += 1
    # Nothing above is visible. The next call is the only atomic step.
    return meta.commit(tenant, bucket, key, manifest, etag=etag_of(manifest))

def etag_of(manifest):
    h = hashlib.sha256()
    for c in manifest:
        h.update(c["cid"].encode())
    return h.hexdigest()                               # deterministic: retried commits match
```

- The commit, stated as the transaction it is
  - `BEGIN` → insert the `PENDING` version row if absent → insert `object_chunks` → verify each chunk's `PRESENT` count meets `required_copies` → `UPDATE chunks SET refcount = refcount + 1` per distinct chunk → flip to `COMMITTED` with `committed_at` → `COMMIT`.
  - Defeater: atomic only because every row lives on the shard owning `(tenant, bucket, key)`; a version must never span shards.
- Java form, same ordering, commit as one unit of work.

```java
ObjectVersion putObject(Meta meta, ChunkStore store, String tenant,
                        String bucket, String key, InputStream in) throws IOException {
    List<ChunkRef> manifest = new ArrayList<>();
    long offset = 0; int seq = 0;
    for (byte[] block : Blocks.of(in, 64 << 20)) {
        String cid = Hashing.sha256().hashBytes(block).toString();
        int acked = 0;
        for (Node n : meta.planPlacement(cid, bucket)) {        // distinct fault domains
            if (store.put(n, cid, block)) acked++;              // idempotent by cid, fsync first
        }
        if (acked < meta.minDurable(bucket)) {
            throw new DurabilityShortfallException(cid, acked); // never commit under-durable bytes
        }
        manifest.add(new ChunkRef(seq++, cid, block.length, offset));
        offset += block.length;
    }
    return meta.commit(tenant, bucket, key, manifest);          // one transaction, one shard
}
```

- Cost paid: two coordination round trips per object, and orphan bytes holding real disk for the grace period after any failed upload.

## 8. Read path and range GET — IC3 baseline

- Resolution: `(tenant, bucket, key)` → latest `COMMITTED` version via `obj_list`, or an explicit version when named.
  - The result is immutable, so it caches without invalidation; only the latest-version pointer needs a short time to live.
- Whole-object GET: read chunks in parallel, stream in `seq` order, verify each against its content id before releasing bytes.
- Range GET
  - Fixed `chunk_size_b` turns offsets into division: `first_seq = floor(start / chunk_size)`, `last_seq = floor(end / chunk_size)`.
  - A 1 MB range of a 1 TB object touches one chunk, not the manifest.
  - Defeater: true only because chunk size is fixed per version and recorded on the version row; content-defined chunking would need an offset index and a binary search.

**Read failure boundaries**

→ The nearest placement returns a checksum mismatch.  
⇒ That placement is marked `SUSPECT` and excluded.  
→ The read retries another placement and enqueues a repair task.

→ Every placement of one chunk is unreachable while the rest are fine.  
⇒ The object is only partially readable.  
→ Fail the GET naming the failed byte range; never silently zero-fill a hole.

- Hot objects: immutability makes a content-addressed chunk trivially cacheable, since the id changes when the bytes change.
  - Two levers: raise the copy count for that object's chunks, or front it with a CDN (the `s4.04` path).
- Cost paid: parallel reads multiply connections, so a 16,384-chunk fetch needs a bounded concurrency window.

## 9. Placement, repair, and scrub — IC3 baseline

- Placement rule
  - Choose `required_copies` nodes with no shared fault domain, all `UP`, free space above the admission floor.
  - Rank by free space and write load so heterogeneous hardware fills evenly.
  - `placement_domain_spread` makes the domain rule a database invariant, not a hope about the allocator.
- Explicit allocator versus a hash ring
  - A ring is stateless and needs no lookup, but cannot express "this rack is 90% full", "this node is draining", or a per-tenant constraint.
  - The explicit allocator pays a row per copy and buys heterogeneity, drain, and constraints.
  - Name the middle ground aloud: CRUSH-style weighted hashing computes placement from a cluster map instead of storing every location.
- Repair loop
  - Chunk servers heartbeat and report inventory; the service diffs expected placements against reports.
  - A missing placement becomes `LOST` and enters the queue: one-copy chunks first, then below-target, then domain violations.
  - Read one good copy (replication) or `k` fragments (coding), write into a domain the chunk does not occupy, record the placement.
  - Reserve a bandwidth ceiling so a large failure cannot starve foreground traffic; raise it only while the one-copy queue is non-empty.
- Scrub: rolling background reads re-verify bytes against their content id; a mismatch marks `SUSPECT` and replaces from a good copy.
  - Without scrub, "3 copies" can silently be one good copy and two rotted ones — scrub is what makes the durability number defensible.
- Node lifecycle: `DRAINING` stops new placements and schedules copy-outs; `DOWN` past the threshold repairs everything the node held.
  - Defeater: an aggressive threshold turns a network blip into a fleet-wide repair storm, so it must exceed expected reboot time.

<a id="s502-10"></a>

## 10. Durability math and erasure coding — IC3 baseline

- The model: durability is a race between losing the remaining copies and repair restoring redundancy.
  - Levers are copy count, repair speed, and failure correlation.
  - Order of magnitude: roughly 10× better per extra independent copy, and roughly 10× better per 10× shorter repair window.
- Replication, `n = 3`
  - `3.0×` storage; survives any 2 losses; repair reads `1×` the lost bytes — the cheapest possible repair.
  - Reads are trivial: any one copy answers, best tail latency.
- Erasure coding, `8+4`
  - `12/8 = 1.5×` storage; survives any 4 of 12 fragments — a *stronger* loss tolerance than 3 copies at half the cost.
  - Repair reads `8` to rebuild `1`: about 8× amplification.
  - Healthy reads touch only the 8 data fragments; a degraded read gathers 8 survivors and decodes, adding CPU and tail latency.
  - Small objects amortize badly: 12 fragments and 12 placement rows for 10 KB of payload.
- The hybrid, which is the production answer
  - Small or hot, or below the coding threshold: 3 copies. Large or cold: 8+4, reached by a lifecycle transcode, not a client-visible change.
  - Facebook's `f4` is the public precedent for moving warm blobs from replication to coding as access rate drops.
- 🗣 "Erasure coding buys bytes and pays network; replication buys network and pays bytes. Choose per object, not per cluster."
- Correlated failure is the real defeater
  - Independence fails for rack power loss, one drive model's firmware bug, operator error, or a bug that deletes correctly on every copy.
  - Fault domains address the first, drive-model diversity the second, versioning and delayed reclaim the last two.
  - Say it explicitly: 11 nines describes device failure, not operator or software failure.

<a id="s502-11"></a>

## 11. Garbage collection of orphan chunks — IC3 baseline

- Two sources of garbage: chunks from an upload that never committed, and chunks whose last referencing version was tombstoned or expired.
- The safe rule
  - Delete only when `refcount = 0`, **and** past the grace period, **and** no pending upload could still reference the chunk.
  - The grace period must exceed the longest legal upload, or a slow but valid upload could lose its chunks before commit.
- Why commit ordering makes this safe
  - Refcounts only increase inside the commit transaction, and only drop through a delete that is itself a transaction.
  - So a chunk at `refcount = 0` outside the grace window is provably unreachable.

**Delete boundaries**

→ A user deletes a 5 TB object.  
⇒ Erasing 81,920 chunks synchronously spikes IO across hundreds of nodes.  
→ Write a tombstone, decrement refcounts asynchronously, pace the reclaim.

→ A tenant deletes a bucket by mistake.  
⇒ Immediate reclamation makes the data unrecoverable.  
→ Retain tombstoned versions for a window before refcounts drop; that window is the only real defence against operator error.

- Mechanics
  - Sweep `chunk_gc` in `created_at` order, re-check the reference inside the transaction that marks the chunk, then unlink on the nodes.
  - Node-side unlink is idempotent: removing an absent content id is a no-op.
  - Alarm on collector lag; free space falling while logical usage is flat is the earliest signal.
- Cost paid: orphan bytes are real capacity, so budget an allowance `(assume 2% of raw)`.

## 12. Failure, operations, and security

| Failure | Blast radius | Detection | Degraded behavior | Recovery |
|---|---|---|---|---|
| Chunk-server disk dies | Chunks on that disk, spread over many objects | Inventory diff versus expected placements | Reads served from survivors; those chunks under-replicated | Repair re-creates copies from peers, one-copy first |
| Whole node dies | Every chunk it held | Missed heartbeats past the down threshold | Same at larger scale; repair ceiling raised | Repair, then revive or decommission the node |
| Rack / fault domain loss | One copy of many chunks, never two | Domain health, under-replicated spike | Objects readable; durability margin reduced, not lost | Repair into other domains; block placements into the failed one |
| Metadata shard unavailable | That key range, reads and writes | Consensus health, per-shard error rate | Availability loss on that keyspace; durability untouched | New leader in the replicated group; no data movement |
| Client crashes mid-upload | One pending upload | Upload passes `expires_at` | Nothing visible; no partial object ever existed | Upload expires; collector reclaims orphans after the grace period |
| Silent bit rot on one copy | One chunk copy | Per-read verification and background scrub | Read fails over and returns correct bytes | Bad placement replaced; the disk watched for a rot pattern |
| Repair storm after correlated failure | Foreground latency fleet-wide | Queue depth, repair-bandwidth saturation | Foreground traffic slows as repair competes for IO | Hold the ceiling; drain the one-copy queue, defer the rest |
| Collector stalled or wedged | Cluster free space | Free space falls while logical usage is flat | Placements crowd onto fuller nodes; writes eventually rejected | Restart and replay `chunk_gc`; the grace period makes delay safe |
| Hot object saturates its copies | One key and the nodes holding it | Per-chunk request rate, node saturation | That object slows; unrelated objects unaffected | Add copies for its chunks; front it with a cache or CDN |
| Noisy-neighbour tenant | One shard's or node's throughput | Per-tenant request and byte rate | That tenant is throttled at the gateway | Enforce the token bucket; move it to a separate cell if repeated |

- Observe
  - Under-replicated count, split "one copy left" versus "below target".
  - Repair queue depth and time-at-reduced-redundancy — the direct input to the durability claim.
  - Scrub coverage, orphan bytes, collector lag.
  - Commit latency and failure rate, separate from byte-transfer latency.
- Retry discipline
  - Chunk writes retry freely with backoff and jitter; content addressing makes them idempotent.
  - Commits retry with the same upload id and tag; a mismatch is a `409`, not a retry.
  - Reads retry a *different* placement and file a repair on checksum failure.
  - Repair tasks are rate limited; a persistently failing source node is quarantined, not retried in a loop.
- Tenant isolation and security
  - Every metadata key is tenant scoped, so a cross-tenant read is impossible at the query level, not merely filtered.
  - Cross-tenant deduplication is off by default; enabling it leaks the existence of identical content.
  - Another tenant's bucket returns `404`, not `403`; quotas cover stored bytes, request rate, and egress.
  - Per-object data key wrapped by a tenant key in the vault (`s5.01`); encryption sits below chunking, so a chunk id addresses ciphertext.
  - Defeater: encrypting before hashing destroys cross-object deduplication — the correct trade, stated openly.
  - Pre-signed URLs are scoped to one bucket, key, method, expiry; delete and policy changes are audited.
- Rollout and rollback safety
  - Chunk format and manifest schema are versioned; write a new version only after every reader parses it.
  - Roll placement-policy changes to one cell, watch under-replicated count and repair bandwidth, then continue.
  - Never change `chunk_size_b` on an existing version; it is per version so the read path survives a policy change.

## 13. Alternatives and IC4 stretch

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| 3× replication | Three full copies in three fault domains | Cheapest repair (`1×` read), trivial reads, best tail latency | `3.0×` storage cost | Hot data, small objects, latency-sensitive reads |
| Erasure coding 8+4 | 8 data plus 4 parity fragments across 12 domains | `1.5×` storage, tolerates 4 losses | ~8× repair amplification, decode CPU on degraded reads, bad small-object economics | Cold or large data where capacity dominates cost |
| Hybrid by size and temperature | Replicate while small or hot; transcode large cold data to coding | Most of the saving without the latency cost | Two code paths, a transcode pipeline, a policy to reason about | The default production answer at real scale |
| Hash-ring allocator | Placement computed from a hash and a cluster map (CRUSH-style) | No per-chunk location rows; placement is a computation | Cannot express drain, heterogeneous capacity, or tenant constraints; map changes move data | Homogeneous fleet where metadata volume binds |
| Explicit allocator | Store every placement, pick targets from live node state | Handles mixed hardware, drain, constraints; placement is auditable | A row per copy, so metadata grows with raw capacity | Mixed hardware, strict domain rules, operational drain |
| Blobs in the KV store | Object bytes as values in the metadata database | One system, one transaction, no manifest problem | Value-size caps; compaction and backup wrecked by large values; no direct byte path | Objects are consistently tiny and the corpus small |

- Recommendation: the deciding variable is **object size × access temperature**, not cluster size.
  - Replicate while small or hot, code when large and cold, and keep the allocator explicit because real fleets are heterogeneous and must be drainable.
- **IC4 stretch — stronger requirement**
  - Survive the loss of a whole region with a stated recovery point.
  - Structurally different: a per-bucket async replication log, a lag metric that *is* the recovery point, and a failover that promotes the remote namespace.
  - Say aloud that read-after-write stays regional and the remote copy is eventually consistent.
  - Reject synchronous cross-region commit unless the target is genuinely zero recovery point — it puts a cross-region round trip in every commit.
- **IC4 stretch — 10× load**
  - At `10^12` objects the metadata tier, not the disks, is the design problem: chunk rows outnumber object rows by an order of magnitude.
  - Adopt a **cell architecture**: each cell owns its metadata shards, chunk fleet, repair service, and collector, with a thin bucket→cell router.
  - Raise chunk size for very large objects (256 MB above 1 TB) so manifest rows grow sublinearly; `chunk_size_b` per version makes that a policy change, not a migration.
  - Move the coldest tier from stored placements toward a computed cluster map, trading flexibility for metadata volume where flexibility matters least.
- **IC4 stretch — cost and blast radius**
  - Cost: on a 5 PB logical corpus the hybrid is roughly `9 PB` raw versus `15 PB` replicated — the number to bring to a cost conversation.
  - Blast radius: a cell bounds a repair storm, a wedged collector, or a bad placement rollout to its own tenants.
  - Placement constraints can pin a critical tenant to dedicated cells, converting shared fate into a capacity cost.
- **IC4 stretch — migration and rollout**
  - Replication → coding is a background transcode: write 12 fragments, verify, swap redundancy and placements in one transaction, reclaim old copies after the grace period.
  - The object is never unreadable during the swap: old copies survive until the new placements are `PRESENT`.
  - Roll out per bucket, coldest first, rate limited per cell, halting when repair depth or foreground latency crosses a threshold.
  - Rollback is a reverse transcode — which is why old copies are retained rather than deleted at swap time.
- Weakest assumption
  - That the declared fault domains are actually independent — no shared power feed, switch, firmware version, or deployment pipeline.
  - Every durability number here collapses if that is wrong, and it is the assumption least likely to be verified.
- Over-engineering warning
  - Do not build coding, cross-region replication, and cell routing on day one.
  - The baseline that earns its keep is content-addressed chunks, manifest commit, fault-domain placement, repair, scrub, and a collector.
  - Coding pays only once the cold corpus is large; adding it early buys repair amplification and a second code path for savings on a corpus that does not yet exist.

## 14. Interview pushback and validation

- **Q1: Why not store blobs in the metadata database and drop the data plane?**
  - `IC3 baseline`
    - Value-size caps exist because large values destroy compaction, cache locality, and backup windows.
    - Claim-check instead: the blob lives in the object store, the database holds a reference.
  - `IC4 stretch`
    - Below a few hundred kilobytes with a corpus that fits one database tier, inlining is simpler and avoids a second failure domain.
    - Above that, every database operation — backup, restore, replication, rebalance — scales with blob bytes rather than metadata bytes.
- **Q2 (premise reversal): The workload is billions of 10 KB thumbnails, not 1 TB objects. Now defend chunking.**
  - `IC3 baseline`
    - I would not chunk: one object is one chunk, the manifest is one row, multipart is unused.
    - I would not code: 12 fragments of 10 KB cost more in rows and IOPS than the bytes saved.
    - The manifest commit survives, collapsed to "insert one committed row after one durable write".
  - `IC4 stretch`
    - The binding constraint becomes metadata row count and small-file IOPS, so the design changes shape: pack objects into large append-only containers, store `(container_id, offset, length)`, and code the *container*.
    - That is the Haystack and `f4` move; the cost is that deletion becomes container compaction instead of a per-object unlink.
- **Q3: Where does 11 nines come from?**
  - `IC3 baseline`
    - It is a target, not a measurement, and describes independent device failure only.
    - It falls out of copy count and repair speed: enough copies that losing the remainder inside the repair window is negligible.
  - `IC4 stretch`
    - The number is dominated by what it excludes — correlated failure, operator error, and bugs that delete correctly everywhere.
    - Those need different mechanisms: domain and drive-model diversity, versioning with delayed reclaim, staged rollout — none of which appear in the arithmetic.
- **Q4: Why is a crash mid-upload not a partial object, and what if two clients PUT one key at once?**
  - `IC3 baseline`
    - Chunk writes mutate no namespace state; the object exists only when the commit writes the `COMMITTED` row, so a crash leaves orphans the collector reclaims.
    - Concurrent PUTs both commit as distinct versions; the latest pointer resolves to whichever committed last and a reader always sees one complete version.
  - `IC4 stretch`
    - Atomicity depends on the manifest living on one shard, so the shard key is `(tenant, bucket, key)`; otherwise I would need two-phase commit or a designated commit shard, and would name the cost.
    - For read-modify-write clients, add a conditional commit on the current entity tag — an explicit `412` instead of silent last-writer-wins.
- **Q5 (premise reversal): Coding is strictly better — half the cost, tolerates four failures. Why keep replication?**
  - `IC3 baseline`
    - Repair cost: rebuilding one fragment reads eight, so the network moves ~8× the lost bytes; replication reads one.
    - Latency: a degraded read gathers eight fragments and decodes, landing in the tail.
    - Small objects multiply placement rows and allocations for very little payload.
  - `IC4 stretch`
    - The real limit is fleet-level: once most of the corpus is coded, repair bandwidth rather than disk capacity binds, and a correlated failure produces a storm the network cannot absorb.
    - So the policy is a bandwidth budget as much as a cost decision, and the hot fraction stays replicated to keep the storm survivable.
- **Q6: Why do clients read chunk servers directly instead of proxying through your service?**
  - `IC3 baseline`
    - Proxying makes the metadata tier scale with total bandwidth instead of request rate.
    - Direct reads keep it small, cacheable, and strongly consistent.
  - `IC4 stretch`
    - The cost is that authorization moves into short-lived grants scoped to one chunk, method, and expiry, enforced by the chunk servers.
    - I would proxy in exactly one case: a compliance requirement that every byte cross an inspection boundary the client cannot be trusted to apply.
- **Q7: What if the collector has a bug and deletes a referenced chunk?**
  - `IC3 baseline`
    - The chunk is content addressed and rebuildable from any surviving placement, so one mistaken unlink is a repair, not a loss.
    - The guard is re-checking the reference inside the transaction that marks the chunk for reclaim.
  - `IC4 stretch`
    - The unrecoverable case is deleting every placement, which no replication factor protects against because the deletion is applied correctly everywhere.
    - Mitigations are structural: a grace period long enough for detection, soft-delete markers before unlink, a canary cell for collector changes, and a deletion-rate alarm that halts the collector.

- Validation scenarios
  - Kill the client after every chunk uploads but before commit; verify nothing is listable and the chunks are reclaimed after the grace period.
  - Retry a commit with an identical part list; verify one version, not two.
  - Corrupt one byte on one copy on disk; verify failover, correct bytes, and a filed repair.
  - Power off a whole fault domain; verify every object stays readable and under-replicated count drains inside the window.
  - Issue a range GET across a chunk boundary; verify exactly two chunks are read.
  - Delete a 5 TB object; verify an immediate response and paced asynchronous reclaim.
  - Transcode a bucket from replication to coding under live reads; verify no read error at the swap.
  - Stall the collector for a day; verify free-space alarms fire before placements start failing.

## 15. Recall card

- "Metadata is a strongly-consistent database problem; data is a placement-and-repair problem. Never let the two mix."
- "The upload is not the commit. Bytes become an object at exactly one transaction."
- "Content addressing is what makes a retry free: the same bytes have the same name."
- "Three copies is a claim about device failure, not about operators or bugs."
- "Erasure coding buys bytes and pays network; replication buys network and pays bytes."
- Wrap-up
  - The metadata plane owns a strongly consistent namespace; the data plane owns immutable content-addressed chunks that clients read directly.
  - A write uploads chunks in any order and becomes visible at one manifest commit, so a crash yields orphans rather than a half-object.
  - Placement spreads copies across fault domains, and a repair-and-scrub loop keeps redundancy an invariant.
  - My weakest assumption is that the declared fault domains are truly independent; correlated failure, not disk failure, is what the durability arithmetic omits.
