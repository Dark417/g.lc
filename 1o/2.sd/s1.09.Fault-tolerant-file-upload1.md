## Interview framing

The level, the evidence, why the problem is hard, and the sentences to open with.

---

> - Target: OCI IC3 ownership of a bounded platform component.
>   - `IC3 baseline` is what must land in every phase.
>   - `IC4 stretch` adds architecture changes under stronger constraints.
>   - These are preparation labels, not Oracle's official rubric.

**What this says in plain words**
You answer as an engineer who owns one clearly-bordered piece of infrastructure, including its failures and its pager. `IC3 baseline` is the floor; `IC4 stretch` is depth added when pushed. Both labels are a study device, not a company grading scale.

**Why it matters**

1. **Bounded controls scope.** Inside the box: the upload protocol, the session state, and the completion decision. Outside: how the object storage replicates bytes, how the client's network behaves, and what the file is eventually used for.
2. **The baseline is a checklist.** Skip the completion-versus-abort race and you dropped the item the deep dive is about.
3. **The labels are yours.** Saying "this is the IC4 answer" claims knowledge of their rubric you do not have.

---

> - Evidence: retain the first-hand report attribution in [the bank](2.sd.md#1infra).
>   - The architecture below is a proposed interview answer.
>   - It does not claim to reproduce Oracle's implementation or an interviewer's accepted answer.

**What this says in plain words**
Someone reported being asked this in a real Oracle interview. The design here is this preparation's own answer, not a leaked design.

**Why it matters**
High confidence the question gets asked, no claim that this protocol is what the interviewer wanted. That distinction matters unusually much here, because Oracle publishes a real multipart upload API, and this design is deliberately stricter than it.

---

> - Why this is hard
>   - Naive: one `PUT` with the whole file and a retry loop around it.

**What this says in plain words**
The obvious design: send the entire file in one request, and if it fails, send it again.

**Why it matters**
It is correct for most files, which is why it is the right naive design to name.

- Worked example of it being fine: a 2-megabyte image over a reliable connection. It takes a moment, it rarely fails, and a retry costs 2 megabytes. Building a session protocol for that would be absurd.

---

> -   - First break: a `10 GiB` transfer that fails at `99%` restarts from zero, and a retry after a lost response can duplicate or corrupt the object.

**What this says in plain words**
Two failures in one line.

1. **Failure at 99% restarts from zero.**
   - Worked example: a 10-gibibyte upload at 100 mebibytes per second takes about 102 seconds. It fails at 101 seconds, having transferred 10.1 gibibytes. All of it is wasted, and the next attempt starts at zero, with the same chance of failing near the end.
   - The cost is not merely the bytes. Worked example on a mobile connection at 5 megabits per second: the same upload takes 4.5 hours, and a failure at 99% costs 4.5 hours of someone's time and data allowance.
2. **A retry after a lost response can duplicate or corrupt.**
   - Worked example: the upload completes, the server stores the object, and the response is lost in the network. The client does not know it succeeded and retries. Without an identity for the operation, the server may now have two objects, or may overwrite a good object with a partial second attempt.

---

> -   - Second break: two devices resume the same upload, or an abort races a completion, and nobody owns the final answer.

**What this says in plain words**
Two concurrency failures, and these are the ones the design is actually about.

1. **Two devices resume the same upload.**
   - Worked example: a user starts an upload on a laptop, it stalls, and they resume on a tablet. The laptop then reconnects and continues too. Both are uploading parts for the same session, possibly different bytes for the same part number, with no rule about which wins.
2. **An abort races a completion.**
   - Worked example: a user presses cancel at the same moment the client sends the completion request. One path deletes the staged bytes, the other assembles them into an object. Depending on timing, the result is a published object with deleted bytes, or a cancellation that produced a file anyway.
   - "nobody owns the final answer" is the precise phrasing: the outcome is decided by network timing rather than by a rule.

---

> -   - Minimum primitives
> -     - Fixed parts with checksums
> -     - A persisted session
> -     - A frozen manifest
> -     - One conditional state transition that decides completion.

**What this says in plain words**
Four parts you cannot drop.

1. **Fixed parts with checksums.** A known size per part, and a verifiable digest of each part's bytes.
2. **A persisted session.** The upload's state stored durably, so it survives both client and server restarts.
3. **A frozen manifest.** The exact ordered list of parts, fixed at the moment completion begins and never changed afterwards.
4. **One conditional state transition that decides completion.**
   - Singular and conditional. Exactly one write decides the outcome, and it applies only if the state is what the caller expects.

**Why it matters**
Each answers one of the four failures above, and the fourth is what resolves both concurrency races with one mechanism.

---

> - 🗣 “Chunking makes retries cheap; the real design is the state machine that decides which bytes become the object.”

**What this says in plain words**
A quotable one-liner; the 🗣 marker means say it roughly verbatim. Two claims:

1. Chunking solves the cost problem, and it is the easy part.
2. The actual design is the state machine deciding which bytes become the final object.

**Why it matters**
It reframes the question within ten seconds, and the reframing is what separates this answer from the common one.

- Worked example of the common answer: split the file into chunks, upload them in parallel, track which succeeded, and reassemble. Every word is correct and it describes only the easy half.
- The hard half is deciding, when several devices and several attempts and an abort request are all in play, which specific set of bytes becomes the object. That is a state machine question, not a transfer question.

---

> - Opening script
>   - “I will treat this as a resumable multipart upload with an explicit completion state machine.”

**What this says in plain words**
The first sentence, announcing the shape and the emphasis: multipart and resumable, with the completion state machine called out explicitly.

---

> -   - “First I confirm the file size, the failure model, and whether another device may resume.”

**What this says in plain words**
Three questions before designing.

1. **File size** sets the part count and the metadata volume.
2. **Failure model** decides what idempotency is needed.
3. **Whether another device may resume** is the one that surprises people.
   - Worked example of why it changes the design: if resume is same-device only, a locally-stored session token is sufficient. If any authorized device may resume, the session must be resumable from server state alone, which means fresh authorization and a file-identity check rather than trust in a saved identifier.

---

> -   - “Then I size parts and concurrency from retry cost, and define an API where every step is idempotent.”

**What this says in plain words**
Part size and concurrency derive from what a retry costs, and every operation must be safe to repeat.

**Why it matters**
"from retry cost" is the deriving principle. Worked example: a larger part means fewer requests and a more expensive retry; a smaller part means cheaper retries and more per-request overhead and more metadata. The part size is the point where those balance, which the capacity section computes.

---

> -   - “The deep dive is part identity and the completion-versus-abort race across the database and storage.”

**What this says in plain words**
Two deep dives, and the second names where the difficulty lives: across two systems.

**Why it matters**
Worked example of why the boundary is the hard part: the database records that the session is completing, and the storage provider assembles the object. Those are two separate commits with no transaction between them, so a crash in the middle leaves a state neither system can resolve alone.

---

> -   - “I will close with failure recovery, cleanup, and where I would change the design under stronger requirements.”

**What this says in plain words**
Announces the ending: recovery, cleanup, and how stronger requirements would change things.

**Why it matters**
Cleanup is named as a first-class closing topic rather than an afterthought. Worked example of why: abandoned uploads leave staged bytes that nothing references, and at 10 gibibytes per session those accumulate into a real storage bill. Cleanup is a cost control, which the stretch section states outright.

## Requirements — IC3 baseline

The numbers warning, the clarifying table, functional scope, the numeric target table, invariants, and non-goals.

---

> - Numerical targets are interview assumptions unless an adjacent primary source states otherwise.

**What this says in plain words**
Every number here was chosen to make the design concrete. None came from Oracle unless a link says so.

**Why it matters**
Worked example: at 10 gibibytes maximum, the design needs 1,280 parts and real metadata planning. At 10 megabytes, a single request with a retry is correct and none of this applies.

---

> | Question | Assumed answer | Why it changes the design |
> |---|---|---|
> | Maximum object size? | `10 GiB` | Fixes part count and metadata volume |
> | Failure model? | Unreliable network, client restarts, lost responses | Forces idempotent parts and an authoritative state query |
> | Can another authorized device resume? | Yes, same tenant and user | Resume needs file identity plus fresh authorization, not just an upload ID |
> | Can a target object be overwritten? | Yes, with a version precondition | Publication needs compare-and-set on the logical key |
> | Integrity contract? | Per-part checksum plus optional whole-file digest | Decides what completion verifies and how long it takes |
> | Who serves the bytes? | Managed object storage; control API is separate | Keeps bytes off the API fleet; introduces provider reconciliation |

**What this says in plain words**
Six questions, the assumed answer, and what each decides.

- **Row: Maximum object size, 10 gibibytes.** Fixes both the part count and how much metadata exists per session.
- **Row: Failure model.**
  - Three failures named: unreliable network, client restarts, lost responses.
  - The third is the one that forces the design. Worked example: a lost response means the client cannot tell success from failure, so every operation must be safe to repeat *and* there must be a way to ask the server authoritatively what happened.
- **Row: Can another authorized device resume?**
  - Yes, and the consequence is stated sharply: "not just an upload ID".
  - Worked example of why an identifier is insufficient: a session identifier saved on one device is a bearer token for someone else's upload if it leaks, and it says nothing about whether the file on the new device is the same file. Resume needs fresh authorization and a check that the local file still matches.
- **Row: Can a target object be overwritten?**
  - Yes, with a version precondition, which means publication is a compare-and-set on the logical key rather than a blind write.
  - Worked example of why: two uploads finish for the same key seconds apart. Without a precondition, the second silently replaces the first, and whichever client checks later sees a version it did not create.
- **Row: Integrity contract?**
  - Per-part checksums always, whole-file digest optionally.
  - "how long it takes" is the cost: a whole-file digest over 10 gibibytes means reading 10 gibibytes and hashing them, which adds real time to completion.
- **Row: Who serves the bytes?**
  - Managed object storage, with the control API separate.
  - Two consequences, and both are load-bearing. Bytes never touch the API fleet, so a 10-gibibyte upload does not consume API bandwidth. And the design now spans two systems whose views must be reconciled, which is the deep dive.

---

> - Functional scope
>   - Split a file into independently retriable parts.
>   - Persist an upload session that survives client and server restarts.
>   - Upload directly to storage through scoped authorization where supported.
>   - Publish the completed object only after required validation.
>   - Support cancellation and orphan cleanup.

**What this says in plain words**
Five capabilities.

1. **Independently retriable parts.** Each part's failure is isolated from the others.
2. **A session surviving both client and server restarts.**
   - Both, and they are different. Worked example: a client restart means the browser or application reopened, and it needs to find its session again. A server restart means the API instance that created the session is gone, and any other instance must serve the session identically, which requires the state to be in a shared store rather than in memory.
3. **Upload directly to storage through scoped authorization.**
   - Scoped meaning the grant permits writing exactly these parts of exactly this session, and nothing else.
4. **Publish only after required validation.** The object does not exist to readers until it has been checked.
5. **Support cancellation and orphan cleanup.** Deliberate abort, and the automatic removal of abandoned sessions.

---

> | Requirement | Target | Enforced by |
> |---|---|---|
> | Maximum file size | `10 GiB` | Session creation rejects larger declared sizes |
> | Default part size | `8 MiB`, server-chosen | Session response fixes part size for the session |
> | Client concurrency | 4 parts in flight | Client semaphore; server per-session in-flight cap |
> | Control API latency | p99 < `200 ms`, excluding byte transfer | Metadata-only writes; no byte proxying |
> | Control-plane availability | `99.95%` | Stateless API fleet; replicated metadata store |
> | Session expiry | `24 h` of inactivity | Expiry reconciler transitions to `ABORTED` |
> | Staging reclaim | Within `24 h` after expiry | Idempotent cleanup worker with retry |
> | Data-plane resilience | Existing grants permit up to 15 min of part uploads during API unavailability | Scoped expiring storage grants; new grants and final publication still need the API |

**What this says in plain words**
Eight promises, each with a number and a mechanism.

- **Row: Maximum file size, rejected at session creation.**
  - Rejected on the *declared* size, before any bytes move. Worked example: a client declaring 40 gibibytes is refused immediately rather than after transferring 10.
- **Row: Default part size, 8 mebibytes, server-chosen.**
  - "server-chosen" is a deliberate decision. Worked example of letting the client choose: clients pick badly, some choosing 64 kilobytes and creating 163,840 parts, others choosing 1 gibibyte and losing the retry benefit. The server fixing it per session makes the metadata volume predictable.
- **Row: Client concurrency, 4 parts in flight, enforced on both sides.**
  - "Client semaphore; server per-session in-flight cap". Worked example of why both: the client's own limit is politeness and can be removed by a modified client. The server's cap is enforcement, and it protects the service from a client that opens 500 concurrent part uploads.
- **Row: Control API latency, p99 under 200 milliseconds, excluding byte transfer.**
  - The exclusion is the point: the API handles metadata only. Worked example of the alternative: an API that proxies bytes has a latency dominated by transfer time, and a 102-second upload is a 102-second request.
- **Row: Session expiry, 24 hours of inactivity, transitioning to `ABORTED`.**
  - The reconciler moves the session to a terminal state, which is what makes the bytes eligible for cleanup.
- **Row: Staging reclaim within 24 hours after expiry, by an idempotent worker with retry.**
  - Idempotent so a partially-completed cleanup can simply be run again.
- **Row: Data-plane resilience, 15 minutes of part uploads during API unavailability.**
  - The most carefully worded row. Worked example: the API fleet is down. A client holding a grant issued 3 minutes ago keeps uploading parts directly to storage for the remaining life of that grant. What it cannot do is get a new grant or complete the upload.
  - So an API outage costs new sessions and completions, and in-flight byte transfer continues. That is a direct consequence of bytes not going through the API.

---

> - Invariants
>   - Tenant and user authorization applies to create, resume, parts, completion, and abort.
>   - A sealed part's number, bytes, and checksum form an immutable identity in this proposed service.
>   - A published object references one complete verified manifest.
>   - Completion and abort cannot both win for the same session generation.
>   - An ETag is an object or part identifier from the provider, not a universal whole-file SHA-256.

**What this says in plain words**
Five statements true at every instant.

1. **Authorization applies to all five operations, named individually.**
   - The enumeration is deliberate. Worked example of the gap it closes: a design that authorizes session creation and then treats the session identifier as sufficient for everything after. Abort in particular is easy to leave unprotected, and it destroys data.
2. **A sealed part's number, bytes, and checksum are one immutable identity.**
   - "in this proposed service" flags that this is stricter than what providers require, which the provider-boundaries section returns to.
   - Worked example of what immutability buys: part 42 with checksum `abc…` always means the same bytes. Re-uploading identical bytes for part 42 is recognized as the same part. Uploading *different* bytes for part 42 is a conflict rather than a replacement.
3. **A published object references one complete verified manifest.** Not a set of parts that happened to be present, but one specific list that was checked.
4. **Completion and abort cannot both win for the same session generation.**
   - "for the same session generation" is the precise scope. The generation is what makes the statement checkable.
5. **An ETag is a provider identifier, not a whole-file hash.**
   - The most commonly misunderstood fact in this topic, stated as an invariant so it cannot be quietly assumed.
   - Worked example: a multipart object's ETag is often a digest of the part digests, with a part count appended. It identifies the object for cache-validation purposes and it is not the SHA-256 of the file's bytes. A client computing the file's SHA-256 and comparing it to the ETag will find they never match, and will conclude the upload corrupted the data.

---

> - Non-goals
>   - Continuous append to an existing object.
>   - Cross-tenant deduplication.
>   - Inline content scanning on the upload path.

**What this says in plain words**
Three exclusions.

1. **Continuous append.** Objects are immutable once published; you cannot add to one.
2. **Cross-tenant deduplication.**
   - Worked example of why it is excluded rather than merely unbuilt: if the service recognized that two tenants uploaded identical content and stored it once, a tenant could learn whether another tenant possesses a particular file by uploading it and observing the speed. That is an information leak created by an optimization.
3. **Inline content scanning.** Scanning during upload would put a scanner on the byte path, which conflicts with bytes not passing through the API at all.

## Capacity and consequence — IC3 baseline

Four estimates. Each ends in the decision it forces.

---

> - Parts
>   - `10 GiB / 8 MiB = 1,280 parts`.
>   - At an illustrative independent `1%` failure probability per attempt, expected retries are about `1,280 × 0.01 / 0.99 ≈ 12.9`.
>   - Retransmission is about `103 MiB`, rather than restarting the whole `10 GiB` object.
>   - Correlated network failure can make retry behavior much worse.
>   - Decision: part size is the retry unit
>     - `8 MiB` bounds wasted retransmission below `1%` of the object while keeping part count in the low thousands.

**What this says in plain words**
The arithmetic that chooses the part size.

1. **1,280 parts.** 10 gibibytes divided by 8 mebibytes.
2. **About 12.9 expected retries** at a 1% per-attempt failure rate.
   - The formula divides by 0.99 because a retry can itself fail. Worked example of the intuition: of 1,280 attempts, about 12.8 fail; of those 12.8 retries, about 0.13 fail again, and so on. The sum converges to roughly 12.9.
3. **About 103 mebibytes retransmitted.** 12.9 × 8 mebibytes.
   - Worked example of the comparison: 103 mebibytes wasted against a 10-gibibyte object is about 1%. The naive design's failure at 99% wastes 10 gibibytes, which is 10,000% of one part. Chunking changed the cost of a failure by four orders of magnitude.
4. **Correlated failure makes it much worse.**
   - Worked example: a tunnel drops for 30 seconds. All four in-flight parts fail together, and every retry during those 30 seconds also fails. The independence assumption is broken, and this is later named the weakest assumption.

**Why it matters — the decision**
"part size is the retry unit" names what is actually being chosen.

- The tension: 8 mebibytes bounds waste below 1% of the object and keeps the part count in the low thousands.
- Worked example of going smaller: 1-mebibyte parts mean 10,240 parts, so the metadata is eight times larger and there are eight times as many requests, each with its own overhead. Waste per failure drops to 1 mebibyte, which was already negligible.
- Worked example of going larger: 64-mebibyte parts mean 160 parts and very little metadata, and each failure wastes 64 mebibytes. On a poor connection a 64-mebibyte part may rarely complete at all, so the retry rate rises and the waste compounds.

---

> - Client memory
>   - Four buffered parts require approximately `32 MiB` before protocol buffers.
>   - Streaming each part can reduce buffering further.
>   - Decision: bound concurrency with a semaphore
>     - Never enqueue all parts with their bytes attached.

**What this says in plain words**

1. **32 mebibytes for four buffered parts.** 4 × 8 mebibytes, before whatever the HTTP and TLS layers hold.
2. **Streaming reduces it further.** A part can be read from disk as it is sent rather than held whole in memory.
3. **Bound concurrency with a semaphore, and never enqueue all parts with bytes attached.**

**Why it matters — the decision**
The prohibition is the useful half, and it describes a real and easy mistake.

- Worked example of the mistake: build a work queue containing 1,280 tasks, each holding its 8 mebibytes of data, then hand the queue to a thread pool with four workers. The concurrency is correctly limited to four, and the queue is holding 10 gibibytes in memory. The program uses the entire file's worth of memory to upload it in small pieces.
- The fix is that a task holds a *reference* to its byte range, and the bytes are read when the task runs. Then memory scales with concurrency, at 32 mebibytes, rather than with file size.

---

> - Throughput
>   - At an assumed `100 MiB/s` aggregate goodput, byte transfer takes `102.4 s`.
>   - Four parallel requests cannot exceed the client's link, storage, or CPU limits.
>   - Hashing and verification time is additional unless pipelined.
>   - Decision: hash each part while the next is in flight
>     - Whole-file verification runs in the finalizer, not on the client's critical path.

**What this says in plain words**

1. **102.4 seconds at 100 mebibytes per second.** 10 gibibytes is 10,240 mebibytes.
   - *Goodput* rather than throughput: the useful data rate after protocol overhead and retransmission, which is what actually determines elapsed time.
2. **Parallelism cannot exceed the underlying limits.**
   - Worked example: four parallel uploads over a link that sustains 100 mebibytes per second still total 100 mebibytes per second, at 25 each. Parallelism helps by keeping the link busy during per-request latency, not by creating bandwidth.
3. **Hashing costs time unless pipelined.**
   - Worked example without pipelining: hash part 1, upload part 1, hash part 2, upload part 2. If hashing 8 mebibytes takes 40 milliseconds, that is 1,280 × 40 milliseconds ≈ 51 seconds added to a 102-second transfer, a 50% increase from a step that could have overlapped.

**Why it matters — the decision**
Two placements, each moving work off a critical path.

- **Hash each part while the next is in flight.** The hashing overlaps the transfer and costs nothing in elapsed time.
- **Whole-file verification runs in the finalizer.**
  - Worked example: verifying a 10-gibibyte digest means reading 10 gibibytes and hashing them. Doing it on the client would require re-reading the entire file after upload. Doing it in the finalizer means the server reads the assembled bytes, and the client's involvement ended when its last part was acknowledged.

---

> - Metadata
>   - `100,000` active maximal sessions imply up to `128 million` part records.
>   - At roughly `200 B` per part row this is on the order of `25 GB` of hot metadata.
>   - Decision: shard part rows by `upload_id`
>     - Enforce per-tenant active-session and staging-byte quotas.
>   - Decision: expiration is part of capacity planning, not just housekeeping.

**What this says in plain words**

1. **128 million part records.** 100,000 sessions × 1,280 parts.
2. **About 25 gigabytes of hot metadata.** 128 million × 200 bytes.
   - "hot" meaning actively read and written, not archived. Worked example of the access pattern: every part upload writes a row, and every resume reads all of a session's rows.

**Why it matters — the two decisions**

- **Shard part rows by upload identifier, and enforce per-tenant quotas.**
  - Sharding by upload identifier keeps one session's parts together, which is what resume reads.
  - Worked example of the quota's purpose: without it, one tenant opens 100,000 sessions and consumes the entire metadata budget and the entire staging capacity, and every other tenant's uploads fail.
- **"expiration is part of capacity planning, not just housekeeping."**
  - The sentence worth remembering. Worked example: 100,000 abandoned sessions holding 10 gibibytes each is 1 petabyte of staged bytes nobody will ever complete, plus 25 gigabytes of metadata describing them. Expiry is not tidiness; it is the only thing that bounds the system's storage.
  - The consequence: the 24-hour expiry and the 24-hour reclaim window are capacity decisions, and lengthening either one directly increases the storage bill.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Retry unit | The amount of work lost when one attempt fails. | What part size actually chooses. |
| Independent failure | Each attempt failing without influencing the others. | The assumption behind the 12.9 figure, and the weakest assumption. |
| Correlated failure | Failures sharing a cause, so they happen together. | Breaks the retry arithmetic badly. |
| Retransmission waste | Bytes re-sent because an attempt failed. | About 1% of the object at 8-mebibyte parts. |
| Per-request overhead | The fixed cost of each request, independent of size. | Why very small parts are wasteful. |
| Semaphore | A counter limiting how many operations run concurrently. | Bounds client memory to concurrency, not file size. |
| Byte-range reference | A task holding where to read bytes rather than the bytes themselves. | Prevents a queue holding the whole file. |
| Goodput | The useful data rate after protocol overhead and retransmission. | What determines elapsed time, unlike raw throughput. |
| Pipelining | Overlapping one step with the next so their times do not add. | Hashing a part while the next uploads. |
| Critical path | The sequence of steps whose total time determines completion. | Hashing and verification are kept off it. |
| Finalizer | The server-side component that verifies and publishes the object. | Where whole-file verification runs. |
| Hot metadata | Data actively read and written, as opposed to archived. | 25 gigabytes of it at full occupancy. |
| Sharding by upload identifier | Keeping one session's part rows together on one shard. | Matches what a resume reads. |
| Staging-byte quota | A per-tenant cap on uploaded-but-unpublished bytes. | Stops one tenant consuming all staging capacity. |
| Expiration as capacity planning | Treating session expiry as the mechanism that bounds storage. | Abandoned sessions would otherwise accumulate without limit. |

## Architecture and flow — IC3 baseline

Diagram first, then each component with the mechanism it buys and the price it charges, then one upload traced end to end.

---

> ```text
> Client -> upload control API -> session / manifest DB
>   |                                |
>   +-> scoped part upload -> private staging object storage
>                                    |
> Complete request -> freeze manifest -> verifier / finalizer
>                                    |
>                          immutable final object/version
>                                    |
>                            publication metadata
>
> Expiry reconciler -> abort state -> retryable staging cleanup
> ```

**What this says in plain words**
Two paths from the client, one finalization chain, and one cleanup loop.

**Reading the two client paths**

1. **Client → upload control API → session / manifest DB.** Metadata only: create the session, record parts, request completion.
2. **Client → scoped part upload → private staging object storage.** The bytes, going directly to storage without passing through the API.

**The most important feature of the diagram is that these two paths are separate.**

- Worked example of what that buys: a 10-gibibyte upload consumes zero API bandwidth. The API handles about 1,282 small metadata requests for that session, and 10 gibibytes move between the client and storage on a path the API never touches.
- Worked example of what it costs: two systems now hold views of the same upload. The database says part 42 is recorded; the storage says an object exists at a staging key. Keeping those consistent is the reconciliation problem that dominates the deep dives.

**Reading the finalization chain**
Complete request → freeze manifest → verifier / finalizer → immutable final object → publication metadata. Four steps, each producing something the next depends on.

**Reading the cleanup loop**
Expiry reconciler → abort state → retryable staging cleanup. Note the ordering: the state changes first, and the bytes are deleted afterwards, which the abort section returns to.

---

> - Control plane owns session metadata and authorization.
>   - It does not proxy file bytes by default.
>   - It issues bounded access for the required session and part scope.
>   - Long-lived storage credentials never go to the client.
>   - Cost: the client now talks to two systems, so the design must reconcile their views.

**What this says in plain words**
Four properties and one cost.

1. **Owns session metadata and authorization.** The authority on what a session is and who may touch it.
2. **Does not proxy bytes by default.** "by default" allows the proxy option, which the alternatives table covers for cases requiring inline inspection.
3. **Issues bounded access for the required session and part scope.**
   - Worked example of the scoping: a grant permits writing staging keys under this session's prefix, for the next 15 minutes, and nothing else. It cannot read other sessions, cannot write elsewhere, and expires.
4. **Long-lived storage credentials never go to the client.**
   - Worked example of the failure this prevents: giving a client a credential with broad storage access so it can upload. That credential now exists on a machine you do not control, and it can read and write anything the credential permits, for as long as it is valid.
5. **The cost: two systems, one reconciliation problem.** Stated plainly rather than buried.

---

> - Storage owns durable byte transfer.
>   - A storage part acknowledgment and a session metadata update may be separate operations.
>   - Reconcile them using stored checksums and provider list or status operations.
>   - Cost: provider semantics for part replacement and completion constrain the service contract.

**What this says in plain words**
Three points and one cost, and the first is the crux.

1. **The storage acknowledgment and the metadata update are separate operations.**
   - Worked example of the gap: the client uploads part 42 directly to storage and storage confirms it. The client then calls the API to record part 42, and that call fails. Storage holds the bytes; the database does not know they exist. Nothing is atomic across the two.
2. **Reconcile using stored checksums and provider listing.**
   - Worked example: on resume, the service lists what storage actually holds and compares against its own records, using checksums to confirm the bytes match what was expected. The two views are made consistent by inspection rather than by a transaction.
3. **The cost: provider semantics constrain the service contract.**
   - Worked example: this design treats a part as immutable once sealed. A provider may permit re-uploading a part number and simply keep the last one. So the service's stricter rule has to be enforced by the service, and it must account for what the provider will actually do underneath. The provider-boundaries section works this through in detail.

---

> - Finalizer owns completion.
>   - It freezes the selected manifest.
>   - It verifies bytes or relies only on an explicitly documented provider checksum contract.
>   - It publishes the object through a recoverable state transition.
>   - Cost: completion is asynchronous, so the API must expose an authoritative state query.

**What this says in plain words**
Three responsibilities and one cost.

1. **Freezes the selected manifest.** Fixing exactly which parts constitute the object.
2. **Verifies bytes, or relies on an *explicitly documented* provider contract.**
   - The qualifier matters. Worked example of the unsafe version: assuming the provider verified integrity because the upload succeeded. Unless the provider documents what it checked, a successful upload means the bytes were accepted, not that they match what was sent.
3. **Publishes through a recoverable state transition.** Recoverable meaning a crash mid-publication can be resolved rather than leaving an unknown state.
4. **The cost: completion is asynchronous, so the API needs an authoritative state query.**
   - Worked example: the client requests completion and receives `202`. The connection drops. The client has no idea whether the object was published. Without a state query it must guess, and both guesses are wrong sometimes. The query is what makes an ambiguous outcome resolvable.

---

> → Authenticate and create or reuse a session using a tenant-scoped idempotency key.  
> → Bind the session to destination, size, and declared file fingerprint.  
> → Upload missing parts with bounded concurrency and stable identities.  
> → Persist each verified part's size, checksum, and storage identifier.  
> → Freeze a manifest and transition from `UPLOADING` to `COMPLETING`.  
> → Verify total size, ordered parts, and required whole-file integrity.  
> → Commit the final object and persist its immutable version.  
> → Publish `COMMITTED` and return the same result on completion retries.

**What this says in plain words**
One upload traced end to end. Walked concretely:

A user uploads a 10-gibibyte archive to key `backups/2026-09.tar` for tenant `acme`.

1. **Authenticate and create or reuse a session with an idempotency key.**
   - "create or reuse" in one step: the same key returns the same session, so a retried creation does not start a second upload.
2. **Bind the session to destination, size, and declared fingerprint.**
   - Session `up-8891` is bound to the key, 10,737,418,240 bytes, and the file's declared digest. Part size is fixed at 8 mebibytes, giving 1,280 parts.
   - The fingerprint is what a later resume checks the local file against.
3. **Upload missing parts with bounded concurrency and stable identities.**
   - "missing" rather than "all", because the same step serves a fresh upload and a resume. Four at a time, each identified by its part number and checksum.
4. **Persist each verified part's size, checksum, and storage identifier.**
   - After storage acknowledges part 42, the API records its size, its checksum, and where it landed. This is the second of the two operations, and the gap before it is the reconciliation problem.
5. **Freeze a manifest and transition to `COMPLETING`.**
   - At 14:05 the client requests completion with the ordered list of 1,280 part identities. The service records that exact list as the frozen manifest and moves the session out of `UPLOADING`.
   - From this instant, no part upload can change the object.
6. **Verify total size, ordered parts, and whole-file integrity.**
   - Sizes sum to the declared 10 gibibytes, parts 1 through 1,280 are all present, and the whole-file digest matches if required.
7. **Commit the final object and persist its immutable version.**
   - Storage assembles the object. The service records version `v-4471` with its location, size, and digest.
8. **Publish `COMMITTED`, and return the same result on retries.**
   - The session reaches its terminal state. A retried completion returns version `v-4471` rather than attempting anything.

**Why it matters**
Steps 5 through 8 are one logical operation split across two systems, and the deep dives are entirely about making that split survivable.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Control plane | The path managing session metadata, authorization, and completion. | Never carries file bytes. |
| Data plane | The path carrying file bytes, directly from client to storage. | Keeps 10 gibibytes off the API fleet. |
| Scoped grant | A credential permitting exactly this session's part uploads, for a limited time. | Replaces giving the client a storage credential. |
| Staging storage | Private storage holding uploaded parts before the object is assembled. | Not visible to readers, and reclaimed if abandoned. |
| Reconciliation | Making two systems' views of the same upload agree, by inspection rather than transaction. | Required because storage and the database commit separately. |
| Provider listing | Asking storage what it actually holds for a session. | The input to reconciliation. |
| Provider semantics | The behavior the storage service actually guarantees, as opposed to what the service promises. | Constrains what the service contract can claim. |
| Frozen manifest | The ordered part list, fixed when completion begins. | After it, no upload can change the object. |
| Finalizer | The component that verifies and publishes the assembled object. | Owns completion. |
| Recoverable state transition | A transition a crash cannot leave in an unresolvable state. | Makes an interrupted publication reconcilable. |
| Authoritative state query | An interface returning the true current state of a session. | The answer when a completion response is lost. |
| Idempotency key | A caller-supplied string making a repeated request safe. | Makes creation return the same session rather than a second one. |
| File fingerprint | A declared identity for the file's content, recorded at session creation. | What a later resume checks the local file against. |
| Immutable version | A published object version that never changes after publication. | What the session records as its result. |
| Expiry reconciler | A background process moving inactive sessions to a terminal state. | Runs before any byte deletion. |

## API and data model — IC3 baseline

The interface table, the identity table, the reference SQL, what it omits, and the service conventions.

---

> | Surface | Contract | Conflict/error behavior |
> |---|---|---|
> | `POST /v1/uploads` | Destination, size, fingerprint; returns session and chosen part size | Same idempotency key plus different payload returns `409` |
> | `PUT /v1/uploads/{id}/parts/{n}` | Bounded bytes and declared checksum | Same sealed identity returns prior result; different bytes conflict |
> | `GET /v1/uploads/{id}/parts` | Cursor page of verified parts | Resume uses all pages, not just the first |
> | `POST /v1/uploads/{id}:complete` | Ordered part manifest and completion key | `202` while verifying; same manifest returns same result |
> | `GET /v1/uploads/{id}` | State and immutable final object version | Authoritative answer after ambiguous completion timeout |
> | `DELETE /v1/uploads/{id}` | Abort an incomplete session | `409` if completion already won; idempotent if already aborted |

**What this says in plain words**
Six operations covering the whole lifecycle.

- **Row: `POST /v1/uploads`.**
  - Takes the destination, size, and fingerprint; returns the session and the server-chosen part size.
  - `409` for a reused key with a different payload, so a client cannot accidentally get a session bound to the wrong file.
- **Row: `PUT /v1/uploads/{id}/parts/{n}`.**
  - "Same sealed identity returns prior result; different bytes conflict" is the immutable-part rule as an interface behavior.
  - Worked example of both branches: re-uploading part 42 with checksum `abc…` when that is already recorded returns the existing result, which makes retries free. Uploading part 42 with checksum `def…` is a conflict, because part 42 already means specific bytes.
- **Row: `GET /v1/uploads/{id}/parts`.**
  - "Resume uses all pages, not just the first" reads as an obvious note and describes a real bug.
  - Worked example: 1,280 parts at 100 per page is 13 pages. A resume implementation reading only the first page sees 100 parts, concludes 1,180 are missing, and re-uploads 9.2 gibibytes that were already there.
- **Row: `POST /v1/uploads/{id}:complete`.**
  - Takes the ordered manifest and a completion key, returns `202` while verifying.
  - "same manifest returns same result" makes completion retryable. Worked example: the response is lost, the client retries with the identical manifest, and the service returns the same outcome rather than starting a second finalization.
- **Row: `GET /v1/uploads/{id}`.**
  - Its stated purpose is the ambiguous-completion case, which is what the asynchronous completion costs.
- **Row: `DELETE /v1/uploads/{id}`.**
  - Two behaviors that are deliberately different. `409` if completion already won, because the object exists and pretending otherwise would be a lie. Idempotent if already aborted, because a second cancel of a cancelled thing is not an error.

---

> | State | Key | Fields/invariant |
> |---|---|---|
> | Session | `(tenant_id, upload_id)` | Destination, expected size/hash, state, generation, expiry, version |
> | Create dedup | `(tenant_id, idempotency_key)` | Request hash and upload ID; bounded retention at least the retry horizon |
> | Part | `(upload_id, generation, part_number)` | Size, SHA-256 or negotiated checksum, provider ETag, verified state |
> | Frozen manifest | `(upload_id, manifest_hash)` | Exact ordered part identities; immutable once completing |
> | Final publication | `(tenant_id, object_key, object_version)` | Verified location, size, digest, source upload ID |

**What this says in plain words**
Five kinds of state, and the generation appearing in the part key is worth pausing on.

- **Row: Session.** Carries both a generation and a version, which do different jobs: the generation identifies an incarnation, the version detects concurrent edits.
- **Row: Part, keyed by upload, generation, and part number.**
  - Worked example of why the generation is in the key: if a session were ever restarted as a new generation, part 42 of generation 1 and part 42 of generation 2 are different things, and keeping both is what lets the old generation's parts be identified and cleaned up rather than confused with the new ones.
- **Row: Frozen manifest, keyed by upload and manifest hash.**
  - Keyed by the hash of its own contents, which makes it self-identifying. Worked example: a retried completion sends the same part list, which hashes to the same value, so the service recognizes it as the same manifest without comparing 1,280 entries.
- **Row: Final publication.** Records the object version together with the session that produced it.

---

> - Reference DDL
>   - Keys and uniqueness match the state table above and the [companion schema](../../1sde/1.backend/2.rest102.md#infra-9).
>   - Staged part bytes and the published object live in object storage; SQL holds sessions, dedup, part identities, frozen manifests, and publication records.

**What this says in plain words**
The SQL holds identities and state. Every actual byte is in object storage.

---

> ```sql
> CREATE TABLE upload_sessions (
>   tenant_id text NOT NULL, upload_id text NOT NULL, object_key text NOT NULL,
>   declared_bytes bigint NOT NULL CHECK (declared_bytes >= 0), declared_sha256 text NOT NULL,
>   part_size_bytes bigint NOT NULL CHECK (part_size_bytes > 0),
>   state text NOT NULL CHECK (state IN ('UPLOADING','COMPLETING','COMMITTED','ABORTED')),
>   generation bigint NOT NULL CHECK (generation >= 1),
>   frozen_manifest_hash text,                -- set on UPLOADING -> COMPLETING; never changes afterwards
>   completion_fence text,                    -- operation identity of the in-flight completion attempt
>   expires_at timestamptz NOT NULL, version bigint NOT NULL,
>   PRIMARY KEY (tenant_id, upload_id),
>   CHECK (state IN ('UPLOADING','ABORTED') OR frozen_manifest_hash IS NOT NULL)
> );
> CREATE INDEX upload_sessions_expiry ON upload_sessions (expires_at)
>   WHERE state IN ('UPLOADING','COMPLETING');
> CREATE INDEX upload_sessions_cleanup ON upload_sessions (expires_at) WHERE state = 'ABORTED';
> ```

**What this says in plain words**
The session table, holding the state machine and both fencing mechanisms.

- **Four states.** `UPLOADING`, `COMPLETING`, `COMMITTED`, `ABORTED`. Two working states and two terminal ones.
- **`declared_bytes` and `declared_sha256`.** What the client said the file is, recorded at creation so completion can check against it.
- **`frozen_manifest_hash`** with "set on `UPLOADING` → `COMPLETING`; never changes afterwards".
  - Worked example of the immutability mattering: a completion retry sends its manifest. If the stored hash matches, it is the same request. If it differs, the client is trying to complete the same session with a different set of parts, which must be refused.
- **`completion_fence`**, the operation identity of the in-flight completion attempt.
  - Worked example: completion attempt A is running and stalls. A second completion request starts attempt B with a new fence. A resumes and tries to finish, but the stored fence is now B's, so A's write fails. Without the fence, A could publish an object based on state that B has moved past.
- **`CHECK (state IN ('UPLOADING','ABORTED') OR frozen_manifest_hash IS NOT NULL)`.**
  - Read it as: `COMPLETING` and `COMMITTED` require a frozen manifest.
  - Worked example of what it prevents: a session marked `COMMITTED` with no record of which parts it committed. The object exists and nothing says what is in it. The constraint makes that row impossible to write.
- **`upload_sessions_expiry`, a partial index** covering only `UPLOADING` and `COMPLETING`.
  - The expiry reconciler's work queue: only sessions that can still expire. Worked example: a year of completed sessions is irrelevant to it, and this index never contains them.
- **`upload_sessions_cleanup`, a partial index** covering only `ABORTED`.
  - The cleanup worker's separate queue. Two indexes because two different workers do two different jobs on two different populations.

---

> ```sql
> CREATE TABLE upload_create_dedup (
>   tenant_id text NOT NULL, idempotency_key text NOT NULL,
>   request_hash text NOT NULL, upload_id text NOT NULL,
>   expires_at timestamptz NOT NULL,          -- at least the client retry horizon
>   PRIMARY KEY (tenant_id, idempotency_key),
>   FOREIGN KEY (tenant_id, upload_id) REFERENCES upload_sessions
> );
> CREATE INDEX upload_create_dedup_expiry ON upload_create_dedup (expires_at);
> ```

**What this says in plain words**
The creation-deduplication table.

- **The primary key is the enforcement.** A duplicate creation conflicts on insert and the existing session is returned.
- **`request_hash`** makes the mismatch case detectable rather than silently returning the wrong session.
- **`expires_at` at least the client retry horizon.** Worked example of getting it wrong: the record expires after an hour, and a client that retries after two hours creates a second session for the same file, doubling the staged bytes.

---

> ```sql
> CREATE TABLE upload_parts (
>   upload_id text NOT NULL, generation bigint NOT NULL,
>   part_number integer NOT NULL CHECK (part_number > 0),
>   tenant_id text NOT NULL,
>   size_bytes bigint NOT NULL CHECK (size_bytes >= 0), checksum text NOT NULL,
>   staging_ref text NOT NULL,                -- immutable attempt-specific staging key
>   provider_etag text,                       -- opaque validator, not a digest
>   verified boolean NOT NULL DEFAULT false,
>   PRIMARY KEY (upload_id, generation, part_number),
>   FOREIGN KEY (tenant_id, upload_id) REFERENCES upload_sessions
> );
> ```

**What this says in plain words**
One row per part, and two of its columns encode the design's central ideas.

- **`part_number CHECK (> 0)`.** Parts are numbered from 1, matching the service convention below.
- **`staging_ref`** with "immutable attempt-specific staging key".
  - The mechanism behind safe concurrent uploads of the same part. Worked example: two devices upload part 42 simultaneously. Each writes to its own unique staging key, so neither overwrites the other. The metadata row then records whichever key is published first, and the other's bytes are simply unreferenced and cleaned up.
  - Worked example of the alternative: both write to a shared key `parts/42`. One overwrites the other mid-write, and the result may be a blend of two uploads that matches neither checksum.
- **`provider_etag`** with "opaque validator, not a digest", repeating the invariant at the point where the value is stored so nobody uses it as a hash.
- **`verified boolean DEFAULT false`.**
  - Worked example of why a separate flag: a part row can exist because an upload was attempted, without its bytes having been confirmed. Only verified parts may appear in a manifest, so the flag separates "we know about this part" from "we have checked it".

---

> ```sql
> CREATE TABLE frozen_manifests (
>   upload_id text NOT NULL, manifest_hash text NOT NULL,
>   tenant_id text NOT NULL, generation bigint NOT NULL,
>   part_identities jsonb NOT NULL,           -- ordered (part_number, checksum); immutable
>   frozen_at timestamptz NOT NULL,
>   PRIMARY KEY (upload_id, manifest_hash),
>   FOREIGN KEY (tenant_id, upload_id) REFERENCES upload_sessions
> );
> ```

**What this says in plain words**
The frozen manifest as a durable row rather than a transient in-memory list.

- **`part_identities`** holding ordered pairs of part number and checksum, marked immutable.
  - Both fields are needed. Worked example: the number gives the position in the assembled file, and the checksum says exactly which bytes belong there. A manifest of numbers alone would not pin the content.
- **Keyed by the manifest hash**, so the manifest identifies itself.
- **Storing it as a row rather than computing it** is what makes completion recoverable. Worked example: the finalizer crashes mid-verification. On restart, the exact list it was verifying is still there, so it resumes rather than re-deriving a list that may have changed.

---

> ```sql
> CREATE TABLE object_versions (
>   tenant_id text NOT NULL, object_key text NOT NULL, object_version text NOT NULL,
>   location text NOT NULL, size_bytes bigint NOT NULL CHECK (size_bytes >= 0),
>   sha256 text NOT NULL, source_upload_id text NOT NULL, published_at timestamptz NOT NULL,
>   PRIMARY KEY (tenant_id, object_key, object_version),
>   UNIQUE (tenant_id, source_upload_id),     -- one session publishes at most one version
>   FOREIGN KEY (tenant_id, source_upload_id) REFERENCES upload_sessions
> );
> ```

**What this says in plain words**
One row per published object version, with a uniqueness constraint doing real work.

- **`UNIQUE (tenant_id, source_upload_id)`** with "one session publishes at most one version".
  - The strongest guarantee in the schema, enforced by the database rather than by careful code.
  - Worked example: two completion attempts both reach the point of publishing. The first inserts its version. The second violates this constraint and fails. The session cannot produce two objects, whatever the concurrency.
  - This is the duplicate-object failure from the interview framing, closed by one constraint.
- **`sha256` stored on the published version**, so the object's integrity can be checked later independently of the upload that produced it.
- **Versions are rows rather than overwrites**, so publishing over an existing key adds a version rather than destroying the previous one.

---

> - Not captured by the DDL
>   - Staged bytes, the final object, and the provider's own multipart state (`ListParts`) live in object storage; scoped upload grants are signed tokens, not rows.
>   - Deviation from the companion: states are `UPLOADING`/`COMPLETING`/`COMMITTED`/`ABORTED` rather than `OPEN`/`FINALIZING`/`FAILED`; the part key gains `generation` and drops `tenant_id` as the state table says; `frozen_manifests` and `object_versions` are added so the frozen manifest and final publication are rows rather than a text manifest.

**What this says in plain words**
Two notes.

1. **Three things live outside SQL**, and the third is the interesting one: the provider keeps its *own* multipart state, queryable through a listing operation.
   - Worked example of why that matters: the service has a part table, and the provider has its own list of parts it holds. Those are two independent records of the same thing, and reconciliation compares them.
   - Grants are signed tokens, not rows, so there is nothing to look up or revoke individually; they expire.
2. **The companion deviations**, with the reasoning: different state names, a generation added to the part key, and two tables added so the manifest and the publication are durable rows.

---

> - Proposed service conventions
>   - Require parts numbered `1..N` for simple validation.
>   - All non-final parts have the negotiated size.
>   - The last part has the remaining size.
>   - Empty files use a documented zero-byte path.
>   - This is a service convention, not a universal multipart API rule.

**What this says in plain words**
Four rules, and a disclaimer that they are this service's choices.

1. **Parts numbered 1 through N, contiguously.**
   - Worked example of what this buys: validation is counting. If the manifest has 1,280 entries numbered 1 to 1,280 with no gaps, it is complete. No set arithmetic, no missing-range detection.
2. **All non-final parts are exactly the negotiated size.**
   - Worked example of what this buys: the total size is derivable, and any part with an unexpected size is immediately wrong. It also means a part's position in the file is computable from its number alone.
3. **The last part holds the remainder.** 10 gibibytes is not an exact multiple of 8 mebibytes, so the final part is smaller.
4. **Empty files use a documented zero-byte path.**
   - The degenerate case handled explicitly. Worked example of leaving it undefined: a zero-byte file has no parts, so the manifest is empty, and validation logic expecting at least one part either rejects a legitimate file or crashes.
5. **The disclaimer: a service convention, not a universal rule.**
   - Important, because the provider-boundaries section shows that the underlying provider permits noncontiguous part numbers. This service is stricter on purpose, and the strictness buys simple validation, and it must be enforced by the service rather than assumed from the provider.

## Part integrity and safe resume — IC3 baseline

The first deep dive. Resume identity, concurrent same-part uploads, late writers, and checksums.

---

> - Resume identity
>   - Save the upload ID locally with size and file fingerprint.
>   - Reauthorize before returning session state.
>   - Verify the local file still matches the session.
>   - List verified parts and upload only missing identities.
>   - A path or filename alone is not an immutable file identity.

**What this says in plain words**
Five steps, and the last is the warning that motivates the rest.

1. **Save the upload identifier locally, with the size and fingerprint.**
   - Three values, not one. The identifier finds the session; the size and fingerprint prove the local file is still the one the session is for.
2. **Reauthorize before returning session state.**
   - Worked example of why: the upload started yesterday under a user who has since been removed from the tenant. Returning the session state without re-checking would let a revoked user continue and complete an upload.
3. **Verify the local file still matches.**
   - Worked example of the corruption this prevents: a user starts uploading `report.pdf`, then replaces it with a different file of the same name, then resumes. Parts 1 to 400 are from the old file and parts 401 to 1,280 from the new one. The completed object is a splice of two files that passes every part checksum, because each part's checksum was computed from whatever bytes were there at the time.
4. **List verified parts and upload only what is missing.** The actual resume.
5. **A path or filename is not an immutable identity.**
   - The sentence that makes step 3 necessary. A path names a location, and the content at that location can change entirely while the name stays the same.

---

> - Concurrent same-part upload
>   - Avoid overwriting a shared staging key blindly.
>   - Upload to immutable attempt-specific storage keys.
>   - Conditionally publish the first valid part identity in metadata.
>   - A duplicate with identical checksum reuses that identity.
>   - A different checksum receives a conflict and its unused staging bytes are cleaned up.

**What this says in plain words**
Five rules resolving what happens when two uploads of the same part number race.

1. **Do not blindly overwrite a shared staging key.**
   - Worked example of the corruption: both devices write to `staging/up-8891/part-42`. Device A is 60% through writing when device B starts writing the same key. Depending on the storage's behavior, the result may be A's first 60% followed by B's remainder, which is a blend matching neither checksum, and which was acknowledged as a successful write to both.
2. **Upload to immutable attempt-specific keys.**
   - Worked example: A writes `staging/up-8891/part-42/attempt-7f3a` and B writes `staging/up-8891/part-42/attempt-9c21`. Neither can touch the other's bytes. Both uploads succeed and both objects are intact.
3. **Conditionally publish the first valid identity in metadata.**
   - The metadata row for part 42 is written conditionally, so whichever arrives first wins, and the winner is decided by one database write rather than by which upload finished first.
4. **A duplicate with an identical checksum reuses the identity.**
   - Worked example: both devices uploaded the same bytes, because it is the same file. A's identity is published. B's request presents the same checksum, is recognized as the same part, and returns success. B's staging object is unreferenced and cleaned up. The user sees two successful uploads and one part.
5. **A different checksum receives a conflict.**
   - Worked example: the two devices have different files. B's checksum differs from the published one, so B receives a conflict rather than replacing part 42. That is correct: the session is bound to one file, and B is uploading a different one.

**Why it matters**
The pattern is worth naming: write to unique locations, then decide the winner in one conditional metadata write. The expensive, non-atomic byte transfer is made safe by never having two writers touch one location, and the cheap, atomic decision is made in a database.

---

> - Late part writers
>   - Seal the manifest before finalization.
>   - Reject metadata publication once the session leaves `UPLOADING`.
>   - Direct storage uploads may finish later, but cannot alter the frozen manifest.
>   - Cleanup removes their unreferenced immutable bytes.

**What this says in plain words**
Four rules about a part that arrives after completion has begun.

1. **Seal the manifest before finalization.** The list is fixed first, and verification happens against a fixed list.
2. **Reject metadata publication once the session leaves `UPLOADING`.** The single rule that makes late writers harmless.
3. **Direct uploads may still finish; they cannot alter the manifest.**
   - The key structural point, and it follows from bytes not going through the API.
   - Worked example: at 14:05 completion begins and the manifest is frozen. A part upload that started at 14:04:58 is still transferring, and the API cannot stop it, because the bytes are going directly to storage. At 14:05:03 it completes and storage holds the object. The client then calls the API to record it, and that call is rejected because the session is no longer `UPLOADING`. The bytes exist and are referenced by nothing.
4. **Cleanup removes their unreferenced bytes.**

**Why it matters**
The service cannot prevent the byte transfer, so it does not try. It controls the only thing it owns, which is whether the part is ever referenced. The manifest is the boundary, and the bytes are just bytes until something points at them.

---

> - Checksums
>   - Verify each part at receipt or through a documented storage checksum result.
>   - Do not trust a checksum supplied only by the client as proof that stored bytes match.
>   - Hashing the concatenation of part digests is not the SHA-256 of concatenated file bytes.
>   - A standard whole-file SHA-256 requires hashing the ordered bytes or an equivalent supported incremental computation.
>   - A Merkle root is a different integrity contract and must be named as such.

**What this says in plain words**
Five statements about integrity, and the middle three are the ones most often got wrong.

1. **Verify each part at receipt, or through a documented storage checksum result.**
   - Two acceptable sources. The service computes it, or the storage provider does and documents that it did.
2. **Do not trust a client-supplied checksum as proof that stored bytes match.**
   - Worked example of the gap: the client computes the checksum of its local bytes and sends it. The bytes are corrupted in transit. The client's checksum describes what it intended to send, not what arrived. Verifying it against the stored bytes is the check; accepting it as a claim is not.
3. **Hashing the concatenation of part digests is not the SHA-256 of the file.**
   - The most important sentence in the section, and it explains why multipart ETags confuse people.
   - Worked example: the file's SHA-256 is computed over all 10,737,418,240 bytes in order. What is easy to compute after a multipart upload is the hash of the 1,280 part digests concatenated, which is a completely different value derived from a completely different input. Neither is wrong; they are simply not the same number, and one cannot be checked against the other.
4. **A standard whole-file SHA-256 requires hashing the ordered bytes, or an equivalent supported incremental computation.**
   - Worked example of the cost: reading 10 gibibytes and hashing them. There is no shortcut from the parts, which is why the requirements made the whole-file digest optional.
   - "or an equivalent supported incremental computation" allows a hash function's internal state to be carried across parts, where the implementation supports it, giving the same result without a second read.
5. **A Merkle root is a different integrity contract and must be named as such.**
   - A Merkle root is computed by hashing the parts, then hashing those hashes in a tree structure. It is a legitimate and useful integrity value, and it is not the file's SHA-256.
   - Worked example of the confusion this prevents: a service that computes a Merkle root and calls it "the file hash". A client computes SHA-256 locally, compares, finds a mismatch, and reports data corruption that does not exist.
   - The strong version: a Merkle root proves the parts are intact and lets a single part be verified independently, which SHA-256 cannot do. It is a different contract with different properties, and the only error is calling it by the wrong name.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| File fingerprint | A recorded identity for the file's content, checked before resuming. | A path or filename cannot serve this purpose. |
| Reauthorization | Re-checking permission when a session is resumed, not only when created. | A revoked user must not be able to continue. |
| File splice | An object assembled from parts of two different files. | What resuming against a changed local file produces. |
| Attempt-specific staging key | A unique storage key per upload attempt of a part. | Lets concurrent uploads coexist without overwriting. |
| Blind overwrite | Writing to a shared key without knowing whether another writer is active. | Can produce a blend matching neither checksum. |
| Conditional publication | Writing the part's metadata identity only if none is published yet. | Decides the winner with one atomic write. |
| Unreferenced bytes | Staged objects no metadata row points at. | Harmless, and cleaned up. |
| Late writer | A part upload finishing after the manifest was frozen. | Cannot be stopped, and cannot affect the object. |
| Manifest seal | Fixing the part list before verification begins. | The boundary late writers cannot cross. |
| Part checksum | A digest of one part's bytes, verified against what was stored. | Per-part integrity, always required. |
| Whole-file digest | A hash over the file's ordered bytes, such as SHA-256. | Optional, because it requires reading everything. |

## Completion, abort, and provider boundaries — IC3 baseline

The second deep dive. The completion pseudocode, the crash-between-commits case, the abort race, overwrite preconditions, the OCI provider distinction, and the zero-copy caveat.

---

> ```text
> COMPLETE(session, manifest):
>     transaction / compare-and-set:
>         if COMMITTED and manifest matches: return prior object version
>         if UPLOADING: validate part identities and freeze manifest
>         otherwise require same in-progress manifest or return conflict
>         transition to COMPLETING with operation identity
>     outside transaction:
>         verify and finalize immutable object using operation identity
>     transaction:
>         require current completion attempt fence and expected session version
>         require state == COMPLETING and the same frozen manifest hash
>         record verified immutable final object version
>         transition COMPLETING -> COMMITTED
> ```

**What this says in plain words**
Three phases: a short transaction, slow work outside it, then a second short transaction that checks nothing changed.

**First transaction, three branches:**

1. **Already `COMMITTED` with a matching manifest: return the prior version.**
   - The retry case, handled first. Worked example: the response was lost and the client retries. The object exists, the manifest matches, so the same version is returned and nothing is done again.
2. **`UPLOADING`: validate the part identities and freeze the manifest.**
   - The normal case. Validation happens here, inside the transaction, before the state moves.
3. **Otherwise: require the same in-progress manifest, or conflict.**
   - The already-`COMPLETING` case. Worked example: a second completion request arrives while the first is verifying. With the same manifest it is the same request and is allowed to join. With a different manifest it is a conflict, because the session is already committed to a specific part list.

**Then transition to `COMPLETING` with an operation identity**, which becomes the fence.

**Outside the transaction: verify and finalize.**
- This is the slow part, potentially minutes for a 10-gibibyte digest, and it deliberately holds no database transaction. Worked example of the alternative: holding a transaction open for two minutes blocks other writes to that row and consumes a connection for the duration.

**Second transaction, four conditions before committing:**

1. **The current completion fence.** Proves this attempt is still the active one.
2. **The expected session version.** Proves nothing else modified the row.
3. **State is `COMPLETING`.** Proves the session was not aborted meanwhile.
4. **The same frozen manifest hash.** Proves the list being published is the one that was verified.

- All four, and each rules out a different intervening event. Worked example of why the fence alone is insufficient: the fence proves no *newer completion* started, and the state check proves no *abort* happened. Those are different events needing different checks.

**Why it matters**
The shape is the general answer to "slow work that must commit atomically": open a window with a fence, do the work outside any transaction, then close the window only if it is still the same window.

---

> - Crash between storage commit and metadata commit
>   - Retrying a provider commit may not be supported after the upload has disappeared.
>   - Reconcile using the destination object or version and the operation identity.
>   - Never infer failure solely because `ListParts` no longer returns an active upload.
>   - Use a unique immutable final staging object per completion attempt when provider finalization can race.
>   - A fenced metadata transaction selects the published object
>   - Losing artifacts remain unreferenced.
>   - Do not let a stale worker overwrite a shared final key before checking its fence.

**What this says in plain words**
The hardest failure in the design: the storage provider assembled the object and the database never recorded it.

**The situation, walked through:**

| Step | What happened |
|---|---|
| 1 | The finalizer verified the manifest and called the provider's commit. |
| 2 | The provider assembled the object successfully. |
| 3 | The finalizer process died before its second transaction. |
| 4 | The database still says `COMPLETING`. Storage holds a finished object. |

1. **Retrying the provider commit may not work.**
   - Worked example: the provider's multipart upload no longer exists, because it was consumed by the successful commit. A second commit for that upload identifier fails with "no such upload", which looks exactly like the failure case.
2. **Reconcile using the destination object and the operation identity.**
   - The correct recovery: look at the destination. If an object exists bearing this attempt's operation identity, the commit succeeded and the database simply needs updating.
3. **Never infer failure solely because `ListParts` no longer returns an active upload.**
   - The trap, stated as a prohibition. Worked example: the recovery logic asks the provider to list the upload's parts. The provider says the upload does not exist. That is consistent with the upload having been *completed* and with it never having existed. Concluding failure from absence is wrong half the time, and the wrong half leads to re-uploading 10 gibibytes over an object that already exists.
4. **Use a unique immutable final staging object per completion attempt when finalization can race.**
   - Worked example: two completion attempts could each assemble an object. If both write to the final key, the second overwrites the first and which one survives depends on timing. If each assembles into its own uniquely-named object, both exist intact and the metadata transaction decides which becomes the published version. The loser is unreferenced and cleaned up.
   - The same pattern as attempt-specific staging keys for parts, applied at the object level.
5. **A fenced metadata transaction selects the published object, and losers remain unreferenced.**
6. **Do not let a stale worker overwrite a shared final key before checking its fence.**
   - The specific prohibition. Worked example: a stalled attempt resumes after a newer attempt already published. If it writes to the final key before checking its fence, it has destroyed the published object's bytes, and the fence check afterwards is too late. The check must precede the write, not follow it.

---

> - Abort race
>   - A conditional transition selects abort or completion.
>   - If completion already froze the manifest, baseline abort returns conflict.
>   - The reaper follows the same state transition as an explicit abort.
>   - Physical byte deletion happens asynchronously and is retried.

**What this says in plain words**
Four rules resolving cancel-versus-finish.

1. **One conditional transition selects the winner.** Both operations attempt to move the session's state, and exactly one succeeds because both are conditional on the current state.
2. **If completion already froze the manifest, abort returns conflict.**
   - Worked example: the user presses cancel at 14:05:02, and completion froze the manifest at 14:05:00. The session is `COMPLETING`, so the abort is refused. That is the honest answer: the upload is being finalized and cancellation is no longer available.
3. **The reaper follows the same transition as an explicit abort.**
   - The expiry reconciler is not a special path. Worked example of why this matters: if the reaper deleted directly rather than transitioning, it could delete bytes belonging to a session that was completing. Using the same state transition means the reaper is subject to the same conditions, and a completing session's expiry attempt simply fails.
4. **Physical deletion is asynchronous and retried.**
   - Worked example of the ordering: the session moves to `ABORTED` immediately, which is atomic and cheap. Deleting 1,280 staged objects takes time and can partially fail, so it runs afterwards and is retried until done.
   - The consequence, which the pushback section states: cancelling does not free space immediately. The logical state changes at once and the bytes go later.

---

> - Existing object overwrite
>   - Use an expected version or precondition when publishing over a logical key.
>   - Two concurrent completed uploads must not silently overwrite each other's intended version.

**What this says in plain words**
Publication over an existing key is conditional, not a blind write.

**Why it matters**
Worked example of the failure: two users upload different files to `backups/2026-09.tar` within seconds. Both complete. Without a precondition, the second silently replaces the first. The first user's client reported success, and their data is gone, and nothing recorded that it happened.

- With a version precondition, the second publication is told the key has moved on, and the conflict is surfaced to a caller who can decide.
- The word "intended" in the source is precise: each upload intended to create a specific version, and silently satisfying only one of those intentions is the failure.

---

> - OCI distinction
>   - OCI permits noncontiguous part numbers and assembles them in ascending order.
>   - Reusing a part number commits the last uploaded part for that number.
>   - Commit uses part numbers and corresponding ETags.
>   - Completed upload parts are no longer listable through the active-upload interface.
>   - Our stricter immutable-part service must account for those provider semantics.
>   - See [OCI multipart API behavior](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usingmultipartuploads_topic-Using_the_Multipart_Upload_API.htm).

**What this says in plain words**
Four documented provider behaviors, and each differs from this service's rules.

1. **Noncontiguous part numbers are permitted, assembled in ascending order.**
   - Worked example: parts numbered 1, 5, and 9 produce an object of those three parts in that order. This service requires 1 through N, which is stricter and makes validation a count.
2. **Reusing a part number commits the last uploaded part for that number.**
   - The most significant difference. The provider treats a part number as a mutable slot; this service treats it as an immutable identity.
   - Worked example of the consequence: if the service simply passed part uploads through, a second upload of part 42 would silently replace the first at the provider, and the service's records would describe the first while the provider held the second. The stricter rule exists precisely to prevent that divergence, and it must be enforced by the service, because the provider will not enforce it.
3. **Commit uses part numbers and their ETags.** The provider's assembly instruction is a list of numbers and validators, which is what the frozen manifest ultimately becomes.
4. **Completed upload parts are no longer listable through the active-upload interface.**
   - The documented fact behind the "never infer failure from absence" rule. A completed upload's parts disappear from the listing, so absence proves nothing about success or failure.
5. **The service must account for these semantics.**
   - The honest framing: this design is stricter than the provider, and that strictness is a service-level choice enforced in the service's own metadata. Claiming the provider guarantees it would be false.

**Why it matters**
It is the clearest example in the file of separating what a provider documents from what a design promises, and it is exactly the distinction an Oracle interviewer is positioned to probe.

---

> - Zero-copy caveat
>   - A custom object store can publish a manifest over existing chunks.
>   - A managed provider may assemble or copy internally.
>   - Do not promise zero byte copying without that storage contract.

**What this says in plain words**
Three sentences about a claim not to make.

1. **A custom store can publish a manifest over existing chunks.** If you built the storage, completion can be a metadata operation: write a manifest pointing at chunks already in place.
2. **A managed provider may assemble or copy internally.** You cannot see what it does.
3. **Do not promise zero copying without the contract.**
   - Worked example of the difference it makes: if completion is a metadata write, a 10-gibibyte upload completes in milliseconds. If the provider copies 10 gibibytes internally, completion takes as long as the copy, perhaps a minute or more, and the API's completion latency is entirely determined by something undocumented.
   - Worked example of the consequence of guessing: promising sub-second completion, then discovering the provider copies, means the promise was never achievable and nothing in the design can fix it.

|---|---|---|
| Compare-and-set | A write applying only if the row still matches what was read. | Both completion transactions use it. |

## Failure, operations, and security

A nine-row failure table, then what to observe, retry discipline, tenant isolation, and rollout safety.

---

> | Failure | Blast radius | Detection | Degraded behavior | Recovery |
> |---|---|---|---|---|
> | Part response lost | One part | Client timeout | Retry same identity within deadline | Reuse verified part or list authoritative state |
> | Client crashes | One session | Inactivity | Staging remains private | Resume after identity and authorization checks |
> | Local file changes | One resumed upload | Size/fingerprint mismatch | Reject resume | Start a new session |
> | Complete response lost | One session | Ambiguous operation result | Poll current state | Reconcile final object before retrying provider commit |
> | Abort races with completion | One session | Conditional state conflict | Exactly one logical transition wins | Cleanup only unreferenced bytes |
> | Corrupt part | One part | Checksum mismatch | Reject without publishing | Retry verified bytes |
> | Expired authorization | One client's parts | Auth failure | Stop affected uploads | Reauthorize scoped access; keep session identity |
> | Cleanup worker unavailable | Staging capacity | Orphan bytes and age | Restrict new staging if quota reached | Resume idempotent cleanup |
> | Metadata store unavailable | All new sessions and completions | Health check, error rate | In-flight part uploads continue on existing grants | Fail over replica; parts reconcile from storage listing |

**What this says in plain words**
Nine failures, with radius, detection, degraded behavior, and recovery.

- **Row: Part response lost.**
  - Radius one part, which is the entire benefit of chunking expressed as a table row.
  - "Retry same identity within deadline" is safe because the part's identity makes a repeat recognizable.
- **Row: Client crashes.**
  - "Staging remains private" is the security note: uploaded parts are not visible to anyone until publication, so a crashed upload does not expose a partial file.
  - Recovery requires both identity and authorization checks, restating the resume rules.
- **Row: Local file changes.**
  - Degraded behavior is to reject the resume outright, and recovery is a new session. There is no attempt to salvage the parts already uploaded, because a splice of two files is worse than re-uploading.
- **Row: Complete response lost.**
  - "Reconcile final object before retrying provider commit" is the ordering rule from the deep dive: look at the destination first, because a retry may fail for the wrong reason.
- **Row: Abort races with completion.**
  - "Exactly one logical transition wins" and "cleanup only unreferenced bytes". Whichever loses, the bytes belonging to the winner are never touched.
- **Row: Corrupt part.**
  - "Reject without publishing" is the point: corruption is caught at the part level, before anything is assembled, so a corrupt object is never created.
- **Row: Expired authorization.**
  - Radius is "one client's parts", not the session. Worked example: a grant expires mid-upload. That client's part uploads fail, and the session, its recorded parts, and its identity are untouched. Recovery is a new grant, and the upload continues from where it stopped.
- **Row: Cleanup worker unavailable.**
  - Detection is orphan bytes *and age*. Worked example: 400 orphaned objects an hour old is a working system with a backlog; 400 objects four days old is a stuck worker.
  - "Restrict new staging if quota reached" is the backpressure: if cleanup cannot keep up, new uploads are limited rather than letting storage fill without bound.
- **Row: Metadata store unavailable.**
  - The largest radius: no new sessions and no completions.
  - "In-flight part uploads continue on existing grants" is the payoff of bytes bypassing the API. Worked example: the database is down for 10 minutes, and a client with a valid grant keeps uploading parts to storage throughout. What it cannot do is record them or complete.
  - "parts reconcile from storage listing" is the recovery: the parts that arrived during the outage are discovered by asking storage what it holds.

---

> - Observe
>   - Part retry rate and checksum failures.
>   - Effective goodput by file-size cohort.
>   - Oldest `COMPLETING` operation.
>   - Unreferenced staging bytes.
>   - Session quota rejections.
>   - Completion reconciliation outcomes.

**What this says in plain words**
Six measurements, each answering a question the others cannot.

1. **Part retry rate and checksum failures.**
   - Two different signals. Worked example: a high retry rate with no checksum failures means the network is unreliable but the data is intact. Checksum failures mean bytes are being corrupted, which is a far more serious finding.
2. **Effective goodput by file-size cohort.**
   - By cohort, because the experience differs. Worked example: small files may show poor goodput because per-request overhead dominates, while large files show good goodput. One aggregate number would hide both facts.
3. **Oldest `COMPLETING` operation.**
   - The direct detector for the crash-between-commits case. Worked example: a session in `COMPLETING` for 40 minutes, against a normal completion of seconds, means a finalizer died and reconciliation has not run.
4. **Unreferenced staging bytes.** The direct measure of what cleanup owes, and of what is being paid for.
5. **Session quota rejections.** Reveals a tenant hitting its limits, which may be abuse or may be a legitimate need to raise a quota.
6. **Completion reconciliation outcomes.**
   - The subtlest metric. Worked example: reconciliation running frequently and finding objects that were committed but unrecorded means finalizers are crashing after the provider commit. The system heals correctly, so nothing errors, and only this counter reveals the underlying instability.

---

> - Retry discipline
>   - Exponential backoff with jitter.
>   - Bounded attempts and total elapsed deadline.
>   - Respect server retry hints.
>   - Retry only transient transport or service errors.
>   - A checksum or authorization failure requires a corrective action, not infinite retries.

**What this says in plain words**
Five rules, and the last draws the line.

1. **Exponential backoff with jitter.** Progressively longer waits, randomized so clients do not synchronize.
2. **Bounded attempts *and* a total elapsed deadline.**
   - Both, and they bound different things. Worked example: 10 attempts with exponential backoff could span hours. A total deadline of 10 minutes stops that regardless of how few attempts were made.
3. **Respect server retry hints.** If the service says when to come back, honor it rather than using local backoff.
4. **Retry only transient transport or service errors.**
5. **A checksum or authorization failure requires corrective action, not retries.**
   - Worked example of a checksum failure: the bytes stored do not match what was expected. Retrying the identical upload sends the same bytes and fails identically. The corrective action is to re-read the source and send again, or to conclude the source changed.
   - Worked example of an authorization failure: the grant expired. Retrying with the expired grant fails forever. The corrective action is to obtain a new grant, which is a different operation entirely.
   - The principle: retry is for problems that may resolve themselves. A problem with a known cause needs the cause addressed.

---

> - Tenant isolation
>   - Staging prefixes and grants are scoped per tenant and session.
>   - Quotas cap active sessions and staging bytes per tenant.
>   - A tenant's token receives `404` on another tenant's upload IDs, not `403`, to avoid existence leaks.

**What this says in plain words**
Three rules.

1. **Staging prefixes and grants scoped per tenant and session.**
   - Both levels. Worked example: a grant permits writing under `staging/acme/up-8891/` and nothing else. It cannot reach another tenant's data, and it cannot reach another session belonging to the same tenant.
2. **Quotas on active sessions and staging bytes.**
   - Two dimensions, because they fail differently. Worked example: a tenant could open 100,000 tiny sessions, exhausting metadata, or 10 enormous ones, exhausting storage. Capping only one leaves the other open.
3. **`404` rather than `403` for another tenant's upload identifier.**
   - Worked example of the leak: `403` confirms that an upload with that identifier exists and belongs to someone else. An attacker probing identifiers learns which are real, which reveals how much another tenant is uploading and when.

---

> - Rollout and rollback safety
>   - Session and part schema changes follow expand, migrate, contract.
>   - A new finalizer version must accept manifests frozen by the previous version.
>   - Canary the API fleet
>   - In-flight uploads must survive a deploy because grants do not depend on API health.

**What this says in plain words**
Four rules, and the second is specific to this design's long-lived state.

1. **Expand, migrate, contract for schema changes.** Add the new form, move to it, and only then remove the old.
2. **A new finalizer must accept manifests frozen by the previous version.**
   - The rule that follows from sessions living for up to 24 hours.
   - Worked example: a manifest is frozen at 09:00 by version 4. At 11:00 version 5 deploys with a changed manifest format. At 11:05 the finalizer processes that 09:00 manifest. If version 5 cannot read version 4's format, the upload fails at the last step, after 10 gibibytes have been transferred and verified.
   - The general point: any system holding state across a deploy window must be able to read what previous versions wrote, and here the window is a full day.
3. **Canary the API fleet.** Roll to a subset first.
4. **In-flight uploads survive a deploy, because grants do not depend on API health.**
   - The architecture paying a dividend. Worked example: the entire API fleet restarts during a deploy. Clients holding valid grants continue uploading parts to storage throughout, and resume recording them when the API returns. A design that proxied bytes would drop every transfer on every deploy.

## Alternatives and IC4 stretch

The option table, four stretch items, the weakest assumption, and the over-engineering warning.

---

> | Option | What it is | Strength | Weakness | Choose when |
> |---|---|---|---|---|
> | Single request | One whole-object transfer | Simple protocol | Whole-file retry cost | Small objects and reliable links |
> | Fixed-size multipart | Independent numbered parts | Resume and bounded retry unit | Session metadata and cleanup | Baseline large unreliable uploads |
> | Content-defined chunks | Boundaries depend on content | Reuses shifted content | CPU, indexing, privacy complexity | Repeated backup or sync workloads |
> | Proxy all bytes | API relays upload content | Central validation point | API bandwidth and buffering cost | Policy requires inspection inline |
> | Direct storage upload | Scoped client-to-storage transfer | Removes API byte bottleneck | Provider semantics and reconciliation | Baseline managed storage integration |

**What this says in plain words**
Five options across two decisions: how the file is divided, and who carries the bytes.

- **Row: Single request.** The naive design, correct for small files on reliable links, which is most uploads.
- **Row: Fixed-size multipart.** The chosen division. Its weakness is honest: session metadata and cleanup are real ongoing costs, not one-time complexity.
- **Row: Content-defined chunks.**
  - Boundaries determined by the data itself rather than by fixed offsets, typically using a rolling hash over a sliding window.
  - Strength: reuses shifted content. Worked example: a 10-gibibyte file has 1 kilobyte inserted at the beginning. With fixed-size parts every subsequent part's boundaries shift, so all 1,280 parts differ and everything must be re-uploaded. With content-defined boundaries, the boundaries still land at the same content patterns, so only the chunk containing the insertion changes.
  - Weaknesses: rolling-hash CPU over every byte, a chunk index to maintain, and privacy complexity. Worked example of the last: chunk-level deduplication across tenants reveals whether another tenant holds identical content, which is the same leak the non-goals excluded.
- **Row: Proxy all bytes.**
  - Right only when policy requires inline inspection. Worked example of the cost: 10,000 concurrent 10-gibibyte uploads through the API fleet means the API must carry the full aggregate bandwidth and buffer partial transfers, which is a completely different capacity model.
- **Row: Direct storage upload.** The chosen byte path, with provider semantics and reconciliation as the acknowledged price.

---

> - IC4 stretch — stronger publication
>   - Upload to an immutable private version.
>   - Scan or verify before updating the logical public pointer.
>   - Readers see the prior version until publication wins its precondition.
>   - This separates provider completion from application visibility.

**What this says in plain words**
Four steps separating two things that are usually conflated.

1. **Upload to an immutable private version.** The object exists and nobody can read it.
2. **Scan or verify before updating the public pointer.** Malware scanning, policy checks, whatever is required.
3. **Readers see the prior version until publication wins its precondition.**
   - Worked example: `backups/latest.tar` points at version 12. Version 13 is uploaded, scanned, and found clean, and only then does the pointer move. A reader at any instant sees either version 12 complete or version 13 complete, never a partial or unscanned object.
4. **This separates provider completion from application visibility.**
   - The sentence that names the idea. The provider finishing assembly and the object becoming visible to users are two different events, and keeping them separate is what makes scanning possible without a scanner on the upload path.
   - It also resolves the inline-scanning non-goal: scanning is not on the byte path, it is between completion and visibility.

---

> - IC4 stretch — deduplication
>   - Scope dedup by tenant unless cross-tenant information leakage is explicitly addressed.
>   - Content existence and timing can reveal another user's data.
>   - Reference counts and garbage collection require atomic ownership accounting.

**What this says in plain words**
Three points, and the second explains a leak that is easy to miss.

1. **Scope deduplication by tenant by default.** Within one tenant, deduplication is safe because the tenant already has access to all of it.
2. **Content existence and timing reveal another user's data.**
   - Worked example of the attack: an attacker uploads a file they suspect a target possesses. If the upload completes almost instantly, the content already existed and the target has it. If it takes the full transfer time, it did not. The attacker learns a fact about another tenant's data without any access to it, purely from timing.
   - Worked example of the severity: applied to a list of candidate documents, this becomes a way to determine which specific files an organization holds.
3. **Reference counts and garbage collection require atomic ownership accounting.**
   - Worked example of the hazard: two tenants reference the same stored chunk, so the reference count is 2. One deletes their object, decrementing to 1. If a third tenant's upload increments concurrently and the operations are not atomic, the count can end at 1 when it should be 2, and the chunk is deleted while still referenced. That is silent data loss for a tenant who did nothing.

---

> - IC4 stretch — 10× load
>   - Shard metadata by upload ID while retaining tenant indexes for quotas.
>   - Keep bytes off the API fleet.
>   - Bound checksum-worker capacity and finalization backlog.
>   - Adjust part size using measured request overhead and retry cost.

**What this says in plain words**
Four changes at ten times the scale.

1. **Shard by upload identifier, with tenant indexes retained for quotas.**
   - Two access patterns needing two arrangements. Worked example: a resume reads one session's 1,280 parts, which sharding by upload identifier serves perfectly. A quota check asks how many active sessions a tenant has, which sharding by upload identifier scatters across every shard, so a separate tenant index is kept for it.
2. **Keep bytes off the API fleet.** The property that made the design scale, restated as the thing not to abandon under pressure.
3. **Bound checksum-worker capacity and finalization backlog.**
   - Worked example: at 10× the load, 10,000 completions may be queued. Whole-file verification at 10 gibibytes each is enormous read volume. Without a bound, finalization falls behind indefinitely and every user's completion latency grows. With a bound, excess completions wait explicitly or are refused.
4. **Adjust part size using measured overhead and retry cost.**
   - The 8-mebibyte figure was derived from assumptions. At a different scale with measured numbers, the balance may move.

---

> - IC4 stretch — cost and blast radius
>   - Staging bytes are the dominant cost under abandonment
>   - Quota and expiry are cost controls, not only hygiene.
>   - Cell the metadata store per region so a store failure strands one region's sessions, not all.

**What this says in plain words**
Two points about cost and containment.

1. **Staging bytes dominate under abandonment, so quota and expiry are cost controls.**
   - Worked example: 10,000 abandoned sessions averaging 5 gibibytes of uploaded parts is 50 terabytes of storage for objects nobody will ever complete. If expiry were 7 days rather than 24 hours, that figure is seven times larger.
   - The expiry window is therefore a line in the storage budget, and shortening it is a cost decision with a user-experience consequence: a user who leaves an upload overnight loses it.
2. **Cell the metadata store per region.**
   - Worked example: one metadata store for all regions means its failure stops new sessions and completions everywhere. Per region, a failure strands one region's sessions, and elsewhere uploads continue.
   - And in-flight uploads in the affected region continue on existing grants, so even there the impact is bounded to new sessions and completions.

---

> - Weakest assumption
>   - Independent `1%` part failure
>   - A correlated outage multiplies retries and can exhaust the elapsed deadline.
>   - Mitigation: circuit-break the client after consecutive failures and resume later from authoritative state.

**What this says in plain words**
The assumption behind the retry arithmetic, and why it fails.

1. **The assumption:** each part fails independently, at 1%.
2. **A correlated outage breaks it.**
   - Worked example: a tunnel drops for 60 seconds. All four in-flight parts fail. Every retry during those 60 seconds also fails. Instead of 12.9 retries spread across the upload, there are dozens concentrated in one minute, and the exponential backoff means the client is mostly sleeping.
   - "can exhaust the elapsed deadline" is the consequence: the total deadline expires during the outage, and the upload fails even though the file and the session are both fine.
3. **The mitigation: circuit-break after consecutive failures, and resume later from authoritative state.**
   - Worked example: after 5 consecutive failures, the client stops trying entirely rather than continuing to back off. It saves its session identifier and stops. Later, it queries the server for the authoritative list of verified parts and continues from there.
   - Two properties make this work. Stopping early preserves the deadline for a period when progress is possible. And resuming from *server* state rather than local assumptions means whatever did arrive during the failing period is correctly accounted for.
   - The general principle: when failures are correlated, retrying harder makes things worse, and the right response is to stop and return when conditions have changed.

---

> - Over-engineering warning
>   - Do not promise transparent cross-device resume from an upload ID without file identity and fresh authorization.
>   - Do not build content-defined chunking for a one-shot upload service.

**What this says in plain words**
Two warnings, and the first is a correctness one rather than an effort one.

1. **Do not promise transparent cross-device resume from an identifier alone.**
   - Worked example of the failure: a user resumes on a tablet using only the upload identifier. The tablet's copy of the file differs slightly. The resulting object is a splice of two files that passes every part checksum and is corrupt.
   - Worked example of the security failure: the identifier leaks, and whoever holds it can add parts to someone else's upload.
   - So cross-device resume is supportable, and it requires a file-identity check and fresh authorization. Promising it as transparent, meaning it just works from an identifier, is promising something unsafe.
2. **Do not build content-defined chunking for a one-shot upload service.**
   - Worked example of why it does not pay here: content-defined chunking's benefit is reusing unchanged content across *repeated* uploads of similar files. A service where each file is uploaded once has nothing to reuse, so the rolling-hash CPU, the chunk index, and the privacy complexity buy nothing at all.
   - It is the right technique for backup and synchronization workloads, which the option table says, and that is a different product.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Content-defined chunking | Choosing part boundaries from the data itself, typically via a rolling hash. | Survives content shifts; pointless for one-shot uploads. |
| Rolling hash | A hash over a sliding window, recomputed cheaply as the window moves. | The mechanism behind content-defined boundaries. |
| Boundary shift | Fixed-size parts all changing when content is inserted near the start. | The problem content-defined chunking solves. |
| Byte proxying | Routing file content through the API fleet. | Only when policy requires inline inspection. |
| Immutable private version | A published-but-invisible object version awaiting checks. | Separates completion from visibility. |
| Logical pointer | A key readers resolve, updated to point at a new version. | Moved only after verification passes. |
| Publication precondition | A condition the pointer update must satisfy to take effect. | Keeps two uploads from silently overwriting. |
| Cross-tenant deduplication | Storing identical content once across tenants. | Leaks whether another tenant holds a file, via timing. |
| Timing side channel | Inferring hidden information from how long an operation takes. | How deduplication reveals another tenant's content. |
| Reference count | A tally of how many objects point at a shared chunk. | Must be updated atomically or chunks are deleted while referenced. |
| Tenant index | A secondary arrangement supporting per-tenant queries after sharding by upload. | Quota checks need it; the shard key does not serve them. |

A self-assessment grid. The middle column is a checklist; the fourth column is what actually distinguishes a stronger answer.

**Why the fourth column is the one to score**

  - Separating signal: "a number changes a decision".
  - Worked example of passing it: 8 mebibytes is chosen because it bounds waste below 1% of the object while keeping the part count in the low thousands, and both halves of that sentence are arithmetic.   - Must land: immutable part identity, the frozen manifest, and conditional completion.

  - Worked example: the provider assembled the object and the database never recorded it.   - Must land: the failure table, cleanup, and observability.
  - Adds: rollout compatibility, cost controls, and cell blast radius.
  - Separating signal: volunteering degradation and rollout before being asked.

- **Row: Wrap.**
  - Must land: the recap and the central tradeoff.
  - Adds: naming the weakest assumption first.
  - Separating signal: finding the flaw before the interviewer does.

## Interview pushback and validation

Seven challenges, each with a baseline and a stretch answer, then eight things to test.

---

> - Q1: Is the multipart ETag the whole-file hash?
>   - **IC3 baseline**
>     - No universal rule permits that assumption.
>   - **IC4 stretch**
>     - Distinguish provider identity, transport checksum, and application end-to-end digest.

**What is really being asked**
The most common misconception in this topic, asked directly.

**The baseline answer, expanded**
No, and the phrasing is careful: "no universal rule permits that assumption".

- Worked example of what a multipart ETag often is: a digest computed over the concatenated digests of the parts, with the part count appended. That is derived from the parts, not from the file's bytes in order.
- Worked example of the consequence: a client computes the file's SHA-256 locally, compares it to the returned ETag, finds no match, and reports data corruption. Nothing is corrupt; the two values were never comparable.
- "no universal rule" also covers the single-part case, where an ETag may coincidentally equal a content digest. Relying on a coincidence that holds for small files and breaks for large ones produces a bug that appears only above a size threshold.

**The stretch answer, expanded**
Three different values with three different purposes, and conflating any two causes a distinct bug.

1. **Provider identity, the ETag.** Identifies a stored object for cache validation and conditional requests. Answers "is this the same object I saw before?".
2. **Transport checksum.** Detects corruption in transit for one request. Answers "did these bytes arrive as sent?".
3. **Application end-to-end digest.** Computed at the source and verified at the destination. Answers "is the stored file the file the user has?".
- Worked example of why the third is not implied by the second: every part's transport checksum can pass while the assembled object is wrong, because the parts were assembled in the wrong order or one part was from a different file. Per-hop integrity does not compose into end-to-end integrity.

---

> - Q2: A part upload finishes after completion begins.
>   - **IC3 baseline**
>     - The frozen manifest excludes later part identity changes.
>   - **IC4 stretch**
>     - Immutable storage keys plus conditional metadata publication avoid provider overwrite races.

**What is really being asked**
The late-writer race, which is unavoidable because the API cannot stop a direct-to-storage transfer.

**The baseline answer, expanded**
The manifest was frozen, so the late part cannot join the object.

- Worked example: completion freezes the manifest at 14:05:00. A part upload that began at 14:04:58 finishes at 14:05:03. Storage holds the object. The client calls the API to record it, and the call is rejected because the session is no longer `UPLOADING`. The bytes exist and nothing references them.
- The structural point: the service does not try to prevent the transfer, because it cannot. It controls the only thing it owns, which is whether the part is ever referenced.

**The stretch answer, expanded**
There is a second race underneath, at the storage level.

- Worked example: if parts were written to shared keys, the late upload would overwrite `parts/42` while the finalizer was reading it to assemble the object. The finalizer might read a blend of two uploads.
- Immutable attempt-specific keys make that impossible: the late upload writes its own key and cannot touch the one the manifest references.
- So there are two mechanisms for two levels. The frozen manifest handles the metadata race, and immutable keys handle the byte-level race.

---

> - Q3: The provider completed the object but our process crashed.
>   - **IC3 baseline**
>     - Reconcile the object or version before attempting another commit.
>   - **IC4 stretch**
>     - Private immutable staging makes this safe even with concurrent logical-key replacements.

**What is really being asked**
The crash-between-commits case, and whether you know the naive recovery is wrong.

**The baseline answer, expanded**
Look at the destination before re-attempting anything.

- Worked example of the wrong recovery: ask the provider to list the upload's parts. It reports no such upload. Conclude the commit failed and retry. The retry also fails, because the upload was consumed by the successful commit. Now conclude the whole upload failed and start over, re-transferring 10 gibibytes over an object that already exists and is correct.
- The right recovery: check whether the destination holds an object bearing this attempt's operation identity. If it does, the commit succeeded and only the database needs updating.
- The general lesson: absence from a listing is not evidence of failure when success also removes the entry.

**The stretch answer, expanded**
The situation is harder when another upload may be replacing the same logical key concurrently.

- Worked example: upload A crashed after committing. Upload B, for the same key, completed and published version 14. A's recovery looks at the key, sees version 14, and cannot tell whether that is its own object or B's.
- Private immutable staging resolves it: each completion attempt assembles into its own uniquely-named object. A's recovery looks for *its* object by its own operation identity, which B cannot have produced. Then the metadata transaction decides which becomes the published version, and the loser stays unreferenced.

---

> - Q4: The interviewer now asks for continuous append to the same object.
>   - **IC3 baseline**
>     - Immutable multipart completion is no longer the right API contract.
>   - **IC4 stretch**
>     - Use a versioned segment manifest or append log with explicit reader consistency.

**What is really being asked**
A requirement change that invalidates the design. Will you adapt the design, or say it is the wrong design?

**The baseline answer, expanded**
Say the contract no longer fits.

- Worked example of why: this design's entire correctness argument rests on an object being assembled once from a frozen manifest and never changing. Continuous append means the object grows over time, so there is no completion moment, no frozen manifest, and no single verified digest.
- Trying to stretch multipart to cover it produces something incoherent: repeated completions each producing a new object that includes everything before it, with the previous one deleted, which is expensive and racy.

**The stretch answer, expanded**
Name the right shape instead.

- **A versioned segment manifest.** Worked example: the object is a manifest of segments, and appending adds a segment and publishes a new manifest version. A reader resolves a manifest version and sees a consistent set.
- **Or an append log with explicit reader consistency.** Readers read up to a published boundary, which is exactly the durable-prefix idea from the logging design.
- "explicit reader consistency" is the requirement either way: a reader must know what it is allowed to see while a writer is appending, and without that rule a reader can observe a half-written segment.

---

> - Q5: Can completion validate a SHA-256 from only independent part SHA-256 values?
>   - **IC3 baseline**
>     - Not the standard hash of the complete file.
>   - **IC4 stretch**
>     - Negotiate a Merkle-tree contract or stream the full ordered bytes through verification.

**What is really being asked**
Whether you can distinguish two integrity contracts that produce different numbers from the same data.

**The baseline answer, expanded**
No. The standard file hash cannot be derived from independent part hashes.

- Worked example: SHA-256 of the file is computed over all 10,737,418,240 bytes in one continuous pass, where each block's processing depends on the state left by the previous one. Independent part hashes each started from the initial state, so the information needed to chain them is gone.
- Worked example of what can be computed: a hash of the 1,280 part digests concatenated. That is a perfectly good value, and it is not SHA-256 of the file.

**The stretch answer, expanded**
Two ways forward, and they are genuinely different contracts.

1. **Negotiate a Merkle-tree contract.**
   - The integrity value is a root computed from part hashes. Worked example of what it buys beyond a file hash: a single part can be verified independently against the tree, which SHA-256 cannot do, because verifying it requires the whole file.
   - The condition: it must be named as a Merkle root, not presented as the file's hash.
2. **Stream the full ordered bytes through verification.**
   - Read the assembled object and hash it. Worked example of the cost: 10 gibibytes read and hashed in the finalizer, which is why the requirements made the whole-file digest optional.
   - Or use an incremental computation carrying hash state across parts, where supported, which gives the true file hash without a second read.

---

> - Q6: Does a cancelled upload release space immediately?
>   - **IC3 baseline**
>     - Logical abort happens first
>     - Physical cleanup is asynchronous.
>   - **IC4 stretch**
>     - Include abandoned in-flight attempts and reconciliation failures in staging quotas.

**What is really being asked**
Whether you understand that the state change and the byte deletion are separate events.

**The baseline answer, expanded**
No. The session moves to `ABORTED` immediately, which is one atomic row update. Deleting the staged bytes happens afterwards.

- Worked example: a user cancels a 10-gibibyte upload with 800 parts staged. The session is aborted in milliseconds. Deleting 800 objects takes time and can partially fail, so it runs as retried background work.
- The user-visible consequence worth stating: the quota may not free up instantly, and a user who cancels to make room may have to wait.

**The stretch answer, expanded**
The quota must count more than the obvious.

- **Abandoned in-flight attempts.** Worked example: the attempt-specific staging keys from losing concurrent uploads. Those bytes are real and unreferenced, and if the quota counted only referenced parts, a client could consume unlimited storage by repeatedly uploading conflicting parts.
- **Reconciliation failures.** Worked example: objects whose ownership could not be determined, held pending investigation rather than deleted. They occupy space, and excluding them from the quota means the accounting understates real usage.
- The principle: a quota must count every byte the tenant caused to exist, not only the bytes currently referenced by a valid session.

---

> - Q7 (premise reversal): Why not proxy all bytes through the API and skip provider reconciliation?
>   - **IC3 baseline**
>     - The API fleet becomes the bandwidth bottleneck and every deploy interrupts transfers.
>   - **IC4 stretch**
>     - Proxy only when inline inspection is mandatory, and then shard the proxy tier per tenant with its own capacity model.

**What is really being asked**
The premise reversal, and a strong one. The reconciliation problem, the grants, and the two-system complexity all exist because bytes bypass the API. Proxying would remove all of it.

**The baseline answer, expanded**
Two costs, and the second is the one people miss.

1. **The API fleet becomes the bandwidth bottleneck.**
   - Worked example: 1,000 concurrent uploads at 100 mebibytes per second each is 100 gibibytes per second through the API fleet. That is a completely different machine, network, and capacity model from a fleet handling small metadata requests, and it must be provisioned for peak upload bandwidth rather than for request rate.
2. **Every deploy interrupts transfers.**
   - The sharper cost. Worked example: an API instance restarts during a routine deploy, and every upload streaming through it dies mid-transfer. With 102-second uploads and a rolling deploy taking minutes, a substantial fraction of in-flight uploads fail every time you ship.
   - With direct-to-storage, the entire API fleet can restart and clients holding grants keep uploading, which the failure table states.

**The stretch answer, expanded**
Concede the case where proxying is right, and name what it then requires.

- **When inline inspection is mandatory**, such as a regulatory requirement to scan content before it is stored at all, the bytes must pass through something that inspects them. Direct-to-storage cannot satisfy that.
- **Then shard the proxy tier per tenant with its own capacity model.** Worked example: one tenant's 100-gibibyte-per-second burst would otherwise consume the shared proxy tier and stall every other tenant's uploads. Per-tenant sharding contains it, and the capacity model is bandwidth-based rather than request-based.
- The closing framing: the choice is decided by whether inspection must happen before storage. If it can happen after, the stronger-publication pattern gives you scanning without a byte proxy, which is the better answer for almost every case.

---

> - Validation scenarios
>   - Lost part response with identical retry.
>   - Conflicting bytes for the same part number.
>   - Completion versus abort race.
>   - File changed before resume.
>   - Crash after provider commit but before database update.
>   - Expired access token during upload.
>   - Multi-page part listing.
>   - Cleanup racing with a late storage write.

**What this says in plain words**
Eight tests, each mapping to a mechanism discussed earlier.

1. **Lost part response with identical retry.** Assert the retry returns the prior result and no duplicate part exists.
2. **Conflicting bytes for the same part number.** Assert the second upload receives a conflict and its staging bytes are cleaned up.
3. **Completion versus abort race.** Fire both simultaneously and assert exactly one wins, with the loser receiving a conflict.
4. **File changed before resume.** Change the local file, resume, and assert the session is rejected rather than producing a splice.
5. **Crash after provider commit but before database update.** The hardest test. Assert recovery finds the committed object by its operation identity rather than concluding failure from an empty part listing.
6. **Expired access token during upload.** Assert the affected part uploads fail, the session and its recorded parts survive, and a new grant lets the upload continue.
7. **Multi-page part listing.** With more than one page of parts, assert the resume reads every page and does not re-upload parts it already has.
8. **Cleanup racing with a late storage write.** Assert cleanup does not delete bytes that a completing session references, and does delete a late writer's unreferenced bytes.

**Why it matters**
Each item names a mechanism that could be wrong and the observation that would reveal it. Five of the eight reproduce failures described earlier in the file.

| Term | Plain meaning | Why it appears here |
|---|---|---|
| ETag | An opaque provider identifier for a stored object or part. | Answers "same object?", never "same bytes as my file?". |
| Transport checksum | A per-request integrity check for bytes in transit. | Per-hop integrity, which does not compose into end-to-end. |
| End-to-end digest | A hash computed at the source and verified at the destination. | The only value that proves the stored file matches the user's. |
| Frozen manifest | The ordered part list, fixed when completion begins. | Handles the metadata-level late-writer race. |
| Immutable storage key | A unique key per upload attempt of a part. | Handles the byte-level race the manifest cannot. |
| Operation identity | A unique identifier for one completion attempt, carried onto its object. | How recovery recognizes its own committed object. |
| Listing absence | The provider no longer reporting an upload. | Consistent with success and failure, so it proves nothing. |
| Private immutable staging | Each completion attempt assembling into its own uniquely-named object. | Makes recovery safe even with concurrent publications to the same key. |

| Reader consistency | The rule saying what a reader may see while a writer is appending. | Required by any append design. |
| Merkle root | A digest built by hashing parts and then hashing those hashes in a tree. | Allows single-part verification; is not a file hash. |
| Incremental hash computation | Carrying hash state across parts to produce the true file digest without a second read. | The supported shortcut, where available. |

## Recall card

Four one-liners and a four-sentence closing script, memorized rather than improvised.

---

> - “Chunk and checksum make retries small and observable.”

**What this says in plain words**
Two mechanisms with two benefits: chunking makes a failure cheap, and checksums make it visible.

**Why it matters**
"observable" is the word doing unexpected work.

- Worked example of small: a failure costs 8 mebibytes rather than 10 gibibytes.
- Worked example of observable: without per-part checksums, a corrupted part is discovered only when someone opens the finished file, if ever. With them, corruption is caught at the part that carries it, before anything is assembled, and it is attributable to a specific transfer.
- Retries being cheap is the obvious benefit. Failures being attributable is the operational one.

---

> - “Resume requires both stable file identity and current authorization.”

**What this says in plain words**
Two conditions, and "both" is the load-bearing word.

**Why it matters**
Each condition closes a different failure, and having one without the other is not partial safety.

- Worked example of identity without authorization: the correct file resumed by a user whose access was revoked yesterday. The upload is technically coherent and should not have been permitted.
- Worked example of authorization without identity: a properly authorized user resuming against a file they have since replaced. Every part checksum passes and the object is a splice of two files.
- The single word most often missing from an answer here is "both", and it is the difference between a resume that works and one that quietly corrupts.

---

> - “Freeze the manifest, verify integrity, then publish one immutable version.”

**What this says in plain words**
Three steps in a fixed order, and the order is the content.

**Why it matters**
Each step depends on the previous one having completed.

- **Freeze first** so verification has a fixed list to check. Worked example of verifying before freezing: parts could be added between the check and the assembly, so what was verified is not what was published.
- **Verify second** so publication is of something known good.
- **Publish one immutable version third**, so what readers see is exactly what was verified and cannot change afterwards.
- Any reordering breaks the chain: the thing verified must be the thing published, and that is only guaranteed if the list was fixed before the check and immutable after it.

---

> - “Completion and cleanup are recoverable state machines across database and storage boundaries.”

**What this says in plain words**
Both completion and cleanup span two systems, and both are designed so an interrupted run can be resumed rather than leaving an unknown state.

**Why it matters**
It names the actual difficulty of the whole question.

- Worked example for completion: the provider assembled the object and the database never recorded it. Recovery finds the object by its operation identity and finishes the transition.
- Worked example for cleanup: 400 of 800 staged objects were deleted before the worker died. Restarting deletes the remaining 400, because the work is idempotent and the state says what remains.
- "recoverable" is the property to claim, and it is stronger than "reliable": it means every interruption has a defined resolution rather than a low probability of occurring.

---

> - Wrap-up script
>   - “The design is fixed-size parts with immutable identities, a persisted session, and a frozen manifest.”

**What this says in plain words**
Sentence one: three structural choices, each named by the property that matters.

**Why it matters**
"immutable identities" is the phrase to get right. Fixed-size parts alone is the common answer; parts whose number is permanently bound to specific bytes is what makes retries free and conflicts detectable.

---

> -   - “Completion is one conditional transition, so abort and complete cannot both win.”

**What this says in plain words**
Sentence two: the correctness property, with its mechanism and its consequence.

**Why it matters**
"one" and "conditional" are both required.

- Worked example of not-one: two writes deciding completion, so their interleaving determines the outcome.
- Worked example of not-conditional: an unconditional write succeeds regardless of what happened in between, so an abort that already won is silently overwritten.
- Together they give the guarantee: exactly one of the two operations takes effect, decided by a rule rather than by timing.

---

> -   - “The main tradeoff is direct-to-storage upload, which removes the API bottleneck but forces reconciliation with provider semantics.”

**What this says in plain words**
Sentence three: what you chose and exactly what it costs.

- Bought: 10 gibibytes never touch the API fleet, and in-flight uploads survive a full API deploy.
- Paid: two systems hold views of the same upload, reconciled by inspection rather than by a transaction, and the service's stricter part rules must be enforced against a provider that does not share them.

**Why it matters**
The cost is named as a specific engineering obligation rather than as complexity in general. Every difficult case in the two deep dives traces back to this one tradeoff.

---

> -   - “My weakest assumption is independent part failure; I would validate retry behavior under correlated outages first.”

**What this says in plain words**
Sentence four: the flaw, and the specific first test.

**Why it matters**
The assumption is load-bearing in a way that is easy to miss.

- Worked example: independent 1% failure gives about 12.9 retries spread across the upload, which is unremarkable. A 60-second tunnel outage gives dozens of failures concentrated in one minute, during which exponential backoff means the client is mostly asleep, and the total deadline can expire while the file and the session are both perfectly fine.
- "validate retry behavior under correlated outages" is a concrete test: induce a network outage mid-upload and observe whether the client circuit-breaks and resumes, or exhausts its deadline backing off.

### Terms in this section

| Term | Plain meaning | Why it appears here |
|---|---|---|
| Observable failure | A failure attributable to a specific part and transfer. | What per-part checksums provide beyond cheap retries. |
| Stable file identity | A recorded fingerprint proving the local file is still the session's file. | One of the two resume conditions. |
| Current authorization | Permission re-checked at resume, not only at creation. | The other resume condition. |
| File splice | An object assembled from parts of two different files. | What resuming without an identity check produces. |
| Manifest freeze | Fixing the part list before verification begins. | Guarantees the verified list is the published list. |
| Immutable version | A published object version that cannot change afterwards. | What readers see, and it is exactly what was verified. |
| Conditional transition | A state change applying only if the current state matches. | Makes exactly one of abort and complete win. |
| Recoverable state machine | A process whose every interruption has a defined resolution. | Stronger than reliable; completion and cleanup both qualify. |
| Direct-to-storage upload | Bytes travelling from client to storage without passing through the API. | The main tradeoff. |
| Provider semantics | What the storage service actually guarantees. | Must be reconciled against the service's stricter rules. |
| Correlated failure | Failures sharing a cause, so they happen together. | Breaks the retry arithmetic and can exhaust the deadline. |
| Circuit break | Stopping attempts entirely after consecutive failures. | The behavior to validate under a correlated outage. |
