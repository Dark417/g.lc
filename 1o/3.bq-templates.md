# 3c. OCI Values — Plot Shapes, Flows, and Situation Playbooks (no personal stories)

> Siblings: theory + 1P3A groups → `3.bq.md` · story drafts (A/B/C) → `3.bq-bp.md` · this file = value plot shapes + situation playbooks, no personal stories.

> Use: for each value, (1) what plot shape scores, (2) what you actually do in that situation, (3) how you narrate it, (4) traps.
> Then §12 situation playbooks: disagreement with peer, disagreement with a manager who micromanages, production incident, ambiguity, customer asks for the wrong thing, priority flip, missed deadline, own mistake, "what if" hypotheticals.

## 0. Universal spine

```
Situation (2 sent.) → Stakes (1) → What I did, in order (4–6) → Result + number (1) → Cost I paid (1) → What I'd do differently (1)
```

- Cost clause: every value hides a cost. No cost = slogan. Say what you gave up
- Falsifier: for any decision, say what would have changed your mind. Turns opinion into measurement
- Order matters: "first I…, then I…" — they score sequencing (mitigate before root cause, ask before build)
- "I" for actions, "we" for outcomes
- Stop at 2 minutes. Follow-ups are where you score

## 1. Put customers first

- Best plot
  → a request arrived; you found the need behind it; you built the need, not the request; it cost you scope or time
  → platform version: your customer is the service team calling your API
- Real-life flow
  1. Ask why they want it — twice
  2. Find the pain event ("when did this last hurt you?")
  3. Propose the thing that removes the pain; show why the literal request doesn't
  4. If they insist: do the request AND fix the need, or timebox a prototype of yours to prove it
- Presentation flow
  → quote the request → what you learned → what you built instead/also → user-visible result → cost
- Traps
  → no cost → probe until found
  → overrode the customer with no evidence → arrogance
  → "customer" internal and nothing user-visible changed

## 2. Act now, iterate

- Best plot
  → gap nobody assigned; you shipped an ugly v1 in days; you measured; you shipped v2. Both halves required
- Real-life flow
  1. Classify reversibility: reversible → ship rough; one-way (schema, keys, permissions, migration) → design first
  2. Smallest thing that removes the block; days not weeks
  3. Define the one metric that says it worked
  4. Iterate on what the metric or users complained about
- Presentation flow
  → the gap → how rough v1 was, plainly → time to ship → metric → what v2 fixed → where you would NOT do this
- Traps
  → long design phase called "action"
  → v1 never improved
  → reckless with no measurement ("scientific in our approach")

## 3. Nail the basics

- Best plot
  → everyone wanted the advanced thing; a foundation was missing; a breakage proved it; you fixed the foundation under feature pressure; the advanced thing became possible
- Real-life flow
  1. Name the missing basic precisely (tests / monitoring / data model / runbook / inventory)
  2. Point at the breakage it already caused, or the one scheduled to happen
  3. Make the case in cost terms: "each patch costs X; the foundation costs Y once"
  4. Timebox it; ship the foundation; then the feature
- Presentation flow
  → what was wanted → what was missing → the breakage → the case you made and to whom → what became possible
- Traps
  → assigned work presented as judgment
  → gold-plating called fundamentals
  → waiting for complete information (value explicitly rejects this)

## 4. Expect and embrace change

- Best plot
  → priority flipped mid-work; it stung; you understood why; you wrote the handoff; you shipped on the new thing fast
- Real-life flow
  1. Ask why — understand the business reason (situational awareness)
  2. Protect the old work: handoff doc, state of PRs, what's left, risks
  3. Ramp on the new thing with a first deliverable in days
  4. If you disagree with the flip → §10 flow, then commit
- Presentation flow
  → the change and who decided → honest first reaction (brief) → why it was right → the handoff artifact → time to first delivery
- Traps
  → framed as interruption / management churn
  → quietly kept working the old plan
  → total passivity — adapting without understanding why

## 5. Innovate together

- Best plot
  → someone knew what you didn't; their idea replaced yours; you say you were wrong first; result wouldn't exist alone
- Real-life flow
  1. Identify who has the context you lack (data owners, on-call, downstream consumers)
  2. Ask before designing; write the doc with an "open questions" section
  3. Make disagreement cheap: "tell me where this breaks"
  4. Credit by name in the doc/PR
- Presentation flow
  → what you didn't know → who knew → the specific idea adopted over yours → the result
- Traps
  → every good idea turns out to be yours (the #1 failure)
  → listing meetings as collaboration

## 6. Take risks, remain calm

- Two sub-plots; interviewer may probe either
  → risk: safe option rejected; downside sized; bet reversible; result
  → incident: alert → diagnose before touching → mitigate → root cause → guardrail
- Real-life flow (risk)
  1. Name worst case and its cost
  2. Bound it: flag, canary, rollback path, timebox
  3. Take it; watch the metric; call it early if wrong
- Real-life flow (incident) — see §12.3
- Presentation flow
  → the bet or the alert → first move and why → order of actions → numbers (detect, mitigate, blast radius) → guardrail
- Traps
  → heroics with no assessment
  → "risk" with no downside
  → naming a person as root cause

## 7. Own without ego

- Best plot
  → your mistake; you found it or raised it before others; told your lead first; contained in the first hour; structural fix outlived you
  → alt plot: problem outside your lane; you fixed it or found the owner
- Real-life flow
  1. Raise it the moment you know — before fixing, one message: what, impact, what you're doing next
  2. Contain (rollback / disable / stop the writer)
  3. Fix
  4. Add the guardrail that makes the class impossible; write the short postmortem yourself
- Presentation flow
  → the mistake in one sentence, no hedge → who you told and when → first-hour actions → structural change
- Traps
  → mistake that was really someone else's
  → fake mistake ("cared too much")
  → confession with no structural change

## 8. Earn trust, give trust

- Best plot
  → real disagreement; other side steelmanned; you brought evidence; you named your falsifier; resolution; relationship intact
  → bonus plot: you delegated and didn't hover
- Real-life flow — see §12.1 / §12.2
- Presentation flow
  → their position at its strongest → your position → the evidence → "what would have changed my mind" → resolution → afterwards
- Traps
  → won by seniority
  → other side had no reasonable case
  → resolution faded rather than settled
  → confusing with §10: this is HOW you disagree; §10 is what you do AFTER losing

## 9. Take pride in your work

- Best plot
  → a corner you could have cut unnoticed; you didn't; because of a concrete future failure; it cost time; the thing is still maintained/reused
- Real-life flow
  1. Ask: is this one-way? (permissions, audit, migrations, keys, public API) → do it properly
  2. If reversible → ship rough (§2) — pride is knowing which is which
  3. Make it legible: README, dashboard, runbook — pride includes communication
- Presentation flow
  → the corner → why not (future failure) → cost → evidence the standard held
- Traps
  → perfectionism with no delivery (collides with §2)
  → pride with no standard behind it

## 10. Challenge ideas, champion execution

- Best plot (strongest if you lost)
  → decision you disagreed with; you asked why with rigor (prototype/measurement/analysis); you lost; you delivered it properly; you documented your doubt as a risk + metric; you say honestly how it turned out
- Real-life flow
  1. Challenge in writing, with evidence, before the decision freezes
  2. State your falsifier
  3. Once decided: full effort, no sandbagging, no "told you so"
  4. Register residual risk with a metric and a revisit trigger
- Presentation flow
  → the decision → the question you asked → the rigor → outcome (lost) → what you built → the metric you watched → how it turned out
- Traps
  → challenged then disengaged
  → never challenged
  → kept relitigating after the decision

## 11. Cross-value tensions they set up on purpose

| They pit | Resolution axis |
|---|---|
| Act now (§2) vs Take pride (§9) | reversibility: rough for reversible, proper for one-way |
| Challenge ideas (§10) vs Embrace change (§4) | challenge before the decision; commit after |
| Own without ego (§7) vs Earn trust (§8) | own your part fully; never assign blame for others' parts |
| Customers first (§1) vs Nail the basics (§3) | the basic you fix is the one that hurts customers next |
| Take risks (§6) vs Nail the basics (§3) | risk on top of a foundation, not instead of one |

## 12. Situation playbooks

### 12.1 Disagreement with a peer (Earn trust)

- Do
  1. 1:1 first, not in the meeting — "help me understand what you're optimizing for"
  2. Steelman their case back to them until they say "yes, that's it"
  3. Convert to a criterion: latency? cost? blast radius? time-to-ship? — agree on the yardstick before arguing the answer
  4. Bring evidence: benchmark, prototype, incident, cost number. Timebox it (a day, not a week)
  5. State your falsifier out loud: "if X shows Y, I'll drop this"
  6. If still split → ask a third party for a **tiebreak on the criterion**, not for a ruling on who's right
  7. Commit fully to whatever wins; keep the relationship
- Say
  → "I said up front what would change my mind, so it became a measurement instead of an opinion."
- Never
  → escalate first; win by seniority; describe the other side as simply wrong

### 12.2 Disagreement with your manager — who also micromanages (Earn trust / Challenge ideas)

- Reframe first: micromanagement = a trust deficit with a cause. Your job is to shrink the feedback loop until the checking becomes unnecessary
- Do — the design disagreement
  1. Ask what worry drives their preference (risk? timeline? a past incident? optics upward?). Name it back to them
  2. Present **alternatives on the same page**: their option, your option, a hybrid — each with the same 4 columns: risk, cost, time, reversibility. Recommend one; don't hide the recommendation
  3. Offer a **cheap test** that decides it: prototype, canary, dry-run, a metric for a week. "Let's let the data pick"
  4. If they still choose theirs: commit fully, and register your concern as a **written risk with a trigger** ("if error rate > X by week 2, we revisit"). That's how you keep your position without sabotage
  5. If it's one-way and you believe it's genuinely wrong (security, data loss): say so once, in writing, with the specific failure; then commit. You've done your duty; you're not the last line of defense
- Do — the micromanagement itself
  1. Over-communicate proactively: short daily/2-day written updates, demo small increments — remove the reason to check
  2. Ask for the criteria of "done" and the checkpoints they want up front; then hit them
  3. Ask for one scoped area of autonomy; deliver it; expand
  4. Never diagnose them ("you micromanage") — in the interview, describe behaviors: "frequent check-ins on implementation details"
- Say
  → "I laid both options side by side on the same criteria, recommended mine, and proposed a one-week canary to decide. They chose theirs; I built it properly and put a metric on the risk I was worried about."
  → "I shortened the loop myself — written updates every two days and small demos — and the check-ins tapered off."
- Never
  → describe the manager negatively; imply you were right all along; say you complied silently while disagreeing

### 12.3 Production incident (Take risks, remain calm / Own without ego)

- Do — in this order, and narrate the order
  1. Acknowledge the alert; state blast radius in one line (who, how many, since when)
  2. **Look before touching**: dashboards, recent deploys, dependency health. Don't restart the noisy service — it destroys evidence and may not be the cause
  3. Mitigate first: rollback / feature flag off / failover / rate limit. Restore service before understanding it fully
  4. Communicate: who is affected, what you did, ETA for next update. Update on a cadence even if "no change"
  5. Root cause after service is stable; disprove hypotheses, don't just confirm one
  6. Blameless postmortem; guardrail: alert, test, validation, runbook step — a mechanism, not "be more careful"
- Say
  → "Mitigation took N minutes; root cause took N hours. Those are different jobs and I did them in that order."
- Never
  → root cause before mitigation; name a person; "learned to be more careful"

### 12.4 Ambiguous requirement / unfamiliar problem (Act now / Nail the basics)

- Do
  1. Write down known / unknown / assumed
  2. Ask the smallest set of questions that changes the design (not all questions)
  3. Reduce uncertainty cheaply: existing data, a similar system, a timeboxed spike
  4. Act on stated assumptions with reversible steps; put the assumptions in the doc; set a checkpoint to validate
  5. When an assumption breaks, say so and adjust — cheap because the step was reversible
- Say
  → "I didn't wait for full information; I listed my assumptions, took a reversible first step, and set a checkpoint to test them."
- In a coding round, this is the same flow: restate, example, brute force, optimize

### 12.5 Customer asks for the wrong thing (Put customers first)

- Do
  1. Ask for the pain event behind the ask
  2. Show, concretely, why the literal ask doesn't remove the pain (an example case)
  3. Offer the alternative that does; keep their ask on the table
  4. If they insist: do both if cheap; else timebox a prototype of yours; let the result decide
- Say
  → "They asked for X. The thing that actually hurt was Y. I built the Y fix first and shipped X with it."

### 12.6 Priority flip (Expect and embrace change)

- Do: ask why → handoff doc same week → first deliverable on the new thing within days → if you disagree, §10 then commit
- Say: "It stung for a day. Then I wrote the handoff so nobody had to reverse-engineer my work and had something running on the new priority inside two weeks."

### 12.7 Missed or tight deadline (Prioritization)

- Do
  1. Warn the moment risk appears — not on the day
  2. Offer options: cut scope (keep the core), phase delivery, add owner, move date — with your recommendation
  3. Say what gets dropped and where it goes (it doesn't vanish)
  4. Deliver the core; postmortem the estimate
- Say: "I flagged it two weeks early with three options and recommended cutting scope to the two features that mattered for the launch."
- Never: heroics as the answer; surprise on deadline day

### 12.8 Your own mistake (Own without ego)

- Do: one message to lead immediately (what / impact / next) → contain → fix → guardrail → write the postmortem yourself
- Say: "I told my lead before I started fixing it, because a quiet fix would have meant nobody else learned anything."

### 12.9 "What if…" hypotheticals

- Answer with a real story anyway: "Something close to that happened — …" then the flow
- If nothing close: give the flow from the matching playbook above, in first person, in order; they're grading the order

## 13. Phrase bank

- "Help me understand what you're optimizing for."
- "Let's agree on the yardstick before we argue the answer."
- "Here's what would change my mind."
- "Can we let a one-week canary decide?"
- "I'll build it properly; I'd like to register the risk with a metric so we find out early if I was right."
- "Mitigate first, understand second."
- "The guardrail is a mechanism, not a reminder."
- "A rough test tool is a Tuesday. A rough permission model is a breach."
- "I didn't measure that; the signal was that the tickets stopped."
- "What I'd do differently is…"
