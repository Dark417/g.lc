# AI Engineering — World Map

**What this is.** The market blueprint. Every distinct role in the AI ecosystem as of 2026-08, described at full scope (not per-level), the concrete work each one performs, the capability each one demands, and the route from "backend engineer with AI fluency" to **AI Tech Lead / Architect** — the person who designs the system and leads a team to ship it.

**Two tiers.**

- **Tier 1 — Rows.** The roles. Who they are, what they own, what a real JD says, what capability is Core vs Strong-plus vs Not required.
- **Tier 2 — Their jobs.** The recurring units of work each row actually performs. Consolidated into an ownership matrix in §5.

**Convention.** Comp and headcount figures are `order of magnitude:` unless cited. Ecosystem facts anchor to mid-2026 and rot fast. Levels are deliberately ignored — a row describes the _domain of work_, not a rung.

---

## 1. The five axes that actually separate these roles

Every AI job title is a point in this space. Read a JD by locating it here, not by the title.

| Axis                  | Question                                    | Consequence                                                                              |
| --------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Model ownership**   | Do you change the weights?                  | No → engineering role. Yes → science/post-training role, needs ML depth.                 |
| **Data ownership**    | Do you own the corpus/labels/feedback loop? | Owning data = owning quality. Roles without it are downstream of someone else's ceiling. |
| **Runtime ownership** | Do you own the request path in production?  | Yes → on-call, SLOs, cost. This is where backend engineers win.                          |
| **Product ownership** | Do you decide what the system should do?    | Yes → ambiguity, stakeholders, eval definition. This is the lead/architect axis.         |
| **Abstraction level** | App code, platform, or silicon?             | App → frameworks. Platform → distributed systems. Silicon → CUDA/kernels.                |

**Consequence for you:** your leverage is _runtime + data + product_, not _model_. Every row below where model ownership is "No" is a row you can compete in today. Rows where it's "Yes" require a different 2-year investment.

### R1 · Applied AI Engineer / GenAI Product Engineer

**Aliases:** AI Engineer · GenAI Engineer · LLM Application Engineer · Software Engineer, AI Products · AI Solutions Engineer (product side).

**Definition.** A backend/full-stack engineer who ships user-facing features whose behavior is produced by a model. Owns everything around the model; owns none of the model.

**Owns:** the request path, prompt/context assembly, retrieval, tool integrations, output validation, latency and cost SLOs, the feature's eval set.
**Does not own:** weights, training, GPU serving, corpus creation (usually shared with R4).

**Charter & deliverables.** A shipped feature with: a design doc, an eval suite with a pass threshold, a cost-per-request number, a traced runtime, and a rollback story for prompt/model changes.

**Tier 2 — recurring jobs**

1. Translate a fuzzy product ask into a testable spec ("summarize contracts" → what counts as correct?).
2. Choose the archetype: extraction vs RAG vs workflow vs agent — and justify rejecting the fancier one.
3. Build the context assembly layer (budget, ordering, provenance separation).
4. Build/tune retrieval; diagnose whether a bad answer is a retrieval or a generation failure.
5. Design tool schemas and wire them to existing backend services with correct authorization.
6. Enforce structured output and validate against a system of record.
7. Build the golden eval set from real traffic; wire a regression gate into CI.
8. Instrument tracing; define quality SLIs alongside latency SLOs.
9. Drive cost down: caching, context reduction, model routing.
10. Handle the long tail: refusals, partial failures, human escalation paths.
11. Ship prompt/model version changes as deploys with eval gates.
12. On-call for the feature.

**Capabilities**

- _Core:_ strong backend (API, async, queues, DB) · retrieval mechanics (chunking, hybrid, rerank) · agent loop and termination · structured output · eval design · prompt/context engineering · tracing · cost/latency reasoning · one framework deeply (LangGraph / OpenAI Agents SDK / ADK / PydanticAI).
- _Strong-plus:_ vector index internals (HNSW/IVF params) · prompt injection defence · streaming UX · a frontend enough to build the demo · SQL and data modeling.
- _Not required:_ training, GPU kernels, distributed training, research math.

**Distilled JD**

> Build and ship LLM-powered product features end to end. Design retrieval and prompting strategies, integrate tools and internal APIs, define evaluation criteria and measure quality, optimize latency and token cost, and own these services in production. 3+ yrs backend engineering; experience with RAG and agent frameworks; strong systems fundamentals. ML research experience not required.

**Loop shape.** SWE coding round (still LeetCode-shaped) → AI system design (RAG/agent + eval + cost) → backend/system design → behavioral. Sometimes a take-home.

**Adjacency.** ← from backend SWE (your path). → to R2, R3, R21.

**Who hires.** Everyone. Banks, insurers, SaaS, healthcare, retail, consultancies, plus every AI startup's product team. Highest req volume of any row on this map.

### R2 · Agent Engineer / Agentic Systems Engineer

**Aliases:** Agent Engineer · Applied AI Engineer (Agents) · Autonomy Engineer · AI Workflow Engineer.

**Definition.** R1 specialized on the hard part: systems where the model decides the control flow. The job is making a nondeterministic loop reliable enough to trust with side effects.

**Owns:** the loop, tool surface (ACI), state/checkpointing, termination and budget policy, trajectory evaluation, human-in-the-loop gates, failure recovery.
**Does not own:** the model, the corpus.

**Charter & deliverables.** An agent that completes a class of tasks at a stated success rate, with a bounded worst-case cost, a resumable state model, an approval gate on irreversible actions, and a trajectory eval suite.

**Tier 2 — recurring jobs**

1. Decide agent vs workflow, per subtask, and defend the boundary.
2. Design the tool surface: granularity, schemas, error strings the model can act on, idempotency.
3. Implement the loop: step cap, budget cap, wall-clock cap, no-progress detection.
4. Build state: checkpoint at node boundaries, resume, replay for debugging.
5. Design context strategy for long horizons: compaction, offloading to files, subagent isolation.
6. Build trajectory eval — was the path sane, not just the answer plausible.
7. Design the human approval surface (what needs review, what it shows, latency of the gate).
8. Contain blast radius: sandboxing, egress control, identity propagation, reversibility.
9. Diagnose compounding-error failures across long runs.
10. Cost-engineer runs that fan out (subagents multiply tokens).

**Capabilities**

- _Core:_ everything in R1 Core · state machines / durable execution · tool schema design · trajectory eval · sandboxing · concurrency and cancellation · deep familiarity with one agent framework's internals.
- _Strong-plus:_ MCP server/client implementation · computer-use / code-execution agents · queue theory for background agent fleets · prompt-injection threat modeling.
- _Not required:_ training, RL.

**Distilled JD**

> Design and build production agents that use tools to complete multi-step tasks. Define agent architecture (planning, memory, tool interfaces, orchestration), build evaluation for agent trajectories, and make agents reliable, observable and safe under real workloads. Experience shipping an agent to production strongly preferred.

**Loop shape.** Coding → agent design deep-dive (loop, tools, failure, eval) → often a 4–48h take-home building a small agent → behavioral with safety questions.

**Adjacency.** ← from R1. → R21, or founding engineer at agent startups.

**Who hires.** Agent startups, AI-native product companies, enterprise automation teams, coding-agent teams, ops-automation groups.

**Honest note.** This row screens hardest on _shipped in production_. A prototype is a story; an agent that survived a month of real traffic is the credential.

### R3 · AI Platform / LLMOps Engineer

**Aliases:** AI Platform Engineer · LLMOps · MLOps (GenAI) · AI Infrastructure Engineer (app layer) · Foundation Model Platform Engineer.

**Definition.** Builds the internal product that other AI teams build on: one door to models, with routing, caching, quota, tracing, eval infrastructure and spend attribution. The most _classically backend_ role on this map.

**Owns:** gateway, model routing and fallback, caches, rate limits and quotas, tenant isolation, trace/eval pipelines, prompt registry, cost ledger, self-hosted inference (sometimes).
**Does not own:** product prompts, product evals, model weights.

**Charter & deliverables.** A gateway with an SLO, a tracing pipeline every team uses, an eval service, per-team spend reporting, and a paved road that makes the safe thing the easy thing.

**Tier 2 — recurring jobs**

1. Build/operate the LLM gateway: auth, quota, routing, fallback chains, timeouts, retries, streaming passthrough.
2. Implement caching: exact-prefix prompt cache, semantic cache (carefully), response cache with invalidation.
3. Enforce multi-tenancy: budgets, noisy-neighbour isolation, per-tenant rate limits.
4. Build the trace pipeline: span schema, sampling, PII redaction, retention.
5. Build eval infrastructure teams plug into (dataset store, judge runners, CI gates).
6. Run a prompt/model registry with versioning, pinning and staged rollout.
7. Token accounting and chargeback; publish unit economics.
8. Evaluate/self-host inference (vLLM etc.) when unit cost or data residency demands it.
9. Capacity planning against provider rate limits; backpressure design.
10. Security review of tools/MCP servers before they reach the paved road.
11. On-call for the platform.

**Capabilities**

- _Core:_ distributed systems · API gateway patterns · streaming (SSE/websockets) at scale · caching and invalidation · rate limiting and quota accounting · observability (OTel) · IaC · multi-tenancy · cost engineering.
- _Strong-plus:_ vLLM/TensorRT operations · Kubernetes/GPU scheduling · eval methodology · policy engines (OPA) for tool authz.
- _Not required:_ modeling, research, prompt craft.

**Distilled JD**

> Build the platform that powers AI applications across the company: model gateway and routing, prompt and evaluation infrastructure, observability, guardrails, and cost controls. Partner with product teams to make LLM usage safe, observable and economical. Strong distributed systems background required; LLM experience valued but ML research not required.

**Loop shape.** Classical distributed systems design + coding + one AI-flavored round. The least AI-theory of any row here.

**Adjacency.** ← from backend/platform/SRE (your strongest direct match). → R21, or Head of AI Platform.

**Who hires.** Any org with more than one AI team: banks, big tech, large SaaS, AI infra vendors.

### R4 · AI Data Engineer

**Aliases:** Data Engineer (AI/ML) · Knowledge Engineer · RAG Data Engineer · AI Data Platform Engineer.

**Definition.** Owns the offline plane: sources → parse → chunk → embed → index, plus freshness, deletion, lineage and entitlements. The ceiling on retrieval quality is set here, not in the prompt.

**Owns:** ingestion, parsing, chunking policy, embedding jobs, index lifecycle, freshness SLOs, PII/entitlement propagation, backfills, the feedback data flywheel.
**Does not own:** the query-time retriever tuning (shared with R1/R6), the model.

**Charter & deliverables.** A pipeline with a stated freshness SLO, idempotent upserts, a re-embed runbook, tenant-scoped access, deletion compliance, and lineage from an answer back to a source document.

**Tier 2 — recurring jobs**

1. Source connectors and CDC; decide full vs incremental sync.
2. Parsing: layout-aware PDF/HTML/table extraction; deciding when OCR is required.
3. Chunking policy and its versioning; re-chunk migrations.
4. Embedding jobs: batching, throughput, cost, model version pinning.
5. Index lifecycle: upsert keys, tombstones, compaction, rebuild windows.
6. Entitlement propagation so retrieval cannot leak across tenants or clearance levels.
7. Deletion/retention compliance (GDPR right-to-erasure through a vector index).
8. Lineage and provenance so every generated claim maps to a source version.
9. Freshness monitoring and staleness alerts.
10. Feedback capture: thumbs, edits, escalations, landed into a labeled store.

**Capabilities**

- _Core:_ batch and streaming pipelines (Spark/Glue/Flink/dbt) · orchestration (Airflow/Dagster/Step Functions) · SQL and data modeling · idempotency and backfill design · storage formats (Parquet/Delta/Iceberg) · vector store operations · data governance.
- _Strong-plus:_ document parsing at scale · embedding cost optimization · graph construction for GraphRAG · entitlement modeling.
- _Not required:_ prompting depth, agent design, training.

**Distilled JD**

> Build and operate the data pipelines behind our AI products: ingest documents from many sources, parse and normalize them, generate embeddings, maintain vector and lexical indexes, and guarantee freshness, lineage and access control. Experience with large-scale ETL and cloud data platforms required.

**Loop shape.** Data pipeline design + SQL + coding + a light AI round. Very close to what you already do.

**Adjacency.** ← from data/backend engineering. → R1, R6, or Data Platform lead.

**Who hires.** Enterprises with document-heavy domains: banks, insurance, legal, healthcare, government.

### R5 · Evaluation / AI Quality Engineer

**Aliases:** AI Evaluation Engineer · LLM Quality Engineer · Model Evaluation Engineer · AI Test Engineer.

**Definition.** Turns "seems better" into a number with a threshold and a gate. Newest formalized row; the single scarcest skill in the market relative to demand.

**Owns:** eval datasets, metric definitions, judge calibration, regression gates, quality dashboards, the release criteria for prompt/model/index changes.
**Does not own:** the feature, the model.

**Charter & deliverables.** A golden set traceable to real traffic, metric definitions with known error bars, a judge validated against human labels, a CI gate that blocks regressions, and an online quality SLI.

**Tier 2 — recurring jobs**

1. Mine production traces for a representative, stratified eval set (including the tail).
2. Define per-feature metrics: retrieval recall vs groundedness vs task success — and keep them separate.
3. Build and calibrate LLM-as-judge rubrics against human labels; re-calibrate on judge model change.
4. Run human labeling operations: guidelines, inter-annotator agreement, adjudication.
5. Build trajectory eval for agents (tool choice, step efficiency, recovery).
6. Wire regression gates into CI; define the release threshold and the override policy.
7. Detect drift: input distribution, output distribution, model version changes.
8. Run A/B or interleaving experiments online; connect offline metrics to business metrics.
9. Prevent eval-set contamination and overfitting to the golden set.

**Capabilities**

- _Core:_ experimental design · statistics (sampling, confidence intervals, significance) · metric design · labeling operations · CI/CD · data analysis (SQL/pandas).
- _Strong-plus:_ IR metrics (nDCG, MRR) · annotation tooling · causal/experiment analysis · domain expertise in the product area.
- _Not required:_ training, serving.

**Distilled JD**

> Define and build how we measure AI quality: evaluation datasets, automated metrics, LLM-as-judge pipelines, human review workflows, and regression testing for model and prompt changes. Partner with engineering and product to set release criteria.

**Loop shape.** Metric design case study + statistics + coding + product judgment.

**Adjacency.** ← from QA, data science, or backend. → R1, R21. Rare as a first job; common as a _specialty inside_ R1/R2.

**Who hires.** Companies past the demo stage. If a JD mentions evals in the first three bullets, that org is more mature than most.

**Why it matters to you.** This is the highest-leverage differentiator available. Almost every candidate can describe a ReAct loop; almost none can describe judge calibration.

### R6 · Search / Retrieval (IR) Engineer

**Aliases:** Search Engineer · Relevance Engineer · Retrieval Engineer · Information Retrieval Engineer.

**Definition.** Owns query-time retrieval quality as a discipline in its own right — the pre-LLM field that RAG rediscovered. Deeper than R1's retrieval work.

**Owns:** index design, query understanding, ranking pipeline (recall → rerank → fusion), relevance metrics, A/B on ranking changes.
**Does not own:** generation.

**Tier 2 — recurring jobs**

1. Design the recall stage: lexical, dense, filters, and their fusion.
2. Query understanding: normalization, entity recognition, intent classification, rewriting.
3. Ranking: features, learning-to-rank or cross-encoder rerankers, tie-breaking, diversity.
4. Relevance judgment programs and offline metrics (nDCG@k, MRR, recall@k).
5. Latency budgeting across the ranking cascade; caching hot queries.
6. Index sharding, replication and rebuild strategy at corpus scale.
7. Online experimentation on ranking changes; guarding against metric gaming.

**Capabilities**

- _Core:_ IR fundamentals (inverted index, BM25/TF-IDF, scoring) · ANN internals · learning-to-rank basics · Elasticsearch/OpenSearch/Vespa/Lucene · evaluation with graded relevance · latency engineering.
- _Strong-plus:_ embedding model selection and fine-tuning for domain retrieval · late-interaction models (ColBERT-style) · query log mining · multilingual retrieval.
- _Not required:_ generative modeling.

**Loop shape.** IR-specific design + coding + metrics reasoning.

**Adjacency.** ← from backend + OpenSearch experience (you have the ops half). → R1 with a strong retrieval story, or R21.

**Who hires.** Search-centric products, e-commerce, enterprise search vendors, any serious RAG team.

### R7 · Forward-Deployed AI Engineer

**Aliases:** Forward Deployed Engineer (FDE) · AI Solutions Engineer · Field Engineer · Deployment Engineer · Customer Engineer (Technical).

**Definition.** Ships the vendor's AI system inside a customer's environment. Half engineer, half consultant. Extremely high volume of reqs in 2026 because enterprises can't self-serve agentic products.

**Owns:** the customer's implementation — data connections, prompts, evals tuned to their domain, integration with their systems, and the feedback loop back to the product team.

**Tier 2 — recurring jobs**

1. Scope the customer's use case and kill the ones that won't work.
2. Connect their data (the actual hard part: auth, formats, entitlements, quality).
3. Tune retrieval and prompts to their domain; build a domain eval set with their SMEs.
4. Integrate with their stack (SSO, ticketing, CRM, on-prem constraints).
5. Run pilots with success criteria; produce the evidence for a renewal.
6. Handle security review, procurement questions, and compliance artifacts.
7. Feed structured product gaps back to engineering.

**Capabilities**

- _Core:_ R1 Core, plus: rapid prototyping · communication with non-engineers · enterprise integration (SSO/SAML, VPC, on-prem) · debugging in unfamiliar environments · scoping and expectation management.
- _Strong-plus:_ pre-sales instinct · security-questionnaire literacy · patience.
- _Not required:_ research.

**Loop shape.** Coding + a customer-scenario round (they describe a messy deployment, you scope it) + communication-heavy behavioral.

**Adjacency.** ← from consulting or product engineering. → product management, solutions architecture, or back to R1/R21.

**Who hires.** AI vendors selling to enterprises — the fastest-growing headcount line in the sector.

### R8 · AI Security Engineer / AI Red Team

**Aliases:** AI Security Engineer · LLM Security · AI Red Team · Trust & Safety Engineer (technical) · Responsible AI Engineer.

**Definition.** Attacks and defends AI systems. Distinct from classical appsec because the attack surface includes natural language and the model's own reasoning.

**Owns:** threat models for AI features, injection defences, tool authorization design, sandbox architecture, red-team exercises, incident response for AI-specific failures.

**Tier 2 — recurring jobs**

1. Threat-model AI features (STRIDE adapted: injection, exfiltration, excessive agency, supply chain).
2. Red-team agents: adversarial prompts, indirect injection via retrieved content, tool abuse chains.
3. Design defence-in-depth outside the model: allowlists, identity propagation, egress control, approval gates.
4. Build input/output guardrail classifiers and measure their FP/FN cost.
5. Review third-party tools and MCP servers before adoption.
6. Sandbox design for code execution and computer-use agents.
7. Own AI-specific incident response and disclosure.
8. Map controls to OWASP LLM Top 10, NIST AI RMF, and internal policy.

**Capabilities**

- _Core:_ appsec fundamentals (authz, confused deputy, SSRF, sandbox escape) · agent architecture · adversarial thinking · policy engines · detection engineering.
- _Strong-plus:_ offensive security background · fuzzing/automated red-teaming · privacy engineering · regulatory literacy (EU AI Act).
- _Not required:_ training.

**Loop shape.** Security design + attack-the-system exercise + coding.

**Adjacency.** ← from appsec or backend with security ownership. → security architecture, R21 with a safety charter.

**Who hires.** Banks, healthcare, frontier labs, any regulated deployment. Demand outpaces supply sharply.

### R9 · Agent SRE / AI Reliability Engineer

**Aliases:** AI SRE · Agent Operations · Production Engineer (AI) · AI Systems Reliability.

**Definition.** Emerging row: SRE for systems whose failures are semantic, not just 5xx. Runs fleets of agents and the platforms under them.

**Tier 2 — recurring jobs**

1. Define SLIs that include correctness proxies, not just availability and latency.
2. Build runbooks for AI-specific incidents (bad-answer spikes, index staleness, model rollout regressions, runaway spend).
3. Capacity and quota management against provider limits; failover between providers/regions.
4. Cost anomaly detection and kill switches.
5. Rollout engineering: canaries for prompt/model changes, automatic rollback on eval SLI breach.
6. Replay and forensic tooling for nondeterministic runs.
7. Chaos/failure injection at the tool and provider boundary.

**Capabilities**

- _Core:_ SRE practice (SLO/error budget, on-call, postmortems) · observability · IaC · incident command · capacity planning.
- _Strong-plus:_ eval literacy (to define quality SLIs) · FinOps · multi-provider failover design.
- _Not required:_ modeling.

**Loop shape.** Systems design + incident scenario + coding.

**Adjacency.** ← from SRE/platform. Your Datadog/Splunk RCA and biweekly-release ownership maps directly.

**Who hires.** Companies running agents at scale; still a small number, growing fast.

### R10 · Model Risk & AI Governance Engineer

**Aliases:** Model Risk Management (MRM) · AI Governance Engineer · Responsible AI · AI Compliance Engineer · Model Validation.

**Definition.** Makes AI systems auditable and defensible to a regulator. In US banking this sits on top of the SR 11-7 model risk framework; in the EU, on the AI Act's risk tiers.

**Tier 2 — recurring jobs**

1. Maintain the model/system inventory: what models are used where, with what data, by whom.
2. Define and enforce the approval path for a new AI use case (risk tier → required controls).
3. Independent validation: does the eval evidence support the claimed performance?
4. Documentation artifacts: model cards, system cards, data lineage, DPIAs.
5. Ongoing monitoring requirements and attestation cycles.
6. Vendor/third-party model risk assessment.
7. Translate regulation into engineering controls the platform can enforce automatically.

**Capabilities**

- _Core:_ regulatory literacy (SR 11-7, EU AI Act, NIST AI RMF, sector rules) · eval methodology · data lineage · documentation discipline · stakeholder management with Risk/Legal/Audit.
- _Strong-plus:_ the engineering chops to _build_ the controls rather than write policy about them — this combination is rare and well paid.
- _Not required:_ research.

**Loop shape.** Case-based: "a business unit wants an LLM to draft client communications — walk me through approval."

**Adjacency.** ← from engineering inside a regulated firm. This is a genuine advantage of your JPMC background; most AI-native candidates cannot speak this language at all.

**Who hires.** Banks, insurers, healthcare, government, large enterprises, EU-exposed companies.

### R11 · ML Engineer (classical / production ML)

**Aliases:** Machine Learning Engineer · MLE · Applied ML Engineer · Production ML Engineer.

**Definition.** Owns models that are trained on the company's own data and serve predictions: fraud, churn, forecasting, classification, ranking. Distinct from R1 — here the weights are yours.

**Owns:** feature pipelines, training pipelines, model selection and tuning, offline/online evaluation, serving, monitoring, retraining cadence.

**Tier 2 — recurring jobs**

1. Frame the business problem as a learning problem; define the label and the horizon.
2. Build feature pipelines with train/serve consistency (the classic skew bug).
3. Train, tune and select models; manage experiments and reproducibility.
4. Offline evaluation with the right metric for the cost asymmetry (precision/recall/AUC/calibration).
5. Deploy: batch scoring, online serving, or streaming; shadow and canary.
6. Online experimentation to prove business lift.
7. Monitor drift, degradation and feedback loops; own retraining.
8. Manage the model registry and rollback.

**Capabilities**

- _Core:_ supervised learning theory (bias/variance, regularization, cross-validation, leakage) · metric selection and calibration · feature engineering · scikit-learn/XGBoost/PyTorch · feature stores · pipeline orchestration · experiment tracking (MLflow/W&B) · production serving · statistics.
- _Strong-plus:_ causal inference · time series · imbalanced-data techniques · distributed training · deep learning for the modality in question.
- _Not required (usually):_ novel research, kernel-level performance.

**Distilled JD**

> Design, train and deploy machine learning models that power [fraud detection / personalization / forecasting]. Own the full lifecycle: feature engineering, training pipelines, offline and online evaluation, deployment, monitoring and retraining. MS/PhD or equivalent experience; strong Python and ML fundamentals.

**Loop shape.** ML fundamentals round (real math), ML system design (training + serving + monitoring), coding, behavioral.

**Adjacency.** ← from data science or SWE with a 12–24 month investment. → R12, R16, R21.

**Who hires.** Every company with a prediction problem. Larger req volume than the AI-native rows but a genuinely different skill set.

**Honest note.** Do not apply here as a GenAI person. The ML-fundamentals round is not bluffable and rejection is fast.

### R12 · RecSys / Ranking Engineer

**Aliases:** Recommendation Systems Engineer · Ranking Engineer · Ads ML Engineer · Personalization Engineer.

**Definition.** R11's most demanding specialization: ranking under latency budgets at enormous scale, with a feedback loop that alters the data it trains on.

**Tier 2 — recurring jobs**

1. Design the multi-stage funnel: candidate generation → filtering → ranking → re-ranking/policy.
2. Feature engineering with strict train/serve parity and freshness tiers (batch / near-line / request-time).
3. Two-tower / embedding retrieval; ANN serving at scale.
4. Ranking models with calibration for downstream auctions or business rules.
5. Counterfactual evaluation and bias correction (position bias, exposure bias, feedback loops).
6. Online experimentation infrastructure and long-term metric guardrails.
7. Latency budget engineering across the funnel.

**Capabilities**

- _Core:_ R11 Core · IR/ranking · embedding retrieval · online experimentation · counterfactual/off-policy evaluation · very large-scale data processing · latency engineering.
- _Strong-plus:_ auction theory (ads) · sequence models for user behavior · multi-objective optimization.

**Loop shape.** ML design + ranking-specific depth + scale reasoning + coding.

**Who hires.** Big tech, e-commerce, ads, streaming, social.

### R13 · ML Systems / Training Infrastructure Engineer

**Aliases:** ML Systems Engineer · Training Infrastructure · AI Infrastructure Engineer (cluster) · Distributed Training Engineer.

**Definition.** Builds the machinery that makes large training runs possible and efficient. Doesn't design models; makes them trainable.

**Tier 2 — recurring jobs**

1. Cluster and scheduler operation (Slurm/Kubernetes), GPU allocation and preemption policy.
2. Distributed training strategies: data/tensor/pipeline/expert parallelism and their communication costs.
3. Interconnect and collective communication tuning (NCCL, topology awareness).
4. Data loading at the throughput required to keep accelerators busy.
5. Checkpointing, fault tolerance and restart for multi-day runs.
6. Profiling and utilization (MFU); finding the bottleneck between compute, memory bandwidth and network.
7. Cost/efficiency reporting for training spend.

**Capabilities**

- _Core:_ distributed systems · GPU architecture and memory hierarchy · PyTorch internals (DDP/FSDP/DeepSpeed) · networking · performance profiling · Linux/systems programming.
- _Strong-plus:_ CUDA/Triton kernels · compilers (torch.compile, XLA) · numerical precision (bf16/fp8) · storage systems.
- _Not required:_ product sense.

**Loop shape.** Systems design + performance debugging + low-level coding (often C++/CUDA-adjacent).

**Who hires.** Labs, big tech AI infra, GPU clouds, well-funded startups training their own models.

---

### R14 · Inference / Serving Performance Engineer

**Aliases:** Inference Engineer · Model Serving Engineer · Performance Engineer (AI) · GPU Serving.

**Definition.** Owns tokens-per-dollar and tail latency for model serving. The systems-heavy counterpart to R3.

**Tier 2 — recurring jobs**

1. Deploy and tune serving stacks (vLLM, SGLang, TensorRT-LLM); pick the engine per workload.
2. Batching policy: continuous batching, max batch, max wait, admission control, fairness.
3. KV cache management: memory budget, paging, prefix reuse across requests, eviction.
4. Prefill/decode disaggregation and scheduling for mixed workloads.
5. Quantization and its quality/latency tradeoff; validation that quality survived.
6. Speculative decoding and other latency tricks.
7. Autoscaling GPUs against bursty demand; cold-start mitigation.
8. Benchmarking honestly: TTFT, TPOT, throughput-vs-latency frontier under realistic distributions.

**Capabilities**

- _Core:_ GPU memory and compute model · transformer inference mechanics · queueing theory · performance measurement · Kubernetes/GPU ops · C++/Python.
- _Strong-plus:_ CUDA kernels · compiler stacks · hardware-specific tuning (H100/TPU/Trainium).
- _Not required:_ product, prompting.

**Loop shape.** "Design a batching system for one GPU serving synchronous users" is the canonical question — a queueing problem with a KV-cache memory constraint.

**Who hires.** Labs, inference providers, GPU clouds, companies self-hosting at volume.

---

### R15 · Post-Training / Fine-Tuning Engineer

**Aliases:** Post-Training Engineer · Alignment Engineer (applied) · Model Customization Engineer · RLHF Engineer.

**Definition.** Changes model behavior through data and training rather than prompting. The bridge row between engineering and science.

**Tier 2 — recurring jobs**

1. Decide whether the problem is actually a training problem (most are not).
2. Curate and clean training data; build synthetic data pipelines with quality filters.
3. Run SFT / LoRA / QLoRA adaptation; manage hyperparameters and compute budget.
4. Preference tuning (DPO and successors) and reward modeling where applicable.
5. Build the eval that proves the tuned model beat the prompted baseline — including regression on general capability.
6. Package and serve adapters; manage versioning and rollback.
7. Watch for catastrophic forgetting and overfitting to the tuning set.

**Capabilities**

- _Core:_ deep learning fundamentals · transformer internals · training loops and optimization · data curation · HuggingFace stack (transformers, peft, trl) · rigorous evaluation · GPU basics.
- _Strong-plus:_ RL fundamentals · distributed training · synthetic data methodology · tokenizer behavior.
- _Not required:_ frontier research.

**Loop shape.** ML depth + practical training scenario + eval design.

**Who hires.** Companies with domain data and volume economics, model-customization vendors, labs' applied teams.

---

### R16 · Applied Scientist

**Aliases:** Applied Scientist · Research Scientist (applied) · Senior Applied Scientist.

**Definition.** Solves product problems with modeling methods, publishing internally rather than externally. Amazon-style Applied Scientist is the archetype: half scientist, half engineer.

**Tier 2 — recurring jobs**

1. Formulate an ambiguous business problem as a solvable modeling problem.
2. Survey literature and select/adapt methods; run controlled experiments.
3. Build prototypes with credible offline evaluation.
4. Partner with engineers to productionize; own the science quality, not the uptime.
5. Design the online measurement that proves impact.
6. Publish internally; sometimes externally.

**Capabilities**

- _Core:_ strong ML/statistics foundations · experimental design · literature fluency · Python/PyTorch · communication of uncertainty · production-adjacent engineering.
- _Strong-plus:_ domain depth (NLP/CV/OR/econometrics) · publication record · causal inference.
- _Typically gated by:_ MS/PhD or equivalent demonstrated research output.

**Loop shape.** Research/ML depth rounds, method design, coding, science communication.

---

### R17 · Research Engineer (frontier)

**Aliases:** Research Engineer · Member of Technical Staff (engineering) · RE.

**Definition.** The engineer inside a research team: builds the training and evaluation infrastructure that makes experiments fast and trustworthy. Often the strongest pure engineers in a lab.

**Tier 2 — recurring jobs**

1. Implement architectures and training recipes from papers, correctly and fast.
2. Build experiment infrastructure: sweeps, tracking, reproducibility, dataset versioning.
3. Optimize training throughput; profile and remove bottlenecks.
4. Build capability and safety evaluations for models under development.
5. Debug training pathologies (loss spikes, instability, data contamination).
6. Turn research prototypes into something another team can use.

**Capabilities**

- _Core:_ excellent software engineering · deep learning internals · PyTorch/JAX · distributed training · numerical debugging · reading and implementing papers.
- _Strong-plus:_ kernel-level optimization · RL infrastructure · evaluation design.
- _Not required:_ novel research ideas (that's R18) — but taste for them helps.

**Loop shape.** Strong coding, ML depth, systems/performance, research-collaboration behavioral.

---

### R18 · Research Scientist

**Aliases:** Research Scientist · Member of Technical Staff (research).

**Definition.** Generates new methods and knowledge. Judged on ideas that work, usually with a publication or model-capability record behind them.

**Capabilities**

- _Core:_ deep math (linear algebra, probability, optimization, information theory) · deep learning theory and practice · research taste and problem selection · experimental rigor · scientific writing · strong enough engineering to run experiments alone.
- _Strong-plus:_ a specialization (RL, interpretability, multimodal, theory, alignment) · a track record.
- _Gate:_ PhD or equivalent public research output. Effectively closed as a lateral move from engineering.

**Included here only so you can read a JD and correctly decide not to apply.**

### R19 · Data Scientist / Experimentation

**Aliases:** Data Scientist · Product Data Scientist · Experimentation Analyst.

**Definition.** Measures reality: what happened, why, and whether the change helped. Increasingly the partner role for AI features because someone must define what "better" means in business terms.

**Capabilities**

- _Core:_ statistics and experimental design · SQL and data modeling · causal inference · visualization · product judgment · communication.
- _Strong-plus:_ ML for analysis · metric architecture · survey/labeling design.

**Relevance to you.** Not a target, but its skill set (metric design, significance, experiment reading) is exactly what R5 demands and what most engineers lack.

### R20 · Technical AI Product Manager

**Aliases:** AI PM · Product Manager, AI Platform · TPM (AI).

**Definition.** Decides what the AI system should do and what quality bar it must meet before it ships. In AI, the PM must be technical enough to reason about eval and cost or the roadmap is fiction.

**Capabilities**

- _Core:_ problem framing · eval literacy (what to measure and what a number means) · cost and latency intuition · risk assessment · stakeholder management · roadmap sequencing under uncertainty.
- _Strong-plus:_ enough hands-on to prototype · regulatory literacy · pricing/unit economics.

**Relevance.** A landing spot for engineers who prefer the ambiguity side of R21.

---

### R21 · AI Tech Lead / Staff Engineer / AI Architect ← **your destination**

**Aliases:** Staff AI Engineer · AI Architect · Principal Engineer (AI) · Head of AI Engineering · AI Tech Lead.

**Definition.** Owns the _system_ and the _team's ability to deliver it_. Decides archetype, build-vs-buy, platform boundaries, quality bar, and sequencing; makes the calls that are expensive to reverse.

**Owns:** architecture, technical strategy, the quality/cost bar, risk posture, delivery sequencing, and the growth of the engineers doing the work.
**Does not own:** every line of code — and the shift away from that is the actual job change.

**Tier 2 — recurring jobs**

1. Convert a business objective into an AI system design with explicit non-goals.
2. Make the archetype call (extraction / RAG / workflow / agent) and write down why the simpler option was rejected — or chosen.
3. Build-vs-buy: vendor agent platform vs in-house; managed vector DB vs Postgres+pgvector; hosted models vs self-hosted.
4. Define the quality bar _before_ the build: what eval, what threshold, who signs off.
5. Set the cost model: cost per request, unit economics, the budget at which the feature stops making sense.
6. Design the platform/product boundary so teams aren't each rebuilding gateways and evals.
7. Own the risk posture: injection, authorization, human gates, regulatory approval path.
8. Sequence delivery as an MVP ladder with vertical slices; protect the team from horizontal build-out.
9. Set engineering standards: prompt versioning, eval-gated deploys, tracing, model pinning.
10. Run the technical review forum; make decisions reversible where possible and explicit where not.
11. Grow engineers: distribute the interesting work, review designs not just code.
12. Communicate upward in business terms (risk, cost, time) and downward in engineering terms.

**Capabilities**

- _Core:_ everything in R1 + R3 Core at working depth · design-doc writing · build-vs-buy judgment · cost modeling · risk framing · delivery sequencing · technical mentorship · stakeholder communication · the discipline to choose boring and proven.
- _Strong-plus:_ enough R5 to set the quality bar · enough R8 to set the risk bar · enough R11 to know when the answer is a classical model, not an LLM · organizational design (team topology around the platform boundary).
- _Not required:_ research depth, kernel performance.

**The artifacts of this role** (what you should be producing to prove you can do it):

1. A one-page design doc: problem, users, business need, success metric, non-goals, approach, build-vs-buy.
2. An architecture decision record trail with rejected alternatives.
3. An eval strategy with thresholds and a named owner.
4. A cost model spreadsheet with sensitivity to volume and context size.
5. A risk register mapping threats to controls.
6. A phased delivery plan with vertical MVPs.

**How it's assessed.** Ambiguous design rounds, "tell me a decision you reversed," architecture review simulations, and cross-functional behavioral. Nobody asks a lead to invert a binary tree, but every lead loop asks how you decided something under incomplete information.

## 6. The path to AI Tech Lead / Architect

Five steps. Each is defined by what you _own_, not by a title.

| Step                                                 | You own                                                                           | Proof you can produce                                                                 | Typical gap                         |
| ---------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------- |
| **S0 — Backend engineer with AI fluency** (you, now) | Services in the request path; an AI prototype                                     | Shipped backend systems; one agent/RAG prototype with honest limits                   | Retrieval depth, eval discipline    |
| **S1 — Applied AI engineer**                         | One AI feature end to end, in production, on-call                                 | A feature with an eval suite, a cost number, and a trace you can walk someone through | Trajectory eval, injection defence  |
| **S2 — Senior / domain owner**                       | A subsystem others depend on (the retrieval layer, the eval harness, the gateway) | A design doc that was implemented by someone other than you                           | Saying no; scoping                  |
| **S3 — Tech lead**                                   | A team's delivery of an AI system                                                 | Phased plan executed; a reversed decision with reasoning; a mentored engineer         | Communication upward; cost modeling |
| **S4 — Architect / Staff+**                          | Cross-team architecture, platform boundaries, the quality and risk bar            | An ADR trail, a build-vs-buy call with money attached, a standard others adopted      | Organizational leverage             |

**What actually gates S2→S3:** not more knowledge. It's evidence of judgment under incomplete information — decisions you made, wrote down, defended, and sometimes reversed. Start producing that artifact trail now, on the portfolio project, because it's the one thing you cannot retroactively manufacture during a loop.

**12–24 month build plan (specific to you)**

_Months 0–3 — job first._ Do not architect anything. Close the four P0 gaps (retrieval internals, evaluation, agent loop/termination, injection & authz) to interview depth. Land an R1/R3/R4 role. Everything below assumes you have income and a production system to learn on.

_Months 3–9 — S1._ Own one AI feature end to end where you work. Non-negotiables: a golden eval set from real traffic, a CI regression gate, a cost-per-request number, full tracing. Write the design doc even if nobody asked for one. This single feature is worth more than any number of side projects.

_Months 9–15 — S2._ Take the subsystem nobody wants: usually the eval harness or the retrieval layer. Both are unglamorous, high-leverage, and make you the person other teams consult. Publish internal standards (prompt versioning, model pinning, eval-gated deploys). Start reviewing other people's designs.

_Months 15–24 — S3._ Lead a delivery: scope it, sequence it as vertical MVPs, make the build-vs-buy call, defend the cost model, mentor two engineers through it. Produce the six architect artifacts in §R21. At that point the architect loop is a description of your last year rather than a hypothetical.

**Three traps on this path**

1. **Building the platform before there is a product.** Gateways and eval services are seductive; build them when the second team needs them, not the first.
2. **Chasing the frontier.** The ecosystem churns quarterly. Mechanisms (retrieval, queueing, authz, evaluation, cost) are stable; frameworks are not. Invest in the stable layer.
3. **Skipping the boring row.** R4 and R3 work looks less exciting than agent work and is a faster route to architect, because architecture is mostly platform and data decisions.

## 7. Market reality (2026-08, hedged)

- **Req volume**, roughly ordered: R1 > R11 > R4 > R3 > R7 > R6 > R2 > R14 > R5/R8/R10 > R13/R15 > R16/R17/R18.
- **Scarcest skills relative to demand:** evaluation methodology (R5), AI security (R8), and people who can do R3 _and_ speak R10's language.
- **Comp** — order of magnitude only, US, mid-to-senior: applied AI engineering clusters near strong senior backend comp, with frontier labs and well-funded AI infra startups paying a substantial premium (multiple 2026 interview-prep sources report mid-level AI engineering in the ~$140–200K base range and senior/staff ~$200–280K+, varying widely by company type and location). Treat any specific figure as a rumor until you have an offer.
- **The durable filter:** roles where the model is a component of a system you own will keep hiring engineers. Roles that were only prompt-craft have already been absorbed into R1.
