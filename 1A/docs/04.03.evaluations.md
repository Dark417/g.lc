## 0. One-minute version
- What
  - Measuring an LLM system on a fixed dataset so changes can be compared with numbers
  - Targets: a model, a prompt, a RAG pipeline (retrieval + generation), a guardrail
- Why
  - LLM output is open-ended; "looks good" on five examples does not survive a model or prompt change
  - Every change (model version, chunk size, guardrail strength) needs a before/after score
- How
  - Dataset: prompts + reference answers (+ category, + expected labels)
  - Score with one of three methods
    - Automatic metrics: string overlap (ROUGE, BLEU), embedding similarity (BERTScore), exact match
    - LLM-as-a-judge: a second model rates correctness, faithfulness, … with a rubric
    - Humans: rating work teams, slow and costly, the ground truth for the other two
  - Bedrock evaluation jobs run all three; RAG eval scores retrieval only or retrieval + generation
  - Guardrails: labeled allow/block set → ApplyGuardrail → confusion matrix → tune strengths
- Catch
  - Overlap metrics punish correct paraphrases
  - Judges are biased (self-preference, verbosity, position) ⇒ calibrate against human labels
  - A small or stale dataset gives confident wrong answers
  - Offline scores do not guarantee online quality ⇒ sample production traffic too
- 🗣 "No eval set, no change: every prompt, model, or guardrail edit ships with a before/after score."
- 🗣 "Retrieval metrics tell you if the right context arrived; generation metrics tell you if the model used it."
- 🗣 "A guardrail is a classifier: report precision, recall, and false-positive rate per policy."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Classic NLP had task metrics (BLEU for translation, ROUGE for summaries) tied to one reference
  - Generative answers have many correct forms ⇒ overlap metrics under-score good answers
  - Human evaluation is the gold standard but takes days and costs per item
- What changed
  - LLM-as-a-judge (2023+): strong models grade with rubrics, at scale, in minutes
  - Managed jobs (Bedrock Evaluations, 2023–2025) bundle datasets, judges, metrics, reports
- Common use cases
  - Pick a model for a task (quality vs cost vs latency)
  - Regression-test a prompt or RAG change in CI
  - Tune a guardrail's strengths against a false-positive budget
  - Measure bias and harmful-output rates for responsible-AI reviews

### 1.2 Picture

```
 dataset.jsonl (S3 evals/datasets/)                      
   prompt, referenceResponse, category                   
        │                                                
        ▼                                                
 ┌──────────────── Bedrock evaluation job ────────────────┐
 │ inference:  model  |  KB retrieve  |  KB retrieve+gen  │  (or precomputed responses: BYOI)
 │      │                                                 │

 └────────────────────────────┬───────────────────────────┘

 guardrail eval (local harness):
   labeled cases ─► ApplyGuardrail(outputScope=FULL) ─► predicted block? + which policy
                 ─► confusion matrix per policy ─► precision / recall / FPR ─► adjust strengths ─► repeat
```

### 1.3 Three ways to score

| Method | Mechanism | Strength | Weakness | Cost (order of magnitude) |
|---|---|---|---|---|
| Automatic metrics | n-gram overlap, embedding similarity, exact match, classifiers | deterministic, cheap, fast | needs a reference; punishes paraphrase | ~free |
| LLM-as-a-judge | rubric prompt → score + reason from a judge model | scales; handles paraphrase; any criterion | bias; judge cost; drift with judge version | judge tokens per item |
| Human | raters on a work team | ground truth; nuance | slow; costly; inter-rater disagreement | per item per rater |

- Default stack
  - Automatic for regression smoke tests
  - Judge for most quality dimensions
  - Humans on a small sample to calibrate the judge

### 1.4 Automatic metrics: ROUGE, BLEU, BERTScore
- ROUGE-1 (recall-oriented, summarization)
  - Count unigrams shared by candidate and reference (clipped by counts)
  - Precision = overlap / candidate words; recall = overlap / reference words; report F1
- ROUGE-L
  - Longest common subsequence (in order, gaps allowed) between candidate and reference
  - Rewards correct word order without needing contiguous n-grams
- BLEU (precision-oriented, translation)
  - Geometric mean of 1–4-gram precisions × brevity penalty for short candidates
  - Corpus-level metric; noisy per sentence
- BERTScore
  - Embed every token of both texts with a BERT-family model
  - Greedy-match tokens by cosine similarity; average into precision/recall/F1
  - Handles synonyms; still needs a reference; depends on the embedding model
- Limit for all four
  - They measure similarity to one reference, not correctness or groundedness
  - Bedrock's automatic "Accuracy" uses a task-specific metric (e.g. BERTScore for summarization, F1 for QA; check the metric table in the docs)

### 1.5 Bedrock evaluation job types

| Job | `applicationType` | Scoring | Metric names (`metricNames`) | Needs |
|---|---|---|---|---|
| Automatic model eval | `ModelEvaluation` | built-in algorithms | `Builtin.Accuracy`, `Builtin.Robustness`, `Builtin.Toxicity` | `taskType`: Summarization, Classification, QuestionAndAnswer, Generation |
| LLM-as-a-judge model eval | `ModelEvaluation` | judge model | quality: `Builtin.Correctness`, `Completeness`, `Faithfulness`, `Helpfulness`, `Coherence`, `Relevance`, `FollowingInstructions`, `ProfessionalStyleAndTone`; responsible AI: `Harmfulness`, `Stereotyping`, `Refusal` | `evaluatorModelConfig.bedrockEvaluatorModels` |
| Human model eval | `ModelEvaluation` | your work team (SageMaker Ground Truth flow) | your custom metric names | `human.humanWorkflowConfig.flowDefinitionArn` |
| RAG eval, retrieve only | `RagEvaluation` | judge model | `Builtin.ContextRelevance`, `Builtin.ContextCoverage` (coverage needs references) | `ragConfigs[].knowledgeBaseConfig.retrieveConfig` |
| RAG eval, retrieve + generate | `RagEvaluation` | judge model | `Builtin.Correctness`, `Completeness`, `Helpfulness`, `LogicalCoherence`, `Faithfulness`, `Harmfulness`, `Stereotyping`, `Refusal`; citation metrics `CitationPrecision`, `CitationCoverage` (verify) | `ragConfigs[].knowledgeBaseConfig.retrieveAndGenerateConfig` |

- Custom metrics (judge and RAG): `customMetricConfig.customMetrics[].customMetricDefinition` = `name`, `instructions` (rubric prompt with input variables), `ratingScale[]` (`definition` + `value.floatValue` or `stringValue`)
- Bring your own inference (BYOI)
  - Model eval: `inferenceConfig.models[].precomputedInferenceSource.inferenceSourceIdentifier` + `modelResponses` in the dataset
  - RAG eval: `precomputedRagSourceConfig` + retrieved passages / output in the dataset
  - Use: evaluate a non-Bedrock model or your own RAG pipeline with Bedrock's judges
- Request skeleton (`bedrock.create_evaluation_job`)
  - `jobName` (lowercase, digits, hyphens; ≤ 63), `roleArn`, `applicationType`
  - `evaluationConfig.automated.datasetMetricConfigs[]` = `taskType` + `dataset{name, datasetLocation.s3Uri}` + `metricNames[]` (≤ 25)
  - `inferenceConfig.models[].bedrockModel{modelIdentifier, inferenceParams (JSON string)}` or `inferenceConfig.ragConfigs[]`
  - `outputDataConfig.s3Uri`, optional `customerEncryptionKeyId`, `clientRequestToken`
- Lifecycle: `InProgress` → `Completed` | `Failed` (`failureMessages`) | `Stopping` → `Stopped`; `StopEvaluationJob` to cancel
- Cost
  - You pay model inference for the generator and the judge at on-demand rates (no separate eval fee per the pricing page, 2026-11; verify)
  - Judge tokens ≈ (prompt + response + reference + rubric) × metrics × items ⇒ metrics multiply cost

### 1.6 Datasets
- Model eval JSONL (one object per line)
  - `{"prompt": "...", "referenceResponse": "...", "category": "billing"}`
  - `referenceResponse` optional for some metrics; required for Correctness-style comparisons and Accuracy
  - `category` groups scores in the report (per-slice analysis)
  - BYOI adds `"modelResponses": [{"response": "...", "modelIdentifier": "my-model"}]`
- RAG eval JSONL
  - `{"conversationTurns": [{"prompt": {"content": [{"text": "..."}]}, "referenceResponses": [{"content": [{"text": "..."}]}]}]}`
  - One turn per line today (multi-turn: check the docs)
- Size: custom datasets are capped per job (order of magnitude: 1,000 prompts; check the quota page)
- Built-in datasets (automatic eval): `Builtin.Bold`, `Builtin.BoolQ`, `Builtin.NaturalQuestions`, `Builtin.Gigaword`, `Builtin.RealToxicityPrompts`, `Builtin.TriviaQA`, `Builtin.T-Rex`, `Builtin.WomensEcommerceClothingReviews`, `Builtin.Wikitext2`
- What makes a good set
  - Real user questions (sampled from logs, PII scrubbed per 04.02), not invented ones
  - Hard cases and known failures, not only happy paths
  - Answerable and unanswerable questions (tests refusal and faithfulness)
  - Versioned in S3 with the results that used it

### 1.7 LLM-as-a-judge: model choice and bias
- Mechanism
  → judge gets the rubric, the prompt, the candidate response, and the reference  
  → returns a score on the rating scale plus an explanation  
  → Bedrock normalizes built-in metric scores to 0–1  
- Biases (documented in the LLM-judge literature, e.g. Zheng et al. 2023 "MT-Bench")
  - Self-preference: a judge favors outputs from its own model family
  - Verbosity: longer answers score higher
  - Position: in pairwise comparisons, the first (or second) answer wins more often
- Mitigations
  - Judge from a different family than the generator
  - Rubrics with explicit criteria and anchored scale definitions
  - Calibrate: judge vs humans on 50–200 items (order of magnitude); report agreement
  - Pin the judge model version; a judge upgrade changes every score
- Model choice
  - Must be on the supported evaluator list (check the docs; it changes)
  - Stronger judge = better agreement, higher cost; cheaper judge for smoke tests

### 1.8 Evaluating RAG (lecture 21)
- Two stages, two metric families

| Stage | Question | Bedrock metric | Classic IR metric |
|---|---|---|---|
| Retrieval | Did the right chunks come back? | ContextRelevance, ContextCoverage | recall@k, precision@k, MRR, nDCG |
| Generation | Did the answer use them correctly? | Faithfulness, Correctness, Completeness, Citation* | — |
| End to end | Is the user helped? | Helpfulness, LogicalCoherence, Refusal | task success rate |

- Diagnosis grid
  - Low context relevance ⇒ fix retrieval: chunking, embeddings, hybrid search, reranking, metadata filters (02.x)
  - High context relevance, low faithfulness ⇒ fix generation: prompt, model, guardrail grounding threshold (04.01)
  - Low coverage ⇒ top-k too small or chunks too narrow
- Retrieve-only eval is cheaper and isolates the vector store; run it first on every chunking/embedding change
- Online counterpart: Guardrails contextual grounding scores per request = a free faithfulness signal in production

### 1.9 Evaluating guardrails
- A guardrail is a set of binary classifiers ⇒ evaluate it like one
- Dataset: labeled cases
  - `text`, `source` (INPUT/OUTPUT), `expected_blocked`, `policy` label (e.g. `topic:InvestmentAdvice`, `content:PROMPT_ATTACK`, `pii`, `benign`)
  - Include near misses ("what is an index fund?") and benign look-alikes ("kill the process")
- Run
  → ApplyGuardrail per case with `outputScope=FULL` against DRAFT or a candidate version  
  → predicted = action intervened with a BLOCKED hit; record which policies fired  
  → confusion matrix overall and per policy  
- Metrics
  - Precision = TP / (TP + FP): of what we blocked, how much should have been blocked
  - Recall = TP / (TP + FN): of what should be blocked, how much we caught
  - False-positive rate = FP / (FP + TN): share of legitimate traffic we break
  - Also: latency p50/p95, text units (cost) per case
- Tune
  - Recall too low on a category ⇒ raise its strength
  - FPR over budget ⇒ lower strength, sharpen topic definitions, tag only user input
  - Score-based sweep: `InvokeGuardrailChecks` returns raw severity / confidence scores ⇒ plot precision/recall per threshold before choosing a strength
- Gate: promote the version only if per-policy recall ≥ target and FPR ≤ budget (04.01 `promote_draft` is the minimal version of this)

### 1.10 Offline vs online
- Offline: fixed dataset, run on every change (CI), comparable over time
- Online: production traffic
  - Sampled requests judged asynchronously (same judge prompts)
  - User signals: thumbs, retries, escalations
  - Guardrail intervention rate, grounding scores, refusal rate
  - AgentCore online evaluation configs exist for agents (`aws_bedrockagentcore_online_evaluation_config`; out of scope here)
- Loop: online failures → new offline cases → the next change must fix them without regressions

## 2. When to use / not
- Use Bedrock evaluation jobs when
  - Models and KBs are on Bedrock, and you want managed judges, reports, and an audit trail
  - Comparing several models or KB configs on the same dataset
- Use a local harness when
  - Evaluating guardrails (no managed job type for it)
  - Fast inner-loop checks in CI where a job's minutes of startup are too slow
  - Metrics Bedrock does not offer (exact JSON schema validity, tool-call accuracy)
- Do not
  - Use ROUGE/BLEU alone for open-ended answers
  - Trust a judge you have never compared with humans
  - Evaluate on the same examples you used to write the prompt (overfitting)

## 3. Knobs and best practices

| Knob | Values | Trade-off | Change when |
|---|---|---|---|
| Job type | automatic / judge / human / RAG | cost and speed vs nuance | new task → judge; calibration → human |
| Judge model | supported evaluator list | quality vs cost; family bias | generator family changes |
| Metric list | ≤ 25 per dataset config | each metric = judge calls | focus on 3–5 that map to failures |
| Dataset size | up to the per-job cap | confidence vs cost | wide confidence intervals → more items |
| `category` | free text | per-slice insight | quality differs by segment |
| `inferenceParams` | JSON string (temperature, maxTokens) | determinism vs realism | use prod settings; temperature 0 for regression |
| `numberOfResults` (RAG) | 1–100 | coverage vs noise | coverage low → raise |
| Guardrail strengths | NONE…HIGH per category | recall vs FPR | per confusion matrix |
| `outputScope` (guardrail eval) | FULL | bigger responses | always FULL for eval |

- Best practices
  - Version dataset + config + results together ⇒ prevents comparing scores from different sets
  - Report per-category scores, not only the mean ⇒ prevents a regression hiding in a small segment
  - Keep a fixed "golden" set and a growing "failures" set ⇒ prevents overfitting to old cases
  - Calibrate judges on human labels ⇒ prevents optimizing for judge bias
  - Use the same inference params as production ⇒ prevents eval/prod drift
  - Encrypt datasets and results with the CMK, scrub PII first ⇒ eval buckets hold real user text
  - Gate releases on thresholds in CI ⇒ prevents "we'll look at the eval later"

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Evaluations | Managed model + RAG eval jobs (auto, judge, human) | No infra; KB-native RAG metrics; reports; IAM/KMS | Minutes per job; fixed metric set + custom metrics; Bedrock-centric (BYOI helps) | AWS stack, model/KB selection, audit |
| RAGAS | Open-source RAG metrics library (faithfulness, context precision/recall, answer relevancy) | Popular RAG metrics, any LLM as judge | You run it; metric definitions change between versions | Custom RAG pipelines, notebook iteration |
| DeepEval | Open-source pytest-style LLM test framework | Unit-test ergonomics, many metrics, CI-friendly | You host judge calls; metric quality varies | Developer CI gates |
| promptfoo | Open-source CLI for prompt/model matrix tests + red teaming | Fast config-driven comparisons; red-team plugins | Less RAG-specific depth | Prompt A/B and jailbreak testing |
| Custom harness | Your code: dataset → system → scorers | Exactly your metrics (guardrail confusion matrix, schema checks) | You maintain it | Guardrails, tool calls, domain checks |
| Human eval (Ground Truth) | Managed rating workflows | Ground truth | Slow, costly | Calibration, launch reviews |

- Default: Bedrock Evaluations for model and RAG quality, plus a custom harness for guardrails and schema/tool checks, unless the pipeline is not on Bedrock and BYOI is awkward ⇒ RAGAS or DeepEval in CI
- Deciding variable: where inference runs, and whether you need managed reports + audit or fast developer loops

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Good answers score low | ROUGE/BLEU on paraphrases | judge vs metric disagreement | judge or BERTScore; multiple references |
| Judge inflates scores | same family as generator; verbosity | human sample disagrees | different-family judge; rubric anchors |
| Scores jump with no change | judge model or dataset changed | config diff | pin judge version; version datasets |
| Job fails AccessDenied | role trust / S3 / KMS / model access | `failureMessages` | trust bedrock.amazonaws.com + SourceAccount; grants |
| Job fails on dataset | wrong JSONL keys, too many prompts | `failureMessages` | validate locally before upload |
| RAG eval looks fine, prod poor | dataset not like real questions | online sampling | build sets from scrubbed logs |
| Guardrail tuned to a tiny set | 20 cases, no near misses | FP complaints after launch | 100s of cases per policy, benign look-alikes |
| Overfit prompt | eval set used while writing the prompt | holdout set drops | separate dev and test sets |
| Cost blow-up | many metrics × many items × big judge | bill | sample, fewer metrics, cheaper judge for smoke |

## 6. Interview questions

**Q: How would you evaluate a RAG system?**

**L4 answer**
- Dataset of real questions with reference answers
- Retrieval metrics (context relevance/coverage, recall@k) and generation metrics (faithfulness, correctness)
- Bedrock RAG eval job: retrieve-only and retrieve-and-generate

**L5 extra**
- Separate the stages to localize faults: retrieval vs generation diagnosis grid
- Include unanswerable questions to test refusals and faithfulness
- Online: grounding scores and sampled judging; feed failures back into the offline set

**Q: Why not just use ROUGE or BLEU?**

**L4 answer**
- They count word overlap with one reference; correct paraphrases score low; wrong answers with shared words score high

**L5 extra**
- Fine for constrained outputs (extraction, short summaries) and as cheap regression signals
- BERTScore helps with synonyms but still doesn't check facts
- Judges add semantics at the price of bias and cost

**Q: What are the risks of LLM-as-a-judge?**

**L4 answer**
- Self-preference, verbosity, and position bias; cost; non-determinism

**L5 extra**
- Calibrate against human labels and report agreement
- Use a different family, explicit rubrics, pinned versions
- Pairwise comparisons: swap order and average

**Q: How do you evaluate a guardrail?**

**L4 answer**
- Labeled allow/block cases per policy, run through ApplyGuardrail, compute precision/recall/FPR

**L5 extra**
- Per-policy confusion matrices; near misses and benign look-alikes
- Threshold sweep from raw scores (InvokeGuardrailChecks) before picking strengths
- Gate version promotion on recall ≥ target and FPR ≤ budget; shadow in detect mode online

**Q: Offline vs online evaluation?**

**L4 answer**
- Offline: fixed set, comparable, in CI
- Online: real traffic, user signals, sampled judging

**L5 extra**
- Offline catches regressions; online catches distribution shift
- Close the loop: online failures become offline cases

**Q: What does a Bedrock evaluation job need?**

**L4 answer**
- Service role, dataset JSONL in S3, metric names, model or KB config, output S3 URI

**L5 extra**
- Judge model in `evaluatorModelConfig` for judge and RAG jobs
- Role trust with `aws:SourceAccount`; KMS grants for encrypted buckets
- BYOI for non-Bedrock systems

### L5-only

**Q: Design an evaluation program for a customer-support assistant moving from Claude to a cheaper model.**
- Golden set (scrubbed real tickets) + failure set, categories per intent
- Judge job on both models with Correctness, Completeness, Faithfulness, Refusal; human sample for calibration
- Per-category diff and cost/latency per answer; decide per category (router) if the cheap model loses only some
- Guardrail re-eval: new model may produce different outputs ⇒ output-side FPR changes
- Online canary with sampled judging and escalation rate before full switch

**Q: Your judge says quality went up 8% after a prompt change, but complaints rose. What happened?**
- Judge bias (verbosity: new prompt is longer), dataset not representative, or category mix hides a regression
- Check human agreement on the changed items; per-category scores; response length vs score
- Fix the rubric, add complaint cases to the set, re-run before deciding

**Q: How do you keep eval cost bounded at scale?**
- Stratified sampling instead of full sets; cheap judge for smoke, strong judge for release
- Few metrics mapped to known failures; cache responses (BYOI) and only re-judge
- Retrieve-only eval for retrieval changes (no generation cost)
