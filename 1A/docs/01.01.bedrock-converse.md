## 0. One-minute version
- What
  - Bedrock = a managed gateway to many foundation models (Anthropic, Amazon Nova, Meta, Mistral, ...) behind one AWS API
  - Converse = the model-agnostic chat API on the `bedrock-runtime` endpoint
- Why
  - One request shape for every chat model: `messages`, `system`, `inferenceConfig`, `toolConfig`
  - IAM, VPC endpoints, CloudTrail, KMS, and quotas come from AWS, not from a vendor key
- How  
  → pick a model ID or an inference profile ID (`us.anthropic...`)  
  → send `messages` (role + content blocks) + `system` + `inferenceConfig`  
  → read `output.message`, `stopReason`, `usage` (tokens), `metrics.latencyMs`  
  → on `stopReason = tool_use`: run the tool, send back a `toolResult`, call again  
- Catch
  - Converse normalizes the envelope, not the model
    - Prompts, quality, and limits still differ per model
    - Provider-only features go through `additionalModelRequestFields` or `InvokeModel`
  - The service is stateless: you resend the whole history every turn  
    ⇒ cost and latency grow with conversation length
  - On-demand calls throttle (`ThrottlingException`) at account quotas per model per Region
- 🗣 "Converse is a uniform envelope over many models; the history, the tools, and the retries are still your job."
- 🗣 "The tool-use loop is just: model asks, you execute, you answer with the same toolUseId."
- 🗣 "Throttling is a capacity signal: retry with jitter, then add an inference profile or provisioned throughput."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Each model vendor had its own API, auth, SDK, and data-handling terms
  - Enterprises needed one place for IAM, private networking, audit, and billing
- Bedrock (GA 2023-09)
  - Serverless model hosting: no GPUs, no endpoints to size for on-demand use
  - Your prompts and outputs are not used to train the base models (Bedrock data-protection page)
- InvokeModel came first
  - Body = the provider's native JSON  
  ⇒ switching from Claude to Nova meant rewriting request and response parsing
- Converse (2024-05)
  - One message format across chat models, plus tool use, documents, images, guardrails
- Common use cases
  - Chat assistants, summarization, extraction, classification
  - Agents that call tools (backend APIs, databases)
  - Document and image Q&A (invoices, screenshots, PDFs)

### 1.2 Picture

```
app (IAM role a-app)
   │  SigV4 over HTTPS (VPC endpoint bedrock-runtime, 00.01)
   ▼
bedrock-runtime  ── Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream
   │
   ├── modelId = foundation model     anthropic.claude-...-v1:0        (one Region)
   ├── modelId = inference profile    us.anthropic.claude-...-v1:0     (routes across US Regions)
   ├── modelId = app inference profile arn:...:application-inference-profile/xyz (cost tags)
   └── modelId = provisioned model    arn:...:provisioned-model/xyz    (bought capacity)
            │
            ▼
   model provider fleet (run by AWS) → tokens back

bedrock (control plane) ── ListFoundationModels, GetFoundationModel, inference profiles,
                           customization jobs, provisioned throughput, guardrails, logging
```

### 1.3 Control plane vs data plane
- `bedrock` (control plane)
  - Manages things: list models, inference profiles, customization, provisioned throughput, guardrails, invocation logging
  - Low call rates; used by setup code and Terraform
- `bedrock-runtime` (data plane)
  - Runs inference: `Converse`, `ConverseStream`, `InvokeModel`, `InvokeModelWithResponseStream`, `ApplyGuardrail`, `CountTokens`
  - High call rates; on the request path
- Separate endpoints ⇒ separate VPC endpoints and separate IAM actions
- Agents, knowledge bases, prompts, flows have their own pair: `bedrock-agent` / `bedrock-agent-runtime`

### 1.4 Model access and model IDs
- Model access
  - Historically each model had to be enabled per account in the console ("Model access")
  - Today most serverless models are available by default to IAM principals with permission (AWS, 2025)
  - Some providers still need a one-time use-case form or Marketplace subscription (Anthropic first use)
  - Limit: rules change; check the "Access Amazon Bedrock foundation models" page
  - IAM still decides: no `bedrock:InvokeModel` on the model ARN ⇒ `AccessDeniedException`
- Model ID = one model in one Region
  - Format `provider.model-name-version`, e.g. `anthropic.claude-haiku-4-5-20251001-v1:0`
  - ARN `arn:aws:bedrock:<region>::foundation-model/<id>` (no account: AWS owns it)
- Inference profile = a routing alias over one model in several Regions
  - System-defined, cross-Region: `us.`, `eu.`, `apac.` prefix (and `global.` for some models)
  - Bedrock picks a Region in the set with capacity ⇒ fewer throttles, same price as on-demand
  - Some newer models are only offered through an inference profile (calling the bare ID fails with `ValidationException`)
  - Catch: data may be processed in any Region of the set ⇒ check data-residency rules (lecture 136 covers it)
- Application inference profile = your own profile copied from a model or system profile
  - Carries your tags ⇒ cost allocation per app or tenant
  - Called by ARN; created in Terraform here (`a-app-profile`)
- Model lifecycle
  - `ACTIVE` → `LEGACY` → end of life
  - `ListFoundationModels` returns `modelLifecycle.status`; alarm on `LEGACY` models you still call

### 1.5 InvokeModel vs Converse
- `InvokeModel`
  - Body = provider-native JSON bytes
    - Anthropic: `{"anthropic_version": "bedrock-2023-05-31", "max_tokens": ..., "system": ..., "messages": [...]}`
    - Nova, Llama, Titan: each different
  - Response = provider-native JSON bytes; usage in body or in HTTP headers
  - Needed for: embeddings, image generation, and provider features Converse does not expose yet
- `Converse`
  - Typed request: `modelId`, `messages`, `system`, `inferenceConfig`, `toolConfig`, `guardrailConfig`, `additionalModelRequestFields`, `promptVariables`, `requestMetadata`, `performanceConfig`, `serviceTier`, `outputConfig`
  - Typed response: `output.message`, `stopReason`, `usage`, `metrics`, `additionalModelResponseFields`, `trace`
  - Same IAM action as InvokeModel (see 1.10 and the `.tf` header)
- Escape hatches
  - `additionalModelRequestFields`: provider-specific request keys (`top_k`, reasoning settings)
  - `additionalModelResponseFieldPaths`: JSON pointers into the native response (`/stop_sequence`)
- Limit: a feature exposed only by the native API lands in Converse later, if at all  
  ⇒ check the "Supported models and model features" table before choosing

### 1.6 The Converse request and response
- `messages`: list of `{role: user|assistant, content: [blocks]}`
  - Must start with `user` and alternate roles
  - Content blocks: `text`, `image`, `document`, `video`, `toolUse`, `toolResult`, `guardContent`, `cachePoint`, `reasoningContent`, ...
- `system`: list of blocks (`text`, `guardContent`, `cachePoint`)
  - Not every model supports a system prompt (check the feature table)
- `inferenceConfig`
  - `maxTokens`: output cap; hitting it ⇒ `stopReason = max_tokens`
  - `temperature`: 0 = most deterministic, higher = more varied
  - `topP`: nucleus sampling; tune temperature or topP, not both
  - `stopSequences`: strings that end generation ⇒ `stopReason = stop_sequence`
  - Some newer models reject sampling knobs (e.g. recent Claude models reject `temperature` / `topP`; Anthropic docs 2026-11) ⇒ keep them configurable per model
- Response
  - `output.message`: the assistant message; append it as-is to history
  - `stopReason`: `end_turn`, `tool_use`, `max_tokens`, `stop_sequence`, `guardrail_intervened`, `content_filtered`, `malformed_model_output`, `malformed_tool_use`, `model_context_window_exceeded`
  - `usage`: `inputTokens`, `outputTokens`, `totalTokens`, `cacheReadInputTokens`, `cacheWriteInputTokens`
  - `metrics.latencyMs`: server-side time for the whole call
- Prompt caching
  - A `cachePoint` block marks the end of a reusable prefix (system prompt, long document)
  - Later calls with the same prefix bill cached tokens at a discount and start faster
  - Limit: minimum prefix length and TTL are per model; verify with `cacheReadInputTokens > 0`
- `requestMetadata`: key-value tags written to invocation logs (05.01) ⇒ filter logs per tenant or feature

### 1.7 ConverseStream events
- Same request; the response is an event stream over HTTP/2-style chunked frames
- Event order  
  → `messageStart` (role)  
  → `contentBlockStart` (only for tool use and some block types; carries `toolUseId`, `name`)  
  → `contentBlockDelta` ×N (`text`, or `toolUse.input` as partial JSON string, or `reasoningContent`)  
  → `contentBlockStop` (block index)  
  → `messageStop` (`stopReason`)  
  → `metadata` (`usage`, `metrics.latencyMs`)  
- Error events arrive inside the stream: `throttlingException`, `modelStreamErrorException`, `validationException`, `internalServerException`, `serviceUnavailableException`  
  ⇒ a 200 response can still fail halfway; the client must handle mid-stream errors
- Tool input arrives as string fragments  
  ⇒ concatenate per block index, `json.loads` only at `contentBlockStop`
- Why stream
  - Time to first token drops from "whole answer" to "first chunk" (order of magnitude: sub-second vs seconds)
  - Total latency and cost are the same
- Limit: guardrails on streams can run async (sends chunks before the check) or sync (buffers) ⇒ see 04.01

### 1.8 Tool use loop
- `toolConfig.tools[].toolSpec` = `name`, `description`, `inputSchema.json` (JSON Schema)
- `toolConfig.toolChoice`
  - `auto` (default): model decides
  - `any`: must call some tool
  - `tool: {name}`: must call this tool (forced; used for structured output, see 01.05)
  - Limit: some models support only `auto`, and some newer Claude models reject forced choice (Anthropic docs 2026-11)
- Loop  
  → call Converse with tools  
  → `stopReason = tool_use` ⇒ the assistant message holds one or more `toolUse` blocks (`toolUseId`, `name`, `input`)  
  → append that assistant message unchanged  
  → run each tool in your code (validate `input` first)  
  → append one `user` message with all `toolResult` blocks (`toolUseId`, `content: [{json}|{text}]`, `status: error` on failure)  
  → call again; stop on `end_turn` or after N rounds  
- Bedrock never runs your tools; your process does  
  ⇒ authorization and input validation are yours (least privilege, 01.05 and 04.01)
- Parallel tool calls: several `toolUse` blocks in one turn ⇒ answer all of them in one user message
- Cap the rounds  
  ⇒ a confused model can loop forever and burn tokens

### 1.9 Multimodal content blocks
- `image`: `format` (`png`, `jpeg`, `gif`, `webp`) + `source.bytes` (raw bytes in boto3; base64 on the wire)
- `document`: `format` (`pdf`, `csv`, `doc`, `docx`, `xls`, `xlsx`, `html`, `txt`, `md`) + `name` + `source.bytes`
  - `name` allows only letters, digits, single spaces, hyphens, parentheses, square brackets  
    ⇒ sanitize file names; the name is also part of the prompt (injection surface)
  - Optional `citations: {enabled: true}` for models that return citation blocks
- `video` (Nova models): bytes or `s3Location`
- `s3Location` instead of bytes: only some models (Nova); Claude takes bytes
- Limits per request (count, MB, pixel size) are per model
  - Order of magnitude: a handful of documents of a few MB, a few dozen images (ImageBlock / DocumentBlock API reference; check per model)
- Images and PDFs cost input tokens (image tokens scale with pixels)  
  ⇒ resize before sending
- Lecture 22 also covers image generation (Nova Canvas, Titan Image) → `InvokeModel` only, not Converse

### 1.10 Throttling, errors, retries
- IAM
  - `Converse` is authorized by `bedrock:InvokeModel`
  - `ConverseStream` by `bedrock:InvokeModelWithResponseStream`
  - Resource = foundation-model ARN, inference-profile ARN, or provisioned-model ARN
  - A cross-Region profile needs the profile ARN and the foundation-model ARN in every Region it routes to
- Errors

| Error | HTTP | Meaning | Retry? |
|---|---|---|---|
| `ThrottlingException` | 429 | Requests/min or tokens/min quota hit | Yes, backoff + jitter |
| `ServiceUnavailableException` | 503 | Capacity issue | Yes |
| `InternalServerException` | 500 | Service error | Yes, a few times |
| `ModelTimeoutException` | 408 | Generation took too long | Maybe: smaller `maxTokens`, or stream |
| `ModelNotReadyException` | 429 | Model (often imported/custom) not loaded yet | Yes, with longer waits |
| `ModelErrorException` | 424 | Model returned an error | Rarely; log and fail |
| `ValidationException` | 400 | Bad request: role order, schema, unsupported field, bad model ID | No: fix the request |
| `AccessDeniedException` | 403 | IAM, or model not available to the account | No |

- Two retry layers
  - SDK: adaptive retry mode (`app.shared.aws`) retries 429/5xx and slows the client after throttles
  - App: `app.shared.retry.call_with_retry` around a whole call, with a retryable predicate
  - Catch: retries multiply under load ⇒ cap total attempts and fall back (smaller model, profile, queue)
- Quotas
  - Per model, per Region: requests per minute and tokens per minute (on-demand)
  - Tokens/min counts `maxTokens` reserved up front for some models (order of magnitude; check the quotas page)  
    ⇒ an oversized `maxTokens` throttles you sooner
  - Values differ per account; see Service Quotas → Amazon Bedrock

### 1.11 Throughput modes
- On-demand: pay per input/output token, shared capacity, quotas apply
- Cross-Region inference: on-demand price, more capacity, data crosses Regions in the set
- Provisioned throughput: buy model units per hour (no commitment, 1-month, or 6-month)
  - Needed for most custom (fine-tuned) models (01.02)
  - Pay while idle
- Batch inference: JSONL in S3 → async job → JSONL out
  - About 50% of on-demand price for supported models (pricing page; verify)
  - Results in hours, not seconds
- Service tiers on Converse (`serviceTier`: `priority`, `default`, `flex`) and latency-optimized inference (`performanceConfig.latency = optimized`)
  - Only some models and Regions; check before relying on them

## 2. When to use / not
- Use Converse when
  - Chat, extraction, tool use, image or document Q&A on Bedrock models
  - You may swap models later (A/B, cost cascades) without rewriting parsing
  - You need guardrails, prompt caching, or managed prompts (01.03) in one call
- Use InvokeModel when
  - Embeddings (02.01), image generation, rerank
  - A provider feature is not in Converse yet
  - You already have native-format prompts and want byte-exact control
- Use batch inference when
  - Offline bulk jobs (millions of records), no user waiting
- Avoid Bedrock entirely when
  - The model is not on Bedrock and you need GPU control ⇒ SageMaker endpoint or self-hosted vLLM
  - You need a vendor feature on day one ⇒ the vendor API directly (with its compliance trade-offs)

## 3. Knobs and best practices
- Model choice
  - Config, never code: model ID from env (`A_CONVERSE_MODEL_ID`, `a.models.text`)
    - Prevents: redeploying to switch models
  - Prefer an inference profile ID for production traffic
    - Prevents: single-Region throttling
  - Use an application inference profile per app or tenant
    - Prevents: unattributable Bedrock spend
- `inferenceConfig`
  - `maxTokens` sized to the task (classification: tens; answers: hundreds to low thousands)
    - Prevents: early throttling and runaway cost
  - `temperature` 0–0.3 for extraction and tools; higher for creative text
  - `stopSequences` to cut known trailers
- Conversation state
  - Store history behind a port (`ConversationStore`); DynamoDB in production
  - Trim by message count or token budget, keep the first `user` message valid
    - Prevents: `ValidationException` on role order and context-window errors
  - Summarize old turns once history exceeds a budget
- Tools
  - Short, precise `description`s and tight schemas (`required`, `enum`)
  - Validate `input` before executing; return errors as `toolResult` with `status: error`
  - Cap rounds (5 here)
- Streaming
  - Stream every user-facing answer
  - Handle `messageStop` and `metadata` separately: usage arrives last
- Cost
  - `cachePoint` after a long stable system prompt or document
  - Log `usage` and `latencyMs` per call (05.01 adds CloudWatch metrics)
  - Small model first, escalate to a larger one only when needed (cascade)
- Reliability
  - Adaptive SDK retries + app-level backoff with a cap
  - Timeouts: read timeout ≥ longest expected generation (60 s in `app.shared.aws`), or stream
- Security
  - VPC endpoint for `bedrock-runtime` (00.01); IAM scoped to model ARNs (`.tf`)
  - Never put secrets or raw PII in prompts without guardrails (04.01, 04.02)

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Converse | Unified chat API over Bedrock models | One shape for many models; tools, docs, images, guardrails, caching; AWS IAM/VPC/audit | Lowest common denominator; new provider features may lag | Default for chat and tool use on AWS |
| Bedrock InvokeModel | Provider-native JSON through Bedrock | Every provider feature Bedrock exposes; embeddings and images | Per-provider parsing; swapping models = rewrite | Embeddings, image gen, native-only features |
| OpenAI-compatible endpoints (Bedrock's Chat Completions-compatible API, LiteLLM, gateways) | OpenAI request shape in front of many models | Reuse OpenAI SDK code; easy multi-cloud | Mapping gaps (tools, multimodal, caching); support varies per model | Porting an OpenAI-based app; multi-provider gateway |
| Direct vendor API (Anthropic, OpenAI) | The model maker's own endpoint | Newest features first; vendor docs match 1:1 | Separate keys, billing, network path, data terms; no AWS IAM | Feature needed now; not bound to AWS compliance |

- Deciding variable: do you need AWS-native governance (IAM, VPC, CloudTrail, one bill) more than day-one vendor features?
- Default: Converse, unless you need embeddings / image generation / a native-only feature → InvokeModel, or a feature not yet on Bedrock → the vendor API

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Throttling | RPM/TPM quota per model per Region | `ThrottlingException`; CloudWatch `InvocationThrottles` | Backoff + jitter; cross-Region profile; smaller `maxTokens`; quota increase; provisioned throughput |
| Truncated answer | `maxTokens` too low | `stopReason = max_tokens` | Raise cap; ask for shorter output; continue in a new turn |
| Role-order error | History starts with `assistant` or repeats a role | `ValidationException` | Trim history in pairs; merge consecutive same-role turns |
| Tool loop never ends | Model keeps calling tools | Round counter hits the cap | Cap rounds; better tool descriptions; return clear errors |
| Bad tool input | Model invents fields or types | Schema validation fails | Validate, return `status: error`, let the model retry once |
| Mid-stream failure | Error event after 200 OK | Exception while iterating the stream | Treat partial output as failed; retry whole call or tell the user |
| Model unavailable | Bare model ID that needs a profile; legacy model | `ValidationException` / `ResourceNotFoundException` | Use the profile ID; track `modelLifecycle` |
| Access denied | IAM missing profile or destination-Region model ARN | `AccessDeniedException` | Grant profile ARN + `foundation-model` ARNs in all profile Regions |
| Context overflow | History or document too large | `stopReason = model_context_window_exceeded` or `ValidationException` | Trim, summarize, retrieve (RAG) instead of stuffing |
| Cost blow-up | Resending long history every turn | `usage.inputTokens` grows per turn | `cachePoint`; summarize; shorter system prompt |
| Timeout | Long generation on sync call | `ModelTimeoutException` / read timeout | Stream; lower `maxTokens`; raise read timeout |

## 6. Interview questions

**Q1:** What is the difference between InvokeModel and Converse?

**L4 answer**
- InvokeModel takes and returns provider-native JSON
- Converse takes typed messages, system, inference config, and tools, the same for every chat model
- Converse returns `stopReason`, `usage`, and `latencyMs` in a fixed shape

**L5 extra**
- Both are authorized by `bedrock:InvokeModel`; streaming by `InvokeModelWithResponseStream`
- Converse is a normalization layer: provider-only knobs go through `additionalModelRequestFields`
- InvokeModel stays necessary for embeddings and image generation
- Choose Converse to keep a model-swap a config change, not a code change

**Q2:** Walk through a tool-use round trip.

**L4 answer**
- Send `toolConfig` with JSON-schema tool specs
- Model returns `stopReason = tool_use` with `toolUse` blocks
- Run the tool, send a user message with `toolResult` carrying the same `toolUseId`
- Call again until `end_turn`

**L5 extra**
- Append the assistant message unchanged, including any text and reasoning blocks
- Answer every parallel `toolUse` in one user message
- Validate inputs and authorize per caller; Bedrock never executes tools
- Cap rounds, and return errors as `status: error` so the model can recover

**Q3:** Users report slow answers. What do you change?

**L4 answer**
- Switch to ConverseStream so the first tokens show immediately
- Lower `maxTokens` and shorten prompts

**L5 extra**
- Streaming cuts time to first token, not total latency or cost
- Prompt caching (`cachePoint`) cuts prefill time on long stable prefixes
- Smaller model for easy requests; latency-optimized inference where offered
- Measure `metrics.latencyMs` vs client time to separate model time from network and retries

**Q4:** You get `ThrottlingException` at peak. Options?

**L4 answer**
- Retry with exponential backoff and jitter
- Request a quota increase

**L5 extra**
- Cross-Region inference profile spreads load over several Regions at the same price
- Oversized `maxTokens` consumes TPM quota early ⇒ right-size it
- Steady high load → provisioned throughput; offline load → batch
- Cap retries and shed load; retries amplify a capacity problem

**Q5:** What is an inference profile, and why use an application inference profile?

**L4 answer**
- A system inference profile (`us.` prefix) routes one model across several Regions
- An application inference profile is your copy with your tags

**L5 extra**
- IAM must allow the profile ARN and the foundation model in each destination Region
- Data may be processed in any Region in the set ⇒ check residency
- Application profiles give per-app cost allocation and per-app CloudWatch metrics without changing model choice

**Q6:** How do you keep conversation state with a stateless API?

**L4 answer**
- Store messages per conversation and resend them each turn

**L5 extra**
- Store behind a port; DynamoDB keyed by conversation, sorted by sequence, with TTL
- Trim by token budget, keep role alternation valid, summarize old turns
- Cache the stable prefix; per-turn cost otherwise grows linearly with history

**Q7:** Which `stopReason` values must the caller handle?

**L4 answer**
- `end_turn` (done), `tool_use` (run tools), `max_tokens` (truncated)

**L5 extra**
- `guardrail_intervened` / `content_filtered`: show a safe message, don't retry blindly
- `malformed_tool_use` / `malformed_model_output`: retry once, then fail
- `model_context_window_exceeded`: trim or summarize, then retry

**L5-only Q8:** Design the Bedrock call path for a multi-tenant SaaS with a 99.9% SLO.

**L5 answer**
- Model ID and limits per tenant in config; an application inference profile per tenant tier for cost
- Cross-Region profile for capacity; provisioned throughput for the top tier
- Client: adaptive retries, capped app retries, circuit breaker, fallback to a smaller model
- Per-tenant token budgets enforced before the call (TPM is shared across tenants)
- Observability: `usage`, `latencyMs`, `stopReason`, and throttles per tenant via `requestMetadata` + invocation logs
- Trade-off: a fallback model keeps availability but changes quality ⇒ needs evals (04.03)

**L5-only Q9:** When would you leave Converse for a vendor API or self-hosting?

**L5 answer**
- A product-critical feature exists only in the vendor API, and waiting costs more than the governance gap
- The model is not on Bedrock, or you need custom kernels / GPU control → SageMaker or vLLM
- Very high steady volume where owned GPUs beat per-token pricing (only with an ops team)
- Keep a thin internal port (`ChatModel`) so the switch is an adapter change
