## 0. One-minute version
- What
  - OpenSearch = distributed search engine (Lucene inverted index) + a k-NN plugin for vectors
  - Two AWS forms
    - Managed domain: you pick nodes, shards, versions
    - Serverless collection: AWS scales compute in OCUs; you pick a collection type
- Why
  - One engine does BM25, vectors, filters, and aggregations ⇒ hybrid search without glue code
  - Default vector store for Bedrock Knowledge Bases (quick-create uses Serverless)
- How
  - Vectors live in `knn_vector` fields, indexed with HNSW (faiss / lucene) or IVF (faiss)
  - Query = `knn` clause, optional filter inside it, optional `hybrid` with a normalization pipeline
  - Access on AWS = SigV4 (`aoss` or `es`) + IAM + (Serverless) a data-access policy
- Catch
  - Serverless bills OCU-hours even when idle (lecture 17) ⇒ delete dev collections; check the pricing page for the floor
  - Domains need shard sizing, JVM watching, and 3 dedicated masters to stay stable
  - k-NN graphs live in native memory outside the JVM heap ⇒ memory, not disk, sizes the cluster
  - The vector index must exist (right fields, dims) before the Bedrock KB is created
- 🗣 "Serverless trades knobs for no-ops, but not for zero cost: OCUs bill while idle."
- 🗣 "On AOSS, IAM gets you to the door; the data-access policy opens the index."
- 🗣 "Put the filter inside the knn clause, or you post-filter and lose results."

## 1. Concept

### 1.1 Why OpenSearch for vectors
- The pain
  - Separate keyword engine + vector DB ⇒ two writes, two consistency stories, fusion in app code
- Prior art
  - Elasticsearch (2010) for full text; forked as OpenSearch in 2021 (Apache 2.0)
  - Dedicated vector DBs (Milvus, Pinecone) without strong lexical search
- How OpenSearch helps
  - Lucene segments hold both inverted indexes and k-NN graph files
  - The k-NN plugin loads native graphs (faiss) per segment into off-heap memory
  - Hybrid query runs BM25 and k-NN in one request; a search pipeline fuses scores
- Common use cases
  - RAG store behind Bedrock KB
  - Semantic + keyword product search
  - Log analytics (the original workload), now with semantic search on top
- Limits
  - Segment-level graphs ⇒ heavy updates/deletes need merges, cost CPU
  - Billion-scale low-latency needs careful memory planning (quantization, on_disk)

### 1.2 Picture

```
                   ┌──────────── Serverless collection (a-vectors, VECTORSEARCH) ─────────────┐
 app (SigV4 aoss) ─►│ VPC endpoint ──► indexing OCUs ──► S3-backed storage ◄── search OCUs     │◄── Bedrock KB
 via aoss VPCE      │                       │                                     ▲           │    (SourceServices:
                    │     encryption policy (CMK) · network policy · data-access policy       │     bedrock)
                    └──────────────────────────────────────────────────────────────────────────┘

                   ┌──────────── Managed domain ──────────────────────────────────────────────┐
 app (SigV4 es) ───►│ 3 dedicated masters (cluster state, quorum)                             │
                    │ data nodes: primary + replica shards, each shard = Lucene index          │
                    │   per segment: inverted index (BM25) + k-NN graph (native memory)        │
                    │ UltraWarm (S3-backed, read-only) · cold storage (detached)               │
                    └──────────────────────────────────────────────────────────────────────────┘
```

- Write path (domain)  
  → coordinator routes doc to a primary shard by `_id` hash  
  → primary writes translog + in-memory buffer, replicates to replicas  
  → refresh (default 1 s) creates a searchable segment; k-NN graph built for it  
  → merges combine segments and rebuild graphs  
- Read path: query fans out to one copy of every shard → each returns top k → coordinator merges

### 1.3 Managed domains
- Building blocks
  - Data nodes: hold shards; memory-optimized types suit k-NN (graphs need RAM)
  - Dedicated master (cluster manager) nodes: cluster state only, no data
    - Use 3: quorum survives one loss; 2 cannot elect after a failure; 1 is a single point of failure
  - Shards: primary + replicas; primary count is fixed at index creation (reindex or split to change)
  - Multi-AZ with standby: 3 AZs, one held as standby for failover (AWS recommended for production)
- Storage tiers
  - Hot: EBS / instance storage, read-write
  - UltraWarm: S3-backed with a cache, read-only, cheaper per GB; needs dedicated masters
  - Cold: detached from compute, attach before querying ⇒ lowest cost, minutes to access
  - Vector RAG data is hot: k-NN needs graphs in memory
- Changes
  - Most config changes run a blue/green deployment ⇒ hours on big domains, double nodes meanwhile

### 1.4 Domain stability and index management
- Shard sizing (AWS sizing guidance)
  - 10–30 GiB per shard when search latency matters; 30–50 GiB for write-heavy (logs)
  - Too many small shards ⇒ cluster-state and heap overhead per shard
  - Too few large shards ⇒ slow recovery, hot nodes
  - Keep shards per node within the heap guidance (AWS: up to 25 per GiB of heap; check current docs)
- JVM memory pressure
  - Heap ≈ half of RAM, capped near 32 GiB (compressed pointers)
  - AWS recommended alarms: `JVMMemoryPressure` max ≥ 95%, `OldGenJVMMemoryPressure` ≥ 80% (recommended-alarms page)
  - High pressure ⇒ GC pauses ⇒ timeouts ⇒ node drops
- k-NN memory is native (off-heap)
  - Circuit breaker caps graph memory (`knn.memory.circuit_breaker.limit`) ⇒ when tripped, new graphs are rejected
  - Watch `KNNGraphMemoryUsage` and circuit-breaker metrics
- ISM (Index State Management)
  - Policy = states + transitions (age, size, doc count) + actions (rollover, replica count, force_merge, warm, delete)
  - Typical logs policy: hot → warm after 7 d → delete after 90 d
  - For vectors: force_merge after bulk load ⇒ fewer segments ⇒ fewer graphs to search
- Performance knobs (lecture 57)
  - Bulk requests of ~5–15 MB (order of magnitude); parallel clients
  - `refresh_interval: -1` during bulk load, restore after
  - Replicas 0 during initial load, add after (managed domain only)
  - Warm up graphs (`GET /_plugins/_knn/warmup/<index>`) before traffic

### 1.5 Serverless collections
- Collection = a group of indexes with one type, one set of policies, one endpoint
- Types (immutable)
  - `SEARCH`: full text, low-latency queries
  - `TIMESERIES`: logs, append-heavy, newest data hot (provider default)
  - `VECTORSEARCH`: k-NN; what Bedrock KB uses
- Compute
  - Indexing and search scale separately, measured in OCUs (1 OCU = 6 GiB memory + matching vCPU, per AWS docs)
  - Data persists in S3; OCUs cache hot data
  - A minimum OCU floor bills 24/7 even without traffic (exact floor and fractional OCUs: pricing page)
  - Account-level maximum OCU setting caps cost runaway
  - `standby_replicas = DISABLED` (dev): single AZ, about half the floor; immutable
- What you give up vs a domain
  - No shard/replica settings, no ISM (TIMESERIES has lifecycle retention policies), no custom plugins
  - Fewer k-NN knobs exposed; no `?refresh` ⇒ writes visible after a delay
  - Some APIs differ per collection type (check "supported operations")
- Lecture 17 warning
  - A tutorial collection left running is the classic surprise bill
  - The KB quick-create flow creates a collection for you ⇒ delete it with the KB

### 1.6 The three Serverless policies
- Encryption policy (required before the collection exists)
  - AWS-owned key or a CMK; matched by collection name pattern
  - The key is fixed at creation ⇒ wrong key = recreate the collection
- Network policy
  - Public endpoint, VPC endpoints (`aws_opensearchserverless_vpc_endpoint`), and/or AWS service access (`SourceServices: bedrock.amazonaws.com`)
  - Separate rules for the collection endpoint and Dashboards
- Data-access policy
  - Per principal (role ARN): index permissions (`aoss:CreateIndex`, `ReadDocument`, `WriteDocument`, …) and collection permissions
  - IAM must also allow `aoss:APIAccessAll` on the collection ⇒ both gates must pass
- This repo's choice (02.02 `.tf`)
  - VPC endpoint for the app + Bedrock service access for the KB, no public endpoint
  - Trade-off: public + data-access policy is simpler; private removes the internet path but depends on Bedrock service access
  - Fallback if a Region rejects `SourceServices`: `AllowFromPublic = true`, still SigV4 + data-access gated

### 1.7 k-NN plugin: engines, methods, knobs

| Engine | Methods | Strength | Note |
|---|---|---|---|
| faiss | hnsw, ivf | Large scale, fp16 / PQ encoders, efficient filtering (2.9+) | Required by Bedrock KB on Serverless |
| lucene | hnsw | Smaller indexes, efficient filtering, byte vectors | Practical up to tens of millions of vectors (order of magnitude) |
| nmslib | hnsw | Historical default | Deprecated; blocked for new indexes in OpenSearch 3.0 |

- `space_type`: `l2`, `innerproduct`, `cosinesimil`, `l1`, `linf`, `hamming` (binary vectors)
- HNSW parameters: `m` (default 16), `ef_construction` (default 100), `ef_search` (index setting default 100; per query via `method_parameters`, 2.16+)
- IVF parameters: `nlist`, `nprobes`; needs the train API and a stored model
- Disk-based vectors (managed domains, 2.17+)
  - `mode: on_disk` + `compression_level` (`2x` fp16 … `32x` binary; on_disk defaults to 32x)
  - Quantized vectors in RAM for the first pass, full precision on disk for rescoring
  - Trade: ~32x less RAM for extra latency (order of magnitude: tens of ms more)
- Memory sizing for faiss HNSW: 1.1 × (4·d + 8·m) bytes per vector (k-NN docs) ⇒ 1M × 1024 dims ≈ 4.6 GB

### 1.8 The index a Bedrock KB expects
- Bedrock does not create the index on a bring-your-own collection ⇒ create it first (`create_kb_index`)
- Fields (names are yours; they must match the KB `field_mapping`)
  - Vector: `embedding`, `knn_vector`, `dimension = 1024` (Titan V2), `faiss` + `hnsw`, `l2`
  - Text: `text`, type `text` ⇒ the chunk; also what BM25 hybrid search reads
  - Metadata: `metadata`, type `text`, `index: false` ⇒ Bedrock's JSON of system metadata
- Bedrock also writes your sidecar metadata attributes as top-level fields ⇒ those are filterable
- Dimension mismatch between index and embedding model ⇒ KB ingestion fails per document
- Apply order: collection → data-access policy → index (Python) → KB (02.04)

### 1.9 Filtering and hybrid queries
- Post-filtering (`bool { must: knn, filter: … }`)
  - ANN returns k, then the filter drops some ⇒ fewer than k results, sometimes zero
- Efficient filtering (filter inside the `knn` clause)
  - Engine picks per query: few matches ⇒ exact search over them; many ⇒ filtered graph traversal
  - faiss (2.9+) and lucene support it
- Hybrid query  
  → `hybrid.queries = [match(text), knn(embedding)]`  
  → search pipeline `normalization-processor`: `min_max` (or `l2`) normalization  
  → combination `arithmetic_mean` with weights in sub-query order (e.g. 0.3 lexical, 0.7 vector)  
  - RRF alternative: `score-ranker-processor` (2.19+), rank-based, no weights
  - Serverless support for search pipelines: verify on your collection; managed domains support it (2.10+)

## 2. When to use / not
- Use OpenSearch Serverless when
  - Bedrock KB with hybrid search and no cluster team
  - Traffic is steady enough that the OCU floor is small relative to value
- Use a managed domain when
  - You need IVF, on_disk, custom shard layout, ISM, or plugins
  - Very large corpora where per-node memory planning beats OCU pricing
  - You already run OpenSearch for logs/search
- Don't use when
  - Low, spiky traffic on a small corpus ⇒ the idle floor dominates ⇒ S3 Vectors or pgvector
  - Vectors must join with transactional rows ⇒ pgvector
  - You only need a cache of recent answers ⇒ MemoryDB / ElastiCache

## 3. Knobs and best practices

| Knob | Values | Trades | Change when |
|---|---|---|---|
| Collection type | SEARCH / TIMESERIES / VECTORSEARCH | workload fit; immutable | never after create ⇒ choose VECTORSEARCH for KB |
| `standby_replicas` | ENABLED / DISABLED | AZ resilience vs ~half the OCU floor | DISABLED only for dev |
| Encryption key | AWS-owned / CMK | control + audit vs simplicity | regulated data ⇒ CMK |
| Network | public / VPC / AWS service | reachability vs exposure | private data ⇒ VPC + service access |
| Engine | faiss / lucene | scale + KB support vs index size | KB on AOSS ⇒ faiss |
| `m`, `ef_construction` | 16 / 100 default (KB samples use 512 for ef_construction) | recall vs memory + build time | recall plateau |
| `ef_search` | 100 default | recall vs latency | tune on a golden set |
| Shards (domain) | 10–30 GiB each for search | parallelism vs overhead | index growth |
| Dedicated masters (domain) | 3 | stability vs cost | always for production |
| `refresh_interval` (domain) | 1 s default | freshness vs indexing throughput | bulk loads ⇒ -1 temporarily |

- Best practices
  - Exclude the vector from `_source` in responses  
    ⇒ a 1024-dim hit carries ~4 KB of floats nobody reads  
  - Inspect every `_bulk` item; retry only 429 / 5xx  
    ⇒ `_bulk` returns HTTP 200 with per-item failures  
  - Pin the index contract (name, fields, dims) in one config shared with the KB  
    ⇒ a renamed field breaks ingestion silently per document  
  - Delete idle Serverless collections; keep the billing alarm (00.04)  
    ⇒ OCUs bill while idle  
  - Domain: 3 dedicated masters + Multi-AZ, alarms on JVM pressure and k-NN circuit breaker  
    ⇒ prevents split brain and GC-induced node drops  

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| OpenSearch Serverless | OCU-billed collections, AWS-managed shards | No cluster ops; KB quick-create; hybrid search; IAM + policies | Idle OCU floor; fewer knobs; delayed visibility | Bedrock KB default; steady traffic; small team |
| OpenSearch managed domain | Node-based cluster with k-NN plugin | Every knob: IVF, on_disk, ISM, UltraWarm, plugins | Shard sizing, JVM, upgrades, blue/green | Large or tuned workloads; existing OpenSearch ops |
| Aurora PostgreSQL + pgvector | Postgres + HNSW / IVFFlat | Vectors join business rows; ACID; SQL filters; Aurora Serverless v2 can auto-pause to 0 ACU when idle | Index RAM bound; weaker lexical relevance than BM25 engines | Data already in Postgres; modest corpus |
| S3 Vectors | Vector buckets + indexes in S3 | Lowest storage cost; no compute to run; KB-supported | Higher latency than in-memory; no BM25 hybrid; check quotas | Large, cold, cost-first corpora |

- Default: OpenSearch Serverless behind the KB, unless
  - traffic is low and spiky ⇒ S3 Vectors (no idle floor)
  - the data lives in Postgres ⇒ pgvector
  - you need IVF / on_disk / ISM or run at very large scale ⇒ managed domain
- Deciding variable: idle cost vs operational control
  - Serverless = pay a floor to skip ops; domain = pay in engineer time to tune

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Surprise bill | Dev collection left running (lecture 17) | Billing alarm; Cost Explorer by service | Destroy collection; standby DISABLED for dev; max OCU cap |
| 403 on every call | IAM allows `aoss:APIAccessAll` but data-access policy misses the role (or vice versa) | 403 with "no permissions" from AOSS | Add role to data-access policy; check both gates |
| KB creation fails | Index missing, wrong field names, or dims ≠ embedding dims | KB create error / ingestion failures per doc | Create index first with the shared contract |
| Fewer than k hits | Post-filtering with a selective filter | Result count < k | Filter inside `knn` (efficient filtering) |
| Partial bulk failure ignored | `_bulk` HTTP 200 treated as success | Doc counts lower than expected | Parse items; retry 429/5xx; dead-letter 4xx |
| Cluster red / node drops (domain) | Too many shards, JVM pressure, 2 masters | ClusterStatus.red, JVMMemoryPressure ≥ 95% | 3 dedicated masters; shard sizing; bigger heap nodes |
| k-NN circuit breaker | Graphs exceed native memory | Circuit breaker metric; indexing rejected | Quantize / on_disk; more RAM; fewer replicas of cold indexes |
| Hybrid scores nonsense | Hybrid query without the pipeline | Erratic ranking, BM25 dominates | Pass `search_pipeline`; normalize scores |

## 6. Interview questions

**Q1:** Serverless collection or managed domain for a Bedrock KB?

**L4 answer**
- Serverless: no nodes or shards, KB quick-create, scales in OCUs
- Domain: more control, more ops

**L5 extra**
- Serverless bills a minimum OCU floor while idle ⇒ wrong for tiny, spiky workloads
- Domain unlocks IVF, on_disk compression, ISM, and shard layout for large corpora
- Decide by traffic shape and team: steady traffic + no ops team ⇒ Serverless

**Q2:** Why three dedicated master nodes?

**L4 answer**
- Masters manage cluster state; three give a quorum of two
- One master = single point of failure; two cannot elect after one fails

**L5 extra**
- Dedicated masters keep cluster-state work off busy data nodes ⇒ fewer timeouts under load
- Size masters by shard count, not data volume
- Multi-AZ with standby places masters across three AZs

**Q3:** How do you size shards for a domain?

**L4 answer**
- 10–30 GiB per shard for search, 30–50 GiB for logs (AWS guidance)
- Primary count fixed at creation

**L5 extra**
- Too many shards ⇒ heap and cluster-state overhead; too few ⇒ slow recovery and hotspots
- For vectors, memory per node (graphs off-heap) binds before shard size
- Use rollover + ISM for growing indexes instead of oversizing up front

**Q4:** What are the three Serverless policies and what does each gate?

**L4 answer**
- Encryption: which key encrypts the collection
- Network: from where the endpoint is reachable
- Data access: which principals can do what on indexes and the collection

**L5 extra**
- Encryption must exist before the collection, and the key is fixed
- IAM `aoss:APIAccessAll` AND a data-access rule are both required
- Private collections reach Bedrock through `SourceServices: bedrock.amazonaws.com`

**Q5:** Explain efficient filtering in k-NN.

**L4 answer**
- Put the filter inside the `knn` clause
- Avoids post-filtering, which can return fewer than k

**L5 extra**
- The engine switches between exact search over matching docs (selective filter) and filtered HNSW (loose filter)
- faiss 2.9+ and lucene support it
- For tenant isolation at scale, also consider index-per-tenant to avoid noisy neighbours

**Q6:** How do you run hybrid search in OpenSearch?

**L4 answer**
- `hybrid` query with a `match` and a `knn` sub-query
- A search pipeline normalizes and combines scores

**L5 extra**
- BM25 is unbounded, k-NN scores bounded ⇒ min-max normalization before the weighted mean
- Weights follow sub-query order; tune on a golden set
- RRF (2.19+) avoids weights; reranking on top of either improves precision

**Q7:** Bulk indexing returns 200 but documents are missing. Why?

**L4 answer**
- `_bulk` reports failures per item
- Check `errors` and each item's status

**L5 extra**
- Retry only 429 / 5xx with backoff; 4xx (mapping, dims) never succeeds on retry
- On Serverless, writes are not instantly searchable ⇒ do not "read your write" right after bulk
- Keep ids stable so retries are upserts, not duplicates

**L5-only Q8:** Your KB retrieval latency spikes every morning. Diagnose.

**L5 answer**
- Serverless: search OCUs scaling from the floor ⇒ check OCU metrics against traffic
- Domain: graphs evicted from native memory ⇒ cold loads; use warmup, more RAM
- Segment count high after nightly ingestion ⇒ force_merge in a maintenance window
- Measure p99 per stage: embedding, OpenSearch, rerank, LLM

**L5-only Q9:** Move a 100M-vector index from Serverless to a domain to cut cost. Plan it.

**L5 answer**
- Size: 100M × (1.1 × (4·1024 + 8·16)) ≈ 465 GB native graph memory float32 ⇒ use on_disk 32x or fp16
- Build the new index in parallel (blue/green); re-ingest from the source of truth, not by copying graphs
- Dual-read a sample, compare recall@k and p99, then switch the KB (new data source / KB) or the app alias
- Keep Serverless until rollback window closes

**L5-only Q10:** Design tenant isolation for a multi-tenant RAG store.

**L5 answer**
- Small tenants: shared index + mandatory tenant filter inside `knn` + data-access per role where possible
- Large tenants: index or collection per tenant ⇒ isolation, separate deletion, noisy-neighbour control
- Enforce the tenant filter server-side (never trust client filters); KB metadata filters do the same at retrieval
- Trade-off: per-tenant indexes multiply shards/OCUs
