## 0. One-minute version
- What
  - Bedrock model customization = train a private copy of a base model on your data
  - Types: fine-tuning (labeled pairs), continued pre-training (unlabeled text), distillation (teacher → student), reinforcement fine-tuning (grader-driven)
- Why
  - Consistent style, format, or domain behavior that prompting cannot reach at acceptable cost
  - A smaller tuned model can replace a larger general one (cheaper, faster)
- How
  → JSONL dataset to S3 (`customization/train/`)  
  → `CreateModelCustomizationJob` (base model, hyperparameters, service role, output S3)  
  → poll until `Completed`; read loss metrics in S3  
  → serve it: provisioned throughput (most models) or on-demand deployment (some models)  
  → Converse with `modelId` = provisioned model ARN  
- Catch
  - Fine-tuning teaches behavior, not facts that change ⇒ RAG for knowledge
  - Serving usually means provisioned throughput, billed per hour while it exists
  - Data quality dominates: hundreds to thousands of clean examples (order of magnitude)
- 🗣 "Prompt first, RAG for knowledge, fine-tune for behavior."
- 🗣 "The training job is cheap compared with the provisioned throughput you forget to delete."

## 1. Concept

### 1.1 Why customize
- Prompting limits
  - Long instructions and many examples on every call cost tokens and latency
  - Some styles or formats stay inconsistent even with good prompts
- Customization moves that behavior into weights
  - Shorter prompts, more consistent output, sometimes a smaller model
- Limit: weights freeze at training time
  ⇒ facts that change weekly belong in retrieval (02.x)  

### 1.2 Picture

```
S3 a-ai-data-<acct>/customization/
   train/train.jsonl ─┐
   validation/val.jsonl ┤
                        ▼
CreateModelCustomizationJob ── role a-customization-role (reads train/, writes output/, KMS)
   base model + hyperparameters
                        │  hours (order of magnitude)
                        ▼
custom model  arn:...:custom-model/...          + metrics in customization/output/
                        │
   ┌────────────────────┴─────────────────────┐
   ▼                                          ▼
CreateProvisionedModelThroughput      CreateCustomModelDeployment (on-demand, some models)
   arn:...:provisioned-model/...          arn:...:custom-model-deployment/...
                        │
                        ▼
Converse(modelId = provisioned/deployment ARN)
```

### 1.3 Customization types
- Fine-tuning (`FINE_TUNING`)
  - Labeled input → output pairs
  - Teaches a task, style, or format (classification labels, a brand voice, a JSON shape)
- Continued pre-training (`CONTINUED_PRE_TRAINING`)
  - Unlabeled domain text (manuals, filings)
  - Shifts vocabulary and domain familiarity; needs far more data; supported by fewer models
- Distillation (`DISTILLATION`)
  - A large teacher model generates answers for your prompts; a smaller student learns them
  - Can use invocation logs as the prompt source
  - Goal: teacher-like quality at student price and latency on your task
- Reinforcement fine-tuning (`REINFORCEMENT_FINE_TUNING`)
  - A grader (Lambda) scores outputs; training rewards higher scores
  - Newer; only some models (check model support)
- Which models support which type: `ListFoundationModels(byCustomizationType=...)` per Region

### 1.4 LoRA in one paragraph
- Full fine-tuning updates every weight
  ⇒ a full copy of the model per task; expensive to train and to store  
- LoRA (low-rank adaptation) freezes the base weights and learns two small matrices per layer whose product (rank r, e.g. 8–64) approximates the weight update
  - Trainable parameters drop by orders of magnitude (order of magnitude: under 1% of the model)
  - Training needs less GPU memory; adapters are megabytes, not gigabytes
  - Many adapters can share one base model at serving time
- Bedrock does not expose the method as a knob; the service picks the technique per model
  - Self-managed LoRA → SageMaker or open-source (PEFT); Custom Model Import brings weights into Bedrock

### 1.5 Data format
- JSONL: one JSON object per line, UTF-8
- Format depends on the base model (check the model's customization page)
  - Prompt/completion (older text models): `{"prompt": "...", "completion": "..."}`
  - Conversation (Nova and newer): `{"schemaVersion": "bedrock-conversation-2024", "system": [{"text": ...}], "messages": [{"role": "user", ...}, {"role": "assistant", ...}]}`
  - Continued pre-training: `{"input": "<raw text>"}`
- Validation set: separate file, same format, never overlapping with training
- Quotas: maximum records, file size, and tokens per record are per model ⇒ check the quotas page
- Quality rules
  - Outputs must be exactly what you want the model to produce
  - Cover edge cases and refusals; deduplicate; remove PII (04.02)

### 1.6 Hyperparameters
- Passed as a string map in `hyperParameters`; names and ranges are per model
- `epochCount`: passes over the data
  - More = fits better, until it memorizes (overfits)
- `batchSize`: examples per update
  - Larger = smoother updates, more memory; some models fix it
- `learningRate`: update step size
  - Too high = unstable loss; too low = no change
- `learningRateWarmupSteps` (some models): ramp-up steps
- Read training vs validation loss
  - Both falling ⇒ learning
  - Validation rising while training falls ⇒ overfitting ⇒ fewer epochs or more data

### 1.7 Serving a custom model
- Provisioned throughput
  - Buy model units (MUs); no commitment (hourly), 1-month, or 6-month terms
  - Required for most custom models; billed per hour while it exists, used or not
  - Call with `modelId = provisioned model ARN`
- On-demand deployment (`CreateCustomModelDeployment`)
  - Pay per token for supported custom models (check model support)
- Custom Model Import: bring your own open-weight model (Llama, Mistral, ...) and serve it on demand
- Cost order of magnitude: provisioned throughput for one model unit costs tens of dollars per hour for larger models (pricing page; verify)
  ⇒ delete it when idle; tag it; alarm on it (00.04 billing alarm)  

## 2. When to use / not
- Fine-tune when
  - A narrow, repeated task with a stable target output (format, tone, labels)
  - Prompt + few-shot is close but too long, too slow, or too inconsistent
  - Volume is high enough to pay for serving
- Continued pre-training when
  - Heavy domain vocabulary the base model handles poorly, with lots of unlabeled text
- Distillation when
  - A large model already works and you need its quality cheaper and faster
- Do NOT fine-tune when
  - The problem is missing or changing knowledge ⇒ RAG
  - You have fewer than ~hundreds of good examples (order of magnitude)
  - Prompting was not tried seriously first
  - Traffic is low ⇒ provisioned throughput will cost more than the larger model on demand

## 3. Knobs and best practices
- Prove the need first
  - Baseline with prompt engineering (01.05) and RAG on a golden set (04.03)
- Data
  - Clean, deduplicated, representative; hold out a validation and a test set
  - Strip PII; encrypt with the CMK; keep the dataset versioned in S3
- Job
  - `clientRequestToken` for idempotent job creation
  - Service role scoped to `customization/train/` read and `customization/output/` write
  - `vpcConfig` when data must not leave the VPC path
  - Tags on job and custom model for cost tracking
- Evaluate
  - Compare the custom model against the prompt baseline on the same test set before serving
- Serving
  - No-commitment provisioned throughput for tests; delete immediately after
  - Commit only after measuring utilization
- Lifecycle
  - Base models get deprecated ⇒ plan re-training on a newer base

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Prompt engineering | Instructions + examples at request time | Minutes to iterate; no training; works on any model | Tokens per call; consistency limits | Always first |
| RAG | Retrieve documents at request time (02.x) | Fresh, citable knowledge; access control per document | Retrieval quality limits answers; more moving parts | Knowledge is large, private, or changing |
| Fine-tuning | Train weights on labeled pairs | Consistent behavior; shorter prompts; smaller model possible | Data prep; training time; provisioned serving cost; stale knowledge | Stable task/format at high volume |
| Continued pre-training | Train on unlabeled domain text | Domain vocabulary and familiarity | Lots of data; few models; still no fresh facts | Specialized domain language |
| Distillation | Teacher outputs train a student | Large-model quality at small-model cost | Needs a teacher that already works; per-task | Cost/latency reduction of a working pipeline |

- Deciding variable: is the gap knowledge or behavior?
  - Knowledge → RAG
  - Behavior at high volume → fine-tune or distill
- Default: prompt engineering, then RAG for knowledge; fine-tune only when a measured behavior gap remains at volume

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Job fails at validation | Wrong JSONL schema for the base model, record too long | Job `Failed`, `failureMessage` | Validate locally against the model's format and limits |
| Access denied | Role cannot read train/ or write output/, or KMS | `Failed` with S3/KMS error | Fix role policy, KMS grant, trust conditions |
| Overfitting | Too many epochs, small data | Validation loss rises | Fewer epochs, more data, early stop |
| No improvement | Bad or inconsistent labels | Eval equals baseline | Clean data; more examples of hard cases |
| Knowledge goes stale | Facts baked into weights | Wrong answers after changes | Move facts to RAG |
| Idle provisioned throughput | Forgot to delete | Bill; `InService` with no invocations | Delete; tag; alarm; no-commitment for tests |
| Base model deprecated | Lifecycle `LEGACY` | Lifecycle alarm | Re-train on a newer base |

## 6. Interview questions

**Q1:** Fine-tuning vs RAG vs prompt engineering: how do you choose?

**L4 answer**
- Prompting first: cheapest, fastest
- RAG when the model lacks or needs fresh knowledge
- Fine-tuning when behavior (style, format) must be consistent and prompting is not enough

**L5 extra**
- Deciding variable: knowledge gap vs behavior gap
- Fine-tuning has a serving cost (provisioned throughput) that only pays off at volume
- They combine: a fine-tuned model can still use RAG

**Q2:** What is LoRA and why is it cheaper?

**L4 answer**
- Freeze the base model, train small low-rank adapter matrices
- Far fewer trainable parameters

**L5 extra**
- Less GPU memory and smaller artifacts (MB); many adapters share one base at serving
- Quality is close to full fine-tuning for many tasks, not all
- On Bedrock the technique is managed; you control data and hyperparameters

**Q3:** How do you serve a fine-tuned Bedrock model?

**L4 answer**
- Buy provisioned throughput and call its ARN with Converse

**L5 extra**
- Some models support on-demand deployment of custom models (check support)
- No-commitment PT for testing; delete it after
- Tag and alarm: PT bills hourly whether used or not

**Q4:** What do epochCount, batchSize, and learningRate do?

**L4 answer**
- Epochs = passes over data; batch = examples per update; learning rate = step size

**L5 extra**
- Watch train vs validation loss to detect overfitting
- Tune epochs first; learning rate when loss is unstable
- Ranges and defaults differ per base model

**Q5:** What does a good fine-tuning dataset look like?

**L4 answer**
- JSONL in the base model's format, clean and representative, with a validation split

**L5 extra**
- Outputs are the exact target, including refusals and edge cases
- Deduplicated, PII-free, versioned in S3, encrypted
- Hundreds to thousands of examples for a narrow task (order of magnitude)

**L5-only Q6:** Your RAG assistant is accurate but slow and expensive on a large model. Options?

**L5 answer**
- Measure where time goes: retrieval, long context, generation
- Cheaper first: prompt caching, shorter context, smaller model with better prompts
- Distill the large model's answers into a smaller one using invocation logs as prompts
- Serve the student via provisioned throughput only if volume keeps utilization high
- Trade-off: lower per-call cost vs training effort, PT commitment, and retraining on base-model updates
