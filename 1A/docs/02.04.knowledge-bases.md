## 0. One-minute version
- What
  - A managed RAG pipeline: data source → parse → chunk → embed → vector store, plus retrieval and generation APIs
- Why
  - Removes the ingestion plumbing (crawling, change detection, chunking, embedding, upserts, deletes)
  - One API call returns a grounded answer with citations
- How
  - Ingestion job ("sync") per data source: only new, changed, or deleted files are processed
  - `Retrieve` = search only (you build the prompt)
  - `RetrieveAndGenerate` = search + prompt + model + citations, with `sessionId` for follow-ups
  - Knobs per query: `numberOfResults`, `overrideSearchType` (HYBRID / SEMANTIC), metadata `filter`, reranking, guardrail, prompt template
- Catch
  - The vector index must exist with the right fields and dims before the KB (bring-your-own store)
  - Chunking is fixed per data source ⇒ change = new data source + re-ingest
  - Sync is not automatic for S3 ⇒ you trigger it (schedule or event)
  - One running ingestion job per data source ⇒ concurrent triggers get `ConflictException`
  - `RetrieveAndGenerate` is convenient but less controllable than `Retrieve` + Converse
- 🗣 "A Knowledge Base is ingestion-as-a-service plus two APIs: Retrieve if you own the prompt, RetrieveAndGenerate if you don't."
- 🗣 "Sync is incremental, but nothing syncs until you start a job."
- 🗣 "Metadata filters are your authorization boundary inside a shared index; enforce them server-side."

## 1. Concept

### 1.1 Why managed RAG
- The pain
  - DIY RAG = crawler + parser + chunker + embedder + upsert + delete detection + retries + monitoring
  - Most bugs live in ingestion: stale vectors, orphans after deletes, duplicates after retries
- Prior art
  - LangChain / LlamaIndex pipelines on your compute
  - Kendra: managed enterprise search, connectors, no generation step
- How a KB helps
  - Change detection per document ⇒ incremental sync
  - Parsing, chunking, embedding configured declaratively (02.03)
  - Retrieval API with hybrid search, filters, reranking; generation API with citations
- Common use cases
  - Internal Q&A over S3 / Confluence / SharePoint
  - The retrieval tool behind a Bedrock Agent (06.x)
  - Customer-support assistants with source links
- Limits
  - Fixed pipeline stages; custom logic only via parsing prompts and a post-chunking Lambda
  - Quotas on file size, documents per job, and metadata size (check the quotas page)

### 1.2 Picture

```
INGESTION (StartIngestionJob, async)
 S3 kb-docs/  ──►  scan + change detection  ──► parse ──► chunk ──► [Lambda] ──► embed (Titan V2) ──► OpenSearch a-kb-index
 + <file>.metadata.json                         (02.03)   (02.03)                   (02.01)            (02.02)
                                                  KB role a-kb: s3:GetObject, bedrock:InvokeModel, aoss:APIAccessAll, kms

QUERY
 app ──Retrieve────────────► embed query ─► kNN / hybrid + filter ─► [rerank] ─► chunks + scores + locations
 app ──RetrieveAndGenerate─► [query decomposition] ─► Retrieve ─► prompt ($search_results$) ─► LLM ─► [guardrail]
                                                                                    └─► answer + citations + sessionId
```

### 1.3 Ingestion: data source to vectors
- Data source = where documents come from + how they are processed
  - Types: S3, web crawler, Confluence, SharePoint, Salesforce, custom (direct ingestion API)
  - One KB can have several data sources (e.g. one per chunking strategy or per prefix)
- Ingestion job  
  → scan the source  
  → compare with the last sync (new / modified / deleted)  
  → parse, chunk, embed only what changed  
  → upsert vectors; delete vectors of removed files  
  - Statistics: scanned, new indexed, modified indexed, deleted, failed, skipped (unchanged)
  - `COMPLETE` can still contain failed documents ⇒ read `numberOfDocumentsFailed` + `failureReasons`
- `dataDeletionPolicy`
  - `DELETE`: removing the data source removes its vectors
  - `RETAIN` (default): vectors stay ⇒ orphans that still answer queries
- Encryption: data source `serverSideEncryptionConfiguration` (transient data) with the CMK

### 1.4 Retrieve vs RetrieveAndGenerate

| | `Retrieve` | `RetrieveAndGenerate` |
|---|---|---|
| Returns | chunks, scores, locations, metadata | answer, citations, `sessionId` |
| Prompt | yours | template with `$search_results$` |
| Model call | yours (Converse, any model, streaming, tools) | Bedrock's, one model per call |
| Conversation | you manage history | `sessionId` keeps context |
| Use when | agents, custom prompts, multi-source fusion, evals | quick grounded Q&A with citations |

- Streaming variant: `RetrieveAndGenerateStream`
- Default: `Retrieve` + Converse in production services, unless built-in citations and sessions are enough

### 1.5 Search type, filters, reranking
- `numberOfResults`: 1–100, default 5
  - Hierarchical chunking dedupes children into parents ⇒ may return fewer
- `overrideSearchType`
  - `SEMANTIC`: vector only
  - `HYBRID`: vector + keyword on the text field; only for stores that support it (OpenSearch, and some others; check the KB docs)
  - Unset: Bedrock picks
- Metadata filters
  - Sidecar `s3://…/doc.pdf.metadata.json` = `{"metadataAttributes": {"dept": "hr", "year": 2025}}`
  - Operators: `equals`, `notEquals`, `in`, `notIn`, `greaterThan[OrEquals]`, `lessThan[OrEquals]`, `startsWith`, `stringContains`, `listContains`, `andAll`, `orAll`
  - `andAll` / `orAll` need at least two members
  - Applied inside the vector store query (pre-filter), not after
  - Implicit filtering (`implicitFilterConfiguration`): a model derives filters from the query using attribute descriptions
- Reranking (lecture 81 preview)
  - `rerankingConfiguration.bedrockRerankingConfiguration`: reranker `modelArn`, `numberOfRerankedResults`, metadata selection
  - Retrieve wide (e.g. 25), rerank to the top 5
  - Models: `amazon.rerank-v1:0`, `cohere.rerank-v3-5:0` (Region availability varies)
  - Cost: reranker charge per query + latency

### 1.6 Generation: prompt template, citations, sessions, guardrails
- Prompt template (`generationConfiguration.promptTemplate.textPromptTemplate`)
  - `$search_results$` is required; `$query$` and `$output_format_instructions$` are available
  - Dropping `$output_format_instructions$` can break citation parsing
  - Instruct "answer only from the results; say you don't know otherwise"
- Citations
  - Each citation = a span of the generated text + the retrieved references (text, location, metadata)
  - Show them to users; log them for evals (faithfulness, 04.03)
- Sessions
  - First call: no `sessionId`; Bedrock returns one
  - Follow-ups: pass it back ⇒ Bedrock rewrites the follow-up with conversation context
  - Optional `sessionConfiguration.kmsKeyArn`; sessions expire (check the docs for the window)
- Guardrails (04.01)
  - `generationConfiguration.guardrailConfiguration { guardrailId, guardrailVersion }`
  - Response `guardrailAction = INTERVENED` when it blocked or masked
- Query decomposition
  - `orchestrationConfiguration.queryTransformationConfiguration.type = QUERY_DECOMPOSITION`
  - Splits compound questions into sub-queries before retrieval (02.03 §1.9)

### 1.7 Supported stores and KB types
- Vector stores (`storage_configuration.type`)
  - OpenSearch Serverless (quick-create default), OpenSearch managed cluster
  - Aurora PostgreSQL (pgvector, `RDS`), Neptune Analytics (GraphRAG), S3 Vectors
  - Pinecone, Redis Enterprise Cloud, MongoDB Atlas (secrets in Secrets Manager)
- Field mapping: vector field, text field, metadata field (plus primary key for RDS)
- KB types: `VECTOR`, `KENDRA` (Kendra GenAI index), `SQL` (structured, §1.8)
- Embedding config: model ARN + `dimensions` + `embedding_data_type` (`FLOAT32` / `BINARY`)

### 1.8 Structured data: text-to-SQL KBs
- Lecture 38; doc only here
- Mechanism  
  → KB type `SQL`, query engine = Amazon Redshift (provisioned or Serverless)  
  → storage = Redshift databases or AWS Glue Data Catalog tables  
  → the KB generates SQL from the question, runs it, returns rows (`sqlLocation` in results)  
- Accuracy levers
  - Table and column descriptions, inclusion/exclusion of tables and columns
  - Curated queries: example question → SQL pairs
  - Query execution timeout
- Use when answers are aggregations or lookups over tables
- Limit: generated SQL can be wrong yet plausible ⇒ least-privilege read-only DB user, curated examples, review logs

### 1.9 Keeping it fresh
- Lecture 80
- Options
  - Scheduled sync: EventBridge Scheduler → `StartIngestionJob` (hourly / daily)
  - Event-driven: S3 event → Lambda → `StartIngestionJob` with a `clientToken` (idempotent on redelivery)
  - Direct ingestion: `IngestKnowledgeBaseDocuments` for specific documents, seconds-level freshness (custom and S3 data sources)
  - Managed connectors expose a sync schedule in newer API versions (check the docs)
- The concurrency catch  
  → an event arrives while a job runs  
  ⇒ `ConflictException`  
  ⇒ the running job may have scanned before the change landed  
  → defer: queue the event and retry, or rely on the next scheduled sweep  
- Code: `service.handle_s3_event`

## 2. When to use / not
- Use a Bedrock KB when
  - Documents live in supported sources and standard chunking/parsing fits
  - You want citations and incremental sync without running pipelines
  - Agents need a retrieval tool with IAM-governed access
- Use DIY RAG when
  - Custom retrieval logic: multi-index fusion, custom rerankers, graph traversal, per-chunk ACL joins
  - Exotic sources or formats the KB can't parse even with a Lambda
  - You need full control of ingestion latency and batching
- Use Q Business / Kendra when
  - The goal is an employee assistant with many SaaS connectors and per-user ACLs out of the box
- Don't use RAG when the answer is an aggregation over tables ⇒ SQL KB or text-to-SQL

## 3. Knobs and best practices

| Knob | Values | Trades | Change when |
|---|---|---|---|
| Embedding model + dims | Titan V2 256 / 512 / 1024; Cohere | recall vs storage | memory cost or recall issues (requires a new KB) |
| Chunking | FIXED / HIERARCHICAL / SEMANTIC / NONE | precision vs context (02.03) | golden-set results; immutable per data source |
| Parsing | default / FM / BDA | fidelity vs ingestion cost | tables, scans, images |
| `numberOfResults` | 1–100, default 5 | recall vs prompt tokens | answers miss facts |
| `overrideSearchType` | HYBRID / SEMANTIC | exact-term recall vs simplicity | identifier-heavy queries ⇒ HYBRID |
| Metadata filter | operators above | precision + isolation vs sidecar upkeep | multi-tenant, time-bounded queries |
| Reranking | model + numberOfRerankedResults | precision vs latency + cost | top-k precision low |
| Prompt template | custom text | grounding, tone vs citation format | hallucinations, style |
| Guardrail | id + version | safety vs latency | user-facing apps |
| `dataDeletionPolicy` | DELETE / RETAIN | clean index vs keeping vectors | almost always DELETE |

- Best practices
  - Create the index from code with a shared contract (name, fields, dims)  
    ⇒ prevents KB create failures and per-document ingestion errors  
  - Pass `clientToken` on `StartIngestionJob` and `CreateDataSource`  
    ⇒ retries and event redeliveries don't start duplicates  
  - Check job statistics, not just status  
    ⇒ `COMPLETE` with failed documents is common (bad sidecars, size limits)  
  - Put tenant / ACL attributes in sidecars and add the filter server-side on every query  
    ⇒ prevents cross-tenant leakage in a shared index  
  - Evaluate with Bedrock KB evaluations or RAGAS on a golden set before changing knobs (04.03)  
    ⇒ prevents tuning by anecdote  

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Knowledge Bases | Managed ingestion + Retrieve / RetrieveAndGenerate | No pipeline code; incremental sync; citations; IAM; many stores | Fixed stages; chunking immutable; sync to trigger yourself | Default for RAG on AWS |
| DIY RAG (LangChain / LlamaIndex + OpenSearch) | Your pipeline on your compute | Total control: splitters, fusion, rerankers, ACL joins | You own ingestion bugs, scaling, monitoring | Custom retrieval logic or sources |
| Amazon Q Business | Managed enterprise assistant | 40+ connectors, per-user ACLs, ready UI | Less control of prompts and models; per-user pricing | Employee assistant over SaaS data |
| Amazon Kendra (GenAI index) | Managed enterprise search | Connectors, ACL-aware ranking; usable as a KB type | Search-only; index pricing | Existing Kendra estate; search UI |

- Default: Bedrock KB with `Retrieve` + Converse, unless
  - you need retrieval logic the KB can't express ⇒ DIY
  - the product is an internal assistant with SaaS connectors and per-user ACLs ⇒ Q Business
- Deciding variable: how much of the pipeline must be custom

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| KB create fails | Index missing / wrong field names / dims mismatch / role lacks data access | Create error | Apply order; shared contract; data-access policy |
| Stale answers | No sync after document changes | Citations show old content | Event + scheduled sync; direct ingestion |
| Duplicate / missed sync | Concurrent triggers ⇒ ConflictException | Deferred events; job history | Queue + retry; scheduled sweep; clientToken |
| Silent document failures | Bad sidecar JSON, oversized files, unsupported types | `numberOfDocumentsFailed` > 0 | Read failureReasons; fix and resync |
| Orphan vectors | Data source deleted with RETAIN | Answers cite deleted docs | DELETE policy; clean the index |
| Cross-tenant leak | Shared index, filter not enforced | Audit retrieval logs | Server-side mandatory filters; index per tenant |
| Fewer results than asked | Hierarchical chunking parent dedupe | Result count < numberOfResults | Expected; raise numberOfResults |
| Citations missing | Custom template dropped `$output_format_instructions$` | Empty `citations` | Restore the placeholder |
| Guardrail blocks valid answers | Over-strict policy | `guardrailAction = INTERVENED` rate | Tune guardrail (04.01) |

## 6. Interview questions

**Q1:** Walk through what happens when you sync a Knowledge Base.

**L4 answer**
- `StartIngestionJob` scans the data source
- New/changed files are parsed, chunked, embedded, and upserted; deleted files' vectors are removed

**L5 extra**
- Change detection makes it incremental ⇒ cost scales with changes, not corpus size
- One job per data source at a time ⇒ design triggers for `ConflictException`
- `COMPLETE` ≠ all succeeded: check `numberOfDocumentsFailed` and `failureReasons`

**Q2:** Retrieve or RetrieveAndGenerate?

**L4 answer**
- Retrieve returns chunks; you build the prompt and call the model
- RetrieveAndGenerate does all of it and returns citations and a session

**L5 extra**
- Retrieve for agents, custom prompts, streaming with Converse, multi-source fusion, and evaluation
- RetrieveAndGenerate for fast delivery with built-in citations and session handling
- Both accept the same retrieval knobs (filters, hybrid, reranking)

**Q3:** How do metadata filters work, and what are they good for?

**L4 answer**
- Sidecar `<file>.metadata.json` attributes are indexed with each chunk
- Retrieve passes a `filter` (equals, in, andAll, …)

**L5 extra**
- Filters run inside the store query ⇒ no post-filter shortfall
- Use for tenant isolation and recency; enforce server-side, never from client input
- Sidecar changes need a sync; size limits apply (check quotas)

**Q4:** When do you add reranking?

**L4 answer**
- When top results are relevant-ish but not the best
- Retrieve more candidates, rerank, keep the top few

**L5 extra**
- Cross-encoder scores query and chunk jointly ⇒ better precision than embedding similarity
- Costs a reranker call and latency per query
- Pair with hybrid search: hybrid widens recall, reranker sharpens precision

**Q5:** How do you keep a KB up to date?

**L4 answer**
- Trigger `StartIngestionJob` on a schedule or on S3 events

**L5 extra**
- Event path: S3 → Lambda → StartIngestionJob with clientToken from (key, sequencer)
- Conflicts while a job runs ⇒ defer and retry, plus a scheduled sweep for completeness
- `IngestKnowledgeBaseDocuments` for seconds-level updates of specific documents

**Q6:** How do you attach a guardrail and a custom prompt to RetrieveAndGenerate?

**L4 answer**
- `generationConfiguration.guardrailConfiguration` with id + version
- `promptTemplate.textPromptTemplate` with `$search_results$`

**L5 extra**
- Keep `$output_format_instructions$` or citations break
- Use a published guardrail version, not DRAFT, in production
- Check `guardrailAction` and log interventions for tuning

**Q7:** When is a SQL Knowledge Base the right choice?

**L4 answer**
- Questions over tables (counts, sums, filters)
- The KB generates SQL against Redshift and returns rows

**L5 extra**
- Accuracy depends on table/column descriptions and curated example queries
- Run under a read-only, least-privilege DB user; set an execution timeout
- Vector RAG cannot aggregate reliably ⇒ route by question type

**L5-only Q8:** Design a multi-tenant RAG service on Bedrock KB.

**L5 answer**
- Option A: shared KB + index, `tenant` attribute in sidecars, server-side `equals(tenant)` filter on every call
- Option B: KB (or data source + index) per large tenant ⇒ isolation, separate deletion, separate cost
- Ingestion: tenant prefix per data source; sync per tenant
- Audit: log every retrieval with tenant and citations; test for leakage in CI

**L5-only Q9:** Answers became wrong after a document update. Debug it.

**L5 answer**
- Was the job run? Check `list_ingestion_jobs` for a job after the upload
- Did it process the file? Statistics: modified indexed vs skipped vs failed
- Do old and new chunks both exist? Possible if the file was renamed (new id) without deleting the old
- Do citations point to the old version? Then sync or delete/re-add; consider direct ingestion for hot docs

**L5-only Q10:** Bedrock KB vs DIY: the team wants LangChain. Decide.

**L5 answer**
- List required capabilities: sources, parsing, chunking, filters, hybrid, rerank, citations, freshness SLA
- If the KB covers them ⇒ KB: less code, fewer ingestion bugs, IAM, managed sync
- If not (custom fusion, ACL joins, unsupported sources) ⇒ DIY with OpenSearch, and own ingestion SLOs
- Hybrid path: KB for ingestion + Retrieve, LangChain/agents for orchestration on top
