## 0. One-minute version
- What
  - Chunking = splitting documents into the units that get embedded, retrieved, and shown to the model
  - Pre-retrieval = reshaping the user's question before search (rewrite, decompose, HyDE)
- Why
  - One vector per whole document blurs many topics into one point ⇒ poor matching
  - The prompt has a token budget ⇒ send the relevant passage, not the book
- How (Bedrock KB `chunkingStrategy`)
  - `FIXED_SIZE`: `maxTokens` + `overlapPercentage` (console default 300 / 20%)
  - `HIERARCHICAL`: parent + child `maxTokens`, `overlapTokens` (default 1500 / 300 / 60); match child, return parent
  - `SEMANTIC`: cut where embedding distance between sentences jumps (`breakpointPercentileThreshold`, `bufferSize`, `maxTokens`)
  - `NONE`: one chunk per file (pre-chunked or Lambda-chunked)
  - Custom Lambda (`POST_CHUNKING`) for your own logic or metadata
- Catch
  - Chunking is fixed per data source (KB user guide) ⇒ changing it = new data source + full re-ingest
  - Small chunks match precisely but lose context; large chunks keep context but match vaguely
  - Hierarchical returns parents ⇒ fewer results than `numberOfResults`, more tokens per result
  - Semantic chunking calls a model at ingestion ⇒ extra cost and time
- Default: hierarchical for long structured docs, fixed size 300 / 20% as the baseline
- 🗣 "Chunk size is a precision-vs-context dial; hierarchical chunking turns it into two dials."
- 🗣 "Retrieve small, read big: match the child, hand the model the parent."
- 🗣 "Chunking is a schema decision: changing it means re-ingesting everything."

## 1. Concept

### 1.1 Why chunk
- The pain
  - Embedding models have input limits (Titan V2: 8,192 tokens) and average everything into one vector
  - A 50-page manual as one vector matches every query weakly and none strongly
  - Generation models pay per input token, and accuracy drops for facts buried mid-context ("lost in the middle", Liu et al., 2023)
- How chunking helps
  - Each chunk carries one topic ⇒ its vector sits near queries about that topic
  - Retrieval returns only the passages needed ⇒ fewer tokens, sharper answers
- What it costs
  - More chunks = more vectors to store and search
  - Boundaries cut facts in half unless overlap or structure-aware splits are used
- Common use cases
  - Manuals and policies (hierarchical), FAQs (none: one entry per chunk)
  - Transcripts and emails (semantic), code (recursive on syntax boundaries)

### 1.2 Picture

```
document ─► parse (text / FM parser / BDA) ─► chunk ─► [Lambda POST_CHUNKING] ─► embed ─► vector store
                                               │
     FIXED_SIZE      |──300──|                 │
                          |──300──|  (20% overlap)
     HIERARCHICAL    |────────── parent 1500 ──────────|
                     |c 300|c 300|c 300|c 300|c 300|      children embedded, parent returned
     SEMANTIC        |s1 s2 s3 ‖ s4 s5 ‖ s6 s7 s8|        ‖ = embedding distance above the 95th percentile
     NONE            |──────────── whole file ──────────|
```

### 1.3 Fixed size with overlap
- Mechanism  
  → slide a window of `maxTokens`  
  → advance by `maxTokens × (1 − overlap%)`  
  → each window = one chunk  
- Bedrock: `fixedSizeChunkingConfiguration { maxTokens 1–8192, overlapPercentage 1–99 }`
- Default chunking (no config) ≈ 300-token chunks that respect sentence boundaries (KB user guide)
- Strength: predictable size, cost, and latency; the baseline every other strategy must beat
- Limits
  - Ignores structure: splits tables, lists, and sentences
  - Overlap stores ~overlap% more tokens and returns near-duplicate hits
- Code note: `chunkers.fixed_size_chunks` approximates tokens by words (~1.3 tokens per English word, order of magnitude)

### 1.4 Recursive (structure-aware)
- Not a Bedrock strategy; common in LangChain / LlamaIndex, and inside custom Lambdas
- Mechanism  
  → try the coarsest separator (`\n\n` paragraphs)  
  → pieces under budget are merged greedily  
  → oversize pieces are split again with a finer separator (`\n`, `. `, space)  
- Strength: keeps paragraphs and sentences whole
- Limit: chunk sizes vary widely; headings may end up separated from their content

### 1.5 Hierarchical (parent / child)
- Mechanism  
  → split into large parent chunks (e.g. 1,500 tokens)  
  → split each parent into children (e.g. 300 tokens), with `overlapTokens` between neighbours  
  → embed children only  
  → at query time, match children, then replace each with its parent  
- Bedrock: `hierarchicalChunkingConfiguration { levelConfigurations: [parent, child], overlapTokens }`
- Strength: precise matching (small vectors) and rich context (large passages)
- Costs and limits
  - Several matching children of one parent collapse to one result ⇒ fewer results than `numberOfResults`
  - Each result is a full parent ⇒ more prompt tokens per result
  - Parent size must stay within the generator's budget × k

### 1.6 Semantic
- Mechanism  
  → split into sentences  
  → embed each sentence, with `bufferSize` neighbours on each side for stability  
  → distance between consecutive embeddings  
  → cut where the distance exceeds the `breakpointPercentileThreshold` percentile of all distances  
  → enforce `maxTokens` as a hard cap  
- Bedrock: `semanticChunkingConfiguration { maxTokens 1–8192, bufferSize 0–1, breakpointPercentileThreshold 50–99 }`
  - Console defaults: 300 / 0 / 95
  - Higher threshold ⇒ fewer breaks ⇒ larger chunks
- Strength: boundaries follow topic shifts, even without headings
- Limits
  - One embedding call per sentence (window) during ingestion ⇒ cost and time
  - Short, list-like text produces noisy distances ⇒ erratic chunks

### 1.7 None and custom Lambda
- `NONE`
  - Each file becomes one chunk
  - Use when files are already chunk-sized (one FAQ per file) or pre-chunked upstream
- Custom transformation Lambda
  - `customTransformationConfiguration { intermediateStorage.s3Location, transformations: [{ stepToApply: POST_CHUNKING, lambdaArn }] }`
  - The Lambda reads chunk batches from intermediate S3, returns modified chunks and metadata
  - Pair with `NONE` to own chunking end to end, or with any strategy to enrich metadata
  - Cost: you own the Lambda's latency, errors, and scaling during ingestion

### 1.8 Parsing before chunking
- Default parser
  - Extracts text from supported formats (txt, md, html, doc/docx, csv, xls/xlsx, pdf)
  - Tables and images in PDFs lose structure
- Foundation-model parser (`BEDROCK_FOUNDATION_MODEL`)
  - A multimodal model reads each page; optional `parsingPrompt`
  - Better tables and figures; costs model tokens per page
- Bedrock Data Automation parser (`BEDROCK_DATA_AUTOMATION`, 03.01)
  - Managed extraction of text, tables, figures; `parsingModality: MULTIMODAL` keeps images for multimodal retrieval
- The API model also lists `SMART_PARSING` and `MULTI_MODAL_EMBEDDINGS` (boto3 1.44) ⇒ check the KB parsing docs before relying on them
- Rule: fix parsing first; no chunking strategy recovers a table that was flattened into word soup

### 1.9 Pre-retrieval: query rewriting, decomposition, HyDE
- Query rewriting
  - An LLM turns a chatty, context-dependent question into a standalone search query
  - Needed in multi-turn chat ("what about the second one?")
- Query decomposition
  - Split a compound question into sub-questions, retrieve for each, merge
  - Bedrock: `orchestrationConfiguration.queryTransformationConfiguration.type = QUERY_DECOMPOSITION` in RetrieveAndGenerate (02.04)
- HyDE (Hypothetical Document Embeddings, Gao et al., 2022)  
  → LLM writes a hypothetical answer  
  → embed that answer, not the question  
  → search with it  
  - Works because answers look more like documents than questions do
  - Risk: a confidently wrong hypothesis steers retrieval off course
- Multi-query: several paraphrases, union of results (cheap recall boost)
- Cost: each technique adds an LLM call before retrieval (+hundreds of ms; order of magnitude)

### 1.10 Metadata enrichment
- Sidecar `<file>.metadata.json` in S3 ⇒ attributes for filters (department, year, tenant) (02.04)
- Contextual headers: prepend title / section path to each chunk before embedding
  - Anthropic "Contextual Retrieval" (2024) reports fewer retrieval failures by prepending chunk-specific context
- Custom Lambda adds per-chunk metadata (section, page, entity tags)
- Rule: anything users filter by must be metadata, not hoped-for text similarity

## 2. When to use / not

| Content | Strategy | Why |
|---|---|---|
| Manuals, policies, specs with sections | Hierarchical | precise match + section context |
| Uniform prose, blogs, news | Fixed 300 / 20% | simple, predictable |
| Transcripts, emails, chats | Semantic | topic shifts without headings |
| FAQs, tickets, product records | None | already one unit per file |
| Code, Markdown, special formats | Custom Lambda (recursive / syntax-aware) | boundaries need domain rules |
| Scanned PDFs, tables, slides | FM or BDA parser + any of the above | parsing is the bottleneck |

- Don't chunk when the document is short enough to be one coherent unit
- Don't rely on chunking for structured data (tables in a DB) ⇒ text-to-SQL (02.04)

## 3. Knobs and best practices

| Knob | Values | Trades | Change when |
|---|---|---|---|
| `maxTokens` (fixed) | 1–8192, default 300 | precision vs context per hit | answers miss nearby facts ⇒ larger; vague hits ⇒ smaller |
| `overlapPercentage` | 1–99, default 20 | boundary loss vs storage + duplicates | facts cut at boundaries |
| Parent / child `maxTokens` | default 1500 / 300 | context vs prompt tokens | parents overflow the prompt budget |
| `overlapTokens` | ≥ 1, default 60 | boundary loss vs duplication | same as overlap |
| `breakpointPercentileThreshold` | 50–99, default 95 | chunk count vs coherence | chunks too big ⇒ lower it |
| `bufferSize` | 0–1, default 0 | distance stability vs sharpness | noisy breaks ⇒ 1 |
| Parsing strategy | default / FM / BDA | ingestion cost vs fidelity on tables + images | tables or scans in the corpus |
| Pre-retrieval | rewrite / decompose / HyDE | latency + cost vs recall | multi-turn, compound, or vague questions |

- Best practices
  - Build a golden question set first, then compare strategies on recall@k and answer quality  
    ⇒ prevents choosing by intuition  
  - Keep `maxTokens` well under the embedding model limit  
    ⇒ prevents silent truncation  
  - Deterministic chunk ids from content + position  
    ⇒ re-ingest upserts instead of duplicating  
  - Plan the chunking choice before production ingest; test on a copy data source  
    ⇒ avoids a full re-ingest later  
  - Budget prompt tokens: k × chunk (or parent) size + instructions + answer  
    ⇒ prevents truncated context  

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Fixed size + overlap | Token window with overlap | Predictable, cheap, default-friendly | Cuts structure; duplicates | Baseline; uniform prose |
| Hierarchical | Child chunks matched, parents returned | Precision + context | Fewer results, more tokens per result | Long structured documents |
| Semantic | Breaks on embedding-distance jumps | Topic-coherent chunks | Ingestion cost; noisy on lists | Transcripts, unstructured long text |
| None | One chunk per file | No split errors | Blurry vectors for long files | Pre-chunked / short files |
| Custom Lambda | Your code after chunking | Any rule, any metadata | You operate it | Code, special formats, enrichment |
| LangChain / LlamaIndex splitters (DIY) | Library splitters in your pipeline | Many splitters (recursive, Markdown, code) | You run the whole ingestion pipeline | DIY RAG outside Bedrock KB |

- Default: hierarchical (1500 / 300 / 60) for long structured docs, unless
  - documents are short or uniform ⇒ fixed 300 / 20%
  - topics drift without headings ⇒ semantic
- Deciding variable: does a matching passage need its surrounding section to be answerable?
  - Yes ⇒ hierarchical; no ⇒ fixed

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Answer half-missing | Fact split across chunk boundary | Golden-set misses on boundary facts | Overlap; hierarchical; structure-aware split |
| Vague retrieval | Chunks too large / multi-topic | Low precision; many unrelated hits | Smaller chunks or hierarchical children |
| Context overflow | Parents × k exceed the prompt budget | Truncation, high token bills | Smaller parents; lower k; rerank |
| Fewer results than asked | Hierarchical children collapse into parents | Retrieve returns < numberOfResults | Expected; raise numberOfResults |
| Tables garbled | Default parser on complex PDFs | Retrieved text is word soup | FM or BDA parser |
| Stuck with a bad strategy | Chunking immutable per data source | Change request has no update path | New data source + re-ingest; test strategies on a copy |
| Ingestion cost spike | Semantic chunking / FM parsing on a large corpus | Bedrock bill, slow ingestion jobs | Use only on the subsets that need it |

## 6. Interview questions

**Q1:** How do you choose a chunk size?

**L4 answer**
- Start at ~300 tokens with ~20% overlap
- Smaller = precise matches, less context; larger = more context, vaguer matches

**L5 extra**
- Decide with a golden set: recall@k and answer faithfulness per configuration
- Budget the prompt: k × chunk size must fit with instructions and answer
- If answers need surrounding context, switch to hierarchical rather than just growing chunks

**Q2:** Explain hierarchical chunking and its catch.

**L4 answer**
- Parents (large) contain children (small)
- Children are embedded and matched; parents are returned to the model

**L5 extra**
- Several children of one parent dedupe to one parent ⇒ fewer results than `numberOfResults`
- Each result costs more tokens ⇒ fewer results fit
- Overlap applies between neighbours to soften boundary cuts

**Q3:** How does semantic chunking decide where to cut?

**L4 answer**
- Embed sentences, measure distance between neighbours, cut where it jumps

**L5 extra**
- Cut where distance exceeds the Nth percentile (default 95) of all distances in the doc ⇒ relative, not absolute
- `bufferSize` smooths distances with neighbour sentences
- Costs embedding calls at ingestion; `maxTokens` still caps size

**Q4:** You want to change chunking on a live Knowledge Base. What happens?

**L4 answer**
- Chunking is set per data source and can't be changed after creation
- Create a new data source with the new strategy and re-ingest

**L5 extra**
- Run old and new data sources side by side, evaluate on the golden set, then delete the old one
- `dataDeletionPolicy = DELETE` cleans vectors of the removed data source
- Budget a full re-embed: corpus tokens × embedding price

**Q5:** When do you need a custom parser?

**L4 answer**
- PDFs with tables, scans, slides, or images
- Use the FM parser or BDA parser

**L5 extra**
- Parsing errors cannot be fixed downstream by chunking or retrieval
- FM parsing costs per page ⇒ apply to the subset of documents that need it (separate data source)
- Custom parsing prompt can force Markdown tables, preserving structure for chunking

**Q6:** Query rewriting vs decomposition vs HyDE?

**L4 answer**
- Rewriting: make the query standalone and search-friendly
- Decomposition: split compound questions into sub-queries
- HyDE: embed a hypothetical answer instead of the question

**L5 extra**
- Each adds an LLM call ⇒ latency; apply conditionally (multi-turn, long questions)
- HyDE helps when questions and documents use different vocabulary; risky for factual edge cases
- Bedrock KB exposes decomposition natively (`QUERY_DECOMPOSITION`)

**L5-only Q7:** Retrieval works for prose but fails on product spec tables. Fix it.

**L5 answer**
- Diagnose: inspect retrieved chunks; flattened tables lose row/column relations
- Parse with FM/BDA into Markdown tables; keep each table within one chunk (custom Lambda or NONE per table)
- Add metadata (product, version) for filtering; consider hybrid search for model numbers
- If questions are aggregations over rows ⇒ structured store + text-to-SQL instead of RAG

**L5-only Q8:** Design an evaluation to pick a chunking strategy.

**L5 answer**
- Golden set: 100–300 real questions with labeled source passages (order of magnitude)
- Index the corpus once per strategy in separate data sources (or local pipeline)
- Metrics: recall@k / context precision, answer faithfulness and correctness (04.03), tokens per answer, ingestion cost
- Pick the cheapest strategy within the quality target; record the decision since it is costly to change

**L5-only Q9:** Chunks lack context ("it", "the above section"). What do you do?

**L5 answer**
- Contextual headers: prepend title and section path at chunking time
- Contextual retrieval: an LLM writes a 1–2 sentence context per chunk before embedding (ingestion cost up)
- Hierarchical chunking returns the surrounding section anyway
- Measure the gain; enrichment multiplies ingestion cost by roughly one LLM call per chunk
