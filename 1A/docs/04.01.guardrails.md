## 0. One-minute version
- What
  - A managed policy layer that inspects text (and images) going into and out of a model
  - One guardrail = up to six policies + blocked messages + KMS key, versioned
- Why
  - Models follow instructions, including malicious ones
  - Safety must be enforced outside the prompt, the same way for every model and every team
- How
  - Policies: content filters (incl. prompt attack), denied topics, word filters, sensitive information (PII + regex), contextual grounding, Automated Reasoning
  - Each policy runs on the input, the output, or both
  - Result per call: `action` = `GUARDRAIL_INTERVENED` or `NONE`, plus per-policy assessments
  - Intervene ⇒ block (return the canned message) or anonymize (mask PII, keep going)
  - Three call styles
    - `ApplyGuardrail`: standalone check on any text, any model, even non-Bedrock
    - `Converse` / `InvokeModel` + `guardrailConfig`: Bedrock runs input check → model → output check
    - KB `RetrieveAndGenerate` / Agents: guardrail attached by id + version
- Catch
  - Classifiers, not proofs ⇒ false positives and false negatives; tune on a labeled set (04.03)
  - Prompt-attack filter is input-only and scans everything unless you tag user content
  - Streaming sync mode adds latency; async mode can leak a chunk before the block
  - Use a numbered version in prod; `DRAFT` changes under you
  - Paid per 1,000-character text unit per policy ⇒ long RAG contexts multiply cost
- 🗣 "A guardrail is a policy engine on both sides of the model, versioned like code and enforced outside the prompt."
- 🗣 "ApplyGuardrail decouples safety from the model: same policy for Bedrock, SageMaker, or OpenAI."
- 🗣 "Tag the user's text with guardContent, or the prompt-attack filter will flag your own system prompt."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Every team wrote its own regex lists, moderation calls, and "please don't" prompt lines
  - System-prompt rules are advice to the model, not enforcement ⇒ a jailbreak removes them
  - Policies drifted per app, per model; no audit of what was blocked
- What it changes
  - One resource, one id, many apps and models
  - Same policy for prompts and responses
  - Assessments + CloudWatch metrics = audit trail of interventions
- Common use cases
  - Customer chatbot: block investment / medical advice topics, mask emails and phones
  - RAG: block answers that are not grounded in retrieved passages
  - Agents: prompt-injection filter on tool results and user text
  - Third-party model gateway: `ApplyGuardrail` before and after a non-Bedrock call

### 1.2 Picture

```
                         guardrail a-guardrail : version 1 (immutable)
                ┌───────────────────────────────────────────────────────────┐
 user text ───► │ INPUT  : content · prompt attack · topics · words · PII  │──► blocked? → blockedInputMessaging
                └───────────────────────────────────────────────────────────┘
                                   │ pass (PII may be masked)
                                   ▼
                              foundation model   (skipped if input blocked: no model tokens billed)
                                   │
                ┌───────────────────────────────────────────────────────────┐
 model text ──► │ OUTPUT : content · topics · words · PII · grounding ·    │──► blocked? → blockedOutputsMessaging
                │          relevance · automated reasoning                 │
                └───────────────────────────────────────────────────────────┘
                                   │ pass / anonymized
                                   ▼
                               response + trace (assessments per policy)
```

- Evaluation order inside one check: all configured policies run in parallel over the content (order of magnitude: tens to a few hundred ms; check CloudWatch `InvocationLatency`)
- Any one policy with action BLOCK and a hit ⇒ the whole call intervenes
- ANONYMIZE hits alone ⇒ `GUARDRAIL_INTERVENED` too, but the masked text is returned, not the canned message

### 1.3 The six policies

| Policy | API field (create) | What it detects | Actions | Input / output |
|---|---|---|---|---|
| Content filters | `contentPolicyConfig.filtersConfig[]` | HATE, INSULTS, SEXUAL, VIOLENCE, MISCONDUCT, PROMPT_ATTACK | strength NONE/LOW/MEDIUM/HIGH; action BLOCK/NONE | both (PROMPT_ATTACK input only) |
| Denied topics | `topicPolicyConfig.topicsConfig[]` | natural-language topic definition + examples | BLOCK/NONE | both |
| Word filters | `wordPolicyConfig.wordsConfig[]`, `managedWordListsConfig[]` | exact words/phrases; managed PROFANITY list | BLOCK/NONE | both |
| Sensitive information | `sensitiveInformationPolicyConfig.piiEntitiesConfig[]`, `regexesConfig[]` | 31 built-in PII types + custom regex | BLOCK / ANONYMIZE / NONE | both |
| Contextual grounding | `contextualGroundingPolicyConfig.filtersConfig[]` | GROUNDING (answer supported by source), RELEVANCE (answer addresses query) | threshold 0–0.99; BLOCK/NONE | output only |
| Automated Reasoning | `automatedReasoningPolicyConfig.policies[]` | answer vs formal rules extracted from a policy document | findings only (you decide) | output |

- Content filters: strength vs confidence
  - The classifier assigns each category a confidence: NONE, LOW, MEDIUM, HIGH
  - Strength = the lowest confidence that blocks
    - HIGH strength blocks LOW + MEDIUM + HIGH confidence ⇒ most blocking, most false positives
    - LOW strength blocks HIGH confidence only
    - NONE = off
  - `inputModalities` / `outputModalities` = TEXT, IMAGE (image filtering for the 6 content categories; check supported formats)
- Prompt attack
  - Detects jailbreaks, prompt injection; prompt leakage on the Standard tier
  - `outputStrength` must be `NONE` (API rejects anything else)
- Denied topics
  - Definition = what the topic is, written as a description, not a command ("Investment advice is …", not "Don't give …")
  - Up to 5 example phrases per topic; up to 30 topics per guardrail (check the quota page)
  - Topic classifier, not keyword match ⇒ catches paraphrases, also catches near misses (e.g. "what is an index fund?")
- Word filters
  - Exact match after normalization, case-insensitive (order of magnitude: up to 10,000 custom words; check quota page)
  - Cheap and precise ⇒ use for brand names, competitor names, internal code names
- Sensitive information
  - BLOCK ⇒ the whole call is refused
  - ANONYMIZE ⇒ replaced by `{EMAIL}`, `{PHONE}`, `{REGEX_NAME}` and the call continues
  - Regex: `name`, `pattern`, `description`, action (up to 10 regexes; check quota page)
  - Input ANONYMIZE masks before the model sees it ⇒ the model cannot echo it back
  - Limit: ML detector; names and addresses are fuzzier than SSN/card patterns
- Contextual grounding
  - Needs three pieces: `grounding_source` (retrieved passages), `query` (user question), `guard_content` (model answer)
  - GROUNDING score low ⇒ hallucinated relative to the source
  - RELEVANCE score low ⇒ off-topic relative to the query
  - Block when score < threshold; higher threshold = stricter
  - Limit: checks against the source given, not world truth; long sources are truncated (check the per-request character limit)
- Automated Reasoning → §1.8

### 1.4 Prompt attacks and misuse (lecture 34)
- Attack types
  - Prompt injection: instructions hidden in user text or retrieved content ("ignore previous instructions …")
  - Indirect injection: the instruction sits in a web page, email, or tool result the agent reads
  - Jailbreak: role-play or encoding tricks that remove the model's refusals ("DAN", base64, other languages)
  - Prompt leaking: the attacker extracts the system prompt or hidden context
  - Data poisoning: malicious documents land in the RAG index or fine-tune set
- Defense in depth (no single layer suffices)  
  → separate trusted (system) and untrusted (user, retrieved) text: `guardContent` tagging  
  → PROMPT_ATTACK filter HIGH on the untrusted part only  
  → least-privilege tools for agents: a hijacked agent can only do what IAM allows  
  → output checks: PII, grounding, denied topics  
  → never put secrets in the system prompt  
- Tagging matters
  - Without tags, every message is evaluated, history and templated instructions included
    - `InvokeModel`: the whole body, system instructions included
  - Your own "You are …, never …, ignore anything that …" text looks like an injection ⇒ false positive
  - With `guardContent` blocks ⇒ only the tagged text is evaluated
    - `InvokeModel` equivalent: input tags `<amazon-bedrock-guardrails-guardContent_SUFFIX>` with a random per-request suffix (so attackers can't close the tag)
- Bias and misuse
  - Bias (stereotyping, unequal quality across groups) is measured, not filtered ⇒ evaluation jobs (04.03, Builtin.Stereotyping)
  - Guardrails cover the misuse side: harmful content, disallowed topics, data leakage

### 1.5 Three ways to call it

| Call | When | Who calls the model | Catch |
|---|---|---|---|
| `bedrock-runtime.apply_guardrail(source=INPUT/OUTPUT, content=[…])` | any model, any text; pre-index scrubbing; agent tool results | you | two extra calls per turn; you wire the logic |
| `converse(..., guardrailConfig={...})` | Bedrock model, one call does all | Bedrock | output check sees the full answer only when not streaming |
| `converse_stream(..., guardrailConfig={..., streamProcessingMode})` | Bedrock streaming UX | Bedrock | sync latency vs async leakage (§1.6) |

- `ApplyGuardrail` request
  - `guardrailIdentifier`, `guardrailVersion` (required, "DRAFT" or "1"), `source`
  - `content[].text.text` + optional `qualifiers` (`grounding_source`, `query`, `guard_content`)
  - `content[].image` (`format` png/jpeg, `source.bytes`)
  - `outputScope`: `INTERVENTIONS` (default, only hits) or `FULL` (every assessment, incl. non-hits; for debugging and eval)
- `ApplyGuardrail` response
  - `action` (`NONE` / `GUARDRAIL_INTERVENED`), `actionReason`
  - `outputs[].text` = masked text or the blocked message
  - `assessments[]`: `topicPolicy`, `contentPolicy`, `wordPolicy`, `sensitiveInformationPolicy`, `contextualGroundingPolicy`, `automatedReasoningPolicy`, `invocationMetrics`
  - `usage`: units per policy (`topicPolicyUnits`, `contentPolicyUnits`, …); `sensitiveInformationPolicyFreeUnits` (regex, not billed)
  - `guardrailCoverage.textCharacters.guarded / total` = how much of the text was actually checked
- Converse response with guardrail
  - `stopReason = "guardrail_intervened"` ⇒ `output.message` holds the canned blocked message
  - `trace.guardrail` (when `trace="enabled"`): `inputAssessment` (map guardrail id → assessment), `outputAssessments` (map → list), `modelOutput` (raw model text, `enabled_full` only)
  - Limit: `modelOutput` shows the unfiltered answer ⇒ never log it to a widely readable sink

### 1.6 Streaming: sync vs async
- Sync (`streamProcessingMode="sync"`, default)
  - Bedrock buffers chunks, runs the output check, then releases them
  - Pro: nothing unsafe reaches the user; PII masking works
  - Con: time-to-first-token grows by one buffer + one check (order of magnitude: hundreds of ms)
- Async (`"async"`)
  - Chunks go to the user immediately; checks run in the background
  - Hit ⇒ stream stops with `stopReason=guardrail_intervened`, but earlier chunks are already shown
  - Masking (ANONYMIZE) is not applied in async mode ⇒ a PII chunk can leak (User Guide, "streaming" section)
- Pick
  - Default: sync
  - Async only for low-risk content where TTFT matters and you can retract text in the UI

### 1.7 Versions, tiers, detect mode
- DRAFT vs numbered versions
  - `create_guardrail` → working copy `DRAFT`
  - `update_guardrail` → edits DRAFT only
  - `create_guardrail_version` → immutable snapshot `1`, `2`, … of DRAFT
  - Apps pin a number; promote by changing config, roll back by pointing to the old number
  - Terraform: `aws_bedrock_guardrail` = DRAFT, `aws_bedrock_guardrail_version` = snapshot
    - Catch: the version resource does not re-snapshot on DRAFT changes by itself ⇒ replace it (`terraform apply -replace`) or add a new version resource
- Tiers (`tierConfig.tierName`)
  - `CLASSIC`: original classifiers, English/French/Spanish focus
  - `STANDARD`: more languages, more robust to typos and obfuscation, prompt-leakage detection
  - STANDARD requires `crossRegionConfig.guardrailProfileIdentifier` (a system guardrail profile, e.g. `us.guardrail.v1:0`)  
    ⇒ the check may run in another Region of the same geography
  - Applies per policy: content filters, denied topics, contextual grounding (API); Terraform 6.73 exposes it for content + topics only
- Detect mode (dry run)
  - `inputAction` / `outputAction` = `NONE` with `inputEnabled=true` ⇒ evaluated, reported (`detected=true`), not enforced
  - Use: shadow a new policy on live traffic, measure false positives, then flip to BLOCK
- Account / org enforcement
  - `PutEnforcedGuardrailConfiguration` (Terraform `aws_bedrock_enforced_guardrail_configuration`) forces a guardrail on every inference call in the account
  - Assessment shows `appliedGuardrailDetails.guardrailOrigin` = `REQUEST`, `ACCOUNT_ENFORCED`, `ORGANIZATION_ENFORCED`
  - Not used here (would apply to the whole account); listed as a gap

### 1.8 Automated Reasoning checks (lecture 24)
- Plain idea
  - You upload a policy document (HR rules, insurance eligibility)
  - Bedrock extracts variables and logical rules (SMT-style formal logic) into an Automated Reasoning policy
  - At runtime the guardrail translates the Q&A into the same logic and checks it mathematically
- Findings (assessment `automatedReasoningPolicy.findings[]`)
  - `valid`: claims follow from the rules
  - `invalid`: claims contradict the rules (returns `contradictingRules`)
  - `satisfiable`: true under some assumptions, false under others
  - `impossible`: premises contradict each other
  - `translationAmbiguous`, `tooComplex`, `noTranslations`: could not decide
- Behavior: findings only; no blocking; your code decides (rewrite, refuse, ask a clarifying question)
- Config as code
  - Policy lifecycle: `create_automated_reasoning_policy` → build workflow → test cases → `create_automated_reasoning_policy_version`
  - Attach: `automatedReasoningPolicyConfig = {policies: [<policy version ARN>], confidenceThreshold: 0–1}` on create/update guardrail
  - Terraform 6.73: not supported on `aws_bedrock_guardrail` ⇒ SDK only; the Python builder adds it when `A_GUARDRAILS_AR_POLICY_ARN` is set
- Limits
  - Only as good as the extracted rules ⇒ review rules and test cases by hand
  - Narrow domains with crisp rules; poor fit for open-ended chat
  - Region and language availability is limited (check the docs)

## 2. When to use / not
- Use
  - Any user-facing generation: chat, summarization, RAG answers
  - Untrusted input reaching an agent: user text, web pages, tool results
  - A compliance rule must hold for every model and team
  - Non-Bedrock models that need the same policy (ApplyGuardrail)
- Do not use (alone)
  - Authorization: "may this user see document X" is IAM / KB metadata filters, not a guardrail
  - Bulk PII discovery in data at rest ⇒ Macie / Comprehend jobs (04.02)
  - Fact checking against world knowledge ⇒ grounding only checks against the source you pass
  - Hard real-time paths where hundreds of ms per call are unacceptable ⇒ async stream mode or a smaller policy set

## 3. Knobs and best practices

| Knob | Values (default) | Trade-off | Change when |
|---|---|---|---|
| Content strength | NONE/LOW/MEDIUM/HIGH | higher = more recall, more false positives | eval shows misses (raise) or FP rate > target (lower) |
| PROMPT_ATTACK input | HIGH typical | FP on role-play / dev instructions | tag user input before raising |
| Content `inputAction`/`outputAction` | BLOCK (default) / NONE | NONE = detect only | shadow-testing a new policy |
| Denied topic definition | ≤ 200 chars Classic (check) | vague = over-blocking | FP on adjacent topics |
| PII action | BLOCK / ANONYMIZE / NONE | BLOCK = refuse; ANONYMIZE = keep flow | identifiers that must never pass (SSN, card) → BLOCK |
| Regex | pattern + action | catastrophic backtracking, FP on look-alikes | internal ids not in the built-in list |
| Grounding threshold | 0–0.99 | higher = stricter, more refusals | RAG answers hallucinate (raise) |
| Relevance threshold | 0–0.99 | higher = blocks partial answers | off-topic answers |
| Tier | CLASSIC / STANDARD | STANDARD = better, cross-Region | non-English or obfuscated attacks |
| Stream mode | sync / async | latency vs leakage | TTFT critical, low risk |
| Trace | disabled / enabled / enabled_full | full = raw model output in response | debugging only |
| `outputScope` | INTERVENTIONS / FULL | FULL = bigger response | evaluation, score tuning |
| KMS key | AWS-owned / CMK | CMK = control + cost | regulated data |

- Best practices
  - Pin a numbered version in prod ⇒ prevents a DRAFT edit from changing live behavior
  - Tag only untrusted text with `guardContent` ⇒ prevents prompt-attack FP on system prompts
  - Guard input before retrieval, not only before generation ⇒ prevents paying for retrieval + tokens on blocked requests
  - Shadow new policies in detect mode ⇒ prevents a launch-day FP storm
  - Keep a labeled eval set per policy (04.03) ⇒ prevents tuning by anecdote
  - Write blocked messages that tell the user what to do ⇒ prevents silent failure UX
  - Alarm on `InvocationsIntervened` rate (CloudWatch `AWS/Bedrock/Guardrails`) ⇒ detects attacks and regressions
  - Log assessments, not raw text ⇒ prevents the audit log becoming a PII store
  - Both Terraform and SDK show the same policy ⇒ Terraform owns the resource; SDK create/update is for tooling and tests, not for a second source of truth

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Guardrails | Managed policy engine, 6 policies, versioned | One resource for all models; PII + grounding + AR built in; no infra | AWS-only; per-text-unit cost; limited custom logic | AWS stack, managed default |
| NVIDIA NeMo Guardrails | Open-source dialog rails (Colang flows) | Programmable conversation flows; self-hosted | You run it; LLM-based rails add latency | Complex dialog policies, multi-cloud |
| Guardrails AI (open source) | Validators on LLM output (schema, PII, toxicity) | Rich validator hub; structured output repair | Mostly output-side; you host models | Output schema validation + custom checks |
| Llama Guard / ShieldGemma | Open safety classifier models | Self-hosted, tunable taxonomy | You serve and evaluate it; no PII/grounding | Data must stay in your VPC, custom taxonomy |
| Azure AI Content Safety / OpenAI Moderation | Cloud moderation APIs | Simple, cheap per call | Content categories only; other cloud | Already on that cloud |
| System prompt rules | "Never discuss X" in the prompt | Free | Not enforcement; jailbreakable | Never as the only layer |

- Default: Bedrock Guardrails (via `guardrailConfig`, or `ApplyGuardrail` for non-Bedrock models), unless policies must run outside AWS or need dialog-flow logic ⇒ NeMo Guardrails or a self-hosted classifier
- Deciding variable: where the model runs and whether you can accept the per-unit cost on long contexts

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| System prompt flagged as attack | PROMPT_ATTACK evaluates untagged system text | high `InvocationsIntervened`, contentPolicy PROMPT_ATTACK on benign traffic | tag user input with `guardContent` |
| Over-blocking a topic | vague definition, broad examples | FP rate on labeled set; user complaints | sharpen definition; add negative eval cases; detect mode |
| PII leaks in stream | async mode with ANONYMIZE | output logs contain PII | sync mode for PII policies |
| Grounding blocks good answers | threshold too high; source truncated | GROUNDING scores just below threshold | lower threshold; shorter, better passages |
| Grounding not applied | missing `grounding_source` / `query` qualifiers | `contextualGroundingPolicy` absent from assessment | pass all three qualifiers |
| Prod behavior changes silently | app points at DRAFT | version in trace = DRAFT | pin a number |
| Cost spike | long RAG context through every policy | `usage` units; Bedrock bill | guard only user text + answer; drop unneeded policies |
| Throttling | guardrail TPS quota | `ThrottlingException` | retries with jitter; quota increase |
| Regex backtracking / FP | greedy pattern | latency, false hits | anchor patterns, test on corpus |
| Raw output in logs | `trace=enabled_full` in prod | `modelOutput` in logs | `enabled` in prod |

## 6. Interview questions

**Q: What does a Bedrock guardrail consist of, and how is it applied?**

**L4 answer**
- Up to six policies: content filters (incl. prompt attack), denied topics, words, sensitive info, contextual grounding, Automated Reasoning
- Blocked-input and blocked-output messages
- Applied by id + version on Converse/InvokeModel, KB, Agents, or standalone via ApplyGuardrail
- Input check → model → output check; any BLOCK hit returns the canned message

**L5 extra**
- Each check is a parallel set of classifiers; result is an assessment per policy, which is your audit and eval data
- Input block saves model tokens; output block wastes them ⇒ put cheap, high-recall checks on input
- Version pinning is the deployment contract; DRAFT is a dev artifact

**Q: When would you use ApplyGuardrail instead of guardrailConfig on Converse?**

**L4 answer**
- Model is not on Bedrock (SageMaker, OpenAI, on-prem)
- Checking text that is not a model call: retrieved docs before indexing, tool results, user uploads
- You need custom flow between checks (e.g. log, route to human, retry with a different prompt)

**L5 extra**
- Two extra round trips per turn vs one integrated call ⇒ latency budget
- Lets one central "safety service" own policy for many model providers
- With streaming from a non-Bedrock model, you must build your own buffering window (same trade-off as sync mode)

**Q: How does the prompt-attack filter work, and what goes wrong with it?**

**L4 answer**
- Classifier on input for jailbreak, injection (and leakage on Standard tier)
- Output strength must be NONE
- Common FP: your own system prompt looks like instructions

**L5 extra**
- Fix with input tagging (`guardContent` in Converse, tag suffix in InvokeModel) so only untrusted text is scanned
- Indirect injection (RAG docs, tool output) needs ApplyGuardrail on that content too
- It is one layer: least-privilege tools and output checks limit the blast radius when it misses

**Q: Explain contextual grounding. What does it guarantee?**

**L4 answer**
- Scores the answer against a grounding source (GROUNDING) and against the query (RELEVANCE)
- Blocks if a score is under its threshold
- Needs the three qualifiers: grounding_source, query, guard_content

**L5 extra**
- Guarantee is relative to the source passed: wrong retrieval + faithful answer still passes
- Threshold is a precision/recall knob; set it from a labeled set of grounded vs hallucinated answers
- Source length limits ⇒ pass the top-k passages actually cited, not the whole KB result

**Q: BLOCK vs ANONYMIZE for PII — how do you choose?**

**L4 answer**
- BLOCK refuses the whole call; for identifiers that must never flow (SSN, card numbers)
- ANONYMIZE masks with `{TYPE}` and continues; for contact info the task does not need

**L5 extra**
- Input ANONYMIZE removes PII before it reaches model logs and providers
- Masking breaks tasks that need the value ⇒ reversible pseudonymization outside the guardrail (04.02)
- ANONYMIZE is not applied in async streaming ⇒ PII policies force sync mode

**Q: Sync vs async stream processing?**

**L4 answer**
- Sync buffers and checks before sending; safe, slower first token
- Async streams immediately and checks in the background; fast, may show text that later gets blocked

**L5 extra**
- Async skips masking ⇒ PII exposure
- UI must handle a mid-stream stop (retract or replace)
- Choose per route: async for low-risk internal tools, sync for customer-facing

**Q: How do you roll out a guardrail change safely?**

**L4 answer**
- Edit DRAFT, run the eval set against DRAFT with ApplyGuardrail, create a numbered version, switch the app config

**L5 extra**
- Detect mode on live traffic first (`inputAction=NONE`), compare intervention rates
- Canary: route a percentage of traffic to the new version id; alarm on intervention rate and complaint rate
- Rollback = point to the previous number; versions are immutable

### L5-only

**Q: Design guardrails for a multi-tenant agent platform that serves Bedrock and third-party models.**
- Central safety service exposing `check(input|output, tenant)` built on ApplyGuardrail
- Per-tenant guardrail (or version) chosen from tenant config; shared baseline enforced at account/org level
- Untrusted content (tool results, retrieved pages) checked before entering the agent context
- Streaming: own sliding buffer for non-Bedrock models; sync mode for Bedrock
- Metrics per tenant and policy; labeled eval sets per tenant for tuning
- Cost: guard only untrusted spans; cache verdicts for identical retrieved chunks

**Q: Your guardrail blocks 8% of legitimate traffic after launch. What do you do?**
- Pull assessments for blocked requests: which policy, which category, which confidence
- Most often: untagged system prompt (prompt attack) or broad denied topic
- Reproduce with ApplyGuardrail `outputScope=FULL` on a sample; add cases to the eval set
- Fix: tagging, lower strength on that one category, sharpen topic definition; re-run eval; new version; canary
- Prevent: detect-mode shadowing and a FP-rate gate in CI before version promotion

**Q: When is Automated Reasoning worth it over contextual grounding?**
- Grounding = statistical "is this supported by the passage"
- AR = logical "does this follow from the rules", returns contradicting rules
- Worth it for crisp rule sets with high cost of a wrong yes/no (eligibility, policy compliance)
- Cost: rule extraction and test-case curation; findings only, so you build the decision logic
