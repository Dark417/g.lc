## 0. One-minute version
- What
  - RAG = retrieve relevant text, put it in the prompt, then generate
  - An embedding = a fixed-length vector whose direction encodes meaning
  - Vector search = find the stored vectors nearest to the query vector
- Why
  - The model does not know your private or recent data
  - Fine-tuning is slow, costly, and cannot cite sources  
    ⇒ retrieval adds knowledge at query time, and is updated by re-indexing  
- How
  - Index time  
    → chunk documents  
    → embed each chunk  
    → store vector + text + metadata  
  - Query time  
    → embed the question with the same model  
    → kNN search (top k)  
    → stuff chunks into the prompt  
    → generate with citations  
- Catch
  - Exact kNN is O(N·d) per query ⇒ every real store uses ANN (HNSW or IVF), trading recall for speed
  - Index and query must use the same model, dimensions, and normalization
  - Pure vector search misses exact terms (SKUs, error codes) ⇒ hybrid search (BM25 + vector)
  - Memory is the cost driver: 1M × 1024-dim float32 ≈ 4 GB raw, ≈ 4.6 GB in HNSW
- Default on AWS
  - Titan Text Embeddings V2, 1024 dims, normalized
  - OpenSearch Serverless (HNSW, faiss) behind a Bedrock Knowledge Base
- 🗣 "Retrieval quality caps answer quality: the model can't cite what the retriever never returned."
- 🗣 "ANN is a recall-for-latency trade; ef_search and n_probe are the dials."
- 🗣 "Normalize once at write time, then cosine is just a dot product."

## 1. Concept

### 1.1 Why RAG exists
- The pain
  - An LLM's knowledge is frozen at training time and excludes private data
  - Long prompts with "all the documents" exceed the context window and cost per token
  - Fine-tuning teaches style and format better than facts, and cannot cite (01.02)
- Prior art
  - Keyword search (BM25, inverted index): exact terms, no synonyms or paraphrase
  - Enterprise search (Kendra): good connectors, rank-only, no generation
- RAG (Lewis et al., 2020)
  - Retrieve passages with a dense retriever, condition generation on them
  - Knowledge lives in the index ⇒ update = re-embed changed chunks
- Common use cases
  - Internal docs Q&A, support assistants, policy lookups
  - Code and runbook search for agents
  - Semantic cache ("similar question already answered")
- Limit
  - Retrieval fails silently: a wrong chunk produces a fluent wrong answer  
    ⇒ evaluate retrieval separately from generation (04.03)  

### 1.2 Picture: index time vs query time

```
INDEX TIME (batch, async)                       QUERY TIME (online, per request)
docs in S3                                      user question
  │                                               │
  ▼                                               ▼
parse (text, tables, OCR)                       [optional] rewrite / decompose / HyDE (02.03)
  │                                               │
  ▼                                               ▼
chunk (02.03)                                   embed(question)  ← same model + dims + normalize
  │                                               │
  ▼                                               ▼
embed(chunk) ── Titan V2 / Cohere              kNN (ANN) + metadata filter  ── [hybrid: + BM25]
  │                                               │
  ▼                                               ▼
vector store: {vector, text, metadata}  ◄─────  top-k chunks ─► [rerank] ─► prompt ─► LLM ─► answer + citations
```

- Index time is throughput-bound
  - Cost = input tokens embedded, once per chunk version
- Query time is latency-bound
  - Budget order of magnitude: embed ~tens of ms, ANN ~ms to tens of ms, LLM ~seconds  
  ⇒ the LLM dominates latency; retrieval quality dominates correctness  

### 1.3 Embeddings
- Mechanism
  - An encoder model maps text to a vector, trained (contrastive) so similar meanings land close
  - The vector length is fixed per model setting, whatever the input length
  - Long input is averaged into one point ⇒ one vector per chunk, not per book
- Titan Text Embeddings V2 (`amazon.titan-embed-text-v2:0`)
  - `dimensions`: 256 | 512 | 1024 (default 1024)
    - AWS reports ~99% (512) and ~97% (256) of 1024-dim retrieval accuracy (Titan V2 launch blog, 2024)
    - 4x fewer dims = 4x less storage and faster distance math
  - `normalize`: default true ⇒ unit vectors, so dot = cosine
  - `embeddingTypes`: `["float"]` (default), `["binary"]`, or both
    - binary = one bit per dim, for Hamming pre-search + float rescoring
  - Input limit 8,192 tokens / 50,000 characters (Bedrock model parameters page)
  - One text per call; symmetric (same embedding for query and document)
- Cohere Embed (`cohere.embed-english-v3`, `cohere.embed-multilingual-v3`, Embed v4 where available)
  - Asymmetric: `input_type = search_document` at index time, `search_query` at query time
    - Wrong type ⇒ lower recall, no error
  - Up to 96 texts per call; v3 truncates at ~512 tokens (check the model page)
  - Server-side `embedding_types`: float, int8, uint8, binary, ubinary
- Multimodal: Titan Multimodal Embeddings / Nova multimodal embeddings put images and text in one space (lecture 22, 01.x)
- Limits
  - Embeddings from different models (or dims) are not comparable  
    ⇒ changing the model = re-embed the whole corpus  
  - Embeddings blur exact tokens (IDs, numbers, negation) ⇒ hybrid search
  - Domain jargon the encoder never saw clusters poorly ⇒ test on your data before choosing

### 1.4 Similarity metrics

| Metric | Formula | Range | Note |
|---|---|---|---|
| Cosine | a·b / (‖a‖‖b‖) | [-1, 1] | angle only; magnitude ignored |
| Dot (inner product) | a·b | unbounded | = cosine on unit vectors; cheapest |
| L2 (Euclidean) | ‖a − b‖ | [0, ∞) smaller = closer | on unit vectors d² = 2 − 2·cos ⇒ same ranking as cosine |

- Why normalize
  - Unit vectors make all three metrics rank identically
  - Then the store can use dot product (no norms at query time)
  - Unnormalized + dot ⇒ long vectors win regardless of meaning
- OpenSearch names: `cosinesimil`, `innerproduct`, `l2` (02.02); score transforms differ (`1/(1+d)` for L2)
- Rule: use the metric the model was trained for (model card); for Titan V2 normalized, any of the three works

### 1.5 Exact kNN vs ANN
- Exact (brute force)
  - Compare the query with every vector, keep top k
  - Recall = 1.0 by definition
  - Cost O(N·d): 1M × 1024 ≈ 1G multiply-adds per query (order of magnitude)
  - Fine below ~10k–100k vectors, or after a selective filter (OpenSearch switches to exact when few docs match)
- ANN (approximate nearest neighbour)
  - Build a structure that skips most vectors
  - Recall@k < 1.0; tuned by search-time knobs
  - recall@k = |ANN top-k ∩ exact top-k| / k
- The trade triangle
  - Recall ↔ latency ↔ memory
  - Any knob that raises one lowers at least one other
- Measure, don't guess  
  → sample real queries  
  → compute exact top-k as ground truth  
  → sweep `ef_search` / `n_probe`  
  → pick the cheapest setting that meets the recall target (often 0.95; order of magnitude)  
- Code: `similarity.recall_experiment` sweeps IVF `n_probe` against `ExactVectorStore`

### 1.6 HNSW
- Hierarchical Navigable Small World graph (Malkov & Yashunin, 2016)
- Mechanism
  - Every vector is a node linked to its nearest neighbours
  - Layers: layer 0 holds all nodes; each higher layer holds an exponentially smaller random subset
  - Search  
    → enter at the top layer, greedy walk toward the query  
    → drop one layer, continue from the best node  
    → at layer 0, run a beam search of width `ef_search`  
    → return the best k from the beam  
- Knobs
  - `m`: max links per node (layer 0 uses 2m)
    - Higher ⇒ better recall, more memory, slower build
    - OpenSearch default 16
  - `ef_construction`: beam width while inserting
    - Higher ⇒ better graph, slower indexing; default 100 in OpenSearch
  - `ef_search`: beam width at query time
    - Higher ⇒ higher recall, higher latency; tunable per query (OpenSearch 2.16+ `method_parameters`)
- Strengths
  - High recall at low latency, no training step, incremental inserts
- Costs
  - Graph lives in memory: faiss HNSW ≈ 1.1 × (4·d + 8·m) bytes per vector (OpenSearch k-NN sizing doc)
  - Deletes leave tombstones until segments merge
  - Builds are CPU-heavy ⇒ bulk loads are slow

### 1.7 IVF
- Inverted File index (faiss)
- Mechanism  
  → train k-means on a sample to get `nlist` centroids  
  → assign each vector to its nearest centroid's list  
  → at query time, scan only the `nprobes` closest lists  
- Knobs
  - `nlist`: more lists = smaller lists = faster scan, but more misses at the cell borders
  - `nprobes`: more lists scanned = higher recall, higher latency
- Strengths
  - Less memory than HNSW (no graph); pairs well with PQ (IVF-PQ) for billions of vectors
- Costs
  - Needs a training step on representative data (OpenSearch: a separate train API + model)
  - Centroids drift when the data distribution changes ⇒ retrain and reindex
- Default: HNSW, unless memory is the binding constraint at very large N ⇒ IVF(-PQ) or disk-based modes

### 1.8 Quantization
- Idea: store fewer bits per dimension, accept some recall loss, recover it by rescoring

| Scheme | Bytes per 1024-dim vector | Shrink | Recall cost | Where |
|---|---|---|---|---|
| float32 | 4,096 | 1x | none | default |
| float16 (scalar) | 2,048 | 2x | negligible (order of magnitude) | faiss `sq fp16` |
| int8 / byte (scalar) | 1,024 | 4x | small | lucene SQ, faiss `sq`, Cohere int8 |
| binary (1 bit / dim) | 128 | 32x | large unless rescored | OpenSearch `on_disk` 32x, Titan V2 `binary` |
| PQ (m=64 codes) | 64 | 64x | medium–large, data dependent | faiss `pq`, IVF-PQ |

- Memory math (1M vectors × 1024 dims, order of magnitude)
  - float32 ≈ 4 GB; HNSW total ≈ 4.6 GB
  - binary ≈ 128 MB ⇒ fits in a small node's RAM
- Binary quantization mechanism  
  → keep the sign bit of each dimension  
  → distance = Hamming = popcount(a XOR b)  
  → shortlist k × oversample candidates  
  → rescore the shortlist with full-precision vectors (kept on disk)  
- PQ mechanism  
  → split the vector into m sub-vectors  
  → k-means each sub-space into 256 centroids  
  → store one byte (centroid id) per sub-vector  
- Limit: quantization trades recall for memory; measure recall@k after every change

### 1.9 Hybrid search and reranking
- Hybrid = lexical (BM25) + vector, fused
  - BM25 catches exact tokens; vectors catch paraphrase
  - Fusion options
    - Score normalization (min-max or L2) + weighted arithmetic mean (OpenSearch normalization processor)
    - RRF (reciprocal rank fusion): score = Σ 1 / (60 + rank); rank-based, no score scaling
  - Bedrock KB: `overrideSearchType = HYBRID` (store support varies; 02.04)
- Reranking = second stage  
  → retrieve a wide candidate set (e.g. 50)  
  → a cross-encoder scores each (query, chunk) pair jointly  
  → keep the top few (e.g. 5)  
  - Bedrock Rerank API / KB `rerankingConfiguration` (`amazon.rerank-v1:0`, `cohere.rerank-v3-5:0`)
  - Cost: one model call per candidate batch, +latency (hundreds of ms; order of magnitude)
- Default: hybrid + rerank for production Q&A over mixed prose and identifiers, unless latency budget is tight

## 2. When to use / not
- Use vector search / RAG when
  - Answers must come from private, changing, or citable sources
  - Queries are natural language and paraphrase the docs
- Use hybrid when
  - Users search with codes, names, versions, error strings
- Don't use when
  - The data is structured and the question is a query ⇒ text-to-SQL (02.04 §structured)
  - The corpus fits in the context window and changes rarely ⇒ prompt caching may be simpler
  - You need exact lookups by key ⇒ a database, not similarity
  - Facts must be learned as behaviour (format, tone) ⇒ prompting or fine-tuning (01.02)

## 3. Knobs and best practices

| Knob | Values | Trades | Change when |
|---|---|---|---|
| Embedding model | Titan V2, Cohere v3/v4, multimodal | quality per domain vs price | your eval set shows low recall |
| `dimensions` | 256 / 512 / 1024 | recall vs storage + latency | memory-bound, measured recall loss acceptable |
| `normalize` | true (default) | – | keep true unless the model card says otherwise |
| Metric | cosine / dot / l2 | none on unit vectors | match the model card |
| Index | HNSW / IVF / flat | latency vs memory vs build time | N > ~100M or memory bound ⇒ IVF/PQ |
| `m`, `ef_construction` | 16 / 100 default | recall vs build time + memory | recall plateau below target |
| `ef_search`, `n_probe` | per query | recall vs latency | tune last, per workload |
| Quantization | fp16 / int8 / binary / PQ | memory vs recall | memory cost dominates |
| k (top-k) | 3–10 to the LLM, 20–100 to a reranker | context tokens vs recall | answers miss facts ⇒ raise k + rerank |
| Hybrid weights | e.g. 0.3 lexical / 0.7 vector | exact-term vs paraphrase recall | identifier-heavy queries |

- Best practices
  - Pin model id + dims + normalize in config, and store them with the index  
    ⇒ prevents mixing vectors from two models  
  - Cache embeddings by `sha256(model | dims | normalize | text)`  
    ⇒ re-ingest only re-embeds changed chunks; a model change invalidates every key  
  - Keep the original text and metadata next to the vector  
    ⇒ enables re-embedding, citations, and filters  
  - Measure recall@k on a labeled query set before and after every knob change
  - Filter inside the ANN search (efficient filtering), not after  
    ⇒ post-filtering can return fewer than k results  

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| OpenSearch Serverless (vector collection) | Managed OpenSearch, OCU-billed, HNSW/faiss | KB quick-create default; hybrid + filters; no cluster ops | Minimum OCUs billed even idle (check pricing page); fewer index-level knobs | Default for Bedrock KB; need hybrid search |
| OpenSearch Service (managed domain) | Your own cluster with the k-NN plugin | Full control: shards, engines, on_disk, IVF, ISM | You size and operate nodes, JVM, shards | Very large or tuned workloads; existing OpenSearch |
| Aurora PostgreSQL + pgvector | Postgres extension, HNSW / IVFFlat | Vectors next to relational data; SQL joins + filters; transactions | Index must fit memory for speed; behind dedicated engines at large N | Postgres already holds the business data |
| S3 Vectors | S3 vector buckets + vector indexes | Lowest storage cost; no cluster; KB-supported | Higher query latency than in-memory stores; no BM25 hybrid; check quotas | Large, rarely queried corpora; cost first |
| Pinecone | SaaS vector DB (serverless) | Mature API, namespaces, hybrid sparse-dense | Data leaves AWS account boundary; separate vendor | Multi-cloud teams already on Pinecone |
| Neptune Analytics | In-memory graph + vector search | GraphRAG: entities + relations + vectors (KB GraphRAG) | Graph modeling effort; memory-priced | Multi-hop questions over linked entities |
| MemoryDB (Valkey/Redis) | In-memory DB with vector search | Single-digit ms latency, high QPS | All in RAM ⇒ most expensive per GB | Semantic cache, real-time recommendations |
| FAISS in process | Library, no server | Free, fastest for a single node | No durability, replication, filters, or auth | Prototypes, offline batch, edge |

- Default: OpenSearch Serverless behind a Bedrock Knowledge Base, unless
  - the data already lives in Postgres and the corpus is modest ⇒ pgvector
  - the corpus is large and queried rarely ⇒ S3 Vectors
  - latency must be single-digit ms ⇒ MemoryDB
- Deciding variable: steady query rate vs idle cost
  - Low, spiky traffic ⇒ idle OCU floor dominates ⇒ S3 Vectors or pgvector
  - High traffic + hybrid ⇒ OpenSearch

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Garbage similarity | Index and query embedded with different model / dims / input_type | Scores cluster near random; recall collapses after a deploy | Pin model config; store it with the index; re-embed on change |
| Exact terms missed | Pure vector search on IDs, codes, names | Eval set: identifier queries fail | Hybrid BM25 + vector; metadata fields |
| Fewer than k results | Post-filter after ANN with a selective filter | Result count < k | Efficient (in-graph) filtering; exact search on small filtered sets |
| Recall drop at scale | `ef_search` / `n_probe` tuned on a small index | recall@k on golden set falls as N grows | Re-sweep knobs; raise `ef_search`; rebuild with higher `m` |
| OOM / circuit breaker | HNSW graph exceeds native memory | k-NN circuit breaker trips, indexing rejected | Quantize, reduce dims, on_disk mode, bigger nodes |
| Stale answers | Source changed, index not resynced | Citations point to old versions | Event-driven or scheduled sync (02.04) |
| Silent truncation | Chunk longer than model input limit | Token counts at limit; tail facts never retrieved | Chunk below limit; `truncate=NONE` to fail loudly |
| Throttling on ingest | Parallel embed calls exceed quota | `ThrottlingException` spikes | Adaptive retries, bounded workers, batch inference |

## 6. Interview questions

**Q1:** Walk through a RAG request end to end.

**L4 answer**
- Index time: parse → chunk → embed → store vector, text, metadata
- Query time: embed question with the same model → kNN top k → put chunks in the prompt → generate with citations

**L5 extra**
- Index time is throughput-bound and priced per embedded token; query time is latency-bound and the LLM dominates
- Quality levers in order: chunking, hybrid retrieval, reranking, then prompt
- Evaluate retrieval (recall@k, context precision) separately from generation (faithfulness) (04.03)

**Q2:** Cosine, dot product, or L2: which, and why normalize?

**L4 answer**
- Cosine compares angle; dot also counts magnitude; L2 is distance
- On unit vectors all three rank the same

**L5 extra**
- d² = 2 − 2·cos for unit vectors, so the choice is about compute and engine support
- Normalize at write time ⇒ dot product at query time, no norms
- Unnormalized dot lets long vectors dominate regardless of meaning

**Q3:** Explain HNSW and its knobs.

**L4 answer**
- Layered proximity graph; greedy search from sparse top layer to dense bottom layer
- `m` = links per node, `ef_construction` = build beam, `ef_search` = query beam

**L5 extra**
- `ef_search` is the only query-time dial; raise it until recall@k meets target, watch p99
- Memory ≈ 1.1 × (4·d + 8·m) bytes per vector (faiss, OpenSearch sizing) ⇒ dims and m drive cost
- Deletes are tombstones until merge; heavy churn degrades the graph ⇒ periodic reindex

**Q4:** HNSW vs IVF?

**L4 answer**
- HNSW: graph, high recall, no training, more memory
- IVF: k-means cells, scan `nprobes` cells, needs training, less memory

**L5 extra**
- IVF pairs with PQ for billion-scale in RAM budgets; HNSW is the default up to hundreds of millions
- IVF centroids drift with data ⇒ retrain; HNSW handles incremental inserts natively
- Both expose one recall dial (`ef_search` vs `nprobes`)

**Q5:** Your 1024-dim index doesn't fit the memory budget. Options?

**L4 answer**
- Fewer dims (Titan V2 512 or 256)
- Quantize: fp16, int8, binary
- Disk-based mode with rescoring

**L5 extra**
- Binary = 32x smaller; recover recall by oversampling + float rescoring
- Measure recall@k for each option on a golden set; pick the cheapest that meets target
- Or switch store tier: S3 Vectors for cold, rarely queried corpora

**Q6:** Why hybrid search, and how are scores combined?

**L4 answer**
- Vectors miss exact tokens; BM25 misses paraphrase
- Run both and fuse

**L5 extra**
- BM25 scores are unbounded, cosine is bounded ⇒ normalize (min-max) before a weighted mean, or use RRF on ranks
- Weights are a tuning knob per query mix; RRF needs no tuning but ignores score gaps
- Add a reranker on the fused top 50 for the final top 5

**Q7:** You upgrade the embedding model. What happens?

**L4 answer**
- Old and new vectors are not comparable
- Re-embed the full corpus into a new index, then switch

**L5 extra**
- Blue/green index: build new index in parallel, dual-read for eval, flip an alias
- Cache keys include model id ⇒ the upgrade invalidates the cache automatically
- Budget: full corpus tokens × new model price, plus double storage during cutover

**L5-only Q8:** Recall is fine in staging but drops in production. Diagnose.

**L5 answer**
- Check index size: knobs tuned on 100k vectors under-search at 50M ⇒ re-sweep `ef_search`
- Check filters: selective filters with post-filtering return fewer than k
- Check drift: new document types the embedding model clusters poorly
- Check query distribution: production queries are shorter, more keyword-like ⇒ hybrid
- Build a golden set from production logs; track recall@k as a metric, not a one-off test

**L5-only Q9:** Pick a vector store for 200M chunks, 50 QPS, filters by tenant, cost-sensitive.

**L5 answer**
- Memory: 200M × 1024 float32 ≈ 800 GB raw ⇒ in-memory HNSW is expensive
- Options
  - OpenSearch managed with on_disk binary quantization + rescoring
  - S3 Vectors if latency of hundreds of ms is acceptable
  - Titan V2 at 512 dims halves everything
- Tenant filter: efficient filtering or index-per-tenant for large tenants (noisy-neighbour isolation)
- Decide by measured recall@k and p99 at 50 QPS, then cost per month

**L5-only Q10:** When is RAG the wrong answer?

**L5 answer**
- Structured questions over tables ⇒ text-to-SQL
- Behaviour or format learning ⇒ fine-tuning
- Tiny static corpus ⇒ put it in the prompt with caching
- Multi-hop over relations ⇒ GraphRAG (Neptune Analytics)
