## 0. One-minute version
- What
  - A managed service that turns unstructured files into structured output
  - Inputs: documents, images, audio, video
- Why
  - One API replaces OCR + layout + ASR + vision-LLM glue
  - Output is JSON (plus optional Markdown) ready for RAG or downstream systems
- How
  - Standard output: modality defaults (text, summary, tables, transcript, scenes)
  - Custom output: a blueprint lists fields, each with a type and a natural-language instruction
  - A project bundles standard-output config + blueprints
  - Async invoke: input S3 URI + output S3 URI + project ARN + profile ARN → returns an invocation ARN
  - Poll the status, then read `job_metadata.json` and the result JSON from S3
- Catch
  - Async only for large files and video ⇒ you own polling or EventBridge
  - Cross-region inference profile required ⇒ data may be processed in another Region of the geography
  - Per-page / per-minute pricing ⇒ cost scales with file size, not with fields (check the pricing page)
  - Blueprint fields are LLM-inferred ⇒ validate output, do not trust blindly
- 🗣 "BDA is document-AI as a service: point it at S3, get typed JSON back."
- 🗣 "Standard output tells you what is in the file; a blueprint tells you the fields you want."
- 🗣 "BDA can also be the parser of a knowledge base, so ingestion gets tables and transcripts for free."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Extraction pipelines were stitched: Textract for OCR, Transcribe for audio, Rekognition for images, an LLM to structure
  - Each step has its own output shape, errors and cost  
  ⇒ glue code and drift
- BDA unifies it behind one invoke and one result schema per modality
- Common use cases
  - Invoices, forms, contracts → fields
  - Call recordings → transcript + summary
  - Video → chapters, scene summaries
  - Pre-processing before RAG chunking

### 1.2 Picture

```
 S3 bda/input/invoice.pdf
        │ InvokeDataAutomationAsync (project, profile, output uri)
        ▼
 ┌──────────────── BDA ────────────────┐
 │ modality router → standard output   │
 │                 → blueprint fields  │  (custom output)
 └──────────────────┬──────────────────┘
                    ▼
 S3 bda/output/<invocation-id>/job_metadata.json
                              /0/standard_output/0/result.json
                              /0/custom_output/0/result.json
 client ── GetDataAutomationStatus (Created → InProgress → Success | ServiceError | ClientError)
```

### 1.3 Standard vs custom output
- Standard output
  - Always on per modality; you toggle granularity and formats
  - Document: text at DOCUMENT / PAGE / ELEMENT / WORD / LINE granularity, Markdown / HTML / CSV text formats
  - Image: summary, captions, categories (IAB), text
  - Audio: transcript (speaker and channel labels), summary, topics
  - Video: summary, chapters, transcript, text in frames
- Custom output (blueprints)
  - Schema is JSON-schema-like: `class`, `description`, `properties`
  - Each property: `type`, `inferenceType` (explicit = in the file, inferred = derived), `instruction`
  - Blueprint `type` = DOCUMENT, IMAGE, AUDIO or VIDEO
  - Stages: DEVELOPMENT (editable) and LIVE (what projects should pin)
  - Prefer the explicit instruction "return the amount in the invoice footer as a number"

### 1.4 Projects
- A project = reusable config: standard-output settings, custom blueprints, optional sensitive-data detection (PII detect or redact)
- Stage DEVELOPMENT or LIVE; pass the stage at invoke time
- A document may carry several blueprints; BDA picks the matching one (fallback blueprint available)
- Override configuration: modality routing, document splitter, audio language settings

### 1.5 Sync vs async
- Async (`InvokeDataAutomationAsync`)
  - Input and output in S3; returns an invocation ARN; poll or listen on EventBridge
  - Use for batch, long audio, video, large PDFs
- Sync (`InvokeDataAutomation`)
  - Small single files; result returned inline
  - Catch: smaller input limits, check the quota page; the code here shows async because it is the general path

### 1.6 As a knowledge base parser
- Knowledge base data source → parsing strategy "Bedrock Data Automation as parser"
  - Same idea as foundation-model parsing, but BDA handles tables, images and layout
- Trade-off: extra per-page parse cost at ingestion, better chunks at query time
- Detail lives in [02.04 Knowledge Bases](02.04.knowledge-bases.md)

## 2. When to use / not
- Use
  - Mixed modalities with one pipeline
  - Documents with variable layouts where template OCR breaks
  - You want typed JSON and don't want to manage prompts
- Don't use
  - Plain OCR of clean text ⇒ Textract is cheaper
  - Tiny volume, bespoke logic ⇒ prompt a multimodal model directly
  - Data cannot leave the Region geography ⇒ check the inference profile Regions first
  - Need deterministic field coordinates in a fixed form ⇒ Textract Queries / forms

## 3. Knobs and best practices
- Pin the LIVE stage of blueprints in the project ⇒ a DEVELOPMENT edit cannot change production output
- Write instructions like prompts: unit, format, where to look, what to return when absent
- Set `clientToken` on invoke ⇒ a retried submit does not start a second billed job
- Poll with exponential backoff and a deadline; use EventBridge for high volume
- Encrypt output with the shared CMK (`encryptionConfiguration`); the caller needs `kms:GenerateDataKey`
- Keep the output prefix per run ⇒ listing and cleanup stay cheap
- Validate result JSON against a Pydantic model; keep BDA's `confidence` per field and route low confidence to humans
- Sensitive-data detection in the project for PII before the data reaches the LLM (see [04.02](04.02.pii-redaction.md))

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Data Automation | Multimodal extraction, standard + blueprints | One API for 4 modalities; typed JSON; KB parser | Region/profile constraints; per-unit price | Mixed files, variable layouts, RAG ingestion |
| Textract | OCR, forms, tables, queries, specialised invoice/ID APIs | Cheap for pure OCR; bounding boxes | Documents only; no field inference | Clean scans, known forms, coordinates |
| Comprehend | NLP on text you already have | Fast, cheap, deterministic | No OCR, no custom field schema | Entities / sentiment on extracted text |
| Prompt a multimodal LLM | You send the image/PDF and a schema | Most flexible; any logic | You own prompts, retries, cost, drift | Low volume, bespoke schema |

- Default: BDA for multi-modality or variable-layout extraction, unless the input is clean OCR (Textract) or volume is tiny (prompt the model)
- Deciding variable: how many modalities and how variable the layouts are

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| `AccessDenied` on invoke | Policy lacks the profile ARN or project ARN | Error names the resource | Allow `data-automation-profile/*` and the project |
| Job `ClientError` | Unsupported format, file over limits | `get_data_automation_status` errorType + errorMessage | Check supported formats / size quotas, split input |
| Job never finishes in your timeout | Large video | Status stays `InProgress` | Longer deadline or EventBridge |
| Field returned null | Instruction ambiguous or value absent | Compare with sample | Tighten instruction; add `inferenceType` |
| Duplicate billed jobs | Retried submit without token | Two invocation ARNs | Pass `clientToken` |
| Output unreadable | KMS grant missing for the caller | S3 `AccessDenied` / KMS error | Grant `kms:Decrypt` on the CMK |
| Drift after blueprint edit | Project pinned to DEVELOPMENT | Output changes | Promote to LIVE, pin version |

## 6. Interview questions

**Q1:** What is the difference between standard and custom output?

**L4 answer**
- Standard = modality defaults (text, summary, transcript)
- Custom = a blueprint with the fields you want and instructions per field
- Projects combine both

**L5 extra**
- Blueprint fields are inferred by a model ⇒ confidence + validation needed
- Stages (DEVELOPMENT / LIVE) are the change-management lever

**Q2:** How do you run BDA at scale?

**L4 answer**
- Async invoke with S3 in/out; poll status or use EventBridge
- Put S3 events → Lambda/Step Functions to submit

**L5 extra**
- Throttle submissions to the quota; idempotent `clientToken`
- Per-run output prefix; retry only on `ServiceError`, not `ClientError`

**Q3:** BDA vs Textract?

**L4 answer**
- Textract = OCR and structure for documents; BDA = multimodal + field inference

**L5 extra**
- Combine: Textract for coordinates and cheap bulk OCR, BDA for the hard minority
- Price per page decides; benchmark on your own documents

**Q4:** How would BDA improve a RAG pipeline?

**L4 answer**
- As the KB parser: tables, charts and layout become text/Markdown before chunking

**L5 extra**
- Trade-off: ingestion cost vs retrieval quality; measure with RAG evals (see [04.03](04.03.evaluations.md))
- Re-ingest is needed when you change the parser

**Q5:** Why does BDA need a data automation profile ARN?

**L4 answer**
- It is a cross-region inference profile; BDA routes work across Regions

**L5 extra**
- Governance: data may leave the Region ⇒ confirm geography fits residency rules

**L5-only Q6:** Design an invoice-processing pipeline with BDA.

**L5 answer**
- S3 upload → event → submit job (`clientToken` = object version id)
- EventBridge on completion → validate JSON → write to DynamoDB
- Low-confidence or schema failure → human review queue
- Idempotent by object version; DLQ for `ServiceError`
- Cost guard: reject files over the page cap before submit

**L5-only Q7:** BDA output differs between runs. What do you do?

**L5 answer**
- Pin blueprint LIVE version; keep a golden set with expected fields
- Regression test on every blueprint edit; compare field-level accuracy
- Move deterministic fields to Textract queries or regex post-checks
