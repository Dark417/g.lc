## 0. One-minute version
- What
  - Find personal data (names, emails, SSNs, card numbers, keys) in text and remove or replace it
  - Before it reaches a model, an index, a log, or a user who should not see it
- Why
  - Prompts, RAG indexes, and invocation logs are new copies of customer data
  - Each copy widens the GDPR / HIPAA / PCI scope and the breach blast radius
- How
  - Detect: an ML detector returns entity type + character offsets + confidence score
  - Decide per type: mask (`*****`), replace with type (`[EMAIL]`), pseudonymize (`<<EMAIL_1a2b>>`), block, keep
  - Apply edits right-to-left so earlier offsets stay valid
  - Tools by place
    - Data at rest in S3 → Macie (discover) + Comprehend async job (redacted copy)
    - Request / response path → Comprehend `DetectPiiEntities` or Guardrails sensitive-info filter
    - Audio → Transcribe `ContentRedaction`; clinical text → Comprehend Medical `DetectPHI`
- Catch
  - Detectors miss and over-fire ⇒ set a confidence threshold per type and measure it
  - Streaming splits an entity across chunks ⇒ hold back a tail buffer before emitting
  - Masking is irreversible ⇒ use a vault-backed pseudonym when the answer must contain the real value
  - The redaction service itself sees the raw PII ⇒ it belongs inside your compliance boundary
- 🗣 "Redact at every boundary where data gets copied: ingest, prompt, log, response."
- 🗣 "Detection gives offsets; policy decides the action; apply right-to-left."
- 🗣 "Masking forgets, pseudonymization remembers: pick by whether anyone must ever get the value back."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Regexes catch SSNs and cards, but not names, addresses, or "my wife's birthday is …"
  - Hand-built NER models per team, per language, never retrained
  - LLM era adds new copies: prompt logs, vector stores, fine-tune sets, model-provider retention
- What managed detectors add
  - Pretrained ML NER for ~30+ PII types with scores (Comprehend: 36 types in the botocore 1.44 enum, incl. `ALL`)
  - Same API for real-time and batch
  - No model to host
- Common use cases
  - Scrub support tickets before building a RAG index
  - Mask user prompts before they hit model invocation logs
  - Redact call-center transcripts (Transcribe) before analytics
  - Remove PHI from clinical notes before summarization (Comprehend Medical)

### 1.2 Picture: where PII is handled

```
   S3 raw docs ──► Macie (discover, classify)          at rest
        │
        └──► Comprehend async job (ONLY_REDACTION) ──► S3 redacted ──► KB / vector index
                                                                       (pre-index scrubbing)
   user ──► API ──► Comprehend detect + policy ──► pseudonymized prompt ──► Bedrock model
                    (or Guardrails input ANONYMIZE)                              │
                                                                                 ▼
   user ◄── detokenize (authorized only) ◄── Guardrails output check (PII, BLOCK/ANONYMIZE)
                                                                                 │
   logs ◄────────────────────────── only redacted text + entity types, never raw values
```

- Rule: redact at the earliest boundary that copies the data, then again on output
- Output check still matters: the model can produce PII from its training data or from retrieved docs

### 1.3 The toolbox

| Tool | Where | Input | Output | Actions |
|---|---|---|---|---|
| Comprehend `DetectPiiEntities` | request path | text (sync, size-capped) | type, score, begin/end offsets | you apply |
| Comprehend `ContainsPiiEntities` | request path pre-check | text | labels (types + score), no offsets | yes/no gate |
| Comprehend `StartPiiEntitiesDetectionJob` | batch, S3 | files or one-doc-per-line | redacted copy or offsets JSON | MASK / REPLACE_WITH_PII_ENTITY_TYPE |
| Bedrock Guardrails sensitive info | model call path | prompt / answer | masked text or block | BLOCK / ANONYMIZE / NONE + regex |
| Transcribe `ContentRedaction` | audio → text | audio job / stream | `[PII]` in transcript | redacted or redacted_and_unredacted |
| Comprehend Medical `DetectPHI` | clinical text | text | PHI entities + offsets | you apply |
| Amazon Macie | S3 at rest | buckets | findings (EventBridge, Security Hub) | discover only, no inline redaction |

- Guardrails vs Comprehend on the request path
  - Guardrails: one call also does content/topic checks; masks with `{TYPE}`; no per-type confidence threshold exposed as a knob
  - Comprehend: offsets + scores ⇒ your own policy (thresholds, pseudonyms, per-type actions)
- Transcribe (lecture 47, coded in 03.03)
  - Batch: `ContentRedaction = {RedactionType: "PII", RedactionOutput: "redacted" | "redacted_and_unredacted", PiiEntityTypes: [...]}`
  - `redacted_and_unredacted` writes both transcripts ⇒ the unredacted one needs its own access control
  - Streaming: `ContentRedactionType=PII` (redact) or `ContentIdentificationType=PII` (label only)
  - Language support is a subset (check the docs)
- Comprehend Medical (lecture 52)
  - `DetectPHI`: HIPAA-style PHI (names, ages, dates, IDs, addresses, professions …)
  - Detection only; apply offsets with the same `redact_text` logic
- Macie (lecture 225, mention only)
  - Managed + custom data identifiers over S3 objects; sampling-based automated discovery
  - Finds which buckets hold PII ⇒ decides what goes through the redaction job before indexing

### 1.4 Comprehend PII APIs
- `DetectPiiEntities(Text, LanguageCode)`
  - Returns `Entities[]`: `Type`, `Score` (0–1), `BeginOffset`, `EndOffset`
  - Text cap per request (order of magnitude: 100 KB UTF-8; check the quota page) ⇒ chunk long docs and shift offsets
  - Languages: English and Spanish for PII (the shared enum lists more; check the docs)
- `ContainsPiiEntities(Text, LanguageCode)`
  - Returns `Labels[]`: `Name` (type), `Score`
  - No offsets ⇒ a gate: skip detect + redact for the many messages with no PII
- `StartPiiEntitiesDetectionJob`
  - `InputDataConfig.S3Uri` + `InputFormat` (`ONE_DOC_PER_FILE` | `ONE_DOC_PER_LINE`)
  - `OutputDataConfig.S3Uri` + `KmsKeyId`
  - `Mode`: `ONLY_REDACTION` (writes redacted copies) | `ONLY_OFFSETS` (writes entity JSON)
  - `RedactionConfig` (ONLY_REDACTION): `PiiEntityTypes` (or `ALL`), `MaskMode` (`MASK` | `REPLACE_WITH_PII_ENTITY_TYPE`), `MaskCharacter` (one char, e.g. `*`)
  - `DataAccessRoleArn`: Comprehend assumes it to read input and write output
  - `ClientRequestToken`: idempotent start
  - Limit: one MaskMode for every type in the job ⇒ per-type policies need ONLY_OFFSETS + your own apply step
- Pricing shape: per unit of 100 characters, 3-unit minimum per request (Comprehend pricing page, 2026-11) ⇒ tiny messages cost the minimum

### 1.5 Redaction rules as code
- The console shows checkboxes per entity type; in code it is a policy object
  - `entity type → action` (MASK, REPLACE, PSEUDONYMIZE, BLOCK, KEEP)
  - `min_score` per policy (optionally per type)
  - `mask_char`
  - Default action for unlisted types
- Apply algorithm
  → detect entities  
  → drop entities with score < threshold  
  → if any entity's action is BLOCK ⇒ refuse the request  
  → resolve overlaps (keep the higher score, then the longer span)  
  → sort by `BeginOffset` descending  
  → replace `text[begin:end]` with the action's output  
- Why right-to-left: replacing a span changes the length of everything after it; edits from the end keep earlier offsets valid
- Threshold trade-off
  - Low (0.5): catches more, masks "May" (month) as a name ⇒ hurts answer quality
  - High (0.95): clean text, but misses partial names ⇒ leak
  - Set per type: SSN and card at 0.5 (cost of a miss is high), NAME at 0.8 (order of magnitude; tune on data)

### 1.6 Token-level redaction and streaming (lecture 26)
- Token-level = replace only the sensitive spans, keep the rest of the message usable
  - Versus message-level blocking: refuse everything when one entity appears
  - Guardrails ANONYMIZE and Comprehend-based masking are both span-level
- Streaming problem
  - Model output arrives in chunks: `"Call me at 555-"` then `"0142 tomorrow"`
  - Detect on each chunk alone ⇒ neither half looks like a phone number ⇒ leak
- Hold-back window
  → append each chunk to a buffer  
  → when the buffer exceeds 2 × window, run detection on the whole buffer  
  → emit only the prefix that ends `window` characters before the end, moved back to a whitespace and never inside an entity  
  → keep the tail; at end of stream, detect and flush the rest  
- Cost
  - Latency: the user sees text `window` characters late
  - Calls: one detect per flush (order of magnitude: every few hundred characters)
- Bedrock-native equivalent: `streamProcessingMode=sync` with a Guardrails PII filter (04.01); async mode does not mask

### 1.7 Masking vs reversible tokenization

| Technique | Reversible | Linkable across records | Use |
|---|---|---|---|
| Mask (`*****`) | no | no | logs, analytics, model input that never needs the value |
| Replace with type (`[EMAIL]`) | no | no | model input; keeps sentence meaning |
| Deterministic pseudonym (salted HMAC) + vault | yes, via vault | yes (same value → same token) | prompt in, real value back in the answer; joins |
| Random token + vault | yes, via vault | no | strongest privacy; no joins |
| Format-preserving encryption | yes, with key | yes | systems that validate formats (card length) |

- Salted HMAC pseudonym (lecture 210, key salting)
  - `token = TYPE + "_" + HMAC-SHA256(secret_key, type + ":" + value)[:n]`
  - Secret key = the "salt"; without it, tokens cannot be brute-forced from known values (e.g. all phone numbers)
  - Plain unsalted SHA-256 of an SSN is reversible by enumeration (10⁹ values) ⇒ never hash without a key
  - Rotate the key ⇒ new tokens; old mappings stay in the vault
- Vault
  - Port: `tokenize(type, value) → token`, `detokenize(token) → value`
  - Adapter: in-memory here; DynamoDB + KMS or a tokenization service in prod
  - The vault is now the crown jewel: separate account / role, audit every detokenize
- Re-identification happens only at the edge, for an authorized user, after the output guardrail

### 1.8 Comprehend + Lambda + Bedrock (lecture 51)

```
API Gateway ─► Lambda ─► comprehend.contains_pii_entities ──(none)──────────────┐
                           │ (some)                                            │
                           └─► detect_pii_entities ─► policy ─► pseudonymize ──┤
                                                                               ▼
                                                                  bedrock.converse
                                                                               │
                                       guardrail apply_guardrail(OUTPUT) ◄─────┘
                                               │
                                     detokenize (if authorized) ─► response
```

- Lambda holds only the redaction logic; the vault and the model are behind IAM
- Contains-first saves detect calls on the common no-PII path
- Order of magnitude latency added: tens to low hundreds of ms per Comprehend call; measure

## 2. When to use / not
- Use Comprehend-based redaction when
  - You need per-type actions, thresholds, or reversible pseudonyms
  - Scrubbing documents before indexing or fine-tuning
  - The model is not on Bedrock and you want PII out before it leaves your boundary
- Use Guardrails sensitive-info when
  - The call is already a Bedrock call with a guardrail; one call covers PII + content + topics
- Use the async job when
  - Thousands of documents in S3, latency is irrelevant, one mask mode is acceptable
- Do not use
  - As the only control for regulated data ⇒ add access control, encryption, retention
  - For structured columns (DB fields named `email`) ⇒ column-level masking / Lake Formation is exact and cheaper
  - For languages the detector does not support ⇒ results look clean and are not

## 3. Knobs and best practices

| Knob | Values (default) | Trade-off | Change when |
|---|---|---|---|
| `min_score` | 0–1 (code default 0.8) | low = more masking, more FP | misses found in audits (lower) / answers degraded (raise) |
| Action per type | MASK / REPLACE / PSEUDONYMIZE / BLOCK / KEEP | reversible vs not | answer must contain the value → PSEUDONYMIZE |
| `MaskMode` (job) | MASK / REPLACE_WITH_PII_ENTITY_TYPE | REPLACE keeps meaning for RAG | indexing for retrieval → REPLACE |
| `MaskCharacter` (job) | one char (`*`) | none | UI conventions |
| `Mode` (job) | ONLY_REDACTION / ONLY_OFFSETS | OFFSETS = your own policy | per-type actions needed |
| `InputFormat` (job) | ONE_DOC_PER_FILE / ONE_DOC_PER_LINE | per-line = JSONL records | ticket exports |
| Stream window | chars held back (code: 64) | latency vs split-entity leaks | long entities (IBAN, addresses) → larger |
| Contains pre-check | on / off | extra call when PII present | PII rate > ~50% → skip the pre-check (order of magnitude) |
| HMAC key | secret, rotated | rotation breaks joins | key exposure, policy cycle |

- Best practices
  - Redact before indexing, not only at query time ⇒ prevents the vector store from becoming a PII store
  - Log entity types and counts, never matched values ⇒ prevents logs from re-creating the leak
  - Keep thresholds per type ⇒ prevents one global number from either leaking SSNs or mangling names
  - Use REPLACE (type tags) for model input ⇒ keeps grammar so answers stay coherent
  - Keep the HMAC key in KMS / Secrets Manager ⇒ prevents dictionary reversal of pseudonyms
  - Re-check the output with a guardrail ⇒ catches PII the model introduced itself
  - Evaluate on a labeled set with your own data (04.03) ⇒ prevents trusting vendor-average recall

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Comprehend PII (sync) | ML NER API with offsets | Offsets + scores ⇒ any policy; no hosting | Per-call cost and latency; limited languages | Request path with custom rules or pseudonyms |
| Comprehend PII job | Async S3 batch | Cheap at scale, writes redacted copies | One mask mode; minutes of latency | Pre-index scrubbing of S3 corpora |
| Bedrock Guardrails sensitive info | Policy inside guardrail | One call with other safety checks; regex | `{TYPE}` mask only, no thresholds, Bedrock path | Already guarding Bedrock calls |
| Transcribe redaction | ASR with PII redaction | Redacts in the transcript directly | Audio only, language subset | Call-center audio |
| Comprehend Medical DetectPHI | Clinical NER | PHI categories clinical notes need | Medical text only; detection only | Healthcare text |
| Macie | S3 discovery | Finds where PII lives at scale | No inline redaction | Inventory and compliance of buckets |
| Microsoft Presidio (open source) | Regex + NER framework | Self-hosted, extensible, anonymizers incl. encrypt | You host and tune it | Multi-cloud, on-prem, custom recognizers |
| Regex only | Pattern list | Free, exact for formats | Misses names/addresses | Format-bound ids (account numbers) |

- Default: Comprehend `DetectPiiEntities` + policy object on the request path, Comprehend async job for corpora, Guardrails ANONYMIZE as the output net, unless the call is already a Bedrock call with a guardrail and masking with `{TYPE}` is enough ⇒ Guardrails alone
- Deciding variable: does anyone need the original value back (pseudonymize) and do you need per-type thresholds

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Entity split across stream chunks | per-chunk detection | PII in transcripts of streamed answers | hold-back window; sync guardrail mode |
| Garbled text after redaction | left-to-right apply shifts offsets | wrong characters masked in tests | apply right-to-left; resolve overlaps |
| Over-masking | low threshold; "May", "Jordan" as names | answer quality drops; FP audit | per-type thresholds; KEEP list |
| Missed PII | high threshold; unsupported language; OCR noise | sampled audits, canary strings | lower threshold; language detection first; regex backstop |
| Pseudonyms reversed | unsalted hash of low-entropy ids | security review | keyed HMAC, key in KMS |
| Vault leak | broad detokenize rights | CloudTrail on vault access | separate role, audit, rate limits |
| Redacted copy still has PII in metadata | job redacts content, not file names / S3 tags | Macie on output prefix | scrub metadata separately |
| Job fails AccessDenied | role trust or KMS grant missing | job `Message` field | trust `comprehend.amazonaws.com`, KMS grant |
| Long doc rejected | over the sync text cap | `TextSizeLimitExceededException` | chunk + offset shift, or async job |
| Logs hold raw prompts | invocation logging on before redaction | grep logs for canaries | redact before the model call |

## 6. Interview questions

**Q: Where in a RAG system do you redact PII?**

**L4 answer**
- Before indexing: scrub source documents (async job or detect + apply)
- On the request: redact the user prompt before the model and logs
- On the response: guardrail output check

**L5 extra**
- Each place a copy is made is a boundary: index, prompt logs, provider, cache, analytics
- Pre-index redaction must use REPLACE (type tags) to keep retrieval quality
- If answers need real values, keep pseudonyms in the index and detokenize at the edge for authorized users

**Q: Why apply redactions right-to-left?**

**L4 answer**
- Offsets refer to the original string; replacing an early span shifts later offsets

**L5 extra**
- Also resolve overlapping entities first (keep higher score / longer span)
- Offsets are character offsets: test with multi-byte text; mismatched units corrupt text silently

**Q: How do you redact a streaming answer?**

**L4 answer**
- Buffer chunks; emit only text that is safely before any possible entity; hold a tail window

**L5 extra**
- Window size = longest entity you care about + margin; never cut inside a detected entity
- Each flush costs a detect call ⇒ batch by size, not per token
- On Bedrock, guardrail sync mode does this for you; async mode skips masking

**Q: Masking vs tokenization — when each?**

**L4 answer**
- Masking is irreversible: logs, analytics, model input
- Tokenization keeps a mapping in a vault so authorized code can restore values

**L5 extra**
- Deterministic tokens enable joins but are linkable; random tokens are not
- Keyed HMAC prevents dictionary attacks on low-entropy ids
- Vault becomes the high-value target: separate account, audited detokenize

**Q: Comprehend vs Guardrails for PII?**

**L4 answer**
- Comprehend gives offsets and scores, so you write the policy
- Guardrails masks or blocks inside the model call, plus other safety policies

**L5 extra**
- Use both: Comprehend on input for pseudonymization and logs; Guardrails on output as the net
- Guardrails regex covers internal ids; Comprehend has no custom regex ⇒ add your own regex pass

**Q: How do you choose the confidence threshold?**

**L4 answer**
- Labeled sample of real text; measure recall and precision per type at several thresholds

**L5 extra**
- Asymmetric costs: a missed SSN is worse than a masked month ⇒ per-type thresholds
- Re-tune when input distribution changes (new product, new language)

### L5-only

**Q: Design PII handling for a call-center GenAI assistant (audio → summary → CRM).**
- Transcribe with `ContentRedaction` (`redacted` only unless a regulated process needs both)
- Comprehend detect on the transcript for types Transcribe does not cover; pseudonymize customer ids
- Bedrock summary with guardrail (PII ANONYMIZE + grounding on the transcript)
- Detokenize only the CRM fields that need real values, in the CRM write path
- Logs: types + counts; Macie on the transcript buckets; retention limits per bucket

**Q: A regulator asks you to prove no PII reached the model provider. What evidence do you have?**
- Redaction is before the call, enforced in one shared library or gateway
- Invocation logs contain only redacted prompts; sampled audits with canary PII strings
- Detection recall measured per type on a labeled set, with the threshold history
- Gaps to admit: ML recall < 100%, so the claim is "reduced", not "none"
