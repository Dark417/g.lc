## 0. One-minute version
- What
  - Glue Data Quality = rules on your data, written in DQDL, evaluated by a Glue (Spark) run
  - Rules attach to a Data Catalog table, or run inside a Glue ETL job
- Why
  - Bad inputs poison RAG and fine-tuning: duplicates, empty text, wrong language, truncated files
  - Catch them before embedding or training, when fixing is cheap
- How
  - Describe data in the catalog (crawler or Terraform)
  - Write a ruleset (DQDL) → start an evaluation run → read per-rule Pass/Fail and a score
  - Or ask for recommendations: Glue profiles the table and proposes rules
  - Metrics go to CloudWatch; results are queryable by result id
- Catch
  - Runs are Spark jobs billed per DPU-hour with a startup cost (check the pricing page) ⇒ not a per-record gate
  - Rules see a table, not one document ⇒ use it for batch pipelines, not request-time validation
  - Recommended rules are a starting point, not a contract
- 🗣 "Data quality for GenAI = gate the corpus before embedding or training."
- 🗣 "DQDL is declarative: rule type, column, expression; the run returns Pass or Fail per rule."
- 🗣 "Recommendations bootstrap the ruleset; humans own thresholds."

## 1. Concept

### 1.1 Why it was created
- The pain
  - Quality checks lived in ad-hoc Spark/SQL scripts per pipeline
  - Open-source tools (Deequ) needed Spark expertise and plumbing
- Glue DQ is built on Deequ, exposed as managed rules and a DSL (Glue docs)
- Use cases for GenAI
  - Check the document-metadata table before ingest into a knowledge base
  - Check fine-tuning datasets (no empty completions, unique ids, label balance)
  - Gate nightly ETL that builds the corpus

### 1.2 Picture

```
 S3 glue/docs_metadata/*.parquet
        │  catalog table a_ai_data.docs_metadata (crawler or terraform)
        ▼
 DQDL ruleset ──► evaluation run (Glue Spark, role a-glue-dq)
                      │
          ┌───────────┼───────────────┐
          ▼           ▼               ▼
   result (RuleResults) CloudWatch   optional S3 results
   Pass/Fail + score    metrics      (ResultsS3Prefix)
          ▼
   gate: score >= threshold → continue ingestion, else alert
```

### 1.3 Glue in one paragraph (you know it)
- Data Catalog = metadata (databases, tables, partitions) over S3
- Crawler = infers schema and partitions; Terraform declares tables when schema is known
- ETL (Glue Studio, lecture 44) = visual Spark jobs; the same DQ can run as a node

### 1.4 DQDL
- Shape: `RuleType "column" expression`, rules in a `Rules = [ ... ]` list
- Common rule types
  - `IsComplete "col"`: no nulls
  - `Completeness "col" > 0.95`: ratio of non-null
  - `IsUnique "col"`, `Uniqueness "col" > 0.99`
  - `ColumnValues "col" in ["a","b"]` or `> 0`, `matches "regex"`
  - `ColumnLength "col" between 1 and 5000`
  - `RowCount > 0`
  - `CustomSql "select count(*) from primary where ..." = 0`: any check SQL can express
  - Also: `DataFreshness`, `ReferentialIntegrity`, `ColumnCorrelation`, `StandardDeviation`
- Expressions: `=`, `<`, `>`, `between a and b`, `in [...]`
- Rule list is validated when the ruleset is created or updated

### 1.5 Where rules run
- Catalog-attached ruleset
  - Evaluated by a standalone run (`StartDataQualityRulesetEvaluationRun`) or on a schedule
  - No ETL code
- In an ETL job
  - `EvaluateDataQuality` transform inside the Glue script
  - Can route failing rows out (row-level outcomes) before writing
- Rule of thumb: standalone for audit and gates, in-job for row routing

### 1.6 Recommendations and results
- `StartDataQualityRuleRecommendationRun` profiles a table and returns a DQDL ruleset
- Results: per-rule `Pass | Fail | Error`, evaluated metrics, overall score
- CloudWatch: metrics per run for dashboards and alarms (turn on `CloudWatchMetricsEnabled`)
- Anomaly detection is a separate feature built on history; not coded here

### 1.7 Data Wrangler (lectures 40–42, console only)
- SageMaker Data Wrangler (in Canvas / Studio) = visual data prep with built-in transforms, quick-model and export to a pipeline
- Skipped in code: it is a console tool with no stable API surface to show
- When to mention: tabular ML prep; for GenAI corpora use Glue/DQ instead

## 2. When to use / not
- Use
  - Batch corpora feeding RAG/fine-tuning with a Glue-friendly format (Parquet, CSV, JSON)
  - Need audit trail and CloudWatch metrics without running Spark yourself
- Don't use
  - Per-request validation ⇒ plain code (Pydantic) or a guardrail
  - Semantic quality (is the answer correct?) ⇒ evaluations, see [04.03](04.03.evaluations.md)
  - Tiny data ⇒ Great Expectations in a notebook is cheaper

## 3. Knobs and best practices
- Number of workers (default 5) and timeout (default 2,880 min) on every run ⇒ cap cost
- Idempotent start: `ClientToken` so a retry does not start a second run
- Use `CloudWatchMetricsEnabled` and alarm on a failing score
- Keep thresholds in the ruleset, not in code; version rulesets in Terraform
- Start from recommendations, prune noisy rules, add business rules by hand
- Put `CustomSql` on a sample size ceiling for large tables (it scans)
- Scope the service role to the data prefix and CMK only

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Glue Data Quality | Managed DQDL on Glue (Deequ) | No infra; catalog-native; metrics | Spark startup and DPU cost; Glue-bound | Batch lake data on AWS |
| Great Expectations | Python expectation suite | Rich, portable, works anywhere | You run and schedule it | Notebooks, Pandas, non-AWS |
| Deequ | Spark library | Scales; the engine under Glue DQ | You wire Spark | Custom Spark pipelines |
| Databricks DLT expectations | Inline expectations in pipelines | Per-row drop/fail in the pipeline | Databricks only | You are already on Databricks |

- Default: Glue Data Quality for catalog tables on AWS, unless you need portability (Great Expectations) or you live in Databricks (DLT)
- Deciding variable: where the data and pipeline already run

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Run fails to start | Role lacks `iam:PassRole` for the caller | `AccessDenied` | Allow PassRole on the glue role only |
| Run fails immediately | Role cannot read S3 prefix or CMK | Run `ErrorString` | Grant s3:GetObject on the prefix and kms:Decrypt |
| Ruleset rejected | DQDL syntax or column not in table | `InvalidInputException` | Validate; compare with catalog schema |
| Stale schema | Catalog not updated after file change | Rule errors on missing columns | Re-crawl or update table |
| Surprise bill | Many runs, high workers | Glue cost in Cost Explorer | Cap workers/timeout; schedule |
| Duplicate runs | Retry without token | Two run ids | Pass `ClientToken` |
| All rules green, bad corpus | Rules check shape, not meaning | Eval metrics drop | Add semantic evals |

## 6. Interview questions

**Q1:** What is DQDL and how are rules evaluated?

**L4 answer**
- A DSL: rule type + column + expression
- Evaluated by a Glue run over a catalog table; each rule returns Pass/Fail

**L5 extra**
- Engine is Spark/Deequ ⇒ batch, cost per DPU
- Row-level outcomes only through the ETL transform

**Q2:** Catalog ruleset vs `EvaluateDataQuality` in an ETL job?

**L4 answer**
- Catalog = standalone checks on a table
- ETL = checks inside the pipeline, can split good and bad rows

**L5 extra**
- Choose on whether you need to stop or route rows before writing
- Both emit the same result object

**Q3:** Why does data quality matter for RAG?

**L4 answer**
- Duplicates, empty or truncated text and wrong languages degrade embeddings and retrieval

**L5 extra**
- Garbage enters the index permanently; fixing costs a re-embed
- Gate before ingestion; keep metrics per release

**Q4:** How do you get started with rules on a new table?

**L4 answer**
- Run a recommendation run, review, store the ruleset

**L5 extra**
- Recommendations overfit the sample; tune thresholds with domain knowledge

**Q5:** How would you alert on data quality?

**L4 answer**
- Enable CloudWatch metrics and alarm on the score

**L5 extra**
- Gate the pipeline on the score and page on trend, not single dips

**L5-only Q6:** Design a quality gate for a nightly RAG ingestion.

**L5 answer**
- Crawl → evaluate ruleset → score ≥ threshold ⇒ start KB ingestion; else stop + alert
- Quarantine failing partitions, ingest the rest
- Track score per run id with the KB data-source version

**L5-only Q7:** Glue DQ vs Great Expectations for a team on AWS with Pandas jobs?

**L5 answer**
- Glue DQ if data sits in the catalog and pipelines already use Glue
- Great Expectations if jobs are not Spark and portability matters
- Cost, ownership and where the results get consumed decide

## 7. Code map

| Concept / scenario | Python (`app/a03_02_glue_data_quality`) |
|---|---|
| Rules as data → DQDL string | `domain.Rule`, `domain.build_ruleset` |
| Create or update ruleset | `infra.upsert_ruleset` |
