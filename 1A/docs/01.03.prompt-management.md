## 0. One-minute version
- What
  - Bedrock Prompt Management stores prompts as AWS resources
  - A prompt = template with `{{variables}}` + model + inference settings, in one or more variants
- Why
  - Prompts change more often than code
  - Treat them as reviewed, versioned, rollback-able artifacts, owned by more than developers
- How  
  → create the prompt (DRAFT) with variants and input variables  
  → test it, then `CreatePromptVersion` = immutable snapshot `...:prompt/ID:1`  
  → call Converse with `modelId = <prompt version ARN>` and `promptVariables`  
  → roll back = point config at the previous version ARN  
- Catch
  - Converse with a prompt ARN runs the default variant only and ignores your `system` / `inferenceConfig` / `toolConfig` (they live in the prompt)
  - A/B testing variants is your code's job: pick a variant, render, call
  - Another AWS dependency on the request path; cache rendered templates if you render locally
- 🗣 "A prompt version is a deploy artifact: immutable, reviewed, and referenced by ARN."
- 🗣 "Pin the version ARN in config; DRAFT is for the playground, never for production."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Prompts as string literals in code ⇒ every wording change is a code deploy
  - No history of which prompt produced which output
  - Product and domain experts could not edit prompts safely
- Prompt Management (GA 2024-11)
  - Prompts as first-class resources with versions, tags, and IAM
  - Runs directly in Converse, Agents, and Flows (01.04 prompt node)
- Common use cases
  - Shared prompt library across teams (summarize, classify, extract)
  - Safe rollout and rollback of prompt changes
  - Comparing variants (model A vs model B, wording A vs B) in the console

### 1.2 Picture

```
prompt a-prompt  (arn:...:prompt/ABCDE12345)
  DRAFT  ── editable
  │  variant "default"   TEXT  "Summarize {{topic}} for {{audience}} ..."   model + inferenceConfig
  │  variant "concise"   TEXT  "In 3 bullets, summarize {{topic}} ..."      (compare in console)
  │
  ├── CreatePromptVersion → version 1  arn:...:prompt/ABCDE12345:1   (immutable snapshot)
  └── CreatePromptVersion → version 2  arn:...:prompt/ABCDE12345:2

app config: A_PROMPTS_PROMPT_ARN=arn:...:prompt/ABCDE12345:2
   → Converse(modelId=<that ARN>, promptVariables={topic: {text: ...}, audience: {text: ...}})
   → Bedrock renders the default variant, calls its model with its inference config
```

### 1.3 Prompt, variant, template, variables
- Prompt: the resource (name, description, KMS key, tags, `defaultVariant`)
- Variant: one complete way to run it
  - `templateType`: `TEXT` (single string) or `CHAT` (system + messages + optional tool config)
  - `templateConfiguration`: the template text or chat messages, plus `inputVariables`
  - `modelId`: model or inference profile the variant runs on
  - `inferenceConfiguration.text`: `maxTokens`, `temperature`, `topP`, `stopSequences`
  - `additionalModelRequestFields`: provider-specific keys
  - `metadata`: key-value pairs (owner, ticket)
  - Limit: a few variants per prompt (order of magnitude: 3 in the console; check the quota page)
- Variables: `{{name}}` placeholders, declared in `inputVariables`
  - Filled at run time via `promptVariables = {name: {text: value}}`
  - Values are inserted verbatim ⇒ fence untrusted text (01.05)
- CHAT templates can carry `cachePoint` blocks and a tool configuration

### 1.4 Draft and versions
- DRAFT: the working copy; `UpdatePrompt` edits it
- Version: `CreatePromptVersion` snapshots DRAFT into `:1`, `:2`, ...
  - Immutable: to change it, edit DRAFT and create a new version
  - `clientToken` makes version creation idempotent on retries
- Version ARN = the deploy unit
  - Config points at a version ARN
  - Rollback = change config back; no code deploy
- Review process (your process, not the service's)
  - Prompt text also lives in git (Terraform here) ⇒ pull-request review
  - Eval gate before promoting a version (04.03)

### 1.5 Running a managed prompt
- Option A: Converse with `modelId = prompt ARN` (version ARN in production)
  - Pass `promptVariables`; `messages` are appended after the prompt's own messages (CHAT) where allowed
  - You cannot also send `system`, `inferenceConfig`, `toolConfig`, `additionalModelRequestFields` (Converse API reference: they come from the prompt)
  - Runs the default variant
  - IAM: `bedrock:RenderPrompt` on the prompt + `bedrock:InvokeModel` on the variant's model (see the `.tf` comment on uncertainty)
- Option B: `GetPrompt` → render locally → Converse with the variant's model
  - Any variant (A/B), your own system prompt and guardrails, extra messages
  - Cache `GetPrompt` results (they are immutable per version)
- Option C: prompt node in a Flow (01.04) or an Agent's prompt override

## 2. When to use / not
- Use when
  - Several teams or non-developers edit prompts
  - You need version history, rollback, and IAM on prompts
  - You already run on Bedrock (Converse, Flows, Agents)
- Avoid when
  - One small service, prompts change with code anyway ⇒ git is enough
  - Multi-cloud or multi-vendor model routing ⇒ a vendor-neutral prompt store
  - You need built-in A/B traffic splitting and analytics ⇒ an LLM-ops platform

## 3. Knobs and best practices
- Pin version ARNs in config
  - Prevents: DRAFT edits changing production behavior
- One owner per prompt; tags for team and cost
- Name variables clearly; declare every variable used in the template
  - Prevents: unfilled `{{var}}` reaching the model
- Keep the template in git too (Terraform or a seed script)
  - Prevents: console-only changes with no review
- Evaluate each new version on a golden set before promotion (04.03)
- Encrypt with the CMK (`customerEncryptionKeyArn`)
- Cache `GetPrompt` per version when rendering locally
- Use `clientToken` on create calls
  - Prevents: duplicate prompts or versions on retries

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Prompt Management | AWS resource: variants, versions, IAM; runs in Converse/Flows/Agents | Native to Bedrock; immutable versions; no extra vendor; console compare | Bedrock-only; no built-in traffic split or analytics; default-variant only in Converse | AWS-native stack, Bedrock models |
| Prompts in git (files + code) | Templates in the repo, rendered by the app | PR review, CI evals, zero extra service | Change = deploy; non-devs blocked; no runtime lookup | Small team, prompts change with code |
| LangSmith / Langfuse prompt hub | LLM-ops platform prompt registry with labels | Labels (production/staging), tracing linked to prompt versions, A/B analytics, vendor-neutral | Another vendor or self-hosted service; data leaves AWS (SaaS) | Multi-model, heavy experimentation, need tracing + evals together |

- Deciding variable: who edits prompts and how often, and whether you need analytics tied to versions
- Default: Bedrock Prompt Management for Bedrock-only apps (with templates mirrored in git), unless you need cross-vendor experimentation and tracing → Langfuse / LangSmith

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Production uses DRAFT | Config holds the base ARN, not `:N` | Behavior changes without deploy | Pin version ARN; alarm on base-ARN use |
| Missing variable | Template uses `{{x}}` not passed | Literal `{{x}}` in model input / `ValidationException` | Declare `inputVariables`; validate before calling |
| Rejected fields | Sending `system` or `inferenceConfig` with a prompt ARN | `ValidationException` | Move them into the prompt variant |
| Access denied | Missing `RenderPrompt` / `InvokeModel` on the variant model | `AccessDeniedException` | Grant both (and KMS on the CMK) |
| Variant ignored | Expecting Converse to run a non-default variant | Output matches default | Render locally (`GetPrompt`) or change `defaultVariant` + new version |
| Untracked console edits | Edits outside git | Drift between Terraform and service | Terraform owns prompts; `plan` shows drift |
| Model retired | Variant pinned to a legacy model | `ValidationException` / lifecycle alarm | New version with new model; eval first |

## 6. Interview questions

**Q1:** Why manage prompts outside the code?

**L4 answer**
- Prompts change more often than code
- Versions give history and rollback; IAM controls who edits

**L5 extra**
- The version ARN becomes a deploy artifact referenced from config
- Pair it with an eval gate and keep the source in git for review
- Trade-off: one more runtime dependency vs faster, safer iteration

**Q2:** How do you call a managed prompt from code?

**L4 answer**
- Converse with `modelId` = prompt version ARN and `promptVariables`

**L5 extra**
- The prompt supplies model, system, and inference config; you cannot override them in that call
- Only the default variant runs ⇒ local rendering for A/B
- IAM: render permission on the prompt plus invoke on the underlying model

**Q3:** What is the difference between a variant and a version?

**L4 answer**
- Variant = an alternative template/model inside one prompt
- Version = immutable snapshot of the whole prompt (all variants)

**L5 extra**
- Variants are for comparison during design; versions are for release
- Changing the default variant needs a new version to reach production

**Q4:** How would you roll out a prompt change safely?

**L4 answer**
- Edit DRAFT, test, create a version, update config to the new ARN
- Roll back by restoring the old ARN

**L5 extra**
- Eval the new version on a golden set before promotion
- Canary: route a share of traffic to the new version in code, compare metrics
- Log the prompt ARN with each invocation (`requestMetadata`) to attribute regressions

**L5-only Q5:** Bedrock Prompt Management vs Langfuse for a 20-team platform?

**L5 answer**
- Bedrock-only models + strict AWS data boundary → Prompt Management, plus an internal wrapper for A/B and logging
- Several model vendors + heavy experimentation → Langfuse (self-hosted on AWS keeps data in the account)
- Either way: git as source of truth, eval gate, version pinned per service
- Trade-off: native IAM and no extra service vs labels, analytics, tracing linked to prompt versions
