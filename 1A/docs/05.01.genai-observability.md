## 0. One-minute version
- What
  - Three layers of GenAI telemetry: metrics (numbers), logs (payloads), traces (call trees)
  - Bedrock gives metrics for free and logs on request; you add custom metrics and tracing
- Why
  - LLM failures are quiet: slow, throttled, truncated, expensive, or wrong, with HTTP 200
  - Tokens are the cost unit ⇒ token metrics are your bill forecast
- How
  - Built-in `AWS/Bedrock` metrics per `ModelId`: latency, tokens, throttles, errors
  - Model invocation logging writes each request/response to CloudWatch Logs and/or S3
  - Wrap the model call once: record latency, tokens, `stopReason`, errors as custom metrics
  - Alarm on throttles and p90 latency; query logs with Logs Insights
- Catch
  - Invocation logs hold prompts and answers ⇒ PII store; encrypt, restrict, expire
  - Dimensions multiply metric count and cost ⇒ low cardinality only
  - Percentiles beat averages for latency
  - No ground truth here: observability shows health, evaluations show quality
- 🗣 "Metrics tell you something is wrong, logs tell you what, traces tell you where."
- 🗣 "Tokens are the cost and the capacity unit, so graph tokens before anything else."
- 🗣 "Never log a prompt you would not want read in an audit."

## 1. Concept

### 1.1 Built-in metrics (namespace `AWS/Bedrock`)
- Dimension: `ModelId` (check `ListMetrics` for the exact value when you call through an inference profile)
- Core metrics

| Metric | Meaning | Use |
|---|---|---|
| `Invocations` | Successful requests | Traffic |
| `InvocationLatency` | Request latency, ms | p90 / p99 alarm |
| `InputTokenCount` / `OutputTokenCount` | Tokens in and out | Cost, quota headroom |
| `InvocationThrottles` | Requests throttled (429) | Quota alarm |
| `InvocationClientErrors` / `InvocationServerErrors` | 4xx / 5xx | Bug vs outage |

- Newer metrics (verify on the monitoring page): time to first token for streaming, quota-usage estimates, prompt-cache token counts
- Guardrails publish their own namespace (`AWS/Bedrock/Guardrails`: invocations, latency, intervention counts; verify names)
- Metrics have about one-minute granularity; `Sum`, `Average`, and percentiles via `ExtendedStatistics`

### 1.2 Model invocation logging
- Off by default; one configuration per account and Region
- Destinations: CloudWatch Logs, S3, or both
- Delivery flags per data type
  - Text (Converse, InvokeModel text), embedding, image, video
  - Each flag = payloads of that type logged; off = metadata only
- Large payloads
  - Bodies over the CloudWatch event size limit are written to S3 (`large_data_delivery_s3_config`); the log keeps a pointer
- Record fields (verify on a real record)
  - `timestamp`, `requestId`, `modelId`, `operation`, `identity.arn`
  - `input.inputTokenCount`, `output.outputTokenCount`
  - `input.inputBodyJson`, `output.outputBodyJson`
- Use: debugging, audit, offline evaluation datasets, cost attribution by caller
- Catch: it records caller identity, not your tenant id ⇒ pass tenant in `requestMetadata` of Converse (verify in the Converse reference) so it shows up in the log

### 1.3 Custom metrics
- Why: Bedrock metrics don't know your slice, tenant tier, `stopReason`, or business outcome
- `PutMetricData`
  - Batch many points per call (documented up to 1,000 metrics per call; check the quota page)
  - Cost = per metric (distinct name + dimension set) per month + API calls
- Embedded Metric Format (EMF)
  - Write a JSON log line with an `_aws.CloudWatchMetrics` block; CloudWatch extracts metrics from logs
  - No API call and no throttling from your code; good in Lambda and containers
- Dimension cardinality
  - `model_id` × `slice` = small, fine
  - `user_id`, `request_id`, prompt hash = metric explosion and a surprise bill
  - High-cardinality questions belong in logs (Logs Insights), not metrics

### 1.4 Alarms
- Throttles: `Sum(InvocationThrottles) > 0` over 5 min ⇒ quota or burst problem
- Latency: `p90(InvocationLatency)` over threshold, 2 of 3 windows ⇒ ignore one long generation
- Cost proxy: `Sum(OutputTokenCount)` per hour above budget, or an anomaly-detection alarm
- Errors: `InvocationServerErrors > 0`
- `treat_missing_data = notBreaching` for sparse traffic
- Send to SNS (`a-alerts`); a human or a runbook acts

### 1.5 What to log and not
- Log: model id, token counts, latency, `stopReason`, guardrail action, prompt template id and version, tenant tier
- Don't log by default: raw user prompts, retrieved documents, tool outputs with secrets
- If you must (debug, audit)
  - Redact first ([04.02](04.02.pii-redaction.md))
  - Encrypt with a CMK, short retention, narrow read access
  - Sample instead of 100 %

### 1.6 Tracing (brief)
- One user request = many spans: retrieval, rerank, model call, tool call, guardrail
- AWS X-Ray / ADOT, or OpenTelemetry with the GenAI semantic conventions (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, ...; still evolving)
- Agent frameworks and AgentCore emit spans; see the agents group (06) later
- Trace answers "which step is slow", metrics answer "how often"

### 1.7 Picture

```
 app ──converse──► Bedrock ──► AWS/Bedrock metrics (free, per ModelId)
  │                   └──────► invocation logs ─► CW Logs (a-invocations, KMS) + S3 large bodies
  │ wrapper
  └─► MetricsSink ─► PutMetricData / EMF line ─► CloudWatch (A/GenAI, ModelId × Slice)
                                    │
                    alarms (throttles, p90) ─► SNS a-alerts
                    GetMetricData (tokens/time) · Logs Insights (by model, caller)
```

## 2. When to use / not
- CloudWatch + invocation logging
  - Use: AWS-native stack, need health, cost and audit fast, no extra vendor
  - Don't: you need prompt versioning, eval datasets and trace UIs out of the box
- Custom metrics
  - Use: business or slice dimensions Bedrock lacks
  - Don't: per-user dimensions

## 3. Knobs and best practices
- Turn on invocation logging early in dev; decide flags per environment
- Keep text delivery on only where prompts are not sensitive, or after redaction
- Set log retention (30 days here) and encrypt with a CMK
- Alarm on percentiles and on throttles, not on averages
- One wrapper for all model calls ⇒ consistent metrics and dimensions
- Pass `requestMetadata` with tenant and feature ⇒ attributable logs
- Dashboards: tokens/hour by model, p90 latency, throttles, `stopReason=max_tokens` rate (truncation signal)
- Cost attribution: tokens × unit price per model, kept in a table, not hard-coded

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| CloudWatch (+ Bedrock logging) | Native metrics, logs, alarms | Zero setup, IAM-native, one bill | Weak LLM UX (no prompt diff, eval, sessions) | Health, cost, audit on AWS |
| Langfuse | OSS LLM tracing, prompts, evals | Traces, sessions, prompt versions, self-host | You run it (or pay cloud) | Product teams iterating on prompts |
| LangSmith | LangChain's tracing and evals | Deep LangChain/LangGraph integration | SaaS, tied to that ecosystem | LangChain-heavy stack |
| Datadog LLM Observability | APM extension for LLM calls | One pane with infra and APM | Cost; vendor | Already on Datadog |

- Default: CloudWatch for health, alarms, audit; add Langfuse (or similar) when prompt iteration and trace inspection matter
- Deciding variable: who looks at it (SRE vs prompt engineers) and where data may live

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Logging config silently replaced | One config per account/Region, another stack applies | Logs stop | One owner (this file); drift check |
| No logs appear | Role trust or policy wrong; CMK lacks Logs grant | Bedrock delivery errors, empty group | Check trust (SourceAccount), key policy |
| Prompts exposed | Wide read access on the log group | IAM review | Restrict, redact, short retention |
| Metric bill explodes | `user_id` in dimensions | Metric count in Billing | Drop dimension; use logs |
| Alarm never fires | Wrong `ModelId` dimension (profile vs model) | `INSUFFICIENT_DATA` | Check `ListMetrics`, fix dimension |
| Averages hide slowness | Alarm on mean latency | Users complain | Use p90 / p99 |
| Truncated answers unnoticed | `stopReason = max_tokens` | Custom `StopReason` metric | Alarm on its share; raise limit |
| `PutMetricData` throttled | One call per datum | `ThrottlingException` | Batch, or switch to EMF |

## 6. Interview questions

**Q1:** What would you monitor for a Bedrock-backed service?

**L4 answer**
- Latency percentiles, throttles, errors, input/output tokens per model
- Alarms to SNS; dashboards by model

**L5 extra**
- Add `stopReason` mix, guardrail interventions, cache hit rate
- Quality is separate: evaluations, user feedback

**Q2:** Metrics vs logs vs traces for LLM apps?

**L4 answer**
- Metrics: aggregates and alarms; logs: per-request payloads; traces: step timing across components

**L5 extra**
- Cost and cardinality: metrics cheap per series, logs per GB, traces sampled
- Use logs for high-cardinality questions

**Q3:** How do you turn on invocation logging and what's the risk?

**L4 answer**
- One logging configuration: CloudWatch group and/or S3, flags per data type
- Risk: prompts and completions are stored

**L5 extra**
- Encrypt, retain briefly, restrict, redact; large payloads to S3
- One config per account/Region ⇒ single owner

**Q4:** PutMetricData vs EMF?

**L4 answer**
- API call with batching vs a log line CloudWatch converts to metrics

**L5 extra**
- EMF avoids API throttling and latency but depends on log delivery
- Same cardinality cost either way

**Q5:** Which dimensions do you attach?

**L4 answer**
- Model id, slice/feature, maybe environment

**L5 extra**
- Never request or user ids; each combination is a billed metric

**L5-only Q6:** Design cost attribution per tenant.

**L5 answer**
- Pass tenant in `requestMetadata` → invocation logs
- Logs Insights or an S3/Athena job sums tokens per tenant × price table
- Tenant-tier (not tenant-id) as metric dimension for alarms
- Reconcile with the bill monthly; alert on tenants above quota

**L5-only Q7:** Latency doubled after a release but Bedrock metrics look flat. Where do you look?

**L5 answer**
- Bedrock `InvocationLatency` excludes your side: retrieval, rerank, prompt size growth, retries
- Compare wall time vs model-reported `latencyMs` from the wrapper
- Traces by span; check `InputTokenCount` growth (longer prompts = slower)
