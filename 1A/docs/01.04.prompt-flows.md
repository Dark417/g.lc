## 0. One-minute version
- What
  - Bedrock Flows = a managed DAG of nodes for GenAI pipelines
  - Nodes: Input, Prompt, KnowledgeBase, Condition, LambdaFunction, Agent, Iterator/Collector, InlineCode, Storage/Retrieval (S3), Output, ...
- Why
  - Chain prompts, retrieval, and business logic without writing orchestration code
  - Versioned and aliased like a deployable artifact; built visually or as JSON
- How
  → define nodes + connections (Terraform here, or `CreateFlow`)  
  → `PrepareFlow` validates and builds the DRAFT  
  → `CreateFlowVersion` snapshots it; `CreateFlowAlias` points a stable name at a version  
  → `InvokeFlow(flowId, aliasId, inputs)` streams `flowOutputEvent`s and a `flowCompletionEvent`  
- Catch
  - Expressions and data typing are limited; complex logic ends up in Lambda nodes anyway
  - Short, synchronous request/response pipelines; not for long-running or human-in-the-loop work
  - Testing and debugging = traces, not a debugger
- 🗣 "Flows are a managed DAG for prompt chains: great for linear GenAI pipelines, wrong for long-running workflows."
- 🗣 "Invoke the alias, never the draft: the alias is how you deploy and roll back."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Multi-step GenAI tasks (classify → retrieve → answer → format) lived in ad-hoc glue code
  - Each team re-wrote retries, prompt wiring, and versioning
- Flows (GA 2024-11, formerly "Prompt Flows")
  - Visual builder + API for prompt chains with branching and AWS integrations
- Common use cases
  - Route a request by intent (Condition node) to different prompts
  - RAG pipeline: KnowledgeBase node → Prompt node → Output
  - Document processing: Lambda pre-processing → Prompt extraction → S3 Storage node

### 1.2 Picture

```
InvokeFlow(alias)
   │ inputs: [{nodeName: FlowInput, nodeOutputName: document, content: {document: "..."}}]
   ▼
┌───────────┐ document  ┌────────────────────────┐ modelCompletion ┌────────────┐
│ FlowInput │──────────►│ Summarize (Prompt)     │────────────────►│ FlowOutput │──► flowOutputEvent
│  (Input)  │  →topic   │ inline TEXT template   │   →document     │  (Output)  │──► flowCompletionEvent
└───────────┘           │ model + inferenceConfig│                 └────────────┘
                        └────────────────────────┘
                 runs as the flow execution role (a-flow-role): InvokeModel
```

### 1.3 Nodes and connections
- Node = `name`, `type`, `configuration`, `inputs`, `outputs`
  - Input: the flow's entry; one output named `document` (String, Number, Boolean, Object, Array)
  - Output: the flow's exit; one input `document`; each Output node emits one `flowOutputEvent`
  - Prompt: inline template (model, template, inference config) or a managed prompt ARN (01.03); optional guardrail
  - KnowledgeBase: retrieve, or retrieve-and-generate with a model (02.04)
  - Condition: named conditions with expressions over its inputs; first match wins, plus a default branch
  - LambdaFunction: arbitrary code (validation, API calls, DB writes)
  - Agent: call a Bedrock Agent alias
  - Iterator / Collector: fan out over an array, gather results
  - InlineCode: small Python snippets inside the flow
  - Storage / Retrieval: write to / read from S3
  - Lex, Loop nodes: niche; check the docs
- Node input = `name`, `type`, `expression`
  - `expression` is a JSONPath-like selector over the incoming data, e.g. `$.data` or `$.data.field`
- Connection
  - `Data`: `sourceOutput` of one node → `targetInput` of another
  - `Conditional`: from a Condition node's named condition to the next node
- Validation
  - `ValidateFlowDefinition` checks the graph before you create it
  - `PrepareFlow` also validates; status `Prepared` or `Failed` with `validations`

### 1.4 Lifecycle: draft, prepare, version, alias
- DRAFT: editable (`UpdateFlow`); must be prepared after each change
- `PrepareFlow`: async; poll `GetFlow` until `Prepared`
- Version: `CreateFlowVersion` = immutable snapshot (`1`, `2`, ...)
- Alias: `CreateFlowAlias` with `routingConfiguration = [{flowVersion: "1"}]`
  - Callers invoke the alias ID; deploy = `UpdateFlowAlias` to a new version; rollback = point back
  - `concurrencyConfiguration` (`Automatic` or `Manual` + `maxConcurrency`) caps parallel node execution
- The DRAFT can be invoked through the built-in test alias in the console (`TSTALIASID`); never in production

### 1.5 Invoking a flow
- `bedrock-agent-runtime.invoke_flow(flowIdentifier, flowAliasIdentifier, inputs, enableTrace, executionId)`
- Response = event stream
  - `flowOutputEvent`: `nodeName`, `nodeType`, `content.document` (the result)
  - `flowCompletionEvent`: `completionReason = SUCCESS` or `INPUT_REQUIRED`
  - `flowMultiTurnInputRequestEvent`: an Agent node asks the caller for more input (multi-turn)
  - `flowTraceEvent` (with `enableTrace`): node inputs/outputs, condition results, timings
  - Errors inside the stream: `throttlingException`, `validationException`, `dependencyFailedException`, `badGatewayException`, ...
- `executionId` continues a multi-turn execution
- Limit: synchronous call with a timeout (order of magnitude: minutes); long jobs need async patterns elsewhere

### 1.6 Security: the execution role
- The flow runs as its execution role, not as the caller
  - Trust: `bedrock.amazonaws.com`, with `aws:SourceAccount` and `aws:SourceArn` = this account's flows (confused-deputy protection)
  - Permissions: `bedrock:InvokeModel` for prompt nodes; `bedrock:Retrieve` / `RetrieveAndGenerate` for KB nodes; `lambda:InvokeFunction` for Lambda nodes; `bedrock:GetPrompt` / `RenderPrompt` for managed-prompt nodes; KMS for an encrypted flow
- The caller needs `bedrock:InvokeFlow` on the alias ARN
- Whoever creates or updates a flow needs `iam:PassRole` on the execution role

## 2. When to use / not
- Use when
  - A linear or lightly branched GenAI pipeline (seconds, not hours)
  - Non-developers should see or edit the chain visually
  - You want versions + aliases for prompt chains without a deploy pipeline per change
- Avoid when
  - Long-running, retries per step, waits, or human approval ⇒ Step Functions (lecture 301)
  - Open-ended tool use where the model decides the steps ⇒ an agent (06.x)
  - Heavy business logic, unit tests, and code review matter most ⇒ orchestration in code

## 3. Knobs and best practices
- Invoke aliases only; deploy by moving the alias
  - Prevents: DRAFT edits reaching users
- Keep the definition in Terraform (or JSON in git)
  - Prevents: console-only drift with no review
- Use managed prompts (01.03) in prompt nodes when prompts change faster than the graph
- Attach a guardrail to prompt and KB nodes that see user input
- Validate (`ValidateFlowDefinition`) in CI before `UpdateFlow`
- Keep Lambda nodes small and idempotent
  - Prevents: duplicate side effects on retries
- Enable traces in test, sample them in production (cost, PII)
- Least-privilege execution role per flow
- `concurrencyConfiguration: Manual` to protect downstream quotas (model TPM, Lambda concurrency)

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Bedrock Flows | Managed GenAI DAG with prompt/KB/agent/Lambda nodes | Native Bedrock nodes; visual; versions + aliases; no servers | Limited expressions; sync and short; debugging via traces; Bedrock-only | Linear or lightly branched prompt chains |
| Step Functions (+ Bedrock integrations) | General workflow engine, state machine in ASL | Retries per step, waits, callbacks (human approval), long runs, wide AWS integrations | More boilerplate for prompt plumbing; per-transition cost | Long-running, auditable, HITL business workflows |
| Code orchestration (Python/Java, LangGraph) | The app calls Converse/Retrieve itself | Full control, unit tests, any logic, any vendor | You own retries, versioning, deployment | Complex or evolving logic; agents; existing services |

- Deciding variable: duration and control flow
  - Seconds and a fixed chain → Flows
  - Minutes to days, retries, approvals → Step Functions
  - Complex or model-driven logic → code
- Default: orchestration in code for backend services, unless the chain is simple and owned by non-developers → Flows, or long-running / HITL → Step Functions

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Flow not prepared | Invoking after `UpdateFlow` without `PrepareFlow` | `ValidationException` / old behavior | Prepare, then version + move alias |
| Broken wiring | Wrong `sourceOutput` / `targetInput` names or types | `ValidateFlowDefinition` errors; `Failed` status | Validate in CI; consistent naming |
| Wrong expression | `$.data.x` path does not exist | Empty or failed node output in traces | Test with traces; validate input shape |
| Access denied in a node | Execution role lacks model/KB/Lambda permission | `dependencyFailedException` / `accessDeniedException` events | Grant the node's action to the execution role |
| PassRole denied | Creator lacks `iam:PassRole` | `AccessDeniedException` on create/update | Allow PassRole on that role, to bedrock only |
| Throttling | Model TPM shared with other traffic | `throttlingException` event | Manual concurrency; inference profile; retry on the caller |
| DRAFT in production | Invoking the test alias | Behavior changes without release | Invoke a real alias pinned to a version |
| Timeout | Long Lambda or big generation | Stream error / client timeout | Move long work to Step Functions; smaller `maxTokens` |

## 6. Interview questions

**Q1:** What is a Bedrock Flow and what nodes does it have?

**L4 answer**
- A managed DAG of nodes for GenAI pipelines
- Input, Prompt, KnowledgeBase, Condition, Lambda, Agent, Iterator/Collector, Storage, Output

**L5 extra**
- Data connections map named outputs to named inputs with JSONPath-like expressions
- Runs as an execution role; caller needs `InvokeFlow` on the alias
- Each Output node emits one `flowOutputEvent`; completion is a separate event

**Q2:** How do you deploy and roll back a flow?

**L4 answer**
- Prepare the DRAFT, create a version, point an alias at it
- Rollback = point the alias back to the previous version

**L5 extra**
- Definition in Terraform/JSON with CI validation
- Canary: two aliases, or route a share of traffic in the caller
- Prompt nodes referencing managed prompt versions decouple prompt changes from graph changes

**Q3:** Flows vs Step Functions?

**L4 answer**
- Flows: short GenAI chains with native prompt/KB nodes
- Step Functions: general workflows with retries, waits, long runs

**L5 extra**
- Step Functions gives per-step retry policies, callbacks (`waitForTaskToken`) for human approval, and execution history for audit
- Flows trade that for less plumbing on prompt nodes
- Common combo: Step Functions calls Bedrock directly or invokes a flow as one step

**Q4:** How do you secure a flow?

**L4 answer**
- Least-privilege execution role; guardrails on prompt nodes

**L5 extra**
- Trust policy with `aws:SourceAccount` / `aws:SourceArn` (confused deputy)
- `iam:PassRole` restricted to bedrock and to that role
- CMK encryption; traces may contain PII ⇒ control who reads them

**L5-only Q5:** A support team wants a "triage → retrieve → answer → escalate to human" pipeline. Design it.

**L5 answer**
- Triage + retrieve + answer is a short chain → Flow (Condition on intent, KB node, Prompt node with guardrail)
- Escalation to a human waits hours → Step Functions with a task token, which invokes the flow as a step
- Or all in code if the team already owns a service and needs tests
- Trade-off: visual ownership by the support team vs testability and long-running control

  - Condition, KnowledgeBase, Lambda, Iterator/Collector nodes (only Input → Prompt → Output is coded)
  - Multi-turn flows (`flowMultiTurnInputRequestEvent` + `executionId`) are parsed but not driven
  - Flow alias canary / traffic split
