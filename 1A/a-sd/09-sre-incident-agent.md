# #9 · SRE / Incident Response Agent (alert → diagnose → propose/execute runbook)

> Prompt: "Design an on-call agent: when an alert fires, it investigates logs/metrics/traces/recent deploys, posts a diagnosis with evidence, and can execute approved runbook actions."

## §0 Assumptions
- 300 services · 400 alerts/day (60% noisy) · 3–10 real incidents/day `(assume)`
- Diagnosis posted < 3 min after alert; must cite evidence (queries + results)
- Actions: read-only always; writes (rollback, scale, feature-flag off) only from an allow-listed runbook catalog with approval, except pre-approved low-blast-radius ones
- Cost of wrong: outage extension or *causing* an outage → blast-radius tiers
- Stack: alert webhook (PagerDuty/Alertmanager) → FastAPI → job workers · ADK agent · tools over Prometheus/Loki/Tempo/GitHub/ArgoCD/feature flags · Postgres · Slack · Langfuse

## §1 Why an agent `[SW+AI]`
- Baseline: dashboards + runbooks + human. Breaks: first 10 minutes are spent gathering; noisy alerts burn people.
- Model adds: hypothesis-driven investigation (which query next), correlating deploys with symptoms, summarizing for humans.
- **L3 for read-only investigation; L2 (approval-gated) for actions.** Read tools are safe to chain freely; write actions are a fixed catalog executed by code after approval.
- Trigger: investigation path depends on what each query returns.
- **L5:** design around **blast radius tiers** and **evidence-first output**; the second-order risk is alert-storm amplification (agent runs 400 investigations, queries overload observability stack) → admission control and dedup.

## §2 Crux
- **Fast, evidence-backed diagnosis with strictly bounded write authority.**
- Success points: tool set that mirrors what a senior SRE does (metrics, logs, traces, deploy diff, dependency map) · investigation budget · alert dedup/grouping · runbook catalog with tiers · postmortem-quality trace of what the agent did · evals on replayed incidents.
- Business metric: MTTD/MTTR reduction + pages avoided; AI metric: root-cause hit rate on replayed incidents.

## §3 NFR / BoE
| NFR | Target | Enforcer |
|---|---|---|
| Time to diagnosis | p50 2 min, cap 8 min | budget |
| Investigation budget | ≤ 25 tool calls, ≤ 150k tokens, ≤ $1.5 | guard |
| Write safety | tier-0 auto (e.g. scale +1 ≤ 2×), tier-1 approval, tier-2 never | catalog |
| Observability load | ≤ 5 concurrent investigations; queries with limits/time windows | admission control |
| Evidence | every claim links a query + result snapshot | output schema |
| Availability | agent down must not block paging | fail-open to humans |
- 400 alerts → dedup → ~120 investigations/day × 100k tokens = 12M tokens/day ≈ $100–200/day. Cheap; the risk is load on Loki/Prometheus, not $.

## §4 HLD
```
[SW] Alert webhook -> [SW] FastAPI -> [SW] dedup/group (fingerprint, 10-min window) -> admission control -> queue
   worker:
     [SW] context pack: alert, service metadata, owners, recent deploys (last 24 h), dependency graph, runbook links
     [SW+AI] ADK LlmAgent (investigation loop, budget-guarded):
        tools (read): query_metrics(promql, window) | query_logs(logql, limit) | get_traces(service, window) | get_deploys(service) | diff_config | get_dependencies
        tools (write, gated): propose_action(catalog_id, params) -> [SW] tier check -> tier0 execute | tier1 Slack approval | tier2 reject
     -> [AI] diagnosis: {hypothesis, confidence, evidence[{tool_call_id, summary}], recommended_actions[]}
     -> [SW] evidence verifier: every evidence id exists; snapshots stored
     -> [SW] Slack post in incident channel; PagerDuty note
[SW] Postgres (investigations, tool_calls + result snapshots, actions, approvals, evals) · [SW+AI] Langfuse
```

## §5 Components — problem → design
- **Dedup + admission `[SW]`:** alert storms → fingerprint (service, alertname, labels) grouping within 10 min; one investigation per group; max 5 concurrent; overflow → summary "N related alerts, investigating top 1".
- **Context pack `[SW]`:** deterministic pre-fetch before the model thinks: recent deploys (top suspect ~50% of incidents), config diffs, service dependencies, runbook text. Cuts tool calls and hallucinated hypotheses.
- **Read tools `[SW+AI]`:** PromQL/LogQL generated by model but **validated**: time window ≤ 6 h, `limit ≤ 500` lines, allow-listed services/namespaces, query cost estimate (Prometheus `series` count) → reject expensive queries. Results truncated + summarized to ≤ 2k tokens; raw snapshot stored for evidence.
  - **L5:** provide *curated* tools (`error_rate(service)`, `latency_p99(service)`, `deploy_diff`) before raw PromQL; raw as escape hatch. Accuracy and load both improve.
- **Runbook catalog `[SW]`:** `actions(id, name, params_schema, tier, preconditions, rollback)`; tier-0 = reversible, small blast radius (restart one pod, scale +1); tier-1 = rollback deploy, flag off → Slack approve button by an on-call human; tier-2 = DB changes → never. Execution by code with idempotency and automatic rollback on failed postcondition.
- **Diagnosis contract `[SW+AI]`:** JSON schema; evidence ids must reference stored tool calls; confidence bucketed; "insufficient evidence" is a valid outcome (better than a wrong root cause).
- **Loop control `[SW]`:** budget; hypothesis tracker in state (`tested[]`); repeat-query detector; stop when confidence ≥ 0.8 or budget hit.
- **Evals `[AI]`:** replay 100 past incidents with frozen observability snapshots (recorded tool responses); root-cause hit rate, time, tool calls; judge on evidence quality (κ-validated); CI gate on prompt/tool changes; weekly review of false diagnoses.
  - **L5:** capture SRE feedback (`correct / partially / wrong`) on every diagnosis in Slack → drives eval set and tool roadmap.

## §6 API / schema
- `POST /alerts` (webhook) · `GET /investigations/{id}` · `POST /actions/{id}/approve|deny` · `POST /investigations/{id}/feedback`
- `investigations(id, group_fp, service, status, budget_used, diagnosis JSONB, confidence)` · `tool_calls(inv_id, tool, args, result_snapshot_uri, cost_est)` · `actions_catalog` · `action_runs(inv_id, action_id, idem_key, status, approver, rollback_status)` · `evals`

## §7 Hygiene
| Concern | Answer |
|---|---|
| AuthZ | read tools via read-only service identity; writes via catalog with approver identity recorded |
| Idempotency | action idem key; investigation per alert group |
| Timeouts | tool 20 s; investigation 8 min |
| Backpressure | admission cap; per-tool QPS limits toward observability stack |
| Breaker | LLM down → post context pack only; paging unaffected |
| Cache | metric queries 30 s; deploy list 1 min |
| Deploy | prompts/tools versioned; replay gate |
| Audit | every tool call + action + approver stored 1 y |

## §8 Failure → fallback
- Observability stack slow → curated tools only, smaller windows · Budget hit → partial findings + "insufficient evidence" · Action postcondition fails → auto-rollback + page human · Hallucinated evidence → verifier blocks post · Alert storm → dedup + one investigation.

## §9 Pop-up questions
1. **Why not runbooks + automation only?** — Investigation path is data-dependent; runbooks are the *action* half, which we keep deterministic.
2. **Agent makes it worse (rolls back the wrong service)?** — Tiers; tier-1 needs a human; preconditions; auto-rollback; blast radius limits.
3. **Prompt injection via log lines?** — Logs are data; writes only via catalog + approval; no free-form commands.
4. **Alert storm at 3 am?** — Dedup by fingerprint, admission control, per-tool limits.
5. **Wrong root cause with high confidence?** — Evidence-linked diagnosis; verifier; SRE feedback; replay evals; "insufficient evidence" allowed.
6. **How do you eval without real outages?** — Replay past incidents with recorded tool responses; chaos-injected staging incidents.
7. **L5: expand write autonomy?** — Only per action, after measuring precision on replay + weeks of shadow mode; ratchet tiers down slowly.
8. **L5: 10× services?** — Curated tools scale better than raw queries; per-team tool packs; investigation sharding by owning team.

## §10 Trade-offs + defeaters
| Decision | Chosen | Alt | Flips |
|---|---|---|---|
| Write authority | tiered catalog | free-form kubectl | never |
| Tools | curated + validated raw | raw only | tiny estate |
| Trigger | every real alert | on demand | observability stack capacity |
| Output | evidence JSON | prose | never |
- Defeaters: "give it kubectl and let it fix things" · "no budget, let it dig" · "confidence from the model = truth".

## §11 MVP ladder
- MVP0: manual trigger, 4 curated read tools, diagnosis JSON posted to Slack.
- MVP1: alert webhook, dedup, budget, evidence verifier, Langfuse.
- MVP2: tier-0/1 runbook catalog with approvals, replay eval set (30 incidents).
- MVP3: raw query tools with validators, feedback loop, shadow-mode autonomy metrics.

## §12 Memorization card
- Pitch: budgeted, evidence-linked investigation agent with a tiered runbook catalog for actions.
- Autonomy: L3 read / L2 write; trigger = data-dependent investigation path.
- Numbers: 25 tool calls · 8 min · 5 concurrent · 3 tiers · 100 replay incidents.
- Failures: harmful action · hallucinated evidence · alert-storm amplification.
- Defeaters: raw kubectl · no budget · model confidence as truth.
- MVP0→1→2: curated-tool diagnosis → alerts + dedup + verifier → tiered actions + replay evals.
- Done when: define the tiers · explain evidence verifier · describe replay evals.
