## 1. Data Model and Consistency

Questions on how keys, listing, and visibility work.

### 1.1 Folders

**Q:** Are there folders in S3? ([01](03s3.01namespace-objects.md))

**L4 answer**

- No, a flat key space; `a/b/c.txt` is one key
- Listing with prefix + delimiter `/` groups keys into common prefixes that look like folders
- Rename a "folder" = copy + delete each key

**L5 extra**

- Listing cost is per 1,000 keys scanned
  - Deep prefix scans over millions of keys are slow and billed
- Lake layouts (`dt=...` partitions) exist because the prefix is the only index
- 🗣 "Prefix is the only index S3 has."

### 1.2 Consistency

**Q:** Is S3 consistent? ([02](03s3.02consistency-request-rate.md))

**L4 answer**

- Strong read-after-write since Dec 2020
  - New objects, overwrites, deletes, and lists
- Before: eventual for overwrites and deletes, and for LIST

**L5 extra**

- Per key only; no cross-object atomicity
  - A "commit" of many files needs a manifest or a table format such as Iceberg / Delta
- Concurrent writers: last write wins unless you use conditional writes

## 2. Write Paths

Questions on large uploads, direct uploads, and create-only writes.

### 2.1 50 Gigabytes (GB) Upload

**Q:** How do you upload a 50 GB file? ([03](03s3.03multipart-transfer.md))

**L4 answer**

- Multipart upload
  - Create
  - Upload parts in parallel (>= 5 mebibytes (MiB), <= 10,000 parts)
  - Complete
- Use Transfer Manager / `upload_file` so retries and parallelism are handled
- Abort on failure and set an abort-incomplete lifecycle rule

**L5 extra**

- Part size = size / 10,000 minimum
  - 50 GB at 5 MiB parts needs ~10,240 parts ⇒ exceeds the limit
  - So use >= 8 MiB
- Per-part retry is idempotent by part number
- Complete is the atomic commit
- Parallelism is bounded by Network Interface Card (NIC) and memory (threads × part size)

### 2.2 Browser Upload

**Q:** How does a browser upload directly to S3 without exposing credentials? ([04](03s3.04presigned-urls.md))

**L4 answer**

- Server returns a presigned PUT Uniform Resource Locator (URL; or POST policy) with short expiry
- Browser uploads straight to S3; server never handles the bytes

**L5 extra**

- Signed by the server's credentials; role credentials cap the lifetime
- PUT cannot limit size; presigned POST with `content-length-range` can
- Validate afterwards (event notification → scan)
  - The URL holder controls the content

### 2.3 Create If Absent

**Q:** How do you create an object only if it does not exist? ([05](03s3.05conditional-writes.md))

**L4 answer**

- PutObject with `If-None-Match: *`
  - 412 means it already existed
- Retry 409 conflicts

**L5 extra**

- Gives a lock or leader election with only S3 (no DynamoDB)
  - Limit: no Time To Live (TTL) / fencing
  - A crashed holder needs an external expiry
- Before Aug 2024 this needed DynamoDB or head-then-put (racy)

## 3. Protection and Choice

Questions on encryption, retention, and picking a store.

### 3.1 Server-Side Encryption with S3-managed keys (SSE-S3) vs Server-Side Encryption with Key Management Service keys (SSE-KMS)

**Q:** SSE-S3 vs SSE-KMS? ([06](03s3.06encryption.md))

**L4 answer**

- SSE-S3: S3-managed keys, free, no key control
- SSE-KMS: you control the key policy, get CloudTrail audit, can revoke
- Cost: Key Management Service (KMS) request charges and KMS Application Programming Interface (API) rate quotas

**L5 extra**

- Bucket Keys reduce KMS calls by deriving data keys locally from a bucket-level key
- Cross-account readers need both bucket policy and KMS key policy access
- Disabling the KMS key makes all objects under it unreadable

### 3.2 Versioning and Lifecycle

**Q:** How do versioning and lifecycle interact? ([07](03s3.07versioning-lifecycle.md))

**L4 answer**

- Versioning keeps old versions; delete adds a marker
- Lifecycle transitions or expires current and noncurrent versions separately

**L5 extra**

- Without noncurrent expiry, cost grows forever
- Expired-object-delete-marker cleanup is needed to remove orphan markers
- Lifecycle runs asynchronously, so do not rely on exact timing

### 3.3 Storage Choice for Images

**Q:** S3 vs Elastic File System (EFS) vs Elastic Block Store (EBS) vs DynamoDB for storing user-uploaded images? ([98](03s3.98tradeoffs.md))

**L4 answer**

- S3 for the bytes; DynamoDB / Aurora for metadata and the key
- EFS / EBS only if a process needs a file system or block device

**L5 extra**

- S3 per-GB cost and durability beat EFS / EBS
- DynamoDB's 400 kilobytes (KB) item cap rules it out
- Serve through CloudFront with presigned or signed URLs

## 4. L5-Only Questions

Design questions on scale, atomicity, and audit.

### 4.1 200k Objects per Second

**Q:** Design a high-throughput ingest of 200k small objects per second. ([02](03s3.02consistency-request-rate.md))

**L5 answer**

- Above one prefix's 3,500 writes per second
  - Needs at least ~60 prefixes (200,000 / 3,500)
- Hash-spread keys across prefixes, but keep Athena-friendly partitions
  - Trade-off: write rate vs query layout
- Better: batch small records into larger files (Firehose buffering)
  - Per-request cost and listing cost dominate
- Backoff on 503; monitor 5xx

### 4.2 Half-Written Tables

**Q:** Many writers must produce a table; how do readers avoid half-written data? ([05](03s3.05conditional-writes.md))

**L5 answer**

- S3 has no multi-object atomicity
- Write files under a unique run prefix
- Then publish one manifest / table-format commit using a conditional write
- Readers read only the manifest
- Compaction and vacuum clean old files

### 4.3 Audit-Sensitive Presigned Downloads

**Q:** Presigned URLs for an audit-sensitive download: what are the risks? ([04](03s3.04presigned-urls.md))

**L5 answer**

- Bearer token: anyone with it downloads
- CloudTrail logs the signer, not the end user
- Mitigations
  - Short expiry
  - Bind to Internet Protocol (IP) via bucket policy condition, if the network allows
  - Prefer CloudFront signed cookies / URLs with an app-level auth check
