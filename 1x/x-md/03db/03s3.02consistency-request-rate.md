## 1. Consistency

Simple Storage Service (S3) now gives strong read-after-write per key, but nothing across keys.

### 1.1 Guarantee

Since 2020-12-01 S3 is strongly consistent for PUT, DELETE, and LIST.

- All regions, no extra cost (Amazon Web Services (AWS) announcement)
- Covers new objects, overwrites, deletes, and lists

→ PUT returns 200  
⇒ The next GET, HEAD, or LIST sees that object

- Before Dec 2020
  - Eventual for overwrites and deletes
  - Eventual for LIST
- No code: there is no Application Programming Interface (API) to show; the guarantee is implicit in every call

### 1.2 Limits

The guarantee is narrow; three gaps remain.

- Per object key only
  - No multi-object transaction
  - A "commit" of many files needs a manifest or a table format (Iceberg / Delta)
- Two concurrent writers to one key
  - Last writer wins
  - Unless a conditional write is used: see [05 Conditional Writes](03s3.05conditional-writes.md)
- Caches in front (Content Delivery Network (CDN), proxies) can still serve stale bytes
  - Fix: versioned key names or cache invalidation

## 2. Request Rate

S3 throttles per partitioned prefix, not per bucket.

### 2.1 Per-Prefix Limits

Each partitioned prefix supports a fixed request rate (S3 performance guide).

- 3,500 PUT / COPY / POST / DELETE per second
- 5,500 GET / HEAD per second
- The number is guidance, not a Service Level Agreement (SLA)

### 2.2 Scaling Rule

S3 splits hot prefixes automatically, so more prefixes give more aggregate rate.

- S3 partitions prefixes automatically as load grows
- More prefixes ⇒ more aggregate rate
  - Parallelize across prefixes
  - Spread hot writes with a hash or date prefix

→ A sudden spike lands on a new prefix  
⇒ S3 has not partitioned it yet  
⇒ 503 SlowDown  
→ Retry with exponential backoff and jitter (Software Development Kit (SDK) does by default)  
→ Warm up gradually

```java
// illustrative: hash-spread key so writes fan out across prefixes
String key = String.format("%02x/%s", (id.hashCode() & 0xff), id);
```

**Catch**

- Hash prefixes fight query layout
  - Athena wants `dt=...` partitions
  - Trade-off: write rate vs query layout
- First-byte latency is order of tens of milliseconds (ms)
  - Not for low-latency random reads of tiny items

## 3. Ranged GET

A Hypertext Transfer Protocol (HTTP) `Range` header reads only part of an object.

- Uses
  - Read a Parquet footer
  - Resume a download
  - Parallel ranged GETs for big downloads ⇒ throughput beyond one connection
- Bounds are inclusive

**Java**

```java
// infra/_03db_03s3/S3LakeStore.java
@Override
public byte[] getRange(String key, long firstByte, long lastByte) {
    return s3.getObject(GetObjectRequest.builder().bucket(bucket).key(key)
            .range("bytes=" + firstByte + "-" + lastByte).build(), // inclusive bounds
            ResponseTransformer.toBytes()).asByteArray();
}
```

**Python**

```python
# app/infra/_03db_03s3.py
def get_range(key: str, first_byte: int, last_byte: int) -> bytes:
    return _s3().get_object(
        Bucket=_bucket(), Key=key, Range=f"bytes={first_byte}-{last_byte}"
    )["Body"].read()
```

**Catch**

- A start beyond the object size returns 416 InvalidRange
- The range is on stored bytes, not on decrypted logical rows
