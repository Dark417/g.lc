## 0. One-minute version
- What
  - PostgreSQL-compatible engine on a purpose-built distributed storage volume
  - Compute (writer + up to 15 readers) is separate from storage
- Why
  - Classic Postgres HA ships full pages and WAL to a standby with its own disk
    - Every replica = another full copy, another I/O path, minutes to rebuild
  - Aurora ships only redo log records to a shared, 6-way replicated volume
- How
  - Each 10 GB segment lives as 6 copies across 3 AZs
  - Write is durable at 4/6 acks; recovery read quorum is 3/6
  - Readers attach to the same volume, so a replica costs compute, not storage
  - Cluster endpoint → current writer; reader endpoint → DNS round-robin over readers
- The catch
  - Readers lag the writer (AWS: usually under 100 ms) ⇒ no read-your-writes on the reader endpoint
  - Failover flips a DNS name ⇒ clients with cached DNS or long-lived connections hit the old node
  - It is still single-writer Postgres: write throughput is bounded by one instance
- What the app must do
  - Two pools (writer, reader), bounded `maxLifetime`, fresh IAM token per new physical connection, TLS `verify-full`
  - Retry SQLSTATE `40001` / `40P01` / `08xxx` at the transaction boundary, with idempotency keys
  - Pick isolation on purpose: READ COMMITTED default, REPEATABLE READ for snapshots, SERIALIZABLE for invariants
- 🗣 "Aurora moves replication from the database to the storage layer: the writer ships redo log records, and storage turns them into pages."
- 🗣 "A replica is just another compute node on the same volume, so adding one doesn't copy data, but it still lags by milliseconds."
- 🗣 "Retries belong outside the transaction, and only work when the write is idempotent."

## 1. Concept

### 1.1 Why Aurora exists
- Pain before it: Postgres or MySQL on network block storage (EBS) with a synchronous standby
  - Each write = WAL + data page + full-page image + standby copy ⇒ write amplification over the network
  - Paper's measurement (MySQL-based Aurora vs mirrored MySQL, SIGMOD 2017, Table 1)
    - 35× more transactions
    - 7.7× fewer I/Os per transaction
    - Limit: one benchmark from the authors, MySQL engine, 2017 hardware
  - Adding a read replica copied the whole dataset and replayed WAL on its own disk
  - Failover = promote a standby that may need crash recovery
- Insight in the paper
  - The bottleneck moved from CPU/disk to the network between compute and storage
  - So send the smallest thing possible over the network: the redo log
- Common use cases
  - OLTP services that outgrew one RDS instance's read capacity
  - Systems needing fast failover with no data loss inside one Region
  - Spiky or dev/test workloads on Serverless v2

### 1.2 Storage: the log is the database
- Volume is split into 10 GB segments; each segment = a protection group of 6 copies
  - 2 copies per AZ, 3 AZs
- Write path

  → Writer generates redo log records for a transaction  
  → Sends them to all 6 storage nodes of each affected segment  
  → Commit is acknowledged once 4 of 6 nodes persisted the records  
  → Storage nodes later coalesce log records into data pages in the background  
  ⇒ No page writes, no checkpoint I/O, no full-page writes from the writer

- Quorum math (paper, §2.1)
  - V = 6, write quorum Vw = 4, read quorum Vr = 3
  - Vw + Vr > V ⇒ every read quorum overlaps the latest write
  - 2·Vw > V ⇒ two writes cannot both succeed on disjoint sets
  - Lose a whole AZ (2 copies) + 1 more node ⇒ 3 left ⇒ still readable, data intact
  - Lose a whole AZ ⇒ 4 left ⇒ still writable
- Limit: normal reads do **not** use a 3/6 quorum
  - Writer knows which segments are current and reads one (paper §4.2.3)
  - The read quorum is used when rebuilding state during recovery
- Small segments make repair fast
  - Paper: a 10 GB segment repairs in about 10 s on a 10 Gbps link
  - Short repair window ⇒ low chance of a second failure before repair finishes
- Picture

```
       app: writer pool                    app: reader pool
            |                                    |
   cluster endpoint (CNAME)          reader endpoint (DNS round-robin)
            |                                    |
   +----------------+                   +----------------+
   | writer (AZ-a)  |                   | reader (AZ-b)  |
   +-------+--------+                   +-------+--------+
           | redo log records only              | page reads on cache miss
           v                                    v
   +-------------------------------------------------------+
   | shared cluster volume, 10 GB segments x 6 copies      |
   |   AZ-a: [c1][c2]    AZ-b: [c3][c4]    AZ-c: [c5][c6]  |
   |   commit ack at 4/6         recovery read at 3/6      |
   +-------------------------------------------------------+
```

### 1.3 Endpoints, replicas, replica lag
- Cluster (writer) endpoint
  - DNS CNAME to whichever instance is the writer now
  - Use for every write and every read that must see the latest commit
- Reader endpoint
  - DNS round-robin over reader instances
  - Balances **connections**, not queries
    - A pool that opened 10 connections at one moment may land them all on one reader
    - Bounded `maxLifetime` re-resolves DNS and spreads them again
- Instance endpoints and custom endpoints exist for pinning analytics to specific readers
- How a reader stays current
  - Writer streams the same redo records to readers
  - Reader applies them to pages already in its buffer cache; others are read from shared storage
  - No data copy ⇒ replica creation does not copy the dataset
- Replica lag
  - AWS docs: usually well under 100 ms; order of magnitude: tens of ms
  - Spikes under heavy write load or when a reader is CPU-starved
  - Measure: CloudWatch `AuroraReplicaLag`, or `aurora_replica_status()` on the cluster
- Read-after-write caveat

  → Client commits an order on the writer  
  → Next request reads it through the reader endpoint 20 ms later  
  ⇒ Reader may not have applied the commit yet  
  ⇒ "Order not found" or the old status  
  → Route reads that must see own writes to the writer, or pass a version and fall back to the writer when the reader is behind

### 1.4 Failover and DNS
- Trigger: writer instance failure, AZ problem, or a manual failover
- Flow

  → Aurora picks a reader by promotion tier (Terraform: `promotion_tier = count.index`), then size  
  → Promotes it to writer; storage needs no copy because the volume is shared  
  → Updates the cluster endpoint CNAME to the new writer  
  → Old writer restarts and rejoins as a reader  
  ⇒ Every open connection to the old writer breaks (SQLSTATE `08006` or `57P01`)  
  ⇒ Clients that cached the old IP connect to an instance that is now a reader  
  ⇒ Writes on it fail with `25006 read_only_sql_transaction`

- Time
  - AWS docs: service typically restored in under 60 s, often under 30 s (order of magnitude)
  - Aurora endpoint DNS TTL is short (AWS docs: 5 s)
  - Limit: JVMs and OS resolvers may cache longer
    - Java: set `networkaddress.cache.ttl` low (security property, before the first lookup)
- What the client does
  - Evict broken connections (Hikari already evicts `08xxx` and `57P0x`)
  - Also evict on `25006` from the writer pool: stale DNS put it on a reader
  - Retry the whole transaction with backoff that spans the failover window
  - Bound `maxLifetime` so the pool reconnects through fresh DNS
- Faster options
  - AWS Advanced JDBC Wrapper / Python Wrapper: reads cluster topology, reconnects to the new writer without waiting for DNS
  - RDS Proxy: keeps client connections open, re-points them to the new writer

### 1.5 Serverless v2 capacity
- Capacity unit: ACU = about 2 GiB of memory plus matching CPU and network
- Instance scales in fine steps (0.5 ACU) between a configured min and max
  - Terraform here: 0.5–8 ACU
  - AWS ceiling per instance: 256 ACU (user guide, 2024; check current)
  - Newer engine versions allow min 0 with auto-pause (AWS announcement, Nov 2024)
- Mechanism: scales the instance in place, without failover or reconnect
- Costs
  - Buffer cache shrinks with capacity ⇒ cold reads after scale-down
  - Scale-up takes time; a sudden spike from a very low floor hits a small cache
  - `max_connections` is derived from max capacity, not current capacity
- Deciding variable for `min_capacity`: how cold a cache you tolerate at the first request after idle

### 1.6 IAM auth tokens and TLS
- Token = a SigV4-presigned request for action `rds-db:connect`
  - Generated locally by the SDK; no network call (credentials resolve once, then cache)
  - Java: `RdsUtilities.generateAuthenticationToken`; Python: `boto3 client("rds").generate_db_auth_token`
- Validity: 15 minutes, checked **only at login**
  - An open connection outlives its token
  - A token reused for a new connection after 15 min fails with `PAM authentication failed`
  - Rule: generate a fresh token per new physical connection, never once at startup
- Requirements
  - DB user granted `rds_iam` (here `x_app`)
  - IAM policy on `arn:aws:rds-db:<region>:<account>:dbuser:<cluster-resource-id>/x_app` (Terraform `app_aurora`)
  - TLS required for IAM auth; the parameter group also sets `rds.force_ssl = 1`
- TLS mode
  - `sslmode=verify-full` checks the CA chain **and** the hostname
  - `require` encrypts but accepts any certificate ⇒ open to man-in-the-middle
  - Needs the RDS CA bundle on disk (`sslrootcert`)
- Limit: AWS recommends IAM auth below about 200 new connections per second
  - A connection storm after failover (every pod reconnects at once) can exceed it
  - Pools with jittered lifetimes and a small min size soften the storm
- Why not a password: rotates automatically, no secret in config, revoked with the IAM role

### 1.7 Connection pooling and RDS Proxy
- A Postgres connection = one backend OS process on the server
  - Memory per backend: order of magnitude several MB
  - Login with TLS + IAM: order of magnitude tens of ms
  - Rule: pool and reuse connections; never connect per request
- Pool knobs (Hikari names; psycopg_pool equivalents in §3)
  - `maximumPoolSize`: hard cap per process
  - `connectionTimeout`: max wait for a free connection before failing
  - `maxLifetime`: retire a connection after this age (Hikari adds jitter)
  - `idleTimeout`: retire idle connections above `minimumIdle`
- Why `maxLifetime` < 15 min token / failover horizon
  - Not because the token kills open connections; it does not
  - Real reasons
    - Re-resolve DNS regularly ⇒ rebalance across readers, leave a demoted writer
    - Bound how long a connection keeps state from an old instance
    - Exercise the token path regularly, so broken IAM config surfaces early
  - Convention here: 14 min, just under token life
- Sizing
  - Hikari wiki rule of thumb: `cores × 2 + spindles` per database, not per pod
  - Constraint: `pods × pools × maxSize` < `max_connections` minus admin headroom
  - `REQUIRES_NEW` and separate audit connections double per-request demand
- RDS Proxy: managed connection pooler in front of the cluster
  - Multiplexes many client connections onto fewer DB connections
  - Keeps client connections across failover; AWS says failover gets faster
  - Pinning: session state (`SET`, temp tables, some prepared statements) pins a client to one DB connection ⇒ multiplexing lost
  - Costs per vCPU/ACU-hour and adds a hop (order of magnitude: about a millisecond)
  - Choose when: many short-lived clients (Lambda) or connection count, not query load, is the limit

### 1.8 PostgreSQL engine: MVCC and vacuum
- MVCC: every row version carries `xmin` (creator txn) and `xmax` (deleter txn)
  - UPDATE = write a new version, mark the old one dead
  - A snapshot decides which versions a statement sees
  - Result: readers never block writers; writers never block readers
- Cost: dead versions accumulate (bloat)
  - VACUUM marks dead space reusable; autovacuum runs it in the background
  - VACUUM can only remove versions older than the oldest running snapshot (xmin horizon)
  - Result: a transaction left open for hours blocks cleanup for the whole cluster
  - Terraform sets `idle_in_transaction_session_timeout = 60 s` to kill forgotten transactions
- Transaction IDs are 32-bit
  - VACUUM "freezes" old rows; if it falls behind, Postgres stops writes to prevent wraparound
  - Watch `age(datfrozenxid)`
- UPDATE-heavy hot rows also create versions; HOT updates avoid index writes when no indexed column changes

### 1.9 Isolation levels
- PostgreSQL implements three (READ UNCOMMITTED behaves as READ COMMITTED)

| Level | Snapshot | Prevents | Still allows | Error to retry |
|---|---|---|---|---|
| READ COMMITTED (default) | New snapshot per statement | Dirty reads | Non-repeatable reads, lost update in read-modify-write | none (blocked UPDATE re-checks the new row) |
| REPEATABLE READ | One snapshot per transaction (snapshot isolation) | Non-repeatable reads, phantoms (stronger than ANSI) | Write skew | `40001` when updating a row changed after the snapshot |
| SERIALIZABLE | Snapshot + SSI conflict tracking | All anomalies incl. write skew | False-positive aborts | `40001` on a dangerous read-write dependency cycle |

- READ COMMITTED detail
  - A blocked UPDATE waits for the other writer, then re-evaluates its WHERE on the new row version
  - Safe: `UPDATE stock SET n = n - 1 WHERE n > 0`
  - Loses updates: `SELECT n`, then `UPDATE SET n = <app value>`
- SERIALIZABLE = Serializable Snapshot Isolation (Ports & Grittner, VLDB 2012)
  - Reads take SIREAD predicate locks (no blocking)
  - Two concurrent transactions with rw-dependencies both ways ⇒ one aborts with `40001`
  - Index-backed predicates lock index ranges; a sequential scan locks the whole table ⇒ more false positives
  - The application **must** retry the whole transaction
- Readers (hot standby): SERIALIZABLE is not available; use REPEATABLE READ for consistent read-only reports
- Example write skew the code shows: two orders for one customer, each checks "open total + mine ≤ limit"
  - REPEATABLE READ ⇒ both see the old total, both insert ⇒ limit exceeded
  - SERIALIZABLE ⇒ one gets `40001`, the retry sees the other order and rejects

### 1.10 Locking: FOR UPDATE and SKIP LOCKED
- `SELECT … FOR UPDATE` takes a row lock until the transaction ends
  - Use for read-check-write on a row (reserve stock, debit balance)
  - Catch: holds the lock across app logic ⇒ keep the transaction short
  - Catch: lock rows in a stable order (by key) or risk deadlock `40P01`
  - Bound waits with `SET LOCAL lock_timeout` ⇒ `55P03` instead of hanging
  - Simpler when it fits: one conditional statement `UPDATE … SET n = n - k WHERE n >= k`
- `FOR UPDATE SKIP LOCKED` (PostgreSQL 9.5+)
  - Skips rows another transaction locked instead of waiting
  - Result: N workers each grab different rows, so a table works as a job queue
  - Lease pattern used in the code
    - Claim = one short transaction: lock with SKIP LOCKED, set `RUNNING`, `locked_by`, `locked_until`
    - Process outside the transaction
    - Complete only if `locked_by` still matches ⇒ 0 rows = lease lost
    - A reaper resets expired leases to `READY`
  - Delivery is at least once ⇒ job handlers must be idempotent
  - Limit: polling load and index churn; beyond thousands of jobs/s use SQS or Kafka
- Optimistic locking: `version` column, `UPDATE … WHERE id = ? AND version = ?`
  - 0 rows ⇒ someone else changed it ⇒ conflict (HTTP 409), client re-reads
  - No lock held between read and write ⇒ good for human edit flows

### 1.11 Pagination: OFFSET vs keyset
- OFFSET `LIMIT 20 OFFSET 100000`
  - Server still reads and discards 100,000 rows ⇒ cost grows with page number
  - Rows inserted before the offset shift pages ⇒ duplicates or skipped rows
  - Only strength: jump to page k
- Keyset (seek) `WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20`
  - Index seek to the cursor, then read 20 rows ⇒ cost independent of depth
  - Stable under inserts
  - Needs a unique tie-breaker (`id`) because many rows share `created_at`
    - `now()` is transaction start time, so a batch insert gives every row the same timestamp
  - Needs an index matching the ORDER BY: `(customer_id, created_at, id)`, scanned backward
  - Cursor returned to the client as an opaque token
- Default: keyset for APIs and infinite scroll, unless users need numbered page jumps over a small set

### 1.12 JSONB and GIN
- JSONB = parsed binary JSON; keys deduplicated, not order-preserving
  - Operators: `@>` containment, `?` key exists, `->` / `->>` access, jsonpath `@?`
- GIN index = inverted index from keys/values to rows
  - `jsonb_ops` (default): supports `@>`, `?`, `?|`, `?&`
  - `jsonb_path_ops`: supports `@>` and jsonpath only; smaller and faster for containment
  - Write cost: one row insert touches many index entries; `fastupdate` buffers them in a pending list
- JDBC catch: `?` is a bind placeholder ⇒ use `@>` or `jsonb_exists()` instead of the `?` operator
- Limit: a column you filter on every query belongs in a real typed column with a B-tree index

### 1.13 Transactions in application code
- Spring `@Transactional` (Java)
  - Proxy-based ⇒ a call from inside the same bean skips the proxy (self-invocation) ⇒ no transaction
  - Rollback on unchecked exceptions only, by default
  - `REQUIRED`: join the caller's transaction or start one
    - Inner failure marks the whole transaction rollback-only
  - `REQUIRES_NEW`: suspend the caller, run on a **second connection**, commit independently
    - Audit rows survive the caller's rollback
    - Two connections per request ⇒ pool starvation if `pool size ≤ concurrent callers`
  - Several data sources ⇒ name the manager: `@Transactional(transactionManager = "auroraWriterTxManager")`
- psycopg 3 (Python)
  - Pool connections in autocommit mode; transactions are explicit `with conn.transaction():`
  - Nested `conn.transaction()` = SAVEPOINT
  - `SET TRANSACTION ISOLATION LEVEL …` as the first statement, so the level never leaks to the next pool user
- Retry rule

  → Retry wraps the **whole** transaction, from outside it  
  ⇒ Retrying a statement inside an aborted transaction fails with `25P02`  
  → Each attempt is a fresh transaction on a fresh or validated connection  
  → Writes carry an idempotency key (unique column + `ON CONFLICT DO NOTHING`)  
  ⇒ A commit whose ack was lost (connection dropped during COMMIT) is replayed safely  

- Retryable SQLSTATEs used in the code
  - `40001` serialization failure, `40P01` deadlock
  - `08xxx` connection failures, `57P01`–`57P03` shutdown / starting up (failover)
  - `25006` read-only transaction on the writer pool (stale DNS after failover)
  - `55P03` lock timeout
  - Not retried: constraint violations (`23xxx`), syntax, pool-wait timeout without a SQLSTATE (load shedding)

## 2. When to use / not
- Use Aurora PostgreSQL when
  - Relational model, joins, constraints, transactions across rows and tables
  - Read-heavy with replicas, and you want replicas without data copies
  - Fast in-Region failover with no committed-data loss matters
  - Storage grows unpredictably (auto-grows; no volume sizing)
- Avoid when
  - Write throughput beyond one large instance ⇒ shard (Limitless), DynamoDB, or a distributed SQL engine
  - Key-value access at very high scale with single-digit-ms tail latency ⇒ DynamoDB
  - Small, steady, cost-sensitive workload ⇒ RDS PostgreSQL is cheaper and simpler
  - Heavy analytics scans ⇒ Redshift or Athena; keep OLTP and OLAP apart
  - You need Postgres extensions or settings Aurora does not support ⇒ self-managed or RDS

## 3. Knobs and best practices

| Knob | Java (Hikari / pgjdbc) | Python (psycopg_pool) | Deciding variable |
|---|---|---|---|
| Pool max | `maximumPoolSize` (`x.aurora.pool.max-size`) | `max_size` | DB `max_connections` ÷ pods; not request concurrency |
| Wait for connection | `connectionTimeout` 3 s | `timeout` | Fail fast under overload vs ride out blips |
| Max lifetime | `maxLifetime` 14 min | `max_lifetime` 840 s | DNS rebalance cadence; under token life by convention |
| Idle retire | `idleTimeout` 5 min | `max_idle` | Cost of idle backends vs cold reconnect |
| Validate on checkout | JDBC4 `isValid()` when idle > 500 ms (built in) | `check=ConnectionPool.check_connection` | One round trip vs serving a dead connection |
| Batch inserts | `reWriteBatchedInserts=true` | `executemany` (pipeline mode) | Rows per round trip |
| Statement timeout | `options=-c statement_timeout=…` | `options` in kwargs | Longest legitimate query |
| TLS | `sslmode=verify-full` + `sslrootcert` | same libpq keys | Never lower in prod |
| Read-only pool | `setReadOnly(true)` on reader | `SET default_transaction_read_only` | Catch accidental writes to readers |

- Best practices (rule ⇒ failure it prevents)
  - Separate writer and reader pools ⇒ prevents writes landing on replicas and reads missing own writes by accident
  - Fresh IAM token per physical connection ⇒ prevents login failures 15 min after startup
  - Retry outside the transaction with idempotency keys ⇒ prevents duplicate writes on ambiguous commit
  - Keep transactions short, no network calls inside ⇒ prevents lock pile-ups and vacuum blocking
  - Name the transaction manager ⇒ prevents a silent no-op `@Transactional` when several exist
  - Keyset pagination ⇒ prevents deep-page latency growth
  - `CREATE INDEX CONCURRENTLY` on live tables ⇒ prevents a write-blocking lock during index builds
  - Migrations via Flyway/Liquibase, not app startup ⇒ prevents N pods racing DDL
- Tricks
  - `INSERT … ON CONFLICT DO NOTHING RETURNING` + fallback SELECT = idempotent create in one round trip
  - `UPDATE … WHERE n >= k` replaces SELECT FOR UPDATE for simple counters
  - `SERIALIZABLE READ ONLY DEFERRABLE` runs a consistent report with no abort risk (writer only)
  - Version number as a read-your-writes token: read the reader, fall back to the writer if `version < token`

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Aurora PostgreSQL | Postgres engine on shared 6-way quorum storage | Replicas without copies, fast failover, storage auto-grows | Single writer, higher per-I/O or per-ACU cost, AWS-only | Read-heavy OLTP that needs HA and replicas |
| RDS PostgreSQL | Community Postgres on EBS, managed by AWS | Cheaper, closest to upstream, more extensions/versions | Replica = full copy, slower failover (standby promotion) | Small or steady workload, cost first |
| Self-managed PostgreSQL (EC2 / k8s) | You run Postgres, Patroni, backups | Full control of versions, extensions, tuning | You own HA, backups, patching, on-call | Unusual extensions or settings, or non-AWS portability |
| DynamoDB | Managed key-value / document store, partitioned | Horizontal write scale, predictable latency at any size | No joins, access patterns fixed up front, limited transactions | Known key-based access at very high scale |
| Aurora DSQL | Serverless distributed SQL, PostgreSQL-compatible (GA 2025) | Active-active multi-Region, no instances to size | Optimistic concurrency (commit-time `40001`), Postgres feature subset (check docs) | Multi-Region writes and you can accept OCC retries |
| Aurora Limitless Database | Aurora PG sharded across many writers via routers (GA 2024) | Write scale-out while staying in Aurora PG | Shard key design, cross-shard queries cost more | One cluster's writer is the bottleneck |

- Default: Aurora PostgreSQL, unless the workload is small and steady (pick RDS PostgreSQL) or access is pure key-value at very high write scale (pick DynamoDB)
- Deciding variable: write throughput vs one instance's ceiling, then cost per steady I/O

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Writes fail after failover | Cached DNS points the writer pool at the demoted node | `25006 read_only_sql_transaction` | Evict on `25006`, low DNS TTL, bounded `maxLifetime`, retry |
| Broken connections | Failover or reboot | `08006`, `57P01` | Pool eviction + transaction retry with idempotency key |
| Login fails after 15 min | Token generated once at startup | `PAM authentication failed` | Generate token per new physical connection |
| Missing own write | Read through reader endpoint right after commit | Not-found right after create | Writer for read-your-writes, version token fallback |
| Duplicate order | Retry after a lost COMMIT ack | Two rows for one request | Unique idempotency key + `ON CONFLICT DO NOTHING` |
| Retry never succeeds | Retry inside the failed transaction | `25P02 current transaction is aborted` | Retry the whole transaction from outside |
| Pool starvation | `REQUIRES_NEW` or nested pool use with pool ≤ concurrency | Connection timeout, threads blocked | Bigger pool, fewer nested connections |
| Write skew | Invariant across rows under RC/RR | Business rule broken, no error | SERIALIZABLE + retry, or lock a parent row |
| Lost update | Read-modify-write under RC | Overwritten changes | Version column, or atomic `UPDATE … SET n = n - k` |
| Deadlock | Two transactions lock rows in opposite order | `40P01` | Lock in key order; retry |
| Lock pile-up | Long transaction holds `FOR UPDATE` | `pg_locks` waits, `55P03` | Short transactions, `lock_timeout` |
| Stuck job | Worker crashed after claiming | `RUNNING` with past `locked_until` | Lease + reaper; idempotent handler |
| Deep pages slow | OFFSET pagination | Latency grows with page number | Keyset pagination |
| Table bloat | Long or idle transactions block vacuum | Dead tuples rise, `n_dead_tup` | `idle_in_transaction_session_timeout`, autovacuum tuning |
| Reconnect storm | Every pod reconnects at once after failover | IAM auth throttling, CPU spike | Jittered lifetimes, small min idle, RDS Proxy |

## 6. Interview questions

**Q1:** How does Aurora store data differently from RDS PostgreSQL?

**L4 answer**
- RDS writes pages and WAL to its own EBS volume; replicas keep full copies
- Aurora's writer sends only redo log records to a shared storage volume
- Each 10 GB segment has 6 copies in 3 AZs; commit needs 4 acks
- Replicas read the same volume, so they don't copy data

**L5 extra**
- Quorum overlap: 4 + 3 > 6 and 2·4 > 6 ⇒ reads see the latest write, no split writes
- Survives AZ + 1 node for reads, a full AZ for writes
- Normal reads hit one known-current segment, not a quorum
- Small segments repair in seconds, shrinking the double-failure window
- Cost: a network hop per page miss, and pricing per I/O or ACU

**Q2:** A user creates an order and immediately can't see it. Why, and how do you fix it?

**L4 answer**
- The read went to the reader endpoint; the replica had not applied the commit yet
- Lag is usually under 100 ms but not zero
- Read from the writer for flows that must see their own writes

**L5 extra**
- Version or LSN token: client sends the version it wrote; read the reader, fall back to the writer if behind
- Sticky-to-writer window per session after a write
- Trade-off: every fallback adds writer load; measure the fallback rate
- Monitor `AuroraReplicaLag`; a CPU-starved reader lags more

**Q3:** Walk through an Aurora failover from the application's point of view.

**L4 answer**
- Writer dies; Aurora promotes a reader and repoints the cluster endpoint DNS
- Open connections break; the app must reconnect and retry
- Takes tens of seconds (AWS: typically under 60 s)

**L5 extra**
- Cached DNS sends new connections to the demoted node ⇒ `25006`; evict on it
- Retry the whole transaction; a lost COMMIT ack is ambiguous ⇒ idempotency key
- Retry budget must span the failover window, but stay under the request deadline
- AWS JDBC Wrapper or RDS Proxy cut failover time by not depending on DNS

**Q4:** Why use IAM auth, and what breaks if you implement it naively?

**L4 answer**
- No password in config; access follows the IAM role
- Token is valid 15 minutes and needs TLS

**L5 extra**
- Token is checked only at login ⇒ open connections outlive it
- Naive: generate once at startup ⇒ every new connection after 15 min fails
- Fix: password supplier per physical connection (wrapper DataSource / callable kwargs)
- Verified on HikariCP 6.3.3: the pool reads credentials via `getCredentials()`, so overriding `getPassword()` in a subclass does nothing
- AWS recommends under about 200 new IAM connections per second ⇒ jitter reconnects

**Q5:** Explain PostgreSQL's isolation levels and when you'd pick each.

**L4 answer**
- READ COMMITTED default: each statement sees committed data as of its start
- REPEATABLE READ: one snapshot for the transaction
- SERIALIZABLE: behaves as if transactions ran one at a time

**L5 extra**
- RR is snapshot isolation; stronger than ANSI RR (no phantoms) but allows write skew
- RR raises `40001` when updating a row changed after the snapshot (first updater wins)
- SERIALIZABLE is SSI: predicate SIREAD locks, aborts on dangerous dependency cycles, false positives
- Both need whole-transaction retries; SERIALIZABLE unavailable on read replicas

**Q6:** How would you build a job queue on Postgres?

**L4 answer**
- Table of jobs; workers claim with `SELECT … FOR UPDATE SKIP LOCKED LIMIT n`
- Mark them running, process, mark done

**L5 extra**
- Claim and process in separate transactions; claim sets a lease (`locked_until`)
- Complete only if still the lease owner; reaper requeues expired leases
- At-least-once ⇒ idempotent handlers
- Partial index on `READY` rows; limit is polling and index churn ⇒ SQS/Kafka at high rates

**Q7:** Why does OFFSET pagination get slow, and what replaces it?

**L4 answer**
- The database reads and throws away all skipped rows
- Keyset: `WHERE (created_at, id) < cursor ORDER BY … LIMIT n`

**L5 extra**
- Needs a unique tie-breaker and a matching composite index
- Stable under concurrent inserts; cannot jump to page k
- Opaque cursor lets you change the sort key later

**Q8:** Optimistic vs pessimistic locking: when each?

**L4 answer**
- Optimistic: version column, fail on 0 rows updated, client retries
- Pessimistic: `SELECT … FOR UPDATE` blocks others until commit

**L5 extra**
- Optimistic wins with low contention and long think time (human edits)
- Pessimistic wins with high contention on short critical sections
- Often best: one atomic conditional UPDATE, no read at all
- Pessimistic needs key-ordered locking and `lock_timeout`

**L5-only questions**

**Q9:** Design the data layer for a checkout service on Aurora that must survive failover without double charging.
- Writer pool for writes, reader pool for catalog reads; read-your-writes via writer
- Idempotency key per checkout, unique column, `ON CONFLICT DO NOTHING` + fetch
- One transaction: order insert + stock decrement (conditional UPDATE) + outbox row
- Payment call outside the transaction; outbox relay drives it with its own idempotency key
- Retry whole transaction on `40001`/`40P01`/`08xxx`/`25006` with jittered backoff spanning ~30–60 s
- Pool sizing from `max_connections`, not from request concurrency

**Q10:** Your Aurora writer is at 90% CPU from writes. What are your options, in order?
- Find waste first: Performance Insights top SQL, missing indexes, N+1 queries, chatty transactions
- Batch writes, drop unused indexes (each index = extra write)
- Move reads off the writer to replicas or a cache
- Scale up the writer (max ACU / larger class)
- Then partition the write path: Limitless sharding, split by domain, or move a key-value hot path to DynamoDB
- Trade-off: each step adds operational cost; sharding changes the data model

**Q11:** When does SERIALIZABLE hurt more than it helps, and what do you use instead?
- High contention on the same predicate ⇒ abort-retry storms, wasted work
- Sequential scans widen predicate locks to the table ⇒ false positives
- Alternatives
  - Lock a parent row (`SELECT … FOR UPDATE` on the customer) to serialize only that customer
  - Materialize the invariant in a row (running total) and update it atomically
  - Constraint or exclusion constraint where the invariant fits one
