## 0. One-minute version
- **What**
  - Principles are heuristics for one goal: lower the cost of the next change
  - They are not laws; each one trades indirection for flexibility
- **Why**
  - Most cost of a long-lived service is change, not first delivery
  - Change is cheap when it touches one place and breaks nothing far away
- **How** (two forces + two brakes)
  - Raise cohesion: keep things that change together, together (SRP, SoC, ISP, encapsulate what varies)
  - Lower coupling: depend on stable contracts, not details (DIP, OCP, interfaces, LoD, composition)
  - Brakes: KISS and YAGNI stop you paying for change that never comes
  - Spring = these ideas built into a framework (DI = DIP by container, AOP = SoC for cross-cutting code)
- **Catch**
  - Every principle over-applied creates its own smell
  - SRP → class explosion; DRY → wrong shared abstraction; OCP → speculative plugin points
- 🗣 "Principles are a cost model, not a checklist: I apply one when I can name the change it makes cheaper."

| Principle | One line | Smell when violated | 🗣 line to say aloud |
|---|---|---|---|
| [1.1 SRP](#11-srp--single-responsibility) | One module answers to one actor | God class edited by finance, ops and marketing | "One reason to change means one stakeholder, not one method." |
| [1.2 OCP](#12-ocp--openclosed) | Add behavior by adding code, not editing tested code | `switch` on type repeated in many places | "I close code against the variation I have seen twice, not the one I imagine." |
| [1.3 LSP](#13-lsp--liskov-substitution) | A subtype keeps the base type's promises | `instanceof` checks, `UnsupportedOperationException` overrides | "Signatures compile; behavior substitutes — LSP is about the second." |
| [1.4 ISP](#14-isp--interface-segregation) | Clients depend only on methods they use | Stub methods that throw; huge mocks in tests | "Interfaces belong to the client, sized to what it calls." |
| [1.5 DIP](#15-dip--dependency-inversion) | Policy owns the interface; details implement it | Domain imports the AWS SDK or JDBC | "The arrow of source dependency points at the policy, not the database." |
| [2.1 DRY](#21-dry) | One authoritative home per piece of knowledge | Same rule edited in 3 places, one forgotten | "DRY is about knowledge, not identical-looking text." |
| [2.2 KISS](#22-kiss) | Simplest design that meets real requirements | Generic engine for a 5-line rule | "Simple means fewer moving parts, not fewer requirements handled." |
| [2.3 YAGNI](#23-yagni) | Do not build what no requirement needs yet | Plugin system with one plugin | "YAGNI covers features, not things that are expensive to retrofit." |
| [2.4 SoC](#24-separation-of-concerns) | Each part handles one concern | Controller that parses, prices, writes SQL and logs | "Separate concerns so each can change and be tested alone." |
| [2.5 Cohesion / coupling](#25-high-cohesion--low-coupling) | Strong inside, thin between | `Utils` grab-bag; edits ripple across modules | "Cohesion is what changes together; coupling is what breaks together." |
| [2.6 Composition](#26-composition-over-inheritance) | Assemble behavior from parts, not deep subclassing | `LoggingRetryingEmailNotifier` class tree | "Inheritance is the tightest coupling Java offers; I use it only for real is-a." |
| [2.7 Program to interface](#27-program-to-an-interface) | Depend on the narrowest contract you need | Params typed `ArrayList`, `HashMap` | "Accept the widest type I can handle, return the most useful specific one." |
| [2.8 Encapsulate what varies](#28-encapsulate-what-varies) | Wall off the axis of change | Region-specific fee logic inside checkout | "Find the part that changes, put a stable interface in front of it." |
| [2.9 LoD](#29-law-of-demeter) | Talk only to your direct collaborators | `order.getCustomer().getWallet().getBalance()` | "Dots are fine on data and fluent APIs; LoD is about behavior-rich objects." |
| [2.10 Tell-don't-ask](#210-tell-dont-ask) | Tell an object to act; don't pull its state and decide | `if (a.getBalance() >= x) a.setBalance(...)` | "Put the decision next to the data that guards the invariant." |
| [2.11 CQS](#211-command-query-separation-cqs) | A method changes state or returns data, not both | Getter that increments a counter | "Queries must be safe to call twice — except atomic ops where splitting causes races." |
| [2.12 Fail fast](#212-fail-fast) | Reject bad input at the first boundary | Null blows up three services later | "Fail fast per record, degrade gracefully per system." |
| [2.13 POLA](#213-principle-of-least-astonishment-pola) | Behavior matches what name and context suggest | `get` that writes; mutable default args | "If a reader must open the method to know what it does, the name failed." |
| [3.1 IoC](#31-inversion-of-control) | The framework calls your code and owns wiring | `new` of infrastructure inside business code | "Spring owns the object graph; my code owns the business rules." |
| [3.2 DI](#32-dependency-injection) | Dependencies come in through the constructor | `@Autowired` private fields | "Constructor injection makes dependencies visible, final and testable with `new`." |
| [3.3 AOP](#33-aop-for-cross-cutting-concerns) | Cross-cutting code applied by proxies | Copy-pasted timing/tx code; `@Transactional` silently ignored | "Spring AOP is a proxy: calls through `this` never see it." |
| [3.4 Auto-config](#34-convention-over-configuration--auto-configuration) | Sensible beans by default, your bean wins | Mystery beans; startup fails after adding a jar | "Auto-config is `@Conditional` beans that back off when I define my own." |

## 1. Concept

### Map: what every principle is really for

```
                     cost of the next change
                               |
            +------------------+------------------+
            |                                     |
     raise COHESION                         lower COUPLING
  SRP, SoC, ISP,                        DIP, OCP, program-to-interface,
  encapsulate what varies               LoD, tell-don't-ask, composition
            |                                     |
            +------------------+------------------+
                               |
       correctness guards: LSP, CQS, fail fast, least astonishment
                               |
       brakes on over-design:  KISS, YAGNI  (and DRY used carefully)
                               |
       Spring = the same ideas in a framework:
         IoC/DI ............ DIP done by a container
         AOP ............... SoC for cross-cutting concerns
         auto-config ....... convention over configuration
         @ConfigurationProperties ... encapsulate what varies per environment
         JdbcTemplate ...... template method + callbacks (DRY for resources)
```

- Running domain in code: orders → payments → notifications
- Per principle below: idea → example → mechanism → **catch** (where it breaks)

### Part A — SOLID (Java + Python)
- Name and grouping: Robert C. Martin, "Design Principles and Design Patterns" (2000); acronym by Michael Feathers
- Shared goal: classes whose changes stay local and whose substitutes are safe

#### 1.1 SRP — Single Responsibility
- **Idea**
  - A module has one reason to change
  - "Reason" = one actor (stakeholder group), per Martin, *Clean Architecture* (2017)
  - Not "does one thing" — that rule is for functions
- **Example** (`Srp`)
  - Violation: `OrderService.place` prices with tax, stores the order, formats the email
  - Finance, ops and marketing all edit the same class
  - Fix: `PriceCalculator`, `OrderRepository`, `OrderNotifier`; `OrderService` only coordinates
- **Mechanism**
  - Each actor's change request lands in a different file
  - So: smaller diffs, fewer merge conflicts, tests target one reason

**Catch**

→ "One reason" is read as "one method".  
⇒ 40 one-method classes; the flow is spread across files and hard to follow.  
→ Split only when two actors really change the code independently.

→ The split follows technical layers instead of actors.  
⇒ Every feature still edits all the classes (shotgun surgery).  
→ Test: do these methods share fields and change in the same commits? Then they belong together.

#### 1.2 OCP — Open/Closed
- **Idea**
  - Open for extension, closed for modification (Meyer, 1988)
  - Martin's version: extend through polymorphism behind a stable interface
- **Example** (`Ocp`)
  - Violation: `PaymentProcessor.pay` switches on `"CARD" | "PAYPAL"`; a new method edits and retests it
  - Fix: `PaymentMethod` interface + registry keyed by name; a new method is a new class
- **Mechanism**
  - Tested code stays untouched; new behavior is additive
  - Registration (map, Spring list injection) replaces the `switch`

**Catch**

→ You can only close against a variation you predicted.  
⇒ Wrong axis: the abstraction resists the change that actually arrives.  
→ Wait for the second or third real variant (rule of three); then extract.

→ Plugin points added "in case" (direct conflict with YAGNI).  
⇒ Interfaces with one implementation, factories, config-driven loading nobody uses.  
→ Keep a concrete class until a second variant exists.

→ The expression problem: polymorphism makes new *types* cheap but new *operations* expensive.  
⇒ Adding `refund()` to every `PaymentMethod` edits every class anyway.  
→ For a closed set, an exhaustive `switch` is fine; the compiler finds every site (Java 17: enum switch expressions; Java 21: sealed types + pattern `switch`).

#### 1.3 LSP — Liskov Substitution
- **Idea**
  - Code written for a base type works with any subtype, without knowing which
  - Behavioral subtyping (Liskov 1987 keynote; Liskov & Wing 1994)
    - Preconditions not strengthened, postconditions not weakened
    - Invariants preserved; no new exception types callers can't expect
- **Example** (`Lsp`)
  - Violation: `Payment.refund()`; `GiftCardPayment.refund()` throws `UnsupportedOperationException`
  - Callers add `instanceof GiftCardPayment` checks
  - Fix: split capability — `Payment` for all, `Refundable` only for refundable types
- **Mechanism**
  - Callers reason against the contract once, not per subtype
  - Violations surface as type checks in callers — the polymorphism stopped paying

**Catch**

→ Compilers check signatures, never behavior.  
⇒ A subtype can compile and still break callers (stricter validation, different rounding).  
→ Write one contract test suite and run it against every implementation.

→ The JDK itself trades LSP for fewer interfaces: `List.of(...).add(x)` throws.  
⇒ "Optional operations" in `java.util.Collection` docs; callers must know the concrete source.  
→ Python's `collections.abc` splits `Sequence` from `MutableSequence` instead; do the same in your types.

→ Inheritance used only for code reuse, never substituted.  
⇒ LSP looks irrelevant, but the subtype is still assignable to the base type.  
→ If it can't keep the promises, don't inherit — compose.

#### 1.4 ISP — Interface Segregation
- **Idea**
  - No client should depend on methods it does not use
- **Example** (`Isp`)
  - Violation: `OrderStore` with `find`, `save`, `purge`, `exportCsv`
  - The nightly report job only reads but must mock everything
  - Fix: role interfaces `OrderReader`, `OrderWriter`, `OrderAdmin`; one adapter implements all three
- **Mechanism**
  - Smaller dependency surface ⇒ changes to unused methods don't ripple to the client
  - Test fakes are one or two methods

**Catch**

→ One interface per method.  
⇒ Wiring noise; nobody can see the whole capability.  
→ Split by client role (reader, writer, admin), not by method.

→ Splitting by the provider's internals rather than the client's needs.  
⇒ Clients still need three interfaces for one use case.  
→ Let the consumer define the interface; in Python a `typing.Protocol` does this structurally, without the provider knowing.

#### 1.5 DIP — Dependency Inversion
- **Idea**
  - High-level policy and low-level details both depend on abstractions
  - The abstraction is owned by the policy side (the domain package)
- **Example** (`Dip`)
  - Violation: `OrderService` does `new PostgresOrderTable()` and `new SmtpMailer()`
  - Fix: `OrderService(OrderRepository, Notifier)`; ports live with the domain, adapters implement them
  - This is the `domain` / `infra` split every 1x slice uses (hexagonal)
- **Mechanism**
  - Source dependency points opposite to the flow of control
  - So: domain compiles and tests without a database or SDK; adapters swap

**Catch**

→ DIP is confused with DI and IoC.  
⇒ Teams inject concrete classes and believe they "did DIP".  
→ DIP = who owns the interface; DI = how the object arrives; IoC = who controls the flow.

→ A "header interface" for every class, one implementation forever.  
⇒ Double the files, jump-to-definition lands on the interface, no swap ever happens.  
→ Invert at architectural boundaries (I/O, vendors, other teams), not between every pair of classes.

→ The port mirrors the vendor API (`putItem`, `KeyConditionExpression`).  
⇒ The abstraction leaks; swapping DynamoDB for Postgres is impossible anyway.  
→ Shape ports on domain needs: `save(order)`, `findByCustomer(id)`.

### Part B — General principles (Java + Python)

#### 2.1 DRY
- **Idea**
  - "Every piece of knowledge must have a single, unambiguous, authoritative representation" (Hunt & Thomas, *The Pragmatic Programmer*, 1999)
  - About knowledge (rules, schemas), not about similar-looking text
- **Example** (`Dry`)
  - Violation: tax rate `0.08` hard-coded in checkout, invoice and refund
  - Fix: one `TaxPolicy` used by all three
- **Mechanism**
  - One change site per business rule ⇒ no drift between copies

**Catch**

→ Two blocks look identical but encode different knowledge (API validation vs batch backfill validation).  
⇒ A shared helper grows boolean flags; a change for one caller breaks the other.  
→ "Duplication is far cheaper than the wrong abstraction" (Sandi Metz); merge only when the *reason to change* is the same.

→ DRY across services via a shared DTO / utils library.  
⇒ Every service must redeploy in lockstep; the library becomes a distributed monolith.  
→ Share contracts (schemas, OpenAPI), not implementation; tolerate copies of small helpers.

→ DRY applied to tests.  
⇒ Clever shared fixtures hide what each test checks.  
→ Prefer readable, slightly repetitive tests (DAMP).

#### 2.2 KISS
- **Idea**
  - The simplest design that meets the *real* requirements
- **Example** (`Kiss`)
  - Violation: a generic reflection-based rule engine to compute a shipping fee
  - Fix: a five-line function with two `if`s
- **Mechanism**
  - Fewer moving parts ⇒ less to read, fewer failure modes, faster onboarding

**Catch**

→ "Simple" code that drops real requirements (no retry, no idempotency, no timeout).  
⇒ Simplistic, not simple; complexity reappears as incidents.  
→ Keep the essential complexity, cut the accidental (Brooks, "No Silver Bullet", 1986).

→ One giant function called "simple".  
⇒ Easy to write, hard to change.  
→ Simple = few interleaved concerns, not few files.

#### 2.3 YAGNI
- **Idea**
  - Don't build a feature or abstraction until a requirement needs it (Extreme Programming)
- **Example** (`Yagni`)
  - Violation: a `PaymentProviderPlugin` SPI with config-driven class loading, for one provider
  - Fix: a concrete `StripeLikeGateway`; extract an interface when provider two appears
- **Mechanism**
  - Saves build cost, carrying cost, and the cost of guessing wrong (Fowler, "Yagni", 2015)

**Catch**

→ YAGNI applied to things that are expensive to retrofit.  
⇒ Missing idempotency keys, tenant IDs, schema versioning, auth, observability — each costs a migration later.  
→ YAGNI assumes refactoring is cheap; it is not across public APIs, persisted data, or other teams.

#### 2.4 Separation of Concerns
- **Idea**
  - Each part handles one concern (Dijkstra, 1974): HTTP, rules, persistence, logging
  - SRP is SoC applied at class level, measured by actor
- **Example** (`SeparationOfConcerns`)
  - Violation: a handler that parses input, applies discount, builds SQL, and logs
  - Fix: `parse` → `DiscountRule` → `OrderSink` port, each separately testable
- **Mechanism**
  - Reason about and change one concern at a time

**Catch**

→ Concerns read as technical layers only.  
⇒ One feature is scattered across controller/service/repo/dto packages.  
→ Package by feature (vertical slice) first, layers inside it.

→ Cross-cutting concerns (tx, security, metrics) don't fit any layer.  
⇒ Copied into every method.  
→ Use AOP, middleware, or decorators ([3.3](#33-aop-for-cross-cutting-concerns)).

#### 2.5 High cohesion / low coupling
- **Idea**
  - Cohesion: how strongly elements inside a module belong together
  - Coupling: how much a module knows about others (Constantine & Yourdon, *Structured Design*, 1979)
- **Example** (`CohesionCoupling`)
  - Violation: `OrderUtils` with `formatDate`, `calcTax`, `postToSlack`; callers reach into `Order` internals
  - Fix: `ShippingQuote` owns the zip-code rule and exposes `quoteFor(order)`
- **Mechanism**
  - Changes stay inside one module; fewer cross-module edits per feature

**Catch**

→ Coupling "removed" by switching from typed calls to events, maps, or strings.  
⇒ The coupling is still there, now invisible: a renamed field breaks a consumer at runtime.  
→ Coupling moves, it never vanishes; keep it explicit (schemas, contract tests).

→ Judging cohesion by naming instead of evidence.  
⇒ Modules that look tidy still change together.  
→ Use co-change data (`git log` files edited together) to find real seams.

#### 2.6 Composition over inheritance
- **Idea**
  - "Favor object composition over class inheritance" (GoF, 1994)
- **Example** (`CompositionOverInheritance`)
  - Violation: `EmailNotifier` → `RetryingEmailNotifier` → `LoggingRetryingEmailNotifier`
  - n optional features ⇒ up to 2ⁿ subclasses
  - Fix: decorators `Retrying(Logging(Email))` around a `Notifier` interface
- **Mechanism**
  - Behavior is assembled at runtime from small parts
  - No fragile base class: a subclass cannot depend on the base's self-calls (Bloch, *Effective Java*, `InstrumentedHashSet` example)

**Catch**

→ Composition everywhere.  
⇒ Long delegation chains and forwarding boilerplate in Java.  
→ Inheritance is right for a true is-a with a base *designed and documented for extension* (framework abstract classes, sealed data hierarchies).

#### 2.7 Program to an interface
- **Idea**
  - Depend on a supertype contract, not a concrete class (GoF)
  - "Interface" = the contract, not necessarily the `interface` keyword
- **Example** (`ProgramToInterface`)
  - Violation: `totalOf(ArrayList<Order>)` returns `HashMap`
  - Fix: `totalOf(Collection<Order>)` returns `Map`; Python takes `Iterable[Order]`, returns `Mapping`
- **Mechanism**
  - Callers bind to the narrowest contract ⇒ implementation swaps are invisible

**Catch**

→ The interface does not express cost.  
⇒ `List.get(i)` is O(1) on `ArrayList`, O(n) on `LinkedList`; a loop becomes O(n²).  
→ The JDK added the `RandomAccess` marker for this reason; document complexity in the contract.

→ Return types too narrow (`Iterable` when callers need size).  
⇒ Every caller copies into a list.  
→ Accept the widest type you can handle; return the most specific type that is useful.

#### 2.8 Encapsulate what varies
- **Idea**
  - Find the axis of change, put a stable interface in front of it
  - The engine behind OCP and the Strategy pattern
- **Example** (`EncapsulateWhatVaries`)
  - Violation: region fee rules inline in checkout, edited every quarter
  - Fix: `FeePolicy` per region, selected by a map
- **Mechanism**
  - Volatile code is isolated; stable code stops changing

**Catch**

→ Guessing the axis.  
⇒ Abstractions around stable parts, while the real change hits elsewhere.  
→ Encapsulate after observing change, not before.

→ Encapsulating as code what is really data.  
⇒ A deploy for every rate change.  
→ Rates and thresholds that business users edit belong in config or tables, not classes.

#### 2.9 Law of Demeter
- **Idea**
  - A method talks only to: itself, its parameters, objects it creates, its fields (Lieberherr et al., 1988)
  - "Only talk to your immediate friends"
- **Example** (`LawOfDemeter`)
  - Violation: `order.customer().wallet().balance()` inside checkout
  - Fix: `order.canPay(amount)`; the order asks its own collaborators
- **Mechanism**
  - Callers don't depend on the structure of distant objects ⇒ internals can be restructured

**Catch**

→ LoD read as "count the dots".  
⇒ Fluent builders, streams, and record navigation get wrapped for no gain.  
→ Chains that return the same type or plain data are fine; LoD targets behavior-rich objects.

→ Strict LoD on a middle object.  
⇒ It grows dozens of forwarding methods (wide interface).  
→ Pass the needed value in, or move the behavior to where the data is.

#### 2.10 Tell, don't ask
- **Idea**
  - Tell an object what to do; don't pull its state and decide for it
- **Example** (`TellDontAsk`)
  - Violation: service checks `wallet.balance() >= amount` then sets the new balance
  - Fix: `wallet.debit(amount)` enforces "no overdraft" inside
- **Mechanism**
  - The invariant lives in one place, next to the data that guards it

**Catch**

→ Applied to reporting and display.  
⇒ Entities grow `printInvoice`, `toCsv`, `renderHtml`.  
→ Queries for display are fine (that is CQS's "query" side).

→ Everything pushed into entities.  
⇒ God entities that need mailers and repositories.  
→ Entities guard invariants; services orchestrate I/O.

→ Data pipelines (Spark, Databricks) are function-over-data, not objects.  
⇒ Tell-don't-ask does not apply to a DataFrame transform.  
→ Use it for stateful domain objects only.

#### 2.11 Command-query separation (CQS)
- **Idea**
  - A method is a command (changes state, returns nothing) or a query (returns data, no side effects) — not both (Meyer, 1988)
- **Example** (`Cqs`)
  - Violation: `nextOrderNumber()` that also increments the counter
  - Fix: `reserveNumber()` command + `peekNext()` query
- **Mechanism**
  - Queries are safe to repeat, cache, reorder, log, retry, call from a debugger

**Catch**

→ Splitting an atomic read-modify-write into query + command.  
⇒ Check-then-act race: two callers peek the same number.  
→ Keep atomic ops combined: `AtomicLong.incrementAndGet`, `stack.pop`, `INSERT ... RETURNING id`, DynamoDB `UpdateItem` with `ReturnValues`.

→ CQS confused with CQRS.  
⇒ Teams split databases when they only needed cleaner methods.  
→ CQS = method level; CQRS = separate read and write models (Greg Young).

#### 2.12 Fail fast
- **Idea**
  - Detect and report an error at the point closest to its cause (Shore, IEEE Software, 2004)
- **Example** (`FailFast`)
  - Violation: `Order` accepts a negative amount; a downstream job crashes hours later
  - Fix: validate in the record's compact constructor / dataclass `__post_init__`; config validated at startup
- **Mechanism**
  - Short distance between cause and symptom ⇒ cheap diagnosis, no corrupted state propagated

**Catch**

→ Fail fast read as "crash everything".  
⇒ One bad row kills a 1M-row batch.  
→ Fail fast per record (reject, quarantine, DLQ); degrade gracefully per system.

→ Startup fails when an *optional* dependency is briefly down.  
⇒ Crash loops across a fleet during a dependency blip.  
→ Fail startup on invalid config; tolerate unavailable optional dependencies with retries and health checks.

→ Using `assert` as the guard.  
⇒ Java disables asserts by default; `python -O` strips them.  
→ Use explicit checks that raise.

#### 2.13 Principle of least astonishment (POLA)
- **Idea**
  - A component behaves the way its name, signature, and ecosystem lead readers to expect
- **Example** (`LeastAstonishment`)
  - Violation: `getDiscount()` that writes an audit row; Python `def add(item, items=[])` shares one list
  - Real JDK trap: `List<Integer>.remove(1)` removes index 1, not value 1
  - Fix: names that reveal side effects; `None` defaults; explicit `remove(Integer.valueOf(1))`
- **Mechanism**
  - Readers predict behavior from the call site ⇒ fewer wrong assumptions

**Catch**

→ Astonishment is audience-relative.  
⇒ Python properties surprise Java readers; Java getters look odd in Python.  
→ Follow the ecosystem's and the codebase's conventions over personal taste.

### Part C — Spring principles (Java only)
- These are SOLID and SoC built into a framework
- Container internals (bean lifecycle, scopes, `BeanPostProcessor` deep dive) → future doc **06.01 Spring IoC**

#### 3.1 Inversion of Control
- **Idea**
  - The framework calls your code ("Hollywood principle"); the container creates and wires objects
- **Mechanism**
  → Read bean definitions (component scan, `@Bean` methods, auto-config)  
  → Build the dependency graph and instantiate singletons in dependency order  
  → Inject dependencies, run post-processors (which may wrap beans in proxies)  
  → Context ready; your code runs only when called
- **Example** (`PrinciplesConfig`)
  - `@Bean` methods wire the POJO `OrderService` with a repository and notifier

**Catch**

→ Business code calls `applicationContext.getBean(...)`.  
⇒ Service-locator: hidden dependencies, container coupling, untestable without Spring.  
→ Only the composition root (config classes) knows about the container.

→ Wiring errors appear only at startup.  
⇒ That is fail fast (good), but stack traces can be long and indirect.  
→ Keep wiring explicit and small per slice; read the "Parameter 0 of constructor..." line first.

#### 3.2 Dependency Injection
- **Idea**
  - An object receives its dependencies instead of creating them
- **Styles** (`IocDi`)
  - Constructor: required deps, `final` fields, testable with `new`
  - Setter: optional deps that may be reconfigured
  - Field (`@Autowired private`): concise, but hidden and container-only
- **Why constructor**
  - Object is complete and immutable after construction
  - Unit tests need no container: `new OrderService(fakeRepo, fakeNotifier)`
  - A circular dependency fails at startup (Spring Boot ≥ 2.6 forbids cycles by default, 2.6 release notes, Nov 2021)
  - Single constructor needs no `@Autowired` (Spring ≥ 4.3)
  - Long parameter lists stay visible — a free SRP alarm

**Catch**

→ Switching to field injection because the constructor has 9 parameters.  
⇒ The SRP smell is hidden, not fixed.  
→ Split the class.

→ A cycle "fixed" with `@Lazy` or `allow-circular-references=true`.  
⇒ Startup passes; the design flaw and a runtime proxy remain.  
→ Extract the shared logic into a third bean.

#### 3.3 AOP for cross-cutting concerns
- **Idea**
  - Transactions, security, metrics, retries, caching applied around methods without editing them
  - Spring AOP is proxy-based: only method calls on Spring beans, made *through the proxy*, are advised
- **JDK dynamic proxy vs CGLIB**
  - JDK proxy: implements the bean's interfaces; only interface methods advised; casting to the class fails
  - CGLIB: runtime subclass; advises public/protected/package methods; never `final` or `private` methods
  - Spring Boot defaults to CGLIB (`spring.aop.proxy-target-class=true`, since Boot 2.0)
  - CGLIB proxies are created without calling the constructor (Objenesis) ⇒ a `final` method running on the proxy sees `null` fields
- **Self-invocation trap**
  → Caller → proxy.`checkout()` → target.`checkout()`  
  → target calls `this.writeLedger()` directly — the proxy is not in the path  
  ⇒ `@Transactional`, `@Async`, `@Cacheable`, `@Retryable` on `writeLedger` are silently ignored
- **Fixes** (best first)
  - Move the advised method to a separate bean (`Aop.SplitCheckout` + `Aop.LedgerWriter`)
  - Inject yourself lazily via `ObjectProvider<Self>` and call through it (`Aop.SelfInjectedCheckout`)
  - `AopContext.currentProxy()` with `exposeProxy=true` (couples code to Spring)
  - AspectJ compile/load-time weaving (advises self-calls; heavier build)
- **Example** (`Aop`)
  - `TimingAspect` times the POJO `OrderService` by bean name (no annotation on the POJO)
  - `TxAspect` + `@DemoTransactional` mimic `@Transactional`, so the trap is observable without a database

**Catch**

→ `@Transactional` on a method that throws a checked exception.  
⇒ Default rollback is only for `RuntimeException` and `Error` (Spring Framework docs).  
→ Set `rollbackFor`, or throw unchecked domain exceptions.

→ Several aspects on one method without explicit order.  
⇒ Retry inside a transaction retries on a doomed transaction; metrics may count attempts, not requests.  
→ `@Order` aspects explicitly (retry outside tx).

#### 3.4 Convention over configuration / auto-configuration
- **Idea**
  - Sensible defaults from what is on the classpath and in config; your own bean wins
- **What Spring Boot does at startup**
  → `SpringApplication.run` builds the `Environment` (command line, env vars, `application-{profile}.yml`, `application.yml`)  
  → `@SpringBootApplication` = `@Configuration` + `@ComponentScan` + `@EnableAutoConfiguration`  
  → User configuration classes are parsed first  
  → `AutoConfigurationImportSelector` loads candidates from `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (Boot ≥ 2.7; `spring.factories` before)  
  → Each candidate is filtered by `@ConditionalOnClass`, `@ConditionalOnMissingBean`, `@ConditionalOnProperty`, `@ConditionalOnWebApplication`  
  → Survivors register beans; singletons are created; the embedded web server starts  
  → `ApplicationReadyEvent`
- **Example** (`AutoConfig.NotifierAutoConfiguration`)
  - `@ConditionalOnProperty(x.principles.notifier=sms)` → SMS notifier
  - Else `@ConditionalOnMissingBean(Notifier.class)` → default log notifier
- **Debug**
  - `--debug` prints the condition evaluation report; Actuator `/actuator/conditions` shows it at runtime

**Catch**

→ A jar on the classpath activates a feature.  
⇒ Adding `spring-jdbc` makes Boot want a DataSource URL at startup.  
→ Exclude it explicitly — `XApplication` excludes `DataSourceAutoConfiguration` for exactly this reason.

→ `@ConditionalOnMissingBean` in an ordinary `@Configuration`.  
⇒ Result depends on parse order; it is only reliable in real auto-configuration classes (processed after user config).  
→ Use it in auto-config registered in `AutoConfiguration.imports`; in app code, wire explicitly.

#### 3.5 Non-invasive POJO programming
- **Idea**
  - Business classes don't extend or import the framework
  - Origin: Spring reacted to EJB 2, which forced container interfaces on every bean (Rod Johnson, 2002)
- **Example** (`IocDi.OrderService`)
  - No Spring imports; built by a `@Bean` method; unit-tested with `new`
- **Mechanism**
  - Domain logic survives framework upgrades and runs in tests, batch jobs, Lambdas

**Catch**

→ Annotations are still coupling (`@Transactional`, `@Entity` on domain types).  
⇒ Pure POJO domain costs mapping layers.  
→ Pragmatic line: framework annotations on adapters and services, none in core rules.

→ Proxies need non-final classes.  
⇒ Records and final classes cannot be CGLIB-proxied; advice on them fails at startup.  
→ Keep advised beans as ordinary classes; records for data.

#### 3.6 Externalized configuration
- **Idea**
  - One artifact; behavior differs per environment via config, not code
  - Property sources in precedence order (high → low): command line, env vars, profile files, `application.yml`
  - Relaxed binding: env `X_PRINCIPLES_ENABLED` → `x.principles.enabled`
- **`@ConfigurationProperties` vs `@Value`** (`PrinciplesProperties`, `ExternalConfig`)
  - `@ConfigurationProperties`: typed, grouped, immutable record, JSR-380 validated at startup
  - `@Value("${key:default}")`: one value, supports SpEL, no validation, key strings scattered
- **Profiles**
  - `@Profile("prod")` beans, `application-prod.yml`, activated by `spring.profiles.active`

**Catch**

→ Profiles used as feature flags or `if (env.equals("prod"))` in code.  
⇒ Prod-only paths never run in tests.  
→ Profiles only for environment wiring; feature flags for features.

→ Secrets in `application.yml`.  
⇒ Secrets in git and in every artifact.  
→ Inject from a secrets manager or env at runtime; IAM auth where possible.

#### 3.7 Template-style boilerplate removal
- **Idea**
  - The framework owns the fixed steps of a resource's lifecycle; you pass only the variable part as a callback
  - `JdbcTemplate`, `TransactionTemplate`, `RestClient`, `KafkaTemplate`
- **Mechanism** (`JdbcTemplate.query(sql, rowMapper)`)
  → get connection (bound to the current transaction if any)  
  → prepare statement, execute, iterate rows → your `RowMapper`  
  → translate `SQLException` into the `DataAccessException` hierarchy  
  → close everything in `finally`
  - Template method + callbacks (lambdas), not GoF inheritance
- **Example** (`TemplateMethod`)
  - Violation: every call copies open/retry/close/translate
  - Fix: `MiniTemplate.execute(callback)` owns retry, close and error translation once

**Catch**

→ The template hides cost.  
⇒ `jdbc.query` inside a loop is N+1 queries that look like one line each.  
→ Batch (`batchUpdate`, `IN` lists) and watch query counts.

→ Exception translation hides vendor detail.  
⇒ Retry logic can't see the SQL state it needs.  
→ Inspect `getCause()` / `SQLException.getSQLState()` where retry depends on it.

## 2. When to use / not
- **Apply firmly when**
  - Code is long-lived and changes often (core services, shared platform APIs)
  - Several teams or many contributors touch it
  - The boundary is public or persisted (APIs, schemas, events) — retrofitting is expensive
  - Testing needs to run without real infrastructure (DIP, DI, ports)
- **Relax when**
  - Spikes, notebooks, one-off migrations, throwaway scripts
  - Stable code nobody has touched in a year
  - Only one variant exists and none is on the roadmap (YAGNI beats OCP)
  - Performance-critical inner loops where indirection costs (order of magnitude: virtual calls are cheap on the JVM after JIT; allocations and remote calls are not)
- **Never relax**
  - LSP for types you expose to others
  - Fail fast on configuration and on input at trust boundaries
  - Idempotency and observability on networked commands (not covered by YAGNI)

## 3. Knobs and best practices
- **Design rules** (rule → failure it prevents)
  - Rule of three before abstracting → wrong shared abstraction
  - Invert dependencies at I/O and vendor boundaries first → untestable domain
  - One contract test suite per interface with >1 implementation → silent LSP breaks
  - Let the consumer own small interfaces (Java role interfaces, Python `Protocol`) → fat interfaces
  - Closed set of variants → enum / sealed type + exhaustive `switch`; open set → interface + registry → OCP misuse
  - Validate in constructors (compact record constructor, `__post_init__`) → invalid objects travelling far
  - Use co-change history to choose seams → cosmetic, not real, cohesion
- **Spring knobs**

| Knob | Default | What it trades | Change when |
|---|---|---|---|
| `spring.aop.proxy-target-class` | `true` (Boot) | CGLIB everywhere vs JDK proxies on interfaces | Almost never; set `false` only to enforce interface-only proxies |
| `@EnableAspectJAutoProxy(exposeProxy=true)` | `false` | Enables `AopContext.currentProxy()` | Legacy code that can't split beans |
| `spring.main.allow-circular-references` | `false` (Boot ≥ 2.6) | Startup passes with cycles | Temporary migration only |
| `spring.main.lazy-initialization` | `false` | Faster startup vs late wiring errors | Dev loops; avoid in prod (defeats fail fast) |
| `debug=true` / `--debug` | off | Prints auto-config condition report | Diagnosing "why is/isn't this bean here" |
| `@Order` on aspects | undefined order | Deterministic advice nesting | Any method with 2+ aspects |
| `@Validated` on `@ConfigurationProperties` | off | Startup fails on bad config | Always for required config |

- **Spring best practices**
  - Constructor injection, `final` fields, no `@Autowired` on single constructors
  - Advised methods public, non-final, called from another bean
  - `@ConfigurationProperties` records + `@Validated` for any group of ≥2 related keys
  - `@ConditionalOnMissingBean` only in auto-config classes
  - Guard optional features with `@ConditionalOnProperty` (every 1x slice does)

## 4. Comparison

**Tensions between principles**

| Tension | Pulls toward | Pulls against | Resolve by |
|---|---|---|---|
| DRY vs decoupling | One shared helper / library | Independent deploys and owners | Same reason to change → merge; different owners → duplicate |
| YAGNI vs OCP | Concrete code now | Extension point for future variants | Extract on the 2nd real variant; refactor is cheap inside one repo |
| KISS vs SOLID | Fewer classes | Ports, adapters, role interfaces | SOLID at boundaries, KISS inside a module |
| LoD vs fluent APIs | Wrap every chain | Builders, streams, records | LoD only for behavior-rich objects |
| Composition vs inheritance | Decorators, delegation | Reuse of a designed base class | Inherit only from bases designed for extension |
| Tell-don't-ask vs SoC | Logic inside the entity | Entity free of I/O | Entity guards invariants; service does I/O |
| CQS vs atomicity | Split read and write | One atomic op | Keep atomic ops combined |
| Fail fast vs availability | Crash on bad state | Keep serving | Reject per request/record; never crash the fleet on optional deps |

- Default: concrete, simple code inside a module; SOLID-style abstractions at I/O, vendor and team boundaries, unless the variation has already appeared twice.

**DI styles**

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| Constructor | Deps as constructor args | Immutable, explicit, testable with `new`, cycles fail fast | Long arg lists visible | Required dependencies (default) |
| Setter | Deps via setters | Optional / reconfigurable | Object can be half-built | Optional dependency with a sane default |
| Field | `@Autowired` on fields | Shortest | Hidden deps, no `final`, needs container in tests | Never in production code; maybe test classes |

- Default: constructor injection, unless the dependency is genuinely optional (setter or `ObjectProvider`).

**Proxy mechanisms**

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| JDK dynamic proxy | `java.lang.reflect.Proxy` implementing interfaces | No bytecode generation; target class untouched | Interface methods only; cast to class fails | Interface-only design, `proxy-target-class=false` |
| CGLIB (Spring) | Runtime subclass of the bean class | Works without interfaces; Boot default | No `final`/`private` methods; final classes and records impossible | Default in Spring Boot |
| AspectJ weaving | Compile/load-time bytecode weaving | Advises self-calls, fields, constructors | Build/agent complexity | Self-invocation or non-bean objects must be advised |

- Default: Spring's CGLIB proxies, unless self-calls or non-Spring objects must be advised (AspectJ).

**Config binding**

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| `@ConfigurationProperties` record | Typed group bound by prefix | Validation, relaxed binding, IDE metadata, immutable | One more class | ≥2 related keys, anything required |
| `@Value("${k:d}")` | Single injected value | Quick; SpEL | No validation; keys scattered as strings | One isolated value or a SpEL expression |
| `Environment.getProperty` | Programmatic lookup | Dynamic keys | Stringly typed, late failure | Framework/infra code with computed keys |

- Default: `@ConfigurationProperties` + `@Validated`, unless it is a single isolated value.

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Class explosion | SRP read as "one method per class" | Feature needs 10 files to read; tiny classes with one caller | Merge by actor / co-change; SRP is per stakeholder |
| Wrong abstraction | DRY on look-alike code | Shared helper with boolean flags or `if (caller == X)` | Inline back into callers, re-extract later |
| Speculative generality | OCP / YAGNI ignored | Interfaces with one impl, unused config hooks | Delete; keep concrete until a 2nd variant |
| LSP break | Subtype throws or tightens checks | `instanceof` in callers; contract tests fail on one impl | Split capability interfaces; compose |
| Fat interface | One interface for all clients | Mocks stub many unused methods | Role interfaces per client |
| Leaky port | Port mirrors vendor API | Domain code mentions SDK types/expressions | Reshape port around domain operations |
| Hidden coupling | "Decoupled" via events/maps | Runtime break after a field rename | Schemas, contract tests, consumer-driven contracts |
| Fragile base class | Subclass relies on base self-calls | Base change breaks subclasses | Composition / decorators; `final` by default |
| Check-then-act race | CQS split of atomic op | Duplicate numbers/IDs under load | Atomic op (`incrementAndGet`, conditional write) |
| Batch killed by one row | Fail fast at system level | Job fails on a single bad record | Validate per record, quarantine / DLQ |
| `@Transactional` ignored | Self-invocation, `private`/`final` method | No tx in logs; partial writes on error | Separate bean, `ObjectProvider` self, AspectJ |
| No rollback | Checked exception from `@Transactional` | Data committed after an error | `rollbackFor` or unchecked exceptions |
| `null` fields in bean | `final` method called on CGLIB proxy | NPE only when proxied | Remove `final`; don't call through proxy internals |
| Mystery beans / startup failure | Auto-config triggered by a new jar | `--debug` condition report | Exclude auto-config or define your own bean |
| Bad config reaches runtime | `@Value` without validation | Failure on first use, not at startup | `@ConfigurationProperties` + `@Validated` |
| Prod-only path untested | Profile-specific code branches | Bugs only in prod | Profiles for wiring only; test each profile's context |

## 6. Interview questions

**Q1: Explain SOLID with an example from your own systems.**

**L4 answer**
- SRP: a data-platform ingestion service split into parse, validate, persist, publish — each owned by a different concern
- OCP: new file formats added as new `RecordParser` implementations in a registry
- LSP: every parser honors the same contract — same errors on bad input, no extra exceptions
- ISP: the reporting job depends on `OrderReader` only, not on writer/admin methods
- DIP: the service depends on a `LakeWriter` port; S3/Delta adapters implement it

**L5 extra**
- I apply them at boundaries, not everywhere: DIP at I/O, OCP only where variants exist
- I name the cost: each interface is a file and an indirection; I accept it only where a change or a test needs it

**Q2: How do you decide when to split a class (SRP)?**

**L4 answer**
- When two different actors request changes to it independently
- Signals: unrelated field groups, merge conflicts, tests needing unrelated setup

**L5 extra**
- Evidence over taste: `git log` co-change shows which methods change together
- Over-splitting is a real failure: if a feature now spans 10 tiny classes, I merge by actor

**Q3: Give an LSP violation and how you would catch it.**

**L4 answer**
- `GiftCardPayment.refund()` throws `UnsupportedOperationException`; callers add `instanceof`
- Fix: `Refundable` capability interface implemented only by refundable payments

**L5 extra**
- Compilers check signatures, not behavior; I catch LSP with a shared contract test suite run against each implementation
- The JDK accepts LSP breaks in `List.of` ("optional operations") — a deliberate trade of fewer interfaces for runtime failures

**Q4: DIP vs DI vs IoC?**

**L4 answer**
- IoC: framework controls the flow and calls my code
- DI: dependencies are supplied from outside (constructor)
- DIP: high-level policy owns the abstraction; details implement it

**L5 extra**
- You can do DI without DIP (inject concrete classes) and DIP without a container (manual wiring in `main`)
- The DIP test: does the domain package import the SDK? If yes, the arrow points the wrong way

**Q5: When is duplication better than DRY?**

**L4 answer**
- When two pieces look alike but represent different knowledge with different reasons to change
- Merging them couples their callers

**L5 extra**
- Example: shared "common utils" across Databricks jobs and online services — one upgrade forces both to redeploy
- Share contracts (schemas), not implementation; rule of three before extracting

**Q6: YAGNI vs OCP — an agent tool registry has three tools today. Do you add a plugin interface?**

**L4 answer**
- Three real tools with the same shape is already the "rule of three"
- A `Tool` interface + registry keyed by name is justified; dynamic class loading is not

**L5 extra**
- Close against the variation seen (new tools), not imagined ones (new protocols)
- Retrofit-expensive parts are not YAGNI: tool input schemas, idempotency of side-effecting tools, per-tool timeouts and audit

**Q7: Composition or inheritance for notifiers with retry and logging?**

**L4 answer**
- Composition: `Retrying(Logging(Email))` decorators over a `Notifier` interface
- Inheritance needs a class per combination

**L5 extra**
- Inheritance couples to the base's self-calls (fragile base class); decorators don't
- Decorator order is a contract: metrics outside retry counts requests, inside counts attempts

**Q8: Why does Spring recommend constructor injection?**

**L4 answer**
- Required deps explicit, fields `final`, object complete after construction
- Unit tests use `new` without a container

**L5 extra**
- Cycles fail at startup (Boot ≥ 2.6 forbids them by default); field injection hid them
- Long constructors expose SRP violations that field injection hides

**Q9: Why is `@Transactional` sometimes ignored?**

**L4 answer**
- Spring applies it through a proxy; `this.method()` skips the proxy
- Also ignored on `private` and `final` methods

**L5 extra**
- Fixes ranked: separate bean, `ObjectProvider<Self>`, `AopContext.currentProxy()`, AspectJ weaving
- Also check rollback rules (checked exceptions commit by default) and aspect order with retries

**Q10: JDK dynamic proxy vs CGLIB?**

**L4 answer**
- JDK: implements interfaces, advises interface methods only
- CGLIB: subclasses the class; cannot advise `final`/`private` methods; Boot's default

**L5 extra**
- CGLIB instantiates via Objenesis without running the constructor; a `final` method on the proxy sees `null` fields
- Records and final classes cannot be class-proxied at all

**Q11: What does Spring Boot actually do at startup? How does auto-config decide?**

**L4 answer**
- Builds the `Environment`, scans user config, then imports auto-config candidates from `AutoConfiguration.imports`
- Each candidate is kept only if its `@Conditional...` checks pass

**L5 extra**
- User config is processed first, so `@ConditionalOnMissingBean` lets my bean win; the same annotation in normal config is order-dependent
- Debug with `--debug` or `/actuator/conditions`; exclude unwanted auto-config explicitly

**Q12: `@ConfigurationProperties` vs `@Value`? How do you use profiles?**

**L4 answer**
- `@ConfigurationProperties`: typed, grouped, validated at startup
- `@Value`: single value, no validation
- Profiles switch environment wiring (`application-prod.yml`)

**L5 extra**
- Validation at startup is fail fast for config; a typo in `@Value` fails on first use or never
- No `if (prod)` in code; feature flags are not profiles; secrets never in yml

**L5-only**

**Q13: You inherit a 5k-line service class in a JPMC-style data platform. Plan the refactor without stopping delivery.**
- Characterization tests around current behavior first
- Find seams with co-change history and actors (pricing, persistence, notification)
- Strangle: extract one actor's code behind a port per release; keep the facade stable
- Stop when the remaining class is cohesive — not when it is "small"

**Q14: Design an extensible agent tool registry that is not over-engineered.**
- `Tool` interface: name, input schema, `invoke(input)`; registry map; startup validation of duplicate names (fail fast)
- LSP: every tool honors the same timeout, error, and idempotency contract; contract tests per tool
- ISP: the planner sees `ToolCatalog` (describe), the executor sees `ToolInvoker`
- Not built yet: hot reloading, remote plugin loading — until a real need appears

**Q15: Where do these principles hurt in distributed systems?**
- LoD and fine-grained interfaces → chatty remote calls; remote APIs should be coarse-grained
- DRY across services → shared libraries force lockstep deploys
- Tell-don't-ask across a network → a command needs idempotency keys and retries
- Fail fast at startup on a remote dependency → fleet-wide crash loops
