## 0. One-minute version
- What
  - A managed key-value and document store
  - Every item is addressed by a partition key, plus an optional sort key
- Why
  - Single-digit-millisecond reads and writes that stay flat as the table grows
  - No servers, no connection pools, no vacuum, no failover to run
- How
  - `hash(PK)` picks a partition
  - Items with the same PK sit together, sorted by SK (an "item collection")
  - Each partition is replicated three ways across AZs
  - You model the table from the access patterns, not from entities
- Catch
  - One partition caps at 3,000 RCU / 1,000 WCU  
    ⇒ a hot key throttles even when the table has spare capacity  
  - Queries only work on keys you designed  
    ⇒ a new access pattern means a new GSI or a backfill  
  - GSIs are async ⇒ always eventually consistent
  - Item size caps at 400 KB
- Concurrency primitive = the condition expression
  - Create-only, optimistic lock, and idempotency are all "write only if …"
- Transactions exist (up to 100 items) but cost 2x and conflict under contention
- 🗣 "DynamoDB is a distributed hash map of sorted lists: design the keys for the queries, and the scale is free."
- 🗣 "Every correctness guarantee in DynamoDB is a condition expression."
- 🗣 "A short page is not the last page; only a missing LastEvaluatedKey is."

## 1. Concept

### 1.1 Why it was created
- The pain before it
  - Amazon retail hit relational-database scaling limits in the 2004 holiday season (Werner Vogels, "A Decade of Dynamo", 2017)
  - Most of that traffic was key-based: get cart by id, put cart (same source)  
  ⇒ joins and ad-hoc SQL were paid for but rarely used  
- Prior art
  - Dynamo (2007): leaderless, eventual, operated by each team  
    ⇒ powerful, but every team ran its own cluster  
  - SimpleDB: managed, but small table limits and unpredictable latency
- DynamoDB (2012)
  - Managed service, predictable latency, scale by adding partitions
  - Leader-based replication per partition (Multi-Paxos), not Dynamo's leaderless design (USENIX ATC 2022 paper)
- Common use cases
  - Carts, sessions, user profiles, orders by customer
  - Idempotency keys, distributed locks, leases
  - Counters, feature flags, device state, game state
  - Metadata index in front of S3

### 1.2 Picture

```
client ──► request router ──► partition map: hash(PK) → partition
                                   │
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
   ┌────────────────┐     ┌────────────────┐     ┌────────────────┐
   │  partition 1   │     │  partition 2   │     │  partition 3   │
   │ leader  (AZ a) │     │ leader  (AZ b) │     │ leader  (AZ c) │
   │ replica (AZ b) │     │ replica (AZ c) │     │ replica (AZ a) │
   │ replica (AZ c) │     │ replica (AZ a) │     │ replica (AZ b) │
   └────────────────┘     └────────────────┘     └────────────────┘

inside a partition:  PK = CUSTOMER#c1
                       SK = ORDER#2026-01-02T10:00:00.000Z#o1
                       SK = ORDER#2026-01-05T09:30:00.000Z#o2   ← sorted by SK
                       SK = PROFILE
```

- Write path  
  → router hashes PK and finds the partition leader  
  → leader evaluates the condition expression against the current item  
  → leader appends to its log and replicates to the two peers  
  → write is acknowledged once a quorum (2 of 3) has it durable  
- Read path
  - Strong read → served by the leader
  - Eventual read → any replica, may miss the last write (usually by well under a second; order of magnitude)

### 1.3 Partitions and capacity
- Partition = unit of storage and throughput
  - Up to 3,000 RCU and 1,000 WCU per partition (Developer Guide, "Partition key design")
  - About 10 GB per partition (order of magnitude; DynamoDB splits beyond it)
- Capacity units
  - 1 RCU = one strong read/s of up to 4 KB, or two eventual reads/s
  - 1 WCU = one write/s of up to 1 KB
  - Transactional read or write = 2 units
  - Size rounds up: a 4.1 KB strong read = 2 RCU
- Splitting
  - DynamoDB splits a partition when it grows past storage limits or stays hot ("split for heat")
  - Split for heat helps only when the heat spreads across many SK values  
    ⇒ one single item can never exceed one partition's limit  
- Adaptive capacity
  - Lets a hot partition borrow unused table throughput, applied instantly (Developer Guide, "Burst and adaptive capacity")
  - Limit: still capped by the per-partition maximum  
  ⇒ it fixes uneven keys, not a single hot key  
- Hot partition = one PK takes most of the traffic  
  ⇒ `ProvisionedThroughputExceededException` / `ThrottlingException` on that key  
  ⇒ the rest of the table sits idle  
- Write sharding = spread one logical key over N physical keys
  - `STATUS#PENDING` → `STATUS#PENDING#0` … `STATUS#PENDING#9`
  - Calculated suffix (hash of order id) → a single item stays findable
  - Random suffix → best spread, but reads must fan out
  - Reads become scatter-gather: query N shards, merge
  - Cost: N queries per read; pick N from peak writes / 1,000 WCU

### 1.4 Reads: strong vs eventual
- Eventual (default)
  - 0.5 RCU per 4 KB
  - May return a value older than the last acknowledged write
- Strong (`ConsistentRead=true`)
  - 1 RCU per 4 KB = 2x the cost
  - Returns the latest acknowledged write
  - Only on the base table and LSIs  
    ⇒ a GSI query with `ConsistentRead=true` is a `ValidationException`  
  - Higher latency, and fails if the leader is unreachable (rare)
- Read-your-write without a strong read
  - Ask for `ReturnValues=ALL_NEW` on the write itself  
  ⇒ no second read at all  

### 1.5 Indexes: GSI and LSI
- GSI (global secondary index)
  - A second table, keyed differently, maintained by DynamoDB
  - Updated asynchronously ⇒ eventually consistent reads only
  - Own partitions and own capacity
  - Default quota 20 per table (Developer Guide, "Service quotas")
  - Projection decides what is copied: `KEYS_ONLY`, `INCLUDE`, `ALL`
    - `x-orders` uses `INCLUDE` with `orderId`, `customerId`, `amountCents`
  - Sparse index: items without the GSI key attribute are not indexed  
    ⇒ REMOVE `GSI1PK` when an order is done, and it drops out of "pending"  
  - GSI keys need not be unique
  - Back-pressure: a throttled GSI throttles writes to the base table  
    ⇒ size or shard the GSI like the base table  
- LSI (local secondary index)
  - Same PK, different sort key
  - Supports strong reads
  - Must be created with the table; cannot be added later
  - Max 5 per table
  - Item collection (all items with one PK, plus LSI copies) capped at 10 GB  
    ⇒ a growing customer can hit `ItemCollectionSizeLimitExceededException`  
  - Shares the base partition's throughput
- Default: GSI, unless you need strong reads on an alternate sort order and the collection stays under 10 GB

### 1.6 Single-table design
- Access-pattern-first modeling  
  → list every access pattern with its rate and latency target  
  → pick PK/SK so each pattern is one `GetItem` or one `Query`  
  → add a GSI only for patterns the base keys cannot serve  
  → write the key design down (here: the `.tf` header)  
- `x-orders` key design

| Access pattern | Operation | Key |
|---|---|---|
| Get customer profile | GetItem | `PK=CUSTOMER#c`, `SK=PROFILE` |
| Get one order | GetItem | `PK=CUSTOMER#c`, `SK=ORDER#<iso>#<orderId>` |
| Customer's orders, newest first | Query | `PK=CUSTOMER#c`, `begins_with(SK, "ORDER#")`, `ScanIndexForward=false` |
| Customer's orders in a time range | Query | `PK=CUSTOMER#c`, `SK BETWEEN ORDER#<from> AND ORDER#<to>` |
| All PENDING orders, oldest first | Query GSI1 | `GSI1PK=STATUS#PENDING`, sort by `GSI1SK=<iso>` |
| Idempotency check | GetItem / condition | `x-idempotency.idempotencyKey` |

- Why one table
  - Profile + orders share a PK ⇒ one Query returns both (pre-joined)
  - Fewer tables to monitor, back up, and scale
- Sort keys compare as strings, byte by byte
  - Timestamps must be fixed width
    - `2026-01-01T00:00:00Z` sorts after `2026-01-01T00:00:00.123Z` (`Z` > `.`)  
    ⇒ always format with milliseconds: `yyyy-MM-ddTHH:mm:ss.SSSZ`  
  - Numbers inside keys must be zero-padded
- Limit: single-table pays off for known, stable patterns  
  ⇒ for analytics or ad-hoc queries, export to S3 and use Athena  

### 1.7 Condition expressions
- A write carries a predicate; the partition leader checks it atomically with the write
- Patterns
  - Create-only: `attribute_not_exists(PK)`
    - Checked against the one item with the full key (PK + SK), not the whole partition
  - Optimistic lock: `version = :expected`, then `SET version = version + :one`
  - Guarded state change: `#status = :pending`
  - Idempotency record: `attribute_not_exists(idempotencyKey) OR expiresAt < :now`
- Failure
  - `ConditionalCheckFailedException`
  - Still consumes write capacity
  - `ReturnValuesOnConditionCheckFailure=ALL_OLD` returns the current item  
    ⇒ no extra read to see who won  
- Update expressions
  - `SET a = :v`, `SET n = if_not_exists(n, :zero) + :one`
  - `ADD counter :n` (numbers and sets only)
  - `REMOVE attr`
  - `DELETE set :values` (remove elements from a set)
  - `ADD` is not idempotent ⇒ a blind retry double-counts
- Limit: one item per condition  
  ⇒ cross-item invariants need a transaction  

### 1.8 Transactions
- `TransactWriteItems`: up to 100 actions, 4 MB total (Developer Guide, "Transactions"; raised from 25 in 2022)
  - Actions: Put, Update, Delete, ConditionCheck
  - All succeed or none
  - Items may span tables in the same account and Region
  - No two actions may target the same item
- Cost: 2 WCU per KB per item (prepare + commit)
- Idempotency: `ClientRequestToken`
  - Same token within 10 minutes → treated as the same call, not applied twice
  - Same token with different parameters → `IdempotentParameterMismatchException`
  - Limit: 10 minutes covers SDK retries, not a client retrying tomorrow  
    ⇒ keep an idempotency record for the client's retry horizon  
- Cancellation
  - `TransactionCanceledException` carries one reason per action, in request order
  - Codes: `None`, `ConditionalCheckFailed`, `TransactionConflict`, `ThrottlingError`, `ValidationError`, `ItemCollectionSizeLimitExceeded`, `ProvisionedThroughputExceeded`
  - `TransactionConflict` = another transaction or write touched the item ⇒ retry with backoff
  - `ConditionalCheckFailed` = business outcome ⇒ do not retry blindly
- Isolation
  - Serializable between transactions and single-item writes
  - A `Query` or `Scan` is read-committed only: it may return some items of a transaction and not others

### 1.9 Streams and TTL
- Streams
  - Ordered change log per item key (per partition), records kept 24 hours
  - View types: `KEYS_ONLY`, `NEW_IMAGE`, `OLD_IMAGE`, `NEW_AND_OLD_IMAGES` (`x-orders` uses the last)
  - Record: `eventName` (`INSERT` / `MODIFY` / `REMOVE`), `Keys`, `NewImage`, `OldImage`, `SequenceNumber`
  - Each change appears once in the stream
    - Limit: consumers (Lambda, KCL) retry batches ⇒ processing is at-least-once  
    ⇒ make the handler idempotent (key by `eventID` or item version)  
  - Use: outbox / CDC, search indexing, aggregates, cross-Region fan-out
- TTL
  - Item with a Number attribute (`expiresAt`) holding epoch seconds
  - A background process deletes items after that time
    - Deletion is not exact: typically within a few days (Developer Guide, "Time to Live")  
    ⇒ expired items still appear in reads; filter on `expiresAt > :now`  
  - No WCU charge for TTL deletes
  - Deletes appear in the stream as `REMOVE` with `userIdentity.principalId = dynamodb.amazonaws.com`  
    ⇒ archive expired items by consuming those records  
- PITR: restore to any second in the last 35 days (separate from streams)

### 1.10 Capacity modes
- On-demand (`PAY_PER_REQUEST`, used in `x-orders`)
  - Pay per request, no capacity planning
  - Absorbs up to double the previous traffic peak instantly (Developer Guide, "On-demand capacity mode")
  - Spikes beyond that can throttle until DynamoDB adds partitions (order of magnitude: tens of minutes)
  - Per-partition limits still apply ⇒ on-demand does not fix a hot key
- Provisioned
  - Set RCU/WCU per table and per GSI, optionally with auto scaling
  - Auto scaling reacts in minutes ⇒ sharp spikes throttle
  - Cheaper per request for steady, high, predictable load (order of magnitude; check the pricing page)
- Default: on-demand, unless traffic is steady enough to keep provisioned utilization high

## 2. When to use / not
- Use when
  - Access patterns are known and key-addressable
  - You need flat latency from 10 to 10 million requests/s without re-architecting
  - Spiky or unpredictable load with no ops team (on-demand)
  - Idempotency, leases, counters, and session state for other services
- Avoid when
  - Queries are ad-hoc or analytical (aggregates, joins, `GROUP BY`)  
    ⇒ Aurora PostgreSQL, or export to S3 + Athena  
  - Access patterns are still changing every sprint  
    ⇒ each change risks a backfill  
  - Items naturally exceed 400 KB  
    ⇒ store the blob in S3, keep a pointer  
  - Multi-item invariants are the core of the domain (ledgers with many rows per operation)  
    ⇒ possible with transactions, but relational is simpler  
  - Full-text or geo search  
    ⇒ OpenSearch fed by Streams  

## 3. Knobs and best practices
- Key design
  - High-cardinality PK spread evenly
    - Prevents: hot partitions
  - Prefix keys with the entity type (`CUSTOMER#`, `ORDER#`)
    - Prevents: collisions between entity types in one table
  - Fixed-width timestamps and zero-padded numbers in SK
    - Prevents: wrong sort order
- Reads
  - Default eventual reads; strong only where read-after-write matters
    - Prevents: paying 2x for nothing
  - `ProjectionExpression` to fetch only needed attributes
    - Limit: RCU is charged on the full item size, not the projected size
- Pagination
  - Loop until `LastEvaluatedKey` is absent
    - Prevents: silent data loss when a page is short
  - `Limit` caps items evaluated before the filter  
    ⇒ a page can be empty yet have a next key  
  - Each page is at most 1 MB
  - Expose `LastEvaluatedKey` as an opaque base64 cursor
    - Validate it on the way back in (PK matches the caller)
    - Sign or encrypt it if keys are sensitive
- Writes
  - Every non-idempotent write carries a condition
    - Prevents: lost updates and duplicate creates
  - Use `ReturnValues` instead of read-after-write
- Batch
  - `BatchWriteItem`: up to 25 puts/deletes, 16 MB; `BatchGetItem`: up to 100 keys, 16 MB (Developer Guide, "Service quotas")
  - Not atomic, no conditions
  - Partial success returns `UnprocessedItems` / `UnprocessedKeys`  
    → resend only those  
    → sleep with exponential backoff + full jitter  
    → give up after N attempts and surface the leftovers  
  - Duplicate keys inside one batch → `ValidationException`
- Retries
  - SDK retries throttling and 5xx with backoff (adaptive mode in Python, standard in Java)
  - App-level retries only for idempotent or conditional writes
- Scan
  - Reads the whole table, filter applied after read ⇒ full RCU cost
  - Parallel scan (`Segment` / `TotalSegments`) only for offline jobs
  - Prefer a GSI, or "Export to S3" for analytics
- GSIs
  - Project only what the pattern needs (`INCLUDE`)
    - Prevents: write amplification on every base write
  - Shard low-cardinality GSI keys (status, date)
    - Prevents: GSI back-pressure throttling base writes
- Tricks
  - Sparse GSI as a work queue (only items with `GSI1PK` are indexed)
  - Composite SK for hierarchy (`COUNTRY#STATE#CITY`) + `begins_with`
  - Version attribute + `ALL_OLD` on failure = conflict resolution without a read
  - Store counters on a parent item and update them inside the same transaction as the child

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| DynamoDB | Managed key-value / document store, partitioned by hash(PK) | Flat latency at any scale; zero ops; conditions, transactions, streams, TTL | Queries only on designed keys; 400 KB items; GSIs eventual; hot keys capped per partition | Known key-based patterns, spiky load, serverless on AWS |
| Aurora PostgreSQL | Managed relational DB, single writer + replicas, shared storage | SQL, joins, ad-hoc queries, multi-row ACID, constraints | One writer caps write scale; connections and failover to manage | Evolving queries, relational invariants, reporting |
| Cassandra / Amazon Keyspaces | Wide-column, leaderless (Cassandra) or managed CQL (Keyspaces) | High write throughput; tunable consistency; multi-DC (Cassandra) | LWT (Paxos) is slow; tombstones; self-managed ops for Cassandra | Write-heavy time series, CQL portability, multi-cloud |
| MongoDB / DocumentDB | Document DB with secondary indexes and rich queries | Flexible queries on any field; aggregation pipeline | Sharding and index design still needed at scale; DocumentDB is API-compatible, not MongoDB | Document shape varies, queries on many fields, moderate scale |

- Deciding variable: how well you know the access patterns
  - Known, key-addressable, high or spiky scale → DynamoDB
  - Unknown or relational → Aurora PostgreSQL
- Default: DynamoDB for key-addressable access patterns on AWS, unless queries are ad-hoc, relational, or still changing → Aurora PostgreSQL

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| Hot partition | Low-cardinality PK or GSI PK (status, date) | `ThrottledRequests` while table capacity is unused; CloudWatch Contributor Insights top keys | Write sharding; cache reads; redesign key |
| GSI back-pressure | GSI capacity or key skew below base table | Base writes throttled; GSI throttle metrics | Shard GSI key; provision GSI ≥ base; on-demand |
| Lost update | Read-modify-write with no condition | Values silently overwritten | `version` condition; `ALL_OLD` on failure |
| Duplicate create on retry | Client retries after a timeout | Two orders for one request | Idempotency record + order in one transaction |
| Partial batch dropped | `UnprocessedItems` ignored | Missing items, no error | Loop with backoff; alert on leftovers |
| Pagination stops early | Short or empty page treated as the end | Missing results | Loop until `LastEvaluatedKey` is absent |
| Stale read | Eventual read or GSI read right after a write | Read misses the new value | `ConsistentRead` on base table; `ReturnValues` |
| Expired items returned | Relying on TTL deletion time | Expired items in results | Filter `expiresAt > :now`; treat expired as absent in conditions |
| Transaction conflicts | Concurrent writes to the same items | `TransactionConflict` reasons | Backoff retry; shrink transactions; avoid hot items |
| Item too large | Unbounded lists inside one item | `ValidationException` (400 KB) | Split into an item collection; S3 pointer |
| Scan in request path | Missing access pattern | RCU spikes, slow API | Add GSI; export to S3 for analytics |
| Wrong sort order | Variable-width timestamps or numbers in SK | Out-of-order pages | Fixed-width ISO, zero-padded numbers |

## 6. Interview questions

**Q1:** How does DynamoDB decide where an item lives, and what limits a single key?

**L4 answer**
- `hash(PK)` maps the item to a partition
- Items with the same PK are stored together, sorted by SK
- Each partition serves up to 3,000 RCU / 1,000 WCU  
⇒ a single hot key throttles, even with spare table capacity  

**L5 extra**
- Partitions are three-way replicated; a leader handles writes and strong reads (Multi-Paxos)
- Adaptive capacity lends unused throughput to hot partitions; split for heat spreads hot SK ranges
- Neither can split one item ⇒ shard the key (suffix) or cache it
- Pick shard count N from peak WCU / 1,000, and accept N-way fan-out on read

**Q2:** Strong vs eventual reads: cost, where they are available, when to use each?

**L4 answer**
- Eventual: half the cost, may miss the latest write
- Strong: 2x cost, latest acknowledged write
- GSIs only support eventual reads

**L5 extra**
- Strong reads go to the partition leader; eventual reads can use any replica
- Avoid strong reads by returning `ALL_NEW` from the write
- GSI lag is usually small but unbounded under GSI throttling  
  ⇒ never use a GSI read to check uniqueness; use a condition on a base item  

**Q3:** Two users edit the same order at once. How do you prevent a lost update?

**L4 answer**
- Store a `version` number on the item
- Update with `ConditionExpression: version = :expected` and `SET version = version + 1`
- On `ConditionalCheckFailedException` → re-read, re-apply, retry or return 409

**L5 extra**
- `ReturnValuesOnConditionCheckFailure=ALL_OLD` returns the winner's item ⇒ no extra read
- Enhanced Client `@DynamoDbVersionAttribute` adds the condition automatically
- For commutative changes (counters), `ADD` avoids the lock entirely, but is not idempotent
- Expose version as an ETag + `If-Match` in the API

**Q4:** How do you paginate a Query and expose it to API clients?

**L4 answer**
- Each response returns at most 1 MB or `Limit` items
- If `LastEvaluatedKey` is present, pass it as `ExclusiveStartKey`
- Return it to the client as an opaque cursor

**L5 extra**
- `Limit` counts items evaluated before the filter ⇒ pages can be short or empty, but not final
- Base64 the key map; validate the PK on decode so a client cannot jump partitions
- Cursors are stable under inserts (keyset), unlike OFFSET
- No total count: `Select=COUNT` still reads every item

**Q5:** Design keys for "a customer's orders by time" and "all pending orders".

**L4 answer**
- `PK=CUSTOMER#<id>`, `SK=ORDER#<iso>#<orderId>` → Query with `begins_with` or `BETWEEN`
- GSI1: `GSI1PK=STATUS#<status>`, `GSI1SK=<iso>` → oldest pending first

**L5 extra**
- `STATUS#PENDING` is a hot GSI key ⇒ shard it (`STATUS#PENDING#0..N-1`) and scatter-gather
- REMOVE `GSI1PK` on terminal states ⇒ sparse index stays small
- `INCLUDE` projection keeps GSI writes cheap; fetch details from the base table if needed
- Fixed-width timestamps, or the sort order breaks

**Q6:** BatchWriteItem vs TransactWriteItems?

**L4 answer**
- Batch: up to 25 items, not atomic, no conditions, returns `UnprocessedItems`
- Transaction: up to 100 items, all-or-nothing, conditions allowed, 2x cost

**L5 extra**
- Batch partial failure is normal under throttling ⇒ resend leftovers with full-jitter backoff
- Transactions fail as a whole with per-action reasons; `TransactionConflict` is retryable, `ConditionalCheckFailed` is not
- Use batch for bulk loads, transactions for invariants

**Q7:** Make "place order" idempotent.

**L4 answer**
- Client sends an `Idempotency-Key`
- One transaction: put the order (`attribute_not_exists(PK)`) + put the idempotency record (`attribute_not_exists`)
- Record exists → return the stored result

**L5 extra**
- Scope the key by caller (`customerId#key`) so two customers cannot collide
- Store a request hash; same key with a different body → 422
- `ALL_OLD` on the idempotency put returns the stored result inside the cancellation reason
- TTL deletion is lazy ⇒ condition `attribute_not_exists(k) OR expiresAt < :now`
- `ClientRequestToken` only covers 10 minutes of identical calls; the record covers the client's horizon

**Q8:** How do Streams and TTL work together?

**L4 answer**
- TTL deletes items whose `expiresAt` (epoch seconds) has passed, in the background
- Streams emit a `REMOVE` record with the old image for that delete

**L5 extra**
- Deletion is not exact (typically within days) ⇒ filter expired items on read
- TTL deletes carry `userIdentity.principalId = dynamodb.amazonaws.com` ⇒ archive only those to S3
- Streams keep 24 h ⇒ a consumer down longer loses changes; use Kinesis Data Streams for DynamoDB for longer retention

**L5-only Q9:** On a sale day, order writes throttle although the table is on-demand. Diagnose and fix.

**L5 answer**
- Check whether throttles are on the base table or on GSI1
  - All new orders write `GSI1PK=STATUS#PENDING` ⇒ one GSI partition takes every write
  - GSI throttling back-pressures base writes
- Check traffic vs previous peak: on-demand absorbs 2x previous peak instantly, more may throttle
- Fix  
  → shard the GSI key with a calculated suffix  
  → readers scatter-gather N shards and merge by `GSI1SK`  
  → pre-warm: raise warm throughput before the event (or switch to provisioned at peak)  
- Prove it with Contributor Insights on the index

**L5-only Q10:** Product asks for a new access pattern on a live single-table design. How do you ship it?

**L5 answer**
- Can a new GSI serve it from existing attributes?
  - Yes → add the GSI online; DynamoDB backfills; reads must tolerate backfill lag
- New attribute needed?  
  → writers start writing it (dual write)  
  → backfill old items with a parallel scan job, conditional updates, throttled  
  → only then switch reads  
- Ad-hoc or analytical → Export to S3 + Athena, not a GSI

**L5-only Q11:** When would you refuse single-table design?

**L5 answer**
- Entities have unrelated access patterns and different scale ⇒ separate tables isolate capacity and blast radius
- Many teams own the entities ⇒ one table couples their deployments
- Patterns are not known ⇒ start relational, move hot paths later
- Trade-off: single table pre-joins related items; multi-table is simpler to evolve and reason about
