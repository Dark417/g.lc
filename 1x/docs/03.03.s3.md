## 0. One-minute version
- What
  - S3 = regional object store, a flat key → bytes namespace, addressed over HTTPS
  - Object = key + bytes + metadata + optional version id
- Why
  - Cheap, durable bytes without servers, disks, or capacity planning
  - Data lake, backups, user uploads, static assets
- How
  - No real folders: a "folder" is a key prefix, a delimiter groups keys at list time
  - Reads see the latest write: strong read-after-write consistency since Dec 2020
  - Large files go as multipart (5 MiB minimum part except the last, max 10,000 parts, 5 TiB object)
  - Browsers upload directly through presigned URLs, signed by our credentials
  - SSE-KMS encrypts per object; S3 Bucket Keys cut the KMS request count
  - Versioning keeps old bytes; lifecycle moves or expires them
  - Create-only writes use `If-None-Match: *` (since Aug 2024)
- Catch
  - Not a file system: no rename, no append, no partial update, no atomic multi-object change
  - Request rate is per prefix (3,500 writes / 5,500 reads per second), not per bucket
  - Versioning + abandoned multipart uploads silently grow the bill
- 🗣 "S3 is a giant key-value store for blobs; folders are a listing trick, and strong consistency means a successful PUT is immediately readable."
- 🗣 "I put bytes in S3 and a pointer in a database; I never put blobs in the database."

## 1. Concept

### 1.1 Flat namespace
- Bucket → key → object; no hierarchy is stored
- `ListObjectsV2` with `prefix` + `delimiter=/`
  - Keys with the delimiter after the prefix collapse into `CommonPrefixes`
  - Those common prefixes are the "folders"
- Consequence
  - "Rename a folder" = copy + delete every key, not O(1)
  - Listing is paginated: max 1,000 keys per response; continuation token drives the next page
  - A 0-byte key ending in `/` is only a console convention

### 1.2 Consistency
- Since 2020-12-01 S3 gives strong read-after-write for PUT, DELETE, and LIST, in all regions, no extra cost (AWS announcement)
  → PUT returns 200  
  ⇒ the next GET, HEAD, or LIST sees that object  
- Limit
  - Guarantee is per object key; there is no multi-object transaction
  - Two concurrent writers to one key: last writer wins (unless a conditional write is used)
  - Caches in front (CDN, proxies) can still serve stale bytes

### 1.3 Request rate
- Per partitioned prefix: 3,500 PUT/COPY/POST/DELETE and 5,500 GET/HEAD per second (S3 performance guide)
- Scaling rule
  - S3 partitions prefixes automatically as load grows
  - More prefixes ⇒ more aggregate rate (parallelize across prefixes)
- Limit
  - A sudden spike on a new prefix can get 503 SlowDown until S3 partitions; retry with backoff
  - The number is guidance, not an SLA

### 1.4 Multipart upload
- Mechanism
  → `CreateMultipartUpload` returns an uploadId  
  → `UploadPart` (part number 1..10,000, parallel, each retried on its own)  
  → `CompleteMultipartUpload` with the list of part numbers + ETags  
  ⇒ the object appears atomically only after Complete  
- Limits (S3 docs, "Amazon S3 multipart upload limits")
  - Part size 5 MiB to 5 GiB; only the last part may be below 5 MiB
  - Max 10,000 parts, max object 5 TiB
  - Single PUT is capped at 5 GiB
- Catch
  - Unfinished uploads keep stored parts and bill for them ⇒ lifecycle `AbortIncompleteMultipartUpload` (Terraform: 7 days)
  - The multipart ETag is not an MD5 of the content

### 1.5 Presigned URLs
- A URL carrying a SigV4 signature made with the signer's credentials
  - Holder acts as the signer for that one request (method, key, signed headers)
- Expiry
  - Set by us, but effective expiry is capped by the signing credential's lifetime
  - IAM user key: up to 7 days; role / STS session: ends when the session token ends (hours at most)
- Catch
  - Permissions are the signer's at use time: if the signer loses access, the URL fails
  - Signed headers (content-type, SSE) must match exactly, else 403 SignatureDoesNotMatch
  - A leaked URL is a bearer token until it expires
- Presigned POST: adds a policy (key prefix, max size); PUT URLs cannot restrict size

### 1.6 Encryption
- SSE-S3
  - S3-managed keys, free, default for all new objects since Jan 2023
- SSE-KMS
  - Per-object data key wrapped by a KMS key; gives key policy, audit in CloudTrail, per-key disable
  - Cost: every PUT/GET without Bucket Keys calls KMS (request charge + KMS rate quota)
- S3 Bucket Keys
  - S3 gets one bucket-level key from KMS and derives object data keys locally
  - Cuts KMS requests by up to 99% (AWS-stated); Terraform enables `bucket_key_enabled`
  - Limit: not applied to objects already written without it; changes CloudTrail granularity

### 1.7 Versioning and lifecycle
- Versioning
  - Overwrite creates a new version; DELETE adds a delete marker; old bytes stay
  - Versioning can be suspended, never turned off
  - Reading a specific version needs `s3:GetObjectVersion`; listing needs `s3:ListBucketVersions`
- Lifecycle (Terraform: `raw/` → STANDARD_IA at 30 days → GLACIER_IR at 180; noncurrent versions expire at 30 days)
  - Rules run asynchronously (about daily); not exact to the hour
  - Minimum storage duration charges apply to IA (30 days) and Glacier classes

### 1.8 Conditional writes
- `If-None-Match: *` on PutObject (and CompleteMultipartUpload): write only if the key does not exist (AWS, 2024-08)
  → First writer returns 200  
  → Loser gets 412 PreconditionFailed  
  → Concurrent in-flight writers may get 409 ConditionalRequestConflict: retry  
- Use: leader lock files, idempotent "create once", exactly-once landing of a batch
- Limit
  - Create-only; `If-Match` (compare ETag) is a separate conditional for updates
  - On a versioned bucket "exists" means a current non-delete-marker version

### 1.9 Storage classes (brief)

| Class | Use | Retrieval | Catch |
|---|---|---|---|
| STANDARD | hot data | ms, no fee | highest per-GB price |
| INTELLIGENT_TIERING | unknown access | ms for frequent/infrequent tiers | monitoring fee per object |
| STANDARD_IA | rare reads, needs ms | ms, per-GB fee | 30-day minimum, 128 KB billing floor |
| GLACIER_IR | archive, rare ms reads | ms, higher per-GB fee | 90-day minimum |
| GLACIER_FLEXIBLE / DEEP_ARCHIVE | cold archive | minutes to hours | restore request needed; 90 / 180-day minimum |

- Prices change; check the S3 pricing page (not quoted here)

### 1.10 Diagram

```
 client ──presigned PUT──────────────┐
   │                                 ▼
 app ──PutObject / multipart──▶  bucket x-lake-<acct>
   │                              ├─ raw/dt=2026-01-01/part-0.json   (lifecycle → IA → GLACIER_IR)
   │                              ├─ curated/...
   │                              └─ versions + delete markers
   └─ SSE-KMS ──▶ KMS (alias/x-data); Bucket Key = 1 KMS call per bucket-period
```

## 2. When to use / not
- Use
  - Blobs and files from KB to TB, written once, read many
  - Data lake storage for Athena / Redshift / Firehose
  - Direct client uploads through presigned URLs
  - Backups, exports, build artifacts
- Do not use
  - Low-latency random reads of tiny items (use DynamoDB; S3 first-byte latency is order of tens of ms)
  - POSIX semantics: append, rename, locking (use EFS)
  - Block device for a database (use EBS)
  - Frequent in-place small updates to one object (each update rewrites the whole object)

## 3. Knobs and best practices
- Block Public Access on (Terraform does) ⇒ prevents accidental public buckets
- ACLs off (`BucketOwnerEnforced`) ⇒ one permission model: IAM + bucket policy
- Default encryption SSE-KMS + Bucket Key ⇒ KMS audit without per-request KMS cost explosion
- Abort-incomplete-multipart lifecycle ⇒ stops invisible part billing
- Noncurrent-version expiry ⇒ stops versioning cost growth
- Spread hot writes across prefixes (hash or date prefix) ⇒ avoids per-prefix throttling
- Retry 503 SlowDown with exponential backoff and jitter (SDK does by default)
- Parallel ranged GETs for big downloads ⇒ throughput beyond one connection
- Use Transfer Manager / `upload_file` for files ⇒ automatic multipart, parallelism, abort on failure
- Presign with the shortest useful expiry ⇒ smaller leak window
- Store the S3 key (not a presigned URL) in your database ⇒ URLs expire

## 4. Comparison

| Option | What it is | Strength | Weakness | Choose when |
|---|---|---|---|---|
| S3 | Regional object store | Cheap per GB, 11-nines durability design, unlimited size, presigned URLs | No append/rename; higher latency than disk | Blobs, lake, backups |
| EFS | Managed NFS file system | POSIX, shared mount, append, locks | Several times the S3 price per GB (order of magnitude), regional throughput modes | Many instances share a real file system |
| EBS | Network block volume | Lowest latency, boots OS, database disks | One AZ, one instance (Multi-Attach limited), pay for provisioned size | Single-host disk, databases |
| DynamoDB | Key-value / document DB | Single-digit ms, conditional updates, indexes | 400 KB item cap; per-request cost for big values | Metadata and small records |

- Pick for blobs
  - S3 holds the bytes, DynamoDB or Aurora holds metadata + the S3 key
- Default: S3 for blobs, unless a POSIX shared file system (EFS) or a block device (EBS) is required

## 5. Failure modes

| Failure | Trigger | Detect | Fix |
|---|---|---|---|
| 503 SlowDown | Burst above per-prefix rate on a new prefix | 503 in client metrics, CloudWatch 5xx | Backoff + jitter, spread prefixes, warm up gradually |
| 403 SignatureDoesNotMatch | Presigned PUT sent with different headers | 403 on upload | Send exactly the signed headers (content-type, SSE) |
| Presigned URL dies early | Signed with role/STS credentials | Failures before expiry | Sign with longer-lived credentials, or issue URLs just-in-time |
| 403 AccessDenied on KMS | Caller lacks `kms:GenerateDataKey` / `kms:Decrypt` | Error names KMS | Grant KMS use in IAM and key policy |
| Orphan multipart parts | Crash between create and complete | `ListMultipartUploads`, storage cost | Abort in `except`; lifecycle abort rule |
| 412 PreconditionFailed | Create-only write on existing key | Status 412 | Treat as "already exists", not an error |
| 409 ConditionalRequestConflict | Concurrent conditional writes | Status 409 | Retry with backoff |
| Surprise 404 after delete | Delete marker is the latest version | `ListObjectVersions` shows marker | Delete the marker to restore the previous version |
| Cost growth | Versions + IA minimum charges + small objects in IA | Cost Explorer, Storage Lens | Noncurrent expiry, compact small files, right class |
| Stale reads via CDN | Cache in front of S3 | Old ETag at edge | Versioned key names or cache invalidation |

## 6. Interview questions

**Q:** Are there folders in S3?

**L4 answer**
- No, a flat key space; `a/b/c.txt` is one key
- Listing with prefix + delimiter `/` groups keys into common prefixes that look like folders
- Rename a "folder" = copy + delete each key

**L5 extra**
- Listing cost is per 1,000 keys scanned, so deep prefix scans over millions of keys are slow and billed
- Lake layouts (`dt=...` partitions) exist because the prefix is the only index
- 🗣 "Prefix is the only index S3 has."

**Q:** Is S3 consistent?

**L4 answer**
- Strong read-after-write for new objects, overwrites, deletes, and lists since Dec 2020
- Before: eventual for overwrites and deletes, and for LIST

**L5 extra**
- Per key only; no cross-object atomicity (a "commit" of many files needs a manifest or a table format such as Iceberg/Delta)
- Concurrent writers: last write wins unless you use conditional writes

**Q:** How do you upload a 50 GB file?

**L4 answer**
- Multipart upload: create, upload parts in parallel (>= 5 MiB, <= 10,000 parts), complete
- Use Transfer Manager / `upload_file` so retries and parallelism are handled
- Abort on failure and set an abort-incomplete lifecycle rule

**L5 extra**
- Part size = size / 10,000 minimum (50 GB at 5 MiB parts needs ~10,240 parts ⇒ exceeds the limit, so use >= 8 MiB)
- Per-part retry is idempotent by part number; Complete is the atomic commit
- Parallelism is bounded by NIC and memory (threads x part size)

**Q:** How does a browser upload directly to S3 without exposing credentials?

**L4 answer**
- Server returns a presigned PUT URL (or POST policy) with short expiry
- Browser uploads straight to S3; server never handles the bytes

**L5 extra**
- Signed by the server's credentials; role credentials cap the lifetime
- PUT cannot limit size; presigned POST with `content-length-range` can
- Validate afterwards (event notification → scan) since the URL holder controls the content

**Q:** SSE-S3 vs SSE-KMS?

**L4 answer**
- SSE-S3: S3-managed keys, free, no key control
- SSE-KMS: you control the key policy, get CloudTrail audit, can revoke
- Cost: KMS request charges and KMS API rate quotas

**L5 extra**
- Bucket Keys reduce KMS calls by deriving data keys locally from a bucket-level key
- Cross-account readers need both bucket policy and KMS key policy access
- Disabling the KMS key makes all objects under it unreadable

**Q:** How do versioning and lifecycle interact?

**L4 answer**
- Versioning keeps old versions; delete adds a marker
- Lifecycle transitions or expires current and noncurrent versions separately

**L5 extra**
- Without noncurrent expiry cost grows forever
- Expired-object-delete-marker cleanup is needed to remove orphan markers
- Lifecycle runs asynchronously, so do not rely on exact timing

**Q:** How do you create an object only if it does not exist?

**L4 answer**
- PutObject with `If-None-Match: *`; 412 means it already existed
- Retry 409 conflicts

**L5 extra**
- Gives a lock or leader election with only S3 (no DynamoDB), limit: no TTL/fencing, so a crashed holder needs an external expiry
- Before Aug 2024 this needed DynamoDB or head-then-put (racy)

**Q:** S3 vs EFS vs EBS vs DynamoDB for storing user-uploaded images?

**L4 answer**
- S3 for the bytes; DynamoDB/Aurora for metadata and the key
- EFS/EBS only if a process needs a file system or block device

**L5 extra**
- S3 per-GB cost and durability beat EFS/EBS; DynamoDB's 400 KB item cap rules it out
- Serve through CloudFront with presigned or signed URLs

**L5-only questions**

**Q:** Design a high-throughput ingest of 200k small objects per second.

**L5 answer**
- Above one prefix's 3,500 writes per second ⇒ at least ~60 prefixes (200,000 / 3,500)
- Hash-spread keys across prefixes, but keep Athena-friendly partitions: trade-off of write rate vs query layout
- Better: batch small records into larger files (Firehose buffering), since per-request cost and listing cost dominate
- Backoff on 503; monitor 5xx

**Q:** Many writers must produce a table; how do readers avoid half-written data?

**L5 answer**
- S3 has no multi-object atomicity
- Write files under a unique run prefix, then publish one manifest / table-format commit using a conditional write
- Readers read only the manifest; compaction and vacuum clean old files

**Q:** Presigned URLs for an audit-sensitive download: what are the risks?

**L5 answer**
- Bearer token: anyone with it downloads; CloudTrail logs the signer, not the end user
- Use short expiry, bind to IP via bucket policy condition if the network allows, prefer CloudFront signed cookies/URLs with an app-level auth check
